# Koobiq `loader-overlay` Component — Code Review & Improvement Plan

> Scope: `packages/components/loader-overlay` (component, template, tokens, theme, SCSS, Jest spec + snapshot, e2e fixture + Playwright spec, user guides, examples, dev app, API guard report) · Commit `b665e503` · 2026-08-28
> Generated by a multi-dimension review (architecture, correctness, accessibility, public API/types, styles, tests, docs) with manual verification of every finding against the source, the in-repo consumer (`notification-center`), the docs pipeline and `tsconfig.json`. 15 findings confirmed (P0×0, P1×1, P2×7, P3×7); 6 candidate findings refuted during verification (see Appendix A). This document is a review + roadmap; no source is modified by it.

---

## 1. Executive Summary

`KbqLoaderOverlay` is a 124-line component (`loader-overlay.component.ts`) plus three marker directives, a 27-line template, 79 lines of SCSS and a 76-line theme mixin. It paints an `inset: 0` box over its parent block, renders a `kbq-progress-spinner` and optional text/caption, and — uniquely in this package family — reaches *outside* itself in `ngOnInit` to stamp a class onto its parent element so the absolute positioning has something to resolve against. There is exactly one in-repo consumer (`notification-center.html:132`), six docs examples and a Playwright suite of four screenshots.

- **The most serious defect is that the component implements none of the behaviour its own documentation promises about focus.** Both guides state, in a dedicated section, that content behind the overlay is not reachable ("Elements behind the overlay must not be accessible for focus, selection, or clicking", `loader-overlay.en.md:20`; "The system prevents focusing on form elements covered by the overlay", `loader-overlay.en.md:32`). The component sets no `inert`, no `aria-hidden`, no `tabindex`, and installs no focus trap: a keyboard user simply tabs straight into the buttons and inputs hidden under the scrim, and a screen-reader user never learns they are covered. The NgModule even imports CDK `A11yModule` (`loader-overlay.module.ts:1,14`) without using a single symbol from it, which reads like an intention that was never finished (LDR-A11Y-01).
- **Nothing in the rendered subtree carries any accessible semantics at all.** No `aria-busy` on the region being loaded, no live region on the text/caption, and the spinner it renders has no `role="progressbar"` either (`progress-spinner.component.html:1-17`). In the default configuration — no `text`, no `caption`, which is what `notification-center.html:132` uses — the overlay is completely silent to assistive technology while it blocks the entire panel (LDR-A11Y-02). The repo already has the patterns: `notification-center.html:106-108` uses `role="status"` with a localized `aria-label`, `accordion-content.directive.ts:19-24` uses `[attr.inert]` for exactly this "visible but must not be focusable" case.
- **The positioning strategy takes ownership of a DOM node the component does not own.** `ngOnInit` adds `kbq-loader-overlay_parent` (→ `position: relative`) to `elementRef.nativeElement.parentElement` with no check of what that element already is, no refcount and no null guard (`loader-overlay.component.ts:115-123`). Whatever is next to the overlay becomes its containing block — including scroll containers: `.kbq-notification-center-container` has `overflow: auto` (`notification-center.scss:93`) and `.kbq-modal-body` has `overflow-y: auto; max-height: calc(100vh - 260px)` (`modal.scss:120-124`), and the modal case is precisely what the guide recommends `card` for (`loader-overlay.en.md:66-70`). In a scrolled container an `inset: 0` absolutely positioned child scrolls away with the content instead of staying over the visible area, and every shipped fixture pins its height (320px in the example, 350px in the e2e host) so no screenshot can catch it (LDR-ARCH-01, LDR-CSS-01).
- **A documented feature does not exist, and the code that demonstrates it ships anyway.** The guides describe fixed top-offset alignment ("72px by default", `loader-overlay.en.md:50`) and embed `loader-overlay-fixed-top` right underneath; the example writes `<kbq-loader-overlay fixed-top>` (`loader-overlay-fixed-top-example.ts:20`) and the dev app repeats it (`components-dev/loader-overlay/template.html:74`). `fixed-top` is not an input, not an attribute selector and not a CSS hook anywhere in the repository — and because it is a *static attribute* rather than a binding, `strictTemplates: true` (`tsconfig.json:117`) does not catch it. The example renders identically to the default one (LDR-API-01). Separately, the English guide embeds `loader-overlay-on-background` (`loader-overlay.en.md:70`) while the example is registered as `loader-overlay-card`, so the English "On card background" section logs `Could not find example` (`docs-live-example-viewer.ts:137-138`) and renders an empty viewer; the Russian guide gets it right (LDR-DOC-01).

Genuine strengths: the component is small, standalone, `OnPush`, uses the `host` object with no `@HostBinding`, and holds no subscriptions, timers or listeners — there is nothing to leak. Styling is fully token-driven with zero hardcoded colours, `border-radius: inherit` makes it fit rounded cards without configuration, and the `:has()` rule at `loader-overlay.scss:51-53` is a genuinely elegant fix for the "spacing when there is no text" regression (DS-4567). The projection API (indicator/text/caption marker directives with inline fallbacks) is a clean escape hatch, the Playwright suite covers all twelve size/variant combinations in both themes, and an `ng-update` migration already exists for the previous `compact` → `size` rename (`packages/schematics/src/migrations/loader-overlay-size-attr/index.ts`). The gap is not in the rendering — it is that the component's contract with the page around it (focus, semantics, positioning) was never implemented.

## 3. Prioritized Findings (deduplicated, verified)

### P0 — Release blockers

None.

### P1 — High

**LDR-A11Y-01 · Content under the overlay stays focusable and reachable; both guides state the opposite** — `loader-overlay.component.ts:45-124`, `loader-overlay.component.html:1-27`, `loader-overlay.en.md:20, 30-32`, `loader-overlay.ru.md:20, 30-32`, `loader-overlay.module.ts:1, 14`.
The entire component contains no accessibility code: the `host` block (`loader-overlay.component.ts:52-59`) declares five class bindings and nothing else — no `role`, no `tabindex`, no `[attr.inert]`, no `[attr.aria-hidden]` — and the template (`loader-overlay.component.html:1-27`) is a plain `div` wrapper around a spinner and two optional text nodes. The overlay is appended as the last child of its parent, so every focusable element that precedes it keeps its position in the tab order. Painting a background over a button does not remove it from the sequential focus navigation order, does not remove it from the accessibility tree, and does not prevent text selection. The published guides do not describe this as a consumer responsibility — they state it as component behaviour, in both languages and in two separate places: "Elements behind the overlay must not be accessible for focus, selection, or clicking" (`loader-overlay.en.md:20`, `loader-overlay.ru.md:20`) and an entire subsection headed "Focus and keyboard navigation" whose single sentence is "The system prevents focusing on form elements covered by the overlay" (`loader-overlay.en.md:30-32`, `loader-overlay.ru.md:30-32`). The corroborating evidence that this was meant to exist is in the NgModule, which imports CDK `A11yModule` (`loader-overlay.module.ts:1, 14`) and never references a symbol from it — a dependency added for a feature that was not written. The user-visible result: in the shipped card example, which deliberately places two `kbqInput` fields under the overlay (`loader-overlay-card-example.ts:21-31`), a keyboard user tabs into and types in inputs that are visually covered and semantically "loading". This is a WCAG 2.4.3/2.4.7/1.3.1 judgement rather than an automated AXE failure — axe-core does not flag focusable content behind a sibling — but AGENTS.md names focus management as a mandate, and the repo already ships the correct pattern in `accordion-content.directive.ts:19-24`, which binds `[attr.inert]` with a comment explaining this exact hazard.
**Fix:** the overlay cannot safely reach across to its siblings, so introduce the container as a first-class part of the API: add a `[kbqLoaderOverlayContainer]` directive that owns `position: relative`, `[attr.inert]`, `[attr.aria-busy]` and the `kbq-loader-overlay_parent` class, driven by a `loading` input (this also removes the blind parent mutation in LDR-ARCH-01 and gives LDR-A11Y-02 a host for `aria-busy`). Keep the current `parentElement` class-stamping as a deprecated fallback for one minor so existing call sites do not break, and migrate `notification-center.html:132` to the directive in the same change. Guard it with a Jest spec that renders a `<button>` sibling plus the overlay and asserts the container carries `inert` while mounted and loses it after the overlay is destroyed, plus a Playwright case that presses `Tab` from before the container and asserts focus lands after it, never inside. Update both guides once the behaviour actually exists.

### P2 — Should fix

**LDR-A11Y-02 · Nothing is announced: no `aria-busy`, no live region, no accessible name for the spinner-only case** — `loader-overlay.component.ts:52-59`, `loader-overlay.component.html:1-27`, `progress-spinner.component.html:1-17`, `notification-center.html:132`.
`isEmpty` (`loader-overlay.component.ts:96-98`) exists precisely because the overlay is routinely used with neither `text` nor `caption` — that is the configuration the only in-repo consumer ships (`notification-center.html:132` passes only `[transparent]="true"`). In that configuration the entire rendered subtree is: a `div.kbq-loader-overlay__container`, a `kbq-progress-spinner`, and inside it an `<svg focusable="false">` with a `<circle>` (`progress-spinner.component.html:1-11`). There is no `role="progressbar"` anywhere in the repository, no `role="status"`, no `aria-live` and no `aria-label`, so a screen-reader user gets absolute silence while a panel they were reading is replaced by a spinner. When `text`/`caption` *are* supplied they render as plain `div`s (`loader-overlay.component.html:12-14, 22-24`) outside any live region, so a caption that ticks down ("18,7 МБ из 25 МБ — осталось 2 мин", the string used in every example) is never announced either. `aria-busy` appears nowhere in `packages/components`, so there is no existing convention to inherit — but `role="status"` does: `notification-center.html:106-108` wraps its "load more" spinner in `role="status"` with a localized `aria-label`, `app-switcher.html:189` uses `role="status"`, and `filter-bar/pipe-add.ts:61` uses a visually hidden `aria-live="polite" aria-atomic="true"` region. WCAG 4.1.3 (Status Messages, AA).
**Fix:** put `aria-busy="true"` on the container from LDR-A11Y-01 (that is the element whose content is stale, not the overlay). Give `.kbq-loader-overlay__container` `role="status"` + `aria-live="polite"` + `aria-atomic="true"` so `text`/`caption` updates are announced. For the appearance itself, note that a live region inserted together with its content is unreliable across screen readers — use CDK `LiveAnnouncer` (from the `A11yModule` the NgModule already imports but does not use) in `ngOnInit`. Source the default announcement for the `isEmpty` case from `kbqInjectA11yLocaleConfiguration()` by adding a `loading` key to the `a11y` section of `en-US.ts`, `ru-RU.ts`, `es-LA.ts`, `pt-BR.ts` and `tk-TM.ts`, per the AGENTS.md rule that component-provided ARIA text must come from the locale config. Add a `jest-axe` case to `loader-overlay.component.spec.ts` following `accordion.spec.ts`, and a spec asserting the announced string changes when `[text]` is rebound.

**LDR-ARCH-01 · `ngOnInit` mutates its parent element unconditionally, with no guard, refcount or null check** — `loader-overlay.component.ts:19, 62-63, 82, 115-123`, `loader-overlay.scss:5-7`, `notification-center.scss:109-111`.
```ts
ngOnInit(): void {
    this.parent = this.elementRef.nativeElement.parentElement;
    this.renderer.addClass(this.parent, kbqLoaderOverlayParent);
}
```
Four separate problems in six lines. (1) `.kbq-loader-overlay_parent { position: relative; }` (`loader-overlay.scss:5-7`) is applied whatever the parent already is: a parent that was deliberately `position: sticky`, `absolute` or `fixed` silently becomes `relative` for as long as the overlay is mounted, and the rule is a single class (specificity 0,1,0) with no `:where()` scoping, so which declaration wins depends on stylesheet injection order. (2) `parent` is declared `HTMLElement | null` (`:82`) but `Renderer2.addClass(el: any, name: string)` types its first argument as `any`, so the nullable type is discarded silently; the DOM renderer's implementation is `el.classList.add(name)`, which throws on `null` — the same class of regression the workspace already hit when `Renderer.setStyle(null)` stopped being a no-op in Angular 20. (3) There is no refcount: two overlays sharing a parent means the first one destroyed strips the positioning context from the second. (4) The reference is captured once at init; if the host is moved in the DOM afterwards (portal re-attach, `ViewContainerRef.move`), the class is added to one element and removed from another. The design also leaks into consumers by construction — `notification-center.scss:109-111` has to write a rule against `.kbq-loader-overlay_parent`, a class name it never applies itself, to push `border-radius: inherit` down the chain so the overlay's own `border-radius: inherit` (`loader-overlay.scss:32`) resolves to something.
**Fix:** ship the `[kbqLoaderOverlayContainer]` directive from LDR-A11Y-01 as the supported way to establish the containing block, and make it own `border-radius: inherit` too so `notification-center.scss:109-111` can be deleted. While the fallback path remains, harden it: early-return when `parentElement` is `null`, read `getComputedStyle(parent).position` through `inject(KBQ_WINDOW)` and only add the class when it is `static`, record in a field whether the class was actually added so `ngOnDestroy` is symmetric, and refcount via a `data-` counter attribute so sibling overlays do not strip each other. Cover with specs for: null parent, already-positioned parent left untouched, class removed on destroy, two overlays in one parent.

**LDR-CSS-01 · In a scrolling parent the overlay scrolls away with the content** — `loader-overlay.scss:16-35`, `notification-center.scss:87-93`, `modal.scss:120-124`, `loader-overlay-card-example.ts:36-38`, `e2e.ts:96-102`.
The host is `position: absolute` with `top/right/bottom/left: 0` (`loader-overlay.scss:21, 28-31`) inside a containing block the component itself creates on the parent (LDR-ARCH-01). When that parent is a scroll container, an absolutely positioned child is laid out against the container's padding box and then *scrolls with the content* — it does not stay pinned over the visible area. Both documented hosts are scroll containers: `.kbq-notification-center-container` sets `overflow: auto` (`notification-center.scss:93`), and `.kbq-modal-body` sets `overflow-y: auto; max-height: calc(100vh - 260px)` (`modal.scss:120-124`) — and the modal is exactly the case the `card` section of the guide is written for (`loader-overlay.en.md:66-70`). The consequence is that a loader over a long, scrolled form covers the first screenful and then slides out of view, leaving the rest of the content uncovered while the operation is still running — which is also what makes LDR-A11Y-01 worse, since the exposed part is fully interactive. Nothing in the test suite can catch this: the docs example pins its content to `height: 320px` (`loader-overlay-card-example.ts:36-38`), the e2e card host to `height: 350px` (`e2e.ts:96-102`), and the states fixture to 170px cells (`e2e.ts:71-75`), so no fixture ever scrolls.
**Fix:** decide the contract explicitly. Either document that the overlay covers the *scrollable* area (and then have the container directive from LDR-A11Y-01 apply `overflow: hidden` while loading, which is the usual expectation for a blocking loader anyway), or support the "cover the viewport of the scroll container" case with `position: sticky` on an inner wrapper. Whichever is chosen, add an e2e fixture whose container scrolls (content taller than a fixed-height `overflow: auto` box, scrolled to the bottom before the screenshot) so the behaviour is pinned by a baseline.

**LDR-BUG-01 · Decorator content queries feed an `OnPush` template, so conditionally projected slots never render** — `loader-overlay.component.ts:50, 84-98, 111-113`, `loader-overlay.component.html:2-26`.
`externalIndicator`/`externalText`/`externalCaption` are plain `@ContentChild` decorator queries (`:111-113`); the template branches on them through the `isExternal*` getters (`loader-overlay.component.html:2, 8, 18`), and the component is `ChangeDetectionStrategy.OnPush` (`:50`). Content queries are refreshed as part of the *declaring* (parent) view's change detection, while the overlay's own view is only re-rendered when it is marked dirty. Nothing marks it dirty: the query result changing is not an input change and raises no event. So for
```html
<kbq-loader-overlay>
    @if (showDetails()) { <div kbq-loader-overlay-text>…</div> }
</kbq-loader-overlay>
```
flipping `showDetails` updates `externalText` and even updates the host class binding `[class.kbq-loader-overlay_empty]` (host bindings also run in the parent view), but the `@if (isExternalText)` branch inside the overlay's template is never re-evaluated — the projected node exists but its `<ng-content>` slot was never created, so it is silently not rendered. The reverse flip leaves the `@else` fallback unrendered too. The existing spec cannot see this: all three host components (`loader-overlay.component.spec.ts:88-138`) project statically and are checked exactly once.
**Fix:** migrate the three queries to signal queries — `readonly externalText = contentChild(KbqLoaderOverlayText)` — which create a reactive dependency when read from the template and mark the `OnPush` view dirty on change; make the `isExternal*` getters `computed()` or read the signals directly in the template. Use the optional (non-`.required`) form, as the repo's earlier signal-queries migration showed `.required` throws NG0951 in production builds. Add a spec that toggles a projected `[kbq-loader-overlay-text]` with `@if` after the first `detectChanges()` and asserts the rendered text follows.

**LDR-API-01 · `fixed-top` is a phantom attribute shipped in the docs example and the dev app** — `loader-overlay-fixed-top-example.ts:20`, `components-dev/loader-overlay/template.html:74`, `loader-overlay.en.md:46-52`, `loader-overlay.ru.md:46-52`.
The guides document two alignment behaviours that do not exist: vertical centring "with optical compensation… the compensation height equals 40% of the block height" and "Fixed top-offset alignment is also available (72px by default)" (`loader-overlay.en.md:48, 50`). The component only ever centres — `justify-content: center` on both the host and the inner container (`loader-overlay.scss:25, 41`) — and there is no `fixed-top` input, attribute selector, host binding or CSS rule anywhere in the repository. The example embedded directly under that paragraph nevertheless writes `<kbq-loader-overlay fixed-top>` (`loader-overlay-fixed-top-example.ts:20`), and the dev app copies it (`components-dev/loader-overlay/template.html:74`). Because `fixed-top` is a static attribute rather than a property binding, `strictTemplates: true` (`tsconfig.json:117`) raises nothing — unlike a `[fixed-top]` binding, which would be a hard NG8002. The rendered result is byte-identical to `loader-overlay-default`, so the docs page shows the same picture twice with different captions, and a consumer copying the snippet gets a silently ignored attribute.
**Fix:** decide whether the design still calls for the feature. If yes, implement it as `readonly fixedTop = input<boolean, unknown>(false, { transform: booleanAttribute })` driving a `kbq-loader-overlay_fixed-top` class that switches the container to `justify-content: flex-start` with a `--kbq-loader-overlay-size-*-fixed-top-offset` token (72px per the guide), and fix the example to use the camelCase input. If no, delete `packages/docs-examples/components/loader-overlay/loader-overlay-fixed-top/`, its entry in `index.ts:4, 12, 20`, the regenerated `example-module.ts` records, the dev-app usage and the guide paragraphs in both languages. Either way add the example (or its removal) to the e2e states fixture so the two variants are visually distinguishable in a baseline.

**LDR-DOC-01 · The English guide embeds an example id that does not exist** — `loader-overlay.en.md:70`, `loader-overlay.ru.md:70`, `docs-examples/components/loader-overlay/index.ts:2, 10, 24`, `docs-live-example-viewer.ts:137-138`.
The final section of the English guide embeds `<!-- example(loader-overlay-on-background) -->` (`loader-overlay.en.md:70`). The example is registered as `loader-overlay-card` — that is the directory name, the class name `LoaderOverlayCardExample`, the selector, and the key in the generated `example-module.ts:3858-3868` — and the Russian mirror embeds it correctly (`loader-overlay.ru.md:70`). `loader-overlay-on-background` appears in exactly one file in the whole repository: that line. At runtime `DocsLiveExampleViewer.loadExample()` hits `if (!EXAMPLE_COMPONENTS[exampleName])`, writes `Could not find example: loader-overlay-on-background` to the console and returns (`docs-live-example-viewer.ts:137-141`), leaving the viewer chrome mounted with no example inside. So the "On card background" section — the documentation for the newest feature of the component (`card`, added in DS-3474) — is a blank box for every English reader while it works for Russian ones.
**Fix:** change `loader-overlay.en.md:70` to `<!-- example(loader-overlay-card) -->`. Then close the class of defect: add a docs check that cross-references every `<!-- example(<id>) -->` in `packages/components/**/*.{en,ru}.md` against the keys of `EXAMPLE_COMPONENTS` in `packages/docs-examples/example-module.ts` and fails the build on an unknown id — one `node -e` script in the docs pipeline, since the generated map is a plain object literal.

**LDR-TEST-01 · Five Jest cases cover none of the component's risky behaviour** — `loader-overlay.component.spec.ts:27-86`, `__snapshots__/loader-overlay.component.spec.ts.snap:3-8`, `e2e.ts:6-122`.
The spec has five `it` blocks: default `transparent`, inline params render, spinner-only renders, projected params render, and a class snapshot. Nothing exercises `card` (`loader-overlay.component.ts:80`) — the newest input, shipped with a `color-mix()` theme branch and a JSDoc claim that it "overrides `transparent`", verified only by a screenshot. Nothing exercises `size` beyond the default (`spinnerSize`'s `compact`/`big` mapping at `:100-102` is untested, and the `normal` case — where the spinner is deliberately promoted to `big` — is untested in both suites). Nothing exercises `transparent: false`. Nothing at all covers the parent-class lifecycle of LDR-ARCH-01: that `kbq-loader-overlay_parent` is added on init and removed on destroy is the component's single side effect on the outside world and has zero assertions. There is no `jest-axe` case, although five sibling packages have one. And the one assertion that does look like coverage is hollow: `expect(containerElement.nativeElement.classList).toContain('kbq-loader-overlay_empty')` (`:60`) pins a class that no stylesheet in the repository reads (LDR-CSS-02), so it can never fail for a reason a user would notice. The Playwright suite is better — 12 state combinations × 2 themes plus the card-in-modal case (`e2e.playwright-spec.ts:8-30`) — but every fixture is height-pinned so it structurally cannot see LDR-CSS-01.
**Fix:** add Jest cases for (a) `[card]="true"` applying `kbq-loader-overlay_card` alongside the variant class, (b) `spinnerSize` for all three `KbqDefaultSizes` values asserted on the rendered `kbq-progress-spinner`, (c) `[transparent]="false"` applying `_filled` and not `_transparent`, (d) parent gains `kbq-loader-overlay_parent` after `detectChanges()` and loses it after `fixture.destroy()`, (e) the conditional-projection case from LDR-BUG-01, (f) a `jest-axe` pass. Rename the host components to drop nothing (they already follow the no-`Kbq` convention). Add the scrolling e2e fixture from LDR-CSS-01. Delete or re-point the `_empty` assertion once LDR-CSS-02 is resolved.

### P3 — Nice to have / hygiene

**LDR-CSS-02 · `kbq-loader-overlay_empty` is a dead modifier with a public getter and a test behind it** — `loader-overlay.component.ts:55, 96-98`, `loader-overlay.component.spec.ts:60`, `tools/public_api_guard/components/loader-overlay.api.md:26-27`.
The host binds `[class.kbq-loader-overlay_empty]` to an `isEmpty` getter that evaluates four conditions on every change detection, `isEmpty` is exported as public API, and the spec asserts the class is present — but a repository-wide search for `kbq-loader-overlay_empty` returns exactly those three occurrences plus the host binding itself. No stylesheet, in this package or any other, matches the class. Either the styling it was meant to trigger was lost (the `:has()` rule at `loader-overlay.scss:51-53` supersedes at least the spacing part of it, per DS-4567) or it is a leftover.
**Fix:** if the class is intended as a public styling hook, document it in the guide and keep it; otherwise delete the host binding, the `isEmpty` getter and the spec assertion, and re-approve the API report.

**LDR-CSS-03 · Hard-coded `z-index: 10`, marked `// todo` in the source** — `loader-overlay.scss:34-35`, `notification-center.scss:88-89`.
```scss
// todo
z-index: 10;
```
The overlay's stacking order is an untokenized magic number carrying its author's own `// todo`. It has no relationship to the rest of the library's stacking scale — the one in-repo consumer raises its scrollbar track to `--kbq-scrollbar-track-z-index: 101` in the very container the overlay lives in (`notification-center.scss:88-89`), an order of magnitude above the overlay. Today that collision is masked because the loader replaces the list rather than covering it (`notification-center.html:131-133`), but any consumer with a positioned child above `z-index: 10` inside the covered block will punch through the scrim, and there is no token to raise it against.
**Fix:** replace with `z-index: var(--kbq-loader-overlay-z-index)` defined in `loader-overlay-tokens.scss`, pick the value against the existing scale (the scrollbar-track and modal tokens are the neighbours to compare with), and delete the `// todo`.

**LDR-CSS-04 · Most of the token and theme layer resolves to identical values** — `loader-overlay-tokens.scss:2-18`, `_loader-overlay-theme.scss:4-43`, `loader-overlay.scss:17-19`.
The size layer defines nine custom properties across three sizes, but `--kbq-loader-overlay-size-{big,normal,compact}-overlay-padding-horizontal` are all `var(--kbq-size-3xl)` (`loader-overlay-tokens.scss:2, 5, 8`) and the big/normal `loader-margin-bottom` pair is identical too (`:3, 6`) — so `--padding-horizontal` cannot vary by size at all, and the three-branch cascade at `loader-overlay.scss:59-75` exists to set values that never differ. The same holds in the theme: `--kbq-loader-overlay-transparent-text-color` and `--kbq-loader-overlay-filled-text-color` are both `var(--kbq-foreground-contrast)`, and the two caption colours are both `var(--kbq-foreground-contrast-secondary)` (`loader-overlay-tokens.scss:13-14, 16-17`), so the twelve-line `filled`/`transparent` split in `_loader-overlay-theme.scss:5-31` differs only in the background. The fallbacks at `loader-overlay.scss:17-19` are unreachable, since `loaderSizeClass` always emits one of the three size classes. And the `card` override wins over `filled`/`transparent` only on source order: `.kbq-loader-overlay_card.kbq-loader-overlay_filled` (`_loader-overlay-theme.scss:33-35`) and `.kbq-loader-overlay_filled.kbq-loader-overlay` (`:5-8`) both have specificity (0,2,0), so reordering the mixin — or a consumer re-including it — silently inverts the result. The file's own `// FIXME: move to unified mixin if necessary` (`:4`) marks the area as known debt.
**Fix:** collapse the identical token pairs into a single non-size-qualified property (keep the per-size names only where the values actually differ — currently just `content-gap-vertical` and the compact `loader-margin-bottom`), drop the unreachable defaults, hoist the shared text/caption colours out of the `filled`/`transparent` branches, and break the specificity tie explicitly (`&.kbq-loader-overlay_card` nested inside the two variant blocks, or a single `background` declaration whose token is selected by the modifier). The four existing screenshots are the regression net.

**LDR-API-02 · Internal members are public API; `text`/`caption` are typed as if always present** — `tools/public_api_guard/components/loader-overlay.api.md:15-51`, `loader-overlay.component.ts:68, 73, 84-102, 111-113`.
The API report exposes `externalIndicator`, `externalText`, `externalCaption` (the raw content-query results), the three `isExternal*` getters, `isEmpty` and `spinnerSize` — eight members that exist purely to drive the component's own template, all of them `// (undocumented)`. Only `card` carries a JSDoc comment; even the component class itself is `// @public (undocumented)`, and the package has no `@packageDocumentation`. Separately, `text` and `caption` are declared `@Input() text: string;` (`:68, 73`) with no initializer and no `?`. `strictPropertyInitialization` is not enabled in this workspace, so this compiles, but the runtime value before the first binding is `undefined` while the API report tells consumers `text: string` (`loader-overlay.api.md:18, 44`) — and the docs site renders that report directly (`structure.ts:727-728`, `hasApi: true`). Any consumer doing `overlay.text.length` gets a type-checked crash.
**Fix:** make the three query fields and the four internal getters `protected` (they are only read from the template and the host block), type `text`/`caption` as `string | undefined` — or migrate them per LDR-ARCH-02, where `input<string>()` gets the optionality right by construction — and add JSDoc to the members that stay public. Then `yarn run build:components && yarn run approve-api` (build first: the guard reads `dist/*.d.ts`). Tightening visibility is technically breaking, so schedule with the next minor.

**LDR-ARCH-02 · Decorator inputs and queries with stale migration TODOs; two unused CDK modules in the NgModule** — `loader-overlay.component.ts:65-73, 111-113`, `loader-overlay.module.ts:1-2, 14-15`.
Two of the five inputs are still `@Input()` fields carrying the Angular migration tool's own skip comments verbatim ("TODO: Skipped for migration because: This input is used in a control flow expression (e.g. `@if` or `*ngIf`) and migrating would break narrowing currently", `:65-67, 70-72`). AGENTS.md mandates `input()`, and the stated blocker no longer applies: `@if (text) { {{ text }} }` migrates to `@if (text(); as value) { {{ value }} }` without losing narrowing. AGENTS.md also forbids committing comments that describe change history. The three content queries (`:111-113`) predate the signal-query convention and are the direct cause of LDR-BUG-01. Separately, the NgModule imports `A11yModule` and `PlatformModule` (`loader-overlay.module.ts:1-2, 14-15`) although the component imports only `KbqProgressSpinner` (`loader-overlay.component.ts:47`) and uses no CDK symbol; both leak into the generated module type in the API report (`loader-overlay.api.md:8-9, 76`), so every consumer of `KbqLoaderOverlayModule` transitively pulls them in.
**Fix:** migrate `text`/`caption` to `input<string>()` with the `as` form in the template, migrate the queries to `contentChild()` (LDR-BUG-01), delete both TODO blocks, and drop `PlatformModule` from the NgModule. Keep `A11yModule` only once LDR-A11Y-01/LDR-A11Y-02 actually use it — otherwise drop it too. Also consider `kbqInjectNativeElement()` (`packages/components/core/utils`) in place of the raw `inject<ElementRef<HTMLElement>>(ElementRef)` at `:62`, matching `accordion-content.directive.ts:39`.

**LDR-DOC-02 · The guides specify five behaviours the component does not implement** — `loader-overlay.en.md:24-26, 38, 42-44, 48-50`, `loader-overlay.ru.md:24-26, 38, 42-44, 48-50`.
Beyond the `fixed-top` case tracked as LDR-API-01, the "Design and animation" section describes measurements that the CSS does not produce. "Padding from the overlay edges is 10% of its width" (`:43`) — the padding is `var(--kbq-size-3xl)`, a fixed length, on all three sizes (`loader-overlay-tokens.scss:2, 5, 8`). "Maximum width of the text and caption under the spinner is 480px" (`:44`) — the container is `width: 80%; max-width: 80%` and the text/caption `max-width: 90%` (`loader-overlay.scss:44-45, 9-13`); 480px appears nowhere. "Center alignment with optical compensation… 40% of the block height" (`:48`) — plain `justify-content: center`. "The default text is 'Loading'" (`:25`) — `text` has no default, so the default overlay renders a bare spinner, which is also why LDR-A11Y-02 matters. And "Default state: Opaque overlay" (`:24`) contradicts both the input name and the token, since the default `transparent: true` resolves to a 90%-alpha scrim in light and 75% in dark (`css-tokens-light.css:30`, `css-tokens-dark.css:30`) — while the very next section describes it as "90% opacity" (`:38`). Both language mirrors carry all five, so there is no correct version to fall back on.
**Fix:** reconcile the guides against the implementation section by section — either implement the missing behaviour (the 480px cap and the optical compensation are cheap: a `max-width` token on `.kbq-loader-overlay-text`/`-caption` and a `padding-bottom` on the container) or delete the paragraph. Give `text` a locale-sourced default if the "Loading" default is still wanted (same locale key as LDR-A11Y-02). Rewrite the "Default state" paragraph to name the actual default (`transparent: true`, semi-transparent scrim).

**LDR-DOC-03 · `examples.loader-overlay.*.md` are dead placeholder stubs** — `examples.loader-overlay.en.md:1-5`, `examples.loader-overlay.ru.md:1-5`, `structure.ts:719-730`.
Both files contain only the "🚧 Documentation in progress 🚧" boilerplate. The docs entry sets `hasExamples: false` (`structure.ts:729`), so the Examples tab never renders and these are not a broken user surface — they are two dead files that a reader grepping the package will mistake for a real gap, and that the docs build still ships. The six real examples are all embedded in the Overview guide instead.
**Fix:** delete both files, or populate them with the six `<!-- example(…) -->` embeds and flip `hasExamples` to `true` at `structure.ts:729`. Deleting is the cheaper option given the guide already shows every example.

## 4. Recommended Remediation Phases

**Phase 1 — Make the published contract true (docs-only, no API change).**
IDs: LDR-DOC-01, LDR-API-01 (documentation half), LDR-DOC-02, LDR-DOC-03. Fix the `loader-overlay-on-background` embed, decide the fate of `fixed-top`, reconcile the design paragraphs with the shipped CSS, remove the dead stubs. This lands first because it is zero-risk, it is what users hit today, and it settles which features Phase 2 has to implement.

**Phase 2 — Accessibility and container ownership.**
IDs: LDR-A11Y-01, LDR-A11Y-02, LDR-ARCH-01, LDR-CSS-01. Introduce `[kbqLoaderOverlayContainer]` as the supported host: it owns `position: relative`, `border-radius: inherit`, `[attr.inert]`, `[attr.aria-busy]` and the scroll-container decision, and it removes the blind `parentElement` mutation. Add `role="status"`/`aria-live` on the inner container plus a `LiveAnnouncer` announcement sourced from a new `a11y.loading` locale key across all five locale files. Keep the old parent-class path as a deprecated fallback and migrate `notification-center.html:132` in the same change; harden the fallback with the null/computed-position/refcount guards. This is the phase with real user impact and it depends on Phase 1 only for the `fixed-top` decision.

**Phase 3 — Reactivity and API modernization.**
IDs: LDR-BUG-01, LDR-ARCH-02, LDR-API-02. Migrate the three content queries to `contentChild()` (fixing the conditional-projection defect), `text`/`caption` to `input<string>()`, drop the migration TODOs and the unused CDK module imports, tighten member visibility. Requires `yarn run build:components` then `yarn run approve-api`; the visibility change is breaking, so schedule with the next minor.

**Phase 4 — Styles and tokens.**
IDs: LDR-CSS-02, LDR-CSS-03, LDR-CSS-04. Remove the dead `_empty` modifier, tokenize `z-index`, collapse the identical token/theme branches and break the `card` specificity tie explicitly. Purely internal; the four existing screenshots are the acceptance net.

**Phase 5 — Close the test gap.**
IDs: LDR-TEST-01. Add the Jest cases for `card`, `size`/`spinnerSize`, `transparent: false`, the parent-class lifecycle, conditional projection and `jest-axe`, plus the scrolling e2e fixture. Runs last because most of these assertions describe behaviour that Phases 2–4 define, but the `card`/`size`/`transparent` cases can land in parallel with Phase 1.

## 5. Verification Strategy

General gates, after every phase, run sequentially — never two heavy builds at once:
- `npx jest packages/components/loader-overlay` plus the consumer suite `npx jest packages/components/notification-center` (the only in-repo consumer, and the one whose SCSS depends on the parent class).
- `yarn run eslint` and `yarn run stylelint` on touched files; `yarn run prettier`.
- `yarn run build:components`, then `yarn run check-api` (the guard reads `dist/*.d.ts`, so the build must come first). `approve-api` only in Phase 3, where the surface intentionally changes.
- Screenshots only via `yarn run e2e:docker` / `yarn run e2e:docker:update-snapshots` — the four committed baselines are Linux, compared at `threshold: 0` with no platform suffix.
- Manual smoke: `yarn run dev:loader-overlay` (the dev app renders all six examples plus four hand-built cases and a `toggleLoading` button that exercises destroy/re-create).

Per-phase acceptance assertions:
- **Phase 1:** the English docs page for Overlay renders an example under "On card background" and the browser console is clean — no `Could not find example` (`docs-live-example-viewer.ts:138`). If `fixed-top` was removed, `grep -rn "fixed-top" packages/` returns nothing outside a changelog; if implemented, the fixed-top and default examples are visually different in the same screenshot. Every `<!-- example(id) -->` in the two guides resolves against `EXAMPLE_COMPONENTS`.
- **Phase 2:** in the dev app, pressing `Tab` repeatedly from above a loading container never places focus inside it, and `document.activeElement` after the last preceding control is the first control *after* the container. VoiceOver/NVDA announce the loading state once on appearance and announce caption updates. `jest-axe` passes on a fixture with focusable content under the overlay. A spec asserts the container carries `aria-busy="true"` and `inert` while mounted and neither after destroy. A new scrolling e2e baseline shows the chosen behaviour (covered scrollable area, or pinned to the visible box) rather than an overlay that has scrolled out of frame.
- **Phase 3:** the conditional-projection spec passes — toggling a projected `[kbq-loader-overlay-text]` after the first CD changes the rendered output. `check-api` reports only the intended removals (`externalIndicator`, `externalText`, `externalCaption`, `isExternal*`, `isEmpty`, `spinnerSize` become non-public; `text`/`caption` change type) and the module-type entry loses `PlatformModule`. `build:components` still compiles `notification-center`.

## Appendix A — Review Methodology

Every file in the package was read in full (`cat -n`), then followed outward: the single in-repo consumer (`notification-center.html`, `.scss`, `.ts`), the six docs examples and their generated registration in `packages/docs-examples/example-module.ts`, the dev app, the docs navigation entry in `apps/docs/src/app/structure.ts`, the live-example loader in `apps/docs/src/app/components/live-example-viewer/docs-live-example-viewer.ts`, the API guard report and its api-extractor registration, the `ng-update` migration for the earlier `compact` → `size` rename, and the last 14 commits touching the package. Claims about styling were checked against the live token set (`node_modules/@koobiq/design-tokens/web/new/css-tokens-{light,dark}.css`) and against the two containers the component is documented to live in (`modal.scss`, `notification-center.scss`). Claims about Angular semantics were checked against the installed framework source where behaviour mattered (`@angular/platform-browser/fesm2022/dom_renderer.mjs:617-622` for `Renderer2.addClass`). Accessibility findings were calibrated against in-repo precedent — `accordion-content.directive.ts:19-24` for `inert`, `notification-center.html:106-108` and `app-switcher.html:189` for `role="status"`, `filter-bar/pipe-add.ts:61` for a live region — and stated as WCAG judgements, not automated AXE failures, since axe-core does not flag focusable content behind a sibling element. No build, test suite or formatter was run.

Refuted during verification:
- **"The `[class]` host binding at `loader-overlay.component.ts:54` wipes the static `kbq-loader-overlay` class and any consumer class"** — refuted. Angular's styling precedence keeps lower-priority classes that a higher-priority map binding does not name, and the committed Jest snapshot proves it empirically: `__snapshots__/loader-overlay.component.spec.ts.snap:4-8` records `kbq-loader-overlay`, `kbq-loader-overlay_big` and `kbq-loader-overlay_transparent` all present simultaneously.
- **"`[card]="true"` with the default `transparent: true` produces unreadable text (contrast foreground over a card surface)"** — refuted. `--kbq-foreground-contrast` is `oklch(13.5% …)` in light and `oklch(97.1% …)` in dark (`css-tokens-light.css:32`, `css-tokens-dark.css:32`), i.e. the ordinary readable foreground rather than an inverse one, and `--kbq-loader-overlay-card-overlay-background` resolves to `--kbq-background-card`, the same-polarity surface. No contrast failure in either theme.
- **"The `:has()` spacing rule breaks because the `@if` blocks leave comment anchors between the spinner and the text"** — refuted. Comment nodes are not elements, so the `+` combinator in `loader-overlay.scss:51-53` still matches across them; this rule is the DS-4567 fix (`50a78e605`) and works as written.
- **"The overlay does not block mouse interaction with the covered content"** — refuted. The host is an `inset: 0` box that paints a background in all three variants (`_loader-overlay-theme.scss:5-43`) and never sets `pointer-events: none`, so pointer events over the covered area do land on the overlay. Only keyboard focus, text selection and assistive-technology access leak through — which is what LDR-A11Y-01 claims, narrowed accordingly.
- **"`size="normal"` is invalid for the spinner, since `ProgressSpinnerSize` is `'compact' | 'big'`"** — refuted. `spinnerSize` (`loader-overlay.component.ts:100-102`) maps everything except `compact` to `big`, and `KbqProgressSpinner.size` is declared `ProgressSpinnerSize | string` (`progress-spinner.component.ts:53-57`), so the `string` return type-checks under `strictTemplates`. The `normal` size differs from `big` only in typography and the content gap, which is a design decision, not a defect.
- **"The package is missing from the docs navigation or from the API guard configuration"** — refuted. `structure.ts:719-730` lists it with `hasApi: true` and `apiId: 'loader-overlay'`, and `tools/api-extractor/config.json:33` includes the package. All six AGENTS.md structure files are present (tokens, theme, module, public-api, spec, e2e pair), matching the inventory.

Corrected on verification:
- **LDR-A11Y-01** was first drafted as "the overlay does not trap focus". A focus *trap* is the wrong remedy for a non-modal region — it would strand keyboard users inside a spinner. Reworded around `inert`/`aria-hidden` on the covered container, matching `accordion-content.directive.ts:19-24`; severity unchanged.
- **LDR-CSS-01** was initially folded into LDR-ARCH-01 as one "parent mutation" item. They were split because they have different fixes (ownership/robustness vs. layout contract) and because the scroll-container consequence is what makes LDR-A11Y-01 user-visible in the documented modal case.
- **LDR-DOC-01** was initially drafted as "the Examples tab is broken". `hasExamples: false` (`structure.ts:729`) means there is no Examples tab at all, so the damage is confined to the Overview tab of the English guide; the stub files are merely dead and were downgraded to LDR-DOC-03 (P3).
- **LDR-API-01** was initially filed as a P3 documentation nit. It was raised to P2 once `components-dev/loader-overlay/template.html:74` turned up using the same phantom attribute — the feature is referenced from three places (guide, docs example, dev app) and implemented in none.
