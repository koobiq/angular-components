# Koobiq `divider` Component — Code Review & Improvement Plan

> Scope: `packages/components/divider` (component, tokens, theme, SCSS, Jest spec, e2e fixture + Playwright spec, user guides, API guard report) · Commit `b665e503` · 2026-08-28
> Generated by a multi-dimension review (architecture, correctness, accessibility, public API/types, styles, tests, docs) with manual verification of every finding against the source, the in-repo consumers, and `tsconfig.json`. 10 findings confirmed (P0×0, P1×2, P2×4, P3×4); 4 candidate findings refuted during verification (see Appendix A). This document is a review + roadmap; no source is modified by it.

---

## 1. Executive Summary

`KbqDivider` is the smallest shipped component in the library: a 44-line class with an empty template, two boolean inputs (`vertical`, `paddings`), 7 CSS custom properties and a one-declaration theme mixin. There are **no release blockers** — the component cannot really break at runtime — but its two P1s are both *contract* failures, where what the library promises and what it delivers have drifted apart.

- **The published user guide documents an input that does not exist.** Two of the guide's four sections tell consumers to use `[inset]`; `KbqDivider` has no `inset` member, and because the workspace compiles with `strictTemplates: true` (`tsconfig.json:117`) both snippets are hard NG8002 compile errors, not silently-ignored attributes. The same guide's list example additionally uses `*ngFor`/`*ngIf` (banned by AGENTS.md) and `kbq-list-icon`, a selector that exists nowhere in the repo (DIV-DOC-01).
- **The component ships no separator semantics, and consumers have each invented their own.** There is no `role`, no `aria-orientation`, no `aria-hidden`. In-repo consumers have patched around it three different ways: `app-switcher.html:82` writes `role="separator"` by hand, `list/e2e.ts:419` writes `aria-hidden="true"`, and every other call site writes nothing at all. A component whose only purpose is to communicate structure communicates none of it programmatically (DIV-A11Y-01).
- **The vertical variant's sizing does not work in the layout it is used in.** `height: 100%` (`divider.scss:20`) resolves to `0` in the flex rows where vertical dividers actually live. This is not theoretical: **all three** in-repo vertical consumers override the height, two of them with `!important` (`actions-panel-container.scss:23`, `filters.scss:37`, `notification-center.scss:57-59`). The same specificity problem forces `filters.scss:41-42` to `!important` its margins past `.kbq-divider_paddings`, with a load-bearing comment explaining why (DIV-CSS-01, DIV-CSS-02).
- **Test coverage is one assertion.** The Jest spec contains a single case that checks the `vertical` class; `paddings`, the horizontal default, the coercion setters and the defaults are unverified. The spec's host component also carries the `Kbq` prefix that this repo's convention reserves for library classes (DIV-TEST-01, DIV-TEST-02).

Genuine strengths worth preserving: `OnPush` + standalone + host-object bindings with no `@HostBinding`, fully token-driven styling with zero hardcoded colors, a real Playwright screenshot covering all four state combinations in light and dark, and an NgModule wrapper retained for legacy consumers. For a component this size the *code* is close to right; the gap is entirely in its contract surface — docs, semantics, and the sizing assumptions it imposes on its callers.

## 3. Prioritized Findings (deduplicated, verified)

### P0 — Release blockers

None.

### P1 — High

**DIV-DOC-01 · The user guide documents an `inset` input that does not exist, and the snippets do not compile** — `divider.en.md:13-19, 27-51`, `divider.ru.md:15-19, 27-53`.
`KbqDivider` exposes exactly two inputs, `vertical` and `paddings` (`divider.component.ts:21-43`); there is no `inset` member anywhere in the package, and none in the API guard report (`tools/public_api_guard/components/divider.api.md`). The guide nevertheless devotes a whole section to it ("Add the `inset` attribute…", `divider.en.md:13-19`) and uses it again inside the list example (`divider.en.md:41`). Under this workspace's `strictTemplates: true` (`tsconfig.json:117`) `<kbq-divider [inset]="true">` is not a no-op — it is an NG8002 "Can't bind to 'inset'" compile failure, so a consumer copying the documented snippet gets a build break, not a cosmetic difference. The same list example compounds the problem with three further defects: `*ngFor`/`*ngIf` structural directives (AGENTS.md mandates `@for`/`@if`), `kbq-list-icon`, a selector that appears nowhere in the repository, and `class="demo-2"`, a leftover from the upstream Material docs this file was adapted from. Both language mirrors carry all four defects identically, so there is no correct version for a reader to fall back on.
**Fix:** delete the "Inset divider" section from `divider.en.md`/`divider.ru.md` and drop `[inset]` from the list example, or implement `inset` if the visual is still wanted (a `.kbq-divider_inset` modifier with a `--kbq-divider-size-inset-offset` token is a ~6-line change and would preserve the docs as written — decide deliberately rather than by omission). Rewrite the list example against the current `list` API: `@for`/`@if`, `kbq-icon` with the real list-icon class, and drop `demo-2`. Add a docs smoke assertion — the docs site already compiles guide snippets in `yarn run e2e:docs`, so a corrected snippet stays corrected.

**DIV-A11Y-01 · No separator semantics; every consumer invents its own** — `divider.component.ts:10-15` (host block), consumers `app-switcher/app-switcher.html:17, 82`, `list/e2e.ts:419`, `filter-bar/filters.html:66, 87, 104, 140`, `notification-center/notification-center.html:37`.
The host block binds three classes and nothing else — no `role`, no `aria-orientation`, no `aria-hidden`. A `<kbq-divider>` is therefore an unknown element with no accessible semantics: a screen reader reading the app-switcher's grouped list, the filter-bar's segmented toolbar or a dropdown's grouped menu gets no boundary announcement at all, so groupings that are obvious visually are invisible non-visually (WCAG 1.3.1, Info and Relationships). The evidence that consumers feel this gap is in the tree: `app-switcher.html:82` writes `<kbq-divider role="separator" />` by hand while the *same file* at line 17 writes a bare `<kbq-divider />`; `list/e2e.ts:419` and `list-selection.component.spec.ts:2908` write `aria-hidden="true"`. Three call sites, three different answers, from three different authors. Note this is a WCAG judgement rather than an automated failure — axe does not flag an unknown element with no role, which is exactly why it has survived this long. The correct default is `role="separator"` plus `aria-orientation="vertical"` when `vertical` is set (`aria-orientation` **is** valid on `role="separator"`, unlike on `role="group"`), with an opt-out for purely decorative use.
**Fix:** add to the host block: `role: 'separator'`, `'[attr.aria-orientation]': "vertical ? 'vertical' : null"` (horizontal is the ARIA default, so emit nothing there). Add a `decorative` input that swaps to `role="presentation"` + `aria-hidden="true"` for dividers that only repeat a visual boundary, then delete the hand-rolled `role`/`aria-hidden` attributes at the five consumer call sites so the library speaks with one voice. Cover with a Jest case per branch and re-run the `list` and `app-switcher` suites, which assert on those attributes today.

### P2 — Should fix

**DIV-CSS-01 · `height: 100%` makes the vertical divider zero-height in the layout it is actually used in** — `divider.scss:18-21`; consumer workarounds at `actions-panel/actions-panel-container.scss:21-25`, `filter-bar/filters.scss:34-42`, `notification-center/notification-center.scss:55-59`.
`.kbq-divider_vertical` sizes itself with `width: var(--kbq-divider-size-vertical-width); height: 100%`. A percentage height resolves against the parent's *definite* height; in the flex rows where vertical dividers live — `notification-center.scss:55` sets `align-items: center`, `filters.scss:35` sets `align-self: center` — the parent has no definite height and the flex item is not stretched, so the divider computes to `0` and disappears. Every in-repo vertical consumer discovered this independently and patched it locally: `height: var(--kbq-actions-panel-vertical-divider-height) !important`, `height: var(--kbq-size-m) !important`, `height: var(--kbq-size-m)`. Three consumers, three overrides, two `!important` — the component is shipping a default that no caller can use. External consumers hit the same wall with no in-repo precedent to copy.
**Fix:** replace `height: 100%` with `align-self: stretch` (correct inside flex/grid rows, which is where vertical dividers belong) and add a `--kbq-divider-size-vertical-height` token defaulting to `auto` so a caller can pin a height through the token instead of an `!important` override. Verify against all three consumers before removing their overrides, and extend the e2e fixture with a flex-row case (see DIV-TEST-01) — the current fixture puts the divider in a fixed-height `<td>`, the one context where `height: 100%` happens to work.

**DIV-CSS-02 · `paddings` defaults to `true` and outranks consumer margins, forcing `!important`** — `divider.component.ts:34-43`, `divider.scss:11-15, 22-26`; consumer at `filter-bar/filters.scss:39-42`.
`paddings` defaults to `true`, so every `<kbq-divider />` written without a binding silently gains `var(--kbq-size-xxs)` of margin on two sides. A consumer wanting different spacing is fighting `.kbq-divider.kbq-divider_horizontal.kbq-divider_paddings` (0,3,0 specificity) from a single-class rule, which loses. `filters.scss:39-41` documents the outcome in a comment that is worth quoting in full because it is an accurate bug report against this component: the `!important` is "load-bearing" because it "overrides the divider's own higher-specificity `.kbq-divider_paddings` margin rule". A defaulted-on cosmetic behaviour that can only be escaped with `!important` or an extra binding is a poor default, and the plural name `paddings` describes margins, not padding.
**Fix:** two independent moves, either of which helps. (1) Flatten the specificity: emit the margins from `.kbq-divider_paddings` alone rather than nesting it under the orientation modifiers, so a consumer's own class can win. (2) Route the margins through the tokens the consumer can already set — `.kbq-divider { margin-block: var(--kbq-divider-size-horizontal-margin-vertical, 0) }` with the modifier only switching the token on — which removes the need for `!important` entirely and lets `filter-bar` set `--kbq-divider-size-vertical-margin-horizontal` instead. Flipping the default to `false` is the cleanest API but is breaking; if taken, pair it with a `ng-update` migration adding `paddings` to existing call sites (see `project_breaking_changes_need_migration_schematics`).

**DIV-API-01 · Legacy `@Input` accessors with stale migration TODOs, and no `ngAcceptInputType_*` under `strictTemplates`** — `divider.component.ts:18-43`.
Both inputs are accessor pairs carrying the auto-generated "Skipped for migration because: Accessor inputs cannot be migrated as they are too complex" TODO (`:19-20, 32-33`). Neither is complex: each is `coerceBooleanProperty` over a private backing field, the exact shape `input({ transform: booleanAttribute })` exists to replace. The comment is doubly misleading — it is untrue, and it discourages the next reader from touching it. Separately, the setters are typed `boolean` with no `static ngAcceptInputType_vertical: BooleanInput` declaration, so under `strictTemplates: true` the bare-attribute form the guide recommends ("Add the `vertical` attribute…", `divider.en.md:23`) does not type-check — `<kbq-divider vertical>` passes `''`, which is not assignable to `boolean`. Migrating to `input({ transform: booleanAttribute })` fixes the coercion, the typing and the TODOs in one move, and `booleanAttribute` supersedes the CDK `coerceBooleanProperty` import.
**Fix:** `readonly vertical = input(false, { transform: booleanAttribute });` and the same for `paddings`; update the three host bindings to call the signals; drop the `@angular/cdk/coercion` import. This changes the API report (accessor pairs become `InputSignal`s), so run `yarn run build:components` then `yarn run approve-api` — build first, the guard reads `dist/*.d.ts`. Reading `vertical` externally is not currently done anywhere in the repo, so the signal migration has no in-repo consumer cost.

**DIV-TEST-01 · One assertion covers the whole component** — `divider.spec.ts:16-24`; missing cases across `divider.spec.ts`, `e2e.ts`.
The Jest spec has exactly one `it`, asserting that `vertical: true` yields `kbq-divider` + `kbq-divider_vertical` classes. Untested: the `kbq-divider_horizontal` default (the mutually-exclusive `[class.kbq-divider_horizontal]': '!vertical'` binding is the component's only real logic), the `paddings` input and its `true` default, and the coercion path — `coerceBooleanProperty('')`/`'false'` behaviour is exactly the kind of thing that changes silently under the DIV-API-01 migration and would go unnoticed. The Playwright fixture is better (four combinations, light + dark) but places every divider inside a fixed-height 50×50 `<td>` (`e2e.ts:28-35`), the single layout context in which DIV-CSS-01 does not reproduce — so the screenshot suite actively conceals the component's most-worked-around defect.
**Fix:** add Jest cases for the horizontal default, `paddings` on/off, both defaults read off a bare `<kbq-divider />`, and coercion of `''`/`'false'`; add the ARIA assertions from DIV-A11Y-01 once implemented. Add a second e2e row placing a vertical divider between two buttons in a `display: flex; align-items: center` container — that row is the regression guard for DIV-CSS-01, and its baseline must be produced through `yarn run e2e:docker:update-snapshots` (native runs fail on font rasterization alone).

### P3 — Nice to have / hygiene

**DIV-TEST-02 · Test host uses the reserved `Kbq` prefix and an uninitialized field** — `divider.spec.ts:27-35`.
`KbqDividerTestComponent` takes the `Kbq` prefix this repo reserves for library exports; test hosts and helpers are named without it (this is convention, not lint-enforced, so it drifts silently). The host's `vertical: boolean;` is also declared without an initializer, so its value is `undefined` until the single test assigns it — a second test that forgets the assignment would exercise `!undefined → horizontal` while reading as "default".
**Fix:** rename to `DividerTestComponent` and initialize `vertical = false;`. When adding the DIV-TEST-01 cases, prefer separate small hosts (or `TestBed.runInInjectionContext` with a bare `<kbq-divider />`) over one mutable host, so each case states its own preconditions.

**DIV-API-02 · Every public member is `// (undocumented)` in the API report** — `tools/public_api_guard/components/divider.api.md:9-19`, `divider.component.ts:18, 34`.
`KbqDivider`, `KbqDividerModule`, `vertical` and `paddings` all carry `// @public (undocumented)`. The only prose in the class is a bare `//` comment (`:18`, "Whether the divider is vertically aligned"), which does not reach the report — API Extractor reads `/** … */` only. `paddings` has no comment at all, so its non-obvious `true` default and its margins-not-padding meaning are documented nowhere: not in the class, not in the report, not in the guide. Note the inverse hazard when fixing this: adding a JSDoc block to a public member removes the `(undocumented)` marker and therefore changes `divider.api.md`, so the `check-api` job fails until `approve-api` is re-run (see `project_jsdoc_on_public_member_changes_api_md`).
**Fix:** convert `:18` to a `/** */` block, add one for `paddings` stating the `true` default and that it emits margins, add a class-level block describing the two orientations. Fold this into the DIV-API-01 rebuild + `approve-api` cycle so the report churns once rather than twice.

**DIV-STYLE-01 · Token-set asymmetry and one always-dead cross-package reference** — `divider-tokens.scss:1-8`, `divider.scss:7-27`; cross-reference at `code-block/code-block-tokens.scss:134`.
Three small style-surface issues. (1) The horizontal branch sets both `min-height` and `height` (`divider.scss:8-9`) while the vertical branch sets only `width` (`:19`) — a vertical divider in a shrinking flex row has no floor, and the asymmetry is unexplained. (2) The token names embed the dimension twice (`--kbq-divider-size-horizontal-width`, `--kbq-divider-size-vertical-width`); `--kbq-divider-size-thickness` would describe both and halve the set. (3) `code-block-tokens.scss:134` reads `var(--kbq-divider-color, var(--kbq-line-contrast-less))`, but `--kbq-divider-color` is declared *scoped to `.kbq-divider`* (`divider-tokens.scss:1, 7`), so it is never in scope inside `.kbq-code-block` and the fallback is taken 100% of the time — a reference that reads as a theming link but is dead.
**Fix:** add `min-width` to the vertical branch to mirror `min-height`; consider collapsing the two width tokens into one thickness token behind the existing names (keep the old names as aliases for one minor). Either delete the dead `--kbq-divider-color` reference in `code-block-tokens.scss:134` in favour of the fallback it always uses, or promote `--kbq-divider-color` to a `:root`-level token if a shared divider colour across packages is actually intended.

**DIV-DOC-02 · `examples.divider.*.md` are dead placeholder files** — `examples.divider.en.md:1-5`, `examples.divider.ru.md:1-5`, `apps/docs/src/app/structure.ts:511-517`.
Both files carry the standard "🚧 Documentation in progress 🚧" stub. Unlike the equivalent finding in other packages, these are not a broken user-facing surface: the docs structure entry sets `hasExamples: false` (`structure.ts:516`), so the Examples tab is never rendered for divider and the files are unreachable. They are simply two dead files that will keep showing up in "in progress" greps and inviting someone to fill them in. Two real examples do exist and are already embedded in the guide (`divider-overview`, `divider-vertical`, `packages/docs-examples/components/divider/`).
**Fix:** decide one way. Either delete both stubs (the guide already embeds both examples inline, so nothing is lost), or populate them with the two `<!-- example(…) -->` embeds and flip `hasExamples: true` in `structure.ts`. Deleting is the lower-cost option and matches what the structure entry already declares.

## 4. Recommended Remediation Phases

**Phase 1 — Fix the published contract.**
IDs: DIV-DOC-01, DIV-A11Y-01. Remove or implement `inset` and repair the list example in both guides; add `role="separator"` + `aria-orientation` with a `decorative` opt-out and strip the five hand-rolled consumer attributes. These are what an external consumer actually hits first, and neither depends on anything below. Ship with Jest ARIA cases and a `yarn run e2e:docs` pass over the corrected snippets.

**Phase 2 — Make the vertical variant usable.**
IDs: DIV-CSS-01, DIV-CSS-02, DIV-STYLE-01. Swap `height: 100%` for `align-self: stretch` plus a height token, flatten the `paddings` specificity, mirror `min-height` with `min-width`. Then delete the three consumer height overrides and the `filter-bar` margin `!important` — the removal of those workarounds is the acceptance criterion, not just the CSS diff. Requires updated Playwright baselines via Docker.

**Phase 3 — Modernize the API surface.**
IDs: DIV-API-01, DIV-API-02. Migrate both accessor pairs to `input({ transform: booleanAttribute })`, drop the CDK coercion import and the false TODOs, add JSDoc to every public member. One `yarn run build:components && yarn run approve-api` cycle covers both. Behaviourally inert if the coercion cases from Phase 4 land first.

**Phase 4 — Close the test and hygiene gaps.**
IDs: DIV-TEST-01, DIV-TEST-02, DIV-DOC-02. Bring the Jest spec from one case to full input/default/coercion coverage, rename and initialize the test host, add the flex-row e2e row that guards DIV-CSS-01, and resolve the dead examples stubs. Best sequenced before Phase 3 in practice — the coercion cases are what makes the signal migration verifiable rather than assumed.

- **Phase 4:** `npx jest packages/components/divider` reports the new cases green; deliberately reverting `[class.kbq-divider_horizontal]` to a constant makes at least one case fail (mutation check — a class-assertion suite that passes against a broken binding is worth nothing).

## Appendix A — Review Methodology

Findings were gathered by reading the complete package (every `.ts`, `.scss`, `.md` file, both screenshots' fixture and spec), then cross-checking each candidate against three independent sources: the workspace compiler settings (`tsconfig.json`), the API guard report (`tools/public_api_guard/components/divider.api.md`), and every in-repo consumer of `<kbq-divider>` found by grep across `packages/` (11 call sites in `actions-panel`, `app-switcher`, `dropdown`, `filter-bar`, `list`, `notification-center`, plus dev apps and docs examples). Consumer evidence is what upgraded DIV-CSS-01 and DIV-A11Y-01 from style opinions to confirmed defects — in both cases the workaround already exists in the tree, written independently by multiple authors. Design tokens were verified as resolvable against `@koobiq/design-tokens/web/new/css-tokens-{light,dark}.css`.

Refuted during verification:
- **"`ViewEncapsulation.None` leaks the divider's styles into consumers"** — refuted. It is the library-wide convention (every sibling component uses it), every rule is namespaced under `.kbq-divider`, and the tokens are scoped to the same class rather than `:root`. No leak surface.
- **"`coerceBooleanProperty` is deprecated and must be replaced"** — refuted as stated. `coerceBooleanProperty` is not deprecated in `@angular/cdk` 20.x; `booleanAttribute` supersedes it stylistically. The real reason to migrate is the accessor→signal move and the missing `ngAcceptInputType_*`, which is why this is folded into DIV-API-01 rather than filed on its own.
- **"`--kbq-divider-color` is undefined and computes to `inherit`"** — refuted. `--kbq-line-contrast-less` is defined in both light and dark token files (`css-tokens-light.css:75`, `css-tokens-dark.css:75`), so the reference resolves. The genuinely dead reference is the *reverse* direction, from `code-block` into the divider's element-scoped token, and is filed under DIV-STYLE-01.
- **"Missing `role` is an AXE failure and therefore a P0 under AGENTS.md"** — refuted as an automated failure. axe-core does not flag a custom element carrying no role; the gap is a WCAG 1.3.1 judgement plus a demonstrable consumer-inconsistency problem. Filed as P1 on those grounds, not P0.

Corrected on verification:
- **DIV-DOC-02** was initially drafted as "the Examples tab is broken for divider", matching the equivalent finding in other packages. `structure.ts:516` sets `hasExamples: false`, so the tab never renders; the impact was narrowed from a broken user surface to two unreachable files, and the severity dropped from P2 to P3.
- **DIV-CSS-01** was initially drafted as "vertical divider may collapse in some layouts". Grepping the consumers showed it collapses in *every* in-repo layout — all three vertical call sites already override the height — so the wording moved from conditional to confirmed and the fix acquired a concrete acceptance test (delete the overrides).
