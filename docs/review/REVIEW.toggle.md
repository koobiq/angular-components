# Koobiq `toggle` Component — Code Review & Improvement Plan

> Scope: `packages/components/toggle` (component, template, tokens, theme, SCSS, Jest spec, e2e fixture + Playwright spec, user guides, examples, dev app, API guard report) and the `KbqCheckable` primitive it is built on · Commit `b665e503` · 2026-08-28
> Generated by a multi-dimension review (architecture, correctness, accessibility, public API/types, styles, tests, docs) with manual verification of every finding against the source, the `KbqCheckbox` sibling, the design-token package, the vendored `axe-core`, `playwright.config.ts` and git history. 17 findings confirmed (P0×0, P1×3, P2×7, P3×7); 6 candidate findings refuted during verification, 2 corrected (see Appendix A). This document is a review + roadmap; no source is modified by it.

---

## 1. Executive Summary

`KbqToggleComponent` is a 329-line form control that renders a visually hidden `<input type="checkbox" role="switch">` inside a `<label>` and paints the switch with three divs. Since `ffb491a51` (`feat(core): extract shared KbqCheckable primitive (#DS-3498)`) it shares state, click resolution and the `ControlValueAccessor` with `kbq-checkbox` through the `KbqCheckable` host directive. There are **no release blockers** — the happy path (click, `[(ngModel)]`, `[formControl]`) works and is covered by 36 Jest cases — but the component has drifted away from its sibling in three places where the drift is a *contract* failure, and the accessibility surface of the two non-default states (indeterminate, loading) is wrong.

- **A published core token silently does nothing.** `KBQ_CHECKABLE_CLICK_ACTION` is exported from `@koobiq/components/core` (`core.api.md:1162`) and documented as "Injection token that can be used to specify the default click behavior for checkable controls" (`checkable.ts:25-26`). `kbq-toggle` is the only place in the repository that ever *reads* it (`toggle.component.ts:196`) — and it also provides it on its own component injector (`toggle.component.ts:55-59`), which shadows any application-level provider and hard-maps the value to the legacy `KBQ_CHECKBOX_CLICK_ACTION`. `kbq-checkbox` never reads it at all (`checkbox.ts:115`). Providing the documented token at the app root therefore has no effect on any component in the library (TGL-API-01).
- **`<kbq-toggle disabled>` renders an enabled control.** The `disabled` accessor pair is typed `any` with no `booleanAttribute` transform (`toggle.component.ts:122-129`), so the static attribute form passes the empty string, which is falsy: the native input stays enabled, the `.kbq-disabled` class is not applied, and `strictTemplates` cannot catch it because the setter accepts `any`. `KbqCheckbox` does have the transform (`checkbox.ts:145-152`), and the difference is visible in the two API reports (`toggle.api.md:47-48` has no `ngAcceptInputType_disabled`; `checkbox.api.md:53` does). The library's own examples use exactly this static-attribute idiom for other inputs (`toggle-label-left-example.ts:12`) (TGL-BUG-01).
- **The documented indeterminate state is announced as "off".** The input carries a hard-coded `role="switch"` (`toggle.component.html:3`) together with `[attr.aria-checked]="getAriaChecked()"`, which returns `'mixed'` when indeterminate (`checkable.ts:90-92`). WAI-ARIA does not support `mixed` on `switch`; user agents fall back to `false`. So the toggle draws the mixed dash while assistive technology reports it as unchecked — for a state the user guide devotes a whole section to (`toggle.en.md:15-19`) (TGL-A11Y-01).
- **`loading` is a half-implemented state.** `onInputClick` bails out before `event.stopPropagation()` and before the native-input resync (`toggle.component.ts:234-267`), so a click during loading reaches ancestor `(click)` handlers twice and leaves `input.checked` desynchronised from the model — which matters because the input carries `name`/`value` and is serialised by native form submission. Meanwhile the control looks disabled (`'[class.kbq-disabled]': 'disabled || loading()'`, `:67`) but keeps `tabIndex=0`, no `disabled`, and no `aria-disabled` (TGL-BUG-02, TGL-A11Y-02).
- **The test suite has one assertion that cannot fail and several that assert the implementation back to itself.** `e2e.playwright-spec.ts:21-34` reads `boundingBox()` once, clicks the "big" switch, then re-asserts the *same two local variables* — the test passes no matter what `[big]` does. In Jest, the disabled-interaction case clicks the host element rather than the label or input (`toggle.component.spec.ts:106-112`), the indeterminate case compares `aria-checked` against the component's own `checked` (`:521-534`), and `loading` is covered only by a CSS-class check (`:566-577`) even though the fixture already has the click spy that would catch TGL-BUG-02 (TGL-TEST-01, TGL-TEST-02).

Genuine strengths worth preserving: the migration to the shared `KbqCheckable` primitive is well executed and well commented (`toggle.component.ts:56-58`, `:205-207`, `:321`), the deprecated `ControlValueAccessor` shims carry honest `@deprecated` notes rather than being silently deleted, styling is fully token-driven with a dedicated `-tokens.scss` and `_-theme.scss` pair and zero hardcoded colours, `ViewEncapsulation.None` + `OnPush` + host-object bindings follow the repo conventions with no `@HostBinding`/`ngClass`/`*ngIf`, the DOM order puts the focusable input first inside a real `<label for>` (so label association is correct without any ARIA), and the e2e fixture covers 2 colours × 5 states × 2 checked values in light and dark.

## 3. Prioritized Findings (deduplicated, verified)

### P0 — Release blockers

None.

### P1 — High

**TGL-API-01 · The published `KBQ_CHECKABLE_CLICK_ACTION` token is shadowed by the component's own provider and has no effect anywhere** — `toggle.component.ts:55-59, 196`, `core/common-behaviors/checkable.ts:25-26`, `checkbox/checkbox.ts:115`, `tools/public_api_guard/components/core.api.md:1162`.
`KBQ_CHECKABLE_CLICK_ACTION` is public API and its JSDoc says it "can be used to specify the default click behavior for checkable controls" (`checkable.ts:25-26`). A repo-wide grep finds exactly three occurrences outside its own declaration, all inside `toggle.component.ts`: the import (`:24`), a component-level provider (`:58`) and the field initializer that reads it (`:196`). The provider is the problem — `providers: [{ provide: KBQ_CHECKABLE_CLICK_ACTION, useFactory: () => inject(KBQ_CHECKBOX_CLICK_ACTION, { optional: true }) }]` sits on the `<kbq-toggle>` node injector, which is the *first* injector consulted when the component's own field initializer runs `inject(KBQ_CHECKABLE_CLICK_ACTION, { optional: true })`. An application that provides `{ provide: KBQ_CHECKABLE_CLICK_ACTION, useValue: 'noop' }` at the root is therefore never reached: every toggle resolves its own provider, which reads only the legacy `KBQ_CHECKBOX_CLICK_ACTION`. `KbqCheckbox` makes the mismatch complete by reading `KBQ_CHECKBOX_CLICK_ACTION` directly (`checkbox.ts:115`) and never consulting the checkable token at all. Net effect: the token the core package advertises as the shared configuration point configures nothing, in either component. The existing spec (`toggle.component.spec.ts:537-563`) only ever provides `KBQ_CHECKBOX_CLICK_ACTION`, which is why the shadowing is invisible to CI.
**Fix:** delete the component-level provider (`toggle.component.ts:55-59`) and resolve the fallback chain in the field initializer instead — `inject(KBQ_CHECKABLE_CLICK_ACTION, { optional: true }) ?? inject(KBQ_CHECKBOX_CLICK_ACTION, { optional: true }) ?? undefined` — so an app-level `KBQ_CHECKABLE_CLICK_ACTION` wins and `KBQ_CHECKBOX_CLICK_ACTION` remains a backwards-compatible fallback; make `KbqCheckbox` read the same chain so the two siblings agree. Add two specs: one providing only `KBQ_CHECKABLE_CLICK_ACTION: 'noop'` at the TestBed root and asserting a label click does not toggle, and one providing both tokens and asserting the checkable token wins.

**TGL-BUG-01 · `disabled` and `checked` have no boolean coercion, so the static-attribute form is silently inert** — `toggle.component.ts:120-129, 146-154`, `toggle.component.html:12-13`, `tools/public_api_guard/components/toggle.api.md:47-48`.
`@Input() set disabled(value: any)` stores whatever it receives straight into the `KbqCheckable.disabled` model (`toggle.component.ts:127-129`). Written as a static attribute, `<kbq-toggle disabled>` passes the empty string; `''` is falsy, so `[disabled]="disabled"` leaves the native input enabled (`toggle.component.html:13`), `'[class.kbq-disabled]': 'disabled || loading()'` evaluates to `false` (`:67`), and `effectiveTabIndex` keeps the control in the tab order (`checkable.ts:87`). The control is fully interactive while the markup says it is disabled. `checked` has the same shape (`toggle.component.ts:148-154`): `<kbq-toggle checked>` sets the model to `''`, `getAriaChecked()` returns `'false'`, and nothing turns on. Two things make this worse than ordinary type sloppiness: the setter is typed `any`, so `strictTemplates` (`tsconfig.json:117`) raises nothing and no `ngAcceptInputType_disabled` is generated (contrast `checkbox.api.md:53`); and the sibling component does it correctly — `KbqCheckbox` declares `@Input({ transform: booleanAttribute }) disabled: boolean` (`checkbox.ts:145-152`), as does the toggle's own `indeterminate` (`:164`) and `loading` (`:183`). `git show ffb491a51^:packages/components/toggle/toggle.component.ts` shows `set disabled(value: any)` predates the `KbqCheckable` refactor, so this is long-standing debt rather than a regression. The static-attribute idiom is not hypothetical here: the shipped docs example writes `<kbq-toggle labelPosition="left">` (`toggle-label-left-example.ts:12-14`).
**Fix:** add `transform: booleanAttribute` to both accessor inputs (`@Input({ transform: booleanAttribute })` on `disabled` and on `checked`) and narrow the setter parameter types from `any` to `boolean`; the getter for `disabled` should return `boolean`, which also removes the `any` from the API report. Rebuild and `approve-api` — `ngAcceptInputType_disabled`/`_checked` will appear. Guard with specs that render `<kbq-toggle disabled>` and `<kbq-toggle checked>` from static markup and assert `input.disabled === true` / `input.checked === true` and the corresponding host classes.

**TGL-A11Y-01 · `role="switch"` combined with `aria-checked="mixed"` makes the documented indeterminate state announce as "off"** — `toggle.component.html:2-7, 15`, `core/common-behaviors/checkable.ts:90-92`, `toggle.component.ts:76`, `toggle.en.md:15-19`.
The hidden input hard-codes `role="switch"` (`toggle.component.html:3`) and binds `[attr.aria-checked]="getAriaChecked()"` (`:7`), where `getAriaChecked()` returns `'mixed'` whenever `indeterminate` is set (`checkable.ts:90-92`). WAI-ARIA's `switch` role explicitly does not support the `mixed` value — unlike `checkbox`, which it otherwise inherits from — and user agents treat the invalid value as `false`. Visually the component switches to its mixed rendering (the `@switch` animation hides the circle and the theme shows the dash, `toggle.component.ts:76` + `toggle.scss:77-97`), so a sighted user sees "partially on" while a screen-reader user is told the switch is off. Note that the explicit `role="switch"` is what causes this: the underlying `<input type="checkbox">` also receives `[indeterminate]="indeterminate"` (`toggle.component.html:15`), and the native checkbox role *does* map indeterminate to `mixed` correctly. The state is a first-class documented feature — `toggle.en.md:15-19` / `toggle.ru.md:15-19` give it its own section and a live example (`toggle-indeterminate-example.ts:11`) — while the same guide's recommendations tell readers not to use a toggle for anything that is not binary (`toggle.en.md:44`), so the guide is internally inconsistent about whether the state should exist at all. This is a WCAG 4.1.2 (Name, Role, Value) judgement, **not** an automated AXE failure: the vendored `axe-core` is 3.5.6 and its `valid-attr-value` check validates `aria-checked` against the attribute's own value list without consulting the element's role (`node_modules/axe-core/lib/checks/aria/valid-attr-value.js:52-65`), so nothing in CI flags it.
**Fix:** make the role conditional — `[attr.role]="indeterminate ? null : 'switch'"` — so the element falls back to its native `checkbox` role while mixed, where `aria-checked="mixed"` is valid and the native `indeterminate` property already agrees; keep `role="switch"` for the binary states. If the design team confirms indeterminate should not exist on a switch at all, the alternative is to deprecate the `indeterminate` input on `kbq-toggle` (behind an `ng-update` migration) and resolve the guide's self-contradiction in the same change. Guard with a spec asserting `role` is absent and `aria-checked === 'mixed'` while indeterminate, and `role === 'switch'` with `aria-checked === 'true'|'false'` otherwise, and extend the Playwright indeterminate case to cover dark theme too.

### P2 — Should fix

**TGL-BUG-02 · The `loading` early-return skips `stopPropagation()` and the native-input resync** — `toggle.component.ts:234-267`, `toggle.component.html:1-20`, `core/common-behaviors/checkable.ts:116-120`.
`onInputClick` opens with `if (this.loading()) return;` (`:235`), *before* the `event.stopPropagation()` at `:243` whose seven-line comment (`:236-242`) explains precisely why it is needed: the root container is a `<label>`, so a user click produces both the real click and the label-generated click on the input, and without the guard both bubble out of `<kbq-toggle>`. While `loading` is true that guard is gone, so every ancestor `(click)` handler — and the component's own consumers, e.g. `packages/components-dev/input/template.html:5` — fires twice per click. The early return also skips the `else if (!this.disabled) { this.checkable.resetNativeInput(...) }` branch (`:263-267`), which exists exactly to undo the browser's default activation when the component declines to toggle. So a click or Space press during loading leaves `input.checked === true` while `checked` stays `false`; because the `[checked]="checked"` binding did not change, Angular never rewrites the property, and the input keeps the wrong DOM state. That input carries `[attr.name]` and `[attr.value]` (`toggle.component.html:10-11`), so a native `<form>` submission during the loading window serialises a value the component says is off. Nothing prevents the click either: the shared `.kbq-progress` utility only paints a shimmer overlay and sets no `pointer-events` (`core/styles/common/_animation.scss:51-61`). The documented loading example holds the state for three seconds (`toggle-loading-example.ts:23-29`), which is a wide enough window to hit by hand.
**Fix:** move the `loading()` check below `event.stopPropagation()`, and fold it into the decision instead of short-circuiting — e.g. treat `loading()` like `disabled` in `resolveClick` by passing `'noop'`, so the existing reset branch runs: `const { shouldToggle, shouldClearIndeterminate } = this.checkable.resolveClick(this.loading() ? 'noop' : this.clickAction);`. Add a spec on the existing `LoadingToggle` fixture (`toggle.component.spec.ts:580-603`) that sets `loading = true`, clicks the label, and asserts `onToggleClick` fired once, `checked` is unchanged and `inputElement.checked === false`.

**TGL-BUG-03 · `onTouched` never fires on focus or blur, so a form control the user tabs past stays untouched** — `toggle.component.ts:210-216, 257`, `checkbox/checkbox.ts:212-216, 342-346`, `toggle.component.spec.ts:393-402`.
`KbqCheckable` is the registered `ControlValueAccessor` (`checkable.ts:10-14, 62`) and stores the forms callback in `onTouched` (`:140-142`). The toggle invokes it in exactly one place: inside `onInputClick`, and only on the `shouldToggle` branch (`toggle.component.ts:257`). It monitors focus (`focusMonitor.monitor(this.elementRef.nativeElement, true)`, `:211`) purely for the `.cdk-keyboard-focused` styling hook and never subscribes to the returned stream. Consequences: tabbing into the control and out again leaves the control `untouched`, as does clicking it while `clickAction: 'noop'` or while `loading`. Angular's convention — and this repo's own implementation in the sibling — is to mark touched on interaction with the field regardless of whether the value changed: `KbqCheckbox` subscribes to its focus monitor and calls `this.checkable.onTouched()` for any non-null origin (`checkbox.ts:212-216, 342-346`). A form containing both controls therefore computes `touched` inconsistently, and any validation UI keyed on `touched` never appears for a toggle the user visited but did not flip. The spec only asserts the *initial* untouched state (`toggle.component.spec.ts:393-402`); nothing asserts the transition.
**Fix:** subscribe in `ngAfterViewInit` the way the checkbox does — `this.focusMonitor.monitor(this.elementRef.nativeElement, true).pipe(takeUntilDestroyed(this.destroyRef)).subscribe((origin) => { if (origin) this.checkable.onTouched(); })` — keeping the existing `stopMonitoring` teardown. Better still, move the subscription into `KbqCheckable` so both hosts inherit it and the duplication disappears. Guard with a spec that focuses the input via `FocusMonitor.focusVia(input, 'keyboard')`, blurs it, and asserts `ngModel.touched === true` without the value having changed.

**TGL-A11Y-02 · While `loading` the control looks and behaves disabled but reports itself as enabled** — `toggle.component.ts:67, 183, 235`, `toggle.component.html:13, 16, 22`, `toggle.scss:130-132`.
`loading` drives three visual affordances — the host gets `.kbq-disabled` (`toggle.component.ts:67`), which removes `cursor: pointer` (`toggle.scss:130-132`) and applies the disabled palette (`_toggle-theme.scss:51-53`), and the bar gets the `.kbq-progress` shimmer (`toggle.component.html:22`) — and one behavioural block (`toggle.component.ts:235`). None of it reaches the accessibility tree: the input's `[disabled]` binding is driven by `disabled` alone (`toggle.component.html:13`), `tabIndex` comes from `effectiveTabIndex`, which only reacts to `disabled` (`checkable.ts:87`), and there is no `aria-disabled` or `aria-busy` anywhere in the template. A screen-reader user therefore encounters a focusable switch that announces as operable, activates it, and gets no state change and no feedback. This is the same "looks disabled but is not" gap as TGL-BUG-02, seen from the ARIA side, and it is the closest the component comes to a read-only state — there is no `readonly` input on `kbq-toggle` (nor on its siblings), so `loading` is the only non-editable-but-visible mode the component offers.
**Fix:** bind `[attr.aria-disabled]="disabled || loading() ? 'true' : null"` and `[attr.aria-busy]="loading() ? 'true' : null"` on the input, and rename the host class binding so the visual disabled state and the semantic one cannot drift (e.g. keep `'[class.kbq-disabled]': 'disabled || loading()'` but add a distinct `'[class.kbq-toggle_loading]': 'loading()'` for anything loading-specific). Do **not** set the native `disabled` while loading — that would move focus off the control mid-interaction. Cover with a spec asserting `aria-disabled`/`aria-busy` toggle with `[loading]` while `input.disabled` stays `false`, and extend the e2e fixture's existing `loading` column (`e2e.ts:59`) with an assertion-based Playwright case.

**TGL-A11Y-03 · Enter activates the switch without preventing the browser default, so inside a `<form>` the same keystroke also submits** — `toggle.component.html:19`, `toggle.component.spec.ts:647-651`.
`(keydown.enter)="input.click()"` is bound directly on the native input (`toggle.component.html:19`). It exists because a native checkbox does not respond to Enter, only to Space — but the handler calls `click()` and returns without touching the event, so the browser's implicit form submission on Enter still runs. In an enclosing `<form>` (the shape the spec's own `ToggleWithFormDirectives` host uses, `toggle.component.spec.ts:647-651`, and the shape a settings page uses) pressing Enter on a toggle both flips it and submits the form, which is not what either the WAI-ARIA switch pattern or the native control does. The keystroke also routes through `onInputClick`, so while `loading` it hits TGL-BUG-02's desync path as well.
**Fix:** take the event and stop the default — `(keydown.enter)="$event.preventDefault(); input.click()"`, or move the handler into the class as `onEnterKeydown(event: KeyboardEvent)` so the intent is documented. Add a spec that dispatches `keydown.enter` on a toggle inside a `<form>` and asserts the toggle flipped while the form's `(ngSubmit)` spy was not called.

**TGL-A11Y-04 · The projected `kbq-hint` is inside the `<label>`, so the whole hint becomes part of the switch's accessible name** — `toggle.component.html:1, 28-38`, `toggle-multiline-example.ts:15-24`.
The root `<label [attr.for]="inputId">` wraps everything, including `<ng-content select="kbq-hint" />` (`toggle.component.html:37`). Because the label is associated with the input, its entire text content contributes to the input's accessible name — so the hint is announced as part of the name rather than as a description. The shipped `toggle-multiline` example makes the consequence concrete: the hint is a full sentence with inline markup (`toggle-multiline-example.ts:18-22`, six lines of prose and two `<span>`s), which becomes the name of a switch whose actual label is the two words above it. Providing `[aria-labelledby]` does not help: it replaces the name but leaves the hint unassociated entirely, so the description is then lost rather than merely misplaced. Note this is a shared pattern — `checkbox.html:30-36` has the same structure — so the fix belongs in both packages, but the toggle is where the library's own documentation ships the long-hint variant.
**Fix:** give the hint wrapper a generated id (`[id]="inputId + '-hint'"`) and bind `[attr.aria-describedby]` on the input to it when a hint is projected; then either move the hint outside the `<label>` (keeping the layout with grid/flex ordering) or leave it in place and mark it `aria-hidden="true"` for the name computation while `aria-describedby` supplies the description. Guard with a spec asserting the input's `aria-describedby` points at the hint element and that the computed label text excludes the hint.

**TGL-TEST-01 · The Playwright "should have correct size" test cannot fail** — `packages/components/toggle/e2e.playwright-spec.ts:21-34`.
```ts
const { width, height } = (await getFirstToggle(component).boundingBox()) ?? {};
expect(width).toBe(28);
expect(height).toBe(16);
await getBigToggle(component).click();
expect(width).toBe(28);
expect(height).toBe(16);
```
`width` and `height` are plain locals destructured once; clicking the "big" checkbox cannot change them, so the second pair of assertions re-checks values already asserted and proves nothing about `[big]`. It is the only assertion-based (non-screenshot) case in the suite, and it happens to be the one covering the input whose CSS is dead (TGL-CSS-01) — so the suite gives false confidence in exactly the place where the implementation is questionable. The `indeterminate` case (`:36-43`) is also light: unlike the other two screenshot cases it captures light theme only.
**Fix:** re-measure after the click (`const after = await getFirstToggle(component).boundingBox()`) and assert against the intended big dimensions — after TGL-CSS-01 decides what those are. Add the dark-theme capture to the `indeterminate` case for parity with `states`. Regenerate baselines only via `yarn run e2e:docker:update-snapshots`.

**TGL-TEST-02 · Three Jest cases assert the implementation back to itself or nothing at all, and the highest-risk paths are untested** — `toggle.component.spec.ts:19, 106-112, 521-534, 566-577, 610-611, 630-631`.
The suite has 36 cases across 15 `describe` blocks, but several do not test what their names claim. *(a)* "should not toggle `checked` state upon interaction while disabled" (`:106-112`) calls `toggleNativeElement.click()` — a click dispatched on the `<kbq-toggle>` host itself. Clicks do not propagate downward, and label activation only fires for clicks inside the `<label>`, so the input's handler never runs; the assertion would hold even if `disabled` were completely broken. *(b)* "should change from indeterminate to checked on input click" (`:521-534`) ends with `expect(innerInput.attributes['aria-checked']).toBe(fixture.componentInstance.toggle().checked.toString())` — it compares the rendered attribute against the component's own state, so both being wrong together still passes, and it never asserts `checked === true` or `indeterminate === false`. *(c)* The `loading` block (`:566-577`) asserts only that the class named by `const toggleLoadingCssClass = 'kbq-disabled'` (`:19`) is present — the same class `disabled` produces — and never that a click is ignored, which is why TGL-BUG-02 survived. Finally, the `SingleToggle` host already carries the scaffolding that would catch the double-click bug — a wrapper `<div (click)="parentElementClicked = true" (keyup)="parentElementKeyedUp = true">` (`:610`) and the two fields (`:630-631`) — but no test ever reads either field. Nothing covers `[big]`, `labelPosition="right"`, `indeterminateChange`, `touched`, or `KBQ_CHECKABLE_CLICK_ACTION`.
**Fix:** drive (a) through `labelElement.click()` or `inputElement.click()`; make (b) assert the literal `'true'` plus `toggle().checked === true` and `toggle().indeterminate === false`; give (c) a behavioural case (see TGL-BUG-02) and drop the misleading `toggleLoadingCssClass` alias. Either assert `parentElementClicked` in the double-click test or delete the dead fields and handlers. Add cases for `indeterminateChange` emission on click, `touched` after blur, and the click-action token chain.

### P3 — Nice to have / hygiene

**TGL-ARCH-01 · The component keeps a private copy of the `TransitionCheckState` machine that `KbqCheckable` already provides** — `toggle.component.ts:191, 306-318`, `core/common-behaviors/checkable.ts:75, 122-127`, `checkbox/checkbox.ts:184, 304`.
`KbqCheckable` exposes `currentCheckState` as a signal and `transitionCheckState()` with the no-op guard (`checkable.ts:75, 122-127`), and `KbqCheckbox` uses them (`checkbox.ts:184, 304`). `kbq-toggle` instead declares `protected currentCheckState: TransitionCheckState` as a plain field (`toggle.component.ts:191`) and reimplements the identical guard privately (`:314-318`), then needs the constructor `effect()` (`:207`) to keep the field in step with the signals it duplicates. The result is one state machine written twice, only one of which is a signal, and the animation state is exposed as `protected` in the API report (`toggle.api.md:45`) where the checkbox's is not. The primitive was extracted for exactly this in `ffb491a51`.
**Fix:** delete the local field and the private `transitionCheckState`, bind `[@switch]="checkable.currentCheckState()"` (or expose a `protected readonly currentCheckState = this.checkable.currentCheckState` alias), and route `setTransitionCheckState()` through `this.checkable.transitionCheckState(...)` as the checkbox does. The constructor `effect()` can then stay as the form-driven sync point, or be dropped if the setters already cover every write path. Requires `approve-api` (the `protected currentCheckState` line disappears).

**TGL-ARCH-02 · `toggle` is the only production file in the library that imports another component's entry point** — `toggle.component.ts:22`, `checkbox/checkbox-config.ts:11-16`.
`import { KBQ_CHECKBOX_CLICK_ACTION } from '@koobiq/components/checkbox'` (`toggle.component.ts:22`) exists solely to read one legacy `InjectionToken`. A repo-wide grep for `@koobiq/components/checkbox` outside the checkbox package returns seven hits: six are `e2e.ts` fixtures, and this one. Every consumer of `@koobiq/components/toggle` therefore pulls the entire checkbox entry point — component, template, styles, required-validator — into its dependency graph for a token that is 16 lines of code. The token's own type already lives in core (`checkbox-config.ts:11` re-exports `KbqCheckableClickAction` from `@koobiq/components/core`).
**Fix:** together with TGL-API-01, move the backwards-compatibility fallback out of the toggle: re-declare `KBQ_CHECKBOX_CLICK_ACTION` as a deprecated alias inside `core/common-behaviors/checkable.ts` (re-exported from the checkbox entry point for source compatibility) so the toggle can read both tokens without importing a sibling package. Verify with `yarn run build:components` that the toggle bundle no longer references the checkbox entry point.

**TGL-API-02 · Type and API-surface hygiene in the public report** — `tools/public_api_guard/components/toggle.api.md:20-25, 47-48, 62-65, 83-95`, `toggle.component.ts:36, 38-41, 118, 270-304`.
Four issues, all visible in the generated report. *(a)* `ToggleLabelPositionType` is declared but not exported (`toggle.component.ts:36`), producing the `ae-forgotten-export` warning at `toggle.api.md:62-65`; consumers cannot name the type of `labelPosition`. *(b)* `get disabled(): any / set disabled(value: any)` (`:47-48`) leaks `any` into the public surface — fixed by TGL-BUG-01. *(c)* `value` is declared `input<string>(undefined!)` (`toggle.component.ts:118`), so the published type says `InputSignal<string>` (`:93`) while the runtime default is `undefined`; the non-null assertion papers over a type that should be `string | undefined`. *(d)* `KbqToggleChange` is an undocumented class with two mutable public fields and no constructor (`toggle.component.ts:38-41`, `toggle.api.md:20-25`), and the four `@deprecated` CVA shims (`writeValue`, `registerOnChange`, `registerOnTouched`, `setDisabledState`, `toggle.component.ts:270-304`) remain public with no removal target named beyond "the next major version".
**Fix:** export `ToggleLabelPositionType` (and consider `'before' | 'after'` for parity with `KbqCheckbox`'s `labelPosition`, behind an `ng-update` migration); type `value` as `input<string | undefined>(undefined)`; convert `KbqToggleChange` to a readonly-field class or an interface and give it JSDoc; record the removal version for the deprecated shims in the changelog and schedule their deletion. All of these change `toggle.api.md`, so build first, then `approve-api`.

**TGL-CSS-01 · The `.kbq-toggle_big` size override is a no-op and one declared token is never referenced** — `toggle-tokens.scss:2-7`, `toggle.scss:100-128`, `node_modules/@koobiq/design-tokens/web/new/css-tokens.css:1314-1319`.
`--kbq-toggle-size-big-height` and `--kbq-toggle-size-normal-height` are both `var(--kbq-size-l)` and `--kbq-toggle-size-big-width` and `--kbq-toggle-size-normal-width` are both `28px` (`toggle-tokens.scss:2-6`), so the `.kbq-toggle.kbq-toggle_big .kbq-toggle-bar { height; width }` block (`toggle.scss:117-121`) resolves to exactly the values it overrides. The upstream token package agrees — it ships only the height tokens, both mapped to `--kbq-size-l` (16px) (`css-tokens.css:1316, 1319`) — so `[big]` changes only typography and the vertical alignment padding (`_toggle-theme.scss:93-116`, `toggle.scss:123-127`), never the switch itself. Separately, `--kbq-toggle-size-big-horizontal-content-padding` is declared (`toggle-tokens.scss:7`) but never read: both `.kbq-toggle__content` margin rules use the *normal* token (`toggle.scss:108, 112`) and there is no big-specific override. Finally, `.kbq-toggle__content` is declared at the top level rather than nested under `.kbq-toggle` (`toggle.scss:100`), and with `ViewEncapsulation.None` that selector applies to any element carrying the class anywhere in the app.
**Fix:** decide with design whether `big` should change the switch dimensions. If not, delete the `.kbq-toggle_big` size block (`toggle.scss:117-121`) and the two big size tokens, and rename the remaining ones without the `normal` infix; if yes, set real values in `toggle-tokens.scss` and fix the Playwright assertion (TGL-TEST-01) to prove them. Either way, reference the big content-padding token from a `.kbq-toggle_big .kbq-toggle__content` rule or delete it, and nest `.kbq-toggle__content` under `.kbq-toggle`.

**TGL-CSS-02 · The switch's own motion has no `prefers-reduced-motion` guard, and the Playwright suite cannot detect that** — `toggle.component.ts:72-91`, `toggle.scss:56, 69`, `core/styles/common/_animation.scss:57-59`, `playwright.config.ts:101`.
Three things move: the Angular `switch` trigger animates the circle's `left` between states (`toggle.component.ts:72-91`), the bar transitions `background` over 100 ms (`toggle.scss:56`), and the indeterminate thumb transitions `left` over 50 ms on hover and keyboard focus (`toggle.scss:69`, driven by `:77-97`). None is wrapped in `@media (prefers-reduced-motion: reduce)` — the only such guard in the component's dependency chain belongs to the shared loading shimmer (`_animation.scss:57-59`). Angular's animation engine does not consult the media query on its own, so a user with reduced motion enabled still gets the sliding thumb. This is WCAG 2.3.3 (AAA), so it is hygiene rather than an AA failure, but it is worth noting that the visual suite cannot help: `playwright.config.ts:101` sets `reducedMotion: 'reduce'` for every context, which only flips the media query — so every committed baseline under `__screenshots__` was captured with the shimmer frozen and the thumb motion fully active, and a regression in either direction would look identical.
**Fix:** wrap the two CSS transitions in `@media (prefers-reduced-motion: reduce) { transition: none; }` and gate the Angular trigger — either inject `KBQ_WINDOW` and check `matchMedia('(prefers-reduced-motion: reduce)')` to pick a zero-duration animation, or move the circle's movement to CSS so a single media query covers all three. Since the baselines already run under `reducedMotion: 'reduce'`, add one Playwright case that asserts the computed `transition-duration` is `0s` in that context.

**TGL-STYLE-01 · Redundant `[id]`/`[attr.id]` host bindings, and an empty `id` leaks onto the host** — `toggle.component.ts:65-66, 110-114`, `toggle.component.spec.ts:119-125`.
The host block binds the same expression twice — `'[id]': 'id'` sets the DOM property and `'[attr.id]': 'id'` sets the attribute (`toggle.component.ts:65-66`); one of them is enough, and `KbqCheckbox` carries the same duplication (`checkbox.ts:73-74`), so it is copy-paste rather than intent. The pair also behaves inconsistently with `inputId`: the getter falls back to the generated `uniqueId` when `id` is empty (`toggle.component.ts:112-114`), but the host bindings do not, so `<kbq-toggle [id]="''">` renders `<kbq-toggle id="">` while its input gets `kbq-toggle-N-input`. The spec exercises exactly this path (`toggle.component.spec.ts:119-125`) but only asserts the input's id.
**Fix:** keep a single binding (`'[attr.id]': 'id || uniqueId'`) and drop the other, so the host and the input derive their ids from the same expression; extend the existing spec to assert the host id as well.

**TGL-DOC-01 · Dead example stubs, a self-contradicting section heading, and undocumented inputs** — `examples.toggle.en.md:1-5`, `examples.toggle.ru.md:1-5`, `apps/docs/src/app/structure.ts:1089-1100`, `toggle.en.md:31-39`, `toggle.ru.md:31-39`, `packages/components-dev/all/template.html:1157-1233`, `packages/components-dev/toggle/template.html:24-27`.
`examples.toggle.en.md` and `.ru.md` are both the "🚧 Documentation in progress 🚧" placeholder, but the docs entry sets `hasExamples: false` (`structure.ts:1099`), so the Examples tab never renders and the two files are simply dead — a cleanup item, not a broken user surface. The guide itself has a real inconsistency: the section headed "Label on the right" / "Подпись справа" (`toggle.en.md:31`, `toggle.ru.md:31`) opens by saying the *toggle* is placed to the right of the label, and both of its examples use `labelPosition="left"` (`toggle-multiline-example.ts:15`, `toggle-label-left-example.ts:12-14`) — the heading names the wrong element. Neither guide documents `big`, `labelPosition`, `clickAction`, `aria-label`/`aria-labelledby`, `name`/`value` or the `change`/`indeterminateChange` outputs; readers get only the API tab generated from the (largely `(undocumented)`) report. The dev apps have rotted alongside: `packages/components-dev/all/template.html` applies `class="kbq-toggle_small"` ten times (`:1157` onward) although no such class exists anywhere in the SCSS (only `.kbq-toggle_big`, `toggle.scss:117`), and the toggle dev app's "Normal" column opens with `<kbq-toggle [big]="true">` (`packages/components-dev/toggle/template.html:24-27`).
**Fix:** delete both `examples.toggle.*.md` stubs (or populate them and flip `hasExamples` to `true` — eight examples already exist under `packages/docs-examples/components/toggle/`); rename the section to "Label on the left" / "Подпись слева" in both guides, or reword the body to match; add short prose for `big`, `labelPosition`, `clickAction` and the ARIA inputs. In the dev apps, remove the dead `kbq-toggle_small` class and move the stray `[big]` toggle into the "Big Toggles" column.

## 4. Recommended Remediation Phases

**Phase 1 — Contract repairs.**
IDs: TGL-API-01, TGL-BUG-01, TGL-ARCH-02. Unshadow `KBQ_CHECKABLE_CLICK_ACTION`, delete the component-level provider, move the legacy-token fallback into core so the sibling-package import disappears, and add `booleanAttribute` to `disabled`/`checked`. These are the two published contracts that are currently untrue, and both fixes are small and independently testable. Requires `build:components` + `approve-api` (the `any` accessors and the new `ngAcceptInputType_*` entries change the report). No user-visible behaviour regresses; apps relying on the old falsy-empty-string behaviour of `<kbq-toggle disabled>` were already broken.

**Phase 2 — Interaction and state correctness.**
IDs: TGL-BUG-02, TGL-BUG-03, TGL-A11Y-03. Fold `loading` into `resolveClick` so the reset branch runs and `stopPropagation` is never skipped; subscribe the focus monitor so `onTouched` fires on blur; prevent the Enter default. All three land with behavioural specs on fixtures that already exist. Depends on nothing in Phase 1 but should follow it so the click-action refactor lands first.

**Phase 3 — Accessibility of the non-default states.**
IDs: TGL-A11Y-01, TGL-A11Y-02, TGL-A11Y-04. Make the `switch` role conditional on `indeterminate`, expose `aria-disabled`/`aria-busy` for `loading`, and split the hint out of the accessible name via `aria-describedby`. TGL-A11Y-01 needs a design decision (keep the mixed state or deprecate it), so start that conversation at the beginning of the phase; TGL-A11Y-04 should be applied to `kbq-checkbox` in the same change since the template shape is shared.

**Phase 4 — Tests and dead weight.**
IDs: TGL-TEST-01, TGL-TEST-02, TGL-ARCH-01, TGL-CSS-01, TGL-CSS-02, TGL-API-02, TGL-STYLE-01, TGL-DOC-01. Fix the tautological Playwright assertion and the three hollow Jest cases, adopt `KbqCheckable.currentCheckState`, resolve the `big` sizing question and remove whichever half is dead, add the reduced-motion guards, tidy the API surface and the ids, and clean the docs and dev apps. Screenshot baselines only via `yarn run e2e:docker:update-snapshots`.

## 5. Verification Strategy

General gates (after every phase, run sequentially — never in parallel with another agent's build):
- `npx jest packages/components/toggle` plus `npx jest packages/components/core/common-behaviors/checkable.spec.ts` and `npx jest packages/components/checkbox` — the shared primitive means a toggle change can break the checkbox.
- `yarn run eslint` and `yarn run stylelint` and `yarn run prettier` on the touched files.
- `yarn run build:components`, then `yarn run check-api`; `approve-api` only in Phases 1 and 4, where the surface intentionally changes.
- `yarn run dev:toggle` for a manual smoke pass (the template covers `[formControl]`, both label positions, hints, fixed-width and fill layouts).
- Anything visual: `yarn run e2e:docker`, never a native Playwright run — the baselines are Linux at `threshold: 0`.

Per-phase assertions:
- **Phase 1:** a TestBed that provides only `{ provide: KBQ_CHECKABLE_CLICK_ACTION, useValue: 'noop' }` at the root produces a toggle that does not flip on click; providing both tokens lets the checkable one win; `<kbq-toggle disabled>` written as static markup renders `input.disabled === true` and the host carries `.kbq-disabled`. `check-api` shows `disabled: boolean` and new `ngAcceptInputType_disabled`/`_checked` lines and nothing else unexpected. `build:components` output for the toggle entry point no longer references `@koobiq/components/checkbox`.
- **Phase 2:** with `[loading]="true"`, one label click fires the consumer's `(click)` handler exactly once, leaves `checked` unchanged and leaves `inputElement.checked === false`; focusing and blurring without activating flips `ngModel.touched` to `true`; `keydown.enter` inside a `<form>` flips the toggle while `(ngSubmit)` is not called.
- **Phase 3:** while `indeterminate`, the input has no `role` attribute and `aria-checked === 'mixed'`; otherwise `role === 'switch'` and `aria-checked` is `'true'`/`'false'`. While `loading`, `aria-disabled === 'true'` and `aria-busy === 'true'` with `input.disabled === false`. The input's `aria-describedby` resolves to the hint element, and the accessible name computed from the label excludes the hint text. Run an AXE pass over the dev-app page in all three states.
- **Phase 4:** the Playwright size case measures *after* the `big` click and the assertion fails if the override is removed without updating it; the three rewritten Jest cases fail when the corresponding behaviour is deliberately broken (mutate `onInputClick`'s disabled guard and confirm the disabled case now goes red); `grep -rn "kbq-toggle_small" packages/` returns nothing; both `examples.toggle.*.md` are gone or the docs Examples tab renders the eight examples in both locales.

## Appendix A — Review Methodology

Every file in `packages/components/toggle` was read in full, then cross-checked against four external surfaces: the `KbqCheckable` primitive and its spec in `packages/components/core/common-behaviors/`, the `KbqCheckbox` sibling (which shares the primitive and is the natural control for "is this divergence intentional?"), the generated API reports for `toggle`, `checkbox` and `core`, and the live design-token set in `node_modules/@koobiq/design-tokens/web/new/`. Consumers were enumerated with `grep -rn "kbq-toggle" --include="*.html" --include="*.ts" packages/` (39 call sites, all in dev apps, e2e fixtures and docs examples — the toggle has no in-library consumers), and `grep -rn "KBQ_CHECKABLE_CLICK_ACTION"` across `packages/` and `apps/` established that TGL-API-01's token is read in exactly one place. Severity follows the repo's shared scale; `git log --oneline -15 -- packages/components/toggle/` (15 commits, of which `ffb491a51`, `ca4d8c98d` and `0787063a2` are the substantive ones) was used to date the divergences rather than to infer them.

Refuted during verification:
- **"`setDisabledState` is not implemented, so `formControl.disable()` does nothing."** — It is implemented, twice. The registered `ControlValueAccessor` is `KbqCheckable` (`checkable.ts:10-14, 62`), whose `setDisabledState` sets the `disabled` model (`:145-147`); the toggle's own copy (`toggle.component.ts:302-304`) is honestly marked `@deprecated Unused`. `toggle.component.spec.ts:452-466` proves the reactive-forms path works end to end.
- **"The toggle should expose a `readonly` input like other form controls."** — Not a defect. Neither `kbq-checkbox` nor `kbq-radio` has one; the library's convention for a non-editable checkable is `disabled`, and `loading` covers the transient case. What *is* wrong is that `loading` does not surface itself to assistive technology — filed as TGL-A11Y-02 instead of a feature request.
- **"`focusMonitor.monitor()` in `ngAfterViewInit` leaks because nothing unsubscribes."** — `monitor()` registers the element and returns a stream; the toggle never subscribes, so there is no subscription to leak, and `stopMonitoring(this.elementRef.nativeElement)` in `ngOnDestroy` (`toggle.component.ts:215`) releases the registration on the same element it monitored. The real defect is the *missing* subscription, filed as TGL-BUG-03.
- **"The `change` output double-fires because the native `change` event also bubbles out of the hidden input."** — `onChangeEvent` stops it (`toggle.component.ts:226-228`) and `toggle.component.spec.ts:157-171` asserts exactly one emission per label click.
- **"The package is missing from the API guard configuration."** — `toggle` is listed at `tools/api-extractor/config.json:61` and `tools/public_api_guard/components/toggle.api.md` is present and current.
- **"The constructor `effect()` writes the plain `currentCheckState` field, so the `[@switch]` binding goes stale under `OnPush`."** — Not filable from static analysis. `currentCheckState` is also written from the `checked` setter (`:152`), the `indeterminate` setter (`:175`) and `onInputClick` (`:258`), all inside a change-detection pass that already refreshes the view, and the effect is documented as a belt-and-braces sync for the form-driven path (`:205-207`). Confirming or refuting staleness would need a runtime experiment, which this review does not perform; the duplication itself is filed as TGL-ARCH-01.

Corrected on verification:
- **TGL-BUG-01** was drafted as "the `KbqCheckable` refactor dropped `booleanAttribute` from `disabled`". `git show ffb491a51^:packages/components/toggle/toggle.component.ts` shows `set disabled(value: any)` at line 113 of the pre-refactor file, so the coercion was never there. Severity unchanged; the wording now says long-standing debt rather than regression, and the sibling comparison replaced the git-history argument as the evidence that it is unintentional.
- **TGL-A11Y-01** was drafted as an automated AXE failure. The vendored `axe-core` is 3.5.6, and its `valid-attr-value` check validates `aria-checked` against the attribute's own value list without consulting the role (`node_modules/axe-core/lib/checks/aria/valid-attr-value.js:52-65`), so no rule fires. Re-filed as a WCAG 4.1.2 / ARIA-specification judgement with the "not detected by CI" fact stated explicitly, which is also why it needs a hand-written spec.
