# Koobiq `datepicker` Component — Code Review & Improvement Plan

> Scope: `packages/components/datepicker` (9 TS files, 5 templates, 6 stylesheets, 5 Jest specs, e2e fixture + Playwright spec, tokens, theme, user guides, API guard report; ~6,570 lines) · Commit `b665e503` · 2026-08-28
> Generated by a multi-dimension review (architecture, RxJS & lifecycle, correctness, accessibility, performance, public API/types, styles, tests, docs) with manual verification of every finding against the source, the in-repo consumers (`filter-bar`, `time-range`), the API guard report, the design-token set and `tsconfig.json`/`playwright.config.ts`. 17 findings confirmed (P0×1, P1×5, P2×6, P3×5); 6 candidate findings refuted during verification (see Appendix A). This document is a review + roadmap; no source is modified by it.

---

## 1. Executive Summary

`datepicker` is the largest package reviewed so far: a masked text input (`datepicker-input.directive.ts`, 1,533 lines — the single biggest file in `packages/components`), an overlay-hosted calendar built from four components (`KbqDatepicker`, `KbqDatepickerContent`, `KbqCalendar`, `KbqCalendarHeader`, `KbqMonthView`, `KbqCalendarBody`), a toggle icon, an animation set and a validator trio. It is consumed inside the library by `time-range` (four datepicker instances) and by `filter-bar`'s date pipe (which uses the rarely-documented inline `[kbqCalendar]` mode), and it carries 110 Jest cases — real, substantial engineering.

- **The one release blocker is that the calendar popup cannot be operated from a keyboard at all.** `grep -n "keydown\|KeyboardEvent\|ARROW\|HOME\|END" month-view.component.ts calendar.component.ts calendar-header.component.ts calendar-body.component.ts` returns nothing: there is no key handling anywhere in the calendar. Every control inside it is *deliberately* removed from the tab order — both `kbq-select`s (`calendar-header.html:6, 33`), all three navigation buttons (`:66, 78, 91`), every date cell (`calendar-body.html:19`) — and the toggle that opens it is likewise `[tabindex]="-1"` (`datepicker-toggle.component.ts:39`). Opening the panel moves no focus into it. A keyboard or screen-reader user can reach the popup, see it appear, and then interact with nothing in it (DP-A11Y-01).
- **The calendar table has no grid semantics either.** No `role="grid"`/`gridcell`, no `aria-selected`, `aria-disabled` or `aria-current`; selection, "today" and disabled state exist only as CSS classes (`calendar-body.html:24-26`), and a comment at `calendar-body.html:4-7` claims a cell is marked `aria-hidden` when nothing in the template sets it. Meanwhile the package carries **two** localization mechanisms: the header correctly uses `kbqInjectA11yLocaleConfiguration()` (`calendar-header.html:62, 74, 87`), while `KbqDatepickerIntl` (`datepicker-intl.ts:5-14`) holds ten hardcoded English strings that reach no template at all (DP-A11Y-02, DP-ARCH-01).
- **Two correctness defects have a clear reproduction.** A `<input kbqDatepicker>` used *without* `ngModel`/`formControl` — the exact shape of the spec's own `StandardDatepicker` host (`datepicker.spec.ts:1572`) — throws `TypeError` on the first unparseable keystroke, because `onInput` dereferences `this.control` unguarded (`datepicker-input.directive.ts:760`) while `updateValue` two lines of code away uses `this.control?.` (`:942`). And a `[max]` supplied as a midnight date rejects its own last day, because the validator compares with `compareDateTime` (`:1423-1429`) — precisely the case the documented "Datepicker + Timepicker" pairing creates (DP-BUG-01, DP-BUG-02).
- **The calendar's colours ship only with the popup.** `datepicker-tokens.scss` and `@include kbq-datepicker-theme()` are pulled in exclusively by `KbqDatepickerContent`'s `styleUrls` (`datepicker.component.ts:74`, `datepicker-content.scss:28-29`), so the public standalone `<kbq-calendar>` mode is unthemed. `filter-bar` works around this three separate ways in two files (DP-CSS-01) — the strongest single piece of consumer evidence in this package.
- **Tests are numerous but the a11y ones are hollow.** Two `describe('a11y')` blocks (`calendar.spec.ts:94, 296`) dispatch a fake `focus` at elements with no focus handler and press `ENTER` at a table with no keydown handler; they pass *because* the feature is missing. A third test (`datepicker.spec.ts:305`) puts both of its assertions inside a floating `fixture.whenStable().then(...)` in a synchronous `it`, so they never run. Three cases whose names promise keyboard behaviour, none of which can fail (DP-TEST-01).

Genuine strengths worth preserving: the masked-input engine is genuinely good work — locale-driven digit layout derived from the format string, caret management per date part, arrow-key increment clamped against `min`/`max` year/month/day, paste normalisation, and a validation-tooltip hook; the timezone and locale reactivity added in `#DS-3248`/`#DS-3897` is carefully commented and correct (`datepicker-input.directive.ts:598-622`); the overlay positioning has four fallback positions with a documented viewport margin and is guarded by two assertion-based Playwright tests that probe the trigger↔panel gap with `elementFromPoint` (`e2e.playwright-spec.ts:65-119`) — a far better test than a screenshot; `injectRequiredDateAdapter()` turns a bare `NullInjectorError` into a named message and is covered by a spec; and `KbqDatepickerToggleIconComponent` is the most modern file in the package (signal input, `toObservable`/`outputToObservable`, `takeUntilDestroyed`, documented rationale for re-running `watchStateChanges`).

## 3. Prioritized Findings (deduplicated, verified)

### P0 — Release blockers

**DP-A11Y-01 · The calendar popup is mouse-only by construction: no key handling, every control removed from the tab order, and focus never enters the panel** — `calendar-body.html:19-20`, `calendar-header.html:6, 33, 66, 78, 91`, `datepicker-toggle.component.ts:39`, `datepicker.component.ts:434-443`, `month-view.component.ts`, `calendar.component.ts`, `calendar-body.component.ts` (no keydown handler in any of them).
There is no keyboard handling anywhere below `KbqDatepickerContent`: grepping the four calendar files for `keydown`, `KeyboardEvent`, `ARROW`, `HOME` or `END` returns nothing, and the only interaction path on a date cell is `(click)="cellClicked(item)"` on a `<td [tabindex]="-1">` (`calendar-body.html:12-21`). This is not an oversight of a single element — every focusable thing in the panel has been *explicitly* taken out of the tab order: the month `kbq-select` (`calendar-header.html:6`), the year `kbq-select` (`:33`), the previous / today / next buttons (`:66, 78, 91`), and every one of the 28–31 date cells. The toggle that opens the calendar is the same story: `<kbq-datepicker-toggle-icon>` renders an `<i kbq-icon-button>` with `[tabindex]="-1"` (`datepicker-toggle.component.ts:39`) and opens only from `(click)` (`:53`), so it is not reachable by Tab either. Finally, `openAsPopup()` attaches the portal and updates the position but never moves focus into it (`datepicker.component.ts:434-443`) — `A11yModule` is imported by `datepicker-module.ts:1` and then used nowhere. The net user experience for a keyboard-only or screen-reader user: `Alt+↓` on the input opens a panel (`datepicker-input.directive.ts:949-951`); focus stays on the input; Tab does not enter the panel; nothing inside responds to a key; `Escape` or `Tab` closes it again (`:714-715, 945-947`). Also note there is no visible *active-cell* affordance to fall back on: the `.kbq-calendar__body_active` class the template applies (`calendar-body.html:14`) has no style rule anywhere in the package or its theme — it exists only for three unit assertions. The mitigating path is real and worth stating plainly: the input directive does handle keys well (arrow-key increment per date part, `Home`/`End`/`PageUp`/`PageDown` caret movement, digit masking — `datepicker-input.directive.ts:694-745, 1293-1345`), so a date *can* be entered without a mouse. That is why this is filed as a keyboard-operability failure of the calendar widget (WCAG 2.1.1) and of AGENTS.md's explicit "focus management" mandate, rather than as a total loss of the component. It is still a P0: a shipped, documented, screenshot-tested UI surface that no keyboard user can touch, in the library's most-composed form control.
**Fix:** implement the ARIA APG date-picker grid on `KbqCalendarBody`. (1) Give the body a roving-tabindex: one `<td [tabindex]="isActiveCell(...) ? 0 : -1">` and a `keydown` handler on the table implementing `←/→` (±1 day), `↑/↓` (±7 days), `Home`/`End` (week bounds), `PageUp`/`PageDown` (±1 month, `+Shift` = ±1 year), `Enter`/`Space` (select), with the active cell driven by `KbqCalendar.activeDate` so month rollover reuses the existing `activeDate` setter. Use `FocusKeyManager` if the cell set can be expressed as a `QueryList`; otherwise `focusVia(cell, 'keyboard')` so the focus ring is restored (see `project_kbq_focus_ring_mechanism`). (2) Remove `[tabindex]="-1"` from the three header buttons and both selects so the header is tabbable in DOM order. (3) Make the toggle a real `<button type="button">` (or add `role="button"` + `tabindex="0"` + `keydown.enter`/`keydown.space`) with an accessible name from `kbqInjectA11yLocaleConfiguration()`. (4) On open, focus the active cell; on close, restore focus to the trigger (see DP-A11Y-03). Guard with Jest cases that drive each key and assert `activeDate`/`selected` changed — and delete the three vacuous cases in DP-TEST-01 first, since they currently assert the *opposite* behaviour and will start failing. Add a keyboard scenario to `e2e.playwright-spec.ts`.

### P1 — High

**DP-A11Y-02 · The calendar table carries no grid ARIA, and a template comment documents an `aria-hidden` that is never written** — `calendar-body.html:1-33`, `month-view.html:1-23`, `calendar.html:9-19`.
The rendered calendar is a plain `<table>` (`month-view.html:1`) with a `<tbody kbq-calendar-body>` of `<td>`s. There is no `role="grid"` on the table, no `role="row"`/`gridcell`, no `aria-selected` on the selected day, no `aria-disabled` on filtered-out days, no `aria-current="date"` on today, and no `aria-label` on the grid naming the displayed month. All three states exist purely as CSS classes on an inner `<div>`: `kbq-calendar__body-today`, `kbq-disabled` and `kbq-selected` (`calendar-body.html:24-26`). A screen reader therefore reads the panel as a table of bare numbers with no indication of which is selected, which is today, or which cannot be chosen — and, because of DP-A11Y-01, with no way to move a virtual cursor into it in application mode. Two further specifics. First, the comment at `calendar-body.html:4-7` states "We mark this cell as aria-hidden so it doesn't get read out as one of the days in the week" about the leading spacer `<td>`; nothing in the template sets `aria-hidden`, so the comment is a false description of shipped behaviour (the spacer is announced as an empty cell). Second, `month-view.html:10-12` puts a second header row inside `<thead>` whose only content is a purely decorative `<th colspan="7">` divider, which is announced as a column-header row; and the weekday `<th>`s (`:5`) carry `[attr.aria-label]="day.long"` but no `scope="col"`, so the association between a day cell and its weekday header is never established. Note this is a WCAG 1.3.1 / 4.1.2 judgement plus an APG-conformance gap, not an automated axe failure — axe does not flag a `<table>` for lacking `role="grid"`, which is exactly why it has survived.
**Fix:** on the `<table>` add `role="grid"` and `[attr.aria-label]` naming the displayed month/year from the date adapter; on each `<tr>` `role="row"`; on each date `<td>` `role="gridcell"`, `[attr.aria-selected]="selectedValue() === item.value"`, `[attr.aria-disabled]="!item.enabled"` and `[attr.aria-current]="todayValue() === item.value ? 'date' : null"`, with the visible number kept as the cell's text. Add `aria-hidden="true"` to the leading spacer `<td>` (`:9`) — making the existing comment true — and to the divider `<th>` (`month-view.html:11`), and `scope="col"` to the weekday `<th>`s. Land this together with DP-A11Y-01, since `role="gridcell"` without a roving tabindex is only half a fix. Cover with Jest assertions per attribute plus a `jest-axe` pass on an opened calendar.

**DP-A11Y-03 · The popup is not a dialog, has no focus trap, and restores focus through an unsound non-null assertion** — `datepicker.component.ts:366-368, 391-393, 448-455`, `datepicker-content.html:1-15`.
`createPopup()` builds an `OverlayConfig` with a position strategy, backdrop, direction, scroll strategy and `panelClass: 'kbq-datepicker__popup'` — and nothing else (`:448-455`). The content host declares only `class: 'kbq-datepicker__content'` plus the animation bindings (`:77-81`): no `role="dialog"`, no `aria-modal`, no `aria-label`. `A11yModule` is imported by the NgModule (`datepicker-module.ts:1`) but `cdkTrapFocus` appears nowhere in the package, so there is no focus containment and no focus restoration contract. The restoration that does exist is unsound: `focusedElementBeforeOpen` is assigned only inside `if (this.document)` (`:366-368`) from `_getFocusedElementPierceShadowDom()`, whose CDK signature is `(): HTMLElement | null`, and `close()` then calls `this.focusedElementBeforeOpen!.focus()` behind a bare `!` (`:392`). The `if (this.document)` guard is itself dead — `DOCUMENT` is always provided — so the assertion is guarding against the wrong thing while the real `null` case (no active element) is unguarded. `close()` is also reachable from `ngOnDestroy()` (`:305`) with the default `restoreFocus = true`, i.e. a datepicker destroyed while open will force focus onto a possibly-detached element. Today the crash is masked because focus never leaves the input (DP-A11Y-01) so `activeElement` is always a real node; the moment focus is moved into the panel — which the DP-A11Y-01 fix requires — this code path becomes load-bearing.
**Fix:** add `role="dialog"`, `aria-modal="true"` and an `[attr.aria-label]` (from `kbqInjectA11yLocaleConfiguration()`, replacing the dead `KbqDatepickerIntl.calendarLabel` — see DP-ARCH-01) to the `KbqDatepickerContent` host block; wrap the content in `cdkTrapFocus` with `cdkTrapFocusAutoCapture` (or drive it manually via `FocusTrapFactory` so the initial focus can be the active cell rather than the first tabbable node). Replace the `!` with `this.focusedElementBeforeOpen?.focus()` and delete the dead `if (this.document)` guard. Add a Jest case asserting Tab from the last control in the panel returns to the first, and one asserting focus lands back on the toggle after `close()`.

**DP-BUG-01 · A `kbqDatepicker` input used without a form control throws `TypeError` on the first unparseable keystroke or blur** — `datepicker-input.directive.ts:747-771 (760)`, `773-832 (791, 809, 819)`, `1447-1458`; contrast `:942`.
`this.control` is assigned in exactly one place — `setControl()` (`:1447-1458`), called only from `validate()` (`:668-672`), which Angular invokes only when an `NgControl` is present. A `<input kbqDatepicker>` bound through the directive's own `value` `@Input` instead of `ngModel`/`formControl` therefore leaves `control` `undefined` for its entire lifetime. `onInput` then dereferences it unguarded: when the typed text is non-empty and does not parse, it takes the `else` branch and calls `this.control.updateValueAndValidity()` (`:760`) → `TypeError: Cannot read properties of undefined`. The path is trivially reachable: typing a single digit into an empty field enters `onKeyDown`'s final `else` (`:743`, since `/^\D$/` does not match a digit), which schedules `onInput`; `getDateFromString('1')` returns `null` because the string is shorter than the first digit group (`:1006-1008`), and `viewValue` is `'1'`. Blur reaches the same code through `onBlur() → onInput()` (`:847`). `parseOnBlur` repeats the pattern three more times (`:791, 809, 819`). That the guard is *known* is visible two hundred lines away: `updateValue` writes `this.control?.updateValueAndValidity({ emitEvent: false })` with optional chaining (`:942`). No test covers it — seven of the spec's own host components use `[kbqDatepicker]` with no form directive (`datepicker.spec.ts:1572, 1589-1590, 1613, 1666, 1681, 1809, 1822`), and none of them types into the input.
**Fix:** replace the four unguarded dereferences with `this.control?.updateValueAndValidity()`, matching `:942`. Better, hoist the whole "revalidate" call into a private `requestValidation()` method so there is one site to get right, and call `this.validatorOnChange()` when there is no control so a standalone consumer still gets `dateChange`/`incorrectInput` semantics. Guard with a Jest case that builds `StandardDatepicker` (no `ngModel`), dispatches a digit keydown followed by `blur`, and asserts no throw and `value === null`.

**DP-BUG-02 · A `[max]` created at midnight rejects its own last day whenever the value carries a clock** — `datepicker-input.directive.ts:1422-1429` (and symmetrically `:1413-1420`), `datepicker.en.md:19-23, 31-33`, `packages/docs-examples/components/datepicker/datepicker-minimax/datepicker-minimax-example.ts:39-55`.
`maxValidator` compares with `compareDateTime` (`:1426`), which walks year → month → day → **hours → minutes → seconds → milliseconds** (`@koobiq/date-adapter`). Every documented way of producing a boundary yields midnight: `DateAdapter.createDate(year, month, day)` builds `DateTime.fromObject({year, month, day})` with a zero clock, and that is exactly what the shipped example does — `readonly maxDate = this.adapter.createDate(2024, 7, 25)` (`datepicker-minimax-example.ts:55`). So a value of 25 Aug 2024 **13:00** fails `kbqDatepickerMax` against a max of 25 Aug 2024 00:00, even though the user picked the last day the calendar itself offers: `KbqMonthView.shouldEnableDate` uses day-granularity `compareDate` (`month-view.component.ts:211-212`), so the cell is enabled, clickable, and then invalid. A non-zero clock is not exotic here — it is the library's own recommended pattern: `saveTimePart()` deliberately preserves the time component of the existing value when a calendar date is picked (`datepicker-input.directive.ts:903-918`), and `datepicker.en.md:31-33` documents pairing the datepicker with a timepicker over one model (`datepicker-and-timepicker-example.ts`), which is precisely how the clock becomes non-zero. To be explicit about what is *not* being claimed: the split between `[minDate]/[maxDate]` (calendar limits only) and `[min]/[max]` (validation only) is deliberate repo design, correctly used by `time-range` and already refuted as a finding in `REVIEW.time-range.md` — no bridge between them is proposed here. The defect is the granularity mismatch inside the `[min]/[max]` surface alone.
**Fix:** decide the semantics deliberately and document them. The lower-risk option: compare with day granularity in `minValidator`/`maxValidator` (`compareDate`), so `[min]`/`[max]` mean "this calendar day inclusive" and match what the calendar renders; keep `compareDateTime` only if a `[max]` is later given an explicit time-bearing form. The alternative: keep `compareDateTime` and normalise the bound at the setter (`min` → start of day, `max` → end of day) in `set min`/`set max` (`:415-433`). Either way add a Jest case that sets `[max]` from `createDate(...)` and asserts a same-day value at 13:00 is valid, plus a line in `datepicker.en.md`/`datepicker.ru.md` under "Date selection restriction" naming both surfaces and the time granularity.

**DP-CSS-01 · The calendar's tokens and theme ship only with the popup, so the public standalone `<kbq-calendar>` renders unthemed** — `datepicker.component.ts:74`, `datepicker-content.scss:1, 28-29`, `datepicker-tokens.scss:1`, `_datepicker-theme.scss:3-48`; consumer workarounds at `filter-bar/pipes/pipe-date.scss:1, 4, 138-139` and `filter-bar/pipes/pipe-date.html:53`.
`datepicker-tokens.scss` scopes all 27 custom properties to `.kbq-datepicker__content` (`:1`), and `datepicker-content.scss` is the only file that calls `@include kbq-datepicker-theme()` / `kbq-datepicker-typography()` (`:28-29`). Both files are `styleUrls` of `KbqDatepickerContent` alone (`datepicker.component.ts:74`). `KbqCalendar`, `KbqMonthView`, `KbqCalendarBody` and `KbqCalendarHeader` contribute only layout SCSS. Consequence: `<kbq-calendar>` used directly — a fully public, exported component with `exportAs: 'kbqCalendar'`, paired with the `input[kbqCalendar]` selector on the input directive (`datepicker-input.directive.ts:241`) — gets no colour rules at all until some `KbqDatepickerContent` is instantiated elsewhere in the app, and no element-scoped tokens ever. The in-repo consumer proves it: `filter-bar`'s date pipe reaches across the package boundary to `@use '../../datepicker/datepicker-theme'` and `'../../datepicker/datepicker-tokens'` (`pipe-date.scss:1, 4`), re-includes both mixins at file scope (`:138-139`), **and** hand-applies the popup's own class to a plain `<div>` — `class="kbq-date-period kbq-datepicker__content"` (`pipe-date.html:53`) — purely to bring the token block into scope. Three workarounds, one consumer, for one missing decision.
**Fix:** move `datepicker-tokens.scss` and the `@include kbq-datepicker-theme()` / `kbq-datepicker-typography()` calls onto `KbqCalendar` (`styleUrls: ['calendar.scss', 'datepicker-tokens.scss']`), and re-scope the token block from `.kbq-datepicker__content` to `.kbq-calendar, .kbq-datepicker__content` so both entry points carry it. Keep the container-level tokens (`--kbq-datepicker-size-container-*`, `--kbq-datepicker-container-background/shadow`) on `.kbq-datepicker__content`, since only the popup has a surface. Then delete `pipe-date.scss:1, 4, 138-139` and the `kbq-datepicker__content` class at `pipe-date.html:53` — removing those four lines *is* the acceptance criterion, not the SCSS diff. Re-run `yarn run e2e:docker` for `filter-bar` and `datepicker`; baselines must come from `e2e:docker:update-snapshots`.

### P2 — Should fix

**DP-BUG-03 · `[attr.required]` renders `required="false"`, which makes the input required** — `datepicker-input.directive.ts:250`; correct pattern one package away at `checkbox/checkbox-required-validator.ts:19`.
The host block binds `'[attr.required]': 'required'` with a raw boolean. Angular removes an attribute binding only for `null`/`undefined`; for `false` it calls `setAttribute('required', 'false')`. `required` is a boolean *content* attribute, so its mere presence — whatever the value — makes the element required: native constraint validation reports `valueMissing`, `:required` matches, and assistive technology announces "required". The field is only correct by accident: `_required` starts as `undefined` (`:333`), so an untouched datepicker emits nothing; the moment a consumer writes `[required]="false"` or toggles a bound flag from `true` back to `false`, the input becomes permanently required in the DOM while `KbqFormField` (which reads the `required` *property*, not the attribute) still styles it as optional. The same file gets the neighbouring binding right — `'[attr.disabled]': 'disabled || null'` (`:251`) — and `checkbox-required-validator.ts:19` uses the canonical `required ? "" : null`. `timepicker.directive.ts:134` carries the identical defect and should be fixed in the same change.
**Fix:** `'[attr.required]': 'required ? "" : null'` in both `datepicker-input.directive.ts:250` and `timepicker.directive.ts:134`. Add a Jest case asserting `input.hasAttribute('required')` is `false` after `[required]="false"` and `true` after `[required]="true"`, and that `input.validity.valueMissing` follows.

**DP-BUG-04 · Reopening while the exit animation is still running destroys the overlay that was just re-attached** — `datepicker.component.ts:378-399, 421-443`.
`close()` starts the exit animation and subscribes `instance.animationDone.pipe(take(1)).subscribe(() => this.destroyOverlay())` (`:386-388`), then immediately flips `_opened = false` and emits `closedStream` — the teardown is asynchronous but the state flag is not. If `open()` runs before the 100 ms exit animation completes, `openAsPopup()` finds `this.popupRef` non-null and `this.popupRef.hasAttached()` still `true`, so it skips the re-attach entirely (`:430-435`) and nothing resets `KbqDatepickerContent.animationState` from `'void'` back to a visible state. The pending `animationDone` then fires and calls `destroyOverlay()` (`:414-419`), disposing the overlay while `_opened === true`. The user sees the panel fade out and never come back, and the *next* click on the toggle is swallowed by `open()`'s `if (this._opened) return` guard (`:358`) — it takes two more clicks to recover. The trigger is ordinary: both the dev app and three shipped examples put `(click)="datepicker.toggle()"` on the whole `kbq-form-field` (`components-dev/datepicker/template.html:19`, `datepicker-minimax-example.ts:34`, `datepicker-required-example.ts:23`), so a double-click on the field is exactly close-then-open inside the animation window.
**Fix:** make the close teardown cancellable. Store the exit subscription and unsubscribe it at the top of `open()`; in `openAsPopup()`, when `popupRef.hasAttached()` is already true, reset the content instance's `animationState` to the enter state (see DP-BUG-06) and `markForCheck()` instead of returning silently. Alternatively track a `closing` flag and have `open()` await `destroyOverlay()` before re-attaching. Guard with a `fakeAsync` Jest case that calls `close()`, then `open()` after `tick(50)`, then `flush()`, and asserts `.cdk-overlay-pane` is still in the DOM and `opened === true`.

**DP-BUG-05 · Two statements in the input directive compute a result and discard it, silently disabling the behaviour they were written for** — `datepicker-input.directive.ts:859`, `1495-1497`.
Both are one-token defects with real consequences. (1) `onPaste` normalises the pasted separators with `rawValue.replace(/[^A-Za-z0-9]+/g, this.separator);` (`:859`) — `String.prototype.replace` is pure, the result is thrown away, and `rawValue` is unchanged. Everything downstream therefore runs against the raw clipboard text: the `^(?<first>\d+)\W(?<second>\d+)\W(?<third>\d+)$` match at `:866` happens to tolerate a single non-word separator, so `2024/08/25` still parses, but anything the normaliser was meant to repair — doubled separators, a trailing dot, mixed `-`/`.`/`/` — falls through to `setViewValue(rawValue)` (`:869`) and lands in the field as unparsed junk. (2) `getDigitPositions` ends with `if (!this.firstDigit || !this.secondDigit || !this.thirdDigit) { Error(\`Can' t use this format: ${format}\`); }` (`:1495-1497`) — the `Error` is *constructed* and never thrown. A `KBQ_DATE_FORMATS.dateInput` the parser cannot decompose therefore produces no diagnostic at all; the directive continues with `firstDigit === null` and dies later with an opaque `TypeError` at the first `this.firstDigit!.length` (`:1006`), far from the cause. The message also contains a stray space (`Can' t`).
**Fix:** (1) `rawValue = rawValue.replace(/[^A-Za-z0-9]+/g, this.separator);` and add a paste case with `2024//08//25` and `25-08-2024`. (2) `throw createMissingDateImplError(...)`-style: `throw Error(\`Can't use this format: ${format}\`);`, and add a Jest case providing a deliberately undecomposable `KBQ_DATE_FORMATS` and asserting the thrown message. Both are covered by `yarn run eslint` rules if `no-unused-expressions` is enabled for the package — worth checking as part of the fix.

**DP-LIFE-01 · `setControl` subscribes to the form control forever, and three Subjects are never completed** — `datepicker-input.directive.ts:1447-1458 (1454)`, `656-660`, `491-499`; `datepicker.component.ts:304-311`.
`setControl()` opens `this.control.valueChanges.subscribe((value) => (this._value = value))` (`:1454`) and stores no handle; `ngOnDestroy` (`:656-660`) unsubscribes only `datepickerSubscription`. Because the `AbstractControl` is usually owned by a parent component or a service, it outlives the directive, so the closure keeps a destroyed `KbqDatepickerInput` (and through it the `ElementRef`, the `KbqErrorStateTracker` and the whole datepicker graph) reachable for the control's lifetime — a genuine retain in any list/table that creates and destroys date fields. The write itself is also questionable: it assigns `_value` directly, bypassing `set value` and therefore skipping `deserialize`, `lastValueValid` and `formatValue`, so a programmatic `control.setValue(...)` updates the model but not the rendered text. Separately, `ngOnDestroy` completes `valueChange` and `disabledChange` but not `stateChanges`, and `KbqDatepicker.ngOnDestroy` (`:304-311`) completes `disabledChange` but not `stateChanges` or `selectedChanged` — while `KbqCalendar.ngOnDestroy` (`calendar.component.ts:196-200`) does complete its own, so the package is inconsistent with itself. Finally, `kbqValidationTooltip` subscribes to `incorrectInput` and schedules `setTimeout(() => tooltip.hide(), validationTooltipHideDelay)` with no stored id (`:491-499`), so a rapid destroy leaves a timer firing `hide()` on a torn-down tooltip.
**Fix:** pipe the `valueChanges` subscription through `takeUntilDestroyed(this.destroyRef)` and route the write through `this.value = value` (verify against the existing `formControl` specs at `datepicker.spec.ts:707-769` before changing the assignment). Complete `stateChanges` in both `ngOnDestroy`s and `selectedChanged` in `KbqDatepicker`'s. Store the tooltip timer id and clear it in `ngOnDestroy`, or replace it with `timer(...).pipe(takeUntilDestroyed())`.

**DP-ARCH-01 · Two localization mechanisms; the exported one is dead, English-only and re-provided over its own root provider** — `datepicker-intl.ts:1-42`, `calendar.component.ts:166-172`, `datepicker-module.ts:38`, `calendar-header.spec.ts:23`; contrast `calendar-header.html:62, 74, 87`.

This removes a public class, so it is a breaking change: pair it with an `ng-update` migration in `packages/schematics` (there is precedent — `locale-configuration-providers` and `v20-upgrade` already rewrite datepicker symbols) and run `build:components` + `approve-api`.

**DP-TEST-01 · Three tests pass because the feature they name does not exist, and one asserts nothing at all** — `calendar.spec.ts:94-131, 296-330 (307, 316)`, `datepicker.spec.ts:305-322`; disabled suites at `calendar.spec.ts:169`, `datepicker.spec.ts:1346, 1535`.

**DP-BUG-06 · `animationState` is never set to `'enter'`, so the panel's entrance transition can never match** — `datepicker.component.ts:79, 98, 118-121`, `datepicker-animations.ts:12-31`; contrast `actions-panel/actions-panel-container.ts:134, 186`.

## 4. Recommended Remediation Phases

**Phase 1 — Make the calendar operable and audible.**
IDs: DP-A11Y-01, DP-A11Y-02, DP-A11Y-03, DP-TEST-01, DP-ARCH-01. This is one unit and must land together: a roving tabindex without grid roles is half a fix, grid roles without a focus trap leave the panel unbounded, and the three vacuous tests assert the *current* (broken) behaviour and will start failing the moment keys are handled — so they must be rewritten in the same change. Fold DP-ARCH-01 in here rather than later, because the dialog label and the toggle's accessible name need a live localization source and `KbqDatepickerIntl` is where a careless fix would reach for them. Highest user impact; touches no parsing logic.

**Phase 2 — Fix the confirmed correctness defects.**
IDs: DP-BUG-01, DP-BUG-02, DP-BUG-03, DP-BUG-05. Four independent, small, well-anchored changes: guard `this.control`, settle the `min`/`max` granularity, emit `required` as a proper boolean attribute (with the identical `timepicker` fix), and make the two discarded-result statements do their job. Each ships with the Jest case named in its finding. No API change, no visual change, no dependency on Phase 1.

**Phase 3 — Overlay lifecycle and theming reach.**
IDs: DP-BUG-04, DP-BUG-06, DP-CSS-01, DP-LIFE-01. The open/close race and the never-set `animationState` touch the same two methods and should be done together. `DP-CSS-01` is separable but belongs here because its acceptance criterion is the deletion of four lines in `filter-bar`, which needs a Docker screenshot round for both packages. `DP-LIFE-01` joins as the teardown sweep across the same files.

**Phase 4 — API and hygiene.**
IDs: DP-API-01, DP-ARCH-02, DP-CSS-02, DP-DOC-01. Remove the dead inputs/outputs, type the five `any`s, resolve the `KbqFormFieldControl` provider, migrate the trivially-convertible accessor inputs and convert the two `ngOnChanges` blocks to effects, delete the orphaned toggle CSS and the dead tokens, and rewrite the guides and the dev app. One `build:components` + `approve-api` cycle covers the whole phase; schedule the breaking parts (removing `KbqDatepickerIntl` from Phase 1, removing public inputs here) with the same minor and one `ng-update` migration.

## Appendix A — Review Methodology

Findings were gathered by reading the complete package — every `.ts`, `.html`, `.scss` and `.md` file, all five Jest specs, the e2e fixture and the Playwright spec — and then following each candidate outward rather than trusting the first read. Four independent corroboration sources did most of the work. (1) **The in-repo consumers**: `filter-bar/pipes/pipe-date.{html,scss}` and `time-range/time-range-editor.html` are the only two places outside the package that compose it, and both turned out to hold decisive evidence — filter-bar's three theming workarounds established DP-CSS-01, and time-range's correct double binding of both min/max surfaces (already documented in `REVIEW.time-range.md:120`) is what narrowed DP-BUG-02 from a wrong finding to a right one. (2) **Sibling implementations**: `checkbox/checkbox-required-validator.ts:19` and `actions-panel/actions-panel-container.ts:186` show the same problems solved correctly one package away, which is what turned DP-BUG-03 and DP-BUG-06 from style opinions into defects. (3) **The API guard report** (`tools/public_api_guard/components/datepicker.api.md`, 506 lines), which exposed the never-emitted output and the five `any`s. Refuted during verification:
- **"`datepicker-input.directive.ts` ships a UTF-8 BOM, which breaks tooling"** — refuted as a package defect. The BOM is repo-wide: a scan of `packages/components/*/*.ts` finds it on 20+ files across `accordion`, `autocomplete`, `button`, `dropdown`, `input`, `list` and others. It is a workspace-level editor-settings question, not a datepicker finding.
- **"`[minDate]/[maxDate]` do not restrict the value, so they should feed `[min]/[max]`"** — refuted. The split is deliberate repo design (`[minDate]/[maxDate]` limit the calendar, `[min]/[max]` validate), it is used correctly by `time-range` (`time-range-editor.html:37-44, 60-68`), and `REVIEW.time-range.md:120` already refuted the same candidate. Only the *granularity* inside `[min]/[max]` is wrong, which is DP-BUG-02.
- **"`[class]="item.cssClasses!"` on the date cell overwrites the static class and the `[class.…]` bindings"** — refuted. Angular's styling precedence merges static classes, the map binding and per-class bindings, with per-class bindings winning; `calendar-body.spec.ts:87` observes a `[class.…]`-driven class coexisting with the static one, and `month-view.spec.ts:147-158` exercises the `dateClass` map path. No collision.
- **"`KbqDatepickerModule` exports `KbqFormFieldModule` without importing it — a compile error"** — refuted. Angular permits an NgModule to re-export a module it does not import, and the package builds in CI. The re-export is deliberate, so consumers of `KbqDatepickerModule` get the form-field directives the documented markup requires.
- **"The package violates the SSR rules by touching browser globals"** — refuted. There is no bare `window` or `getComputedStyle` anywhere in the package; `DOCUMENT` is injected (`datepicker.component.ts:143`), `_getFocusedElementPierceShadowDom()` is the CDK helper, and `set disabled` explicitly null-checks `element.blur` for SSR (`datepicker-input.directive.ts:454-460`). The unsound `!` at `datepicker.component.ts:392` is a null-safety issue, filed under DP-A11Y-03, not an SSR one.
- **"`KbqDatepicker.opened` is both an `@Input` and an `@Output` (aliased `opened`), so `[(opened)]` silently closes the panel"** — refuted. Angular forms a two-way binding only from an output named `<input>Change`; the alias here is `opened`, not `openedChange` (`datepicker.api.md:249`), so `[(opened)]` does not compile into a banana box and no such loop exists.

Corrected on verification:
- **DP-A11Y-01** was first drafted as P1, on the reasoning that the input directive's rich key handling gives keyboard users a complete alternative path. Reading `datepicker-toggle.component.ts:39` changed the picture: the toggle is `[tabindex]="-1"` as well, so there is no keyboard route *to* the calendar either, and the panel is not merely hard to use but structurally unreachable. Raised to P0, with the mitigating text-entry path stated explicitly inside the finding rather than used to soften it.
- **DP-BUG-02** was first drafted as "the documented min/max restriction only validates and does not limit the calendar" — the same candidate `REVIEW.time-range.md` had already refuted. Reading `compareDateTime` in `@koobiq/date-adapter` against `LuxonDateAdapter.createDate` (which builds a midnight `DateTime`) relocated the real defect to the boundary's time granularity, and `saveTimePart` (`datepicker-input.directive.ts:903-918`) plus the shipped datepicker+timepicker example supplied the reproduction.
- **DP-CSS-01** was first drafted as "the calendar has no theme file". It has one (`_datepicker-theme.scss`); the defect is that only `KbqDatepickerContent` includes it, so the impact narrowed from "no theme" to "no theme in the standalone `<kbq-calendar>` mode" — and gained a concrete acceptance test once `filter-bar`'s three workarounds were found.
- **DP-TEST-01** was first filed as "the a11y describes are thin". Reading them showed something sharper: they do not merely under-test, they are *guaranteed green by the absence of the feature they name*, which is the mechanism by which DP-A11Y-01 survived 110 test cases. The wording moved from "thin" to "cannot fail", and the finding was given the mutation-check acceptance criterion.
