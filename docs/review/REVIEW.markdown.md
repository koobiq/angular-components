# Koobiq `markdown` Component — Code Review & Improvement Plan

> Scope: `packages/components/markdown` (component, service, alias tables, NgModule, tokens, theme, SCSS, both Jest specs + snapshot, e2e fixture + Playwright spec, user guides, examples, API guard report) · Commit `b665e503` · 2026-08-28
> Generated by a multi-dimension review (security/sanitization, architecture, correctness, accessibility, SSR, public API/types, styles, tests, docs) with manual verification of every finding against the source, the installed `marked@17.0.3`, the in-repo consumers and the docs pipeline. 15 findings confirmed (P0×1, P1×2, P2×6, P3×6); 8 candidate findings refuted and 3 corrected during verification (see Appendix A). This document is a review + roadmap; no source is modified by it.

## 1. Executive Summary

`KbqMarkdown` is a 116-line component plus a 46-line service that runs `marked.parse()` over either the `markdownText` input or the text projected into a hidden `<pre>`, rewrites the resulting tag names to add `kbq-markdown__*` classes, and writes the string into a `<div>` via `[innerHtml]`. It is one of the few components in the library whose entire job is to render a *document* — and the only one that hands a raw HTML string to the DOM.

- **The headline defect is that the rendered HTML is never sanitized by anything.** `getResultHTML()` wraps the parser output in `DomSanitizer.bypassSecurityTrustHtml()` (`markdown.component.ts:99`), which is precisely the call that tells Angular *not* to sanitize; `marked@17` removed the `sanitize` option years ago and, verified against the installed copy, passes `<img src=x onerror=…>`, `<iframe src="javascript:…">`, `<div onclick=…>` and `[click](javascript:alert(1))` through byte-for-byte. The service's JSDoc carries a `NOTE! Method does not sanitize the output HTML string` (`markdown.service.ts:12`), but the component that consumers actually use carries no warning, and neither user guide mentions sanitization at all. Any application that feeds this component content it did not author — comments, tickets, imported documents, model output — has a stored-XSS sink it cannot discover from the documentation (MD-BUG-01).
- **Two contracts are simply broken.** The tag-aliasing pass matches on a tag-name *prefix*, so `<aside>`, `<audio>`, `<address>`, `<article>`, `<abbr>`, `<link>` and `<track>` in raw HTML are shredded into malformed anchors and list items — verified output for `<aside>x</aside>` is `<a class="kbq-markdown__a"side>x</aside>` (MD-BUG-02). And `KbqMarkdownService` is neither `providedIn: 'root'` nor listed in the component's `providers`; it exists only in `KbqMarkdownModule.providers` (`markdown.module.ts:11`), so a consumer who follows AGENTS.md ("always use standalone components over NgModules") and writes `imports: [KbqMarkdown]` gets a `NullInjectorError` at construction (MD-ARCH-01).
- **State handling is one-directional.** Clearing `markdownText` to `null`/`''` is swallowed by the setter's truthiness guard (`markdown.component.ts:65`), leaving the previous document rendered forever (MD-BUG-03); the projected-content path is read exactly once from `afterNextRender` (`:77-83`), so `<kbq-markdown>{{ text }}</kbq-markdown>` never re-renders (MD-BUG-04) and produces nothing at all on the server, since `afterNextRender` does not run during SSR (MD-SSR-01).
- **Layout and a11y gaps sit on the generated output nobody tests.** `.kbq-markdown__ol > li > *` forces `display: inline-block` (`markdown.scss:78-80`), which is exactly what `marked` emits for a nested list, a loose `<p>` or a fenced code block inside a numbered step — none of which appear in any example, fixture or spec (MD-CSS-01). The `<pre>` code block is `overflow-x: auto` with no `tabindex`, which is the shape axe-core's `scrollable-region-focusable` rule (wcag2a / WCAG 2.1.1) exists to flag (MD-A11Y-01).
- **The test suite proves the markup renders, not that it is correct.** Two of the three component cases are 890 lines of whole-tree `toMatchSnapshot()` (`__snapshots__/markdown.component.spec.ts.snap`); nothing asserts the sanitization contract, nothing re-binds `markdownText`, nothing covers a nested list, and there is no axe pass anywhere in the package (MD-TEST-01).

Genuine strengths worth preserving: the component is modern where it counts — standalone, `OnPush`, signal state, `viewChild.required`, `effect()` instead of lifecycle hooks — and the DS-4849 link work is properly done, delegating anchor styling to the shared `.kbq-link` classes and restoring the focus ring through `FocusMonitor` with a real behavioural test (`markdown.component.spec.ts:180-191`). The 14 docs examples, both language guides and a live Examples tab (`structure.ts:741`) make this one of the better-documented packages in the library, the token file is complete and every base token it references resolves in both themes, and `KBQ_MARKDOWN_MARKED_OPTIONS` is a well-shaped extension point — it is also, conveniently, the exact hook through which most of the findings below can be fixed.

## 3. Prioritized Findings (deduplicated, verified)

### P0 — Release blockers

**MD-BUG-01 · Rendered markdown bypasses the Angular sanitizer entirely; raw HTML, inline event handlers and `javascript:` URLs reach `innerHTML` untouched** — `markdown.component.ts:36, 98-100`, `markdown.service.ts:18-20`, `markdown.en.md`, `markdown.ru.md`.
The pipeline is three steps and none of them sanitizes. (1) `KbqMarkdownService.parseToHtml()` calls `marked.parse()` and returns the string; its own JSDoc states the contract plainly — `NOTE! Method does not sanitize the output HTML string` (`markdown.service.ts:12`). (2) `marked@17.0.3` (`package.json:44`, `node_modules/marked/package.json:5`) has no `sanitize` option at all — the `MarkedOptions` interface (`node_modules/marked/lib/marked.d.ts:496-530`) exposes only `hooks`, `renderer`, `tokenizer`, `extensions` and `walkTokens` — and by design passes raw HTML through. Verified against the installed copy: `<img src=x onerror=alert(1)>` round-trips unchanged, `<div onclick="alert(1)">hi</div>` round-trips unchanged, `<iframe src="javascript:alert(1)"></iframe>` round-trips unchanged, `[click](javascript:alert(1))` becomes `<a href="javascript:alert(1)">click</a>`, and `![x](javascript:alert(1))` becomes `<img src="javascript:alert(1)" alt="x">`. (3) `getResultHTML()` then wraps that string in `this.sanitizer.bypassSecurityTrustHtml(...)` (`markdown.component.ts:99`) — the one API whose entire purpose is to stop `ɵɵsanitizeHtml` from running — and the template binds it with `[innerHtml]="resultHtml()"` (`markdown.component.ts:36`). The net effect is `element.innerHTML = <attacker-controlled string>` with no filter anywhere in the chain.
The live vectors are event-handler attributes (`onerror`, `onload`, `onclick`, …) and `javascript:` URLs on `<a>`/`<img>`/`<iframe>`; an injected `<script>` element does *not* execute, because `innerHTML` never runs scripts it inserts — but that is the only thing standing between this component and arbitrary script execution, and it stops none of the above. Arbitrary element injection is also unrestricted: `<iframe>`, `<form>`, `<style>` and `<link>` all land in the host application's DOM. The repo is demonstrably aware of this class of bug elsewhere: the docs app HTML-escapes every interpolated value before its own `bypassSecurityTrustHtml`, with a comment saying so — "so a future refactor that makes them attacker-controlled cannot reintroduce an XSS sink through the surrounding `bypassSecurityTrustHtml`" (`apps/docs/src/app/components/live-example/markdown-content.ts:31-43`). The component ships no equivalent guard and no warning: `markdown.en.md` and `markdown.ru.md` cover headings, lists, tables and line breaks and never once say that the input must be trusted. A code-scanning-driven security pass touched this exact file eight commits ago (`c5d5a7649` "fix(security): repair the regular expressions and path handling found by code scanning") and repaired only the `\s` escape in the alias regex — the sanitizer bypass was not addressed.
**Fix:** make safe rendering the default and opt-out explicit. Concretely: (a) stop calling `bypassSecurityTrustHtml` unconditionally — bind the parser output through the normal sanitizing path (`[innerHtml]` on a plain `string` runs `ɵɵsanitizeHtml`, which strips event handlers, `javascript:` URLs and `<script>`/`<iframe>`), and reserve the bypass for an explicit, documented `[trustedHtml]="true"` (or a `KBQ_MARKDOWN_TRUST_HTML` token) that a consumer must set when it owns the content; (b) if the default sanitizer is too lossy for the library's needs, replace it with an explicit allow-list — a `marked` `hooks.postprocess` or a `renderer` that drops disallowed elements/attributes and rejects any `href`/`src` whose scheme is not in `http/https/mailto/#` — rather than leaving the pass-through as-is; (c) in the same renderer, emit `rel="noopener noreferrer"` on any anchor that carries a `target` (marked emits no `target` today, so this is future-proofing, not a current hole); (d) add the security contract to `markdown.en.md`/`markdown.ru.md` and to the `KbqMarkdown` class JSDoc, not only to the service method. Guard it with Jest cases in `markdown.component.spec.ts` that render `<img src=x onerror=…>`, `<a href="javascript:…">` and `<iframe>` through the component and assert on the *rendered DOM* (`outputWrapper.innerHTML`) that the handler attribute is absent and the `href` no longer starts with `javascript:` — assert against the DOM, not the service's string, so the test covers the whole chain including the bypass.

### P1 — High

**MD-BUG-02 · Tag aliasing matches on a tag-name prefix, corrupting common raw-HTML elements and duplicating `class` attributes** — `markdown.service.ts:22-45`, `markdown.values.ts:2-23`, `markdown.service.spec.ts:18-25`.
`transform()` rewrites the parser output with `transformed.replace(new RegExp(\`<${tag}\`, 'g'), …)` for each of the 20 entries in `MARKDOWN_TAGS_TO_CLASS_ALIAS` (`markdown.service.ts:26`). The pattern is unanchored and has no boundary after the tag name, so `<a` matches the opening of every tag whose name starts with `a`, `<li` matches `<link`, and `<tr` matches `<track`. Because `marked` HTML-escapes ordinary text but hands *raw HTML* through untouched, author markup is exactly what reaches this pass — a property the package's own spec relies on and documents (`markdown.service.spec.ts:18-19`: "`marked` hands raw HTML through untouched, so an author's own markup is what reaches the tag aliasing"). Verified output for real input:

| input | output |
|---|---|
| `<aside>x</aside>` | `<a class="kbq-markdown__a"side>x</aside>` |
| `<audio controls>` | `<a class="kbq-markdown__a"udio controls>` |
| `<address>y</address>` | `<a class="kbq-markdown__a"ddress>y</address>` |
| `<article>hi</article>` | `<a class="kbq-markdown__a …"rticle>hi</article>` |
| `<abbr title="x">y</abbr>` | `<a class="kbq-markdown__a …"bbr title="x">y</abbr>` |
| `<link rel="stylesheet">` | `<li class="kbq-markdown__li"nk rel="stylesheet">` |
| `<track kind="k">` | `<tr class="kbq-markdown__tr"ack kind="k">` |

Every one of these produces a mismatched open/close pair, so the browser's parser invents structure the author did not write; `<article>` in a markdown document silently becomes an unclosed anchor swallowing the rest of the block. The same pass also injects a second `class` attribute onto raw HTML that already has one — `<a href="u" class="mine">z</a>` becomes `<a class="kbq-markdown__a kbq-link kbq-text-only kbq-link_use-visited" href="u" class="mine">z</a>`, and the author's class is dropped because browsers keep the first occurrence. The `th`/`p` entries were already split into `MARKDOWN_WHOLE_TAGS_TO_CLASS_ALIAS` for exactly this reason (`markdown.values.ts:26-33` — "separating `th` and `p` to prevent it's conflict with `thead` and `pre`"), which shows the collision class was understood but only patched for the two cases that broke *generated* output; the raw-HTML cases were never enumerated.
**Fix:** stop rewriting the serialized HTML with regular expressions. Replace `transform()` with a `marked` `Renderer` subclass supplied through `KBQ_MARKDOWN_MARKED_OPTIONS`, which receives structured tokens and emits the class on the element it is actually rendering — this removes the whole prefix-collision class, fixes the duplicate `class` attribute, and is the natural place to also implement the URL allow-list (MD-BUG-01), the `<pre tabindex="0">` (MD-A11Y-01) and the heading offset (MD-A11Y-02). If a string pass must be kept as an interim, at minimum anchor each pattern on a tag-name boundary — `new RegExp('<' + tag + '(?=[\\\\s/>])', 'g')` — and merge into an existing `class` attribute instead of prepending a second one. Extend `markdown.service.spec.ts` with a case per collision family (`<aside>`, `<link>`, `<track>`, `<a class="mine">`) asserting the tag name survives intact.

**MD-ARCH-01 · `KbqMarkdownService` is provided only by the legacy NgModule, so the standalone component throws `NullInjectorError`** — `markdown.service.ts:8`, `markdown.module.ts:9-13`, `markdown.component.ts:31-46`, `public-api.ts:1-4`.
`KbqMarkdownService` is declared `@Injectable()` with no `providedIn` (`markdown.service.ts:8`). `KbqMarkdown` injects it in a field initializer (`markdown.component.ts:46`) and declares no `providers` of its own (the decorator at `:31-44` has `selector`, `template`, `styleUrls`, `changeDetection`, `encapsulation` and `host` only). The single place the service is registered is `KbqMarkdownModule.providers` (`markdown.module.ts:11`). `public-api.ts:1` exports the standalone component directly, so `imports: [KbqMarkdown]` is a first-class, type-checking usage — and it fails at construction with `NullInjectorError: No provider for KbqMarkdownService`. This contradicts two explicit AGENTS.md rules at once ("Always use standalone components over NgModules"; "Use the `providedIn: 'root'` option for singleton services"), and AGENTS.md describes `<component-name>.module.ts` as existing "for legacy support" — i.e. the path that works is the deprecated one. The failure is invisible in-repo because every consumer imports the module: all 14 docs examples, both Jest host components (`markdown.component.spec.ts:24, 36, 102`), `e2e.ts:7, 19` and `components-dev/all/module.ts:59`. It is also invisible in the documentation, because neither guide shows an import at all — `markdown.en.md`/`markdown.ru.md` mention only the `marked` npm dependency. There are zero other references to `KbqMarkdownService` anywhere in `packages/`, `apps/` or `tools/`, so nothing depends on the current per-module instance semantics.
**Fix:** change the decorator to `@Injectable({ providedIn: 'root' })` and drop the `providers: [KbqMarkdownService]` entry from `markdown.module.ts` (keeping it is harmless but creates a second instance under the module). Add a Jest case that builds a host with `imports: [KbqMarkdown]` — the standalone component, not the module — and asserts it renders; that case fails today and is the regression guard. Add an import snippet to both guides showing the standalone form. This changes no public type signature, so the API guard report is unaffected.

### P2 — Should fix

**MD-BUG-03 · Clearing `markdownText` leaves the previously rendered document on screen** — `markdown.component.ts:59-72, 85-91`.
The setter guards on truthiness *and* inequality: `if (value && this.markdownText !== value) { this.resultHtml.set(...) }` (`:65-67`). Assigning `null` or `''` therefore updates the backing field (`:69`) but never touches `resultHtml`, so the last non-empty document stays rendered indefinitely. A consumer binding `[markdownText]="selectedItem()?.description ?? null"` and switching to an item without a description keeps showing the previous item's text — a stale-content bug that reads as a data leak in list/detail UIs. The same guard makes the `else` branch of the constructor's `effect()` (`:88-90`) unreachable after the first successful render: once `resultHtml()` is truthy it never becomes falsy again, so `stopMonitoringLinks()` is only ever reached from `ngOnDestroy` and from the top of `startMonitoringLinks()`.
**Fix:** split the two concerns — keep the equality check, drop the truthiness check, and set `this.resultHtml.set(value ? this.getResultHTML(value) : null)`. Decide and document what an empty `markdownText` means when content is also projected (most useful: fall back to the projected text, which requires MD-BUG-04's reactive read). Add Jest cases that bind a value, assert the output, rebind to `null` and to `''`, and assert `.kbq-markdown__output` is empty.

**MD-BUG-04 · Projected markdown is read exactly once and never re-rendered** — `markdown.component.ts:51, 76-83`.
The projected-content path lives entirely in `afterNextRender` (`:77-83`), which by definition fires once. `contentWrapper` is read there and nowhere else, so nothing observes the `<pre>` afterwards: `<kbq-markdown ngPreserveWhitespaces>{{ doc() }}</kbq-markdown>`, or any projected content behind `@if`/`@for`, renders whatever text existed at first paint and then freezes. Content projection is not a fringe usage here — it is the *primary* documented usage: 13 of the 14 docs examples use it, the e2e fixture uses it (`e2e.html:2-64`), and both guides demonstrate only that form. The guard `if (!this.markdownText && contentWrapper?.nativeElement.textContent)` additionally means that a component which starts with a `markdownText` value and later has it cleared can never fall back to its projected content, because the one chance to read it has passed.
**Fix:** replace the one-shot read with an observation of the projected subtree — a `ContentObserver`/`MutationObserver` on `contentWrapper().nativeElement` (subscribing in the constructor, torn down via `DestroyRef`) that pushes `textContent` into a `projectedText` signal, with `resultHtml` derived from `computed(() => markdownText() ?? projectedText())`. Debounce is unnecessary; the `<pre>` only changes when Angular re-renders the projection. Add a Jest case that binds an interpolated value into the projection, changes it, and asserts the output HTML changes.

**MD-SSR-01 · The projected-content path renders nothing during server-side rendering** — `markdown.component.ts:77-83`, `markdown.scss:6-8`.
`afterNextRender` callbacks are browser-only — they are skipped entirely on the server — and they are the sole writer of `resultHtml` for projected content. A server-rendered page containing `<kbq-markdown ngPreserveWhitespaces>…</kbq-markdown>` therefore emits `<div class="kbq-markdown__output"></div>` with nothing inside it, while the raw markdown source sits in the sibling `<pre class="kbq-markdown__input">` that `markdown.scss:6-8` sets to `display: none`. The consequences are (a) the document is absent from the SSR payload, so crawlers and no-JS clients see an empty region, and (b) after hydration the content appears in one step, producing a layout shift proportional to the document's height — which for the `markdown-article` example is most of a screen. The `markdownText` input path is unaffected, because its setter runs during input binding on the server too; the asymmetry between the two documented usages is itself undocumented. Nothing else in the package is SSR-hostile: the component references no browser global, reaching the DOM only through `viewChild` `ElementRef`s, so `KBQ_WINDOW` is not needed here.
**Fix:** MD-BUG-04's `computed()`-based read fixes this as a side effect only if the projected text is obtained without a DOM read. Since it cannot be (the text is inside a projected `<pre>`), either (a) read `contentWrapper().nativeElement.textContent` synchronously in `ngAfterContentInit`/`ngAfterViewInit`, which does run on the server, and keep the mutation observer as the browser-only incremental path, or (b) document the limitation explicitly and steer SSR consumers to `[markdownText]`. Option (a) is preferable and cheap. Verify with the SSR dev flow rather than a unit test: the server response for a projected fixture must contain `<h1 class="kbq-markdown__h1">`.

**MD-CSS-01 · `display: inline-block` on every child of an ordered-list item breaks nested lists, loose paragraphs and code blocks inside numbered steps** — `markdown.scss:66-82` (specifically `:78-80`).
`.kbq-markdown__ol > li > * { display: inline-block; }` exists so the first child sits on the same line as the CSS-counter marker, but it is applied to *every* element child of the `<li>`. Verified against `marked@17`, all three of the following produce block children of an `<ol>`'s `<li>`: a nested list (`1. first\n    - sub a` → `<li>first<ul><li>sub a</li>…</ul></li>`), a loose list (`1. first\n\n2. second` → `<li><p>first</p></li>`), and a fenced block inside a step (`<li><p>step</p><pre><code>…</code></pre></li>`). Forced to `inline-block`, the nested `<ul>` shrink-wraps and floats up beside the parent text instead of forming an indented block, the loose `<p>` loses its block layout while keeping `.kbq-markdown__p`'s vertical margins, and the `<pre>` shrink-wraps so its `overflow-x: auto` (`markdown.scss:107-109`) no longer has a constrained width to scroll within. None of these shapes appears anywhere in the package's coverage: `markdown-list-example.html:1-15` uses only flat lists, `e2e.html` has no list at all, and the two Jest snapshots use flat lists only — so the committed light/dark baselines cannot catch the regression either.
**Fix:** narrow the rule to the inline run that must share the marker's line rather than all children — e.g. keep `li > p:first-child { display: inline-block; margin: 0; }` and let everything else stay block — or drop the marker hack entirely in favour of `list-style-position: outside` with `list-style-type: decimal` plus the existing gutter padding, which needs no `display` override at all. Add a nested/loose/code-in-step list to `e2e.html` and regenerate the baselines with `yarn run e2e:docker:update-snapshots`.

**MD-A11Y-01 · The scrollable code block has no keyboard access** — `markdown.scss:107-115`, `__snapshots__/markdown.component.spec.ts.snap:469-477`.
`.kbq-markdown__pre { position: relative; overflow-x: auto; … }` makes every fenced code block a horizontally scrollable region, and the rendered element carries nothing else — the snapshot shows `<pre class="kbq-markdown__pre"><code class="kbq-markdown__code">…</code></pre>` with no `tabindex`, no `role` and no focusable descendant. A scrollable container with no keyboard-reachable content is exactly what axe-core's `scrollable-region-focusable` rule flags (tags `cat.keyboard`, `wcag2a`, `wcag211`); it fires whenever the content actually overflows, which for a code block is the normal case rather than the edge case. AGENTS.md states the component library "MUST pass all AXE checks", and no axe assertion exists anywhere in this package, so the violation has never been surfaced. The same shape is claimed for `.kbq-markdown__table` (`markdown.scss:148-153`) but does not apply there — see MD-CSS-02, where that declaration turns out to be inert for a different reason.
**Fix:** emit `tabindex="0"` on the `<pre>` (via the renderer introduced for MD-BUG-02), which is the minimal remedy the rule accepts; add `role="region"` with an `aria-label` sourced from `kbqInjectA11yLocaleConfiguration()` if the block should also be announced as a landmark, but do not hardcode English text. Guard with a `jest-axe` case in `markdown.component.spec.ts` rendering a fenced block, and note that jsdom will not compute overflow — the durable guard is a direct assertion that the rendered `<pre>` carries `tabindex="0"`.

**MD-TEST-01 · The suite proves the markup renders, not that it is correct** — `markdown.component.spec.ts:167-192`, `__snapshots__/markdown.component.spec.ts.snap` (890 lines), `markdown.service.spec.ts:13-40`, `e2e.playwright-spec.ts:8-13`.
The component spec has three cases. Two of them (`:168-172`, `:174-178`) are whole-`DebugElement` `toMatchSnapshot()` calls over the same 90-line kitchen-sink document, which is why the snapshot file is 890 lines — nearly five times the size of every source file in the package combined. Snapshots of that granularity make any class or spacing change a blind re-approval and assert nothing specific about behaviour; the two cases also differ only in *how* the same document is supplied (input vs projection), so the pair duplicates 890 lines to cover one axis. The third case (`:180-191`) is the only behavioural assertion, and it is a good one. The service spec adds three cases (`:13-40`) covering alias mechanics, added by the DS-5215 security commit. What is not covered anywhere: the sanitization contract (MD-BUG-01), rebinding or clearing `markdownText` (MD-BUG-03), reactive projected content (MD-BUG-04), the standalone-import path (MD-ARCH-01), the prefix-collision families (MD-BUG-02), nested/loose lists (MD-CSS-01), and any axe pass (MD-A11Y-01). The Playwright suite is one screenshot pair of one composite fixture (`e2e.playwright-spec.ts:8-13`), which does not include a focused link — so the DS-4849 focus-ring fix has a unit test but no visual guard.
**Fix:** keep one snapshot (drop the duplicate — assert the *projected* path against the *input* path's output instead, which tests the equivalence directly and deletes ~445 lines of baseline), then add targeted cases for each of the gaps listed above. Prefer assertions on the rendered `.kbq-markdown__output` DOM over the service's string wherever the bypass is part of what is being tested. Add a focused-link row to `e2e.html` so the `.cdk-keyboard-focused` outline has a baseline.

### P3 — Nice to have / hygiene

**MD-A11Y-02 · Heading depth is dictated by the document, with no offset for the embedding page** — `markdown.component.ts:34-37`, `markdown.values.ts:5-10`, `e2e.html:3-8`, `packages/docs-examples/components/markdown/markdown-overview/markdown-overview-example.html:2-7`.
`# Heading` renders `<h1 class="kbq-markdown__h1">` verbatim, and the component offers no way to shift the range. Any page that embeds a markdown block below its own `<h1>` — the normal case for a description panel, a release-notes drawer or a help popover — gets a second `<h1>` and a heading outline that no longer reflects the page structure (WCAG 1.3.1; note this is a structural judgement, not an automated axe failure — axe's `heading-order` rule is tagged `best-practice`, not `wcag2a`). The library's own docs pipeline needed exactly this control and built it outside the component: `apps/docs/src/app/components/live-example/markdown-content.ts:15-19` defines the heading classes it consumes as `[2, 3, 4, 5]`, deliberately starting at `h2`, and the docs app does not use `KbqMarkdown` at all — it reuses the `.kbq-markdown__*` classes with its own renderer.
**Fix:** add an optional `headingLevelOffset` input (default `0`) applied by the same renderer that MD-BUG-02 introduces, clamping the result to `h1`–`h6`, and document it in both guides as the way to embed a document inside an existing page outline.

**MD-LIFE-01 · The microtask that starts focus monitoring is not cancelled on destroy** — `markdown.component.ts:85-91, 94-96, 102-115`.
The `effect()` schedules `Promise.resolve().then(() => this.startMonitoringLinks())` (`:87`) rather than calling it directly — an ordering hack (the microtask lands after Angular has applied `[innerHtml]` in the synchronous change-detection pass) that carries no comment explaining why it is there, which AGENTS.md's comment policy specifically asks for. The microtask holds a strong reference to the component and is not cancellable: if the view is destroyed between the effect run and the microtask, `ngOnDestroy` → `stopMonitoringLinks()` (`:95`) runs against an empty `links` array, and the microtask then calls `focusMonitor.monitor()` on anchors in a detached subtree that nothing will ever stop monitoring. The window is narrow but real, and it grows with any consumer that renders markdown inside a rapidly toggled `@if`.
**Fix:** guard the callback with the component's `DestroyRef` (`const destroyed = signal(false)` set from `destroyRef.onDestroy`, or simply check a `private destroyed` flag before monitoring), and add a one-line comment stating why the work is deferred to a microtask at all. Better still, drop the microtask: `afterNextRender`/`afterEveryRender` expresses "after the DOM has been written" directly and is cancelled with the view.

**MD-CSS-02 · Fifteen published tokens are never read, `overflow-x` on the table is inert, and the heading loop shadows its own index** — `markdown-tokens.scss:3, 6, 9, 12, 15, 18, 21, 24, 31, 36, 37, 43, 44, 54, 70`, `markdown.scss:23-34, 148-153`.
Diffing the 73 `--kbq-markdown-*` declarations against every `var()` reference in `markdown.scss` and `_markdown-theme.scss` (including the `#{$i}` interpolated ones) leaves 15 tokens that nothing reads: `--kbq-markdown-h{1..6}-size-max-width`, `-p-size-max-width`, `-list-size-max-width`, `-blockquote-size-max-width`, `-image-size-max-width`, the `--kbq-markdown-size-max-width: 650px` they all point at, `-blockquote-size-border-radius`, `-blockquote-size-border-width`, `-code-size-border-width` and `-code-border`. Because tokens are the library's documented customization surface, a consumer setting `--kbq-markdown-size-max-width: 900px` to widen an article gets silence — the only width constraints that exist are two hardcoded `max-width: 100%` rules on `img` and `table`. Separately, `.kbq-markdown__table { max-width: 100%; overflow-x: auto; display: table; }` (`markdown.scss:148-153`) sets `overflow` on a `display: table` box, where it does not establish a scroll container, so a table too wide for its column content overflows its parent instead of scrolling. Finally, `markdown.scss:23-34` nests a `@for $i from 1 through 6` *inside* another `@for $i from 1 through 6`, shadowing the loop variable; the emitted 36 adjacency rules are what was intended, but the shadowing makes the block read as a bug on every future visit.
**Fix:** either wire the `max-width` family into the corresponding selectors (which is what the token names promise, and would be a visible change requiring new baselines) or delete all 15 declarations; do not leave them advertised and inert. Wrap the table in a `<div class="kbq-markdown__table-wrapper">` with `overflow-x: auto` — which also gives MD-A11Y-01's `tabindex="0"` a sensible home for wide tables. Rename the inner loop variable to `$j`.

**MD-API-01 · Internal alias tables and the class prefix are exported as public mutable arrays** — `tools/public_api_guard/components/markdown.api.md:15, 28, 58, 61`, `markdown.values.ts:1-36`, `public-api.ts:4`.
`public-api.ts:4` re-exports the whole of `markdown.values.ts`, so `MARKDOWN_TAGS_TO_CLASS_ALIAS`, `MARKDOWN_WHOLE_TAGS_TO_CLASS_ALIAS` and `CLASS_PREFIX` all appear as `// @public` in the API report despite each carrying a `@docs-private` JSDoc tag (which affects docs generation, not TypeScript visibility). The two arrays are exported as mutable `string[]`: any consumer can `MARKDOWN_TAGS_TO_CLASS_ALIAS.push('section')` and change the rendering of every `KbqMarkdown` instance in the application, and the alias set becomes a frozen contract the library cannot change without a breaking-change migration. `CLASS_PREFIX` is genuinely load-bearing outside the package — `apps/docs/.../markdown-content.ts:13, 19` derives its DOM query strings from it, with a comment explaining that this keeps a prefix change in sync — so that one should stay public. `protected resultHtml` also surfaces in the report (`markdown.api.md:28`), which is API-Extractor behaviour rather than a defect but adds noise.
**Fix:** keep `CLASS_PREFIX` public (it has a real consumer) and type it `as const`; declare both alias arrays `as const` / `readonly string[]` so they cannot be mutated in place, and consider dropping them from `public-api.ts` entirely once the renderer of MD-BUG-02 makes them internal. Requires `yarn run build:components && yarn run approve-api` (the guard reads `dist/*.d.ts`); removing exports is breaking and needs an `ng-update` migration entry, so schedule with the next major.

**MD-DOC-01 · The guides omit the security contract, the mandatory `ngPreserveWhitespaces`, the module import and the limits of the line-break recipe** — `markdown.en.md:1-68`, `markdown.ru.md:1-68` (specifically `:62-68`).
Four gaps, all verified against the files. (1) Neither guide mentions sanitization, trust boundaries or the service's `NOTE!` — see MD-BUG-01. (2) Every single example, the e2e fixture and both spec hosts use `ngPreserveWhitespaces` on the element, because without it Angular collapses the whitespace that markdown's block syntax depends on — and the string `ngPreserveWhitespaces` appears zero times in either guide, so a reader copying the prose rather than the example gets mangled output with no explanation. (3) Neither guide shows an import; the only setup instruction is `npm install marked` (`markdown.en.md:7-11`). Combined with MD-ARCH-01 this means the documented setup path does not actually produce a working component. (4) `markdown.en.md:66` / `markdown.ru.md:66` say to "add `\n` at the end of the line" with `{ breaks: true }`. That works only because the example's template is a TypeScript template literal, where the compiler resolves the escape into a real newline (`markdown-line-break-with-markdown-text-input-example.ts:11-13`). In an external `.html` template or a static attribute the two characters stay literal, and — verified against `marked@17` with `breaks: true` — render as the visible text `First line\nSecond line`. The e2e fixture inherits the same inline-template dependency (`e2e.ts:9-11`).
**Fix:** add a `kbq-callout` security note to both guides stating that the input must be trusted (or, after MD-BUG-01, describing the opt-in bypass); add a short "Setup" section with the standalone import and the `ngPreserveWhitespaces` requirement and why it exists; and reword the line-break section to say that `\n` must be a real newline in the bound string, showing both the inline-template and the component-field forms. Document `KBQ_MARKDOWN_MARKED_OPTIONS`, `kbqMarkdownMarkedOptionsProvider` and `KbqMarkdownService` by name — all three are public API and none is named in either guide.

**MD-STYLE-01 · Type and construction hygiene** — `markdown.component.ts:47, 57-59, 80-81`, `markdown.service.ts:22-45`, `markdown.component.ts:38`.
Five small items, each verified. `sanitizer` (`:47`) is the only injected field without `readonly`, unlike its three siblings at `:46, 48, 73`. `markdownText` still carries the Angular-migration TODO ("Accessor inputs cannot be migrated as they are too complex", `:57-58`) and remains a decorator accessor pair; once MD-BUG-03 simplifies the setter, the remaining logic is a plain derivation and the input can become `input<string | null>(null)` with a `computed()`. `contentWrapper` is a `viewChild.required` (`:51`), whose read either returns an element or throws — so the optional chaining at `:80-81` (`contentWrapper?.nativeElement`) is dead and misleadingly suggests the value can be absent. `transform()` constructs 22 `RegExp` objects and performs 22 full-string passes on every single parse (`markdown.service.ts:25-42`); the patterns are constant and belong at module scope (moot if MD-BUG-02's renderer lands, which removes the pass entirely). And `styleUrls: ['./markdown.scss', 'markdown-tokens.scss']` (`:38`) mixes a relative-prefixed path with a bare one; AGENTS.md asks for paths relative to the component TS file, so the second entry should read `'./markdown-tokens.scss'`.
**Fix:** add `readonly` to `sanitizer`; drop the dead `?.` at `:80-81`; normalize the `styleUrls` entry; hoist the alias regexes to module constants (or delete them with the renderer); migrate `markdownText` to a signal input once MD-BUG-03 lands, which also clears the TODO. All are covered by the existing suite plus `yarn run eslint`.

## 4. Recommended Remediation Phases

**Phase 1 — Close the sanitization hole and make the component usable standalone.**
IDs: MD-BUG-01, MD-ARCH-01. These are the two findings an external consumer hits first, and neither depends on anything below. Land the safe-by-default rendering path with an explicit, documented trust opt-in, plus the `providedIn: 'root'` change, together with the DOM-level Jest cases described in each finding — including one host that imports `KbqMarkdown` standalone. This phase changes rendered output for documents containing raw HTML, so it needs `yarn run e2e:docker:update-snapshots` and a review of the two baselines.

**Phase 2 — Replace the regex rewrite with a `marked` renderer.**
IDs: MD-BUG-02, MD-A11Y-01, MD-A11Y-02, MD-CSS-02 (table wrapper). One structural change resolves four findings: a `Renderer` supplied through `KBQ_MARKDOWN_MARKED_OPTIONS` emits classes on the tokens it renders (killing the prefix collisions and the duplicate `class`), adds `tabindex="0"` to `<pre>`, applies `headingLevelOffset`, and wraps tables in a real scroll container. Sequence after Phase 1 so the URL allow-list can live in the same renderer rather than being written twice. Acceptance is the collision table in MD-BUG-02 rendering intact.

**Phase 3 — Fix the input and projection lifecycle.**
IDs: MD-BUG-03, MD-BUG-04, MD-SSR-01, MD-LIFE-01. Make `resultHtml` a `computed()` over a signal input and an observed `projectedText`, read the projection synchronously in a lifecycle hook that also runs on the server, and tie the focus-monitoring callback to `DestroyRef`. These four share one refactor of the component's state flow and should not be split. Verified by the new rebind/clear/re-project Jest cases plus an SSR response check.

**Phase 4 — Styles, tests and documentation.**
IDs: MD-CSS-01, MD-TEST-01, MD-DOC-01, MD-API-01, MD-STYLE-01. Fix the ordered-list `inline-block` rule and add the nested/loose/code-in-step fixture rows; collapse the duplicated 890-line snapshot into an equivalence assertion and fill the coverage gaps opened by Phases 1–3; rewrite the two guides' setup, security and line-break sections; freeze the exported alias arrays. `MD-API-01` is the only breaking piece and can be deferred to the next major independently of the rest.

## Appendix A — Review Methodology

Findings were gathered by reading every file in the package (`markdown.component.ts`, `markdown.service.ts`, `markdown.values.ts`, the module and barrels, all three SCSS files, both Jest specs and the 890-line snapshot, the e2e fixture pair, both guides and both examples files), then cross-checking each candidate against five independent sources: the installed parser (`node_modules/marked@17.0.3` — its `.d.ts` option surface and its actual output, exercised through small `node -e` probes rather than any build or test run), the API guard report, the docs navigation (`apps/docs/src/app/structure.ts:732-742`), the docs app's own markdown pipeline (`apps/docs/src/app/components/live-example/markdown-content.ts`), and a repo-wide grep for consumers. The security findings are anchored in verified parser output rather than inferred from the parser's reputation; every corrupted-tag row in MD-BUG-02 is a real transform result, produced by re-running the exact regex construction from `markdown.service.ts:26` over `marked` output. Design tokens were verified as resolvable: the semantic tokens the theme reads (`--kbq-foreground-contrast`, `--kbq-foreground-contrast-secondary`, `--kbq-line-contrast-less`, `--kbq-background-contrast-fade`) are present in both `css-tokens-light.css` and `css-tokens-dark.css`, and the `--kbq-size-*` family resolves from `new/css-tokens.css`.

Refuted during verification:
- **"Injected `<script>` tags execute, so this is remote code execution by default"** — refuted as stated. `innerHTML` does not execute `<script>` elements it inserts. The bypass is still a P0, but on the strength of event-handler attributes and `javascript:` URLs, which were verified to survive; the finding is worded accordingly rather than overclaimed.
- **"External links need `rel=\"noopener noreferrer\"`"** — refuted as a present-day security defect. `marked` emits no `target` attribute (verified for `[t](https://x)` and for raw `<a href>`), so links open in the same tab and reverse tabnabbing does not apply. Adding `rel` is only required once a consumer's renderer sets `target="_blank"`; folded into MD-BUG-01's fix as future-proofing rather than filed separately.
- **"`.kbq-markdown__a` has no visible focus indicator"** — refuted. `_link-theme.scss:131-133` applies `kbq-link-geometry()` to `.kbq-link`, which does suppress the native ring (`:13-15`, `&:focus { outline: none }`), but `:180-184` restores it on `.cdk-keyboard-focused` — the class the component's `FocusMonitor` wiring adds (`markdown.component.ts:102-109`), verified behaviourally by `markdown.component.spec.ts:180-191`. The DS-4849 fix is complete.
- **"`FocusMonitor` monitors leak on every re-render"** — refuted for the steady-state path. `startMonitoringLinks()` opens with `stopMonitoringLinks()` (`markdown.component.ts:103`) and `ngOnDestroy` clears the remainder (`:94-96`). Only the destroy-race window survives, filed at P3 as MD-LIFE-01.
- **"The component uses browser globals and violates the SSR rule"** — refuted. It touches the DOM only through `viewChild` `ElementRef`s; there is no bare `window`, `document` or `getComputedStyle`, so `KBQ_WINDOW` is not required. The SSR problem is `afterNextRender` alone (MD-SSR-01).
- **"`--kbq-markdown-*` references an undefined design token"** — refuted; every referenced base token resolves in both themes. The real token defect runs the other way: 15 tokens are declared and never read (MD-CSS-02).
- **"`examples.markdown.*.md` are dead 🚧 stubs, as in sibling packages"** — refuted. `structure.ts:741` sets `hasExamples: true`, and both files carry real `<!-- example(…) -->` embeds for `markdown-headers-combinations` and `markdown-article`, both registered in `packages/docs-examples/example-module.ts:3936`. The Examples tab is live and correct.
- **"`reducedMotion: 'reduce'` (`playwright.config.ts:101`) freezes a transition in the committed baselines"** — refuted for this package. Neither `markdown.scss`, `markdown-tokens.scss` nor `_markdown-theme.scss` declares a `transition`, an `animation` or a `prefers-reduced-motion` block, so the two screenshots are motion-independent. Recorded here so the next reviewer does not re-derive it.

Corrected on verification:
- **MD-BUG-01** was drafted as an XSS finding centred on `<script>` injection. Verifying `innerHTML` semantics narrowed the mechanism to event-handler attributes, `javascript:` URLs and arbitrary element injection; the severity stayed at P0 because those three are sufficient and because the defect is on by default and undiscoverable from the component's documentation.
- **MD-BUG-02** was drafted as "the alias regex is unanchored and could match inside body text". `marked` HTML-escapes text, so that half is false; the corruption is confined to raw HTML the parser passes through — which is a supported and explicitly tested input (`markdown.service.spec.ts:18-25`). The finding stands with a narrower, fully enumerated trigger.
- **MD-DOC-01's line-break item** was drafted as "the documented `\n` recipe does not work". It does work in the shipped example, because a TypeScript template literal resolves the escape before the string reaches Angular; it fails only in an external `.html` template or a static attribute. Re-filed as a documentation-precision defect at P3 rather than a broken feature.
