# Koobiq `progress-bar` Component — Code Review & Improvement Plan

> Scope: `packages/components/progress-bar` (component, directives, template, tokens, theme, SCSS, Jest spec, e2e fixture + Playwright spec and its two committed baselines, user guides, docs examples, dev app, API guard report) · Commit `b665e503` · 2026-08-28
> Generated by a multi-dimension review (architecture, correctness, accessibility, performance, public API/types, styles, tests, docs) with manual verification of every finding against the source, the in-repo consumers, `playwright.config.ts`, the bundled `axe-core` rule metadata and a byte-level decode of the committed screenshot baselines. 12 findings confirmed (P0×1, P1×2, P2×4, P3×5); 5 candidate findings refuted during verification (see Appendix A). This document is a review + roadmap; no source is modified by it.

## 1. Executive Summary

`KbqProgressBar` is a 54-line component with a 14-line template, two projection directives, four size tokens and four theme tokens. It has never received a functional fix: of the 33 commits touching the package, every one is a migration, a token bump, an e2e restructuring or a lint/format sweep. That shows — the component is small and tidy, and three of its four behaviours are quietly wrong.

- **An indeterminate bar renders as a 100 %-complete determinate bar for every user who has "reduce motion" enabled.** `progress-bar.scss:52-54` kills the animation with `animation: none`, but the bar's width exists *only inside the keyframes* (`progress-bar.scss:7-17`), so the fill element falls back to `width: auto` — full width — over a track it completely covers. This is not a hypothesis: `playwright.config.ts:101` sets `reducedMotion: 'reduce'` for the whole suite, and decoding the committed baseline `__screenshots__/01-light.png` shows the indeterminate row filled solid `#3D76F4` from x=7 to x=604 while the determinate 50 % row above it stops at x=304. The repository has been shipping and screenshot-approving a progress bar that tells a specific accessibility cohort that an unbounded operation is finished (PB-A11Y-01).
- **Only one of the six documented/available `color` values renders anything at all.** The theme mixin sets both `background-color`s under `.kbq-progress-bar.kbq-theme` (`_progress-bar-theme.scss:4`), and that is the only rule in the repository that gives the track or the fill a colour. Any other value — including the `'contrast'` and `'error'` already used in `packages/components-dev/all/template.html:712, 718`, and the `'primary'`/`'secondary'`/`'error'` enum the published guide documents at `progress-bar.en.md:46-56` — leaves both surfaces transparent. Because the text and caption colours are set *outside* the `.kbq-theme` scope (`_progress-bar-theme.scss:14-20`), the label and caption still render, so the component looks alive while the indicator itself is gone (PB-CSS-01, PB-BUG-01).
- **A progress bar with no progress semantics.** The host block (`progress-bar.component.ts:33-38`) binds an id and two modifier classes and nothing else: no `role="progressbar"`, no `aria-valuenow`/`aria-valuemin`/`aria-valuemax`, no accessible name, no `aria-busy`. `grep -rn progressbar packages/` returns zero hits across the entire library. The `[kbq-progress-bar-text]` slot that consumers use as the visible label (`components-dev/progress-bar/template.html:25`) is not wired to the bar by `aria-labelledby` either (PB-A11Y-02).
- **The tests cannot fail.** Four of the seven Jest cases assert `expect(…).toBeDefined()` on values that are `null` when the thing under test is missing — `DebugElement.query` returns `null`, `getAttribute` returns `null`, and `toBeDefined()` accepts both (`progress-bar.component.spec.ts:47, 58, 65, 83`). Three of those four never call `detectChanges()`, so the `@switch` block and the host binding they claim to check have not even been evaluated. The single Playwright test is the one covering indeterminate mode, and per PB-A11Y-01 its baseline is a picture of the bug (PB-TEST-01).

Genuine strengths worth preserving: modern Angular throughout — standalone, `OnPush`, signal `input()`s, host-object bindings, native `@switch`, zero `@HostBinding`/`ngClass`/`*ngIf`; no RxJS, no lifecycle hooks and therefore nothing to leak; fully token-driven styling with not one hardcoded colour and every referenced token resolving in both light and dark; clamping that is correct in both directions and is the one thing the Jest spec really does verify; two live docs examples embedded directly in the guide; a dev app that exercises all four text/caption projection combinations; and a `prefers-reduced-motion` guard that at least shows someone thought about the cohort — the fallback is simply wrong, not absent.

## 3. Prioritized Findings (deduplicated, verified)

### P0 — Release blockers

**PB-A11Y-01 · Under `prefers-reduced-motion: reduce` the indeterminate bar renders as a full, finished determinate bar** — `progress-bar.scss:7-17, 38-43, 49-55`; corroborated by `playwright.config.ts:101` and `packages/components/progress-bar/__screenshots__/01-light.png`.
The fill element `.kbq-progress-bar__line` is given `height: 100%`, a `transform-origin` and a border radius (`progress-bar.scss:38-43`) — but **no width**. In indeterminate mode the width is supplied exclusively by the keyframes, which interpolate it from `25%` to `40%` (`progress-bar.scss:8, 13`). The reduced-motion guard at `:52-54` sets `animation: none`, which removes the only declaration that ever sized the element; the fill then falls back to the block default `width: auto`, i.e. 100 % of `.kbq-progress-bar__inner`, painted with `--kbq-progress-bar-bar-foreground` on top of a track it now fully covers. A user with the OS-level "reduce motion" preference — a setting made *for* people with vestibular disorders — is therefore shown a completed progress bar for an operation whose duration is by definition unknown. It is indistinguishable from `[value]="100"`. There is no consumer-side workaround short of re-declaring library CSS.
The evidence is in the repository, not in theory. `playwright.config.ts:99-102` applies `contextOptions: { reducedMotion: 'reduce' }` to every project, so the e2e suite renders exactly this state; `expect.toHaveScreenshot.animations: 'disabled'` (`:87`) would produce the same outcome independently. Decoding `__screenshots__/01-light.png` (612×220, colour type 2, device scale 2) row by row: the determinate 50 % row at y=52–59 runs fill `61,118,244` from x=7 to x=304 and track `227,230,236` from x=306 to x=604 — correct; the indeterminate row at y=160–167 runs `61,118,244` unbroken from x=7 to x=604 with no track visible at all. `01-dark.png` shows the identical structure with the dark palette. The approved baseline *is* the defect, which is why review after review has passed over it. Note the mirror-image inconsistency in the same file: the determinate `transition: width 0.3s` (`:46`) is **not** inside any reduced-motion guard, so the motion that should be reduced is kept and the motion that carried meaning is deleted.
**Fix:** stop making the fill's existence depend on the animation. Declare a static `width: 25%` on `.kbq-progress-bar_indeterminate .kbq-progress-bar__line` outside the keyframes and let the animation only override it, so `animation: none` degrades to a partial bar that cannot be read as "complete"; drop `width` from the keyframes entirely as part of PB-PERF-01 and animate `transform: translateX()` on that fixed-width element instead. Inside the `prefers-reduced-motion` block, replace the bare `animation: none` with a non-vestibular indicator that still reads as "in progress" — an `opacity` pulse on the same element is the usual choice and is not a motion trigger under WCAG 2.3.3 — and move the determinate `transition: width` into the same block so the two modes are consistent. Add the acceptance test described in PB-TEST-01: an e2e row rendered with `reducedMotion: 'reduce'` whose indeterminate bar is measurably narrower than its determinate `[value]="100"` neighbour. The two baselines must be regenerated with `yarn run e2e:docker:update-snapshots` (native runs fail on font rasterization alone), and the diff should be inspected rather than rubber-stamped — the current picture is exactly what an unreviewed approval produces.

### P1 — High

**PB-CSS-01 · The theme mixin styles only `color="theme"`; every other colour renders an invisible bar** — `_progress-bar-theme.scss:3-12`, `progress-bar.component.ts:52`, `progress-bar.en.md:46-61`; consumers `packages/components-dev/all/template.html:712, 718`.
`KbqProgressBar` extends `KbqColorDirective`, whose setter adds `kbq-<color>` to the host element (`core/common-behaviors/color.ts:57-63`), and the constructor seeds it with `KbqComponentColors.Theme` (`progress-bar.component.ts:52`). The theme mixin then scopes both of its `background-color` declarations under `.kbq-progress-bar.kbq-theme` (`_progress-bar-theme.scss:4`). A grep for `kbq-progress-bar` across every `.scss`/`.css` in `packages/` and `apps/` returns hits inside this package only, and there is no generic `.kbq-contrast`/`.kbq-error` background rule in `packages/components/core/styles/` — so that one selector is the sole source of colour for the track and the fill. Set any other value and both surfaces stay transparent: `<kbq-progress-bar [color]="'error'" …>` at `components-dev/all/template.html:718` and `[color]="'contrast'"` at `:712` render nothing at all, and the published guide's own section — "`color` … Enum ('primary', 'secondary', 'error') … Default: 'primary'" with three copy-pasteable snippets (`progress-bar.en.md:46-56`) — describes a palette that is neither the component's actual default nor drawn from `KbqComponentColors` (`primary`/`secondary` are `ThemePalette` members, `core/common-behaviors/color.ts:7-17`) and none of whose values work. The failure is quiet in the worst way: `_progress-bar-theme.scss:14-20` colours `.kbq-progress-bar-text` and `.kbq-progress-bar-caption` *without* the `.kbq-theme` qualifier, so the label and caption still appear and the component looks present while the indicator has vanished.
Contrast the sibling: `_progress-spinner-theme.scss:102-116` routes its stroke through a `--stroke` custom property with an unconditional default and per-colour overrides for `.kbq-contrast` and `.kbq-contrast-fade`, so an unrecognised colour degrades to the default rather than to nothing.
**Fix:** adopt the spinner's shape. In `_progress-bar-theme.scss`, declare `--track` and `--fill` on `.kbq-progress-bar` unconditionally (defaulting to `--kbq-progress-bar-bar-background` / `-foreground`), have `__inner`/`__line` read those, and add `&.kbq-contrast`, `&.kbq-contrast-fade`, `&.kbq-error` blocks that only re-point the two custom properties — with matching `--kbq-progress-bar-bar-{contrast,error}-…` entries in `progress-bar-tokens.scss`. Then decide the supported set deliberately and rewrite `progress-bar.en.md:46-61` (and add the section to `progress-bar.ru.md`, see PB-DOC-01) to list the `KbqComponentColors` values that actually exist. Guard it with a Jest case asserting the host class per `[color]` value and with an e2e row per supported colour — the current fixture (`e2e.ts:38-41`) exercises only the default, which is why no screenshot has ever caught this.

**PB-A11Y-02 · No `role="progressbar"`, no `aria-value*`, no accessible name** — `progress-bar.component.ts:11-25, 33-38`, `progress-bar.component.html:1-14`.
The host block binds `[attr.id]` and two modifier classes; the template emits two `<ng-content>` slots and a pair of `<div>`s. Nothing in the package carries a role, a value, a range or a name, and `grep -rn "progressbar" packages/ --include="*.ts" --include="*.html"` returns **zero** hits across the whole library — neither this component nor `progress-spinner` has ever exposed progress semantics. Assistive technology therefore sees an unknown element containing two anonymous boxes: the visual fill percentage, the only information the component exists to convey, is available to sighted users and to nobody else (WCAG 1.3.1 Info and Relationships, and 4.1.2 Name, Role, Value for the value part). The `[kbq-progress-bar-text]` directive (`progress-bar.component.ts:11-17`) is what consumers use as the visible label — `components-dev/progress-bar/template.html:25` and the toast integration at `packages/components/toast/e2e.ts:29` — but it is projected *before* the bar as a plain styled `<div>` with no `id` and no `aria-labelledby` link, so even that association is lost. Be precise about the class of failure: axe-core does not flag a custom element that simply carries no role, so this is a WCAG judgement plus a `kbqInjectA11yLocaleConfiguration()` mandate violation from AGENTS.md, not an automated AXE failure — which is exactly why it has survived 33 commits.
**Fix:** add to the host block `role: 'progressbar'`, and value bindings that are emitted only in determinate mode, where they are meaningful: `'[attr.aria-valuemin]': 'mode() === "determinate" ? 0 : null'`, the same for `aria-valuemax` with `100`, and `'[attr.aria-valuenow]': 'mode() === "determinate" ? percentage : null'` — omitting `aria-valuenow` is the specified way to express an indeterminate `progressbar`, and it must stay omitted rather than be pinned to `0`. Add an `ariaLabel` input plus `'[attr.aria-labelledby]'` resolved from a `contentChild(KbqProgressBarText)` that is given a generated id (`kbq-progress-bar-text-N`), falling back to a default string; per AGENTS.md that default must come from `kbqInjectA11yLocaleConfiguration()`, which means adding a `progressBar` key to `KbqA11yLocaleConfiguration` (`core/locales/types.ts:13-38`) and to each locale's `a11y` section. Guard with a Jest suite that asserts the attributes per mode and one `expect(await axe(fixture.nativeElement)).toHaveNoViolations()` case — only five component specs in the library have an axe case today, and this component's inherited `duplicate-id-aria` exposure (PB-BUG-02) makes it worth being one of them.

### P2 — Should fix

**PB-BUG-01 · `setDefaultColor()` is never called, so a falsy `[color]` erases the bar** — `progress-bar.component.ts:49-53`; contrast `progress-spinner.component.ts:75-80`; mechanism in `core/common-behaviors/color.ts:52-66`.
`KbqColorDirective.color`'s setter reads `const color = value || this.defaultColor` (`color.ts:53`) and, when the result is falsy, removes the previous `kbq-<color>` class and adds nothing (`:57-63`). `defaultColor` is only ever populated by `setDefaultColor()` (`:75-77`). `KbqProgressBar`'s constructor assigns `this.color = KbqComponentColors.Theme` but never calls `setDefaultColor` — whereas `KbqProgressSpinner`'s constructor does both, on consecutive lines (`progress-spinner.component.ts:78-79`). The consequence is that `[color]="null"`, `[color]="''"` or a binding that is `undefined` at runtime strips `kbq-theme` from the host, which per PB-CSS-01 is the only selector the theme mixin keys on, and the bar becomes invisible. This is the ordinary shape of a real binding — `[color]="statusColor"` where `statusColor` is not yet resolved — and the JSDoc on `setDefaultColor` describes precisely this case: "this color will be used as a default value. For example `[color]="'' | false | undefined | null"`" (`color.ts:74`).
**Fix:** add `this.setDefaultColor(KbqComponentColors.Theme);` next to the existing assignment in `progress-bar.component.ts:52`, matching the sibling exactly. Cover with a Jest case that binds `[color]="null"` and asserts the host still carries `kbq-theme`; the mutation check is that reverting the one-line fix makes it fail. Land it together with PB-CSS-01 — once the theme mixin has an unconditional default, this fault becomes cosmetic rather than fatal, but the missing call is still a divergence from the sibling with no reason behind it.

**PB-BUG-02 · The same `id` is written to two elements** — `progress-bar.component.ts:34` and `progress-bar.component.html:3`.
The host binds `'[attr.id]': 'id()'` and the template's inner track `<div>` binds `[id]="id()"` to the same signal. Every rendered `<kbq-progress-bar>` therefore contains two elements with an identical `id` — by default `kbq-progress-bar-0`, `…-1`, and so on from the module-level counter at `progress-bar.component.ts:6, 41`; with a consumer-supplied `[id]="'upload'"` both become `upload`. The document is invalid HTML, `document.getElementById()` and `#id` selectors silently resolve to whichever comes first (the host), and a consumer who points a `<label for>` or an `aria-describedby` at the bar gets an ambiguous target. Nothing in the package or the repository ever reads the inner div's id — it is dead, and removing it is behaviour-preserving. On the AXE question, be exact: in the bundled `axe-core` 4.12.1 (`node_modules/jest-axe/node_modules/axe-core`) both `duplicate-id` and `duplicate-id-active` are tagged `deprecated` and ship `enabled: false`, so a bare duplicate is not an automated failure today; `duplicate-id-aria` **is** enabled and tagged `wcag2a`/`wcag412`, so the violation materialises the moment any consumer references the bar's id from an ARIA attribute or a label — which is the only reason to expose an `id` input in the first place.
**Fix:** delete `[id]="id()"` from `progress-bar.component.html:3`. If the inner track genuinely needs a handle (it will, once PB-A11Y-02 moves `role="progressbar"` onto it or wires `aria-labelledby`), derive a distinct one — `[id]="id() + '-inner'"` — rather than reusing the host's. Add a Jest assertion that `fixture.nativeElement.querySelectorAll('[id]').length === 1` for a single bar, and include the axe case from PB-A11Y-02 with a host that also renders `<label [attr.for]>` pointing at the bar, so `duplicate-id-aria` has something to fire on if the duplication returns.

**PB-PERF-01 · The infinite indeterminate animation interpolates `width`, forcing layout on every frame** — `progress-bar.scss:7-17, 49-51`.
`@keyframes kbq-progress-bar-indeterminate` animates two properties: `transform: translateX()`, which the compositor can handle on its own thread, and `width` from `25%` to `40%`, which cannot be composited — every frame of the 2.1 s loop invalidates layout for the fill, its track and their ancestors, then repaints. The animation is `infinite` (`:50`), so the cost is paid for as long as the bar is on screen, which for an indeterminate indicator means "for as long as the slow operation runs" — precisely when the main thread is least available. Multiple simultaneous bars multiply it: the e2e fixture already renders two (`e2e.ts:38-41`), and the toast integration (`packages/components/toast/e2e.ts:29`, `docs-examples/components/toast/toast-hide-overview/…:19`) puts one in every stacked toast. The `width` interpolation also makes the `translateX()` percentages non-linear, because a percentage translate resolves against the element's own — simultaneously changing — width, so the motion the designer specified is not the motion that renders.
**Fix:** move the size out of the keyframes. Give `.kbq-progress-bar_indeterminate .kbq-progress-bar__line` a static `width: 25%` (which PB-A11Y-01 needs anyway) and rewrite the keyframes to interpolate only `transform`, using `translateX()` plus `scaleX()` if the 25 %→40 % growth is a wanted part of the motion — both are compositor-only. `will-change: transform` is not needed once `width` is gone. Verify with a DevTools performance trace over one loop: zero "Layout" entries attributable to `.kbq-progress-bar__line`, where the current implementation produces one per frame. This edits the same rules as PB-A11Y-01 and invalidates the same two baselines, so ship them as one change.

**PB-TEST-01 · Four of seven Jest cases assert nothing, three never run change detection, and the only e2e picture is the P0 bug** — `progress-bar.component.spec.ts:32-37, 39-48, 50-59, 61-66, 79-84, 95-99`; `e2e.ts:38-41`; `e2e.playwright-spec.ts:9-19`.
`DebugElement.query()` returns `null` when the predicate matches nothing, and `Element.getAttribute()` returns `null` when the attribute is absent; `expect(null).toBeDefined()` **passes**. Four cases are built entirely on that: `:47` ("should show determinate line"), `:58` ("should show indeterminate line"), `:65` ("should show determinate line by default") and `:83` ("should auto generate id") would all stay green if the `@switch` block and the `[attr.id]` host binding were deleted outright. Three of the four make it worse by never calling `fixture.detectChanges()` after `TestBed.createComponent` (`:32-37`, `:61-66`, `:79-84`) — the `@switch` compiles to update-mode instructions and host bindings run in update mode, so at the moment those cases assert, the line elements do not exist and the `id` attribute has not been written. They are not weak assertions; they are assertions against an unrendered view. Two further gaps sit in the same file: the test host declares `mode: ProgressBarMode;` and `id: string;` with no initialiser (`:96-98`), so `[mode]="undefined"` is bound for most of the suite — a signal `input()` does not fall back to its declared default when a binding explicitly supplies `undefined`, so `mode()` is `undefined`, *neither* host modifier class is applied and the determinate `transition: width` is silently absent, while the template still renders a determinate line via the `@default` branch (`progress-bar.component.html:8-10`); and `percentage` is only ever asserted on the component instance (`:28, 36`), never against the rendered `style.width`, so the one line of arithmetic that reaches the DOM is untested end to end. On the Playwright side there is a single test (`e2e.playwright-spec.ts:9-19`) over a two-cell fixture, and per PB-A11Y-01 its indeterminate baseline is a picture of the defect.
**Fix:** replace every `toBeDefined()` with a positive assertion — `expect(el.query(By.css('.kbq-progress-bar__line_determinate'))).not.toBeNull()` plus `expect(el.query(By.css('…_indeterminate'))).toBeNull()` so each case pins the branch it names — and add the missing `fixture.detectChanges()` calls. Initialise the host fields (`mode: ProgressBarMode = 'determinate'; id = 'first';`) and add a dedicated case for the explicit-`undefined` binding that asserts what should happen. Add a DOM-level width case (`[value]="40"` ⇒ `line.style.width === '40%'`, and `-50`/`140` ⇒ `0%`/`100%`), a `[color]` class case (PB-CSS-01, PB-BUG-01), an axe case (PB-A11Y-02), and an id-uniqueness case (PB-BUG-02). Extend `e2e.ts` with rows for `value` 0 and 100, one text-plus-caption row, one row per supported colour, and an indeterminate row rendered under `reducedMotion: 'reduce'` next to a `[value]="100"` determinate one — the acceptance criterion for PB-A11Y-01 is that those two cells look *different*. Every case above must be mutation-checked: break the binding it covers and confirm it goes red, because this suite's whole failure mode is passing against a broken component.

### P3 — Nice to have / hygiene

**PB-API-01 · `percentage` is a public getter recomputed on every check, and every exported member is `// (undocumented)`** — `progress-bar.component.ts:45-47`; `tools/public_api_guard/components/progress-bar.api.md:11-25, 28-33, 36-44, 46-55`.
`percentage` is a plain getter over a signal read, bound in the template at `progress-bar.component.html:9`, so it is re-evaluated on every change-detection pass instead of memoising like the `computed()` AGENTS.md prescribes for derived state. It is also `public`, and consequently part of the published API report (`progress-bar.api.md:19`) — the Jest spec is the only thing that reads it, and it reads it precisely because it never checks the DOM (PB-TEST-01). The clamp is additionally unguarded against non-finite input: `Math.max(0, Math.min(100, NaN))` is `NaN`, which Angular writes as `width: NaN%`, an invalid declaration the browser discards, leaving the previous width in place. Separately, the report contains nine `// (undocumented)` markers and closes with "(No `@packageDocumentation` comment for this package)" — `id`, `value`, `mode`, `percentage`, `ProgressBarMode` and both projection directives ship with no prose anywhere, in a package whose two most confusing details (the `[0,100]` range and the indeterminate contract) live only in the guide.
**Fix:** convert to `protected readonly percentage = computed(() => { const v = this.value(); return Number.isFinite(v) ? Math.max(MIN_PERCENT, Math.min(MAX_PERCENT, v)) : MIN_PERCENT; });` — `protected` is enough for a template binding under `strictTemplates` and removes it from the public surface. Add `/** */` blocks to `KbqProgressBar`, its three inputs and both directives, stating the `[0,100]` clamp and that `value` is ignored in indeterminate mode. Both changes rewrite `progress-bar.api.md` (the members move, and JSDoc deletes the `(undocumented)` markers), so run `yarn run build:components` first and then `yarn run approve-api` — the guard reads `dist/*.d.ts`, and the `api` CI job stays red until it is re-approved.

**PB-DOC-01 · The two guides have drifted apart, and neither documents the projection directives** — `progress-bar.en.md:11-61`, `progress-bar.ru.md:11-44`.
Three separate problems. (1) The EN guide is 61 lines and the RU guide is 44: RU stops after the `mode` section and is missing both `#### color` (`en.md:46-56`) and `### Theming` (`:58-61`), so the two language surfaces describe different components. Since PB-CSS-01 establishes that the `color` sections are wrong anyway, the fix direction is to correct EN and then mirror it, not to translate the current text. (2) `KbqProgressBarText` and `KbqProgressBarCaption` are exported public API (`public-api.ts:1`, `progress-bar.api.md:28-33, 46-52`), are the reason the component has a projection surface at all, and are exercised in the dev app (`components-dev/progress-bar/template.html:25, 30, 35-36`) and by `toast` — yet neither guide mentions them, in either language. A consumer has no documented way to discover that a label and a caption slot exist. (3) `en.md:19` reads "This will fill 30% of the hole progress bar" — "hole" for "whole", in published copy.
**Fix:** rewrite `#### color` against the colour set that PB-CSS-01 actually implements, add a `#### kbq-progress-bar-text / kbq-progress-bar-caption` section with a projection snippet lifted from the dev app, fix the typo, and then bring `progress-bar.ru.md` to structural parity section for section. `yarn run e2e:docs` compiles guide snippets, so a corrected `color` example stays corrected once PB-CSS-01 lands.

**PB-DOC-02 · `examples.progress-bar.*.md` are dead placeholder files** — `examples.progress-bar.en.md:1-5`, `examples.progress-bar.ru.md:1-5`, `apps/docs/src/app/structure.ts:802-813`.
Both files carry the standard "🚧 Documentation in progress 🚧" stub. This is not a broken user-facing surface: the docs structure entry sets `hasExamples: false` (`structure.ts:812`), so the Examples tab never renders for progress-bar and the files are unreachable. They are simply two dead files that keep surfacing in "in progress" greps. Two real examples exist and already render inside the guide through the `<!-- example(progress-bar-overview) -->` and `<!-- example(progress-bar-indeterminate) -->` markers (`progress-bar.en.md:25, 44`, mirrored in RU), backed by `packages/docs-examples/components/progress-bar/`.
**Fix:** decide one way. Either delete both stubs — the guide already embeds both examples, so nothing is lost — or populate them with the two `<!-- example(…) -->` embeds and flip `hasExamples: true` at `structure.ts:812`. Deleting is the lower-cost option and matches what the structure entry already declares.

**PB-LIFE-01 · The dev app leaks its interval; `ngOnDestroy` clears an id it never captured** — `packages/components-dev/progress-bar/module.ts:33, 36, 38-44`.
`DevApp implements OnDestroy` and declares `intervalId: number;` (`:36`), but the constructor calls `setInterval(…)` at `:39` **without assigning the returned handle**, so `intervalId` stays `undefined` and `clearInterval(this.intervalId)` at `:43` is a no-op. The timer keeps ticking on a destroyed component and keeps writing `this.percent` forever. It is dev-app-only, so no shipped code is affected, but this is the file a contributor opens to see how the component is driven, and it teaches the wrong pattern. The same class also carries `themePalette = ThemePalette;` (`:33`) which `template.html` never references — a leftover from the `[color]` snippets in `progress-bar.en.md:52-56`. The e2e fixture has a comparable nit: an empty `constructor() {}` at `e2e.ts:36`.
**Fix:** assign the handle (`this.intervalId = setInterval(…)`), or better, drop `OnDestroy` and use `interval(INTERVAL).pipe(takeUntilDestroyed())` in an injection context, which cannot be got wrong. Delete the unused `themePalette` field and the empty `e2e.ts` constructor.

**PB-STYLE-01 · Three inert declarations and one unused `@use` in the stylesheet** — `progress-bar.scss:3, 21, 40, 46, 52-54`.
Four small style-surface issues, none behavioural on its own. (1) `@use '../core/styles/common/tokens' as *;` (`:3`) is never used in this file — the two typography mixins it provides are consumed by `_progress-bar-theme.scss`, which has its own `@use` at its line 1; Sass modules are file-scoped, so the import here is dead. (2) `transform-origin: top left` on `.kbq-progress-bar__line` (`:40`) has no effect: the only transform ever applied is `translateX()`, which ignores the transform origin. It becomes load-bearing the moment PB-PERF-01 introduces `scaleX()`, so it is worth keeping *with a comment* rather than deleting blind. (3) `overflow: hidden` on the host (`:21`) duplicates the guard that already exists on `.kbq-progress-bar__inner` (`:32`) and additionally clips anything painted outside the host box by projected content — an outline or `box-shadow` focus ring on a link inside `[kbq-progress-bar-caption]` would be cut off; the inner element is the only one that needs clipping. (4) The reduced-motion guard covers only the indeterminate branch (`:52-54`) and not the determinate `transition: width 0.3s` (`:46`) — see PB-A11Y-01, where the two are addressed together.
**Fix:** delete the `@use` at `:3`; drop `overflow: hidden` from the host and keep it only on `__inner`, verifying against the Playwright baselines that nothing shifts; annotate or remove `transform-origin` depending on the PB-PERF-01 outcome. `yarn run stylelint` will not catch any of these, so they need a reading pass — and remember that an empty `//` line fails `scss/comment-no-empty`, so separate comment paragraphs with a blank line (`project_scss_comment_no_empty`).

## 4. Recommended Remediation Phases

**Phase 1 — Repair the indeterminate bar.**
IDs: PB-A11Y-01, PB-PERF-01. Both rewrite the same two rules — the keyframes and `.kbq-progress-bar_indeterminate .kbq-progress-bar__line` — and both invalidate the same two baselines, so they must ship as one change or the screenshots churn twice. Move the width out of the keyframes onto a static declaration, animate `transform` only, and replace the bare `animation: none` reduced-motion fallback with something that still reads as "in progress". This is the only P0 and the only defect that actively misinforms users; nothing below depends on it, so it goes first.

**Phase 2 — Make `color` mean something.**
IDs: PB-CSS-01, PB-BUG-01. Restructure `_progress-bar-theme.scss` around unconditional `--track`/`--fill` custom properties with per-colour overrides, following `_progress-spinner-theme.scss:102-116`, and add the missing `setDefaultColor(KbqComponentColors.Theme)` call. The acceptance criterion is that `components-dev/all/template.html:712, 718` renders three visible bars where it currently renders one. Adds tokens, so it lands before the docs rewrite that has to describe them.

**Phase 3 — Give the bar semantics and a unique id.**
IDs: PB-A11Y-02, PB-BUG-02. Add `role="progressbar"` with mode-aware `aria-value*`, an `ariaLabel` input and an `aria-labelledby` link to the projected text; remove the duplicated `[id]` from the template in the same pass, because a `progressbar` whose id is ambiguous is what turns the dormant `duplicate-id-aria` rule live. Requires a new `progressBar` key in `KbqA11yLocaleConfiguration` and in every locale's `a11y` section, and one `build:components` + `approve-api` cycle for the new input.

**Phase 4 — Make the suites capable of failing.**
IDs: PB-TEST-01. Replace the four vacuous `toBeDefined()` assertions, add the missing `detectChanges()` calls, initialise the host fields, and add DOM-level width, colour, ARIA and id-uniqueness cases plus the e2e rows that guard Phases 1–3. In practice this is best interleaved with each phase above rather than deferred — the mutation check (break the binding, confirm red) is what distinguishes these tests from the ones being replaced.

**Phase 5 — API, styles and documentation hygiene.**
IDs: PB-API-01, PB-STYLE-01, PB-LIFE-01, PB-DOC-01, PB-DOC-02. Convert `percentage` to a `protected computed()` with a finite-value guard, add JSDoc across the public surface, clean the four inert style declarations, fix the dev app's interval, rewrite the `color` and projection sections of both guides against what Phases 2–3 actually shipped, and resolve the dead examples stubs. Bundle the API-report churn from PB-API-01 with Phase 3's so `approve-api` runs once.

## 5. Verification Strategy

General gates, run sequentially (never in parallel — see `project_no_parallel_heavy_builds`):
- `npx jest packages/components/progress-bar`, plus `packages/components/toast`, the only shipped package that embeds a `<kbq-progress-bar>`.
- `yarn run eslint`, `yarn run stylelint`, `yarn run prettier` on touched files.
- `yarn run build:components`, then `yarn run check-api`; `approve-api` only in Phases 3 and 5, where the surface intentionally changes — and always after a fresh build, since the guard reads `dist/*.d.ts`.
- `yarn run e2e:docker` for anything visual; baselines regenerate only through `yarn run e2e:docker:update-snapshots`, and every regenerated frame in this package must be eyeballed rather than approved on a green diff — the current baseline is what unreviewed approval produces.
- Manual smoke: `yarn run dev:progress-bar` (all four projection combinations plus a live-ticking value) and `yarn run dev:all` (the three `[color]` variants at `template.html:712-718`), each with the OS "reduce motion" setting toggled on and off.

Per-phase assertions:
- **Phase 1:** with `prefers-reduced-motion: reduce` forced, an indeterminate bar and a determinate `[value]="100"` bar rendered side by side produce different pixels — measured on the regenerated baseline, not asserted by eye. A DevTools performance trace over one full 2.1 s loop attributes zero Layout entries to `.kbq-progress-bar__line`, against one per frame today. With the preference off, the animation still traverses the track end to end.
- **Phase 2:** `<kbq-progress-bar [color]="'error'">` and `[color]="'contrast'"` render a visible track and fill in both themes; `[color]="null"` renders identically to no binding at all. Deleting `setDefaultColor` again makes the null-binding Jest case fail.
- **Phase 3:** `getComputedRole()` on the host reports `progressbar`; `aria-valuenow` is present and equal to the clamped percentage in determinate mode and **absent** in indeterminate mode; `aria-valuemin`/`aria-valuemax` are `0`/`100`; the accessible name resolves to the projected `[kbq-progress-bar-text]` when present and to the locale default otherwise, and follows a `setLocale()` change. `querySelectorAll('[id]')` returns exactly one element per bar, and a host that labels the bar via `aria-describedby` passes `duplicate-id-aria`.
- **Phase 4:** every new Jest case is mutation-checked — deleting the `@switch` block, the `[style.width.%]` binding, the `[attr.id]` host binding or the `role` each turns at least one case red. The four rewritten cases must fail against today's `git stash`ed component, which the `toBeDefined()` versions do not.
- **Phase 5:** `check-api` diffs only the `percentage` visibility change and the removal of `(undocumented)` markers. `progress-bar.en.md` and `progress-bar.ru.md` have the same section list; grepping the guides for `themePalette` and `'primary'` returns nothing; `yarn run e2e:docs` compiles every snippet.

## Appendix A — Review Methodology

Findings were gathered by reading the complete package — all six TypeScript files, the template, all three stylesheets, both guides, both example stubs, the e2e fixture and its Playwright spec — then cross-checking each candidate against six independent sources: the `KbqColorDirective` base class it inherits from (`packages/components/core/common-behaviors/color.ts`), the sibling `progress-spinner` package (which turned two "this looks odd" observations into confirmed divergences), every in-repo consumer found by grepping `kbq-progress-bar`/`KbqProgressBar` across `packages/` and `apps/` (toast's e2e fixture and two docs examples, three dev apps, two docs examples of its own), the API guard report, `apps/docs/src/app/structure.ts`, and the design token files. Two verifications were done mechanically rather than by reading: the bundled `axe-core` rule metadata was queried with `node -e` (`axe.getRules()`) to establish which duplicate-id rules are actually enabled at version 4.12.1, and both committed PNG baselines were decoded with `node`'s `zlib` — IHDR parse, scanline defilter, run-length segmentation per row — to establish what the approved screenshots actually depict. That decode is what turned PB-A11Y-01 from a suspicion into the document's only P0.

Refuted during verification:
- **"The component references undefined design tokens"** — refuted. All eight `var(--kbq-…)` references resolve: `--kbq-background-contrast-fade`, `--kbq-icon-theme`, `--kbq-foreground-contrast` and `--kbq-foreground-contrast-secondary` are all present in both `@koobiq/design-tokens/web/new/css-tokens-light.css` and `-dark.css`, and `--kbq-size-s`, `--kbq-size-xxs`, `--kbq-size-3xs` are defined in `web/css/size.css:6-9`. `timing.$ease-in-out-quad` also exists (`core/styles/functions/_timing.scss:23`).
- **"The duplicate `id` is an AXE failure and therefore a P0 under the AGENTS.md a11y mandate"** — refuted as an automated failure. In the bundled axe-core 4.12.1 both `duplicate-id` and `duplicate-id-active` carry the `deprecated` tag and `enabled: false`; only `duplicate-id-aria` is enabled, and it fires only when the duplicated id is referenced from an ARIA attribute or a label. Filed as P2 (PB-BUG-02) on HTML-validity and consumer-ambiguity grounds instead.
- **"`value` is not clamped, so out-of-range input breaks the bar"** — refuted. `percentage` (`progress-bar.component.ts:45-47`) clamps in both directions, and it is the one thing the Jest spec genuinely verifies (`-50 → 0`, `140 → 100`, `progress-bar.component.spec.ts:6-10, 19-30`). Only the non-finite case is unguarded, which is folded into PB-API-01 rather than filed on its own.
- **"The module-level `idIterator` produces colliding ids"** — refuted. `idIterator++` (`progress-bar.component.ts:6, 41`) is evaluated once per instance in the field initialiser and is monotonic within a document; `jest.config.js:13-14` resets module state between cases, which affects only the numbering seen by tests, not uniqueness. The real id defect is duplication *within* one instance (PB-BUG-02).
- **"`overflow: hidden` on the host clips long projected text"** — refuted as stated. The host is `display: block` and its children are block-level, so text wraps rather than overflowing horizontally, and the host's height is content-driven. The residual risk is narrower — outlines and shadows painted outside the host box by interactive content in the slots — and is filed at that reduced claim inside PB-STYLE-01.

Corrected on verification:
- **PB-A11Y-01** was first drafted as a P2 test-quality finding: "the Playwright baseline captures the indeterminate bar in a meaningless state, because `toHaveScreenshot` disables animations". Tracing *why* the baseline looks the way it does showed that Playwright's `animations: 'disabled'` is not the cause — `playwright.config.ts:101` sets `reducedMotion: 'reduce'`, which activates the component's own `@media` block at `progress-bar.scss:52-54`. The screenshot is therefore an accurate rendering of what real reduced-motion users see, and the finding moved from a test gap to the package's only P0.
- **PB-BUG-01** was first drafted at P1 alongside PB-CSS-01, both described as "the bar can render invisible". Reading `color.ts:52-66` showed the two have different triggers and different fixes — one is a missing one-line constructor call reachable only through a falsy binding, the other is a theme mixin that covers one value out of six — so they were split, and the narrower one dropped to P2.
- **PB-DOC-02** was first drafted as "the Examples tab is broken for progress-bar". `structure.ts:812` sets `hasExamples: false`, so the tab never renders; the impact narrowed from a broken user surface to two unreachable files and the severity dropped from P2 to P3.
