# Koobiq `split-button` Component — Code Review & Improvement Plan

> Scope: `packages/components/split-button` · Commit `af6e64fe` · 2026-07-04
> Generated by a multi-dimension review (parallel research passes + manual adversarial verification of every finding against source). 19 findings confirmed (P0×1, P1×2, P2×8, P3×8); 2 candidate findings refuted during verification (see Appendix A).

---

## 1. Executive Summary

- `KbqSplitButton` is a small, focused composite (174 lines): it styles two projected `KbqButton`s as a single control and wires an optional `KbqDropdownTrigger`. The core propagation logic (style/color/disabled → nested buttons) is sound and covered by 27 passing Jest cases (8.9 s, all green at `af6e64fe`).
- **The release blocker is accessibility.** Neither `KbqSplitButton` nor the underlying `KbqDropdownTrigger` exposes `aria-haspopup`/`aria-expanded`/`aria-controls` (the entire `dropdown` package contains zero ARIA attributes), and every shipped example — docs, e2e, unit fixtures — uses an icon-only menu trigger with no accessible name. A screen reader announces an unnamed button that gives no hint it opens a menu (WCAG 4.1.2, 2.4.6). The fix is shared with the `dropdown` package.
- **Lifecycle is the weakest code area.** The component's only RxJS subscription (`buttons.changes`) is never unsubscribed, and a 50 ms `setTimeout` both survives component destruction and crashes with a `TypeError` when the host has no client rects (hidden tab, `display: none`) because `getClientRects()[0]` is destructured unguarded.
- **The public API carries legacy debt.** Three accessor inputs (`kbqStyle`, `color`, `disabled`) with stale "Skipped for migration" TODOs coexist with one signal input (`panelAutoWidth`); `kbqStyle`'s getter and setter are type-asymmetric (set `'outline'`, get `'kbq-button_outline'`); the `color` override silently disables the reset-to-`defaultColor` behavior the base `KbqColorDirective` provides.
- **Tests cover statics well, dynamics not at all.** All 27 unit cases exercise static templates; the component's only reactive path (`buttons.changes`), destroy-time cleanup, and accessibility have zero coverage. Playwright ships 4 screenshots across 3 tests, dark theme in only one of them.
- Genuine strengths worth preserving: `OnPush`, host object bindings (no `@HostBinding`), standalone component with an NgModule wrapper for legacy consumers, fully token-driven SCSS with no hardcoded colors.

## 3. Prioritized Findings (deduplicated, verified)

### P0 — Release blockers

**SPB-A11Y-01 · Menu trigger has no popup semantics and no accessible name (shared with `dropdown`)** — `packages/components/dropdown/dropdown-trigger.directive.ts:108-116`, `packages/docs-examples/components/split-button/split-button-overview/split-button-overview-example.ts:21-23`.
The `KbqDropdownTrigger` host object sets only `class`, `[class.kbq-pressed]` and mouse/keyboard handlers — no `aria-haspopup`, no `aria-expanded`, no `aria-controls`; a grep across the entire `dropdown` package finds zero ARIA attributes. On top of that, every shipped split-button example (docs overview, e2e harness, unit fixtures) renders the menu trigger as `<button kbq-button><i kbq-icon="kbq-chevron-down-s_16"></i></button>` — an icon-only button with no `aria-label` and no visually hidden text. A screen-reader user hears an unnamed button and has no way to know it opens a menu or whether that menu is open (WCAG 4.1.2 Name/Role/Value, 2.4.6 Headings and Labels). The repo's own AGENTS.md mandates passing AXE and WCAG AA.
**Fix:** in `KbqDropdownTrigger`, add host bindings `'[attr.aria-haspopup]': '"menu"'`, `'[attr.aria-expanded]': 'opened'`, and `[attr.aria-controls]` pointing to the panel id while open (this fixes every dropdown consumer at once, not just split-button). In split-button docs and all examples, add `aria-label` to the icon-only trigger (e.g. `aria-label="More actions"` / `aria-label="Дополнительные действия"`); document it as required for icon-only triggers. Couples with SPB-DOC-01 and SPB-TEST-02.

### P1 — High

**SPB-BUG-01 · `buttons.changes` subscription is never unsubscribed** — `packages/components/split-button/split-button.ts:120-125`.
`ngAfterContentInit` subscribes to `this.buttons.changes.pipe(delay(0))` with no `takeUntilDestroyed`, no stored `Subscription`, and the class implements no destroy hook at all. Every destroyed `KbqSplitButton` instance leaves a live subscriber behind; `delay(0)` additionally re-schedules emissions onto the macrotask queue, so a notification can run the update callbacks *after* the component is destroyed, touching detached DOM via `updateClasses()`.
**Fix:** inject `DestroyRef` (`private readonly destroyRef = inject(DestroyRef)`) and pipe `takeUntilDestroyed(this.destroyRef)` before `subscribe` (note: `ngAfterContentInit` is not an injection context, so the parameterless `takeUntilDestroyed()` form won't work there). Add a destroy-path regression test (see SPB-TEST-01).

**SPB-BUG-02 · Uncancelled 50 ms timer dereferences `getClientRects()[0]` unguarded** — `packages/components/split-button/split-button.ts:161-171`.
When `panelAutoWidth` is set, `updateDropdownParams` schedules `setTimeout(..., 50)` and inside it destructures `const { width } = this.nativeElement.getClientRects()[0]`. Two defects: (a) the timer id is never stored or cleared, so the callback fires after destroy (and re-arms on every `buttons.changes` emission); (b) `getClientRects()` returns an **empty** `DOMRectList` when the element has no layout boxes — `display: none` ancestor, detached node after destroy, collapsed container — so `[0]` is `undefined` and the destructure throws `TypeError: Cannot destructure property 'width' of undefined`. The unit test masks this by mocking `getClientRects` to always return a rect (`split-button.spec.ts:304`).
**Fix:** replace the raw timer with `afterNextRender` (injector-scoped, auto-disposed) or store the id and clear it via `DestroyRef.onDestroy`; read `getBoundingClientRect().width` (never empty) or guard `rects.length` before destructuring; skip the update when width is `0`. Add the hidden-host regression test.

### P2 — Should fix

**SPB-ARCH-01 · Duplicate `<ng-content select="[kbq-button]" />` — the second slot is dead** — `packages/components/split-button/split-button.ts:20-24`.
The inline template declares the same selector twice. Angular assigns every matching projected node to the **first** matching slot, so the second `<ng-content>` never receives anything; it only misleads maintainers into believing there are two distinct slots (e.g. one per button). Runtime behavior is unaffected — this is dead template code at the heart of the component.
**Fix:** collapse to a single `<ng-content select="[kbq-button]" />`. If the original intent was "exactly two buttons", enforce it via the existing `buttons` query (`buttons.length > 2` warning) instead of projection slots.

**SPB-BUG-03 · Content validation runs after the update calls, then throws synchronously** — `packages/components/split-button/split-button.ts:109-118`.
`ngAfterContentInit` first runs all five `update*` calls against a possibly-empty `buttons` list and only then throws `kbq-split-button must contain at least one button`. The updates silently no-op, then the throw aborts change detection mid-cycle — the error surfaces as an unhandled CD exception that is hard to trace back to the offending template (the unit test at `split-button.spec.ts:46-50` confirms the throw escapes `detectChanges()`).
**Fix:** move the guard to the first line of the hook. Consider downgrading to a `console.error`/dev-mode-only throw so a misconfigured template degrades instead of killing the whole CD pass in production.

**SPB-API-01 · `color` override silently disables base reset-to-default semantics** — `packages/components/split-button/split-button.ts:71-77`, base: `packages/components/core/common-behaviors/color.ts:100-117`.
The base `KbqColorDirective` setter maps a falsy value to `this.defaultColor` (explicit reset support). The split-button override starts with `if (!value) return;`, so `[color]=""` or programmatic reset is swallowed — the component keeps the previous color forever (a unit test even pins this behavior: `should not update color when an empty value is set`, `split-button.spec.ts:162-172`). Meanwhile the constructor assigns `this.color = KbqComponentColors.ContrastFade` instead of using the `defaultColor` field designed exactly for this.
**Fix:** set `this.defaultColor = KbqComponentColors.ContrastFade` and delete the early return, delegating falsy handling to the base setter; keep `updateColor(...)` propagation. Re-point the pinned unit test at the corrected semantics.

**SPB-API-02 · `kbqStyle` getter/setter are type-asymmetric; getter doubles as host-class provider** — `packages/components/split-button/split-button.ts:50-59`, host: `split-button.ts:30`.
The setter accepts a raw style (`'outline'` / `KbqButtonStyles.Outline`), but the getter returns the prefixed CSS class (`'kbq-button_outline'`) because the host binding `'[class]': 'kbqStyle'` uses it to drive theme selectors (`_split-button-theme.scss` matches `.kbq-split-button.kbq-button_filled...`). Round-tripping breaks: `sb.kbqStyle = sb.kbqStyle` yields the class `kbq-button_kbq-button_outline`. The declared getter type (`string`) also hides the contract from consumers.
**Fix:** keep the input symmetric (getter returns what the setter accepted) and move the class computation to a separate protected getter for the host binding (e.g. `protected get hostStyleClass() { return `kbq-button_${this._kbqStyle}`; }`). This is an API-visible change — route through `yarn run check-api`/`approve-api` in Phase 3.

**SPB-A11Y-02 · Host exposes no grouping semantics** — `packages/components/split-button/split-button.ts:28-34`.
The host is a plain styled `<kbq-split-button>` container: two adjacent buttons with no programmatic relationship. Assistive technology perceives two unrelated buttons; the visual divider is a CSS `::before` (correctly decorative). The WAI-ARIA pattern for split buttons recommends grouping the pair.
**Fix:** add `role="group"` to the host object plus an optional accessible-name input (`aria-label`), and document the recommendation. Low-risk, pairs naturally with the SPB-A11Y-01 change.

**SPB-ARCH-02 · Mixed input API: three legacy accessor inputs beside one signal input** — `packages/components/split-button/split-button.ts:45,48-91`.
`panelAutoWidth` is a modern `input<boolean>()`, while `kbqStyle`, `color`, `disabled` are `@Input` accessor pairs each carrying the stale auto-migration comment "Skipped for migration because: Accessor inputs cannot be migrated as they are too complex." The same pattern exists in `button`/`button-group`/`core` (this is repo-wide debt, not a split-button invention), but the mixture inside one 174-line class makes the API style incoherent and blocks the signal-based rewrite of the propagation logic.
**Fix:** migrate the three accessors to `input()` with `effect`-driven propagation (or transform functions), coordinated with the identical migration in `button`/`button-group` so the imperative `button.kbqStyle = ...` writes keep working. If sibling coordination is deferred, at least delete the stale TODO comments and document the accessors as intentional.

**SPB-TEST-01 · The only reactive code path (`buttons.changes`) has zero test coverage** — `packages/components/split-button/split-button.spec.ts` (whole file), target: `split-button.ts:120-125`.
All 27 cases use static templates; no test adds or removes a button after init, so the `buttons.changes` subscription — the code that motivated `delay(0)`, re-classing, and re-running `updateDropdownParams` — is never executed by the suite. Destroy-time behavior (SPB-BUG-01/02 fixes) is also untestable today because nothing exercises it.
**Fix:** add cases with `@if`-toggled buttons: (a) second button appears → classes/style/color re-applied, `styles-for-nested` host class flips; (b) button removed → `first`/`second` classes reassigned; (c) fixture destroyed before the `delay(0)`/`setTimeout(50)` callbacks run → no errors, no further DOM writes (use `jest.spyOn(console, 'error')` + fake timers).

**SPB-TEST-02 · No accessibility tests at all** — `packages/components/split-button/split-button.spec.ts`.
The suite asserts CSS classes and input propagation only. Nothing asserts ARIA attributes, accessible names, or keyboard behavior — while AGENTS.md requires every component to pass AXE checks. The gaps of SPB-A11Y-01/02 went unnoticed precisely because no test could catch them.
**Fix:** after the Phase 2 fixes land, add specs asserting: trigger has `aria-haspopup="menu"`, `aria-expanded` toggles with open state, icon-only trigger with `aria-label` exposes the name, host carries `role="group"`. Adopt `jest-axe` for a no-violations smoke on the overview fixture if/when the repo adds it.

### P3 — Nice to have / hygiene

**SPB-STYLE-01 · Copy-pasted JSDoc: "Whether the checkbox is disabled."** — `packages/components/split-button/split-button.ts:79`.
The `disabled` input doc comment was copied from a checkbox. It leaks into IDE tooltips and generated docs.
**Fix:** reword to "Whether the split-button (and all nested buttons) is disabled."

**SPB-STYLE-02 · Magic 50 ms timeout with a hand-wavy comment** — `packages/components/split-button/split-button.ts:162-163`.
"we need to use a timeout of about 50ms to wait for the styles to apply" encodes a layout race as a constant; on a slow frame the width is read too early, on a fast one 50 ms is wasted latency.
**Fix:** superseded by the SPB-BUG-02 rework — `afterNextRender` removes the magic number entirely. If a delay must remain, name the constant and explain the actual dependency.

**SPB-STYLE-03 · One private method is an arrow-function field, siblings are regular methods** — `packages/components/split-button/split-button.ts:154`.
`updateDropdownParams = () => {...}` is the only arrow-function member; it is never passed as a callback, so the binding buys nothing and the style diverges from `updateClasses`/`updateColor`/`updateStyle`/`updateDisabledState`.
**Fix:** convert to a regular private method.

**SPB-STYLE-04 · Theme file mixes `:before` and `::before`** — `packages/components/split-button/_split-button-theme.scss:66,99,104,110` vs `:8,16,23`.
Single- and double-colon pseudo-element syntax are mixed within one file (the base `split-button.scss` consistently uses `::before`).
**Fix:** normalize to `::before`; consider enabling the corresponding stylelint rule repo-wide.

**SPB-ARCH-03 · Decorator content query + plain getters instead of signal query + `computed()`** — `packages/components/split-button/split-button.ts:40,95-101`.
`@ContentChildren(KbqButton)` sits next to the already-migrated `contentChild(KbqDropdownTrigger)` signal query; `firstDisabled`/`secondDisabled` are plain getters re-evaluated on every CD cycle of host bindings. A `contentChildren(KbqButton)` signal + two `computed()`s would make the derived state reactive and delete the manual `changes` subscription altogether (which also structurally fixes SPB-BUG-01). Prefer the optional (non-`required`) query form — the repo has already been bitten by `.required` queries throwing NG0951 in prod builds.
**Fix:** migrate in Phase 4 together with SPB-ARCH-02; the `buttons.changes.subscribe` block becomes an `effect` on the query signal.

**SPB-DOC-01 · Docs have no Accessibility section** — `packages/components/split-button/split-button.en.md`, `split-button.ru.md`.
The docs cover styles, content, states and recommendations, but never mention keyboard interaction or the `aria-label` requirement for the icon-only menu trigger — the exact omission that produced SPB-A11Y-01 in every consumer copy-pasting the examples.
**Fix:** add an "Accessibility" section (EN+RU): required `aria-label` on icon-only triggers, keyboard model (Tab reaches both buttons, Enter/Space activates, menu keys per dropdown), grouping semantics.

**SPB-TEST-03 · Playwright coverage: dark theme in one test only, no interaction states** — `packages/components/split-button/e2e.playwright-spec.ts:11-37`.
Three tests produce 4 screenshots; only "with title, prefix and suffix" captures dark theme. The e2e harness (`e2e.ts`) renders a rich 6-styles × 13-states matrix, but no screenshot captures the open-dropdown state or keyboard-focus divider behavior (`_split-button-theme.scss:28-35`).
**Fix:** add dark variants for the first two tests and one open-dropdown screenshot; the harness already supports it.

**SPB-TEST-04 · Spec hygiene: foreign fixture inside a suite, redundant `detectChanges`** — `packages/components/split-button/split-button.spec.ts:210-219`.
The "disabled input" suite (built around `TestAppInputs`) creates an unrelated `TestApp` fixture inside one test, with a leftover `fixture.detectChanges()` on the suite's own fixture that the test never uses. Harmless but confusing.
**Fix:** move the case to the `firstDisabled/secondDisabled` suite (which already uses `TestApp`) and drop the stray `detectChanges()`.

## 4. Recommended Remediation Phases

**Phase 1 — Lifecycle & crash safety.**
IDs: SPB-BUG-01, SPB-BUG-02, SPB-BUG-03 + regression tests from SPB-TEST-01(c).
Self-contained inside `split-button.ts`; no API changes, no coordination needed. `DestroyRef` + `takeUntilDestroyed` + guarded width read land as one commit. Write the destroy/hidden-host tests first (fail → pass).

**Phase 2 — Accessibility (plus the shared `dropdown` change).**
IDs: SPB-A11Y-01, SPB-A11Y-02, SPB-DOC-01, SPB-TEST-02.
The `aria-haspopup`/`aria-expanded` host bindings belong in `KbqDropdownTrigger` and benefit every dropdown consumer — coordinate as a separate PR against `packages/components/dropdown` with its own review, then update split-button examples/docs (`aria-label` on icon-only triggers, `role="group"` host). This clears the P0.

**Phase 3 — Public API cleanup.**
IDs: SPB-API-01, SPB-API-02, SPB-ARCH-01.
`defaultColor` adoption, symmetric `kbqStyle`, single projection slot. API-visible: run `yarn run build:components` then `yarn run check-api`, and `approve-api` for the intended diff. Update the pinned color-reset unit test.

**Phase 4 — Reactive modernization.**
IDs: SPB-ARCH-02, SPB-ARCH-03, SPB-STYLE-02 (absorbed), SPB-STYLE-03.
`contentChildren()` signal + `computed()` + `effect` replaces the manual subscription and the accessor inputs migrate to `input()`. Coordinate the accessor migration with the identical debt in `button`/`button-group`; if that coordination stalls, ship the query/`computed` part alone — it already deletes the subscription.

**Phase 5 — Hygiene.**
IDs: SPB-STYLE-01, SPB-STYLE-04, SPB-TEST-03, SPB-TEST-04.
Doc comment, pseudo-element normalization, extra screenshots, spec cleanup. Safe to fold into any of the phases above.

## Appendix A — Review Methodology

Two parallel research passes (component deep-dive; review-format extraction) followed by manual verification of every candidate finding against source at `af6e64fe`. Each finding above was confirmed by reading the referenced lines; line numbers are from the working tree at review time.

Refuted during verification (excluded from findings):
1. *"Component is not standalone"* — false: no `standalone: false` in the decorator, so it is standalone by Angular v19+ default; `KbqSplitButtonModule` (`split-button.module.ts`) imports/exports the standalone component as the repo's deliberate legacy-support wrapper.
2. *"`updateDisabledState`'s `undefined` guard hides bugs"* — the guard (`split-button.ts:149`) is deliberate: it prevents clobbering per-button `disabled` bindings when the group-level input was never set (`_disabled` is uninitialized by design).

Also corrected: an initial automated pass reported "16 test cases"; the actual count is 27 `it()` blocks (verified by reading the spec and by the Jest run).
