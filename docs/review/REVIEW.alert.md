> Scope: `packages/components/alert` + shared `core/common-behaviors` (color), `icon/icon-button`, `button`, `link` touchpoints, and the `filter-bar` consumer · Commit `ba927bfd` · 2026-07-13

## 1. Executive Summary

- **The published API is misdescribed and partly self-contradictory — the two highest-severity findings.** The API-guard snapshot `alert.api.md` predates the Angular-20 signal migration and still lists the pre-migration decorator surface (`compact: boolean`, `button: KbqButton`) instead of the shipped `InputSignal`/`Signal` members, so a breaking TS-API change went unrecorded by the mechanism that exists to record it (`ALERT-API-01`). Separately, `alertColor` is an asymmetric accessor whose getter returns a CSS class (`kbq-alert_error`) while the setter takes a raw color, so the published input does not round-trip and reads back a value you cannot assign to it (`ALERT-API-02`).
- **The unit suite is a single smoke assertion — every behavior ships untested.** The whole Jest spec renders a bare `<kbq-alert />` and asserts one static host class (`ALERT-TEST-01`); deleting the `Info → Contrast` icon mapping, the color/style/compact host classes, or the `|| KbqAlertColors.Info` fallback would keep CI green.
- **Accessibility is the broadest weak dimension, but confined to documented patterns and guidance — no in-component release blocker.** The component host correctly stays role-less (right for static alerts), yet nothing documents `role="alert"`/`aria-live` for dynamically shown ones — the repo's own consumer had to hand-add it (`ALERT-A11Y-01`). The documented close control is a non-button `<i kbq-icon-button>`: focusable but not keyboard-activatable and unnamed in every example and the e2e fixture (`ALERT-A11Y-02`). Status is conveyed by icon color alone (`ALERT-A11Y-03`), and in the light theme the default-style warning and success icons compute below the 3:1 non-text-contrast minimum against the shared background (`ALERT-A11Y-04`).
- **A cluster of small correctness and half-migration defects.** The normal-size icon padding is mis-wired (base rule omits `padding-top`, the titled branch consumes the *no-title* token, leaving `--kbq-alert-size-normal-icon-padding-top` dead) so icons sit 2px off spec (`ALERT-BUG-01`); the projected icon is tinted once in `ngAfterContentInit` and never re-reacts to a later `alertColor` change or a late-arriving icon (`ALERT-BUG-02`); and `alertColor` remains a decorator accessor with no `markForCheck`, alongside signal inputs (`ALERT-ARCH-01`).
- **What's strong:** the component is on the modern baseline — standalone, `OnPush`, `host` object bindings, signal `contentChild()` queries, `input()` for `compact`/`alertStyle`, native `@if` control flow, a clean BEM + design-token style architecture, and the empty slot directives + retained legacy `NgModule` follow an established repo idiom (not debt). The skeleton is right; the API contract, the tests, and the a11y guidance are not.
- **Key next actions:** Phase 1 (API integrity + accessibility guidance) has the highest leverage; Phase 2 (correctness/lifecycle of `alertColor` and the icon tint) is a coordinated breaking change; Phase 3 (tests) should land as the regression net for Phases 2–4.

## 3. Prioritized Findings (deduplicated, verified)

### P1 — High

**ALERT-API-01 · API-guard snapshot is stale: `alert.api.md` predates the signal migration and misdescribes the shipped API** — `tools/public_api_guard/components/alert.api.md:21-41`, `packages/components/alert/alert.component.ts:68-76`
`alert.component.ts` now uses `input()`/`contentChild()`, whose emitted `.d.ts` exposes `InputSignal<…>`/`Signal<…>` members and `"isSignal": true` markers in the `ɵcmp` declaration. The committed snapshot still shows the pre-migration decorator surface — `compact: boolean;`, `alertStyle: KbqAlertStyles | string;`, `button: KbqButton;` — and an `isSignal`-free `ɵcmp`. Git history pins the miss: `alert.api.md` was last touched in `f635c230` ("removed theme style"), while the signal migration landed later in `17bc91dd` ("angular 20"), which *did* regenerate `toggle.api.md` (see `toggle.api.md:30-93` — `readonly big: …InputSignal<boolean>`, `"isSignal": true`) but skipped alert. The signal migration is itself a breaking TS-API change (`alert.compact` property → `alert.compact()` call) and it went unrecorded by the guard that exists to catch exactly this — meaning `approve-api` was not re-run against a fresh build after the migration. Anyone auditing SemVer impact or consuming the report gets the wrong API.
**Fix:** `yarn run build:components` then `yarn run approve-api` (the guard reads `dist/*.d.ts`, so the build must precede it or it revalidates stale output — the likely root cause of the miss); review the alert diff for `InputSignal`/`Signal`/`isSignal` markers, and record the signal migration as a breaking change in the changelog if the 20.x notes omit it. This single approve-api pass should absorb the snapshot side effects of `ALERT-API-04`, `ALERT-API-06`, `ALERT-API-07`, `ALERT-ARCH-03`, `ALERT-ARCH-04`, and `ALERT-DOCS-01`.

**ALERT-API-02 · Asymmetric `alertColor` accessor: you set `'error'` but read back `'kbq-alert_error'`, and a round-trip corrupts state** — `packages/components/alert/alert.component.ts:80-89` (host binding `:59`; `tools/public_api_guard/components/alert.api.md:18-19`)
The getter returns `` `kbq-alert_${this._alertColor}` `` while the setter stores the raw color, and the getter exists only to feed host `'[class]': 'alertColor'` (`:59`) — an input accessor doing class-name formatting. The published pair (`get alertColor(): string` / `set alertColor(value: string | KbqAlertColors)`) is not round-trip-safe: after `[alertColor]="'error'"`, reading `alert.alertColor` yields `'kbq-alert_error'`, so `alert.alertColor === KbqAlertColors.Error` is always false, and a single read-then-write (`alert.alertColor = alert.alertColor`, a proxying wrapper, or state save/restore) stores `'kbq-alert_error'` into `_alertColor`, producing the double-prefixed class `kbq-alert_kbq-alert_error` — which matches no rule in `_alert-theme.scss:16-50`, so the alert silently loses its background. Normal template usage never triggers it (no in-repo code reads the input programmatically), so this is a published-API trap, not a runtime regression on the main path — but that is exactly the P1 API category by the toast precedent (`TOAST-API-01/02`).
**Fix:** Mirror the in-repo precedent that already separates the two concerns — `KbqColorDirective` has `get color()` (raw, `color.ts:101-103`) and `get colorClassName()` (class string, `color.ts:94-96`). Make the getter return `this._alertColor` and bind the host class via a dedicated `protected get alertColorClass()`; retyping the getter is itself a behavioral break for anyone reading it, so land it with the `input()` migration (`ALERT-ARCH-01`) and re-`approve-api`.

**ALERT-TEST-01 · Unit suite is a single static-class smoke test; all alert logic ships untested** — `packages/components/alert/alert.component.spec.ts:23-25` (sole test), `:28-35` (bare `TestApp`); untested surface `packages/components/alert/alert.component.ts:57-101`, `alert.component.html:1-23`
The entire Jest suite is one `it('should add class')` asserting `classList.contains('kbq-alert')`, and `TestApp`'s template is a bare `<kbq-alert />` with no inputs and no projected content, so even that test exercises nothing configurable. Zero coverage exists for: the `alertColor` accessor round-trip and its `|| KbqAlertColors.Info` falsy fallback; `alertStyle`/`isColored` → `kbq-alert_default` vs `_colored`; `compact()` → `_normal` vs `_compact`; `kbq-alert_dismissible` on a projected close button; the `ngAfterContentInit` icon tint (the `Empty → _alertColor` assignment, the `Info → Contrast` special case at `:99`, and the leaves-non-`Empty`-alone guard); and all template branches (`@if (iconItem() || icon())`, `@if (control())`, `[hidden]="!closeButton()"`) plus the `_title`/`_has-button` modifier toggles. Concrete failure: deleting the `Info → Contrast` mapping or the setter fallback breaks every default info alert yet the suite stays green. Even the simple `link` component has 5 unit tests.
**Fix:** Expand `TestApp` with bindable inputs and projected icon/title/close/control content, then add three grouped blocks: (1) host classes — `alertColor` set/get round-trip incl. falsy→`kbq-alert_info`, default/colored, normal/compact, dismissible-when-projected; (2) `ngAfterContentInit` — `Empty` icon receives `_alertColor`, info alert receives `Contrast`, an explicitly-colored icon is left untouched; (3) template — `.kbq-alert__icon`/`.kbq-alert__button-stack` render only when their content is projected, and the `*_title`/`_has-button` classes toggle. While there, drop the redundant `KbqAlertModule` from `TestBed.configureTestingModule` (`spec:13`) since the standalone `TestApp` already imports it. Land with Phase 2 as its regression net.

### P2 — Should fix

**ALERT-ARCH-01 · Half-migrated input API: `alertColor` is a legacy `@Input()` accessor without `markForCheck`, alongside signal inputs** — `packages/components/alert/alert.component.ts:78-89`, `:59-64`
`compact` and `alertStyle` are signal inputs, but `alertColor` remains a decorator getter/setter, leaving the component with two reactivity models — the only decorator `@Input` in the file, acknowledged by the migration TODO at `:78-79`. Unlike the equivalent skipped-migration accessors in `toggle.component.ts:108-118` / `:141-148` (which inject `ChangeDetectorRef` and call `markForCheck()` in the setter), this setter performs no change notification. Verified against installed `@angular/core`: host bindings run in the declaring (parent) view's `refreshView`, so an imperative write via the public setter goes stale precisely when nothing else dirties the parent chain — a Default-CD zone app self-heals on the next tick, but an OnPush-parent or zoneless app leaves the host `'[class]'` stale indefinitely. It also blocks reactive derivation (the icon-tint `effect()` fix in `ALERT-BUG-02` needs a signal to track). Folding in the performance angle: the getter-based host bindings (`alertColor`, `isColored` invoked twice per pass) are re-evaluated every CD cycle instead of `computed()` — negligible on a leaf component, but resolved for free by the same migration.
**Fix:** Migrate to `readonly alertColor = input(KbqAlertColors.Info, { transform: (v: KbqAlertColors | string | null) => v || KbqAlertColors.Info })` and derive the host class via `computed()`; make `isColored` a `computed()`. This is the keystone for `ALERT-API-02`, `ALERT-BUG-02`, and `ALERT-API-03`. Interim minimum if the migration must wait: inject `ChangeDetectorRef` and `markForCheck()` in the setter.

**ALERT-BUG-01 · Normal-size icon padding is mis-wired: the titled branch uses the no-title token and the base no-title padding is missing, leaving `--kbq-alert-size-normal-icon-padding-top` dead** — `packages/components/alert/alert.component.scss:29-41` (base rule `:29-31`, wrong token `:36`), `alert-tokens.scss:15`
The compact block wires this correctly: the base `.kbq-alert__icon` gets `padding-top: var(--kbq-alert-size-compact-no-title-icon-padding-top)` (2px) and the `_title` branch overrides with `--kbq-alert-size-compact-icon-padding-top` (4px). The normal block deviates twice: (1) the base rule sets only margin, so a normal alert *without* a title renders its icon with `0` top padding instead of the intended 2px; (2) the `_title` branch consumes the *no-title* token (2px) instead of `--kbq-alert-size-normal-icon-padding-top` (4px). Verified against `@koobiq/design-tokens` (`icon-padding-top: 4px`, `no-title-icon-padding-top: 2px`; `--kbq-size-xxs = 4px`, `--kbq-size-3xs = 2px`), the token defined at `alert-tokens.scss:15` is consumed nowhere in the repo, and normal-size icons sit 2px off spec next to the subheading title. Because the Playwright baselines pin the current (wrong) pixels — and the no-title normal-icon state is absent from the baselines entirely (`ALERT-TEST-02`) — CI cannot catch it.
**Fix:** Mirror the compact wiring — add `padding-top: var(--kbq-alert-size-normal-no-title-icon-padding-top)` to the base `.kbq-alert__icon` rule and change the `_title` branch to `padding-top: var(--kbq-alert-size-normal-icon-padding-top)`; regenerate the two screenshot baselines.

**ALERT-BUG-02 · Icon auto-coloring is a one-shot mutation in `ngAfterContentInit` — never reacts to `alertColor` changes or late-arriving icons** — `packages/components/alert/alert.component.ts:95-101`
The hook runs exactly once and, after the first assignment, `icon.color !== Empty` so the guard permanently rejects re-tinting. Two verified scenarios: (a) `<kbq-alert [alertColor]="status()">` with an uncolored projected icon — when `status` changes error→success the container recolors (the `'[class]'` host binding re-evaluates) but the icon keeps its stale `kbq-error` class (the color setter mutates `classList` directly, `color.ts:105-119`), yielding a red icon on a green alert; (b) `icon()`/`iconItem()` are live signal queries, so an icon rendered later by a consumer `@if` toggles the template's icon wrapper yet stays `kbq-empty` because the hook never re-fires. `alert.en.md:1` positions the component to "signal a status change", so dynamic color is a mainstream scenario. Severity is P2 (not P1): no in-repo consumer breaks (`filter-save-popover` recreates the whole alert via `@if`; all examples use static colors), the trigger needs dynamic `[alertColor]` plus reliance on auto-tint, and the workaround (explicit `[color]` on the icon) is trivial.
**Fix:** After the `input()` migration (`ALERT-ARCH-01`), replace the hook with an `effect()` that tracks `icon() || iconItem()` and the color, recording the last auto-assigned value so consumer-set colors are respected (re-tint only when `color === Empty || color === lastAutoColor`). Note the proposed `effect()` cannot track color until `alertColor` is a signal, so this must land with `ALERT-ARCH-01` (or mirror `_alertColor` into a private signal).

**ALERT-BUG-03 · `alert-content` example: clicking the close button does nothing (`state` toggled but never read)** — `packages/docs-examples/components/alert/alert-content/alert-content-example.html:65,78`, `alert-content-example.ts:37`
Both close buttons in the third row bind `(click)="state = !state"` (declared `state = true`), but — unlike `alert-close-example` — nothing in the template binds `[@hideShowAnimator]="state"` or otherwise reads `state` (grep for `hideShowAnimator` over the template returns nothing; the trigger declared at `ts:24-29` is dead). On the public docs "Content" page a user clicks the X and nothing happens, contradicting the guide's claim that the block "can be hidden by clicking the icon button" (`alert.en.md:19`). A single shared `state` could not close the two alerts independently even if bound. Severity P2 (docs-example-only, per the toast precedent capping docs defects at P2).
**Fix:** Bind `[@hideShowAnimator]` per alert with independent state fields (as `alert-close-example` does), or drop the close buttons from this example; also delete the dead `hideShowAnimator` metadata (see `ALERT-DOCS-03`).

**ALERT-API-03 · Enum-or-string unions (`KbqAlertStyles | string`, `string | KbqAlertColors`) accept any typo at compile time** — `packages/components/alert/alert.component.ts:76,85`
TypeScript absorbs `Enum | string` into plain `string` (string enums are string subtypes), so `strictTemplates` accepts any typo: `[alertStyle]="'colred'"` compiles and silently renders the default style (isColored strict-compares at `:91-93`), and `alertColor="danger"` compiles and produces the class `kbq-alert_danger`, which matches nothing in `_alert-theme.scss:16-50` (only error/warning/success/info are themed) — a total, diagnostic-free loss of styling from a one-character typo. The enums buy nothing they don't already cover. The current repo direction is closed literal unions (`flag.api.md` `KbqFlagShape = 'rectangle' | 'square' | 'circle'`; `toggle`'s `ToggleLabelPositionType`).
**Fix:** Narrow to `` KbqAlertStyles | `${KbqAlertStyles}` `` (and the color analogue), which keeps existing consumers compiling — `filter-save-popover.ts:48-49` passes the string literals `'error'`/`'colored'` — while rejecting typos. Narrowing is breaking for arbitrary-string passers, so target the next major with an interim dev-mode warning for unknown values; if custom color strings are an intended extension point, document that contract.

**ALERT-API-04 · `compact` lacks a `booleanAttribute` transform — static `<kbq-alert compact>` silently does nothing** — `packages/components/alert/alert.component.ts:75`
Without a transform, the static-attribute form binds the literal string `''` to the input; `''` is falsy, so `!compact()` keeps `kbq-alert_normal` — the attribute is a silent no-op, and `compact()` then returns `''` rather than a boolean, violating the declared type. `compact="true"` only accidentally works (passes the string `'true'`). All in-repo usages happen to use `[compact]="…"` (`e2e.ts`, `filter-save-popover.ts:50`), so the trap is latent for external consumers — exactly who a design-system input contract must protect. The repo norm is the transform (`booleanAttribute` appears 85× across 40+ component files, including the newest, `flag.ts:42`).
**Fix:** `readonly compact = input(false, { transform: booleanAttribute });` (import from `@angular/core`) — additive; folds into the `ALERT-API-01` approve-api pass (type becomes `InputSignalWithTransform<boolean, unknown>`).

**ALERT-API-05 · No outputs at all — no `closed`/`dismissed` event; every consumer hand-wires the close behavior** — `packages/components/alert/alert.component.ts:67-102`
The component reserves and styles a close-button slot and applies the `kbq-alert_dismissible` host class (`:64`), but ships no output and no built-in dismiss behavior (`api.md:41` outputs map is `{}`). Every consumer re-implements it: `alert-close-example.ts:25` toggles an animation flag on `(click)`; `filter-save-popover.ts:44-54` wraps the alert in `@if` with its own flag. Nothing standardizes when "dismissed" fires. Repo precedent for completing such an API: `tags/tag.component.ts:314` `readonly removed = output<KbqTagEvent>()`.
**Fix:** Add `readonly closed = output<void>()` emitted from a `(click)` listener on the `.kbq-alert__close-button` wrapper (or host-forwarded from `KbqAlertCloseButton`); purely additive, and pairs naturally with the `ALERT-A11Y-02`/`ALERT-A11Y-06` a11y fixes.

**ALERT-DOCS-01 · Entire public surface has zero JSDoc — every export and member is `(undocumented)` in the API report** — `packages/components/alert/alert.component.ts:15-102` (report `tools/public_api_guard/components/alert.api.md:15-100`)
There is not a single doc comment in the package; all 8 exports and every member carry `(undocumented)`. The docs site's API reference is generated from source comments (`package.json:180` `docs:api-gen`), so the alert API tab renders with empty descriptions — nothing explains what `Colored` vs `Default` means, that `alertColor` drives the icon auto-coloring, or what contract each slot directive fulfills. Below the AGENTS.md maintainability bar and the repo's current standard (`flag.ts` documents every input with `@default` tags; `button.api.md` has documented members).
**Fix:** Add English JSDoc (repo policy — comments must be English) to `KbqAlert`'s inputs/getters, the three directives, and both enums, then fold the re-approve into the `ALERT-API-01` build+approve-api pass. This is what fills the auto-generated API tab that the guide's missing input tables (`ALERT-DOCS-02`) rely on.

**ALERT-A11Y-01 · No `role="alert"`/`aria-live` mechanism or guidance for dynamically shown alerts** — `packages/components/alert/alert.component.ts:57-65`, `alert.en.md:17-21`, `packages/components/filter-bar/filter-save-popover.ts:47`
Re-adjudication of monorepo **A11Y-30**, confirmed at P2. The host applies only classes — which is *correct* for statically rendered alerts, since forcing `role="alert"` would double-announce page-load content (WAI-ARIA APG). But the component and docs offer no mechanism and no guidance: `alert.en.md`/`alert.ru.md` contain zero mentions of `role`/`aria-live`/`aria-atomic` despite positioning the component for status changes and problems (`:1`) and documenting dynamic hide (`:19`). The library's own consumer proves the gap — `filter-save-popover.ts:47` hand-adds `role="alert"` to its conditionally rendered error alert, knowledge external consumers won't have. P2 (not P0 like toast's `TOAST-A11Y-01`) because alert is frequently static and persistent, and correct usage is one attribute away — a guidance defect, matching the original A11Y-30 rating.
**Fix:** Add an accessibility section to both guides: for dynamically inserted alerts set `role="alert"` (or `aria-live="polite"` + `aria-atomic="true"` for non-urgent status), citing the `filter-save-popover` usage; optionally expose it as an input, or recommend `LiveAnnouncer` from `@angular/cdk/a11y` (already a dependency).

**ALERT-A11Y-02 · Documented close control (`<i kbq-icon-button>`) is focusable but has no button role, no keyboard activation, and no accessible name** — `packages/docs-examples/components/alert/alert-close/alert-close-example.ts:21-26`, `alert-content/alert-content-example.html:61-66,74-79`, `packages/components/alert/e2e.ts:46-50`, `packages/components/icon/icon-button.component.ts:24-32`
Re-adjudication of monorepo **A11Y-32**, confirmed and applied to alert. `KbqIconButton` uses an attribute selector and its host binds only `tabindex`/`disabled` — no `role="button"`, no `keydown` handling anywhere in the icon package. Every alert close usage in the repo puts it on an `<i>` with a `(click)` handler and no `aria-label`/`aria-labelledby` (grep for `aria-|role=` across the alert docs-examples and `e2e.ts` returns zero). Result: a keyboard user Tabs to the control (`tabindex=0`) but Enter/Space do nothing — the documented "Hide" feature (`alert.en.md:19`) is mouse-only (WCAG 2.1.1), and a screen reader announces a nameless generic element (WCAG 4.1.2). Severity P2 (not P0 like toast's `TOAST-A11Y-02`) because the alert component ships no close control — only a slot; the root defect is the icon package (A11Y-32), and the alert-side manifestation lives entirely in docs examples and the visual-regression fixture — the exact `TOAST-A11Y-06` case.
**Fix:** In all docs examples and `e2e.ts`, use a native button with a name — `<button kbq-alert-close-button kbq-icon-button="kbq-xmark-s_16" aria-label="Close">` (RU examples: «Закрыть»); the `button.kbq-icon-button` styles already exist (`icon-button.scss:26-29`). Add an a11y note to the Hide section of both guides. The `role`/`keydown` root-cause fix belongs to the icon package; optionally `KbqAlertCloseButton` can add defensive `role="button"` + Enter/Space forwarding when its host is not a native button.

**ALERT-A11Y-03 · Alert severity is conveyed only by icon color/glyph, with no text alternative for assistive technology** — `packages/components/alert/alert-tokens.scss:43-54`, `alert.en.md:9`, `alert.component.ts:95-101`, `packages/docs-examples/components/alert/alert-status/alert-status-example.html:1-24`
All four default-style variants share one background (every `--kbq-alert-default-*-container-background` is `var(--kbq-background-contrast-less)`), and `alert.en.md:9` states alerts "stand out only by the icon color"; `ngAfterContentInit` auto-tints the icon to the status color, reinforcing color as the sole channel. Icons expose no text alternative and are not `aria-hidden`, so error/warning/success/info status is invisible to screen-reader users unless the message text restates it — and in `alert-status-example` all four alerts share identical body text. Worse for the critical pair: warning and error use the *same* glyph `kbq-triangle-exclamation_16`, so even sighted differentiation between them is color-only (WCAG 1.4.1 / 1.1.1). Consumers control all text, so this is a docs/pattern gap (matching toast's `TOAST-A11Y-04` at P2), not a component code defect.
**Fix:** Docs guidance — include the severity in the title/text or add visually-hidden severity text (`<span class="cdk-visually-hidden">Error:</span>`); mark decorative status icons `aria-hidden="true"` in examples; and give error and warning distinct glyphs in the status example.

**ALERT-A11Y-04 · Default-style warning and success status icons compute below the 3:1 non-text-contrast minimum (light theme)** — `packages/components/alert/alert-tokens.scss:46`, `packages/components/icon/icon-tokens.scss:8`, `alert.component.ts:98-99`
For a default-style warning alert the auto-assigned icon color resolves `kbq-warning → --kbq-icon-warning-color → --kbq-icon-warning`. In the shipped light theme (`@koobiq/design-tokens/web/css-tokens-light.css`), `--kbq-icon-warning` is `hsl(38,100%,42%)` ≈ `rgb(214,136,0)` and `--kbq-background-contrast-less` is `hsl(229,15%,96%)` ≈ `rgb(243,244,246)`: computed contrast ≈ **2.59:1**, below the WCAG 1.4.11 (AA) 3:1 minimum. The success icon fails too (`--kbq-icon-success` ≈ **2.79:1**); error passes (4.33:1) and info/contrast passes (14.2:1). Because the docs declare the icon the *only* thing distinguishing default alerts (`alert.en.md:9`), this graphic is required to understand the content, so 1.4.11 applies. ## Appendix A — Review Methodology

Seven specialized reviewers ran in parallel — architecture & conventions, correctness & lifecycle, accessibility, public API & types, performance + templates & styles, tests, and docs & examples + shared touchpoints — each scoped to its dimension with seeded suspicions from a maintainer pre-read and required to attach a verbatim source quote to every claim. The 50 raw findings were deduplicated into 37 candidates, then every candidate was adversarially verified by three skeptics (disjoint batches) against the actual source at this commit and, where behavior depended on the framework, against installed sources: `@angular/core` 20.3.25 (`input()`/`contentChild` `descendants` default, host-binding change detection and `markForCheck`), `@koobiq/design-tokens` (light-theme contrast numbers and size tokens, computed by hand), and `sass 1.93.3` (compiled to check the `mixed-decls` claim, which was refuted). Verdicts were confirmed (24) or adjusted (13); none were refuted, though several finder suspicions were disproved and are listed at the end of §3. Prior monorepo findings A11Y-30, A11Y-32 and A11Y-15 were re-adjudicated with fresh code evidence rather than inherited. Severity was held to the toast-review precedent, deliberately resisting inflation on a small presentational component: the alert host itself ships no accessibility blocker (P0×0) because it renders only classes and provides slots; its accessibility failures live in the documented patterns, examples, and guidance.
