# Koobiq `input` Component — Code Review & Improvement Plan

> Scope: `packages/components/input` (`KbqInput`, `KbqInputPassword`, `KbqNumberInput`, `KbqInputMono`, `MinValidator`/`MaxValidator`, tokens/theme SCSS, three Jest specs, e2e fixture + Playwright spec, user guides, API guard report) · Commit `b665e503` · 2026-08-28
> Generated by a multi-dimension review (architecture, RxJS/lifecycle, correctness, accessibility, performance, public API/types, styles, tests, docs) with manual verification of every finding against the source, the in-repo consumers, the API guard report, `tsconfig.json` and small `node` probes against jsdom/`Intl`. 18 findings confirmed (P0×1, P1×4, P2×8, P3×5); 8 candidate findings refuted during verification (see Appendix A). This document is a review + roadmap; no source is modified by it.
> `input` is the canonical `KbqFormFieldControl`; the container side is reviewed separately in [`REVIEW.form-field.md`](./REVIEW.form-field.md) and is **not** repeated here. Four findings from that review were re-checked and are now fixed in `form-field` — they are listed as refuted in Appendix A rather than restated.

## 1. Executive Summary

`packages/components/input` is 4,318 lines across three near-independent control directives — `KbqInput` (331 lines), `KbqInputPassword` (295 lines) and `KbqNumberInput` (588 lines) — plus a 92-line pair of `min`/`max` validators. It is the busiest control in the library: `kbqInput` appears in `app-switcher`, `filter-bar` (5 pipe templates), `search-expandable` and every form-field dev surface. The container-level accessibility blockers from the form-field review have since landed (`aria-describedby`, the named password toggle, `aria-invalid`), so what is left is defects the control itself owns.

- **The one release blocker is a global platform mutation.** `KbqNumberInput`'s constructor calls `Object.defineProperty(Object.getPrototypeOf(this.nativeElement), 'valueAsNumber', …)` (`input-number.ts:281-289`). That is `HTMLInputElement.prototype` — so constructing a single koobiq number input silently rewrites `valueAsNumber` for **every `<input>` in the application**, including third-party widgets and native `type="date"`/`type="number"` fields, permanently, with no teardown and no opt-out. A jsdom probe confirms an unrelated input then reports `12.5` for `"12,5"` where the platform specifies `NaN`. There is no consumer workaround and no test covers it (INP-BUG-01).
- **Two directives mint DOM ids from the same namespace with two independent counters.** `input.ts:24` and `input-password.ts:9` each declare `let nextUniqueId = 0`, and both build `` `kbq-input-${nextUniqueId++}` `` (`input.ts:100`, `input-password.ts:90`). A page holding one text input and one password input — a login form, the docs Overview page, the package's own dev app and its own e2e fixture — emits two elements with `id="kbq-input-0"`. `form-field.html:2` renders `<label [attr.for]="control().id">`, so the password field's label resolves to the *text* input (INP-A11Y-01).
- **The number input is fragile in exactly the places its history says it is.** 12 of the 22 commits that ever touched `input-number.ts` are bug fixes, five of them about fractional values or caret position. The float-correction helper still drifts — one arrow-key press on `1.005` with `step="0.001"` renders `1,0059999999999998` in the field (INP-BUG-03); the package's own `MinValidator`/`MaxValidator` `parseInt` their bounds, so `[min]="0.5"` validates against `0` (INP-BUG-02); adding `type="number"` — which two of the repo's own dev apps do — makes the browser's value sanitizer reject every formatted value and blank the field (INP-BUG-05); and `KbqNumberInput.control` is declared and never assigned, so its `ngControl` is permanently `undefined` (INP-BUG-04).
- **Nothing in 89 Jest cases asserts a single ARIA attribute**, the `min`/`max` validator directives have zero tests and zero in-repo call sites, and the Playwright suite is five screenshots with no typing, no stepping and no locale switch (INP-TEST-01, INP-TEST-02).

Genuine strengths worth preserving: the `ErrorStateMatcher` wiring is thorough and genuinely well tested (17 of the 25 `input.spec.ts` cases drive the four matcher strategies including DI overrides); `kbqInjectAutofilled()` is used correctly on both text controls and the DS-4096 autofill styling in `_form-field-theme.scss:80-97` is some of the most carefully reasoned CSS in the repo; SSR discipline is real (no bare `window`/`document` anywhere in the package, an explicit `element.blur` null-guard at `input-number.ts:227-233`, an explicit `validity?.badInput` guard at `input.ts:318-323`); the locale plumbing added in DS-3897 (`kbqInjectLocaleConfiguration` + the `untracked` re-format effect at `input-number.ts:291-298`) is a model for how a control should follow a runtime locale change; and `input-number.spec.ts` is 1,671 lines of real behavioural coverage of keyboard filtering, pasting and thousand-separator masking.

## 3. Prioritized Findings (deduplicated, verified)

### P0 — Release blockers

**INP-BUG-01 · `KbqNumberInput` permanently rewrites `HTMLInputElement.prototype.valueAsNumber` for the whole application** — `input-number.ts:281-289`, `input-number.ts:84-86`.
The constructor runs `if ('valueAsNumber' in this.nativeElement) { Object.defineProperty(Object.getPrototypeOf(this.nativeElement), 'valueAsNumber', { get() { … } }); }`. `Object.getPrototypeOf(anInputElement)` is `HTMLInputElement.prototype` — not the element — so this is not a per-instance shim: it replaces the platform accessor for **every `<input>` in the document**, whether or not it has anything to do with koobiq. The replacement returns `parseFloat(normalizeSplitter(this.value))`, i.e. it treats `,` as a decimal point and returns `null` where the DOM specification requires `NaN`. Verified with a jsdom probe: after the patch, an `<input>` that never saw `kbqNumberInput` and holds `"12,5"` reports `valueAsNumber === 12.5`; the platform contract is `NaN`. On the typed inputs where `valueAsNumber` is *defined as milliseconds since the epoch* (`type="date"`, `"month"`, `"week"`, `"time"`) the replacement returns `parseFloat` of the date string instead — `"2024-01-15"` becomes `2024`. The patch has no teardown in `ngOnDestroy` (`input-number.ts:301-304`), so it survives the directive; a second jsdom probe confirms the redefinition is silent rather than throwing, because the native descriptor is `configurable: true` and a descriptor supplying only `get` preserves the remaining attributes — so repeated construction never fails loudly either. Nothing in the repo reads `valueAsNumber` and no test covers this code path, which is why it has survived. The only thing keeping it off the server is the `'valueAsNumber' in this.nativeElement` guard; a DOM shim that does implement the property would take a process-wide prototype patch shared by every SSR request.
**Fix:** delete the block. If a locale-aware numeric read is genuinely wanted, expose it as a member of the directive — `get valueAsNumber(): number | null { return this.value; }` — which is already what `_value` holds after `viewToModelUpdate` normalizes it (`input-number.ts:518-528`), needs no DOM patching, and is typed. Guard the removal with a Jest case that constructs a `kbqNumberInput`, then asserts that a sibling plain `<input>` with value `"12,5"` still reports `NaN` from `valueAsNumber` — that case fails today and passes after the change.

### P1 — High

**INP-A11Y-01 · `KbqInput` and `KbqInputPassword` generate colliding DOM ids, so the form field's `<label for>` targets the wrong control** — `input.ts:24, 100, 146-152, 224`, `input-password.ts:9, 90, 128-134, 197`, `form-field.html:2`.
Both files declare their own module-scoped `let nextUniqueId = 0;` and both build the fallback id with the *same* prefix: `` protected uid = `kbq-input-${nextUniqueId++}` `` (`input.ts:100`, `input-password.ts:90`). Two independent counters over one namespace means the first `kbqInput` on a page and the first `kbqInputPassword` on the same page both get `kbq-input-0`, the second of each gets `kbq-input-1`, and so on. The id reaches the DOM unconditionally — the constructor forces the setter (`this.id = this.id`, `input.ts:224` / `input-password.ts:197`) and the host binds `'[attr.id]': 'id'` (`input.ts:38`, `input-password.ts:23`). `KbqFormField` then renders `<label class="kbq-form-field__label" … [attr.for]="control().id">` (`form-field.html:2`), and `for` resolves to the *first* element in document order with that id — so on a login form the password field's label focuses the username field, and clicking it never reaches the password. Every other package in the library avoids this by namespacing its prefix (`kbq-textarea-` at `textarea.component.ts:211`, `kbq-select-` at `select.component.ts:1070`, `kbq-tree-select-`, `kbq-datepicker-`, `kbq-timepicker-`); `input` is the only one that reuses a sibling's. The collision is not hypothetical: it reproduces in the package's own e2e fixture (`e2e.ts:40` and `e2e.ts:109` render eight of each on one page), in its dev app (`components-dev/input/template.html:22` and `:108`), and on the published docs Overview page, which embeds `input-overview` and `input-password-overview` together. This is a WCAG 1.3.1 / 3.3.2 label-association failure with a functional symptom, not merely a duplicate-id lint nit.
**Fix:** give the password control its own namespace — `` `kbq-input-password-${nextUniqueId++}` `` in `input-password.ts:90` — or, better, replace both module counters with `inject(_IdGenerator).getId('kbq-input-')` / `'kbq-input-password-'` so the counter is application-scoped rather than module-scoped and survives lazy-loaded duplicates of the bundle. Add a Jest case that renders one `<input kbqInput>` and one `<input kbqInputPassword>` in one fixture and asserts `new Set(ids).size === 2`, plus a case asserting each `<label>`'s `for` resolves to its own control (`document.getElementById(label.htmlFor) === input`).

**INP-BUG-05 · `type="number"` on a `kbqNumberInput` blanks the field, and the library's own dev apps do it** — `input-number.ts:507-516, 400-442`, `input.ts:305-310`; call sites `components-dev/all/template.html:501-508`, `components-dev/form-field/template.html:332-339`.
`KbqNumberInput` renders its value through `setViewValue()`, which assigns the *formatted* string — thin-space group separators and a comma fraction separator under the default `ru-RU` configuration (`core/locales/formatters.ts:136-143`). A native `<input type="number">` runs the value sanitization algorithm on assignment and rejects anything that is not a valid floating-point number. Verified in jsdom: assigning `"1 234,5"` to a `type="number"` input yields `""`, while the same assignment to a `type="text"` input round-trips. So with `type="number"` present, every value with a fraction — and every value ≥ 1000 while `withThousandSeparator` is on (its default, `input-number.ts:183`) — silently disappears from the field while the model still holds it. The same probe shows `selectionStart` is `null` on `type="number"`, which disables the whole caret-preservation path: the read at `input-number.ts:402`, the restore at `:512-515` and the separator-offset correction at `:417-432` all become no-ops. Two of the repo's own dev templates set exactly this combination alongside `[step]="0.5"`, so the first arrow press there empties the field. `KbqInput` already owns the mechanism to prevent this — `validateType()` rejects nine input types via `KBQ_INPUT_INVALID_TYPES` (`input.ts:12-22, 305-310`) — but `number` is not on the list, and the number input never checks the host type. The `input.scss` rules that exist to hide native spinners (`input.scss:20-27`, `input.kbq-input[type='number']`) are the mirror image of the same confusion: they never match a koobiq number input, because it is `type="text"`.
**Fix:** in `KbqNumberInput`'s constructor, throw a dev-mode error when `nativeElement.type === 'number'` (reuse the `getKbqInputUnsupportedTypeError` shape from `input-errors.ts:1-3` with a message naming `kbqNumberInput`), or force `nativeElement.type = 'text'` and warn. Fix the two dev templates. Decide the fate of `input.scss:20-27` in the same change — either delete the dead `[type='number']` block or keep it and document that `<input kbqInput type="number">` (without `kbqNumberInput`) is the supported native-number path. Cover with a Jest case asserting the throw, and one asserting a fractional value survives a round trip through `setViewValue` on the default host.

**INP-BUG-02 · `MinValidator`/`MaxValidator` truncate their bounds with `parseInt`, so fractional `min`/`max` validate against the wrong number** — `input-number-validators.ts:44-46, 88-91`, host bindings `:18, :63`.
Both directives build their validator as `Validators.min(parseInt(this.min() as unknown as string, 10))` / `Validators.max(parseInt(this.max() …))`. `parseInt` stops at the decimal point, so `[min]="0.5"` installs `Validators.min(0)` — a control holding `0.2` is reported valid — and `[max]="9.5"` installs `Validators.max(9)`, so `9.3` is reported invalid. This is not a theoretical type: the number input is explicitly float-capable (`isFloat` at `input-number.ts:88-90`, a `fractionSeparator` in every locale, and an `integer` input at `:161` whose whole purpose is to opt *out* of fractions), and the dev app binds fractional steps (`components-dev/input/template.html:147`, `[step]="0.5"`). The cast `this.min() as unknown as string` is itself the tell: the signal is declared `input<number>()` (`:22`) and then forced through a string parser. Two further defects sit in the same 92 lines. (1) The host bindings `'[attr.min]': 'min() ? min() : null'` (`:18`) and the `max` equivalent (`:63`) are falsy-checked, so a *bound* `[min]="0"` — the single most common lower bound — removes the `min` attribute from the DOM entirely, while the static form `min="0"` keeps it (the attribute value is the truthy string `"0"`). (2) The exported class names `MinValidator` and `MaxValidator` are the exact names `@angular/forms` exports, so `import { MinValidator } from '@koobiq/components/input'` shadows the framework's in any file that needs both; the selectors also differ from Angular's (which are scoped to `input[type=number]`), so on a `type="number"` control both validators install and one of them truncates.
**Fix:** replace both `parseInt(…, 10)` calls with `coerceNumberProperty(this.min())` (or plain `Number(...)` plus a `Number.isFinite` guard), and drop the `as unknown as string` casts. Change the host bindings to `min() == null ? null : min()`. Rename the exports `KbqMinValidator`/`KbqMaxValidator` with `@deprecated` aliases for one minor, then `yarn run build:components && yarn run approve-api`. Add `input-number-validators.spec.ts` — the file has no test at all today (see INP-TEST-01) — with cases for a fractional bound, a zero bound reaching the DOM attribute, and `registerOnValidatorChange` firing on a rebind.

**INP-A11Y-02 · The number input exposes no numeric semantics: `type="text"`, no spinbutton role, no `aria-value*`, no `inputmode`** — `input-number.ts:118-129` (host block), `input.ts:176-193` (default `type = 'text'`), `stepper.ts:68-87`.
`<input kbqNumberInput>` carries no `type` attribute at any in-repo call site that matters, so the browser default applies and it is announced as a plain text field. The directive adds nothing: its host block binds only `blur`/`focus`/`paste`/`keydown`/`input` (`input-number.ts:121-127`), and a grep for `role`/`aria-` across the whole package returns exactly two hits, both `[attr.aria-invalid]`. There is therefore no `role="spinbutton"`, no `aria-valuenow`/`aria-valuemin`/`aria-valuemax`/`aria-valuetext`, and — because `min`/`max` reach the DOM only through the validator directives, which require a form directive and drop a bound `0` (INP-BUG-02) — often no native `min`/`max` attribute either. A screen-reader user is told "edit text", never the current value's numeric meaning nor the permitted range, and gets no feedback when `onKeyDown` silently `preventDefault()`s a letter (`input-number.ts:384-386`). The `kbq-stepper` buttons are deliberately `aria-hidden="true"` with `tabindex="-1"` (`stepper.ts:69-70, 73`), which is the right call *given* that arrow keys work — but it means the ARIA surface is entirely on the input, and the input has none. Separately, no `inputmode` is set anywhere in the package, so mobile users get a full alphabetic keyboard for a field that rejects letters; the same platforms report `keyCode === 229` for virtual-keyboard input, which bypasses the entire `onKeyDown` filter and leaves `onInput` as the only real guard.
**Fix:** add to the `KbqNumberInput` host block: `role: 'spinbutton'`, `'[attr.aria-valuenow]': 'value'`, `'[attr.aria-valuetext]': 'viewValue'` (so the formatted, locale-correct string is announced rather than the raw number), `'[attr.aria-valuemin]': 'min === -Infinity ? null : min'`, `'[attr.aria-valuemax]': 'max === Infinity ? null : max'`, and `'[attr.inputmode]': "integer() ? 'numeric' : 'decimal'"`. Note the `min`/`max` bindings must read the coerced constructor values, which is another reason to settle INP-API-03 first. Guard with Jest cases asserting each attribute after a `writeValue`, after a `stepUp`, and after an `[integer]` flip, and add a `jest-axe` run over a `<kbq-form-field>` + `kbq-label` + number input template.

### P2 — Should fix

**INP-BUG-03 · The float-correction helper still drifts, and the drift is rendered digit-for-digit into the field** — `input-number.ts:100-110, 462-484, 552-587`.
`add()` exists to avoid IEEE-754 drift when stepping: it scales both operands by the larger of the two precisions, adds, and scales back. It fails whenever the two operands have different fraction lengths, because the scaling itself drifts — a `node` probe gives `add(1.005, 0.001) === 1.0059999999999998`. `stepUp`/`stepDown` write that value straight into `_value` and into the view (`:467-469`, `:479-481`), and `formatNumber` splits the number's `toString()` and formats the fraction **one character at a time** (`:580-586`) with no rounding at all — `maximumFractionDigits: 20` (`:563`) applies only to the integer part. The result the user sees after a single arrow press on `1.005` with `step="0.001"` is `1,0059999999999998`. `getPrecision` has a second hole: it splits on `.` in the `toString()` output, so any number in exponential notation (`(1e-7).toString() === '1e-7'`) reports precision `1` and bypasses the correction entirely. This area has the worst regression history in the package — 12 of the 22 commits touching `input-number.ts` are `fix(...)`, and five of those are specifically about fractional values (`DS-4514` handle fraction part properly, `DS-4474` parsing and validation of fractional values, `DS-2633` fractional value not displayed after initialization) — which is exactly the signature of a helper that keeps being patched instead of replaced.
**Fix:** stop doing decimal arithmetic in binary floats. Compute the step in integer space against a decimal scale derived from the *declared* `step`/`bigStep` and the current value (`const scale = 10 ** Math.max(decimals(step), decimals(value))`, then `(Math.round(value * scale) + Math.round(step * scale)) / scale`), and round the result to that scale before storing it. Derive `decimals()` from the string form with an exponent-aware branch so `1e-7` is handled. Add Jest cases for `add(1.005, 0.001)`, `add(0.1, 0.25)`, a step from `1e-7`, and an end-to-end case asserting the *rendered* `viewValue` after `stepUp` on `1.005` — asserting the model alone would have missed this bug.

**INP-BUG-04 · `KbqNumberInput` declares the `KbqFormFieldControl` surface and never populates it; `control` is never assigned** — `input-number.ts:130, 142-150, 248-250, 260, 527`.
`private control: AbstractControl;` (`:260`) is declared and assigned nowhere in the file — a grep for `this.control` returns exactly two hits, the declaration and the read at `:249`. So `get ngControl() { return this.control; }` (`:248-250`) always returns `undefined`, and the call at `:527`, `this.ngControl?.updateValueAndValidity({ emitEvent: false })`, is a permanent no-op sitting at the end of the view→model path where it reads as a deliberate validation refresh. The same pattern runs through the rest of the interface implementation: `id`, `placeholder`, `empty`, `required` and `errorState` (`:142-150`) are declared to satisfy `implements KbqFormFieldControl<any>` (`:130`) and are never written, so they are `undefined` for the lifetime of the directive. Nothing breaks today only because `KbqNumberInput` does not provide `KbqFormFieldControl` — its `providers` array holds only `KBQ_NUMBER_INPUT_VALUE_ACCESSOR` (`:120`) — and `KbqInput` matches the same host (`selector: 'input[kbqInput],input[kbqNumberInput]'`, `input.ts:27`) and supplies the real implementation. But the members are `@public` in the guard report (`input.api.md:229-272`) with `ngControl` typed `any`, so a consumer reading `numberInputRef.errorState` gets `undefined` with no type error, and `KbqStepper` had to duck-type its way around the whole thing (`stepper.ts:23-45, 132-145`).
**Fix:** drop `implements KbqFormFieldControl<any>` from `KbqNumberInput` — it is not the form field's control and does not need to claim to be — and with it the five unassigned members and the dead `control`/`ngControl` pair. Keep exactly what `KbqStepper` needs (`controlType`, `step`, `stepUp`, `stepDown`, `disabled`, `focus`, `onContainerClick`) and let `KbqInput` own the interface. If the `updateValueAndValidity` call was meant to re-run validators after a normalization, note that `cvaOnChange` already routes through `FormControl.setValue`, which runs them — so delete it rather than repair it. `approve-api` after; the removed members were never assigned, so no consumer can be relying on their value.

**INP-API-01 · `startFormattingFrom` is a public input that nothing reads** — `input-number.ts:185-188, 560-568`, `core/locales/formatters.ts:141`, `core/locales/types.ts:265`.
`readonly startFormattingFrom = input<number>();` is declared with a JSDoc promising "Include thousand separator from custom index. For example, it will be useful in tables." The value is never read. The only consumer of the name is `createLocalizedNumberFromParts`, which reads `this.config.startFormattingFrom` (`:566-567`) — the *locale* configuration, not the input. A repo-wide grep for `startFormattingFrom` returns five hits: the locale type, the single locale that sets it (`ruRUFormattersData`, value `4`), the dead input, and the two config reads. Because it is a signal input rather than a template attribute, binding `[startFormattingFrom]="3"` compiles cleanly under `strictTemplates` and does nothing at all — the consumer gets no error and no effect, and the only way to discover the truth is to read the source. It is also exported in the guard (`input.api.md:275`), so removing it is a breaking change that has to be scheduled rather than slipped in.
**Fix:** wire it — `formatOptions.useGrouping = intPart >= Math.pow(10, this.startFormattingFrom() ?? this.config.startFormattingFrom)` with the surrounding `if` relaxed to `!= null` so an explicit `0` works — which honours both the documented input and the locale default. If per-instance control is genuinely not wanted, delete the input instead and move the sentence into the guide as "controlled by the active locale". Either way add a Jest case asserting that `[startFormattingFrom]="3"` groups `1234` while the ru default (4) does not — `input-number.spec.ts:1345` already asserts the un-grouped ru behaviour, so the new case is its mirror.

**INP-API-03 · `min`/`max`/`step` have two competing sources, and the static-attribute source does not compile under `strictTemplates`** — `input-number.ts:163-181, 270-279`, `input-number.spec.ts:172`, `tsconfig.json:114-118`.
The constructor reads `step`, `big-step`, `min` and `max` as host attributes via `new HostAttributeToken(...)`, coerces them with `isDigit`, and falls back to `SMALL_STEP`/`BIG_STEP`/`-Infinity`/`Infinity` (`:271-279`). The same four values are also plain `@Input()`s typed `number` (`:165-181`). When a template supplies a *static* attribute, both mechanisms fire and the input wins — so `<input kbqNumberInput min="3">` leaves `this.min` holding the **string** `"3"` rather than the number the constructor computed, and every downstream use (`Math.max(…, this.min)` at `:465`, `this.min >= 0` at `:356`) works only by JavaScript coercion. Worse, that static form does not type-check: the workspace sets `strictTemplates: true` (`tsconfig.json:117`), which implies `strictAttributeTypes`, so `min="3"` / `max="10"` / `step="0.5"` on a `number`-typed input is a TS2322 in any consumer app. The package ships no `ngAcceptInputType_*` declarations — a grep across all of `packages/components` returns zero — and the only place the attribute form appears is `input-number.spec.ts:172`, which Jest compiles without Angular template type-checking, so the break is invisible in CI. `big-step` is a third variant: it is readable only as a kebab-case host attribute, since the input is named `bigStep`. The same gap applies to the boolean accessor inputs on `KbqInput`/`KbqInputPassword` — `<input kbqInput required>` passes `''` to a `boolean` setter and is a compile error for consumers, yet `input.spec.ts:158` and `:174` write exactly that.
**Fix:** pick one mechanism. Migrate all four to `input(…, { transform: numberAttribute })` (which accepts both the string attribute and the bound number and fixes the typing), keep the `HostAttributeToken` reads only for `big-step` behind an explicit alias, and delete the coercion branch from the constructor. Add `static ngAcceptInputType_required: BooleanInput` / `_disabled: BooleanInput` to `KbqInput` and `KbqInputPassword`, or migrate those accessor pairs to `input({ transform: booleanAttribute })` (umbrella `ARCH-09` tracks the same debt). Verify by AOT-compiling a scratch template containing `<input kbqNumberInput min="3" step="0.5">` and `<input kbqInput required>` — both are errors today.

**INP-LIFE-01 · Every keystroke on the number input schedules an in-zone `setTimeout` plus a microtask, neither of which is cancelled on destroy** — `input-number.ts:400-442, 301-304`.
`onInput` wraps its entire body in a bare `setTimeout(...)` (`:404`) and, when `withThousandSeparator` is on, schedules a further `Promise.resolve().then(...)` inside it to correct the caret after a separator is inserted or removed (`:417-432`). Three consequences. (1) Both run inside the Angular zone, so each keystroke costs two extra change-detection passes over the whole application on top of the one the `input` event already triggers — for a form of number inputs under `OnPush` ancestors this is the dominant cost of typing. (2) Neither handle is stored and `ngOnDestroy` (`:301-304`) only completes the two `EventEmitter`s, so a directive destroyed between the keystroke and the timeout still runs `setViewValue` against a detached node and still calls `cvaOnChange` on a control the view no longer owns. (3) The model update is deferred by a full macrotask, so `FormControl.value` is stale for anything reading it synchronously after the `input` event — which is why every one of the 56 cases in `input-number.spec.ts` has to be `fakeAsync` and `tick()`. The caret logic this defers is the package's most-fixed area (`DS-3237` "properly set cursor position on number removal") and is covered only in jsdom, where `selectionStart` is a plain property with no layout behind it.
**Fix:** replace the bare `setTimeout` with `afterNextRender` (matching `KbqReactivePasswordHint`/`KbqPasswordToggle`, which already use it) or with `timer(0).pipe(takeUntilDestroyed(this.destroyRef))`, and run the caret correction through `ngZone.runOutsideAngular`, re-entering only if a value actually changed. Assert the teardown with a Jest case that dispatches `input`, destroys the fixture, then `flush()`es and asserts `cvaOnChange` was not called. Add the real-browser half in Playwright (see INP-TEST-02): type `1234567` into the e2e number field and assert `selectionStart` after each separator insertion.

**INP-ARCH-01 · `KbqInput` and `KbqInputPassword` are a 300-line copy-paste that has already diverged in ways the container depends on** — `input.ts:48-324` vs `input-password.ts:35-295`; consumer `form-field.ts:389-396`.
The two classes are the same class twice: identical injected fields, identical `errorState`/`focused`/`autofilled`/`stateChanges`/`controlType` blocks, identical `disabled`/`id`/`required`/`value` accessor pairs with identical "Skipped for migration" TODOs, identical `ngOnChanges`/`ngOnDestroy`/`ngDoCheck`/`updateErrorState`/`focus`/`onBlur`/`onContainerClick`/`dirtyCheckNativeValue`/`isBadInput`. Roughly 250 of `input-password.ts`'s 295 lines have a byte-near twin in `input.ts`. The duplication has already produced silent divergence, and one of the divergences is load-bearing. `KbqInput.stateChanges` is `Subject<void>` and emits nothing (`input.ts:83, 275`); `KbqInputPassword.stateChanges` is `Subject<any>` and emits `null` from five sites and `{ focused: this.focused }` from `focusChanged` (`input-password.ts:69, 261`). `KbqFormField` reads that payload through an inline cast — `const focused = (state as { focused?: boolean } | undefined)?.focused;` (`form-field.ts:393`) — to decide whether to push a password-strength error. Other drift: `empty` checks `isNeverEmpty()` in one and not the other (`input.ts:284` vs `input-password.ts:182`); `focusChanged` uses opposite guard styles; the id namespace collides (INP-A11Y-01); and `input-password.ts:155` still carries a commented-out line copied from the `type` setter it does not have.

Do this *after* the accessor-to-signal migration in INP-API-03 so the base is written once in the target style. In the same change, make the focus payload explicit: either declare `stateChanges: Subject<KbqFormFieldControlState>` on the interface with a `{ focused?: boolean }` shape that all three controls emit, or replace the container's cast with a read of `control().focused`, which is already public on every control and needs no payload at all.

**INP-TEST-01 · `MinValidator`/`MaxValidator` have no tests and no in-repo call sites; three more public behaviours are untested** — `input-number-validators.ts` (92 lines, 0 cases), `input-number.spec.ts` (1,671 lines, 56 cases), `input.module.ts:8, 20-21, 28-29`.

**INP-TEST-02 · 89 Jest cases assert no ARIA at all, and the Playwright suite is five screenshots** — `input.spec.ts` (25 cases), `input-number.spec.ts` (56), `input-password.spec.ts` (8), `e2e.playwright-spec.ts:1-74`.

**INP-API-02 · Generic unprefixed helpers and framework-shadowing class names on the public surface** — `input.api.md:35-73, 300-345`, `input-number.ts:59-65, 81-110, 128`, `input.ts:329`.

**INP-ARCH-02 · Dead branches and misleading names in the number input** — `input-number.ts:356, 570`, `input-password.ts:71, 204-206`.
Three small items. (1) `const localeId = !this.localeService || this.localeService.id === 'es-LA' ? 'ru-RU' : this.localeService.id;` (`:570`) is a hardcoded locale remap with no comment. Verified with a `node` probe that it has no observable effect: the `Intl` locale here only chooses the group-separator character, and `formatNumberWithLocale` (`core/formatters/number/formatter.ts:31-41`) overwrites every group part with `viewGroupSeparator` whenever the config defines one — which the `es-LA` config does (`core/locales/formatters.ts:56-62`). Formatting `1234567.89` through the real algorithm yields `"1 234 567,89"` under both `'es'` and `'ru-RU'`. The branch names the one locale for which it cannot matter, while the locales where the `Intl` id *does* matter (`en-US`, `pt-BR`, which set no `viewGroupSeparator`) get no such protection. (2) `isMinusAllowed` (`:356`) is inverted: when it is `true` the very next statement is `event.preventDefault()`, i.e. the flag means minus is *not* allowed. (3) `KbqInputPassword.checkRule` (`input-password.ts:71`) is a public `Subject` that `ngOnDestroy` never completes, unlike its sibling `stateChanges` (`:204-206`); the in-repo subscriber is safe because `KbqPasswordHint` uses `takeUntilDestroyed` (`password-hint.ts:207-213`), but an external subscriber of the public member never receives a completion. Its only trigger, the public `checkRules()` (`:235-237`), is called nowhere in the repo and is documented nowhere.
**Fix:** delete the `es-LA` branch and, if a koobiq-id→`Intl`-id mapping is actually needed, put it in the locale data next to `groupSeparator` where the other locales can use it too. Rename `isMinusAllowed` to `shouldBlockMinus`. Complete `checkRule` in `ngOnDestroy` alongside `stateChanges`, and either document `checkRules()` in `input.en.md`/`input.ru.md` as the "re-validate the password hints" hook or mark it `@docs-private`.

**INP-STYLE-01 · The package ships no styles of its own, and `_input-theme.scss` is not a theme** — `input.scss:1-39`, `input-tokens.scss:1-4`, `_input-theme.scss:1-19`, `form-field.ts:96-113`.

**Fix:** rename `_input-theme.scss` to `_input-typography.scss` (updating the `@use` at `input.scss:4`), or move the mixin into `input.scss` outright since it has one caller. **INP-TEST-03 · 22 test hosts carry the reserved `Kbq` prefix, and one test's assertions sit in a floating promise** — `input.spec.ts:57, 72, 87, 106, 121, 135, 149, 162, 181`, `input-number.spec.ts:77, 118, 135, 153, 177, 199, 216, 236, 260, 285`, `input-password.spec.ts:63, 86, 109`; `input.spec.ts:252-267`.
This repo reserves the `Kbq` prefix for library exports and names test hosts without it — a convention, not a lint rule, so it drifts silently. ## Appendix A — Review Methodology

Every file in the package was read in full (`cat -n` on all 14 `.ts`, 3 `.scss` and 4 `.md` files, plus the e2e fixture and Playwright spec), then each candidate finding was cross-checked against four independent sources: the API guard report (`tools/public_api_guard/components/input.api.md`, 349 lines), the workspace compiler settings (`tsconfig.json:114-118`), every in-repo consumer found by grep across `packages/` and `apps/`, and `git log` per file. Four claims that could not be settled by reading were verified with small `node` probes rather than assumed: the `valueAsNumber` prototype patch was reproduced in jsdom (global reach, silent redefinition, `null`-for-`NaN`); the float-drift and rendered-string chain was reproduced by re-implementing `getPrecision`/`add`/`formatNumber` verbatim; the `es-LA` branch was disproved by running the real formatting algorithm under both locale ids; and `type="number"` value sanitization and `selectionStart` behaviour were confirmed in jsdom. `git log` supplied the corroboration for INP-BUG-03 and INP-LIFE-01: 12 of the 22 commits touching `input-number.ts` are fixes, five of them about fractional values or caret position.

The four cross-package accessibility items the form-field review assigned to this package were re-checked against current source before writing, and all four have since been implemented — they appear below as refuted rather than restated, so this document does not contradict its companion.

Refuted during verification:
- **"`KbqInput` does not implement `ControlValueAccessor`, so `setDisabledState` and `onTouched` are missing"** — refuted. `KbqInput` deliberately delegates value access to Angular's `DefaultValueAccessor`; the disabled state is reflected because the getter reads `ngControl.disabled` (`input.ts:118-124`) into the `[attr.disabled]` host binding (`:40`), and `onTouched` fires from `DefaultValueAccessor`'s own blur handler. `KbqNumberInput` implements all four CVA methods (`input-number.ts:315-332`) and calls `onTouched()` on blur (`:340`), covered by `input-number.spec.ts:607` "should mark as touched on blur". The CVA contract is complete; the real defects are elsewhere in that class (INP-BUG-04, INP-LIFE-01).
- **"Hints and errors are never linked to the control via `aria-describedby` (FF-A11Y-02)"** — refuted as still-open. `KbqFormField.updateDescribedByIds()` (`form-field.ts:522-543`) now computes the id set on every `ngAfterContentChecked` and writes it through `kbqSetDescribedByIds` (`form-field-control.ts:86-98`), which preserves consumer-set ids. `KbqInput` correctly does *not* implement the optional `setDescribedByIds` hook, so the default host-element path applies. No action for `input`.
- **"The password toggle is an icon-only control with no role, name or toggle state (FF-A11Y-04)"** — refuted as still-open. `password-toggle.ts:63-70` now renders `role="button"`, `[attr.aria-label]="accessibleName"` sourced from `kbqInjectA11yLocaleConfiguration()` (`:94, :163-167`), and `[attr.aria-pressed]="!hidden"`, with Enter and Space handlers on the host (`:84-85`).
- **"`aria-invalid` is missing on `KbqInput` (FF-A11Y-05)"** — refuted. `input.ts:41` and `input-password.ts:27` both bind `'[attr.aria-invalid]': 'errorState'`. `KbqSelect` is out of scope here.
- **"A second `kbqNumberInput` throws `TypeError: Cannot redefine property` on the `valueAsNumber` patch"** — refuted by jsdom probe. The native descriptor is `configurable: true`, and a redefinition supplying only `get` preserves `configurable`, `enumerable` and the original setter, so repeated construction is silent. This makes INP-BUG-01 worse, not better: the patch never fails loudly and never reverts.
- **"`getPrecision`/`add` are dead helpers left over from an older stepper"** — refuted. Both are on the live stepping path (`input-number.ts:465, 477`) and both are `@public` in the guard report (`input.api.md:36, 42`). The defect is their arithmetic (INP-BUG-03), not their reachability.
