# Koobiq `file-upload` Component — Code Review & Improvement Plan

> Scope: `packages/components/file-upload` (both components, the `KbqFileUploadBase` base class, the dropzone service/directive/overlay, the three primitives, all six stylesheets, both templates, 145 Jest cases, the e2e fixture + Playwright spec, both user guides, both examples pages, the API guard report) · Commit `b665e503` · 2026-08-28
> Generated by a multi-dimension review (architecture, RxJS/lifecycle, correctness, accessibility, public API/types, styles, tests, docs) with manual verification of every finding against the source, the in-repo consumers, `@angular/forms` internals and `tsconfig.json`/`playwright.config.ts`. 14 findings confirmed (P0×0, P1×4, P2×6, P3×4); 6 candidate findings refuted during verification (see Appendix A). This document is a review + roadmap; no source is modified by it.

## 1. Executive Summary

`file-upload` is the largest package reviewed so far: 1,743 lines of TypeScript across six files, two templates (96 + 127 lines), six stylesheets (655 lines), 145 Jest cases and four Playwright screenshots. It ships two form controls (`kbq-single-file-upload` / `kbq-multiple-file-upload`, dispatched by the `kbq-file-upload:not([multiple])` / `kbq-file-upload[multiple]` selector pair), a full-screen and a local dropzone, and three reusable primitives (`KbqFileUploadContext`, `KbqFileLoader`, `KbqFileList`). It has **no release blockers** — every path works for a sighted mouse user — but the two dimensions the component is actually judged on, *accessibility* and *form integration*, both have real defects.

- **The most serious defect is that the file-removal control is not a button.** Both templates render it as `<i kbq-icon-button="kbq-circle-xmark_16">` (`single-file-upload.component.html:35-43`, `multiple-file-upload.component.html:61-67`). `KbqIconButton` puts `tabindex="0"` on that `<i>` (`icon/icon-button.component.ts:35, 63-72`) and adds no `role` and no accessible name, so a keyboard user lands on an unnamed tab stop — one per file — that **Enter and Space cannot activate**, because a bare `<i>` produces no synthetic click. The only way to remove a file with a keyboard is to guess Delete or Backspace, which neither guide mentions. Four other in-repo `kbq-icon-button` call sites each solved this differently (`form-field/stepper.ts:67-88` takes it out of the tab order entirely, `search-expandable.html:33-39` adds an explicit `(keyup.enter)`, `dropdown/e2e.ts:322` adds `aria-label`, and the package's own docs example writes `<button kbq-button aria-label="Delete">`); file-upload is the only one that does none of them (FUP-A11Y-01).
- **`writeValue()` writes back into the form.** The `file`/`files` setters call `cvaOnChange` (`single-file-upload.component.ts:113-117`, `multiple-file-upload.component.ts:121-125`) and `writeValue()` goes through those setters (`:290-297`, `:309-315`). Angular's model→view callback therefore re-enters the view→model pipeline: every programmatic `setValue`/`patchValue` marks the control **dirty** and emits `valueChanges` twice, and because `FormControl.reset()` calls `markAsPristine()` *before* `setValue()` (`@angular/forms/fesm2022/forms.mjs:3888-3892`), a reset uploader ends up dirty. `writeValue` also fires the public `(fileChange)`/`(filesChange)` output, so a programmatic patch looks to the consumer exactly like a user picking a file (FUP-BUG-01).
- **Nothing about the file list reaches assistive technology.** The whole package emits exactly two ARIA attributes (`role="list"`, `role="listitem"`). The guide advertises per-file errors — "only the corresponding item in the list receives the error state" (`file-upload.en.md:45`) — but that state is a CSS class and an icon colour and nothing else: no `aria-invalid`, no live region, and the projected `kbq-hint` error messages are never linked to the control, although `KbqHint.id` exists precisely for that and `form-field.ts:519-542` already implements the wiring (FUP-A11Y-02).
- **A published primitive is wrong in three ways at once.** `KbqFileList.remove()` (`primitives/file-picker.ts:140-157`) returns the items it *kept*, deletes every occurrence rather than the first, and emits no event — contradicting its own one-line JSDoc on all three counts. All three are frozen by tests, including one named `should return removed items` that asserts the survivors (`primitives/file-picker.spec.ts:467-471`) (FUP-API-01).
- **`accept` does not accept anything.** It is joined into the native input's `accept` attribute and nowhere else (`single-file-upload.component.ts:164-166`), so it filters the OS dialog and is bypassed completely by drag-and-drop — and by the dialog's own "All files" option. The team knew: the two specs that would prove filtering are `xdescribe`d with `// TODO: real-life scenario & test results with the same data are different (#DS-4300)` (`file-upload.spec.ts:1179-1213`), and the dev app labels a bare `[accept]` uploader "with pdf/png files accepted" with no validator behind it (`components-dev/file-upload/template.html:74-79`) (FUP-BUG-02).

Genuine strengths worth preserving: this is a modern, signal-first package — `input()`/`output()`/`model()`/`computed()`, `hostDirectives` used well (the context/file-list split is a genuinely good decomposition, and the primitives are separately documented and separately tested), `OnPush` on every component, `inject(KBQ_WINDOW)` and `isPlatformBrowser` guards for SSR, `runOutsideAngular` around every drag listener, and locale text resolved through `KBQ_LOCALE_SERVICE` with an `InjectionToken` *and* a per-instance `[localeConfig]` override. The test suite is large and mostly honest (145 cases, test hosts correctly named without the `Kbq` prefix, real drop events dispatched through the real directive), the Playwright matrix covers 40+ state cells in light and dark, the docs ship 29 working examples, and the one breaking change in the recent history (`07c0bea44`, DS-5229) landed with a full `ng-update` schematic — README, data table, implementation and 250 lines of migration spec. The repo's own rules are being followed here.

## 3. Prioritized Findings (deduplicated, verified)

### P0 — Release blockers

None.

### P1 — High

**FUP-A11Y-01 · The per-file remove control is a nameless, roleless tab stop that Enter and Space cannot activate** — `single-file-upload.component.html:35-43`, `multiple-file-upload.component.html:28-33, 61-67`; `icon/icon-button.component.ts:26-43, 63-72`; `icon/icon.component.ts:22-33`.
Both uploaders render removal as `<i kbq-icon-button="kbq-circle-xmark_16" class="kbq-file-upload__action" (click)="…">`. `KbqIconButton`'s host block binds `'[attr.tabindex]': 'tabindex'` with a default of `0` (`icon-button.component.ts:35, 72`) and nothing else that matters here — no `role`, no `aria-label` — and `KbqIcon`, its base, adds none either (`icon.component.ts:28-32`). The result is a focusable `<i>` with the implicit role `generic`: a screen reader announces nothing at all, and pressing Enter or Space does nothing, because only `<button>`/`<a>`/`<input>` synthesize a click from those keys. Removal is still *possible* — `(keydown.backspace)`/`(keydown.delete)` are bound, on the icon itself in the single uploader (`:41-42`) and on the `kbq-list-item` row in the multiple one (`:32-33`, reached only by bubbling from the focused icon, since `KbqListItem` has no `tabindex`) — but Delete/Backspace as the sole activation keys appear in neither `file-upload.en.md` nor `file-upload.ru.md`. In a 20-file list a keyboard user therefore walks 20 identical unnamed stops, none of which responds to the two keys they will actually try. The `fileUpload` locale section has no a11y strings to draw a label from either (`core/locales/en-US.ts:29-49` — compare `codeBlock`, which ships `copyTooltip`/`downloadTooltip`), so AGENTS.md's "source all component-provided default ARIA text from `kbqInjectA11yLocaleConfiguration()`" cannot currently be satisfied without adding keys. Four sibling call sites show the repo already knows this pattern is not a button: `form-field/stepper.ts:67-88` writes `aria-hidden="true" [tabindex]="-1"` and provides arrow keys instead; `datepicker/datepicker-toggle.component.ts:33-42` uses `[tabindex]="-1"`; `search-expandable/search-expandable.html:33-39` adds an explicit `(keyup.enter)` next to `(click)`; `dropdown/e2e.ts:322` puts `kbq-icon-button` on an `<a>` with `aria-label="Settings"`. The package's own docs example does it correctly too — `<button kbq-button aria-label="Delete">` (`docs-examples/components/file-upload/file-upload-primitive/file-upload-primitive-example.ts:72-79`). This is a WCAG 2.1.1 (Keyboard) and 4.1.2 (Name, Role, Value) judgement rather than an automated failure: default axe-core rules do not flag a focusable element with no widget role. **Fix:** change both call sites to `<button kbq-icon-button type="button" [attr.aria-label]="…">`, which gets role, name and Enter/Space activation from the platform in one move; if the `<i>` must stay for styling reasons, add `role="button"`, `[attr.aria-label]`, and `(keydown.enter)`/`(keydown.space)` handlers that call `preventDefault()`. Source the label from a new `fileUpload.a11y.removeFile` key (interpolating the file name — "Remove report.pdf") added to every locale under `core/locales/`, read through `kbqInjectA11yLocaleConfiguration()`. Keep Delete/Backspace as an accelerator and document it in both guides. Guard with a Jest case that focuses the control, dispatches `keydown.enter`, and asserts the file is gone, plus a `jest-axe` run over a rendered multi-file list (five packages already do this — see FUP-TEST-01).

**FUP-BUG-01 · `writeValue()` re-enters the form pipeline: every programmatic value marks the control dirty and re-emits the public output** — `single-file-upload.component.ts:113-117, 290-297`; `multiple-file-upload.component.ts:121-125, 309-315`; `node_modules/@angular/forms/fesm2022/forms.mjs:3199-3217, 3352-3359, 3370-3376, 3888-3897`.
`writeValue()` assigns through the `file`/`files` setter, and that setter calls `this.cvaOnChange(...)`. `cvaOnChange` is the callback Angular registers in `setUpViewChangePipeline` (`forms.mjs:3352-3359`): it sets `control._pendingDirty = true` and, because `updateOn` defaults to `'change'`, calls `updateControl`, which runs `control.markAsDirty()`, a second `control.setValue(..., {emitModelToViewChange: false})` and `dir.viewToModelUpdate(...)` (`:3370-3376`). So a consumer's `control.setValue(file)` produces: one extra `valueChanges` emission, one extra validation pass, one `ngModelChange`/`update` emission, and a control that is now **dirty** although the user has touched nothing. The sharpest case is `reset()`, which calls `markAsPristine()` at `forms.mjs:3890` and `setValue()` at `:3892` — in that order — so a reset file-upload comes back dirty, and any consumer whose error display keys off `dirty` shows errors on a freshly cleared form. Initialization is safe only by accident: `setUpControl` calls `writeValue` at `:3207`, before `setUpViewChangePipeline` at `:3214`, so the first write still hits the no-op default. On top of that, `writeValue` emits `this.fileChange`/`this.filesChange` (`:296`, `:314`) — a component *output*, whose contract is "the user changed the selection" — so a background `patchValue` is indistinguishable from a user action for any consumer that starts an upload from that output. A secondary, smaller effect of the same method: the SSR guard `if (!isPlatformBrowser(this.platformId)) return;` (`:292`, `:311`, added for DS-4414) discards *all* values on the server, including plain `KbqFileItem[]` arrays that touch no browser API, so a server-rendered form with a pre-populated file list renders empty. **Fix:** split the write path. Keep a private `setFileList(value)` that only writes `fileList.list` and calls `cdr.markForCheck()`; have `writeValue()` call it, and have the public `file`/`files` setters plus the user-interaction handlers call it *and* `cvaOnChange`. Remove the `fileChange`/`filesChange` emission from `writeValue()`. Narrow the SSR guard to the `File`/`FileList` branches only. Cover with Jest cases asserting that `control.setValue(item)` leaves `control.pristine` true and emits `valueChanges` exactly once, that `control.reset()` leaves the control pristine, and that `(fileChange)` does not fire for a programmatic write — three assertions the current 145-case suite does not make.

**FUP-A11Y-02 · Per-file error state, upload progress and hint text have no non-visual channel** — `multiple-file-upload.component.html:35, 51-56, 82-86`; `single-file-upload.component.html:20-27, 48-52`; `single-file-upload.component.ts:271-286`; `form-field/hint.ts:21-30`, `form-field/form-field.ts:519-542`; `file-upload.en.md:45`.
A repo-wide grep over the package returns exactly two ARIA attributes: `role="list"` and `role="listitem"`. The error state a consumer is told to rely on — "When an invalid file is selected, only the corresponding item in the list receives the error state, not the entire component" (`file-upload.en.md:45`, same in `.ru.md:45`) — is carried by `[class.kbq-error]="file.hasError"` on the row (`multiple-file-upload.component.html:35`) and an icon colour swap (`:64`), with no `aria-invalid`, no `role="alert"` and no live region. The error *messages* are projected `kbq-hint`s dropped into a plain `<div class="kbq-file-upload__hint">` (`:82-86`, `single-file-upload.component.html:48-52`); `KbqHint` carries an `id` input whose JSDoc says "Referenced by the `aria-describedby` of the form field control" (`hint.ts:22-23`) and `KbqFormField` implements exactly that wiring (`form-field.ts:519-542`, with four dedicated specs) — file-upload projects the hint and links nothing, so a screen-reader user reaching the file input hears its name and no constraint, no hint, and no error. The asymmetry between the two components makes it worse: the single uploader at least derives `hasError` from the control status itself (`single-file-upload.component.ts:271-286`), while the multiple one requires the consumer to set `hasError` on each item by hand, so nothing in the multiple uploader knows which message belongs to which row. Progress is in the same position: `<kbq-progress-spinner [value]="asyncData.progress || 0">` replaces the file icon (`single-file-upload.component.html:24`, `multiple-file-upload.component.html:44-48`) and `grep -rn "progressbar" packages/ apps/` returns zero hits repo-wide, so "uploading, 40%" and "upload finished" are announced by nothing — and file-upload, the spinner's heaviest consumer, did not build the `role="status"` wrapper that `notification-center.html:104-110` had to build for itself. **Fix:** three changes, in order. (1) Implement `setDescribedByIds` on both components (the `KbqFormFieldControl` shape is already half-present via `stateChanges`/`errorState`) and write `aria-describedby` on the file input from the projected `KbqHint` ids, reusing `form-field-control.ts:82-96`. (2) Put `aria-invalid` on the file input and, per row, an `aria-describedby` pointing at the message for that file, plus `role="alert"` on the hint that appears on transition to invalid. (3) Add a visually hidden `role="status"` region owned by the component that announces additions, removals and per-file errors ("report.pdf added, 3 files", "report.pdf: file size exceeds the limit"). Track `role="progressbar"` under PSP-A11Y-01 in the progress-spinner review rather than here, and delete the `notification-center` wrapper once it lands. Verify with a Jest case per branch and one `jest-axe` pass over an invalid multi-file list.

**FUP-API-01 · `KbqFileList.remove()` contradicts its own JSDoc three ways, and the spec pins all three** — `primitives/file-picker.ts:140-157`; `primitives/file-picker.spec.ts:455-492`; `tools/public_api_guard/components/file-upload.api.md:146-159`.
The doc comment reads "Removes the first occurrence of the specified item. Returns removed items and emits event" (`:140`). The body does none of that. The filter predicate is `const isRemoved = currentItem !== item` — true for the items that *survive* — and the `removed` array is filled from that same branch (`:146-150`), so the method returns everything it kept. It removes every occurrence, not the first, because `Array.prototype.filter` has no early exit. And it emits nothing: `itemRemoved` is emitted only by `removeAt()` (`:170`). Each of the three defects has a test that locks it in: `should return removed items` asserts `removed` equals `[file1, file3]` after removing `file2` (`file-picker.spec.ts:467-471`) — the name and the assertion say opposite things; `should remove all occurrences when duplicates exist` (`:480-485`) documents the opposite of "first occurrence"; and `should not emit itemRemoved event` (`:487-492`) asserts the missing emission as if intended. Nothing inside the library calls `remove()` — both components delete through `removeAt()` (`multiple-file-upload.component.ts:364`) — so no shipped behaviour is broken, but `KbqFileList` is `@public` with `remove(item: T): T[]` in the API report (`file-upload.api.md:152`), it is exported for exactly this kind of standalone use, and the docs advertise it in the "Primitives" example. Any consumer who writes `const [gone] = list.remove(item)` gets the wrong file. **Fix:** implement the documented contract — find the index with `findIndex`, delegate to `removeAt(index)` so the `itemRemoved` emission and the return value come from one place, and return `[]` when the item is absent. Then rewrite the three specs to match: `expect(removed).toEqual([file2])`, a duplicate case asserting only the first copy disappears, and an `itemRemoved` emission assertion. If "remove all occurrences, emit nothing" is the behaviour actually wanted, the JSDoc and the method name are what must change (`removeAll`), and `itemRemoved` should still fire once per removed item — but decide it deliberately rather than leaving three tests that certify a contradiction. This changes `file-upload.api.md` only if the signature changes; if it does, `yarn run build:components` then `yarn run approve-api` (build first — the guard reads `dist/*.d.ts`).

### P2 — Should fix

**FUP-LIFE-01 · The full-screen dropzone's document listeners outlive the component and multiply on every re-init** — `dropzone.ts:90-105, 111-150, 152-155`; `single-file-upload.component.ts:247-259`; `multiple-file-upload.component.ts:279-291`; `dropzone.ts:264-283, 300-327`.
`KbqFullScreenDropzoneService.init()` subscribes to four `document.body` drag events, each terminated by `takeUntil(this.dropAbort)` (`:113-148`). `dropAbort` is emitted from exactly one place, `stop()` (`:153-155`), and `ngOnDestroy()` calls only `close()` (`:103-105`). The service is provided per component (`providers: [KbqFullScreenDropzoneService]` on both), so destroying a `kbq-file-upload` that had `[fullScreenDropZone]` on leaves four live body listeners behind that keep calling `open()` and `onDrop()` against a disposed component for the rest of the session. Second problem, same code: the `effect()` that drives the service calls `init(config)` on every truthy value without calling `stop()` first, so changing `[fullScreenDropZone]` from `true` to a config object (or from one object to another) adds four more listeners on top of the existing four — one physical drop then emits `filesDropped` twice and adds the file twice. Third, the single uploader opens its `filesDropped` subscription *inside* that effect (`single-file-upload.component.ts:248`), so it too is duplicated on every effect run; the multiple uploader does the same subscription once in the constructor (`multiple-file-upload.component.ts:279`), which is the correct shape and makes the asymmetry the evidence. Fourth, `KbqLocalDropzone.open()` calls `this.init()` every time the overlay is created (`:280`), and those subscriptions are scoped to `takeUntilDestroyed(this.destroyRef)` rather than to the overlay, so every drag-in/drag-out cycle strands three more subscriptions on a disposed overlay element. **Fix:** in `ngOnDestroy()` call `this.dropAbort.next(); this.dropAbort.complete();` before `close()`; make `init()` idempotent by calling `stop()` at its top; move the `filesDropped` subscription in `single-file-upload.component.ts` out of the `effect()` and into the constructor next to `multiple-file-upload.component.ts:279`; and in `KbqLocalDropzone.init()` terminate the three streams with `takeUntil(overlayRef.detachments())` instead of the directive's `destroyRef`. Cover with Jest cases that destroy the fixture and assert a subsequent body `drop` reaches nothing, and that toggling `[fullScreenDropZone]` between two configs still yields exactly one `filesDropped` per drop.

**FUP-BUG-02 · `accept` only hints the OS dialog — dropped files are never checked against it** — `single-file-upload.component.ts:95, 164-166, 338-348`; `multiple-file-upload.component.ts:102, 237-239, 350-356`; `primitives/file-drop.ts:26-44`; `file-upload.spec.ts:1179-1213`; `components-dev/file-upload/template.html:74-79`.
`accept` is an `input<string[]>()` whose only consumer is the `acceptedFiles` getter, `this.accept()?.join(',') || '*/*'`, bound to the hidden input's `accept` attribute (`:164-166`). Nothing else reads it. `onFileDropped()` maps whatever arrived straight into `KbqFileItem`s (`:338-348`, `:350-356`), and `KbqDrop.onDrop()` walks the `DataTransfer` entries with no type check at all (`file-drop.ts:35-43`) — so a `.exe` dropped onto a `[accept]="['.pdf']"` uploader is added like any other file, and even in the dialog path the user can switch the file-type filter to "All files". The team is aware: the two specs that would prove filtering sit in an `xdescribe` marked `// TODO: real-life scenario & test results with the same data are different (#DS-4300)` (`file-upload.spec.ts:1179-1213`), and they assert exactly the behaviour that does not exist. The documented answer is to repeat the same array in a validator — `[accept]="accept"` plus `FileValidators.isCorrectExtension(this.accept)` in the same component (`docs-examples/.../file-upload-single-accept-validation-example.ts:21, 39-43`) — but the input's name promises rejection, the guides never mention `accept` at all, and the dev app demonstrates the misunderstanding directly by labelling a validator-free `[accept]="['.pdf','.png']"` uploader "with pdf/png files accepted" (`components-dev/file-upload/template.html:74-79`). **Fix:** decide and document. Either (a) enforce it — filter incoming files in `onFileDropped`/`onFileSelectedViaClick` through the same matcher `FileValidators.isCorrectExtension` uses, and add a `rejected` output carrying the discarded files so the consumer can explain the rejection (silent discarding is its own accessibility problem, see FUP-A11Y-02); or (b) rename it to `acceptHint`, deprecate `accept` with an `ng-update` migration, and state in both guides that filtering requires a validator. Either way, un-skip `file-upload.spec.ts:1179-1213` — with (a) the two cases pass as written; with (b) they should be deleted and replaced by a case asserting only the `accept` attribute value. Note while fixing: `FileValidators.isCorrectExtension` builds `new RegExp(\`${specifier}$\`)` (`core/forms/validators.ts:195-199`), so `.` is a wildcard and `image/*` is not a valid MIME wildcard — worth a matching ticket against `core`.

**FUP-BUG-03 · The single uploader's hidden input is `multiple`, and every file past the first is silently discarded** — `single-file-upload.component.html:65-79` (`[multiple]="true"` at `:74`); `primitives/file-picker.ts:44-55, 88-98`; `single-file-upload.component.ts:322-335, 338-348`.
`KbqFileLoader` computes `innerMultiple = this.fileUploadContext?.multiple() ?? this.multiple()` (`file-picker.ts:90`) and renders `[attr.multiple]="innerMultiple()"` (`:49`). For a plain `<kbq-single-file-upload>` the context's `multiple` is an `input(null, { transform: booleanAttribute })` whose *initial* value bypasses the transform and stays `null` (`file-picker.ts:28`), so the `??` falls through to the loader's own input — which the single template binds to `true` (`single-file-upload.component.html:74`). The OS dialog therefore lets the user select any number of files for a single-file field, and `onFileSelectedViaClick` keeps `target.files?.item(0)` (`:325`) and drops the rest with no message, no error state and no output. The drop path behaves the same way: `files[0]` (`:342`). A user who selects five documents sees one row appear and has no way to tell which one the component kept or that four were thrown away. Nothing in the 145-case suite asserts the `multiple` attribute of the single uploader's input in either direction, so the binding reads as a copy-paste from the multiple template rather than a decision. **Fix:** bind `[multiple]="false"` (or drop the binding, letting the `null` context value produce no attribute) so the dialog enforces single selection natively. For the drop path, which the browser cannot constrain, keep taking the first file but emit the discarded ones through the `rejected` output proposed in FUP-BUG-02 and announce the truncation in the live region from FUP-A11Y-02. Add a Jest case asserting `input.multiple === false` on `kbq-single-file-upload` and `true` on `kbq-multiple-file-upload` — a two-line test that would have caught this.

**FUP-A11Y-03 · `onTouched` is never called on blur, so the default `ErrorStateMatcher` stays silent** — `single-file-upload.component.ts:153-156, 322-371`; `multiple-file-upload.component.ts:227-229, 339-410`; `core/error/error-state-matcher.ts:59-63`; `select/select.component.ts:1487-1495`.
The default matcher is `!!(control?.invalid && (control.touched || form?.submitted))` (`error-state-matcher.ts:59-63`), so `touched` is half of what makes a file-upload show its error. Both components call `onTouched()` only from value-changing handlers — `onFileSelectedViaClick`, `onFileDropped`, `deleteItem`/`onFileAdded`/`deleteFile` — and there is no blur handling anywhere in the package: no `(blur)`/`(focusout)` in either template, no `FocusMonitor.monitor` on the host (the injected `FocusMonitor` is used only for `focusVia` after a deletion). A user who tabs into a `required` uploader, decides not to attach anything and tabs on therefore leaves `touched === false`, and the "file is required" error stays invisible until the form is submitted — while every native input in the same form goes red immediately, because Angular's built-in `DefaultValueAccessor` marks them touched on blur. The repo's own comparable custom CVA does it correctly: `KbqSelect.onBlur()` calls `this.onTouched()` and pushes `stateChanges` (`select.component.ts:1487-1495`). Note the CVA is otherwise complete — `setDisabledState` is implemented on both components (`:316-319`, `:333-336`) and Angular calls it unconditionally since `setDisabledStateDefault` is `'always'` (`forms.mjs:3188, 3211-3213`) — `onTouched` is the one missing leg. **Fix:** monitor the host with `FocusMonitor` (already injected) and call `onTouched()` + `stateChanges.next()` when the origin goes `null`, or bind `(focusout)` on the root element guarded by `!elementRef.nativeElement.contains(event.relatedTarget)` so moving between the browse link and the remove button does not count as leaving. Cover with a Jest case that focuses the file input, blurs it, and asserts `control.touched` and the `kbq-error` class.

**FUP-A11Y-04 · Removing a file from the middle of the list drops focus onto `<body>`** — `multiple-file-upload.component.ts:359-383`; compare `single-file-upload.component.ts:350-371`.
`deleteFile()` restores focus only in the empty case: `if (this.files.length === 0) { setTimeout(() => focusMonitor.focusVia(input, origin ?? 'keyboard')); return; }` (`:372-382`). There is no `else`. A keyboard user who deletes file 3 of 5 has just destroyed the element that held focus — the `@for` row is removed from the DOM — so focus falls back to `<body>` and the next Tab restarts from the top of the document. In a five-file list that is four lost positions per deletion. The single uploader does not have the bug only because its list can never have a "middle": its condition (`single-file-upload.component.ts:360`) is tautological — `this.file` was set to `null` two lines earlier at `:355`, so `if (this.file === null)` is always true and the trailing `return` at `:369` is dead code. WCAG 2.4.3 (Focus Order) and the "focus management" clause of AGENTS.md's accessibility mandate. **Fix:** in `deleteFile`, capture the index, and after removal focus the remove control of `Math.min(index, files.length - 1)` when the list is non-empty, falling back to the file input when it is empty — the same `setTimeout` + `focusVia` shape already used, so the origin handling is unchanged. Delete the tautological branch in `deleteItem` and keep only its body. Cover with a `fakeAsync` Jest case: three files, focus row 2's control, press Delete, assert `document.activeElement` is row 2's control (formerly row 3's file) rather than `document.body`.

**FUP-TEST-01 · The suite verifies that bindings exist, not that a user can reach them** — `file-upload.spec.ts:228-253, 299-309, 864-874, 1179-1213`; `e2e.ts:116-208`; `e2e.playwright-spec.ts:1-80`.
The suite is large — 145 cases over three spec files — and its value is concentrated in the value pipeline (add/remove/duplicate strategy/async validation, all genuinely good). The interaction surface is where it is thin. The keyboard-removal case dispatches a `KeyboardEvent` directly at the row element (`file-upload.spec.ts:228-253`: `query(By.css('.kbq-file-upload__item')).nativeElement.dispatchEvent(...)`), an element with no `tabindex` that a user can never focus — so the test proves the handler is bound and says nothing about whether the interaction is reachable, which is precisely the gap FUP-A11Y-01 describes. `should focus label after file removed` asserts `document.activeElement` is the `cdk-visually-hidden` *input*, not a label (`:299-309`, `:864-874`) — the name and the assertion disagree. Two cases are disabled (`xdescribe`, `:1179-1213`, FUP-BUG-02). No spec anywhere asserts an ARIA attribute, and no `jest-axe` import exists in the package although five sibling packages (`accordion`, `app-switcher`, `button-toggle`, `list`, `navbar`) already run it. On the visual side the fixture builds a 40+ cell matrix of states (`e2e.ts:116-208`) but never sets `loading` or `progress` on any cell, so `kbq-progress-spinner` — one of the two things the component renders — has no baseline at all; `dev-focused` is simulated by adding `cdk-focused`/`cdk-keyboard-focused` classes to `.kbq-file-upload__action` only (`e2e.ts:231-235`), never to the browse link; and the Playwright spec takes four screenshots and performs no drag, no keyboard and no assertion of anything else (`e2e.playwright-spec.ts:1-80`). **Fix:** add the reachability cases named in FUP-A11Y-01/03/04 (Enter on the focused control, blur→touched, mid-list focus restoration), a `jest-axe` pass over an empty, a filled and an invalid uploader, and the `input.multiple` assertion from FUP-BUG-03. Rename `should focus label after file removed` to say "file input". Add an e2e row with `loading: true` and `progress: 40` for both components so the spinner and its determinate arc get a baseline, and one with the browse link focused; regenerate through `yarn run e2e:docker:update-snapshots` only. Validate the additions by mutation — removing `(keydown.delete)` from the template must turn a case red.

**FUP-CSS-01 · 22 of the 83 declared custom properties are read by nothing, including both focus-outline tokens** — `file-upload-tokens.scss:14-15, 22, 26-28, 41, 57-58, 70, 79, 94-95, 99-100`; `multiple-file-upload.component.scss:170`; `single-file-upload.component.scss:125, 136`.
Cross-checking every `--kbq-file-upload-*` declaration in `file-upload-tokens.scss` against every `var(--kbq-file-upload-*)` in the package's six stylesheets leaves 22 declared-and-never-read names. Custom properties on a component root are a published theming contract, so a consumer who sets one and sees nothing happen has no way to tell a dead token from a specificity problem. Three groups stand out. `--kbq-file-upload-single-states-focused-focus-outline-color` (`:41`) and `--kbq-file-upload-multiple-states-focused-focus-outline-color` (`:95`) promise a focus indicator the package never draws — the only `outline` declaration anywhere in it is `outline: none` on the dropzone content (`dropzone.scss:28`). The three `*-grid-divider-color` tokens (`:70, 79, 94`) describe a divider that no rule references. **FUP-CSS-02 · The package's only animation ignores `prefers-reduced-motion`, and the visual baselines cannot see it** — `dropzone.scss:1-15`; `dropzone.ts:177, 282`; `playwright.config.ts:101`; compare `accordion/accordion.scss:62`, `progress-spinner/progress-spinner.scss:68`, `progress-bar/progress-bar.scss:52`, `skeleton/skeleton.scss:56`, `notification-center/notification-center.scss:105`, `dropdown/dropdown-item.scss:74`, `core/styles/common/_animation.scss:57`.
`.kbq-dropzone-overlay` starts at `opacity: 0` with `transition: opacity 100ms ease-in-out` and is faded in by a `setTimeout` that adds `kbq-dropzone-overlay__attached` (`dropzone.scss:10-15`; the timeouts are `dropzone.ts:177` and `:282`). Seven other packages answer `@media (prefers-reduced-motion: reduce)` for their transitions; this one does not, so a user who has asked for reduced motion still gets the fade on a full-screen overlay that covers the entire viewport — the largest animated surface the library produces. The gap is invisible to CI in both directions: `playwright.config.ts:101` sets `reducedMotion: 'reduce'` on every browser context, so the baselines are taken in the state the media query would target, and since the query does not exist the screenshots look identical either way. **Fix:** wrap the transition in `@media (prefers-reduced-motion: reduce) { transition: none; }` following `core/styles/common/_animation.scss:57`, and consider driving the reveal from the overlay's own attach hook rather than a bare `setTimeout`, so a dropped frame cannot leave the overlay at `opacity: 0`. No baseline change is expected, which is itself the check.

## 4. Recommended Remediation Phases

**Phase 1 — Make the controls operable and the state audible.**
IDs: FUP-A11Y-01, FUP-A11Y-02, FUP-A11Y-04, FUP-A11Y-03. Turn the remove control into a real button with a localized name, restore focus after a mid-list deletion, mark the control touched on blur, then wire `aria-describedby`, `aria-invalid` and a `role="status"` region. These are one body of work — the live region is what makes the silent-discard behaviours in Phase 2 explainable — and none of them depends on anything below. Ships with the new locale keys, the Jest reachability cases and the first `jest-axe` run in the package.

**Phase 2 — Fix the form contract.**
IDs: FUP-BUG-01, FUP-API-01. Split the `writeValue` path from the user-interaction path so programmatic values stop marking the control dirty and stop firing the public outputs, and correct `KbqFileList.remove()` together with the three specs that certify its current behaviour. Both are contract repairs with no visual component; Phase 1's tests do not depend on them, but the acceptance criteria (a pristine control after `reset()`, a correct return value from `remove()`) are simple assertions worth landing early.

**Phase 3 — Decide what `accept` means, and stop discarding files silently.**
IDs: FUP-BUG-02, FUP-BUG-03, FUP-LIFE-01. Choose enforcement or renaming for `accept` and un-skip the two disabled specs either way; bind `[multiple]="false"` on the single uploader; add the `rejected` output that gives both cases something to say. Fold in the dropzone lifecycle repairs (`dropAbort` on destroy, idempotent `init()`, the subscription moved out of the `effect()`, overlay-scoped local-dropzone streams) since they touch the same drag path and their regression tests share a fixture. `accept` renaming, if chosen, needs an `ng-update` schematic — the package already has one to copy (`packages/schematics/src/migrations/file-upload-deprecated-outputs/`).

**Phase 4 — Close the test, API and style gaps.**
IDs: FUP-TEST-01, FUP-API-02, FUP-DOC-01, FUP-CSS-01, FUP-CSS-02. Add the progress/focus e2e rows and the mutation check, correct the `@default` tags and delete `hasFocus`, add the two missing English example embeds plus the accessibility and `accept` sections, remove the 22 dead tokens and gate the dropzone fade behind `prefers-reduced-motion`. One `build:components` + `approve-api` cycle covers the API changes; one Docker screenshot run covers everything visual.
