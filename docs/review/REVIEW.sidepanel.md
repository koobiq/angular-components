# Koobiq `sidepanel` Component — Code Review & Improvement Plan

> Scope: `packages/components/sidepanel` (service, ref, container, 5 content directives, animations, config, tokens, theme, SCSS, Jest spec, e2e fixture + Playwright spec, user guides, examples, API guard report) · Commit `b665e503` · 2026-08-28
> Generated by a multi-dimension review (architecture, RxJS/lifecycle, correctness, accessibility, public API/types, styles, tests, docs) with manual verification of every finding against the source, the CDK sources the package builds on (`node_modules/@angular/cdk/fesm2022/`), the seven shipped docs examples, the dev app and `playwright.config.ts`. 19 findings confirmed (P0×0, P1×2, P2×6, P3×11); 5 candidate findings refuted during verification (see Appendix A). This document is a review + roadmap; no source is modified by it.

## 1. Executive Summary

`kbq-sidepanel` is an overlay-and-animation package: a service that opens CDK overlays (`sidepanel.service.ts`, 218 lines), a hand-written ref that drives close/backdrop/animation choreography (`sidepanel-ref.ts`, 156 lines), a `BasePortalOutlet` container (`sidepanel-container.component.ts`, 182 lines) and five content directives (`sidepanel-directives.ts`, 172 lines). It supports four positions, three sizes, stacked panels with an offset indent, and two documented modes — modal and non-modal. It is not a CDK `Dialog` wrapper; the overlay, the focus trap, the backdrop and the animation state machine are all assembled here.

- **The panel is never a dialog to assistive technology.** The container host block (`sidepanel-container.component.ts:38-50`) binds `class`, `id`, `tabindex` and the animation trigger, and nothing else: no `role="dialog"`, no `aria-modal`, no `aria-label`/`aria-labelledby`. Nothing outside the overlay is hidden from AT either, which is the step CDK's own `Dialog` performs when its first dialog opens (`dialog.mjs:611-623`). A sighted keyboard user is correctly trapped inside the panel; a screen-reader user gets no announcement that anything opened, no name for the region, and a virtual cursor that still roams the whole page behind it (SP-A11Y-01).
- **Non-modal sidepanels block page scrolling — the one thing the mode is named after.** `createOverlay()` hard-codes `scrollStrategy: this.overlay.scrollStrategies.block()` (`sidepanel.service.ts:163`) for every panel, and `KbqSidepanelConfig` (`sidepanel-config.ts:19-52`) exposes no way to change it. CDK's `BlockScrollStrategy` pins `html { position: fixed; top: -Ypx }` (`overlay-module.mjs:46-60`), so the documented "Non-modal mode (without page blocking) … all elements behind it remain interactive" (`sidepanel.en.md:30-32`, `sidepanel.ru.md:30-32`) and the example that demonstrates it (`sidepanel-normal-mode-example.ts:72-75`) freeze the page they are supposed to leave alone (SP-BUG-01).
- **The package does not style the portal host, and every shipped call site works around it.** Component-based panels are attached inside `.kbq-sidepanel-content`, a flex column (`sidepanel.scss:162-170`), but the attached component's own host element is left as a plain block, so header/body/footer collapse. All three in-repo component-portal call sites patch it by hand, two different ways: `host: { class: 'layout-column flex' }` in `sidepanel-disable-close-example.ts:23` and `components-dev/sidepanel/module.ts:85-87`, and `:host { display: flex; flex-direction: column; height: 100% }` in `sidepanel-with-dynamic-config-update-example.ts:38-44` (SP-CSS-01).
- **Lifecycle bookkeeping has three independent defects.** A component- or route-scoped `KbqSidepanelService` never closes its panels on destroy, because `open()` pushes into the *parent's* array while `ngOnDestroy()` iterates the always-empty local one (`sidepanel.service.ts:17-31, 75`); `closeSidepanels()` reverses the live `openedSidepanels` array in place (`sidepanel.service.ts:171`); and `close()`'s re-entrancy guard tests `Subject.closed`, which RxJS 7 never sets on `complete()` (`sidepanel-ref.ts:128`) (SP-LIFE-01, SP-BUG-02, SP-BUG-03).
- **Test coverage is broad but its one focus test proves nothing.** 31 Jest cases cover open/close/id/data/backdrop/indent, yet the single test about focus captures `document.activeElement` *before* the fixture exists and then asserts against that stale snapshot (`sidepanel.spec.ts:378, 399-401`) — it passes whether or not focus ever entered the panel. Two adjacent backdrop tests are near-identical with contradictory titles (`:243-261` vs `:263-276`), and the Playwright suite runs on WebKit (`e2e.playwright-spec.ts:4`) while the only project the config defines is Chrome (`playwright.config.ts:68-76`) (SP-TEST-01, SP-TEST-02).

Genuine strengths worth preserving: the four-position transform table (`sidepanel-animations.ts:15-47`) is symmetric and complete, and the stacking choreography — lower panel scales back, second-from-top fades out, backdrops cross-fade so only one dim layer is ever visible — is a genuinely nice piece of work that the spec actually verifies (`sidepanel.spec.ts:243-276`). The container guards its own destruction before animating (`sidepanel-container.component.ts:134, 142`), the overlay is disposed exactly once on the closing animation's `done` phase (`sidepanel-ref.ts:97-106`), every animation subscription that should fire once is `take(1)`-bounded, the close button sources its accessible name from `kbqInjectA11yLocaleConfiguration()` (`sidepanel-directives.ts:86`) as AGENTS.md requires, all consumed design tokens resolve against the live token set, and the overflow-shadow wiring between body, header and footer is covered by three real-browser Playwright assertions rather than screenshots (`e2e.playwright-spec.ts:58-93`).

## 3. Prioritized Findings (deduplicated, verified)

### P0 — Release blockers

None.

### P1 — High

**SP-A11Y-01 · The sidepanel container is not a dialog to assistive technology** — `sidepanel-container.component.ts:38-50`, `sidepanel-container.component.html:6-8`, `sidepanel-directives.ts:68-99`.
The container's host block declares exactly five bindings — `class`, `[class]`, `[class.kbq-sidepanel_nested]`, `[attr.id]`, `[attr.tabindex]` — plus the `[@state]` trigger (`sidepanel-container.component.ts:38-50`). There is no `role`, no `aria-modal`, and no accessible name anywhere in the package; `KbqSidepanelHeader` renders its title into a plain `<div class="kbq-sidepanel-title">` (`sidepanel-directives.ts:77-79`) with no `id` for anything to point at. Separately, nothing outside the overlay is ever hidden from assistive technology — the step CDK performs in its own `Dialog` via `_hideNonDialogContentFromAssistiveTechnology` when the first dialog opens (`dialog.mjs:611-623`). The consequences split by user: a sighted keyboard user is fine, because `CdkTrapFocus` is wired correctly and defaults to on for backdropped panels (`sidepanel-container.component.html:6`, `sidepanel-container.component.ts:86-93`); a screen-reader user gets no announcement that a dialog opened, a nameless generic region if they do land in it, and a virtual cursor that still walks the entire page behind the "modal" panel, because a focus trap constrains Tab, not browse mode. This is a WCAG 4.1.2 (Name, Role, Value) judgement rather than an automated AXE failure — axe-core does not flag a `<kbq-sidepanel-container>` that simply carries no role — but AGENTS.md states WCAG AA as a mandate, and consumers cannot patch it from outside: `overlayPanelClass` adds classes, not attributes.
**Fix:** add to the container host block `'[attr.role]': '"dialog"'`, `'[attr.aria-modal]': 'trapFocus ? "true" : null'` (reusing the existing modality getter at `sidepanel-container.component.ts:91-93`), and `'[attr.aria-labelledby]': 'ariaLabelledBy'` / `'[attr.aria-label]': 'sidepanelConfig.ariaLabel ?? null'`. Add `ariaLabel?: string` and `ariaLabelledBy?: string` to `KbqSidepanelConfig`; default `ariaLabelledBy` to `` `${id}-title` `` and have `KbqSidepanelHeader` stamp that same id on its `.kbq-sidepanel-title` element via a host binding, so the common case needs no consumer action. Guard with a Jest case asserting `role`, `aria-modal` and a resolvable `aria-labelledby` target on the container, and add `jest-axe` to the sidepanel spec the way the modal/dropdown specs do it.

**SP-BUG-01 · Non-modal sidepanels block page scrolling, contradicting the mode's own name** — `sidepanel.service.ts:157-168` (`:163`), `sidepanel-config.ts:19-52`; docs `sidepanel.en.md:30-32` / `sidepanel.ru.md:30-32`; consumers `sidepanel-normal-mode-example.ts:72-75`, `sidepanel-overlayed-example.ts:29-32`.
`createOverlay()` builds one `OverlayConfig` for every panel and hard-codes `scrollStrategy: this.overlay.scrollStrategies.block()` (`sidepanel.service.ts:163`). `KbqSidepanelConfig` has ten fields (`sidepanel-config.ts:19-52`) and none of them is a scroll strategy, so there is no public way to opt out. CDK's `BlockScrollStrategy.enable()` caches the scroll position, writes `html { left: -Xpx; top: -Ypx }` and adds `cdk-global-scrollblock`, which is `position: fixed` (`overlay-module.mjs:46-60`); it engages whenever the document actually overflows (`:89-100`). The published guide's headline for the mode is literally "Non-modal mode (without page blocking) … so all elements behind it remain interactive" (`sidepanel.en.md:30-32`; RU `:30-32` says "без блокировки страницы"), and both examples that demonstrate it open with `hasBackdrop: false` (`sidepanel-normal-mode-example.ts:74`, `sidepanel-overlayed-example.ts:31`) — so the docs page itself freezes when the reader tries the example. There is a second-order effect too: `BlockScrollStrategy._canBeEnabled()` returns `false` while the class is already present (`overlay-module.mjs:94-96`), so with stacked panels only the first one owns the block, and closing *that* panel while an upper one is still open releases the page scroll.
**Fix:** derive the strategy from modality — `scrollStrategy: config.hasBackdrop ? this.overlay.scrollStrategies.block() : this.overlay.scrollStrategies.reposition()` — and additionally expose `scrollStrategy?: () => ScrollStrategy` on `KbqSidepanelConfig` for consumers who need `noop()` or a custom one. Guard with a Jest case asserting `document.documentElement.classList.contains('cdk-global-scrollblock')` is `true` for a default panel and `false` for `{ hasBackdrop: false }`, and a second case that opens two panels, closes the lower one and asserts the block survives.

### P2 — Should fix

**SP-LIFE-01 · A child-level `KbqSidepanelService` closes nothing when it is destroyed** — `sidepanel.service.ts:17-31, 75`.
The service is written for a multi-level injector hierarchy: it injects a `skipSelf` parent (`:17`), keeps a private `openedSidepanelsAtThisLevel` (`:18`), and exposes `openedSidepanels` which delegates to the parent when one exists (`:21-25`). `ngOnDestroy()` then closes `this.openedSidepanelsAtThisLevel` with the comment "Only close the sidepanels at this level on destroy since the parent service may still be active" (`:27-31`). But `open()` pushes into `this.openedSidepanels` (`:75`) — the *getter* — so whenever a parent service exists the ref lands in the parent's array and `openedSidepanelsAtThisLevel` stays empty forever. The destroy hook is therefore a no-op in exactly the configuration it was written for, and the repo exercises that configuration deliberately: `sidepanel.spec.ts:455-456` provides `KbqSidepanelService` on a component with the comment "Testing for service with parent service". The visible result is an orphaned panel: destroy the owning component or route with a panel open and the overlay stays attached, its focus trap stays alive, and — combined with SP-BUG-01 — the page behind stays unscrollable with nothing left holding a ref to close it. The same shape exists upstream in CDK's `Dialog` (`dialog.mjs:625` pushes into the getter, `:643-659` iterates the local array), but it bites far harder here because `KbqSidepanelService` is `@Injectable()` provided from `KbqSidepanelModule` (`sidepanel.module.ts:33-36`) rather than `providedIn: 'root'`, so extra levels appear whenever a lazy module or a component imports the module.
**Fix:** push into `this.openedSidepanelsAtThisLevel` in `open()` and make `openedSidepanels` return the parent's list concatenated with the local one for read paths (`getSidepanelById`, `getOpenedSidepanelsWithSamePosition`, `getClosestSidepanel`), or keep the single shared array and have `ngOnDestroy()` close the subset whose refs this instance created. Guard with a Jest case that opens a panel from a component-provided service, destroys that component's fixture, and asserts `overlayContainerElement.querySelector('kbq-sidepanel-container')` is `null`.

**SP-CSS-01 · The component-portal host is unstyled, and all three shipped call sites hand-roll the same workaround** — `sidepanel.scss:162-170`, `sidepanel-container.component.html:6-8`; consumers `sidepanel-disable-close-example.ts:23`, `components-dev/sidepanel/module.ts:85-87`, `sidepanel-with-dynamic-config-update-example.ts:38-44`.
`.kbq-sidepanel-content` is the layout engine of the panel: `display: flex; flex-direction: column; flex: 1; min-height: 0` (`sidepanel.scss:162-170`), and `.kbq-sidepanel-body` relies on it with `overflow-y: auto; flex: 1; min-height: 0` (`:201-206`). Template portals stamp their nodes directly into it and work. Component portals do not: `CdkPortalOutlet` inserts the attached component's *host element* in between, and that element is a plain block with no flex participation, so `kbq-sidepanel-body` never becomes a flex item, never scrolls, and the footer stops sticking. Nothing in the package styles that element and nothing documents the requirement, so every consumer rediscovers it — `host: { class: 'layout-column flex' }` in `sidepanel-disable-close-example.ts:23` and `components-dev/sidepanel/module.ts:85-87`, and an inline `:host { display: flex; flex-direction: column; height: 100% }` in `sidepanel-with-dynamic-config-update-example.ts:38-44`. Three call sites, two incompatible spellings, one of them depending on the `layout-column`/`flex` global utility classes that a library consumer may not load at all. Note the spec's own `SimpleSidepanelExample` (`sidepanel.spec.ts:477-483`) has no such host styling, which is why no test notices.
**Fix:** style the portal host from the package: `.kbq-sidepanel-content > * { display: flex; flex-direction: column; flex: 1; min-height: 0; min-width: 0; }` in `sidepanel.scss` next to the `.kbq-sidepanel-content` rule (a `> *` rule is safe here — the outlet holds exactly one attached root). Then delete the three consumer workarounds, which is the regression check: the disable-close and dynamic-config examples must still render a scrolling body and a pinned footer with their host styles removed. Add a Playwright row that opens a *component*-portal panel with overflowing body content and asserts the footer shadow, mirroring `e2e.playwright-spec.ts:59-66` which today only covers the template-portal fixture.

**SP-BUG-02 · `closeSidepanels()` reverses the live `openedSidepanels` array in place** — `sidepanel.service.ts:170-174` (`:171`), `:87-89`, `:180-217`.
`const reversedOpenedSidepanels = [...sidepanels.reverse()];` spreads *after* calling `Array.prototype.reverse()`, which mutates the receiver. `closeAll()` passes the live array (`:88`), so a single `closeAll()` permanently flips the open-panel order that the rest of the service treats as a stack. Everything downstream is index-derived and runs *later*, after the closing animation: `updateAnimationState()` bails unless the ref is the last element (`:184`), `getLowerSidepanelsWithSamePosition()` reads the array tail (`:213-216`), `removeOpenSidepanel()` promotes the panel it believes is underneath (`:196-206`), and a subsequent `open()` picks its `lower`/`bottom` neighbours the same way (`:105-109`). After the reversal all of these address the wrong panels, so the scale-back/fade choreography plays on the wrong panel or not at all. The correct form is `[...sidepanels].reverse()`; CDK's own `Dialog.closeAll()` uses a non-mutating `reverseForEach` for exactly this reason (`dialog.mjs:632`). A closely related weakness sits in the same area and should be fixed with it: stacking state is captured once at open time — `KBQ_SIDEPANEL_WITH_INDENT` is computed from the count of same-position panels in `attachContainer()` (`:115`) and read once into a plain field (`sidepanel-container.component.ts:57`) — so closing a *lower* panel leaves the upper one still rendering an indent strip for a panel that no longer exists, and clicking that strip closes it.
**Fix:** change `:171` to `const reversedOpenedSidepanels = [...sidepanels].reverse();`. Guard with a Jest case that opens three panels, calls `closeAll()`, and asserts `sidepanelService.openedSidepanels` is empty *and* that a fourth panel opened afterwards gets `withIndent === false`. Separately, make `withIndent` a signal recomputed from `openedSidepanels` (or push it down from `removeOpenSidepanel()`), covered by a case that opens two panels, closes the lower one, and asserts `.kbq-sidepanel-indent` count is `0`.

**SP-API-01 · `hasBackdrop` cannot be changed after open, and both the docs and the shipped example say otherwise** — `sidepanel.service.ts:157-168`, `examples.sidepanel.en.md:1-5` / `examples.sidepanel.ru.md:1-5`, `sidepanel-with-dynamic-config-update-example.ts:56-60`.
`hasBackdrop` is read exactly once, when the `OverlayConfig` is constructed (`sidepanel.service.ts:159`); nothing re-reads `config.hasBackdrop` afterwards, so assigning `sidepanelRef.config.hasBackdrop = false` on an open panel does nothing. The Examples tab nevertheless states that "`KbqSidepanelConfig` properties, such as `hasBackdrop` and `disableClose`, can also be changed after the sidepanel is already open, via `KbqSidepanelRef.config`" (`examples.sidepanel.en.md:3`, identically in `.ru.md:3`). Only the second half is true — `disableClose` *is* re-read at close time (`sidepanel-ref.ts:121`) — and the example that ships under that sentence proves the first half is not: it reaches past the public API into the raw CDK overlay, `this.sidepanelRef.overlayRef.backdropElement!.hidden = !value` (`sidepanel-with-dynamic-config-update-example.ts:59`). That is the workaround a consumer will copy, and it throws `TypeError` on any panel opened with `hasBackdrop: false`, because `backdropElement` is then `null` and the `!` only silences the compiler.
**Fix:** make `hasBackdrop` live — in `KbqSidepanelRef`, watch the value (a setter on the ref, or a small `hasBackdrop` signal on the config surface) and call `overlayRef.attachBackdrop()` / `overlayRef.detachBackdrop()` accordingly, re-applying the `kbq-overlay-dark-backdrop` class that `sidepanel-ref.ts:44` currently adds only in the constructor. Then rewrite the example to use `sidepanelRef.config.hasBackdrop = value` and delete the `overlayRef` access. Guard with a Jest case that flips `hasBackdrop` on an open panel in both directions and asserts `.cdk-overlay-backdrop` appears and disappears. If live toggling is judged out of scope, the minimum is to correct both `examples.sidepanel.*.md` sentences to name only `disableClose`.

**SP-CSS-02 · The theme mixin restyles a shared backdrop class globally, with `!important`** — `_sidepanel-theme.scss:19-21`, `sidepanel.scss:242`, `sidepanel-container.component.ts:35, 37`.
`kbq-sidepanel-theme()` ends with `.kbq-overlay-dark-backdrop { background: var(--kbq-background-overlay) !important; }` (`_sidepanel-theme.scss:19-21`). The mixin is included from `sidepanel.scss:242`, which is a `styleUrls` entry of a component compiled with `ViewEncapsulation.None` (`sidepanel-container.component.ts:35, 37`) — so the rule is injected into the document head, unscoped, the first time any sidepanel is used, and applies to every element carrying that class anywhere in the application. `kbq-overlay-dark-backdrop` is a shared name: `sidepanel-ref.ts:44` applies it here, and it is the conventional dark-backdrop class for overlays generally. Two concrete costs: the sidepanel package silently repaints backdrops it does not own, and the `!important` makes the declaration unbeatable by a consumer's own theme without a second `!important`. It is also unnecessary — the token it sets is the same `--kbq-background-overlay` the class would normally carry.
**Fix:** scope the rule to the sidepanel's own overlay host, which is already tagged for exactly this purpose: `sidepanel.service.ts:48` adds `kbq-sidepanel-overlay` to `overlayRef.hostElement`, so write `.kbq-sidepanel-overlay .kbq-overlay-dark-backdrop { background: var(--kbq-sidepanel-overlay-background); }` — which also revives the dead token from SP-CSS-04 — and drop the `!important`. Verify by rendering a modal and a sidepanel on the same dev page and confirming the modal's backdrop is unchanged with the sidepanel package loaded.

**SP-TEST-01 · The only focus test asserts against a snapshot taken before the component exists** — `sidepanel.spec.ts:377-404` (`:378`, `:399-401`).
The test named "should set focus inside modal when opened by dropdown" begins with `const activeElement: HTMLElement | null = document.activeElement as HTMLElement;` (`:378`) — captured before `TestBed.createComponent` on the next line, so it is `<body>` — then opens a dropdown, clicks an item to open a sidepanel, and asserts `expect(activeElement).not.toBe(buttonElement)`, `expect(activeElement).not.toBe(dropdownItems[0])`, `expect(activeElement).toBeTruthy()` (`:399-401`). All three compare the stale snapshot; `document.activeElement` is never re-read after the panel opens. The test passes identically if focus never moves, if the focus trap is removed, or if the panel fails to render — and the name says "modal", not sidepanel. That leaves the package's entire focus behaviour untested: nothing covers `cdkTrapFocusAutoCapture` moving focus into the panel, nothing covers `CdkTrapFocus.ngOnDestroy` returning focus to the trigger (`a11y-module.mjs:570-577`), nothing covers `[cdkFocusInitial]` (used in `e2e.ts:59` and `sidepanel-sizes-example.html:23`), and nothing covers the `trapFocus`/`trapFocusAutoCapture` config overrides (`sidepanel-container.component.ts:86-93`), which are two of only ten config fields.
**Fix:** rewrite the test to read `document.activeElement` *after* `flush()` and assert `overlayContainerElement.querySelector('.kbq-sidepanel-content')!.contains(document.activeElement)`; rename it to drop "modal". Add three more cases: focus returns to the trigger button after `close()` completes; `{ trapFocusAutoCapture: false }` leaves focus on the trigger; `[cdkFocusInitial]` inside the content wins over the first tabbable element. Add a Playwright row that Tab-cycles a modal panel and asserts focus never leaves `.kbq-sidepanel-content`.

### P3 — Nice to have / hygiene

**SP-A11Y-02 · Non-modal panels have neither a focus trap nor focus restoration, while the guide promises both unconditionally** — `sidepanel-container.component.ts:86-93`, `sidepanel-container.component.html:6`, `sidepanel-ref.ts:110-113`; docs `sidepanel.en.md:54-56, 68-70` / `sidepanel.ru.md:54-56, 68-70`.
Both modality getters fall back to backdrop presence: `trapFocus` and `trapFocusAutoCapture` are `?? !!this.sidepanelConfig.hasBackdrop` (`sidepanel-container.component.ts:87, 92`). With `hasBackdrop: false` — the documented non-modal and stacked modes, and what both of those examples pass — the trap is disabled *and* `CdkTrapFocus` never records `_previouslyFocusedElement`, because it is only captured inside `_captureFocus()` under `autoCapture` (`a11y-module.mjs:578-582`). So neither of the guide's two blanket statements holds for half its documented modes: "focus cycles only through elements inside the panel … and does not leave the panel" (`sidepanel.en.md:56`) and "When the sidepanel closes, focus returns by default to the element that triggered it" (`:70`). In the same area, the Escape handler filters `keyCode === ESCAPE` and closes without `event.preventDefault()` (`sidepanel-ref.ts:110-113, 120-124`), so the browser's own Escape behaviour still runs alongside the close.
**Fix:** either default `trapFocusAutoCapture` to `true` independently of `hasBackdrop` (restoration is desirable in both modes and costs nothing when the trap is off), or amend both guides to scope the two claims to modal mode. Add `event.preventDefault()` in the Escape branch when the panel actually closes. Cover with Jest cases asserting restoration for `{ hasBackdrop: false }` and that Escape's default action is prevented.

**SP-BUG-03 · `close()`'s re-entrancy guard is dead code** — `sidepanel-ref.ts:127-140` (`:128`).
`close()` is guarded by `if (!this.afterClosed$.closed)`. In RxJS 7.8.2 — verified directly — `Subject.complete()` sets `isStopped` and leaves `closed` at `false`; only `unsubscribe()` sets `closed`. `afterClosed$` is only ever completed (`sidepanel-ref.ts:105`), so the guard is permanently open and every `close()` call runs the body: it overwrites `this.result` (`:137`) and adds another `animationStateChanged.pipe(filter(done), take(1))` subscription that detaches the backdrop (`:130-135`). The damage is bounded — after teardown `containerInstance.exit()` returns early on the `destroyed` flag (`sidepanel-container.component.ts:142`) — but the intended protection does not exist: a second `close('B')` after `close('A')` and before the animation finishes silently changes the result the consumer receives.
**Fix:** replace the predicate with a dedicated `private closing = false` flag set on first entry, or test `!this.afterClosed$.isStopped`. Guard with a Jest case that calls `close('A')` then `close('B')` synchronously and asserts `afterClosed()` emits `'A'`.

**SP-BUG-04 · Explicit `undefined` config values overwrite the defaults and crash the animation setup** — `sidepanel.service.ts:37-40`, `sidepanel-container.component.ts:158-168` (`:159, 162`), `:170-175`.
`open()` merges with `{ ...(this.defaultOptions || new KbqSidepanelConfig()), ...config }` (`:37-40`). Object spread copies own enumerable keys including those whose value is `undefined`, so `open(Cmp, { position: this.maybePosition })` with an unset optional replaces the `KbqSidepanelPosition.Right` default (`sidepanel-config.ts:32`) with `undefined`. `setAnimation()` then dereferences it as non-null — `const position: KbqSidepanelPosition = this.sidepanelConfig.position!` followed by `kbqSidepanelTransformAnimation[position].in` (`sidepanel-container.component.ts:159, 162`) — and throws `Cannot read properties of undefined (reading 'in')` before the panel ever renders; `setPanelClass()` would meanwhile stamp `kbq-sidepanel-container_undefined` (`:174`), and `size` would produce `kbq-sidepanel_undefined` (`:82`). The two `!` assertions are what turn a defaulting bug into a crash.
**Fix:** filter undefined keys during the merge — build `fullConfig` from the defaults and then assign only the config entries whose value is not `undefined` — and replace the two `!` assertions with `?? KbqSidepanelPosition.Right`. Guard with a Jest case calling `open(Cmp, { position: undefined, size: undefined })` and asserting the panel opens with the right/medium defaults.

**SP-BUG-05 · An outside click inside one non-modal panel closes an unrelated panel at a different position** — `sidepanel-ref.ts:115-119`; fixture `e2e.ts:96-103`.
The close-trigger merge includes `overlayRef.outsidePointerEvents().pipe(filter(event => isHtmlElement(event.target) && !!event.target.closest('.kbq-sidepanel-container')))` (`sidepanel-ref.ts:115-119`) — it closes this panel whenever a click lands inside *any* sidepanel container that is not this one. `OverlayOutsideClickDispatcher` walks attached overlays top-down and breaks at the first one containing the target (`overlay-module.mjs:658-669`), and every sidepanel subscribes, so the reachable case is a click in a *lower* panel closing the panels above it. For same-position stacks that is the documented behaviour ("Clicking the vertical area exposed by the panel underneath closes the top panel", `sidepanel.en.md:42`). But the filter never consults position, so with two backdrop-less panels at different edges — `right` and `left`, the combination the e2e fixture itself opens (`e2e.ts:96-103`) — clicking inside the right panel closes the left one, even though they do not overlap and neither is "underneath" the other. With `hasBackdrop: true` the effect is masked because the upper panel's backdrop intercepts the click first.
**Fix:** narrow the filter to the same-position stack, e.g. `filter(event => … && event.target.closest('.kbq-sidepanel-container')?.classList.contains(\`kbq-sidepanel-container_${this.config.position}\`))`, or better, route this through the service which already knows the stack (`getOpenedSidepanelsWithSamePosition`, `sidepanel.service.ts:176-178`). Guard with a Jest case opening `{ position: Right, hasBackdrop: false }` and `{ position: Left, hasBackdrop: false }`, clicking inside the right container, and asserting both remain open.

**SP-ARCH-01 · `KbqSidepanelClose` carries a dead template-portal fallback and a stale comment** — `sidepanel-directives.ts:32, 42-54, 164-172`; `sidepanel.service.ts:52-63`.
`sidepanelRef` is injected optionally and immediately re-asserted non-null (`sidepanel-directives.ts:32`), and `ngOnInit` installs a `setTimeout` that walks the DOM to find the enclosing container id and looks the ref up by id (`:42-54`, helper at `:164-172`). The comment justifying it says "embedded views cannot be given a custom injector" (`:44-49`). That has not been true for several CDK majors, and this package does not rely on it: `open()` passes `this.createInjector(fullConfig, ref, container)` as the fourth `TemplatePortal` argument (`sidepanel.service.ts:61`), and `CdkPortalOutlet.attachTemplatePortal` forwards it to `createEmbeddedView(..., { injector: portal.injector })` (`portal.mjs:514-518`). The proof is structural: `KbqSidepanelHeader`, `KbqSidepanelBody` and `KbqSidepanelFooter` all inject `KbqSidepanelRef` *non*-optionally (`sidepanel-directives.ts:111, 125, 145`) and are used inside `<ng-template>` panels throughout the e2e fixture (`e2e.ts:47-68`) and the docs examples, which would fail with NG0201 if the injector were absent. The dead path costs a `setTimeout` per close button and a window in which clicking the button throws on `null.close()`.
**Fix:** delete `ngOnInit`, `getClosestSidepanel` and the stale comment; make the injection required (`inject(KbqSidepanelRef)`) and drop the `!`. Keep `ngOnChanges` — the `kbq-sidepanel-close` / `kbqSidepanelClose` alias proxy is still needed. The existing template-portal specs (`sidepanel.spec.ts:59-70`) plus the e2e fixture are the regression guard.

**SP-ARCH-02 · The service is NgModule-only, and the module swaps `FocusTrapFactory` application-wide** — `sidepanel.service.ts:12`, `sidepanel.module.ts:33-36`.
`KbqSidepanelService` is a bare `@Injectable()` (`sidepanel.service.ts:12`) whose only registration is `KbqSidepanelModule.providers` (`sidepanel.module.ts:34`). In a repo whose stated direction is standalone components, a consumer who imports only the standalone directives has no service and no `provideKbqSidepanel()`-style function to reach for; importing the NgModule is the only route, which is also what creates the extra injector levels behind SP-LIFE-01. The same providers array contains `{ provide: FocusTrapFactory, useClass: ConfigurableFocusTrapFactory }` (`:35`), an unscoped override of a `providedIn: 'root'` CDK service: importing the sidepanel module changes the focus-trap implementation used by *every* trapping component in the application (modal, dropdown, popover), not just sidepanels. Nothing in the package requires the configurable variant — no `ConfigurableFocusTrap` API is used anywhere in the sources.
**Fix:** mark the service `@Injectable({ providedIn: 'root' })` (keeping the module registration for the nested-service scenario) or add a `provideKbqSidepanel()` function, and remove the `FocusTrapFactory` override unless a specific behaviour depends on it — if one does, document it in the module's JSDoc. Both changes alter the API report, so schedule `build:components` + `approve-api` with them.

**SP-API-02 · `KbqSidepanelAnimationState` is used in two public signatures but never exported** — `tools/public_api_guard/components/sidepanel.api.md:100-101, 121`, `public-api.ts:1-6`.
`public-api.ts` re-exports config, container, directives, ref, module and service, but not `./sidepanel-animations` — while `KbqSidepanelContainerComponent` exposes `animationState: KbqSidepanelAnimationState` and `setAnimationState(state: KbqSidepanelAnimationState)`, both `@public`. The API report records the consequence verbatim: `Warning: (ae-forgotten-export) The symbol "KbqSidepanelAnimationState" needs to be exported by the entry point index.d.ts` (`sidepanel.api.md:100`). A consumer holding a `KbqSidepanelRef` can read `containerInstance.animationState` but cannot name its type. The same report shows the package's typing debt more broadly: `KbqSidepanelRef<T = any, R = any>`, `KbqSidepanelConfig<D = any>`, `KBQ_SIDEPANEL_DATA: InjectionToken<any>`, `sidepanelResult: any`, and 24 `// (undocumented)` markers; in the sources, `sidepanel.service.ts:60` casts the template context `as any` and `sidepanel-ref.ts:51` casts `event.toState as any`.
**Fix:** add `export * from './sidepanel-animations';` to `public-api.ts` (it also legitimises `kbqSidepanelAnimations` for consumers writing their own container), then `yarn run build:components && yarn run approve-api`. Separately, type the template-portal context as `{ $implicit: D | null; sidepanelRef: KbqSidepanelRef<T> }` to remove the `as any` at `sidepanel.service.ts:60`, and type `event.toState` as `KbqSidepanelAnimationState` at `sidepanel-ref.ts:51`.

**SP-CSS-03 · The open panel is a `position: fixed` container that re-anchors fixed descendants** — `sidepanel.scss:33-37, 86-88`, `sidepanel-animations.ts:21, 55-56`, `sidepanel-container.component.ts:44-49`.
`.kbq-sidepanel-container` is `position: fixed` (`sidepanel.scss:37`) and always carries a non-`none` `transform`: the static rule sets `transform: translateX(100%)` per position (`sidepanel.scss:88, 99, 110, 121`), and the `Visible` animation state overwrites it inline with `style({ transform: '{{transformOut}}', opacity: 1 })` (`sidepanel-animations.ts:55-56`) where `transformOut` is `'translateX(0)'` (`:21`). Angular writes `state()` styles as inline styles that persist for as long as the element stays in that state, so an open panel permanently carries `transform: translateX(0)` — which makes it the containing block for every `position: fixed` descendant. Anything inside a sidepanel that expects to be anchored to the viewport is instead anchored to the panel. This is not hypothetical inside this repo: `docs/review/REVIEW.skeleton.md` (SKL-CSS-02) files the shimmer band's viewport-wide `position: fixed` against exactly these lines, and the skeleton package's own flagship example puts ~30 skeletons inside a sidepanel. The `translateX(0)` in particular is a no-op transform that exists only to name the resting state.
**Fix:** this one is mostly a documentation and awareness item on the sidepanel side — the transform is load-bearing for the slide animation and cannot simply be dropped. Add a short "Layout constraints" note to `sidepanel.en.md` / `sidepanel.ru.md` stating that the panel establishes a containing block for `position: fixed` descendants, so overlays and sticky decorations inside it must be `absolute`/`sticky` or routed through the CDK overlay container. Coordinate the actual fix with SKL-CSS-02, whose remediation is on the skeleton side.

**SP-CSS-04 · A declared token and a stamped class are both dead** — `sidepanel-tokens.scss:20`, `sidepanel.service.ts:48`.
`--kbq-sidepanel-overlay-background: var(--kbq-background-overlay)` is declared under the "THEME TOKENS" banner (`sidepanel-tokens.scss:20`) and consumed nowhere in the repository — the backdrop rule that would use it reaches for `--kbq-background-overlay` directly instead (`_sidepanel-theme.scss:20`). It also shadows a same-named global token that ships marked deprecated (`@koobiq/design-tokens/web/new/css-tokens-light.css:957`), so the local declaration is both dead and confusing. Symmetrically, `overlayRef.hostElement.classList.add('kbq-sidepanel-overlay')` (`sidepanel.service.ts:48`) writes a class that no stylesheet in `packages/` or `apps/` selects on.
**Fix:** consume the token where it belongs — it is the natural target for the scoped backdrop rule in SP-CSS-02, `.kbq-sidepanel-overlay .kbq-overlay-dark-backdrop { background: var(--kbq-sidepanel-overlay-background); }` — which resolves both halves of this finding at once and makes the class load-bearing. If SP-CSS-02 is not taken, delete both instead.

**SP-TEST-02 · Two duplicate Jest cases with contradictory names, and a Playwright suite that runs off-project** — `sidepanel.spec.ts:243-261, 263-276`; `e2e.playwright-spec.ts:4`, `playwright.config.ts:68-76, 83-88, 101`.
The cases "should have only one dark backdrop with multiple sidepanels by default" (`:243-261`) and "should be able to add more than one dark backdrop with multiple sidepanels" (`:263-276`) open three default panels and make the same assertion — that all but one backdrop has `opacity: 0`. The first also asserts `backdropElements.length` equals the number of `open()` calls, i.e. that there *are* three backdrops, which contradicts its own title; the second's title promises a configuration ("be able to add more than one") that it never sets. Neither varies `hasBackdrop` or `backdropClass`, so the second case adds no coverage. On the Playwright side, `e2e.playwright-spec.ts:4` declares `test.use({ browserName: 'webkit' })` while the only project in `playwright.config.ts:68-76` is `Chrome` with `devices['Desktop Chrome HiDPI']` — the five committed baselines under `__screenshots__/` are therefore WebKit renderings produced under a Chrome device profile, compared at `threshold: 0` (`playwright.config.ts:83-88`). `webkit` is installed deliberately (`package.json:298`) and `deprecated/scrollbar` does the same, so the pin is intentional; it is undocumented and unexplained, which is the problem. Coverage gaps in the same suite: no row for `top`/`bottom` positions despite full SCSS support (`sidepanel.scss:71-83, 108-128`) and a fixture button that opens them (`e2e.ts:35-41`), and dark theme covered only for the nested case (`:53-54`).
**Fix:** delete the second backdrop case and rename the first to what it verifies ("should show only the topmost backdrop when multiple sidepanels are open"), or make it real by opening panels with mixed `hasBackdrop`. Add a one-line comment at `e2e.playwright-spec.ts:4` explaining why WebKit is required here. Add a `top-bottom` screenshot row using the existing `e2eSidepanelTopBottom` button, regenerating baselines only with `yarn run e2e:docker:update-snapshots`.

**SP-DOC-01 · The keyboard table documents two shortcuts the component does not implement** — `sidepanel.en.md:74-80` / `sidepanel.ru.md:74-80`; `sidepanel-ref.ts:110-113`.
The "Keyboard controls" table lists three rows: `Ctrl + Enter` — "Perform the primary action of the sidepanel"; `Esc` — close; `Enter` — "Submit the form when pressing Enter in any text input" (`sidepanel.en.md:78-80`, identically at `sidepanel.ru.md:78-80`). The package handles exactly one key: `overlayRef.keydownEvents().pipe(filter(event => event.keyCode === ESCAPE))` (`sidepanel-ref.ts:110-113`). There is no `ENTER` handling anywhere in the package — and the comparison is not abstract, because the sibling `modal` component, which the guide's own "When to use" section points at (`sidepanel.en.md:5`), *does* implement `Ctrl + Enter` (`modal.component.ts:478`). A consumer reading both guides reasonably concludes the sidepanel behaves the same way. Two smaller docs-side nits belong with this: `sidepanel-sizes-example.ts:25` declares `size = KbqSidepanelPosition.Right` — a field named for one enum, holding another, and never read — and `sidepanel-sizes-example.html:11-17` overrides the body padding with inline styles instead of the `--kbq-sidepanel-size-content-padding-*` tokens the package provides.
**Fix:** either implement the `Ctrl + Enter` primary action following `modal.component.ts:478` (emitting on the ref so the consumer decides what "primary" means), or mark both rows in the two guides as guidance for consumers to implement rather than built-in behaviour. Delete the dead `size` field from the sizes example and replace its inline padding with token overrides.

**Phase 1 — Dialog semantics and the non-modal contract.**

**Phase 3 — Layout and theme scoping.**

**Phase 4 — API surface and reactive config.**

Refuted during verification:
- **"Escape closes every stacked sidepanel at once"** — refuted. `OverlayKeyboardDispatcher._keydownListener` walks attached overlays top-down, dispatches to the first with keydown subscribers and `break`s (`overlay-module.mjs:554-568`); every `KbqSidepanelRef` subscribes, so exactly one panel receives each Escape. The behaviour matches `sidepanel.spec.ts:102-111`.
- **"The close-trigger merge subscription in `KbqSidepanelRef` leaks"** — refuted. It is never explicitly unsubscribed, but `OverlayRef.dispose()` completes `_backdropClick`, `_keydownEvents` and `_outsidePointerEvents` (`overlay-module.mjs:1006-1008`); only `indentClickEmitter` stays open, and it lives on the already-destroyed container, so the retained graph is a single collectable cycle rather than a root-held one.
- **"`KbqSidepanelHeader`/`Body`/`Footer` inject `KbqSidepanelRef` non-optionally and therefore break inside template portals"** — refuted, and the refutation became the evidence for SP-ARCH-01. `CdkPortalOutlet.attachTemplatePortal` forwards `portal.injector` into `createEmbeddedView` (`portal.mjs:514-518`) and `sidepanel.service.ts:61` supplies it, so the ref is available in embedded views; the e2e fixture (`e2e.ts:47-68`) is a live proof.
- **"`enter()` calling `detectChanges()` can throw after the view is destroyed"** — refuted. Both `enter()` and `exit()` return early on the `destroyed` flag set in `ngOnDestroy` (`sidepanel-container.component.ts:99-103, 134, 142`).
- **"Inline backdrop-opacity writes bypass `Renderer2` and break SSR"** — refuted. The writes at `sidepanel-ref.ts:86, 92` are only reachable from an `open()` call, which constructs a CDK overlay; nothing in the package touches `document` or `window` at module scope or during server rendering, so there is no SSR path to break. No `KBQ_WINDOW` finding is warranted.

Corrected on verification:
- **SP-LIFE-01** was drafted as "mis-ported from Angular Material".
