# Koobiq `textarea` Component — Code Review & Improvement Plan

> Scope: `packages/components/textarea` (directive, tokens, theme, SCSS, Jest spec, e2e fixture + Playwright spec, user guides, API guard report) plus the `form-field` contract it plugs into and every in-repo call site · Commit `b665e503` · 2026-08-28
> Generated by a multi-dimension review (architecture, RxJS/lifecycle, correctness, accessibility, performance, public API/types, styles, tests, docs, SSR) with manual verification of every finding against the source, the in-repo consumers, `tsconfig.json`, the design-token set and a jsdom probe of the measurement primitives. 13 findings confirmed (P0×0, P1×2, P2×5, P3×6); 7 candidate findings refuted during verification (see Appendix A). This document is a review + roadmap; no source is modified by it.

## 1. Executive Summary

`KbqTextarea` is a 373-line directive on `textarea[kbqTextarea]` that plugs a native textarea into `kbq-form-field` (`KbqFormFieldControl`, `ErrorStateMatcher`, `stateChanges`) and adds one behaviour of its own: auto-resize. It does **not** implement `ControlValueAccessor` — value flow is Angular's own `DefaultValueAccessor` plus a `ngDoCheck` dirty check — and that half of the component is correct and well covered. Everything that goes wrong goes wrong in the nine lines of arithmetic inside `grow()` (`textarea.component.ts:300-325`).

- **The auto-resize height is computed once per value change and never re-derived.** There is no `ResizeObserver`, no `ViewportRuler`, no `window:resize` anywhere in the package (verified by grep), and the one escape hatch — `KBQ_PARENT_ANIMATION_COMPONENT` (`:236`) — is provided by exactly one component in the whole library, `KbqTabGroup` (`tabs/tab-group.component.ts:94`). Narrow the window, drag a splitter, collapse a sidebar and the text rewraps to more lines while the pinned `min-height` stays put; because auto-grow mode also sets `overflow-y: hidden` (`textarea.scss:24-27`), the overflowing text is clipped with **no scrollbar at all**. Measure the control while its container is hidden and every quantity is `NaN`, so the height is never set in the first place (THA-BUG-01).
- **The measurement cancels out the padding it is required to include.** `diff` is `getComputedStyle().height − clientHeight`, i.e. content-box minus padding-box, i.e. exactly `−(paddingTop + paddingBottom)`; the result is then written to `min-height` on an element with `box-sizing: border-box`, where it must *include* that padding. With the shipped tokens the box comes out 10 px — half a line — short, and `freeRowsHeight`'s default of one whole line hides it. Two in-repo consumers set `[freeRowsHeight]="0"` (`filter-bar/pipes/pipe-text.html:29`, `components-dev/textarea/template.html:11`) and land exactly on the clipped case (THA-BUG-02). The `maxRows` clamp repeats the mistake and adds a unit mismatch, so a `[maxRows]="5"` field caps at 4.5 visible rows and trips the limit a row early (THA-BUG-03).
- **None of this is observable from the Jest suite.** A jsdom probe of the exact primitives `grow()` uses returns `lineHeight: "normal"`, `height: ""`, `scrollHeight: 0`, `clientHeight: 0` — every intermediate value is `NaN` or `0`, so `grow()` is a guaranteed no-op under unit test and `maxRowLimitReached` is permanently `false`. The three "grow behavior" cases (`textarea.component.spec.ts:313-369`) therefore assert *scheduling* — that `grow` was called, and called in a microtask — never geometry, and the one `kbq-textarea_max-row-limit-reached` assertion (`:304-310`) is vacuous: it would pass against a hardcoded `false` (THA-TEST-01).
- **Every keystroke pays for a live DOM clone and two forced reflows.** `grow()` clones the control, appends it into the form field's infix, reads `getComputedStyle().height`, `clientHeight` and `scrollHeight`, then removes it — write, read, write, read, in a microtask ahead of paint. `clone.remove()` is not in a `finally`, so a throw between insert and remove strands a duplicate `<textarea>` — carrying the same `id`, `name` and `aria-describedby` — permanently in the form (THA-PERF-01).

Genuine strengths, and they are not small. The form-control half of this directive is the best-behaved in the library: it is the **only** koobiq form control that binds `aria-invalid` (`:44` — `form-field`'s own review files the absence on `KbqInput`/`KbqSelect` as FF-A11Y-05), it forwards `required` to the native attribute, and its `id` is what `form-field`'s `<label for>` and `aria-describedby` wiring hang off. The `ErrorStateMatcher` integration is exemplary and is genuinely tested — 12 of the 24 Jest cases drive the default matcher, `ShowOnFormSubmitErrorStateMatcher`, `ShowOnControlDirtyErrorStateMatcher`, a DI-provided matcher and a custom one, including the async-validator regression from DS-4760. SSR is handled deliberately rather than by accident (`Platform.isBrowser` guards, `KBQ_WINDOW` instead of the global). And the Playwright suite is real behavioural coverage — grow, shrink, maxRows ceiling, and a scroll-on-focus regression guard — not just a screenshot.

## 3. Prioritized Findings (deduplicated, verified)

### P0 — Release blockers

None.

### P1 — High

**THA-BUG-01 · Auto-grow measures only on value/state change: a resized or previously-hidden container leaves a stale height, and `overflow-y: hidden` then clips the text** — `textarea.component.ts:236, 238, 241-258, 300-325`; `textarea.scss:24-27`; `tabs/tab-group.component.ts:94`.
`grow()` runs from exactly two sources: the `stateChanges` stream (`:238`) and the one-shot `setTimeout(this.grow, 0)` in `ngOnInit` (`:257`). `stateChanges` fires on value change, focus change, error-state change, `disabled`, and `ngOnChanges` — never on a geometry change. A grep of the package for `resize`, `Resize`, `fromEvent` and `ViewportRuler` returns nothing, while `SharedResizeObserver` is the established pattern in at least ten sibling packages (`actions-panel`, `clamped-text`, `code-block`, `dl`, `inline-edit`, `core/overflow-shadow`, …). The consequence is direct: the textarea's width is `100%` of the form field (`textarea.scss:15`), so any container width change rewraps the text into more lines, while the `min-height` pinned by the last `grow()` stays where it was — and in auto-grow mode `overflow-y` is `hidden` (`textarea.scss:24-27`), so the extra lines are clipped with no scrollbar and no visual indication that text exists below the fold. Widening produces the mirror defect: a permanent block of blank space.
The hidden-container case is worse because it never recovers. `getComputedStyle(el).height` on a `display: none` element resolves to `auto`, so `parseInt(…)` yields `NaN` (`:310`), `diff` is `NaN` (`:311`), `height` is `NaN` (`Math.max` propagates it, `:315`), and `coerceCssPixelValue(NaN)` produces the string `"NaNpx"` — not a valid CSS `<length>`, so the CSSOM drops the declaration and the element keeps whatever height it had. `rowsCount` becomes `NaN` and `maxRowLimitReached` silently reports `false` (`:207-209`). Nothing re-measures when the container is shown: the sole recovery hook is `this.parent?.animationDone.subscribe(() => this.ngOnInit())` (`:236`), and `KBQ_PARENT_ANIMATION_COMPONENT` is provided by exactly one component in the entire library — `KbqTabGroup` (`tabs/tab-group.component.ts:94`, verified by repo-wide grep). Modals, sidepanels, accordions, `@if` blocks and `[hidden]` toggles all get nothing. The same freeze applies before `ngOnInit`'s microtask has run: `freeRowsHeight` is still `undefined` at that point (`:170, 254`), so an early `stateChanges` emission drives the same `NaN` path.
**Fix:** subscribe the host element to CDK's `SharedResizeObserver` (or `ViewportRuler.change()` if element-level observation is too costly), outside the Angular zone, debounced, and call `grow()` only when the observed *width* actually changed — width is the only geometry input that alters wrapping, so caching the last measured width also removes redundant work for the height-only changes the observer reports after `grow()` writes `min-height`. Fold the visibility case in for free: `ResizeObserver` fires a `0×0` entry when an element is hidden and a real one when it is shown again, which is precisely the "re-measure when visible" signal that `animationDone` was approximating for tabs only. Guard `grow()` with an explicit `if (!Number.isFinite(lineHeight) || !this.elementRef.nativeElement.offsetParent) return;` so a hidden measurement is skipped rather than written as `NaNpx`. Add the e2e rows from THA-TEST-01 (narrow the viewport with a filled textarea; render one inside a `@if` that starts `false`) — those two rows are the regression guard.

**THA-BUG-02 · The grow formula subtracts the vertical padding it is required to include, so the box is half a line short; `[freeRowsHeight]="0"` consumers get clipped text** — `textarea.component.ts:310-315, 321-323`; `textarea.scss:17, 19`; `textarea-tokens.scss:4`; consumers `filter-bar/pipes/pipe-text.html:29`, `components-dev/textarea/template.html:11`.
Three lines decide the height:
`const outerHeight = parseInt(getComputedStyle(textarea).height, 10)` (`:310`) — CSSOM resolves `height` to the **content-box** height, regardless of `box-sizing`.
`const diff = outerHeight - +textarea.clientHeight` (`:311`) — `clientHeight` is the **padding-box** height, so with no horizontal scrollbar `diff` is exactly `−(paddingTop + paddingBottom)`.
`const height = Math.max(this.minHeight, +clone.scrollHeight + diff + this.freeRowsHeight)` (`:315`) — `scrollHeight` already includes both paddings, so `scrollHeight + diff` cancels them out and leaves the bare content height.
That value is then assigned to `textarea.style.minHeight` (`:321`) on an element declared `box-sizing: border-box` (`textarea.scss:17`), where `min-height` must *include* the padding. With the shipped tokens — `--kbq-textarea-size-padding-vertical: 5px` (`textarea-tokens.scss:4`) and `text-normal` line-height `20px` (`@koobiq/design-tokens/web/new/css-tokens.css:282`) — an *n*-line value produces `min-height = n·20 + freeRowsHeight − 0`, of which only `n·20 + freeRowsHeight − 10` is content box. Two user-visible consequences. First, with the default `freeRowsHeight` (`= lineHeight`, `:254`) the gap under the last line is 10 px, not the 20 px the input's own JSDoc promises ("Distance from the last line to the bottom border", `:167`) — a documented number that is off by 2×. Second, and worse, a consumer who asks for no gap at all gets a box **10 px shorter than its own content**, and because auto-grow mode sets `overflow-y: hidden` (`textarea.scss:24-27`) the bottom half of the last line is simply clipped. That is not hypothetical: `filter-bar/pipes/pipe-text.html:29` (`<textarea kbqTextarea rows="1" [freeRowsHeight]="0" [maxRows]="5">`) and the package's own dev app (`components-dev/textarea/template.html:11`) both do exactly this. `freeRowsHeight` is doing double duty as a padding-compensation fudge factor, which is why setting it to its documented no-op value breaks the layout.
**Fix:** stop cancelling the padding. Measure the clone's `scrollHeight` (which is already a padding-box quantity) and use it directly as the border-box `min-height`: `const height = Math.max(this.minHeight, clone.scrollHeight + this.freeRowsHeight)`, deleting `outerHeight` and `diff` entirely — they exist only to convert between box models that `box-sizing: border-box` has already reconciled. If a scrollbar-width correction is genuinely needed, compute it explicitly as `textarea.offsetHeight - textarea.clientHeight` (border + scrollbar) rather than inferring it from a content/padding mismatch. Guard the change with a Playwright case that sets `[freeRowsHeight]="0"` and asserts `scrollHeight === clientHeight` on the control (no hidden overflow) for a two-line and a five-line value; then re-check `filter-bar`'s pipe editor, whose one-row-then-grow behaviour is the tightest consumer of this arithmetic.

### P2 — Should fix

**THA-BUG-03 · The `maxRows` ceiling omits the padding and `rowsCount` divides a padded height by a bare line height, so the limit trips a row early and caps at `maxRows − 0.5` visible rows** — `textarea.component.ts:205-209, 315, 319, 321-323`; consumers `docs-examples/components/username/username-custom/username-custom-example.ts:59`, `username-playground/username-playground-example.ts:33`.
Two unit mismatches in three lines. `this.rowsCount = Math.floor(height / this.lineHeight)` (`:319`) divides a height that contains padding *and* `freeRowsHeight` by a bare line height; with the shipped tokens (20 px line, 10 px padding, `freeRowsHeight = 20`) the arithmetic from THA-BUG-02 gives `height = n·20 + 20` for *n* real lines, so `rowsCount` is always `n + 1`. `maxRowLimitReached` (`:207-209`) therefore flips as soon as the content reaches `maxRows` lines rather than exceeding them. At that moment the clamp writes `min-height = maxRows × lineHeight` (`:322`) — the only place in the file where padding is *not* added — which under `box-sizing: border-box` leaves `maxRows × lineHeight − 10px` of content box, i.e. `maxRows − 0.5` rows. Net effect for `[maxRows]="5"`: the fifth line is what triggers the cap, and the cap then shows four and a half lines with the fifth bisected. The off-by-one also fires on an *empty* field: with `rows="1" [maxRows]="1"` — the shape used by both `username` docs examples — `rowsCount` is 2 before a character is typed, so `maxRowLimitReached` is true from the first measurement and the field ships with `.kbq-textarea_max-row-limit-reached` permanently applied. It happens to look right there, which is why it has survived; it is still not what the code says it does. This is also the exact area DS-5158 (`1be11b8aa`, "fix(textarea): canGrow limit when maxRows") last reworked, so it is a proven regression surface.
**Fix:** derive rows from content, not from the final box: `const contentHeight = clone.scrollHeight - paddingTop - paddingBottom; this.rowsCount = Math.round(contentHeight / this.lineHeight);` (cache the two paddings alongside `lineHeight` in `ngOnInit`, they are already read there at `:247-251`). Make `maxRowLimitReached` an explicit `this.maxRows() != null && this.rowsCount > this.maxRows()` so an unset `maxRows` is a stated condition rather than a `NaN` comparison (see THA-API-02). Clamp with padding included: `this.maxRows() * this.lineHeight + paddingTop + paddingBottom`. Cover with a Playwright case asserting that a `[maxRows]="5"` control with exactly five lines has `scrollHeight === clientHeight` (all five visible, no scroll) and that the sixth line is what introduces the scrollbar — the current suite (`e2e.playwright-spec.ts:92-105`) only asserts that the height stops growing, which passes at any wrong ceiling.

**THA-PERF-01 · `grow()` inserts a live clone of the control and forces two synchronous reflows on every keystroke; the clone is removed without `try/finally`** — `textarea.component.ts:300-325`, host binding `:49`.
On every `input` event `dirtyCheckNativeValue()` (`:357-364`) emits `stateChanges`, which schedules `grow()` on `asapScheduler` (`:238`) — a microtask, i.e. before paint, on the critical path of the keystroke. `grow()` then does: `cloneNode(false)` of the textarea, `renderer.appendChild(parentNode, clone)` into the live document (`:306-308`), `getComputedStyle(textarea).height` (forced style+layout flush), `textarea.clientHeight` (layout), `clone.style.minHeight = '0'` (invalidate), `clone.scrollHeight` (second forced layout), `clone.remove()`, then `textarea.style.minHeight = …` (invalidate for the next frame). `runOutsideAngular` (`:303`) suppresses change detection but does nothing about layout cost. Two further hazards ride along. The clone is a shallow copy, so it carries the host's `id`, `name`, `data-testid`, `required` and the `aria-describedby` that `form-field` writes (`form-field.ts:541-544`) — for the duration of the measurement the document contains a duplicate element id, a second same-named control inside the enclosing `<form>`, and a second match for any `data-testid` locator. And `clone.remove()` (`:317`) is not inside a `finally`, so any throw between `:308` and `:317` — the same class of hazard already filed against `kbq-title` as TTL-ARCH-01 — strands that duplicate textarea in the form permanently. Note the last measurement write is a raw DOM write (`:321`) two lines after a `Renderer2` call (`:308`), so the file is inconsistent with itself about which abstraction owns the DOM.
**Fix:** wrap the insert/measure in `try { … } finally { clone.remove(); }` and strip identity from the clone before insertion (`clone.removeAttribute('id'); clone.removeAttribute('name'); clone.removeAttribute('data-testid'); clone.setAttribute('aria-hidden', 'true'); clone.tabIndex = -1;`). Then reduce how often the whole dance runs: cache the last measured `(value.length, clientWidth)` pair and return early when neither changed, and move the write behind `afterNextRender({ write: … })` so the read and the write land in the framework's own read/write phases instead of interleaving. The standard `height: auto` → `scrollHeight` → `height` trick on the element itself is one reflow instead of two and needs no clone; the clone exists to avoid a visible collapse frame, which `afterNextRender` phasing also solves.

**THA-LIFE-01 · The `animationDone` subscription has no teardown, re-invokes `ngOnInit()` by hand, and neither deferred callback is destroy-guarded — `grow()` on a detached node throws inside `Renderer2.appendChild`** — `textarea.component.ts:236, 238, 244, 257, 264-266, 308`.
Two lines of the same constructor disagree with each other: `:238` correctly pipes `stateChanges` through `takeUntilDestroyed()`, while `:236` — `this.parent?.animationDone.subscribe(() => this.ngOnInit())` — has no teardown at all. `animationDone` is an `output<void>()` on `KbqTabGroup` (`tabs/tab-group.component.ts:205`), so the subscription lives as long as the *tab group*, not as long as the textarea; a textarea destroyed inside a still-mounted tab group keeps receiving events and re-running its own `ngOnInit()` (behind an `// eslint-disable-next-line @angular-eslint/no-lifecycle-call`, `:235`, which is the code admitting the shape is wrong). `ngOnInit` then schedules a `Promise.resolve().then(…)` (`:244`) and a `setTimeout(this.grow, 0)` (`:257`), neither of which is cancelled in `ngOnDestroy` (`:264-266`, which only completes `stateChanges`). Running `grow()` on a detached element is not benign: `this.renderer.parentNode(textarea)` returns `null`, and `DefaultDomRenderer2.appendChild` calls `isTemplateNode(parent)` → `parent.tagName` with no null guard (`@angular/platform-browser/fesm2022/dom_renderer.mjs:557-559, 703-705`), so it throws `TypeError: Cannot read properties of null`. Note the sibling `insertBefore` right below it *does* guard with `if (parent)`, so this is a real asymmetry in the renderer and not something to rely on. The same crash is reachable without tabs at all: destroy the control within the same macrotask it was created in — an `@if` toggled twice, or `inline-edit` (`inline-edit/e2e.ts:239`) leaving edit mode immediately — and the pending `setTimeout` fires on the orphan.
**Fix:** replace both deferred callbacks with `afterNextRender` in the constructor's injection context (`afterNextRender({ read: () => { …measure lineHeight/padding… }, write: () => this.grow() })`) — it is cancelled automatically on destroy, runs only in the browser (removing the need for the `isBrowser` guard at `:242`), and matches the pattern `form-field`'s review prescribes for exactly this (FF-SSR-01/02/03). Add `.pipe(takeUntilDestroyed())` to the `animationDone` subscription and replace the manual `ngOnInit()` call with a private `measureAndGrow()` so the eslint suppression can go. Add a guard at the top of `grow()`: `const parent = this.renderer.parentNode(textarea); if (!parent) return;`. Cover with a spec that creates the fixture, destroys it inside the same tick and asserts no error is thrown after `tick()`.

**THA-TEST-01 · The auto-resize algorithm is structurally unobservable in Jest, and one of its three class assertions is vacuous** — `textarea.component.spec.ts:287-311, 313-369`; `e2e.playwright-spec.ts:34-106`.
A jsdom probe of the exact primitives `grow()` reads returns `getComputedStyle(el).lineHeight === "normal"` (→ `parseInt` `NaN`), `getComputedStyle(el).height === ""` (→ `NaN`), `el.clientHeight === 0` and `el.scrollHeight === 0`. Every intermediate in `grow()` is therefore `NaN` or `0` under unit test: `lineHeight`, `minHeight` and `freeRowsHeight` are all `NaN` after `ngOnInit` (`:245-254`), `height` is `NaN` (`:315`), `rowsCount` is `NaN` (`:319`), and `maxRowLimitReached` is permanently `false` (`:207-209`). The suite reflects this honestly but does not compensate: all three "grow behavior" cases (`:313-369`) assert *scheduling* — that `stateChanges.next` fired, that it fired once, that `grow` runs in a microtask rather than synchronously — and none asserts a height. Worse, `should not have kbq-textarea_max-row-limit-reached class when maxRows is not exceeded` (`:304-310`) passes for the wrong reason: the class can never be applied in jsdom, so the assertion would also pass if the binding at `:41` were replaced with a constant `false`. There is no positive case for that class anywhere. The Playwright suite carries all of the real coverage — 8 tests: one screenshot pair, grow/shrink, the `maxRows` ceiling, and a scroll-on-focus guard — but it exercises a single fixed 320 px column (`e2e.ts:105-113, 137-145`), never resizes the viewport, never renders the control hidden and then shows it, never varies `freeRowsHeight`, and has no screenshot of the max-row-limit-reached state (the states fixture at `e2e.ts:9-69` sets `canGrow="false"` on every cell that reaches the screenshot). Given that THA-BUG-01, -02 and -03 all live in those nine lines, this gap is the reason they are still here.
**Fix:** move the geometry contract to Playwright, where it can be observed, and keep Jest for wiring. Add to `e2e.ts`: a `freeRowsHeight` fixture (0 / default / explicit), a `@if`-gated fixture that starts hidden, and a resizable-width fixture; add to `e2e.playwright-spec.ts` a case per P1/P2 finding — `scrollHeight === clientHeight` after a viewport narrow (THA-BUG-01), the same assertion with `[freeRowsHeight]="0"` (THA-BUG-02), exactly-`maxRows` lines fully visible (THA-BUG-03) — and a screenshot row for the limit-reached state, produced through `yarn run e2e:docker:update-snapshots` (native runs fail on font rasterization alone; `playwright.config.ts:101` also pins `reducedMotion: 'reduce'` for every context, so the committed baselines are the reduced-motion state and any animation-dependent row must be written to pass there). In Jest, either stub `getComputedStyle`/`scrollHeight` explicitly so `rowsCount` becomes assertable, or delete the vacuous `:304-310` case and replace it with one that sets `rowsCount` through the public path and asserts both class branches — a class assertion that passes against a hardcoded `false` is worth nothing.

**THA-API-01 · Five accessor `@Input`s with stale migration TODOs and no `ngAcceptInputType_*`: the bare `required`/`disabled` attribute forms the repo's own spec uses do not type-check under `strictTemplates`** — `textarea.component.ts:69-78, 90-93, 123-141, 147-156, 162-170, 176-185, 191-203`; `tools/public_api_guard/components/textarea.api.md:60-63`; `tsconfig.json:117`; `textarea.component.spec.ts:77, 93`.
`canGrow`, `disabled`, `id`, `required` and `value` are all getter/setter `@Input` pairs, each carrying an auto-generated `// TODO: Skipped for migration because: Accessor inputs cannot be migrated as they are too complex` (`:69-70, 123-124, 147-148, 176-177, 191-192`), plus two more TODOs of other flavours on `errorStateMatcher` (`:90-92`) and `freeRowsHeight` (`:168-169`). None of the five is complex: `canGrow` is `!maxRowLimitReached && _canGrow` over a plain field, `required` is `coerceBooleanProperty` over a plain field, `id` is a `|| uid` fallback — all expressible as `input()` + `computed()`. The API report shows the concrete cost: only `ngAcceptInputType_canGrow` and `ngAcceptInputType_freeRowsHeight` exist (`textarea.api.md:60-63`), generated from their `transform` options; `disabled`, `required`, `id`, `placeholder` and `value` have none. With `strictTemplates: true` (`tsconfig.json:117`) a static attribute is type-checked as the string it actually is, so `<textarea kbqTextarea required>` assigns `''` to a `boolean` setter — an AOT compile error. The repo's own Jest hosts write exactly that form twice (`textarea.component.spec.ts:77, 93`) and get away with it only because Jest compiles templates JIT without type-checking; the guide meanwhile tells readers to configure the control "using the `disabled` attribute" (`textarea.en.md:19`). Note also the asymmetry with the sibling control: `KbqInput` binds `'[attr.disabled]': 'disabled || null'` (`input/input.ts:40`) while `KbqTextarea` binds the DOM property `'[disabled]': 'disabled'` (`:45`).
**Fix:** migrate all five to signals — `readonly canGrowInput = input(true, { transform: booleanAttribute, alias: 'canGrow' })` with a `readonly canGrow = computed(() => !this.maxRowLimitReached() && this.canGrowInput())`, `readonly required = input(false, { transform: booleanAttribute })`, `readonly id = input('', { transform: (v: string) => v || this.uid })` — which produces the missing `ngAcceptInputType_*` declarations for free and deletes all seven TODO comments. `disabled` must keep its `ngControl` delegation, so make it a `computed()` over a `model()`/`input()` backing signal. This changes the API report (accessor pairs become `InputSignal`s), so run `yarn run build:components` then `yarn run approve-api` — build first, the guard reads `dist/*.d.ts`. Because `value`, `disabled` and `required` are read by `form-field` through the `KbqFormFieldControl` abstract class (`form-field-control.ts:8, 32, 35`), coordinate the signal migration with `KbqInput`/`KbqSelect` or keep the plain-property shape on those three and migrate only `canGrow`/`id`/`placeholder`; either way, the missing `ngAcceptInputType_*` can be added by hand as a one-line stopgap.

### P3 — Nice to have / hygiene

**THA-API-02 · `maxRows` is published as `InputSignal<number>` but its runtime default is `undefined`** — `textarea.component.ts:87, 207-209`; `tools/public_api_guard/components/textarea.api.md:59`.
`readonly maxRows = input<number>(undefined!)` uses a non-null assertion to smuggle `undefined` past the type system; the API report duly advertises `readonly maxRows: i0.InputSignal<number>` (`textarea.api.md:59`), so a consumer reading `textareaRef.maxRows()` is handed `undefined` typed as `number`. The only guard is that `this.rowsCount > this.maxRows()` (`:208`) happens to evaluate `false` against `undefined`, which is accidental rather than intentional — and it is the same anti-pattern `form-field`'s review filed as FF-LOGIC-01, where `input<number>(undefined!)` on `min`/`max` produced `NaN` comparisons that always failed. It also means `maxRows` being unset and `maxRows` being exceeded are indistinguishable at the type level. Separately, `maxRows` is silently inert when `canGrow` is `false` — `grow()` returns at `:301` before `rowsCount` is ever written — and nothing says so.
**Fix:** `readonly maxRows = input<number | undefined>(undefined)` (or `input<number>()` with an explicit optional read), and make the guard explicit: `get maxRowLimitReached() { const max = this.maxRows(); return max != null && this.rowsCount > max; }`. Document the `canGrow` dependency in the JSDoc and in the guide (THA-DOC-01). `approve-api` after.

**THA-API-03 · `KBQ_TEXTAREA_VALUE_ACCESSOR` is dead, typed `{ value: any }`, and the `empty`/`isBadInput` getters bypass it; the class ships with no JSDoc** — `textarea.component.ts:31, 217, 224-228, 344-346, 367-372, 212`; `tools/public_api_guard/components/textarea.api.md:26-32, 38-95`.
The token is exported publicly (`:31`) but has zero providers anywhere in the repo or the docs app — the only reference is the directive injecting it from itself (`:224`). Its contract is `{ value: any }`, so it defeats type-checking at the one place it is used, and the abstraction is incomplete anyway: `value` reads through `this.valueAccessor` (`:195`) while `empty` (`:345`) and `isBadInput` (`:369`) read `this.elementRef.nativeElement` directly, so a consumer who *did* provide a custom accessor would see `value` and `empty` disagree. `isBadInput` is declared `: boolean` but returns `validity && validity.badInput`, i.e. `undefined` when `validity` is absent (the platform-server case its own comment describes, `:368`). Around it, the report shows a wide internal surface: `defaultErrorStateMatcher`, `parentForm`, `parentFormGroup`, `ngControl`, `updateErrorState()`, `onBlur()`, `previousNativeValue: any`, `uid`, and `grow` as a public mutable arrow field a consumer can reassign (`textarea.api.md:52`). And `KbqTextarea` itself is `// @public (undocumented)` (`:31` of the report) — the package's primary export has no class-level description in the generated API tab, which is what `structure.ts:1026` (`hasApi: true`) renders.
**Fix:** either delete `KBQ_TEXTAREA_VALUE_ACCESSOR` behind an `ng-update` migration (nothing in the repo or the docs uses it) or complete it — type it `{ value: string | null }`, route `empty`/`isBadInput` through it, and give it its own file the way `input/input-value-accessor.ts` does. Make `previousNativeValue`, `updateErrorState`, `onBlur` and `grow` `protected`, type `isBadInput` `: boolean` with `return !!validity?.badInput`, and add a class-level JSDoc block describing the two sizing modes and the `form-field` requirement. All of this churns `textarea.api.md`, so fold it into one `build:components` + `approve-api` cycle with THA-API-01/-02 rather than three.

**THA-ARCH-01 · `updateErrorState()` duplicates `KbqErrorStateTracker`, and the NgModule imports two modules it never uses** — `textarea.component.ts:282-293`; `core/common-behaviors/error-state.ts:70-96`; `datepicker/datepicker-input.directive.ts:894-895`; `textarea.module.ts:8`.
`updateErrorState()` (`:282-293`) is a line-for-line copy of `KbqErrorStateTracker.updateErrorState()` (`core/common-behaviors/error-state.ts:86-96`), the class core already ships for this and that `datepicker-input.directive.ts:894-895` already delegates to. The duplication is why `parentForm`, `parentFormGroup`, `defaultErrorStateMatcher` and `updateErrorState` are public members of `KbqTextarea` at all — they exist to satisfy the `HasErrorState` shape that the tracker encapsulates. (The older `mixinErrorState` is not the target: it `console.warn`s that it is deprecated, `error-state.ts:45-48`.) Separately, `textarea.module.ts:8` declares `imports: [A11yModule, FormsModule, KbqTextarea]` while exporting only `[KbqTextarea, KbqFormFieldModule]`: `KbqTextarea` is a directive with no template, so neither `A11yModule` nor `FormsModule` can affect it, and because they are not re-exported they do not help consumers either. Both are dead weight that the API report records in `ɵmod` (`textarea.api.md:108`), and a consumer using `[(ngModel)]` still has to import `FormsModule` themselves.
**Fix:** replace the hand-rolled block with `private readonly errorStateTracker = new KbqErrorStateTracker(this.defaultErrorStateMatcher, this.ngControl, this.parentFormGroup, this.parentForm, this.stateChanges)` and delegate `updateErrorState()`/`errorState` to it, following `datepicker-input.directive.ts`; that also lets the four supporting members become `private`. Drop `A11yModule` and `FormsModule` from the NgModule imports, or — if the intent was to spare consumers the `FormsModule` import — move `FormsModule` into `exports` deliberately and say so in the guide. Both changes alter `textarea.api.md`; batch with the THA-API-* cycle. Re-run the 24 Jest cases: the `ErrorStateMatcher` block is a complete behavioural spec for this swap and should stay green unchanged.

**THA-CSS-01 · One class carries two unrelated meanings, the resizer glyph hardcodes two hex colours, and one token is dead** — `textarea.component.ts:40-41`; `textarea.scss:24-40`; `textarea-tokens.scss:3, 6, 10`.
(1) `'[class.kbq-textarea-resizable]': '!canGrow'` (`:40`) applies the same class for two states that have nothing to do with each other: "the consumer turned auto-grow off, give them a native drag handle", and "auto-grow reached its ceiling, turn scrolling on" (because `canGrow`'s getter folds in `maxRowLimitReached`, `:72-74`). The stylesheet then has to walk it back — `.kbq-textarea_max-row-limit-reached { resize: unset }` (`textarea.scss:38-40`) cancels the `resize: vertical` the first class just granted — and the limit-reached state additionally inherits `min-height: var(--kbq-textarea-size-min-height)` (`:31`), which is meaningless there and survives only because the inline `min-height` written by `grow()` outranks it. A consumer styling `.kbq-textarea-resizable` (to hide the drag handle, say) silently also restyles the maxRows state. The naming compounds it: `kbq-textarea-resizable` is a plain suffix while its sibling `kbq-textarea_max-row-limit-reached` is a BEM modifier. (2) `--kbq-textarea-resizer-icon` inlines `fill="%238a8fa8"` for light and `fill="%23626884"` for dark (`textarea-tokens.scss:6, 10`); neither hex appears anywhere in `@koobiq/design-tokens/web/`, so the drag handle is the one part of this component that does not follow the palette and will not follow a consumer's theme override. (3) `--kbq-textarea-size-max-height: 96px` (`textarea-tokens.scss:3`) is referenced by nothing in `packages/` or `apps/` — a token consumers can set with no effect. Minor: `box-sizing: border-box` is declared twice (`textarea.scss:17` and again at `:25`).
**Fix:** split the class — keep `.kbq-textarea-resizable` bound to the raw `_canGrow` input and introduce `.kbq-textarea_scrollable` (or just let `.kbq-textarea_max-row-limit-reached` own `overflow-y: auto` directly) for the ceiling state, then delete the `resize: unset` walk-back and the stray `min-height`. Recolour the resizer through a token — `--kbq-textarea-resizer-color: var(--kbq-icon-contrast-fade)` composed into the `url()` via `%23` interpolation is not possible in a data-URI, so either ship the glyph as a masked `background-color` (`mask-image` + `background: currentColor`) or move it to `_textarea-theme.scss` where the two palettes already live. Delete `--kbq-textarea-size-max-height` and the duplicate `box-sizing`. All of these change rendering, so re-baseline through `yarn run e2e:docker:update-snapshots`.

**THA-DOC-01 · The guide describes the `canGrow` default backwards, never mentions `freeRowsHeight`, and `examples.textarea.*.md` are dead stubs** — `textarea.en.md:5-7, 11-13`, `textarea.ru.md:5-7, 11-13`; `textarea.component.ts:84, 167-170`; `examples.textarea.en.md:1-5`, `examples.textarea.ru.md:1-5`; `apps/docs/src/app/structure.ts:1018-1028`.
"When the `canGrow` attribute is enabled, the text field will automatically adjust its height" (`textarea.en.md:7`, mirrored at `textarea.ru.md:7`) reads as opt-in; `_canGrow` defaults to `true` (`:84`), so auto-resize is what you get unless you turn it *off* — which is why the overview example has to write `canGrow="false"` (`docs-examples/components/textarea/textarea-overview/textarea-overview-example.ts:13`) to demonstrate the plain variant. A reader who never writes `canGrow` gets the auto-resize behaviour the guide presents as optional, including the `overflow-y: hidden` clipping described in THA-BUG-01/-02. The `maxRows` section (`:13`) likewise omits that `maxRows` does nothing at all when `canGrow` is `false` (`grow()` returns at `:301`). And `freeRowsHeight` — a public input with a non-obvious default, load-bearing enough that two in-repo call sites set it explicitly — appears in neither guide, so its only documentation is the one-line JSDoc at `:167`, whose stated meaning is off by 2× (THA-BUG-02). Finally, both `examples.textarea.*.md` files carry the standard "🚧 Documentation in progress 🚧" stub, but `structure.ts:1027` sets `hasExamples: false`, so the Examples tab never renders and these are simply two unreachable files (all five examples are already embedded in the guide).
**Fix:** rewrite the Auto-resize section around the real default ("auto-resize is on by default; set `[canGrow]="false"` for a fixed, user-resizable field"), add a `freeRowsHeight` paragraph with its unit and default once THA-BUG-02 has settled what that default actually means, and state the `maxRows` ⇒ `canGrow` dependency in the Maximum-number-of-rows section. Both languages. Delete the two `examples.textarea.*.md` stubs (the guide already embeds every example, and `hasExamples: false` means nothing is lost) rather than filling them.

**THA-SSR-01 · Nothing sizes the control on the server, so an SSR'd multi-line textarea paints at two rows and jumps on the client's first macrotask** — `textarea.component.ts:241-258`; `e2e.playwright-spec.ts:37-41`.
`ngOnInit` returns before doing anything when `isBrowser` is false (`:242`), and `grow()` does the same (`:301`), which is correct — but it means the server emits a `<textarea>` with no `min-height` at all, so it renders at the UA default of two rows regardless of how many lines the value has. On the client the height is applied from a `setTimeout(…, 0)` (`:257`), i.e. after hydration and after the first paint, so an SSR page containing a filled auto-grow textarea shows a guaranteed layout shift. The Playwright suite documents the magnitude indirectly: `should grow initially when ngModel has multiple lines` asserts the settled height exceeds 50 px (`e2e.playwright-spec.ts:40`) for a three-line value whose pre-grow height is roughly 50 px. The same jump happens in CSR, one macrotask after render. The mechanism is also off-convention: `Promise.resolve().then()` + `setTimeout(…, 0)` is what `form-field`'s review asks the package family to replace with `afterNextRender` (FF-SSR-01/02/03), and doing so here fixes the destroy-safety half of THA-LIFE-01 at the same time.
**Fix:** move the measurement into `afterNextRender({ read, write })` (see THA-LIFE-01) so the height lands in the framework's first render pass rather than a macrotask after it — that alone removes most of the visible jump. For SSR specifically, emit a server-side approximation from the value itself: bind `[attr.rows]` to `value.split('\n').length` (clamped by `maxRows`) when `!isBrowser`, so the server-rendered box is already close to the final height and the client's first `grow()` is a small correction instead of a doubling. Guard with an e2e case that measures `boundingBox().height` before and after hydration and asserts the delta is under one line height.

## 4. Recommended Remediation Phases

**Phase 1 — Build a harness that can see the bug.**
IDs: THA-TEST-01. Nothing below is safely verifiable first: the Jest suite cannot observe geometry at all, and the Playwright suite tests one fixed-width column. Add the `freeRowsHeight`, hidden-then-shown and resizable-width fixtures to `e2e.ts`, the matching assertions to `e2e.playwright-spec.ts`, and a limit-reached screenshot row. Write them to **fail** against today's code — a harness that is green before the fix proves nothing — and land the baselines through Docker.

**Phase 2 — Correct the measurement arithmetic.**
IDs: THA-BUG-02, THA-BUG-03. Remove `outerHeight`/`diff` and let `scrollHeight` be the border-box quantity it already is; derive `rowsCount` from content height rather than the padded final box; add the padding to the `maxRows` clamp; make `maxRowLimitReached` an explicit null check. Pure arithmetic, no API change, and Phase 1's new cases flip from red to green as the acceptance criterion. Re-verify `filter-bar`'s pipe editor and both `username` examples, the three call sites whose current appearance depends on the current (wrong) numbers.

**Phase 3 — Re-measure at the right times, safely.**
IDs: THA-BUG-01, THA-LIFE-01, THA-PERF-01, THA-SSR-01. One rewrite of the same block: `afterNextRender` replaces the `Promise`/`setTimeout` pair, `SharedResizeObserver` replaces the value-change-only trigger, `takeUntilDestroyed` and a null-parent guard close the crash path, `try/finally` and an identity-stripped clone close the DOM hazards, and a cached `(length, width)` pair keeps the added observer from multiplying the per-keystroke cost. Ship with the hidden-container and viewport-narrow cases from Phase 1 as the proof.

**Phase 4 — API surface, architecture and docs.**
IDs: THA-API-01, THA-API-02, THA-API-03, THA-ARCH-01, THA-CSS-01, THA-DOC-01. Migrate the accessor inputs to signals (which supplies the missing `ngAcceptInputType_*` and deletes seven stale TODOs), fix the `maxRows` type, resolve or complete `KBQ_TEXTAREA_VALUE_ACCESSOR`, delegate to `KbqErrorStateTracker`, drop the dead NgModule imports, split the overloaded class, tokenize the resizer colour, and correct both guides. One `yarn run build:components` + `yarn run approve-api` cycle covers every API-report change; visibility tightening is technically breaking, so schedule with the next minor/major and pair `KBQ_TEXTAREA_VALUE_ACCESSOR`'s removal with an `ng-update` migration.

## Appendix A — Review Methodology

Every file in the package was read in full (`textarea.component.ts` 373 lines, `textarea.component.spec.ts` 549 lines / 24 cases, `e2e.ts` 183 lines / 4 fixtures, `e2e.playwright-spec.ts` 132 lines / 8 tests, three SCSS files, four Markdown files, the module and barrel files). Each candidate was then cross-checked against five independent sources: the workspace compiler settings (`tsconfig.json:114-118`), the API guard report (`tools/public_api_guard/components/textarea.api.md`, and `tools/api-extractor/config.json:54` confirming the package is guarded), the live design-token set (`@koobiq/design-tokens/web/new/`), every in-repo call site of `kbqTextarea` found by grep (38 hits across `filter-bar`, `form-field`, `inline-edit`, `core/forms`, three dev apps, and the `textarea`/`username`/`validation` docs examples), and the git history of the package (15 commits; DS-5158 and DS-4760 are both fixes inside the code under review). Two claims were settled empirically rather than by reasoning: a jsdom probe of `getComputedStyle().lineHeight`/`.height`, `clientHeight`, `scrollHeight` and `HTMLTextAreaElement.cloneNode(false).value` (the Jest environment's actual behaviour), and a read of the installed `@angular/platform-browser` renderer to confirm that `appendChild` has no null-parent guard where `insertBefore` does. Findings that belong to `form-field` rather than to this package were deliberately left to `REVIEW.form-field.md`; where the two touch, this document cites the FF id rather than restating it.

Refuted during verification:
- **"`cloneNode(false)` is a shallow clone, so `grow()` measures an empty textarea"** — refuted, and it was the most attractive-looking candidate. The HTML cloning steps propagate a textarea's value, verified directly in this workspace's jsdom: a clone of `<textarea>abc\ndef\nghi</textarea>` reports `value === "abc\ndef\nghi"`, and after `el.value = "x\ny"` a fresh clone reports `"x\ny"`. The committed Playwright grow/shrink assertions (`e2e.playwright-spec.ts:43-67`) would also fail outright if this were broken.
- **"Hints and errors are never linked to the control by `aria-describedby`"** (i.e. `form-field`'s FF-A11Y-02 still applies) — refuted at this commit. `form-field.ts:541-544` writes the attribute onto the control's host element via `kbqSetDescribedByIds`, `form-field-control.ts:59-66` documents `setDescribedByIds` as the *opt-out* for controls that need it elsewhere, and `form-field.spec.ts:837-886` asserts the behaviour. FF-A11Y-02 was fixed by `1944972f9`, after that review's commit (`96fee28c`).
- **"The textarea has no accessible name, because `kbq-label` is a bare directive with no `for`"** — refuted. `form-field.html:2` renders a real `<label class="kbq-form-field__label" [attr.for]="control().id">` and `KbqTextarea` binds `[attr.id]` to the same `id` (`:42`), with a generated `uid` fallback forced in the constructor (`:233`).
- **"`aria-invalid` is missing on the control"** — refuted; `:44` binds it, and `KbqTextarea` is the only koobiq form control that does (`form-field`'s FF-A11Y-05 files the *absence* on `KbqInput`/`KbqSelect`). `aria-invalid="false"` on a valid control is valid ARIA, not noise.
- **"`@Input() disabled` on an element that also carries `[formControl]` triggers Angular's reactive-forms `disabled` warning"** — refuted. That warning is emitted by `NgModel`/`FormControlDirective` for a `disabled` binding on the *form directive*; `disabled` here is `KbqTextarea`'s own input, and its getter delegates to `ngControl.disabled` when a control is present (`:126-132`), so the two never fight.
- **"The missing colour mixin in `_textarea-theme.scss` is a defect"** — refuted; the file legitimately owns typography only (`_textarea-theme.scss:3-7`). Colours, placeholder colours and the autofill treatment all come from `form-field/_form-field-theme.scss:22-50, 76-90`, which styles `.kbq-textarea` alongside `.kbq-input` and `.kbq-tag-input`. This is the delegation the review inventory warns not to file blindly.
- **"No `maxlength` support and no character counter is a textarea defect"** — refuted as a textarea finding, and deferred. There is no counter anywhere in the library (`grep -rni maxlength packages/` returns only validators and one hand-rolled `kbq-hint` counter at `docs-examples/components/form-field/form-field-with-hint/form-field-with-hint-example.ts:15`). Making a live counter *announce* would require `aria-live` on `kbq-hint`, which is `form-field`'s surface and adjacent to FF-A11Y-03; a `maxlength` passthrough on the textarea alone would not fix the announcement.

Corrected on verification:
- **THA-BUG-02** was first drafted as "the auto-grown box is one whole row too tall, because `freeRowsHeight` defaults to a full line". Tracing `diff` showed the formula *also* cancels the vertical padding, so the two errors partly offset: the real slack is half a row, and the defect flips from cosmetic to clipping the moment a consumer sets `[freeRowsHeight]="0"` — which two in-repo call sites do. The severity moved from P3 to P1 on that consumer evidence.
- **THA-TEST-01** was first drafted as "auto-resize behaviour is only covered by Playwright", a routine P3. The jsdom probe showed the three Jest grow cases *cannot* observe geometry and that the `max-row-limit-reached` assertion passes against a hardcoded `false`, which makes it an actively misleading test rather than a missing one. Raised to P2 and re-scoped around the vacuous assertion.
- **THA-LIFE-01** was first filed as a plain missing-teardown leak. Following `grow()` onto a detached node showed `Renderer2.appendChild(null, clone)` throws — `isTemplateNode(parent)` dereferences `parent.tagName` with no guard (`dom_renderer.mjs:557-559, 703-705`) — so it is a crash path, not only a leak, and the fix acquired an explicit null-parent guard.
- **THA-BUG-01** was first scoped to window resize only. Working through the `NaN` propagation showed the hidden-container case is strictly worse (the height is never written at all, and only `KbqTabGroup` provides a recovery hook), so the finding was widened and the fix reframed around `ResizeObserver`'s `0×0` entry, which covers both.
