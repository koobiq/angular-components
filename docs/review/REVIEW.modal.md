# Koobiq `modal` Component — Code Review & Improvement Plan

> Scope: `packages/components/modal` (component + template, imperative service and builder, control service, composition directives, CSS-unit pipe, click-position util, tokens/theme/animation SCSS, both Jest specs, e2e fixture + Playwright spec, user guides, API guard report) · Commit `b665e503` · 2026-08-28
> Generated by a multi-dimension review (architecture, RxJS & lifecycle, correctness, accessibility, performance, public API/types, styles, tests, docs) with manual verification of every finding against the source, the in-repo consumers, the installed `@angular/cdk` 20.2.14 sources and the workspace configuration. 15 findings confirmed (P0×1, P1×4, P2×5, P3×5); 6 candidate findings refuted during verification (see Appendix A). This document is a review + roadmap; no source is modified by it.

---

## 1. Executive Summary

`KbqModalComponent` (750 lines) plus `KbqModalService` / `ModalBuilderForService` (168 lines), `KbqModalControlService` (126 lines) and four composition directives (81 lines) make up the library's only blocking-dialog primitive. It has two front doors that behave very differently: the imperative `modalService.create()/open()/confirm()` path, which is well exercised, and the declarative `<kbq-modal [(kbqVisible)]>` path, which is barely wired up at all. Most of the serious findings below sit exactly on that seam.

- **The dialog is invisible to assistive technology.** The entire package emits exactly one ARIA attribute — the close button's `aria-label` (`modal.component.html:86`). There is no `role="dialog"`, no `aria-modal="true"`, no `aria-labelledby` pointing at `kbqTitle`, and nothing marks the page behind the overlay as `inert`/`aria-hidden`. A screen-reader user gets no announcement that a dialog opened and can keep reading and operating the page underneath with the virtual cursor while the visual focus trap holds sighted keyboard users inside. On the service path there is no consumer workaround at all — no input or option adds host attributes (MDL-A11Y-01).
- **A modal outlives whatever opened it.** `ModalBuilderForService` disposes its overlay only from the `kbqAfterClose` subscription (`modal.service.ts:46, 53-58`); nothing is tied to the caller's `DestroyRef`, and `overlay.create()` leaves `disposeOnNavigation` at its `false` default. Destroy the opener — route change, `*ngIf` — and the dialog stays on screen over the new view, `afterClose` never emits, and `document.body { overflow: hidden }` set by `changeBodyOverflow` (`modal.component.ts:732-740`) is never released, because `ngOnDestroy` (`:389-393`) only touches `container`, which is `undefined` on the service path (MDL-LIFE-01).
- **On the declarative path the close affordances do nothing.** `handleCloseResult` closes only when the trigger is a *function* (`modal.component.ts:502-527`); `kbqOnOk`/`kbqOnCancel` default to `EventEmitter`s (`:254, :274`), and only `KbqModalService.create()` overwrites them with closures (`modal.service.ts:97-105`). So on a plain `<kbq-modal>` the ×, the mask click and the predefined OK/Cancel buttons emit and return without closing. The repo's own dev app demonstrates it: `template.html:62-70` renders such a modal and nothing in `module.ts` ever sets `htmlModalVisible` back to `false` (MDL-BUG-01). The same seam swallows `kbqCloseByESC`, which `onKeyDown` never reads (MDL-BUG-02).
- **Focus handling is a best-effort DOM guess, not a contract.** Initial focus is `getElementsByTagName('button')[0]?.focus()` in `ngAfterViewInit` (`modal.component.ts:384-386`) — one shot, at construction time, on whichever `<button>` happens to be first in the DOM. A modal with no button (`modalService.create({ kbqContent: 'text' })`) never receives focus at all, so `cdkTrapFocus` (`modal.component.html:30`) never has anything to contain, and the `FocusMonitor` registration opened in `open()` is never torn down (MDL-A11Y-02, MDL-LIFE-03). Focus capture and restoration live entirely in `open()`/`close()`, which only the service path calls (`modal.service.ts:45`).
- **The control service still retains modals it was already patched to release.** DS-4755 (`dd05a3ce2`) added unregistration to `removeOpenModal`, but inside the `index > -1` guard (`modal-control.service.ts:66-85`), so it only covers modals that actually opened. Every `<kbq-modal>` that is created and destroyed without ever being shown stays in the root-level `registeredMetaMap` forever, together with its component, DOM and subscriptions — and the spec case written to guard exactly that path exercises the opposite one (`modal-control.service.spec.ts:53-66`) (MDL-LIFE-02, MDL-TEST-01).

Genuine strengths worth preserving: the scroll-shadow integration is the best-tested part of the package — 6 of the 8 Playwright cases assert real computed shadows on both the templated and the fully custom composition paths (`e2e.playwright-spec.ts:33-107`); the `KBQ_MODAL_DATA` + `options.injector` design is documented, exemplified and covered by a spec (`modal.spec.ts:554-573`) and by a dedicated Examples-tab page; styling is entirely token-driven with a clean light/dark split and no hardcoded colors; the close button already sources its accessible name from `kbqInjectA11yLocaleConfiguration()` in both the templated and the composed header (`modal.component.ts:98`, `modal.directive.ts:43`), with a Jest case pinning it (`modal.spec.ts:189-202`); and the guide is a thorough, genuinely bilingual 151-line design document with nine live examples behind it.

## 3. Prioritized Findings (deduplicated, verified)

### P0 — Release blockers

**MDL-A11Y-01 · The dialog carries no dialog semantics and never hides the page behind it** — `modal.component.ts:79-82` (host block), `modal.component.html:16-30, 53-93`, `modal.directive.ts:33-37`, `modal.service.ts:68-73`.
Grepping the whole package for `role`/`aria-` returns exactly two hits, both the close button's `aria-label` (`modal.component.html:86`, `modal.directive.ts:25`). The component host declares only `class: 'kbq-modal'` and a `keydown` handler (`modal.component.ts:79-82`); `.kbq-modal-wrap` carries `tabindex="-1"` and nothing else (`modal.component.html:16-21`); `.kbq-modal-container` and `.kbq-modal-content` carry classes and `cdkTrapFocus` (`:22-30`). Consequences, in order of severity: (1) no `role="dialog"` — nothing tells a screen reader a dialog was opened, so the user's reading position and mental model do not change; (2) no `aria-modal="true"` and no `inert`/`aria-hidden` on the application root — the virtual cursor walks straight past the overlay into the page underneath and can activate controls there while the sighted keyboard user is locked inside the trap, which is exactly the inconsistency `aria-modal` exists to prevent; (3) no `aria-labelledby`/`aria-describedby` — the `kbqTitle` and `kbqCaption` the caller supplies (`modal.component.html:56-79`) are never associated with the dialog, so even after a `role` is added the dialog would be announced unnamed; (4) with stacked modals (an explicitly supported and documented scenario, `modal.en.md:123-127`, `e2e.ts:45-60`) nothing hides the lower dialog from assistive tech either. Be precise about the class of failure: axe-core does **not** flag this — its `aria-dialog-name` rule only fires on elements that already declare `role="dialog"` — so the automated suite is green. This is a WCAG 4.1.2 (Name, Role, Value) and 1.3.1 (Info and Relationships) judgement, and AGENTS.md states WCAG AA as a mandate. What makes it a release blocker rather than a P1 is the absence of any workaround on the imperative path: `ModalOptions` (`modal.type.ts:27-66`) exposes `kbqClassName`, `kbqWrapClassName`, `kbqStyle` and `kbqBodyStyle` — class and style hooks only — so a consumer calling `modalService.create()` has no supported way to add a single attribute to the dialog element. Note the same gap exists in `sidepanel` (`grep -rn "aria-modal" packages/components/` returns nothing repo-wide), so the fix should be designed once for both.
**Fix:** move the dialog semantics onto `.kbq-modal-container` (the element that is visually and conceptually the dialog, `modal.component.html:22-29`): `role="dialog"`, `aria-modal="true"`, and `[attr.aria-labelledby]` pointing at an id generated for the `.kbq-modal-title` node, falling back to a new `kbqAriaLabel` option in `ModalOptions` when the modal has no title (the confirm and no-header variants, `modal.en.md:18-22`). Add `[attr.aria-describedby]` for `kbqCaption` when present. Because the overlay container is a direct child of `<body>`, `aria-modal="true"` is sufficient in modern AT, but pair it with `inert` on the application root while `openModals.length > 0` — `KbqModalControlService` already owns that counter (`modal-control.service.ts:22-24`) and `accordion-content.directive.ts:24` is the in-repo precedent for the `[attr.inert]` binding. For stacked dialogs, apply `inert` to every open modal except the topmost. Guard with a `jest-axe` case per variant (default/confirm/custom, titled and untitled) plus a spec asserting `getAttribute('aria-labelledby')` resolves to the rendered title text; extend `e2e.ts` with a keyboard-only walk that proves the background is unreachable.

### P1 — High

**MDL-LIFE-01 · A service-created modal outlives its opener, keeps the page scroll-locked, and never emits `afterClose`** — `modal.service.ts:29-47, 53-58, 60-65, 68-73`, `modal.component.ts:389-393, 607-628, 732-740`.
`KbqModalService` is `providedIn: 'root'` (`modal.service.ts:76`) and hands the dialog to a `ModalBuilderForService` that is owned by nobody: it holds the `OverlayRef` and `ComponentRef` and disposes them from exactly one place — the `kbqAfterClose` subscription set up in its constructor (`:46` → `destroyModal()` at `:53-58`). No `DestroyRef`, no `takeUntilDestroyed`, and `overlay.create()` is called with no config (`:69`), so CDK's defaults apply: `disposeOnNavigation = false` and `scrollStrategy = new NoopScrollStrategy()` (verified in `@angular/cdk/fesm2022/overlay-module.mjs:336, 367`). Destroy the component that called `create()` — a route change, an `*ngIf`, a closed tab in a shell app — and every one of those links is severed: the overlay stays attached to the root container and the dialog remains painted over whatever renders next; `kbqAfterClose` never fires, so a consumer awaiting `firstValueFrom(modalRef.afterClose)` waits forever; and the `body { overflow: hidden }` written by `changeBodyOverflow(1)` on open (`modal.component.ts:609, 732-740`) is never removed, because the release path lives in the close continuation (`:624`) and `ngOnDestroy` (`:389-393`) only disposes `container` — which is `undefined` for service modals, since `modal.service.ts:31-33` deliberately sets `options.kbqGetContainer = undefined` before `Object.assign`. The user-visible result is a permanently unscrollable page. Two aggravating details: `changeVisibleFromInside` returns early without emitting when `kbqVisible` already equals the target (`modal.component.ts:631-641`), so `afterClose` has no emission guarantee even on the happy path if `close()` races or repeats; and `changeProps`'s blanket `Object.assign` (`modal.service.ts:60-65`) will happily overwrite the `readonly kbqAfterClose` emitter with one supplied in `ModalOptions.kbqAfterClose` (`modal.type.ts:51`) — `readonly` is a compile-time annotation only — which means overlay disposal itself hangs off an emitter the caller controls and can complete.
**Fix:** give the dialog a lifecycle owner. In `KbqModalService.create()`, resolve a `DestroyRef` from `options.injector ?? this.injector` and register `destroyModal()` on it, so the modal is torn down with its opener; pass `new OverlayConfig({ disposeOnNavigation: true })` to `overlay.create()` as a second line of defence. Move the scroll-lock release out of the close continuation into `KbqModalControlService` (which already owns `openModals`) or into `KbqModalComponent.ngOnDestroy`, so it is refcount-correct under abrupt destruction. Make `close()` emit unconditionally — or document explicitly that `afterClose` is not guaranteed — and stop letting `changeProps` overwrite the output emitters: filter the assigned keys against a whitelist derived from `ModalOptions`, or drop `kbqAfterOpen`/`kbqAfterClose` from `ModalOptions` entirely (they duplicate the `afterOpen`/`afterClose` observables on the returned ref). Guard with a spec that creates a modal from a child component, destroys the child fixture, and asserts the overlay container is empty and `document.body.style.overflow` is `''`.

**MDL-BUG-01 · On the declarative path the ×, the mask and the predefined buttons never close the dialog** — `modal.component.ts:254, 274, 457-466, 490-499, 502-527`, `modal.service.ts:97-105`, consumer `packages/components-dev/modal/template.html:62-70` + `module.ts:164, 318`.
`handleCloseResult` branches on the *runtime type* of the trigger: an `EventEmitter` is emitted and the method returns; only a plain function reaches `caseClose(...)` and therefore `this.close(...)` (`modal.component.ts:502-527`). Both triggers default to emitters — `@Input() @Output() readonly kbqOnOk = new EventEmitter<T>()` (`:254`) and the same for `kbqOnCancel` (`:274`) — and the only place they are replaced by closures is `KbqModalService.create()`, which substitutes `() => {}` when the option is not a function (`modal.service.ts:97-105`). Consequence: on `<kbq-modal>` used declaratively, `onClickCloseBtn()` → `onClickOkCancel('cancel')` → emit-and-return (`modal.component.ts:490-499`); the mask click takes the identical route (`:457-466`), so `kbqMaskClosable` is inert there too; and the predefined OK/Cancel buttons (`modal.component.html:144-158`) behave the same. The dialog can then only be closed by writing `false` back to `kbqVisible` from a `(kbqOnCancel)` handler — a requirement stated in no guide, no JSDoc and no example. The repo's own dev app is the proof: `template.html:62-70` renders `<kbq-modal [kbqOkText] [kbqCancelText] [kbqTitle] [(kbqVisible)]="htmlModalVisible">` with no `(kbqOnOk)`/`(kbqOnCancel)` bindings, and `module.ts` only ever sets `htmlModalVisible = true` (`:318`); nothing sets it back, so the fixture's own ×, Accept and Cancel are dead until the unrelated `closeAll()` timer fires. Meanwhile `modal.en.md:36-46` lists the × and the Cancel button as the two required ways to close a dialog, without distinguishing the two APIs.
**Fix:** decide the contract and make it uniform. The lower-risk option: in `handleCloseResult`, emit on the `EventEmitter` branch *and then* run the same `canClose`/`close()` continuation, so emit-only becomes a notification rather than a veto, and keep the veto semantics exclusively on the function form (which already supports returning `false`). If the emit-only behaviour must be preserved for compatibility, then move the service's defaulting into the component — initialise `kbqOnOk`/`kbqOnCancel` to closures and let a template binding *replace* them via `@Output` subscription rather than swapping the member — and document the difference in `modal.en.md`/`modal.ru.md`. Either way, fix `packages/components-dev/modal/template.html:62-70` so the shipped fixture can actually be dismissed. Guard with Jest cases that click `.kbq-modal-close`, the mask and the OK button on a declarative host and assert `kbqVisible` became `false` and `kbqVisibleChange` emitted.

**MDL-A11Y-02 · Initial focus is a DOM guess that can miss entirely; containment and restoration exist only on the service path** — `modal.component.ts:378-387, 395-405, 407-418`, `modal.component.html:30, 147, 188`, `modal.en.md:62-85`.
Three separate weaknesses in one mechanism. (1) *The target is guessed.* `ngAfterViewInit` runs `this.getElement().getElementsByTagName('button')[0]?.focus()` and then `(querySelector('button[autofocus]'))?.focus()` (`:384-386`) — the first `<button>` in document order across the whole dialog, including projected content. For a titled, closable modal that button is the × in the header (the header precedes the body in `modal.component.html:53-93`), which directly contradicts the published rule "Focus is placed on the first available element inside the dialog body" (`modal.en.md:70`). (2) *It can miss completely.* `modalService.create({ kbqContent: 'text' })` renders no header (no `kbqTitle`) and no footer (no `kbqOkText`/`kbqCancelText`/`kbqFooter`, `modal.component.html:117`), so there is no `<button>` at all: focus stays on the trigger *behind* the dialog. `cdkTrapFocus` on `.kbq-modal-content` (`modal.component.html:30`) is applied without `cdkTrapFocusAutoCapture`, so it never pulls focus in — it only wraps focus that is already inside — and the documented promise "focus moves only through elements inside the window" (`modal.en.md:64`) is broken. The same happens whenever the dialog's content arrives asynchronously (`@if`, `@defer`, a data load), because `ngAfterViewInit` is a one-shot at construction time. Compare `sidepanel`, which exposes the knob the modal lacks: `[cdkTrapFocusAutoCapture]="trapFocusAutoCapture"` (`sidepanel-container.component.html:6`, configured at `sidepanel-config.ts:26`). (3) *Restoration is service-only.* `focusedElementBeforeOpen` and the origin are captured in `open()` (`:396-397`) and replayed in `close()` (`:409-416`), and `open()` is called from exactly one place — `modal.service.ts:45`. A declarative `<kbq-modal>` toggled through `kbqVisible` goes through `ngOnChanges → handleVisibleStateChange` (`:342-347`), which touches neither, so it neither moves focus in on show nor restores it on hide, contradicting `modal.en.md:76-85`.
**Fix:** replace the two `.focus()` calls with a real initial-focus policy: set `[cdkTrapFocusAutoCapture]="true"` on `.kbq-modal-content` so CDK's `focusInitialElement()` handles `[cdkFocusInitial]`, `autofocus` and first-tabbable in the documented order, and add a `kbqAutoFocus: 'first-tabbable' | 'dialog' | 'first-heading' | false` option to `ModalOptions` mapping onto it — `'dialog'` (focus the container itself, which already needs a `tabindex="-1"` as part of MDL-A11Y-01) is the correct default for long scrollable bodies, exactly the case `modal.en.md:74` describes. Drive open/close focus from a single place that both paths reach — `handleVisibleStateChange` — rather than from `open()`/`close()`, so the declarative path inherits capture and restoration. Guard with specs for: a button-less modal (focus lands inside the dialog), Tab/Shift+Tab from the last/first control (stays inside), and a declarative show/hide cycle (focus returns to the trigger).

**MDL-LIFE-02 · The root registry keeps every modal that was never opened** — `modal-control.service.ts:34-39, 42-51, 66-85, 87-125`, `modal.component.ts:375, 389-393`, history `dd05a3ce2`.
`registerModal()` is called unconditionally from `ngOnInit` (`modal.component.ts:375`) and writes an entry into `registeredMetaMap` — a plain `Map` held by the root-level service instance (`modal-control.service.ts:34, 37-39, 47`). The only removal path is `removeOpenModal()`, and the unregistration block DS-4755 added sits *inside* the `if (index > -1)` guard that tests membership of `openModals` (`:66-85`). `openModals` is only ever appended from the `afterOpen` subscription (`:44`), which fires 300 ms after `open()`. So a modal that is created and destroyed without ever being shown — the normal life of a `<kbq-modal>` declared in a template the user never triggers — leaves behind a permanent entry holding the `KbqModalRef` (i.e. the whole `KbqModalComponent`, its view, its detached DOM and its two live subscriptions). `KbqModalComponent.ngOnDestroy` (`:389-393`) does not unregister. The git history shows this is the second lap around the same defect: `dd05a3ce2` "fix(modal): unregister modal ref after close (#DS-4755)" added exactly nine lines inside that guard. A second, smaller retention rides along: `handleMultipleMasks` subscribes to `modalRef.beforeClose` (`:108-123`) with no teardown, and the closure captures `visibleModalsWithMask`, an array of *other* modal components — so each stacking event pins a set of sibling dialogs for as long as the emitter lives. That same block is also duplicated work: everything it does to `modalRef` (`:111-112, 117`) is invariant with respect to the loop variable, so it re-runs once per previously-masked modal.
**Fix:** unregister on destroy, not on close. Add a `deregisterModal(modalRef)` to `KbqModalControlService` that unsubscribes both stored subscriptions and deletes the map entry regardless of `openModals` membership, and call it from `KbqModalComponent.ngOnDestroy`; keep `removeOpenModal` for the `afterAllClose` bookkeeping only. Bound the second retention by piping the `beforeClose` subscription through `takeUntilDestroyed` (or the same `deregisterModal` teardown), and hoist the `modalRef`-only statements out of the `forEach`. Guard with a spec that creates and destroys a declarative modal fixture without opening it and asserts `hasRegistered()` is `false` afterwards — that is precisely the case the existing spec claims to cover but does not (see MDL-TEST-01).

### P2 — Should fix

**MDL-BUG-02 · `kbqCloseByESC` is ignored on the declarative path, and Escape there bypasses `kbqOnCancel`** — `modal.component.ts:173, 365, 472-487`, `modal.service.ts:31-33, 37-43`.
Escape is handled in two unrelated places with different rules. On the service path, `ModalBuilderForService` subscribes to `overlayRef.keydownEvents()` after `kbqAfterOpen` and correctly filters on `options.kbqCloseByESC` before calling `handleCloseResult('cancel', () => true)` (`modal.service.ts:37-43`) — so the cancel callback runs and the veto contract holds. On the declarative path the host handler runs instead: `onKeyDown` closes when `event.keyCode === ESCAPE && this.container instanceof OverlayRef` (`modal.component.ts:472-477`). It never reads `kbqCloseByESC` (`:173`), so `<kbq-modal [kbqCloseByESC]="false">` still closes on Escape — a data-loss hazard for a dialog whose whole point is to be dismissed deliberately. It also calls `this.close()` directly rather than routing through `handleCloseResult`, so `kbqOnCancel` never fires and a handler that would have vetoed the close is skipped — contradicting the guide's own keyboard table, which defines Escape as equivalent to the Cancel button (`modal.en.md:92`). The two paths are mutually exclusive by construction: `modal.service.ts:31-33` forces `kbqGetContainer` to `undefined` for service modals, so `this.container` (`modal.component.ts:365`) is `undefined` there and the host branch is unreachable; declarative modals get the default `() => this.overlay.create()` (`:335`) and so always take the host branch.
**Fix:** delete the Escape branch from `onKeyDown` and give the declarative path the same subscription the builder uses — the component already knows its `OverlayRef` (`this.container`), so the `keydownEvents()`/`kbqCloseByESC`/`handleCloseResult('cancel', …)` sequence can move into the component and serve both paths, with the builder's copy removed. Guard with two Jest cases per path: Escape with `kbqCloseByESC: false` leaves the modal open, and Escape with the default invokes `kbqOnCancel` before closing.

**MDL-LIFE-03 · The focus-origin probe reaches into a CDK private field and can leave a `FocusMonitor` registration behind** — `modal.component.ts:395-405, 407-418`.
`open()` does two questionable things to recover the focus origin for restoration. First, `this.previouslyFocusedElementOrigin = this.focusMonitor['_lastFocusOrigin']` (`:397`) — a bracket-access read of a private-by-convention field on `FocusMonitor` (`@angular/cdk/fesm2022/focus-monitor.mjs:206`). The bracket form silences both TypeScript and the linter, so a CDK rename would not fail the build: the field would read `undefined`, `focusVia(el, undefined)` would fall through to `'program'`, and the only symptom would be a missing focus ring after close — the exact scenario `modal.spec.ts:504-539` was written to pin, which would then start failing for a reason unrelated to its name. Second, `focusMonitor.monitor(this.modalContainer(), true).pipe(take(1)).subscribe(() => this.focusMonitor.stopMonitoring(this.modalContainer()))` (`:399-402`) relies on a focus event to arrive inside the container to unwind itself. `monitor()` registers the element in `FocusMonitor._elementInfo` — a plain `Map`, not a `WeakMap` (`focus-monitor.mjs:219, 298`) — and attaches global listeners (`:299`); `stopMonitoring` is the only thing that deletes the entry and removes the listeners (`:302-309`). When focus never lands inside the dialog — the button-less case from MDL-A11Y-02, or a modal closed within the 300 ms before `ngAfterViewInit`'s `.focus()` — the subject never emits, `stopMonitoring` is never called, and the detached `.kbq-modal-container` element stays reachable from a root-provided singleton for the life of the application, with its listener count still charged.
**Fix:** read the origin through public API — `inject(InputModalityDetector).mostRecentModality` gives the same information without touching CDK internals, or capture the origin from the *trigger's* own monitor stream if one is already running. Replace the `take(1)` self-teardown with an unconditional one: keep the subscription in a field and call `stopMonitoring(this.modalContainer())` from `ngOnDestroy` as well, or pipe it through `takeUntilDestroyed`. Guard with a spec that opens and closes a button-less modal and asserts `focusMonitor` has no registration left (readable via a `stopMonitoring` spy call count).

**MDL-CSS-01 · The body height cap is a magic constant that breaks the documented "header and footer stay visible" contract** — `modal.scss:120-134`, `modal-tokens.scss:1-18`, `modal.en.md:52-58`, fixture `e2e.ts:27-43`.
`.kbq-modal-body` sets `max-height: calc(100vh - 260px)` (`modal.scss:124`) — a hardcoded pixel budget that stands in for the sum of the container's `top: var(--kbq-size-5xl)` offset (48 px, `modal.scss:11`), the header, the footer and the bottom gutter. None of those are actually fixed: the header grows with a two-line `kbqTitle` plus a two-line `kbqCaption` (both clamped at two lines, `modal.scss:95-118`), the footer grows if the buttons wrap, and both disappear entirely for a modal with neither. When the real chrome exceeds the assumed ~212 px, the dialog overflows the viewport and the only scroller left is `.kbq-modal-wrap` (`modal.scss:60-72`, `overflow: auto`) — so the *whole* dialog scrolls and the header and footer leave the screen, directly contradicting "Only the central part (body) of the dialog scrolls. The header and footer remain visible" (`modal.en.md:56`). When the chrome is smaller than assumed, the body is capped short of the space available and the documented "occupies the full available screen height, minus 48px padding on each side" (`modal.en.md:54`) is not reached either. The e2e fixture is built precisely on the overflowing case — a four-line title plus a two-line caption at a 450×550 viewport (`e2e.ts:27-43`, `e2e.playwright-spec.ts:10-20`) — so the baseline screenshots have already normalised the wrong layout.
**Fix:** stop budgeting in pixels. Make `.kbq-modal-container` the height authority — `max-height: calc(100vh - 2 * var(--kbq-size-5xl)); display: flex; flex-direction: column` — and let the body take `flex: 1; min-height: 0; overflow-y: auto`, so header and footer are laid out at their real heights and only the body scrolls, at any content size. Expose the outer inset as `--kbq-modal-size-viewport-inset` rather than reusing `--kbq-size-5xl` at `modal.scss:11`. Verify against the existing fixture at 450×550 and add a second e2e case with a single-line title and no footer, whose acceptance criterion is that the body reaches the bottom gutter; baselines must be regenerated with `yarn run e2e:docker:update-snapshots`.

**MDL-PERF-01 · Consumer callbacks and a class-string rebuild run on every change-detection pass** — `modal.component.ts:556-565, 568-578`, `modal.component.html:24, 32-40, 102-113, 128-135`.
The template drives almost all of its structure through method calls rather than fields. `getButtonCallableProp(button, 'show' | 'loading' | 'disabled')` appears three times per footer button (`modal.component.html:128, 133, 135`) and, when the property is a function, *invokes consumer code* with the content-component instance as an argument (`modal.component.ts:556-565`) — the documented form in `IModalButtonOptions` (`modal.type.ts:88-90`) and the one used by the shipped specs (`modal.spec.ts:230-282`). Every change-detection pass over the modal's view therefore re-runs every callback of every footer button; a five-button footer means fifteen user-function calls per pass, and nothing in the JSDoc warns that these must be cheap and side-effect-free. `getContainerClasses()` (`modal.component.ts:568-578`) allocates an array, filters an object and joins a new string on every pass, feeding a `[class]` binding (`modal.component.html:24`) that must then be diffed against the previous string. `isModalType`, `isTemplateRef`, `isNonEmptyString`, `isComponent` and `isModalButtons` are likewise re-evaluated inside `@switch` blocks (`:32-40, 102-113, 119-126`). The view is small, so this is a hazard rather than a live regression — but it is checked on every click inside the dialog, since template event bindings mark the `OnPush` view dirty.
**Fix:** compute the derived state once. Convert `getContainerClasses()` to a `computed()` over `kbqClassName`/`kbqSize`/`modalAnimationClassMap`, and resolve `kbqFooter` button props into a memoised array recomputed on the same signals rather than per binding; the `is*` type tests can become `computed()` flags on the inputs. If the callback form must keep its per-pass semantics for compatibility, document that requirement on `IModalButtonOptions.show`/`loading`/`disabled` (`modal.type.ts:88-90`). Guard with a spec that counts invocations of a `show` callback across two change-detection cycles.

**MDL-TEST-01 · A duplicated pair, a mislabelled case, and no coverage of any defect above** — `modal-control.service.spec.ts:53-66, 68-81`, `modal.spec.ts:66-81, 213-228, 284-341`.
`modal-control.service.spec.ts` contains two `it` blocks whose bodies are byte-identical (verified by diffing lines 54-66 against 69-81): "should unregister modal ref when afterClose emits without prior afterOpen" and "should remove modal ref from openModals and unregister it when afterClose emits". The first title describes exactly the leak of MDL-LIFE-02 — and the body contradicts it, calling `ref.afterOpen.next()` before `ref.afterClose.next()`, i.e. exercising the opened path. Written as its title says, it would fail today. The rest of the suite is broad but leaves every defect in this document unguarded: nothing presses Escape (both paths), nothing clicks × / the mask / OK on a declarative host, nothing asserts focus containment or that focus entered the dialog at all (the two focus specs at `:409-471` assert only `not.toBe(buttonElement)`, which a modal that never moved focus anywhere would also satisfy — a trigger that had focus loses it as soon as anything else is clicked), nothing runs `jest-axe`, and nothing destroys a fixture with a modal open. Two further cases are hollow: `:66-81` claims to "trigger both afterOpen/kbqAfterOpen" but `changeProps`' `Object.assign` (`modal.service.ts:63`) makes the passed emitter *become* `instance.kbqAfterOpen`, so both subscriptions land on one object and the assertion `toHaveBeenCalledTimes(2)` only proves a single emitter fired twice; and `:213-228` is titled "should trigger nzOnOk/nzOnCancel" — the `nz` prefix of the upstream ng-zorro project this package was forked from. The Playwright side is the healthy half: 8 tests, 6 of which assert real computed shadows on both composition paths (`e2e.playwright-spec.ts:33-107`).
**Fix:** delete the duplicate and rewrite the survivor to match its title — register a ref, emit `afterClose` *without* `afterOpen`, assert `hasRegistered()` is `false`; it becomes the regression guard for MDL-LIFE-02. Rename `nzOnOk/nzOnCancel`. Replace `:66-81` with two cases, one subscribing only to `modalRef.afterOpen` and one only to the passed emitter. Add: an Escape case per path (MDL-BUG-02), a declarative close-affordance case (MDL-BUG-01), a button-less-modal focus case and a Tab-wrap case (MDL-A11Y-02), a destroy-the-opener case asserting the overlay is gone and `body.style.overflow` is cleared (MDL-LIFE-01), and a `jest-axe` case per modal type (MDL-A11Y-01).

### P3 — Nice to have / hygiene

**MDL-API-01 · The public surface is undocumented, leaks internals, and carries 20 stale migration TODOs** — `tools/public_api_guard/components/modal.api.md:89-246, 272-275, 340-348`, `modal.component.ts:104-274`, `modal.type.ts:65`.
The API report marks nearly every member of `KbqModalComponent` `// (undocumented)` — roughly 90 entries between `:89` and `:246`, including all 27 inputs. Members that are plainly internal are `@public`: `animateMaskTo` (`:96`), `handleCloseResult` (`:127`), `getKbqFooter` (`:125`), `maskAnimationClassMap`/`modalAnimationClassMap` (`:209-211`), `transformOrigin` (`:237`), the five `is*` AoT helpers (`:131-139`), and the whole `ModalBuilderForService` class (`:340-348`) despite its `@docs-private` tag (`modal.service.ts:16-18`) — `@docs-private` does not affect TypeScript visibility. Two `ae-forgotten-export` warnings are baked into the report: `AnimationState` (`:95`) and `CssUnitPipe` (`:272-275`), both referenced from exported declarations but absent from the entry point. Types: `ModalOptions.data?;` (`modal.type.ts:65`) is declared with no type annotation at all and lands in the report as `data?: any` (`:352`); `KbqModalComponent<T = any, R = any>` defaults `R` to `any` while its own base `KbqModalRef<C = any, R = unknown>` defaults it to `unknown`. And 20 auto-generated `// TODO: Skipped for migration because:` comments (`modal.component.ts:104-274`) still sit above inputs that are individually trivial — the four "Accessor inputs cannot be migrated as they are too complex" cases (`:128-136, 186-194, 197-206, 240-249`) are get/set pairs over a private boolean with no logic whatsoever.
**Fix:** JSDoc every input on `KbqModalComponent` and every field of `ModalOptions` (one block each, stating defaults — `kbqMaskClosable: false` and `kbqCloseByESC: true` are the surprising ones), tighten `animateMaskTo`, `handleCloseResult`, `getKbqFooter`, the animation class maps, `transformOrigin` and the `is*` helpers to `protected`, export `AnimationState` and `CssUnitPipe` from `public-api.ts` or move them out of exported signatures, and give `data` a type (`data?: unknown`). Migrate the four trivial accessor pairs to `input({ transform: booleanAttribute })` and delete their TODOs. All of this changes `modal.api.md`, so batch it into one `yarn run build:components && yarn run approve-api` cycle — build first, the guard reads `dist/*.d.ts`, and adding JSDoc alone flips the `(undocumented)` markers and reddens the `api` job until re-approved.

**MDL-ARCH-01 · Composition directives inject the host class; scroll shadows are implemented twice; the overlay marker class is service-only** — `modal.directive.ts:33-37, 39-44, 58-65, 67-76`, `modal.component.html:54, 118`, `modal.service.ts:70`, consumer `select.component.ts:1732-1736`, `content-panel-with-grid-example.ts:230-238`.
Three related architecture smells. (1) `KbqModalTitle`, `KbqModalBody` and `KbqModalFooter` each `inject(KbqModalComponent)` — the concrete host class (`modal.directive.ts:40, 59, 75`) — although they use only `kbqClosable`, `componentColors`, `onClickCloseBtn()` and `bodyOverflow`. AGENTS.md states the opposite rule explicitly ("inject a narrow `InjectionToken` scoped to the members it uses, not the host's concrete class"), and the concrete dependency forces `modal.directive.ts` to import `modal.component.ts`, making the two files mutually dependent through `public-api.ts`. (2) The scroll shadows exist in two implementations. The templated path uses the core directives `[kbqOverflowShadowTop]`/`[kbqOverflowShadowBottom]` (`modal.component.html:54, 118`), whose host binding is `'[style.box-shadow]': 'ref()?.overflow()?.top ? shadow() : null'` with the token as the default (`core/overflow-shadow/overflow-shadow.ts:146-156, 164-177`). The composed path re-implements the identical binding by hand, routing the state through a `bodyOverflow` signal on the modal (`modal.component.ts:292`, written by `KbqModalBody`'s effect at `modal.directive.ts:62-64`, read by `KbqModalTitle` at `:36` and `KbqModalFooter` at `:71`) with the same hardcoded token strings. Two code paths, one behaviour, and only the second needs the signal round-trip. (3) The `kbq-modal-overlay` marker class is added only in `ModalBuilderForService.createModal()` (`modal.service.ts:70`), never on the declarative path's overlay (`modal.component.ts:335`); the one in-repo consumer that keys off it — `select.component.ts:1732-1736`, which compares overlay child-node positions to decide whether an outside click should close the panel — therefore cannot see a declarative modal at all. Related consumer friction worth noting: `KbqModalTitle` wraps projected content in a `-webkit-line-clamp: 2` box (`modal.scss:95-103`), so a caller who wants actions next to the title must pierce encapsulation — `content-panel-with-grid-example.ts:234-238` does exactly that with `::ng-deep .example-modal-title .kbq-modal-title { display: flex; … }`.
**Fix:** define a `KBQ_MODAL` injection token exposing the four members the directives need, provide it from `KbqModalComponent`, and switch the three `inject()` calls to it — that also breaks the file-level cycle. Replace the hand-rolled bindings in `KbqModalTitle`/`KbqModalFooter` with `hostDirectives: [KbqOverflowShadowTop]` / `[KbqOverflowShadowBottom]` wired to the `KbqModalBody`'s container, deleting `bodyOverflow` and its effect. Move the `kbq-modal-overlay` class onto the overlay in `KbqModalComponent` so both paths carry it. Add a projection slot (`<ng-content select="[kbqModalTitleActions]">`) outside the clamped box so the `::ng-deep` workaround can be deleted.

**MDL-CSS-02 · Dead rule, dead binding, two unused tokens, and an inert `transform-origin` computation** — `modal.scss:21-30, 44-50, 161-163`, `modal-tokens.scss:9, 15`, `modal.component.html:25`, `modal.component.ts:664-670, 719-726`, `modal-util.ts:11-14, 28-32`.
Five pieces of dead weight, all verified by grep across `packages/` and `apps/`. (1) `.kbq-modal-open { overflow: hidden }` (`modal.scss:161-163`) — the class is applied nowhere in the repository; body scroll locking is done with an inline style through `Renderer2` instead (`modal.component.ts:736`). (2) The `.kbq-modal_no-footer .kbq-modal-body` rule is commented out behind a Russian TODO deferring it to 2.0 (`modal.scss:44-50`), yet the class binding that feeds it is live (`modal.component.html:25`) and its token `--kbq-modal-size-content-padding-bottom-without-footer` (`modal-tokens.scss:15`) has zero readers — so a footerless modal is missing its documented bottom padding and the machinery to fix it is half-shipped. (3) `--kbq-modal-size-close-button-margin-left` (`modal-tokens.scss:9`) has no readers either; the close button is positioned absolutely instead (`modal.scss:52-57`). (4) The `&.zoom-enter, &.zoom-appear` block at `modal.scss:21-30` is explicitly labelled `DEPRECATED: Unused. Will be removed in next major release.` and wrapped in a `stylelint-disable`. (5) `updateTransformOrigin` (`modal.component.ts:719-726`) is scheduled through a `setTimeout` (`:669`) to read the last document click position, but `ModalUtil` initialises that position to `{ x: -1, y: -1 }` (`modal-util.ts:12`) and returns the object unconditionally, so the truthiness guard at `:723` always passes — a keyboard-opened modal gets an origin computed from `-1`. It does not matter visually, because the `mcZoomIn` keyframes end at `transform: scale(1)` (`_modal-animation.scss:89-99`), against which `transform-origin` is a no-op — which makes the whole document-wide click listener (`modal-util.ts:20-24`, registered at module load and never removed) unused machinery.
**Fix:** delete (1), (3) and (4) outright. For (2), either implement the rule and keep the binding, or delete both the binding and the token. For (5), delete `updateTransformOrigin`, the `setTimeout` at `:669`, the `transformOrigin` field and its binding (`modal.component.html:27`), and `modal-util.ts` in its entirety — or, if the zoom-from-click-point effect is still wanted, restore it properly by making the keyframes actually scale from the origin and by returning `null` from `getLastClickPosition()` before the first click. Note the removals touch the API report (`transformOrigin` is `@public`), so fold them into the MDL-API-01 `approve-api` cycle.

**MDL-STYLE-01 · No reduced-motion support, and fixed 300 ms timers gate the public events** — `_modal-animation.scss:1-113`, `modal.component.ts:664-681`, `modal.type.ts:20-24`, `playwright.config.ts:101`.
`_modal-animation.scss` defines four keyframes and applies them unconditionally; there is no `@media (prefers-reduced-motion: reduce)` anywhere in the package, although nine sibling packages have one (`accordion`, `app-switcher`, `dropdown`, `notification-center`, `progress-bar`, `progress-spinner`, `skeleton`, and `core/styles/common/_animation.scss`). A full-viewport zoom-and-fade is the most motion-heavy thing the library renders, so it is the least appropriate place to ignore the preference. The e2e configuration makes the gap concrete rather than theoretical: `playwright.config.ts:101` sets `reducedMotion: 'reduce'` for every browser context, so the baselines are captured under a preference the component does not honour. Independently, the timing is not tied to the animation at all: `animateTo` resolves a promise from a bare `setTimeout(…, MODAL_ANIMATE_DURATION)` (`modal.component.ts:675-680`) with `MODAL_ANIMATE_DURATION = 300` (`modal.type.ts:24`), and `handleVisibleStateChange` emits `kbqAfterOpen`/`kbqAfterClose` only after it resolves (`:615-627`). Every consumer therefore waits a fixed 300 ms for `afterClose` regardless of motion preference or of whether the animation actually ran, and every Jest case must `tick(600)` (`modal.spec.ts:16`) — a constant the spec had to double to be safe.
**Fix:** add a `@media (prefers-reduced-motion: reduce)` block to `_modal-animation.scss` setting `animation: none` on all four state classes, following the convention in `core/styles/common/_animation.scss`. Drive the promise from the real `animationend` event on `.kbq-modal-container` with the timer as a fallback, so `afterOpen`/`afterClose` fire as soon as the animation is over — immediately under reduced motion. Once the events are event-driven, the `ANIMATION_DURATION * 2` padding in the spec can shrink to a `flush()`.

**MDL-DOC-01 · Three behaviours the guide promises are not implemented** — `modal.en.md:56, 70, 93`, `modal.ru.md:56, 70, 93`, `modal.component.html:168-184`.
The bilingual guide is thorough and is the component's main contract for consumers, which makes its inaccuracies load-bearing. (1) The keyboard table's third row promises "Submit the form by pressing Enter in any text input" (`modal.en.md:93`) — nothing in the package implements it: `onKeyDown` handles only Escape and Ctrl+Enter (`modal.component.ts:472-487`), the body is not wrapped in a `<form>`, and the predefined footer buttons carry no `type="submit"` (`modal.component.html:144-158`), so native implicit submission cannot fire either. (2) "Focus is placed on the first available element inside the dialog body" (`:70`) is contradicted by the actual first-button-in-the-document rule (see MDL-A11Y-02). (3) "Only the central part (body) of the dialog scrolls. The header and footer remain visible" (`:56`) is contradicted by the fixed body cap (see MDL-CSS-01). Both language files carry all three identically, so there is no correct version to fall back on. Two smaller divergences are worth folding into the same pass: the confirm variant's body (`modal.component.html:168`) is a bare `.kbq-modal-body` without the `kbqOverflowShadowContainer` and without `kbq-scrollbar`, so a long confirm dialog scrolls with the native scrollbar and no shadows, unlike every other variant — undocumented either way; and `KbqModalService.delete()` (`modal.service.ts:165-167`) maps to `confirmType: 'warn'`, a name mismatch that appears in no guide.
**Fix:** delete the Enter row or implement it (wrap the body in a `<form>` and give the main-action button `type="submit"` — note that would also give the `[kbq-modal-main-action]` marker a native meaning). Reword (2) and (3) to describe the shipped behaviour, or land MDL-A11Y-02 and MDL-CSS-01 first and leave the text as the specification they are verified against. Bring the confirm body to parity with the default body, or document the difference. Both language files must be edited together; the docs site compiles guide snippets under `yarn run e2e:docs`, so a corrected snippet stays corrected.

## 4. Recommended Remediation Phases

**Phase 1 — Make the dialog a dialog.**
IDs: MDL-A11Y-01, MDL-A11Y-02. Add `role="dialog"`, `aria-modal="true"` and a real `aria-labelledby`/`kbqAriaLabel` to `.kbq-modal-container`, mark the application root `inert` while modals are open (and every non-topmost dialog in a stack), then replace the two `.focus()` guesses with `cdkTrapFocusAutoCapture` plus a `kbqAutoFocus` option and move focus capture/restore into `handleVisibleStateChange` so both entry paths get it. These are the two findings a user actually cannot work around, and A11Y-02's `tabindex="-1"` on the container is a prerequisite of A11Y-01's `'dialog'` focus mode. Ships with `jest-axe` cases per variant and a keyboard-only e2e walk.

**Phase 2 — Close the lifecycle holes.**
IDs: MDL-LIFE-01, MDL-LIFE-02, MDL-LIFE-03. Tie overlay disposal to the opener's `DestroyRef` and set `disposeOnNavigation: true`; move the body-scroll release to a destroy-safe owner; unregister from `KbqModalControlService` on destroy rather than on close and bound the `beforeClose` subscription; make the `FocusMonitor` teardown unconditional and read the focus origin through public API. Sequenced after Phase 1 because the button-less-modal case from A11Y-02 is what makes the LIFE-03 leak reachable. Acceptance is a destroy-the-opener spec, not a code diff.

**Phase 3 — Unify the two entry paths.**
IDs: MDL-BUG-01, MDL-BUG-02. Make `handleCloseResult` close on the `EventEmitter` branch too (or move the defaulting into the component), and give Escape one implementation that honours `kbqCloseByESC` and routes through `kbqOnCancel` on both paths. Fix the dev-app fixture that currently cannot be dismissed. This is deliberately after Phase 2: changing when `close()` runs is much safer once teardown is correct. Both changes are behavioural on a published API, so decide with the team whether the `EventEmitter` veto semantics need an `ng-update` note.

**Phase 4 — Layout, performance and tests.**
IDs: MDL-CSS-01, MDL-PERF-01, MDL-TEST-01, MDL-STYLE-01. Replace the `calc(100vh - 260px)` cap with a flex-column container, memoise the per-pass callbacks and class string, add the reduced-motion block and make `afterOpen`/`afterClose` animation-driven, then bring the Jest suite up to cover every finding above. Playwright baselines must be regenerated through Docker after the layout change.

**Phase 5 — Surface hygiene.**
IDs: MDL-API-01, MDL-ARCH-01, MDL-CSS-02, MDL-DOC-01. Document and tighten the public members, introduce the `KBQ_MODAL` token and collapse the duplicated shadow mechanism, delete the dead CSS/tokens/`transform-origin` machinery, and reconcile the guides with the shipped behaviour. Scheduled last so the API report churns exactly once; the visibility tightening is technically breaking and belongs with the next minor.

## Appendix A — Review Methodology

Every file in the package was read in full with `cat -n` — the component and its 200-line template, the service and builder, the control service, the four composition directives, the pipe, the click-position util, all five SCSS files, both Jest specs, the e2e fixture and Playwright spec, both guides and both examples stubs. Each candidate was then cross-checked against four independent sources. First, the installed framework: `@angular/cdk` 20.2.14 was read directly for `FocusMonitor._elementInfo`/`stopMonitoring`/`_lastFocusOrigin` (`fesm2022/focus-monitor.mjs:206, 219, 298-309`), for `OverlayConfig`'s defaults (`fesm2022/overlay-module.mjs:336, 340, 367`) and for `DomPortalOutlet.attachComponentPortal` (`fesm2022/portal.mjs:272-316`), so claims about leaks, scroll strategy and attach ordering rest on source rather than memory. Second, the in-repo consumers: 100 references to the modal API across `packages/` and `apps/` were enumerated, and the two that constitute evidence were read in place — `select.component.ts:1732-1736` (the `kbq-modal-overlay` position probe) and `content-panel-with-grid-example.ts:230-238` (the `::ng-deep` title override) — along with the dev app, which turned out to ship a declarative modal that cannot be dismissed. Third, git history: 86 commits touch the package; `dd05a3ce2` (DS-4755) was read as a diff because it fixed the previous lap of MDL-LIFE-02 and defines exactly how much of that leak is already closed. Fourth, configuration and generated artefacts: `tools/public_api_guard/components/modal.api.md`, its registration at `tools/api-extractor/config.json:34`, the docs entry at `apps/docs/src/app/structure.ts:743-754` (`hasExamples: true`), and `playwright.config.ts:101`. Every design token consumed by the package was resolved against `@koobiq/design-tokens/web/new/css-tokens-{light,dark}.css`; all resolve, and the two dead ones reported in MDL-CSS-02 are dead by having no *readers*, not by being undefined. Accessibility findings are stated as WCAG judgements, not automated failures, and say so explicitly. No build, test suite or formatter was run.

Refuted during verification:
- **"`modal-util.ts` uses the global `document` and breaks SSR"** — refuted. The module-level construction is guarded by `typeof document === 'undefined' ? undefined : document` (`modal-util.ts:28-32`), the listener registration is optional-chained (`:21`), and the component itself takes `DOCUMENT` through DI (`modal.component.ts:100`) rather than touching globals. The genuine problem with that file is that its output is never used (MDL-CSS-02), not that it is unsafe.
- **"`ModalBuilderForService` leaks its `kbqAfterOpen`/`kbqAfterClose` subscriptions"** — refuted as a leak. Both emitters are owned by the modal component, which the builder also owns; once `destroyModal()` runs, builder, component and subscriptions become unreachable together, and `OverlayRef.dispose()` completes the `keydownEvents()` inner stream. The retention that *is* real lives in the root-provided `KbqModalControlService` map and is filed as MDL-LIFE-02.
- **"Native `.focus()` in `ngAfterViewInit` bypasses `FocusMonitor`, so the auto-focused button shows no focus ring"** — refuted. `KbqButton` monitors its own host element (`button.component.ts:669-671`), so `FocusMonitor` still attributes the origin of a programmatic focus from the last input modality and applies `.cdk-keyboard-focused`, which is what `_button-theme.scss:104` renders the ring from. The defect in that code is *which* element is focused, and whether anything is (MDL-A11Y-02).
- **"`examples.modal.*.md` embed only one of the nine examples, so the Examples tab is broken"** — refuted. `structure.ts:753` sets `hasExamples: true`, and the repo convention is that the Examples tab is *disjoint* from the guide rather than a copy of it: the guide embeds eight examples (`modal.en.md:3, 22, 28, 60, 115, 121, 127, 133`) and the Examples tab contributes the ninth, `modal-component-with-injector`, with real prose in both languages. Working as designed.
- **"Two stacked modals both keep an enabled focus trap, so Tab escapes into the lower dialog"** — refuted as stated. Each `cdkTrapFocus` wraps focus within its own region via its own anchors, and the newer overlay is appended last, so ordinary tabbing stays in the top dialog. The real stacking defect is that neither dialog is hidden from assistive technology, which is folded into MDL-A11Y-01.
- **"`@Input() @Output() readonly kbqOnOk` is an illegal duplicate declaration"** — refuted. Angular accepts both decorators on one member and the compiler records it in both maps; the generated report shows `kbqOnOk` in the inputs *and* the outputs of `ɵcmp` (`modal.api.md:243`). It is confusing, and it is what makes MDL-BUG-01 possible, but it is not itself an error.

- **MDL-BUG-01** was drafted as "the close button never closes the modal".
