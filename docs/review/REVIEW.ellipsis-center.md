# Koobiq `ellipsis-center` Component — Code Review & Improvement Plan

> Scope: `packages/components/ellipsis-center` (directive, Jest spec, entry points, user guides, examples stubs, API guard report) plus its two in-repo consumers and the docs navigation · Commit `b665e503` · 2026-08-28
> Generated by a multi-dimension review (architecture, correctness, RxJS/lifecycle, accessibility, performance, public API/types, styles, tests, docs, SSR) with manual verification of every finding against the source, the consumers, `tsconfig.json` and the API guard. 13 findings confirmed (P0×0, P1×3, P2×8, P3×2); 5 candidate findings refuted during verification (see Appendix A). This document is a review + roadmap; no source is modified by it.

---

## 1. Executive Summary

`KbqEllipsisCenterDirective` is a 132-line directive that subclasses `KbqTooltipTrigger` to truncate a long single-line string in the middle and offer the full value as a tooltip. The idea is good and the tooltip integration is genuinely clever. The execution has drifted: the package ships **no stylesheet, no e2e fixture, no dev app, no examples and no docs entry**, and three of its four inputs are either dead, clobbered or mis-measured.

- **The package ships no CSS, so on its own the directive does nothing visible.** `refresh()` splits the string into `.kbq-ellipsis-center_data-text-start` / `_data-text-end` spans, but the middle ellipsis is produced entirely by `text-overflow: ellipsis` on the start span — CSS that lives nowhere in the package. Both in-repo consumers discovered this and pasted the *same 14 declarations* independently: `file-upload/file-upload.scss:21-37` and `docs-examples/.../breadcrumbs-truncate-center-items-example.ts:58-72`. An external consumer who imports the module and binds `kbqEllipsisCenter` gets the untruncated string back, with no error anywhere (ELC-CSS-01).
- **`minVisibleLength` is a published input that is never read.** It is declared at `ellipsis-center.directive.ts:38`, listed in the API report, and bound by two call sites — `single-file-upload.component.html:27` (`[minVisibleLength]="10"`) and the breadcrumbs example (`[minVisibleLength]="15"`) — and the class body never mentions it again (ELC-API-01).
- **`refresh()` overwrites the tooltip's own `disabled` input.** Line 103 assigns `this.disabled` imperatively; `multiple-file-upload.component.html:54` binds `[kbqTooltipDisabled]="disabled"` on the very same element, one line above the `kbqEllipsisCenter` binding. The imperative write wins until the bound expression next changes, so a disabled file-upload row can still pop a tooltip (ELC-BUG-01).
- **Where to cut the string is guessed from a hardcoded 7 px per character, and is only recomputed on `window:resize`.** `charWidth` (`:40`) is a font-independent constant that the two consumers already disagree about (7 vs 5), and the split point is derived from *half the container width* rather than from measured text. Because invalidation is bound to the window, a container that changes width without the window doing so — a splitter drag, a sidepanel toggle, a table column resize — keeps stale truncation (ELC-BUG-03, ELC-BUG-02). The one functional fix in the package's history, `ba3f316e7` (DS-3936, "name column width recalculation"), was in exactly this area.
- **The three-case Jest spec is green for the wrong reasons.** `ellipsis-center.directive.spec.ts:77` asserts through `innerText`, which jsdom does not implement, so it reads back the own property the implementation just wrote; and because jsdom performs no layout, the un-mocked `scrollWidth` is `0`, which forces `disabled = true` and means the splitting branch the test is named after (`'should properly split content on refresh'`) never executes (ELC-TEST-01).

Genuine strengths worth preserving: subclassing the tooltip trigger is the right call — the full text is a hover away, and self-disabling the tooltip when the text already fits (`:103`) is exactly the behaviour users expect. The split leaves the *complete* string in the DOM (start + end concatenate to the original), so assistive technology reads the real value rather than a mangled one — an accident of design that many "middle ellipsis" implementations get wrong. Resize handling is debounced through a `Subject` with a configurable interval, and the subscription is torn down in `ngOnDestroy`.

## 3. Prioritized Findings (deduplicated, verified)

### P0 — Release blockers

None.

### P1 — High

**ELC-CSS-01 · The package ships no stylesheet, so the middle ellipsis only appears if the consumer writes the CSS themselves** — `packages/components/ellipsis-center/` (no `.scss` file in the package), `ellipsis-center.directive.ts:77-125`; consumer copies at `file-upload/file-upload.scss:21-37` and `docs-examples/components/breadcrumbs/breadcrumbs-truncate-center-items/breadcrumbs-truncate-center-items-example.ts:58-72`.
`refresh()` writes the head of the string into `.kbq-ellipsis-center_data-text-start` and the tail into `.kbq-ellipsis-center_data-text-end` (`:83-98, 117-118`). Nothing else happens: no `…` character is inserted anywhere, and `start + end` reconstitutes the original string exactly. The visible truncation is produced solely by `overflow: hidden; text-overflow: ellipsis` on the start span and by `flex: 0 1 auto` / `flex: 1 0 auto` giving the tail priority — declarations that exist only in consumer code. The package contains just `ellipsis-center.directive.ts`, its spec, `index.ts`, `public-api.ts`, `ng-package.json` and four markdown files; there is no `.scss`, no `-tokens.scss`, no `_-theme.scss`. The proof that this is a real defect rather than a design choice is that the two in-repo consumers wrote *byte-identical* 14-declaration blocks in two different files and two different languages (SCSS and an inline `styles:` string) — the classic signature of a missing library-owned style.
**Fix:** add `ellipsis-center.scss` to the package with the block both consumers converged on (`display: flex` on `.kbq-ellipsis-center`, `flex: 0 1 auto; overflow: hidden; text-overflow: ellipsis; white-space: pre` on the start span, `flex: 1 0 auto; overflow: hidden; white-space: pre` on the end span), import it the way sibling packages do, then delete `file-upload.scss:21-37` and the duplicate in the breadcrumbs example. Removal of both copies with no visual change is the acceptance criterion. Guard it with the Playwright fixture from ELC-TEST-01 — this is a pure-CSS effect that only a screenshot can catch.

**ELC-API-01 · `minVisibleLength` is published, bound by two consumers, and never read** — `ellipsis-center.directive.ts:17, 38`; `tools/public_api_guard/components/ellipsis-center.api.md:22`; consumers `file-upload/single-file-upload.component.html:27`, `docs-examples/.../breadcrumbs-truncate-center-items-example.ts:32`.
`const MIN_VISIBLE_LENGTH = 50` (`:17`) is used for exactly one thing: the default value of `readonly minVisibleLength = input<number>(MIN_VISIBLE_LENGTH)` (`:38`). Grepping the class for `minVisibleLength` returns those two lines and nothing else — `refresh()` computes its slice index from `clientWidth`, `charWidth` and the string length only (`:109-114`). The input therefore has no effect whatsoever, yet it is part of the published surface (`ellipsis-center.api.md:22`, and the directive declaration lists it as a real input at `:32`), and two in-repo call sites bind it with deliberate-looking values (`10` for a file name, `15` for a breadcrumb). Both authors believed they were setting a floor on how much text stays visible; neither got one. The name also promises the one guarantee the algorithm most obviously lacks — at a narrow width, `lastCharsLength` can exceed the string length and the start fragment collapses to empty.
**Fix:** implement it or delete it, and say which in the changelog. Implementing is the smaller change and matches consumer intent: clamp the slice with `Math.min(Math.max(lastCharsLength, 0), Math.max(this._kbqEllipsisCenter.length - this.minVisibleLength(), 0))` so at least `minVisibleLength` characters of the head survive, and skip truncation entirely when the string is shorter than the floor. Deleting it is breaking and needs an `ng-update` migration stripping the attribute from templates (see `project_breaking_changes_need_migration_schematics`). Either way add a Jest case that binds `minVisibleLength` and asserts the start fragment's length — the absence of exactly that case is why this survived a year.

**ELC-BUG-01 · `refresh()` imperatively overwrites the tooltip's `disabled` input, fighting `[kbqTooltipDisabled]`** — `ellipsis-center.directive.ts:103`; `tooltip/tooltip.component.ts:305-316`; consumer `file-upload/multiple-file-upload.component.html:51-56`.
Line 103 assigns `this.disabled = this.elementRef.nativeElement.clientWidth > dataTextStart.scrollWidth` inside the deferred callback. `disabled` is not a private field of this class: it is the inherited `@Input('kbqTooltipDisabled')` accessor of `KbqTooltipTrigger` (`tooltip.component.ts:308-316`), whose setter also hides an open tooltip. `multiple-file-upload.component.html` binds both on the same element — `[kbqTooltipDisabled]="disabled"` at line 54 and `[kbqEllipsisCenter]="file.file.name"` at line 55. Angular writes the binding only when the bound expression changes, so after any `refresh()` (initial render, every resize, every file-name change) the directive's own value stands until the next distinct value of the consumer's `disabled` flag. In practice: a file-upload rendered in a disabled state whose name overflows will show the hover tooltip that the consumer explicitly turned off. The reverse also holds — a consumer that wants the tooltip always on cannot get one for text that fits.
**Fix:** stop writing the inherited input. Track the fit in a private field (`private textFits = signal(false)`) and expose the effective state through the base class the supported way — override the getter, or better, keep the consumer's binding authoritative and compute `disabled ||= textFits()` at the point the tooltip decides to show. Add a Jest case binding `[kbqTooltipDisabled]="true"` to overflowing text and asserting no tooltip opens after a resize, plus the mirror case; both fail against today's code.

### P2 — Should fix

**ELC-BUG-02 · Truncation is recomputed only on `window:resize`, so container-driven width changes leave stale text** — `ellipsis-center.directive.ts:23, 61-65`; prior fix in the same area `ba3f316e7` (DS-3936).
The only invalidation source is the host listener `'(window:resize)': 'resizeStream.next($event)'` (`:23`), debounced into `refresh()` (`:61-65`). Every other width change is invisible to the directive: a `kbq-splitter` drag, a sidepanel opening, a table column resize, a font swap, a `kbq-file-upload` list gaining a scrollbar, or a parent going from `display: none` to visible (where the initial measurement ran against `clientWidth === 0`). The failure is silent and asymmetric — text truncated for a narrow container stays truncated after the container grows, so the user sees an ellipsis with empty space next to it. The repo already treats this class of problem with `ResizeObserver` in at least six packages (`clamped-text/clamped-text.ts`, `actions-panel/actions-panel.ts`, `code-block/code-block.ts`, `core/overflow-shadow/overflow-shadow.ts`, `dl/dl.component.ts`, `breadcrumbs`), so the pattern and its testing helpers are established. That the one functional commit in this package's history is `ba3f316e7` — *"fix(ellipsis-center,file-upload): name column width recalculation"* — is direct evidence that recalculation timing is where this component breaks in the field.
**Fix:** replace the window listener with a `ResizeObserver` on the host element, keeping the same debounced `Subject` so `debounceInterval` still applies; follow `clamped-text.ts` for construction/teardown and for the jsdom shim used in its spec. Keep the window listener only if a text-metrics dependency on zoom is wanted, and note that a `ResizeObserver` also fixes the `clientWidth === 0` first-measurement case for free. Regression test: a spec that shrinks the host through the observer callback and asserts the fragments changed.

**ELC-BUG-03 · The cut point is guessed from a hardcoded average character width and always claims half the container** — `ellipsis-center.directive.ts:40, 109-114`; consumers disagree at `docs-examples/.../breadcrumbs-truncate-center-items-example.ts:33` (`[charWidth]="5"`) vs the default `7`.
`lastCharsLength = Math.round(clientWidth / 2 / averageCharWidth)` (`:110`) then `sliceIndex = length - lastCharsLength` (`:111`). Two assumptions are baked in: that every glyph is `charWidth` pixels wide, and that the tail should occupy exactly half of the container regardless of how long the string is or what the head needs. Neither survives contact with a proportional font — `iiii` and `WWWW` differ by a factor of three in the default UI font, and Cyrillic, CJK and monospace stacks each need a different constant, as do the browser's zoom levels. The consumers demonstrate the problem rather than solving it: the breadcrumbs example had to drop to `5` to make its own string fit, while `file-upload` keeps `7`. Because the tail span is `flex: 1 0 auto` (no shrink) in the CSS both consumers use, an underestimate does not degrade gracefully — the tail keeps its natural width and squeezes the head out entirely.
**Fix:** measure instead of guessing. Either (a) binary-search the split index against `scrollWidth` on a hidden measuring span — six to eight reflows for a 60-character name, done once per resize, which is what the debounce is for — or (b) use `CanvasRenderingContext2D.measureText` with the host's computed font, which needs no layout at all. Keep `charWidth` as a deprecated escape hatch for one minor. Verify with a Playwright case in a fixed-width container using two strings of equal length but very different glyph widths — today they truncate at the same index, which is the bug.

**ELC-LIFE-01 · `refresh()` runs twice on init, calls `detectChanges()` from an input setter, and leaves an uncancelled `setTimeout`** — `ellipsis-center.directive.ts:31-36, 55-59, 102-121`.
Three lifecycle problems in one flow. (1) The input setter calls `this.refresh()` and then `this.cdr.detectChanges()` (`:33-35`) — a synchronous full change-detection run of the *host component's* view, triggered from inside that same view's binding update. It is the classic path to `ExpressionChangedAfterItHasBeenCheckedError`, and the comment above it ("check the view to properly calculate text-start and text-end on text initialized") describes a symptom, not a reason. (2) `ngOnInit` (`:55-59`) then calls `refresh()` again, so first render always builds the spans twice and schedules two macrotasks. (3) Each `refresh()` schedules a bare `setTimeout` (`:102`) whose handle is never stored and never cleared; on destroy the pending callback still runs, reads `clientWidth` off a detached element, writes the inherited `disabled` input on a destroyed directive and calls `markForCheck()` on a destroyed view. Under Zone.js (the workspace uses `zone.js` polyfills — `angular.json:40`) every one of those timeouts also triggers an application-wide change-detection tick.
**Fix:** drop the `detectChanges()` call and the duplicate init path — set `_kbqEllipsisCenter` in the setter and let `ngOnInit` plus the resize stream own refreshing, or move the whole thing to `input()` + `effect()` and delete the accessor (see ELC-API-02). Replace the `setTimeout` with `afterNextRender()` (Angular ≥17, SSR-safe and automatically cancelled with the injector) or store the handle and `clearTimeout` it in `ngOnDestroy` and at the top of `refresh()`. A `fakeAsync` spec that destroys the fixture and then calls `flush()` must not throw — it does today.

**ELC-LIFE-02 · `ngAfterViewInit` overrides the base implementation without calling `super`, dropping the tooltip's own wiring** — `ellipsis-center.directive.ts:61-65`; base at `tooltip/tooltip.component.ts:559-565`, acknowledged at `tooltip.component.ts:504-507`.
`KbqTooltipTrigger.ngAfterViewInit()` does three things: subscribes to `parentPopup.closedStream` to hide the tooltip when the surrounding pop-up closes, starts `focusMonitor.monitor()` on the host, and pushes `cdk-overlay-pane_ignore-pointer-events` onto the overlay's panel classes when `ignoreTooltipPointerEvents` is set (`tooltip.component.ts:560-564`). The subclass replaces the hook wholesale with its resize subscription and never calls `super.ngAfterViewInit()`, so none of that runs. The consequences are concrete: an ellipsis tooltip inside a dropdown, popover or modal is not hidden when that pop-up closes, and `[kbqTooltipArrow]`-style options that ride on the panel class are silently inert. The tooltip's own constructor comment names this directive as one of the subclasses that skip the super call (`:506`) and works around it by moving *some* wiring into the constructor — but `parentPopup` and the panel class were left behind. Note `ngOnDestroy` does call `super` (`:68`), so the asymmetry is almost certainly an oversight rather than a decision.
**Fix:** call `super.ngAfterViewInit()` as the first statement of the override. If focus monitoring on a non-interactive host is genuinely unwanted, say so in a comment and opt out explicitly rather than by omission. Add a spec that opens the directive inside a `KbqPopover`, closes the popover and asserts the tooltip overlay is detached.

**ELC-SSR-01 · The rendered text is written with `innerText`, which bypasses `Renderer2` and does nothing under server rendering** — `ellipsis-center.directive.ts:117-118`, contrast with `:93-101, 123-124`.
`refresh()` is careful to build and attach its spans through `Renderer2` (`createElement`, `addClass`, `createText`, `appendChild`) and then abandons that discipline for the two writes that actually matter: `dataTextStart.innerText = start; dataTextEnd.innerText = end`. Direct DOM writes bypassing `Renderer2` do not work under server rendering, so the server emits the spans as first built at `:100-101` — the *entire* string in the head span and an empty tail — while the client later rewrites them. On top of that, `clientWidth` and `scrollWidth` are both `0` on the server, so `disabled` (`:103`) computes to `false` and the server-side branch is the truncating one. `innerText` is also the reason the spec's central assertion is meaningless (ELC-TEST-01): jsdom does not implement it, so assigning creates an own property and leaves `textContent` untouched.
**Fix:** replace both assignments with `Renderer2` text nodes — remove the span's children and `appendChild(renderer.createText(value))`, or keep a reference to the text node created at `:100-101` and use `renderer.setValue(node, value)`. That change alone makes the directive SSR-correct *and* makes the existing spec able to observe real output through `textContent`. While there, gate the measurement behind `afterNextRender()` (ELC-LIFE-01) so no measurement is attempted on the server at all.

**ELC-A11Y-01 · The tooltip carrying the full text is unreachable by keyboard, because the host is never made focusable** — `ellipsis-center.directive.ts:19-25`; consumers `file-upload/single-file-upload.component.html:27` (a `<div>`), `multiple-file-upload.component.html:51-56` (a `<span>`).
The directive's host block adds one class and one window listener; it never sets `tabindex`, and both consumers apply it to non-interactive elements. The tooltip's default triggers include `focus`, but an element that cannot receive focus never fires it, so a sighted keyboard-only user has no way to reveal the full file name — the information is available on hover and nowhere else (WCAG 2.1.1, and the "hoverable/persistent" expectations of 1.4.13). Screen-reader users are unaffected, because the DOM retains the complete string (start + end concatenate to the original), which is why this is P2 rather than P1: the failure is scoped to keyboard-without-AT. The base class already knows how to do this — it sets `tabindex="0"` on the host in the `forDisabledComponent` path (`tooltip.component.ts:545`) — so the mechanism exists and is simply not applied here.
**Fix:** when the text is actually truncated (`disabled === false`), set `tabindex="0"` on the host through `Renderer2` and remove it when the text fits, so the tab order does not fill with inert stops. Keep the tooltip's `focus` trigger. Verify with a Jest case asserting the attribute appears and disappears with the fit state, and one AXE run over the file-upload fixture to confirm no new violation is introduced by the added stop.

**ELC-TEST-01 · Three Jest cases, whose only substantive assertion cannot fail** — `ellipsis-center.directive.spec.ts:37-78`, especially `:58-78`; no `e2e.ts`, no `*.playwright-spec.ts` in the package.
Case 1 (`:38-43`) asserts the directive instantiates. Case 2 (`:45-56`) reaches through the bracket escape hatch into `['content']`. Case 3 (`:58-78`), named *"should properly split content on refresh"*, is vacuous three times over: it asserts on `startEl.innerText`/`endEl.innerText`, and jsdom does not implement `innerText`, so it reads back the own properties the implementation wrote at `:117-118` rather than the rendered text; its comparison is `startEl.innerText.length + endEl.innerText.length <= text.length`, which holds by construction because the two fragments are a partition of the same string; and it mocks `clientWidth` to `150` (`:68`) while leaving `scrollWidth` at jsdom's layout-free `0`, so `:103` evaluates `150 > 0` and takes the *non*-truncating branch — the split the test is named after never runs. Nothing covers `minVisibleLength` (which is why ELC-API-01 survived), the resize debounce, the `disabled` transitions, or destroy-time behaviour. The package has no e2e fixture and no Playwright suite at all, which for a component whose entire output is a CSS-dependent visual effect is the gap that matters most.
**Fix:** rewrite case 3 to assert on `textContent` after ELC-SSR-01 lands, and mock `scrollWidth` alongside `clientWidth` so both branches are reachable; add cases for `minVisibleLength`, the fit/no-fit `disabled` transition, `debounceInterval` through `fakeAsync` + `tick`, and destruction with a pending timeout. Add `e2e.ts` + `e2e.playwright-spec.ts` with a fixed-width container in light and dark, covering a fitting string, an overflowing one and a post-resize state; generate the baselines only via `yarn run e2e:docker:update-snapshots`. Mutation check: reverting `refresh()` to a no-op must make at least two cases fail — today it makes none.

**ELC-DOC-01 · The component has no entry in the docs navigation, so its guide is unreachable while the SEO map advertises the page** — `apps/docs/src/app/structure.ts` (no `ellipsis-center` entry anywhere in the file), `apps/docs/src/app/seo-descriptions.ts:102-105`, `ellipsis-center.en.md:1`, `ellipsis-center.ru.md:1`, `examples.ellipsis-center.en.md:1-5`.
`structure.ts` is the single source of docs navigation, and it contains no `ellipsis-center` entry — the package is one of exactly two in that position (the other being `title`, whose entry points at the wrong path). The consequence is that `ellipsis-center.en.md` and `.ru.md` are never rendered, and both are a single sentence long — the *same* sentence stored in `seo-descriptions.ts:103-104`, so there is no API table, no input list, no note that consumer CSS is mandatory (ELC-CSS-01), and no example. `examples.ellipsis-center.{en,ru}.md` are the standard "🚧 Documentation in progress 🚧" stubs and, with no structure entry at all, are unreachable too. Meanwhile the SEO description map does carry an entry, so the build advertises metadata for a page that does not exist. There is also no `packages/docs-examples/components/ellipsis-center/` directory and no `packages/components-dev/ellipsis-center/` app — the component cannot be run in isolation at all.
**Fix:** add a `structure.ts` entry under the same group as its natural neighbours, then grow the guide into a real page: what it does, the required host CSS until ELC-CSS-01 lands, the input table (with `minVisibleLength` resolved either way), and the interaction with the tooltip inputs it inherits. Add `packages/docs-examples/components/ellipsis-center/` with one overview example and flip `hasExamples: true`, or delete the two stub files. Add `packages/components-dev/ellipsis-center/` so `yarn run dev:ellipsis-center` exists like it does for every sibling.

### P3 — Nice to have / hygiene

**ELC-ARCH-01 · Six of the AGENTS.md structure files are missing and the NgModule lives inside the directive file** — `packages/components/ellipsis-center/` (9 files total), `ellipsis-center.directive.ts:128-132`.
The package contains `ellipsis-center.directive.ts`, `ellipsis-center.directive.spec.ts`, `index.ts`, `public-api.ts`, `ng-package.json` and four markdown files. Against the structure AGENTS.md prescribes it is missing `<c>.scss` (ELC-CSS-01), `<c>-tokens.scss`, `_<c>-theme.scss`, `<c>.module.ts`, `e2e.ts` and `e2e.playwright-spec.ts`; `KbqEllipsisCenterModule` is declared at the bottom of the directive file instead (`:128-132`). Tokens and theme may legitimately be unnecessary for a directive that paints nothing — but that decision is nowhere recorded, and the absent stylesheet shows the reasoning was not applied deliberately. The dev app and docs-examples directories are absent as well (ELC-DOC-01), making this the least-scaffolded package in `packages/components`.
**Fix:** extract `KbqEllipsisCenterModule` into `ellipsis-center.module.ts` re-exported from `public-api.ts` (no API-report change: the class and its module declaration are unchanged), add the stylesheet from ELC-CSS-01 and the e2e pair from ELC-TEST-01. If tokens and a theme mixin are genuinely not needed, state that in a one-line comment at the top of the stylesheet so the next reader does not re-litigate it.

**ELC-API-02 · A write-only accessor input with a stale migration TODO, an exposed `Subject`, and no documentation on any member** — `ellipsis-center.directive.ts:29-51`; `tools/public_api_guard/components/ellipsis-center.api.md:14-30, 47`.
Four small surface problems. (1) `kbqEllipsisCenter` is a setter with no getter (`:31`), so the API report publishes `set kbqEllipsisCenter(value: string)` (`api.md:20`) and the current value cannot be read back by anyone, including subclasses. It carries the auto-generated "Accessor inputs cannot be migrated as they are too complex" TODO (`:29-30`), which is untrue — the body is an assignment plus a refresh, exactly what `input()` + `effect()` replaces (and doing so also resolves ELC-LIFE-01). (2) `resizeStream` is a public `Subject<Event>` on the published surface (`api.md:30`); `@docs-private` hides it from the docs site but not from consumers, who can `next()` into it and force refreshes. (3) `minVisibleLength` and `charWidth` are `input<number>(…)` with no `numberAttribute` transform, unlike `debounceInterval` (`:46`), so under `strictTemplates: true` (`tsconfig.json:114-118`) the static-attribute form `charWidth="5"` is a compile error while `debounceInterval="0"` is fine — an inconsistency with no rationale. (4) The report is `(undocumented)` on the class and on every member except `debounceInterval` and `refresh`, and the file ends with "(No `@packageDocumentation` comment for this package)" (`api.md:47`).
**Fix:** migrate `kbqEllipsisCenter` to `input.required<string>()` with an `effect()` that refreshes, delete the TODO, and add `numberAttribute` to the two remaining numeric inputs for consistency. Make `resizeStream` `private` and expose `refresh()` as the supported imperative entry point (it is already public). Add JSDoc to the class and every public member. All of this changes `ellipsis-center.api.md`, so run `yarn run build:components` and then `yarn run approve-api` — build first, the guard reads `dist/*.d.ts` (`project_api_guard_needs_build_first`), and adding JSDoc alone is enough to churn the report (`project_jsdoc_on_public_member_changes_api_md`).

## 4. Recommended Remediation Phases

**Phase 1 — Make the component self-contained.**
IDs: ELC-CSS-01, ELC-ARCH-01. Ship `ellipsis-center.scss`, extract the NgModule, then delete both copies of the consumer CSS. ## Appendix A — Review Methodology

Findings were gathered by reading the entire package (all 9 files), then following the directive outward: to its base classes (`KbqTooltipTrigger` in `tooltip/tooltip.component.ts`, `KbqPopUpTrigger` in `core/pop-up/pop-up-trigger.ts`) to establish what the subclass inherits and what it overrides; to every in-repo consumer found by grepping `kbqEllipsisCenter`/`ellipsis-center` across `packages/`, `apps/` and `tools/` (two shipping call sites in `file-upload`, one docs example in `breadcrumbs`, plus the tooltip guide's cross-reference); to the API guard report and `tools/api-extractor/config.json`; to `apps/docs/src/app/structure.ts` and `seo-descriptions.ts`; and to the package's 12-commit history. Consumer evidence is what upgraded ELC-CSS-01 and ELC-API-01 from observations to confirmed defects — a byte-identical CSS block in two unrelated files, and two independent bindings of an input that does nothing.

Refuted during verification:
- **"The split spans destroy the accessible name — screen readers read a mangled string"** — refuted. `start` is `slice(0, sliceIndex)` and `end` is `slice(sliceIndex)` (`:113-114`), so their concatenation is exactly the original string and no `…` character is ever inserted into the DOM. The truncation is purely visual (`text-overflow`), so the accessible name stays complete. The real accessibility gap is keyboard reachability of the tooltip, filed as ELC-A11Y-01.
- **"`(window:resize)` uses the global `window` and violates the SSR rule about `KBQ_WINDOW`"** — refuted. That is Angular's event-target syntax in the `host` object, resolved by the renderer's event manager, not a global reference in code; the `KBQ_WINDOW` mandate does not apply. The genuine SSR defect is the `innerText` write (ELC-SSR-01).
- **"`[debounceInterval]="0"` in `multiple-file-upload` has no effect, because the signal is read once in `ngAfterViewInit`"** — refuted as stated. Inputs are set before `ngAfterViewInit` runs, so a static binding does apply; only later *changes* to the value are ignored. Recorded as a note inside ELC-LIFE-01 rather than as its own finding.
- **"The package carries an untyped member on its public surface (`tools/check-public-api-any/baseline.json:19` records 1)"** — refuted. The tool counts `any|unknown` in the golden report (`tools/check-public-api-any/index.ts:33-37`), and the single hit is the `unknown` in `InputSignalWithTransform<number, unknown>` (`ellipsis-center.api.md:18`) — the shape `numberAttribute` transforms always produce. Not the author's to remove.
- **"The package is missing from the API guard configuration"** — refuted. It is listed at `tools/api-extractor/config.json:22` and `tools/public_api_guard/components/ellipsis-center.api.md` exists and is current (it was added by `ba3f316e7`).

Corrected on verification:
- **ELC-BUG-01** was first drafted as "the tooltip can never be disabled by a consumer". Reading `tooltip.component.ts:308-316` and Angular's binding semantics showed the truth is narrower and more subtle: the imperative write wins until the bound expression next changes value. The wording moved from "never" to a clobbering race, and the fix changed from "remove the binding" to "keep the consumer authoritative".
- **ELC-A11Y-01** was first drafted as P1 on the grounds that the full text is unavailable to assistive technology. Verifying the slice arithmetic showed the DOM keeps the complete string, so AT is unaffected; the finding was narrowed to keyboard-only access and dropped to P2.
- **ELC-TEST-01** initially claimed only that the spec asserts through `innerText`. Tracing the mocked `clientWidth` against jsdom's layout-free `scrollWidth` showed a second, larger problem — the branch the test is named after never executes — which is now the lead of the finding.
