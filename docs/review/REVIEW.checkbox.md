# Koobiq `checkbox` Component — Code Review & Improvement Plan

> Scope: `packages/components/checkbox` (component, template, tokens, theme, required-validator, Jest spec, e2e fixture + Playwright spec, both user guides, docs examples, dev app, API guard report) · Commit `b665e503` · 2026-08-28
> Generated by a multi-dimension review (architecture, correctness, accessibility, RxJS/lifecycle, public API/types, styles, tests, docs) with manual verification of every finding against the source, the shared `KbqCheckable` primitive in `@koobiq/components/core`, the sibling `toggle`/`radio` implementations, `tsconfig.json`, `playwright.config.ts` and `@koobiq/design-tokens`. 13 findings confirmed (P0×1, P1×3, P2×4, P3×5); 9 candidate findings refuted during verification (see Appendix A). This document is a review + roadmap; no source is modified by it.

---

## 1. Executive Summary

`KbqCheckbox` is a 347-line component that delegates its state machine to the shared `KbqCheckable` host directive (`packages/components/core/common-behaviors/checkable.ts`), extracted in `ffb491a51` (#DS-3498). The forms plumbing that extraction produced is genuinely good — and it is the *only* dimension that is. Everything the component still owns itself, namely its ARIA surface, its focus feedback and its style sheet, has at least one confirmed defect.

- **A checkbox without projected label text has no accessible name and no way to give it one (CHK-A11Y-01).** The class JSDoc promises the opposite — "if you want to omit a label and still have the checkbox be accessible, you may supply an `[aria-label]` input" (`checkbox.ts:59-60`) — but no such input exists and `checkbox.html` never writes `aria-label` or `aria-labelledby` onto the native input. The direct sibling extracted from the same primitive in the same commit *does* have both (`toggle.component.ts:105-106`, `toggle.component.html:8-9`). The spec even registers two host components written for exactly these cases (`checkbox.component.spec.ts:22-23, 956-972`) that no test ever instantiates. An `<input type="checkbox">` with an empty associated `<label>` is a violation of axe-core's `label` rule, and AGENTS.md states the library "MUST pass all AXE checks".
- **The indeterminate state is announced as "checked" whenever both flags are set, and the docs example ships in exactly that state (CHK-A11Y-02).** `getAriaChecked()` short-circuits on `checked` before it ever tests `indeterminate` (`checkable.ts:90-92`), while the SCSS renders the mixed mark (`checkbox.scss:76-84`). `checkbox-indeterminate-example.ts:36-37, 79` deliberately keeps `parentChecked` true while `parentIndeterminate` is true, so the published example shows a dash and announces "checked". The Jest spec asserts this mismatch as intended behaviour at `checkbox.component.spec.ts:121-125`.
- **`onTouched` fires when the checkbox gains focus, not when it loses it (CHK-BUG-01).** `onInputFocusChange` calls it under `if (focusOrigin)` (`checkbox.ts:342-346`) — `FocusMonitor` emits the origin on focus and `null` on blur — so tabbing *onto* a required checkbox marks the control touched and reveals its validation error before the user has done anything. The JSDoc two hundred lines above says "Called when the checkbox is blurred" (`checkbox.ts:205`). `radio` gets this right on blur (`radio.component.ts:494-499`); `toggle` does it on interaction (`toggle.component.ts:257`). Three sibling controls, three different answers, and the transition is untested behind a TODO inherited from upstream Material (`checkbox.component.spec.ts:716-717`).
- **The label's vertical padding is silently zero because two custom properties are defined nowhere (CHK-CSS-01).** `checkbox.scss:37, 39` read `--kbq-checkbox-size-normal-padding-top` / `-padding-bottom`; a repo-wide grep plus `@koobiq/design-tokens` finds no definition, so both declarations are invalid at computed-value time and fall back to `0`. The references have been dangling since `978caa2c0` (2024-10-15) and the tokens file never contained them. Separately, two of the six `--kbq-checkbox-size-big-*` tokens are inert (CHK-CSS-02).
- **The Playwright suite's "focused" row does not render the focus ring (CHK-TEST-01).** `e2e.ts:19` puts `cdk-keyboard-focused` on the `<kbq-checkbox>` host; the theme keys the ring off the *input* (`_checkbox-theme.scss:51, 60`). Six of the 24 checkboxes in `01-light.png`/`01-dark.png` are therefore baselined as normal, and the focus ring — the component's only keyboard affordance — has zero coverage in either suite.

Genuine strengths worth preserving: the `KbqCheckable` extraction is a well-executed refactor — a single `ControlValueAccessor` shared by checkbox and toggle, with `resolveClick()` kept pure so callers own their own event ordering, and honest `@deprecated Unused` markers on the four superseded methods rather than silent removal. The Jest spec is one of the larger ones in the library (42 cases over 1014 lines) and covers the click-action matrix, `ngModel`, `formControl` disabling and the double-click-through-label hazard properly. Lifecycle handling is exact: the one `FocusMonitor` subscription is torn down in `ngOnDestroy` (`checkbox.ts:212-220`). Docs are above the library average — five real examples, `hasExamples: true`, both languages, no stubs. The problems are concentrated, not systemic.

## 3. Prioritized Findings (deduplicated, verified)

### P0 — Release blockers

**CHK-A11Y-01 · A label-less checkbox cannot be given an accessible name, and the class documents an `[aria-label]` input that does not exist** — `checkbox.ts:55-61`, `checkbox.html:8-23`; sibling implementation at `toggle.component.ts:105-106` + `toggle.component.html:8-9`; orphaned fixtures at `checkbox.component.spec.ts:22-23, 956-972`.
The component's own class-level JSDoc closes with "However, if you want to omit a label and still have the checkbox be accessible, you may supply an `[aria-label]` input" (`checkbox.ts:59-60`). `KbqCheckbox` declares no `aria-label` input, no `aria-labelledby` input and no `aria-describedby` input, and the template writes exactly one ARIA attribute onto the native input — `aria-checked` (`checkbox.html:12`). Anything a consumer writes as `<kbq-checkbox aria-label="Select all">` lands as a plain attribute on the `<kbq-checkbox>` host, which carries no role and is not the element the accessibility tree reads; the `<input type="checkbox">` inside keeps its wrapping `<label for>` (`checkbox.html:1`) whose subtree is empty, so its accessible name computes to the empty string. axe-core's `label` rule flags a checkbox input with no accessible name at *serious* impact, so this is an automated AXE failure, not merely a WCAG judgement — and AGENTS.md states plainly that components "MUST pass all AXE checks".
Three independent pieces of evidence say the gap is an oversight rather than a decision. First, `KbqToggleComponent` — extracted from the same `KbqCheckable` primitive in the same commit (`ffb491a51`, #DS-3498), with the same `inputId` getter and the same `<label for>` structure — declares `ariaLabel`/`ariaLabelledby` aliased inputs (`toggle.component.ts:105-106`) and forwards both to its input (`toggle.component.html:8-9`). Second, the checkbox spec registers `CheckboxWithAriaLabel` and `CheckboxWithAriaLabelledby` in its `TestBed` imports (`checkbox.component.spec.ts:22-23`) and defines both hosts (`:956-972`), but no `it` block ever calls `TestBed.createComponent` on either — the fixtures were written for tests that never landed. Third, label-less checkboxes are already in the tree: `e2e.ts:14-21` renders 24 of them and `components-dev/all/template.html:251` another, so the failing configuration is one the repo itself exercises.
**Fix:** mirror the toggle exactly. Add `readonly ariaLabel = input<string>('', { alias: 'aria-label' });` and `readonly ariaLabelledby = input<string | null>(null, { alias: 'aria-labelledby' });` to `KbqCheckbox`, then bind `[attr.aria-label]="ariaLabel() || null"` and `[attr.aria-labelledby]="ariaLabelledby()"` on the input in `checkbox.html` next to the existing `[attr.aria-checked]`. Do not default the text — a checkbox with visible content must keep its projected name, so both attributes must emit `null` when unset. Delete the aliased attributes from the host element if a consumer wrote them there (Angular leaves the static attribute in place; document that the input is the supported surface). Guard it by finally using the two orphaned hosts: one case asserting `input.getAttribute('aria-label') === 'Super effective'`, one asserting `aria-labelledby === 'some-id'`, and one asserting that a checkbox *with* projected text emits neither attribute. Add a `jest-axe` assertion over `CheckboxWithAriaLabel` — that is the check that turns this from a convention into a gate. This is additive and does not break the API report beyond two new `InputSignal` rows.

### P1 — High

**CHK-A11Y-02 · `aria-checked` reports `true` while the checkbox renders the mixed mark; the flagship docs example ships in that state** — `packages/components/core/common-behaviors/checkable.ts:89-92`, `checkbox.html:12, 18`, `checkbox.scss:66-84`; docs example `packages/docs-examples/components/checkbox/checkbox-indeterminate/checkbox-indeterminate-example.ts:36-37, 79`; spec lock-in at `checkbox.component.spec.ts:121-125`.
`getAriaChecked()` is `this.checked() ? 'true' : this.indeterminate() ? 'mixed' : 'false'` — `checked` wins unconditionally. The visual layer resolves the same collision the opposite way: `.kbq-checked .kbq-checkbox-checkmark { display: block }` (`checkbox.scss:66-74`) is overridden by the later, equal-specificity `.kbq-indeterminate .kbq-checkbox-checkmark { display: none } / .kbq-checkbox-mixedmark { display: block }` (`checkbox.scss:76-84`), so indeterminate wins on screen. The native `indeterminate` property is also set (`checkbox.html:18`), which by itself would make the platform report `mixed` — but the explicit `aria-checked="true"` overrides it in the accessibility tree. A sighted user sees a dash meaning "some of the group"; a screen-reader user hears "checked", meaning "all of the group". These are different answers to the same question (WCAG 4.1.2 Name, Role, Value).
This is not a theoretical combination. `checkbox-indeterminate-example.ts:79` computes `this.parentChecked = this.parentIndeterminate || length === checked`, i.e. it *deliberately* sets `checked` true whenever `indeterminate` is true, and the component initialises with both flags true (`:36-37`). That example is embedded in both published guides (`checkbox.en.md:17`, `checkbox.ru.md:19`) and rendered in the dev app (`components-dev/checkbox/module.ts:14`), so the mis-announced state is the first thing a user of the indeterminate feature sees. The Jest spec pins the behaviour rather than catching it: at `checkbox.component.spec.ts:121-125` it asserts `checkboxInstance.indeterminate === true`, `inputElement.indeterminate === true`, `inputElement.checked === true` and then `aria-checked === 'true'`.
**Fix:** invert the precedence in `KbqCheckable.getAriaChecked()` so `indeterminate` is tested first: `return this.indeterminate() ? 'mixed' : this.checked() ? 'true' : 'false';`. That matches the platform's own resolution (a native input with `indeterminate = true` reports `mixed` regardless of `checked`) and matches what the SCSS already draws, so no visual change is needed. Update `checkbox.component.spec.ts:125` to expect `'mixed'` and add the symmetric case to `packages/components/core/common-behaviors/checkable.spec.ts`. Because `getAriaChecked()` is shared, re-run the `toggle` suite — `toggle.component.html:7` binds the same method and `toggle` has the same collision. Then decide separately whether `checkbox-indeterminate-example.ts:79` should stop setting `parentChecked` under `indeterminate` at all; keeping both flags is legal, but the example would read better if it did not.

**CHK-BUG-01 · `onTouched` fires on focus-in instead of blur, so validation errors appear before the user has interacted** — `checkbox.ts:204-210, 212-216, 341-346`; siblings at `radio.component.ts:494-499` and `toggle.component.ts:257`; untested per `checkbox.component.spec.ts:716-717`.
`ngAfterViewInit` subscribes to `FocusMonitor.monitor(input)` and routes every emission to `onInputFocusChange`, which calls `this.checkable.onTouched()` under `if (focusOrigin)` (`checkbox.ts:343-345`). `FocusMonitor` emits the `FocusOrigin` (`'keyboard'`, `'mouse'`, `'touch'`, `'program'`) when the element *gains* focus and `null` when it loses it, so the guard selects precisely the wrong half of the stream: the registered `ControlValueAccessor` touch handler runs on focus-in and never on blur. For a form control that is the difference between "the user has left this field" and "the user has arrived at this field". A `Validators.requiredTrue` checkbox styled through `ng-touched` flashes its error the instant it receives keyboard focus during a tab traversal the user has not even paused on, and `formControl.touched` becomes true for controls the user only passed over.
The JSDoc directly above the field contradicts the wiring: "Called when the checkbox is blurred. Needed to properly implement ControlValueAccessor" (`checkbox.ts:205`). The library has no shared answer here — `KbqRadioButton` monitors its host and calls `this.radioGroup.touch()` under `if (!focusOrigin && this.radioGroup)`, i.e. on blur (`radio.component.ts:494-499`), while `KbqToggleComponent` calls `this.checkable.onTouched()` inline in its click handler (`toggle.component.ts:257`) and never wires the focus stream at all. Three checkable controls, three semantics. Nothing catches it because the only `touched` assertion in the suite is the initial-state one (`checkbox.component.spec.ts:706-718`), and the transition is explicitly deferred by a TODO carried over from upstream Angular Material: "TODO(jelbourn): test that `touched` and `pristine` state are modified appropriately" (`:716-717`).
**Fix:** invert the guard to `if (!focusOrigin) { this.checkable.onTouched(); }` in `onInputFocusChange` (`checkbox.ts:342-346`), matching `radio.component.ts:495`. Keep the subscription — the same stream is what applies `cdk-keyboard-focused`, which CHK-TEST-01 depends on. Then delete the `:716-717` TODO and replace it with two real cases against `CheckboxWithFormDirectives`: focus the input via `FocusMonitor.focusVia(input, 'keyboard')` and assert `ngModel.touched === false`; then dispatch `blur` and assert `ngModel.touched === true`. Per `project_input_modality_in_specs`, drive focus through `FocusMonitor` rather than a raw `input.focus()` so the origin is deterministic. While in the file, decide whether `toggle`'s click-time `onTouched()` should converge on the same rule — that is a `toggle` change, but the divergence should be recorded rather than left to drift.

**CHK-CSS-01 · The label's vertical padding resolves to zero because two custom properties are defined nowhere** — `checkbox.scss:36-39`; token set at `checkbox-tokens.scss:1-13`; introduced dangling in `978caa2c0` (2024-10-15).
`.kbq-checkbox__layout` declares `padding-top: var(--kbq-checkbox-size-normal-padding-top)` and `padding-bottom: var(--kbq-checkbox-size-normal-padding-bottom)` (`checkbox.scss:37, 39`). Neither property is declared in `checkbox-tokens.scss` — which defines six `--kbq-checkbox-size-normal-*` properties, none of them these two (`:2-7`) — nor anywhere else in `packages/`, `apps/`, or `@koobiq/design-tokens` (`node_modules/@koobiq/design-tokens/web/new/css-tokens.css` and the light/dark files). A `var()` with no fallback that resolves to nothing makes the whole declaration *invalid at computed-value time*; `padding-top`/`padding-bottom` are not inherited, so both take their initial value of `0`. The checkbox therefore has no vertical padding at all, and its clickable/hover box is exactly the height of the frame and text.
This passes every gate in the repo: Sass emits the `var()` verbatim, `stylelint` does not resolve custom properties, and Jest never computes styles. `git log -S` shows the two references were introduced by `978caa2c0` "fix(layout): removed map.get from properties used in styles (#DS-2972)" on 2024-10-15, while the same search against `checkbox-tokens.scss` returns nothing — the token names never existed, so the references were born dangling and have been inert for the entire life of the current token set. That the clickable zone is a real problem area is corroborated independently: `3ead7ccd8` "fix(checkbox): clickable zone cursor (#DS-5156)" added the two dedicated Playwright assertions at `e2e.playwright-spec.ts:26-50`, which check the cursor but not the box.
**Fix:** decide the intent, then close the loop in one direction. If vertical padding is wanted, add `--kbq-checkbox-size-normal-padding-top` and `--kbq-checkbox-size-normal-padding-bottom` to `checkbox-tokens.scss` alongside the existing `--kbq-checkbox-size-normal-top` (`:7`), plus the `-big-` pair, and reference the big pair from a `.kbq-checkbox_big .kbq-checkbox__layout` rule — the variant currently overrides no padding at all. If it is not wanted, delete both declarations rather than leaving dead `var()` calls that read as configuration. Either way this shifts pixels, so the `01-*.png` and `02-*.png` baselines must be regenerated with `yarn run e2e:docker:update-snapshots` (never natively — see `project_playwright_screenshots_ci_only`). Guard the class of bug, not just the instance: a stylelint rule or a small CI script that greps every `var(--kbq-checkbox-…)` reference in the package against the union of `checkbox-tokens.scss` and the design-token files would have caught this in 2024 and will catch the next one (see `project_rebase_silently_breaks_css_var_refs`).

### P2 — Should fix

**CHK-A11Y-03 · The projected `kbq-hint` is inside the `<label>`, so the caption becomes part of the accessible name instead of a description** — `checkbox.html:1, 30-36`; `KbqHint` contract at `packages/components/form-field/hint.ts:22-23`; the correct pattern at `packages/components/form-field/form-field.ts:519-530`; affected examples at `packages/docs-examples/components/checkbox/checkbox-overview/checkbox-overview-example.html:2-13`.
`checkbox.html` opens a `<label ... [attr.for]="inputId">` at line 1 and does not close it until line 37, so `<ng-content select="kbq-hint" />` at line 35 renders *inside* the label together with the projected text. Accessible-name computation for an input walks its associated label's subtree, which means the hint text is concatenated into the name rather than exposed as a description. `KbqHint` is built for the other role — its own JSDoc says the id is "Referenced by the `aria-describedby` of the form field control" (`hint.ts:22`) — and `KbqFormField` implements exactly that, collecting hint and error ids and writing them to the control (`form-field.ts:519-530`), with three Jest cases guarding it (`form-field.spec.ts:837, 843, 853`). `KbqCheckbox` is not a `KbqFormFieldControl` (the seven implementors are `input`, `input-number`, `input-password`, `textarea`, `datepicker-input`, `timepicker`, `time-range`), so it cannot borrow that wiring and has written none of its own: the generated `KbqHint.id` is never referenced by anything.
The user-visible effect is a long, badly ordered name. In `checkbox-overview-example.html:2-5` the `<kbq-hint>` is authored *before* the label text, so the accessible name reads "kbq-hint Default" — the caption is announced first and the actual label second. All six checkboxes in that example, which is the first embed in both guides (`checkbox.en.md:7`), have the problem. There is a second consequence: because the hint sits inside the click target, clicking a multi-line caption toggles the checkbox, which for a caption that carries explanatory text is usually not what the author wanted.
**Fix:** move `<ng-content select="kbq-hint" />` out of the `<label>` — close the label after `.kbq-checkbox__inner-container` and the label span, and render the hint as a sibling inside a wrapper that keeps the current flex column. Then adopt the form-field pattern: query the projected hint with `contentChild(KbqHint)` and bind `[attr.aria-describedby]="hint()?.id() ?? null"` on the input, reusing `updateDescribedByIds`-style id joining if more than one hint should be supported. Add Jest cases asserting that the input's accessible name excludes the caption and that `aria-describedby` points at the hint's id, mirroring `form-field.spec.ts:837`. Reordering the DOM changes layout, so re-baseline `02-light.png`/`02-dark.png` through Docker; `e2e.ts:53-80` already covers hints in eight configurations, which is the right regression surface.

**CHK-BUG-02 · Clearing `indeterminate` writes the primitive's signal directly, bypassing the public input and staling Angular's binding cache** — `checkbox.ts:296-301` versus the setter at `checkbox.ts:171-194`; spec covers only the two-way case (`checkbox.component.spec.ts:869`).
On a click that should clear the mixed state, `onInputClick` schedules `Promise.resolve().then(() => { this.checkable.indeterminate.set(false); this.indeterminateChange.emit(false); })` (`checkbox.ts:297-300`). That writes the `KbqCheckable` model signal directly rather than going through `KbqCheckbox`'s `indeterminate` setter (`:178-194`), which is the member Angular's `@Input` binding slot tracks. Angular only invokes a setter when the bound expression's value changes against the previously written value, so after this back-door write the input cache still holds `true` while the component's state is `false`. A consumer binding one-way — `[indeterminate]="someDerivedFlag"` — whose expression legitimately stays `true` across the click never gets the setter called again, and the checkbox stays stuck in the cleared state with no way to restore it short of toggling the expression through `false` and back. The deferred microtask also means the `change` output (emitted synchronously at `:311`) fires while `indeterminate` is still `true`, so a `(change)` handler observes a state the component is one tick away from abandoning, and `indeterminateChange` always arrives *after* `change`.
The spec does not reach the failure because `SingleCheckbox` binds two-way: `[(indeterminate)]="isIndeterminate"` (`checkbox.component.spec.ts:869`). The emitted `indeterminateChange(false)` pushes the host field to `false`, so setting it back to `true` at `:118` is a genuine value change and the setter runs. Every `indeterminate` assertion in the suite (`:79, 96, 118, 144, 193, 246, 429, 504, 519`) goes through that same two-way host. The identical construct exists in `toggle.component.ts:250-255`, so a fix should be considered for both.
**Fix:** route the clear through the same path as an external write — either call the public setter (`this.indeterminate = false;`, which already emits `indeterminateChange` and drives `transitionCheckState`, so the manual `emit` at `:299` becomes a double emission and must be dropped) or keep the signal write and additionally reset the binding cache. The first is simpler and removes duplicated logic. Then reconsider the `Promise.resolve()` at all: it exists to let the native input settle after the browser's own click handling, but since `resetNativeInput` (`checkable.ts:117-120`) already exists for the `noop` path, a synchronous clear followed by an explicit native reset is likely sufficient and removes the `change`-before-`indeterminateChange` ordering surprise. Add a Jest case with a *one-way* `[indeterminate]` host whose expression stays `true`: click, `flush()`, then assert the checkbox is not indeterminate, then trigger a CD pass and assert it is indeterminate again. That case fails today.

**CHK-CSS-02 · Two of the six `--kbq-checkbox-size-big-*` tokens have no effect on rendered geometry** — `checkbox.scss:23-24, 19-20, 41, 103-119, 140-144`; token declarations at `checkbox-tokens.scss:8-13`.
The `big` variant declares its own `--padding` on the host (`checkbox.scss:104`), built from `--kbq-checkbox-size-big-width` and `--kbq-checkbox-size-big-horizontal-content-padding`. But `.kbq-checkbox__layout` — the element that actually consumes `var(--padding)` at `:41` and `:143` — declares its *own* `--padding` from the `normal` tokens at `:24`. A custom property declared on an element always beats the value inherited from its parent, so the `_big` override at `:104` is shadowed on the only element that reads it and is dead in both the label-after and label-before layouts. Separately, `.kbq-checkbox_big .kbq-checkbox__frame` (`:112-119`) overrides only `border-radius` and `border-width`; the frame's `height`/`width` continue to come from `--kbq-checkbox-size-normal-width` at `:19-20`. `--kbq-checkbox-size-big-width` reaches only `.kbq-checkbox__inner-container` (`:108-109`), which is `position: absolute` and contains a visually-hidden input plus a self-sized frame, so changing it moves nothing visible.
Nothing looks wrong today only because the values coincide: `--kbq-checkbox-size-normal-width` and `--kbq-checkbox-size-big-width` are both `var(--kbq-size-l)` (`checkbox-tokens.scss:2, 8`, resolving to `16px` per `css-tokens.css:1293`), and the two `horizontal-content-padding` tokens are both `var(--kbq-size-s)` (`:5, 11`). The tokens are a published theming surface, so a consumer who sets `--kbq-checkbox-size-big-width: 20px` to enlarge the big variant gets a 20px invisible container around an unchanged 16px frame and unchanged label padding — a silent no-op that will read as a bug in the token set rather than in the CSS. This is latent, not currently visible, hence P2.
**Fix:** stop redeclaring `--padding` on `.kbq-checkbox__layout`. Declare it once on `.kbq-checkbox` (host) from the normal tokens and let `.kbq-checkbox_big` override it there — inheritance then does the work and `:104` becomes live. Add `height`/`width` from `--kbq-checkbox-size-big-width` to the `.kbq-checkbox_big .kbq-checkbox__frame` block at `:112-119` so the token drives the visible box, and drop the sizing from `.kbq-checkbox__inner-container` at `:108-109` where it does nothing. Guard it with a Playwright assertion rather than a screenshot: set `--kbq-checkbox-size-big-width` to a distinct value on a fixture checkbox and assert the frame's `boundingBox().width` follows — a screenshot cannot distinguish "token applied" from "token happened to match".

**CHK-TEST-01 · The e2e "focused" state applies the class to the wrong element, so the focus ring has no coverage in either suite** — `e2e.ts:19` versus `_checkbox-theme.scss:51-57, 60-66`; baselines `__screenshots__/01-light.png`, `01-dark.png`.
`E2eCheckboxStateAndStyle` renders a 24-cell grid over `states × colors × types` and simulates the focused state with `[class.cdk-keyboard-focused]="state === 'focused'"` on the `<kbq-checkbox>` host (`e2e.ts:19`). The theme scopes the focus ring to the native input: `.kbq-checkbox .kbq-checkbox-input.cdk-keyboard-focused + .kbq-checkbox__frame` (`_checkbox-theme.scss:60-66`) and the checked/indeterminate variant at `:51-57`. A class on the host produces `.kbq-checkbox.cdk-keyboard-focused`, which never matches a descendant selector, so the six "focused" cells (3 types × 2 colors) render exactly like the "normal" cells and were baselined that way. The same fixture proves the author's intent was sound: `[class.kbq-hover]` on line 18 *does* match, because the theme's hover rule is `&.kbq-hover` on the host itself (`:25-31`). One line works and the adjacent line does not, for a reason that is invisible in the screenshot.
The consequence is that four theme declarations for `--kbq-checkbox-theme-states-focused-*` and four for `-checked-focused-*` (`checkbox-tokens.scss:26-31`) have no test of any kind: the Jest spec asserts focus only through `document.activeElement` (`checkbox.component.spec.ts:361-368`) and never inspects the `cdk-keyboard-focused` class or the rendered outline. Since `FocusMonitor` is also the subscription CHK-BUG-01 mis-wires, the entire focus pathway of the component — ring plus touched semantics — is unverified. Note that flakiness is not a reason to avoid real focus here: `playwright.config.ts:101` sets `reducedMotion: 'reduce'` for every browser context, and the package declares no `transition` or `animation` at all.
**Fix:** in `e2e.ts`, move the class to the input, e.g. render the focused row through a small wrapper that applies `cdk-keyboard-focused` to `.kbq-checkbox-input`, or — better — drive real focus in the Playwright spec with `page.keyboard.press('Tab')` / `locator.focus()` and let `FocusMonitor` apply the class itself, which also exercises `focusVia`. Re-baseline through `yarn run e2e:docker:update-snapshots`; expect the six focused cells to change, and treat any *other* cell changing as a regression. Add a Jest case that calls `checkboxInstance.focus()` (which uses `focusVia(input, 'keyboard')`, `checkbox.ts:320-322`) and asserts `inputElement.classList.contains('cdk-keyboard-focused')` — that assertion is cheap and would have caught the fixture error, since it names the element the theme actually keys off.

### P3 — Nice to have / hygiene

**CHK-API-01 · Input typing is asymmetric across the four accessor inputs, and a deprecated export is typed `any`** — `checkbox.ts:41-45, 126, 133-163, 173`; `tools/public_api_guard/components/checkbox.api.md:25, 53-55, 70`.
Four inputs are accessor pairs over the `KbqCheckable` signals, but only two carry a transform: `disabled` uses `booleanAttribute` (`checkbox.ts:145`) and `tabIndex` uses `numberAttribute` (`:156`), so Angular emits `ngAcceptInputType_disabled` and `ngAcceptInputType_tabIndex` (`checkbox.api.md:53-55`). `checked` (`:133`) and `indeterminate` (`:173`) are bare `@Input()`s typed `boolean` with neither a transform nor a widening declaration, so under this workspace's `strictTemplates: true` (`tsconfig.json:117`) the bare-attribute form works for `<kbq-checkbox disabled>` — which the repo uses at `e2e.ts:53` and `components-dev/all/template.html:241` — but `<kbq-checkbox checked>` and `<kbq-checkbox indeterminate>` are type errors, since `''` is not assignable to `boolean`. Two more surface issues sit in the same report: `KBQ_CHECKBOX_CONTROL_VALUE_ACCESSOR` is exported as `any` (`checkbox.ts:41`, `checkbox.api.md:25`) despite AGENTS.md's "Avoid the `any` type", and `required` is `input<boolean, unknown>(undefined, …)` (`:126`) so it reads as `InputSignalWithTransform<boolean | undefined, unknown>` (`checkbox.api.md:70`) — a three-state boolean whose JSDoc says only "Whether the checkbox is required." Nine members carry `// (undocumented)`, including `big`, `getAriaChecked`, `inputElement` and `tabIndex`. Finally, five migration TODOs claim these inputs "cannot be migrated as they are too complex" (`:93-94, 113-114, 131-132, 143-144, 154-155, 171-172`); for `checked`, `disabled`, `indeterminate` and `tabIndex` that is now inaccurate — they are thin proxies over signals the primitive already owns.
**Fix:** add `@Input({ transform: booleanAttribute })` to `checked` and `indeterminate` so the four accessor inputs behave alike and the bare-attribute form compiles. Type the deprecated provider as `Provider` (as `checkbox-required-validator.ts:4` already does) instead of `any`. Give `required` a `false` default so its read type collapses to `boolean`, and state in its JSDoc that it only forwards to the native input. Add JSDoc to the nine undocumented members. Every one of these changes the API report, so batch them into a single `yarn run build:components && yarn run approve-api` cycle — the guard reads `dist/*.d.ts`, so build first and confirm the `dist` mtime moved (see `project_api_guard_needs_build_first` and `project_jsdoc_on_public_member_changes_api_md`).

**CHK-ARCH-01 · The host emits `disabled="false"` on every enabled checkbox, binds `id` twice, and the NgModule file deviates from the prescribed name** — `checkbox.ts:71-81`, `checkbox-module.ts`; Angular behaviour at `node_modules/@angular/core/fesm2022/debug_node.mjs:9517-9524`; sibling host block at `toggle.component.ts:62-70`.
Three small conventions issues in the same block. (1) `'[attr.disabled]': 'disabled'` (`checkbox.ts:75`) is an *attribute* binding over a boolean. Angular removes an attribute only when the value is `null`/`undefined`; anything else is stringified (`setElementAttribute` in `debug_node.mjs:9517-9524`), so an enabled checkbox renders `<kbq-checkbox disabled="false">`. The attribute is inert on a custom element, but it makes the selector `kbq-checkbox[disabled]` match every checkbox in the document, which is a trap for consumer CSS and for Playwright locators — the package's own spec correctly uses `kbq-checkbox.kbq-disabled` instead (`e2e.playwright-spec.ts:42`). The state is already exposed correctly by `[class.kbq-disabled]` on the next line, and `toggle`'s host block has no `[attr.disabled]` at all (`toggle.component.ts:62-70`). (2) `'[id]': 'id'` and `'[attr.id]': 'id'` (`:73-74`) bind the same value through two mechanisms; the pair is only harmless because declaration order happens to put the attribute removal last when `id` is `null` (the case `checkbox.component.spec.ts:264-270` exercises). `toggle` copies the same pair, so this is a shared idiom worth settling once. (3) The NgModule lives in `checkbox-module.ts`, while AGENTS.md prescribes `<component-name>.module.ts`; `datepicker` shares the deviation and `skeleton` uses a bare `module.ts`, so the convention has three spellings in the repo.
**Fix:** delete `'[attr.disabled]': 'disabled'` and rely on `.kbq-disabled`, or change it to `'[attr.disabled]': "disabled || null"` if some consumer genuinely depends on the attribute — grep first; today nothing in `packages/` or `apps/` selects `kbq-checkbox[disabled]`. Drop `'[attr.id]'` and keep the property binding (or the reverse), applying the same decision to `toggle` so the two stay aligned. Renaming `checkbox-module.ts` is a file move with a `public-api.ts:3` update and no API-report impact; it is only worth doing as part of a repo-wide pass that also fixes `datepicker` and `skeleton`, otherwise leave it and record the deviation.

**CHK-CSS-03 · A modifier class that overrides nothing, and 45 theme tokens duplicated verbatim into another package** — `checkbox.scss:46-52, 133-138`, `checkbox.html:4-6`; duplicate at `packages/components/core/selection/pseudo-checkbox/pseudo-checkbox-tokens.scss:1-59`.
`.kbq-checkbox__inner-container_no-side-margin` sets `margin-left: 0; margin-right: 0` (`checkbox.scss:133-138`) to undo margins that `.kbq-checkbox__inner-container` never applies — that rule sets only `display`, `position`, `top` and `left` (`:46-52`), and a grep for the class across all SCSS finds no other declaration of any margin on it. The class is a complete no-op, kept alive by a template expression that re-reads `checkboxLabel.textContent` on every change-detection pass (`checkbox.html:4-6`) and by two Jest cases that assert the *class* rather than any effect (`checkbox.component.spec.ts:831-834, 837-841`) — a coverage shape that would keep passing if the rule were deleted. Separately, `pseudo-checkbox-tokens.scss` is byte-identical to `checkbox-tokens.scss` apart from its selector: both are 59 lines and a diff after normalising `.kbq-checkbox` to `.kbq-pseudo-checkbox` is empty. That means 45 theme tokens plus 12 size tokens exist in two places, and a palette change like `0787063a2` (#DS-4739) has to be applied twice or the two controls drift.
**Fix:** delete `.kbq-checkbox__inner-container_no-side-margin` and the `[class.…]` binding at `checkbox.html:4-6` unless the intended margins are restored, in which case declare them on `.kbq-checkbox__inner-container` first so the modifier has something to override; either way replace the two class-assertion tests with an assertion on the computed style. For the token duplication, extract the shared declarations into one Sass mixin in `packages/components/core/styles/` and `@include` it from both selectors, which keeps the emitted CSS identical while giving palette changes a single edit point. Neither change touches rendered pixels, so existing baselines stay valid.

**CHK-TEST-02 · Two dead spec hosts, a case whose name contradicts its body, and an inherited TODO standing in for the missing coverage** — `checkbox.component.spec.ts:22-23, 278-280, 716-717, 831-841, 956-972`.
Four hygiene problems in an otherwise solid 1014-line, 42-case suite. (1) `CheckboxWithAriaLabel` and `CheckboxWithAriaLabelledby` are imported into the `TestBed` (`:22-23`) and defined (`:956-972`) but never instantiated — the compiler and linter are both happy because they are referenced by the imports array, so the dead fixtures are invisible to tooling. They are the fixtures CHK-A11Y-01 needs. (2) `it('should make the host element a tab stop')` (`:278`) asserts `inputElement.tabIndex`, not the host's; the host has no `tabindex` at all, so the name states something that is false about the component. (3) The two `no-side-margin` cases (`:831-841`) assert class presence for a rule that declares nothing (CHK-CSS-03). (4) The `TODO(jelbourn)` at `:716-717` — carried over from upstream Angular Material along with the fixture names — defers exactly the `touched`/`pristine` transition coverage that would have caught CHK-BUG-01, on a stated blocker (`async()`/`fakeAsync()` interaction) that no longer applies in this workspace.
**Fix:** use the two orphaned hosts in the CHK-A11Y-01 cases rather than deleting them. Rename `:278` to `should make the native input a tab stop`. Replace the class assertions at `:831-841` per CHK-CSS-03. Delete the `:716-717` TODO once the CHK-BUG-01 cases land — a TODO that has outlived its blocker is worse than no comment, because it tells the next reader the gap is known and unfixable. Note the suite already follows the repo's naming convention correctly (`SingleCheckbox`, `CheckboxWithNgModel` and the rest carry no `Kbq` prefix), so no rename pass is needed there.

**CHK-DOC-01 · The RU guide carries machine-translation artefacts, and neither guide documents the `clickAction` input or four other public inputs** — `checkbox.ru.md:12, 15, 16, 23`, `checkbox.en.md:19-30`; inputs at `checkbox.ts:90, 98, 101, 110, 115`.

## 4. Recommended Remediation Phases

**Phase 1 — Make the component announce what it renders.**
IDs: CHK-A11Y-01, CHK-A11Y-02, CHK-A11Y-03. Add the `aria-label`/`aria-labelledby` inputs and forward them; invert the `getAriaChecked()` precedence in the shared primitive; move `kbq-hint` out of the `<label>` and link it with `aria-describedby`. This is the only phase that clears a P0 and the only one an external consumer feels immediately. Order within the phase does not matter, but CHK-A11Y-02 touches `packages/components/core`, so the `toggle` and `checkable` suites must run alongside the checkbox suite.

**Phase 2 — Fix the forms and interaction semantics.**
IDs: CHK-BUG-01, CHK-BUG-02. Invert the `FocusMonitor` guard so `onTouched` fires on blur; route the indeterminate clear through the public setter so the input binding cache stays coherent. Both are small diffs guarded by new Jest cases, and both are behaviour changes an application can observe, so they should ship together with a release note rather than folded into a styling release.

**Phase 3 — Repair the style surface.**
IDs: CHK-CSS-01, CHK-CSS-02, CHK-CSS-03. Resolve the two dangling padding properties (define them or delete the declarations), un-shadow `--padding` and wire `--kbq-checkbox-size-big-width` to the visible frame, delete the no-op modifier and de-duplicate the pseudo-checkbox token block. Sequence after Phase 1: CHK-A11Y-03 reorders the DOM, so doing both before regenerating baselines means one Docker snapshot cycle instead of two.

**Phase 4 — Make the suites tell the truth.**
IDs: CHK-TEST-01, CHK-TEST-02. Drive real focus in the Playwright spec so the ring is actually rendered, re-baseline, then clean up the dead hosts, the mis-named case and the expired TODO. Deliberately after Phases 1–3 so the new baselines capture the corrected DOM and padding, and so the fixtures CHK-A11Y-01 revives are already in use.

**Phase 5 — API and documentation hygiene.**
IDs: CHK-API-01, CHK-ARCH-01, CHK-DOC-01. Align the four accessor inputs' transforms, type the deprecated provider, add the missing JSDoc, drop the redundant host bindings, and rewrite the RU guide plus the click-action section. Last because it is the phase that churns `checkbox.api.md`, and doing it once after the earlier phases have settled the public surface avoids two `approve-api` cycles.

General gates, run sequentially — never in parallel, per `project_no_parallel_heavy_builds`:

- `yarn run e2e:docker` for anything visual; regenerate baselines only with `yarn run e2e:docker:update-snapshots` — the four `__screenshots__` PNGs are Linux, compared at `threshold: 0` with no platform suffix.
- Manual smoke: `yarn run dev:checkbox` (its template covers all six state axes plus all five docs examples) and `yarn run dev:all`, which is the only place a bare `<kbq-checkbox />` with no label appears outside the e2e fixture.

Per-phase acceptance assertions:
- **Phase 1:** `<kbq-checkbox aria-label="Select all" />` yields an input whose `getAttribute('aria-label')` is `Select all`, and a `jest-axe` run over that fixture reports zero `label` violations — this is the assertion that closes the P0, not the presence of the input. A checkbox with projected text emits neither aria attribute. With `checked` and `indeterminate` both true, `aria-checked` is `mixed` and the mixed mark is the visible one. The accessible name of an overview-example checkbox no longer contains the hint text, and `aria-describedby` resolves to the hint's generated id.
- **Phase 2:** focusing a `ngModel` checkbox through `FocusMonitor.focusVia` leaves `ngModel.touched === false`; blurring it makes it `true`. A host binding `[indeterminate]` one-way to an expression that stays `true` returns to the indeterminate state after a click plus one change-detection pass — reverting the fix must make that case fail (mutation check).
- **Phase 3:** the computed `padding-top` of `.kbq-checkbox__layout` is either a resolved token value or absent by design, with no `var()` in the stylesheet that fails to resolve; a script comparing every `var(--kbq-checkbox-…)` reference in the package against `checkbox-tokens.scss` plus the design-token files reports zero unmatched names. Setting `--kbq-checkbox-size-big-width` to a distinct value changes `.kbq-checkbox__frame`'s measured `boundingBox().width` on a big checkbox.
- **Phase 4:** in the regenerated `01-light.png`/`01-dark.png`, the six focused cells differ from the six normal cells; every other cell is byte-identical to its pre-change baseline. `npx jest packages/components/checkbox` reports the two revived aria hosts as exercised, and no `TestBed` import remains without a corresponding `createComponent`.
- **Phase 5:** the `check-api` diff contains only the intended transitions — two new aria `InputSignal` rows, `ngAcceptInputType_checked`/`_indeterminate`, `required` narrowing to `boolean`, `Provider` replacing `any`, and removed `(undocumented)` markers. `yarn run e2e:docs` renders both guides, and every input named in the prose exists in `checkbox.api.md`.

## Appendix A — Review Methodology

Findings were gathered by reading the complete package (every `.ts`, `.html`, `.scss` and `.md` file, both e2e files and all four screenshot baselines' fixtures), then following each candidate outward to an independent source. Four cross-checks did most of the work. First, the shared primitive: `KbqCheckbox` delegates state, click resolution and the entire `ControlValueAccessor` to `KbqCheckable` (`packages/components/core/common-behaviors/checkable.ts`, 153 lines), so several apparent checkbox defects turned out to live in core, and several apparent core defects turned out to be checkbox-only. Second, the siblings: `toggle` was extracted from the same primitive in the same commit and `radio` solves the same problems independently, which turned three findings from opinions into demonstrated inconsistencies (`aria-label` forwarding, `onTouched` timing, `[attr.disabled]`). Third, the published docs examples were read as consumers rather than as documentation — `checkbox-indeterminate-example.ts` is what proved CHK-A11Y-02 is reachable rather than theoretical. Fourth, every `var(--kbq-…)` reference in the package was checked against `checkbox-tokens.scss` and `@koobiq/design-tokens/web/new/`, which is how CHK-CSS-01 surfaced. Consumers were enumerated by grepping `<kbq-checkbox` across `packages/` and `apps/`: 5 e2e fixtures, 5 dev apps, 12 docs examples, and no production call sites inside the library itself.

Refuted during verification:
- **"`ControlValueAccessor` is incomplete — `setDisabledState` and `onTouched` are missing"** — refuted. The accessor Angular actually binds is `KbqCheckable`, registered through `hostDirectives: [KbqCheckable]` (`checkbox.ts:82`) and its `NG_VALUE_ACCESSOR` provider (`checkable.ts:10-14, 62`). It implements all four members, `setDisabledState` included (`checkable.ts:130-147`), and `checkbox.component.spec.ts:801-814` proves `formControl.disable()` reaches `inputElement.disabled`. `KbqCheckbox`'s own four methods are correctly labelled `@deprecated Unused` (`checkbox.ts:230-264`) and still delegate correctly if called directly. The real defect is *when* `onTouched` fires, not whether it exists — filed as CHK-BUG-01.
- **"`aria-checked="mixed"` is never emitted for the indeterminate state"** — refuted. `checkbox.html:12` binds `getAriaChecked()`, which returns `'mixed'` (`checkable.ts:90-92`), and `checkbox.component.spec.ts:85` asserts it. The defect is the precedence when `checked` and `indeterminate` are both set — filed as CHK-A11Y-02 with a much narrower claim.
- **"`indeterminate` is not cleared when the user clicks"** — refuted. It is cleared (`checkbox.ts:296-301`) and covered by four Jest cases (`checkbox.component.spec.ts:95, 191, 245, 428`). The defect is the mechanism — a direct signal write that bypasses the public input — filed as CHK-BUG-02.
- **"The `<label>` is not associated with the input"** — refuted. `checkbox.html:1` binds `[attr.for]="inputId"` and `:17` binds `[id]="inputId"`, both from the same getter (`checkbox.ts:121-123`); the label also physically wraps the input, so the association is doubly established. `checkbox.component.spec.ts:259-270` verifies both the user-supplied and generated id paths, and `:289-307` verifies the double-click hazard that wrapping creates is handled.
- **"Playwright screenshots are flaky because the check and mixed marks animate"** — refuted. A grep for `transition` and `animation` across every `.scss` in the package returns nothing; the marks are toggled with `display` (`checkbox.scss:61-84`). `playwright.config.ts:101` additionally sets `reducedMotion: 'reduce'` for every browser context. Unlike `toggle`, the checkbox never consumes `currentCheckState` — see the Corrected list below.
- **"Design tokens referenced by the component do not resolve"** — refuted for everything except the two names in CHK-CSS-01. All colour tokens resolve in both themes (`--kbq-line-contrast-fade`, `--kbq-states-line-focus-theme`, `--kbq-background-error-less`, `--kbq-states-line-focus-error` are each present once in `css-tokens-light.css` and once in `-dark.css`), and all size tokens resolve via `css-tokens.css:1285, 1293, 1298`. Only `--kbq-checkbox-size-normal-padding-{top,bottom}` are undefined anywhere.
- **"`KbqColorDirective` writes `classList` directly, which breaks SSR"** — refuted as a checkbox finding. The direct DOM write is at `packages/components/core/common-behaviors/color.ts:52-64` and is inherited by roughly twenty components; it belongs to a core review. The checkbox package itself contains no `window`, `document` or `getComputedStyle` access, so it has no SSR hazard of its own.
- **"Enter should toggle the checkbox, as it does on `toggle` (`toggle.component.html:19`)"** — refuted. Per the WAI-ARIA authoring practices a checkbox is activated with Space, which the native input already handles; Enter inside a form must submit the form. `toggle`'s `(keydown.enter)` binding is appropriate for a switch and would be a defect here.
- **"`examples.checkbox.en.md` / `.ru.md` are dead placeholder stubs"** — refuted. `structure.ts:433` sets `hasExamples: true`, so the Examples tab renders, and both files carry a real embed of `block-checkbox` plus a written description rather than the "🚧 Documentation in progress 🚧" boilerplate found elsewhere. All five referenced examples exist under `packages/docs-examples/components/checkbox/` and are registered in `example-module.ts:1106-1156`. This is one of the better-maintained example surfaces in the library.

Corrected on verification:
- **CHK-CSS-01** was first drafted as "the checkbox has too little vertical padding", a design opinion that would have been dismissed. Reading `checkbox-tokens.scss` and then grepping the whole tree plus `@koobiq/design-tokens` showed the two referenced properties are defined nowhere, which makes it a dangling-`var()` defect with a mechanical fix and a mechanical guard. The severity moved from P3 to P1 and the fix acquired a repo-wide preventative.
- **CHK-TEST-01** started as "the e2e fixture has no focused state". It has one (`e2e.ts:19`) — it just applies the class to the host while the theme keys off the input (`_checkbox-theme.scss:51, 60`). The finding changed from "missing coverage" to "coverage that silently baselines the wrong pixels", which is worse, because a reviewer looking at the fixture would reasonably conclude the ring was covered.
- **CHK-A11Y-01** was drafted as a P1 titled "`aria-label` is not forwarded to the native input". Three discoveries raised it to P0: the class JSDoc actively promises the input (`checkbox.ts:59-60`), the sibling extracted from the same primitive in the same commit implements it (`toggle.component.ts:105-106`), and the spec contains two orphaned fixtures written for it. Together those make it an unmet published contract with an automated AXE consequence rather than a missing convenience.
- **CHK-BUG-02** was initially drafted as "the deferred `Promise.resolve()` clear is a race". Tracing the microtask showed the ordering itself is deterministic under both zone-based and signal-driven change detection; the actual defect is narrower and more certain — the write bypasses the `@Input` setter, so Angular's binding cache goes stale for one-way bindings. The claim was rewritten around that, and the severity settled at P2 because every in-repo binding is two-way and therefore unaffected.
