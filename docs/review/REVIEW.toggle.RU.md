## 1. Резюме

`KbqToggleComponent` — форм-контрол на 329 строк, который рендерит визуально скрытый `<input type="checkbox" role="switch">` внутри `<label>` и рисует сам переключатель тремя div'ами. С коммита `ffb491a51` (`feat(core): extract shared KbqCheckable primitive (#DS-3498)`) он делит состояние, разрешение клика и `ControlValueAccessor` с `kbq-checkbox` через host-директиву `KbqCheckable`. **Блокеров релиза нет** — счастливый путь (клик, `[(ngModel)]`, `[formControl]`) работает и покрыт 36 Jest-кейсами, — но компонент разошёлся с соседом в трёх местах, где расхождение является нарушением *контракта*, а доступность двух недефолтных состояний (indeterminate, loading) сделана неверно.

- **Опубликованный токен ядра тихо ничего не делает.** `KBQ_CHECKABLE_CLICK_ACTION` экспортируется из `@koobiq/components/core` (`core.api.md:1162`) и документирован как «Injection token that can be used to specify the default click behavior for checkable controls» (`checkable.ts:25-26`). `kbq-toggle` — единственное место в репозитории, где токен вообще *читается* (`toggle.component.ts:196`), и он же предоставляет этот токен в собственных `providers` (`toggle.component.ts:55-59`), перекрывая любого провайдера уровня приложения и жёстко замыкая значение на легаси-токен `KBQ_CHECKBOX_CLICK_ACTION`. `kbq-checkbox` не читает его вовсе (`checkbox.ts:115`). Итог: предоставление документированного токена в корне приложения не влияет ни на один компонент библиотеки (TGL-API-01).
- **`<kbq-toggle disabled>` рендерит активный контрол.** Пара аксессоров `disabled` типизирована как `any` и не имеет трансформа `booleanAttribute` (`toggle.component.ts:122-129`), поэтому статическая форма атрибута передаёт пустую строку, а она ложна: нативный input остаётся включённым, класс `.kbq-disabled` не навешивается, а `strictTemplates` (`tsconfig.json:117`) ничего не ловит, потому что сеттер принимает `any`. У `KbqCheckbox` трансформ есть (`checkbox.ts:145-152`), и разница видна в двух API-отчётах (`toggle.api.md:47-48` — без `ngAcceptInputType_disabled`; `checkbox.api.md:53` — с ним). Идиома статического атрибута здесь не гипотетическая: собственный пример библиотеки пишет `<kbq-toggle labelPosition="left">` (`toggle-label-left-example.ts:12`) (TGL-BUG-01).
- **Документированное состояние indeterminate озвучивается как «выключено».** На input жёстко прописан `role="switch"` (`toggle.component.html:3`) вместе с `[attr.aria-checked]="getAriaChecked()"`, который возвращает `'mixed'` при indeterminate (`checkable.ts:90-92`). WAI-ARIA не поддерживает значение `mixed` для роли `switch`; user agent трактует его как `false`. То есть компонент рисует смешанное состояние, а вспомогательные технологии сообщают, что переключатель выключен — для состояния, которому пользовательский гайд посвящает отдельный раздел (`toggle.en.md:15-19`) (TGL-A11Y-01).
- **`loading` реализован наполовину.** `onInputClick` выходит из обработчика до `event.stopPropagation()` и до ресинхронизации нативного input (`toggle.component.ts:234-267`), поэтому клик во время загрузки дважды доходит до родительских обработчиков `(click)` и оставляет `input.checked` рассинхронизированным с моделью — а это важно, потому что на input есть `name`/`value` и он сериализуется при нативной отправке формы. При этом контрол выглядит выключенным (`'[class.kbq-disabled]': 'disabled || loading()'`, `:67`), но сохраняет `tabIndex=0`, не получает `disabled` и не получает `aria-disabled` (TGL-BUG-02, TGL-A11Y-02).
- **В тестах есть проверка, которая не может упасть, и несколько, которые сверяют реализацию саму с собой.** `e2e.playwright-spec.ts:21-34` один раз читает `boundingBox()`, кликает по «big»-переключателю и повторно проверяет *те же самые локальные переменные* — тест пройдёт при любом поведении `[big]`. В Jest кейс про взаимодействие в disabled кликает по хост-элементу, а не по label или input (`toggle.component.spec.ts:106-112`), кейс про indeterminate сравнивает `aria-checked` с собственным `checked` компонента (`:521-534`), а `loading` покрыт только проверкой CSS-класса (`:566-577`) — при том что в фикстуре уже есть шпион на клик, который поймал бы TGL-BUG-02 (TGL-TEST-01, TGL-TEST-02).

Настоящие сильные стороны, которые стоит сохранить: миграция на общий примитив `KbqCheckable` выполнена аккуратно и хорошо прокомментирована (`toggle.component.ts:56-58`, `:205-207`, `:321`), устаревшие заглушки `ControlValueAccessor` честно помечены `@deprecated`, а не удалены молча; стилизация полностью на токенах, с парой `-tokens.scss` + `_-theme.scss` и без единого захардкоженного цвета; `ViewEncapsulation.None` + `OnPush` + host-объект соответствуют конвенциям репозитория без `@HostBinding`/`ngClass`/`*ngIf`; порядок DOM ставит фокусируемый input первым внутри настоящего `<label for>` (то есть связка с подписью корректна без всякого ARIA); e2e-фикстура покрывает 2 цвета × 5 состояний × 2 значения checked в светлой и тёмной теме.

### P1 — Высокий приоритет

**TGL-API-01 · Опубликованный токен `KBQ_CHECKABLE_CLICK_ACTION` перекрыт собственным провайдером компонента и нигде не работает** — `toggle.component.ts:55-59, 196`, `core/common-behaviors/checkable.ts:25-26`, `checkbox/checkbox.ts:115`, `tools/public_api_guard/components/core.api.md:1162`.
`KBQ_CHECKABLE_CLICK_ACTION` входит в публичный API, а его JSDoc заявляет, что токен «can be used to specify the default click behavior for checkable controls» (`checkable.ts:25-26`). Grep по всему репозиторию находит ровно три вхождения помимо объявления, и все — в `toggle.component.ts`: импорт (`:24`), провайдер уровня компонента (`:58`) и инициализатор поля, который его читает (`:196`). Проблема именно в провайдере — `providers: [{ provide: KBQ_CHECKABLE_CLICK_ACTION, useFactory: () => inject(KBQ_CHECKBOX_CLICK_ACTION, { optional: true }) }]` живёт на node-инжекторе элемента `<kbq-toggle>`, а это *первый* инжектор, к которому обращается инициализатор поля самого компонента при вызове `inject(KBQ_CHECKABLE_CLICK_ACTION, { optional: true })`. Приложение, которое положило в корень `{ provide: KBQ_CHECKABLE_CLICK_ACTION, useValue: 'noop' }`, до этого провайдера не доходит: каждый toggle резолвит собственный, а тот читает только легаси-токен `KBQ_CHECKBOX_CLICK_ACTION`. `KbqCheckbox` доводит рассогласование до конца, читая `KBQ_CHECKBOX_CLICK_ACTION` напрямую (`checkbox.ts:115`) и вообще не обращаясь к checkable-токену. Итог: токен, который пакет core рекламирует как общую точку конфигурации, не конфигурирует ничего — ни в одном из двух компонентов. Существующая спека (`toggle.component.spec.ts:537-563`) предоставляет только `KBQ_CHECKBOX_CLICK_ACTION`, поэтому перекрытие невидимо для CI.
**Fix:** удалить провайдер уровня компонента (`toggle.component.ts:55-59`) и разрешать цепочку фолбэков прямо в инициализаторе поля — `inject(KBQ_CHECKABLE_CLICK_ACTION, { optional: true }) ?? inject(KBQ_CHECKBOX_CLICK_ACTION, { optional: true }) ?? undefined` — чтобы токен уровня приложения выигрывал, а `KBQ_CHECKBOX_CLICK_ACTION` оставался обратно совместимым фолбэком; заставить `KbqCheckbox` читать ту же цепочку, чтобы соседи согласовались. Добавить две спеки: одна предоставляет в корне TestBed только `KBQ_CHECKABLE_CLICK_ACTION: 'noop'` и проверяет, что клик по label не переключает контрол; вторая предоставляет оба токена и проверяет, что побеждает checkable-токен.

**TGL-BUG-01 · У `disabled` и `checked` нет приведения к boolean, поэтому форма статического атрибута молча не работает** — `toggle.component.ts:120-129, 146-154`, `toggle.component.html:12-13`, `tools/public_api_guard/components/toggle.api.md:47-48`.
`@Input() set disabled(value: any)` кладёт в модель `KbqCheckable.disabled` всё, что получил (`toggle.component.ts:127-129`). В виде статического атрибута `<kbq-toggle disabled>` передаёт пустую строку; `''` ложна, поэтому `[disabled]="disabled"` оставляет нативный input включённым (`toggle.component.html:13`), `'[class.kbq-disabled]': 'disabled || loading()'` вычисляется в `false` (`:67`), а `effectiveTabIndex` сохраняет контрол в порядке обхода табом (`checkable.ts:87`). Контрол полностью интерактивен, хотя разметка утверждает обратное. У `checked` та же форма (`toggle.component.ts:148-154`): `<kbq-toggle checked>` кладёт в модель `''`, `getAriaChecked()` возвращает `'false'`, и ничего не включается. Хуже обычной небрежности с типами это делают две вещи: сеттер типизирован как `any`, поэтому `strictTemplates` (`tsconfig.json:117`) ничего не сообщает и `ngAcceptInputType_disabled` не генерируется (сравните с `checkbox.api.md:53`); и соседний компонент делает правильно — `KbqCheckbox` объявляет `@Input({ transform: booleanAttribute }) disabled: boolean` (`checkbox.ts:145-152`), как и собственные `indeterminate` (`:164`) и `loading` (`:183`) у toggle. `git show ffb491a51^:packages/components/toggle/toggle.component.ts` показывает `set disabled(value: any)` ещё до рефакторинга `KbqCheckable`, то есть это давний долг, а не регрессия. Идиома статического атрибута здесь не гипотетическая: поставляемый пример пишет `<kbq-toggle labelPosition="left">` (`toggle-label-left-example.ts:12-14`).
**Fix:** добавить `transform: booleanAttribute` обоим аксессор-инпутам (`@Input({ transform: booleanAttribute })` на `disabled` и на `checked`) и сузить типы параметров сеттеров с `any` до `boolean`; геттер `disabled` должен возвращать `boolean`, что заодно уберёт `any` из API-отчёта. Пересобрать и выполнить `approve-api` — появятся `ngAcceptInputType_disabled`/`_checked`. Прикрыть спеками, которые рендерят `<kbq-toggle disabled>` и `<kbq-toggle checked>` из статической разметки и проверяют `input.disabled === true` / `input.checked === true` и соответствующие host-классы.

**TGL-A11Y-01 · `role="switch"` в сочетании с `aria-checked="mixed"` заставляет документированное состояние indeterminate озвучиваться как «выключено»** — `toggle.component.html:2-7, 15`, `core/common-behaviors/checkable.ts:90-92`, `toggle.component.ts:76`, `toggle.en.md:15-19`.
На скрытом input жёстко прописан `role="switch"` (`toggle.component.html:3`) и привязан `[attr.aria-checked]="getAriaChecked()"` (`:7`), где `getAriaChecked()` возвращает `'mixed'` при выставленном `indeterminate` (`checkable.ts:90-92`). Роль `switch` в WAI-ARIA явно не поддерживает значение `mixed` — в отличие от роли `checkbox`, от которой она в остальном наследуется, — и user agent трактует недопустимое значение как `false`. Визуально компонент переключается в смешанное отображение (анимация `@switch` прячет кружок, тема показывает чёрточку: `toggle.component.ts:76` + `toggle.scss:77-97`), то есть зрячий пользователь видит «частично включено», а пользователь скринридера слышит, что переключатель выключен. Причина именно в явном `role="switch"`: на тот же `<input type="checkbox">` приходит `[indeterminate]="indeterminate"` (`toggle.component.html:15`), и нативная роль checkbox отображает indeterminate в `mixed` корректно. Состояние — полноценная документированная возможность: `toggle.en.md:15-19` / `toggle.ru.md:15-19` отводят ему отдельный раздел и живой пример (`toggle-indeterminate-example.ts:11`), — при этом раздел рекомендаций того же гайда советует не использовать переключатель ни для чего небинарного (`toggle.en.md:44`), так что гайд сам себе противоречит в вопросе, должно ли это состояние существовать. Это суждение по WCAG 4.1.2 (Name, Role, Value), а **не** автоматическая ошибка AXE: вендоренный `axe-core` — версии 3.5.6, и его проверка `valid-attr-value` валидирует `aria-checked` по списку допустимых значений самого атрибута, не заглядывая в роль элемента (`node_modules/axe-core/lib/checks/aria/valid-attr-value.js:52-65`), так что в CI это ничем не ловится.
**Fix:** сделать роль условной — `[attr.role]="indeterminate ? null : 'switch'"`, — чтобы в смешанном состоянии элемент откатывался к нативной роли `checkbox`, где `aria-checked="mixed"` допустим и уже согласован с нативным свойством `indeterminate`; для бинарных состояний оставить `role="switch"`. Если дизайн подтвердит, что indeterminate у switch не должно быть вовсе, альтернатива — задепрекейтить инпут `indeterminate` у `kbq-toggle` (с миграцией `ng-update`) и той же правкой снять противоречие в гайде. Прикрыть спекой, проверяющей отсутствие `role` и `aria-checked === 'mixed'` в indeterminate и `role === 'switch'` с `aria-checked === 'true'|'false'` в остальных случаях, и добавить тёмную тему в Playwright-кейс про indeterminate.

### P2 — Стоит исправить

**TGL-BUG-02 · Ранний выход по `loading` пропускает `stopPropagation()` и ресинхронизацию нативного input** — `toggle.component.ts:234-267`, `toggle.component.html:1-20`, `core/common-behaviors/checkable.ts:116-120`.
`onInputClick` начинается с `if (this.loading()) return;` (`:235`) — *до* `event.stopPropagation()` на `:243`, чей семистрочный комментарий (`:236-242`) объясняет, зачем этот вызов нужен: корневой контейнер — `<label>`, поэтому клик пользователя порождает и настоящий клик, и сгенерированный label'ом клик на input, и без защиты оба всплывают наружу из `<kbq-toggle>`. Пока `loading` истинен, защиты нет, так что каждый родительский обработчик `(click)` — и потребители компонента, например `packages/components-dev/input/template.html:5` — срабатывает дважды на клик. Ранний выход также пропускает ветку `else if (!this.disabled) { this.checkable.resetNativeInput(...) }` (`:263-267`), которая существует ровно для того, чтобы откатить дефолтную активацию браузера, когда компонент отказался переключаться. В результате клик или нажатие Space во время загрузки оставляют `input.checked === true` при `checked === false`; поскольку значение биндинга `[checked]="checked"` не изменилось, Angular не перезаписывает свойство, и input остаётся в неверном DOM-состоянии. На этом input есть `[attr.name]` и `[attr.value]` (`toggle.component.html:10-11`), поэтому нативная отправка `<form>` в окне загрузки сериализует значение, которое компонент считает выключенным. Клик ничем и не блокируется: общая утилита `.kbq-progress` рисует только мерцающий оверлей и не выставляет `pointer-events` (`core/styles/common/_animation.scss:51-61`). Документированный пример загрузки держит состояние три секунды (`toggle-loading-example.ts:23-29`) — окно, в которое легко попасть руками.
**Fix:** перенести проверку `loading()` ниже `event.stopPropagation()` и встроить её в решение вместо короткого замыкания — например, трактовать `loading()` как `disabled` в `resolveClick`, передав `'noop'`: `const { shouldToggle, shouldClearIndeterminate } = this.checkable.resolveClick(this.loading() ? 'noop' : this.clickAction);`, — тогда сработает существующая ветка сброса. Добавить спеку на уже существующую фикстуру `LoadingToggle` (`toggle.component.spec.ts:580-603`), которая ставит `loading = true`, кликает по label и проверяет, что `onToggleClick` сработал один раз, `checked` не изменился, а `inputElement.checked === false`.

**TGL-BUG-03 · `onTouched` не вызывается по фокусу или блюру, поэтому контрол, мимо которого пользователь прошёл табом, остаётся untouched** — `toggle.component.ts:210-216, 257`, `checkbox/checkbox.ts:212-216, 342-346`, `toggle.component.spec.ts:393-402`.
Зарегистрированный `ControlValueAccessor` — это `KbqCheckable` (`checkable.ts:10-14, 62`), который хранит колбэк форм в `onTouched` (`:140-142`). Toggle вызывает его ровно в одном месте: внутри `onInputClick` и только в ветке `shouldToggle` (`toggle.component.ts:257`). Мониторинг фокуса (`focusMonitor.monitor(this.elementRef.nativeElement, true)`, `:211`) заведён исключительно ради стилевого хука `.cdk-keyboard-focused`, и на возвращаемый поток никто не подписывается. Последствия: заход табом и уход обратно оставляют контрол `untouched`; то же самое при клике с `clickAction: 'noop'` и при `loading`. Конвенция Angular — и собственная реализация репозитория в соседнем компоненте — помечать touched при взаимодействии с полем независимо от того, изменилось ли значение: `KbqCheckbox` подписывается на свой focus monitor и вызывает `this.checkable.onTouched()` для любого ненулевого origin (`checkbox.ts:212-216, 342-346`). **TGL-STYLE-01 · Дублирующие host-биндинги `[id]`/`[attr.id]`, и пустой `id` протекает на хост** — `toggle.component.ts:65-66, 110-114`, `toggle.component.spec.ts:119-125`.
Host-блок дважды биндит одно и то же выражение — `'[id]': 'id'` ставит DOM-свойство, а `'[attr.id]': 'id'` — атрибут (`toggle.component.ts:65-66`); достаточно одного, и `KbqCheckbox` несёт то же дублирование (`checkbox.ts:73-74`), то есть это копипаста, а не замысел. Пара ещё и ведёт себя несогласованно с `inputId`: геттер откатывается на сгенерированный `uniqueId`, когда `id` пуст (`toggle.component.ts:112-114`), а host-биндинги — нет, поэтому `<kbq-toggle [id]="''">` рендерится как `<kbq-toggle id="">`, тогда как его input получает `kbq-toggle-N-input`. Спека проходит ровно по этому пути (`toggle.component.spec.ts:119-125`), но проверяет только id инпута.
**Fix:** оставить один биндинг (`'[attr.id]': 'id || uniqueId'`) и удалить второй, чтобы хост и input выводили идентификаторы из одного выражения; расширить существующую спеку проверкой id хоста.

**TGL-DOC-01 · Мёртвые заглушки примеров, самопротиворечивый заголовок раздела и недокументированные инпуты** — `examples.toggle.en.md:1-5`, `examples.toggle.ru.md:1-5`, `apps/docs/src/app/structure.ts:1089-1100`, `toggle.en.md:31-39`, `toggle.ru.md:31-39`, `packages/components-dev/all/template.html:1157-1233`, `packages/components-dev/toggle/template.html:24-27`.
`examples.toggle.en.md` и `.ru.md` — обе плейсхолдеры «🚧 Documentation in progress 🚧», но запись в документации выставляет `hasExamples: false` (`structure.ts:1099`), поэтому вкладка Examples не рендерится вовсе и оба файла просто мертвы — это уборка, а не сломанная пользовательская поверхность. А вот в самом гайде есть настоящая нестыковка: раздел с заголовком «Label on the right» / «Подпись справа» (`toggle.en.md:31`, `toggle.ru.md:31`) открывается фразой о том, что справа от подписи расположен *переключатель*, и оба его примера используют `labelPosition="left"` (`toggle-multiline-example.ts:15`, `toggle-label-left-example.ts:12-14`) — заголовок называет не тот элемент. Ни один из гайдов не описывает `big`, `labelPosition`, `clickAction`, `aria-label`/`aria-labelledby`, `name`/`value` и выходы `change`/`indeterminateChange`; читателю остаётся только вкладка API, сгенерированная из отчёта, где почти всё помечено `(undocumented)`. Dev-приложения деградировали заодно: `packages/components-dev/all/template.html` десять раз применяет `class="kbq-toggle_small"` (начиная с `:1157`), хотя такого класса нет ни в одном SCSS (есть только `.kbq-toggle_big`, `toggle.scss:117`), а колонка «Normal» dev-приложения toggle открывается элементом `<kbq-toggle [big]="true">` (`packages/components-dev/toggle/template.html:24-27`).
**Fix:** удалить обе заглушки `examples.toggle.*.md` (либо наполнить их и перевести `hasExamples` в `true` — восемь примеров уже есть в `packages/docs-examples/components/toggle/`); переименовать раздел в «Label on the left» / «Подпись слева» в обоих гайдах либо переписать текст под заголовок; добавить короткое описание `big`, `labelPosition`, `clickAction` и ARIA-инпутов. В dev-приложениях убрать мёртвый класс `kbq-toggle_small` и перенести случайно попавший `[big]`-переключатель в колонку «Big Toggles».

## 5. Стратегия верификации

Общие гейты (после каждой фазы, последовательно — никогда параллельно со сборкой другого агента):
- `npx jest packages/components/toggle`, а также `npx jest packages/components/core/common-behaviors/checkable.spec.ts` и `npx jest packages/components/checkbox` — из-за общего примитива правка toggle может сломать checkbox.
- `yarn run eslint`, `yarn run stylelint` и `yarn run prettier` по затронутым файлам.
- `yarn run build:components`, затем `yarn run check-api`; `approve-api` — только в Фазах 1 и 4, где поверхность меняется намеренно.
- `yarn run dev:toggle` для ручного прогона (шаблон покрывает `[formControl]`, обе позиции подписи, подсказки, фиксированную ширину и fill-раскладки).
- Всё визуальное — `yarn run e2e:docker`, никогда нативным запуском Playwright: базовые линии линуксовые, `threshold: 0`.

Проверки по фазам:
- **Фаза 1:** TestBed, предоставляющий в корне только `{ provide: KBQ_CHECKABLE_CLICK_ACTION, useValue: 'noop' }`, даёт переключатель, который не срабатывает по клику; при обоих предоставленных токенах побеждает checkable-токен; `<kbq-toggle disabled>`, написанный статической разметкой, даёт `input.disabled === true` и класс `.kbq-disabled` на хосте. `check-api` показывает `disabled: boolean` и новые строки `ngAcceptInputType_disabled`/`_checked` — и ничего сверх ожидаемого. Вывод `build:components` для entry point toggle больше не ссылается на `@koobiq/components/checkbox`.
- **Фаза 2:** при `[loading]="true"` один клик по label вызывает `(click)` потребителя ровно один раз, оставляет `checked` без изменений и оставляет `inputElement.checked === false`; фокус и блюр без активации переводят `ngModel.touched` в `true`; `keydown.enter` внутри `<form>` переключает контрол, а `(ngSubmit)` не вызывается.
- **Фаза 3:** в состоянии indeterminate у input нет атрибута `role`, а `aria-checked === 'mixed'`; в остальных случаях `role === 'switch'`, а `aria-checked` равен `'true'`/`'false'`. При `loading` — `aria-disabled === 'true'` и `aria-busy === 'true'` при `input.disabled === false`. `aria-describedby` инпута резолвится в элемент подсказки, а доступное имя, вычисленное из label, текст подсказки не содержит. Прогнать AXE по странице dev-приложения во всех трёх состояниях.
- **Фаза 4:** Playwright-кейс на размер измеряет *после* клика по `big`, и ассерт падает, если переопределение убрать, не обновив тест; три переписанных Jest-кейса краснеют, когда соответствующее поведение намеренно ломают (испортить сторожевую проверку disabled в `onInputClick` и убедиться, что кейс про disabled стал красным); `grep -rn "kbq-toggle_small" packages/` ничего не находит; обе `examples.toggle.*.md` удалены либо вкладка Examples в документации рендерит восемь примеров на обеих локалях.

## Приложение A — Методология ревью

Каждый файл в `packages/components/toggle` прочитан целиком, затем сверен с четырьмя внешними поверхностями: примитивом `KbqCheckable` и его спекой в `packages/components/core/common-behaviors/`, соседним `KbqCheckbox` (он делит примитив и является естественным контролем для вопроса «расхождение намеренное?»), сгенерированными API-отчётами для `toggle`, `checkbox` и `core` и живым набором design-токенов в `node_modules/@koobiq/design-tokens/web/new/`. Потребители перечислены через `grep -rn "kbq-toggle" --include="*.html" --include="*.ts" packages/` (39 мест вызова, все — в dev-приложениях, e2e-фикстурах и примерах документации: внутрибиблиотечных потребителей у toggle нет), а `grep -rn "KBQ_CHECKABLE_CLICK_ACTION"` по `packages/` и `apps/` установил, что токен из TGL-API-01 читается ровно в одном месте. Оценка серьёзности следует общей шкале репозитория; `git log --oneline -15 -- packages/components/toggle/` (15 коммитов, из которых содержательны `ffb491a51`, `ca4d8c98d` и `0787063a2`) использовался, чтобы датировать расхождения, а не чтобы их выводить.

Опровергнуто при верификации:
- **«`setDisabledState` не реализован, поэтому `formControl.disable()` ничего не делает».** — Реализован, причём дважды. Зарегистрированный `ControlValueAccessor` — это `KbqCheckable` (`checkable.ts:10-14, 62`), чей `setDisabledState` выставляет модель `disabled` (`:145-147`); собственная копия toggle (`toggle.component.ts:302-304`) честно помечена `@deprecated Unused`. `toggle.component.spec.ts:452-466` доказывает, что путь реактивных форм работает от начала до конца.
- **«У toggle должен быть инпут `readonly`, как у других форм-контролов».** — Не дефект. Ни у `kbq-checkbox`, ни у `kbq-radio` его нет; конвенция библиотеки для нередактируемого checkable-контрола — `disabled`, а временный случай покрывает `loading`. Неправильно здесь другое: `loading` не сообщает о себе вспомогательным технологиям — это и заведено как TGL-A11Y-02, а не как запрос фичи.
- **«`focusMonitor.monitor()` в `ngAfterViewInit` течёт, потому что никто не отписывается».** — `monitor()` регистрирует элемент и возвращает поток; toggle никогда не подписывается, значит и утекать нечему, а `stopMonitoring(this.elementRef.nativeElement)` в `ngOnDestroy` (`toggle.component.ts:215`) снимает регистрацию с того же элемента, который мониторился. Настоящий дефект — *отсутствие* подписки, заведён как TGL-BUG-03.
- **«Выход `change` срабатывает дважды, потому что нативное событие `change` тоже всплывает из скрытого input».** — `onChangeEvent` его останавливает (`toggle.component.ts:226-228`), а `toggle.component.spec.ts:157-171` проверяет ровно одну эмиссию на клик по label.
- **«Пакет отсутствует в конфигурации API guard».** — `toggle` перечислен в `tools/api-extractor/config.json:61`, а `tools/public_api_guard/components/toggle.api.md` существует и актуален.
- **«Конструкторный `effect()` пишет в обычное поле `currentCheckState`, поэтому биндинг `[@switch]` устаревает при `OnPush`».** — Из статического анализа не заводится. `currentCheckState` пишется также из сеттера `checked` (`:152`), сеттера `indeterminate` (`:175`) и `onInputClick` (`:258`), и все они выполняются внутри прохода change detection, который и так обновляет представление, а сам эффект документирован как подстраховочная синхронизация для форм-пути (`:205-207`). Подтвердить или опровергнуть устаревание можно только рантайм-экспериментом, которого это ревью не проводит; само дублирование заведено как TGL-ARCH-01.

Скорректировано при верификации:
- **TGL-BUG-01** черновой формулировкой был «рефакторинг `KbqCheckable` потерял `booleanAttribute` у `disabled`». `git show ffb491a51^:packages/components/toggle/toggle.component.ts` показывает `set disabled(value: any)` на строке 113 дорефакторингового файла — приведения там не было никогда. Серьёзность не изменилась; формулировка теперь говорит о давнем долге, а не о регрессии, и сравнение с соседним компонентом заменило аргумент от истории git как доказательство ненамеренности.
- **TGL-A11Y-01** черновой формулировкой был «автоматическая ошибка AXE». Вендоренный `axe-core` — версии 3.5.6, и его проверка `valid-attr-value` валидирует `aria-checked` по списку значений самого атрибута, не заглядывая в роль (`node_modules/axe-core/lib/checks/aria/valid-attr-value.js:52-65`), так что ни одно правило не срабатывает. Переформулировано как суждение по WCAG 4.1.2 / спецификации ARIA с явным указанием «CI это не ловит» — потому и нужна написанная вручную спека.
