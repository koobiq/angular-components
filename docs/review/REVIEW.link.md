# Koobiq `link` Component — Code Review & Improvement Plan

> Scope: `packages/components/link` (directive, tokens, theme, Jest spec, e2e fixture + Playwright spec, both user guides, 14 docs examples, dev app, API guard report) · Commit `b665e503` · 2026-08-28
> Generated by a multi-dimension review (architecture, correctness, accessibility, public API/types, styles, tests, docs) with manual verification of every finding against the source, the compiled CSS bundle, 30 in-repo consumer files and the live design-token set. 14 findings confirmed (P0×0, P1×5, P2×5, P3×4); 7 candidate findings refuted during verification (see Appendix A). This document is a review + roadmap; no source is modified by it.

---

## 1. Executive Summary

`KbqLink` is a 187-line attribute directive (`[kbq-link]`) with no template, no NgModule logic and one of the widest consumer footprints in the library: 30 files hand-write its `.kbq-link__text` class (118 occurrences) and 42 call sites hand-write `.kbq-link_external`. There are no release blockers — nothing here crashes — but the package has the worst *contract* record reviewed so far: a whole documented feature emits no CSS, and four separate accessibility defects survive because every consumer patched around them locally instead of reporting them.

- **An entire published feature is dead CSS.** The `@media print` block is nested one level too deep in `_link-theme.scss:193-206`, so Sass emits `.kbq-link .kbq-link_print` — a *descendant* selector — while `.kbq-link_print` is applied to the same element as `.kbq-link` (`link.component.ts:35, 42`). The compiled bundle confirms it verbatim (`dist/e2e/browser/styles-VY327GDA.css:13763-13773`). The `print` input, `printUrl`, `[attr.print]`, a guide section, a published example, a Jest case and four dev-app rows all exist and all produce nothing visible, because every one of them checks the attribute rather than the rendering. The fix is one `&` (LNK-CSS-01).
- **Accessibility is the weakest dimension in the package, and the consumers prove each gap.** A "disabled" link keeps its `href`, gets an invalid `disabled` attribute instead of `aria-disabled`, and stays activatable from a screen reader's links list (LNK-A11Y-01) — the tooltip package grew a whole `forDisabledComponent` escape hatch around this case. Non-anchor hosts get `tabindex="0"` with no role and no key handling, so `clamped-text.ts:53` writes `role="button"` by hand and twelve published examples pair every `(click)` with a hand-written `(keydown.enter)` (LNK-A11Y-02). `outline: none` is unconditional while the replacement ring needs a class only `FocusMonitor` adds, so every link inside `<kbq-markdown>` has no focus indicator at all and the docs site had to re-add one itself (LNK-A11Y-03). There is not a single `role` or `aria-*` attribute anywhere in `packages/components/link/`.
- **`noUnderline` and `pseudo` links are distinguished from body text by colour alone, and the colour is not far enough apart.** Composited against `--kbq-background-bg`, link text versus body text measures **2.69:1 in light and 2.24:1 in dark** — under the 3:1 that WCAG technique G183 requires when colour is the only channel — and those two variants never paint an underline at rest (LNK-A11Y-04).
- **12 `target="_blank"` anchors ship with no `rel` and no new-tab cue.** `rel=` appears zero times in the link package, its examples and its dev app, while the sibling `dropdown` examples and the docs app both write `rel="noopener noreferrer"`. The external affordance is a bare `kbq-north-east_16` icon with no accessible name and no `aria-hidden` (LNK-A11Y-05).
- **Five Jest assertions cover the whole directive, all of them class-presence checks**, every interactive state in the Playwright fixture is faked with a hand-written class, and one dark baseline was simply never taken (`02-dark.png` is absent) (LNK-TEST-01).

Genuine strengths worth preserving: the styling is entirely token-driven with zero hardcoded colours and resolves cleanly against both live token files; six of nine inputs are already modern signal inputs with `booleanAttribute` transforms; the one RxJS subscription is correctly torn down with `takeUntilDestroyed` and the `FocusMonitor` monitor/stopMonitoring pair is balanced; the bilingual design guide is unusually thorough, with 14 working examples and real screenshots; and the multiline hit-area work (`--kbq-link-size-multiline-hit-area-gap: calc((1lh - 1em) / 2)`, `link-tokens.scss:4`) is a genuinely elegant solution to a hard problem. The code is not careless — it is under-verified, and every one of the findings below is something a test would have caught.

## 3. Prioritized Findings (deduplicated, verified)

### P0 — Release blockers

None.

### P1 — High

**LNK-CSS-01 · The `@media print` rule compiles to a descendant selector, so the entire print feature emits nothing** — `_link-theme.scss:193-206`, `link.component.ts:35, 42, 48, 110-123`; compiled proof at `dist/e2e/browser/styles-VY327GDA.css:13763-13773`.
Inside `@mixin kbq-link-theme()` the print block is nested as `.kbq-link { … @media print { .kbq-link_print:not(.kbq-disabled) { … } } }` (`:132, 193-206`). Sass bubbles the `@media` out of the selector but keeps `.kbq-link` as an *ancestor*, so what ships is `.kbq-link .kbq-link_print:not(.kbq-disabled)::after` — a descendant combinator. The compiled bundle reads exactly that. `.kbq-link_print` is bound onto the *same* element as `.kbq-link` by the host block (`link.component.ts:35, 42`), so the selector cannot match anything, ever. Everything downstream is therefore inert: the `print` input (`:110-117`), `printMode`/`printUrl` (`:121-123`), the `[attr.print]` binding (`:48`), the `content: ':\a' attr(print)` pseudo-element that is the whole point of the feature, and the underline suppression that goes with it. This is not an obscure corner — the guides give it a section with a worked CVE example (`link.en.md:93-102`, `link.ru.md:93-102`), there is a published example (`link-print-example.ts`), a Jest case (`link.component.spec.ts:44-62`) and four dev-app rows (`components-dev/link/template.html:32, 35, 184, 187`). Every one of them asserts or displays the *attribute*, never the rendered result, which is exactly why a fully dead feature has survived since it was written. The missing character is a single `&`.
**Fix:** change `.kbq-link_print:not(.kbq-disabled)` to `&.kbq-link_print:not(.kbq-disabled)` at `_link-theme.scss:194`. Guard it so it cannot rot again: a Playwright case with `page.emulateMedia({ media: 'print' })` over a `[print]` link and a screenshot, or — cheaper and deterministic — a Jest case that walks `document.styleSheets`, finds the `@media print` group and asserts its `selectorText` contains `.kbq-link.kbq-link_print`. While in the area, note that `updatePrintUrl` strips only `^https?://` via `baseURLRegex` (`link.component.ts:30, 184`), so the guide's promise that "«http://www» can be omitted" (`link.en.md:95`) is only met when the caller hand-writes the whole string — which is precisely what `link-print-example.ts:15` does.

**LNK-A11Y-01 · A "disabled" link keeps its `href` and its link semantics; the state reaches nobody except sighted pointer users** — `link.component.ts:45-47, 66-73, 80-87`, `_link-theme.scss:186-191`.
`disabled` produces exactly three effects: the class `.kbq-disabled`, the attribute `disabled`, and `tabindex="-1"` (via the `tabIndex` getter, `:82`). `disabled` is not a valid attribute on `<a>`, `<span>` or `<label>` — the three element types this directive is actually applied to in this repository — so the HTML parser and the accessibility tree ignore it completely. Nothing sets `aria-disabled`, nothing neutralises `href`, and there is no `click` handler anywhere in the class to call `preventDefault()`. The only real barrier is `pointer-events: none` (`_link-theme.scss:188`) plus the negative tabindex, and neither is exposed to assistive technology: a screen-reader user browsing NVDA's Elements List or the VoiceOver rotor still sees an ordinary enabled link, and activating it from there fires a synthetic `click()`, which `pointer-events` does not block — the navigation happens. That is WCAG 4.1.2 (Name, Role, Value): the state is not programmatically determinable, and the component behaves differently for different input methods. The `pointer-events: none` also swallows every hover, which is exactly why the tooltip package had to grow a `forDisabledComponent` escape hatch that re-adds `tabindex="0"` from the outside and reads `KbqLink.disabledSignal` directly (`tooltip.component.ts:536-552`), with a dedicated spec (`tooltip.spec.ts:926-928`) and a published example (`tooltip-disabled-for-component-example.ts:26-36`) built around the link case specifically. This is a WCAG judgement, not an automated AXE failure — axe-core has no rule for an invalid `disabled` attribute on an anchor, which is part of why it has lasted.
**Fix:** in the host block, replace `'[attr.disabled]': 'disabled || null'` with `'[attr.aria-disabled]': 'disabled || null'`, keeping the native `disabled` attribute only when the host really is a form control. Add a `(click)` host listener that calls `preventDefault()` and `stopImmediatePropagation()` while `disabled`, so no input path — pointer, keyboard, or a synthetic AT click — can navigate; keep `href` in place so the element retains its link role and the state stays a *state* rather than a role change. Cover with Jest cases asserting `aria-disabled="true"` and `tabindex="-1"` on a disabled link, plus one that dispatches `element.click()` on a disabled link and asserts `defaultPrevented`. Re-run `packages/components/tooltip` afterwards — its `forDisabledComponent` suite is the closest thing to an integration test this behaviour has.

**LNK-A11Y-02 · Non-anchor hosts become focusable with no role and no keyboard activation, while the guide promises Enter and Space** — `link.component.ts:33, 40, 47, 89`, `link.en.md:120-126`, `link.ru.md:120-126`.
The selector is the bare attribute `[kbq-link]` (`:33`), and the host unconditionally binds `'[attr.tabindex]': 'tabIndex'` (`:47`) with a default of `0` (`:89`). Applied to a `<span>` — which is what the `pseudo` variant exists for — this produces a focusable element with no role, no role name for a screen reader to announce, and no key handling whatsoever: the directive binds no `keydown`, so Enter and Space do nothing. The consumers make the gap unmistakable. `clamped-text.ts:53` hand-writes `role="button"` onto its `<span kbq-link noUnderline pseudo>`. Twelve published examples pair every `(click)` with a hand-written `(keydown.enter)` — `toast-actions-overview-example.html:12, 15, 19, 22`, `toast-hide-overview-example.html:2, 29`, `toast-link-overview-example.html:10`, `toast-multiline-example.ts:17`, `toast-overview-example.ts:17`, `toast-progress-bar-overview-example.ts:23`, `toast-report-overview-example.ts:23`, `toast-types-overview-example.html:2`, `toast-user-data-example.html:2`, `validation-message-global-with-links-example.html:13, 15, 17` — and even after all that hand-wiring, Space still does nothing at any of them, while `link.en.md:124` / `link.ru.md:124` publishes a key table promising "Space \ ⏎ — Follow the link". `file-upload` solved it the other way and cancels the directive's default at four call sites with `[tabIndex]="-1"` (`single-file-upload.component.html:66, 85`, `multiple-file-upload.component.html:97, 116`), because a focusable `<label>` with no role is worse than an unfocusable one. There are zero `role` or `aria-*` attributes anywhere under `packages/components/link/`.
**Fix:** stop emitting `tabindex` unconditionally — only bind it when the host is not natively focusable (no `<a href>`), and only when the link is meant to be interactive. Add `'[attr.role]'` resolving to `null` for a real `<a href>`, `'button'` when `pseudo()` is set, and `'link'` for a non-anchor host that is not pseudo. Add a `keydown` host listener that activates on Enter always and on Space when the resolved role is `button`, by dispatching a click on the host — that is what makes the published key table true rather than aspirational. The acceptance criterion is deleting the hand-rolled `role="button"` at `clamped-text.ts:53` and the twelve `(keydown.enter)` handlers, and having every one of those suites stay green. Correct the key table in both guides at the same time (see LNK-DOC-01).

**LNK-A11Y-03 · `outline: none` is unconditional while the replacement ring needs a directive-only class, so `<kbq-markdown>` links have no focus indicator at all** — `_link-theme.scss:13-15, 180-184`, `markdown.service.ts:28`, `link.component.ts:137-139, 145-147`; workaround at `apps/docs/src/styles/_markdown.scss:20-25`.
`.kbq-link:focus { outline: none }` is emitted for every element carrying the class (compiled at `dist/e2e/browser/styles-VY327GDA.css:13580`). Its replacement is `.kbq-link.cdk-keyboard-focused { outline-style: solid; … }` (`_link-theme.scss:180-184`), and `.cdk-keyboard-focused` is added only by CDK `FocusMonitor`, which only runs where a `KbqLink` instance exists (`link.component.ts:137-139`). The library itself breaks that assumption: `KbqMarkdownService.transform()` stamps `kbq-link kbq-text-only kbq-link_use-visited` onto every `<a>` in rendered Markdown as a **string** (`markdown.service.ts:28`), with no directive attached — so those anchors inherit the suppression and never receive the ring. Keyboard users tabbing through any `<kbq-markdown>` output get no focus indicator whatsoever, which is a WCAG 2.4.7 (Focus Visible, Level AA) failure. `packages/components/markdown/_markdown-theme.scss` has no `:focus` rule of its own — verified by grep — and the docs site had to add one itself at `apps/docs/src/styles/_markdown.scss:20-25`, re-deriving the outline from the link tokens with hardcoded fallbacks. That fix ships with the docs app, not the library, so every other `kbq-markdown` consumer still has the bug. The same class dependency also means `KbqLink.focus()` (`:145-147`), which calls the native `.focus()`, produces `.cdk-program-focused` rather than `.cdk-keyboard-focused` and therefore draws no ring either.
**Fix:** make the suppression conditional. Drop the blanket `&:focus { outline: none }` and paint the ring from `&:focus-visible` using the same three tokens, keeping the `.cdk-keyboard-focused` rule alongside it for consumers that drive focus through `FocusMonitor`. `:focus-visible` covers the directive-backed *and* the class-only case in one rule, and the acceptance test is concrete: deleting `apps/docs/src/styles/_markdown.scss:20-25` must change nothing. Separately, change `focus()` to `this.focusMonitor.focusVia(this.getHostElement(), 'keyboard')` so a programmatic focus is visible (see `project_kbq_focus_ring_mechanism`). Add a Playwright case that presses Tab onto a link inside a `<kbq-markdown>` fixture and screenshots the result.

**LNK-A11Y-04 · `noUnderline` and `pseudo` links are distinguished from body text by colour alone, at 2.69:1 (light) and 2.24:1 (dark)** — `_link-theme.scss:17-24, 119-124, 145-150, 157-162`, `link-tokens.scss:10-11`.
The geometry mixin sets `text-decoration-color: transparent` on every link (`:22`), and only `&:not(.kbq-link_pseudo, .kbq-link_no-underline)` ever paints it back (`:119-124`). A `noUnderline` link therefore has **no** underline in any state — resting, hover, active or focus — and a `pseudo` link has none at rest, gaining one only on hover and active (`:145-150, 157-162`). What is left to distinguish a link from the sentence around it is colour: `--kbq-link-text: var(--kbq-foreground-theme)` (`link-tokens.scss:10`) against body text `--kbq-foreground-contrast`. Composited over `--kbq-background-bg` those two give **2.69:1 in light and 2.24:1 in dark**, below the 3:1 that WCAG technique G183 requires when colour is the only distinguishing channel (SC 1.4.1, Use of Color, Level A). Both colours clear 4.5:1 against the background itself (link text measures 5.11:1 light / 6.08:1 dark), so this is specifically a link-versus-surrounding-text failure and not a general text-contrast one. It is not theoretical: `packages/e2e/template.html:9` uses `compact noUnderline` for a link list, `clamped-text.ts:53` uses `noUnderline pseudo` at the end of a paragraph of clamped body text, and every toast action and validation link in the docs is a `pseudo` link inline in a sentence. Worth recording alongside: even where the underline *is* painted, its own contrast against the background is only **1.68:1 (light) / 1.96:1 (dark)** (`--kbq-line-theme-fade`, `link-tokens.scss:11`), so the underline is a faint hint rather than a robust second channel — which weakens the "the underline carries it" defence for the default variant too.
**Fix:** give the underline-less variants a non-colour affordance at rest rather than raising the link colour (raising it would fight the 4.5:1 the link already comfortably passes against the background). A dashed or dotted `text-decoration-style` on `.kbq-link_pseudo` is both the traditional meaning of "pseudo-link" and the smallest change; `noUnderline` needs a deliberate decision — if it genuinely means "no affordance at all", document that it may only be used where the link is not inline in running text, and say so in both guides. Add a contrast assertion to the token pipeline (a small `node -e` check comparing `--kbq-link-text` to `--kbq-foreground-contrast` over `--kbq-background-bg` in both token files) so a future palette change cannot silently make this worse, and consider raising `--kbq-line-theme-fade` toward 3:1 so the default underline is a real second channel.

### P2 — Should fix

**LNK-A11Y-05 · `target="_blank"` links ship without `rel`, without a new-tab cue, and with an external icon that has no accessible name** — 12 call sites under `packages/docs-examples/components/link/`, `link.en.md:53-63`, `link.ru.md:53-63`, `icon.component.ts:22-33, 128-146`.
`target="_blank"` appears 12 times in the link package's published examples — `link-application-example.ts:15, 22`, `link-caption-example.ts:14`, `link-external-example.ts:13`, `link-icons-example.ts:13`, `link-overview-example.ts:13, 19, 26, 35, 49`, `link-target-blank-example.ts:13`, `link-visited-example.ts:14` — and `rel=` appears **zero** times anywhere under `packages/components/link/`, `packages/docs-examples/components/link/` or `packages/components-dev/link/`. The repository already knows better in two other places: `dropdown-item-link-example.ts:19, 20, 23` writes `rel="noopener noreferrer"` on all three of its `target="_blank"` anchors, and the docs app writes it too (`apps/docs/src/app/components/component-viewer/component-viewer.template.html:27`). Across all of `packages/docs-examples`, 30 anchors use `target="_blank"` and exactly 3 carry a `rel` — all three in `dropdown`. The accessibility half of this is the worse half: evergreen browsers imply `noopener` for `target="_blank"`, but `noreferrer` is not implied and older or embedded engines are not covered, and — more importantly — nothing announces that the link opens a new tab, which is WCAG 3.2.5 / technique G201. The affordance the design system chose for "external" is a bare icon, `<i kbq-icon="kbq-north-east_16">`, and `KbqIcon` adds no `role` and no `aria-hidden` of its own (`icon.component.ts:22-33`) while injecting raw `<svg>` into the host (`:128-146`); depending on the AT the icon is therefore either silent, conveying nothing, or announced as an unnamed image inside the link's accessible name. The repo's own convention is to write `aria-hidden="true"` by hand — 28 icon call sites do, including `alert-content-example.html:4, 19` — and not one of the link examples does.
**Fix:** add `rel="noopener noreferrer"` to all 12 examples and to `components-dev/link/template.html`, and document it in the `.kbq-link_external` callout (`link.en.md:53-61`, `link.ru.md:53-61`) right next to the icon instruction that is already there. Give the external affordance an accessible name from `kbqInjectA11yLocaleConfiguration()` — a visually-hidden span ("opens in a new tab") emitted by the directive when it detects `target="_blank"`, plus `aria-hidden="true"` on the icon — rather than leaving every consumer to invent one. Add a docs smoke assertion to `yarn run e2e:docs` that every rendered `a[target="_blank"]` carries a `rel` containing `noopener`; that single assertion also protects the 27 non-link examples currently missing it.

**LNK-CSS-02 · `.kbq-link__text` is a load-bearing, entirely undocumented structural contract — 118 hand-written occurrences across 30 files** — `_link-theme.scss:17-24, 43-51, 63-71, 76-84, 88-106, 120-124`, `link.component.ts:43-44`, guides `link.en.md`, `link.ru.md`.
When a link contains an icon, the host receives `.kbq-text-with-icon` instead of `.kbq-text-only` (`link.component.ts:43-44`), and from that moment every underline rule targets `.kbq-link__text` rather than the host (`_link-theme.scss:18, 121, 196-197`); the icon gaps (`:43-51, 63-71, 76-84`) and all the `.kbq-link_external` spacing corrections (`:88-106`) do the same. A consumer who writes the obvious markup — `<a kbq-link><i kbq-icon="…"></i>Text</a>` — silently gets a link with **no underline at all**, because there is no `.kbq-link__text` element for the decoration to land on. The class is never applied by the directive, is not mentioned once in `link.en.md` or `link.ru.md`, and cannot appear in the generated API tab because it is a CSS class rather than a member. The result is 118 hand-written `class="kbq-link__text"` occurrences across 30 files, including inside the library itself (`clamped-text.ts:58, 61`, `time-range-title.ts:23`) and throughout the docs app (`copy-button.ts:28`, `stackblitz-button.ts:11`, `component-viewer.template.html:29`). The sibling class `.kbq-link_external` is at least documented in a callout (`link.en.md:58`, `link.ru.md:58`) and appears 42 times — but even that is cargo-culted onto five icon-less links where its only rule (`_link-theme.scss:87`, which requires `.kbq-text-with-icon`) cannot apply: `link-caption-example.ts:14`, `link-overview-example.ts:13, 19, 47-55`, `link-visited-example.ts:13`. `.kbq-text-with-dot` is a third such class — four theme rules reference it (`_link-theme.scss:120, 146, 158, 197`), it is hand-written in the dev app and in `alert-content-example.html:7, 22`, and it is documented nowhere at all.
**Fix:** two routes, and the second is the real one. (a) Document all three classes in a "Markup contract" section of both guides, each with a compiling snippet — cheap, and it stops the bleeding. (b) Stop requiring them: have the directive wrap unwrapped text nodes itself, or select the decoration onto `> *:not(.kbq-icon)` and bare text so it lands automatically, keeping `.kbq-link__text` honoured when present so no existing consumer breaks. Stage (b) behind (a). jsdom does not apply the theme stylesheet, so the regression guard has to be a Playwright row — add an icon-plus-unwrapped-text link to `e2e.ts` and let the screenshot prove the underline is there.

**LNK-BUG-01 · The `disabled` getter reads an asynchronously-updated mirror, so an imperative read returns the previous value** — `link.component.ts:62-76, 126, 130-135`, `tooltip.component.ts:542`.
`set disabled(value)` writes only `disabledSignal` (`:71-73`); `_disabled` — the field the getter actually returns (`:67-69`) — is updated from a `toObservable(this.disabledSignal).subscribe(…)` created in the constructor (`:134`). Angular's own JSDoc for `toObservable` states that "the signal's value will be propagated into the Observable's subscribers using an `effect`", and effects are scheduled, never synchronous. Every host binding that decides the rendered state reads the lagging mirror — `'[class.kbq-disabled]': 'disabled'`, `'[attr.disabled]': 'disabled || null'`, and `'[attr.tabindex]': 'tabIndex'` whose getter branches on `this.disabled` (`:45-47, 82`) — while the one external consumer of the same state reads the signal directly: the tooltip's `forDisabledComponent` effect calls `this.forDisabledComponent()!.disabledSignal()` (`tooltip.component.ts:542`). Two readers, two sources, one effect flush apart. The imperative read is unambiguously wrong: `exportAs: 'kbqLink'` (`:50`) publishes the getter to templates and `tooltip.spec.ts:927` does exactly `#link="kbqLink"`, so `link.disabled = true; link.disabled // still false` is what a caller gets. Writing a plain field from inside an effect also marks no view dirty, so under `OnPush` with zoneless change detection nothing schedules the pass that would repaint `.kbq-disabled`. The mirror exists purely for backwards compatibility and is already slated for deletion by three `@todo 20` comments (`:62, 125, 133`).
**Fix:** delete `_disabled` (`:126`) and the constructor subscription (`:134`), and make the getter `return this.disabledSignal();`. That is synchronous, reactive, removes the divergence with the tooltip's reader, and is exactly what the `@todo 20` notes already plan — and it is not a breaking change, since the accessor pair survives. Guard it with a Jest case that assigns `disabled` and reads it back in the same tick, and one that asserts `.kbq-disabled` and `tabindex="-1"` after a single `detectChanges()`.

**LNK-BUG-02 · `printUrl` is written inside a bare microtask with no change-detection signal** — `link.component.ts:56, 130-131, 182-186`, `link.component.spec.ts:44-62`.
`updatePrintUrl()` defers into `Promise.resolve().then(…)` and assigns the plain field `printUrl` (`:183-185`). Nothing afterwards marks the view dirty — no signal, no `markForCheck`, no `renderer.setAttribute`, even though `Renderer2` is already injected and used elsewhere in the class (`:56, 161-176`) — so the `[attr.print]` binding (`:48`) only picks the value up if some unrelated change detection happens to run afterwards. The component's own Jest case documents the fragility precisely: it needs `tick(); detectChanges();` before the first assertion, then `tick(); detectChanges(); tick(); detectChanges();` — four calls — to observe a single input change (`:55-60`). Under `OnPush` with zoneless change detection the attribute can simply never appear. The deferral itself is not gratuitous — reading `href` synchronously in the constructor would be premature — but the mechanism is. This defect is currently masked by LNK-CSS-01: the attribute it feeds is read by no matching CSS rule, so nobody has noticed.

If the microtask must stay for the `href` read, follow the assignment with `this.changeDetectorRef.markForCheck()` or write the attribute directly through `renderer.setAttribute`. Rewrite the spec so it needs one `tick()` and one `detectChanges()` — a spec that needs four is the code telling you it is wrong. This changes the API report (`set print` becomes an `InputSignal`), so batch it with LNK-API-01.

### P3 — Nice to have / hygiene

**LNK-API-01 · Nine inputs, two JSDoc comments, one `any`, and internals in the published report** — `link.component.ts:30, 60, 91-128`, `tools/public_api_guard/components/link.api.md:18-77`, `apps/docs/src/app/structure.ts:703-704`.

Adding JSDoc removes `(undocumented)` markers and therefore changes `link.api.md`, so batch all of it into one `yarn run build:components && yarn run approve-api` cycle — build first, the guard reads `dist/*.d.ts`.

**LNK-ARCH-01 · Two overlapping content queries for the same target, with opposite `descendants` defaults and different consumers** — `link.component.ts:28, 60, 104-106, 128, 153-180`.
The directive queries `KbqIcon` twice: `@ContentChildren(forwardRef(() => KbqIcon), { read: ElementRef }) icons` (`:60`) and `readonly icon = contentChild(KbqIcon)` (`:128`). `@ContentChildren` defaults to `descendants: false` — direct children only — while `contentChild` defaults to `descendants: true`; both defaults are stated explicitly in Angular's own typings. The two feed different behaviour: `icon()` drives `hasIcon` (`:104-106`), which chooses between `.kbq-text-only` and `.kbq-text-with-icon` and therefore decides *where the underline lands* (LNK-CSS-02); `icons` drives `.kbq-icon_left` / `.kbq-icon_right` (`:159-180`). A link whose icon sits one level deeper than a direct child consequently loses its `.kbq-text-only` underline while gaining no spacing classes — the two halves disagree by construction. The same method also bails out whenever the host has a single non-comment child (`:167`), so an icon-only link gets `.kbq-text-with-icon` — no underline anywhere, since there is no `.kbq-link__text` — and no position classes either, with no accessible name to compensate. The `forwardRef` at `:60` is unnecessary: `KbqIcon` is a plain import from another package (`:28`) with no cycle to break. Mixing a decorator query and a signal query for the same token in one class also cuts against the repo's signal-query convention.
**Fix:** collapse to a single `readonly icons = contentChildren(KbqIcon, { read: ElementRef, descendants: true })` with `readonly hasIcon = computed(() => this.icons().length > 0)`; that removes the `forwardRef`, the `QueryList`, `ngAfterContentInit` and the `changes` subscription in one move, and lets `updateClassModifierForIcons` run from an `effect()`. Decide deliberately what an icon-only link should be — most likely `.kbq-text-only` plus a required `aria-label` — rather than letting it fall through the `:167` guard. Cover both branches with Jest cases (LNK-TEST-01). This changes the API report, so fold it into the LNK-API-01 `approve-api` cycle.

**LNK-DOC-01 · The published examples contradict the guide they illustrate** — `link-general-example.ts:11`, `link-pseudo-example.ts:11`, `link-visited-example.ts:12-27`, `link-overview-example.ts:17-30, 60-63`, `link.en.md:104-126`, `link.ru.md:104-126`.
Four distinct problems in files that ship to the docs site. (1) Both guides devote an illustrated section to browser behaviour — "the markup uses the `<a>` tag", with a captioned screenshot of an "Improper link. The browser did not identify the element as a link" (`link.en.md:104-118`, `link.ru.md:104-118`) — and the very first example the same guide embeds is `<a kbq-link>Scan report</a>` with no `href` (`link-general-example.ts:11`), which *is* the improper link in the screenshot: an anchor without `href` has no link role, and the directive then makes it focusable anyway (LNK-A11Y-02). `link-pseudo-example.ts:11` has the same shape on a `<span>`. (2) `link-visited-example.ts:17-18` binds `[useVisited]="visited"` and sets `visited = true` on click, conflating "enable visited styling" with "is visited" — `:visited` is set by the browser from history, not by the app — and the example ships with `useVisited` initially `false` (`:27`), so a link the user genuinely has visited stays unstyled until it is clicked again. (3) `link-overview-example.ts:17-30` contains the same six-line block twice, verbatim, and `:60-63` declares two dead fields (`active`, `focus`); the example is referenced by no guide at all, only by two dev apps. (4) The key table (`link.en.md:120-126`, `link.ru.md:120-126`) lists Space as following the link — native anchors activate on Enter only, and `pseudo` links on neither.
**Fix:** give the general and pseudo examples a real `href` (or `href="#"`, which `link-prepositions-example.ts:13` already does) so the docs stop demonstrating the anti-pattern they warn about two sections later; rewrite `link-visited-example` to set `useVisited` statically and explain in prose that `:visited` comes from browser history; deduplicate `link-overview-example` and delete `active`/`focus`; and correct the key table to Enter only, adding a pseudo-link row once LNK-A11Y-02 lands. Note the `examples.link.*.md` files are *not* a defect here — they embed `link-with-caption`, the one example the guide does not, which is exactly the disjoint-tab convention (`structure.ts:705` sets `hasExamples: true`).

**LNK-STYLE-01 · Duplicate tokens, a stale TODO, and a state class the library never applies** — `link-tokens.scss:11, 13-22`, `_link-theme.scss:165-178`, `e2e.ts:110, 136, 145, 153`.
Six of the fifteen theme tokens are aliases of one another. `--kbq-link-border-bottom`, `--kbq-link-state-hover-border-bottom` and `--kbq-link-state-active-border-bottom` are all `var(--kbq-line-theme-fade)` (`link-tokens.scss:11, 20, 22`), so hover and active change the text colour while leaving the underline byte-identical; the three visited underline tokens (`:14, 16, 18`) are likewise all `var(--kbq-line-visited-fade, var(--kbq-line-visited))`. That fallback chain carries a `/* @TODO (#DS-3002) */` (`:13`) that predates the current token set — `--kbq-line-visited-fade` is defined in both `css-tokens-light.css` and `css-tokens-dark.css`, so the fallback is dead code and the ticket can be closed. Separately, `.kbq-visited` (`_link-theme.scss:165`) is written by nothing in the library: the only four occurrences in the entire repository are in this package's own e2e fixture (`e2e.ts:110, 136, 145, 153`), where it fakes a state the browser owns. The real path is the `:visited` branch on the same line, which no test can exercise — and which deserves a browser check before more work goes into it, since browsers restrict `:visited` to a small allow-list of colour properties in which `color` is honoured but `text-decoration-color` generally is not, meaning the three visited underline tokens may never paint at all on a real anchor. (`.kbq-hovered` and `.kbq-active`, by contrast, are a library-wide convention used across 25 packages and are not a defect here.)
**Fix:** collapse the six duplicates to two (`--kbq-link-border-bottom` and `--kbq-link-state-visited-border-bottom`), or give hover and active genuinely distinct values if the design intends a difference; drop the `--kbq-line-visited` fallback and close DS-3002. Decide what `.kbq-visited` is for — either apply it from the directive as a real, testable opt-in state, or delete it from the theme and stop faking it in the fixture. Verify the `:visited` underline in a real browser before keeping `--kbq-link-state-visited-border-bottom` at all; if it does not paint, the honest fix is to drop the token and document that visited links differ by text colour only.

## Appendix A — Review Methodology

Findings were gathered by reading every file in the package (`link.component.ts`, `_link-theme.scss`, `link-tokens.scss`, both spec files, both guides, both example stubs, the fixture and the module), then cross-checking each candidate against five independent sources: the **compiled CSS bundle** in `dist/`, which is what turned the print finding from a suspicion into a certainty; the **API guard report** and `tools/api-extractor/config.json`; **every in-repo consumer** found by grepping `kbq-link`, `kbq-link__text`, `kbq-link_external` and `kbq-text-with-dot` across `packages/` and `apps/` (30 files, 118 + 42 + 18 occurrences); the **live design-token set** at `@koobiq/design-tokens/web/new/css-tokens-{light,dark}.css`, with contrast ratios computed from the OKLCH values by explicit sRGB conversion and alpha compositing rather than estimated; and **git history** (15 commits). Consumer workarounds are what upgraded four candidates from opinions to confirmed defects — in each case someone had already written the patch locally and nobody had filed the bug.

Refuted during verification:
- **"The link tokens are undefined and silently compute to nothing"** — refuted. All twelve upstream tokens the theme consumes (`--kbq-foreground-theme`, `--kbq-line-theme-fade`, `--kbq-foreground-visited`, `--kbq-line-visited-fade`, `--kbq-line-visited`, the four `--kbq-states-foreground-*`, `--kbq-states-line-focus-theme`, `--kbq-states-foreground-disabled`, `--kbq-states-line-disabled`) are defined in both `css-tokens-light.css` and `css-tokens-dark.css`.
- **"The focus outline fails WCAG 1.4.11 non-text contrast"** — refuted. `--kbq-states-line-focus-theme` composited over the page background measures 3.28:1 (light) and 3.94:1 (dark), both above the 3:1 threshold. The 1.56:1 figure against the link glyph colour is not the comparison the criterion asks for: the element background is transparent, so the outline borders the page background on both sides.
- **"Missing `role`/`aria-*` is an AXE failure and therefore P0 under AGENTS.md"** — refuted as an *automated* failure. axe-core has no rule for a `<span tabindex="0">` carrying no role, nor for an invalid `disabled` attribute on an anchor. All four accessibility findings are WCAG judgements corroborated by consumer workarounds, and are filed P1 on those grounds rather than P0.
- **"`link.component.spec.ts:30` reads `attributes.tabIndex` in camelCase and should throw"** — refuted. A `node -e` probe against this workspace's jsdom resolves both `attributes.tabIndex` and `attributes.tabindex` to the same `Attr`. The assertion is stylistically fragile but works.
- **"The `toObservable(...)` subscription in the constructor leaks because it has no `takeUntilDestroyed`"** — refuted as a leak. `toObservable` registers its own `DestroyRef.onDestroy` teardown for the underlying effect, and nothing emits after destruction. The defect on that line is timing, not lifetime — filed as LNK-BUG-01.
- **"`examples.link.*.md` are broken because they embed one example while fourteen exist"** — refuted. `structure.ts:705` sets `hasExamples: true`, and the repo convention is that the Examples tab is *disjoint* from the guide; `link-with-caption` is precisely the one example the guide does not embed, so the file is correct as written.
- **"Whitespace text nodes break `updateClassModifierForIcons`"** — refuted for template-authored markup. `getNodesWithoutComments` (`core/utils/utils.ts:28-32`) filters comment nodes only, so whitespace text nodes would shift `findIndex` and suppress `.kbq-icon_left` — but the workspace nowhere overrides `preserveWhitespaces`, so Angular's default removal of whitespace-only text nodes applies and the query sees element nodes only. The real defects in that method are the single-child bail-out and the query mismatch, filed under LNK-ARCH-01.

Corrected on verification:
- **LNK-CSS-01** was first drafted as "the print styles may not be specific enough". Reading the compiled bundle (`dist/e2e/browser/styles-VY327GDA.css:13763-13773`) showed the emitted selector is a descendant combinator that cannot match at all, so the finding moved from a specificity worry to a fully dead feature and the severity rose to P1 — it is now the headline.
- **LNK-A11Y-04** was first drafted as "link text fails colour contrast". Computing the ratios showed both link colours comfortably clear 4.5:1 against the background (5.11:1 light, 6.08:1 dark); the actual failure is the 2.69:1 / 2.24:1 link-versus-body-text ratio, and only for the two variants that suppress the underline. Scope narrowed, evidence quantified.
- **LNK-A11Y-03** was first drafted against `KbqLink.focus()` calling native `.focus()` instead of `focusVia`. That is real but minor, and is folded into the fix; source verification showed the larger defect is the unconditional `outline: none` paired with a directive-only ring class, which strands every consumer that applies `.kbq-link` as a plain string — the library's own Markdown renderer included.
