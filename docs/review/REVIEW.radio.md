# Koobiq `radio` Component — Code Review & Improvement Plan

> Scope: `packages/components/radio` (group directive + button component, template, tokens, theme, SCSS, Jest spec, e2e fixture + Playwright spec, user guides, API guard report, all 5 docs examples, dev app, in-repo consumers) · Commit `b665e503` · 2026-08-28
> Generated by a multi-dimension review (architecture, RxJS/lifecycle, correctness, accessibility, public API/types, styles, tests, docs) with manual verification of every finding against the source, the in-repo consumers, `tsconfig.json`, `playwright.config.ts` and the CDK sources in `node_modules`. 15 findings confirmed (P0×0, P1×3, P2×7, P3×5); 6 candidate findings refuted or corrected during verification (see Appendix A). This document is a review + roadmap; no source is modified by it.

---

## 1. Executive Summary

`KbqRadio` is a 562-line port of Angular Material's pre-MDC radio, carried forward through the Angular 19 and 20 migrations without a semantic pass. It renders a real `<input type="radio">` and delegates arrow-key navigation and roving focus entirely to the browser's native radio-group behaviour — which is a defensible design, but it makes the `name` attribute the single load-bearing contract in the component, and that contract is not honoured consistently.

- **Two radio buttons used outside a `kbq-radio-group` un-check each other across the entire application.** `KbqRadioButton` registers a listener on the CDK's app-global `UniqueSelectionDispatcher` (`providedIn: 'root'`, `unique-selection-dispatcher.mjs:41`) that compares `name === this.name` (`radio.component.ts:478`). A group-less button never assigns `name`, so the comparison is `undefined === undefined` — always true. Checking one group-less radio silently un-checks every other group-less radio in the app, in unrelated routes, overlays and dialogs. The DOM disagrees: the HTML radio-group rules require a non-empty `name`, so the native inputs are correctly independent while the component's own state is not (RAD-BUG-01).
- **`role="radiogroup"` never gets an accessible name, and the library ships no way to give it one.** The host block hard-codes `role: 'radiogroup'` (`radio.component.ts:56`) and stops there — no `aria-labelledby`, no `aria-label`, no `kbq-label` integration. All seven group labels in the library's own published examples are rendered as detached `<div class="kbq-form__label">` siblings (`radio-overview-example.ts:16, 30`, `radio-style-example.ts:17, 31`, `radio-content-example.html:4, 18`, `radio-group-example.ts:13`), so every documented usage produces an unnamed radiogroup (RAD-A11Y-01).
- **The projected `<kbq-hint>` lives inside the `<label>`, so the hint is swallowed into the radio's accessible name instead of describing it.** `radio.component.html:1, 26` puts `<ng-content select="kbq-hint" />` inside the wrapping label, which makes `radio-multiline-example.ts:18` announce a 140-character name per option. `KbqHint`'s own JSDoc says its `id` exists to be "Referenced by the `aria-describedby` of the form field control" (`hint.ts:22`) — radio is the one consumer that hard-wires it into the name instead (RAD-A11Y-02).
- **The `ControlValueAccessor` — the group's entire reason to exist — has zero test coverage.** The Jest spec has 17 cases (`radio.spec.ts`), imports `FormsModule` and `ReactiveFormsModule`, and never binds `ngModel` or `formControl` in either host. `writeValue`, `registerOnChange`, `registerOnTouched` and `setDisabledState` are never invoked; neither is `focus()`, keyboard interaction, or any ARIA assertion. The one in-repo product consumer, `time-range-editor.html:2`, drives the group entirely through `[formControl]` (RAD-TEST-01).
- **Two smaller contract failures with visible in-repo evidence.** `[name]` is a documented public input on the button (`radio.component.ts:426-429`) that `ngOnInit` unconditionally overwrites with the group's name (`:489`); the dev app binds it at `template.html:45` and `:87` and gets nothing (RAD-BUG-03). And `.kbq-radio-label` has no `position` (`radio.scss:23-32`), so the `.cdk-visually-hidden` input — `position: absolute; left: 0` — escapes to whatever positioned ancestor happens to be up the tree; the sibling `checkbox` fixes exactly this with a load-bearing comment at `checkbox.scss:28-29` (RAD-CSS-01).

Genuine strengths worth preserving: the component builds on a real native `<input type="radio">` rather than a `div` with hand-rolled key handling, which is why arrow-key selection, group traversal and the roving tab stop all work correctly for free; `OnPush` plus an explicit `markForCheck()` protocol between group and buttons; a fully token-driven theme (all 20 colour tokens resolve in both `css-tokens-light.css` and `-dark.css`) with a complete error palette; a Playwright fixture covering 24 state combinations across two themes; and the selection-model logic itself — the interplay of `checked`, `value`, `selected` and the dispatcher — is careful and, once the `name` contract holds, correct. The gap is not in the state machine; it is in what the component tells the platform and assistive technology about itself.

## 3. Prioritized Findings (deduplicated, verified)

### P0 — Release blockers

None.

### P1 — High

**RAD-BUG-01 · Radio buttons used outside a group share `name === undefined` and un-check each other application-wide** — `radio.component.ts:426-429, 429, 467-482, 484-491`, `node_modules/@angular/cdk/fesm2022/unique-selection-dispatcher.mjs:20-24, 41`.
`KbqRadioButton`'s constructor registers a listener on the CDK `UniqueSelectionDispatcher`: `if (id !== this.id && name === this.name) { this.checked = false; }` (`:478-480`). The dispatcher is `providedIn: 'root'` (`unique-selection-dispatcher.mjs:41`) and `notify()` fans out to *every* registered listener with no scoping whatsoever (`:20-24`) — the `name` comparison inside the listener is the only isolation mechanism. `name` is declared as a bare `@Input() name: string;` with no initializer (`:429`) and is assigned exactly once, inside `ngOnInit`, and only when a parent group exists (`:484-490`). A `<kbq-radio-button>` written without a `kbq-radio-group` therefore keeps `name === undefined` for its entire lifetime, and `undefined === undefined` is `true`. Checking one such button fires `this.radioDispatcher.notify(this.id, this.name)` (`:337`) and un-checks every other group-less radio button anywhere in the running application — a different route, a modal, a popover, a lazily-loaded feature. The bug is invisible in this repo only because the Jest spec's `DisableableRadioButton` host (`radio.spec.ts:339-351`) instantiates exactly one group-less button; add a second and the suite reproduces it. Note the asymmetry with the platform: the HTML radio-group rules require a *non-empty* `name` for two radios to belong to the same group, so the native `<input>` elements underneath are correctly independent while the component's own `checked` state is not — the DOM and the component disagree about what a group is.
**Fix:** give each button a fallback identity instead of `undefined`. Either default the field — `@Input() name: string = this.uniqueId;` — or, better, guard the listener: `if (id !== this.id && name === this.name && name != null) { this.checked = false; }`, and in `ngOnInit` use `this.name = this.radioGroup?.name ?? this.name ?? this.uniqueId;` so a group-less button falls back to its own unique id and a grouped one still inherits (see RAD-BUG-03 for the inheritance half). Guard it with a Jest case that mounts two independent `<kbq-radio-button>`s with no group, checks the first, checks the second, and asserts the first is *still* checked — that assertion fails today.

**RAD-A11Y-01 · `role="radiogroup"` never receives an accessible name, and the component offers no way to supply one** — `radio.component.ts:52-62` (host block), consumers `radio-overview-example.ts:16, 30`, `radio-style-example.ts:17, 31`, `radio-content-example.html:4, 18`, `radio-group-example.ts:13`, `time-range-editor.html:2-74`.
The group host block hard-codes `role: 'radiogroup'` and two layout classes and binds nothing else (`:55-60`). There is no `aria-label` input, no `aria-labelledby` input, no `kbq-label` content query, and no integration with `KbqFormFieldControl` the way form-field-based controls get one. A `radiogroup` is not a name-from-content role, so unless a consumer hand-writes `aria-labelledby` on the element, the group reaches assistive technology as an unnamed grouping: a screen-reader user hears "radio button, 1 of 5, William Anderson" with no indication of *what* is being chosen. The evidence that this is not hypothetical is that **every published example does it wrong in the same way**: all four example files render the group's visible label as a plain sibling `<div class="kbq-form__label">Normal</div>` immediately before the group (7 occurrences across the four files), with no `id`/`aria-labelledby` pair. A grep for `aria-` across every `kbq-radio-group` call site in `packages/` and `apps/` returns nothing. The one product consumer is worse: `time-range-editor.html:2-74` puts two `kbq-form-field`s, two datepickers and two timepickers *inside* the radiogroup (`:25-71`), so the unnamed group also owns six controls that are not radios. Be precise about the claim: axe-core ships no default rule requiring an accessible name on `role="radiogroup"`, so this is a WCAG 1.3.1 / 3.3.2 judgement backed by seven wrong examples, not an automated AXE failure — which is exactly why it has survived unnoticed.
**Fix:** add to `KbqRadioGroup` an `ariaLabel`/`ariaLabelledby` pair sourced through `kbqInjectA11yLocaleConfiguration()` for any default text, bound in the host block as `'[attr.aria-label]': 'ariaLabel() || null'` and `'[attr.aria-labelledby]': 'ariaLabelledby() || null'`. Then fix the examples: give each `kbq-form__label` div an `id` and point the group at it — `<div id="radio-size-label" class="kbq-form__label">Normal</div><kbq-radio-group aria-labelledby="radio-size-label">`. Prefer this over inventing a `kbq-label` projection, which would change the layout the design already specifies. Guard with a Jest case asserting `getAttribute('aria-labelledby')` round-trips, and add a `jest-axe` run over a labelled and an unlabelled group so the difference is visible in CI. For `time-range`, move the date/time block out of the radiogroup element and keep the radios alone inside it.

**RAD-A11Y-02 · The projected `<kbq-hint>` sits inside the `<label>`, so the hint becomes part of the radio's accessible name instead of its description** — `radio.component.html:1, 21-27`, `packages/components/form-field/hint.ts:22-23`, consumers `radio-content-example.html:22, 27, 32, 37, 42`, `radio-multiline-example.ts:18`, `components-dev/radio/template.html:15, 24, 35, 57, 67`.
`radio.component.html:1` opens a `<label class="kbq-radio-label" [attr.for]="inputId">` that wraps the whole component, and `:26` places `<ng-content select="kbq-hint" />` inside it, next to the main `<ng-content />` at `:23`. The accessible name of a labelled `<input>` is the label's text content, so the hint text is concatenated into the name rather than exposed as a description. In the library's own "Text with Caption" example that turns five options into names like "William Anderson Lawyer" (`radio-content-example.html:20-23`); in `radio-multiline-example.ts:16-19` each option's accessible name becomes the label plus a 140-character sentence, announced in full on every arrow-key move through the group. This is not a subtlety the library is unaware of — `KbqHint` documents its own `id` input as "Unique ID for the hint. Referenced by the `aria-describedby` of the form field control" (`hint.ts:22-23`), and `kbq-form-field` uses it exactly that way. Radio is the outlier that projects the same component into a name-forming position. Ten in-repo call sites (five docs-example, five dev-app) are affected, plus every e2e cell with `hint: true` (`e2e.ts:92-110`, 12 of 24 cells).
**Fix:** keep the DOM layout — moving the hint out of the label would break `.kbq-radio__text-container`'s flex column (`radio.scss:86-89`) — and override the name instead. Give the text span a stable id (`<span class="kbq-radio__text" [id]="inputId + '-label'">`), query the projected hint with `contentChild(KbqHint)`, and on the input bind `[attr.aria-labelledby]="inputId + '-label'"` plus `[attr.aria-describedby]="hint()?.id() ?? null"`. An explicit `aria-labelledby` wins over the wrapping label, so the name becomes just the option text and the hint arrives as a description that AT can defer or skip. Guard with a Jest case that renders a button with a `kbq-hint` and asserts `input.getAttribute('aria-labelledby')` resolves to the option text only, and that `aria-describedby` resolves to the hint text.

### P2 — Should fix

**RAD-A11Y-03 · `focus()` leaves no visible focus ring, and the group cannot be focused at all** — `radio.component.ts:493-499, 506-509`, `_radio-theme.scss:28-34, 40-46`.
`KbqRadioButton.focus()` calls `this.inputElement().nativeElement.focus()` — a bare native focus. `ngAfterViewInit` monitors the host with `focusMonitor.monitor(this.elementRef, true)` (`:494`), so CDK classifies the resulting focus event; with no preceding input event it resolves to origin `program` and stamps `cdk-program-focused`, not `cdk-keyboard-focused`. The theme keys the entire focus indicator off `.cdk-keyboard-focused` — both the ring (`_radio-theme.scss:28-34`) and its checked variant (`:40-46`), backed by 8 dedicated tokens (`radio-tokens.scss:22-29, 49-56`). The result is that the only public API for moving focus to a radio produces focus with no visible indicator, which is a WCAG 2.4.7 problem for the flows that need it most: "scroll to and focus the first invalid control" after a failed submit. Compounding it, `KbqRadioGroup` exposes no `focus()` at all (`radio.api.md:81-119`), so there is no supported way to move focus to a radio *group* — a caller must reach into `groupInstance.radios.first.focus()` and then discover it produces no ring. Nothing in `packages/` calls `KbqRadioButton.focus()` today, which is why this has not surfaced.
**Fix:** route the programmatic focus through the monitor so the origin is honoured: `focus(origin: FocusOrigin = 'program'): void { this.focusMonitor.focusVia(this.inputElement(), origin); }` (see `project_kbq_focus_ring_mechanism`). Add `focus(origin?: FocusOrigin)` to `KbqRadioGroup` that forwards to the checked radio, or to the first enabled one when nothing is checked — which mirrors the browser's own roving rule. Guard with a Jest case asserting the host carries `cdk-keyboard-focused` after `focus('keyboard')` and `cdk-program-focused` after `focus()`; add a `cdk-keyboard-focused` row to the e2e grid (see RAD-TEST-01) so the 8 focus tokens finally have a screenshot.

**RAD-A11Y-04 · The group communicates neither required nor invalid state; the error appearance is a per-button `[color]` opt-in** — `radio.component.ts:52-62, 141-155`, `radio.component.html:10`, `_radio-theme.scss:76-80`, consumer `radio-style-example.ts:33-51`.
The group accepts `required` (`:144-152`) and forwards it to each button's getter (`:402-405`), which reaches the DOM only as the native `required` property on the visually hidden input (`radio.component.html:10`). The `radiogroup` element itself never gets `aria-required="true"`, which is where AT expects to hear it for a group, and there is no `aria-invalid` anywhere in the package. Meanwhile the component ships a complete error palette — 27 `--kbq-radio-error-*` tokens (`radio-tokens.scss:34-60`) driving a full `.kbq-error` branch (`_radio-theme.scss:76-80`) — that is reachable only by setting `[color]="ThemePalette.Error"` **on every individual button**, because the group has no `color` passthrough. The library's own style example demonstrates the cost: `radio-style-example.ts:33-51` repeats `[color]="themePalette.Error"` five times to turn one group red. So the component has a rich invalid *appearance* with no programmatic counterpart and no connection to the form state that would justify showing it.
**Fix:** two moves. (1) Bind `'[attr.aria-required]': "required ? 'true' : null"` on the group host, and `'[attr.aria-invalid]': "errorState ? 'true' : null"` once an error state exists. (2) Add a `color` input on `KbqRadioGroup` that the buttons read as a fallback, exactly as `labelPosition` already does (`radio.component.ts:417-420`), so one binding colours the group; then simplify `radio-style-example.ts` to a single group-level binding. If group-level validation is wanted rather than manual colouring, wire `ErrorStateMatcher` into `KbqRadioGroup` the way form-field controls do and derive both `.kbq-error` and `aria-invalid` from it — that is the larger change and should be a deliberate decision, not a side effect.

**RAD-BUG-02 · The native `<input type="radio">` carries no `value` and an auto-generated `name`, so native form submission is meaningless** — `radio.component.html:2-14`, `radio.component.ts:176-177, 344-367`.
The template binds `[attr.name]`, `[checked]`, `[disabled]`, `[id]`, `[required]` and `[tabIndex]` on the native input — and never `value`. An `<input type="radio">` with no `value` attribute submits the literal string `"on"`. The `name` it submits under is `kbq-radio-group-${nextUniqueId++}` (`:177`) unless the consumer overrides it, i.e. a counter-derived string that changes between renders and between application loads. A plain `<form>` POST containing a Koobiq radio group therefore transmits `kbq-radio-group-3=on` — the field name is unstable and the payload does not identify which of the five options was chosen. This matters because the component *chose* to render a real native input; that choice is what makes arrow-key navigation and the roving tab stop work for free (see Appendix A), and it simultaneously sets the expectation that the control participates in the form. Every in-repo consumer uses `ngModel` or `formControl` (`time-range-editor.html:2`, `components-dev/radio/template.html:11`, `timepicker-variations-example.html:2`), so nothing in the repo is currently broken by it — but the published surface promises something it does not deliver. A secondary consequence: `required` propagates to the native input (`radio.component.html:10`), so an unselected required group triggers native constraint validation and the browser anchors its validation bubble to a 1-pixel clipped input whose position is itself unreliable (see RAD-CSS-01).
**Fix:** bind the value through: `[attr.value]="value"` on the input, guarding the non-string case — `KbqRadioButton.value` is `any` (`:347-350`), so serialize with `value == null ? null : String(value)` and document that native submission only round-trips string-like values. Leave the auto-generated `name` as a fallback but state in the guide that a group intended for native submission must set `[name]` explicitly. Guard with a Jest case that renders a group inside a `<form>`, checks the second option, and asserts `new FormData(form).get(name)` equals the option's value rather than `"on"`.

**RAD-BUG-03 · `[name]` on a radio button inside a group is a public input that `ngOnInit` silently discards** — `radio.component.ts:426-429, 484-491`, consumer `components-dev/radio/template.html:45, 87`.
`name` is a documented public input — "Analog to HTML 'name' attribute used to group radios for unique selection" (`:426-427`) — and it appears in the API report (`radio.api.md:38`). But `ngOnInit` runs after input binding and unconditionally overwrites it whenever a group is present: `this.name = this.radioGroup.name;` (`:489`). Because Angular only re-applies an input when its bound expression changes, a constant binding is never re-applied, so the consumer's value is gone for good. The dev app is the proof: `components-dev/radio/template.html:45` and `:87` write `[name]="data.value"` on buttons inside a `<kbq-radio-group>`, evidently intending each button to form its own selection group (both are `[disabled]="true"` and one is pre-checked), and the binding does nothing at all. The reverse direction is also silent — a group whose `name` is changed after content init writes the new name into the buttons' fields without refreshing their views (RAD-LIFE-01) — so `name` is unreliable in both directions.
**Fix:** make the inheritance conditional rather than unconditional: `this.name ??= this.radioGroup.name;` at `:489`, so an explicitly bound name wins and an unbound one still inherits. Combine with the RAD-BUG-01 fallback so the three cases — explicit name, inherited name, no group — each resolve to a distinct non-`undefined` value. Then either delete the dead `[name]` bindings from `components-dev/radio/template.html:45, 87` or keep them and let the dev app demonstrate the now-working behaviour. Guard with a Jest case asserting that `<kbq-radio-button name="custom">` inside a group still reports `name === 'custom'` after `detectChanges()`.

**RAD-CSS-01 · `.kbq-radio-label` is unpositioned, so the visually hidden input escapes to an arbitrary ancestor** — `radio.scss:19-32`, `radio.component.html:2-5`, `packages/components/core/styles/common/_visually-hidden.scss:12, 26-30`; sibling precedent at `packages/components/checkbox/checkbox.scss:28-29`.
The native input carries `cdk-visually-hidden` (`radio.component.html:5`), which is `position: absolute` with `left: 0` (`_visually-hidden.scss:12, 30`). Its containing block is the nearest positioned ancestor. `.kbq-radio-label` sets `display: inline-flex` and no `position` (`radio.scss:23-32`), and the host `.kbq-radio-button` is also unpositioned (`:19-21`); the only positioned box in the component, `.kbq-radio-label-content` (`:37`), is the input's *sibling*, not its ancestor. So the hidden input resolves its `left: 0` against whatever positioned element happens to be up the page — a card, an overlay pane, or the document. The CDK source calls this hazard out in a comment on the very rule: `left` "was chosen here, because it's the least likely to break overrides where the element might have been positioned" (`_visually-hidden.scss:26-30`). The sibling `checkbox` component — same DOM shape, same hidden input — fixes it explicitly and says so: `// required for '.cdk-visually-hidden' input to be positioned correctly` followed by `position: relative` (`checkbox.scss:28-29`). Radio has the identical structure and the fix is simply absent. Visible symptoms are horizontal focus-scroll jumps in scrollable containers and a native validation bubble (RAD-BUG-02) anchored far from the control it belongs to.
**Fix:** add `position: relative;` to `.kbq-radio-label` (`radio.scss:23`) with the same explanatory comment `checkbox.scss:28` carries, so the next reader does not delete it as redundant. This changes no visual geometry — `.kbq-radio-label-content`'s absolutely positioned circles already resolve against their own `position: relative` parent — so the existing Playwright baselines should be byte-identical; verify with `yarn run e2e:docker` and treat any diff as a real regression rather than approving it.

**RAD-LIFE-01 · The group's `name` setter mutates OnPush children without marking them for check** — `radio.component.ts:76-79, 231-235, 272-274`, `radio.component.html:6`.
`KbqRadioGroup` has an explicit protocol for pushing state into its OnPush children: `markRadiosForCheck()` (`:231-235`) walks the `QueryList` and calls `radio.markForCheck()`. The `labelPosition` (`:91`), `disabled` (`:136`) and `required` (`:151`) setters all use it. The `name` setter does not — it calls `updateRadioButtonNames()` (`:78`), which writes `radio.name = this.name` on each child (`:273`) and returns. Writing a plain field on a child component does not mark that component's view dirty, and `name` reaches the DOM only through `[attr.name]="name"` (`radio.component.html:6`). So changing `[name]` on a group after content init updates the buttons' TypeScript fields — which is enough for the `UniqueSelectionDispatcher` comparison to keep working — while leaving the rendered `name` attribute stale. Since native radio-group membership, arrow-key traversal and the roving tab stop are all keyed on that attribute (see Appendix A), the DOM and the component drift apart precisely where it matters most. No in-repo consumer changes `[name]` at runtime (`components-dev/radio/template.html:33, 75` bind a constant), so this is latent rather than currently breaking.
**Fix:** call `this.markRadiosForCheck()` at the end of `updateRadioButtonNames()` (`:274`), or simply have the `name` setter call both helpers, matching the other three setters. Guard with a Jest case that binds `[name]` to a component field, changes it, runs `detectChanges()`, and asserts the rendered `input.getAttribute('name')` — not the instance field — reflects the new value.

**RAD-TEST-01 · The `ControlValueAccessor`, keyboard and ARIA surfaces are entirely untested, and the e2e grid never captures focus** — `radio.spec.ts:1-351` (17 cases), `e2e.ts:70-111`, `e2e.playwright-spec.ts:9-17`, `playwright.config.ts:101`.
The spec imports `FormsModule` and `ReactiveFormsModule` in both hosts (`:313, 340`) and never uses them: neither host template binds `ngModel` or `formControl` (`:314-328, 341-343`). Consequently `writeValue`, `registerOnChange`, `registerOnTouched`, `setDisabledState` and `touch()` — the five methods that make `KbqRadioGroup` a form control, and the reason `time-range-editor.html:2` can use `[formControl]` at all — have no coverage; the suite reaches the same state by assigning `groupInstance.value` directly (`:176, 207, 257`). Also untested: keyboard interaction of any kind, every ARIA attribute including the hard-coded `role="radiogroup"`, `focus()`, `inputId`, the `labelPosition` DOM class (`:70-84` asserts the instance property, never `.kbq-radio-label-before`), and the group-less path beyond a single `disabled` toggle. On the visual side, the e2e fixture builds a 24-cell grid over size × label position × hover × hint × disabled (`e2e.ts:70-111`) but has no focused row, so the 8 focus tokens (`radio-tokens.scss:22-29, 49-56`) and both `.cdk-keyboard-focused` theme branches (`_radio-theme.scss:28-34, 40-46`) are never screenshotted. Note that `playwright.config.ts:101` sets `reducedMotion: 'reduce'` for every context, so the committed baselines capture the reduced-motion rendering — relevant if a transition is ever added to the ring.
**Fix:** add a `RadioGroupWithNgModel` host (`[(ngModel)]`) and a `RadioGroupWithFormControl` host, and assert the full round trip: model → `writeValue` → checked radio; click → `registerOnChange` callback → model; `control.disable()` → `setDisabledState` → every native input disabled; blur → `registerOnTouched`. Add keyboard cases driving `ArrowDown`/`ArrowRight` on the checked input and asserting the group value moves. ### P3 — Nice to have / hygiene

**RAD-API-01 · `isFocused` is a published input that nothing reads** — `radio.component.ts:445`, `tools/public_api_guard/components/radio.api.md:33-34, 66`.
`readonly isFocused = input<boolean>(false);` is declared on `KbqRadioButton`, appears in the API report as `// (undocumented) readonly isFocused: i0.InputSignal<boolean>` and in the component declaration's input map (`radio.api.md:66`). **RAD-API-02 · Type lies across the public surface, and 14 stale "Skipped for migration" TODOs** — `radio.component.ts:69-70, 82-83, 95-96, 113-114, 127-128, 142-143, 316-317, 345-346, 370-371, 386-387, 400-401, 415-416, 427-428, 448-449, 399-412, 442-443, 467-468`, `tools/public_api_guard/components/radio.api.md:19, 31, 57`.
Three distinct type problems, all visible in the API report. (1) `radioGroup: KbqRadioGroup;` (`:443`) is declared non-nullable but assigned from `inject(KbqRadioGroup, { optional: true })!` (`:468`) — the non-null assertion launders a genuine `null`. The class itself knows better and guards with `this.radioGroup != null` in four places (`:327, 356, 374, 485`), so the type contradicts the code, and it defeats `strictNullChecks` for every consumer reading `radio.radioGroup`. (2) As a direct consequence, `get required(): boolean` (`:403-405`) returns `this._required || (this.radioGroup && this.radioGroup.required)`; for a group-less button `_required` is `undefined` (`:412`, declared without an initializer) and `this.radioGroup` is `null`, so the getter returns `null` through a `boolean` signature — TypeScript cannot catch it precisely because of (1). (3) `inputElement` is `viewChild.required<ElementRef>('input')` with no element generic, surfacing as `Signal<ElementRef<any>>` in the report (`radio.api.md:31`), and `KBQ_RADIO_GROUP_CONTROL_VALUE_ACCESSOR` is typed `any` (`radio.api.md:19`). **Fix:** type the injection honestly — `radioGroup: KbqRadioGroup | null` — then let the compiler find the real null paths; that also forces `required` to be written as `this._required || this.radioGroup?.required || false`. Narrow `inputElement` to `viewChild.required<ElementRef<HTMLInputElement>>('input')` and give `KBQ_RADIO_GROUP_CONTROL_VALUE_ACCESSOR` an explicit `Provider` type. ## Appendix A — Review Methodology

Findings were gathered by reading the complete package — `radio.component.ts` (562 lines), its template, all three SCSS files, the Jest spec, the e2e fixture and Playwright spec, both guides and both example stubs — then cross-checking each candidate against five independent sources: the workspace compiler settings (`tsconfig.json:114-118`), the API guard report (`tools/public_api_guard/components/radio.api.md`, 133 lines), the CDK sources the component depends on (`node_modules/@angular/cdk/fesm2022/unique-selection-dispatcher.mjs`, `packages/components/core/styles/common/_visually-hidden.scss`), the design-token files, and every in-repo call site of `<kbq-radio-group>`/`<kbq-radio-button>` found by grep across `packages/` and `apps/`. Consumer evidence is what carried RAD-A11Y-01, RAD-A11Y-02, RAD-BUG-03 and RAD-CSS-01 from opinion to confirmed defect: in each case the wrong pattern is already committed to the tree, in the library's own examples, dev app or a sibling component's compensating fix. All 20 colour tokens the theme references were verified present in both `css-tokens-light.css` and `css-tokens-dark.css`, and the size tokens in `css-tokens.css` (`--kbq-size-l: 16px`, `--kbq-size-border-width: 1px`).

Refuted during verification:
- **"Every radio input renders `tabindex="0"` (`radio.component.html:11`, `radio.component.ts:388-397`), so a five-option group is five tab stops instead of one"** — refuted. Browsers implement the roving convention for `<input type="radio">` in radio-specific focus logic that keys off radio-group membership, not off the author's tabindex: an unchecked radio is skipped for sequential navigation whenever another radio in its group is checked, and the group is only left once. A non-negative author `tabindex` does not defeat that rule. The explicit `tabindex="0"` is therefore inert for tab order; what the roving behaviour *does* depend on is the `name` attribute, which is why RAD-BUG-01, RAD-BUG-03 and RAD-LIFE-01 are filed and this one is not.
- **"The package implements no keyboard navigation at all"** — refuted as a defect, though true as a statement about the source: a grep for `keydown`, `KeyboardEvent`, `FocusKeyManager` and `focusVia` across `packages/components/radio/` returns nothing. The component renders a real `<input type="radio">` with a shared `[attr.name]` (`radio.component.html:2-6`), so the browser supplies arrow-key movement and selection natively, and `onInputChange` (`radio.component.ts:534-553`) picks up the resulting `change` event, updates the group and calls the CVA callback. Arrow keys work — for radios that share a non-empty `name`.
- **"The `focusMonitor.monitor()` subscription in `ngAfterViewInit` (`radio.component.ts:494-498`) is never unsubscribed and leaks"** — refuted. `ngOnDestroy` calls `focusMonitor.stopMonitoring(this.elementRef)` (`:502`), which completes the monitor's subject and terminates the subscription; the dispatcher listener is likewise released via `removeUniqueSelectionListener()` (`:503`).
- **"Consumers override `.kbq-radio-group`'s layout, so the default is wrong"** — refuted. The six overrides found (`layout-flex-overview-example.css:1-9` and four siblings, `timepicker-variations-example.css:1-7`) only switch `inline-flex` to `flex` and add example-page margins; they re-declare `flex-direction: column`, which the component already sets (`radio.scss:5-7`). The vertical-only layout is deliberate — `radio.en.md:30` explicitly redirects horizontal layouts to Button Toggle.
- **"The `--kbq-radio-*` tokens do not all resolve"** — refuted. Every one of the 20 semantic colour references in `radio-tokens.scss` is defined in both `@koobiq/design-tokens/web/new/css-tokens-light.css` and `-dark.css`. The genuine token problems are duplication and two unreferenced declarations, filed as RAD-STYLE-01.

Corrected on verification:
- **RAD-A11Y-01** was first drafted as an automated AXE failure and therefore a P0 under the AGENTS.md accessibility mandate. axe-core ships no default rule requiring an accessible name on `role="radiogroup"`, so the claim was rewritten as a WCAG 1.3.1 / 3.3.2 judgement and kept at P1 on the strength of seven wrong labels in the library's own published examples. The related observation that `time-range-editor.html:2-74` nests six non-radio form controls inside the radiogroup was folded in as context rather than filed as a separate automated failure, because axe's `aria-required-children` only requires that at least one `radio` be present, which it is.
- **RAD-A11Y-03** was drafted as "`focus()` is broken" at P1. It does move focus correctly; what is missing is the visible indicator (the theme keys the ring off `cdk-keyboard-focused` only) and a group-level entry point. Narrowed and dropped to P2.
- **RAD-BUG-02** was drafted at P1 as "native form submission is broken". Every in-repo consumer drives the group through `ngModel` or `formControl`, so nothing currently ships broken; the defect is that the component renders a real native input and does not honour what that implies. Dropped to P2 with the impact stated honestly.
