# Koobiq `tabs` Component — Code Review & Improvement Plan

> Scope: `packages/components/tabs` (5 components + 4 directives, paginated header base class, tokens, theme, SCSS, 4 Jest specs, e2e fixture + Playwright spec, user guides, API guard report) · Commit `b665e503` · 2026-08-28
> Generated by a multi-dimension review (architecture, RxJS/lifecycle, correctness, accessibility, performance, public API/types, styles, tests, docs) with manual verification of every finding against the source, the in-repo consumers, the docs examples, `tsconfig.json` and `playwright.config.ts`. 15 findings confirmed (P0×1, P1×3, P2×7, P3×4); 6 candidate findings refuted during verification (see Appendix A). This document is a review + roadmap; no source is modified by it.

---

## 1. Executive Summary

`tabs` is the largest single-purpose package in the library — 5,164 lines across two independent tab implementations that share one base class: `KbqTabGroup` (label + content pairs, `tab-group.component.ts`, 465 lines) and `KbqTabNavBar` (routing-style links, `tab-nav-bar.ts`, 350 lines), both extending or driving `KbqPaginatedTabHeader` (625 lines). It is consumed by `code-block`, the docs application itself and 16 documentation examples.

- **The headline defect is that the primary component ships no ARIA tabs pattern at all.** `tab-group.html` renders `<div class="kbq-tab-label">` and `<kbq-tab-body>` with ids, `tabindex` and click handlers, and **zero** `role`, `aria-selected`, `aria-controls` or `aria-labelledby`. A screen-reader user gets an unlabelled div soup with no way to tell which tab is current or which region it controls. The damning part is that `KbqTabNavBar` in the *same package* implements the full pattern correctly (`tab-nav-bar.ts:88-90, 239-257, 332-341`), and `KbqTabGroup` already computes both id halves (`getTabLabelId`/`getTabContentId`) and binds them — only the six attributes that would connect them are missing (TAB-A11Y-01).
- **Two of the three P1s are single-expression bugs with disproportionate blast radius.** `getTabIndex()` returns `null` for a disabled tab and `0` only for the *selected* one, so a group whose selected tab is disabled — which is the default when the first tab is disabled — has no tab with `tabindex="0"` and is completely unreachable by <kbd>Tab</kbd>; two committed e2e fixtures are already in that state (TAB-A11Y-02). And `subscribeToResize()` reads the `vertical` input signal **in the constructor**, before Angular has written any input, so it always early-returns: the resize subscription is never created, the `(window:resize)` host listener feeds a `Subject` nobody is listening to, and the tab-label overflow tooltip is computed exactly once (TAB-BUG-01).
- **`[vertical]` cannot be used as a binding.** The vertical layout comes from `KbqVerticalTabsCssStyler`, a selector-matched directive with a *static* host class; Angular matches attribute selectors against property-binding names, so `<kbq-tab-group [vertical]="false">` still gets `kbq-tab-group_vertical` and can never lose it. `KbqPaginatedTabHeader.vertical` compounds this with a one-way latch that permanently sets `disablePagination = true` (TAB-BUG-02).
- **Half the theme is wired to the wrong token family.** All four `on-surface` branches of `_tabs-theme.scss` call `kbq-tab-item-style(…, on-background)` — one of them carries a `FIXME` admitting it — so the 26 `--kbq-tabs-tab-item-*-on-surface-*` custom properties declared in `tabs-tokens.scss` are never read by anything (TAB-CSS-01).
- **81 Jest cases contain not one ARIA assertion**, the `[tabNavPanel]` path (the only ARIA-wired code in the package) has no test whatsoever, and the visual fixture silently self-destructs: `e2e.ts:244` indexes `labels[4]` of a four-tab group inside one `afterNextRender` callback, throwing before the third state-setup runs, so the committed baselines are missing the vertical icon-only focus rings entirely (TAB-TEST-01, TAB-TEST-02).

Genuine strengths worth preserving: the keyboard model itself is complete and correct — arrows, <kbd>Home</kbd>/<kbd>End</kbd> and manual activation on <kbd>Space</kbd>/<kbd>Enter</kbd>, with `preventDefault` on exactly the right key set (`paginated-tab-header.ts:296-323`) and disabled-item skipping delegated to `FocusKeyManager`, covered by 10 focused specs. Lazy content really is lazy (`KbqTabBodyPortal` attaches on `beforeCentering` and detaches on `afterLeavingCenter`, with a spec proving only the active body is in the DOM). Teardown is disciplined — `takeUntilDestroyed(destroyRef)` throughout the base class, `mouseleave` bound `runOutsideAngular`, passive touch listeners. `KbqTabNavBar` is a genuinely good accessible tablist. And the styling is entirely token-driven with a clean `filled`/`transparent` × `on-background`/`on-surface` matrix — the matrix is simply not plugged in yet.

## 3. Prioritized Findings (deduplicated, verified)

### P0 — Release blockers

**TAB-A11Y-01 · `KbqTabGroup` renders no part of the ARIA tabs pattern, while its own sibling in the same package renders all of it** — `tab-group.html:1-57`, `tab-header.html:1-35`, `tab-body.html:1-13`, `tab-label-wrapper.directive.ts:19-22`; contrast `tab-nav-bar.ts:88-90, 169-176, 239-262, 332-341`.
A grep for `role` and `aria-` across the package returns 17 hits, and **every one of them is in `tab-nav-bar.ts`**. The tab group's markup is: `<kbq-tab-header>` with no role, `<div class="kbq-tab-list__content">` with no role, `<div class="kbq-tab-label" [attr.tabindex] [id]>` with no `role="tab"`, no `aria-selected`, no `aria-controls`, and `<kbq-tab-body [id]>` with no `role="tabpanel"`, no `aria-labelledby`, no `tabindex`. To a screen reader the entire widget is a group of focusable generic containers: the user cannot tell that these are tabs, cannot tell which one is current, and gets no association between the strip and the region it drives. This is a WCAG 4.1.2 (Name, Role, Value) and 1.3.1 (Info and Relationships) failure — note it is a *judgement*, not an automated hit: axe-core does not flag a `div` that simply carries no role, which is precisely why this has survived a full redesign (DS-4761) untouched. Three things make it a blocker rather than a gap. First, **there is no consumer workaround**: the label and body elements are generated by the group's own template, so an application cannot add the attributes without post-hoc DOM surgery. Second, **the plumbing is already complete** — `getTabLabelId(i)` and `getTabContentId(i)` (`tab-group.component.ts:336-343`) exist for exactly this purpose and are already bound at `tab-group.html:22` and `:50`; the only thing missing is the six attributes that would connect the two ids. Third, the package itself proves the team considers this required: `KbqTabNavBar` emits `role="tablist"` when a panel is supplied, `KbqTabLink` emits `role="tab"` + `aria-selected` + `aria-controls` + `aria-disabled`, and `KbqTabNavPanel` emits `role="tabpanel"` + `aria-labelledby` — and `code-block.html:6` and the docs app both rely on it. As a secondary defect on the same surface, `KbqTabLabelWrapper` writes a bare `[attr.disabled]` onto a `<div>` (`tab-label-wrapper.directive.ts:21`), an attribute HTML defines only for form controls and which no assistive technology reads, where `KbqTabLink` correctly writes `aria-disabled` (`tab-nav-bar.ts:172`).
**Fix:** six bindings, no logic change. On `.kbq-tab-list__content` (`tab-header.html:14`) add `role="tablist"` plus `[attr.aria-orientation]="vertical ? 'vertical' : null"` (valid on `role="tablist"`, unlike on `role="group"`). On the label div (`tab-group.html:10-29`) add `role="tab"`, `[attr.aria-selected]="selectedIndex === $index"`, `[attr.aria-controls]="getTabContentId($index)"` and `[attr.aria-disabled]="tab.disabled"`. On `<kbq-tab-body>` (`tab-group.html:46`) add `role="tabpanel"`, `[attr.aria-labelledby]="getTabLabelId($index)"` and `tabindex="0"` so a panel with no focusable content is still reachable. Replace the bare `[attr.disabled]` in `tab-label-wrapper.directive.ts:21` with `aria-disabled` (keep the CSS hook on `.kbq-disabled`, which is what `_tabs-common.scss:44` actually targets — the attribute selector is unused). Guard with Jest cases asserting each attribute and its pairing (`aria-controls` on tab *N* equals the `id` of body *N*), plus a `jest-axe` pass on a rendered group; add the same assertions for the vertical variant so TAB-A11Y-04 cannot regress.

### P1 — High

**TAB-A11Y-02 · A disabled selected tab removes the entire tab strip from the tab order** — `tab-group.component.ts:383-390`, `tab-group.html:14`, `tab-group.component.ts:144-164, 456-464`; reproduced by `e2e.ts:54-58` and `e2e.ts:100-110`.
`getTabIndex()` is three lines: `if (tab.disabled) return null;` then `return this.selectedIndex === index ? 0 : -1;`. It is bound as `[attr.tabindex]` on every label (`tab-group.html:14`), so a disabled tab gets **no** `tabindex` attribute at all — a bare `<div>`, unfocusable — while every non-selected tab gets `-1`. When the selected tab is the disabled one, no element in the strip carries `tabindex="0"` and <kbd>Tab</kbd> skips the whole widget; the only way in is a mouse click on an enabled tab. This is not a contrived configuration: the default selection is index 0 regardless of its disabled state (`getTabIndexToSelect()` → the `activeTab` getter's `default:` branch returns `this.tabs.get(0)`, `tab-group.component.ts:161-163`), so `<kbq-tab-group>` whose first tab is disabled ships in this state. Two committed fixtures are already there — `e2e.ts:100-110` is a single-tab group with `[disabled]="$first"`, and `e2e.ts:54-58` binds `[activeTab]="tabs[2]"` to a `tabId` that does not exist among the two rendered tabs, so the string branch falls back to `tabs.get(0)`, which is `[disabled]="$first"`. The underlying design choice is that the roving `tabindex` tracks *selection* rather than *focus*, which the ARIA APG defines the other way round for manually-activated tablists; that alone is a minor deviation (after arrow-navigating without activating, tabbing away and back returns to the selected tab, losing the focus position), but combined with the `null` for disabled it becomes a total lockout. `KbqTabLink` has the same selection-based shape (`tab-nav-bar.ts:224-230`) but returns `-1` rather than `null`, so the nav bar degrades gracefully where the group does not.
**Fix:** return `-1`, never `null`, for disabled tabs, and key the `0` off the header's `focusIndex` rather than `selectedIndex`: `return tabHeader.focusIndex === index ? 0 : -1`. Because `focusIndex` reads `keyManager.activeItemIndex` and `FocusKeyManager` skips disabled items by default, the `0` then always lands on a focusable tab. Separately, make the default selection skip disabled tabs — in the `activeTab` getter's `default:` branch prefer the first enabled tab — so the initial state is coherent even for consumers who never touch `focusIndex`. Guard with a Jest case asserting that a group whose first tab is disabled still has exactly one element with `tabindex="0"`, and a mutation check: reverting the fix must fail it.

**TAB-BUG-01 · The resize pipeline is dead code — an input signal is read in the constructor** — `tab-group.component.ts:105, 112, 220-223, 225-232, 402-404, 434-446`; consumer `tab-label-wrapper.directive.ts:66-76`.
`subscribeToResize()` opens with `if (!this.vertical()) { return; }` and is called exactly once, from the constructor (`:231`). Angular writes signal inputs *after* the instance is constructed, so `this.vertical()` returns its declared default `false` on every single instantiation, including `<kbq-tab-group vertical>`. The subscription is therefore never created: `resizeSubscription` stays `Subscription.EMPTY` for the component's whole life, and the host listener `'(window:resize)': 'resizeStream.next($event)'` (`:105`) pushes into a `Subject` that has no subscribers — one in-zone window listener per tab group on the page, doing nothing but triggering a change-detection tick per resize event. The user-visible consequence is that `checkOverflow()` runs exactly once, from `ngAfterViewInit` (`:322`), so a vertical tab label that becomes truncated later — window resize, splitter drag, sidebar collapse, a label whose text changes — never gains its tooltip, and one that stops being truncated keeps a stale one (`tab.overflowTooltipTitle` is only ever written by `checkOverflow`, `tab-label-wrapper.directive.ts:67`). That single call is itself misplaced: it mutates `tab.overflowTooltipTitle`, which the *same view* already read this cycle through `[kbqTooltip]="tab.tooltipTitle"` and `[kbqTooltipDisabled]="… !tab.isOverflown"` (`tab-group.html:24-25`), which is the textbook shape for `ExpressionChangedAfterItHasBeenCheckedError` in dev mode — masked today only because the sole environment that exercises it is jsdom, where `scrollWidth` and `clientWidth` are both `0` and the comparison never flips. Note the repo has already condemned this exact pattern elsewhere: the `title-encapsulation` migration removes `KbqTitleDirective.resizeStream` with the rationale that "the directive now injects the CDK `SharedResizeObserver` … so a manual `resizeStream.next(event)` has no counterpart" (`packages/schematics/src/migrations/title-encapsulation/data.ts:7-11, 39-44`).
**Fix:** delete `resizeStream`, the `(window:resize)` host binding and `subscribeToResize()` entirely, and observe the header element with the CDK `SharedResizeObserver` (or `ViewportRuler.change()`) subscribed with `takeUntilDestroyed`, gated on the *current* value of `vertical()` inside the handler rather than at construction — an element observer additionally catches container resizes that no window event reports, which the current design misses even in principle. Move the `checkOverflow()` call out of `ngAfterViewInit` into `afterNextRender` (or follow it with `changeDetectorRef.markForCheck()`) so the write happens outside the checked cycle. Guard with a spec that stubs `scrollWidth > clientWidth` on a label, fires the observer, and asserts the tooltip becomes enabled — and a second that asserts it becomes disabled again when the overflow goes away. Removing the public `resizeStream` is breaking; pair it with a warn-only `ng-update` entry alongside the existing `title-encapsulation` one.

**TAB-BUG-02 · `[vertical]` is unusable as a binding: the layout class comes from a selector-matched directive, and `disablePagination` latches one-way** — `tab-group.component.ts:55-59, 123`, `tab-group.scss:14-24`, `paginated-tab-header.ts:148-164`.
`KbqVerticalTabsCssStyler` matches `kbq-tab-group[vertical]` and applies a **static** host class `kbq-tab-group_vertical` (`tab-group.component.ts:56-58`); that class is the sole source of the vertical layout (`tab-group.scss:14-24`, `tab-nav-bar.scss:30-38`) — grep confirms nothing else ever sets it. Angular matches attribute selectors against property-binding names as well as static attributes, so `<kbq-tab-group [vertical]="isVertical">` matches the styler whatever `isVertical` evaluates to, and the class is applied unconditionally and permanently. Meanwhile the real `vertical` input signal (`:123`) correctly drives `[class.kbq-tab-label_vertical]`, `[class.kbq-tab-label_horizontal]` and `[vertical]` on the header (`tab-group.html:5, 17, 19`). The result for `[vertical]="false"` is an incoherent hybrid: the group is `flex-direction: row` with `overflow-y: auto` on the header container, while the labels and the header itself are in horizontal mode. Nothing in the repo exercises this — the e2e fixture and the dev app both use the static-attribute form (`e2e.ts:113, 120, 133, 178`, `components-dev/tabs/template.html:35`), which is the one case that happens to work. Independently, `KbqPaginatedTabHeader`'s `vertical` setter (`paginated-tab-header.ts:151-158`) sets `disablePagination = true` when true but never restores it when false, so a header that has ever been vertical permanently loses its paginator arrows — and because `disablePagination` is itself a public `@Input` (`:146`), a consumer setting it explicitly on a vertical nav bar gets it silently overwritten depending on binding order.
**Fix:** delete `KbqVerticalTabsCssStyler` and bind the class from the component instead — `'[class.kbq-tab-group_vertical]': 'vertical()'` in the `KbqTabGroup` host block, and the equivalent on `KbqTabNavBar` (which has no `vertical` input of its own today and inherits the setter from the base class). Removing an exported directive is breaking; keep the class exported as a deprecated no-op for one minor with an `ng-update` warn entry, since it is exported from `public-api.ts` and listed in `tabs.api.md:416-421`. In the base class, replace the latch with a derived read — `get disablePagination() { return this._disablePagination || this._vertical; }` — so the flag is never destructively overwritten. Guard with a Jest case that toggles `[vertical]` true→false and asserts both the host class and `showPaginationControls` follow, which fails against today's code in both halves.

### P2 — Should fix

**TAB-A11Y-03 · Focus is dropped when the active tab is removed, and the documented closable-tab recipe cannot be operated from the keyboard** — `tab-group.component.ts:239-262`, `paginated-tab-header.ts:241-263`; documented pattern at `tabs.en.md:67-75` / `tabs.ru.md:67-75`, implemented in `packages/docs-examples/components/tabs/tabs-add-tab/tabs-add-tab-example.ts:16-35, 67-76` and `tabs-add-tab-vertical/tabs-add-tab-vertical-example.ts:17-31, 79-88`.
When tabs change, `KbqTabGroup` re-derives the index and re-subscribes to label state (`:239-262`) and `KbqPaginatedTabHeader` realigns scroll and pagination (`:241-255`); neither touches focus. If the removed tab is the one holding DOM focus, that element is destroyed and focus falls back to `<body>` — the user loses their place and, in a keyboard-only session, has to tab in from the top of the document. WCAG 2.4.3 (Focus Order). This is not hypothetical: "Creating tabs — create and delete tabs like in a browser" is a documented feature with two live examples, and both drop focus the same way (`removeTab()` reassigns `activeTab` and never calls `focus()`, in contrast to `addTab()`, which does — via a `setTimeout(…, 100)` race, `tabs-add-tab-example.ts:64`). The same two examples put `tabindex="-1"` on the close button (`tabs-add-tab-example.ts:23`, `tabs-add-tab-vertical-example.ts:23`), so a keyboard user cannot reach it at all — the entire delete affordance is mouse-only. And the horizontal example is the only `kbqTabNavBar` in the repository that omits `[tabNavPanel]` (compare the vertical one at `:15`, `code-block.html:6`, `component-viewer.template.html:10`, `design-tokens-viewer.ts:26`), which under `tab-nav-bar.ts:88-90` means it emits no `role="tablist"` and its links emit no `role="tab"`/`aria-selected` — the flagship "browser-like tabs" demo has zero tab semantics.
**Fix:** in the `tabs.changes` handler, capture whether the header owned focus before the change (`tabListContainer.nativeElement.contains(document.activeElement)`), and if so call `tabHeader.focusIndex = clampTabIndex(newIndex)` afterwards so focus lands on the neighbouring tab; do the same in `KbqPaginatedTabHeader` for the nav-bar path. In both examples, make the close control a real `<button kbq-icon-button>` inside the tab with no negative `tabindex`, add `[tabNavPanel]` to the horizontal one, and replace the `setTimeout(…, 100)` in `addTab()` with `afterNextRender`. Guard with a Jest case that focuses the last tab, removes it, and asserts `document.activeElement` is the new last label rather than `document.body`.

**TAB-A11Y-04 · A vertical `tablist` never announces `aria-orientation="vertical"`, while horizontal arrows silently do nothing** — `tab-nav-bar.ts:55-64, 88-90`, `paginated-tab-header.ts:296-323`; live usages at `components-dev/tabs/template.html:35`, `packages/docs-examples/components/tabs/tabs-add-tab-vertical/tabs-add-tab-vertical-example.ts:15`.
`KbqTabNavBar`'s host block binds `[attr.role]='role'` and nothing else — no `aria-orientation`. With `[tabNavPanel]` supplied the element becomes `role="tablist"`, whose ARIA default orientation is horizontal, so assistive technology tells the user to press ←/→. But `handleKeydown` gates the arrows on `this.vertical` (`paginated-tab-header.ts:308-314`): in vertical mode ←/→ fall through to no branch at all and are still `preventDefault`-ed by the tail guard (`:320-322`), so they are consumed and do nothing, while ↑/↓ — which the AT did not advertise — are the working keys. `aria-orientation` **is** valid on `role="tablist"` (unlike on `role="group"`, where `jest-axe` fails `aria-allowed-attr`), and the repo handles it deliberately in four other components: `list-selection.component.ts:194`, `button-toggle.component.ts:97, 191`, `button-group.ts:157`, `dl.component.ts:70`. Tabs is the outlier.
**Fix:** add `'[attr.aria-orientation]': "role === 'tablist' ? (vertical ? 'vertical' : 'horizontal') : null"` to the `KbqTabNavBar` host block, and the same expression to the `role="tablist"` element introduced by TAB-A11Y-01 for the group. Emit nothing when there is no tablist role, so a plain navigation nav bar stays clean. Guard with Jest cases in both orientations plus a negative case asserting the attribute is absent without `[tabNavPanel]`, mirroring `button-toggle.component.spec.ts:896-911`.

**TAB-BUG-03 · `useExisting: forwardRef(() => this)` in the decorator metadata points at nothing** — `tab-group.component.ts:94`; consumer `packages/components/textarea/textarea.component.ts:61, 236`.
The provider is written inside the `@Component({…})` argument object, which is evaluated at module scope — the arrow function's lexical `this` is the module's `this`, which under `"module": "ES2022"` (`tsconfig.json:6`) is `undefined`, not the class. `noImplicitThis` is not enabled in this workspace, so TypeScript accepts it silently. `KBQ_PARENT_ANIMATION_COMPONENT` is therefore aliased to nothing, and the one consumer — `KbqTextarea`, which subscribes to `parent.animationDone` to re-run its autosize when a tab body animates in (`textarea.component.ts:236`) — never gets a parent. Because it injects with `{ optional: true, host: true }` the failure is silent rather than fatal, and the `host: true` scope means the lookup would not have crossed from a tab body's projected content up to the tab group anyway: the wiring is broken twice over, and the intended feature (a textarea inside a tab re-measuring itself when its tab becomes visible) has never worked.
**Fix:** write `useExisting: forwardRef(() => KbqTabGroup)` — the whole point of `forwardRef` here is to name the class before its declaration is complete. Then decide whether the feature is wanted: if so, drop `host: true` from `textarea.component.ts:61` so the token can be found on an ancestor, and add a spec placing a `<kbq-textarea>` inside a `<kbq-tab>` that asserts the autosize re-runs on `animationDone`. If not, delete the provider and the token's tabs-side wiring rather than leaving a dead alias.

**TAB-API-01 · `KbqTabGroup.disabled` is a published input that nothing reads** — `tab-group.component.ts:180-193`, `tools/public_api_guard/components/tabs.api.md:184-185, 196, 231`.
The accessor pair, its `_disabled` backing field and its `ngAcceptInputType_disabled` declaration all exist and are all `@public`; the input appears in the generated docs API table for the component. Grep across the package finds three `.disabled` reads in `tab-group.component.ts` and every one of them is `tab.disabled` (`:375, 385`) — the group-level flag is referenced only by its own setter's no-op guard (`:188`). Neither template binds it, no SCSS selector targets a group-level disabled class, and there is no such class to target. `<kbq-tab-group disabled>` therefore compiles, type-checks, appears in the documentation and does nothing at all — the worst kind of API, one that a consumer will reasonably believe in.
**Fix:** either implement it — a `[class.kbq-disabled]` on the host plus short-circuits in `handleClick()` and `handleKeydown()`, matching how `KbqTabLink.disabled` behaves — or delete the input, its backing field and its `ngAcceptInputType_*`. Deletion is the smaller change and is breaking, so pair it with an `ng-update` warn entry. Either way run `yarn run build:components` then `yarn run approve-api`; the guard reads `dist/*.d.ts`, so build first.

**TAB-PERF-01 · The tab header runs `Default` change detection over three layout-reading getters** — `tab-header.component.ts:42, 65-89`, `tab-header.html:18-20`, `tab-nav-bar.ts:92-114`, `tab-nav-bar.html:18-20`; also `tab-group.component.ts:271-319, 456-464`.
`KbqTabHeader` is declared `changeDetection: ChangeDetectionStrategy.Default` (`:42`) — the only component in the package that is not `OnPush`, and AGENTS.md mandates `OnPush`. Its template binds three getters that each hit the layout engine: `activeTabOffsetLeft` reads `offsetLeft`, `activeTabOffsetWidth` reads `offsetWidth` (`:65-85`), and `activeTabDisabled` walks `items` (`:87-89`). Under `Default`, all three are re-evaluated on *every* application-wide tick regardless of whether anything in the tab header changed, and `offsetLeft`/`offsetWidth` force a synchronous style-and-layout flush each time. `KbqTabNavBar` carries the identical getters (`tab-nav-bar.ts:92-114`) but is `OnPush`, which is the proof that `Default` is not required here. Compounding it, `KbqTabGroup.ngAfterContentChecked` — which by definition runs on every check — calls `getTabIndexToSelect()`, whose `activeTab` getter allocates a fresh array via `this.tabs.toArray()` and, in the `tabId` case, linear-scans it (`tab-group.component.ts:146-163, 456-464`), then calls `this.activeTab` a second time at `:291` and iterates all tabs at `:304`. The docs application itself renders a `kbqTabNavBar` on every component page, and `code-block` renders one per code block.
**Fix:** switch `KbqTabHeader` to `ChangeDetectionStrategy.OnPush` — the class already calls `changeDetectorRef.markForCheck()` at all six points where it mutates rendered state (`paginated-tab-header.ts:271, 280, 288, 518, 541`, `:341`), which is what `OnPush` needs. Then move the ink-bar geometry off getters: compute `left`/`width` once in `updatePagination()`/`scrollToLabel()` into two fields and bind those, so layout is read on demand rather than per tick. ### P3 — Nice to have / hygiene

**TAB-TEST-02 · 81 Jest cases, zero ARIA assertions, and the only ARIA-wired code path is untested** — `tab-group.spec.ts` (802 lines, 32 cases), `tab-header.spec.ts` (447 lines, 24 cases), `tab-nav-bar.spec.ts` (200 lines, 11 cases), `tab-body.spec.ts` (197 lines, 14 cases), `e2e.playwright-spec.ts:9-32`.
Not one of the four specs asserts on `role`, `aria-selected`, `aria-controls`, `aria-labelledby` or `aria-orientation`, which is why TAB-A11Y-01 and TAB-A11Y-04 are invisible to CI. More pointedly, `[tabNavPanel]` — the input that switches the nav bar into full tablist semantics and the one that `code-block`, the docs component viewer and the design-tokens viewer all depend on — appears in no spec at all: `tab-nav-bar.spec.ts` only ever builds a bare `<nav kbqTabNavBar>` (`:175, 193`), which takes the `getAttribute`-passthrough branch of every ARIA getter. On the visual side, one screenshot pair covers 16 tab-group variants in a single image, so any regression lands as one large diff with no isolation, and the Playwright spec opens with a "Flaky test workaround: click to underlined tab to ensure proper bottom outline rendering" (`e2e.playwright-spec.ts:14-15`) — a click that hides whatever is wrong with the ink bar's *initial* placement, which is precisely the state a user sees on page load. **Fix:** add a `tabNavPanel` describe block covering `role`, `aria-selected`, `aria-controls`↔panel `id`, `aria-labelledby`↔active link `id`, and the `tabIndex` flip between active and inactive links; add the TAB-A11Y-01 assertions for the group; add `jest-axe` passes for both. Split the e2e fixture into per-variant `data-testid` blocks with their own screenshots so a diff names the variant. Then delete the workaround click at `e2e.playwright-spec.ts:15` and, if the baseline changes, file the ink-bar ordering bug it was hiding rather than restoring the click.

**TAB-API-02 · The API report carries a committed extractor warning, a duplicated type and leaked internals** — `tools/public_api_guard/components/tabs.api.md:236-237, 212, 288, 424`, `public-api.ts:1-10`, `paginated-tab-header.ts:37`, `tab-header.component.ts:25`.
Four hygiene issues on one surface. (1) The report contains `Warning: (ae-forgotten-export) The symbol "KbqPaginatedTabHeader" needs to be exported by the entry point index.d.ts` (`:236`) — both public header components extend it, so consumers see `extends KbqPaginatedTabHeader` in the type signature and cannot name the type; `public-api.ts` exports `tab-header.component` but not `paginated-tab-header`. (2) `ScrollDirection` is declared twice with identical bodies, once in `paginated-tab-header.ts:37` and once in `tab-header.component.ts:25`; only the second is exported, so the first is dead and the two will drift. (3) `resizeStream` is a public `Subject<Event>` (`:212`) that consumers can push into — the same leak the `title` package is currently migrating away from. (4) `getInnerText(): any` (`:288`) is `any` only because `labelContent` is declared as a bare `ElementRef` (`tab-label-wrapper.directive.ts:28`); it also reads `innerText`, which this workspace's jsdom does not implement, so any future spec asserting through it would be reading back nothing. **Fix:** export `paginated-tab-header` from `public-api.ts` (or mark the base `@internal` and add `stripInternal` — note `@internal` alone does not remove a member from the guard). Type `labelContent` as `ElementRef<HTMLElement>` and `getInnerText(): string`, switching to `textContent`. Add JSDoc to the public inputs. Batch all of it into one `yarn run build:components && yarn run approve-api` cycle so the report churns once — remember that adding JSDoc alone removes the `(undocumented)` marker and fails `check-api` until re-approved.

**TAB-ARCH-01 · Nine unresolved migration TODOs, decorator queries, and no-op setter guards** — `tab-group.component.ts:129-131, 142-144, 171-173, 176-178, 180-182, 187-191`, `paginated-tab-header.ts:70-72, 144-146, 149-151`, `tab-body.component.ts:69-71, 99-101`, `tab-label-wrapper.directive.ts:30-36`, `tab.component.ts:73-75, 86-88`, `tab-nav-bar.ts:185-192, 216-223`.
The package carries fifteen `// TODO: Skipped for migration because:` comments in three flavours — "Accessor inputs cannot be migrated as they are too complex", "Your application code writes to the input", and "Class of this input is referenced in the signature of another class". Several are untrue as written: `KbqTab.disabled` (`tab.component.ts:88-97`) and `KbqTabLabelWrapper.disabled` (`tab-label-wrapper.directive.ts:36-45`) are plain `booleanAttribute` accessor pairs whose setters do nothing but an `if (value !== this._disabled)` guard that cannot fire twice with the same value anyway — exactly what `input({ transform: booleanAttribute })` replaces. `KbqTabHeader`/`KbqTabNavBar` still use `@ContentChildren`/`@ViewChild` decorator queries (`tab-header.component.ts:57-61`, `tab-nav-bar.ts:68-72`) alongside `viewChild.required` in the group (`tab-group.component.ts:116-118`), so the package mixes both conventions in adjacent files. `KbqTabBody` still declares `beforeCentering`/`afterLeavingCenter` as `@Output() EventEmitter` (`tab-body.component.ts:84-87`) next to two `output()` siblings. `tab-group.component.ts:240` leaves a commented-out line of dead code, which AGENTS.md prohibits.
**Fix:** migrate the two genuinely simple accessor pairs and the two `@Output`s; keep `selectedIndex`, `activeTab` and `headerPosition` as accessors for now (they really are written to internally, and `activeTab`'s getter is load-bearing). Migrate the decorator queries to signal queries in the *optional* form with a guard, not `.required` — the repo's earlier signal-queries migration showed `.required` reads during render throw NG0951 only in production builds. Delete the commented-out line at `:240`. Each migration changes `tabs.api.md`; fold them into the TAB-API-02 approve cycle.

**TAB-DOC-01 · The hot-key table omits the only arrows that work for vertical tabs** — `tabs.en.md:77-85`, `tabs.ru.md:77-85`; behaviour at `paginated-tab-header.ts:304-322`.
Both guides document ←, →, <kbd>Home</kbd>, <kbd>End</kbd> and <kbd>Space</kbd>/<kbd>Enter</kbd>. `handleKeydown` also handles ↑ and ↓, and in vertical mode those are the *only* working arrows while ←/→ are swallowed by the `preventDefault` tail guard (`:320-322`) without doing anything. Vertical tabs get two dedicated sections in the same guide (`tabs.en.md:7-15`) and three e2e variants, so the gap is between the documented and the shipped keyboard model for a first-class feature. The guides also have no accessibility section at all — nothing states that activation is manual (focus moves without selecting until <kbd>Space</kbd>/<kbd>Enter</kbd>), which is a deliberate and correct design choice worth telling consumers about, and nothing warns that `KbqTabNavBar` only becomes a real tablist when `[tabNavPanel]` is supplied — the single most consequential undocumented fact in the package, and the one the `tabs-add-tab` example gets wrong (see TAB-A11Y-03).
**Fix:** add ↑ and ↓ rows to both tables, noting that the vertical/horizontal pairs are mutually exclusive. Add a short "Accessibility" section to both guides covering manual activation, the roving tab order, and the `[tabNavPanel]` requirement, and cross-link it from the "Tabs and navigation" section. Once TAB-A11Y-01 lands, state the emitted roles so consumers know what their own tests can assert against.

## Appendix A — Review Methodology

Every file in the package was read in full (`cat -n` over all 35 `.ts`/`.html`/`.scss`/`.md` files, 5,164 lines), then each candidate finding was cross-checked against four independent sources: the workspace compiler and test settings (`tsconfig.json:6, 114-118`; `playwright.config.ts:96-104`), the API guard report (`tools/public_api_guard/components/tabs.api.md`, 428 lines) together with `tools/api-extractor/config.json:52`, every in-repo consumer of `kbq-tab-group`/`kbqTabNavBar` found by grep across `packages/` and `apps/` (`code-block`, `icon/e2e.ts`, the dev app, the docs component viewer and the design-tokens viewer), and all 16 documentation examples under `packages/docs-examples/components/tabs/`. Consumer and example evidence is what upgraded three findings from opinion to confirmed defect: `[tabNavPanel]` is supplied at every nav-bar call site *except* the flagship closable-tabs example, all vertical usages in the tree use the static-attribute form that hides TAB-BUG-02, and the `on-surface` token family has zero readers anywhere in the repository. Design tokens were verified as resolvable against `@koobiq/design-tokens/web/css/size.css` (`--kbq-size-3xl: 32px`, `--kbq-size-xxs: 4px`, `--kbq-size-3xs: 2px`). Severity calibration deliberately weighted "can a consumer work around this?" — TAB-A11Y-01 is a P0 chiefly because the affected elements are generated by the component's own template.

Refuted during verification:
- **"Tab content is eagerly rendered for every tab"** — refuted. `KbqTabBodyPortal` attaches only on `beforeCentering` and detaches on `afterLeavingCenter` (`tab-body.component.ts:220-234`), and `tab-group.spec.ts:434-444` asserts that only the active tab's text is in the DOM. Lazy rendering works, including the explicit `*kbqTabContent` template form (`tab-group.spec.ts:458-475`).
- **"`animationDuration` defaults to `'0ms'`, so the `translateTab` transitions never fire their callbacks and content is never detached"** — refuted. Angular's animation engine emits `start`/`done` for zero-duration transitions, which is why `onCentered`/`afterLeavingCenter` still drive the portal and why `tab-group.spec.ts:182-193` observes `animationDone` at the default duration.
- **"`cdkObserveContent` on the tab list will loop with `Default` change detection"** — refuted. `onContentChanges()` diffs the header's `textContent` before re-entering the zone (`paginated-tab-header.ts:328-344`), with a comment naming the upstream issue this guard was written for. The `Default` strategy is still worth removing (TAB-PERF-01), but not for this reason.
- **"The `(window:resize)` host listener leaks after the component is destroyed"** — refuted. Host listeners are torn down with the view. The real defects on that line are that nothing is subscribed (TAB-BUG-01) and that `resizeStream` is never `complete()`d, unlike the equivalent in `navbar.component.ts:288`.
- **"`aria-orientation` on the `kbq-tab-group` host would fix the vertical case"** — refuted as a fix. The host has no `role`, and `aria-orientation` is only meaningful on a role that supports it; putting it on a roleless element is noise, not semantics. It belongs on the `role="tablist"` element that TAB-A11Y-01 introduces, which is why the two findings are sequenced together.
- **"The guide's '32×32px clickable area' claim for `iconOnly` is wrong"** — refuted. `.kbq-tab-label_icon-only.kbq-tab-label_underlined` sizes to `calc(--kbq-size-3xl - --kbq-size-xxs)` = 28 px content plus a 2 px transparent border on each side (`_tabs-common.scss:80-89`, `tabs-tokens.scss:7, 10`), i.e. a 32×32 border box — and the sentence sits inside the "Underlined tabs" section, so it is accurate in context.

Corrected on verification:
- **TAB-BUG-01** was first drafted as "the resize handler is debounced but runs in the Angular zone" — a routine perf note. Reading the constructor showed the subscription is never created at all, because a signal input is read before Angular writes it, so the debounce is moot and the whole feature is dead. Severity moved from P2 performance to P1 correctness, and the `ngAfterViewInit` write-after-read hazard was folded in as the same root cause.
- **TAB-A11Y-02** was drafted as "the roving `tabindex` tracks selection instead of focus", an ARIA APG deviation worth a P2 at most. Tracing the `null` branch for disabled tabs against the default-selection path turned the same three-line method into a complete keyboard lockout, with two committed e2e fixtures already in that state; it moved to P1 and the APG point became the mechanism rather than the finding.
- **TAB-BUG-03** was initially drafted as "the provider throws a `NullInjectorError` at runtime". The consumer injects with `{ optional: true, host: true }` (`textarea.component.ts:61`), so the observable effect is a silently missing re-measure rather than a crash, and the `host: true` scope means the lookup was never going to reach the tab group anyway. Severity dropped from P1 to P2 and the wording moved from "crashes" to "wired to nothing, twice over".
