# Ревью компонента: `input`

> Область: `packages/components/input` (`KbqInput`, `KbqInputPassword`, `KbqNumberInput`, `KbqInputMono`, `MinValidator`/`MaxValidator`, SCSS с токенами и темой, три Jest-спеки, e2e-фикстура и Playwright-спека, руководства пользователя, отчёт API guard) · Коммит `b665e503` · 2026-08-28
> Подготовлено многомерным ревью (архитектура, RxJS/жизненный цикл, корректность, доступность, производительность, публичный API и типы, стили, тесты, документация) с ручной проверкой каждой находки по исходникам, по потребителям внутри репозитория, по отчёту API guard, `tsconfig.json` и небольшим `node`-проверкам на jsdom и `Intl`. Подтверждено 18 находок (P0×1, P1×4, P2×8, P3×5); 8 кандидатов опровергнуты при проверке (см. Приложение A). Документ — это ревью и дорожная карта; исходный код им не меняется.

Четыре находки того ревью были перепроверены и уже исправлены в `form-field` — они перечислены в Приложении A как опровергнутые, а не пересказаны заново.

## 1. Резюме

`packages/components/input` — это 4318 строк в трёх практически независимых директивах-контролах: `KbqInput` (331 строка), `KbqInputPassword` (295) и `KbqNumberInput` (588), плюс пара валидаторов `min`/`max` на 92 строки. Это самый востребованный контрол библиотеки: `kbqInput` встречается в `app-switcher`, `filter-bar` (5 шаблонов пайпов), `search-expandable` и во всех dev-стендах form-field. Блокеры доступности уровня контейнера из ревью form-field с тех пор исправлены (`aria-describedby`, озвучиваемый переключатель пароля, `aria-invalid`), так что осталось то, за что отвечает сам контрол.

- **Единственный блокер релиза — глобальная мутация платформы.** Конструктор `KbqNumberInput` вызывает `Object.defineProperty(Object.getPrototypeOf(this.nativeElement), 'valueAsNumber', …)` (`input-number.ts:281-289`). Это `HTMLInputElement.prototype` — то есть создание одного числового поля koobiq молча переписывает `valueAsNumber` для **каждого `<input>` в приложении**, включая сторонние виджеты и нативные поля `type="date"`/`type="number"`, навсегда, без отката и без возможности отказаться. Проверка на jsdom подтверждает: посторонний input после этого возвращает `12.5` для `"12,5"`, тогда как платформа предписывает `NaN`. Обходного пути у потребителя нет, тестов на этот код нет (INP-BUG-01).
- **Две директивы генерируют DOM-идентификаторы из одного пространства имён двумя независимыми счётчиками.** В `input.ts:24` и `input-password.ts:9` объявлено по своему `let nextUniqueId = 0`, и обе строят `` `kbq-input-${nextUniqueId++}` `` (`input.ts:100`, `input-password.ts:90`). Страница с одним текстовым и одним парольным полем — форма входа, страница Overview в документации, dev-приложение самого пакета и его же e2e-фикстура — отдаёт два элемента с `id="kbq-input-0"`. `form-field.html:2` рендерит `<label [attr.for]="control().id">`, поэтому лейбл парольного поля указывает на *текстовый* input (INP-A11Y-01).
- **Числовое поле хрупко ровно там, где на это указывает его история.** 12 из 22 коммитов, когда-либо затронувших `input-number.ts`, — исправления багов, пять из них про дробные значения или позицию каретки. Хелпер компенсации плавающей точки по-прежнему «плывёт»: одно нажатие стрелки на `1.005` при `step="0.001"` рисует в поле `1,0059999999999998` (INP-BUG-03); собственные `MinValidator`/`MaxValidator` пропускают границы через `parseInt`, поэтому `[min]="0.5"` валидирует против `0` (INP-BUG-02); добавление `type="number"` — а так делают два dev-приложения самого репозитория — заставляет браузерный санитайзер отклонять любое отформатированное значение и очищает поле (INP-BUG-05); а `KbqNumberInput.control` объявлено и никогда не присваивается, поэтому его `ngControl` навсегда `undefined` (INP-BUG-04).
- **Ни один из 89 Jest-кейсов не проверяет ни одного ARIA-атрибута**, у директив-валидаторов `min`/`max` нет ни тестов, ни точек использования в репозитории, а Playwright-набор — это пять скриншотов без ввода, без шагов и без смены локали (INP-TEST-01, INP-TEST-02).

Сильные стороны, которые стоит сохранить: проводка `ErrorStateMatcher` продумана и действительно хорошо покрыта (17 из 25 кейсов `input.spec.ts` прогоняют четыре стратегии матчера, включая переопределение через DI); `kbqInjectAutofilled()` применён корректно на обоих текстовых контролах, а стилизация автозаполнения из DS-4096 в `_form-field-theme.scss:80-97` — один из самых аккуратно обоснованных кусков CSS в репозитории; дисциплина SSR настоящая (во всём пакете нет ни одного голого `window`/`document`, есть явная проверка `element.blur` в `input-number.ts:227-233` и явная проверка `validity?.badInput` в `input.ts:318-323`); работа с локалью, добавленная в DS-3897 (`kbqInjectLocaleConfiguration` плюс эффект переформатирования с `untracked` в `input-number.ts:291-298`), — образец того, как контрол должен реагировать на смену локали в рантайме; а `input-number.spec.ts` — это 1671 строка реального поведенческого покрытия фильтрации клавиш, вставки из буфера и маскирования разделителей разрядов.

## 3. Приоритизированные находки (дедуплицированы, верифицированы)

### P0 — Блокеры релиза

**INP-BUG-01 · `KbqNumberInput` навсегда переписывает `HTMLInputElement.prototype.valueAsNumber` для всего приложения** — `input-number.ts:281-289`, `input-number.ts:84-86`.
Конструктор выполняет `if ('valueAsNumber' in this.nativeElement) { Object.defineProperty(Object.getPrototypeOf(this.nativeElement), 'valueAsNumber', { get() { … } }); }`. `Object.getPrototypeOf(anInputElement)` — это `HTMLInputElement.prototype`, а не сам элемент, поэтому речь не о подмене на одном экземпляре: заменяется платформенный аксессор для **каждого `<input>` в документе**, независимо от того, имеет ли он хоть какое-то отношение к koobiq. Замена возвращает `parseFloat(normalizeSplitter(this.value))`, то есть трактует `,` как десятичную точку и возвращает `null` там, где спецификация DOM требует `NaN`. Проверено на jsdom: после патча `<input>`, никогда не видевший `kbqNumberInput` и хранящий `"12,5"`, сообщает `valueAsNumber === 12.5`; контракт платформы — `NaN`. На типах, где `valueAsNumber` *определён как миллисекунды с эпохи* (`type="date"`, `"month"`, `"week"`, `"time"`), замена вместо этого возвращает `parseFloat` строки даты: `"2024-01-15"` превращается в `2024`. Отката в `ngOnDestroy` нет (`input-number.ts:301-304`), так что патч переживает саму директиву; вторая проверка на jsdom показывает, что повторное определение проходит молча, а не бросает исключение, потому что нативный дескриптор — `configurable: true`, а дескриптор, задающий только `get`, сохраняет остальные атрибуты, — то есть повторное создание директивы тоже никогда не падает громко. Ничто в репозитории не читает `valueAsNumber`, и ни один тест не проходит по этой ветке — поэтому она и дожила до сегодняшнего дня. От сервера патч удерживает только проверка `'valueAsNumber' in this.nativeElement`; DOM-шим, который это свойство реализует, получил бы патч прототипа, общего для всех SSR-запросов процесса.
**Fix:** удалить блок. Если локале-зависимое числовое чтение действительно нужно, вынести его в член директивы — `get valueAsNumber(): number | null { return this.value; }`, — что и так уже лежит в `_value` после нормализации в `viewToModelUpdate` (`input-number.ts:518-528`), не требует патчинга DOM и типизировано. Прикрыть удаление Jest-кейсом, который создаёт `kbqNumberInput`, а затем проверяет, что соседний обычный `<input>` со значением `"12,5"` всё ещё возвращает `NaN` из `valueAsNumber`: сегодня этот кейс падает, после правки — проходит.

### P1 — Высокий приоритет

**INP-A11Y-01 · `KbqInput` и `KbqInputPassword` генерируют конфликтующие DOM-идентификаторы, из-за чего `<label for>` формы-поля указывает не на тот контрол** — `input.ts:24, 100, 146-152, 224`, `input-password.ts:9, 90, 128-134, 197`, `form-field.html:2`.
Оба файла объявляют собственный `let nextUniqueId = 0;` уровня модуля, и оба строят запасной id с *одинаковым* префиксом: `` protected uid = `kbq-input-${nextUniqueId++}` `` (`input.ts:100`, `input-password.ts:90`). Два независимых счётчика на одно пространство имён означают, что первый `kbqInput` на странице и первый `kbqInputPassword` на той же странице получают `kbq-input-0`, вторые — `kbq-input-1` и так далее. Идентификатор попадает в DOM безусловно: конструктор принудительно дёргает сеттер (`this.id = this.id`, `input.ts:224` / `input-password.ts:197`), а хост биндит `'[attr.id]': 'id'` (`input.ts:38`, `input-password.ts:23`). Далее `KbqFormField` рендерит `<label class="kbq-form-field__label" … [attr.for]="control().id">` (`form-field.html:2`), а `for` разрешается в *первый* по порядку документа элемент с таким id — то есть в форме входа лейбл парольного поля фокусирует поле логина, и кликом по нему до пароля не добраться. Все остальные пакеты библиотеки избегают этого, выделяя себе префикс (`kbq-textarea-` в `textarea.component.ts:211`, `kbq-select-` в `select.component.ts:1070`, `kbq-tree-select-`, `kbq-datepicker-`, `kbq-timepicker-`); `input` — единственный, кто переиспользует соседский. Коллизия не гипотетическая: она воспроизводится в собственной e2e-фикстуре пакета (`e2e.ts:40` и `e2e.ts:109` рендерят по восемь штук на одной странице), в его dev-приложении (`components-dev/input/template.html:22` и `:108`) и на опубликованной странице Overview документации, где `input-overview` и `input-password-overview` встроены рядом. Это нарушение WCAG 1.3.1 / 3.3.2 (связь лейбла с полем) с функциональным симптомом, а не просто замечание линтера про дубликат id.
**Fix:** выдать парольному контролу собственное пространство имён — `` `kbq-input-password-${nextUniqueId++}` `` в `input-password.ts:90`, — а лучше заменить оба модульных счётчика на `inject(_IdGenerator).getId('kbq-input-')` / `'kbq-input-password-'`, чтобы счётчик был на уровне приложения, а не модуля, и переживал ленивую загрузку дубликата бандла. Добавить Jest-кейс, который рендерит один `<input kbqInput>` и один `<input kbqInputPassword>` в одной фикстуре и проверяет `new Set(ids).size === 2`, плюс кейс, проверяющий, что `for` каждого `<label>` разрешается в свой контрол (`document.getElementById(label.htmlFor) === input`).

**INP-BUG-05 · `type="number"` на `kbqNumberInput` очищает поле, и dev-приложения самой библиотеки так делают** — `input-number.ts:507-516, 400-442`, `input.ts:305-310`; точки использования `components-dev/all/template.html:501-508`, `components-dev/form-field/template.html:332-339`.
`KbqNumberInput` отображает значение через `setViewValue()`, который присваивает *отформатированную* строку — с тонкими пробелами в разрядах и запятой в качестве дробного разделителя при конфигурации по умолчанию `ru-RU` (`core/locales/formatters.ts:136-143`). Нативный `<input type="number">` при присваивании прогоняет алгоритм санитизации значения и отклоняет всё, что не является корректным числом с плавающей точкой. Проверено на jsdom: присваивание `"1 234,5"` полю `type="number"` даёт `""`, тогда как то же присваивание полю `type="text"` проходит без потерь. То есть при наличии `type="number"` любое значение с дробной частью — и любое значение ≥ 1000, пока включён `withThousandSeparator` (значение по умолчанию, `input-number.ts:183`), — молча исчезает из поля, хотя модель его по-прежнему хранит. Та же проверка показывает, что `selectionStart` на `type="number"` равен `null`, а это выключает весь механизм сохранения каретки: чтение в `input-number.ts:402`, восстановление в `:512-515` и коррекция смещения при добавлении разделителя в `:417-432` превращаются в no-op. Два собственных dev-шаблона репозитория задают ровно эту комбинацию рядом с `[step]="0.5"`, поэтому первое нажатие стрелки там опустошает поле. Механизм для предотвращения такого у `KbqInput` уже есть — `validateType()` отклоняет девять типов через `KBQ_INPUT_INVALID_TYPES` (`input.ts:12-22, 305-310`), — но `number` в списке нет, а числовое поле тип хоста вообще не проверяет. Правила `input.scss`, спрятанные для скрытия нативных стрелок (`input.scss:20-27`, `input.kbq-input[type='number']`), — зеркальное отражение той же путаницы: они никогда не совпадают с числовым полем koobiq, потому что оно `type="text"`.
**Fix:** в конструкторе `KbqNumberInput` бросать ошибку в dev-режиме, если `nativeElement.type === 'number'` (переиспользовав форму `getKbqInputUnsupportedTypeError` из `input-errors.ts:1-3` с сообщением, называющим `kbqNumberInput`), либо принудительно ставить `nativeElement.type = 'text'` и писать предупреждение. Починить два dev-шаблона. В том же изменении решить судьбу `input.scss:20-27`: либо удалить мёртвый блок `[type='number']`, либо оставить и задокументировать, что `<input kbqInput type="number">` (без `kbqNumberInput`) — поддерживаемый нативный числовой путь. Закрыть Jest-кейсом на выброс ошибки и кейсом, проверяющим, что дробное значение переживает круг через `setViewValue` на хосте по умолчанию.

**INP-BUG-02 · `MinValidator`/`MaxValidator` обрезают свои границы через `parseInt`, поэтому дробные `min`/`max` валидируются не по тому числу** — `input-number-validators.ts:44-46, 88-91`, хост-биндинги `:18, :63`.
Обе директивы собирают валидатор как `Validators.min(parseInt(this.min() as unknown as string, 10))` / `Validators.max(parseInt(this.max() …))`. `parseInt` останавливается на десятичной точке, поэтому `[min]="0.5"` ставит `Validators.min(0)` — контрол со значением `0.2` считается валидным, — а `[max]="9.5"` ставит `Validators.max(9)`, и `9.3` объявляется невалидным. Это не абстрактный случай: числовое поле явно рассчитано на дроби (`isFloat` в `input-number.ts:88-90`, `fractionSeparator` в каждой локали и input `integer` в `:161`, весь смысл которого — *отказаться* от дробей), а dev-приложение биндит дробные шаги (`components-dev/input/template.html:147`, `[step]="0.5"`). Само приведение `this.min() as unknown as string` — уже признак проблемы: сигнал объявлен как `input<number>()` (`:22`), а затем прогоняется через строковый парсер. В тех же 92 строках сидят ещё два дефекта. (1) Хост-биндинги `'[attr.min]': 'min() ? min() : null'` (`:18`) и аналогичный для `max` (`:63`) проверяют на «ложность», поэтому *забинженный* `[min]="0"` — самая частая нижняя граница — вовсе убирает атрибут `min` из DOM, тогда как статическая форма `min="0"` его сохраняет (значение атрибута — истинная строка `"0"`). (2) Имена экспортируемых классов `MinValidator` и `MaxValidator` в точности совпадают с экспортами `@angular/forms`, поэтому `import { MinValidator } from '@koobiq/components/input'` затеняет фреймворковый в любом файле, где нужны оба; селекторы тоже отличаются от ангуляровских (те ограничены `input[type=number]`), так что на контроле `type="number"` устанавливаются оба валидатора, и один из них обрезает границу.
**Fix:** заменить оба вызова `parseInt(…, 10)` на `coerceNumberProperty(this.min())` (или обычный `Number(...)` с проверкой `Number.isFinite`) и убрать приведения `as unknown as string`. Изменить хост-биндинги на `min() == null ? null : min()`. Переименовать экспорты в `KbqMinValidator`/`KbqMaxValidator`, оставив `@deprecated`-алиасы на один минор, затем `yarn run build:components && yarn run approve-api`. Добавить `input-number-validators.spec.ts` — сегодня у файла нет ни одного теста (см. **INP-BUG-03 · Хелпер компенсации плавающей точки всё равно «плывёт», и дрейф посимвольно выводится в поле** — `input-number.ts:100-110, 462-484, 552-587`.
`add()` существует, чтобы избежать дрейфа IEEE-754 при шаге: он масштабирует оба операнда на большую из двух точностей, складывает и масштабирует обратно. Он ломается всегда, когда у операндов разная длина дробной части, потому что дрейфует само масштабирование — `node`-проверка даёт `add(1.005, 0.001) === 1.0059999999999998`. `stepUp`/`stepDown` пишут это значение прямо в `_value` и во вью (`:467-469`, `:479-481`), а `formatNumber` разбивает `toString()` числа и форматирует дробную часть **посимвольно** (`:580-586`) вообще без округления: `maximumFractionDigits: 20` (`:563`) применяется только к целой части. То, что видит пользователь после одного нажатия стрелки на `1.005` при `step="0.001"`, — это `1,0059999999999998`. У `getPrecision` есть вторая дыра: он разбивает по `.` вывод `toString()`, поэтому любое число в экспоненциальной записи (`(1e-7).toString() === '1e-7'`) сообщает точность `1` и полностью обходит компенсацию. У этого участка худшая история регрессий в пакете — 12 из 22 коммитов, затронувших `input-number.ts`, это `fix(...)`, и пять из них именно про дробные значения (`DS-4514` handle fraction part properly, `DS-4474` parsing and validation of fractional values, `DS-2633` fractional value not displayed after initialization), — что и есть подпись хелпера, который чинят вместо того, чтобы заменить.
**Fix:** прекратить делать десятичную арифметику в двоичных float. Считать шаг в целочисленном пространстве относительно десятичного масштаба, выведенного из *объявленных* `step`/`bigStep` и текущего значения (`const scale = 10 ** Math.max(decimals(step), decimals(value))`, затем `(Math.round(value * scale) + Math.round(step * scale)) / scale`), и округлять результат до этого масштаба перед сохранением. `decimals()` выводить из строкового представления с отдельной веткой для экспоненты, чтобы `1e-7` обрабатывалось корректно. Добавить Jest-кейсы на `add(1.005, 0.001)`, `add(0.1, 0.25)`, шаг от `1e-7` и сквозной кейс, проверяющий *отрисованный* `viewValue` после `stepUp` на `1.005`: проверка только модели этот баг бы не поймала.

Проверить AOT-компиляцией черновика шаблона с `<input kbqNumberInput min="3" step="0.5">` и `<input kbqInput required>`: сегодня и то и другое — ошибки.

**INP-LIFE-01 · Каждое нажатие клавиши в числовом поле планирует `setTimeout` в зоне плюс микротаску, и ни то ни другое не отменяется при уничтожении** — `input-number.ts:400-442, 301-304`.

(1) Оба выполняются внутри зоны Angular, поэтому каждое нажатие клавиши стоит двух дополнительных проходов обнаружения изменений по всему приложению сверх того, который уже вызывает событие `input`, — для формы из числовых полей под `OnPush`-предками это доминирующая цена ввода. - **Фаза 2:** фикстура с одним `kbqInput` и одним `kbqInputPassword` даёт два различных `id`, а `document.getElementById(label.htmlFor)` для каждого лейбла — его собственный контрол. `Validators.min(0.5)` отклоняет `0.2`, а `[min]="0"` оставляет `min="0"` в DOM. `stepUp` от `1.005` при `step="0.001"` рисует `1,006`, и проверяется это по `viewValue`, а не по модели. `KbqNumberInput` больше не значится как `KbqFormFieldControl` в `input.api.md`.
- **Фаза 3:** `getComputedRole` на числовом поле сообщает `spinbutton`; `aria-valuenow` следует за `stepUp`/`stepDown`/`writeValue`; `aria-valuetext` содержит сгруппированную строку в формате локали; `inputmode` меняется вместе с `[integer]`. Прогон `jest-axe` по шаблону «лейбл + контрол + подсказка + ошибка» чистый. Ввод семизначного числа в dev-приложении показывает в профайлере один проход обнаружения изменений на нажатие, а не три.
- **Фаза 4:** дифф `check-api` содержит только запланированные переименования, пометки `@deprecated` и удаления; черновой AOT-шаблон с `<input kbqNumberInput min="3" step="0.5">` и `<input kbqInput required>` компилируется, чего сегодня не происходит; `yarn run styles:build-all` после переименования файла темы даёт неизменившийся бандл form-field.
- **Фаза 5:** `npx playwright test packages/components/input/e2e.playwright-spec.ts` зелёный на браузерах CI вместе с новыми интерактивными кейсами; намеренный откат правки `parseInt` из фазы 2 роняет хотя бы один кейс валидаторов (мутационная проверка); сайт документации рендерит оба руководства с исправленным примером числового поля и новым разделом API на обеих локалях.

## Приложение A — Методология ревью

Каждый файл пакета прочитан целиком (`cat -n` по всем 14 `.ts`, 3 `.scss` и 4 `.md`, плюс e2e-фикстура и Playwright-спека), после чего каждая находка-кандидат перепроверена по четырём независимым источникам: отчёту API guard (`tools/public_api_guard/components/input.api.md`, 349 строк), настройкам компилятора воркспейса (`tsconfig.json:114-118`), всем потребителям внутри репозитория, найденным grep по `packages/` и `apps/`, и `git log` по каждому файлу. Четыре утверждения, которые нельзя было закрыть одним чтением, проверены небольшими `node`-пробами, а не приняты на веру: патч прототипа `valueAsNumber` воспроизведён на jsdom (глобальный охват, молчаливое переопределение, `null` вместо `NaN`); цепочка «дрейф → отрисованная строка» воспроизведена дословной перереализацией `getPrecision`/`add`/`formatNumber`; ветка `es-LA` опровергнута прогоном настоящего алгоритма форматирования под обеими локалями; поведение санитизации значения и `selectionStart` при `type="number"` подтверждено на jsdom. `git log` дал подкрепление для INP-BUG-03 и INP-LIFE-01: 12 из 22 коммитов, затрагивающих `input-number.ts`, — исправления, пять из них про дробные значения или каретку.

Четыре межпакетных пункта доступности, которые ревью form-field адресовало этому пакету, перед написанием были перепроверены по текущим исходникам, и все четыре уже реализованы — ниже они значатся как опровергнутые, а не пересказаны, чтобы документ не противоречил своему компаньону.

Опровергнуто при проверке:
- **«`KbqInput` не реализует `ControlValueAccessor`, поэтому у него нет `setDisabledState` и `onTouched`»** — опровергнуто. `KbqInput` намеренно делегирует доступ к значению ангуляровскому `DefaultValueAccessor`; состояние disabled отражается, потому что геттер читает `ngControl.disabled` (`input.ts:118-124`) в хост-биндинг `[attr.disabled]` (`:40`), а `onTouched` вызывается собственным blur-обработчиком `DefaultValueAccessor`. `KbqNumberInput` реализует все четыре метода CVA (`input-number.ts:315-332`) и вызывает `onTouched()` на blur (`:340`), что покрыто кейсом `input-number.spec.ts:607` «should mark as touched on blur». Контракт CVA полон; настоящие дефекты этого класса лежат в другом месте (INP-BUG-04, INP-LIFE-01).
- **«Подсказки и ошибки не связаны с контролом через `aria-describedby` (FF-A11Y-02)»** — опровергнуто как всё ещё открытое. `KbqFormField.updateDescribedByIds()` (`form-field.ts:522-543`) теперь пересчитывает набор id на каждом `ngAfterContentChecked` и записывает его через `kbqSetDescribedByIds` (`form-field-control.ts:86-98`), сохраняя id, заданные потребителем. `KbqInput` корректно *не* реализует необязательный хук `setDescribedByIds`, поэтому применяется путь по умолчанию — запись на хост-элемент. Для `input` действий не требуется.
- **«Переключатель пароля — иконка без роли, имени и состояния (FF-A11Y-04)»** — опровергнуто как всё ещё открытое. `password-toggle.ts:63-70` теперь рендерит `role="button"`, `[attr.aria-label]="accessibleName"` из `kbqInjectA11yLocaleConfiguration()` (`:94, :163-167`) и `[attr.aria-pressed]="!hidden"`, а обработчики Enter и Space висят на хосте (`:84-85`).
- **«У `KbqInput` нет `aria-invalid` (FF-A11Y-05)»** — опровергнуто. `input.ts:41` и `input-password.ts:27` оба биндят `'[attr.aria-invalid]': 'errorState'`. `KbqSelect` в область этого ревью не входит.
- **«Второй `kbqNumberInput` бросает `TypeError: Cannot redefine property` на патче `valueAsNumber`»** — опровергнуто пробой на jsdom. Нативный дескриптор — `configurable: true`, а переопределение, задающее только `get`, сохраняет `configurable`, `enumerable` и исходный сеттер, поэтому повторное создание проходит молча. Это делает INP-BUG-01 хуже, а не лучше: патч никогда не падает громко и никогда не откатывается.
- **«`getPrecision`/`add` — мёртвые хелперы, оставшиеся от старого степпера»** — опровергнуто. Оба находятся на живом пути шага (`input-number.ts:465, 477`) и оба `@public` в отчёте guard (`input.api.md:36, 42`). Дефект — в их арифметике (INP-BUG-03), а не в достижимости.
- **«В пакете отсутствует `_input-theme.scss`»** — опровергнуто. Файл существует (`_input-theme.scss`, 19 строк); он просто содержит миксин типографики, а не цветовую тему, что, согласно инвентаризации, допустимо для контрола, живущего внутри form-field. Оформлено как замечание к именованию в INP-STYLE-01, а не как отсутствие файла.
- **«Файлы `examples.input.*.md` — заглушки `🚧 Documentation in progress 🚧`»** — опровергнуто. Оба файла содержат настоящий заголовок и настоящую вставку `<!-- example(input-change-password) -->`, а `structure.ts:623` задаёт `hasExamples: true`, так что вкладка Examples рендерится корректно. Пробел в документации — в отсутствующем описании API в основном руководстве (INP-DOC-01), а не на поверхности примеров.

Скорректировано при проверке:
- **INP-BUG-01** изначально формулировалась как «числовое поле подменяет `valueAsNumber` на собственном элементе» и оценивалась как P2. Чтение `Object.getPrototypeOf(this.nativeElement)` и подтверждение глобального охвата на jsdom подняли её до P0: патч не ограничен элементом директивы, не откатывается и меняет платформенный API для кода, которого библиотека вообще не касалась.
- **INP-A11Y-01** изначально формулировалась как «двум директивам стоит завести общий счётчик id» — стилистическая придирка. Подтверждение, что оба счётчика дают побайтово одинаковые строки, и прослеживание `[attr.for]="control().id"` из `form-field.html:2` до итоговой ошибочной связки подняли находку до P1 с функциональным симптомом.
- **INP-BUG-05** изначально была оформлена как пробел в документации («не задокументировано, что `type="number"` не поддерживается»). Проба на jsdom показала, что это активно очищает поле, а grep нашёл два dev-шаблона внутри репозитория, которые так делают, — поэтому находка стала дефектом P1 с защитой на стороне библиотеки в качестве исправления.
- **Пункт про `es-LA` в INP-ARCH-02** изначально был оформлен как баг форматирования уровня P2 («испанские числа форматируются по русским правилам»). Прогон настоящего алгоритма под обеими локалями дал идентичный результат, потому что `viewGroupSeparator` перезаписывает символ разделителя; пункт опустился до P3 как мёртвый код.
