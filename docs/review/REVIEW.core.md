## 1. Executive Summary

`core` is not a component — it is the shared foundation every other package composes: date adapters and formatters, the locale layer, the pop-up trigger base class, error-state tracking, focus/key management, the selection primitives, the theme service, the SCSS entry point and the design-token bridge. It is the single highest-churn package in the repository (**341 commits**), the one with the largest published surface (**5 900 lines** of API report, **525** `@public` declarations), and by a wide margin the one with the most untyped members (**62** of the repo's 547 `any`/`unknown` entries in `tools/check-public-api-any/baseline.json` — 11 % of the total from one package).

- **The most serious defect is that the foundation cannot be rendered on a server.** `KbqThemeService` is `providedIn: 'root'` and calls `this.window.matchMedia(...)` in a *field initializer* (`services/theme.service.ts:274`). The bundled server DOM in `@angular/platform-server` implements neither `matchMedia` nor `localStorage` (zero occurrences of either in `fesm2022/init.mjs`), and `KBQ_WINDOW`'s factory hands back that partial object rather than failing loudly (`tokens/window.ts:7-22`). The proof is already in the tree: `apps/docs/src/config.server.ts:6-54` is a hand-written 48-line `KBQ_WINDOW` shim with a load-bearing comment ("Without these, reaching one would hit `undefined` and crash SSR"), while the in-repo SSR dev harness (`packages/components-dev/ssr/config.server.ts`) has no such shim — and `docs/guides/theming.en.md:76` tells server-rendered apps to use exactly this service (CORE-SSR-01).
- **Two published contracts are untrue.** The locale service writes `document.documentElement.lang` from `setLocale()` (`locales/locale-service.ts:190`) but never from its constructor (`:168-183`), so an application that fixes its locale through `kbqLocaleIDProvider` and never switches at runtime gets accessible names in one language under a document declared in another — aggravated by the default being `ru-RU` (`:30`, `locales/a11y.ts:11`), which 12 components read for their ARIA text (CORE-A11Y-01). And `formatters/number/number-formatter.en.md:1` promises that the number pipes "update the output when the language changes"; they are `pure: false` with no cache and no `markForCheck()`, so they build a fresh `Intl.NumberFormat` on **every change-detection pass** (`formatters/number/formatter.ts:200, 269`) and still fail to repaint an `OnPush` host on `setLocale()` — the exact two problems the date family's `BaseLocaleAwareFormatterPipe` solves 30 lines away (CORE-PERF-01).
- **The foundation ships three of several things it exists to unify.** Three error-state mechanisms coexist — `mixinErrorState` (zero users, warns on every construction), `KbqErrorStateTracker` (2 users), and a byte-identical 11-line `updateErrorState()` hand-copied into **six** components (CORE-ARCH-01). Two `FocusKeyManager` symbols coexist: 8 components use the `core` fork, 2 use CDK's, and the fork has no `destroy()` and cannot take arrays or signals (CORE-ARCH-02). And `core/testing` — `MockNgZone`, `patchElementFocus`, `createMouseEvent` — is re-exported straight from the production entry point (`public-api.ts:30`) into every consumer's bundle (CORE-API-01).
- **The most-depended-on subsystem has no tests at all.** `pop-up/` is 1 221 lines, is the base class for both `tooltip` and `popover`, and contains **zero** spec files; `select/` (671 lines, `KbqAbstractSelect`) has none either, and `option/` (1 041 lines) has three cases. Two lifecycle defects live in exactly that untested area: a subscription registered per `show()` that never terminates (CORE-LIFE-01) and host listeners that are removed from the wrong element after `setExternalNativeElement()` (CORE-LIFE-02) — a path a published docs example exercises.

Genuine strengths, and they are substantial. The subsystems that have been through a recent refactor are among the best-documented code in the repository: the locale layer (DS-3897), the time-zone layer (DS-3248), the select-all primitives (DS-3969) and the theme service (DS-3003) all carry JSDoc that explains *why* rather than restating the signature, including the DI traps a reader would otherwise rediscover the hard way. `docs/guides/localization.en.md` and `formatters/date/date-formatter.en.md` are honest about their own legacy — the date guide has a table that tells you which of the three pipe families goes stale and which one reformats on every tick. `tools/check-public-api-any` is a ratchet that fixes the `any` count per package so cleanup cannot be silently undone. `kbqDeepMerge` returns its base untouched when a patch is empty, which is what makes locale overrides referentially stable for `OnPush`. The problems below are almost entirely *accumulated* ones — old mechanisms that were never removed after their replacements landed — not fresh mistakes.

## 3. Prioritized Findings (deduplicated, verified)

### P0 — Release blockers

None.

### P1 — High

**CORE-SSR-01 · `KbqThemeService` cannot be constructed on the server, and `KBQ_WINDOW` ships no server implementation** — `services/theme.service.ts:274, 316`, `tokens/window.ts:7-22`; consumer workaround at `apps/docs/src/config.server.ts:6-54`; missing at `packages/components-dev/ssr/config.server.ts:1-11`; contract at `docs/guides/theming.en.md:76`.
`KbqThemeService` is `@Injectable({ providedIn: 'root' })` and its field initializer runs `private readonly media = this.window.matchMedia('(prefers-color-scheme: dark)')` (`:274`), followed by `fromEvent<MediaQueryListEvent>(this.media, 'change')` in the constructor (`:316`). Neither is guarded by `Platform.isBrowser`, and there is no other `matchMedia` call anywhere in `packages/components` — this is the single unguarded browser-only API in the package. `KBQ_WINDOW` does not save it: its factory returns `inject(DOCUMENT).defaultView || window` (`tokens/window.ts:9-14`), and under Angular SSR `defaultView` is *non-null* — it is the bundled server DOM in `@angular/platform-server/fesm2022/init.mjs`, which contains **zero** occurrences of `matchMedia` and **zero** of `localStorage`. So the `if (!_window) throw` guard at `:16-18` never fires, the token hands back a window that is missing the members `core` actually uses, and the failure surfaces as `this.window.matchMedia is not a function` during the first server render. The evidence that this is not theoretical is in two places in the tree at once: `apps/docs/src/config.server.ts` overrides `KBQ_WINDOW` with a hand-written 48-line object stubbing `matchMedia`, `localStorage`, `location`, `addEventListener`, `getComputedStyle` and `setTimeout`, with a comment at `:44-45` explaining that "without these, reaching one would hit `undefined` and crash SSR"; the SSR dev harness at `packages/components-dev/ssr/config.server.ts` provides only `provideServerRendering()` and a time-zone provider, and therefore cannot render any page that touches the theme service. Meanwhile `docs/guides/theming.en.md:76` directs server-rendered applications straight at this service ("Apps rendered on the server can store it in a cookie instead, so the server already knows which theme to render"), and `KbqThemeCookieStore` (`theme.service.ts:198-241`) exists purely to serve that scenario — a store built for SSR, reachable only through a service that crashes on the server. Note the store layer is already correct: every `localStorage` access in `KbqThemeLocalStorageStore` is wrapped in `try/catch` with an explicit "no-op on the server" comment (`:157-190`). Only the media query was missed.
**Fix:** two independent moves, both needed. (1) Guard the media query: replace the field initializer with a lazily-created, `Platform.isBrowser`-gated value — `private readonly media = inject(Platform).isBrowser ? this.window.matchMedia('(prefers-color-scheme: dark)') : null`, make `systemPrefersDark` default to `false` when it is `null`, and skip the `fromEvent` wiring in that branch (`KbqRectangleItem.getOuterElementWidth()` at `navbar/rectangle-item.ts:42` is the in-repo pattern to copy). (2) Ship the shim: export a `kbqServerWindowProvider()` from `core/tokens` implementing the members `core` actually touches (`matchMedia`, `localStorage`, `getComputedStyle`, `location`, `addEventListener`/`removeEventListener`, `setTimeout`), delete the hand-written copy in `apps/docs/src/config.server.ts` in the same commit — its deletion is the acceptance criterion — and add it to `packages/components-dev/ssr/config.server.ts` so the in-repo SSR harness exercises the path. Guard with a spec that instantiates `KbqThemeService` in a `TestBed` whose `KBQ_WINDOW` is `{}` and asserts it constructs and reports `colorScheme() === 'light'`.

**CORE-A11Y-01 · The document language never follows the initial locale, only subsequent switches** — `locales/locale-service.ts:30, 168-183, 186-193`, `locales/a11y.ts:8-13`; test gap at `locales/locale-service.spec.ts:46-60`.
`KbqLocaleService` owns the `lang` attribute — it injects `KBQ_LOCALE_SERVICE_LANG_ATTR_NAME` (`:166`), whose JSDoc states its purpose as "Attribute name to be used to set the locale in the html element" (`:98`), and writes it with `this.document.documentElement.setAttribute(this.langAttrName, id)` (`:190`). That write lives **only** inside `setLocale()`. The constructor takes a different path: it calls `this._localeId.set(id || KBQ_DEFAULT_LOCALE_ID)` and `this._data.set(this.register(...))` directly (`:178-180`) and never touches the document. The result is an asymmetry with a real accessibility consequence: an application that fixes its locale the documented way — `providers: [kbqLocaleIDProvider('en-US'), kbqLocaleServiceProvider()]` (`docs/guides/localization.en.md:43`) — renders English strings while `<html lang>` keeps whatever `index.html` declared, and an application that never provides a locale service at all gets the `ru-RU` defaults (`:30`; `KBQ_A11Y_LOCALE_CONFIGURATION`'s factory is literally `() => ruRULocaleData.a11y`, `locales/a11y.ts:11`) under an English document. Twelve components read those strings for their accessible names (`breadcrumbs`, `content-panel`, `datepicker/calendar-header`, `dl`, `form-field/cleaner`, `form-field/password-toggle`, `inline-edit`, `modal` ×2, `notification-center`, `popover`, `sidepanel`), so a screen reader is handed "Закрыть", "Показать пароль" and "Предыдущий месяц" with an English speech synthesizer — WCAG 3.1.1 (Language of Page) and 3.1.2 (Language of Parts). This is a WCAG judgement, not an automated axe failure: axe checks that `lang` is present and valid, not that it matches the language of the text. The gap survived because both `lang` specs call `setLocale()` explicitly before asserting (`locale-service.spec.ts:49, 58`); nothing asserts the constructor's behaviour.
**Fix:** move the document write into a private `applyLang(id)` and call it from both the constructor (after `:178`) and `setLocale()`. Add the mirror spec — construct the service with `kbqLocaleIDProvider('en-US')` and assert `document.documentElement.lang === 'en-US'` *without* calling `setLocale`. Separately, document the `ru-RU` default's accessibility consequence in `docs/guides/localization.en.md` next to the existing paragraph at `:24-25`, and state there that an application whose UI language is not Russian must provide a locale service even if it never switches locales at runtime.

**CORE-PERF-01 · The number and filesize pipes rebuild `Intl.NumberFormat` on every change-detection pass and still miss locale changes on `OnPush` hosts** — `formatters/number/formatter.ts:148-152, 160, 187, 200, 218-225, 233, 260, 269, 284-290, 297`, `formatters/filesize/formatter.ts:15-34, 50`; contract at `formatters/number/number-formatter.en.md:1`; correct counterpart at `formatters/date/formatter.pipe.ts:104-170`.
All four pipes in this family — `kbqNumber`, `kbqTableNumber`, `kbqRoundNumber`, `kbqDataSize` — are declared `pure: false` (`:151, 224, 289`, `filesize/formatter.ts:17`), so `transform()` runs on every check of the host view. None of them caches anything: `KbqDecimalPipe.transform` re-parses `digitsInfo` (`:187`) and constructs `new Intl.NumberFormat(currentLocale, options)` (`:200`) on every single call, and `KbqTableNumberPipe` does the same at `:260, 269`. Constructing an `Intl.NumberFormat` is the expensive half of number formatting — it is precisely why the date family caches — and `kbqTableNumber` is named, documented and intended for tables, i.e. for hundreds of simultaneous instances. Worse, the locale reactivity the guide promises does not work where it matters: each pipe subscribes to `localeService.changes` and the handler is `(newId: string) => (this.id = newId)` (`:160, 233, 297`) — it writes a field and calls **no** `markForCheck()`. An impure pipe is only evaluated when its host view is checked, and an `OnPush` host is not checked unless something marks it, so `setLocale()` at runtime leaves every number rendered inside an `OnPush` component (which AGENTS.md mandates for every component in the library) formatted in the previous locale. `formatters/number/number-formatter.en.md:1` states the opposite in its first sentence: "Formatters apply the norms of the current locale and update the output when the language changes." The fix already exists in the same package: `BaseLocaleAwareFormatterPipe` (`formatters/date/formatter.pipe.ts:104-170`) caches by `(value, args, localeId, timezone)` and calls `this.changeDetectorRef.markForCheck()` from both the locale subscription (`:124-125`) and the time-zone effect (`:133`) — the same approach `AsyncPipe` uses. Only the 15 new `kbq*` date pipes extend it.
**Fix:** move the number/filesize pipes onto the same base. Concretely: extract the caching half of `BaseLocaleAwareFormatterPipe` into a small `BaseCachedLocaleAwarePipe` that owns the `(value, args, localeId)` cache and the `markForCheck()` wiring, have `KbqDecimalPipe`/`KbqTableNumberPipe`/`KbqRoundDecimalPipe`/`KbqDataSizePipe` extend it, and memoize the `Intl.NumberFormat` itself by `(locale, options)` in a bounded module-level `Map` — `datetime/timezone.ts:71-93` is the in-repo pattern for a bounded formatter cache, LRU eviction included. Guard with two specs: one asserting that a second `transform()` with identical arguments does not construct a new formatter (spy on `Intl.NumberFormat`), and one that renders `{{ 1234567 | kbqTableNumber }}` inside an `OnPush` host, calls `setLocale('en-US')`, and asserts the rendered text changed without any other input changing. The second spec fails today.

### P2 — Should fix

**CORE-ARCH-01 · Three competing error-state mechanisms; the one that works is copy-pasted into six components** — `common-behaviors/error-state.ts:34-64, 70-97`, `error/error-state-matcher.ts:1-63`; duplicates at `input/input.ts:249-260`, `input/input-password.ts:222-233`, `textarea/textarea.component.ts:282-293`, `select/select.component.ts:1203-1214`, `tree-select/tree-select.component.ts:969-980`, `tags/tag-list.component.ts:536-547`; tracker users at `datepicker/datepicker-input.directive.ts:535`, `timepicker/timepicker.directive.ts:409`.
`core` publishes three ways to compute an error state and no guidance on which to use. (1) `mixinErrorState` (`error-state.ts:34-64`) has **zero** callers anywhere in the repository — the only mention outside `core` is a comment in `file-upload/file-upload.ts:117` explaining that its author chose not to use it — yet it logs `console.warn('mixinErrorState deprecated and will be deleted in next major release')` from its constructor in dev mode (`:45-48`), i.e. once per instance, which for a list of options would be once per row. (2) `KbqErrorStateTracker` (`:70-97`) is the intended replacement and has two users, `datepicker` and `timepicker`. (3) Six components implement the same eleven lines by hand, character-for-character identical across all six: `const oldState = this.errorState; const parent = this.parentFormGroup || this.parentForm; const matcher = this.errorStateMatcher || this.defaultErrorStateMatcher; …`. Six copies means six places to change when the semantics move, and it means the tracker — which `core` maintains and tests — governs two of the eight form controls in the library. The likely reason nobody adopted it is mechanical: `KbqErrorStateTracker`'s constructor takes five positional arguments (`:77-83`) including a `Subject<void>` the caller must own, so wiring it costs more than copying the method. Note the matcher layer itself is fine and widely used — `kbqErrorStateMatcherProvider` and the four shipped matchers appear across 8-10 spec suites.
**Fix:** give the tracker an injection-context factory — `kbqInjectErrorStateTracker(stateChanges: Subject<void>)` that resolves `ErrorStateMatcher`, `NgControl`, `FormGroupDirective` and `NgForm` itself with `{ optional: true }` — so adoption is one line instead of five arguments. Migrate the six components to it one at a time, each with its existing error-state specs unchanged as the regression guard (`input.spec.ts`, `select.component.spec.ts` and `tag-list.component.spec.ts` all already assert `errorState` transitions). Then delete `mixinErrorState`, `mixinDisabled` and `mixinTabIndex` together (see CORE-API-03) — that is a breaking API change and needs an `ng-update` schematic in `packages/schematics`.

**CORE-LIFE-01 · Every `show()` registers a subscription on the trigger's `DestroyRef` that never terminates** — `pop-up/pop-up-trigger.ts:387-393`, `pop-up/pop-up.ts:47, 59-65`.
`KbqPopUpTrigger.show()` wires the freshly attached pop-up's visibility stream with `this.instance.visibleChange.pipe(distinctUntilChanged(), takeUntilDestroyed(this.destroyRef)).subscribe(...)` (`pop-up-trigger.ts:387-393`). The `DestroyRef` is the **trigger's**, not the instance's — and `takeUntilDestroyed` registers an `onDestroy` callback that is only unregistered when the chain tears down, which happens either when the trigger is destroyed or when the source completes. `KbqPopUp.ngOnDestroy()` completes `onHideSubject` and `hovered` (`pop-up.ts:63-64`) but **not** `visibleChange` (`:47`), and Angular does not complete `EventEmitter` outputs on destroy. So the chain never terminates: a trigger that is shown and hidden *N* times accumulates *N* live subscriptions to *N* destroyed component instances plus *N* `onDestroy` registrations on its own `DestroyRef`, none of which are released until the trigger itself is destroyed. For a tooltip on a toolbar button in a long-lived application, *N* is however many times the user hovered it. The neighbouring `afterHidden()` subscription three lines above (`:381`) does not have the problem — `onHideSubject` *is* completed — and the `viewportRuler` subscription six lines below correctly uses `takeUntilDestroyed(this.instance.destroyRef)` (`:405`), so the file already contains both correct patterns.
**Fix:** change `:388` to `takeUntilDestroyed(this.instance.destroyRef)`, matching `:405`, and add `this.visibleChange.complete()` to `KbqPopUp.ngOnDestroy()` (`pop-up.ts:59-65`) as a belt-and-braces measure for any other subscriber. Guard with a spec in the (currently non-existent — see CORE-TEST-01) `pop-up` suite that shows and hides a tooltip 50 times and asserts the trigger's subscription count does not grow; a cheaper proxy is to assert that a destroyed instance's `visibleChange.observed === false`.

**CORE-LIFE-02 · Host listeners are removed from the wrong element after `setExternalNativeElement()`** — `pop-up/pop-up-trigger.ts:297-303, 516-544, 578-588, 667-675`; consumer at `tooltip/tooltip.component.ts:642-651`; exercised by `packages/docs-examples/components/tooltip/tooltip-dynamic/tooltip-dynamic-example.ts:42`.
`initListeners()` binds the trigger's DOM listeners through `this.addEventListener`, which resolves its target lazily: `this.getNativeElement().addEventListener(event, listener)` (`:668-670`). `getNativeElement()` returns `this.externalNativeElement || this.elementRef.nativeElement` (`:581`). `setExternalNativeElement(value)` (`:586-588`) reassigns that field at runtime and never resets it. `KbqTooltipTrigger.showForMouseEvent()` calls it with `event.currentTarget` (`tooltip.component.ts:647`) — long after `ngOnInit` bound the listeners on the host. From that moment `getNativeElement()` returns the external element permanently, so `ngOnDestroy()`'s `this.listeners.forEach(this.removeEventListener)` (`:300`) calls `removeEventListener` on the *external* element for handlers that were added to the *host*: the host keeps its `mouseenter`/`mouseleave`/`click` handlers forever, and because those handlers are bound closures over the directive, they keep the destroyed directive and its overlay machinery reachable. `clearListeners()` (`:641-645`) has the same defect, so a later `initListeners()` — which `trigger` setters call — compounds it by binding a second set on the external element while the first set stays on the host. This is a real code path, not a hypothetical: the published `tooltip-dynamic` docs example drives it on every `mouseover` (`tooltip-dynamic-example.ts:42`). Related, smaller: `ngOnDestroy()` also never completes the `hovered` `BehaviorSubject` (`:109`), unlike `KbqPopUp`, which does (`pop-up.ts:64`).
**Fix:** store the bound target alongside the handler — change `listeners` from `Map<string, EventListener>` to `Map<string, { target: HTMLElement; listener: EventListener }>`, or capture `const target = this.getNativeElement()` once in `initListeners()` and keep it in a private `listenerTarget` field that `clearListeners()`/`ngOnDestroy()` use. Then make `setExternalNativeElement()` rebind explicitly: `clearListeners(); this.externalNativeElement = value; this.initListeners();`. Add `this.hovered.complete()` to `ngOnDestroy()`. Guard with a spec that calls `showForMouseEvent` against a second element, destroys the fixture, dispatches `mouseenter` on the original host and asserts no overlay is created.

**CORE-ARCH-02 · The `ListKeyManager` fork has diverged from CDK's: no `destroy()`, `QueryList`-only, and two `FocusKeyManager` symbols now coexist** — `a11y/key-manager/list-key-manager.ts:22, 63-77, 143-186, 371-378`, `a11y/key-manager/focus-key-manager.ts:14`, `a11y/key-manager/activedescendant-key-manager.ts:16`; CDK counterpart at `node_modules/@angular/cdk/list-key-manager.d.d.ts:36-37, 138`; consumers split 8/2.
`core` forks CDK's `ListKeyManager` (459 lines) and the fork has fallen behind on two contracts. (1) **No `destroy()`.** CDK's declares `destroy(): void` (`list-key-manager.d.d.ts:138`); the fork has none, so `typeaheadSubscription` (`list-key-manager.ts:152`) is torn down only by a *second* call to `withTypeAhead()`. The typeahead chain is `letterKeyStream.pipe(tap(...), debounceTime(200), …)` (`:154-186`) — a pending debounce survives the host component's destruction and then calls `setActiveItem(index)` on a stale item array and pushes through `this.change` (`:213-215`), reaching a subscriber whose view is gone. `tabOut` and `change` are never completed either. No consumer calls `destroy()` — a repo-wide grep for `keyManager.destroy` returns nothing — because the fork does not offer it. (2) **`QueryList` only.** The fork's constructor is `constructor(private _items: QueryList<T>)` (`:63`); CDK's accepts `QueryList<T> | T[] | readonly T[]` and, with an `Injector`, `Signal<T[]>` (`:36-37`). That is why the signal-queries migration could not convert key-manager-backed option lists, and it is why the repo now runs **two** `FocusKeyManager` classes with the same name: `accordion/accordion.ts:1` and `tabs/paginated-tab-header.ts:1` import CDK's (accordion passing the second `Injector` argument that the fork does not have), while `app-switcher`, `autocomplete`, `dropdown`, `list`, `navbar`, `select`, `tags` and `tree` import `core`'s. A reader looking at `FocusKeyManager` in this repository cannot tell which one they have without checking the import. Two smaller residues of the fork: `withTypeAhead()` only validates `getLabel` when `_items.length` is non-zero at configuration time (`:145-147`), so a list populated asynchronously skips the check and throws from `item.getLabel!()` (`:178`) on the user's first keystroke instead; and `getItemsArray()` still branches on `this._items instanceof QueryList` (`:456`) although the declared type makes the other branch unreachable.
**Fix:** decide the direction deliberately rather than by omission. Preferred: delete the fork and re-export CDK's `ListKeyManager`/`FocusKeyManager`/`ActiveDescendantKeyManager` from `core/a11y`, keeping `IFocusableOption`/`Highlightable` as aliases — CDK's has every method the fork has plus `destroy()`, `withPageUpDown`, array/signal sources and `trackBy`, and the eight consumers change only their teardown. If the fork must stay (`setFocusOrigin`/`getFocusOrigin` and `setNextPageItemActive` are local additions), then at minimum add `destroy()` completing `tabOut`, `change` and `letterKeyStream` and unsubscribing `typeaheadSubscription`, call it from all eight consumers' `ngOnDestroy`, widen the constructor to `QueryList<T> | readonly T[]`, and move the `getLabel` validation into the typeahead subscriber. Guard with a `fakeAsync` spec that presses a letter, destroys the host before the 200 ms debounce elapses, and asserts `change` does not emit (`list-key-manager.spec.ts` already has 44 cases to extend).

**CORE-API-01 · Test-only helpers are published from the production entry point** — `public-api.ts:30`, `testing/public-api.ts:1-6`, `testing/event-objects.ts:1`, `testing/mock-ng-zone.ts:10-16`, `testing/element-focus.ts:8-11`; API report at `tools/public_api_guard/components/core.api.md:268, 313, 4533-4546, 4661, 5884`.

## 4. Recommended Remediation Phases

**Phase 1 — Make the foundation renderable on a server.**
IDs: CORE-SSR-01, CORE-SSR-02. Guard `KbqThemeService`'s media query behind `Platform.isBrowser`, publish a `kbqServerWindowProvider()` from `core/tokens`, delete the hand-written shim in `apps/docs/src/config.server.ts` and add the provider to the SSR dev harness. **Phase 2 — Repair the two published contracts.**
IDs: CORE-A11Y-01, CORE-PERF-01. Write `lang` from the locale service's constructor as well as `setLocale()`, and move the number/filesize pipes onto a cached, `markForCheck`-ing base with a memoized `Intl.NumberFormat`. Both are behaviour changes a consumer can observe, both are cheap, and both come with a spec that fails today. Independent of Phase 1 and of each other.

**Phase 3 — Close the two lifecycle holes, with the tests that should have caught them.**
IDs: CORE-TEST-01, CORE-LIFE-01, CORE-LIFE-02, CORE-ARCH-04. Write `pop-up/pop-up-trigger.spec.ts` first — the two leaks are only demonstrable with it — then fix the `destroyRef` target and the listener-target tracking, and clean up the triple `subscribeOnClosingActions()` and the `instance: any` escape in the same pass. Add the `kbqDeepMerge` and error-state-matcher specs here too; they are prerequisites for Phase 4's refactors being verifiable rather than assumed.

**Phase 4 — Consolidate the duplicated foundations.**
IDs: CORE-ARCH-01, CORE-ARCH-02, CORE-API-01, CORE-API-03, CORE-API-04, CORE-ARCH-03. **Phase 5 — Documentation and hygiene.**
IDs: CORE-API-02, CORE-DOC-01, CORE-STYLE-01. ## Appendix A — Review Methodology

`core` is roughly 26 000 lines across 27 subdirectories, which is more than one pass can read honestly. The review therefore started by enumerating every subdirectory with its source and spec line counts, then selected subsystems by two criteria — number of dependents inside the repository, and blast radius of a defect. That produced the in-depth list in the Scope line above (locale layer, formatters, `pop-up/`, theme service, key managers, selection, datetime, error state, `KBQ_WINDOW`/utils, forms, the SCSS entry points, the public entry point) and an explicit deferred list (`option/`, `overlay/`, `select/common.ts`, `highlight/`, `search/`, `overflow-shadow/`, `form-field/`, `keycodes/`, `validation/`, `styles/typography`, `styles/visual`). Every candidate was then cross-checked against at least one independent source: the workspace compiler settings (`tsconfig.json:17-22, 114-118` — note `strict` is *not* on; `strictNullChecks` and `strictFunctionTypes` are, `noImplicitAny` is not), the API guard report and the `any` ratchet baseline, `playwright.config.ts`, the published guides under `docs/guides/`, the bundled server DOM in `node_modules/@angular/platform-server/fesm2022/init.mjs`, the CDK declarations in `node_modules/@angular/cdk/`, and — most productively — in-repo consumers found by grep. Consumer evidence is what upgraded CORE-SSR-01 from a code smell to a confirmed defect (the shim already exists in `apps/docs`), what made CORE-ARCH-01 concrete (six byte-identical copies), and what made CORE-LIFE-02 real rather than theoretical (a published docs example drives the path). Refuted during verification:
- **"`KBQ_LOCALE_SERVICE` used with `useClass` silently builds a second instance and breaks `setLocale`"** — the behaviour is real but it is not an undocumented trap. `docs/guides/localization.en.md:28-30` warns about it in as many words, and `kbqLocaleServiceProvider`'s own JSDoc repeats the warning (`locales/locale-service.ts:251-263`). No finding.
- **"A nested `kbq*LocaleConfigurationProvider` shadows the sections an ancestor overrode, because Angular does not merge `multi` tokens across DI levels"** — refuted for the current code. `kbqLocaleConfigurationOverrideProvider` contributes a second `multi` entry whose factory re-contributes the inherited batch via `inject(..., { skipSelf: true, optional: true })` (`locales/configuration.ts:39-47`), and `kbqInjectLocaleConfiguration` de-duplicates with a `Set` that preserves ancestor-before-descendant precedence (`:74-77`). Both moves carry comments explaining exactly this hazard. The trap predates DS-3897 (`9d5b99010 feat(core): type the locale layer`) and is fixed.
- **"The 34 unprefixed and `ImpurePipe` date pipes are an undocumented duplicate API"** — refuted as stated. `formatters/date/date-formatter.en.md:24-31` is a table naming all three families and their trade-offs verbatim, including "**the string goes stale on a locale change**" for the unprefixed family and "an impure pipe with no cache: reformats on every change detection cycle" for the suffixed one, and it marks `kbq*` as recommended. What survives is only the missing `@deprecated` tag, folded into CORE-API-03's fix.
- **"Importing `SharedResizeObserver` from `@angular/cdk/observers/private` is a supply-chain hazard"** — refuted as a finding. It is the established convention in this repository (`core/overflow-shadow`, `actions-panel`, `clamped-text`, `code-block`), and `overflow-shadow.ts:54, 94` documents why the observer is needed. Worth re-checking on each CDK major, not worth a ticket.
- **"The number pipes read a `null` locale because `KBQ_LOCALE_ID` has no factory"** — refuted. `KbqLocaleService.changes` is a `BehaviorSubject` seeded with the active id in the constructor (`locales/locale-service.ts:182`), so the subscription at `formatters/number/formatter.ts:160` delivers the current id synchronously at construction. The pipes' locale *value* is correct; only their reactivity and caching are not (CORE-PERF-01).
- **"`ListKeyManager` leaks its `QueryList.changes` subscription"** — refuted. Angular calls `QueryList.destroy()` on view destruction, which completes `changes`, so the subscription at `list-key-manager.ts:65-75` terminates on its own. The real gap is the missing `destroy()` for the typeahead stream, which no lifecycle completes (CORE-ARCH-02).
- **"`KBQ_WINDOW` throws a clear error when no window is available on the server"** — refuted. `inject(DOCUMENT).defaultView` is non-null under Angular SSR, so the `if (!_window) throw` guard at `tokens/window.ts:16-18` never fires; the token returns a partially-implemented window instead. Folded into CORE-SSR-01 as part of its evidence.
- **"`packages/components/_index.scss` forwards only `core`"** — corrected. It is three lines and forwards three `core` paths (`core`, `core/styles/theming/theming`, `core/styles/koobiq-theme`), which is what makes CORE-ARCH-03's inverted dependency reachable from the library's root SCSS entry point rather than only from a deep import.
