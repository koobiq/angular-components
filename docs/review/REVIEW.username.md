# Koobiq `username` Component — Code Review & Improvement Plan

> Scope: `packages/components/username` (component, template, both pipes + the text builder, tokens, SCSS, Jest spec + snapshot, e2e fixture + Playwright spec, user guides, API guard report, docs examples, dev app, in-repo consumers) · Commit `b665e503` · 2026-08-28
> Generated by a multi-dimension review (architecture, correctness, accessibility, i18n/RTL, public API & types, styles, tests, docs) with manual verification of every finding against the source, the API guard report, the design-token set and the workspace compiler settings. 15 findings confirmed (P0×0, P1×3, P2×8, P3×4); 6 candidate findings refuted during verification (see Appendix A). This document is a review + roadmap; no source is modified by it.

## 1. Executive Summary

`kbq-username` renders a person from a `KbqUserInfo` record: a formatted full name, a login, and a site hint, in three layout modes and four visual styles. The package is small (131 + 126 + 76 + 35 lines of TS/HTML) and modern — signals throughout, `OnPush`, host object, no `@HostBinding`, no RxJS, no `window`. The defects are not in the rendering machinery; they are in the *formatting contract*, and they are the kind that fail silently.

- **The component drops the user's name whenever the profile lacks one of `firstName` / `lastName`.** `hasFullName` requires **both** (`username.ts:124`), and every branch of the template is gated on it (`username.html:8, 23, 26`). A profile like `{ lastName: 'Root', login: 'mroot' }` renders only `mroot`; a profile with a first and middle name but no surname and no login renders an **empty element**. Meanwhile `KbqUsernamePipe.transform` on the same record returns `"Root"` — so the search example (`username-search-example.ts:86-91`) matches on a string the component refuses to display. Nothing in the 18-case Jest suite covers a partial profile (USR-BUG-01).
- **The custom pipe's own default format cannot work with the shipped default mapping.** `kbqDefaultFullNameFormatCustom = 'L f. m.'` (`constants.ts:5`) uses the `L` key, but the `KBQ_PROFILE_MAPPING` factory only maps `f`, `m`, `l`, `.` (`constants.ts:23-29`) — and the type it satisfies, `KbqFormatKeyToProfileMapping`, *excludes* `F`/`M`/`L` by construction (`types.ts:41-48`). Unmapped letters are emitted verbatim (`username.pipe.ts:84-88`), so `{{ user | kbqUsernameCustom }}` with the library's own defaults prints `L M. A.` — a literal capital `L` where the surname belongs (USR-BUG-02).
- **Injecting the pipe, exactly as the guide instructs, silently bypasses a scoped mapping.** Both pipes carry `@Injectable({ providedIn: 'root' })` *and* `@Pipe` (`username.pipe.ts:11-15, 55-59`), producing both a `ɵprov` and a `ɵpipe` (`username.api.md:69-71, 113-115`). The injected instance is a root singleton, so its `inject(KBQ_PROFILE_MAPPING)` resolves at the root injector and never sees the component-level override that the token exists for and that the docs example itself uses (`username-custom-example.ts:86-88`). `username.en.md:27` promises the injected `transform` "returns the same string the component renders by default"; with any scoped mapping that is untrue (USR-ARCH-01).
- **Names are abbreviated by code unit and shown without any accessible expansion.** Initials are taken with `fieldValue[0]` (`username.pipe.ts:40, 93`), which splits a surrogate pair — a name starting outside the BMP yields a lone surrogate rendered as `�.` (USR-BUG-03). The rendered element carries no `role`, no `aria-label`, no `<abbr>`; the `kbq-title` tooltip defaults to the host's own `textContent` (`title.directive.ts:171-172`), i.e. the same abbreviated string, so nothing anywhere exposes the unabbreviated name, and the `(corp)` parenthetical has no programmatic label (USR-A11Y-01). The package contains zero ARIA attributes and no `kbqInjectA11yLocaleConfiguration()` usage.
- **Test coverage is broad in shape and hollow in substance.** All 18 Jest cases pass an explicit `customMapping`, so the shipped `KBQ_PROFILE_MAPPING` default — the thing every default-configured consumer actually runs — is never executed once (`username.spec.ts:36-41, 77-85`). Only two cases touch the component itself, and neither `isCompact`, nor truncation, nor `KbqUsernameModule` is exercised anywhere; the single Playwright screenshot renders auto-sized `<td>`s where nothing can ever overflow (USR-TEST-01).

Genuine strengths worth preserving: the layout SCSS is a small, well-factored piece of work — a `_kbq-username-content-wrapper` mixin that transparently redirects every layout rule onto a projected custom view (`username.scss:5-10`), four style variants driven entirely by two CSS custom properties, the repo's own `rtl-prop` helper for the inline gap, and zero hardcoded colours. The public surface is signal-first with correct `booleanAttribute` coercion, the `kbqBuildUsernameText` helper is a thoughtful answer to "how do I search over what this renders", and six real docs examples cover the component from overview to a filter-bar integration.

## 3. Prioritized Findings (deduplicated, verified)

### P0 — Release blockers

None.

### P1 — High

**USR-BUG-01 · A profile missing either `firstName` or `lastName` loses its name entirely, and can render an empty element** — `username.ts:119-125`, `username.html:7-10, 21-28`.
`hasFullName` is `userInfo?.lastName && userInfo?.firstName` (`username.ts:124`) — a logical AND, so it is falsy unless **both** fields are present. Every place the formatted name reaches the DOM is gated on it: the non-compact branch renders the primary span only `@if (hasFullName())` (`username.html:8-10`), and the compact branch does the same, falling back to the login only when `hasFullName()` is false (`username.html:23-28`). The consequences for ordinary data are severe and silent. `{ lastName: 'Root', login: 'mroot' }` renders `mroot` and nothing else — the surname is discarded even though `KbqUsernamePipe.transform` on that record returns `"Root"` (the loop at `username.pipe.ts:33-45` skips absent fields individually, exactly as it should). `{ firstName: 'Maxwell', middleName: 'Alan' }` — a profile with a name but no login — renders **nothing at all**: no primary span, no login, an empty `<kbq-username>` element with three modifier classes and no text. Mononymic names, service accounts, imported directories with a single `displayName` mapped onto `lastName`, and most non-Western naming systems all land in this hole. The divergence is directly observable in the shipped search example: `username-search-example.ts:86-91` filters on `kbqBuildUsernameText({ name: this.usernamePipe.transform(user), … })`, so a query matching a partial profile's surname produces a result row that displays no surname. No Jest case constructs a partial profile — `mockProfile` (`username.spec.ts:29-33`), `TestComponent.userInfo` (`:188-193`) and the e2e fixture (`e2e.ts:43-49`) are all fully populated.
**Fix:** stop treating "has a full name" as a precondition for rendering a name. Replace `hasFullName` with `hasName = computed(() => !!this.formattedName())`, where `formattedName` is the pipe result computed once (see USR-ARCH-01 for how to obtain a correctly-scoped pipe instance), and gate the primary span on that — the pipe already degrades gracefully to whatever fields exist. Keep the login fallback for the genuinely nameless case, and add an explicit empty-state branch so `<kbq-username>` with an unusable profile renders a deliberate placeholder rather than an empty box. Guard with a Jest table over `{}`, `{ lastName }`, `{ firstName }`, `{ firstName, middleName }`, `{ login }` and the full record, asserting the rendered `textContent` in both `isCompact` states — five of those six cases fail against the current implementation.

**USR-BUG-02 · `kbqUsernameCustom`'s own default format is incompatible with the shipped default mapping and prints a literal `L`** — `constants.ts:5, 20-30`, `username.pipe.ts:64-97`, `types.ts:41-48`.
`KbqUsernameCustomPipe.transform` defaults `format` to `kbqDefaultFullNameFormatCustom = 'L f. m.'` (`username.pipe.ts:66`, `constants.ts:5`). Its resolution rule is: look the character up in the mapping; if there is no mapped field, **emit the character verbatim** (`username.pipe.ts:84-88`) — that is how the spaces and dots in the format survive. But the default `KBQ_PROFILE_MAPPING` factory maps only `f`, `m`, `l` and `.` (`constants.ts:25-28`), and it is typed `satisfies KbqFormatKeyToProfileMapping<…>` (`constants.ts:29`) — a mapped type that *excludes* `FirstNameFull`, `MiddleNameFull` and `LastNameFull` by construction (`types.ts:41-48`). So `L` is unmapped, falls into the verbatim branch, and `{{ user | kbqUsernameCustom }}` with the library's own defaults renders `L M. A.` for Maxwell Alan Root: a capital `L` standing where the surname should be. The token accepts the extended shape too (`constants.ts:20-22`), so the fix is a one-line default — but nothing pushes a consumer towards it, and the evidence that people hit this is in the repo: `username-custom-example.ts` provides an extended `KBQ_PROFILE_MAPPING` at component level (`:86-88`) *and* passes the same object again as the third pipe argument (`:47`), belt and braces, for a call that should have needed neither. The mirror-image defect exists on the plain pipe: `KbqUsernamePipe` with a `F`/`M`/`L` format returns the empty string (every key is unmapped, so `profile[undefined]` is falsy and the loop emits nothing, `username.pipe.ts:35-43`), which is at least type-discouraged rather than wrong-looking.
**Fix:** make the shipped default mapping satisfy `KbqFormatKeyToProfileMappingExtended` — add `[KbqUsernameFormatKey.FirstNameFull]: 'firstName'`, `MiddleNameFull: 'middleName'`, `LastNameFull: 'lastName'` to the factory in `constants.ts:23-29` and change the `satisfies` clause accordingly. That keeps `KbqUsernamePipe` unchanged (it ignores keys its own format never contains) and makes `kbqUsernameCustom` correct out of the box. Additionally make the verbatim-emit branch loud in dev mode: `!field` should distinguish "this character is punctuation/whitespace" from "this character is a `KbqUsernameFormatKey` with no mapping", and `console.warn` in the latter case — silently printing a format key as literal text is the mechanism that hid this. Guard with a Jest case that resolves the pipe **without** a `customMapping` argument and asserts `'Root M. A.'`; today no test in the file omits that argument.

**USR-ARCH-01 · The pipes are root singletons, so `inject(KbqUsernamePipe)` — the documented pattern — ignores any scoped `KBQ_PROFILE_MAPPING`** — `username.pipe.ts:11-17, 55-61`, `constants.ts:17-30`, `username.en.md:27`, `username.ru.md:23`, `username.api.md:69-71, 113-115`.
Both pipe classes carry two Angular decorators: `@Injectable({ providedIn: 'root' })` above `@Pipe({ … })` (`username.pipe.ts:11-15` and `:55-59`). The compiler emits both records — the API report shows `ɵpipe` *and* `ɵprov` on each class (`username.api.md:67-71, 111-115`) — which means there are two independent instantiation paths with two different injectors. Used in a template, the pipe is instantiated per view against the node injector, so a component-level `{ provide: KBQ_PROFILE_MAPPING, useValue: … }` is visible. Obtained with `inject(KbqUsernamePipe)`, it is the **root** singleton, and its `inject(KBQ_PROFILE_MAPPING, { optional: true })` (`username.pipe.ts:17`) resolves against the root injector — the scoped override is invisible. Providing a mapping at component or route level is the token's entire purpose (`constants.ts:17-19`, and `username-custom-example.ts:86-88` does exactly that), so the same class deliberately produces two different strings for the same profile depending on how you got hold of it. Both guides recommend precisely the injected form for search — "inject `KbqUsernamePipe` as a service and call its `transform` method — it returns the same string the component renders by default" (`username.en.md:27`, `username.ru.md:23`) — and two shipped examples follow that advice (`username-search-example.ts:67`, `username-filter-bar-option-example.ts:47`). The promise holds only for consumers who never scope the mapping; for everyone else the filter silently searches a different string than the list displays.
**Fix:** decouple the two roles. Keep `@Pipe` on the pipe classes and drop `@Injectable({ providedIn: 'root' })`; expose the formatting logic as a plain injectable service (`KbqUsernameFormatter`, `providedIn: 'root'`) whose `transform` takes the mapping as an argument, or as a free function `kbqFormatUsername(profile, format, mapping)`, and have both pipes delegate to it. Consumers who want the component's exact string then call `kbqFormatUsername(profile, format, inject(KBQ_PROFILE_MAPPING))` from their own injection context, which resolves the mapping where *they* live. Update `username.en.md:27` / `username.ru.md:23` and both examples to the new form. This changes the public surface, so run `yarn run build:components` then `yarn run approve-api`; removing `providedIn: 'root'` from a class consumers may already inject is breaking and needs an `ng-update` migration (see `project_breaking_changes_need_migration_schematics`). Guard with a spec that provides a component-scoped `KBQ_PROFILE_MAPPING` and asserts the injected and template paths agree — today they do not.

### P2 — Should fix

**USR-API-01 · One format enum, two mutually incompatible interpretations, and JSDoc that is wrong for both** — `types.ts:4-35, 41-57`, `username.pipe.ts:33-45, 81-94`.
`KbqUsernameFormatKey` documents its lowercase members as the short form and its uppercase members as the full form: "Short form of the first name (e.g., `John` → `J`)" (`types.ts:5-8`), "Full form of the first name" (`:10-13`). Neither pipe implements that. `KbqUsernameCustomPipe` derives shortness from the letter's **case** — `const isShort = letter === letter.toLowerCase()` (`username.pipe.ts:90`) — which matches the JSDoc, but only because the mapping happens to define both cases; the enum value itself carries no meaning. `KbqUsernamePipe` derives shortness from a **following dot** — `const isShort = array[index + 1] === KbqUsernameFormatKey.Dot` (`username.pipe.ts:39`) — so in its own default format `'lf.m.'` (`constants.ts:7`) the `l` key, documented as "Short form of the last name" (`types.ts:26-28`), produces the *full* surname, and `f` produces an initial only because a `.` follows it. Two pipes, one enum, opposite rules, and a doc comment that describes the second one's fields while the first one is the library default. The two format constants compound it: `kbqDefaultFullNameFormat` and `kbqDefaultFullNameFormatCustom` carry byte-identical JSDoc — "Default name format: Last name full, first and middle as initials." (`constants.ts:4-7`) — for strings (`'lf.m.'`, `'L f. m.'`) that are not interchangeable in either direction.
**Fix:** document the rule at the point where it is implemented. Give each pipe a class-level JSDoc block stating its own rule ("`KbqUsernamePipe`: a key followed by `.` renders an initial, otherwise the full value; separators are inserted automatically" vs "`KbqUsernameCustomPipe`: lowercase keys render an initial, uppercase render the full value; every unmapped character is emitted verbatim"), rewrite the per-member JSDoc on `KbqUsernameFormatKey` to describe the *field* rather than a form the enum does not control, and give the two default constants distinct comments naming the pipe each belongs to. Reflect both rules in `username.en.md` / `username.ru.md`, which today mention neither. Adding JSDoc to public members removes their `(undocumented)` markers and changes `username.api.md`, so fold this into the same `build:components` + `approve-api` cycle as USR-API-03.

**USR-A11Y-01 · No accessible semantics, no expansion of the abbreviated name, and an unlabelled `(site)` parenthetical** — `username.ts:76-94` (host block), `username.html:9, 13-19, 22-33`, `title.directive.ts:171-172`; zero ARIA in the package.
The host block binds a class and nothing else (`username.ts:89-92`); a grep for `aria-`, `role=` or any a11y-locale identifier across `packages/components/username/` returns no hits at all. Three consequences. (1) The only string any assistive technology can reach is the abbreviated one — `Root M. A. mroot (corp)` — and there is no `<abbr title>`, no `aria-label`, and no visually-hidden expansion anywhere. The `kbq-title` directive on each part looks like it might help, but a bare `kbq-title` attribute resolves to an empty string and the directive then falls back to the host's own trimmed `textContent` (`title.directive.ts:171-172`), so the tooltip shows the *same* abbreviated text; and it only appears when the text is clipped, which by design never happens in `text` mode (`username.scss:91-99`). (2) `(corp)` is a parenthetical whose meaning — "site" — is conveyed by punctuation alone (`username.html:17, 31`); there is no label of any kind, so a screen-reader user hears "parenthesis corp parenthesis" with no indication of what it qualifies. (3) The name, the login and the site are three sibling spans with no grouping, so they read as one undifferentiated run. Note the honest framing: axe-core does not flag a custom element that carries no role, so this is not an automated AXE failure — it is a WCAG 1.3.1 (Info and Relationships) judgement plus a plain usability gap. AGENTS.md additionally mandates that component-provided default ARIA text come from `kbqInjectA11yLocaleConfiguration()`; twelve sibling packages do so (`breadcrumbs`, `content-panel`, `dl`, `form-field`, `inline-edit`, `modal`, `notification-center`, …) and `username` has no locale section at all — `core/locales/types.ts` defines per-component configurations for eight other components and none for this one.
**Fix:** three concrete moves. (a) Bind the unabbreviated name as explicit tooltip content instead of relying on the fallback: `[kbq-title]="unabbreviatedName()"` on the primary span, where `unabbreviatedName` formats with `'L F M'`-style full keys — `title.directive.ts:171-172` already prefers an explicit `titleContent` over `viewValue`, so this costs nothing and works for both mouse and keyboard (the keyboard path is live at `title.directive.ts:241-247`). (b) Add a `KbqUsernameLocaleConfiguration` section to `core/locales/types.ts` following the shape of `KbqAppSwitcherLocaleConfiguration` (`:76-84`), with a `siteLabel` string, and render it into a `<span class="cdk-visually-hidden">` before the site hint. (c) Give the host `role="group"` with an `aria-label` composed from the same locale section, or drop the parenthetical markup in favour of two labelled parts — decide deliberately. Guard with a `jest-axe` pass plus an assertion on `getComputedAccessibleName`-equivalent text for a fully populated profile.

**USR-BUG-03 · Initials are taken by code unit, so a non-BMP first character becomes a lone surrogate** — `username.pipe.ts:39-40, 90-93`.
Both pipes abbreviate with `fieldValue[0]` (`username.pipe.ts:40` and `:93`), which returns the first UTF-16 **code unit**, not the first character. For any name whose first character lies outside the Basic Multilingual Plane the result is an unpaired high surrogate, which browsers render as `�`: a profile with a first name starting `U+1D4A5` yields `Root \uD835. \uD801.` where correct output is `Root 𝒥. 𐑐.`. This affects mathematical alphanumerics used stylistically in display names, historic and extended CJK planes, and emoji in names — all of which occur in real directory data. Cyrillic, Greek, Hebrew, Arabic and standard CJK are BMP and unaffected, so the bug is invisible in every fixture in the repo (`username.spec.ts:29-33`, `e2e.ts:43-49`, all six docs examples). A second, related sharp edge: `fieldValue[0]` also splits a base character from its combining marks, so a name beginning with a decomposed letter loses its diacritic in the initial.
**Fix:** replace both `fieldValue[0]` sites with a code-point-aware first character — `[...String(fieldValue)][0]` is the minimal change and is correct for surrogate pairs; `Intl.Segmenter`'s grapheme granularity additionally keeps combining marks attached, at the cost of a `KBQ_WINDOW`-free but runtime-gated API (it is available in every browser this library targets, but guard it for the server bundle). Note `fieldValue` is typed `T[keyof T]` and reaches `[0]` only because `noImplicitAny` is off (`tsconfig.json:3-26` sets `strictNullChecks` but never `strict`/`noImplicitAny`), so the coercion to string should be explicit rather than incidental. Guard with a Jest case over `{ firstName: '𝒥ohn', lastName: 'Root' }` asserting `'Root 𝒥.'` — it fails today.

**USR-API-02 · `KbqUsernameSecondaryHint` is public, is used by the component's own template, and is missing from `KbqUsernameModule`** — `module.ts:5-12`, `username.ts:51-58, 78-84`, `username.html:17, 31`, `username.api.md:104, 134-140`.
`KbqUsernameSecondaryHint` is declared (`username.ts:51-58`), exported from the package barrel via `index.ts:4`, and published as `// @public` in the API report (`username.api.md:134-140`). It is one of the three styling hooks the component's own template uses (`username.html:17, 31`) and is correctly listed in the standalone component's `imports` (`username.ts:83`). But the NgModule's `COMPONENTS` array names only six symbols and omits it (`module.ts:5-12`), which the API report confirms — the `ɵmod` declaration lists exactly six imports and six exports (`username.api.md:104`). Every consumer that goes through `KbqUsernameModule` — which is four of the six shipped examples (`username-custom-example.ts:37`, `username-search-example.ts:20`, `username-filter-bar-option-example.ts:18`, `list-intermediate-state-example.ts:39`) — therefore cannot use the directive inside a `<kbq-username-custom-view>`. And the failure is **silent**: `kbqUsernameSecondaryHint` is an attribute selector on a plain `<span>`, so an unmatched directive is not a template error under `strictTemplates`; the class simply never lands, and the hint renders in the primary colour instead of the secondary one, indistinguishable from a theming bug.
**Fix:** add `KbqUsernameSecondaryHint` to the `COMPONENTS` array in `module.ts:5-12`. Add a spec that imports `KbqUsernameModule` (not the standalone component) into a host using all three styling directives and asserts the three `kbq-username__*` classes are present — a module-completeness test is the only thing that catches this class of omission, and the package has none. This changes `username.api.md:104`, so rebuild and `approve-api`.

**USR-CSS-01 · The secondary colour is keyed on an adjacent-sibling selector, so a login with no name renders in the primary colour** — `username-tokens.scss:1-6`, `username.scss:12-27`, `username.html:8-20`.
`--kbq-username-secondary-color` defaults to `inherit` (`username-tokens.scss:3`), and the only place the `default` style assigns it a real value is `.kbq-username_default { .kbq-username__secondary-hint, .kbq-username__primary + .kbq-username__secondary { --kbq-username-secondary-color: var(--kbq-foreground-contrast-secondary); } }` (`username.scss:22-27`). The second selector requires an immediately preceding `.kbq-username__primary` element. The template does not guarantee one: the primary span is rendered only `@if (hasFullName())` (`username.html:8-10`) while the secondary span is rendered independently `@if (profile.login)` (`:12`). So for exactly the profiles that trip USR-BUG-01 — a login with no complete name — the secondary span has no primary sibling, keeps `inherit`, and resolves to the *primary* colour `var(--kbq-foreground-contrast)` (`username.scss:14`), while the nested site hint inside it *does* get the secondary colour (its selector is unconditional, `username.scss:23`). The result is a login rendered in full-contrast text with a lower-contrast `(corp)` after it — visually the opposite of the intended hierarchy. The same trap catches custom views that place the secondary part first or wrap either part in a container, which the `KbqUsernameCustomView` API explicitly invites. The committed screenshots cannot show it: the e2e fixture uses one fully populated profile (`e2e.ts:43-49`).
**Fix:** drop the sibling dependency. Assign `--kbq-username-secondary-color: var(--kbq-foreground-contrast-secondary)` on `.kbq-username_default .kbq-username__secondary` and `.kbq-username_default .kbq-username__secondary-hint` unconditionally (`username.scss:22-27`), which is what the rule was trying to express. If the sibling selector was intended to make a lone secondary part read as primary, express that intent as an explicit modifier instead, so it survives custom views. Add an e2e row with a login-only profile and a name-only profile (which also guards USR-BUG-01), and regenerate the baselines with `yarn run e2e:docker:update-snapshots` — native runs fail on font rasterization alone.

**USR-I18N-01 · No bidi isolation, and the name conventions are hardcoded Russian** — `constants.ts:4-7`, `username.pipe.ts:40-42, 116-126`, `username.html:17, 31`, `username.scss` (no `unicode-bidi` / `dir` anywhere), `core/locales/types.ts:59-124`.
Two distinct internationalization gaps, both anchored. (1) **Bidi.** `KbqUsernamePipe.transform` concatenates the profile fields into a single string with plain spaces (`username.pipe.ts:42`), that string is rendered into one span (`username.html:9`), and `kbqBuildUsernameText` joins name, login and a parenthesized site the same way (`username.pipe.ts:123-125`). None of these apply directional isolation, and the stylesheet sets neither `unicode-bidi` nor `dir` on any of the three part classes. An RTL surname followed by a Latin login therefore reorders visually under the bidi algorithm, and the hardcoded parentheses around the site (`username.pipe.ts:121`, `username.html:17, 31`) mirror and can detach from their content — the classic bidi spillover that neutral characters at a directional boundary produce. The component does place login and site in separate spans, which helps in the component but not in `kbqBuildUsernameText`, whose whole purpose is to reproduce the visible string outside the component. (2) **Locale.** `kbqDefaultFullNameFormat = 'lf.m.'` (`constants.ts:7`) is "surname, then given and patronymic initials" — the Russian/CIS convention, hardcoded as the library-wide default with no locale hook; the dot after an initial is baked into the enum itself (`types.ts:34`); the `(…)` site wrapper is hardcoded in two places. The library does have a locale mechanism, and its default locale data is Russian (`core/locales/a11y.ts:11`), with per-component sections defined for eight other components (`core/locales/types.ts:41-124`) — `username`, the one component whose output is *entirely* a naming convention, has none.
**Fix:** for bidi, prefer CSS over string surgery: add `unicode-bidi: isolate` to `.kbq-username__primary`, `.kbq-username__secondary` and `.kbq-username__secondary-hint` in `username.scss`, and set `dir="auto"` on the primary span so a wholly-RTL name gets the correct base direction. Do **not** inject `U+2068`/`U+2069` into `KbqUsernamePipe`'s output — that string is consumed by `kbqBuildUsernameText` and by consumer search filters (`username-search-example.ts:86-91`), and invisible characters would break `includes()` matching; instead add the isolates only inside `kbqBuildUsernameText` behind an opt-in option alongside `formatLogin`/`formatSite` (`username.pipe.ts:100-108`). For locale, add a `KbqUsernameLocaleConfiguration` section to `core/locales/types.ts` carrying `fullNameFormat` and the site wrapper, resolve `fullNameFormat`'s default through it instead of the module-level constant, and document that `[fullNameFormat]` overrides the locale. Guard with a Jest case asserting the pipe output for a Hebrew surname plus a Latin login, and an e2e row inside a `[dir=rtl]` container.

**USR-DOC-01 · Both guides document a `custom` mode that does not exist, and omit two of the five inputs** — `username.en.md:13`, `username.ru.md:11`, `types.ts:66`, `username.ts:96-111`.
`KbqUsernameMode` is `'stacked' | 'inline' | 'text'` (`types.ts:66`). Both guides instruct the reader to "use the `custom` mode with the `KbqUsernameCustomView` directive" (`username.en.md:13`; `username.ru.md:11` says the same in Russian). There is no `custom` mode: the custom view is selected by content projection alone (`username.html:2-4`, `username.ts:116`) and works in every one of the three real modes, as the docs' own example demonstrates by binding `[mode]="selectedMode"` over `['inline', 'stacked', 'text']` (`username-custom-example.ts:45, 102`). Because the phrase appears only in prose and never in a copyable snippet, a reader who follows it writes `[mode]="'custom'"` and gets a `strictTemplates` type error (`tsconfig.json:117`) rather than a silent misrender — annoying rather than build-breaking, which is why this is P2 and not P1. Separately, two of the five public inputs are documented nowhere: `isCompact` (`username.ts:98-99`) — which changes the output substantially, hiding the login whenever a full name is present (`username.html:22-33`) and being used by a shipped consumer (`inline-edit-select-example.ts:42, 60`) — and `fullNameFormat` (`:100-101`), whose accepted syntax is the subject of USR-API-01. The guides also never state which of the two pipes a reader should reach for.
**Fix:** delete the phrase "the `custom` mode" from `username.en.md:13` and `username.ru.md:11` and replace it with "project a `<kbq-username-custom-view>`; it composes with any `mode` and `type`". Add a short section documenting `isCompact` (with the login-suppression behaviour spelled out) and `fullNameFormat` (with the `KbqUsernamePipe` dot rule from USR-API-01) in both languages, and a one-paragraph "which pipe" note. The docs site compiles guide snippets in `yarn run e2e:docs`, so any snippet added here stays honest.

**USR-TEST-01 · 18 cases that never execute the shipped default mapping, and a screenshot that cannot show overflow** — `username.spec.ts:35-73, 75-121, 155-169`, `e2e.ts:16-49`, `e2e.playwright-spec.ts:9-16`.
The Jest file has 18 cases in four suites, and every single pipe case passes an explicit `customMapping` as the third argument (`username.spec.ts:50, 56, 62, 69, 92, 98, 104, 110, 117`), built locally at `:36-41` and `:77-85`. The `KBQ_PROFILE_MAPPING` factory in `constants.ts:23-29` — the mapping every default-configured application actually runs — is therefore never executed by a test, which is precisely why USR-BUG-02 has survived since the component was introduced (`6fae4d71f`, DS-3296). The component itself gets two cases (`:156-169`): one snapshots the host classes, one asserts a custom view suppresses the default primary span. Nothing covers `isCompact` (the field exists on `TestComponent` at `:196` and is never changed), `mode`/`type` beyond the default snapshot, the login/site branches, partial profiles (USR-BUG-01), `KbqUsernameModule` (USR-API-02), or the `KbqMappingMissingError` path. The Playwright layer is one test producing two screenshots (`e2e.playwright-spec.ts:9-16`); its fixture puts each `<kbq-username>` in an auto-sized `<td>` (`e2e.ts:17-27`) with one short profile, so the cells always fit and the `kbq-title` truncation behaviour — the reason `kbq-title` is on three spans in the first place — is never rendered in a clipped state. Note that all committed baselines are captured with `reducedMotion: 'reduce'` (`playwright.config.ts:101`), which is immaterial for the current static table but will matter for any tooltip-opening row added later.
**Fix:** four additions, in order of value. (a) A pipe suite that omits `customMapping` entirely and asserts both pipes' defaults — this is the regression guard for USR-BUG-02. (b) A component table over partial profiles asserting rendered text in both `isCompact` states — the guard for USR-BUG-01. (c) A module-completeness case importing `KbqUsernameModule` — the guard for USR-API-02. (d) An e2e row with a fixed narrow container and a long name, so the screenshot captures the truncated state, plus a login-only row for USR-CSS-01; regenerate baselines only with `yarn run e2e:docker:update-snapshots`. Also delete the two `'FML'` fixtures at `username.spec.ts:56` and `:62`: they read as uppercase-key coverage but return `''` because of the null/array guard at `username.pipe.ts:27`, never reaching the format loop.

### P3 — Nice to have / hygiene

**USR-PERF-01 · `kbq-title` and its three observers are attached even in `text` mode, where nothing can ever clip** — `username.html:9, 13, 22`, `username.scss:85-99`, `types.ts:59-66`, `title.directive.ts:224-239`.
Each `kbq-title` host registers a `SharedResizeObserver` subscription on its parent, a `ContentObserver` (a `MutationObserver`) on the same element, and a `FocusMonitor` monitor (`title.directive.ts:224-239`), plus `mouseenter`/`mouseleave` listeners. The template attaches it unconditionally to two spans in the non-compact branch and one in the compact branch (`username.html:9, 13, 22`), regardless of `mode()`. But `kbq-truncate-line` — the only thing that makes clipping possible — is applied solely under `.kbq-username_stacked` and `.kbq-username_inline` (`username.scss:91-99`); `text` mode is documented as "Plain text, no layout styling. No text-ellipsis" (`types.ts:64`) and sets `display: inline` (`:85-89`). So in `text` mode the entire measurement apparatus is instantiated for an outcome that the stylesheet has ruled out. In a list of a few hundred usernames — the `list-intermediate-state` and filter-bar patterns the docs promote — that is several hundred needless observer registrations.
**Fix:** make the attribute conditional on the mode. The cleanest form without duplicating the template is to hoist the two rendering branches into small internal templates and stamp the `kbq-title` attribute only for `stacked`/`inline`; the pragmatic form is `[kbq-title]` on a wrapper `@if (mode() !== 'text')` branch. Measure before and after with a 500-row fixture rather than assuming — the observers are shared, so the win is registration cost, not per-event cost.

**USR-API-03 · Public-surface documentation gaps, a leaky computed type, and an unreachable error** — `username.ts:18-28, 119-125`, `constants.ts:13-15, 20-30`, `username.pipe.ts:21-25, 69-73`, `username.api.md:39, 52, 97, 107`.
Four small things on the same surface. (1) `KbqUserInfo` is tagged `@docs-private` (`username.ts:20-21`) yet it is the type of `userInfo`, the component's flagship input, and is published as `// @public` (`username.api.md:39`) — the docs site will hide the shape of the one object a consumer must construct. (2) `KbqUsernamePipe` and `KbqUsernameModule` are the only two classes in the package with no JSDoc, and the report marks both `// @public (undocumented)` (`username.api.md:97, 107`); the sibling `KbqUsernameCustomPipe` has a proper block (`username.pipe.ts:51-54`). (3) `hasFullName` is `computed(() => userInfo?.lastName && userInfo?.firstName)`, which returns the *string* when both are present — the report types it `i0.Signal<string | false | undefined>` (`username.api.md:52`) instead of `Signal<boolean>`. (4) `KbqMappingMissingError` is unreachable: `KBQ_PROFILE_MAPPING` is created with a `factory` and therefore defaults to `providedIn: 'root'` (`constants.ts:20-29`), so `inject(KBQ_PROFILE_MAPPING, { optional: true })` (`username.pipe.ts:17, 61`) can never return null and neither `throw` at `username.pipe.ts:24` or `:72` can fire — short of a consumer explicitly providing `useValue: null`. It is nonetheless exported as public API (`username.api.md:36`), named in PascalCase like a class while being a factory function (`constants.ts:13-15`). Minor naming note while in the area: the input is `type` but its type is `KbqUsernameStyle` (`username.ts:111`, `types.ts:68-76`).
**Fix:** drop `@docs-private` from `KbqUserInfo` and give it real member JSDoc; add class blocks to `KbqUsernamePipe` and `KbqUsernameModule`; wrap `hasFullName` in `!!(…)`; either delete `KbqMappingMissingError` and the two dead `throw`s, or make them reachable by dropping the token's default factory (a breaking change that would force every consumer to provide a mapping — almost certainly not what you want, so deleting is the right call). All of these move `username.api.md`, so batch them with USR-API-01 and USR-API-02 into one `yarn run build:components && yarn run approve-api` cycle rather than three.

**USR-ARCH-02 · Package-structure deviations and fixture leftovers** — `packages/components/username/` (no `public-api.ts`), `username.scss:12-43, 58` (no `_username-theme.scss`), `e2e.ts:51, 53-66`.
Three hygiene items. (1) The package has no `public-api.ts`; `index.ts` re-exports the five source files directly (`index.ts:1-5`). 54 of the component packages ship a `public-api.ts` as AGENTS.md's structure section prescribes, so this is a real if harmless divergence — it means there is no single file stating what is public, and the `export *` form makes every future addition public by default. (2) There is no `_username-theme.scss`. This one is **not** a defect: the theme lives in a `_kbq-username-theme()` mixin defined at `username.scss:12-43` and included at `:58`, and the convention partials are only ever `@use`d by their own component stylesheet anyway (`divider.scss:1`, `badge.component.scss:3`) — nothing aggregates them. Extracting it is worth doing purely so `username` looks like its siblings and so a consumer grepping for `_*-theme.scss` finds the colour rules where they expect. (3) The e2e fixture carries an empty `constructor() {}` (`e2e.ts:51`), a mutable non-`readonly` `userInfo` (`:43`), and two legacy angle-bracket casts `<KbqUsernameMode[]>` / `<KbqUsernameStyle>` (`:55-57`) that `satisfies` or a typed array literal would express better.
**Fix:** add `public-api.ts` listing the intended exports and reduce `index.ts` to `export * from './public-api';`; move `_kbq-username-theme()` into `_username-theme.scss` and `@use` it from `username.scss` exactly as `divider.scss:1` does; delete the empty constructor, mark `userInfo` `readonly`, and replace the casts. None of this changes the API report if the `public-api.ts` re-exports the same symbols — verify with `check-api` rather than assuming.

**USR-TEST-02 · A `describe` block named after the wrong class, an unawaited `compileComponents`, and colliding case names** — `username.spec.ts:14-21, 35, 75, 87-89`, `__snapshots__/username.spec.ts.snap:11`.
`describe(KbqUsernamePipe.name, …)` opens the suite for `KbqUsernameCustomPipe` at `username.spec.ts:75` — the body injects `KbqUsernameCustomPipe` (`:87-89`) but the suite is labelled `KbqUsernamePipe`, the same label as the suite at `:35`. The consequence is already visible on disk: the custom pipe's snapshot is filed under `exports[\`KbqUsernamePipe should format full name using custom format 1\`]` (`__snapshots__/username.spec.ts.snap:11`), attributed to the wrong class. Both suites also contain an identically named case, `'should format full name using default format'` (`:49` and `:91`), so if either ever gains a snapshot assertion the keys collide outright. Separately, the shared `createComponent` helper calls `TestBed.configureTestingModule({…}).compileComponents()` without awaiting or returning the promise (`:15`) and then creates the component synchronously — this happens to work because the components use `templateUrl` that the Jest transform inlines, but it is a latent hang the moment a resource is not inlined. `CustomView` at `:213` also reuses the `test-component` selector already taken by `TestComponent` at `:171`.
**Fix:** change `:75` to `describe(KbqUsernameCustomPipe.name, …)` and delete the stale snapshot key so it is regenerated under the right name; give the two default-format cases distinguishing names; drop the unused `.compileComponents()` call (or `await` it in a `beforeEach`); give `CustomView` its own selector. Test hosts here already follow the repo's no-`Kbq`-prefix convention (`TestComponent`, `CustomView`), which is worth preserving as cases are added.

## 4. Recommended Remediation Phases

**Phase 1 — Make the rendered name match the data.**

**Phase 4 — Close the test, docs and structure gaps.**

## Appendix A — Review Methodology

Every file in the package was read in full (`cat -n`), then each candidate finding was cross-checked against four independent sources: the API guard report (`tools/public_api_guard/components/username.api.md`, 153 lines) for what is actually published, the workspace compiler settings (`tsconfig.json`) for what the type system does and does not catch, the live design-token set (`@koobiq/design-tokens/web/new/css-tokens-{light,dark}.css`) for token resolution, and every in-repo consumer found by grepping `kbq-username|KbqUsername|kbqUsername` across `packages/` and `apps/`. The two pipes' behaviour was verified by re-implementing their loops in a standalone `node -e` script and running the shipped default format against the shipped default mapping — that is how USR-BUG-02 was confirmed rather than inferred, and how the surrogate-pair output in USR-BUG-03 was produced. The committed light-theme screenshot was read directly to check rendered spacing. The **RxJS & Lifecycle** scorecard dimension is omitted: the package contains no RxJS, no lifecycle hooks and no subscriptions of its own.

Refuted during verification:
- **"The missing `_username-theme.scss` breaks theming or leaves colours unthemed"** — refuted. The theme mixin exists inline at `username.scss:12-43` and is included at `:58`, and the convention partials in sibling packages are only `@use`d by their own component stylesheet (`divider.scss:1`, `badge.component.scss:3`) — nothing aggregates `_*-theme.scss` files across the library. All four colour tokens the mixin consumes resolve in both themes. Downgraded to a structural nit inside USR-ARCH-02.
- **"`username-custom-example.ts` uses `<kbq-form-field>` and `<kbq-label>` without importing `KbqFormFieldModule`"** — refuted. `KbqTextareaModule` re-exports `KbqFormFieldModule` (`textarea/textarea.module.ts:9`), so the example compiles.

The gap rule is indeed scoped to `.kbq-username_inline:not(.kbq-username_inherit)` (`username.scss:72-82`), but the secondary span's own template text node carries a leading space (`username.html:13-14`) that survives Angular's whitespace removal because the node is not whitespace-only, and the committed baseline shows correct separation in both the `text` and `inherit` cells of `__screenshots__/01-light.png`.
