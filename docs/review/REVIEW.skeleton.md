# Koobiq `skeleton` Component — Code Review & Improvement Plan

> Scope: `packages/components/skeleton` (directive + style-loader component, SCSS, NgModule, Jest spec, user guides, examples stubs, API guard report) · Commit `b665e503` · 2026-08-28
> Generated by a multi-dimension review (architecture, correctness, accessibility, performance, public API/types, styles, tests, docs) with manual verification of every finding against the source, the live design-token set, both in-repo host applications, and the three shipped docs examples. 12 findings confirmed (P0×0, P1×2, P2×5, P3×5); 7 candidate findings refuted during verification (see Appendix A). This document is a review + roadmap; no source is modified by it.

---

## 1. Executive Summary

`KbqSkeleton` is an 80-line package: one attribute/element directive (`skeleton.ts`), a 59-line stylesheet loaded on demand through `_CdkPrivateStyleLoader`, an NgModule wrapper, and a three-case Jest spec. Its one piece of logic is a cross-instance animation-phase sync — a module-level timestamp plus a negative `animation-delay` so that every skeleton on the page rides the same wave. There are **no release blockers**: nothing here throws, leaks or breaks a build. What is broken is the *rendered result*, and specifically the fact that nobody in this repository has ever looked at the rendered result the library actually ships.

- **The library never renders its own skeleton.** `skeleton.scss:37` paints the placeholder with `--kbq-skeleton-background`. In the live token set that value carries an alpha channel — `oklch(… / 0.08)` in light, `/ 0.10` in dark (`css-tokens-light.css:964`, `css-tokens-dark.css:964`) — so the overlay is 92 % transparent. Both in-repo host applications override it: `apps/docs/src/main.scss:3-4` and `packages/components-dev/skeleton/styles.scss:1-2` each `@use` the **deprecated** token files, whose `--kbq-skeleton-background` is fully opaque. These are the only two `web/deprecated` imports in the entire repository. The docs site, the dev app and every published screenshot therefore show an opaque skeleton, while an external consumer following the documented setup gets a translucent wash — and for the `[kbqSkeleton]` directive form, whose whole job is to mask live content, the content underneath stays fully legible (SKL-CSS-01).
- **The component ships no loading semantics whatsoever.** The host block (`skeleton.ts:35-38`) binds two classes and nothing else: no `role`, no `aria-busy`, no `aria-hidden`, no `inert`, no announcement from `kbqInjectA11yLocaleConfiguration()`. `pointer-events: none` (`skeleton.scss:29`) removes the mouse but not the keyboard or the accessibility tree, and `outline-color: transparent` (`:31`) suppresses the focus ring of a host that is still focusable. Neither guide has an Accessibility section (SKL-A11Y-01).
- **The wave is anchored to the viewport with `position: fixed`, which silently re-anchors inside any transformed ancestor** — including `kbq-sidepanel`, whose open state applies a persistent `transform: translateX(0)` (`sidepanel-animations.ts:21, 55-56`). That is precisely the scenario the component's own flagship example ships (`skeleton-in-sidepanel-example.ts:36, 53, 70, 90`) and the guide promotes (`skeleton.en.md:13-17`) (SKL-CSS-02).
- **A purely visual, animation-driven component has no visual test.** There is no `e2e.ts`, no `e2e.playwright-spec.ts` and no `__screenshots__` directory — skeleton is one of only five real component packages in that state. The three Jest cases assert an inline CSS custom property against a hand-written `getComputedStyle` stub (`skeleton.spec.ts:14-24`); not one of them observes a class, a pseudo-element or a colour (SKL-TEST-01).

Genuine strengths worth preserving: the phase-sync idea is elegant and its arithmetic is correct (verified against all three spec scenarios); `prefers-reduced-motion: reduce` is honoured (`skeleton.scss:56-58`), which most animated components in this library do not bother with; the directive is fully modern — `input()` with `booleanAttribute`, `inject()`, `kbqInjectNativeElement()`, `KBQ_WINDOW` instead of the global `window`, host-object bindings, no decorators-as-bindings; the on-demand style loader follows the pattern `scrollbar.ts:188, 205` already established; and the three docs examples are real, non-trivial and cover both API forms. The code is in good shape. The *pixels* have never been checked.

## 3. Prioritized Findings (deduplicated, verified)

### P0 — Release blockers

None.

### P1 — High

**SKL-CSS-01 · The shipped background token is translucent, and both in-repo applications secretly override it with the deprecated opaque one** — `skeleton.scss:37`, `node_modules/@koobiq/design-tokens/web/new/css-tokens-light.css:964`, `css-tokens-dark.css:964`; overrides at `apps/docs/src/main.scss:3-4` and `packages/components-dev/skeleton/styles.scss:1-2`.
The placeholder surface is a single declaration: `&::before { … background-color: var(--kbq-skeleton-background); }` (`skeleton.scss:33-39`). In the live token set that variable is `oklch(24.7% 0.1052 257.1 / 0.08)` for light and `oklch(84.5% 0.0860 281.6 / 0.10)` for dark — an alpha of 0.08 / 0.10, i.e. an overlay that is 90-92 % transparent. Nothing else in `skeleton.scss:11-59` hides the host's content: there is no `color`, `opacity`, `visibility` or `text-indent` rule anywhere in the file. For the element form `<kbq-skeleton />` the difference over a plain page background is small; for the `[kbqSkeleton]` **directive** form it is the whole feature, because the directive is applied to an element that already contains real content, and an 8 %-alpha wash leaves that content completely legible. The library's own shipped example does exactly this — `<kbq-alert [kbqSkeleton]="loading()">` wrapping an icon and three lines of prose (`skeleton-directive-example.ts:17-22`) — so a consumer toggling `loading` sees the text stay readable under a faint tint instead of being replaced by a placeholder.
The corroborating evidence is unusually direct: **both** applications in this repository refuse the shipped value. `apps/docs/src/main.scss:3-4` and `packages/components-dev/skeleton/styles.scss:1-2` each `@use '@koobiq/design-tokens/web/deprecated/css/components/skeleton/skeleton-{light,dark}.css'`, whose `--kbq-skeleton-background` is `hsla(229, 15%, 96%, 100%)` / `hsla(229, 15%, 17%, 100%)` — **fully opaque** (`deprecated/.../skeleton-light.css:6`, `skeleton-dark.css:6`). Both imports load *after* the live token set (`main.scss:1` and `packages/components-dev/main.scss:4-6`) at equal `.kbq-light` specificity, so the deprecated value wins. These are the only two `web/deprecated` imports in the whole repository; `git log -L` shows both were introduced by the original skeleton PR (`c100ccbc9`, DS-3647), presumably when the new token set had no skeleton entries yet. It now does, with different values, and nobody noticed. The net effect is that the docs site, the dev app and every screenshot the team looks at render a skeleton that no external consumer can obtain.
**Fix:** decide which value is canonical, then make one of them true. If opaque is the design intent, raise it against `@koobiq/design-tokens` so `--kbq-skeleton-background` in `web/new/css-tokens-{light,dark}.css` becomes opaque, and delete both deprecated imports (`apps/docs/src/main.scss:3-4`, `packages/components-dev/skeleton/styles.scss:1-2`) — their removal is the acceptance criterion, not the token diff. If translucency is intentional, then the directive form needs a second mechanism to hide the host's content (`color: transparent` on the subtree, or `visibility: hidden` on children with the pseudo-elements re-shown), and `skeleton-directive-example.ts` must demonstrate that it works. Either way, guard it with the Playwright fixture from SKL-TEST-01: one row for `<kbq-skeleton />` on the page background and one for `[kbqSkeleton]` over a text-bearing `kbq-alert`, in both themes, with **no** deprecated token import in the e2e app.

**SKL-A11Y-01 · No loading semantics of any kind, and the focus ring is suppressed on a host that stays focusable** — `skeleton.ts:33-40` (host block), `skeleton.scss:28-31`; guides `skeleton.en.md`, `skeleton.ru.md` (no Accessibility section).
The entire host contract is `class: 'kbq-skeleton'` plus `'[class.kbq-skeleton_disabled]': '!enabled()'` (`skeleton.ts:35-38`). There is no `role`, no `aria-busy`, no `aria-hidden`, no `inert`, and no announcement sourced from `kbqInjectA11yLocaleConfiguration()` — which AGENTS.md names as the required source for component-provided ARIA text. Three consequences follow, all of them from lines you can read:
(1) *The pending state is not communicated.* A screen-reader user gets no signal that the region is loading, and — because the content under a `[kbqSkeleton]` host is still in the accessibility tree — is read the "not yet ready" content as though it were final. `aria-busy="true"` exists for exactly this and costs one host binding.
(2) *The blocked state is only half-blocked.* `pointer-events: none` (`skeleton.scss:29`) removes mouse interaction, but it has no effect on tab order or on assistive-technology navigation. Any focusable descendant of a `[kbqSkeleton]` host remains reachable by keyboard while being visually obscured by the `::before` overlay (`skeleton.scss:33-39`, which paints above ordinary content because `clip-path: inset(0)` at `:27` makes the host a stacking context and the overlay carries `z-index: 1`). That is WCAG 2.4.7 (Focus Visible) and 4.1.2 (Name, Role, Value) territory.
(3) *The host's own focus indicator is deleted.* `outline-color: transparent` (`skeleton.scss:31`) is applied unconditionally to the host, so a focusable element wearing `[kbqSkeleton]` loses its outline-based focus ring while remaining focusable — an explicit removal, not an omission.
Be precise about the class of failure: axe-core does **not** flag a custom element that simply carries no role, so this is a WCAG judgement plus an AGENTS.md mandate ("It MUST follow all WCAG AA minimums, including focus management … and ARIA attributes"), not an automated AXE failure. It is also a library-wide gap rather than a skeleton-only one — `progress-spinner.component.html:1-17` and the `loader-overlay` package carry no ARIA either — but skeleton is the worst case of the three because the directive form deliberately obscures *live* content.
**Fix:** add to the host block `'[attr.aria-busy]': "enabled() || null"` and `'[attr.role]': "enabled() ? 'status' : null"` with `'[attr.aria-live]': "enabled() ? 'polite' : null"`, plus a visually-hidden label sourced from `kbqInjectA11yLocaleConfiguration()` (add a `skeleton.loading` entry alongside the existing a11y locale keys in `packages/components/core/locales/a11y.ts`). Make the obscured subtree genuinely inert for the directive form — `'[attr.inert]': "enabled() || null"` is one binding and it removes focusability, pointer events and AT exposure in one move, superseding both `pointer-events: none` and the `outline-color: transparent` hack; keep the CSS as the no-`inert` fallback. Add an `### Accessibility` section to both guides stating what is announced and that the wrapped subtree becomes inert. Cover with Jest cases per attribute per `enabled()` branch and a `jest-axe` pass over a `[kbqSkeleton]` host containing a focusable button, asserting the button is not in the tab order while the skeleton is on.

### P2 — Should fix

**SKL-CSS-02 · The `position: fixed` wave re-anchors inside any transformed ancestor, including the sidepanel from the component's own example** — `skeleton.scss:41-54`; `sidepanel-animations.ts:21, 55-56`, `sidepanel-container.component.ts:44-51`; consumer `skeleton-in-sidepanel-example.ts:36, 53, 70, 90`, promoted by `skeleton.en.md:13-17` / `skeleton.ru.md:13-17`.
The shimmer is a viewport-wide band: `&::after { position: fixed; inset-block: 0; left: calc(var(--kbq-skeleton-wave-width) * -1); width: var(--kbq-skeleton-wave-width); animation: wave … }` (`skeleton.scss:41-54`) travelling from `translateX(-100px)` to `translateX(100vw)` (`:1-9`), clipped back to each skeleton's own box by `clip-path: inset(0)` (`:27`). The design is deliberate and clever: one band, one timeline, every skeleton on the page lit in geometric order. It rests entirely on the band's containing block being the viewport — and **any** ancestor with a non-`none` `transform`, a `filter`, `backdrop-filter`, `will-change` on those, or `contain: paint` becomes the containing block for fixed-position descendants instead.
This is not hypothetical. `kbq-sidepanel-container` binds `[@state]` on its host (`sidepanel-container.component.ts:44-51`), and the `Visible` state applies `style({ transform: '{{transformOut}}', opacity: 1 })` (`sidepanel-animations.ts:55-56`) where `transformOut` is `'translateX(0)'` (`:21`). Angular `state()` styles are written inline and persist for as long as the element is in that state, so an **open** sidepanel always carries a non-`none` transform. The wave band inside it is then anchored to the panel, `inset-block: 0` spans the panel rather than the viewport, and the keyframes still travel `100vw` — so the shimmer crosses a 400 px panel in the first few percent of the 1200 ms cycle and is absent for the rest of it, and it is no longer in phase with skeletons outside the panel. The library's flagship example puts roughly thirty skeletons inside exactly that panel (`skeleton-in-sidepanel-example.ts:35-95`), and the guide's only "usage example" section is about it.
**Fix:** stop depending on the containing block. Either (a) make the band `position: absolute` inside the skeleton and drive it with a percentage keyframe (`from { transform: translateX(-100%) } to { transform: translateX(calc(100% + 100cqw)) }`), accepting a per-element sweep and keeping cross-element sync purely through the existing negative `animation-delay`; or (b) keep the viewport-wide band but re-express the travel in terms of the band's own containing block so a transformed ancestor degrades gracefully instead of silently. Whichever is chosen, add an e2e row (SKL-TEST-01) that renders skeletons inside an element with `transform: translateX(0)` and screenshots mid-animation — that row is the regression guard, and it must be produced with `yarn run e2e:docker:update-snapshots`.

**SKL-CSS-03 · `@keyframes wave` is an unprefixed, globally scoped animation name** — `skeleton.scss:1, 54`; siblings `progress-bar.scss:7`, `progress-spinner.scss:7`, `scrollbar-track.scss:23`, `core/styles/common/_animation.scss:41`; lint config `.stylelintrc.js`.
`@keyframes` names live in a single flat, document-wide namespace, last declaration wins, and `SkeletonStyleLoader` (`skeleton.ts:22-28`) injects this stylesheet globally with `ViewEncapsulation.None`. The name chosen is `wave` — about as collision-prone as it gets. Every other animation in the library is namespaced: `kbq-progress`, `kbq-progress-bar-indeterminate`, `kbq-progress-spinner-indeterminate`, `kbq-scrollbar-fade`; the only other exceptions are the legacy `mc*` names in `_modal-animation.scss` and a vendored `os-*` name in deprecated scrollbar code. So `wave` is the single unprefixed animation name the library ships. A consumer application (or another library) that defines its own `@keyframes wave` in a stylesheet loaded after koobiq's silently replaces the skeleton's shimmer with theirs — and the reverse, koobiq stealing an app's `wave`, is just as likely and far more confusing to debug. `.stylelintrc.js` has no `keyframes-name-pattern` rule, so nothing catches it.
**Fix:** rename to `kbq-skeleton-wave` in `skeleton.scss:1` and `:54`. The name is not part of the public API — no `.md`, no example and no consumer references it — so this is a safe, non-breaking rename. Add `'keyframes-name-pattern': ['^kbq-', …]` to the `componentsRules` override in `.stylelintrc.js` so the next one is caught by `yarn run stylelint` rather than by a bug report.

**SKL-CSS-04 · Toggling the skeleton changes the host's layout and paint model — the layout shift the component exists to prevent** — `skeleton.scss:11, 25-31`; the guide's own rationale at `skeleton.en.md:23` / `skeleton.ru.md:23`.
Everything in the rule is gated on `:not(.kbq-skeleton_disabled)` (`skeleton.scss:11`), so `position: relative`, `overflow: hidden`, `clip-path: inset(0)`, `user-select: none`, `pointer-events: none`, `border-color: transparent` and `outline-color: transparent` (`:25-31`) all appear and disappear as `enabled()` flips. Three of those are not cosmetic. `overflow: hidden` establishes a block formatting context, which stops margins collapsing through the element — a `[kbqSkeleton]` host whose children have vertical margins is measurably taller while the skeleton is on and snaps back when it turns off. It also clips any descendant that legitimately overflows: a badge, a dropdown panel, a `kbq-title` tooltip anchor. `clip-path: inset(0)` makes the host a stacking context and clips the host's own `outline` and `box-shadow` to a sharp rectangle, so a card with a shadow loses it while loading. The guide sells the component on exactly the opposite promise — "to provide a sense of page structure and minimize layout shifts" (`skeleton.en.md:23`).
**Fix:** move the geometry-neutral parts out of the `:not()` gate so they are stable across the toggle. `position: relative` and `clip-path: inset(0)` can be applied unconditionally to `.kbq-skeleton` at negligible cost (both are inert without the pseudo-elements); `overflow: hidden` is the one that must stay gated, so replace it with `overflow: clip` — which clips without establishing a BFC or a scroll container and therefore does not change margin collapsing. Add the `[kbqSkeleton]`-on-a-margin-bearing-container case to the e2e fixture with an on/off pair of screenshots; equal heights across the pair is the assertion.

**SKL-PERF-01 · The render hook interleaves a forced style read with a style write, once per instance** — `skeleton.ts:54-62, 71-79`; ~30 instances in `skeleton-in-sidepanel-example.ts:35-95`.
`afterRenderEffect(() => { … this.syncAnimation(enabledAt); })` (`skeleton.ts:54-62`) is registered with a single callback, which places it in the combined `mixedReadWrite` phase — the phase Angular's own documentation tells you to avoid because it is the one that cannot be batched. Inside it, `syncAnimation` does `this.window.getComputedStyle(this.element).getPropertyValue(…)` (`:73-75`), a forced style recalculation, immediately followed by `this.element.style.setProperty(…)` (`:78`), a style invalidation. With N skeletons mounting in the same frame the browser is driven through N read/invalidate cycles instead of one batched read followed by one batched write. The shipped sidepanel example mounts about thirty skeletons in a single `@placeholder` block (`skeleton-in-sidepanel-example.ts:35-95`), and a table or grid placeholder — the documented primary use case — trivially exceeds that. Separately, the value being read is a constant: `--kbq-skeleton-animation-duration` is `1200ms` for every instance (`skeleton.scss:13`), yet each instance re-reads it on every enable.
**Fix:** split the hook into its declared phases — `afterRenderEffect({ earlyRead: () => …getPropertyValue(…), write: (duration) => …setProperty(…) })` — so all reads happen before any write. Cache the parsed duration in a root-provided service (or a module-level memo keyed on the resolved value) and re-read it only when the resolved value could have changed, rather than once per instance per enable. Guard with a spec that mounts 50 skeletons and asserts `getComputedStyle` is called once, not fifty times.

**SKL-TEST-01 · A purely visual component has no visual test, and the unit tests observe nothing visual** — `packages/components/skeleton/` (no `e2e.ts`, no `e2e.playwright-spec.ts`, no `__screenshots__`); `skeleton.spec.ts:9-33, 66-111`.
Skeleton is one of only five real component packages in `packages/components/` without an e2e fixture (the others being `dynamic-translation`, `resizer`, `sidebar` and `time-range`), and it is by some distance the most visual of them: the component *is* a background colour, a border radius, a clip and an animation. The three Jest cases that do exist (`skeleton.spec.ts:67, 79, 93`) assert exactly two things — the presence of the `kbq-skeleton_disabled` class and the string value of the `--kbq-skeleton-animation-delay` inline custom property — and the second of those is read back through a `KBQ_WINDOW` stub whose `getComputedStyle` returns a hard-coded `'1200ms'` (`skeleton.spec.ts:14-24`). No test observes a colour, a pseudo-element, the wave, the `prefers-reduced-motion` branch, the element-vs-directive rendering difference, or the bare-attribute form `<div kbqSkeleton>`. Consequently every finding above — the translucent token, the transformed-ancestor wave, the BFC toggle — is invisible to CI, which is why they have survived four commits.
**Fix:** add `e2e.ts` + `e2e.playwright-spec.ts` following the `progress-spinner` package's shape, with rows for: `<kbq-skeleton />` at three widths on the page background; `[kbqSkeleton]` over a text-bearing `kbq-alert`, on and off (SKL-CSS-01, SKL-CSS-04); skeletons inside an ancestor carrying `transform: translateX(0)` (SKL-CSS-02); and a `prefers-reduced-motion: reduce` variant. Critically, the e2e application must load **only** `@koobiq/design-tokens/web/new/…` — importing the deprecated skeleton tokens there would reproduce the blind spot this finding is about. Baselines are Linux and compared at `threshold: 0`, so generate them with `yarn run e2e:docker:update-snapshots` and nothing else. On the Jest side add cases for the bare-attribute form, `kbqSkeleton="false"` coercion, and the `ngOnDestroy` reset branch.

### P3 — Nice to have / hygiene

**SKL-ARCH-01 · Cross-instance sync is carried by module-level mutable state** — `skeleton.ts:14-17, 50, 59, 65-69`.
`animationStartTime` and `count` are `let` bindings at module scope, mutated from the constructor (`:50, 59`) and `ngOnDestroy` (`:66-68`). The arithmetic is correct — I traced all three spec scenarios plus the disabled-instance-keeps-the-counter-alive case and found no wrong delay (see Appendix A) — but the mechanism has three costs. It is shared across every Angular application that loads the bundle, so two independently bootstrapped apps on one page (micro-frontends, the docs site's example sandboxes) share one animation clock and one counter. It is unreachable from DI, so it cannot be stubbed, inspected or reset in a test — and indeed the `count === 0` reset branch (`:66-68`) is the one code path in the package with no test at all. And the `count++` / `--count` pairing has no owner: any future early return or throw between them silently strands the counter above zero forever.
**Fix:** move both values into a `@Injectable({ providedIn: 'root' })` `KbqSkeletonAnimationSync` service exposing `register(): number` (returns the delay) and `unregister()`. That makes the clock per-application, testable via `TestBed.inject`, and gives the counter a single owner. It also gives SKL-PERF-01 somewhere natural to cache the parsed duration. This is internal — the service need not be exported from `index.ts`, so the API report is unaffected.

**SKL-CSS-05 · Component tokens live inside the `:not()` rule, and the duration is parsed with unit-blind `parseFloat`** — `skeleton.scss:11-17`, `skeleton.ts:73-78`.
The six CSS custom properties (`--kbq-skeleton-min-height`, `-animation-duration`, `-animation-delay`, `-border-radius`, `-wave-width`, `-z-index`) are declared inline at `skeleton.scss:12-17` rather than in a `skeleton-tokens.scss`, and — more consequentially — they are declared **inside** `.kbq-skeleton:not(.kbq-skeleton_disabled)`, a two-class selector with specificity (0,2,0). Sibling packages declare theirs at one class: `.kbq-progress-spinner { … }` (`progress-spinner-tokens.scss:1`), `:where(.kbq-scrollbar-viewport, …)` (`scrollbar-tokens.scss:1`, specificity 0 by design). The practical difference is that a consumer cannot retheme skeleton from an ancestor scope: `.my-theme { --kbq-skeleton-wave-width: 200px }` is inherited but immediately shadowed by the element's own declaration, and even `.kbq-skeleton { … }` loses. They must either match `:not(.kbq-skeleton_disabled)` themselves or use an inline style. Nothing in the code requires the tokens to be gated — the JS reads the duration only when the skeleton is enabled anyway.
Second issue, same area: `parseFloat(getPropertyValue('--kbq-skeleton-animation-duration'))` (`skeleton.ts:73-75`) is unit-blind. The declared default is `1200ms` so it works, but a consumer who overrides it as `1.2s` — the equally idiomatic spelling, and the one `scrollbar-tokens.scss:6` uses for its own duration token — silently yields `1.2`, making `elapsed % 1.2` a meaningless phase and destroying the sync the whole class exists for. An override of `0` yields `NaN` and writes `--kbq-skeleton-animation-delay: NaNms`, which makes the `animation` shorthand at `:54` invalid at computed-value time and stops the wave entirely.
**Fix:** extract `skeleton-tokens.scss` declaring the six properties on `.kbq-skeleton` alone, and `@use` it from `skeleton.scss`; keep only the *behavioural* declarations under the `:not()` gate. In `syncAnimation`, parse the value properly — accept both `ms` and `s` (`/^([\d.]+)(ms|s)$/`, multiply by 1000 for `s`) — and guard the result: `if (!Number.isFinite(durationMs) || durationMs <= 0) return;` so a bad override degrades to an unsynchronised-but-visible wave instead of a dead one. Document the accepted units in the token's comment.

**SKL-API-01 · One identifier serves three roles, and the API report is undocumented** — `skeleton.ts:34, 39, 47`; `tools/public_api_guard/components/skeleton.api.md:10-32`.
`kbqSkeleton` is simultaneously the attribute selector (`skeleton.ts:34`), the `exportAs` name (`:39`) and the input alias (`:47`), while the class member behind the input is called `enabled`. The combination produces at least one shape that reads badly: disabling the element form is written `<kbq-skeleton [kbqSkeleton]="false" />` — an element that names itself a skeleton, told by an attribute of the same name that it is not one. It is documented nowhere (see SKL-DOC-01). In the API report, `KbqSkeletonModule` and `ngOnDestroy` both carry `// @public (undocumented)` (`skeleton.api.md:22-30, 14-15`) and the file ends with `// (No @packageDocumentation comment for this package)` (`:32`); only `enabled` has a JSDoc block.
**Fix:** add JSDoc to `KbqSkeletonModule` and a `@packageDocumentation` block to `index.ts` describing the two usage forms; leave `ngOnDestroy` alone (it is an interface implementation). Document the element-form disable idiom explicitly in the class JSDoc, or introduce a clearer alias for it. Note the ordering hazard: adding JSDoc to a public member removes its `(undocumented)` marker and therefore changes `skeleton.api.md`, so the `api` CI job fails until `yarn run build:components && yarn run approve-api` is re-run — build first, the guard reads `dist/*.d.ts`.

**SKL-DOC-01 · The component's only input is documented nowhere, and the examples stubs are dead** — `skeleton.en.md:1-30`, `skeleton.ru.md:1-30`, `examples.skeleton.en.md:1-5`, `examples.skeleton.ru.md:1-5`, `apps/docs/src/app/structure.ts:912-921`.
Both guides describe what a skeleton is and when to use it, and both mention the directive form in one line — "The `[kbqSkeleton]` directive is applied to an existing element" (`skeleton.en.md:7`, `skeleton.ru.md:7`). Neither says that `[kbqSkeleton]` **takes a boolean**, that it defaults to `true`, that binding it is how you turn the skeleton off, or that the same input works on the `<kbq-skeleton>` element. That single input is the entire public API of the package. A reader has to infer it from the example source (`skeleton-directive-example.ts:17`) or from the API tab. Neither guide has an Accessibility section (see SKL-A11Y-01), and neither documents the CSS custom properties a consumer might want to retheme (see SKL-CSS-05). Separately, `examples.skeleton.en.md` and `.ru.md` are the standard "🚧 Documentation in progress 🚧" stubs; `structure.ts:920` sets `hasExamples: false`, so the Examples tab never renders and these are two unreachable files rather than a broken user surface — the three real examples are already embedded in the guides via `<!-- example(…) -->` and all three ids resolve in `packages/docs-examples/example-module.ts:5526, 5539, 5552`.
**Fix:** add a short API paragraph to both guides covering the boolean input, its `true` default, both host forms and the `<kbq-skeleton [kbqSkeleton]="false" />` idiom; add the `### Accessibility` section from SKL-A11Y-01; add a short retheming note listing the six custom properties. Delete both `examples.skeleton.*.md` stubs — the guides already embed every example, and `hasExamples: false` already declares them unreachable.

**SKL-TEST-02 · Spec hygiene: the module is named but never exercised, and two mocks are dead** — `skeleton.spec.ts:1-6, 10-24, 66, 93-111`.
Five small problems in a 112-line file. (1) `describe(KbqSkeletonModule.name, …)` (`:66`) labels the suite after the NgModule, but every test host imports the standalone `KbqSkeleton` directly (`:43, 56`) and `KbqSkeletonModule` is imported at `:6` for its `.name` alone — the module's `imports`/`exports` wiring (`module.ts:6-9`) is never instantiated by any test. (2) `NoopAnimationsModule` is added to every fixture (`:11`) although the package uses no Angular animations at all. (3) The `KBQ_WINDOW` stub provides `performance: { now: () => Date.now() }` (`:20-22`) which the implementation never calls — it uses the global `Date.now()` (`skeleton.ts:57`); the mock is a fossil of an earlier implementation and quietly implies a contract that does not exist. (4) The third case is named `'should sync animation when disabled changes'` (`:93`) but what it actually verifies is the delay computed when skeletons are **enabled** at staggered times. (5) `getSkeletonAnimationDelay(second)).toBe('0ms')` (`:110`) passes because `String(-0) === '0'`; that is correct but accidental, and worth a comment or an explicit `-0` normalisation.
**Fix:** rename the suite to `describe('KbqSkeleton', …)` and add one case that builds a host importing `KbqSkeletonModule` so the module wiring is covered; drop `NoopAnimationsModule` and the `performance` stub; rename the third case to what it asserts (`'should offset the animation delay for skeletons enabled later'`). While there, add the cases named in SKL-TEST-01 (bare attribute, `"false"` coercion, destroy/reset branch) and the ARIA cases from SKL-A11Y-01.

## 4. Recommended Remediation Phases

**Phase 1 — Make the shipped skeleton the skeleton the team sees.**
IDs: SKL-CSS-01, SKL-TEST-01. These are one piece of work: the token divergence cannot be closed with confidence until there is a screenshot of the shipped default, and the e2e application must be built without the deprecated import so it renders what a consumer renders. Land the fixture and the baselines first, then change the token (or add the content-hiding rule), then delete `apps/docs/src/main.scss:3-4` and `packages/components-dev/skeleton/styles.scss:1-2`. The deletion of those two imports is the acceptance criterion.

**Phase 2 — Loading semantics.**
IDs: SKL-A11Y-01, SKL-DOC-01. Add `aria-busy` / `role="status"` / a localized visually-hidden label and make the wrapped subtree `inert`; document the boolean input, the accessibility behaviour and the custom properties in both guides; delete the dead examples stubs. Depends on nothing above but benefits from Phase 1's fixture, which can carry the axe assertion.

**Phase 3 — Style-layer correctness.**
IDs: SKL-CSS-02, SKL-CSS-03, SKL-CSS-04, SKL-CSS-05. Re-express the wave so it survives a transformed ancestor, rename `wave` to `kbq-skeleton-wave` and add the stylelint pattern, swap `overflow: hidden` for `overflow: clip` and lift the geometry-neutral declarations out of the `:not()` gate, extract `skeleton-tokens.scss` and make the duration parse unit-aware. Every item here is guarded by a Phase 1 e2e row, so this phase is where the new baselines earn their keep. Requires `yarn run e2e:docker:update-snapshots`.

**Phase 4 — Internals, performance and API hygiene.**
IDs: SKL-ARCH-01, SKL-PERF-01, SKL-API-01, SKL-TEST-02. Move the sync clock into a root service, split `afterRenderEffect` into `earlyRead`/`write` and cache the duration there, add the missing JSDoc and `@packageDocumentation`, clean the spec. Behaviourally inert if Phases 1-3 landed with tests. Requires one `yarn run build:components && yarn run approve-api` cycle for the JSDoc-driven report change.

## Appendix A — Review Methodology

Every file in the package was read in full (`skeleton.ts` 80 lines, `skeleton.scss` 59, `skeleton.spec.ts` 112, `module.ts`, `index.ts`, `ng-package.json`, four `.md` files). Each candidate finding was then cross-checked against four independent sources: the live design-token set in `node_modules/@koobiq/design-tokens/web/new/css-tokens-{light,dark}.css` and its `deprecated/` counterpart; the two applications that host the component (`apps/docs`, `packages/components-dev/skeleton`) and their global style entry points; the three shipped docs examples plus the `sidepanel` and `alert` packages they compose with; and the API guard report together with `tools/api-extractor/config.json` and `apps/docs/src/app/structure.ts`. Library-wide comparisons (`@keyframes` naming across all component SCSS, `_CdkPrivateStyleLoader` usage, which packages ship an `e2e.ts`, a `*-tokens.scss`, a `_*-theme.scss`, a `public-api.ts` or a bare `module.ts`) were computed by enumerating `packages/components/*/` rather than by sampling, so the "only one" and "one of five" claims above are counts, not impressions. `git log -L` was used to date the two deprecated-token imports.

The single strongest piece of evidence in this review is a workaround: both in-repo applications import a deprecated token file to avoid the value the library ships. That is what turned SKL-CSS-01 from a colour opinion into a confirmed defect, and it is also why SKL-TEST-01 is filed at P2 rather than as a routine coverage gap — the missing screenshot is the reason the divergence went unnoticed for four commits.

Refuted during verification:
- **"`_CdkPrivateStyleLoader` is a private Angular API and must not be depended on"** — refuted as skeleton-specific. `scrollbar.ts:2, 205, 252` uses the same import and the same `*-style-loader` component shape, and CDK's own `_VisuallyHiddenLoader` is built identically. If the dependency is a risk it is a library-wide one, not a finding against this package.
- **"The style loader races the first `afterRenderEffect`, so `parseFloat` can read an empty string"** — refuted. `_CdkPrivateStyleLoader.load()` calls `createComponent` synchronously (`node_modules/@angular/cdk/fesm2022/style-loader.mjs:33-36`) from the directive constructor (`skeleton.ts:52`), so the `<style>` element exists before any render hook runs. The `NaN` hazard is real but reachable only through a bad consumer override, and is filed under SKL-CSS-05.
- **"The global counter produces a wrong delay because it counts disabled instances"** — refuted. `count` is incremented for every instance while `animationStartTime` is set only by enabled ones (`skeleton.ts:50, 59`), so a permanently disabled host does keep the anchor alive past the point where no skeleton is animating. I traced it: every instance enabled afterwards shares that same anchor, so they remain mutually in phase, and the delay is taken modulo the duration so a stale anchor cannot grow unbounded. No wrong delay is reachable. The residual concern is architectural only and is filed as SKL-ARCH-01.
- **"`module.ts` instead of `skeleton.module.ts`, and the missing `public-api.ts`, violate the AGENTS.md package structure"** — refuted as a defect. Twelve packages use a bare `module.ts` (`actions-panel`, `clamped-text`, `content-panel`, `dynamic-translation`, `flag`, `inline-edit`, `overflow-items`, `resizer`, `skeleton`, `time-range`, `top-bar`, `username`) and ten have no `public-api.ts`. This is an established alternate convention in the repository, not something skeleton got wrong.
- **"`--kbq-skeleton-background` and the three wave colours are undefined and compute to nothing"** — refuted. All four resolve in `css-tokens-light.css:964-967` and `css-tokens-dark.css:964-967`, and `--kbq-size-l` / `--kbq-size-xxs` resolve in `css-tokens.css:1293`. The defect is the *value* of one of them, not its absence.
- **"Missing `ChangeDetectionStrategy.OnPush`"** — not applicable to `KbqSkeleton`, which is a directive. It is genuinely absent from `SkeletonStyleLoader` (`skeleton.ts:22-27`) where CDK's equivalent sets it, but that component is created detached and never attached to `ApplicationRef`, so it is never change-detected at all. No impact; not filed.
- **"No `prefers-reduced-motion` handling"** — refuted. `skeleton.scss:56-58` disables the wave under `prefers-reduced-motion: reduce`, leaving the static placeholder. This is a strength, not a gap.

Corrected on verification:
- **SKL-CSS-01** was first drafted as "the skeleton colour tokens are missing from the live token set", by analogy with the deprecated-path import in `apps/docs/src/main.scss`. The tokens exist. What is actually wrong is that their *values* differ — translucent in the live set, opaque in the deprecated one — and that both in-repo applications silently pin themselves to the deprecated values, so no surface in this repository renders the shipped default. The finding was rewritten around that divergence and kept at P1.
- **SKL-A11Y-01** was first drafted as P0 on the strength of the AGENTS.md "MUST pass all AXE checks" mandate. axe-core does not flag a custom element that carries no role, and the two sibling loading components (`progress-spinner`, `loader-overlay`) have the same gap, so it is a WCAG 1.3.1 / 2.4.7 / 4.1.2 judgement plus a mandate violation, not an automated failure. Filed at P1.
- **SKL-CSS-02** was first drafted as "`position: fixed` on a pseudo-element is wrong". It is deliberate and well-executed — paired with `clip-path: inset(0)` (`skeleton.scss:27`) precisely because `clip-path` clips fixed descendants where `overflow: hidden` does not — so the finding was narrowed to the one case where the technique fails silently, and only survived because that case is the component's own documented sidepanel example.
