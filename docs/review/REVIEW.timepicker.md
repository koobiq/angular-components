# Koobiq `timepicker` Component — Code Review & Improvement Plan

> Scope: `packages/components/timepicker` (directive, constants, SCSS, Jest spec, e2e fixture + Playwright spec, user guides, API guard report) · Commit `b665e503` · 2026-08-28
> Generated by a multi-dimension review (architecture, correctness, RxJS/lifecycle, accessibility, public API/types, styles, tests, docs) with manual verification of every finding against the source, the in-repo consumers, the Luxon date adapter and `tsconfig.json`. 14 findings confirmed (P0×0, P1×3, P2×5, P3×6); 6 candidate findings refuted during verification (see Appendix A). This document is a review + roadmap; no source is modified by it.

---

## 1. Executive Summary

`KbqTimepicker` is a single 1061-line directive (`timepicker.directive.ts`) that turns a native `<input>` into a masked, segment-editable time field. It is its own `ControlValueAccessor`, its own `Validator` and its own `KbqFormFieldControl`, it owns the caret, and it is consumed in three production surfaces inside the repo: `filter-bar`'s date-period popover (`pipe-datetime.html:87, 122`), `time-range`'s editor (`time-range-editor.html:32, 56`) and three docs examples. It has **no release blockers**, but its three P1s all belong to one family: *the text in the field and the value in the form can disagree, and nothing detects it.*

- **The parse error the component publishes can never fire from user interaction.** `onInput` sets `lastValueValid = false` and then returns *without* calling `onChange` (`timepicker.directive.ts:559-565`), and `onPaste` returns early on an unparseable clipboard (`:522-524`). Since a validation run only happens when the value changes, `parseValidator` (`:1008-1012`) is never re-evaluated while the input holds text it could reject. Paste `2024-01-05 10:20` into a timepicker and the field displays that string — written straight into the DOM by `formatUserPaste` (`:662`), a helper whose name promises a pure transform — while the form still holds the previous time and reports `VALID`, permanently. `filter-bar` already documents relying on this error (`pipes/pipe-date-base.ts:271-272`) (TP-BUG-03).
- **Backspace, Delete, Ctrl+X, Ctrl+Z and drag-and-drop never reach the directive at all.** The host binds `(keydown)` but not `(input)` (`:127-141`), and `onKeyDown` explicitly routes `DELETE`, `BACKSPACE` and every `ctrlKey`/`metaKey` combination to `noop()` (`:588-594`). Select-all + Delete therefore empties the field while the model keeps the old time and the control stays valid until blur — and the guide's promise that drag-and-drop pasting "triggers validation during input" (`timepicker.en.md:62`) is met by no listener whatsoever (TP-BUG-02).
- **12-hour paste puts noon and midnight on the wrong day.** `getDateFromTimeString` does `hours += 12` for any `p`/`pm` suffix (`:975-977`), so `12:30 pm` becomes hour **24**, and Luxon's `set({hour: 24})` rolls silently into the next day at `00:30` — a 12-hour error plus a one-day shift. `12:30 am` gets the right time on the wrong day. The eleven am/pm tests (`timepicker.spec.ts:390-532`) assert only `.toString()).toContain('00:03:00')`, so they pass while the date advances (TP-BUG-01).

Genuine strengths, and they are recent and deliberate: the locale-reactive placeholder built from `kbqInjectLocaleConfiguration()` + `effect()` with a load-bearing comment explaining why the read precedes the guard (`:452-463`); the timezone re-render subscription with `takeUntilDestroyed` and an equally careful comment (`:465-469`); a complete `ErrorStateMatcher` integration covered by 14 dedicated Jest cases across four matcher strategies (`timepicker.spec.ts:951-1113`); and the DS-3985 fix (`:543-546`) which shipped with a genuine *behavioural* Playwright test rather than another screenshot (`e2e.playwright-spec.ts:15-30`). 63 Jest cases and light/dark screenshots make this one of the better-tested directives in the library — the gap is that almost none of that coverage touches the keyboard path where the defects live.

## 3. Prioritized Findings (deduplicated, verified)

### P0 — Release blockers

None.

### P1 — High

**TP-BUG-03 · `kbqTimepickerParse` is unreachable from user input; unparseable text leaves a stale model reporting `VALID`** — `timepicker.directive.ts:515-531, 533-570, 652-672, 1008-1012`; consumer `filter-bar/pipes/pipe-date-base.ts:271-272`.
The directive publishes a parse error, `{ kbqTimepickerParse: { text: this.viewValue } }` (`:1011`), whose guard is `this.focused || this.empty || this.lastValueValid` (`:1009`). Both paths that can set `lastValueValid = false` then decline to trigger a validation run: `onInput` sets it at `:538` and returns at `:559-565` without calling `onChange`, and `onPaste` returns at `:522-524` before it ever reaches `this.value = …`. Angular re-runs a control's validators when its value changes, when `updateValueAndValidity()` is called, or when `registerOnValidatorChange`'s callback fires — none of which happens here (`min`/`max` setters are the only callers of `validatorOnChange`, `:287, :301`). `ngDoCheck → updateErrorState()` does not help: `KbqErrorStateTracker.updateErrorState` reads `control.invalid` through the matcher (`core/common-behaviors/error-state.ts:86-97`), it does not revalidate. The user-visible sequence is worse than "no error": paste `2024-01-05 10:20` and `formatUserPaste` writes the raw string into the DOM as a side effect of a *format* helper (`:662`, `this.setViewValue(value)` inside the "no hours group" branch) before `onPaste` bails out. The field now shows `2024-01-05 10:20`, the form still holds the previous `DateTime`, the control is `VALID` and untouched by any error styling — and blurring does not fix it, because `onBlur` (`:505-513`) routes through the same `formatUserPaste` + `onInput` pair and hits the same early return. The sibling `KbqDatepickerInput`, written against the same shape, does the missing call: `this.control.updateValueAndValidity()` in exactly this branch (`datepicker/datepicker-input.directive.ts:757-762`). And a consumer already assumes the error works — `pipe-date-base.ts:271-272` documents `kbqTimepickerParse` as one of the states it deliberately leaves "to the field's own error styling".
**Fix:** in `onInput`'s failure branch, mirror the datepicker: when `viewValue` is non-empty and unparseable, call `this.control?.updateValueAndValidity()` (the `AbstractControl` is already captured in `setControl`, `:1049-1058`) so `parseValidator` runs; keep the existing `onChange(null)` for the empty case. Separately, move the `setViewValue(value)` out of `formatUserPaste` — a function named `format*` must not write to the DOM — and have `onPaste` emit `incorrectInput` and restore the last valid rendering when `getDateFromTimeString` returns `null`, instead of leaving the clipboard text on screen. Guard with two Jest cases (paste unparseable text → control is `INVALID` with `kbqTimepickerParse` and the model unchanged; type unparseable text then blur → same) and one Playwright case in `e2e.ts` covering the visible error state.

**TP-BUG-02 · No `(input)` listener: Backspace, Delete, Ctrl+X, Ctrl+Z and drag-and-drop never update the model** — `timepicker.directive.ts:127-141, 580-624`; docs claim at `timepicker.en.md:62`, `timepicker.ru.md` (same section).
The host block binds `(blur)`, `(focus)`, `(paste)` and `(keydown)` (`:137-140`) — there is no `(input)`, no `(drop)`, no `(change)`. Every value update therefore depends on `onKeyDown` scheduling `setTimeout(this.onInput)` (`:616, :622`), and `onKeyDown`'s second branch explicitly excludes the destructive keys from doing so: `[DELETE, BACKSPACE, TAB].includes(keyCode) || event.ctrlKey || event.metaKey` falls into `noop()` (`:588-594`). The consequences are concrete. Select-all + <kbd>Delete</kbd> empties the visible field while the form control keeps the previous `DateTime`, stays `VALID`, and — if the control carries `Validators.required` — never reports the field as empty; `onChange(null)` (`:561`) is reachable only from `onBlur`. <kbd>Ctrl</kbd>+<kbd>X</kbd> and <kbd>Ctrl</kbd>+<kbd>Z</kbd> behave identically. Dragging text onto the input fires `drop` + `input`, neither of which is listened to, so the guide's statement that "when copying values from the clipboard **or pasting them using drag-and-drop**, validation during input is triggered" (`timepicker.en.md:62`) describes behaviour that does not exist. Anything watching `valueChanges` live — `filter-bar`'s period preview, `time-range`'s cross-field `rangeValidator` (`time-range-editor.ts:151`) — reads the stale time for the whole editing session. Note the same `isKeyForByPass` shape exists in `datepicker-input.directive.ts:957-964`, so the fix is a family fix, but the timepicker's version is the more damaging one because it has no revalidation fallback (TP-BUG-03).
**Fix:** add `'(input)': 'onInput()'` to the host block and delete the `setTimeout(this.onInput)` calls at `:616, :622, :742` — `setViewValue` writes through `Renderer2.setProperty(el, 'value', …)` (`:1034-1036`), which does **not** dispatch an `input` event, so there is no feedback loop. Remove `DELETE`/`BACKSPACE` from the bypass list (they now need no special casing) and keep the bypass only for `TAB` and clipboard/undo shortcuts, which the native `input` event already covers. Pair it with `(compositionstart)`/`(compositionend)` flags that suppress the `setViewValue` rewrite while an IME composition is active — rewriting `.value` mid-composition aborts it in Chromium and WebKit. Regression tests: a Jest case that dispatches a real `input` event after clearing the value and asserts `ngModel.value === null`, and a Playwright case in `e2e.playwright-spec.ts` that fills, selects all, presses `Delete` and asserts the bound model is empty *before* blur.

**TP-BUG-01 · 12-hour paste maps noon and midnight to hour 24, silently advancing the date by one day** — `timepicker.directive.ts:971-977`, `timepicker.constants.ts:28`; test blind spot at `timepicker.spec.ts:486-496`.
`AM_PM_FORMAT_REGEXP` (`timepicker.constants.ts:28`) accepts `[0-1]?[0-9]` for hours, so `12:30 pm` matches. The branch then runs `if (/[p]/i.test(amPm[3]) || (/[a]/i.test(amPm[3]) && hours === 12)) { hours += 12; }` (`:975-977`) — with no `hours === 12` special case for PM and no modulo — producing `hours = 24`, which is fed to `dateAdapter.createDateTime(..., 24, 30, 0, ...)`. The Luxon adapter implements that as `createDate(y, m, d).set({ hour, … })` (`@koobiq/luxon-date-adapter/index.esm.js:440-447`), and `DateTime.set({ hour: 24 })` does not throw or invalidate — it rolls over: `2024-05-10` + `hour: 24` yields `2024-05-11T00:30`, `isValid === true` (verified directly against the installed Luxon). So `12:30 pm` renders as `00:30` **on the next day**, and `12:30 am` renders the correct `00:30` also on the next day. Both matter beyond the clock face: `minValidator`/`maxValidator` compare with `compareDateTime`, which orders by year → month → day *before* hours (`@koobiq/date-adapter/index.esm.js:47-54`), so a one-day shift silently satisfies or violates every configured bound; and in `filter-bar/pipes/pipe-datetime.html:87` the same `FormControl` is bound to both a date input and the timepicker, so the shifted day is rendered back into the date field. `13:30 pm` produces hour 25 and the same rollover. The eleven am/pm regression tests (`timepicker.spec.ts:390-532`) all assert with `expect(value.toString()).toContain('HH:mm:ss')` — a substring check on the time only — so the `12:3 aM` case at `:486-496` passes today while the date silently becomes `1970-01-02`.
**Fix:** replace the branch with an explicit 12-hour conversion — `hours = hours % 12; if (isPm) hours += 12;` — after rejecting `hours > 12` as not a valid 12-hour clock reading (emit `incorrectInput` instead of coercing). Tighten `AM_PM_FORMAT_REGEXP` to `(1[0-2]|0?[0-9])` so `13:30 pm` cannot match at all. Then decide the docs question in TP-DOC-01: either document 12-hour paste as a supported input, or remove the branch. Rewrite the eleven am/pm tests to assert the full ISO string (`expect(adapter.toIso8601(value)).toBe(…)`) rather than a time substring — as written they cannot fail on a date shift, which is exactly how this survived.

### P2 — Should fix

**TP-A11Y-01 · `[attr.required]="false"` marks the field required, and `aria-invalid` is never set** — `timepicker.directive.ts:127-141` (host block, `:133-134`); compare `input/input.ts:41-42`, `input/input-password.ts:27-28`, `textarea/textarea.component.ts:46`, `checkbox/checkbox-required-validator.ts:19`.
Two independent gaps in one nine-line host block. (1) `'[attr.required]': 'required'` is an *attribute* binding, and Angular removes an attribute only for `null`/`undefined` — every other value is stringified. `_required` is uninitialised (`:250`), so an untouched timepicker is fine; but the moment a consumer writes `[required]="isRequired"` and the expression is `false`, the DOM gets `required="false"`, which HTML treats as a present boolean attribute: the field becomes required for native constraint validation, matches `:required` in CSS, and is announced as "required" by screen readers. The correct forms are both already in this repo — `KbqInput`, `KbqInputPassword` and `KbqTextarea` use the property binding `'[required]': 'required'`, and `KbqCheckboxRequiredValidator` uses the explicitly-guarded attribute form `'[attr.required]': 'required ? "" : null'`. Two lines above, the same host block already guards the twin case correctly: `'[attr.disabled]': 'disabled || null'` (`:133`). (2) There is no `[attr.aria-invalid]`. `KbqInput` — whose class this directive puts on its own host (`class: 'kbq-input kbq-timepicker'`, `:128`) so that the form-field theme paints it — sets `'[attr.aria-invalid]': 'errorState'` (`input.ts:41`), and `form-field.spec.ts:889-896` asserts that contract for inputs. A timepicker in an error state is styled red and announced as valid. WCAG 4.1.2 / 3.3.1; note this is a WCAG judgement plus an in-repo inconsistency, not an automated axe failure (axe does not flag a missing `aria-invalid`).
**Fix:** change `'[attr.required]': 'required'` to `'[required]': 'required'` (matching the three sibling controls) and add `'[attr.aria-invalid]': 'errorState'`. Apply the identical pair to `KbqDatepickerInput` (`datepicker-input.directive.ts:250`), which carries the same defect, so the two masked inputs stop diverging from the plain one. Cover with Jest cases asserting no `required` attribute for `[required]="false"` and `aria-invalid="true"` once the matcher reports an error state — the existing `ErrorStateMatcher` suite (`timepicker.spec.ts:951-1113`) already builds every fixture these need.

**TP-LIFE-01 · `control.valueChanges` is subscribed without teardown and writes `_value` behind the setter** — `timepicker.directive.ts:1049-1058`; reproduction path at `filter-bar/pipes/pipe-datetime.html:28, 51-52, 87`.
`setControl` — called from `validate()` (`:627`), i.e. from a validation run — does `this.control.valueChanges.subscribe((value) => (this._value = value))` with no `takeUntilDestroyed`, no stored `Subscription` and no unsubscribe in `ngOnDestroy` (`:485-487` completes only `stateChanges`). The `AbstractControl` reliably outlives the directive: in `filter-bar` the `formGroup` lives on the pipe component while both timepickers live inside `<ng-template #content>` behind `@if (isListMode)` (`pipe-datetime.html:28, 51`), so every popover open/close and every switch between list and period mode destroys and recreates the directives against the same surviving control — one retained `KbqTimepicker` (and its `ElementRef`, and the detached `<input>`) per cycle, each still writing `_value` on a dead instance. The write itself is the second half of the finding: it assigns the raw emission straight to the private field, bypassing the `value` setter's `deserialize` + `getValidDateOrNull` pipeline (`:313-321`). A `control.setValue('10:00')` therefore leaves `_value` holding a `string` typed as `D`, which `getTimeStringFromDate` then hands to `dateAdapter.isValid` (`:948`), and which the locale `effect()` (`:462`) later re-runs through `deserialize`, silently nulling the value and clearing the field.
**Fix:** pipe the subscription through `takeUntilDestroyed(this.destroyRef)` (inject `DestroyRef`; `setControl` runs outside the injection context, so the explicit `destroyRef` overload is required) and assign through the public setter — `this.value = value` — or, better, drop the subscription entirely and let `writeValue` be the single write path, since Angular already calls it for every `setValue`/`patchValue`. Guard with a Jest case that creates and destroys the host ten times against one `FormControl` and asserts the observer count on `valueChanges` does not grow.

**TP-CSS-01 · Ten lines of SCSS: one dead token reference, one hardcoded container width, one dead host binding** — `timepicker.scss:1-10`; `input/input.scss:14, 17`; `form-field/form-field.ts:96-113`; host binding at `timepicker.directive.ts:135`, `getSize()` at `:489-491`.
`.kbq-timepicker { padding-right: var(--kbq-timepicker-size-padding-right, var(--kbq-size-s)); }` (`:5`) references a token that exists nowhere in `@koobiq/design-tokens` — a grep for `kbq-timepicker` across the whole installed `web/` tree returns zero hits — so the fallback `--kbq-size-s` (`8px`) is taken 100% of the time, and the package's own `@TODO` at `:4` says as much. That declaration also sits in a specificity tie: `.kbq-input` sets the `padding` shorthand (`input/input.scss:17`) at the same 0,1,0 weight, and the timepicker only wins because `'../timepicker/timepicker.scss'` is listed *after* `'../input/input.scss'` in `KbqFormField`'s `styleUrls` (`form-field.ts:103` vs `:106`) — the comment there warns that removing an entry unstyles a control, but not that reordering silently changes this one. The second rule, `.kbq-form-field-type-timepicker { width: 136px; }` (`:8-10`), is a control reaching up to size its container by a magic number, identical for `HH:mm` and `HH:mm:ss` and identical in every locale — while the guide states the width is "built by the formula _left padding + mask + right padding_" and that "the mask width will be different for each language" (`timepicker.en.md:86-90`). Because `.kbq-input` is `width: 100%` (`input/input.scss:14`) inside that fixed box, the `'[attr.size]': 'getSize()'` host binding (`:135`) — the only place the component adapts to its format, returning 5 or 8 — can never affect layout, and it also overwrites any `size` a consumer sets (someone tried: `components-dev/timepicker/template.html:65, 75`, both commented out).
**Fix:** three small moves. Register `--kbq-timepicker-size-padding-right` in the design-tokens package or delete the reference and use `var(--kbq-size-s)` directly, so the value stops pretending to be themeable. Replace the `136px` constant with per-format tokens (`--kbq-timepicker-size-width-short` / `--kbq-timepicker-size-width-full`) selected by a `kbq-timepicker_full` modifier on the host, which is what the guide already promises. Then either delete the `[attr.size]` binding and `getSize()`, or make the container width follow it — shipping both a live `size` attribute and a constant CSS width that overrides it is the current state and it cannot be right either way. Baselines must be regenerated with `yarn run e2e:docker:update-snapshots`.

**TP-TEST-01 · The only digit-by-digit typing test asserts the string it wrote itself** — `timepicker.spec.ts:641-671`; helper at `core/testing/event-objects.ts:47-62`.
`'Manual keyboard input digit-by-digit'` is the sole test for the component's primary interaction, and it verifies nothing. It builds its events with `createKeyboardEvent('keydown', ONE)` — a helper whose `key` parameter is optional and here omitted, so `event.key` is `undefined` (`event-objects.ts:61`) and `onKeyDown`'s `/^\D$/.test(event.key)` branch (`:607`) is skipped in favour of the `setTimeout(this.onInput)` fallback (`:622`). The test is not `fakeAsync` and never ticks, so that timer never runs. It then assigns `inputNativeElement.value = '1' + …` by hand and dispatches a fake `'input'` event for which **no host listener exists** (see TP-BUG-02), and asserts `value` is `'1:00:00'` — the exact string the previous line wrote. Both assertions in the test are self-fulfilling; deleting the entire `onKeyDown`/`onInput` implementation would leave it green. Around it, the wider suite (63 cases) has no coverage at all for: Backspace/Delete, cut/undo, drag-and-drop, IME composition, `kbqTimepickerParse`, the 12-PM case (TP-BUG-01), `[required]`, `kbqValidationTooltip`, or the caret position after a segment edit — the last being the whole point of `createSelectionOfTimeComponentInInput`.
**Fix:** rewrite the case around real events: pass the `key` argument to `createKeyboardEvent`, wrap in `fakeAsync` + `tick()`, and assert the *model* (`ngModel().value`) and `selectionStart`/`selectionEnd` rather than the input string the test just set. Add the mutation check that makes it meaningful — with the assertion in place, reverting `onInput`'s caret restoration (`:551-556`) must fail at least one case. Then add the missing cases listed above, and move the interaction-heavy ones (caret, Delete, drag-drop) into `e2e.playwright-spec.ts`, which already demonstrates the pattern at `:15-30`. Also fix the two fixtures typing `timeFormat: string` and binding it to `[format]: TimeFormats` (`:686, :766`) — Jest does not run Angular's template type-checker, so those bindings compile in the spec but would be an NG error in application code under `strictTemplates: true` (`tsconfig.json:117`).

**TP-DOC-01 · The published guide contradicts the implementation in three places** — `timepicker.en.md:21, 62, 86-90`, `timepicker.ru.md:25` and the mirrored sections.
Three statements a consumer would reasonably act on are untrue. (1) "Time input is only allowed in 24-hour format" (`:21`, RU `:25`) — the component accepts 12-hour text on paste through `AM_PM_FORMAT_REGEXP` (`timepicker.constants.ts:28`) and eleven Jest cases exercise it (`timepicker.spec.ts:390-532`); the feature is real, undocumented, and broken at noon (TP-BUG-01). (2) "When copying values from the clipboard **or pasting them using drag-and-drop**, validation during input is triggered" (`:62`) — the host has no `(drop)` and no `(input)` binding (`:127-141`), so drag-and-drop bypasses everything until blur (TP-BUG-02). (3) The "Design and animation" section states the field width is built as "_left padding + mask + right padding_", that "the mask width will be different for each language", and that "the right padding is always 16px" (`:86-90`) — while the implementation is a single `width: 136px` for both formats and every locale, plus an 8px right padding from an undefined token (TP-CSS-01). Separately, not one of the ten public inputs is described in prose anywhere: `format`, `min`, `max`, `value`, `required`, `placeholder`, `id`, `errorStateMatcher` and `kbqValidationTooltip` appear only in the generated API tab (`structure.ts:1038-1039` sets `hasApi: true`), where 54 of the report's entries carry `// (undocumented)`.
**Fix:** decide the 12-hour question first (TP-BUG-01) and then make `:21` state the outcome — either "24-hour only, with 12-hour clipboard text converted on paste" or a removal of the branch. Delete the drag-and-drop clause, or implement it as part of TP-BUG-02 and keep it. Rewrite the width paragraph to describe what ships, or change what ships (TP-CSS-01) — the two must be reconciled in one commit, not separately. Add an "Inputs" section covering `format`/`min`/`max` (including the date-comparison semantics from TP-API-02) to both guides, and JSDoc to the corresponding members, remembering that JSDoc on a public member removes its `(undocumented)` marker and therefore requires a `build:components` + `approve-api` cycle.

### P3 — Nice to have / hygiene

**TP-API-01 · Internals, caret setters and a dead getter are all public; four `any`s; 54 undocumented members** — `tools/public_api_guard/components/timepicker.api.md`; `timepicker.directive.ts:80, 87, 351-353, 367-369, 515, 533, 580`.
The report exposes the entire implementation: `onInput`, `onKeyDown`, `onPaste($event: any)`, the `selectionStart`/`selectionEnd` accessor pairs, `viewValue`, `getSize`, `isFullFormat`/`isShortFormat`, and `hasSelection` — which is referenced *nowhere in the repository* (a grep for `hasSelection` returns only its own declaration at `:351`), while `spaceKeyHandler` open-codes the same comparison at `:735`. Four members are typed `any`: `KBQ_TIMEPICKER_VALUE_ACCESSOR` (`:80`), `KBQ_TIMEPICKER_VALIDATORS` (`:87`), `onPaste`'s parameter (`:515`, an implicit `any` the workspace permits because `noImplicitAny` is off — only `strictNullChecks` is set, `tsconfig.json:21`), and `get ngControl(): any` (`:367-369`), which returns an `AbstractControl` where `KbqFormFieldControl` declares `readonly ngControl: NgControl | null` (`form-field/form-field-control.ts:23`). 54 entries carry `// (undocumented)`. Several uninitialised private fields also make `boolean` getters return `undefined` on a fresh instance (`_disabled` `:220`, `_required` `:250`, `_id` `:233`) — harmless today because the host bindings and the form field both coerce, but a declared type that is not true of the first read.
**Fix:** delete `hasSelection`; make `onInput`/`onKeyDown`/`onPaste` and the caret accessors `protected`; type `onPaste(event: ClipboardEvent)`, the two providers `Provider`, and `ngControl` as `NgControl | null` (which will require `setControl` to stop storing a bare `AbstractControl` — see the note in Appendix A about why the current shape works by duck-typing). Initialise the three private fields. Add JSDoc to the members that stay public. One `yarn run build:components && yarn run approve-api` cycle covers the whole batch; the visibility tightening is breaking, so schedule it with the next major.

**TP-ARCH-01 · Ten identical false migration TODOs, `validate()` as a registration hook, and five uncleared timers** — `timepicker.directive.ts:171-172, 186-187, 201-202, 222-223, 239-240, 252-253, 278-279, 292-293, 306-307, 325-326`; `:327-347`; `:345, 616, 622, 742, 819`.
Ten `@Input()` accessor pairs each carry the auto-generated "Skipped for migration because: Accessor inputs cannot be migrated as they are too complex" comment. It is untrue of most of them — `id`, `required` and `placeholder` are one-line coercions that `input({ transform: … })` covers directly — and it discourages the next reader from touching any of them. `validate()` doubles as the control-registration hook (`:626-630` calls `setControl`), so a `Validator` method has a lifecycle side effect and `this.control` is never reset if the control is swapped. The `kbqValidationTooltip` setter (`:327-347`) reaches into another component and permanently rewrites its configuration — `tooltip.enterDelay`, `tooltip.trigger = 'manual'`, `tooltip.initListeners()` — which is why binding the form-field's own `#tooltip="kbqTooltip"` to it (as `timepicker-overview-example.ts:18-20` does) silently disables that tooltip's hover trigger for the rest of its life; re-binding the input subscribes to `incorrectInput` again with no unsubscribe of the previous handler. Finally, five `setTimeout` sites (`:345, 616, 622, 742, 819`) are never stored and never cleared: rapid typing queues several caret-restoration callbacks that each re-derive `getTimeEditMetrics` against whatever the value is by then, and all five can still run after destroy.
**Fix:** migrate the simple accessors to `input({ transform: … })` and delete the TODOs from the rest with a one-line note saying why they stay (`format` and `value` genuinely need the setter side effects); move `setControl` out of `validate()` into `registerOnChange`, which Angular calls exactly once with the control in scope. Document the `kbqValidationTooltip` mutation in JSDoc and unsubscribe the previous `incorrectInput` handler before subscribing a new one. Replace the caret timers with a single stored handle cleared before each schedule and in `ngOnDestroy` (or `afterNextRender`, matching the pattern the form-field package standardised on).

**TP-API-02 · `min`/`max` compare the whole date, not the time of day, and nothing says so** — `timepicker.directive.ts:1014-1028`; `@koobiq/date-adapter/index.esm.js:47-54`; consumers `filter-bar/pipes/pipe-datetime.html:87-92`, `docs-examples/.../timepicker-field-validation-example.ts:36-37`.
`minValidator`/`maxValidator` call `dateAdapter.compareDateTime`, which orders by year → month → day → hours → minutes → seconds → ms. For a control whose entire UI is a clock, that means `[min]` and `[max]` are *instant* bounds, not time-of-day bounds: a value on a different calendar day satisfies or violates them purely on the date, before the hours are ever compared. Both readings appear in the repo and neither is documented. `filter-bar` relies on the instant semantics — the same `FormControl` feeds a date input and the timepicker, and `[min]`/`[max]` are the period bounds (`pipe-datetime.html:87-92`) — so full comparison is correct there. The docs example reads as time-of-day and only works because both sides are derived from `adapter.today()` (`timepicker-field-validation-example.ts:36-37`); point the same example at a value from a different day and the bounds stop constraining the clock. This is *not* the datepicker's `[minDate]`/`[maxDate]` vs `[min]`/`[max]` split — the timepicker has no calendar surface, so there is nothing to bridge (see Appendix A) — it is an undocumented choice between two defensible meanings.
**Fix:** document the instant semantics in the guides and in JSDoc on both inputs, with the one-sentence consequence ("a value on another day is compared by date first"). If time-of-day bounds are also wanted, add them as separate inputs rather than changing these — `filter-bar` depends on the current behaviour and a silent change would break its period validation.

**TP-A11Y-02 · No `inputmode`, and non-Latin letters from an IME are treated as separators** — `timepicker.directive.ts:127-141, 583-587, 607-620, 678-690`; `core/keycodes/keycodes.ts:152-154`.
The host sets `autocomplete="off"` but no `inputmode`, so a digits-only masked field opens the full alphabetic keyboard on mobile — and every letter it offers is then rejected by `isLetterKey` (`:583`), which is a pure keyCode range test over Latin `A`–`Z` (`keycodes.ts:152-154`). A character that arrives without a Latin keyCode — an IME, a virtual keyboard, `keyCode 229` — misses that guard and falls through to `/^\D$/.test(event.key)` (`:607`), where `replaceSymbols`'s `(?<symbol>\W)` (`:681`) matches it, because JavaScript's `\w` is ASCII-only: typing `ф` after one digit produces `01` instead of an `incorrectInput` emission (verified directly against the regex). Separately, the arrow-key model — where <kbd>↑</kbd>/<kbd>↓</kbd> change the selected segment and the whole segment is programmatically re-selected afterwards (`:818-825`) — is announced to a screen reader only as a value change on a plain text input; there is no `aria-valuetext` or live region naming the segment being edited, which the guide describes as the primary editing mode (`timepicker.en.md:27-31`).
**Fix:** add `'[attr.inputmode]': '"numeric"'` to the host block. Replace the `isLetterKey` guard with a positive test — accept only `/^\d$/` plus the separator set, reject everything else with `incorrectInput` — so the rule stops depending on keyCodes and covers every layout and input method. For the arrow model, consider announcing the edited segment through a visually-hidden live region, and cover the whole thing with an axe run in the e2e fixture (`e2e.ts` already renders eight states and would need one assertion).

**TP-STYLE-01 · Misnamed constants, a dead ternary branch, an unused field and deprecated `keyCode`** — `timepicker.constants.ts:30-32`; `timepicker.directive.ts:421, 581, 747-749, 810-812, 845-855, 886-896`.
`SECONDS_PER_MINUTE = 59`, `MINUTES_PER_HOUR = 59` and `HOURS_PER_DAY = 23` are maxima, not counts — the names say the opposite of the values, and all three are exported publicly. The arithmetic that consumes them is correct only because it compares with `>` / `<` rather than `>=` (`:845-855, :886-896`), so a future reader "fixing" the names to 60/60/24 would silently break the wrap-around. `const nextDividerPos = this.viewValue.indexOf(':', cursorPos); cursorPos = nextDividerPos ? nextDividerPos + 1 : 0;` appears twice (`:747-749, :810-812`): `indexOf` returns `-1` when there is no further separator, and `-1` is truthy, so the intended `: 0` branch is dead and the wrap to the hours segment happens through `-1 + 1 = 0` by accident. The `separator` field (`:421`) holds `':'` and is read once (`:787`) while every other site hardcodes the literal. `onKeyDown` reads the deprecated `event.keyCode` (`:581`) throughout, which is also what forces the keyCode-based letter test in TP-A11Y-02.
**Fix:** rename the constants to `MAX_SECONDS`/`MAX_MINUTES`/`MAX_HOURS` (keeping the old exports as deprecated aliases for one minor, since they are public), replace both ternaries with an explicit `nextDividerPos === -1 ? 0 : nextDividerPos + 1`, and either use `this.separator` everywhere or delete it. Migrate `keyCode` to `event.key` alongside the TP-A11Y-02 rewrite. None of this changes behaviour, so the existing 63 cases are the regression guard.

**TP-DOC-02 · `examples.timepicker.*.md` are dead stubs, and the dev app is 60% commented out** — `examples.timepicker.en.md:1-5`, `examples.timepicker.ru.md:1-5`, `apps/docs/src/app/structure.ts:1031-1041`; `components-dev/timepicker/template.html:41-91`, `module.ts:57, 62, 66, 69-70, 89-95`.
Both example stubs carry the standard "🚧 Documentation in progress 🚧" text, and `structure.ts:1040` sets `hasExamples: false`, so the Examples tab never renders and the two files are unreachable — dead files rather than a broken user surface, exactly as in `divider`. Three real examples exist and are already embedded in the guide (`packages/docs-examples/components/timepicker/`). The dev app is worse than dead: 51 of its 92 template lines are commented-out markup (`template.html:41-91`), including the only attempts at `kbqValidationTooltip`, a `[formControl]` binding and the `size` experiment, and `module.ts` still declares `placeholder`, `formControlValue`, `testForm`, `isDisabled`, `selectedLanguage`, `toggleDisable()` and `ngModelChange()` for a template that uses none of them. The result is that `yarn run dev:timepicker` — the manual smoke surface every phase below relies on — exercises neither the disabled state, nor `required`, nor the validation tooltip.
**Fix:** delete both stubs (the guide embeds all three examples inline, so nothing is lost) or populate them and flip `hasExamples: true`; deleting matches what `structure.ts` already declares. Strip the commented-out blocks from the dev template and the now-unused members from `module.ts`, then add live rows for disabled, `[required]="false"` (the TP-A11Y-01 case), the validation tooltip and both formats side by side, so the manual pass has something to look at.

## Appendix A — Review Methodology

Findings were gathered by reading every file in the package (`timepicker.directive.ts` in full, plus constants, SCSS, module, spec, e2e fixture and Playwright spec, both guides and both example stubs), then cross-checking each candidate against five independent sources: the workspace compiler settings (`tsconfig.json:1-30, 114-118`), the API guard report, the three sibling controls that implement the same `KbqFormFieldControl` contract (`input`, `textarea`, `datepicker`), every in-repo consumer found by grep (`filter-bar`, `time-range`, `form-field/e2e.ts`, three docs examples, four dev apps), and the installed date adapters. The Luxon rollover behind TP-BUG-01 was confirmed by executing `DateTime.set({ hour: 24 })` against the installed Luxon rather than reasoning about it; the `\W`-matches-Cyrillic claim in TP-A11Y-02 and the `12:30 pm → 24` arithmetic were confirmed the same way. Consumer evidence is what upgraded TP-BUG-03 and TP-LIFE-01 from code smells to confirmed defects — in both cases the affected code path already exists in the tree.

Refuted during verification:
- **"The missing `timepicker-tokens.scss` and `_timepicker-theme.scss` are a defect"** — refuted. Theming is delegated to `form-field` by an explicit two-sided contract: the host adds `class: 'kbq-input kbq-timepicker'` (`timepicker.directive.ts:128`) so the shared `.kbq-input` rules in `_form-field-theme.scss:22, 74` paint it, and that theme separately enumerates `.kbq-form-field-type-timepicker` by name for the focus/error states (`_form-field-theme.scss:110`). The only style the package legitimately owns is layout, and that is where the real finding is (TP-CSS-01).
- **"`[min]`/`[max]` should be split from calendar limits the way `datepicker` splits `[minDate]`/`[maxDate]`"** — refuted. The timepicker has no calendar surface, so `[min]`/`[max]` are validation inputs only and the split the datepicker deliberately maintains is trivially satisfied here; there is nothing to bridge. The genuine issue is the undocumented *instant* comparison semantics, filed separately as TP-API-02.
- **"Hints and errors are never associated with the control (`aria-describedby`)"** — refuted. `KbqFormField` now writes the attribute on the control's host element by default (`form-field.ts:540-544`, `kbqSetDescribedByIds` in `form-field-control.ts:86-98`), and the timepicker's host *is* that element, so the association works without the control implementing anything.
- **"`get ngControl(): any` breaks the form field's `ng-*` class forwarding"** — refuted as a runtime defect. `shouldForward` reads only `untouched`/`touched`/`pristine`/`dirty`/`valid`/`invalid`/`pending` (`form-field.ts:159-165, 474-476`), all of which the `AbstractControl` stored here provides, so the seven class bindings work by duck-typing. `ngControl.control` (`form-field.ts:553`) genuinely is `undefined` for a timepicker, but the only caller is the password-strength path, which a timepicker never reaches. The type lie itself remains, under TP-API-01.
- **"The `incorrectInput` subscription in the `kbqValidationTooltip` setter leaks"** — refuted. `output()` returns an `OutputEmitterRef` whose listeners are released through the owning directive's `DestroyRef`, so destruction cleans it up. The real hazards in that setter are re-binding within one lifetime and the untracked `setTimeout` at `:345`, both filed under TP-ARCH-01.
- **"`replaceNumbers` corrupts the value when the same digit run appears twice, because `String.replace` replaces the first occurrence"** — refuted. Clamping only ever shortens a run and the three runs are consumed left to right, so the first occurrence is the intended one in every input constructed to break it (`70:70`, `111:111`, `23:60:60`, `9:99`, `11:111`). Kept as a readability concern inside TP-STYLE-01 rather than filed as a bug.

Corrected on verification:
- **TP-BUG-03** was drafted as "an unparseable paste is written into the input" — a paste-path cosmetic defect. Reading `parseValidator` and `onInput` together showed the deeper failure: nothing calls `updateValueAndValidity()` on a failed parse from *any* path, so the published `kbqTimepickerParse` error is unreachable and the stale value is reported valid indefinitely. Scope widened from paste to every input path; severity held at P1 and it became the lead finding.
- **TP-BUG-01** was drafted as a P3 documentation nit ("12-hour paste is undocumented"). Executing the branch showed `hours += 12` produces hour 24, which Luxon rolls into the next day, so noon lands on the wrong hour *and* the wrong day and both bypass `min`/`max` by shifting the date term of `compareDateTime`. Promoted to P1; the documentation half moved to TP-DOC-01.
