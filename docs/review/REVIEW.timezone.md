## 1. Executive Summary

`timezone` is a two-component package: `KbqTimezoneSelect` (a 118-line subclass of `KbqSelect` with its own forked template) and `KbqTimezoneOption` (a 69-line subclass of `KbqOption` with a two-column offset/city layout), plus a tooltip directive, two pipes and 118 lines of exported utilities. The package **ships no timezone data at all** — `KbqTimezoneZone[]` is entirely consumer-supplied, and the only IANA-aware code in the repo (`kbqResolveTimezoneOffset`) is never used to produce what the component renders. That division of labour is defensible, but the two utilities the package *does* export to bridge consumer data into the component are both wrong.

- **The single most serious defect is `timezonesSortComparator`**: it returns `parseOffset(first.offset)` instead of the difference of the two offsets (`timezone.utils.ts:90-94`). It is not a valid comparator — `cmp(+5, +2)` and `cmp(+2, +5)` both return a positive number — and its country-name tiebreak is dead in both call paths, because `getZonesGroupedByCountry` overwrites `countryName` with the bucket label before sorting. Feeding it a realistic world-wide list produces `Los Angeles | New York | Moscow | Berlin | Tokyo | Mumbai | London | Sydney` where the offsets ask for `… | London | Berlin | Moscow | Mumbai | Tokyo | …` (TZ-BUG-01).
- **`getZonesGroupedByCountry` does not group by country** despite its JSDoc saying so. It reads `Intl.DateTimeFormat().resolvedOptions().timeZone` at call time (`timezone.utils.ts:21`) and produces at most two groups: the host machine's country, and one "Other" bucket holding every other zone with its `countryName` rewritten. The same input therefore renders differently on a Moscow laptop, on CI, and on an SSR server versus the browser that hydrates it (TZ-ARCH-01).
- **Offsets are frozen strings, so DST is never applied.** `KbqTimezoneZone.offset` is an undocumented `string` that the option renders verbatim; the zone `id` is used only as the form value. `parseOffset` passes `Date.now()` into `kbqResolveTimezoneOffset`, but that argument is dead for exactly the fixed-offset strings the model carries — the only date-aware path in the package never runs on its own data shape. A `Europe/Berlin` row authored as `01:00:00` says `UTC+01:00` all summer (TZ-BUG-03).
- **The forked select template has drifted from its origin.** `timezone-select.component.html:39-84` still binds the deprecated no-op `offsetY`, has lost the `viewportMargin` that `select.html:98` added to stop the panel overflowing the viewport edge, and has lost the `kbq-select-footer` / `kbq-select-matcher` projections — so a footer written against the documented "same capabilities as select" contract is not dropped but rendered *inside the option list* by the catch-all `<ng-content />` (TZ-TPL-01).
- **The package's only localized string is latched after its first application**, and every shipped example, the dev app and the e2e fixture hard-code Russian UI strings that appear unchanged on the English documentation site (TZ-I18N-01).

Genuine strengths: the select spec is real work — 37 cases covering panel width policies, keyboard navigation, forms integration, search thresholds and the option tooltip, including a deliberate "consumed as a bare standalone component" regression case with an explanatory comment. The tooltip directive uses `SharedResizeObserver` rather than per-instance window listeners, debounces and throttles both observers, guards every geometry read behind `Platform.isBrowser`, and tears down all three subscriptions with `super.ngOnDestroy()` reaching the base's `stopMonitoring`. The Playwright suite covers closed states, panel states and search in both themes, and `core/option/optgroup.html:4` explicitly whitelists `kbq-timezone-option`, so the composition with `kbq-optgroup` is intentional rather than accidental.

## 3. Prioritized Findings (deduplicated, verified)

### P0 — Release blockers

None.

### P1 — High

**TZ-BUG-01 · `timezonesSortComparator` is not a valid comparator, and its tiebreak is dead in both call paths** — `timezone.utils.ts:87-94`, `timezone.utils.ts:29-36`, `timezone.utils.ts:44-50`, `timezone.utils.spec.ts:56-65`.
The body is `first.offset !== second.offset ? parseOffset(first.offset) : first.countryName.localeCompare(second.countryName)`. The first branch returns the *absolute* offset of the first argument, never a difference, so the result depends only on which zone is passed first: `cmp(+05:00, +02:00)` returns `300` and `cmp(+02:00, +05:00)` returns `120` — both "first is greater". Sorting is therefore whatever the engine's sort algorithm happens to make of an inconsistent comparator. Running the real function over a realistic world-wide list yields `Los Angeles | New York | Moscow | Berlin | Tokyo | Mumbai | London | Sydney` where offset order asks for `Los Angeles | New York | London | Berlin | Moscow | Mumbai | Tokyo | Sydney`. Two further degradations compound it: any zone at `00:00:00` returns `0`, i.e. "equal to everything", even though the offsets differ; and `parseOffset` returns `NaN` for anything `kbqResolveTimezoneOffset` rejects (`timezone.utils.ts:10`, `?? NaN`), which V8 treats as `0`. The second branch is dead in *both* ways the comparator is reachable: `getZonesGroupedByCountry` rewrites every zone's `countryName` to the bucket label before sorting (`:29-36`), so inside the "Other" bucket it compares `'Other'` with `'Other'`, and inside a real country group every zone shares that country's name — in either case it returns `0` and the tie falls back to input order rather than to city name. The unit test locks the bug in: both assertions at `:57-59` only check the sign of the *first* argument's offset, so they pass for the wrong reason and would keep passing if the second argument were removed entirely.
**Fix:** return `parseOffset(first.offset) - parseOffset(second.offset)`, guard both sides against `NaN` (treat an unparsable offset as sorting last rather than as `0`), and change the tiebreak to `first.city.localeCompare(second.city)` — `countryName` cannot discriminate inside a group keyed by country. Replace the two vacuous specs with a mutation-proof pair: sort an *unsorted* multi-offset array and assert the resulting offset sequence is ascending, plus assert antisymmetry directly (`Math.sign(cmp(a, b)) === -Math.sign(cmp(b, a))` for a handful of pairs) — the current tests pass against the broken implementation, so anything weaker is worthless.

**TZ-ARCH-01 · `getZonesGroupedByCountry` does not group by country and silently depends on the host machine's time zone** — `timezone.utils.ts:13-65` (esp. `:21`, `:22-24`, `:29-36`, `:44-50`), `timezone.utils.spec.ts:67-83`.
The JSDoc says "Grouping timezones by countries". What the function does is pick one privileged country — `priorityCountry` if given, otherwise the country of whichever data row matches `Intl.DateTimeFormat().resolvedOptions().timeZone` (`:21-24`) — and put *everything else* into a single bucket labelled `otherCountriesLabel`, rewriting each zone's `countryName` to that label on the way in (`:29-36`). The result is at most two groups, never a per-country grouping. Three consequences, all verified: (1) the output depends on the machine, so the shipped overview example renders one group called `Другие страны` on a UTC host and one called `Russia` on a Moscow host, from byte-identical input; (2) under SSR the server's zone is the server's, not the user's, so the server-rendered group label and ordering differ from what the browser computes on hydration — a mismatch no `KBQ_WINDOW` guard catches, because the global here is `Intl`, not `window`; (3) the aggregate bucket's `countryCode` is taken from `zones[0]` (`:46`), i.e. an arbitrary member, which is why the package's own spec asserts the self-contradictory `{ countryCode: 'ru', countryName: 'Other' }` at `:71-79`. The subsequent priority lookup keys off that same `countryCode` (`:53-55`), so the field is both meaningless and load-bearing.
**Fix:** split the responsibility. Keep a genuine `getZonesGroupedByCountry(data)` that buckets by `countryCode` and sorts groups by `countryName`, and add an explicit, side-effect-free `promoteCountry(groups, countryCode)` for the priority behaviour. Take the host zone out of the function entirely — let the caller pass it (`priorityCountry`), exactly as the search example already does at `timezone-search-overview-example.ts:91-93`; if a convenience default is wanted, expose it as a separate `kbqResolveHostCountry(data)` helper so the impurity is visible at the call site. Drop the `countryName` rewrite and give `KbqTimezoneGroup.countryCode` `string | null` so the aggregate bucket can say "none". Guard with specs that pass an explicit `priorityCountry`, assert one group per country, and assert that two calls with different `process.env.TZ` produce identical output.

### P2 — Should fix

**TZ-BUG-02 · The option tooltip carries the *unfiltered* city list while the option renders the *filtered* one, and the show/hide decision is measured on the filtered box** — `timezone-option.directive.ts:45`, `:54-60`, `:83-91`, `timezone-option.component.html:19-28`, `timezone-option.component.ts:64-68`.
The tooltip content is `this.option.viewValue`, which concatenates `timezone.city` and the raw `timezone.cities` (`timezone-option.component.ts:65-67`) — the search filter is never applied to it. The visible list, by contrast, runs through `| citiesByFilter: highlightText()` (`timezone-option.component.html:22-25`). `checkTooltipDisabled` then counts the line boxes of the *filtered* span (`:86`) and disables the tooltip when there are three or fewer. During a search the two disagree in both directions: an option whose filtered list collapses to one line gets no tooltip at all, even though the tooltip is the only place the full list is reachable; and an option that still wraps opens a tooltip listing cities the search has just excluded — the user is shown the very rows they filtered out. The `ContentObserver` subscription (`:54-60`) re-reads `viewValue` whenever the filtered DOM mutates, so it faithfully re-installs the same unfiltered string on every keystroke.
**Fix:** decide which string the tooltip is for and make both sides agree. If the tooltip is "the full list" (the useful reading), keep `viewValue` as the content but base `checkTooltipDisabled` on whether the *unfiltered* list would overflow — or simply enable it whenever the filtered rendering is shorter than the full list. If it is "the rest of what is clipped", route `viewValue` through `filterCitiesBySearchString` with the same `highlightText()`. Cover with a spec that sets `highlightText` to a token matching one city, asserts the rendered `.kbq-timezone-option__cities` text, and asserts the tooltip content matches the intended contract.

**TZ-BUG-03 · Offsets are static strings that nothing ever recomputes, so a DST zone is mislabelled for half the year** — `timezone.models.ts:2-3`, `timezone.utils.ts:9-11`, `timezone-option.component.html:1-11`, `utc-offset.pipe.ts:8-10`, `core/datetime/timezone.ts:95-123`, `tools/public_api_guard/components/timezone.api.md:143`.
`KbqTimezoneZone.offset` is a bare `string` with no documented format or semantics (it is `// (undocumented)` in the API report), and the option renders it verbatim: `timezone.offset | utcOffset` → `offsetFormatterAsObject` → `offset()`, which only reformats the sign and drops the seconds field. The IANA `id` is used solely as the form value (`timezone-option.component.ts:57-60`). The package therefore has no way to produce a correct label for a zone that observes DST — a row authored as `{ id: 'Europe/Berlin', offset: '01:00:00' }` reads `UTC+01:00` in July. The one date-aware path in the package is inert: `parseOffset` passes `Date.now()` into `kbqResolveTimezoneOffset` (`timezone.utils.ts:10`), but `parseFixedOffset` short-circuits before the timestamp is ever consulted for a fixed-offset string (`core/datetime/timezone.ts:111-113`), which is exactly the shape `KbqTimezoneZone.offset` carries — and even if it did resolve, the result feeds sorting only, never display. The repo already owns the correct primitive: `kbqResolveTimezoneOffset('Europe/Berlin', Date.now())` returns the offset in force *now*, cached per zone with a bounded formatter map (`core/datetime/timezone.ts:71-93`). The defect is invisible in the shipped fixture because every row in `docs-examples/components/timezone/timezone-data.ts` is Russian, and Russia has not observed DST since 2014.
**Fix:** make `offset` optional in `KbqTimezoneZone` and derive it from `id` when absent — `offsetFormatter` (and the option template) should call `kbqResolveTimezoneOffset(zone.id, Date.now())` and fall back to the supplied string only for fixed-offset entries. Document the field's contract on the interface (a fixed offset that the consumer is responsible for keeping current, or omitted so the library resolves it). Recompute on `KbqDateTimezoneService.changes` if the app switches zones. Guard with a spec that fakes the clock to a January and a July instant for `Europe/Berlin` and asserts `UTC+01:00` and `UTC+02:00` respectively.

**TZ-TPL-01 · The forked select template has drifted from `select.html` on five bindings, and two projections now land in the option list** — `timezone-select.component.html:39-84` against `select/select.html:87-155`, `timezone.api.md:117`, `timezone.en.md:1`.
`KbqTimezoneSelect` extends `KbqSelect` but re-declares the whole template instead of reusing it, and the copy has fallen behind: (1) `[cdkConnectedOverlayOffsetY]="offsetY"` at `:45` binds a member that `select.component.ts:335-341` marks `@deprecated noop … Will be removed in 21.0.0` — the panel gap now comes from `--kbq-connected-overlay-gap`; (2) `[cdkConnectedOverlayViewportMargin]="viewportMargin"` is absent, although `select.component.ts:343-349` documents precisely why it exists ("CDK's fit check … runs before the `kbq-connected-overlay_below/_above` gap padding is applied"), so the timezone panel can overflow the viewport edge by the gap where the select cannot; (3) the panel has no `(click)="handleClick($event)"`, the handler that closes the select when a footer is clicked (`select.component.ts:1655`); (4) `.kbq-select__content` has no `[class.kbq-scrollbar]` (deprecated selector, so cosmetic only); (5) the `kbq-select-footer` and `kbq-select-matcher` projections are gone, and this is the one that bites — the API report's content selectors are `["kbq-timezone-select-trigger", "kbq-cleaner", "[kbqSelectSearch]", "[kbq-select-search-empty-result]", "*"]` (`timezone.api.md:117`), so a projected footer is not dropped, it falls into the trailing catch-all `<ng-content />` at `:81` and renders **inside the scrollable option list**. The footer is a documented select feature with its own example (`select.en.md:95-97`), and `timezone.en.md:1` promises "the same capabilities, except for multiple selection". `KbqSelect.footer` is a content query (`select.component.ts:392`), so it still resolves and still feeds the panel-height maths — the node is simply drawn in the wrong place.
**Fix:** stop forking. Either give `KbqSelect` an overridable panel-content template and have `KbqTimezoneSelect` supply only the timezone-specific class/tokens, or — as a smaller step — bring the copy back in sync: drop the `offsetY` binding, add `[cdkConnectedOverlayViewportMargin]="viewportMargin"` and `(click)="handleClick($event)"`, and add the `kbq-select-footer,[kbq-select-footer]` and `kbq-select-matcher,[kbq-select-matcher]` projections in the same positions as `select.html`. Add a Jest case that projects a `<kbq-select-footer>` into `kbq-timezone-select` and asserts it is *not* a descendant of `.kbq-select__content`, and a Playwright case with the panel opened against the bottom viewport edge. Then add a comment at the top of the template naming `select.html` as the source, so the next select change is mirrored.

**TZ-I18N-01 · The one localized string is applied once and then latched; everything else is hard-coded, in Russian, on the English site** — `timezone-select.component.ts:101-117`, `core/select/common.ts:88-93`, `timezone.utils.ts:16-18`, `docs-examples/components/timezone/timezone-search-overview-example.ts:48,53,98,116`, `timezone-overview-example.ts:48`, `timezone-trigger-overview-example.ts:56`, `e2e.ts:40,195,201`.
`KbqTimezoneLocaleConfiguration` has exactly one member, `searchPlaceholder` (`core/locales/types.ts:116-120`), and the constructor effect applies it only when the projected search has no placeholder yet (`timezone-select.component.ts:107-116`). Because `setPlaceholder` writes straight into the input's `placeholder` and `hasPlaceholder()` reads it back (`core/select/common.ts:88-93`), the effect's own write makes the guard true on every subsequent run — so when the locale changes at runtime, the effect re-runs, sees a placeholder (the one it wrote in the previous locale) and skips. The string is latched to whichever locale was active first, which contradicts the point of `kbqInjectLocaleConfiguration` and the token's own JSDoc ("the rest keep following the active locale", `:43-46`). Separately, nothing else in the package is localizable: `getZonesGroupedByCountry`'s `otherCountriesLabel` defaults to the hard-coded English `'Other'` (`timezone.utils.ts:18`) rather than reading the locale section, and country/city names come from consumer data. And the locale mechanism is never exercised by anything the team ships: all three docs examples, the dev app and the e2e fixture pass the Russian literals `'Другие страны'`, `'Город или часовой пояс'` and `'Ничего не найдено'` — the search example's `[placeholder]` at `:48` is precisely the consumer placeholder that suppresses the locale one — and those examples are embedded unchanged into the **English** guide (`timezone.en.md:5,26,32`), so an English reader sees a Russian group label, a Russian search placeholder and a Russian empty-result message.
**Fix:** track the applied string instead of probing the DOM — keep the locale value the effect last wrote in a field and only skip when the current placeholder differs from it (that preserves "a consumer placeholder wins" while still following locale changes). Add `otherCountriesLabel` to `KbqTimezoneLocaleConfiguration` and all five locale files, and default the utility to `kbqInjectLocaleConfiguration`'s value at the call site rather than to `'Other'`. Replace the Russian literals in `packages/docs-examples/components/timezone/**` and `e2e.ts` with English (the docs site renders the same example component in both locales, so English is the only neutral choice) and let the placeholder come from the locale layer so the mechanism is demonstrated rather than bypassed. Guard with a spec that switches locale with `KbqLocaleService.setLocale` and asserts the rendered placeholder changes.

**TZ-API-01 · `multiple` is inherited, unguarded, and silently renders a half-broken trigger** — `timezone-select.component.html:7`, `:20-22`, `select.component.ts:671-682`, `timezone.en.md:1`, `timezone.ru.md:1`.
Both guides state that timezone select supports everything the select does "except for multiple selection", but nothing enforces it. `multiple` is a public inherited `@Input` whose setter only throws when the selection model already exists (`select.component.ts:676-679`), so `<kbq-timezone-select [multiple]="true">` set before initialisation is accepted, compiles cleanly under `strictTemplates`, and puts the component into a state the forked template cannot render: `:7` applies `kbq-select__trigger_multiple`, `multiSelection` turns on for every option, but the template has no tag list — it falls through to `<span class="kbq-select__matcher-text">{{ triggerValue }}</span>` at `:21`, and `triggerValue` returns only `selectionModel.selected[0].viewValue`. The user selects five zones and the field shows one. The options render no pseudo-checkbox either, because `timezone-option.component.html` does not use `option.html`.
**Fix:** override the `multiple` setter in `KbqTimezoneSelect` to throw a named dev-mode error (mirroring `getKbqSelectDynamicMultipleError`) when a truthy value is assigned, and state in both guides that the input is rejected rather than merely unsupported. If multiple selection is wanted later, the template needs the `multiSelection` branch from `select.html:24-64` and the option needs the checkbox. Guard with a spec asserting the throw.

**TZ-TEST-01 · The utils spec encodes the comparator bug, and whole public surfaces are untested** — `timezone.utils.spec.ts:56-65`, `:67-83`, `timezone-option.component.spec.ts:1-42`, `timezone-select.component.spec.ts`, `e2e.playwright-spec.ts:17-30`.
The two comparator assertions only ever check the sign of the first argument's offset (`:58-59`), so they are satisfied by an implementation that ignores its second parameter entirely — which is exactly the implementation shipped (TZ-BUG-01). The single grouping test (`:68-82`) exercises the degenerate host-dependent path and asserts its self-contradictory output (`countryCode: 'ru'` on a group named `'Other'`) as if it were the contract, and `priorityCountry` — the parameter every real consumer passes — has no test at all. `timezone-option.component.spec.ts` is one case asserting `viewValue`; the option's actual surface (`highlightText`, `foldDiacritics`, the `citiesByFilter` pipe in the template, the two-column offset rendering) is untouched. Across the 37 cases in `timezone-select.component.spec.ts` there is no reference to `customTrigger`, `kbq-timezone-select-trigger`, `configuration` or `searchPlaceholder`, so the custom-trigger directive and the entire locale mechanism are unverified. The Playwright suite captures light and dark for the closed and panel-state fixtures but only `02-light.png` for the search fixture (`e2e.playwright-spec.ts:21-29`), and no screenshot exercises the option tooltip or a filtered list.
**Fix:** land the comparator and grouping specs described in TZ-BUG-01 / TZ-ARCH-01 first (they must fail against today's code). Add: a `priorityCountry` grouping case; an option case binding `highlightText` and asserting both the `<mark class="kbq-highlight-background">` output and the filtered `.kbq-timezone-option__cities` text; a custom-trigger case asserting `kbq-timezone-select-trigger` content replaces `triggerValue`; a locale case per TZ-I18N-01; and a dark screenshot for `E2eTimezoneWithSearch` plus a filtered-panel screenshot. Regenerate baselines only with `yarn run e2e:docker:update-snapshots`.

### P3 — Nice to have / hygiene

**TZ-PERF-01 · `checkTooltipDisabled` runs a full `detectChanges()` per option with no rendering consequence** — `timezone-option.directive.ts:83-91`, `:47`, `:49-60`.
The callback ends with `this.changeDetectorRef.detectChanges()` on every invocation — once synchronously inside `ngAfterViewInit`, then on every debounced resize entry and every throttled content mutation — and it runs unconditionally, whether or not `disabled` actually changed. Nothing in `timezone-option.component.html` reads `disabled`; tooltip visibility is driven imperatively by `KbqTooltipTrigger`, so the change-detection pass has no output. With a 26-row fixture this is invisible; with a full IANA list it is one synchronous CD run per option per resize frame, plus a nested CD pass during `ngAfterViewInit`.
**Fix:** compute the new value, return early when it equals `this.disabled`, and drop the `detectChanges()` call entirely (add `markForCheck()` only if a future template binding needs it). Verify with a spy asserting the callback is a no-op when the line count is unchanged.

**TZ-API-02 · Public API hygiene: an untyped export, two forgotten exports and an internal constant** — `tools/public_api_guard/components/timezone.api.md:60-61`, `:143`, `:147`, `:164`, `timezone.utils.ts:67`, `public-api.ts:1-6`.
`offset(value)` has no parameter type (`timezone.utils.ts:67`), and the report duly records `export function offset(value: any): string` — an `any` in the published surface, for a function whose only callers pass a string. `UtcOffsetPipe` and `CitiesByFilterPipe` are imported by the NgModule but absent from `public-api.ts`, producing two permanent `ae-forgotten-export` warnings in the guard report (`:60-61`); as a side effect the pipes are unusable by consumers even though the module imports them. `TOOLTIP_VISIBLE_ROWS_COUNT` (`:164`) is an implementation detail of the clamp. `offsetFormatterAsObject` publishes a one-key `{ [UTC: string]: string }` object whose only purpose is to be re-expanded by `keyvalue` in the template. And `KbqTimezoneZone.offset` is `// (undocumented)` (`:143`) despite being the field whose semantics TZ-BUG-03 turns on.
**Fix:** type `offset(value: string)`; either export the two pipes from `public-api.ts` (and from the NgModule's `exports`) or rename them with a leading underscore and mark them `@docs-private`; make `TOOLTIP_VISIBLE_ROWS_COUNT` non-exported or `@docs-private`; add JSDoc to every member of `KbqTimezoneZone` and `KbqTimezoneGroup`. Then `yarn run build:components && yarn run approve-api` — note that adding JSDoc alone changes the report by removing `(undocumented)` markers, so the `api` job will fail until re-approved.

**TZ-ARCH-02 · `KbqTimezoneOption` drops the `KBQ_TITLE_TEXT_REF` provider it inherits in name only, and its tooltip lives in a separate directive standalone consumers will miss** — `timezone-option.component.ts:28-33`, `core/option/option.ts:141-146`, `:169`, `timezone-option.directive.ts:13-19`, `:46`.
Angular copies `providers` to a subclass only when that subclass has no decorator of its own — a rule the sibling file states verbatim at `timezone-select.component.ts:83-84` and acts on. `KbqTimezoneOption` has its own decorator and re-declares only the `KbqOption` alias, so the `{ provide: KBQ_TITLE_TEXT_REF, useExisting: KbqOption }` entry from `core/option/option.ts:141-146` is lost; and because the timezone template has no `#kbqTitleText`, the inherited `@ViewChild('kbqTitleText') textElement` (`option.ts:169`) is permanently `undefined`. Nothing crashes today — `KbqTitleDirective` injects the token as `{ host: true, optional: true }` and falls back to the host element — but a `[kbq-title]` inside a timezone option measures the whole two-column row instead of a text span, and any future consumer reading `option.textElement` (as `select/select-option.directive.ts:29-31` does for plain options) would throw. Separately, the clamp and the tooltip both live in `KbqTimezoneOptionTooltip`, a *separate* directive that sets `-webkit-line-clamp` imperatively at `timezone-option.directive.ts:46`; a consumer who imports the exported standalone `KbqTimezoneOption` without also importing the directive gets neither, silently, and the guides never mention the pairing.
**Fix:** re-declare the `KBQ_TITLE_TEXT_REF` provider in `KbqTimezoneOption`'s `providers` pointing at itself, and add `#kbqTitleText` to the label span (or override `textElement`). Move `-webkit-line-clamp: 3` into `timezone-option.component.scss` next to the existing `-webkit-box` rules so the clamp survives without the directive, and either add `KbqTimezoneOptionTooltip` to `KbqTimezoneOption`'s own `hostDirectives` or document the required import pair in both guides.

**TZ-ARCH-03 · `KbqTimezoneModule` imports nine things it does not use and exports neither the pipes nor `KbqOptgroup`** — `timezone.module.ts:17-42`, `timezone-overview-example.ts:16`.
The module declares no template of its own; all four exported classes are standalone with their own `imports`. Yet it imports `OverlayModule`, `KbqOptionModule`, `KbqSelectModule`, `KbqIconModule`, `KbqTagsModule`, `KbqToolTipModule`, `KbqHighlightModule`, `KeyValuePipe`, `A11yModule` and both pipes, and exports none of them. The pipes are therefore unreachable for consumers (and produce the warnings in TZ-API-02), while `KbqOptgroup` — which every shipped example needs — is *not* exported, which is why each example additionally imports `KbqOptionModule` (`timezone-overview-example.ts:16`). `KbqFormFieldModule` is exported without being imported, which Angular allows but which makes the intent unclear.
**Fix:** reduce `imports` to the four standalone classes actually re-exported, add `KbqOptionModule` (or at least `KbqOptgroup`) to `exports` so the documented usage works from the module alone, and resolve the pipes per TZ-API-02.

**TZ-CSS-01 · The option theme, typography and token block are each emitted twice into the global stylesheet** — `timezone-option.component.scss:43-44`, `timezone-select.component.scss:12-13`, `timezone-option.component.ts:27`, `timezone-select.component.ts:60-65`.
Both components use `ViewEncapsulation.None`, and both include the same two mixins from `_timezone-option-theme.scss` (`kbq-timezone-option-theme()` and `kbq-timezone-option-typography()`) and the same `timezone-option-tokens.scss`. Every rule in those files is therefore emitted twice — identical, so there is no cascade hazard, but the payload is doubled and any future divergence between the two copies would be resolved by style-injection order, which is not something the source expresses. On top of that, `timezone-select.component.ts:60-61` pulls the whole of `../select/select.scss` and `../select/select-tokens.scss` across the package boundary by relative path, so an application using both `kbq-select` and `kbq-timezone-select` ships the select stylesheet twice.
**Fix:** include the theme/typography mixins and the token file from exactly one component (the option is the natural owner, since every rule is scoped under `.kbq-timezone-option` or `.kbq-timezone-select__panel`), and drop them from the other. For the select stylesheet, prefer a shared partial the two components both `@use` over a cross-package `styleUrls` path, or scope the timezone panel to the classes `getPanelClasses()` already emits.

**TZ-STYLE-01 · `filterCitiesBySearchString` drops the separator space on rejoin, and its offset guard matches far more than a UTC offset** — `timezone.utils.ts:96`, `:103-118`, `timezone.utils.spec.ts:95-99`.
The function splits `cities` on `','` and rejoins on `','` (`:114-117`), so the `', '` separator the data format uses survives only as a leading space on each retained element — the result can begin with a space, which the spec documents as expected behaviour at `:96-99` (`.toBe(' Kazan')`). In the default HTML rendering that leading space collapses and is invisible, but the function is public API and any consumer using it for a tooltip, an `aria-label` or a non-HTML surface gets the stray character. The guard regex `UTC_OFFSET_PATTERN` (`:96`) has every group optional, so it matches the empty string, a lone `-`, `—`, `−` or `+`, a lone backslash, and any bare one- or two-digit token — all of which are silently dropped from the filter rather than searched for. The leading `\\?` (an optional literal backslash) has no explanation anywhere in the file or its history.
**Fix:** split on `/\s*,\s*/` and rejoin on `', '`; make the regex require at least a digit or a sign (`/^[-—−+]?\d{1,2}(?::\d{1,2})?$/`) and delete the `\\?` prefix or comment why it exists. Update the spec's `' Kazan'` expectations to `'Kazan'` — they currently pin the defect.

**TZ-DOC-01 · The `examples.timezone.*.md` files are dead stubs, and the Russian guide's select link is not root-relative** — `examples.timezone.en.md:1-5`, `examples.timezone.ru.md:1-5`, `apps/docs/src/app/structure.ts:1054-1065`, `timezone.ru.md:9`.
Both `examples.timezone.*.md` still carry the "🚧 Documentation in progress 🚧" placeholder, but the navigation entry sets `hasExamples: false` (`structure.ts:1064`), so the Examples tab never renders and the two files are simply dead weight — worth deleting rather than filling, since the three examples are already embedded in the main guide (`timezone.en.md:5,26,32`). Separately, `timezone.ru.md:9` links to `[Select](ru/components/select)` without the leading slash, where the English guide correctly uses `/en/components/select` — a document-relative link resolves under the current route rather than at the site root. This one is repo-wide rather than timezone-specific (25 root-relative-less links across `*.ru.md` against 87 correct ones), so fix it here and sweep the rest separately.
**Fix:** delete both stub files (or set `hasExamples: true` and populate them with the three `<!-- example(…) -->` embeds, if the Examples tab is wanted). Change `timezone.ru.md:9` to `/ru/components/select` and note the repo-wide sweep as a follow-up in the docs review.

## 4. Recommended Remediation Phases

**Phase 1 — Fix the two exported utilities.**
IDs: TZ-BUG-01, TZ-ARCH-01, and the specs from TZ-TEST-01 that cover them. These are the package's real product — every consumer, every shipped example and the e2e fixture route their data through both functions, and both are wrong in ways no current test can detect. Land the corrected comparator and the split `groupByCountry` / `promoteCountry` API together with mutation-proof specs; `getZonesGroupedByCountry`'s signature change is breaking, so schedule with the next major and add an `ng-update` migration under `packages/schematics` (confirm with the maintainers before writing it).

**Phase 2 — Correctness the user can see.**
IDs: TZ-BUG-02, TZ-BUG-03, TZ-I18N-01. Make the tooltip and the rendered list agree, let the offset be derived from the IANA id so DST is right, and unlatch the locale placeholder while replacing the Russian literals in the shipped examples. All three are independent of Phase 1 and each is visible to an end user; TZ-BUG-03 needs the `KbqTimezoneZone.offset` JSDoc from TZ-API-02 to be written at the same time so the new contract is stated where consumers read it.

**Phase 3 — Reconverge with `select`.**
IDs: TZ-TPL-01, TZ-API-01. Bring the forked template back in line with `select.html` (or remove the fork), and reject `multiple` explicitly instead of half-rendering it. Do this after Phase 2 so the template edits and the locale edits do not collide in the same file, and finish with the Playwright viewport-edge case.

**Phase 4 — Structure, API surface and styles.**
IDs: TZ-PERF-01, TZ-API-02, TZ-ARCH-02, TZ-ARCH-03, TZ-CSS-01, TZ-STYLE-01. Tighten the published surface, restore the lost provider and clamp, de-duplicate the emitted CSS, and clean up the filter helper. Requires one `yarn run build:components` + `yarn run approve-api` cycle; the pipe-export and `TOOLTIP_VISIBLE_ROWS_COUNT` decisions are SemVer-visible, so batch them with Phase 1's breaking change.

**Phase 5 — Close the remaining test and docs gaps.**
IDs: TZ-TEST-01 (remainder), TZ-DOC-01. Add the option-level highlight/filter cases, the custom-trigger case, the dark search screenshot and the filtered-panel screenshot; delete or populate the dead example stubs and fix the Russian link.

## 5. Verification Strategy

General gates, run sequentially — never in parallel, and never as part of an unrelated agent's run:
- `npx jest packages/components/timezone`, plus the suites of what it extends and what extends nothing else: `packages/components/select`, `packages/components/core` (option, select-common, highlight, datetime).
- `yarn run eslint`, `yarn run stylelint`, `yarn run prettier` on touched files.
- `yarn run build:components`, then `yarn run check-api` (the guard reads `dist/*.d.ts`, so the build must come first and its `dist` mtime must actually advance); `approve-api` only in the phases where the surface changes on purpose.
- `yarn run e2e:docker` for anything visual; baselines regenerated only with `yarn run e2e:docker:update-snapshots` — the committed `__screenshots__` are Linux, compared at `threshold: 0`.
- Manual smoke in `yarn run dev:timezone`, which renders all three docs examples.

Per-phase assertions:
- **Phase 1:** sorting an *unsorted* multi-country list yields a strictly non-decreasing offset sequence, and `Math.sign(cmp(a, b)) === -Math.sign(cmp(b, a))` for every pair in a sample — a suite that stays green when the second argument is deleted from the comparator has proven nothing, so verify by mutation. Grouping: running the same input twice under two different `process.env.TZ` values produces byte-identical output, and a three-country input produces three groups.
- **Phase 2:** with a search token matching one city, the tooltip text and the rendered `.kbq-timezone-option__cities` describe the same set. With the clock faked to 2026-01-15 and 2026-07-15, a `Europe/Berlin` row renders `UTC+01:00` and `UTC+02:00`. Switching locale at runtime changes the rendered search placeholder; a consumer-supplied placeholder still survives the switch.
- **Phase 3:** a projected `<kbq-select-footer>` is not a descendant of `.kbq-select__content`, and clicking it closes the panel. A panel opened against the bottom viewport edge keeps `defaultOffsetY` of clearance in the Playwright screenshot. `[multiple]="true"` throws a named error.
- **Phase 4:** `check-api` diff contains only the intended type change, the pipe decision and the removed `(undocumented)` markers; the built CSS bundle contains `kbq-timezone-option__offset` exactly once per rule; a spy shows `detectChanges` is not called when the measured line count is unchanged; `[kbq-title]` inside a timezone option resolves `KBQ_TITLE_TEXT_REF` to the option itself.

## Appendix A — Review Methodology

Findings were gathered by reading every file in the package (`timezone-select.component.{ts,html,scss}`, `timezone-option.component.{ts,html,scss}`, `timezone-option.directive.ts`, `timezone.utils.ts`, `timezone.models.ts`, both pipes, the module, `public-api.ts`, the three tokens/theme SCSS files, all three specs, `e2e.ts`, `e2e.playwright-spec.ts`, both guides and both example stubs), then cross-checking each candidate against four independent sources: the code it extends (`select/select.component.ts` + `select.html`, `core/select/common.ts`, `core/option/option.ts` + `option.html`, `core/pop-up/pop-up-trigger.ts`, `tooltip/tooltip.component.ts`, `core/datetime/timezone.ts`, `core/highlight/highlight-base.ts`); the API guard report and `tools/api-extractor/config.json`; every consumer of the package in the repo (the three docs examples, the dev app, the e2e fixture — there are no in-library consumers, which is itself why consumer-workaround evidence is unavailable here); and git history (20 commits touching the package, notably DS-5091 for the tooltip rework, DS-3244 for the panel-width unification and DS-3732 for smart search). Two findings were confirmed by executing the real algorithms over the shipped data with `node -e` rather than by reading alone (TZ-BUG-01's ordering, TZ-ARCH-01's degenerate grouping). Design tokens were checked for resolvability against `@koobiq/design-tokens/web/new/`. Accessibility findings were deliberately *not* duplicated: the missing combobox/listbox/option semantics belong to `select` and `core/option` and are tracked as SEL-A11Y-01…03 in `REVIEW.select.md`.

Refuted during verification:
- **"The `(mouseenter)` host binding overrides the base's hover handler, so the tooltip never opens"** — refuted. `KbqPopUpTrigger.initListeners()` binds `mouseenter → show` with a raw `addEventListener` (`core/pop-up/pop-up-trigger.ts:516-543`) during `ngAfterViewInit`, i.e. *after* Angular has registered the directive's host listener. `handleElementEnter()` therefore updates `disabled` first and the base's `show()` then honours it. The override is the intended sequencing, not a lost call — the same pattern is used by `select/select-option.directive.ts:75-81`.
- **"`focusMonitor.monitor()` without a matching `stopMonitoring()` leaks one `_elementInfo` entry per option"** — refuted. `FocusMonitor.monitor()` dedups per element and returns the existing subject (`@angular/cdk` `focus-monitor.mjs:281-290`), and `super.ngOnDestroy()` at `timezone-option.directive.ts:72` reaches `KbqTooltipTrigger.ngOnDestroy`, which calls `stopMonitoring(this.elementRef.nativeElement)` (`tooltip.component.ts:570-574`). Both registrations resolve to the same element and are removed together.
- **"`.kbq-highlight-background` is styled nowhere, so search matches render with the browser's default yellow `<mark>`"** — refuted. `core/styles/_koobiq-theme.scss:20` includes `kbq-highlight-background-theme()` alongside `kbq-highlight-theme()`; the tokens it references resolve in both themes.
- **"`@for (utcItem of … | utcOffset | keyvalue; track utcItem)` re-creates the DOM every change-detection cycle"** — refuted. `KeyValuePipe` is impure but differ-backed, and `utcOffset` is a *pure* pipe, so as long as `timezone.offset` is unchanged the same object reference reaches the differ and the same `KeyValue` instances come back. The track identity is stable.
- **"Defaulting `KBQ_TIMEZONE_DEFAULT_CONFIGURATION` to `ruRULocaleData.timezone` is a locale defect"** — refuted as a timezone finding. This is the repo-wide convention: `app-switcher`, `filter-bar`, `navbar`, `notification-center`, `datepicker`, `timepicker`, `time-range`, `code-block`, `clamped-text` and `actions-panel` all do exactly the same. The real i18n defect (TZ-I18N-01) is elsewhere.
- **"The `with search` Playwright screenshot is captured mid-`@fadeInContent` and is therefore flaky"** — refuted. `playwright.config.ts:101` sets `reducedMotion: 'reduce'` on every browser context, and `toHaveScreenshot` retries until the frame is stable.
- **"The missing `[cdkConnectedOverlayPanelClass]` binding means the timezone pane never gets `kbq-select-overlay`"** — refuted. `KbqAbstractSelect.resetOverlay()` adds the class imperatively (`core/select/common.ts:299-303`), reached through the inherited `setOverlayPosition()`. Kept inside TZ-TPL-01 as the one drift item with no behavioural consequence, so the finding is not read as five equal problems.
- **"The `--kbq-timezone-option-*` tokens reference undefined CSS variables"** — refuted. All four referenced base tokens resolve: `--kbq-size-xxs` and `--kbq-size-3xs` in `@koobiq/design-tokens/web/new/css-tokens.css`, `--kbq-foreground-contrast` and `--kbq-foreground-contrast-secondary` in both `css-tokens-light.css` and `css-tokens-dark.css`.

Corrected on verification:
- **TZ-BUG-01** was drafted as "the timezone list renders in the wrong order". Verified against the shipped fixture: `timezone-data.ts` is already offset-ascending and short enough that V8's insertion sort never reorders it, so the shipped examples look correct and the defect is invisible in the dev app and in the screenshots. Severity kept at P1 because the function is public API consumed with arbitrary data, and it is the specific reason the bug survived a Jest suite.
- **TZ-BUG-03** was drafted as "offsets are computed for a fixed date, so DST is wrong". Verified: they are not computed at all. `parseOffset` does pass `Date.now()`, but `parseFixedOffset` short-circuits before the timestamp is read for the fixed-offset strings the model carries, and the resolved value feeds sorting only — never the rendered label. The finding was rewritten around the missing derivation rather than a stale date.
- **TZ-I18N-01** started as "the search placeholder is not localized". Verified: it *is* localized, once — the effect's own write to the input makes its `hasPlaceholder()` guard true, so it latches. The finding was widened to cover the hard-coded `'Other'` default and the Russian literals in the shipped examples, which is where the user-visible damage actually is.
