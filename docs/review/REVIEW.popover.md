## 1. Executive Summary

- **A well-styled, feature-rich popover whose trigger layer and shared base leak and mis-position under real-world conditions.** The component surface (header/content/footer templates, confirm variant, 20 placements, stick-to-window, overflow shadows) is genuinely rich and visually disciplined — but scroll, resize, input-updates-while-open, and destroy-while-open all expose defects in `KbqPopoverTrigger` and `core/pop-up`. Of 69 confirmed findings (0×P0, 9×P1, 30×P2, 30×P3), more than half of the correctness rows are `core/pop-up` debt inherited by the whole pop-up family (tooltip, app-switcher, notification-center).
- **Leaks and lifecycle carry two of the nine P1s.** Every popover trigger — in the *default* configuration — subscribes to the global `ScrollDispatcher.scrolled()` with no teardown, leaking its subscriber graph for app lifetime and pinning CDK's global scroll listener (POP-BUG-01; verbatim copy in app-switcher). And `stickToWindow` positioning is wiped by every CDK position re-apply: the first ancestor scroll, window resize, or input update while open snaps the popover off the stuck edge (POP-BUG-02).
- **Hover mode is broken end-to-end, and pure-standalone usage crashes.** A dead `this.leaveDelay ?? 500` (the base initializes `leaveDelay = 0`, so `0 ?? 500` is `0`) makes the effective hover leave-delay 0 ms: the panel closes before the pointer can cross the 8 px gap — the documented hover mode's interactive content is unreachable even for pointer users (WCAG 1.4.13) — while the auto-hide watchdog degenerates into an `interval(0)` burning CPU the whole time open, and the JSDoc's "default 500 ms" is false (POP-BUG-03). Separately, importing `KbqPopoverTrigger` standalone throws `NullInjectorError` because the scroll-strategy provider lives only in the NgModule — an 8-copy repo-wide pattern (POP-ARCH-01).
- **Accessibility contributes three P1s.** The icon-only close button has no accessible name — a hard AXE `button-name` (critical) failure in every documented `hasCloseButton` usage (POP-A11Y-01); the trigger exposes no `aria-expanded`/`aria-haspopup`/`aria-controls`, so the default click flow with string content is fully silent for screen-reader users (POP-A11Y-02). Zero ARIA on the whole chain is the core gap; the focus trap itself is real and ON by default (a prior claim to the contrary was refuted).
- **i18n: confirm defaults ship in Russian.** `KbqPopoverConfirmComponent` hardcodes «Вы уверены, что хотите продолжить?» / «Да» with zero locale-service integration, and the entire confirm / `hasCloseButton` / `closeOnScroll` / `leaveDelay` surface is undocumented — non-RU apps render Russian UI by default and screen readers speak it with the app's voice profile (POP-A11Y-03).
- **The test suite has a credibility problem.** The "non-button keyboard trigger" test silently reads the wrong fixture and duplicates an earlier test — and its intended fixture is itself a `<button>`, so the claimed coverage never existed (POP-TEST-01); the entire closing/visibility contract (outside click, backdrop, preventClose, closeOnScroll, delays, `visibleChange`) is untested (POP-TEST-02); worst, the suite's own `TestScheduler` provider black-holes the hover auto-hide interval — the test infrastructure actively masked shipped production bug POP-BUG-03 (POP-TEST-03).
- **The P2 tail is heavy and user-visible.** Destructive confirm actions can execute twice after an input change while open (POP-BUG-05); notification-center/app-switcher permanently poison shared `CdkScrollable`s, disabling `closeOnScroll` popovers for the app session (POP-BUG-04); destroy-while-open leaks an app-wide class that drops every future overlay's z-index (POP-BUG-10); the confirm popover has shipped with no content padding since the DS-2611 refactor (POP-TPL-01); and focus drops to `<body>` on every close path except Esc (POP-A11Y-05).
- **What's strong.** Zero XSS surface (no `innerHTML`/`bypassSecurityTrust` anywhere in popover or core/pop-up); a modern Angular baseline (all four classes standalone + OnPush, host-object bindings only, uniform `inject()`, native `@if`, safe signal adoption started); designed-in lifecycle hygiene where it exists (`KbqPopUp.ngOnDestroy` clears both timers and completes its subjects, trigger streams consistently `takeUntilDestroyed`, hover watchdog outside the zone); focus trap real and ON by default with dialog-style initial focus capture and Esc on both trigger and panel; `public-api.ts` exactly matches `popover.api.md` with the core 14 inputs consistently `kbqPopover*`-aliased; the tests that do exist are honest DOM-first tests (all 3 trigger modes + ENTER/SPACE/ESC, a tight TemplateRef+context test, offset tests protecting a subtle arrow-margin nudge, Playwright overflow tests with `expect.poll` in light+dark); styles are disciplined BEM with a reusable overflow-shadow wiring and an invisible arrow seam in both schemes; perf fundamentals in place (overlay/portal cached and reused, 20 ms scroll throttle, debounced content observation).

## 3. Prioritized Findings (deduplicated, verified)

### P0 — Release blockers

None found. Neither of the nine P1s crashes or loses data on a default core flow: the two discovered crash paths (hover-triggered confirm `TypeError` in POP-BUG-09; disposed-portal `Error` on the keydown path in POP-LIFE-01) sit behind opt-in configurations, the P1 leak degrades gradually rather than blocking, the a11y/i18n P1s block specific user groups but not the primary pointer flow, and hover mode itself is opt-in.

### P1 — High

**POP-BUG-01 · Global `scrolled()` subscription with no teardown — every trigger leaks for app lifetime** — `packages/components/popover/popover.component.ts:453-466` (sub :455, default gate :398).
`ngAfterContentInit` subscribes to the root-singleton `scrollDispatcher.scrolled()` with no `takeUntilDestroyed` — the only subscription in the file without teardown (the sibling three lines up at :447-450 has it) — and it runs in the *default* configuration (`closeOnScroll` defaults to `null` at :398, which is exactly the value that wires this path). Every trigger created and destroyed (a `@for` of rows, route navigations) leaves its full subscriber graph — `ElementRef` with detached DOM, host view — retained by the dispatcher's `_scrolled` Subject forever; CDK keeps its global document scroll listener alive as long as it has observers (`scrolling.mjs:284`), so the listener is pinned for app lifetime. Ghost callbacks keep running `classList.contains` and `getBoundingClientRect` on detached elements and can call `hide()` on destroyed triggers. Verifier repro: mount/unmount 100 triggers → 100 live subscriptions, permanently. A verbatim copy exists in `app-switcher.ts:524-536`.
**Fix:** add `.pipe(takeUntilDestroyed(this.destroyRef))`, matching :447-450; fix the app-switcher twin in the same PR series.

**POP-BUG-02 · `stickToWindow` styles wiped by every CDK position re-apply (shared)** — `packages/components/core/pop-up/pop-up.ts:176-216`; `popover.component.ts:98-110,490,498-514`.
`setStickPosition` writes manual pixel inset styles onto the overlay pane, but it is re-invoked *only* from the per-show `visibleChange` subscription. Verified against CDK internals: `RepositionScrollStrategy` (`overlay-module.mjs:266-284`) re-runs `apply()` on every throttled scroll, and `FlexibleConnectedPositionStrategy._setOverlayElementStyles`/`_getExactOverlayX/Y` (`:2044-2072`) reset all four inset styles and re-write connected coordinates; resize is worse (`_isInitialRender = true` → a full `_resetOverlayElementStyles`, `:1355-1364,1981-1990`). So the first ancestor scroll, window resize, or any input update while open (`updateData` → `updatePosition(true)` → `reapplyLastPosition`, :498-514) snaps a stuck popover off the window edge back to its connected position. `updateData` (:490) also re-copies `instance.arrow = this.arrow`, undoing the `arrow = false` that stickToWindow set (`pop-up.ts:186`) — a misplaced arrow reappears. Notification-center carries a compensating resubscribe (`notification-center.ts:472`); popover has nothing.
**Fix:** re-run `setStickPosition` after every strategy apply — subscribe `positionChanges`/ViewportRuler *after attach* in the core trigger (the NC pattern); NC keeps its compensating pattern until this lands, then removes it.

**POP-BUG-03 · Dead `0 ?? 500` — hover leaveDelay is effectively 0 ms: hover mode unusable, `interval(0)` watchdog, false JSDoc (shared mechanics)** — `popover.component.ts:312,423,426`; `pop-up-trigger.ts:166,378-388,518-524`.
The base trigger initializes `leaveDelay = 0` (`pop-up-trigger.ts:166`); the popover's `kbqTrigger` setter then does `this.leaveDelay = this.leaveDelay ?? 500;` (:312) — `0 ?? 500` evaluates to `0`, so the branch is dead, and the subclass's bare re-declaration (:426) emits no assignment either. Consequences, all verified: (1) on trigger mouseleave, hide is scheduled with `setTimeout(…, 0)` (:518-524) — the pointer cannot cross the 8 px trigger→panel gap within one macrotask (the gap hit-tests to the listener-less overlay pane), so the documented hover mode's interactive content is unreachable *even for pointer users*: the shipped `popover-hover` example's input and two buttons cannot be clicked — a WCAG 1.4.13 (hoverable) failure; (2) the auto-hide watchdog becomes `interval(0, scheduler)` (:378-388) ticking every ~0–4 ms outside Angular for the *entire* time the popover is open — pure CPU churn — and it independently hides on its first tick when neither side is hovered, so fixing the mouseleave path alone is insufficient; (3) the JSDoc "default 500 ms" (:423) is false at runtime. The spec's `TestScheduler` provider black-holed the interval, which is why the suite never caught this (see POP-TEST-03).
**Fix:** `|| 500` or a was-set flag; floor the watchdog interval off the resolved value; add a fakeAsync regression test — which requires the POP-TEST-03 fix first, since the provider swallows the interval.

**POP-A11Y-01 · Icon-only close button has no accessible name (AXE `button-name`, critical)** — `popover.component.html:74-80`; `button.component.ts:197-205`; `icon-registry.ts:287-288,312-313`.
The close button contains only an `<i kbq-icon>` glyph. The `kbq-button` host contributes only `aria-disabled`/`tabIndex` (:197-205), and the font-icon path of `kbq-icon` adds only CSS classes — `aria-hidden` is set only on registry-SVG icons (:287-288,312-313). The button therefore announces as a bare "button": a hard AXE `button-name` (critical) failure in every documented `hasCloseButton` usage (the header/content/width/close examples all ship it).
**Fix:** localized `aria-label` (i18n token + input) on the button, plus `aria-hidden="true"` on the icon.

**POP-A11Y-02 · Trigger exposes no `aria-expanded`/`aria-haspopup`/`aria-controls` — the default click flow is fully silent for screen readers** — `popover.component.ts:153-158` (host).
The trigger host binds only classes and event handlers; grep confirms zero `aria-*`/`role` across the whole chain, including the base hosts and CDK panes (the ConfigurableFocusTrap inserts only `aria-hidden` anchor divs). With string content, `focusFirstTabbableElement()` returns false, focus stays on the trigger, and the panel renders silently at the end of `<body>` — nothing is announced and nothing is discoverable. In the default `'click, keydown'` configuration the SR flow is fully silent (WCAG 4.1.2; note this is not an automated-AXE rule — the P1 rests on 4.1.2 in the default config).
**Fix:** host `attr.aria-expanded`/`attr.aria-haspopup="dialog"`/`attr.aria-controls` bindings gated on `hasClickTrigger`, wired to a generated panel id.

**POP-A11Y-03 · Confirm defaults hardcoded in Russian; no locale integration; confirm surface undocumented (shared: core/locales)** — `popover-confirm.component.ts:81,89-90` (tokens :18-19); `core/locales` (0 popover sections); `popover.en.md` (0 mentions).
`KbqPopoverConfirmComponent` defaults to «Вы уверены, что хотите продолжить?» / «Да» as field initializer and constructor fallback; the override tokens are `new InjectionToken<string>('')` with empty descriptions; `core/locales` has sections for select/datepicker/…/notificationCenter but none for popover; and the confirm trigger, `hasCloseButton`, `closeOnScroll`, and `leaveDelay` have zero mentions in `popover.en.md` or the docs examples. Non-RU applications ship Russian UI by default with no documented override path, and screen readers speak the Russian strings with the app's configured voice profile (WCAG 3.1.2).
**Fix:** register a popover section in the `KBQ_LOCALE_SERVICE` locale data (the tokens stay as overrides, with real descriptions); document the confirm API.

**POP-ARCH-01 · Pure-standalone import crashes: the NgModule is load-bearing for the scroll strategy (shared — 8 copies repo-wide)** — `popover.component.ts:132,165`; `popover.module.ts:34-35`.
`KBQ_POPOVER_SCROLL_STRATEGY` (:132) is created without a factory default, and the trigger field-injects it non-optionally at construction (`protected scrollStrategy = inject(KBQ_POPOVER_SCROLL_STRATEGY)`, :165); the only provider lives in `KbqPopoverModule` (:34-35). A consumer following the repo's own standalone-first mandate (`imports: [KbqPopoverTrigger]`) gets `NullInjectorError` at directive instantiation. All ~13 module-importing docs example files mask this; there are zero standalone usages in-repo, so the repo never trips over its own trap. Verified as an 8-copy repo-wide pattern: popover:132, tooltip:110, app-switcher:112, dropdown:41, datepicker:38, autocomplete:61, core/select:17, notification-center:69 (= NC-ARCH-01, pattern confirmed repo-wide).
**Fix:** give the token a factory default (`reposition({ scrollThrottle: 20 })`), keep the module provider as an override; open one repo-wide ticket for the other 7 copies.

**POP-TEST-01 · "Non-button keyboard trigger" test reads `#test7` — a silent duplicate; the intended fixture is a `<button>` anyway** — `popover.spec.ts:457` (template `#test8` :444; consumer :211-212).
The viewChild backing the "check the popover open by keyboard on elements other than button" test reads `'test7'` (:457), so the test at :211 runs against `#test7`'s button — a 100% duplicate of the test at :189, and any regression on `#test8` passes unnoticed. Worse: `#test8` (:444) is *itself* a `<button>`, so the claimed non-button coverage never existed even if the reference were fixed.
**Fix:** point the viewChild at `'test8'` **and** make `#test8` a non-button host (`div` with `tabindex="0"`).

**POP-TEST-02 · Closing/visibility semantics entirely untested** — `popover.spec.ts` (absent).
There are no tests for: outside-click close, backdrop click (+ `hasBackdrop`/`backdropClass`), `kbqPopoverPreventClose`, `closeOnScroll`, `hideIfNotInViewPort`/`hideIfScrolledOutOfView`, the `kbq-hide-nested-popup` path, `disabled`, `touchend`, or enter/leaveDelay timing — and `visibleChange` is never spied anywhere. "When it closes" is the component's regression-prone hot spot (the `delay(0)` + preventHide filter pipeline) and it has zero coverage.
**Fix:** a new "closing behavior" describe block with `visibleChange` spy sequences, landed alongside the Phase 1/2 bug fixes to lock semantics.

### P2 — Should fix

- **POP-BUG-04 · `kbqPopoverPreventHide` protocol poisons shared `CdkScrollable`s — closeOnScroll popovers stop closing for the app session (shared)** — `pop-up-trigger.ts:654-661` (gate :655-657); `notification-center.ts:470-476`; `app-switcher.ts:541-546`. `scrolled()` emits the long-lived `CdkScrollable` directive instance, not a per-dispatch event; NC/app-switcher write `kbqPopoverPreventHide`/`type` onto it and never clear, so the base hide-gate skips forever on that scrollable (= NC-BUG-02 popover side, still open). **Fix:** per-emission wrapper events or a WeakSet, or clear the flags after the delayed read (`radio.component.ts:530-531` is the safe per-Event variant); coordinate the NC + app-switcher migration in the same release.
- **POP-BUG-05 · `setupButtonEvents` re-subscribes `onConfirm` on every `updateData` — one click emits confirm/hide N×** — `popover-confirm.component.ts:93-110` (paths: show :364; setters :251/266/279/365/378 + :63/:78). Any input change while the confirm popover is open adds a trigger-scoped subscription: destructive confirm actions execute twice or more, and dormant subs accumulate on the trigger destroyRef across reopens (= BUG-36, still open). **Fix:** subscribe once per attach, scoped to `instanceDestroyRef` (the getter already exists: `popover.component.ts:404-407`).
- **POP-BUG-06 · Re-hover during leaveDelay cannot cancel the pending hide — popover closes under the cursor (shared)** — `pop-up-trigger.ts:346-348,518-524,393-402`; `pop-up.ts:72-74,100-116`. `trigger.show()` early-returns while an instance exists, making `KbqPopUp.show`'s `clearTimeout(hideTimeoutId)` unreachable; `hide()` also stacks timers (it clears `showTimeoutId`, not `hideTimeoutId`). Today it needs an explicit `kbqLeaveDelay`; it becomes default-visible once POP-BUG-03 restores the 500 ms default (= NC-LIFE-03, still open). **Fix:** `clearTimeout(hideTimeoutId)` at the top of `KbqPopUp.hide()`; on re-enter with a live instance, call `instance.show(delay)` instead of early-returning.
- **POP-BUG-07 · `hasBackdrop` toggled after first open → popover uncloseable by pointer** — `popover.component.ts:434-440,537-542`; `pop-up-trigger.ts:417-419`. The overlay config is consumed once (the overlay ref is cached), but the closing actions re-read the flag per show: a false→true reopen has no backdrop element yet closing actions become `backdropClick()/NEVER` — only Esc/touchend/programmatic close works; `backdropClass` changes after first open are ignored. **Fix:** dispose/recreate the overlay when config-affecting inputs change between opens.
- **POP-BUG-08 · Arrow-alignment offset uses tooltip geometry — the arrow misses small triggers by up to 13 px (shared)** — `constants.ts:70`; `pop-up-trigger.ts:51-90` (gBCR :568); `popover.scss:8-11,132`. `ARROW_BOTTOM_MARGIN_AND_HALF_HEIGHT = round(parseInt("12px")·√2) = 17` derives from the **deprecated** `TooltipSizeArrowSize` design token, but the popover arrow center sits 30 px from the panel corner (`$arrow-padding` 24 + `$arrow-size`/2) — on the 8 corner placements every trigger narrower than 34 px gets the arrow exactly 13 px past its center (the miss decays 13→0 up to 60 px; the constant is itself 2 px off even for tooltip). This is the concrete defect behind `@TODO DS-2514`. **Fix:** per-component arrow-offset parameter derived from the component's own SCSS geometry; move off the deprecated token (design-tokens coordination); fix tooltip's own 2 px miss and rewrite/close the DS-2514 TODO in the same PR.
- **POP-BUG-09 · Confirm template lacks `#popover` — offset/stickToWindow silently dead; hover-triggered confirm throws `TypeError`** — `popover-confirm.component.html:1-20` (the main `popover.component.html:2` has the ref); `popover.component.ts:93,98-113`; `pop-up.ts:173`. The inherited `@ViewChild('popover')` refreshes with 0 matches and clobbers the injected `elementRef`, so the `ngAfterViewInit` guard fails: `kbqPopoverOffset` and `kbqPopoverStickToWindow` no-op on `[kbqPopoverConfirm]` with no error, and a hover-triggered confirm throws `TypeError` in `addEventListenerForHide` (`nativeElement` of `undefined`). **Fix:** add `#popover` to the confirm template (or switch to a required signal query that fails loudly).
- **POP-BUG-10 · `cdk-overlay-container_dropdown` class add/remove asymmetry — app-wide z-index leak; collides with dropdown/select** — `popover.component.ts:442,468-482,566-580`; `core/styles/common/_overlay.scss:45-47`; dropdown-trigger:720-726; select:1963-1970. Destroy-while-open never removes the class, dropping all future overlays to z-index 999 app-wide; `classAddedToOverlayContainer` is never reset; and a preventClose-blocked `hide()` still strips the class — including one added by dropdown/select, which manage the *same* class with their own flags. **Fix:** remove the class in `ngOnDestroy`/detach; reset the flag; only remove when `super.hide()` actually proceeds; coordinate with dropdown/select.
- **POP-A11Y-04 · Panel has no `role="dialog"` / `aria-labelledby`** — `popover.component.html:1` (+confirm html:1); header text div html:26 has no id. Landing in the panel gives a screen-reader user no context (WCAG 1.3.1/4.1.2) (= prior A11Y-21, still open, upgraded Likely→Confirmed; + the role half of A11Y-33). **Fix:** `role="dialog"` + an id on the header + `aria-labelledby` (fallback `aria-label` input); confirm: dialog role + `aria-label` from `confirmText`.
- **POP-A11Y-05 · Focus dropped to `<body>` on every close path except Esc** — `popover.component.html:76`; `popover-confirm.component.ts:104-110`; `popover.component.ts:123-127` (the only restore path), :545, :548-564. Close button, confirm, `closeOnScroll`, `hideIfScrolledOutOfView`, and outside/backdrop click all detach with the focused element removed; the focus trap guarantees focus was inside, which makes it worse (WCAG 2.4.3). **Fix:** centralize in hide/detach — if `overlayElement.contains(document.activeElement)`, restore via `FocusMonitor.focusVia` (not native `.focus()`, which skips the kbq keyboard focus ring).
- **POP-A11Y-06 · Hover-triggered popover steals keyboard focus on open** — `popover.component.ts:112,496`; `popover-hover-example.ts:15-23`. `focusFirstTabbableElement()` runs unconditionally per attach regardless of trigger; the auto-hide watchdog checks hover only, so the subsequent detach lands keyboard focus on `<body>` (WCAG 2.4.3) — a pointer graze relocates keyboard focus. **Fix:** gate initial focus capture on click/keydown/programmatic triggers.
- **POP-A11Y-07 · `kbqTrigger="hover"` is keyboard-inaccessible and not Esc-dismissible without focus (shared)** — `pop-up-trigger.ts:493-503,331-335`; panel Esc is a host binding at `popover.component.ts:77`. focus/blur listeners bind only when the trigger string includes `'focus'`, and both Esc handlers require focus on the trigger or inside the panel (WCAG 2.1.1; 1.4.13-dismissible — the 1.4.13-hoverable half lives in POP-BUG-03). **Fix:** treat hover as hover+focus (the tooltip convention); add a document-level Esc handler while open.
- **POP-A11Y-08 · Scrollable content region not keyboard-focusable** — `popover.scss:44-51,53-59`; `popover-tokens.scss:6` (max-height 480 px). A hard AXE `scrollable-region-focusable` failure whenever content exceeds 480 px (WCAG 2.1.1). **Fix:** conditional `tabindex="0"` (+ `role="region"`/`aria-label`) when overflowing — the overflow state is already tracked (`popover.component.html:32-38`).
- **POP-LIFE-01 · Untracked keydown `setTimeout(() => this.show())` + disposed-overlay reuse → uncaught `Error` (shared)** — `pop-up-trigger.ts:505-511,416-419,276-282`. Live in the *default* `'click, keydown'` trigger: an Enter/Space that destroys the trigger in the same tick leaves an orphan timer; `createOverlay()` then returns the disposed ref (never nulled) and attach throws `Error('This PortalOutlet has already been disposed')` (= NC-LIFE-04, still open, elevated to P2 for popover because the default trigger includes keydown). **Fix:** track/clear the timer in `ngOnDestroy`; null `overlayRef` after dispose.

### Corrected on verification

No finding was refuted outright; eight claims were corrected during adversarial verification:

1. **A11Y-33 "focus trap off by default" — refuted.** `updateData` → `updateTrapFocus(trigger !== 'focus')` overwrites the `false` initializer on every show, so the trap is effectively ON for the default `'click, keydown'` trigger; `EmptyFocusTrapStrategy` no-ops only the inert focus-yank — CDK's Tab-wrap anchors stay enabled.
2. **The a11y agent's strength claim "WCAG 1.4.13 hoverable satisfied" — reversed.** With the effective leaveDelay of 0, the panel closes before the pointer crosses the 8 px gap — 1.4.13-hoverable is *violated* (folded into POP-BUG-03).
3. **POP-BUG-05's premise "default leaveDelay 500 ms" — corrected.** The runtime default is 0 (dead `0 ?? 500`); the re-hover bug currently needs an explicit `kbqLeaveDelay` and becomes default-visible once POP-BUG-03 is fixed.
4. **POP-TEST-07's claim ":531 subscribeOnClosingActions re-subscribes → leak" — corrected.** It self-unsubscribes its predecessor (:649); not a leak but an untested hot path — the real accumulation is the per-show `afterHidden`/`visibleChange` subs.
5. **POP-TPL-03's claim "deprecated token removal breaks parseInt silently" — corrected.** Removal is a loud build error (named import); the silent failure mode is the token value ceasing to be numeric (`parseInt` → `NaN` silently disables the offset corrections).
6. **POP-API-05's claim "`EventEmitter<any>` violates the base contract" — corrected.** It structurally *satisfies* `EventEmitter<string>`; it weakens the contract to `any` (P2→P3).
7. **POP-BUG-09's silent-offset impact — narrowed and extended.** A static 8 px SCSS margin covers the default look, so only non-default `kbqPopoverOffset`/`stickToWindow` are silently dead — but verification found a *new* impact: a hover-triggered confirm throws `TypeError` in `addEventListenerForHide` (now part of POP-BUG-09).
8. **POP-ARCH-02's "inert no-op" mechanism — corrected.** The real mechanism is the singleton `FocusTrapManager` stack (only the top trap active — a Koobiq popover over a CDK dialog disables the dialog's Tab-wrap) plus a cross-module interaction with KbqModal/Sidepanel providing the factory *without* the inert override, giving standalone consumers the focus-yank strategy; P1→P2.
