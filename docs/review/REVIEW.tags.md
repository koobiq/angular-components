# Koobiq `tags` Component — Code Review & Improvement Plan

> Scope: `packages/components/tags` (all four docs surfaces — Tag, Tag list, Tag input, Tag autocomplete: components, directives, tokens, theme, SCSS, 3 Jest specs, e2e fixture + Playwright spec, 4 user guides ×2 locales, API guard report, in-repo consumers) · Commit `b665e503` · 2026-08-28
> Generated by a multi-dimension review (architecture, RxJS/lifecycle, correctness, accessibility, performance, public API/types, styles, tests, docs) with manual verification of every finding against the source, the in-repo consumers (`select`, `tree-select`, `form-field`), `apps/docs/src/app/structure.ts`, `packages/docs-examples`, `playwright.config.ts` and git history. 19 findings confirmed (P0×1, P1×4, P2×7, P3×7); 6 candidate findings refuted during verification (see Appendix A). This document is a review + roadmap; no source is modified by it.

---

## 1. Executive Summary

`tags` is the largest package in the library — 7,750 source lines across 4 TypeScript files (`tag.component.ts` 788, `tag-list.component.ts` 999, `tag-input.ts` 434, `tag-text-control.ts` 20), 3 Jest specs totalling 225 cases, and four separate docs entries (`structure.ts:970-1017`). It is also load-bearing: `kbq-select` and `kbq-tree-select` render one `<kbq-tag>` per selected option in their triggers (`select/select.html:32-45`, `tree-select/tree-select.html:32-45`), so every defect here is a defect in the two most-used form controls in the library.

- **The release blocker is accessibility.** `kbq-tag-list` is a roving-focus, multi-select, destructive composite widget with **zero ARIA semantics**: a repo-wide grep for `aria`/`role` across every non-spec source file in the package returns nothing. No `role="listbox"`/`role="option"`, no `aria-selected`, no `aria-multiselectable`, no accessible name. Selection is signalled by background colour alone (`_tag-theme.scss:36-42`), and `Delete` on a focused tag removes **every selected tag** (`tag.component.ts:597-609`) — a destructive action whose precondition a screen-reader user cannot perceive. This is the same class of gap already filed as P0 in `REVIEW.select.md` and `REVIEW.form-field.md` (TAG-A11Y-01, TAG-A11Y-02, TAG-A11Y-03, TAG-A11Y-04).
- **A state flag leaks across the programmatic/user boundary.** `notifyPendingTagChange()` is called *before* `tagEnd` is emitted (`tag-input.ts:333`), and `tagEnd` fires on every blur of the input — including an empty one. If the consumer's handler declines to add a tag (every shipped example guards with `if (value)`), `pendingUIChange` stays `true` forever, and the *next* programmatic tag change is misreported as a user edit: `(change)`, `(valueChange)` and the `ControlValueAccessor`'s `onChange` all fire, marking a pristine form dirty (TAG-BUG-01).
- **Selection changes silently.** `unselectAll()` deselects every tag with `emitEvent` defaulted to `false` (`tag-list.component.ts:842` → `tag.component.ts:687`), and it runs on every focus of the tag input (`tag-input.ts:398`) and every focus loss of the list (`tag-list.component.ts:950`). Consumers tracking selection through the documented `(selectionChange)` output silently desynchronise (TAG-BUG-02).
- **The paste path is a parallel, unguarded implementation of the typing path.** `onPaste()` emits `tagEnd` directly instead of going through `emitTagEnd()`, so it skips the `ngControl.invalid` gate the typing path applies; its empty-clipboard guard `(data && data.length === 0)` is unreachable, so an empty paste emits a spurious tag; and `distinct` de-duplicates against existing tags but not within the pasted batch (TAG-BUG-03).
- **14 of 225 Jest cases are disabled**, including the entire `error messages` block (`tag-list.component.spec.ts:1062`), which asserts an `aria-invalid` attribute the component never sets — the skip is hiding a real gap rather than a flaky test. The `dropped` output and all three `ControlValueAccessor` methods have zero coverage (TAG-TEST-01).

Genuine strengths, and there are real ones: the range-selection model added in DS-4264 is the best-tested part of the package — 16 dedicated cases covering pointer/keyboard interop, RTL, shrink-deselection, disabled skipping and anchor invalidation on `tags.changes` (`tag-list.component.spec.ts:1228-1520`), and the implementation correctly invalidates the anchor when either endpoint leaves the list (`tag-list.component.ts:498-504`). The `KbqTagSeparator` contract added in DS-4712 is a genuinely well-designed API — `appliesTo: ['input' | 'paste']` cleanly separates keystroke separators from paste-only regexes, it is documented with a working snippet in both locales (`tag-input.en.md:66-89`), and it is the only part of the package with real end-to-end Playwright coverage including clipboard round-trips (`e2e.playwright-spec.ts:70-121`). Teardown is mostly disciplined (`takeUntilDestroyed` on the drop-list, drag and directionality streams; a dedicated `tagsSubscriptions$` gate for the per-tag streams), the `pendingUIChange`/`Promise.resolve()` deferral genuinely does avoid `ExpressionChangedAfterItHasBeenChecked`, and the DS-5236 direct-DOM `tabIndex` write is correctly commented with the `eventCoalescing` reason it exists.

## 3. Prioritized Findings (deduplicated, verified)

### P0 — Release blockers

**TAG-A11Y-01 · The tag list is a destructive multi-select composite with no ARIA semantics at all** — `tag-list.component.ts:81-94` (host block), `tag.component.ts:219-236` (host block), `_tag-theme.scss:36-42`, `tag.component.ts:597-609`.
A grep for `aria` or `role=` across every non-spec `.ts`/`.html`/`.scss` file in `packages/components/tags` returns **zero matches**. `<kbq-tag-list>` carries `class`, five state classes, `[attr.tabindex]`, `[id]` and three event bindings — and nothing else. `<kbq-tag>` carries `[attr.tabindex]`, `[attr.disabled]`, nine state classes and three event bindings — and nothing else. So the widget presents to assistive technology as an unlabelled `div` containing focusable unlabelled `div`s.

The consequences compound rather than merely add up. (1) The list runs a `FocusKeyManager` roving pattern (`tag-list.component.ts:468-471`) with every tag at `tabindex="-1"` (`tag.component.ts:395-400` returns `_tabindex = -1` for any tag inside a list), which is the correct *mechanics* for `role="listbox"`/`role="option"` — but without the roles a screen reader announces no position, no set size and no "listbox" context, so the user has no way to know arrow keys do anything. (2) Selection state exists only as `.kbq-selected` and is rendered only as a background/text colour swap (`_tag-theme.scss:36-42`); there is no `aria-selected`, which is both WCAG 4.1.2 (Name, Role, Value) and WCAG 1.4.1 (Use of Color) at AA. (3) That invisible state gates a **destructive** action: `Delete`/`Backspace` on a focused tag removes *all* selected tags when any are selected, and only the focused one otherwise (`tag.component.ts:600-604`). A screen-reader user cannot perceive how many tags a keypress is about to destroy. (4) `Ctrl+A` selects everything (`tag-list.component.ts:677, 699-704, 824-834`) with no announcement, so the blast radius can change without any perceivable event. (5) The list has no `aria-label`/`aria-labelledby` of its own; inside a `<kbq-form-field>` the `<kbq-label>` is linked to the *input*, not the list (`tag-list.component.ts:223-225` returns the input's id from `KbqFormFieldControl.id`), so a standalone Tag list — the whole `tag-list` docs entry — has no accessible name whatsoever.

AGENTS.md states accessibility as a mandate ("MUST pass all AXE checks", WCAG AA). To be precise about which claim is which: axe-core does **not** flag a custom element that simply carries no role, so this is a WCAG judgement, not an automated AXE failure — which is exactly why it has survived. It is graded P0 for consistency with the two published sibling reviews that filed the identical gap at the same severity (`REVIEW.select.md:11, 26`; `REVIEW.form-field.md:11, 24`) and because the destructive-action-with-invisible-state combination has no consumer-side workaround for the `kbq-select` trigger, where the tags are rendered by the library, not the application.
**Fix:** on `KbqTagList`'s host add `role: 'listbox'`, `'[attr.aria-multiselectable]': 'selectable() ? "true" : null'`, `'[attr.aria-disabled]': 'disabled || null'`, and an `ariaLabel`/`ariaLabelledby` input pair defaulting to the form-field label id when one is present. On `KbqTag`'s host add `'[attr.role]': 'tagList ? "option" : null'`, `'[attr.aria-selected]': 'tagList && selectable ? selected : null'`, `'[attr.aria-disabled]': 'disabled || null'`. Route the key manager's active item through `aria-activedescendant` **or** keep the current real-focus roving (both are valid for `listbox`; real focus is simpler here and already works). Guard with Jest cases asserting the attributes in each branch (list vs standalone, selectable vs not) and, once jest-axe is adopted repo-wide, `expect(await axe(fixture.nativeElement)).toHaveNoViolations()` on a selectable+removable list. Re-run the `select` and `tree-select` suites, which render `kbq-tag` in their triggers.

### P1 — High

**TAG-BUG-01 · `pendingUIChange` survives a `tagEnd` the consumer declined, so the next programmatic change is reported as a user edit** — `tag-input.ts:329-336`, `tag-list.component.ts:555-558, 514-521, 855-863, 906-908`.
`KbqTagList` distinguishes user-initiated tag changes from programmatic ones with a single boolean. `notifyPendingTagChange()` sets it (`tag-list.component.ts:556`), and the `tags.changes` handler consumes it: `if (currentTags && this.pendingUIChange) { this.pendingUIChange = false; this.propagateTagsChanges(); }` (`:517-520`). The flag is only ever cleared inside that branch — so if no `tags.changes` emission follows, it stays set indefinitely.

It is set on paths that routinely produce no tag change. `KbqTagInput.emitTagEnd()` calls `notifyPendingTagChange()` *before* emitting (`tag-input.ts:333`), and `blur()` calls `emitTagEnd()` whenever `addOnBlur` is true — which is the default (`tag-input.ts:221`) — with no check that the input is non-empty. So merely focusing and leaving an empty tag input emits `tagEnd` with `value: ''` and arms the flag; every shipped example then discards it (`if (value)`, e.g. `tag-input-with-form-control-validators-example.ts:83`), so no tag is added and no `tags.changes` fires. The same happens through `tagBeforeRemoveChanges` (`tag-list.component.ts:906-908`), which arms the flag on `tag.removed` even if the consumer's `(removed)` handler decides not to remove anything.

The next time tags change for *any* reason — a server response, a `writeValue` from the form, an `@if` toggling a tag in — `propagateTagsChanges()` runs and calls `this.change.emit(...)`, `this.valueChange.emit(...)` and `this.onChange(valueToEmit)` (`:859-861`). Because `onChange` is the `ControlValueAccessor` callback, Angular's view-to-model pipeline runs `markAsDirty()` on the control: a form the user never touched becomes dirty, unsaved-changes guards trip, and `(change)` fires for an edit that did not happen.
**Fix:** make the flag correlate with an actual emission rather than an intention. Either (a) move `notifyPendingTagChange()` out of `emitTagEnd()` and have the *list* arm it when it observes a `tags.changes` within the same task as a `tagEnd`, or (b) keep the call but add an early return in `emitTagEnd()` when `this.empty`, and clear the flag on a microtask if `tags.changes` did not fire (`Promise.resolve().then(() => this.pendingUIChange = false)` scheduled alongside the arm). Option (b) is the smaller change and also fixes the spurious empty-value `tagEnd` on blur. Guard with a spec that focuses and blurs an empty tag input, then pushes a tag programmatically, and asserts `(change)` did **not** emit and `formControl.pristine` is still `true`.

**TAG-A11Y-02 · `kbqTagRemove` is a click-only, unnamed, `tabindex="-1"` control** — `tag.component.ts:751-788`; consumers `select/select.html:38-44`, `tree-select/tree-select.html:38-44`.
The directive's host block is `class: 'kbq-tag-remove kbq-tag-trailing-icon'`, `'[attr.tabindex]': '-1'`, `'(click)': 'handleClick($event)'`, `'(focus)': 'focus($event)'` (`:753-758`). There is no `role="button"`, no `aria-label`, and no `keydown` listener — so the control is not in the tab order, and pressing Enter or Space on it (were it reachable) does nothing. It is always applied to a non-interactive element in practice: every docs example and both select triggers put it on an `<i>`.

Inside a `kbq-tag-list` there is a keyboard fallback — the tag itself handles `Delete`/`Backspace` (`tag.component.ts:597-609`) — but outside one there is none. A standalone `<kbq-tag removable>` that is not `selectable` resolves `tabindex` to `-1` (`tag.component.ts:395-400`: the `return 0` branch requires `this.selectable`), so neither the tag nor its remove icon can be reached by keyboard at all. The `kbq-select`/`kbq-tree-select` triggers are exactly this shape — `[selectable]="false"` on every trigger tag (`select.html:35`) — which is why `REVIEW.select.md:57` already files "in multiple mode a selected value can only be removed by mouse" as a select-side P1. This finding is that P1's root cause, and fixing it here fixes it in both consumers at once. The `(focus)` handler that only calls `event.stopPropagation()` (`:765-767`) is also dead weight on an element that can never receive focus.
**Fix:** add to `KbqTagRemove`'s host block `role: 'button'`, `'[attr.tabindex]': 'parentTag.disabled ? null : 0'`, `'[attr.aria-label]': 'ariaLabel()'` sourced from `kbqInjectA11yLocaleConfiguration()` (add a `tag.remove` entry to `KbqA11yLocaleConfiguration` in `core/locales/types.ts` and `ru-RU`/`en-US` data, following `form-field/cleaner.ts`), and `'(keydown.enter)'`/`'(keydown.space)'` mapped to `handleClick` with `preventDefault`. Separately, make a standalone `removable` tag focusable by extending the `tabindex` branch at `tag.component.ts:397` to `(this.selectable || this.removable)`. Guard with a Jest case that keys Enter on the remove icon and asserts `(removed)` emitted, plus a case asserting the localized `aria-label`; re-run `select.component.spec.ts` and `tree-select.component.spec.ts`.

**TAG-BUG-02 · `unselectAll()` clears the selection without emitting `selectionChange`** — `tag-list.component.ts:841-844`, `tag.component.ts:686-702`; callers `tag-input.ts:396-400`, `tag-list.component.ts:948-952`.
`unselectAll()` is `this.tags.forEach((tag) => tag.setSelectedState(false))`. `setSelectedState` destructures its options with `const { isUserInput = false, emitEvent = false } = options` (`tag.component.ts:687`), so passing no options means **no event**. Every other selection mutation in the package does the opposite: `selectViaInteraction()` passes `{ isUserInput: true, emitEvent: true }` (`:525`), and both branches of `extendSelectionTo()` pass `emitEvent: true` (`tag-list.component.ts:961, 989`).

`unselectAll()` is not a rare path. It runs on **every focus of the tag input** (`tag-input.ts:398`) and on **every focus loss of the list** (`tag-list.component.ts:950`, from the `FocusMonitor` subscription). So the ordinary sequence "Ctrl+click three tags, then click into the input to type a fourth" silently drops the entire selection. Since `KbqTagList` exposes no aggregate selection output — `tagSelectionChanges` is a `@docs-private` getter (`:139-141`) and see TAG-API-02 for why subscribing to it is unsafe — the per-tag `(selectionChange)` output is the documented integration point ("Programmatic selection through the component API", `tag-list.en.md:31`). A consumer mirroring selection into its own state therefore keeps showing three selected tags that are no longer selected, and any action keyed off that mirror (a bulk operation, an enabled/disabled button) acts on a stale set.
**Fix:** give `unselectAll()` an options parameter defaulting to `{ emitEvent: true }` and pass it through to `setSelectedState`, keeping a `{ emitEvent: false }` escape hatch for the internal focus-loss path if a silent reset is genuinely wanted there — but the input-focus path (`tag-input.ts:398`) is a user action and must emit. Add `emitEvent: true` at both call sites, or better, add an aggregate `selectionChange` output on `KbqTagList` that emits the current `selected` array on every transition, which is what consumers actually want. Guard with a spec that selects two tags, focuses the input, and asserts two `selectionChange` events with `selected: false`.

**TAG-BUG-03 · The paste path bypasses validation, emits on an empty clipboard, and de-duplicates incompletely** — `tag-input.ts:355-393`, compared with `:329-336`.
`onPaste()` is a second, independent implementation of "turn text into tags" and it diverges from `emitTagEnd()` on four points.

*Validation.* `emitTagEnd()` gates emission on `if (!this.hasControl() || (this.hasControl() && !this.ngControl.invalid))` (`:330`). `onPaste()` never calls it — it emits `this.tagEnd.emit({ input, value: item })` directly in a loop (`:389`). So an application that puts a validator on the tag input (the pattern `tag-input.en.md` and `examples.tag-input.en.md:9-16` both demonstrate) has that validator honoured when the user types and silently skipped when the user pastes.

*Empty clipboard.* The guard is `if ((data && data.length === 0) || !this.addOnPaste()) return;` (`:362`). The first disjunct is unreachable: if `data` is truthy its `length` cannot be `0`. So pasting an empty string falls through, `getPasteSeparatorPatterns('')` returns `[]` (every `''.search(...)` is `-1`), `dividedString` becomes `['']`, and the method arms `pendingUIChange` (`:386`, see TAG-BUG-01) and emits a `tagEnd` with `value: ''`. The intent was plainly `data.length === 0`.

*Dead branch.* `if (items.length === 0) { items.push(data); }` (`:375-377`) can never run — `String.prototype.split` always returns at least one element, so `dividedString` and therefore `items` always have length ≥ 1.

*Incomplete `distinct`.* When `distinct()` is set, `items` is filtered against the tags that already exist (`:380-382`) but never against itself, so pasting `a,a,b` with `distinct` produces two `a` tags. The keydown path cannot hit this because it only ever considers one value at a time (`:331`).
**Fix:** collapse the two paths. Extract a private `emitValue(value: string): boolean` holding the validation gate, the `distinct` check against a running set, and the empty-value check; have `emitTagEnd()` call it once and `onPaste()` call it per item, accumulating accepted values into the set so intra-batch duplicates are caught. Correct the guard to `if (!data.length || !this.addOnPaste()) return;` and delete `:375-377`. Guard with specs for: paste while the bound control is invalid (no `tagEnd`), paste of an empty string (no `tagEnd`), and `distinct` paste of `a,a,b` (two tags). The existing 10 `distinct` cases in `tag-input.spec.ts` give the fixture to extend.

### P2 — Should fix

**TAG-A11Y-03 · `aria-describedby` lands on the non-focusable `<kbq-tag-list>`, and `aria-invalid` is never set at all** — `tag-list.component.ts:74-78, 362-364`; `form-field/form-field.ts:241-244, 539-544`; `form-field/form-field-control.ts:62-66`.
`KbqFormField` resolves its describedby target as `contentChild.required(KbqFormFieldControl, { read: ElementRef })` (`form-field.ts:241-244`) and writes the hint/error ids onto that element unless the control implements the optional `setDescribedByIds` hook — a hook whose JSDoc says verbatim that it exists for controls where `aria-describedby` "has to be placed on an element other than the one" the token resolves to (`form-field-control.ts:62-66`). `KbqTagList` provides itself as `KbqFormFieldControl` (`tag-list.component.ts:75`) and does **not** implement the hook — a repo-wide grep finds no implementer at all. So the ids are written to `<kbq-tag-list>`.

But `<kbq-tag-list>` is not the element the user focuses when a tag input is present: `tabIndex` returns `null` whenever `this.tagInput` is set (`:362-364`), so the host is removed from the tab order entirely and focus lives on the `<input kbqTagInputFor>`. `aria-describedby` on a non-focusable ancestor is not announced. The result: for Tag input and Tag autocomplete — two of the four docs entries — hints and validation errors are never read out on focus, which is the exact WCAG 3.3.2 defect `REVIEW.form-field.md:37-39` filed against the whole family and which has since been fixed *in the form field* by the `kbqSetDescribedByIds` machinery, leaving `tags` as the control that does not benefit from it. Separately, `aria-invalid` is bound on `KbqInput`, `KbqInputPassword`, `KbqSelect` and `KbqTextarea` but on nothing in this package, so the error state is not exposed either.
**Fix:** implement `setDescribedByIds(ids: string[])` on `KbqTagList` and forward it to the registered `KbqTagTextControl`'s native element when one exists (falling back to the host when the list is used standalone) — that needs an `elementRef` or a `setDescribedByIds` member on the `KbqTagTextControl` interface (`tag-text-control.ts:5-20`). Add `'[attr.aria-invalid]': 'errorState'` to `KbqTagInput`'s host block and, for the standalone list, to `KbqTagList`'s. Then **re-enable** the `error messages` block in `tag-list.component.spec.ts:1062` (see TAG-TEST-01) — its two `aria-invalid` assertions and its `aria-describedby` assertion become the regression guard, once retargeted from `tagListEl` to the input.

**TAG-A11Y-04 · Nothing announces removal or selection, and the package sources no text from `kbqInjectA11yLocaleConfiguration()`** — `tag.component.ts:552-556, 761-788`, `tag-list.component.ts:786-798`; contrast `core/locales/a11y.ts:29-31` and its 14 in-repo users.
When a tag is removed, the only feedback is visual and positional: `updateFocusForDestroyedTags()` moves the key manager to the nearest surviving index, or to the input if the list emptied (`tag-list.component.ts:787-795`). Nothing tells assistive technology that a removal happened, how many tags were removed (recall `Delete` removes the whole selection), or how many remain. There is no live region anywhere in the package, and `LiveAnnouncer` is not used anywhere in the library — so this is a library-wide convention gap rather than a `tags`-specific regression, and it should be fixed here first because `tags` is the one component whose primary interaction is destructive.

The focus move is also conditional in a way that widens the gap: `lastDestroyedTagIndex` is only recorded when the removed tag had `hasFocus` (`tag-list.component.ts:900-902`), which `KbqTagRemove.handleClick` fakes by assigning `this.parentTag.hasFocus = true` before calling `remove()` (`tag.component.ts:776`). A programmatic removal — a "clear all" button, a server-driven update — moves no focus and announces nothing, so a screen-reader user gets no signal at all.

Separately, AGENTS.md requires component-provided default ARIA text to come from `kbqInjectA11yLocaleConfiguration()`. Fourteen packages do this (`breadcrumbs`, `modal`, `form-field/cleaner.ts`, `notification-center`, …); `tags` has no ARIA text to localise precisely because it has none at all, so this becomes actionable the moment TAG-A11Y-01/02 land.
**Fix:** inject `LiveAnnouncer` in `KbqTagList` and announce on the `tagRemoveChanges` stream — a localized template such as `"{tag} removed, {count} remaining"` sourced from a new `tags` section of `KbqA11yLocaleConfiguration`. Announce the selection count on `Ctrl+A` and on range extension. Replace the `hasFocus = true` hack at `tag.component.ts:776` by recording `lastDestroyedTagIndex` for every removal and only *restoring focus* when the list previously held it. Guard with specs that spy on `LiveAnnouncer.announce` for single removal, multi-removal and select-all.

**TAG-API-01 · `[selectable]="false"` on a tag inside a tag list is silently ignored** — `tag.component.ts:366-368`, compare `:279-281`, `:382-384`, `:414-416`.
The four flags that a tag can inherit from its list each compose differently, and one of them composes wrongly:

| Flag | Expression | Per-tag `false` wins? |
|---|---|---|
| `editable` | `this._editable ?? !!this.tagList?.editable()` | yes |
| `removable` | `this._removable && (this.tagList?.removable ?? true)` | yes |
| `disabled` | `this._disabled \|\| (this.tagList?.disabled ?? false)` | n/a (list must be able to force it) |
| `selectable` | `this._selectable \|\| !!this.tagList?.selectable()` | **no** |

Because `KbqTagList.selectable` defaults to `true` (`tag-list.component.ts:334`), the `||` means every tag inside every tag list is selectable and `[selectable]="false"` on an individual tag has no effect — it cannot be opted out of the roving selection, `Space` still toggles it, `Ctrl+A` still includes it, and `Delete` still destroys it as part of the selection. The intent that per-tag opt-out should work is visible in the library itself: `select.html:35` and `tree-select.html:35` both bind `[selectable]="false"`, and it works there only because those tags have no `KbqTagList` ancestor (`this.tagList` is `null`, so the right-hand operand is `false`).
**Fix:** change to the `??` form used by `editable`: `get selectable() { return this._selectable ?? !!this.tagList?.selectable(); }` with `private _selectable: boolean | undefined;`. That preserves "inherit from the list when unset" while letting an explicit `false` win, matching `editable` and `removable`. This is a behaviour change for anyone relying on the current OR, so land it with the next minor and note it in the changelog. Guard with a spec asserting `Space`, `Ctrl+A` and `handleSelectionInteraction` all skip a `[selectable]="false"` tag inside a selectable list.

**TAG-LIFE-01 · `registerInput()` subscribes forever and mirrors the inner control's errors onto the outer one** — `tag-list.component.ts:565-575, 529-533`.
```ts
if (this.ngControl && inputElement.ngControl?.statusChanges) {
    inputElement.ngControl.statusChanges.subscribe(() =>
        this.ngControl.control!.setErrors(inputElement.ngControl!.errors)
    );
}
```
Two problems, both flagged by the author's own `// todo need rethink about it (#DS-3740)` on `:569`. First, the subscription has no teardown — no `takeUntilDestroyed`, no `takeUntil(this.tagsSubscriptions$)` — so it outlives the tag list for as long as the inner control lives. Second, `AbstractControl.setErrors` **replaces** the entire errors object, so every status change on the inner input overwrites whatever the outer control's own validators produced. A list bound to `new FormControl([], [Validators.required])` whose inner input is valid gets `setErrors(null)` and is thereby reported valid, `required` and all, until something calls `updateValueAndValidity()` again. That is the mechanism behind the `error messages` spec block being disabled (TAG-TEST-01).

Separately, `ngOnDestroy` (`:529-533`) calls `this.tagsSubscriptions$.next()` but never `.complete()`, leaving the `Subject` alive; `stateChanges` is correctly completed on the line above, so the omission is an oversight rather than a convention.
**Fix:** pipe the subscription through `takeUntilDestroyed(this.destroyRef)` and merge rather than replace: `this.ngControl.control!.setErrors({ ...omitTagInputErrors(this.ngControl.control!.errors), ...inputElement.ngControl!.errors })`, namespacing the forwarded keys (e.g. `tagInput: {...}`) so the outer control's own errors are never touched — the same shape `form-field.ts:552-556` uses for the password-strength error. Add `this.tagsSubscriptions$.complete()` to `ngOnDestroy`. Guard by re-enabling the `error messages` block and adding a case where both the outer `required` and an inner `maxLength` are violated simultaneously.

**TAG-CSS-01 · Only 4 of the 9 `KbqComponentColors` are themed; the rest render as unstyled transparent tags** — `_tag-theme.scss:55-73`, `core/common-behaviors/color.ts:19-31, 55-65`.
`kbq-tag-theme()` styles exactly four selectors: `.kbq-theme`, `.kbq-contrast-fade`, `.kbq-error`, `.kbq-warning`. `KbqColorDirective` accepts any of the nine `KbqComponentColors` members (plus arbitrary strings — the input is typed `KbqComponentColors | ThemePalette | string`) and blindly writes `kbq-${color}` onto the host (`color.ts:59-62`). So `[color]="colors.Success"`, `colors.ThemeFade`, `colors.Contrast` and `colors.Empty` all compile — `strictTemplates` cannot help, the type is `string` — and produce a tag with no background, no text colour and no focus outline, because `_kbq-tag-state` sets all three from `--kbq-tag-<type>-*` variables that only exist for the four themed types (`tag-tokens.scss:11-94`).

The most damaging member is `KbqComponentColors.Default`, which is `'contrast'` (`color.ts:29`) — the enum entry whose name promises the safe choice produces `.kbq-contrast`, which is unthemed. The docs never state the restriction: `tag.en.md:5-7` says "Color" and embeds `tag-fill-and-style`, whose example happens to show exactly the four supported values (`tag-fill-and-style-example.ts:16-35`), and `e2e.ts:56-61` enumerates the same four — so the limitation is encoded three times without ever being written down.
**Fix:** either add the missing token sets and theme branches (the natural mapping is `success-fade-on`, mirroring `error-fade-on`), or narrow the surface: give `KbqTag` its own `color` input typed `KbqTagColor = 'theme' | 'contrast-fade' | 'error' | 'warning'` (`kbqStyle`-like open strings are an intentional extension point elsewhere in the library, but `color` on a tag is not), and add a dev-mode `console.warn` for an unsupported value. Whichever path, document the supported set in `tag.en.md`/`tag.ru.md`. Guard with a Playwright case extending `E2eTagStateAndStyle`'s `colors` array to all nine and asserting the snapshot.

**TAG-TEST-01 · 14 of 225 Jest cases are disabled, and the disabled block is hiding a real gap** — `tag-list.component.spec.ts:731, 746, 771, 784, 834, 844, 852, 987` (`xit`), `:1062` (`xdescribe`, 6 cases).
The package has 225 `it(...)` cases (66 + 113 + 46). Eight are individually skipped and the entire `error messages` block is skipped. That block is not a flaky-test skip: three of its assertions read `tagListEl.getAttribute('aria-invalid')` (`:1078, 1091, 1106`) and one reads `tagListEl.getAttribute('aria-describedby')` (`:1144, 1157`) — attributes the component never sets (TAG-A11Y-03), so the block documents intended behaviour that was never implemented and was then muted rather than filed. The other eight skips cover forms integration (`should set the view value from the form`, `should update the form value when the view changes`, `should set the control to dirty when the tag list's value changes in the DOM`, `should not set the control to dirty when the value changes programmatically`) — precisely the `ControlValueAccessor` semantics that TAG-BUG-01 breaks.

Beyond the skips, three surfaces have zero coverage. `dropped` — the output backing the documented drag-and-drop feature (`tag-list.en.md:58-62`, `tag-input.en.md:60-64`, plus `tag-list-draggable`, `tag-input-draggable` and `tag-autocomplete-draggable` examples) — appears **zero** times in any spec; the only drag tests assert CSS classes (`:1774-1802`). `writeValue`, `registerOnChange` and `setDisabledState` appear zero times. And the 9 Playwright tests never drag either, so the entire reorder path — `CdkDropList` `orientation: 'mixed'`, `elementContainerSelector`, the `pendingUIChange` arm at `:936` — ships untested. By contrast, range selection has 16 dedicated cases (`:1228-1520`), which is what good coverage in this package looks like.
**Fix:** in order — (1) re-enable `:1062` after TAG-A11Y-03, retargeting the assertions from `tagListEl` to the input element; (2) re-enable the four forms-integration `xit`s as the regression guards for TAG-BUG-01, fixing them rather than the source if they encode stale expectations; (3) add a `dropped` spec driving `CdkDropList.dropped` through the CDK test harness and asserting both the emitted `{ previousIndex, currentIndex, tag }` and that `pendingUIChange` propagated; (4) add a Playwright drag case to `E2eTagListStates` using `dragTo`. Each re-enabled case must be either green or converted into a filed defect — no case may be re-skipped.

**TAG-PERF-01 · Every tag instantiates `CdkDrag` and a child-checking `FocusMonitor`, including in select triggers where neither can ever fire** — `tag.component.ts:237, 245, 704-714, 716-737`; consumers `select/select.html:32-45`, `tree-select/tree-select.html:32-45`.
`KbqTag` declares `hostDirectives: [CdkDrag]` unconditionally (`:237`), so every instance constructs a `DragRef`, binds pointer/touch listeners to its root element and registers with the CDK's global drag registry — regardless of whether a `CdkDropList` ancestor exists or `draggable` is ever true. It also calls `focusMonitor.monitor(this.elementRef, true)` in `ngAfterViewInit` (`:717`); the `true` is `checkChildren`, the more expensive mode, which walks up from every focus event in the document to test containment.

The cost is not hypothetical, because `kbq-tag` is not only used in tag lists. `kbq-select` and `kbq-tree-select` render one `<kbq-tag>` per selected option directly in their triggers (`select.html:31-45`), with `[selectable]="false"` and no drop list — so a multi-select showing 50 chosen values pays for 50 `DragRef`s and 50 child-checking focus monitors that can never do anything. `KbqTag`'s own focus subscription then runs `if (!this.tagList && origin !== 'mouse') this.select()` on each of them (`:727`), which immediately returns because `selectable` is false.
**Fix:** the clean version is to drop `hostDirectives: [CdkDrag]` and apply `cdkDrag` from the *list's* template — but the tags are content-projected, so that is not available. The practical version: keep the host directive but make it inert by construction — `this.drag.disabled = true` is already synced (`:712-714`), so additionally skip `setupDragInitialProperties()`'s `started` subscription when `!this.tagList` (`:704-710`), and make the focus monitor conditional: `monitor(this.elementRef, !!this.tagList)` so standalone tags use the cheap mode. Longer term, split a `KbqTagDraggable` host directive that `KbqTagList` applies only when `draggable` is set. Measure with a dev-app page rendering a 200-value `kbq-select` and comparing `DragRef` instance counts before/after.

### P3 — Nice to have / hygiene

**TAG-BUG-04 · The list's `removable` setter overwrites each tag's own `removable`** — `tag-list.component.ts:342-352, 925-927`, `tag.component.ts:381-390`.
`set removable(value)` calls `syncTagsRemovableState()`, which does `this.tags?.forEach((tag) => (tag.removable = this.removable))` — assigning through the tag's *setter*, which writes `_removable` (`tag.component.ts:386-388`). Any `<kbq-tag [removable]="false">` inside the list is therefore permanently reset to the list's value. The sync is also redundant: `KbqTag.removable`'s getter already ANDs with the list (`:383`), so the composition works without it. The `?.` guard means a static `removable` attribute is harmless (the setter runs before `tags` is populated); the clobber only fires when `[removable]` is toggled at runtime.
**Fix:** delete `syncTagsRemovableState()` and its two call sites (`:349`, `:927`); the getter composition already covers it. Add a spec that sets `[removable]="false"` on one tag inside `<kbq-tag-list [removable]="flag">`, toggles `flag`, and asserts that tag stays non-removable.

**TAG-API-02 · The per-tag stream getters snapshot the current tags and go stale** — `tag-list.component.ts:139-186`.
`tagSelectionChanges`, `tagFocusChanges`, `tagBlurChanges`, `tagRemoveChanges` and `tagEditChanges` are all `get x() { return merge(...this.tags.map(...)); }`. `merge` fixes its source list at subscribe time, so a consumer subscribing once — the natural reading of a public `Observable` getter — stops receiving events for every tag added afterwards, and keeps a reference to every tag removed. `KbqTagList` knows this and works around it internally by re-subscribing from scratch on each `tags.changes` behind a `tagsSubscriptions$` reset gate (`:865-870, 493-522`); consumers get no such help and no warning in the JSDoc. Four of the five are `@public` in the guard (`tags.api.md:290-295`) with only `tagBeforeRemoveChanges` marked `protected`, so this is a shipped contract.
**Fix:** replace each getter with a `switchMap` over the query list — `this.tags.changes.pipe(startWith(this.tags), switchMap((tags) => merge(...tags.map(...))))` — so the stream re-merges automatically, and simplify `resetTags()` to a single subscription each. Alternatively mark all five `protected` and expose one aggregate `selectionChange`/`removed` output pair (which also fixes TAG-BUG-02's ergonomics); that is breaking, so schedule with a major.

**TAG-API-03 · `KbqTagTextControl` is public API but is not exported, and 14 `any`s cross the value surface** — `tags.api.md:172-174, 274`; `public-api.ts:1-4`; `tag-text-control.ts:5-20`.

A consumer writing a custom text control — the documented reason the interface exists ("Interface for a text control that is used to drive interaction with a kbq-tag-list", `tag-text-control.ts:1`) — cannot name its type. Separately, `value`, `KbqTagListChange.value`, `valueChange`, `onChange`, `writeValue`, `KbqTag.value` and `KbqTag.tabindex` are all `any` (14 occurrences across the two component files), against AGENTS.md's "avoid `any`; use `unknown` when the type is uncertain".
**Fix:** add `export * from './tag-text-control';` to `public-api.ts`, then `yarn run build:components && yarn run approve-api` (build first — the guard reads `dist/*.d.ts`). Introduce a generic parameter `KbqTagList<T = unknown>` so `value: T[]` and `KbqTagListChange<T>` are typed, keeping `any` only where an untyped `ControlValueAccessor` boundary genuinely demands it.

**TAG-ARCH-01 · Dead host modifier classes (one of them always applied), a dead deprecated public method, and migration leftovers** — `tag.component.ts:11, 224-226, 309, 454-480`; 21 `TODO: Skipped for migration` comments across the three files.

**TAG-CSS-02 · Drag transitions ignore the repo's reduced-motion convention, and 20 colour tokens are dead** — `tag.scss:90-92`, `tag-list.scss:15-17`, `tag-tokens.scss:14-94`; `playwright.config.ts:99-101`.
Two `transition: transform` rules run unconditionally: `.kbq-tag.cdk-drag-animating` (300ms) and `.kbq-tag-list.cdk-drop-list-dragging .cdk-drag` (250ms). **TAG-STYLE-01 · `KbqTag.focus()` discards the focus origin the key manager passes it, plus two smaller robustness nits** — `tag.component.ts:540-544`; `core/a11y/key-manager/focus-key-manager.ts:21-29`; contrast `tree/tree-option.component.ts:323-326`; `tag-input.ts:258-260, 417-419`.
`IFocusableOption` declares `focus(origin?: FocusOrigin): void` and `FocusKeyManager.setActiveItem` calls `this.activeItem.focus(this.origin)` (`focus-key-manager.ts:26-28`). `KbqTag.focus()` takes no parameter and calls the bare `this.elementRef.nativeElement.focus()`. Two things are lost: the origin (so the CDK falls back to inferring it from the last input modality rather than the intent the list expressed via `setFocusOrigin`, `tag-list.component.ts:878`) and `preventScroll` — `KbqTreeOption` passes `{ preventScroll: focusOrigin === 'mouse' }` for exactly this reason, so arrow-navigating a wrapped multi-row tag list or refocusing after a mouse-driven removal can scroll the container. Two smaller items in the same bucket: `KbqTagInput.ngOnChanges()` dereferences `this._tagList.stateChanges` unguarded (`:259`) although the `tagList` setter only assigns when the value is truthy (`:198-203`), so a template that binds `[kbqTagInputFor]` to a not-yet-resolved reference throws; and `private trimValue(value)` (`:417`) has an implicit `any` parameter (legal here — `tsconfig.json` sets `strictNullChecks` but not `noImplicitAny` — but out of step with the file).
**Fix:** change the signature to `focus(origin?: FocusOrigin): void` and use `this.focusMonitor.focusVia(this.elementRef, origin ?? 'program')` (which is also what restores the `cdk-keyboard-focused` ring deterministically) with `{ preventScroll: origin === 'mouse' }`. Guard `ngOnChanges` with `this._tagList?.stateChanges.next()`. Type `trimValue(value: string): string`.

General gates, after every phase, sequentially — never in parallel, and never alongside another agent's build:

- `yarn run e2e:docker` for anything that touches SCSS — the `__screenshots__` baselines are Linux, compared with `threshold: 0` and no platform suffix, so a native run fails on font rasterisation alone.
- Manual smoke in `yarn run dev:tag` (`packages/components-dev/tag/template.html`, 217 lines covering all four surfaces).

Per-phase acceptance assertions — what *proves* the fix, not just what to run:
- **Phase 1:** the DOM of a rendered tag list contains `role="listbox"` with `aria-multiselectable`, and every tag `role="option"` with an `aria-selected` that flips on `Space` and on `Ctrl+A`. ## Appendix A — Review Methodology

Findings were gathered by reading the package end to end — all four TypeScript sources, all three Jest specs, the e2e fixture and Playwright spec, all four bilingual guides, the four examples-stub files, the three SCSS files and the token file — then following each candidate outward to its consumers, its docs entry, its examples, the API guard report and git history. Composition claims (`editable`/`selectable`/`removable`/`disabled`) were checked against the getters directly rather than the docs. Cross-package claims were checked against the actual current source of `form-field` and `autocomplete`, not against the published sibling reviews, because both have moved since those were written — see the corrections below. Severity calibration follows the shared scale and, where the same class of gap already appears in a published sibling review, that review's grading (`REVIEW.select.md`, `REVIEW.form-field.md`).

Refuted during verification:
- **"An empty tag input with an open autocomplete panel swallows `Enter`, so an option cannot be selected."** `KbqTagInput.onKeydown`'s empty-input branch does call `preventDefault()` and `stopPropagation()` (`tag-input.ts:266-274`) without the `panelOpen && activeOption` exemption the non-empty branch has. But both listeners are host bindings on the *same* element, so `stopPropagation` does not stop the sibling, and `KbqAutocompleteTrigger.handleKeydown` never checks `event.defaultPrevented` before calling `activeOption.selectViaInteraction()` (`autocomplete-trigger.directive.ts:406-409`). Selection works. Fragile, but not a defect.
- **"Disabling the tag list leaves each tag's `CdkDrag` enabled, so tags stay draggable."** `syncDragDisabledState()` only runs from `KbqTag`'s own `disabled` setter (`tag.component.ts:420`), so `drag.disabled` is indeed stale when the *list* is disabled — but CDK's `DragRef.disabled` getter is `this._disabled || !!(this._dropContainer && this._dropContainer.disabled)` (`node_modules/@angular/cdk/fesm2022/drag-drop.mjs:633`), and `KbqTagList`'s `disabled` setter already disables the drop list (`tag-list.component.ts:306, 944-946`). The stale field is inert.
- **"The remove icon is never themed, because the theme mixin targets `.kbq-icon.kbq-empty`."** `KbqColorDirective`'s constructor assigns `KbqComponentColors.Empty` (`core/common-behaviors/color.ts:69-71`), which writes `kbq-empty` onto the host, so a bare `<i kbq-icon kbqTagRemove>` does match `_tag-theme.scss:9-11`. The rule is live.
- **"`.kbq-tag-list:focus-visible { outline: none }` removes the focus indicator with nothing replacing it."** `tag-list.scss:11-13` does exactly that, but the host's `(focus)` handler immediately delegates into the key manager (`tag-list.component.ts:618-634` → `setFirstItemActive()`), and an empty list is not tabbable at all (`updateTabIndex()` sets `-1` at `:777`). The focused tag then gets its `outline` from `_tag-theme.scss:29-32`. No unindicated focus state is reachable.
- **"`writeValue` never renders anything, so `[formControl]` on `kbq-tag-list` is broken."** `writeValue` does only `this.value = value` (`tag-list.component.ts:580-582`), but the documented pattern has the consumer render the tags itself from the control value (`tag-input-with-form-control-validators-example.ts:36-41`), so the CVA is intentionally one-directional. The real defect is in the *other* direction and is filed as TAG-BUG-01.
- **"`addHostClassName()` writes classes via raw `classList` in the constructor and breaks SSR."** `tag.component.ts:483-497` writes to `elementRef.nativeElement.classList`, which Angular's server DOM implements. AGENTS.md bans the global `window` (hence `KBQ_WINDOW`) and direct `innerText`, neither of which appears in this package.
