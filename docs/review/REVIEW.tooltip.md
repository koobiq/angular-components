## 1. Executive Summary

- **A compact, widely-reused trigger directive that is functionally solid for pointer users and structurally silent for everyone else.** Tooltip has no P0 and — unlike popover — no correctness P1: the default hover flow shows, positions, and hides correctly, lifecycle hygiene is largely right, and the two legacy subclasses (warning/extended) were cleanly unified into a `modifier` input with zero duplication. All four P1s are additively fixable: three accessibility failures and one dependency-injection trap.
- **Accessibility is the headline problem — the tooltip does not exist for assistive technology.** The pop-up has no `role="tooltip"` and the trigger never sets `aria-describedby`, so a screen-reader user focusing `<button kbqTooltip="Delete permanently">` hears only "button" (TIP-A11Y-01 — prior `REVIEW.md` A11Y-07/A11Y-20, both still open). On top of that, the default `ignoreTooltipPointerEvents=true` makes every hover tooltip click-through — the pointer cannot land on it, a WCAG 1.4.13 _hoverable_ failure in the default configuration (TIP-A11Y-02) — and a hover tooltip on a non-focusable element cannot be dismissed with Escape because the only Escape handler sits on the trigger's own `keydown` (TIP-A11Y-03, 1.4.13 _dismissable_).
- **Pure-standalone import crashes.** `KBQ_TOOLTIP_SCROLL_STRATEGY` has no factory default and its only provider lives in `KbqToolTipModule`, so `imports: [KbqTooltipTrigger]` — the repo's own standalone-first mandate — throws `NullInjectorError` at directive construction (TIP-ARCH-01; the verified tooltip copy of the 8-copy repo-wide POP-ARCH-01 pattern).
- **The correctness tail is real but all-P2, split evenly between inherited base debt and tooltip-own input plumbing.** From `core/pop-up`: the `hideWithTimeout` watchdog degenerates into an `interval(0)` busy-loop because tooltip defaults `leaveDelay=0` (TIP-BUG-01, ex-POP-BUG-03 re-qualified); re-hover during the leave window cannot cancel the pending hide and the untracked timer can fire after destroy (TIP-BUG-02); the `keydown` listener bypasses `createListener`, leaving a stale `triggerName` that can wrongly suppress a keyboard-opened tooltip (TIP-BUG-06). Tooltip-own: input reactivity is implemented three inconsistent ways, leaving `[kbqTooltipArrow]`/`[kbqTooltipOffset]` inert while open (TIP-BUG-05); `applyRelativeToPointer` permanently nulls the user's `placementPriority` (TIP-BUG-03); and the `forDisabledComponent` effect silently clobbers an explicitly bound `kbqTooltipDisabled` (TIP-BUG-04).
- **One shared object quietly couples every tooltip in the app.** `KBQ_TOOLTIP_OPEN_TIME_PROVIDER` uses `useValue: { value: 0 }` — a single module-scope literal — so _all_ tooltips share one `openTime`, and the magic `MIN_TIME_FOR_DELAY = 2000` makes any tooltip shown within 2 s of any other skip its own `enterDelay` (TIP-ARCH-02). Plausibly intended rapid-reshow UX, but undocumented, unconfigurable, falsely component-scoped — and it silently collapsed the test suite's timing: every `tick(410)` in the spec exercises a 0 ms delay, so the documented 400 ms `enterDelay` has no real coverage (TIP-TEST-01).
- **The tests that exist are honest; the gaps are wide.** 15 DOM-first Jest tests cover hover/focus show-hide, disabled, TemplateRef context, arrow-offset math, `forDisabledComponent`, and reactive `modifier`/`header` — but Escape, click-trigger closing, `relativeToPointer`, `hideWithTimeout` timing, the imperative `showForMouseEvent`/`showForElement` API, output emissions, and the negative focus-origin path all have zero coverage (TIP-TEST-02), and Playwright ships exactly two screenshot tests against a fixture that force-shows tooltips programmatically (TIP-TEST-03).
- **API hygiene carries a heavy P3 tail.** The input alias family splits into `kbqTooltip*` and unprefixed (`kbqPlacement`, `kbqTrigger`, …) with no rule (TIP-API-06); `context` is `any` end-to-end and falsy contexts are silently dropped (TIP-API-04); the imperative show API is simultaneously `@docs-private` and the officially demonstrated dynamic pattern (TIP-API-02); `kbqTooltipColor`'s getter returns a different value than the setter accepts (TIP-API-01); and the docs have no API table at all — `hideWithTimeout`, `ignoreTooltipPointerEvents`, and `forDisabledComponent` appear in no prose in either language (TIP-API-08).
- **What's strong.** Zero XSS surface (no `innerHTML`/`bypassSecurityTrust` anywhere in the chain); standalone + OnPush + host-object + uniform `inject()` baseline with native `@if` in the template; designed-in lifecycle hygiene (trigger streams under `takeUntilDestroyed`, the viewport-ruler and watchdog subscriptions correctly scoped to the _instance_ `destroyRef`, `FocusMonitor.monitor`/`stopMonitoring` paired, `KbqPopUp.ngOnDestroy` clears both timers and completes its subjects); the two legacy subclasses replaced by a single `modifier` input with documented reactivity (`ngOnChanges` mirror) instead of code duplication; JSDoc coverage on inputs far above popover's; 16 docs examples covering placements, offsets, variants, and dynamic usage; disciplined BEM styles driven by CSS tokens with theme/typography mixins.

## 3. Prioritized Findings (deduplicated, verified)

### P0 — Release blockers

None found. No default core flow crashes or loses data: the one discovered crash path (`showForElement` on a disabled trigger, TIP-BUG-08) sits behind a `@docs-private` imperative API with no in-repo callers; the standalone `NullInjectorError` (TIP-ARCH-01) is real but every in-repo and documented usage imports the NgModule, so it bites only standalone-first consumers; and the a11y P1s block user groups but not the primary pointer flow.

### P1 — High

**TIP-A11Y-01 · No `role="tooltip"`, no `aria-describedby` — the tooltip does not exist for screen readers, and dynamic updates are never announced** — `tooltip.component.html:1`; `tooltip.component.ts:131-136` (host), `:490-502` (updateData).
The pop-up root `<div #tooltip class="kbq-tooltip">` carries only presentational classes — no `role`, no `id`. The trigger host binds only `[class.kbq-tooltip_open]`, `(keydown)`, `(touchend)`; nothing in the chain ever sets `aria-describedby` or calls CDK's `AriaDescriber` (grep across the package returns zero `aria-`/`role` matches). The overlay renders at the end of `<body>`, disconnected from the trigger in the accessibility tree, so an NVDA/VoiceOver user focusing `<button kbqTooltip="Delete permanently">` sees the tooltip appear and hears only "button" (WAI-ARIA APG tooltip pattern; WCAG 4.1.2, 1.1.1). Compounding it, `updateData()` mutates open-tooltip content with `detectChanges()` but there is no `aria-live`/`LiveAnnouncer` anywhere, so content that changes while open ("Saving…" → "Saved") is silent too. Prior `REVIEW.md` A11Y-07 and A11Y-20, both still open, merged here.
**Fix:** adopt the `MatTooltip` pattern — inject `AriaDescriber`, call `describe(triggerEl, message, 'tooltip')` on show / `removeDescription` on hide/destroy for string content; add `role="tooltip"` + a stable generated `id` to the pop-up and point `aria-describedby` at it for template content; re-describe on content change (or use a polite live region for genuinely dynamic status text). Add Jest assertions for `aria-describedby` on the trigger and `role="tooltip"` on the overlay.

**TIP-A11Y-02 · `ignoreTooltipPointerEvents` defaults to `true` — every hover tooltip is click-through and un-hoverable (WCAG 1.4.13 _hoverable_ fails in the default config)** — `tooltip.component.ts:167` (default), `:434-436` (panel class push), `:358-360` (overlayConfig).
`ignoreTooltipPointerEvents = input<boolean>(true)` and `ngAfterViewInit` pushes `cdk-overlay-pane_ignore-pointer-events` onto the panel class, so by default the pane has `pointer-events: none`. WCAG 1.4.13 requires that pointer-triggered content can be hovered ("the pointer can be moved over the additional content without it disappearing"); with pointer events disabled, a screen-magnification user moving toward the tooltip to read it can never land on it — the trigger's `mouseleave` fires and the tooltip hides under the pointer. This is the default for every hover tooltip (partial mitigation: the opt-in `hideWithTimeout` keeps it open while the pointer crosses; one verifier voted P2 on that basis — P1 retained 2:1 as a default-config failure). Secondary hygiene: the push is an in-place mutation of the per-instance `overlayConfig.panelClass` array relying on `ngAfterViewInit` firing exactly once before the first `createOverlay`; popover instead recomputes its config in a getter.
**Fix:** flip the default to `false` (or pair the default with hover-persistence so the pointer can rest on the tooltip), keep click-through as a documented opt-in with the 1.4.13 caveat; compute `panelClass` immutably from the signal in a getter/`computed` instead of the lifecycle push.

**TIP-A11Y-03 · Hover tooltip cannot be dismissed with Escape — the only Escape handler lives on the un-focused trigger (WCAG 1.4.13 _dismissable_ fails) (shared)** — `pop-up-trigger.ts:335-339`; `tooltip.component.ts:134`; `tooltip.en.md` (close triggers list).
The sole Escape handling is `keydownHandler` bound to the trigger host `(keydown)` — `if (this.isOpen && event.keyCode === ESCAPE) this.hide()`. Keyboard events fire only on the focused element, so for the default `hover, focus` trigger, hovering a non-focusable host (`<span kbqTooltip>`, an icon) opens a tooltip while focus is elsewhere; Escape goes to the focused element and the tooltip stays. The overlay pane is not focused and has no keydown handler. The docs list only cursor-away/blur/scroll as close mechanisms, confirming the gap. Failure scenario: a large tooltip overlaps the next control; the user presses Escape; nothing happens. One verifier voted P2 (keyboard-_focus_-triggered tooltips do dismiss) — P1 retained 2:1 because the failing case is the default hover mode.
**Fix:** while any tooltip is open, listen for Escape at the document level (outside the zone, torn down on hide/destroy) and/or subscribe `overlayRef.keydownEvents()`; cover with a test dispatching a document-level ESCAPE over a hover tooltip.

**TIP-ARCH-01 · Pure-standalone import of `KbqTooltipTrigger` throws `NullInjectorError` — the NgModule is load-bearing for the scroll strategy (shared — 8 copies repo-wide)** — `tooltip.component.ts:110` (token), `:144` (non-optional inject); `tooltip.module.ts:14,17` (only provider).
`KBQ_TOOLTIP_SCROLL_STRATEGY` is created without a `factory`/`providedIn` default, the trigger field-injects it non-optionally at construction, and the only provider lives in `KbqToolTipModule`. A consumer following the repo's own standalone-first mandate (`imports: [KbqTooltipTrigger]`) crashes at directive instantiation. Every in-repo usage imports the module, masking the trap — `tooltip-dynamic-example.ts` even does `new KbqTooltipTrigger()` via `runInInjectionContext` and works only because the surrounding component imports the module. Verified tooltip copy of POP-ARCH-01 (8 copies repo-wide). One verifier voted P2 (latent — no documented standalone usage exists); P1 retained 2:1 as a crash against the repo's own mandate.
**Fix:** give the token a self-providing default — `new InjectionToken('kbq-tooltip-scroll-strategy', { providedIn: 'root', factory: () => { const overlay = inject(Overlay); return () => overlay.scrollStrategies.close(); } })` — keeping the module provider as an override; fix the popover twin in the same PR and open the repo-wide ticket for the remaining copies.

### P2 — Should fix

- **TIP-BUG-01 · `interval(0)` auto-hide watchdog busy-loops for the whole open lifetime of a `hideWithTimeout` tooltip (shared)** — `pop-up-trigger.ts:391-401`; tooltip defaults `leaveDelay = 0` (`tooltip.component.ts:262`), `hideWithTimeout` (`:177`). With `[kbqHideWithTimeout]="true"` and `kbqLeaveDelay` unset — exactly what the shipped `tooltip-interactive-example.ts:18` does — `show()` starts `interval(this.leaveDelay) === interval(0)` on the async scheduler: a `setInterval(…, 0)` loop running two filter predicates every ~0–4 ms, outside Angular, for as long as the tooltip is open. Scoped to the instance `destroyRef` (not a leak) and opt-in (downgraded from the popover-side P1 = POP-BUG-03), but pure main-thread churn on a documented pattern. **Fix:** skip the watchdog when `leaveDelay <= 0` or floor the period (e.g. 500 ms); better, replace polling with an event-driven `timer(leaveDelay)` started on mouseleave and cancelled on re-hover.
- **TIP-BUG-02 · Re-hover during the `hideWithTimeout` leave window cannot cancel the pending hide; the untracked timer can fire after destroy (shared)** — `pop-up-trigger.ts:531-534` (untracked `setTimeout(hide, leaveDelay)`), `:350` (show early-returns while instance exists), `:280-286` (ngOnDestroy clears no timers); `pop-up.ts:72-74` (unreachable `clearTimeout`). With a non-zero `kbqLeaveDelay`, leaving and re-entering the trigger within the window still hides the tooltip under the cursor at t = leaveDelay (the early return means `KbqPopUp.show`'s `clearTimeout(hideTimeoutId)` is never reached), and destroying the host inside the window still fires `hide()` on a torn-down trigger (= POP-BUG-06 tooltip side). **Fix:** store the timer id, clear it on mouseenter and in `ngOnDestroy`; on re-enter with a live instance call `instance.show(delay)` instead of early-returning; add `clearTimeout(hideTimeoutId)` at the top of `KbqPopUp.hide()`.
- **TIP-BUG-03 · `applyRelativeToPointer` permanently nulls the user's `placementPriority`** — `tooltip.component.ts:544` (`this.placementPriority = null`), `:457-458`. If a consumer binds both `[kbqRelativeToPointer]="true"` and `[kbqPlacementPriority]`, the first mouseenter silently and irreversibly discards the priority input — never restored after close, still null after toggling `relativeToPointer` off, so later non-pointer shows use the wrong fallback set. The documented "does not work with kbqPlacementPriority" describes ignoring, not destroying, the input. **Fix:** don't mutate the backing field — pass a local override into the position computation while the pointer-relative origin is active.
- **TIP-BUG-04 · The `forDisabledComponent` effect unconditionally overwrites `disabled` every cycle, silently clobbering an explicit `kbqTooltipDisabled`** — `tooltip.component.ts:409-422` (effect), `:246-252` (disabled setter calls `hide()`). The effect runs `this.disabled = !disabled` whenever the wrapped component's signal changes: a co-bound `[kbqTooltipDisabled]` is overwritten on the next tick with no documented precedence, and an enable-transition of the wrapped control force-hides an open tooltip. Borderline-intended design; the defect is the silent clobbering. **Fix:** derive `disabled` from a `computed` combining both sources; let the effect manage only focusability; document precedence.
- **TIP-BUG-05 · `[kbqTooltipArrow]`/`[kbqTooltipOffset]` changes while open are inert — input reactivity exists in three inconsistent flavors** — `tooltip.component.ts:337,341` (plain fields, no setter, absent from ngOnChanges), `:390-400` (ngOnChanges handles only modifier/header), `:89-96` (margins applied only in `show()`), `:490-502`. content/context/customClass push via setters, modifier/header via `ngOnChanges`, arrow/offset not at all — changing them while open does nothing until the next show/hide cycle, and even an indirect `updateData()` never re-runs `applyPopupMargins`. The spec masks this: the arrow test mutates the field only across a close/reopen (`tooltip.spec.ts:156`). **Fix:** one mechanism — fold arrow/offset into the same `ngOnChanges` (re-applying margins when open), or migrate the inputs to `input()` + a single effect calling `updateData()`; add a change-while-open spec.
- **TIP-BUG-06 · `keydown` is the only trigger listener not wrapped in `createListener` — stale `triggerName` corrupts the focus gate (shared)** — `pop-up-trigger.ts:518-524` vs `:508-515`; consumed by the gate at `tooltip.component.ts:451`. A keyboard ENTER/SPACE open under `kbqTrigger="focus, keydown"` inherits the previous event's `triggerName`; if that was `'focus'` with a non-keyboard `_lastFocusOrigin`, the keydown-driven `show()` wrongly early-returns and the tooltip never appears. Latent for the default `hover, focus` trigger (= POP-BUG-13). **Fix:** register keydown via `createListener` (or set `triggerName = 'keydown'` in the handler) in core, so popover benefits too.
- **TIP-A11Y-04 · The focus gate reads CDK's private `_lastFocusOrigin` and suppresses all non-keyboard origins — brittle, and hides tooltips from programmatic focus** — `tooltip.component.ts:451`, `:432`. `show()` gates focus-triggered opens on `this.focusMonitor['_lastFocusOrigin'] !== 'keyboard'` — a private, undocumented CDK field (verified in `focus-monitor.d.ts`); a CDK rename silently turns the guard into "always suppress" with no compile error. CDK classifies script-driven `element.focus()` as `'program'`, so focus moved by step wizards or AT never shows the tooltip. The public alternative is already half-wired: `ngAfterViewInit` calls `focusMonitor.monitor(el)` and discards the returned `Observable<FocusOrigin>`. Prior `REVIEW.md` ARCH-02, still open (line drifted :412 → :451). **Fix:** subscribe to `monitor()`'s observable (`takeUntilDestroyed`), cache the origin, gate on it — treating `'keyboard'`/`'program'`/`null` as show-worthy and suppressing only `'mouse'`/`'touch'`; add the negative focus-after-mousedown test.
- **TIP-A11Y-05 · `forDisabledComponent` produces an unlabeled focusable `<div>` with a hand-rolled inline outline that is never removed on re-enable** — `tooltip.component.ts:415-419`; `tooltip-disabled-for-component-example.ts:16-20`; asserted only partially in `tooltip.spec.ts:295-332`. When the wrapped control is disabled the effect sets `tabindex="0"` plus inline `outline-color` on the wrapper div: (1) no role/accessible name — a screen reader hears an empty element; (2) `outline-color` alone renders nothing under a common `outline-style: none` reset and bypasses the repo's FocusMonitor-gated `.cdk-keyboard-focused` ring convention (WCAG 2.4.7); (3) the enable branch resets only `tabindex`, so a disable→enable→disable cycle leaves stale inline style. **Fix:** drive host state declaratively (`[attr.tabindex]`, a class styled in SCSS), use the standard focus-ring mechanism, give the wrapper a role/name reflecting the disabled control, and link `aria-describedby` (with TIP-A11Y-01).
- **TIP-ARCH-02 · App-wide shared `openTime` singleton + magic `MIN_TIME_FOR_DELAY = 2000`; provider declared in two scopes** — `tooltip.component.ts:56-59` (module-scope `useValue` literal), `:61`, `:70,87`; `tooltip.module.ts:18`. `useValue` never clones, so every injector hands out the _same_ object: any tooltip shown within 2 s of any other skips its own `enterDelay` app-wide, a programmatic show resets every tooltip's delay, and the component-level provider falsely implies per-instance scoping (the module registration is shadowed dead). Plausibly intended rapid-reshow UX — but undocumented, unconfigurable, cross-component global mutable state on a magic number. **Fix:** register once; document and name the behavior; make the window configurable (token or a `providedIn: 'root'` tracker service); pin the intent with a spec (see TIP-TEST-01).
- **TIP-LIFE-01 · Per-show `visibleChange` subscription accumulates on the trigger `DestroyRef` — the destroyed instance's emitter never completes (shared)** — `pop-up-trigger.ts:370-376`; `pop-up.ts:59-65` (completes `onHideSubject`/`hovered`, not `visibleChange`). Each open attaches a fresh instance and subscribes its `visibleChange` with `takeUntilDestroyed(this.destroyRef)` — the _trigger's_ lifetime. Angular does not auto-complete `EventEmitter`s on destroy, so every open/close cycle strands one dead subscription + one `DestroyRef` callback; unbounded for persistent triggers (a toolbar button hovered 2000 times = ~2000 stranded subs). `afterHidden` is fine — `onHideSubject.complete()` releases it (= POP-BUG-14 tooltip side). **Fix:** scope the subscription to `this.instance.destroyRef` (the viewport-ruler two lines below already does), or complete `visibleChange` in `KbqPopUp.ngOnDestroy`.
- **TIP-API-01 · `kbqTooltipColor` accessor is asymmetric: the setter accepts a raw color, the getter returns the `kbq-`-prefixed class — a broken round-trip** — `tooltip.component.ts:322-329`, consumed at `:523`. `get color()` returns `'kbq-contrast'` while `set color` stores raw values; read-then-write (input cloning) yields `_color = 'kbq-contrast'` → class `kbq-kbq-contrast` → the tooltip silently loses its theme. Latent (no shipped path round-trips), but the getter is really an internal CSS-class helper masquerading as the input's read side. **Fix:** make the getter symmetric (return the raw value) and expose the class form as a separate `colorClass` getter used by `updateClassMap`.
- **TIP-API-02 · `showForElement`/`showForMouseEvent` are `@docs-private` yet are the officially documented dynamic-tooltip API** — `tooltip.component.ts:462-464,476-487`; `tooltip-dynamic-example.ts:37-42`; `tooltip.api.md` lists both as public. The JSDoc on `showForElement` documents it as the intended public path, the shipped docs example instantiates `new KbqTooltipTrigger()` and calls `showForMouseEvent(event)` as the recommended pattern, and the API guard records both as public members — while `@docs-private` hides them from the doc site and implies they may change freely. One verifier voted P3; retained P2 as a contract contradiction on a first-party-documented path. **Fix:** decide the contract — remove `@docs-private` and document them in `tooltip.en.md`/`ru.md`, or remove the docs example's direct usage and provide a supported alternative.
- **TIP-TEST-01 · The shared `openTime` singleton collapses `enterDelay` to 0 across the whole spec — no test exercises the 400 ms path or the `MIN_TIME_FOR_DELAY` logic** — `tooltip.spec.ts:86,115,183,195,217,357,381` (all `tick(410)`); root at `tooltip.component.ts:56-59,87`. `openTime.value` persists across tests (no reset, same module-scope object) and consecutive fakeAsync zones start milliseconds apart in wall-clock terms, so `Date.now() - openTime.value < 2000` holds for every tooltip after the very first — `super.show(0)` fires immediately and every `tick(410)` verifies a 0 ms delay. An `enterDelay` regression would pass CI. Downgraded from P1: the mechanism it hides is intended UX, so no _shipped_ bug is masked — this is false coverage. **Fix:** reset the token in `afterEach` (`TestBed.inject(KBQ_TOOLTIP_OPEN_TIME).value = 0`); add tests pinning (a) first show honors `enterDelay`, (b) a show within 2 s bypasses it, (c) a show after >2 s re-applies it.

## Appendix A — Review Methodology

This review was produced by 8 parallel dimension agents — correctness & bugs, accessibility, RxJS/lifecycle, performance, architecture & conventions, API & types, tests, and templates/styles — each reading the tooltip package and `core/pop-up` source directly at HEAD `c183a1bb`, with the prior `REVIEW.md` and `REVIEW.popover.md` findings supplied as leads to confirm, refute, or re-scope (never to copy). The 86 raw findings were deduplicated by a merge agent applying the popover review's category-attribution rule (user-visible misbehavior → BUG regardless of reporting dimension; teardown hygiene → LIFE; i18n-rooted a11y → A11Y), yielding 50 canonical items. Every canonical item was then adversarially verified by 3 independent verifiers with disjoint lenses — refutation (actively try to disprove against source), reproduction/impact (trace the concrete runtime scenario, consulting CDK/Angular/RxJS internals in `node_modules`: `focus-monitor.d.ts` for the private-field claim, `overlay-module.mjs` for the disposal guards, RxJS `interval` semantics, `@koobiq/design-tokens` for token resolution), and severity & citation audit (every `file:line` re-opened, severities calibrated against the shared ladder). Verdicts were combined by majority vote: 0 of 50 items were refuted outright, 8 claims were materially corrected (§3, "Corrected on verification"), 4 severity downgrades were applied by majority (including two claimed P1s), and 4 minority severity dissents were recorded and disclosed. One canonical item was a deliberate non-finding: the popover review's P1 scroll-subscription leak was checked against the tooltip chain and dispositioned as not applicable, leaving 49 actionable findings (0×P0, 4×P1, 16×P2, 29×P3). Grades in §2 derive from each dimension's P1 count and severity tail, with modifiers for systemic patterns and verified strengths, mirroring the popover review's rubric.
