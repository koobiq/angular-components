# Koobiq `dynamic-translation` Component — Code Review & Improvement Plan

> Scope: `packages/components/dynamic-translation` (component + slot directive + helper, Jest spec and its DOM snapshots, user guides, examples stubs, API guard report, docs-examples, dev app) · Commit `b665e503` · 2026-08-28
> Generated by a multi-dimension review (architecture, correctness, public API/types, templates, tests, docs) with manual verification of every finding against the source, the shipped examples, `tsconfig.json`, the API guard report and executable transcriptions of the parser. 11 findings confirmed (P0×0, P1×2, P2×4, P3×5); 6 candidate findings refuted during verification (see Appendix A). This document is a review + roadmap; no source is modified by it.

---

## 1. Executive Summary

`dynamic-translation` is a 191-line, style-free package (`dynamic-translation.ts`) that lets a translatable string carry component slots: `KbqDynamicTranslation` splits `text` on a `[[slotName:context]]` grammar, `KbqDynamicTranslationSlot` supplies the `TemplateRef` for each name, and `KbqDynamicTranslationHelper` is an escape hatch that builds those slots as raw DOM elements for callers who have no template to give. It has **no in-repo consumers** — the only call sites are the two shipped examples, the dev app and the SSR dev app — so every defect below is aimed at external consumers, and none of it is caught by another package's test suite.

- **The parser interpolates slot names straight into a `RegExp` source with no escaping** (`dynamic-translation.ts:104`), and then destructures the match as `[full, name, context]` (`:109`) — an assumption that the interpolated names contribute exactly zero capture groups. A name containing `(` shifts every group index, so one slot named `x(1)` silently hands `undefined` as the context to an *unrelated* slot named `y`; a name containing `[` or a trailing `\` throws `SyntaxError` from inside a `computed()`, taking the whole view down; and a name containing `.`, `+`, `|` or `$` quietly matches the wrong text or nothing at all. All four behaviours were reproduced against a line-for-line transcription of `parseSlots` (DTR-BUG-01).
- **The helper only works for its first render.** `replaceSlots()` is scheduled with `afterNextRender` in the constructor (`:172-174`), which Angular documents as running "once" — yet `text` and `slots` are `input.required` signals (`:162, 164`). Rebinding either — the locale-switch case the component exists for — renders fresh `<span data-slot-name>` placeholders that are never substituted, while the elements from the first pass stay orphaned in the DOM because `nativeElement.replaceWith()` (`:188`) is invisible to Angular's node bookkeeping (DTR-BUG-02).
- **The helper stands outside Angular's security and rendering model.** `renderer.createElement(tag)` (`:182`) and `renderer.setAttribute(key, value)` (`:186`) accept any tag and any attribute name from `KbqDynamicTranslationHelperSlot` with no allow-list; neither `Renderer2` method applies a sanitizer (`@angular/platform-browser/fesm2022/dom_renderer.mjs:536, 588`), so `tag: 'script'` or `key: 'onerror'` reach the DOM verbatim — the one thing Angular's template compiler exists to prevent. The same method emits the literal string `"null"` whenever a slot has no context (DTR-ARCH-01, DTR-BUG-03).
- **Tests are 11 cases, 9 of them DOM snapshots, and none of them touch the helper.** `KbqDynamicTranslationHelper` — 55 of the file's 191 lines — has zero coverage; the snapshots are coupled to `kbq-link`'s host classes (`__snapshots__/dynamic-translation.spec.ts.snap:9-16`), so an unrelated link change breaks this package; and there is no metacharacter case, no e2e fixture and no Playwright spec (the umbrella review already lists the package under TEST-19, `REVIEW.md:341`) (DTR-TEST-01).

Genuine strengths worth preserving: the *design* is the right one — a pure `computed()` over `text()` and `slots()` (`:88-90`) with correct signal-dependency tracking through each slot's `name()` (`:97`), so the primary component re-parses exactly when it should and nothing else; text chunks go through `{{ }}` interpolation (`:70`) rather than `innerHTML`, so the translation string itself carries no injection surface; unknown slot markers are deliberately left as literal text and there is a test proving it (`dynamic-translation.spec.ts:149-157`); the package is fully signal-based, `OnPush`, standalone, with an NgModule retained for legacy consumers, and it correctly ships no SCSS at all, because it renders nothing of its own. The defects are concentrated in two places — the regex construction and the `KbqDynamicTranslationHelper` escape hatch — and both are self-contained enough to fix without touching the design.

## 3. Prioritized Findings (deduplicated, verified)

### P0 — Release blockers

None.

### P1 — High

**DTR-BUG-01 · Slot names are interpolated into the `RegExp` source unescaped, and the match is destructured positionally** — `dynamic-translation.ts:96-124`, principally `:104` and `:109`.
`parseSlots` builds its scanner as ``new RegExp(`\\[\\[(${Object.keys(slotTemplatesByName).join('|')})(?::(.+?))?\\]\\]`, 'g')`` (`:104`), then reads the result as `const [slotMatch, slotName, slotText] = match` (`:109`) — i.e. it assumes the interpolated names contribute exactly two capture groups in total, its own. `name` is a plain `input.required<string>()` (`:49`) with no documented character restrictions (`dynamic-translation.en.md:7` describes `slotName` only as "the key of the registered component"), so nothing enforces that assumption. Four distinct failure modes follow, all reproduced against a line-for-line transcription of `parseSlots`:
*(1) Hard crash.* A name containing `[` (`\[\[(a[)(?::(.+?))?\]\]` → "Unterminated character class") or ending in `\` ("Unterminated group") makes the `RegExp` constructor throw. The constructor runs inside `parsedSlots` (`:88-90`), a `computed()` read from the template (`:64`), so the `SyntaxError` surfaces during change detection and the entire view fails to render — not just this component.
*(2) Cross-slot context corruption.* With names `['x(1)', 'y']` the source becomes `\[\[(x(1)|y)(?::(.+?))?\]\]`. Against `[[y:CTX]]` the match array is `["[[y:CTX]]", "y", null, "CTX"]`, so `slotText` reads position 2 — `null`/`undefined` — while the real context sits at position 3. **One slot with parentheses in its name silently destroys the context of every other slot in the same component**, and the caller gets an empty render with no error at all.
*(3) Wrong-name matching.* `(bold)` as a name yields `slotName === 'bold'` for `[[bold:CTX]]` but `slotText === 'bold'` (the inner group again); `a(b)` yields `slotName === 'ab'`, which then misses `slotTemplatesByName` (`:119`) and renders nothing, deleting the marker from the output.
*(4) Quiet over/under-matching.* `.` in a name matches any character, so a dotted i18n key such as `errors.notFound` also matches `[[errorsXnotFound:C]]`; `+`, `*`, `?` behave as quantifiers; `$` and `|` make the name unmatchable or split it. None of these produce a diagnostic.
**Fix:** escape each name before interpolation — `const escape = (s: string) => s.replace(/[.*+?^${}()|[\]\\]/g, '\\$&')` — and sort the keys by descending length before `join('|')` so a longer name always wins its prefix. Switch the two capture groups to *named* groups (`(?<name>…)` / `(?<context>…)`) and read `match.groups!.name` / `match.groups!.context` instead of positions, which makes the parse immune to any future group added to the alternation. Guard the construction so a still-invalid name degrades to "no slots" rather than throwing out of a `computed()`. Add Jest cases for each of the four modes above — a name with `(`, a name with `[`, a name with `.`, and a two-slot fixture where only one name carries a metacharacter (that last one is the regression guard for mode 2) — asserting on `textContent`, not on a snapshot.

**DTR-BUG-02 · `KbqDynamicTranslationHelper` substitutes its placeholders exactly once, so any input change silently breaks it** — `dynamic-translation.ts:162-190`, principally `:172-174` and `:188`.
The helper's only substitution pass is `afterNextRender(() => { this.replaceSlots(); })` registered in the constructor (`:172-174`). Angular's own API documentation for that hook reads "Use `afterNextRender` to read or write the DOM once" (`@angular/core/index.d.ts:2448`) — it does not repeat. But `text` and `slots` are `input.required` signals (`:162, 164`), and `slots` even has a dedicated `effect()` rebuilding `slotsByName` on every change (`:167-170`), so the class is explicitly written for inputs that change. When they do, `KbqDynamicTranslation` re-parses, `@for` re-instantiates the slot templates, and a fresh `<span #replaceableSlotContainer>` (`:146-150`) is rendered — which nothing ever replaces. The user sees the slot content vanish. The residue is worse than a plain disappearance: substitution is performed with `nativeElement.replaceWith(elementToRender)` (`:188`), a raw DOM call Angular knows nothing about, so when the original embedded view is later destroyed Angular's `nativeRemoveNode` calls `removeChild` on a node whose parent is already `null` (`@angular/core/fesm2022/debug_node.mjs:5937-5939` → `dom_renderer.mjs:567-569`, `oldChild.remove()`), which is a no-op — the element from the *first* pass is never removed either. This is exactly the locale-switch scenario the package is named for: swap the translated `text` and the helper stops working.
**Fix:** replace the one-shot hook with a reactive one — an `effect()` that reads `this.replaceableSlotContainers()` (a signal query, so it re-runs when the placeholder set changes) and performs the substitution, or `afterEveryRender` if the DOM read must stay post-render. Do the substitution through `Renderer2` so Angular keeps ownership: `renderer.insertBefore(renderer.parentNode(nativeElement), elementToRender, nativeElement)` followed by `renderer.removeChild(parent, nativeElement)`, never `Element.replaceWith`. Better still, stop substituting and render the element from the template instead — `<ng-container *ngComponentOutlet>` or a one-line `@switch` over the supported tags removes the entire placeholder dance. Cover with a Jest case that binds the helper, asserts the rendered tag, then calls `setInput('text', …)` and asserts the *new* content — the current suite would pass against the broken code because it never instantiates the helper at all (DTR-TEST-01).

### P2 — Should fix

**DTR-ARCH-01 · The helper builds DOM with an unrestricted tag and attribute set, outside Angular's sanitizers and outside its node ownership** — `dynamic-translation.ts:32-37, 177-190`; example at `packages/docs-examples/components/dynamic-translation/dynamic-translation-with-dynamic-component-creation/dynamic-translation-with-dynamic-component-creation-example.ts:29-49`.
`replaceSlots()` takes `tag` and `attributes` verbatim off `KbqDynamicTranslationHelperSlot` (`:32-37`) and feeds them to `renderer.createElement(tag)` (`:182`) and `renderer.setAttribute(elementToRender, key, value)` (`:186`). Neither `Renderer2` method sanitizes: `DefaultDomRenderer2.createElement` is `this.doc.createElement(name)` and `setAttribute` is `el.setAttribute(name, value)` (`node_modules/@angular/platform-browser/fesm2022/dom_renderer.mjs:536, 588`). Angular's security model lives in the *template compiler* — `[innerHTML]`, `[href]`, `[style]` are routed through `DomSanitizer` by security context — and this code path bypasses all of it by construction. A `slots` array carrying `{ tag: 'script' }`, or `{ tag: 'img', attributes: [{ key: 'onerror', value: '…' }] }`, or `{ tag: 'a', attributes: [{ key: 'href', value: 'javascript:…' }] }` produces exactly what it says, and a `<script>` inserted through `replaceWith` — a DOM insertion, not `innerHTML` — does execute. The mitigating fact is that `slots` is developer-supplied rather than read from the translation string (the *string* only reaches a text node via `renderer.createText`, `:184`, which is safe). The aggravating fact is that this is a component sold for rendering localization data, where the "developer-supplied" boundary is exactly where teams put content loaded from a translation service. Separately, the shipped example demonstrates the escape hatch without any teardown: it calls `createComponent` + `applicationRef.attachView` inside an `effect()` (`…-example.ts:30-46`) and never calls `detachView` or `componentRef.destroy()`, so the created view stays attached to `ApplicationRef` and is change-detected on every tick for the lifetime of the app, even after the host example is destroyed.
**Fix:** constrain the surface. Type `tag` as a union of the tags the helper is meant to support (`'b' | 'strong' | 'i' | 'em' | 'a' | 'span'` covers every documented use) rather than `string`, and reject anything else in dev mode with a `RuntimeError`; refuse attribute keys matching `/^on/i` and run `href`/`src` values through `DomSanitizer.sanitize(SecurityContext.URL, …)`. Document in the class JSDoc that `slots` is a trust boundary. Fix the example to keep the `ComponentRef` and call `destroy()` in a `DestroyRef.onDestroy` callback, and move the `createComponent` call out of the `effect()` (it currently re-creates on every effect run). If the helper's remit is genuinely "arbitrary DOM", the honest move is to delete it in favour of `*ngComponentOutlet`, which is sanitized and lifecycle-managed for free.

**DTR-BUG-03 · A context-less slot makes the helper render the literal string `"null"`; a list context flattens to a comma string** — `dynamic-translation.ts:120, 149, 180, 184`.
The placeholder writes its payload into an attribute: `[attr.data-slot-content]="slot.content || content"` (`:149`). When the marker carries no context — `[[bold]]`, which the parser explicitly supports and which has its own test (`dynamic-translation.spec.ts:85-93`) — `content` is `undefined` (`:120` propagates the unmatched group), and if `slot.content` is unset the binding value is `undefined`. Angular removes an attribute whose bound value is `== null` (`@angular/core/fesm2022/debug_node.mjs:9518-9520`), so `getAttribute('data-slot-content')` (`:180`) returns `null` — the non-null assertion `!` on that line asserts a fact that is false — and `renderer.createText(null)` (`:184`) resolves to `document.createTextNode(null)` (`dom_renderer.mjs:554-556`), whose spec-mandated coercion yields the four-character string `null`. So `<kbq-dynamic-translation-with-dynamic-component-creation text="[[bold]]" [slots]="[{name:'bold',tag:'b'}]" />` renders `<b>null</b>` on screen. The same round-trip through an attribute destroys list contexts: `[[items:(a,b,c)]]` gives `content` the array `['a','b','c']` (`:120`), which Angular stringifies to `"a,b,c"` for the attribute, so the helper can only ever render a comma-joined string where the primary component renders a real list.
**Fix:** stop round-tripping the payload through DOM attributes. Keep the parsed context in a component field keyed by placeholder index (the `@for` already has `$index`) and read it directly in `replaceSlots()`, which removes the `null` coercion, the two false `!` assertions (`:179-180`) and the array flattening in one move. If the attribute must stay, guard it: `renderer.createText(slotContent ?? '')`. Add Jest cases for `[[name]]` (asserts empty, not `"null"`) and for a list context through the helper.

**DTR-BUG-04 · With no declared slots the alternation collapses to `()` and starts eating markers out of the text** — `dynamic-translation.ts:96-104`.
`slotTemplatesByName` is empty whenever a `<kbq-dynamic-translation>` has no `*kbqDynamicTranslationSlot` children — a legitimate state during `@if`-gated slots, or while `contentChildren` is still resolving. `Object.keys({}).join('|')` is `''`, so line 104 produces `\[\[()(?::(.+?))?\]\]`: an alternation of one empty branch, which matches the empty string. Verified consequences: `'a [[]] b'` parses to `text('a ') + slot(template: null) + text(' b')`, and `'a [[:ctx]] b'` parses to `text('a ') + slot(template: null, $implicit: 'ctx') + text(' b')`. In both cases the `[[…]]` run is consumed and, because `slot.template` is `null`, `*ngTemplateOutlet` renders nothing (`:67`) — the characters are silently deleted from the user's string. This directly contradicts the component's documented and tested behaviour for unrecognised markers: with at least one slot declared, `[[undefinedSlot:…]]` is preserved verbatim as text, and there is a passing test asserting exactly that (`dynamic-translation.spec.ts:149-157`, snapshot at `__snapshots__/dynamic-translation.spec.ts.snap:140-148`). The invariant holds in every case except the one nobody wrote a test for.
**Fix:** short-circuit before building the regex — `if (!Object.keys(slotTemplatesByName).length) return text ? [{ type: 'text', text, template: null }] : [];` — which is also the cheaper path for the common "plain string" case. Add a Jest case with a host that declares no slots and a `text` containing `[[]]`, `[[:x]]` and `[[foo:bar]]`, asserting `textContent` is unchanged.

**DTR-TEST-01 · The helper is entirely untested and the parser is tested through `kbq-link`-coupled DOM snapshots** — `dynamic-translation.spec.ts` (158 lines, 11 cases), `__snapshots__/dynamic-translation.spec.ts.snap` (199 lines, 9 snapshots); missing `e2e.ts`, `e2e.playwright-spec.ts`.
Three separate gaps. *(1) Zero helper coverage.* `KbqDynamicTranslationHelper` is 55 of the file's 191 lines (`:139-191`) and the spec never imports it — only `KbqDynamicTranslation` and `KbqDynamicTranslationModule` (`:6-7`). DTR-BUG-02 and DTR-BUG-03 are both in that untested half, which is why they have survived since the package landed. *(2) Snapshot monoculture with a foreign dependency.* 9 of the 11 cases end in `toMatchSnapshot()` on a `nativeNode`, so they assert a whitespace-heavy DOM dump rather than a parse result — and the host imports `KbqLinkModule` (`:27, 30`), so `kbq-link`'s host classes and `tabindex` are baked into this package's baselines (`…snap:9-16, 105-112, 172-179`). A change in the link component breaks dynamic-translation's suite, and conversely a real parser regression that happens to produce plausible DOM is approved with `-u` without anyone reading it. *(3) No metacharacter or real-browser coverage.* There is a "special characters" case (`:117-127`) but it varies the *context*, never the slot *name* — the entire DTR-BUG-01 surface is untested. There is no `e2e.ts` and no Playwright spec; the umbrella review already lists the package among the seven without a visual spec (`docs/review/REVIEW.md:341, 650`). Minor hygiene in the same file: `createComponent`'s `providers` parameter (`:9-13`) is never used by any case, `NoopAnimationsModule` (`:11`) is imported for a package with no animations, every case calls `fixture.detectChanges()` after `autoDetectChanges()` has already been enabled (`:16`), and the test host is needlessly `export`ed (`:41`).
**Fix:** convert the parse assertions to `textContent`/`querySelector` checks so they state the expected parse rather than the expected DOM, and keep snapshots only for the two structural cases (multi-slot, list slot) where the shape is the point. Replace `KbqLinkModule` in the host with plain `<a>`/`<strong>` so the baselines stop depending on another package. Add a `describe` block for `KbqDynamicTranslationHelper` covering: initial render of `tag` + attributes, a `setInput('text', …)` re-render (DTR-BUG-02), a context-less slot (DTR-BUG-03), and a list context. Add `e2e.ts` + `e2e.playwright-spec.ts` with one fixture showing a link slot and a list slot inline in a paragraph — the value of this component is that slots flow inline with the surrounding text, which JSDOM cannot verify. Baselines only through `yarn run e2e:docker:update-snapshots`.

### P3 — Nice to have / hygiene

**DTR-BUG-05 · The `[[name:context]]` grammar has no escaping and several inconsistent edges** — `dynamic-translation.ts:104, 110, 120`.
Five verified edges, none documented. (1) List items are not trimmed: `[[l:(a, b)]]` yields `['a', ' b']`. (2) An empty list is not a list: `[[l:()]]` fails the `listString` truthiness check at `:120` and falls through to the raw string `'()'`, so the slot receives a string where every other list case gives an array — a type change the consumer's `@for` cannot survive. (3) A list item cannot contain a comma and there is no escape for one. (4) A context cannot contain `]]`: `[[a:p]]q]]` closes at the first pair, leaving `q]]` as trailing text. (5) `.` does not match newlines and no `s` flag is set (`:104`), so a marker split across lines — routine in translation files with wrapped strings — is not recognised at all.
**Fix:** trim list items (`listString.split(',').map((s) => s.trim())`); make `()` yield `[]` by testing `listMatch !== undefined` instead of `listString` truthiness; add the `s` flag to the scanner; and document the two hard limits (no `]]` in a context, no comma inside a list item) in `dynamic-translation.en.md` / `.ru.md` next to the grammar description at line 7. If escaping is wanted, `\]` is the conventional choice and costs one `replace` in the context branch.

**DTR-API-01 · A `@docs-private` component is published, documented, exampled — and named like an example** — `dynamic-translation.ts:136-140, 162-164`, `tools/public_api_guard/components/dynamic-translation.api.md:22-33`, `examples.dynamic-translation.en.md:1-3`, `apps/docs/src/app/structure.ts:542-553`.
`KbqDynamicTranslationHelper` carries `@docs-private` (`:136-138`), which is the repo's marker for "not part of the documented surface". Everything else about it says the opposite: it is exported through `index.ts`, it appears in the API guard as `// @public` (`…api.md:22-33`) — `@docs-private` does not strip a member from the report — it is imported by name in a shipped example, it is the subject of the entire Examples tab (`examples.dynamic-translation.en.md:1-3`, `.ru.md:1-3`), and that tab actually renders because `structure.ts:552` sets `hasExamples: true`. Its two inputs `text` and `slots` have no JSDoc at all, so both are `// (undocumented)` in the report (`…api.md:25-28`), leaving the *only* documented-but-undocumented public component in the package. Its selector, `kbq-dynamic-translation-with-dynamic-component-creation` (`:140`), is the name of a docs example rather than the name of a component — no other selector in the library describes its own demo.
**Fix:** decide which it is. If it is public: drop `@docs-private`, rename the selector to something a consumer would type (`kbq-dynamic-translation-dom`), add JSDoc to the class and both inputs, and document it in the guides beside the template-based form. If it is internal: move it under `packages/components/dynamic-translation/` as a non-exported symbol, replace the example with one that uses the public API, and remove the Examples tab entry. Either way the change touches the API report — `yarn run build:components` then `yarn run approve-api` (build first; the guard reads `dist/*.d.ts`).

**DTR-API-02 · Type-surface debt: a committed extractor warning, `TemplateRef<any>`, no template context guard, and one type that is false at runtime** — `dynamic-translation.ts:22-27, 54, 109`, `tools/public_api_guard/components/dynamic-translation.api.md:13, 63`, `tools/check-public-api-any/baseline.json:18`.
Four items. (1) `KbqDynamicTranslationParsedSlot` (`:22-27`) is referenced by the `protected` `parsedSlots` signal but never exported, so the checked-in API report carries a live `ae-forgotten-export` warning (`…api.md:13`) — a warning that has been committed rather than resolved. (2) `templateRef = inject(TemplateRef)` (`:54`) infers `TemplateRef<any>` (`…api.md:63`), the single `any` this package contributes to the untyped-surface ratchet (`baseline.json:18`). (3) `KbqDynamicTranslationSlot` declares no `static ngTemplateContextGuard`, so under this workspace's `strictTemplates: true` (`tsconfig.json:117`) the `let context` in `*kbqDynamicTranslationSlot="'x'; let context"` is typed `any` — the docs' own snippets (`dynamic-translation.en.md:13, 18-22`) iterate `context` with `@for` and get no checking whatsoever. (4) At `:109`, `slotText` is destructured out of a `RegExpExecArray` and is therefore typed `string`, but is `undefined` for every context-less marker; the compiler then permits `.exec(slotText)` at `:110` against a signature that requires a `string`. `noUncheckedIndexedAccess` is not enabled (only `strictNullChecks`, `tsconfig.json:21`), so nothing catches it.
**Fix:** export `KbqDynamicTranslationParsedSlot` (or make `parsedSlots` `private` and expose nothing) to clear the warning; type the injection as `inject<TemplateRef<{ $implicit: string | string[] }>>(TemplateRef)`; add `static ngTemplateContextGuard(_dir: KbqDynamicTranslationSlot, _ctx: unknown): _ctx is { $implicit: string | string[] } { return true; }` so the docs' snippets actually type-check; and widen the destructure to `string | undefined` explicitly (moving to named groups per DTR-BUG-01 does this naturally, since `match.groups` is typed as possibly-`undefined` per key). Items 1 and 2 change the API report — fold them into the DTR-API-01 `approve-api` cycle so the report churns once.

**DTR-DOC-01 · The grammar's constraints are undocumented, and the dev app's locale selector is inert on the one component that is about locales** — `dynamic-translation.en.md:7`, `dynamic-translation.ru.md:7`, `packages/components-dev/dynamic-translation/main.ts:5-9`, `template.html:2`.
The guides define the syntax in a single sentence (`…en.md:7`, `…ru.md:7`) and show two snippets. Nothing states that a slot name may not contain regex metacharacters (DTR-BUG-01), that a context may not contain `]]` or a newline, that list items may not contain a comma, or that an unrecognised marker is left as literal text — the last being a genuinely useful guarantee that consumers cannot discover from the docs. Neither guide shows the thing the component's name promises: how `text` is fed from `KbqLocaleService`, and what a consumer must provide for it (`KBQ_LOCALE_SERVICE` is an `InjectionToken` with no factory, `core/locales/locale-service.ts:95`, so `kbqLocaleServiceProvider()` is mandatory). The dev app demonstrates the gap: `template.html:2` renders `<dev-locale-selector />`, but `main.ts:5-9` provides only `provideAnimations()`, so `inject(KBQ_LOCALE_SERVICE, { optional: true })` resolves to `null` and the harness renders the fallback `<div>No provider for KBQ_LOCALE_SERVICE</div>` (`packages/components-dev/locale-selector.ts:11, 19-21, 27`) instead of a locale picker. Sibling dev apps do this correctly — `packages/components-dev/actions-panel/main.ts:30` calls `kbqLocaleServiceProvider()`. Neither shipped example varies with locale either, so `yarn run dev:dynamic-translation` cannot demonstrate a re-translation at all.
**Fix:** add `kbqLocaleServiceProvider()` to `packages/components-dev/dynamic-translation/main.ts`, and give the dev app a second example whose `text` is read from the locale service so switching locales visibly re-parses (this is also the manual acceptance test for DTR-BUG-02). In both guides, add a short "Syntax rules" list under the grammar sentence covering the four constraints above plus the literal-text fallback, and a snippet showing `[text]="localeService.data().…"` with the required provider.

**DTR-STYLE-01 · Small template and parser noise** — `dynamic-translation.ts:64, 67, 70, 110, 111`.
Five items, none behavioural. (1) `:111` writes `text.substring(lastIndex, +match.index)` — a unary plus on `RegExpExecArray.index`, which is already a `number`. (2) `:110` constructs `new RegExp('^\\((.*?)\\)$', 'g')` inside the match loop: a fresh object per match for an anchored pattern, and the `g` flag is meaningless on an anchored single-`exec` regex. Hoist it to a module constant without the flag. (3) `:70` wraps a bare interpolation in `<ng-container>{{ slot.text }}</ng-container>`; the wrapper renders nothing and contributes the blank lines that make the snapshots hard to read (`…snap:4-8`). (4) `:67` uses the legacy `*ngTemplateOutlet` micro-syntax; the umbrella review tracks this as ARCH-29 (`docs/review/REVIEW.md:229`), and `<ng-container [ngTemplateOutlet]="…" [ngTemplateOutletContext]="…" />` is the form used elsewhere in the repo. (5) `:64` tracks the `@for` by `$index`, so any `text` change destroys and rebuilds every slot's embedded view — a slot containing a dropdown, a focused button or any stateful component loses that state on an unrelated text edit. Tracking a stable key (slot name plus occurrence ordinal) would preserve unchanged slots.
**Fix:** drop the `+`, hoist the list regex to a module-level `const LIST_CONTEXT = /^\((.*?)\)$/`, delete the `<ng-container>` wrapper, convert `*ngTemplateOutlet` to the bracket form, and give each parsed slot a stable `key` field to track by. All five are mechanical and can ride along with the DTR-BUG-01 parser rewrite.

## 4. Recommended Remediation Phases

**Phase 1 — Make the parser trustworthy.**
IDs: DTR-BUG-01, DTR-BUG-04, DTR-BUG-05, DTR-STYLE-01. Escape the interpolated names, sort them longest-first, move to named capture groups, short-circuit the empty-slot case, fix the list-context edges, and take the template/parser noise along in the same diff. Nothing else depends on this, and it is the only finding that can crash a consumer's view. Land it with the metacharacter Jest cases described in DTR-BUG-01 — the existing suite would pass unchanged against every one of these bugs, so new tests are the deliverable, not an afterthought.

**Phase 2 — Fix or retire the helper.**
IDs: DTR-BUG-02, DTR-BUG-03, DTR-ARCH-01. Decide first whether `KbqDynamicTranslationHelper` should exist: `*ngComponentOutlet` covers the documented use case with sanitization and lifecycle management included. If it stays, make the substitution reactive, route it through `Renderer2`, stop round-tripping the payload through a DOM attribute, and constrain `tag`/`attributes`. Fix the shipped example's attached-view leak in the same change. Depends on Phase 1 only in that both touch the same file.

**Phase 3 — Close the test gap.**
IDs: DTR-TEST-01. Decouple the snapshots from `kbq-link`, convert the parse cases to explicit assertions, add the helper `describe` block, and add the `e2e.ts` + Playwright pair that proves slots flow inline with their surrounding text. In practice the Phase 1 and Phase 2 regression cases land with their fixes; this phase is the remaining structural work plus the visual baseline (Docker only).

**Phase 4 — Settle the public surface and the docs.**
IDs: DTR-API-01, DTR-API-02, DTR-DOC-01. Resolve the `@docs-private`-versus-published contradiction for the helper, clear the `ae-forgotten-export` warning, add the template context guard and the missing JSDoc, then document the grammar's rules and wire `kbqLocaleServiceProvider()` into the dev app. One `yarn run build:components && yarn run approve-api` cycle covers the whole phase; run it last so the report churns once.

## Appendix A — Review Methodology

Findings were gathered by reading the complete package — all four source/config files, the guides, the examples stubs, the Jest spec and every one of its nine committed snapshots — then cross-checking each candidate against four independent sources: the workspace compiler settings (`tsconfig.json:21, 114-118`), the API guard report and the untyped-surface ratchet (`tools/public_api_guard/components/dynamic-translation.api.md`, `tools/check-public-api-any/index.ts` + `baseline.json:18`), the Angular runtime sources in `node_modules` for every claim about `Renderer2`, attribute binding and `afterNextRender` semantics, and every reference to the package found by grep across the repository (two docs examples, the dev app, the SSR dev app, `structure.ts`, `seo-descriptions.ts` — and no library consumers at all). Because the package has no consumers, the usual strongest evidence (consumer workarounds in the tree) was unavailable; in its place, the parser's four failure modes were established by transcribing `parseSlots` (`dynamic-translation.ts:92-133`) line-for-line into a standalone script and running seventeen inputs through it, and every DOM-level claim was traced to the Angular source rather than inferred.

Refuted during verification:
- **"The package violates the AGENTS.md structure by shipping no `public-api.ts` and naming its NgModule file `module.ts`"** — refuted as a defect. Ten packages ship no `public-api.ts` (`actions-panel`, `clamped-text`, `content-panel`, `dynamic-translation`, `inline-edit`, `overflow-items`, `resizer`, `skeleton`, `time-range`, `username`) and twelve name the file `module.ts`; the overlap is near-total. This is a newer in-repo convention applied consistently, not drift in one package.
- **"Missing `dynamic-translation-tokens.scss`, `_dynamic-translation-theme.scss` and a component stylesheet"** — refuted. The component renders no chrome: it emits text nodes and consumer-authored projected templates, which must inherit the surrounding typography and colour to flow inline correctly. There is nothing to tokenize, and adding an empty theme mixin would be noise. Contrast the inventory note that a missing theme file is only a defect when the colours have to come from somewhere.
- **"The translation string is an HTML-injection vector"** — refuted for `KbqDynamicTranslation`. Text chunks are rendered with `{{ slot.text }}` (`:70`), which Angular escapes, and the slot payload reaches the DOM as a `createText` node (`:184`). No `innerHTML`, no `bypassSecurityTrust*`, anywhere in the package. The genuine injection surface is the developer-supplied `tag`/`attributes` on the *helper*, which is filed separately as DTR-ARCH-01 with an explicit note on where the trust boundary sits.
- **"Prefix-colliding slot names resolve to the wrong template, because `join('|')` produces an unordered alternation"** — refuted as stated. JavaScript alternation backtracks: with names `['link', 'linkExtended']`, `[[linkExtended:v]]` correctly resolves to `linkExtended` (verified). Longest-first sorting is still worth adding as defence-in-depth, but it is folded into DTR-BUG-01 rather than filed as its own defect.
- **"The `g` flag on `slotSelector` leaves a stale `lastIndex` between parses"** — refuted. The regex is constructed fresh inside `parseSlots` on every invocation (`:104`), so `lastIndex` always starts at `0`. The classic stale-`lastIndex` bug requires a hoisted or module-level regex, which this code does not have. (Ironically, the DTR-STYLE-01 suggestion to hoist the *list* regex is safe only because that one is anchored and would lose its `g` flag in the same move.)
- **"Renaming a slot at runtime leaves the parser holding the old template"** — refuted. `parseSlots` reads each slot's `name()` signal (`:97`) from inside the `computed()` (`:88-90`), so a name change is a tracked dependency and invalidates the parse. The reactivity of the primary component is correct; the reactivity defect is confined to the helper (DTR-BUG-02).

Corrected on verification:
- **DTR-BUG-01** was first drafted as a P3 hygiene item ("slot names should be escaped before interpolation"). Executing the transcribed parser changed the picture twice: the `SyntaxError` path throws out of a `computed()` read during change detection, and the capture-group shift makes *one* malformed name corrupt the context of *other*, well-formed slots. Both are silent-or-fatal with no diagnostic, which moved it to P1 and made it the lead of the executive summary.
- **DTR-BUG-04** was first drafted as "any unrecognised marker is silently swallowed". Verification refuted the general claim — with at least one slot declared, `[[foo:bar]]` is preserved verbatim, and `dynamic-translation.spec.ts:149-157` already asserts it. Only the zero-slot degenerate case is broken, so the finding was narrowed to that case and filed at P2 rather than P1.
- **DTR-BUG-02** was first drafted as "content disappears after an input change". Tracing `nativeRemoveNode` (`@angular/core/fesm2022/debug_node.mjs:5937-5939`) showed the substituted element is *also* never removed, because `replaceWith` had already detached the node Angular tracks — so the observable symptom is stale content plus an empty placeholder, not a clean disappearance. The wording and the Phase 2 acceptance assertion were both changed to cover the residue.
