# Ревью компонента: `inline-edit`

> Область: `packages/components/inline-edit` (компонент и 3 директивы, шаблон, SCSS и токены, Jest-спека со снапшотом, e2e-фикстуры и Playwright-спека, руководства пользователя, гайды примеров, отчёт API guard, dev-приложение, 18 docs-примеров) · Коммит `b665e503` · 2026-08-28
> Подготовлено многомерным ревью (архитектура, RxJS и жизненный цикл, корректность, доступность, производительность, публичный API и типы, шаблоны и стили, тесты, документация) с ручной проверкой каждой находки по исходникам, по примерам внутри репозитория, по реальному набору правил axe-core, который подключает `jest-axe`, и по конфигурации компилятора и тестов воркспейса. Подтверждено 16 находок (P0×1, P1×4, P2×6, P3×5); 8 кандидатов отклонены в ходе проверки (см. Приложение A). Документ — это ревью и дорожная карта; исходный код им не изменяется.

## 1. Резюме

`KbqInlineEdit` ([inline-edit.ts](../../packages/components/inline-edit/inline-edit.ts), 736 строк) — один из самых «поведенческих» компонентов библиотеки: он проецирует шаблон просмотра и шаблон редактирования, открывает второй в CDK-оверлее шириной по первому, обрабатывает сохранение и отмену с клавиатуры, мышью и по Tab, связывает соседние inline-edit'ы в цепочку по Tab и показывает тултип валидации, предварительно проскроллив невалидный контрол в зону видимости. В нём 11 инпутов, 3 аутпута, 47 Jest-кейсов и 7 пар Playwright-скриншотов, и его уже 10 раз чинили коммитами `fix(inline-edit)`. Внутри `packages/` у него нет потребителей — единственные места использования это его собственные 18 docs-примеров и e2e-фикстуры, — поэтому его контракт пока никем в репозитории не проверен на прочность.

- **Единственный блокер релиза — автоматически детектируемое нарушение доступности в собственном шаблоне компонента.** Оверлей режима редактирования рендерит два «часовых» с одновременными `aria-hidden="true"` и `tabindex="0"` ([inline-edit.html:46, 92](../../packages/components/inline-edit/inline-edit.html)). Ровно это запрещает включённое по умолчанию правило axe-core `aria-hidden-focus` (serious, `wcag2a`/`wcag412`/`wcag131`), и поскольку focus trap панели явно отключён (`[cdkTrapFocus]="false"`), пользователь клавиатуры действительно на них попадает: это живые табстопы, которые ничего не озвучивают. AGENTS.md говорит прямо: «It MUST pass all AXE checks», а починить чужой шаблон потребитель не может (IE-A11Y-01).
- **Ничто не сообщает вспомогательным технологиям, что режим просмотра редактируемый.** Хост биндит `tabindex` и восемь классов и ни одного ARIA-атрибута (`inline-edit.ts:147-159`): нет `role`, нет доступного имени, нет `aria-expanded` при открытии оверлея, нет `aria-disabled` в неактивном состоянии. Если контент просмотра интерактивный, хост уходит в `tabindex="-1"`, и единственной точкой входа с клавиатуры становится безымянный визуально скрытый `<div tabindex="0">` (`inline-edit.html:14-19`). Отдельно: `KbqInlineEditMenu` штампует `role="button"` (`inline-edit.ts:113`) на элементе, которому не даёт имени — это провал правила axe `aria-command-name` во всех шести местах использования внутри репозитория (IE-A11Y-02, IE-A11Y-03).
- **`commit()` не выполняет ту валидацию, которую обещает его собственный JSDoc.** `isInvalid()` читает `KbqFormField.invalid`, а это `errorState` (`form-field.ts:262-264`) — закешированный флаг, вычисляемый `ErrorStateMatcher`, то есть `touched || submitted` (`error-state-matcher.ts:59-62`). Помечает контролы как touched только клавиатурный путь (`inline-edit.ts:543`); ни `commit()`, ни кнопка «Сохранить» этого не делают. На нетронутом контроле — а это ровно задокументированный сценарий «селект без рамки, commit по `selectionChange`» (`inline-edit.spec.ts:1416`) — `commit()` видит `errorState === false` и пропускает невалидное значение (IE-BUG-01).
- **Опубликованные руководства описывают дизайн, а не компонент.** На 220 строках `inline-edit.en.md` / `inline-edit.ru.md` не названы ни один из 11 инпутов, 3 аутпутов и 2 публичных методов, и нет раздела `### Keyboard`, хотя в соседних гайдах он есть (`list.en.md:108-112`) — то есть отмена по Escape, сохранение по Enter, Ctrl+Enter в textarea и цепочка по Tab не задокументированы. Хуже того, раздел «Валидация» обещает, что система «показывает сообщение об ошибке… и фокус остаётся в поле»: сообщение появляется только если потребитель передал `[validationTooltip]`, а фокус в поле компонент не возвращает никогда (IE-DOC-01).

Что действительно сделано хорошо и стоит сохранить: компонент полностью построен на сигналах и современном API (`input()`/`output()`/`computed()`/`contentChild()`/`viewChild()`, OnPush, host-объект, без `@HostBinding`); он чист по SSR — инжектит `KBQ_WINDOW` и `DOCUMENT` вместо глобалей и прогоняется через SSR dev-приложение (`packages/components-dev/ssr/module.ts:193`); ARIA-имена кнопок сохранения и отмены берутся из `kbqInjectA11yLocaleConfiguration()` ровно так, как требует AGENTS.md; scroll strategy тултипа валидации переопределена **на уровне экземпляра**, а не через DI, и на это есть спека, доказывающая отсутствие протечки в проецируемые тултипы (`inline-edit.spec.ts:983-1000`); а самые запутанные участки кода снабжены по-настоящему полезными комментариями (`inline-edit.ts:176-184, 397-398, 437-447, 449-450`), которые сделали это ревью заметно дешевле.

## 3. Приоритизированные находки (дедуплицированы, верифицированы)

### P0 — Блокеры релиза

**IE-A11Y-01 · Оверлей редактирования рендерит два элемента с `aria-hidden="true"` и `tabindex="0"` — провал axe по умолчанию и два тупиковых табстопа** — `inline-edit.html:46, 92`, `inline-edit.ts:72-93, 605-624`.
Оба «часовых» для Tab написаны как `<div class="cdk-visually-hidden" aria-hidden="true" kbqFocusRegionItem tabindex="0"></div>`. Правило axe-core `aria-hidden-focus` матчит каждый внешний элемент `[aria-hidden="true"]`, а его проверка `focusable-not-tabbable` собирает табируемые элементы **включая сам узел** (`axe-core/lib/commons/dom/get-tabbable-elements.js`) и падает с impact **serious**, если у любого из них `tabindex >= 0` и нет открытого модального диалога. Правило включено по умолчанию в той версии axe-core, которую репозиторий реально запускает, — 4.12.1 из `node_modules/jest-axe/node_modules/axe-core`, — с тегами `cat.name-role-value`, `wcag2a`, `wcag412`. `jest-axe` в репозитории уже используется (`accordion.spec.ts:1518`, `app-switcher.spec.ts:1780`), то есть до красной сборки не хватает одного ассерта, а AGENTS.md формулирует требование прямо: «It MUST pass all AXE checks». Нарушение не теоретическое. Панель отключает свой focus trap (`[cdkTrapFocus]="false"`, `inline-edit.html:52`), поэтому порядок табуляции внутри оверлея — часовой → контролы панели → часовой, а обработчик часового срабатывает только после того, как `focusin` уже выставил `isFocused` (`inline-edit.ts:75, 86-88`): дизайн **требует**, чтобы фокус туда попадал. Пользователь скринридера попадает на элемент, о котором дереву доступности сказано, что его не существует, ничего не слышит и вынужден нажать Tab второй раз. Обхода у потребителя нет: часовые находятся в собственном шаблоне компонента.
**Fix:** удалить обоих часовых и определять границу на самой панели — навесить `(keydown.tab)`/`(keydown.shift.tab)` на `.kbq-inline-edit__panel` и сравнивать `event.target` с первым/последним табируемым потомком, найденным через CDK `InteractivityChecker` (`isTabbable`), как это делает сам `FocusTrap`; тогда `KbqFocusRegionItem` исчезает вместе со своим экспортом (см. IE-API-01). Если форму с часовыми надо сохранить на короткой дистанции, минимум для прохождения axe — убрать `aria-hidden="true"` у обоих; **не** заменять его на `role="presentation"`/`role="none"`, это триггерит `presentation-role-conflict`. Закрепить ассертом `expect(await axe(overlayContainerElement)).toHaveNoViolations()` **в режиме редактирования**, по образцу `app-switcher.spec.ts:1780`.

### P1 — Высокий приоритет

**IE-A11Y-02 · У режима просмотра нет роли, имени и состояния раскрытия; при интерактивном контенте единственный табстоп — безымянный скрытый div** — `inline-edit.ts:147-159, 285-293`, `inline-edit.html:8-19`.
Host-блок биндит `[attr.tabindex]` и шесть классов, и больше ничего: ни `role`, ни `aria-label`/`aria-labelledby`, ни `[attr.aria-expanded]` по `isEditMode()`, ни `[attr.aria-disabled]` рядом с `kbq-inline-edit_disabled`. Поэтому `<kbq-inline-edit>` в режиме просмотра — это неизвестный элемент, который просто оказался фокусируемым: скринридер зачитывает проецируемый текст и никак не сообщает, что Enter или Space откроют редактор, а когда редактор открывается, не озвучивается вообще ничего. Это WCAG 4.1.2 (Name, Role, Value) плюс 1.3.1 — и здесь важно быть точным: это **суждение**, а не автоматический провал, axe не помечает фокусируемый элемент, у которого просто нет роли, поэтому дефект и дожил до сих пор. Ветка с интерактивным контентом делает не лучше, а хуже. Когда контент просмотра попадает под `interactiveSelectors`, `tabIndex()` возвращает `-1` (`inline-edit.ts:290`), и компонент подставляет якорь фокуса — `<div class="kbq-inline-edit__focus-anchor cdk-visually-hidden" tabindex="0">` (`inline-edit.html:14-19`) — без роли, имени и содержимого. Единственная клавиатурная точка входа превращается в элемент, который вспомогательные технологии могут описать только как «пусто». Нужный механизм в библиотеке уже есть: `KbqA11yLocaleConfiguration` (`core/locales/types.ts:13-38`) содержит ключи `save` и `cancel`, задокументированные именно как принадлежащие inline edit, и компонент уже инжектит конфигурацию (`inline-edit.ts:166`).
**Fix:** повесить семантику виджета на `.kbq-inline-edit__view-content` (`inline-edit.html:9`), а **не** на хост: хост с ролью виджета, содержащий кнопку `kbqInlineEditMenu`, начнёт падать по правилу axe `nested-interactive`, тоже включённому по умолчанию в 4.12.1. Перенести туда `[attr.tabindex]` и добавить `role="button"`, `[attr.aria-expanded]="isEditMode()"`, `[attr.aria-disabled]="disabled() || null"` и `[attr.aria-label]` со значением по умолчанию из нового ключа `edit` в `KbqA11yLocaleConfiguration` плюс инпут-переопределение для потребителей, которым нужно имя конкретного поля. Так же поступить с якорем фокуса (он либо становится тем же элементом, либо получает те же атрибуты) и закрыть каждую ветку Jest-кейсом плюс axe-ассертом из IE-A11Y-01.

**IE-A11Y-03 · `kbqInlineEditMenu` штампует `role="button"` на элементе, которому не даёт имени — axe `aria-command-name` падает во всех местах использования** — `inline-edit.ts:110-125` (роль на `:113`); использования в `inline-edit-menu-example.ts:37-42, 62-69`, `e2e.ts:137-142, 193-198`, `inline-edit.spec.ts:1101-1106, 1311`.
`KbqInlineEditMenu` безусловно добавляет `role: 'button'` на тот элемент, к которому потребитель применил директиву. Правило `aria-command-name` из axe-core 4.12.1 (impact **serious**, теги `wcag2a`/`wcag412`, селектор `[role="link"], [role="button"], [role="menuitem"]`, матчер `no-naming-method-matches`) требует у такого элемента видимого текста, `aria-label`, `aria-labelledby` или `title` и специально матчит элементы без нативного способа именования — а `<i>` именно такой. Все использования в репозитории — это иконочный `<i kbqInlineEditMenu kbq-icon-button="…">` без имени: оба меню в задокументированном примере, три фикстуры в `e2e.ts` и хост спеки. `KbqIconButton` проставляет `[attr.tabindex]` (`icon-button.component.ts:34`), так что элемент действительно достижим и действительно безымянный. Обязательство создаёт библиотека — она штампует роль — и никогда его не выполняет, а её собственная документация учит падающему паттерну. В отличие от IE-A11Y-01 обход у потребителя **есть** (добавить `aria-label` на свой элемент), поэтому это P1, а не P0.
**Fix:** перестать хардкодить роль. Либо убрать `role: 'button'` и требовать применять `kbqInlineEditMenu` к настоящему `<button>`/`kbq-button` (иконочная кнопка и так выглядит как кнопка), либо оставить роль и обеспечить имя: добавить в `KbqInlineEditMenu` инпут `aria-label` со значением по умолчанию из нового ключа `menu` в `KbqA11yLocaleConfiguration` плюс `console.warn` в dev-режиме, когда у хоста не резолвится доступное имя, — по той же схеме, что `list` использует для некорректного `multiple`. Затем добавить `aria-label` двум меню в `inline-edit-menu-example.ts` и трём фикстурам `e2e.ts` и прогнать `axe()` по фикстуре с меню в спеке.

**IE-BUG-01 · `commit()` не выполняет «ту же валидацию, что и обычное сохранение» — нетронутое невалидное значение проходит насквозь** — `inline-edit.ts:339-342, 396-411, 542-543, 639-645`; `form-field.ts:262-264`; `error-state.ts:86-97`; `error-state-matcher.ts:59-62`.
JSDoc `commit()` гласит: «Saves the current value and returns to view mode, **running the same validation as a normal save**». Метод вызывает `save()`, который блокируется по `isInvalid()` → `formFieldRefList.some(ref => ref.invalid)` → `!!control.errorState`. Но `errorState` — это не валидность контрола, а **закешированный** булев флаг, пересчитываемый только внутри `KbqErrorStateTracker.updateErrorState()`, который контрол вызывает из `ngDoCheck` (`input.ts:235-241`), по дефолтному `ErrorStateMatcher` — `control.invalid && (control.touched || form.submitted)`. Поэтому невалидный, но **нетронутый** контрол отдаёт `errorState === false`, и `save()` уходит в успешную ветку. Клавиатурный путь это компенсирует, вызывая `markAllAsTouched()` перед отложенным сохранением (`inline-edit.ts:543, 554-555`, где `setTimeout` даёт change detection цикл на обновление `errorState`). `commit()` не делает ни того, ни другого; не делает и кнопка «Сохранить» (`inline-edit.html:69-74` вызывает `save($event)` напрямую). Уязвим ровно тот сценарий, который рекомендует сама документация: селект, коммитящий из `(selectionChange)` (`inline-edit.spec.ts:1413-1428`), где пользователь выбирает опцию мышью и контрол может так и остаться нетронутым, — а гайды рекомендуют предлагать явную пустую опцию («Не указано», `inline-edit.en.md:89-91`), то есть именно то значение, которое отвергает валидатор `required`. Все существующие спеки на невалидное сохранение сначала руками помечают контрол touched (`inline-edit.spec.ts:340, 378, 808`), поэтому дыра для набора невидима. Отдельно отметим: если в шаблоне редактирования вообще нет `KbqFormField` — задокументированная форма с `getValueHandler`/`setValueHandler`, `inline-edit-custom-handler-example.ts:39, 53-54` — `isInvalid()` безусловно возвращает `false` (`inline-edit.ts:642`), то есть валидация там обойдена конструктивно.
**Fix:** сделать `save()` самодостаточным: вызвать `markAllAsTouched()` первым же оператором (убрав оба вызова из `onOverlayKeydown`, см. IE-BUG-03 про остальную часть этого пути) и блокировать по реальной валидности контрола, а не по состоянию отображения — `formFieldRefList().some(ref => ref.control().ngControl?.control?.invalid ?? ref.invalid)`, — оставив `errorState`/`ErrorStateMatcher` решать только, показывать ли **оформление** ошибки. Добавить две спеки: `commit()` на `required`-контроле, которого никто не трогал, должен оставить компонент в режиме редактирования и не эмитить `saved`; кнопка «Сохранить» на том же нетронутом контроле — тоже. Обе падают на текущем коде.

**IE-DOC-01 · Гайды не описывают ни API, ни клавиатуру и обещают поведение ошибок, которого у компонента нет** — `inline-edit.en.md:1-115`, `inline-edit.ru.md:1-107` (Валидация на `:34-42` / `:31-39`); `inline-edit.ts:404, 396-411`; `inline-edit.html:53-64`.
Оба руководства — чистая дизайн-методичка. На 220 строках не упомянуты `showActions`, `showTooltipOnError`, `validationTooltip`, `disabled`, `editModeWidth`, `tooltipPlacement`, `overlayPanelClass`, `getValueHandler`, `setValueHandler`, `canSaveOnEnter`, `interactiveSelectors`, `saved`, `canceled`, `modeChange`, `toggleMode()` и `commit()`, и нет раздела `### Keyboard` — хотя соглашение в репозитории явно есть там, где это важно (`list.en.md:108-112`). **IE-A11Y-04 · Выход из режима редактирования может уронить фокус на `<body>`; сам компонент фокус не возвращает** — `inline-edit.ts:325-327, 396-411, 528-539`; `inline-edit.html:13-19, 47-52`; `@angular/cdk/fesm2022/a11y-module.mjs:571-578, 600-603`.
Ни один путь в `inline-edit.ts` не перемещает фокус при закрытии режима редактирования. `save()` и `cancel()` просто вызывают `toggleMode()`, `[cdkConnectedOverlayOpen]` становится false, embedded view уничтожается, и всё, что было сфокусировано внутри, исчезает. Единственный механизм восстановления — CDK-шный, через `cdkTrapFocusAutoCapture` на панели (`inline-edit.html:49`): `_captureFocus()` запоминает `document.activeElement` в момент присоединения, а `ngOnDestroy()` зовёт `.focus()` на сохранённом узле. Для типичного случая это работает: клик или Enter по хосту, хост фокусируемый, фокус к нему и возвращается. Для случая с интерактивным контентом — **нет**: там хост имеет `tabindex="-1"`, а сфокусирован якорь фокуса, который рендерится под `@if (hasInteractiveContent() && mode() === 'view' && …)` (`inline-edit.html:13`). Во время редактирования этот узел уничтожается, а при возврате в просмотр Angular создаёт **новый**. CDK по-прежнему держит старый, отсоединённый, а `.focus()` на отсоединённом элементе — no-op: фокус падает на `<body>`, и пользователь клавиатуры теряет место на странице. То же происходит после Tab-цепочки, если следующий inline edit отклонил сохранение. Ни один из 47 кейсов спеки нигде не проверяет, где находится фокус.
**Fix:** взять восстановление под свой контроль вместо делегирования. Запоминать элемент входа в `onClick()` и в обработчике Enter на якоре, а в `effect()` на возврат `mode` в `'view'` возвращать фокус через `FocusMonitor.focusVia(el, origin)`, чтобы корректно восстановилось кольцо фокуса (см. `project_kbq_focus_ring_mechanism`), — резолвя якорь лениво в момент восстановления, а не удерживая ссылку на узел через уничтожение. Добавить спеки: после `cancel()` и после успешного `save()` `document.activeElement` должен быть фокусируемым элементом самого inline edit, с проверкой и для обычного хоста, и для хоста с интерактивным контентом (`TestComponent` и `TestWithTagContent` уже существуют).

**IE-BUG-02 · Цепочка по Tab молча рвётся, если у следующего inline edit интерактивный контент** — `inline-edit.ts:626-637` (проверка класса на `:633`), `:285-293`; `inline-edit.html:13-19`.
`saveAndFocusNextInlineEdit()` сохраняет, ждёт макротаск, читает `document.activeElement` и диспатчит синтетический `new KeyboardEvent('keydown', { key: 'Enter' })` — **но только если** на элементе есть класс `kbq-inline-edit`. При этом собственный дизайн компонента гарантирует случай, когда его там нет: если у следующего inline edit контент просмотра интерактивный, `tabIndex()` возвращает `-1` для его хоста (`:290`), и фокус получает `.kbq-inline-edit__focus-anchor` (`inline-edit.html:15`). Цепочка обрывается на первом же поле с тегами или ссылкой — молча, без ошибки, и Tab пользователя уже потрачен. Сопутствуют две проблемы: сам приём (управлять соседним компонентом, диспатча сфабрикованное недоверенное `KeyboardEvent` в узел, найденный через `activeElement`) — это тот же антипаттерн, который в репозитории уже запрещён для событий скролла (DS-5407); и он опирается на то, что host-биндинг Angular `keydown.enter` продолжит матчить `KeyboardEvent`, собранный только с `key` и без `keyCode`.
**Fix:** резолвить соседа структурно, а не по имени класса — `const host = (this.document.activeElement as HTMLElement | null)?.closest('.kbq-inline-edit')` покрывает и хост, и якорь, — и заменить синтетический диспатч настоящим вызовом публичного `toggleMode()` соседнего экземпляра, полученного через небольшой `KbqInlineEditRegistry` (или DI-поиск), а не через DOM. Покрыть фикстурой из двух полей, где во втором лежит тег-лист: Tab из первого должен открывать второе.

**IE-BUG-03 · Каждое нажатие клавиши в режиме редактирования помечает все контролы touched, переводя поле в вид ошибки прямо во время набора** — `inline-edit.ts:542-543, 554, 733-735`; `error-state-matcher.ts:59-62`; подтверждение в `inline-edit-validation-example.ts:41-64`.
`onOverlayKeydown()` безусловно вызывает `this.markAllAsTouched()` **до** switch — то есть каждая стрелка, каждый символ, каждое нажатие Shift помечают все проецируемые контролы как touched. С дефолтным `ErrorStateMatcher` (`control.invalid && (control.touched || form.submitted)`) это значит, что `required`-поле краснеет на первом же нажатии, пока пользователь ещё набирает значение, которое сделает его валидным. Свидетельство того, что это воспринимается как дефект, лежит внутри документации самой библиотеки: `inline-edit-validation-example.ts` везёт специально написанную директиву `ExampleResetTouchedOnFirstInput`, вся работа которой — вызвать `markAsUntouched()` на первом событии `input` после фокуса (`:41-64`), плюс `CustomErrorStateMatcher`, дополнительно требующий `form?.submitted` (`:34-39`). Задокументированный пример, которому нужны два самописных обхода, чтобы компонент вёл себя разумно, — это баг-репорт. Тот же метод затем вызывается второй раз внутри ветки `Enter` (`:554`), где это чистое дублирование.
**Fix:** удалить оба вызова из `onOverlayKeydown()` и сделать `markAllAsTouched()` первым оператором `save()` (это тот же шаг, которого требует IE-BUG-01, поэтому делать их вместе) — пометка touched относится ко времени сохранения, а не ко времени нажатия клавиши. Затем удалить `ExampleResetTouchedOnFirstInput` и `CustomErrorStateMatcher` из примера валидации и убедиться, что демо ведёт себя по-прежнему. Добавить спеку: ввести один символ в нетронутый `required`-контрол и проверить, что form field не перешёл в состояние ошибки.

**IE-LIFE-01 · Fallback-ветка `scrollend` выбрасывает собственный хендл очистки, утекая слушателем `window` и удерживая компонент** — `inline-edit.ts:448-519`, особенно `:451, 495-502, 510-516`, и единственная внешняя отмена на `:359-362`.
`showValidationTooltip()` вешает перехватывающий слушатель `scrollend` на `window`, взводит fallback-таймер на 800 мс и публикует хендл `{ cancel }`, чтобы подписка на `detachments()` оверлея могла всё снять. Fallback-путь этот контракт ломает: `onTimeout()` выставляет `this.validationTooltipScrollHandle = null`, намеренно оставляя слушатель живым (`:498-501`), и комментарий утверждает, что тот «Removed by `cancel()` or the next `onScrollEnd` call», — но `cancel()` достижим **только через** только что выброшенный хендл, поэтому `this.validationTooltipScrollHandle?.cancel()` на `:362` превращается в no-op. С этого момента слушатель недостижим: он переживает отсоединение оверлея и уничтожение компонента, а его замыкание держит живым экземпляр `KbqInlineEdit`. Обнуление хендла заодно снимает защиту от повторного входа на `:451`, так что второе отклонённое сохранение регистрирует **второй** вечный слушатель — их количество растёт с каждым неудачным сохранением. Путь не экзотический: JSDoc сам называет «cases where nothing ends up scrolling» (`:442-443`) — это происходит всегда, когда origin обрезан нескроллируемым предком, — а старые Safari и Firefox `scrollend` не шлют вовсе. Спека проходит ровно по этой ветке (`inline-edit.spec.ts:956-969`) и проверяет лишь, что `show()` не вызван дважды; снятие слушателя не проверяется никогда.
**Fix:** оставлять хендл установленным после срабатывания fallback — `onTimeout()` должен выставлять `shown = true` и ничего больше, — и сделать `cancel()` единственной точкой очистки, вызываемой из `detachments()` как сейчас **и** из `DestroyRef.onDestroy(() => this.validationTooltipScrollHandle?.cancel())`. Расширить существующую спеку проверкой, что после отсоединения был вызван `window.removeEventListener('scrollend', fn, { capture: true })`, и добавить кейс, где два подряд отклонённых сохранения оставляют ровно один слушатель. TODO на `:445-446` (вынести «проскроллить в зону видимости и подождать, пока уляжется» в `packages/components/core`) — правильный долгосрочный дом для этого, и переезжать туда нужно уже с починенным жизненным циклом.

**IE-PERF-01 · Принудительное чтение layout из биндинга шаблона на каждом цикле change detection, на каждом экземпляре** — `inline-edit.html:36`; `inline-edit.ts:261, 311-313`.
`[cdkConnectedOverlayOffsetY]="-overlayOrigin.offsetHeight"` читает `offsetHeight` прямо в выражении биндинга. Angular переоценивает выражения биндингов на каждом цикле change detection данного view — и в режиме просмотра, и в режиме редактирования, — поэтому каждый `<kbq-inline-edit>` на странице форсирует сброс стилей и layout на каждом тике. Компонент явно спроектирован под списки: `inline-edit-vertical-list`, `inline-edit-horizontal-list` и `inline-edit-controls` — первые три примера в гайде, — так что цена это N чтений за тик, причём чтение стоит на «плохой» стороне любой окружающей записи. `overlayOrigin` усугубляет: это обычное изменяемое поле (`:261`), переприсваиваемое из `effect()` (`:311-313`), а не `computed()`, поэтому порядок между значением, которое читает шаблон, и значением, которое пишет эффект, определяется только планировщиком Angular, и ничто не помечает биндинг грязным при изменении.
**Fix:** превратить `overlayOrigin` в `computed(() => this.label() ? this.viewContainer().nativeElement : this.elementRef.nativeElement)` и удалить эффект, а смещение держать в отдельном сигнале, обновляемом в `onAttach()` и на тике `SharedResizeObserver`, на который `setOverlayWidth()` уже подписан (`:711-717`), — том же самом наблюдении, что уже двигает `overlayWidth` и `overlayRef.updatePosition()`. Забиндить `[cdkConnectedOverlayOffsetY]` на этот сигнал. Существующая спека на ресайз (`inline-edit.spec.ts:389-408`) уже подставляет заглушку `SharedResizeObserver` и легко расширяется проверкой обновления смещения.

Всё это меняет `inline-edit.api.md`, поэтому запускать `yarn run build:components`, затем `yarn run approve-api` одним циклом (сборка первой: guard читает `dist/*.d.ts`). Удаление экспорта формально breaking; поскольку потребителей `KbqFocusRegionItem` в репозитории нет, планировать на следующий мажор и обойтись без схематика.

**IE-BUG-04 · Определение интерактивного контента срабатывает один раз и больше никогда; `closest()` не ограничен** — `inline-edit.ts:315-321, 580-590, 592-598`.
`hasInteractiveContent` вычисляется `effect()`-ом, который планирует один `setTimeout` на каждое изменение `interactiveSelectors()` (`:315-321`) и один раз опрашивает `.kbq-inline-edit__view-content` (`:587`). Ни `MutationObserver`, ни перезапуска по изменению проецируемого контента нет, поэтому любой контент просмотра, появившийся после этого первого макротаска — теги, загруженные с сервера, `@if`, переключающийся по приходу значения, крайне распространённая форма `@if (value) { … } @else { placeholder }`, используемая всеми примерами пакета, — не будет замечен. Компонент оставляет `tabIndex()` равным `0`, якорь фокуса не рендерится, и хост вместе с уже интерактивными потомками становятся двумя табстопами, а подсветка `kbq-inline-edit_anchor-focused` не появляется никогда. Отдельно `isInteractiveElement()` вызывает `target.closest(selectors.join(','))` (`:597`) без границы: обход идёт мимо компонента до корня документа, поэтому inline edit, помещённый внутрь `<a>` (например, кликабельная строка таблицы), считает интерактивным любой клик и мышью не открывается вообще. Заодно отметим, что дефолтный список `['a', 'kbq-tag']` (`:228`) не включает `button`, `input` и `[role="button"]` — из-за чего хост спеки вынужден его расширять (`inline-edit.spec.ts:437`), — а сам инпут не описан нигде, кроме JSDoc.
**Fix:** заменить одноразовый таймаут подпиской `ContentObserver` (или CDK `MutationObserverFactory`) на элемент контента просмотра, с debounce и `takeUntilDestroyed()`, перезапуская `detectInteractiveContent()` на каждое изменение контента; ограничить обход `closest()` проверкой `this.elementRef.nativeElement.contains(match)`; и задокументировать `interactiveSelectors`, его значение по умолчанию и семантику «дополнять, а не заменять» в гайде рядом с клавиатурным разделом из IE-DOC-01.

**IE-STYLE-01 · Один мёртвый токен и приватный хелпер, занявший непрефиксованный неймспейс `.kbq-mask`** — `inline-edit-tokens.scss:1-8` (`:6`), `inline-edit.scss:5-40, 42-82, 200-205`.
`--kbq-inline-edit-panel-shadow: var(--kbq-shadow-popup)` объявлен (`inline-edit-tokens.scss:6`) и не читается нигде в репозитории — панель и кнопки действий вместо этого хардкодят `box-shadow: var(--kbq-shadow-popup)` (`inline-edit.scss:202`). Токен, весь смысл которого быть точкой переопределения и который компонент затем обходит, хуже отсутствующего токена: потребитель выставит его и не увидит никакого эффекта. Отдельно локальный миксин `_mask($config)` (`inline-edit.scss:5-40`) генерирует имена классов `.kbq-mask`, `.kbq-mask__fade` и `.kbq-mask__container`. Этих имён нет больше нигде в репозитории, то есть приватный хелпер занял общий, выглядящий общебиблиотечным неймспейс; при `ViewEncapsulation.None` от коллизии с будущей общей утилитой маски их спасает только то, что все правила случайно вложены в `.kbq-inline-edit`. В остальном стилевая поверхность чистая: захардкоженных цветов нет, каждое значение — токен, тема-миксин параметризован корректно.
**Fix:** направить `inline-edit.scss:202` на `var(--kbq-inline-edit-panel-shadow)`, чтобы объявленный токен стал реальной точкой переопределения (или удалить токен). Переименовать классы маски в `kbq-inline-edit__mask*` и убрать параллельные непрефиксованные имена — либо вынести миксин в `packages/components/core/styles`, если общая fade-маска действительно нужна. Ни то, ни другое не меняет визуал, поэтому существующие скриншоты остаются валидными.

**IE-TEST-02 · Мёртвый тестовый хост, `@Directive` в роли базового компонента и значение инпута по умолчанию, которого не видит ни один тест** — `inline-edit.spec.ts:1004-1014, 1009, 1329-1331`.
Три проблемы гигиены спеки. (1) `TestWithFullTabOrder` (`:1329`) объявлен, экспортирован и ни разу не инстанцируется — `git log -S` показывает, что он приехал с `87afa15e` (`fix(inline-edit): handle tab order according to UX guidelines`, DS-4810), а его тесты либо не доехали, либо были удалены; поскольку класс экспортирован, ни одно правило линтера его не помечает, и он так и будет выглядеть покрытием, которого нет. (2) `BaseTestComponent` — это `@Directive({ selector: 'name' })` (`:1004-1007`), используемая исключительно как контейнер полей и делящая селектор `name` со всеми `@Component` в файле. (3) Все шесть хостов, наследующих её, биндят `[showTooltipOnError]="showTooltipOnError()"` из `signal(undefined)` (`:1009`), а `booleanAttribute(undefined)` — это `false`, потому что реализация Angular выглядит как `value != null && value !== 'false'`. Каждый такой хост, соответственно, работает с `showTooltipOnError` **false**, молча переопределяя задокументированный дефолт `true`, и ни один тест набора не проверяет то значение, с которым компонент реально поставляется. В остальном тестовые хосты корректно названы без префикса `Kbq`, как принято в репозитории.
**Fix:** удалить `TestWithFullTabOrder` или дописать ему те кейсы порядка табуляции, ради которых он появился (это единственная фикстура с интерактивным элементом внутри `<kbq-label>` — реальный пробел, см. IE-BUG-04). Заменить базовую `@Directive` обычным (недекорированным) классом или встроить поля в хосты. Перестать биндить опциональные инпуты из `undefined`-сигналов: убрать биндинги у тех хостов, которым они не нужны, чтобы набор гонялся против реальных дефолтов, и добавить явный кейс, проверяющий, что тултип появляется при `showTooltipOnError`, оставленном по умолчанию.

## Приложение A — Методология ревью

Находки собирались сплошным чтением пакета — `inline-edit.ts` (736 строк), `inline-edit.html` (95), `inline-edit.scss` (206), `inline-edit-tokens.scss`, `module.ts`, `index.ts`, `inline-edit.spec.ts` (1 521 строка / 47 кейсов / 7 блоков `describe`), его Jest-снапшот, `e2e.ts` (326) и `e2e.playwright-spec.ts` (123), оба руководства пользователя и оба гайда примеров, — после чего каждый кандидат перепроверялся по пяти независимым источникам: смежному коду библиотеки (`form-field.ts`, `error-state.ts`, `error-state-matcher.ts`, `input.ts`, `dropdown-trigger.directive.ts`, `icon-button.component.ts`, `core/locales/types.ts`), реализациям CDK, которым компонент делегирует (`CdkTrapFocus` в `@angular/cdk/fesm2022/a11y-module.mjs`), реальному набору правил axe-core, который загружает `jest-axe` (4.12.1 из `node_modules/jest-axe/node_modules/axe-core` — корневой `node_modules/axe-core` это другая, более старая копия 3.5.6), отчёту API guard и всем местам использования внутри репозитория, найденным grep'ом. Две находки по доступности были переведены из суждения в подтверждённый автоматический провал чтением JSON правила и его evaluate-функций, а не по названию правила. Поскольку у компонента **нет потребителей внутри `packages/`** — единственные места использования это его собственные docs-примеры, dev-приложение и e2e-фикстуры, — обычное доказательство «обход у потребителя» заменено обходами внутри собственных примеров библиотеки, откуда и взято подтверждение для IE-BUG-03.

Отклонено в ходе проверки:
- **«Пакет не темизирован — нет `_inline-edit-theme.scss`»** — отклонено. Тема-миксин определён локально как `_inline-edit-theme` (`inline-edit.scss:42-82`) и подключён на `:99`; каждый цвет резолвится через токен `--kbq-inline-edit-*`, объявленный в `inline-edit-tokens.scss:1-8`, либо через глобальный семантический токен. Разбиение по файлам — расхождение в соглашении, а не функциональный пробел; единственный реальный стилевой дефект — мёртвый токен в IE-STYLE-01.
- **«`module.ts` нарушает AGENTS.md, где указано `<component-name>.module.ts`»** — отклонено как дефект. 12 из 64 пакетов компонентов используют голый `module.ts` (`actions-panel`, `clamped-text`, `content-panel`, `dynamic-translation`, `flag`, `inline-edit`, `overflow-items`, `resizer`, `skeleton`, `time-range`, `top-bar`, `username`). Это устоявшееся миноритарное соглашение, а не проблема inline-edit. Отсутствие `public-api.ts` (его нет у 10 из 64 пакетов) — та же история, и снято по той же причине.
- **«`cancel()` не может восстановить значение через `[(ngModel)]`»** — отклонено. `setValue()` доходит до `AbstractControl.setValue` (`inline-edit.ts:678`), который запускает зарегистрированный конвейер изменений и вызывает `NgModel.viewToModelUpdate`, эмитя `ngModelChange` обратно в биндинг хоста. `inline-edit.spec.ts:248-278` проверяет полный круг.
- **«Подписки `tabOut` в `setOverlayKeydownListener()` накапливаются между attach/detach»** — отклонено. Часовые живут внутри embedded view оверлея, который `CdkConnectedOverlay` уничтожает при отсоединении; каждый `OutputEmitterRef` сносится вместе со своим `DestroyRef`, поэтому каждое присоединение подписывается на свежие эмиттеры, а старые уже мертвы. Накопления нет.
- **«Reposition scroll strategy протекает в тултипы, проецируемые в режим редактирования»** — отклонено. Она передаётся поэкземплярно через `[kbqTooltipScrollStrategy]` (`inline-edit.html:61`), а не через DI, и JSDoc класса прямо об этом говорит (`inline-edit.ts:176-184`). `inline-edit.spec.ts:983-1000` доказывает, что проецируемый `kbqTooltip` сохраняет библиотечный `CloseScrollStrategy`.
- **«Использование глобальных `window`/`document` ломает SSR»** — отклонено. `KBQ_WINDOW` (`:170`) и `DOCUMENT` (`:169`) инжектятся; все обращения к `addEventListener`/`innerHeight`/`activeElement` идут через них. `inline-edit-overview-example` входит в SSR dev-приложение (`packages/components-dev/ssr/module.ts:193`), то есть путь реально прогоняется.
- **«`examples.inline-edit.*.md` — мёртвые файлы-заглушки»** — отклонено. `structure.ts:611` выставляет `hasExamples: true`, а оба файла содержат по четыре настоящих встраивания `<!-- example(…) -->`, а не заглушку «🚧 Documentation in progress 🚧». Каждый id примера, упомянутый во всех четырёх markdown-файлах, резолвится в каталог под `packages/docs-examples/components/inline-edit/`; единственный пример без ссылки из markdown — `inline-edit-overview` — намеренно используется dev-приложением и SSR-приложением.
- **«Escape утекает за пределы компонента и закрывает окружающее модальное окно»** — отклонено как непривязываемое. `onOverlayKeydown` действительно не вызывает `preventDefault()`/`stopPropagation()` для `Escape` (`inline-edit.ts:547-550`), но событие приходит в обработчик через `OverlayKeyboardDispatcher` CDK, который маршрутизирует только в самый верхний оверлей, а контейнер оверлеев является сиблингом корня приложения — ни одного пути внутри репозитория, где на него отреагировал бы второй компонент, найти не удалось. Защитный `preventDefault()` полезен, но на находку не тянет.

Скорректировано в ходе проверки:
- **IE-A11Y-03** изначально была написана как P0 наравне с IE-A11Y-01, поскольку оба — автоматические провалы axe под одним и тем же требованием AGENTS.md. Понижена до P1 по критерию обхода: безымянный элемент принадлежит потребителю, который может добавить `aria-label` уже сегодня, тогда как часовые из IE-A11Y-01 находятся в собственном шаблоне компонента и снаружи недостижимы.
- **IE-BUG-01** изначально формулировалась как «кнопка «Сохранить» коммитит невалидные значения». Разбор порядка событий показал, что клику предшествует `blur`, помечающий контрол touched, и цикл change detection, обновляющий `errorState`, — то есть в реальном браузере путь кнопки обычно безопасен. Находка сужена до программных путей — `commit()` и прямой `save()`, — которые не помечают контролы touched вообще и которые используются в собственном задокументированном паттерне коммита из селекта.
