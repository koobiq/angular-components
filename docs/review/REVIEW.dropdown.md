# Koobiq `dropdown` Component — Code Review & Improvement Plan

> Scope: `packages/components/dropdown` (panel, trigger directive, item, item-action, lazy content, animations, types, tokens, theme, SCSS, Jest spec, e2e fixture + Playwright spec, user guides, API guard report) plus the shared `core/overlay/panel-width.ts` resolver it composes · Commit `b665e503` · 2026-08-28
> Generated by a multi-dimension review (architecture, RxJS/lifecycle, correctness, accessibility, performance, public API/types, templates/styles, tests, docs) with manual verification of every finding against the source, the in-repo consumers, CDK internals in `node_modules`, and an executed `axe-core` 4.12.1 probe. 17 findings confirmed (P0×1, P1×3, P2×5, P3×8); 6 candidate findings refuted during verification (see Appendix A). Findings that overlap `REVIEW.select.md` (option/key-manager layer) and `REVIEW.popover.md` (`core/pop-up` trigger machinery) are cited rather than re-filed. This document is a review + roadmap; no source is modified by it.

## 1. Executive Summary

`kbq-dropdown` is the library's largest overlay package that is *not* built on `core/pop-up`: `KbqDropdown` (670 lines) owns the panel, the `FocusKeyManager`, the nested-submenu safe-area state machine and the panel-width tokens, while `KbqDropdownTrigger` (817 lines) owns the CDK overlay, positioning, hover chaining and focus restoration. It is consumed all over the repo — app-switcher, navbar, breadcrumbs, filter-bar, inline-edit, split-button, actions-panel, toast — and it is under active development: 3 of its last 5 commits are feature work (`b665e503` secondary action, `d1c4caf7b` smart search, `ef6d0515b` safe triangle).

- **The one release blocker is a hard AXE failure the library ships in its own documentation.** The trigger binds `[attr.aria-expanded]` unconditionally (`dropdown-trigger.directive.ts:124`) with a comment explaining why `aria-haspopup` was deliberately left off — but `aria-expanded` is not a global ARIA attribute, so on a host with no role it is a **critical** `aria-allowed-attr` violation. That is exactly the host the newest feature's published example uses (`<div kbq-dropdown-item [kbqDropdownTriggerFor]>`), and the same shape appears in the toast docs example, the dropdown dev app, the package's own e2e fixture and its own Jest fixture. Confirmed by running axe-core 4.12.1 against the three shapes (DRP-A11Y-01).
- **The newest surface — the secondary action (`#DS-3869`) — is mouse-only for its primary action.** Its documentation mandates a non-button item host ("The menu item itself should be a regular block, not a button", `dropdown.en.md:19`), but `KbqDropdownItem` binds no ENTER/SPACE handler and `ListKeyManager.onKeydown` has no ENTER case, so `<div kbq-dropdown-item (click)="…">` can be reached and highlighted with the arrow keys and then never activated (DRP-A11Y-02). The item-action suite has 12 cases and every one of them drives the mouse.
- **Menu semantics are still absent end to end**, three years after the umbrella review filed it as A11Y-18: no `role="menu"`/`menuitem`, no accessible name on the panel, no `aria-disabled` on disabled items, no Home/End. The evidence that this is a real gap and not a stylistic preference is that `app-switcher` re-implemented the entire pattern on top of the same items by subclassing (`app-switcher-dropdown-site.ts:40-43`, `app-switcher.html:28`) (DRP-A11Y-03).
- **The search integration is half-landed.** `KbqDropdown` now detects a projected `KbqFormField` (`dropdown.component.ts:115-118`) and the trigger pins the panel width for it (`dropdown-trigger.directive.ts:785-816`), but the panel's blanket `(click)="close()"` and its typeahead keydown pipe were never adapted — so **both** in-repo consumers hand-write the identical `stopPropagation` pair plus their own focus/reset logic (`filters.html:81-82` + `filters.ts:239-256`; `dropdown-with-filter-example.ts:49,56,116-128`). Two independent re-implementations of the same workaround is the strongest evidence in this document (DRP-BUG-01).
- **The panel-width policy is right in the resolver and wrong in the CSS floor.** `kbqResolvePanelWidth` deliberately drops `panelMinWidth` for an explicit `panelWidth` (`panel-width.ts:102-103`), and the guide promises the same ("An exact width; `panelMinWidth` is not applied", `dropdown.en.md:92-93`) — but `panelMinWidthToken` feeds the token unconditionally (`dropdown.component.ts:296-300`), so `.kbq-dropdown__panel`'s `min-width: max(var(…-width-min), 100%)` still floors the panel at 200 px and it overflows its own pane whenever `panelWidth < panelMinWidth` (DRP-BUG-02).

Genuine strengths, and there are many: the safe-area state machine is the best-engineered thing in the package — `mousemove` bound outside the Angular zone with an explicit cleanup closure, a grace-period switch that cannot race the animation, and 11 Jest cases covering every branch including the "grazed a disabled sibling" corner. `KBQ_DROPDOWN_SCROLL_STRATEGY` already carries a root factory default, so the standalone-import trap catalogued as POP-ARCH-01 does **not** apply here. `KBQ_DROPDOWN_ITEM_ACTION_HOST` is a textbook narrow-token solution to a circular-import problem, documented with the exact failure mode it avoids. The panel-width work is genuinely shared with select/tree-select/autocomplete through one core resolver with its own 20-case spec, the width-lock-for-search trick is correct and explained, and the `.kbq-dropdown-item-overlay`/z-index interaction with the new action is reasoned through in comments rather than discovered by accident. Every design token the package consumes resolves.

## 3. Prioritized Findings (deduplicated, verified)

### P0 — Release blockers

**DRP-A11Y-01 · `aria-expanded` is bound unconditionally on the trigger host — a critical AXE `aria-allowed-attr` failure on every non-button trigger the library itself ships** — `dropdown-trigger.directive.ts:117-129` (binding `:124`); `packages/docs-examples/components/dropdown/dropdown-item-action/dropdown-item-action-example.ts:60`; `packages/docs-examples/components/toast/toast-actions-overview/toast-actions-overview-example.html:25`; `packages/components-dev/dropdown/template.html:7`; `packages/components/dropdown/e2e.ts:348`; `packages/components/dropdown/dropdown.spec.ts:2588`.
The host block carries a deliberate, well-argued comment about *omitting* `aria-haspopup` (`:120-123`) and then publishes `'[attr.aria-expanded]': 'opened'` (`:124`) on whatever element the directive is applied to. `aria-expanded` is not a global ARIA attribute: on an element whose computed role is `generic` — a bare `<div>`, a `<span>`, or an `<a>` without `href` — it is disallowed. Verified by executing axe-core 4.12.1 (`node_modules/jest-axe/node_modules/axe-core`) over `<div tabindex="0" aria-expanded="false">`, `<span tabindex="0" aria-expanded="false">` and `<a tabindex="0" aria-expanded="false">`: all three fail `aria-allowed-attr` with **impact `critical`**; the `<button>` control in the same probe passes. Every one of those three shapes exists in the repo today: the published documentation example for the *newest* feature uses `<div kbq-dropdown-item [kbqDropdownTriggerFor]="appDropdownNested">` (`dropdown-item-action-example.ts:60`), the toast docs example uses `<a kbq-link pseudo [kbqDropdownTriggerFor]>` with no `href` (`KbqLink` adds no role — `link.component.ts:34-49`), the dropdown dev app uses `<span kbq-link pseudo [kbqDropdownTriggerFor]>`, and the package's own e2e fixture and Jest fixture use the `<div>` form. AGENTS.md states the mandate without qualification ("It MUST pass all AXE checks"), and this is an automated-rule failure, not a WCAG judgement call. The one consumer that got it right did so by hand: `navbar-item.component.ts:597-605` synthesises `role="button"` for its custom-element hosts and documents *why* it must (`:597-598`).
**Fix:** stop emitting the attribute onto role-less hosts. Minimal change: keep a private `hasExpandableRole` check in the trigger — the host's `tagName` is in a natively-actionable set (`BUTTON`, `A[href]`, `SUMMARY`, `INPUT`) or it already carries an explicit `role`/`aria-haspopup` — and bind `'[attr.aria-expanded]': 'hasExpandableRole ? opened : null'`, mirroring the `NATIVELY_ACTIONABLE_TAGS` gate at `navbar-item.component.ts:601`. Better: land DRP-A11Y-03 so the trigger can legitimately publish `role`/`aria-haspopup="menu"`/`aria-controls` and the attribute becomes valid everywhere. Either way, fix the five in-repo call sites (give the docs/e2e/spec `<div>` items `role="menuitem"` once DRP-A11Y-03 lands, or `role="button"` before then) and add a `jest-axe` spec — `expect(await axe(overlayContainerElement)).toHaveNoViolations()` with the dropdown open — to `dropdown.spec.ts`; `jest-axe` is already a devDependency (`package.json:121`) and five other packages already use it.

### P1 — High

**DRP-A11Y-02 · The non-button item host that the secondary-action feature mandates has no keyboard activation path** — `dropdown-item.component.ts:47-61`; `dropdown.component.ts:519-552` (default branch `:539-546`); `dropdown.en.md:19` / `dropdown.ru.md`; `dropdown.spec.ts:2575-2578`, `:1304-1313`.
`b665e503` added `KbqDropdownItemAction` together with a documented requirement that the item host be non-interactive: *"Requires the item's host element to be non-interactive (e.g. `<div kbq-dropdown-item>`), since interactive content cannot validly nest inside another interactive element"* (`dropdown-item-action.ts:22-26`), restated in the user guide as "The menu item itself should be a regular block, not a button." But `KbqDropdownItem`'s host block binds only `(click)`, `(mouseenter)` and `(keydown)='handleActionKeydown($event)'`, and `handleActionKeydown` returns immediately for anything that is not `TAB` (`:180`). The keydown then bubbles to the panel, whose `handleKeydown` forwards the default branch to `this.keyManager.onKeydown(event)` (`dropdown.component.ts:544`) — and CDK's `ListKeyManager.onKeydown` has no `ENTER`/`SPACE` case at all (`node_modules/@angular/cdk/fesm2022/list-key-manager.mjs:152-230`; only TAB, the four arrows, HOME/END behind `withHomeAndEnd()`, PAGE_UP/DOWN behind `withPageUpDown()`, and printable-key typeahead). Net effect: a `<div kbq-dropdown-item (click)="doThing()">` is focusable, arrow-navigable and visually highlighted, and pressing Enter or Space does nothing — WCAG 2.1.1 (Keyboard). The package's own Jest fixture is exactly this shape (`dropdown.spec.ts:2575-2578`: `<div kbq-dropdown-item (click)="primaryClick()">`), and the only test that asserts `primaryClick` fires does so through `dispatchMouseEvent` (`:1304-1313`). Note the same host is also the one that fails DRP-A11Y-01, so this row is doubly broken for keyboard and AT users.
**Fix:** add an ENTER/SPACE branch to `KbqDropdownItem`. In `handleActionKeydown` (rename to `handleKeydown`), when the event target is the host element, `keyCode` is `ENTER` or `SPACE`, and the item is neither `disabled` nor `progress()`, call `event.preventDefault()` and `this.getHostElement().click()` so the consumer's `(click)` binding and the panel's own `(click)="close()"` both fire exactly as they do for the mouse — and skip it when the host is natively actionable (`BUTTON`, `A[href]`) so buttons and links keep their native behaviour instead of double-firing. Guard it with two specs in the `item action` describe: Enter on the `<div>` host calls `primaryClick` once and closes the dropdown; Enter on the projected action does *not* call `primaryClick`.

**DRP-A11Y-03 · No menu semantics anywhere on the chain; the one consumer that needed them re-implemented the pattern by subclassing** — `dropdown.html:2-19`; `dropdown-item.component.ts:28-33,47-61`; `dropdown.component.ts:358`; consumers `app-switcher-dropdown-site.ts:37-44`, `app-switcher-dropdown-app.ts:47-53`, `app-switcher-list-item.ts:58-62`, `app-switcher.html:21-28,160`. *(Carries forward umbrella `REVIEW.md` A11Y-18, still open.)*
The panel is a `<div tabindex="-1" class="kbq-dropdown__panel">` with no `role`, no `aria-label`/`aria-labelledby` and no `id` for the trigger to point `aria-controls` at — and it receives programmatic focus on every mouse/touch open (`dropdown.component.ts:572-592`), so an AT user is dropped into an unnamed generic container. Items carry no `role="menuitem"`; disabled items get `[attr.disabled]` (`dropdown-item.component.ts:55`), which is meaningless on the `<div>`/`<a>` hosts the package documents and is *not* exposed to AT — while the sibling directive in the same package does it correctly (`dropdown-item-action.ts:32` binds `aria-disabled`). Every item is `tabindex="0"` (`:56`, `getTabIndex()` `:153-155`) rather than roving. `withHomeAndEnd()` is never called on the key manager (`dropdown.component.ts:358`), so Home/End do not jump to the first/last item as the WAI-ARIA menu pattern requires. The decision is documented as deliberate in two places (`dropdown-item.component.ts:31-32`, `dropdown-trigger.directive.ts:120-123`) and propagated to `navbar-item.component.ts:597-598` — but `app-switcher` demonstrates the cost: it subclasses `KbqDropdownItem` three times purely to add `role="menuitem"` + `[attr.aria-haspopup]`, wraps the panels in hand-written `<div role="menu" aria-orientation="vertical">` (`app-switcher.html:28,160`), and adds a `role="none"` explainer comment (`:21`) plus its own spec asserting the search field stays outside the menu subtree (`app-switcher.spec.ts:1366-1390`). That work belongs in `dropdown`.
**Fix:** land the menu pattern in the package, in one change so it is coherent: generate a stable `panelId` on `KbqDropdown`, put `role="menu"` + `[attr.aria-orientation]="'vertical'"` + `aria-labelledby` (pointing at the trigger) on the panel div, add `role="menuitem"` + `[attr.aria-disabled]="disabled || null"` to `KbqDropdownItem` (and `aria-haspopup="menu"` + `aria-expanded` when `isNested`), switch `getTabIndex()` to roving (`-1` unless the item is the key manager's active item), call `.withHomeAndEnd()`, and let the trigger publish `aria-haspopup="menu"` + `[attr.aria-controls]="opened ? panelId : null"` — which also retires DRP-A11Y-01's gate. Keep the search field outside the `role="menu"` subtree the way `app-switcher.html:21-28` already does. Then delete the three app-switcher overrides and re-point its spec at the base behaviour.

**DRP-BUG-01 · Projected search fields and footers are only half-supported: the panel closes on any click and swallows every keystroke, so both in-repo consumers hand-write the same workaround** — `dropdown.html:12-13,15-18`; `dropdown.component.ts:115-118,376,519-552`; `dropdown-trigger.directive.ts:785-816`; consumers `packages/components/filter-bar/filters.html:69-85` (`:81-82`) + `filters.ts:239-256`, `packages/docs-examples/components/dropdown/dropdown-with-filter/dropdown-with-filter-example.ts:49,56,116-128`.
`d1c4caf7b` taught the dropdown to *recognise* a projected search field — `contentChild(KbqFormField)` → `hasSearch()` (`dropdown.component.ts:115-118`), `search()?.inOverlay.set(true)` (`:376`), and a width lock so filtering cannot reflow the panel (`dropdown-trigger.directive.ts:785-816`) — but the panel's two blanket host handlers were never adapted. `(click)="close()"` sits on the panel `<div>` (`dropdown.html:12`), which wraps *both* `.kbq-dropdown__content` and the footer `ng-content` (`:15-18`), so a click on the search input, on the cleaner, or on a footer button closes the whole dropdown — even though the guide explicitly invites buttons into the footer (`dropdown.en.md:33`). `(keydown)` (`:13`) forwards everything to `keyManager.onKeydown` (`dropdown.component.ts:544`), whose typeahead consumes printable keys and — because this is a `FocusKeyManager`, not an `ActiveDescendantKeyManager` — moves real DOM focus onto the matched item, i.e. out of the input the user is typing in. Both consumers arrived independently at the same three-part patch: `stopPropagation` on click, `stopPropagation` on keydown, and their own open/close focus-and-reset (`filters.ts:239-256` = `stopEventPropagation` + `searchKeydownHandler` + `onDropdownOpen`'s `setTimeout(() => search.focus())`; the docs example = `(click)="$event.stopPropagation()"`, `handleKeydown` with `event.stopPropagation()`, `handleOpened()`/`handleClosed()`). The docs example's blanket `stopPropagation` has a second cost: Escape typed in the search field can never reach the panel, so it cannot close the dropdown at all.
**Fix:** make `hasSearch()` load-bearing rather than informational. (1) Move `(click)="close()"` off the panel div onto `.kbq-dropdown__content` only, so footer and search clicks no longer close the panel; keep the item-level close path unchanged. (2) In `handleKeydown`, return early for keys other than `ESCAPE`/arrows when `event.target` is inside the projected search field (or is any `input`/`textarea`/`[contenteditable]`), so typeahead and roving focus never fight the input. (3) Focus the search field in `focusFirstItem()` when `hasSearch()` is true, and clear its control on close — the two consumers' `onDropdownOpen`/`handleClosed` then disappear. Guard with specs: clicking the search input keeps the panel open; typing a letter in it leaves `document.activeElement` on the input; Escape in it closes the dropdown; clicking a footer button keeps the panel open. Then delete the workarounds from `filters.ts`/`filters.html` and the docs example.

### P2 — Should fix

**DRP-CSS-01 · The safe-area hover-suppression rule is nested one level wrong and can never match** — `_dropdown-theme.scss:30-36`; `dropdown.component.ts:73-74,412,476-482`; `dropdown.html:6`.
`SAFE_AREA_ACTIVE_CLASS = 'kbq-dropdown__panel_safe-area-active'` is written into `classList` (`dropdown.component.ts:412`), which is bound to the **panel** element via `[class]="classList"` (`dropdown.html:6`) — i.e. it lands on an *ancestor* of every item. The theme rule that is supposed to consume it is written as a descendant of `.kbq-dropdown-item`:
```scss
.kbq-dropdown-item {
    …
    .kbq-dropdown__panel_safe-area-active {
        &.cdk-focused:not(.kbq-dropdown-item_highlighted, .kbq-selected, .kbq-disabled) { … }
    }
}
```
which compiles to `.kbq-dropdown-item .kbq-dropdown__panel_safe-area-active.cdk-focused:not(…)` — it requires a panel *inside* an item, which cannot exist. The feature's own comment states the intent: *"While a safe area protects an open submenu, sibling items passed on the way to it keep their default background instead of flashing the hover state"* (`:30-31`). Because the rule is dead, they still flash: `KbqDropdownItem.handleMouseEnter()` calls `this.focus('mouse')` (`dropdown-item.component.ts:166-169`), which adds `.cdk-focused`, and `_dropdown-theme.scss:25-28` paints the hover state on it. The behavioural half of the safe area (not closing the submenu) works and is covered by 11 Jest cases; the visual half shipped broken in `ef6d0515b` and there is no Playwright coverage of the safe area to have caught it.
**Fix:** invert the nesting so the panel class is the ancestor — `.kbq-dropdown__panel_safe-area-active & { &.cdk-focused:not(…) { … } }`, compiling to `.kbq-dropdown__panel_safe-area-active .kbq-dropdown-item.cdk-focused:not(…)`, which has enough specificity to beat `:25-28`. Add a Playwright case to `e2e.playwright-spec.ts`: open a nested submenu, move the pointer diagonally across a sibling row, screenshot — the sibling must not carry the hover background.

**DRP-BUG-02 · An explicit `panelWidth` smaller than `panelMinWidth` overflows its own overlay pane, contradicting the published contract** — `dropdown.component.ts:290-300`; `dropdown.html:8`; `dropdown.scss:42`; `core/overlay/panel-width.ts:78-104` (`:102-103`); `dropdown.en.md:92-93` / `dropdown.ru.md`.
The shared resolver selects the sizing policy from `panelWidth`, and for an explicit width it deliberately drops the minimum: *"Explicit width. `panelMinWidth` is not applied."* → `{ width: panelWidth, minWidth: '' }` (`panel-width.ts:102-103`). The guide repeats the promise verbatim (`<!-- An exact width; panelMinWidth is not applied --> <kbq-dropdown [panelWidth]="400" />`). But the dropdown has a *second*, CSS-side floor that ignores the policy: `panelMinWidthToken` is a plain `computed()` over `panelMinWidth()` alone (`dropdown.component.ts:296-300`), bound unconditionally as `[style.--kbq-dropdown-size-container-width-min]` (`dropdown.html:8`), and consumed by `.kbq-dropdown__panel { min-width: max(var(--kbq-dropdown-size-container-width-min), 100%); }` (`dropdown.scss:42`). With the default `panelMinWidth` of 200 (`KBQ_PANEL_DEFAULT_MIN_WIDTH`, `panel-width.ts:10`), `[panelWidth]="150"` therefore yields a 150 px pane containing a 200 px panel — 50 px of the menu hangs outside the box CDK positioned, and no `max-width` can pull it back (CSS resolves `min-width` over `max-width`). The existing specs miss it because the only explicit-width case tested is `panelWidth = 344` against the same 200 default (`dropdown.spec.ts:2445-2460`), where `max(200px, 344px)` is a no-op.
**Fix:** mirror the resolver's policy selection in the computed — return `null` from `panelMinWidthToken()` whenever `panelWidth()` resolves to an explicit width (i.e. it is neither `null`/`''` nor `'auto'` nor a non-finite number), so the token falls back to its static default only where the automatic policies apply. Add two specs next to `:2378-2405`: `[panelWidth]="150"` leaves the inline token unset, and `panelWidth` unset keeps `200px`. While there, reconcile the second half of this: `[panelMinWidth]="null"` is typed as valid (`KbqPanelMinWidth = number | null`, "`null` applies no additional minimum", `panel-width.ts:23-24`) but `numberAttribute(null)` is `NaN` (`node_modules/@angular/core/fesm2022/core.mjs:3895-3901`), so `Number.isFinite` fails and the panel silently keeps the static 200 px token — document it or make `null` emit `0px`.

**DRP-LIFE-01 · `closeSubscription` multiplexes two unrelated subscriptions; the `dropdown.closed` subscription is orphaned by the first `open()` and never torn down** — `dropdown-trigger.directive.ts:191-209` (`:197,200`), `:260`, `:336`, `:442-455`, `:679-684`.
One field holds two different things at different times. The `dropdown` setter unsubscribes it and assigns the panel-lifetime subscription to `dropdown.closed` (`:197-207`) — the *only* path into `destroy()`. Then `open()` overwrites the same field with the per-session closing-actions subscription (`:336`) **without unsubscribing** what it held. Consequences, all verified: (1) the `closed` subscription is never referenced again, so `cleanUpSubscriptions()` in `ngOnDestroy` (`:680-684`) cannot reach it — for the "one `kbq-dropdown`, many triggers" pattern the package explicitly supports (`:733-735`, spec `:2053`), every destroyed trigger leaves a live subscriber on the shared panel's `closed` emitter, retaining the trigger, its `ElementRef` with a detached host element and its `ViewContainerRef` until the panel itself is destroyed; (2) reassigning `dropdown` after the first open unsubscribes the *closing-actions* subscription instead of the old panel's, so the trigger stays wired to the previous panel — and since `destroy()` only guards on `!this.overlayRef || !this.opened` (`:443`), a `closed` emission from the abandoned panel while the new one is open will detach the new panel, reset its active item and restore focus. The existing swap test closes before swapping (`dropdown.spec.ts:635-669`), so it never reaches that state. No crash — the orphan is functional, which is exactly why nothing has noticed.
**Fix:** split the field. Keep `closeSubscription` for the `dropdown.closed` subscription only, add a separate `closingActionsSubscription` for `open()`/`destroy()`, and unsubscribe both in `cleanUpSubscriptions()`. Add a leak spec: mount and destroy N triggers pointing at one shared `kbq-dropdown`, then assert `dropdown.closed.observers.length` has not grown; and a cross-talk spec: open panel A, assign panel B, open it, emit `A.closed`, assert B is still attached.

**DRP-A11Y-04 · Focus is pulled back to the trigger on every root close, including outside-click closes that have already moved focus somewhere else** — `dropdown-trigger.directive.ts:442-463` (gate `:459`), `:352-361`, `:686-712` (`:689`).
`destroy()` restores focus when `this.restoreFocus && (reason === 'keydown' || !this.openedBy || !this.isNested())` — and for any root-level trigger `!this.isNested()` is unconditionally `true`, so the branch is taken on *every* close reason. `closingActions()` includes `overlayRef.outsidePointerEvents()` (`:689`), which CDK dispatches from a body-level **`click`** listener (`node_modules/@angular/cdk/fesm2022/overlay-module.mjs:604-607,631-679`) — i.e. after `mousedown` has already given focus to whatever the user clicked. So clicking a text input elsewhere on the page closes the dropdown and then yanks focus off that input back onto the trigger. (Angular Material's `MatMenuTrigger._restoreFocus` has the same shape, so this is inherited convention rather than a novel bug — but the correct behaviour is well defined: restore only when focus is still inside the overlay or on `<body>`.) A second, smaller issue in the same block: when `openedBy` is `undefined` — every programmatic `trigger.close()` after a programmatic open — `focus()` falls through to the native `elementRef.nativeElement.focus()` (`:359`), bypassing `FocusMonitor` and therefore the `cdk-keyboard-focused` ring the library relies on everywhere else.
**Fix:** guard the restore — `const shouldRestore = this.overlayRef.overlayElement.contains(document.activeElement) || document.activeElement === document.body;` and only then call `this.focus(this.openedBy)`. Route the `undefined`-origin path through `focusMonitor.focusVia(el, 'program')` instead of the native call so the origin is always recorded. Cover with a spec: open by mouse, focus an unrelated `<input>` and dispatch a document `click`, assert the dropdown closed **and** `document.activeElement` is still the input.

**DRP-STYLE-01 · A host class is applied but never styled, and the `panelClass` setter wipes the host element's `className`** — `dropdown-item.component.ts:49`; `dropdown.component.ts:200-219` (`:214`).

**DRP-PERF-01 · Typeahead deep-clones each candidate item's subtree on every keystroke** — `dropdown-item.component.ts:194-207`; `dropdown.component.ts:358`.
`getLabel()` does `this.getHostElement().cloneNode(true)`, then `querySelectorAll('[kbq-icon], .kbq-icon, [kbqDropdownItemAction]')` and a removal loop, on every call. `withTypeAhead()` (`dropdown.component.ts:358`) makes CDK's `Typeahead` walk the item array calling `getLabel()` until it finds a prefix match, once per debounced keystroke — so a long menu (the `dropdown-recursive-template` example, filter-bar's saved-filter list, app-switcher's site list) pays O(N) full-subtree clones plus O(N) `querySelectorAll` per typed character, all synchronously in the zone.
**Fix:** memoise the label on the item — compute it once in `ngAfterViewInit` and invalidate from the `CdkObserveContent`/`MutationObserver` the package already has available, or read `this.textElement.nativeElement.textContent` directly (the `#kbqTitleText` wrapper at `dropdown-item.html:3-5` already excludes the leading icon and the projected action by construction), which removes the clone entirely.

**DRP-BUG-03 · Safe-area geometry is captured once and never revalidated against reposition or scroll** — `dropdown-trigger.directive.ts:377-390`; `dropdown.component.ts:401-463` (`:414-446`).
`handleMouseLeave` measures `overlayRef.overlayElement.getBoundingClientRect()` and derives the triangle from it (`:386-387`), then hands both to `activateSafeArea`, whose `mousemove` listener tests the pointer against those frozen coordinates for as long as the safe area lives. The default scroll strategy is `reposition()` (`:64`), so an ancestor scroll or a window resize while the pointer is in transit moves the submenu panel while the safe area keeps checking the old rectangle: `isPointInRect` then never fires where the panel actually is (so the safe area is only released by leaving the triangle), and `isPointInTriangle` can hold the submenu open over a region the panel has vacated.
**Fix:** re-measure on demand — capture the `OverlayRef` instead of the `DOMRect` and read `getBoundingClientRect()` inside the listener (the listener already runs outside the zone, so the layout read is cheap and un-batched), or re-derive both rect and triangle from the position strategy's `positionChanges` while a safe area is active. Add a Jest case that repositions the panel between `mouseleave` and the `mousemove` that should reach it.

**DRP-DOC-01 · `examples.dropdown.*.md` are dead stubs, and `safeArea` is documented as a per-submenu property when it is read off the parent panel** — `packages/components/dropdown/examples.dropdown.en.md:1-5`, `examples.dropdown.ru.md:1-5`; `apps/docs/src/app/structure.ts:531-541` (`hasExamples: false`, `:540`); `dropdown.en.md:49-58` (`:55`) / `dropdown.ru.md`; `dropdown-trigger.directive.ts:382`; `dropdown.component.ts:283-288`.

**Fix:** either delete the two stubs or fill them and flip `hasExamples` to `true` (14 embeds are already available). Reword the safe-area bullet to "locally — on the panel that contains the nested triggers, through its `safeArea` property", in both languages, and add the same clarification to the `safeArea` JSDoc (`dropdown.component.ts:283-288`).

**DRP-STYLE-02 · Four of the package's fourteen TypeScript files carry a UTF-8 BOM** — `dropdown.component.ts:1`, `dropdown-trigger.directive.ts:1`, `dropdown-item.component.ts:1`, `dropdown.spec.ts:1`.

## Appendix A — Review Methodology

Findings were gathered by reading every file in `packages/components/dropdown` end to end, then following each behaviour outward: to the shared resolver (`core/overlay/panel-width.ts` + its spec), to CDK internals in `node_modules` (`list-key-manager.mjs`, `overlay-module.mjs`, `core.mjs`) whenever a claim depended on framework behaviour, to every in-repo consumer of `kbqDropdownTriggerFor` / `kbq-dropdown-item` / `kbqDropdownItemAction`, to the docs examples and dev app, to `apps/docs/src/app/structure.ts`, to `tools/public_api_guard/components/dropdown.api.md`, and to the last 20 commits touching the package. Consumer workarounds were hunted deliberately, on the principle that a hand-written patch around a component is the strongest evidence a defect is real — two of the P1s (DRP-A11Y-03, DRP-BUG-01) rest primarily on that evidence. Severity calibration reuses the umbrella review's scale; overlapping items in `REVIEW.select.md` (option/key-manager layer) and `REVIEW.popover.md` (`core/pop-up`, overlay-container class bookkeeping) are cited rather than re-filed, and umbrella `REVIEW.md` A11Y-18 is carried forward as DRP-A11Y-03.

One claim was verified by execution rather than by reading: DRP-A11Y-01's AXE impact. `axe-core` 4.12.1 (the version `jest-axe@11` resolves) was run in jsdom over `<div tabindex="0" aria-expanded="false">`, `<span tabindex="0" aria-expanded="false">`, `<a tabindex="0" aria-expanded="false">` and `<button aria-expanded="false">` with `runOnly: ['aria-allowed-attr']`. Result: three violations, impact `critical`, "ARIA attribute is not allowed: aria-expanded" — the `<button>` passed. No test suite or build was run for this review.

Refuted during verification:
- **"`subscribeToPositions` leaks — `positionChanges` is subscribed with no teardown"** (`dropdown-trigger.directive.ts:597-606`) — refuted. `FlexibleConnectedPositionStrategy.dispose()` completes `_positionChanges` (`node_modules/@angular/cdk/fesm2022/overlay-module.mjs:1507`), and the trigger disposes its `OverlayRef` — and with it the strategy — in `ngOnDestroy` (`:283-286`). Bounded.
- **"`overlayRef.keydownEvents().subscribe()` leaks"** (`:561`) — refuted for the same reason: `OverlayRef.dispose()` completes `_keydownEvents` (`overlay-module.mjs:1007`).
- **"`panelMinWidth: 0` removes the trigger-width floor, so a narrow panel can be narrower than its trigger"** — refuted. `kbqResolvePanelWidth` computes `floor = Math.max(min, triggerWidth)` (`panel-width.ts:85-86`), so `0` still yields the trigger width as the pane's `minWidth`, and the panel's own `min-width: max(0px, 100%)` then tracks the pane. The behaviour is intentional, documented in the input's JSDoc ("never narrower than this, **nor than its trigger**", `dropdown.component.ts:263-265`) and pinned by `dropdown.spec.ts:2378-2390`. The real contract break is the opposite case — see DRP-BUG-02.
- **"The panel animations ignore `prefers-reduced-motion` (umbrella A11Y-35/36)"** — refuted for this package. The enter transition animates over `0ms` on both tracks (`dropdown-animations.ts:39-40`) and the exit is a 50 ms opacity fade with a 25 ms delay (`:43`) — no motion a reduced-motion user could perceive. The one genuinely animated surface, the `kbq-progress` shimmer, already carries a `@media (prefers-reduced-motion: reduce)` gate (`dropdown-item.scss:74-76`).
- **"Disabled items are reachable with the arrow keys"** — refuted. `ListKeyManager`'s default skip predicate skips items whose `disabled` is truthy, and `KbqDropdownItem.focus()` early-returns for disabled items anyway (`dropdown-item.component.ts:136`). The gap for disabled items is the missing `aria-disabled` (folded into DRP-A11Y-03), not navigation.
- **"Standalone import of `KbqDropdownTrigger` throws `NullInjectorError` (the 8-copy `REVIEW.popover.md` POP-ARCH-01 pattern)"** — refuted for dropdown. `KBQ_DROPDOWN_SCROLL_STRATEGY` was given a `providedIn: 'root'` factory default in `ed029c0da` (`dropdown-trigger.directive.ts:53-60`), with a comment stating exactly that intent. The module provider is no longer load-bearing here.

Corrected on verification:
- **DRP-A11Y-01** was drafted from umbrella A11Y-18's framing as "the trigger publishes no `aria-haspopup`". Reading the source showed the omission is deliberate and reasoned (`dropdown-trigger.directive.ts:120-123`), and that the actual defect runs the other way: the `aria-expanded` that *is* published is invalid on the role-less hosts the library ships in its own examples. That turns a WCAG judgement into an automated-rule failure against an explicit AGENTS.md mandate — severity raised P1 → P0.
- **DRP-BUG-02** was drafted as "`panelMinWidth: 0` does not disable the floor". Verification showed that is the documented, tested, intended behaviour; the finding was re-aimed at the untested inverse (`panelWidth` explicit and smaller than `panelMinWidth`), where the published guide is genuinely untrue and the panel overflows its pane.
- **DRP-LIFE-01** was drafted as "`closeSubscription` is unsubscribed twice". Tracing the assignments showed the orphaned `dropdown.closed` subscription is in fact *load-bearing* — after the first `open()` it is the only remaining path into `destroy()` — so the defect is retention plus swap-time cross-talk, not a double-unsubscribe, and there is no crash to report.
- **DRP-A11Y-04** was drafted as an unqualified focus-steal bug. Comparing against `MatMenuTrigger._restoreFocus` showed the same shape upstream, so the wording was narrowed to the specific unguarded case (restoring when focus has already moved outside the overlay) and the severity held at P2 rather than P1.
