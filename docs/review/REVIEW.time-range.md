> Scope: `packages/components/time-range` (component, editor, title, form-field adapter, service, constants, types, SCSS, Jest spec + snapshot, user guides, examples, API guard report) plus the docs examples, the dev app and the docs navigation · Commit `b665e503` · 2026-08-28

## 1. Executive Summary

`KbqTimeRange` is a five-file feature package: a popover trigger with a formatted title, a radio-driven editor with datepicker/timepicker pairs, a service that turns preset identifiers into ISO ranges, and an adapter that lets the trigger live inside a `kbq-form-field`. It is the only package reviewed so far with a genuine **P0**.

- **The custom range silently drops the end date the user picks.** `mapTimeRange` builds its argument object as `toDate: this.form.controls.toTime.value` (`time-range-editor.ts:263`) — the *time* control feeding the *date* slot, while `toTime` on the next line reads the same control. `combineDateAndTime` takes year/month/day from its first argument and hours/minutes/seconds from its second (`time-range.service.ts:160-170`), so the emitted `endDateTime` keeps whatever calendar date the time control was seeded with and discards the date the user selected. `fromDate` is wired correctly one line above, which is what makes it a typo rather than a design. Worse, the form's own validator reads `form.toDate` correctly (`constants.ts:47-48`), so validation and emission disagree about what the range is (TR-BUG-01).
- **`setDisabledState` is not implemented, so a disabled form control is still fully interactive.** Neither `KbqTimeRange` (`time-range.ts:242-249`) nor `KbqTimeRangeEditor` (`time-range-editor.ts:245-252`) defines it — `grep -rn "setDisabledState" packages/components/time-range/` returns nothing. `form.get('range').disable()` therefore leaves the trigger focusable, the popover openable and Apply live; the only visible consequence is that Angular stops accepting the value (TR-BUG-02).
- **`KbqTimeRangeTitleAsControl` is a `KbqFormFieldControl` whose state never changes.** Every member of the interface is declared and never assigned — `id`, `placeholder`, `focused`, `empty`, `required`, `disabled`, `errorState` are all `undefined` at runtime — `onContainerClick` and `focus` are empty bodies, and `stateChanges` is a `Subject` that nothing ever calls `next()` on (`time-range-title-as-form-field.ts:46-71`). A `kbq-form-field` wrapping it can never learn that its control gained focus, became empty or went invalid, so the label, the error styling and the cleaner all sit on stale state. Two shipped examples are built on it (TR-API-01).
- **`valueCorrected` fires on values that were not corrected.** The guard at `time-range.ts:207-212` emits whenever `'startDateTime' in value` is false, and the `allTime` preset legitimately produces a range with no `startDateTime` (`time-range.service.ts:148-151`), so every write-back of an `allTime` value reports a correction that did not happen (TR-BUG-04).
- **Eleven Jest cases, none of which touch the custom range.** `grep -n "toDate\|toTime" time-range.spec.ts` returns nothing: the from/to controls, the range validator, the apply/cancel round-trip and `writeValue` are entirely uncovered, which is exactly the surface where the P0 lives. There is no e2e fixture and no Playwright spec at all (TR-TEST-01).

Genuine strengths worth preserving: the locale layer is done properly — `kbqInjectLocaleConfiguration` with a dedicated token and an override provider (`time-range.ts:41-53`), and the configuration is a signal so `OnPush` descendants re-render on a locale switch. The service is a clean, testable seam: presets are data (`time-range.service.ts:33-54`), custom presets arrive through DI (`constants.ts:7-10`), and a missing `DateAdapter` produces a named error instead of a bare `NullInjectorError` (`time-range.service.ts:21-24, 56-63`). The editor correctly disables the from/to controls when a preset is selected and reads `controls.*.value` rather than `form.value` because disabled controls drop out of the latter — a subtlety most implementations get wrong, and the comment at `:260` says why.

## 3. Prioritized Findings (deduplicated, verified)

### P0 — Release blockers

**TR-BUG-01 · The custom range emits an end date taken from the time control, discarding the date the user picked** — `time-range-editor.ts:254-267` (the defect is `:263`); `time-range.service.ts:113-135, 160-170`; validator at `constants.ts:39-53`.
`mapTimeRange` assembles the value it hands to `calculateTimeRange`:
`fromTime: controls.fromTime.value`, `fromDate: controls.fromDate.value`, `toDate: controls.toTime.value`, `toTime: controls.toTime.value` (`:261-264`). The third line reads the **time** control into the **date** slot. `calculateTimeRange` then computes `endDateTime` as `combineDateAndTime(checkedRangeValue.toDate, checkedRangeValue.toTime)` (`time-range.service.ts:129-133`), and `combineDateAndTime` takes year, month and day from its first argument and hours, minutes, seconds and milliseconds from its second (`:160-170`). The calendar date of the end of the range therefore comes from whatever date object the *timepicker* holds — which `writeValue` seeded from the previously applied value (`time-range-editor.ts:230-238`) or which `getDefaultRangeValue()` set to today (`time-range.service.ts:88-98`). A user who opens the editor, selects "to: 20 September" and applies gets a range ending today at the chosen time. The start of the range is unaffected: `fromDate` is wired correctly one line above, which is the strongest evidence this is a typo — the same expression appears twice in a four-line object literal. The disagreement is worse than a wrong value: `rangeValidator` reads `form.fromDate`/`form.toDate` directly (`constants.ts:43-50`), so the form validates the range the user *sees* while the component emits a different one — a range the user drew as valid can be emitted inverted, and vice versa. Nothing in the repository would catch it: the Jest spec never mentions `toDate` or `toTime`, and there is no e2e fixture (TR-TEST-01).
**Fix:** change `:263` to `toDate: this.form.controls.toDate.value`. Then add the regression test that should have existed: set `type` to `'range'`, patch the four controls with a from/to pair whose dates differ, read the emitted `KbqTimeRangeRange`, and assert `endDateTime` carries the `toDate` day and the `toTime` clock. Add the mirror case for `startDateTime` so the correct half stays correct, and one e2e case that picks an end date in the calendar and asserts the applied title text. Because the emitted value has been wrong since the feature shipped, treat consumers persisting these ranges as data that may need correcting, and say so in the changelog.

### P1 — High

**TR-BUG-02 · Neither control implements `setDisabledState`, so a disabled form control stays fully interactive** — `time-range.ts:118, 238-249`; `time-range-editor.ts:91, 241-252`.
Both classes declare `implements ControlValueAccessor` and both implement exactly three of its four members: `writeValue`, `registerOnChange`, `registerOnTouched`. `setDisabledState` is optional in the interface, so nothing fails to compile — and nothing else disables the UI either: the trigger is a `kbq-link` whose `tabIndex` getter only reacts to *its own* `disabled` (`link.component.ts:81-83`), and no code path in `time-range` sets it. `form.get('timeRange')!.disable()` therefore leaves the trigger focusable and clickable, opens the popover normally, and lets Apply run `onChange` (`time-range.ts:219-223`) — Angular discards the value because the control is disabled, so the user sees the title update, the form value not change, and no explanation. The editor's own controls are equally unguarded: its inner `FormGroup` is enabled independently of the outer control's state. A disabled state that looks enabled is worse than one that is absent, because it invites the interaction and then swallows it.
**Fix:** implement `setDisabledState(isDisabled: boolean)` on both classes. On `KbqTimeRange`, store it in a signal, bind it to the trigger (`[disabled]` on the `kbq-link`, which already drops `tabindex` to `-1`) and to `kbqPopoverDisabled` so the popover cannot open; on `KbqTimeRangeEditor`, call `this.form.disable({ emitEvent: false })`/`enable()`. Add the host class the rest of the library uses for disabled controls so the visual state matches. Cover with a Jest case that disables the control, clicks the trigger and asserts no overlay attaches, plus one asserting `tabindex="-1"`.

**TR-API-01 · `KbqTimeRangeTitleAsControl` is a published `KbqFormFieldControl` whose every member is a stub** — `time-range-title-as-form-field.ts:16-72`; consumers `docs-examples/components/time-range/time-range-as-form-field/…:35-41` and `…/time-range-custom-option/…:87`.
The class satisfies the `KbqFormFieldControl` interface by declaration only. `id`, `placeholder`, `focused`, `empty`, `required`, `disabled` and `errorState` are declared with types and never assigned anywhere in the package (`:53-67`), so each reads `undefined` at runtime; `onContainerClick` and `focus` have empty bodies (`:69-71`); and `stateChanges` is created as a `Subject<void>` typed down to `Observable<void>` (`:49`) that nothing ever emits on. `KbqFormField` drives its label, its invalid styling, its cleaner and its click-to-focus behaviour off exactly those members and that stream, so a form field wrapping this control renders once against `undefined` state and never updates: it cannot float the label when the value appears, cannot show the error state when the bound control becomes invalid, and clicking the field does not focus anything. The one member that is wired — `ngControl` (`:51`) — is read from the host `KbqTimeRange`, which means the form field *can* see validity through the control and still not react, because nothing tells it to re-check. `[attr.tabindex]': '0'` is hardcoded on the host (`:39`), so the wrapper is a permanent tab stop even when the inner trigger is the real focus target.
**Fix:** implement the contract for real: derive `empty` and `value` from the host's `titleValue`, mirror `focused` from a `FocusMonitor` on the host element, mirror `disabled`/`required`/`errorState` from `ngControl`, generate `id` the way sibling controls do, make `focus()` delegate to the trigger and `onContainerClick()` open the popover, and `next()` `stateChanges` whenever any of them changes (an `effect()` over the signals is the smallest version). Until then, mark the class `@deprecated` in its JSDoc rather than leaving a published type that promises a contract it does not keep. Verify with a Jest case that wraps it in a `kbq-form-field`, makes the outer control invalid and asserts the field takes its error class.

### P2 — Should fix

**TR-BUG-03 · `onTouched` is registered and never called, so the control is never marked touched** — `time-range.ts:241, 246-249`; `time-range-editor.ts:244, 250-252`.
Both classes assign `onTouch = () => {}` and store the framework's callback in `registerOnTouched`, and neither ever invokes it — `grep -n "onTouch(" packages/components/time-range/` finds no call site. The control therefore stays `untouched` for its entire lifetime no matter how much the user interacts with it. Every error-display convention in this repo keys off that state: `ErrorStateMatcher` implementations show errors on `touched || submitted`, and `kbq-form-field` follows the matcher. A `Validators.required` on a time range consequently either never shows its message or shows it immediately, depending on the matcher — but never at the right moment. The natural call site already exists: the popover's visibility change handler (`time-range.ts:230-236`) runs exactly when the user has finished interacting.
**Fix:** call `this.onTouch()` in `onVisibleChange` when `isVisible` becomes `false`, and in the editor when the popover closes. Add a Jest case that opens and closes the popover and asserts `ngControl.touched` flips to `true`; and one asserting a `required` error surfaces only after that.

**TR-BUG-04 · `valueCorrected` fires for `allTime`, where nothing was corrected** — `time-range.ts:201-212`; `time-range.service.ts:148-151, 177-195`.
`writeValue` emits `valueCorrected` when `value && value.type && !('startDateTime' in value && availableTimeRangeTypes.includes(value.type))` (`:207-211`). The `allTime` preset resolves to `this.timeRangeConfig['allTime'].range ?? {}` (`time-range.service.ts:148-151`) — an empty object unless a consumer supplied a custom range — so a well-formed `allTime` value has no `startDateTime` key at all, the `in` test is false, and the emission fires on every write. Since `checkAndCorrectTimeRangeValue` returns that same shape back (`:187-192` recomputes it and gets `{}` again), the payload is identical to the input: the component reports a correction it did not make. Applications that use `valueCorrected` for its documented purpose — "Emit value update if provided value via formControl wasn't valid" (`time-range.ts:145-146`) — will write the value back, triggering another `writeValue`, another emission, and, if they push through the same form control, a loop bounded only by the framework's change-detection guard.
**Fix:** compare intent, not shape: emit only when `corrected` genuinely differs from `value` — a deep comparison of `type`/`startDateTime`/`endDateTime`, or an explicit flag returned from `checkAndCorrectTimeRangeValue` saying whether it changed anything. Test with an `allTime` value written twice, asserting zero emissions, and with an out-of-list type asserting exactly one.

**TR-ARCH-01 · The editor writes `errorState` imperatively onto the first timepicker only, bypassing `ErrorStateMatcher`** — `time-range-editor.ts:189-195`, `:53-57, 134`; template at `time-range-editor.html:29-33, 55-60`.
A `statusChanges` subscription reaches into the view query and assigns `timepickerList.at(0)!.errorState = status === 'INVALID'` (`:191-194`). Three problems follow. The editor renders **two** timepickers, from and to (`time-range-editor.html:32` and `:60`), and only index 0 is ever touched, so a range that fails `fromIsGreaterThanTo` marks the start field and leaves the end field looking valid — the field the user most likely needs to change. The write bypasses the mechanism the repo mandates for exactly this: `RangeErrorStateMatcher` is defined in this very file (`:53-57`) and instantiated (`:134`), so there is already a supported path. And mutating a child component's public field from a parent subscription is fragile in both directions — the child may recompute and clobber it, and the assignment relies on the view query being resolved when the first status arrives, which the non-null assertion papers over.
**Fix:** provide `rangeStateMatcher` to both timepickers through the `ErrorStateMatcher` DI token on the editor (or bind `[errorStateMatcher]` if the timepicker exposes it) and delete the subscription. Assert in Jest that both `kbq-form-field`s carry the invalid class when the from/to order is reversed — today only the first one does.

**TR-TEST-01 · Eleven cases, a snapshot, and no coverage of the range path, the validator or the CVA contract** — `time-range.spec.ts:51-215`, `__snapshots__/time-range.spec.ts.snap`; no `e2e.ts` and no `*.playwright-spec.ts` in the package.
The suite covers initialization, popover opening, radio preselection under three preset configurations, custom range types, the option template and the locale override provider — real cases, well written. What it never does is exercise the feature the component exists for: `grep -n "toDate\|toTime" time-range.spec.ts` returns nothing, so the from/to controls, `rangeValidator`, the apply/cancel round-trip, `writeValue`, `valueCorrected` and the disabled state are all unverified. That is precisely the surface holding TR-BUG-01, TR-BUG-02, TR-BUG-03 and TR-BUG-04 — four findings, one uncovered path. The first case leans on a stored snapshot (`__snapshots__/time-range.spec.ts.snap`, 33 lines), which pins rendered markup without asserting any behaviour and will be re-approved rather than investigated the first time it breaks. The package also has no e2e fixture and no Playwright spec, so nothing verifies the popover, the two calendars or the applied title in a real browser.
**Fix:** add a `describe('custom range')` block covering: emitted `startDateTime`/`endDateTime` for a from/to pair with different dates (the TR-BUG-01 guard), `fromIsGreaterThanTo` blocking Apply, cancel restoring the previous value, `writeValue` with `null` under both `nonNullable` settings, `valueCorrected` emission counts, and `setDisabledState`. Add `e2e.ts` + `e2e.playwright-spec.ts` with the editor open in light and dark, plus one interaction test that picks an end date and asserts the trigger text. Prefer explicit assertions to the snapshot; if it stays, scope it to a fragment whose churn is meaningful. Mutation check: reverting `:263` to `toTime` must fail at least one Jest case.

**TR-DOC-01 · One shipped example is unreachable from the docs, and no input is documented anywhere** — `time-range.en.md:1-27`, `examples.time-range.en.md:1-3`, `apps/docs/src/app/structure.ts:1043-1053`; orphan at `packages/docs-examples/components/time-range/time-range-as-form-field/`.
`packages/docs-examples/components/time-range/` ships seven examples. The guide embeds five (`time-range.en.md:3, 9, 15, 21, 27`) and the Examples tab — live here, since `structure.ts:1052` sets `hasExamples: true` — shows one more, `time-range-custom-option` (`examples.time-range.en.md:3`). `time-range-as-form-field` is referenced by no markdown file at all: it is compiled into `packages/docs-examples/example-module.ts:6408-6418` and rendered only in the dev app (`packages/components-dev/time-range/module.ts:19`), so the single demonstration of `KbqTimeRangeTitleAsControl` — the trickiest part of the public API, and the subject of TR-API-01 — is invisible to users of the documentation site. Separately, neither guide documents a single input: `nonNullable`, `showRangeAsDefault`, `availableTimeRangeTypes`, `defaultRangeValue`, `arrow`, `titleTemplate`, `optionTemplate`, `minDate`/`maxDate` and the `valueCorrected` output are described only in source JSDoc, and the DI tokens `KBQ_DEFAULT_TIME_RANGE_TYPES` / `KBQ_CUSTOM_TIME_RANGE_TYPES` (`constants.ts:7-10`) — the supported way to change the presets — appear in no guide.
**Fix:** embed `time-range-as-form-field` in the guide next to the trigger-customization section, or add it to `examples.time-range.*.md` alongside the option example. Add a properties table to both guides covering all nine inputs, the output, and a short section on providing presets through the two tokens, with the `nonNullable`/`valueCorrected` interaction spelled out — it is the least obvious behaviour in the component and currently has to be reverse-engineered from `writeValue`.

### P3 — Nice to have / hygiene

**TR-STYLE-01 · Missing structure files, a bare `module.ts`, and a banned structural directive** — `packages/components/time-range/` (no `*-tokens.scss`, no `_*-theme.scss`, no `e2e.ts`, no `e2e.playwright-spec.ts`); `module.ts:1-19`; `time-range-title.ts:20`, `time-range-editor.html:9-11`.
Against the layout AGENTS.md prescribes, the package is missing four files: `time-range-tokens.scss`, `_time-range-theme.scss` and the e2e pair. The absent theme files are defensible — `time-range.scss` is 58 lines of pure layout that reference only shared `--kbq-size-*` tokens and paint nothing — but the decision is nowhere recorded. The NgModule lives in `module.ts` rather than `time-range.module.ts`, one of only three packages that deviate (with `checkbox` and `datepicker`, which use hyphens instead). And both templates use `*ngTemplateOutlet` (`time-range-title.ts:20`, `time-range-editor.html:10`) where the repo has been migrating to native control flow; `ng-template` outlets have no `@`-block equivalent, so this is a convention question rather than a rule violation, but the surrounding code has moved on.
**Fix:** rename `module.ts` to `time-range.module.ts` (no API change — the class name and its export path are unchanged). Add a one-line comment at the top of `time-range.scss` recording that the package intentionally ships no colour tokens. Add the e2e pair together with TR-TEST-01. Leave the outlets unless the repo lands a convention for them.

**TR-A11Y-01 · Two unnamed `role="group"`s and an `aria-label` on a plain `<span>`** — `time-range.ts:96`, `time-range-editor.html:20, 26, 50`.
Three small accessibility gaps around otherwise sound markup. The popover footer wraps Apply and Cancel in `<div class="kbq-time-range__buttons" role="group">` (`time-range.ts:96`) and the editor wraps the range block in another `role="group"` (`time-range-editor.html:20`); neither has an accessible name, so a screen reader announces "group" twice with nothing to distinguish them — the role adds a boundary without adding information. The `from`/`to` prefixes carry `[attr.aria-label]` on a bare `<span>` (`:26, :50`), and `aria-label` is not honoured on an element with no role that supports naming, so the attribute is inert; the visible text is already the label, and what is actually missing is an association between that text and the input pair it introduces. Note none of these is an automated AXE failure — an unnamed group passes `aria-allowed-role` and `aria-required-attr`.
**Fix:** give both groups `[attr.aria-label]` from the locale configuration (the strings for "Apply"/"Cancel" and the range label already exist there), or drop `role="group"` where the grouping is purely visual. Replace the `aria-label` on the prefix spans with a real association: give each span an `id` and point the date and time inputs at it with `aria-labelledby`, so "from" is announced as part of each field's name. Verify with `jest-axe` plus explicit assertions on the computed accessible names.

## 4. Recommended Remediation Phases

**Phase 1 — Fix the emitted value.**
IDs: TR-BUG-01, TR-TEST-01 (the range cases only). One-character fix plus the tests that prove it, shipped together. Nothing else in this review matters if the component reports a range the user did not choose, and the missing tests are the reason it lasted.

**Phase 2 — Make the forms contract real.**
IDs: TR-BUG-02, TR-BUG-03, TR-BUG-04, TR-API-01. Implement `setDisabledState` on both classes, call `onTouched` when the popover closes, emit `valueCorrected` only on genuine corrections, and either implement or deprecate the form-field adapter. These are one coherent piece of work: they all concern what the component tells Angular's forms layer about itself.

**Phase 3 — Error surfacing and coverage.**
IDs: TR-ARCH-01, the remaining TR-TEST-01 items. Route the timepickers' error state through the `ErrorStateMatcher` that already exists in the file, then add the e2e fixture and Playwright spec — the component has none, and the popover plus two calendars is exactly the kind of surface screenshots are for.

**Phase 4 — Documentation, structure and accessibility polish.**
IDs: TR-DOC-01, TR-STYLE-01, TR-A11Y-01. Surface the orphan example, write the properties tables and the preset-token section, rename the module file, and name the two groups.

## 5. Verification Strategy

General gates, run sequentially (never in parallel — see `project_no_parallel_heavy_builds`):
- `npx jest packages/components/time-range`, plus `packages/components/datepicker`, `packages/components/timepicker` and `packages/components/radio` — the editor composes all three and Phase 3 touches their error state.
- `yarn run eslint`, `yarn run stylelint`, `yarn run prettier` on touched files.
- `yarn run build:components`, then `yarn run check-api`; `approve-api` only if Phase 2 changes the published surface (adding `setDisabledState` does).
- `yarn run e2e:docker` once the fixture from Phase 3 exists; baselines only via `yarn run e2e:docker:update-snapshots`.
- Manual smoke: `yarn run dev:time-range` (its module renders the orphan form-field example, which is the fastest way to see TR-API-01).

Per-phase assertions:
- **Phase 1:** with `type: 'range'`, `fromDate` 1 Sep 10:00 and `toDate` 20 Sep 18:00, the emitted value's `endDateTime` falls on 20 September at 18:00. Reverting `time-range-editor.ts:263` to `toTime` fails that case. The applied trigger text names both dates.
- **Phase 2:** `control.disable()` leaves the trigger with `tabindex="-1"` and clicking it attaches no overlay. Opening and closing the popover marks the control `touched`. Writing the same `allTime` value twice emits `valueCorrected` zero times. A `kbq-form-field` around `kbq-time-range-title-as-control` takes its invalid class when the bound control is invalid — or the class is deprecated and the guide says so.
- **Phase 3:** reversing from/to marks **both** `kbq-form-field`s invalid; the `statusChanges` subscription is gone and the behaviour is unchanged. Playwright renders the open editor in light and dark.
- **Phase 4:** every input appears in both guides; `time-range-as-form-field` renders on the docs site; `module.ts` is gone with no import churn outside the package; the two groups report accessible names.

## Appendix A — Review Methodology

Findings were gathered by reading the whole package (`time-range.ts`, `time-range-editor.ts` + its 97-line template, `time-range-title.ts`, `time-range-title-as-form-field.ts`, `time-range.service.ts`, `constants.ts`, `types.ts`, the SCSS, the 292-line Jest spec and its snapshot, both guides and both examples files), then following each candidate outward: into `KbqDateAdapter`'s contract to establish what `combineDateAndTime` actually does with its two arguments; into `link.component.ts` to check whether the trigger is keyboard-reachable; into `datepicker.component.ts`/`datepicker-input.directive.ts` to check which of the two min/max surfaces the editor binds; into the seven docs examples and the dev app to find which are reachable; and into the API guard report and the docs navigation. The P0 was found by reading the four-line object literal at `time-range-editor.ts:261-264` against `combineDateAndTime`, and confirmed as unguarded by grepping the spec for the control names.

Refuted during verification:
- **"The popover trigger is not keyboard reachable, because it is an `<a>` with no `href`"** — refuted. `KbqLink` binds `'[attr.tabindex]': 'tabIndex'` with a getter defaulting to `0` (`link.component.ts:47, 81-89`), so the pseudo-link is a tab stop and the popover's keyboard triggers work.
- **"The documented min/max restriction only validates and does not limit the calendar"** — refuted. The editor binds *both* surfaces: `[min]`/`[max]` on the two inputs (`time-range-editor.html:37-38, 61-62`) and `[minDate]`/`[maxDate]` on the two `<kbq-datepicker>` panels (`:44, :68`). This is the split the library intends, and it is done correctly here.
- **"`KbqTimeRangeService.add()` mutates a config shared by every instance"** — refuted. The service is listed in `KbqTimeRange`'s own `providers` (`time-range.ts:111`), so each component instance constructs its own service and its own `timeRangeConfig` object literal (`time-range.service.ts:33-54`). Custom types registered through DI are applied per instance.
- **"Reading input signals in the constructor yields defaults rather than bound values"** — true but handled, not a defect. `KbqTimeRange.ngOnInit` re-runs `writeValue` for exactly this reason, with a comment saying so (`time-range.ts:190-193`), and `KbqTimeRangeEditor.ngOnInit` re-seeds its form from the resolved inputs (`time-range-editor.ts:198-209`).
