# Koobiq `actions-panel` Component — Code Review & Improvement Plan

> Scope: `packages/components/actions-panel` (service, overlay container, ref, config, tokens, SCSS, Jest spec, e2e fixture + Playwright spec, user guides, docs examples, dev app, API guard report) · Commit `b665e503` · 2026-08-28
> Generated by a multi-dimension review (architecture, RxJS/lifecycle, correctness, accessibility, performance, public API/types, styles, tests, docs) with manual verification of every finding against the source, against the `@angular/cdk` 20.2.14 dialog implementation the component inherits from, against `axe-core` 4.12.1, and against every in-repo consumer. 13 findings confirmed (P0×1, P1×3, P2×5, P3×4); 7 candidate findings refuted during verification (see Appendix A). This document is a review + roadmap; no source is modified by it.

## 1. Executive Summary

`KbqActionsPanel` is a service-driven bottom bar for bulk actions on a selection: `open()` returns a `KbqActionsPanelRef`, the panel slides up from the bottom of the viewport, and it stays open *alongside* the content the user is acting on. It is built on `@angular/cdk/dialog` — the only place in the repository that imports `@angular/cdk/dialog` at all — and that inheritance is where its most serious problem comes from.

- **Opening the panel marks the entire application `aria-hidden="true"`.** The container calls `this._trapFocus()` when the entrance animation finishes (`actions-panel-container.ts:211-214`). Because `autoFocus` is hard-coded to `null` (`actions-panel.ts:147`), that call moves no focus at all; its *only* surviving effect is `this._focusTrapped.next()` (`dialog.mjs:344`), which is exactly the signal CDK's `Dialog` waits for before calling `_hideNonDialogContentFromAssistiveTechnology` (`dialog.mjs:615-618`). Every sibling of the overlay container in `<body>` — i.e. the whole app root, including the table whose rows the user just selected — gets `aria-hidden="true"` (`dialog.mjs:809-822`) and stays hidden until the panel closes. The panel is non-modal by design (`hasBackdrop: false`, no focus trap, page still scrollable and clickable), so this hides content that is still fully interactive, and nothing announces the panel's arrival to compensate (APN-A11Y-01).
- **The container renders `role="dialog"` with no accessible name.** The host bindings are inherited verbatim from `CdkDialogContainer` (`dialog.mjs:418-423`, merged by `ɵɵInheritDefinitionFeature`, `debug_node.mjs:16778-16789`), and `DialogConfig.role` defaults to `'dialog'` (`dialog.mjs:50`) while `ariaLabel`/`ariaLabelledBy` default to `null`. axe-core's `aria-dialog-name` rule (serious, `axe.js:31810-31821`) fires on exactly this shape. `KbqActionsPanelConfig` exposes no way for a consumer to set a name or change the role (APN-A11Y-02).
- **`kbqActionsPanelDefaultConfigProvider` replaces the defaults instead of merging them.** `open()` builds its config as `{ ...defaultConfig, ...config }` (`actions-panel.ts:105-108`), so a consumer who provides `kbqActionsPanelDefaultConfigProvider({ disableClose: true })` loses `scrollStrategy`, `direction`, `closeOnNavigation` and `data` in one move. The most visible consequence: with `scrollStrategy` gone, CDK falls back to `DIALOG_SCROLL_STRATEGY` (`dialog.mjs:543-548, 670`) — a **block**-scroll strategy — so the page silently stops scrolling while the actions panel is open, the opposite of the documented `RepositionScrollStrategy` default (`actions-panel-config.ts:89-94`). The one test covering this provider asserts only that the close button disappears (`actions-panel.spec.ts:516-523`) (APN-BUG-01).
- **`ESCAPE` closes the panel only if focus is already inside it.** The service hard-codes `disableClose: true` on the CDK dialog (`actions-panel.ts:154`), disabling `DialogRef`'s body-level ESC handler, and re-implements closing with a host listener `(keydown.escape)` on the container (`actions-panel-container.ts:124`). Host listeners only see events that bubble through the element, and nothing ever moves focus into the panel, so in the normal case — focus still on the page — ESC does nothing. Both guides state flatly that "the `ESCAPE` key closes `KbqActionsPanel`" (`actions-panel.en.md:27`, `actions-panel.ru.md:27`) (APN-BUG-02).

Genuine strengths worth preserving: this is one of the better-tested packages in the library — 43 Jest cases covering open/close from both a component and a `TemplateRef`, both result-carrying close paths, `beforeOpened`/`afterOpened`/`beforeClosed`/`afterClosed` ordering and completion, navigation, destroy, RTL, custom overlay containers, and the `overlayContainer` max-width clamp. The animation/ref handshake has a real fallback timeout for the case where the animation never reports done (`actions-panel-ref.ts:92-95`), the resize subscription is correctly torn down with `takeUntil(afterClosed)` (`actions-panel.ts:198-205`), `syncOverlayMaxWidth` short-circuits when nothing changed so it does not thrash the position strategy (`actions-panel.ts:211-223`), styling is fully token-driven with zero hardcoded colours, and the close button's label comes from the locale layer rather than a hardcoded string (`actions-panel-container.ts:101-102`). The defects are concentrated in what the component inherited from the CDK without auditing, and in the contract its documentation publishes.

## 3. Prioritized Findings (deduplicated, verified)

### P0 — Release blockers

**APN-A11Y-01 · Opening the panel marks the entire application `aria-hidden="true"`, and nothing announces the panel** — `actions-panel-container.ts:211-217, 243-245`, `actions-panel.ts:143-154`; CDK mechanism at `node_modules/@angular/cdk/fesm2022/dialog.mjs:211-214, 307, 340-344, 610-622, 786-807, 809-824`.
The chain is short and entirely verifiable. `KbqActionsPanelContainer` overrides `_contentAttached()` to do nothing but apply `containerClass` (`actions-panel-container.ts:243-245`) and never calls `super._contentAttached()`, so `_initializeFocusTrap()` (`dialog.mjs:399-406`) never runs and `_focusTrap` stays `null` — deliberate, and correct for a non-modal bar. But `onAnimationDone` still calls `this._trapFocus()` when the panel becomes visible (`actions-panel-container.ts:211-214`). With `autoFocus` hard-coded to `null` (`actions-panel.ts:147`), `_trapFocus` falls through its `switch` to `default: this._focusByCssSelector(this._config.autoFocus)` (`dialog.mjs:340-341`), which resolves to `querySelector('null')` and matches nothing — the spec confirms the intent, asserting `document.activeElement` is still `BODY` after opening (`actions-panel.spec.ts:393-401`). What the call *does* accomplish is `this._focusTrapped.next()` (`dialog.mjs:344`). `Dialog.open` subscribes to that stream for the first dialog it opens and, on the first emission, calls `_hideNonDialogContentFromAssistiveTechnology` (`dialog.mjs:610-618`), which walks the overlay container's siblings in `<body>` and sets `aria-hidden="true"` on every one of them that is not a `<script>`, `<style>` or `aria-live` region (`dialog.mjs:809-822`). The attribute is only restored when `openDialogs` drains (`dialog.mjs:786-807`).
For a modal dialog that is correct: focus is trapped inside, a backdrop blocks the page, so nothing outside is reachable. None of that holds here. The actions panel sets `hasBackdrop: false` (`actions-panel.ts:148`), installs no focus trap, and by design leaves the underlying table selectable and scrollable — that is the entire point of the component. So while the panel is open, a screen-reader user can still Tab into, click on and scroll the page, but the page reports nothing: the table, its selection state, the row count the panel is describing, all silent. And because focus is never moved and there is no `aria-live` region or `LiveAnnouncer` call anywhere in the package, the panel's appearance is not announced either — the user's entire experience of "I selected three rows and an action bar appeared" is that the application went quiet. This is a WCAG 1.3.1 / 4.1.2 failure, it is triggered on every single open, and `KbqActionsPanelConfig` (`actions-panel-config.ts:28-102`) exposes no option that avoids it. Note it is *not* an automated axe failure, and the reason is itself a finding — see the Refuted list and APN-A11Y-02.
**Fix:** stop calling `_trapFocus()`. `onAnimationDone` needs it for nothing: no trap exists, `autoFocus` is null, and the spec already asserts that focus must not move. Deleting the call at `actions-panel-container.ts:213` removes the `_focusTrapped` emission and therefore the page-wide `aria-hidden` — verify by asserting in Jest that `document.body.firstElementChild` has no `aria-hidden` attribute while a panel is open. Then add the announcement the component currently lacks: inject `LiveAnnouncer` in the container and announce on `afterOpened` using a new locale string in `KbqActionsPanelLocaleConfiguration` (`packages/components/core/locales/types.ts:57-61`), or give the container `role="region"` + an accessible name (APN-A11Y-02) and a documented `focusPanel()` on the ref so a consumer can move focus deliberately. Guard with a `jest-axe` case plus a DOM assertion on the siblings of `.cdk-overlay-container`.

### P1 — High

**APN-A11Y-02 · The container renders `role="dialog"` with no accessible name, and the role is wrong for a non-modal action bar** — `actions-panel-container.ts:118-125` (host block), `actions-panel-config.ts:28-102`; inherited from `node_modules/@angular/cdk/fesm2022/dialog.mjs:50, 82-84, 90, 414-423`; axe rule at `node_modules/jest-axe/node_modules/axe-core/axe.js:31810-31821`.
`KbqActionsPanelContainer` extends `CdkDialogContainer` and declares its own `host` object with a class, an RTL class, the animation bindings and the escape listener — no ARIA at all. That is not the end of the story: Angular's `ɵɵInheritDefinitionFeature` chains the superclass `hostBindings` function ahead of the subclass's (`node_modules/@angular/core/fesm2022/debug_node.mjs:16778-16789`) and merges static `hostAttrs` across the inheritance chain (`:16731-16742`). So the rendered element carries `tabindex="-1"`, `class="cdk-dialog-container kbq-actions-panel-container"`, `id="cdk-dialog-N"`, `aria-modal="false"` and — the problem — `role="dialog"`, because `DialogConfig.role` defaults to `'dialog'` (`dialog.mjs:50`) and `KbqActionsPanelConfig` never overrides it. `ariaLabel` and `ariaLabelledBy` default to `null` (`dialog.mjs:82-84`) and the panel provides no heading, so the dialog has no accessible name whatsoever.
Two consequences. First, this is a reproducible automated failure: axe-core 4.12.1's `aria-dialog-name` rule selects `[role="dialog"], [role="alertdialog"]` and requires one of `aria-label`, `aria-labelledby` or a non-empty `title` (`axe.js:31810-31821`); impact `serious`. AGENTS.md states the library MUST pass all AXE checks, and no spec in this package runs `jest-axe` today, which is why it has survived. Second, `role="dialog"` is semantically wrong: this is a persistent, non-modal toolbar that coexists with the content, not a dialog that interrupts it — and the wrong role has a nasty side effect, since axe's `focusable-modal-open` check treats *any* visible `[role=dialog]` as proof that a modal is open (`axe.js:17666-17670`), which is what suppresses the `aria-hidden-focus` rule that would otherwise have caught APN-A11Y-01 years ago. The wrong role is hiding the worse bug.
**Fix:** set the role explicitly in the container's host block — `'[attr.role]': "config.role ?? 'region'"` — and add `role?: string` plus `ariaLabel?: string` to `KbqActionsPanelConfig`, threading `ariaLabel` into the CDK config so the inherited `[attr.aria-label]` binding picks it up. Default the accessible name from the locale layer (a new `KbqActionsPanelLocaleConfiguration` entry alongside `closeTooltip`) so an unconfigured panel is still named. Also bind `[attr.aria-modal]` to `null` rather than inheriting `false`, which is noise on a non-dialog role. Guard with a `jest-axe` `toHaveNoViolations()` case over an opened panel — it fails today and must pass after — plus a Jest assertion that the host reports `role="region"` with a non-empty accessible name.

**APN-BUG-01 · `kbqActionsPanelDefaultConfigProvider` replaces the whole default config, silently switching the scroll strategy to block-scroll** — `actions-panel-config.ts:6-19, 89-101`, `actions-panel.ts:105-108, 155`; CDK fallback at `node_modules/@angular/cdk/fesm2022/dialog.mjs:543-548, 670`; test gap at `actions-panel.spec.ts:516-523`.
`KBQ_ACTIONS_PANEL_DEFAULT_CONFIG`'s factory returns `new KbqActionsPanelConfig()` (`actions-panel-config.ts:8`), whose five initialized fields (`data`, `closeOnNavigation`, `direction`, `scrollStrategy`, `disableClose`) are its only own properties — `tsconfig.json:26` sets `useDefineForClassFields: false`, so the uninitialized ones do not exist on the instance. `kbqActionsPanelDefaultConfigProvider` binds the token with a plain `useValue` (`:16-19`) typed as `KbqActionsPanelConfig<D>`, a class whose members are all optional, so `{ disableClose: true }` type-checks. `open()` then merges `{ ...this.defaultConfig, ...config }` (`actions-panel.ts:105-108`) — one flat spread, no per-field defaulting — and the four sibling defaults are simply gone.
The user-visible fallout is the scroll strategy. `openDialog` passes `scrollStrategy: config.scrollStrategy && config.scrollStrategy(this.overlay)` (`actions-panel.ts:155`), which now evaluates to `undefined`; CDK's `_getOverlayConfig` reads `config.scrollStrategy || this._scrollStrategy()` (`dialog.mjs:670`) and `DIALOG_SCROLL_STRATEGY`'s root factory returns a **block**-scroll strategy (`dialog.mjs:543-548`). So an app that customises one unrelated default gets a panel that freezes page scrolling — the exact opposite of the documented `RepositionScrollStrategy` default (`actions-panel-config.ts:89-94`) and directly contrary to the component's purpose, since the user is meant to keep scrolling the table while the bar is up. `closeOnNavigation` and `direction` happen to land on the same values via `DialogConfig`'s own defaults, and `data` degrades from `null` to `undefined`, so the scroll strategy is the one that actually bites. The existing test provides `{ disableClose: true }` and asserts only that the close button is absent (`actions-panel.spec.ts:516-523`), so nothing catches it. The provider is also documented nowhere in the guides — neither `actions-panel.en.md` nor `.ru.md` mentions it.
**Fix:** make the merge explicit rather than a spread. Either type the provider's parameter as `Partial<KbqActionsPanelConfig<D>>` and have the factory return `Object.assign(new KbqActionsPanelConfig(), config)`, or merge against a fresh instance inside `open()`: `const _config = { ...new KbqActionsPanelConfig(), ...this.defaultConfig, ...config }`. Prefer the first — it keeps `KBQ_ACTIONS_PANEL_DEFAULT_CONFIG` a complete config for anyone who injects it directly. Add a Jest case that provides `kbqActionsPanelDefaultConfigProvider({ disableClose: true })`, opens a panel with no per-call config, and asserts the applied scroll strategy is a `RepositionScrollStrategy` (spy through a custom `scrollStrategy` factory, as `actions-panel.spec.ts:448-458` already does), and document the provider in both guides next to the `disableClose` paragraph.

**APN-BUG-02 · `ESCAPE` closes the panel only when focus is already inside it; both guides claim otherwise** — `actions-panel-container.ts:124, 233-238`, `actions-panel.ts:154`, `actions-panel.en.md:25-27`, `actions-panel.ru.md:25-27`; test that hides it at `actions-panel.spec.ts:172-188`.
The service passes `disableClose: true` to the CDK dialog unconditionally (`actions-panel.ts:154`, with the comment "Disable closing since we need to sync it up to the animation ourselves"), which switches off `DialogRef`'s own ESC handling (`dialog.mjs:469-474`). CDK's handler is fed by `OverlayKeyboardDispatcher`, which listens on `body` and routes the event to the top-most overlay *regardless of where focus is* (`node_modules/@angular/cdk/fesm2022/overlay-module.mjs:541-568`) — precisely so components that keep focus on a trigger still respond to ESC. The replacement is a host listener, `'(keydown.escape)': 'handleEscape($event)'` (`actions-panel-container.ts:124`), which only fires for events that bubble through `<kbq-actions-panel-container>`. Nothing ever moves focus into that element: `autoFocus` is `null` (`actions-panel.ts:147`), there is no focus trap (APN-A11Y-01), and the spec explicitly asserts focus stays on `BODY` after opening (`actions-panel.spec.ts:393-401`). The overlay is appended at the end of `<body>`, so reaching the panel by keyboard means tabbing past the entire page first.
The result is that in the normal interaction — select rows in a table, panel appears, press ESC — nothing happens. Both guides state the opposite as a plain fact: "By default, the `ESCAPE` key closes `KbqActionsPanel`" (`actions-panel.en.md:27`, `actions-panel.ru.md:27`). The two Jest cases that cover ESC (`actions-panel.spec.ts:172-188`) dispatch the event directly on the container element, so they exercise the one situation in which the listener does fire and pass while the real interaction fails — a textbook example of a test that encodes the implementation instead of the behaviour.
**Fix:** subscribe to the ref's already-exposed `keydownEvents` stream (`actions-panel-ref.ts:22`, fed by the body-level dispatcher) instead of, or in addition to, the host listener: filter on `ESCAPE` with `!hasModifierKey(event)` and call `close()` when `!config.disableClose`. Keep the host listener so a panel that *does* have focus still closes on ESC without depending on overlay ordering. Note the interaction with stacked overlays — because `DialogRef` already subscribes to `keydownEvents`, this overlay is a candidate target for the dispatcher whether or not it acts (`overlay-module.mjs:563-566`), so re-test with a `kbq-dropdown` open from inside the panel to confirm ESC still closes the dropdown first. Replace the two container-dispatched Jest cases with cases that dispatch on `document.body`.

### P2 — Should fix

**APN-DOC-01 · The `overlayContainer` section documents behaviour the option does not have, and neither snippet in it is usable** — `actions-panel.en.md:76-112`, `actions-panel.ru.md:76-112`, `actions-panel.en.md:50-65`, `actions-panel.ru.md:50-65`; actual behaviour at `actions-panel.ts:156-165, 193-206`, `actions-panel-config.ts:52-55`.
The section opens with "`OverlayContainer` determines where in the DOM tree the actions panel will be displayed. By default - in the document body" and then, under "Configuring container for a specific panel", tells the reader that to "display the actions panel in a specific element (for example, inside a Sidebar)" they should use the `overlayContainer` option. That is not what the option does. `KbqActionsPanelConfig.overlayContainer` is consumed in exactly two places: it becomes the origin of a `flexibleConnectedTo` position strategy (`actions-panel.ts:156-164`) and the source element for the max-width clamp (`:193-206`). The overlay element itself is created by `Dialog` through `createOverlayRef(this._injector, …)` and stays in the global CDK overlay container in `<body>` — a consumer who follows the guide gets a panel that is *positioned over* the sidebar but lives outside it, so it escapes the sidebar's `overflow` clipping and stacking context. The two concepts share a name and the guide conflates them; the config's own JSDoc ("Element in which the actions panel overlay will be connected to", `actions-panel-config.ts:52-55`) is ambiguous enough to have invited it.
Both snippets in the surrounding prose are also broken as written. The "Global container configuration" block ends with an `@NgModule({...})` decorator followed by nothing (`actions-panel.en.md:109-112`, `.ru.md:109-112`) — it does not parse. The `KBQ_ACTIONS_PANEL_DATA` snippet imports `Component, Inject` but calls `inject()`, which it never imports, and references `KbqActionsPanelRef`, which it never imports either (`actions-panel.en.md:50-65`, `.ru.md:50-65`); both `const actionsPanelRef = …` assignments in the guide are also unused locals, which `tsconfig.json:17` (`noUnusedLocals`) would reject in real code.
**Fix:** rename the concept in the prose. Keep "Managing OverlayContainer" for the CDK `OverlayContainer` provider only, and move `overlayContainer` into its own section titled after what it does — anchoring the panel to an element and clamping its width to that element's width — with an explicit sentence saying the overlay still lives in the document body. Rename the config member to `anchor` (or `connectedTo`) behind a deprecated alias, and rewrite its JSDoc. Fix both snippets: complete the `@NgModule` with a class, import `inject` and `KbqActionsPanelRef`, and drop the unused `const`. `yarn run e2e:docs` compiles the guide snippets, so a corrected snippet stays corrected.

**APN-LIFE-01 · `beforeOpened`/`afterOpened` never complete when a panel is superseded before it opens, and `animationStateChanged` is never completed** — `actions-panel-ref.ts:17-19, 70-78, 81-103, 105-125`, `actions-panel-container.ts:141, 165-168`, `actions-panel.ts:117-124`.
`KbqActionsPanel.open()` supports opening a second panel while a first is still up: it queues `actionsPanelRef.open()` on the outgoing panel's `afterClosed` and closes the outgoing one (`actions-panel.ts:117-122`). The new ref's overlay is attached immediately, but its `open()` — the call that emits `beforeOpened` and starts the entrance animation (`actions-panel-ref.ts:70-78`) — is deferred. If a *third* `open()` arrives in that window, the queued ref is closed before it ever opened: `close()` guards on `containerInstance` and nulls it (`:81-103`), so the deferred `open()` becomes a no-op (`:71-73`). At that point `beforeOpenedSubject` (a `ReplaySubject`) and `afterOpenedSubject` have neither emitted nor completed, and nothing will ever complete them. A consumer doing `await lastValueFrom(ref.afterOpened)` — a natural pattern the spec itself uses for the closing streams (`actions-panel.spec.ts:272, 321`) — hangs forever, and the subscription is retained for the lifetime of the ref. `close()` is careful to complete `beforeClosedSubject` (`:99-100`); the opening pair gets no equivalent.
Separately, `animationStateChanged` (`actions-panel-container.ts:141`) is an `EventEmitter` that the container never completes — `ngOnDestroy` calls `super.ngOnDestroy()` and sets a flag (`:165-168`), while `CdkDialogContainer.ngOnDestroy` completes only its own `_focusTrapped` (`dialog.mjs:222-227`). Every `take(1)` subscription on it that never receives its event (`actions-panel-ref.ts:86-96, 106-114, 116-124`) stays live and keeps the container instance — and therefore its detached view — reachable from the ref for as long as the consumer holds the ref. The published examples do release the ref in `afterClosed` (`packages/docs-examples/components/actions-panel/actions-panel-overview/actions-panel-overview-example.ts:77-80`), but `afterClosed` is the stream that does not emit on this path.
**Fix:** in `close()`, complete `beforeOpenedSubject` and `afterOpenedSubject` alongside `beforeClosedSubject` when the panel is closed before it opened, so `lastValueFrom` resolves-or-completes instead of hanging. In `KbqActionsPanelContainer.ngOnDestroy`, call `this.animationStateChanged.complete()` before `super.ngOnDestroy()`. Add Jest cases: open A, open B, open C without awaiting, then assert (a) B's `afterOpened` completes, (b) only C's container is in the DOM after `whenStable()`, and (c) `document.querySelectorAll('.kbq-actions-panel-container').length === 1`. The three-deep open sequence is entirely untested today.

**APN-CSS-01 · The vertical-divider recipe is a private container class, so published examples hand-copy it including `!important`** — `actions-panel-container.scss:21-25`, `actions-panel-tokens.scss:10-16`, `actions-panel-container.ts:96`; duplicated at `packages/docs-examples/components/actions-panel/actions-panel-adaptive/actions-panel-adaptive-example.ts:118-122` and `packages/docs-examples/components/actions-panel/actions-panel-custom-counter/actions-panel-custom-counter-example.ts:151-155`.
The container styles its own divider through `.kbq-actions-panel-container__vertical-divider` (`actions-panel-container.scss:21-25`) — a BEM *element* class of a `@docs-private` internal component, applied in a template consumers cannot see (`actions-panel-container.ts:96`). Panel content is projected inside `.kbq-actions-panel-container`, so the rule *would* apply to a consumer's `<kbq-divider>` if they knew the class name; nobody does. The result is visible in the repository: two of the five shipped examples reproduce the three declarations verbatim under their own class names, `!important` and all —
`background-color: var(--kbq-actions-panel-vertical-divider-background-color); height: var(--kbq-actions-panel-vertical-divider-height) !important; margin: var(--kbq-actions-panel-vertical-divider-margin);`
— which means the library's own documentation teaches consumers to `!important` past a library component's styles. (The `!important` itself is the consumer-side workaround for DIV-CSS-01, filed in `REVIEW.divider.md`: `.kbq-divider_vertical`'s `height: 100%` collapses to zero in the flex row the panel is, and `.kbq-divider.kbq-divider_vertical` outranks a single consumer class. Fixing DIV-CSS-01 removes the need for the `!important` here but not the need for a public class.)
**Fix:** publish the recipe. Either (a) style `.kbq-actions-panel-container .kbq-divider` directly in `actions-panel-container.scss` so any projected divider inherits the panel's treatment with no class at all, or (b) name a public modifier — `.kbq-actions-panel-divider` — document it in both guides, apply it to the container's own divider, and rewrite both examples to use it. (a) is preferable: it is what a consumer expects and it deletes the duplication rather than relocating it. Either way, delete the copied blocks from the two examples; their removal is the acceptance criterion. Land this after DIV-CSS-01 so the `!important` can go too, and refresh the Playwright baselines through `yarn run e2e:docker:update-snapshots`.

**APN-TEST-01 · An unawaited Playwright action, and zero coverage of role, ARIA, focus or announcement** — `e2e.playwright-spec.ts:23-34` (specifically `:30`), `actions-panel.spec.ts` (43 cases, none a11y-related), `e2e.ts:1-89`.
`e2e.playwright-spec.ts:30` reads `getOverflowItemsResultButton(page).click();` with no `await` — the only unawaited action in the file, sitting immediately before `await expect(screenshotTarget).toHaveScreenshot('2-light.png')` on the next line. `toHaveScreenshot` retries until two consecutive frames match, so the assertion usually converges on whichever state wins the race, but the dropdown open and the screenshot are genuinely unordered, and `2-dark.png` is captured two lines later from the same unresolved state. Nothing catches this: the repo's ESLint config has no type-aware `no-floating-promises`, and the e2e override block (`eslint.config.js:479-500`) adds none.
The Jest suite's 43 cases are broad on the service/ref/config surface but assert nothing about the rendered accessibility of the panel: no case reads `role`, `aria-label`, `aria-hidden`, `aria-modal` or `document.activeElement` beyond the one "should not autoFocus" check (`:393-401`), and no case runs `jest-axe`. That is why APN-A11Y-01 and APN-A11Y-02 are both invisible to CI. Two behavioural gaps are also uncovered: the default-config merge (see APN-BUG-01) and the three-deep open sequence (see APN-LIFE-01). Note that all committed screenshots were captured with `reducedMotion: 'reduce'` (`playwright.config.ts:101`, applied to every browser context), so they show the settled state and would not catch an animation-timing regression in any case.
**Fix:** add the missing `await` at `e2e.playwright-spec.ts:30`, and add an explicit `await expect(dropdownPanel).toBeVisible()` before the screenshot so the ordering is asserted rather than assumed. Add a `jest-axe` case that opens a panel over a small host page and asserts `toHaveNoViolations()` — it fails today on `aria-dialog-name` and must pass after APN-A11Y-02. Add DOM assertions for the `aria-hidden` state of `document.body`'s children while a panel is open (APN-A11Y-01) and for the role/name after APN-A11Y-02. Add the two behavioural cases named in APN-BUG-01 and APN-LIFE-01. Keep the e2e fixture as it is otherwise — its three-way resize assertions (`e2e.playwright-spec.ts:36-67`) are assertion-based rather than screenshot-based and are the best part of the suite.

**APN-API-01 · `KbqActionsPanelRef.containerInstance` is typed non-nullable but is `null` after `close()`** — `actions-panel-ref.ts:11-15, 56-63, 71-73, 81-83, 102`; API report at `tools/public_api_guard/components/actions-panel.api.md:113`.
`containerInstance` is a public, mutable, non-optional field typed `KbqActionsPanelContainer` (`actions-panel-ref.ts:15`), and `close()` assigns `this.containerInstance = null!` (`:102`) — the `!` exists precisely to defeat `strictNullChecks` (`tsconfig.json:21`). Internally the class copes by guarding `if (!this.containerInstance) return;` in both `open()` and `close()` (`:71-73, 81-83`), guards TypeScript believes are dead because the type says the field is always present. Externally the field is fully public in the API report (`actions-panel.api.md:113`), so `actionsPanelRef.containerInstance.animationStateChanged` type-checks and throws at runtime any time it is read after close — and the ref survives its container by design, since `afterClosed` fires later. The `@docs-private` tag on the member is a docs-site directive, not an access control.
Two smaller type issues in the same report: `protected readonly config: KbqActionsPanelConfig<any>` (`actions-panel.api.md:73`) leaks an `any` into the public surface — `inject(KbqActionsPanelConfig)` on a generic class widens `D` to `any` — and `protected _contentAttached(): void` (`:74`) publishes a CDK-internal override in the report.
**Fix:** type the field `KbqActionsPanelContainer | null`, drop the `null!` non-null assertion, and let the existing guards become meaningful. This changes `actions-panel.api.md`, so run `yarn run build:components` then `yarn run approve-api` — build first, the guard reads `dist/*.d.ts`. Consumers reading `containerInstance` will now get a compile error where they previously got a runtime one, which is the point; no in-repo call site reads it. Narrow the container's config injection to `inject<KbqActionsPanelConfig>(KbqActionsPanelConfig)` to remove the `any`.

### P3 — Nice to have / hygiene

**APN-STYLE-01 · Entrance and exit animation durations are swapped** — `actions-panel-container.ts:61-74`; constants at `packages/components/core/animation/animation.ts:20-27`.
The exit transition `'visible => void, visible => hidden'` animates for `KbqAnimationDurations.Entering` (`:64`) and the entrance transition `'void => visible'` animates for `KbqAnimationDurations.Exiting` (`:71`). The constants are `Entering = '150ms'` and `Exiting = '125ms'` (`animation.ts:23-24`), so the panel currently takes 125ms to appear and 150ms to leave — the design system's intent inverted. The user-visible difference is 25ms, so this is cosmetic, but it is a plain transposition that will confuse the next reader and any timing that is derived from it (`actions-panel-ref.ts:92-95` computes its fallback from the reported `totalTime`, so it stays correct either way).
**Fix:** swap the two constants. No test asserts on duration; if you want one, assert `totalTime` in the `animationStateChanged` `'start'` event for each direction under `BrowserAnimationsModule` rather than `NoopAnimationsModule`. Screenshots are unaffected — `playwright.config.ts:101` sets `reducedMotion: 'reduce'` for every context and `toHaveScreenshot` waits for the frame to settle regardless.

**APN-STYLE-02 · The host inherits the `cdk-dialog-container` class without CDK's stylesheet — a dormant specificity collision** — `actions-panel-container.ts:118-119`, `actions-panel-container.scss:1-12`; inheritance at `node_modules/@angular/core/fesm2022/debug_node.mjs:16731-16742`; CDK styles at `node_modules/@angular/cdk/fesm2022/dialog.mjs:410`.
`mergeHostAttrsAcrossInheritance` merges the superclass's static `hostAttrs` into the subclass definition, so every `<kbq-actions-panel-container>` renders with `class="cdk-dialog-container kbq-actions-panel-container"`. Component `styles` are *not* inherited, and `actions-panel` is the only importer of `@angular/cdk/dialog` in the repository (verified by grep across `packages/` and `apps/`), so `CdkDialogContainer` is never instantiated and its stylesheet — `.cdk-dialog-container{display:block;width:100%;height:100%;min-height:inherit;max-height:inherit}` (`dialog.mjs:410`) — is never injected. The class is therefore inert today. The day any code instantiates a plain `CdkDialogContainer`, that rule appears globally at specificity (0,1,0) and collides with `.kbq-actions-panel-container { display: flex; height: var(--kbq-actions-panel-height); }` (`actions-panel-container.scss:1-12`) at the same specificity, with the winner decided by stylesheet injection order — the failure mode documented in `project_button_theme_specificity_ties`.
**Fix:** raise the panel's own rules out of the tie: scope them as `kbq-actions-panel-container.kbq-actions-panel-container { … }` or hang the layout on the element selector, so injection order stops mattering. Alternatively strip the inherited class in the container's constructor via `Renderer2.removeClass`, which also removes the misleading `cdk-dialog-container` marker from a component that is not a dialog (see APN-A11Y-02). Add an e2e assertion on the computed `display` and `height` of the container so a future regression is caught rather than eyeballed.

**APN-DOC-02 · Ten `console.log` calls ship in the five published examples** — `packages/docs-examples/components/actions-panel/actions-panel-overview/actions-panel-overview-example.ts:66, 70, 74, 78`, `actions-panel-adaptive/actions-panel-adaptive-example.ts:155, 159`, `actions-panel-close/actions-panel-close-example.ts:63, 67`, `actions-panel-custom-counter/actions-panel-custom-counter-example.ts:187, 191`.
Four of the five examples subscribe to the ref's lifecycle streams purely to `console.log` the event, and all four are rendered on the docs page (`apps/docs/src/app/structure.ts:306-317`, `hasExamples: true`) and in the dev app (`packages/components-dev/actions-panel/module.ts:22-32`). Three of them additionally open their panel automatically from `afterNextRender` (`actions-panel-overview-example.ts:50-52`, `actions-panel-adaptive-example.ts:142-144`), so simply visiting the docs page opens several panels and floods the console. Consumers copy these files verbatim — the docs site offers them as StackBlitz seeds — so the logging propagates into product code.
**Fix:** replace the `console.log` bodies with a visible effect (the adaptive and custom-counter examples already have `KbqToastService` wired for actions — reuse it) or delete the subscriptions entirely where they demonstrate nothing. Keep at most one example that demonstrates the lifecycle streams, and have it render the last event into the DOM so the reader sees it without a devtools panel.

**APN-API-02 · Package structure and API-report hygiene** — `index.ts:1-5`, `module.ts:1-14`, `tools/public_api_guard/components/actions-panel.api.md:73-74, 95-103`.
Three small deviations. (1) The package has no `public-api.ts`; `index.ts` re-exports the five source files directly, so there is no curated boundary between what is exported and what merely happens to be `export`ed — 54 of the 74 component packages have one. (2) `KbqActionsPanelModule` declares `providers: [KbqActionsPanel]` (`module.ts:11`) although the service is already `@Injectable({ providedIn: 'root' })` (`actions-panel.ts:62`); importing the module into a lazily-loaded route therefore creates a second, route-scoped instance whose "only one panel at a time" bookkeeping (`actions-panel.ts:71, 117-126`) is independent of the root one. That is also the mechanism by which the dev app shows five panels simultaneously (`packages/components-dev/actions-panel/module.ts:22-32` — each example provides its own `KbqActionsPanel`), a behaviour the guides never mention. (3) `KbqActionsPanelModule` is the one export still marked `// @public (undocumented)` in the report (`actions-panel.api.md:95`).
**Fix:** add a `public-api.ts` that names the intended exports and have `index.ts` re-export it. Drop `providers: [KbqActionsPanel]` from the module (the `providedIn: 'root'` declaration already covers module importers) and document explicitly in both guides that the single-panel guarantee is per injector, which is why every example uses `providers: [KbqActionsPanel]` + `inject(KbqActionsPanel, { self: true })`. Add a JSDoc block to `KbqActionsPanelModule`. All three touch the API report, so batch them into one `build:components` + `approve-api` cycle.

## 4. Recommended Remediation Phases

**Phase 1 — Stop hiding the application from assistive technology.**
IDs: APN-A11Y-01, APN-A11Y-02. Delete the `_trapFocus()` call, then set an explicit role and a locale-sourced accessible name and add `role`/`ariaLabel` to the config. These two are one change in practice: removing the call fixes the page-wide `aria-hidden`, and correcting the role is what stops axe's `focusable-modal-open` check from masking any future recurrence. Ship with the `jest-axe` case and the `aria-hidden` DOM assertions from APN-TEST-01 in the same PR — without them nothing proves the fix, and nothing prevents the regression.

**Phase 2 — Repair the published contract.**
IDs: APN-BUG-01, APN-BUG-02, APN-DOC-01. Make the default-config merge explicit, route ESC through the body-level keydown dispatcher, and rewrite the `overlayContainer` section plus both broken snippets. All three are cases where a consumer reading the documentation gets behaviour the documentation does not describe; none depends on Phase 1. The `overlayContainer` rename should land behind a deprecated alias, not as a breaking change.

**Phase 3 — Close the lifecycle and typing gaps.**
IDs: APN-LIFE-01, APN-API-01, APN-API-02. Complete the opening subjects and `animationStateChanged`, type `containerInstance` nullable, add `public-api.ts`, drop the redundant module provider, remove the `any` from the injected config. All of these change `actions-panel.api.md`, so batch them into a single `yarn run build:components && yarn run approve-api` cycle rather than three.

**Phase 4 — Styles, tests and examples.**
IDs: APN-CSS-01, APN-STYLE-01, APN-STYLE-02, APN-TEST-01, APN-DOC-02. Publish the divider recipe and delete the two copied blocks (sequence after DIV-CSS-01 in `REVIEW.divider.md` so the `!important` can go with them), unswap the animation durations, break the `cdk-dialog-container` specificity tie, fix the unawaited Playwright click, and clean the `console.log` calls out of the examples. This is the only phase that needs new Playwright baselines, and they must be produced with `yarn run e2e:docker:update-snapshots`.

## Appendix A — Review Methodology

Findings were gathered by reading the complete package (all six TypeScript files, both SCSS files, both guides, both examples stubs, the e2e fixture and Playwright spec, the module and barrel), then following every behaviour the component delegates into the `@angular/cdk` 20.2.14 source it actually ships against — `dialog.mjs` for the container/service/ref contract, `overlay-module.mjs` for the keyboard dispatcher, `observers/private.mjs` for `SharedResizeObserver` — and into `@angular/core`'s `ɵɵInheritDefinitionFeature` to establish exactly which host bindings and attributes the container inherits. That last step is what turned "the container has no ARIA" from an assumption into APN-A11Y-02: the ARIA is there, it is just wrong, and it arrives from a base class the component never audited. Accessibility claims were checked against the `axe-core` 4.12.1 bundle that `jest-axe` 11 actually resolves (`node_modules/jest-axe/node_modules/axe-core`, not the hoisted 3.5.6 at the workspace root), reading the rule definitions rather than reasoning from rule names. Design tokens were confirmed to resolve in both `css-tokens-light.css` and `css-tokens-dark.css`. Consumers were enumerated by grep across `packages/` and `apps/`: five docs examples, two dev apps, one SSR dev app entry, and no other component in the library.

Refuted during verification:
- **"The package is missing `_actions-panel-theme.scss`, so its colours are unthemed"** — refuted. Every colour comes from `actions-panel-tokens.scss:1-17`, which references semantic tokens (`--kbq-background-contrast`, `--kbq-foreground-on-contrast`, `--kbq-line-on-contrast-less`, `--kbq-shadow-card`) that are themselves redefined per theme in `@koobiq/design-tokens/web/new/css-tokens-light.css:14, 48, 89` and `-dark.css`. Those files scope the tokens to `.kbq-light`/`.kbq-dark`, which sit on `<body>` (`packages/components-dev/index.html:10`, `apps/docs/src/assets/stackblitz/src/index.html:62`), so the CDK overlay container — a child of `<body>` — inherits them. A theme mixin would add nothing; this is the correct pattern, not a gap.
- **"Importing `SharedResizeObserver` from `@angular/cdk/observers/private` is an unsafe private-API dependency"** — refuted as an actions-panel finding. Eleven other packages do the same (`clamped-text`, `code-block`, `core/overflow-shadow`, `dl`, `inline-edit`, `navbar`, `overflow-items`, `select`, `timezone`, `title`, plus their specs). It is a library-wide convention with a pinned CDK version (`package.json:22`); filing it here would be arbitrary.
- **"`syncOverlayMaxWidth` sets `max-width` without calling `updatePosition`, so the first render is off-centre"** — refuted. The strategy is built with `.withFlexibleDimensions()` (`actions-panel.ts:161`), under which `FlexibleConnectedPositionStrategy` positions a bounding box and centres the overlay inside it with flexbox alignment rather than an absolute `left`. A later `max-width` change re-centres the element for free, which is why the initial sync at `actions-panel.ts:196` correctly omits the reposition that the resize handler performs.
- **"A panel that is queued and then superseded leaks its overlay"** — refuted. `startCloseAnimation()` moves the trigger from `void` to `hidden`, and although the trigger defines no `void => hidden` transition (`actions-panel-container.ts:58-75`), Angular's animation engine falls back to a zero-duration transition that still emits `start` and `done`. Both the fallback timeout (`actions-panel-ref.ts:92-95`) and the done handler (`:116-124`) therefore run and `dialogRef.close()` disposes the overlay. The real defect on that path is the uncompleted opening subjects, filed as APN-LIFE-01.
- **"The page-wide `aria-hidden` is an axe `aria-hidden-focus` failure"** — refuted as an *automated* failure, and the reason is instructive. `aria-hidden-focus` (`axe.js:31834-31843`, wcag2a/wcag412) passes when its `focusable-modal-open` check passes, and that check treats any visible `[role=dialog]` as proof a modal is open (`axe.js:17666-17670`). The actions panel *is* a visible `[role=dialog]` (APN-A11Y-02), so the rule is suppressed by the very attribute that should not be there. APN-A11Y-01 is filed on WCAG 1.3.1/4.1.2 grounds, not as an axe failure; `aria-dialog-name` is the rule that does fire, and it is filed under APN-A11Y-02.
- **"The close button's `aria-label` must come from `kbqInjectA11yLocaleConfiguration()` per AGENTS.md"** — refuted. `KbqA11yLocaleConfiguration.close` is "Close"/"Закрыть" (`packages/components/core/locales/en-US.ts:5`, `ru-RU.ts:5`), but this button's actual action is deselection — `actionsPanel.closeTooltip` is "Deselect"/"Отменить выбор" (`en-US.ts:63-65`, `ru-RU.ts:63-65`). Reusing the visible tooltip text as the accessible name is the correct behaviour here (WCAG 2.5.3, Label in Name); substituting the generic a11y string would make the name diverge from the visible label.
- **"The entrance animation is not gated behind `prefers-reduced-motion`"** — refuted as a component-specific finding. No component in the library uses an `[@.disabled]` host binding; the only mention of the technique anywhere is a TODO comment on a trigger that is never bound (`packages/components/app-switcher/app-switcher-animations.ts:4-9`). This is a library-wide gap that belongs in a cross-cutting ticket, not in the actions-panel review. Note also that `playwright.config.ts:101` sets `reducedMotion: 'reduce'` on every context, so the committed screenshots would not surface it either way.

Corrected on verification:
- **APN-A11Y-01** was first drafted as "the container installs no focus trap, so the panel is not really modal" and scored P2. Reading `CdkDialogContainer._contentAttached` (`dialog.mjs:211-214`) showed the missing trap is deliberate and correct for a non-modal bar. What is not correct is that `_trapFocus()` is still called anyway, and that its only surviving effect is CDK's page-wide `aria-hidden`. The finding was rewritten around that mechanism and raised to P0.
- **APN-BUG-02** was first drafted as "ESC never closes the panel". The two Jest cases at `actions-panel.spec.ts:172-188` genuinely pass, because they dispatch the event on the container element itself — the one place the host listener does fire. The claim was narrowed to "ESC closes only when focus is already inside the panel", and the spec's role in concealing it became part of the evidence.
- **APN-A11Y-02** was first drafted as "the container has no ARIA semantics at all", by analogy with DIV-A11Y-01 in `REVIEW.divider.md`. Tracing `ɵɵInheritDefinitionFeature` (`debug_node.mjs:16778-16789`, `:16731-16742`) showed the opposite: the container inherits a full set of dialog ARIA bindings from `CdkDialogContainer`, including a `role="dialog"` with no name. The finding inverted from "missing" to "wrong and unnameable".
