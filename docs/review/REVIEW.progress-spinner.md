# Koobiq `progress-spinner` Component — Code Review & Improvement Plan

> Scope: `packages/components/progress-spinner` (component, template, tokens, theme, SCSS, Jest spec, e2e fixture + Playwright spec, user guides, dev app, API guard report) · Commit `b665e503` · 2026-08-28
> Generated by a multi-dimension review (architecture, correctness, accessibility, public API/types, styles, tests, docs) with manual verification of every finding against the source, the 12 in-repo consumers, the design-token files and `playwright.config.ts`. 12 findings confirmed (P0×0, P1×3, P2×5, P3×4); 7 candidate findings refuted during verification (see Appendix A). This document is a review + roadmap; no source is modified by it.

---

## 1. Executive Summary

`KbqProgressSpinner` is a 81-line component with a 17-line template that draws a single SVG `<circle>` and animates it via `stroke-dasharray`/`stroke-dashoffset`. It is one of the most-reused primitives in the library — `loader-overlay`, `select`, `tree`, `tree-select`, `file-upload`, `notification-center` and `dropdown` all embed it. There are no release blockers, but the component gets its one job — *rendering a number as an arc* — measurably wrong at its default size, and it does not exist at all for assistive technology.

- **The determinate arc is calibrated for the wrong radius.** `MAX_DASH_ARRAY = 295` (`progress-spinner.component.ts:30`) and `stroke-dasharray: 295%` (`progress-spinner.scss:22`) are the circumference of the **`big`** circle (`r = 47%` → 2π·47 = 295.31), but the default `compact` size draws `r = 42.5%` (`progress-spinner.component.ts:60`) whose circumference is 267.04. Every compact determinate spinner therefore over-fills by a factor of 1.105: `value="50"` renders a 55.2% arc, `value="75"` renders 82.9%, and **everything from `value="91"` upward renders as a complete ring**. The library's own published example (`progress-spinner-overview-example.ts:16`) uses the default size and steps in 4% increments, so it shows a visibly full circle next to the labels "92%", "96%" and "100%" (PSP-BUG-01).
- **The component has no `role="progressbar"` — and neither does anything else in this repository.** `grep -rn progressbar packages/ apps/` returns zero hits. The host block (`progress-spinner.component.ts:38-43`) binds three classes and `[attr.id]` and nothing else: no role, no `aria-valuenow`/`aria-valuemin`/`aria-valuemax`, no accessible name, no `aria-hidden` on the decorative `<svg>`. A screen-reader user gets no announcement that anything is loading and no reading of the progress value. `notification-center.html:104-110` already works around this by wrapping the spinner in `<div role="status" [attr.aria-label]="localeData.loadingMore">` — the one consumer that cared had to build the semantics itself (PSP-A11Y-01).
- **The published `color` contract is fiction.** `progress-spinner.en.md:46-56` documents `color` as `('primary', 'secondary', 'error')` with a `'primary'` default and three `themePalette.*` snippets. The theme mixin styles exactly three states — the default, `.kbq-contrast` and `.kbq-contrast-fade` (`_progress-spinner-theme.scss:4-17`) — and the real default is `KbqComponentColors.Theme` (`progress-spinner.component.ts:78`). `[color]="'error'"` adds a `kbq-error` class with no rule behind it, which is exactly what two dev call sites already do (`components-dev/all/template.html:735`, `components-dev/loader-overlay/template.html:75`). The Russian guide is worse: it stops at line 44 with no `color` section at all, and its two `value="30"` snippets bind a string to `input<number>` under `strictTemplates: true` (PSP-DOC-01).
- **Three of the nine Jest assertions cannot fail, and the Playwright suite never photographs the animation.** `progress-spinner.component.spec.ts:74` queries `.kbq-progress-spinner__circle_indeterminate`, a class that exists nowhere in the repository; `:96` queries `.kbq-progress-spinner_indeterminate` as a *descendant* of the element that carries it; `:115` asserts `getAttribute('id')` `toBeDefined()`, which `null` satisfies. Meanwhile `playwright.config.ts:101` sets `reducedMotion: 'reduce'` for every context, and `progress-spinner.scss:68-70` answers that with `animation: none` — so the six indeterminate cells in `__screenshots__/01-{light,dark}.png` are baselines of the *reduced-motion fallback*, and the shipped animation has no visual guard at all (PSP-TEST-01, PSP-TEST-02).

Genuine strengths worth preserving: the component is standalone, `OnPush`, host-object-bound with no `@HostBinding`, entirely token-driven with zero hardcoded colours, and it is the only one of the two progress components that calls `setDefaultColor()` so that `[color]="''"` falls back correctly (`progress-spinner.component.ts:79` — `progress-bar.component.ts:52` omits it). The content-projection design (`[kbq-progress-spinner-text]` / `[kbq-progress-spinner-caption]` as separate directives) is clean and mirrors `progress-bar` exactly. The e2e fixture covers 16 state combinations in light and dark, and three past regressions in the same layout area (DS-4565, DS-4606, DS-4799) have each left a targeted fix in the SCSS. The defects are concentrated in the geometry constant, the missing semantics layer and the contract documents — not in the component's structure.

## 3. Prioritized Findings (deduplicated, verified)

### P0 — Release blockers

None.

### P1 — High

**PSP-BUG-01 · The dash constant `295` is the `big` circumference, so determinate progress over-fills by 10.5% at the default `compact` size** — `progress-spinner.component.ts:30, 60, 67-73`, `progress-spinner.scss:22`, `progress-spinner.component.html:9`.
The component implements the standard SVG ring-progress idiom: set `stroke-dasharray` to the circle's circumference *C* and `stroke-dashoffset` to `C · (1 − p)`. The idiom is only correct when the constant equals the circumference of the circle actually drawn. Here the constant is fixed at `295` in two places — `MAX_DASH_ARRAY = 295` (`:30`, feeding `dashOffsetPercent` at `:71-73`) and `stroke-dasharray: 295%` (`progress-spinner.scss:22`) — while the radius is switched by the `size` setter between `'47%'` and `'42.5%'` (`:60`). With `viewBox="0 0 100 100"` (`progress-spinner.component.html:2`) SVG percentages for `r`, `stroke-dasharray` and `stroke-dashoffset` all resolve against a normalized diagonal of 100, so the two cases are: `big` → *C* = 2π·47 = **295.31** (constant is right to 0.1%), `compact` → *C* = 2π·42.5 = **267.04** (constant is 10.47% too large). The visible arc is `(295 − offset)/C = 295p/267.04 = 1.1047·p`. Verified numerically: `value=25` renders 27.6%, `value=44` (the value the e2e fixture pins) renders 48.6%, `value=50` renders 55.2%, `value=75` renders 82.9%, and from `value ≥ 90.52` the arc saturates at a complete ring. `compact` is the default (`:63`) and the size every consumer that shows a *number* uses — `file-upload/multiple-file-upload.component.html:44-47` and `single-file-upload.component.html:24` both feed a real upload percentage into a default-size spinner, so an upload sitting at 92% is drawn as finished. The library's own published example makes it visible: `progress-spinner-overview-example.ts:16` uses the default size and steps `percent` by 4, so four consecutive labels ("92%", "96%", "100%", and the wrapped "104%" clamped to 100) all render the same full circle. The same constant also makes the *indeterminate* arc size depend on `size`: `stroke-dashoffset: 80%` (`progress-spinner.scss:74`) leaves a 70° gap at compact and a 98° gap at big — which is what the adjacent `// TODO: rework this place` (`:72`) is about.
**Fix:** stop hardcoding the circumference. Either (a) drop the percentage radii and use a fixed user-unit radius in the `viewBox`, scaling only through the container, so one constant is correct for both sizes; or (b) derive the constant per size — make `svgCircleRadius` and the dash length a single `computed()` pair (`radius = size() === 'big' ? 47 : 42.5`, `dashArray = 2 * Math.PI * radius`), bind `stroke-dasharray` from the template alongside `stroke-dashoffset` instead of from SCSS, and delete `MAX_DASH_ARRAY` and `progress-spinner.scss:22`. Option (b) is the smaller diff and also fixes the indeterminate gap by expressing `80%` as a fraction of the computed dash length. Guard it with a Jest case asserting `dashOffsetPercent` against `2π·r·(1 − p)` for both sizes and for `value` ∈ {0, 25, 50, 91, 100}, and add an e2e row at `value="92"` at the default size — the current fixture's single `value="44"` cannot distinguish 44% from 48.6%.

**PSP-A11Y-01 · No `role="progressbar"`, no `aria-value*`, no accessible name — and consumers have started building the semantics themselves** — `progress-spinner.component.ts:38-43` (host block), `progress-spinner.component.html:1-17`; consumer workaround at `notification-center/notification-center.html:104-110`.
The host block binds `class`, two modifier classes and `[attr.id]`. There is no `role`, so `<kbq-progress-spinner>` is an unknown element exposed as generic; there is no `aria-valuenow`/`aria-valuemin`/`aria-valuemax`, so the determinate value is never conveyed; there is no `aria-label`/`aria-labelledby`, so even with a role the widget would have no name (WCAG 4.1.2 Name, Role, Value; WCAG 1.3.1 for the loading state that is signalled by animation alone). The decorative `<svg>` (`progress-spinner.component.html:2`) also carries no `aria-hidden="true"`, so AT that exposes `graphics-document` announces an empty graphic. `grep -rn "progressbar" packages/ apps/` returns **zero hits** — neither this component nor its sibling `progress-bar` implements the role anywhere in the library. The evidence that this hurts is already in the tree: `notification-center.html:104-110` wraps the spinner in `<div role="status" data-testid="kbq-notification-center-load-more" [attr.aria-label]="localeData.loadingMore">` and sources the string from its own locale section (`core/locales/en-US.ts:242`), i.e. one consumer re-implemented the announcement the component should provide, and the other eleven call sites announce nothing. Note this is a WCAG judgement, not an automated AXE failure — axe-core does not flag a custom element carrying no role, which is why it has survived unnoticed. The correct pattern also requires that `aria-valuenow` be **omitted entirely** in `mode="indeterminate"` (an indeterminate `progressbar` with a `valuenow` is announced as a stalled determinate one); the component's existing `mode()` signal makes that a one-line conditional.
**Fix:** add to the host block: `role: 'progressbar'`, `'[attr.aria-valuemin]': "mode() === 'determinate' ? 0 : null"`, `'[attr.aria-valuemax]': "mode() === 'determinate' ? 100 : null"`, `'[attr.aria-valuenow]': "mode() === 'determinate' ? clampedValue() : null"` (reuse the clamp already in `percentage`, `:67-69`), and `'[attr.aria-label]': 'ariaLabel() ?? a11y().loading'` with an `ariaLabel` input for overrides. Per AGENTS.md the default string must come from `kbqInjectA11yLocaleConfiguration()`, so add a `loading` key to `KbqA11yLocaleConfiguration` (`core/locales/types.ts:13-37`) and to all five locale files alongside the existing `notificationCenter.loadingMore` precedent. Put `aria-hidden="true"` on the `<svg>`. Finally, give the existing `id` input a purpose: when `[kbq-progress-spinner-text]` content is projected, emit `aria-labelledby` pointing at it instead of a synthetic label. Cover with Jest cases per mode (determinate exposes all three `aria-value*`; indeterminate exposes none) and delete the hand-rolled `role="status"` wrapper in `notification-center` once the component speaks for itself. Apply the identical change to `progress-bar` in the same pass — the two components share the gap.

**PSP-DOC-01 · The guide documents a `color` enum the component does not implement, omits `size` entirely, and the RU mirror is truncated and does not type-check** — `progress-spinner.en.md:46-61`, `progress-spinner.ru.md:1-44`; contract at `_progress-spinner-theme.scss:4-17`, `progress-spinner.component.ts:52-63, 78-79`.
Four separate contract failures in two files. (1) `progress-spinner.en.md:48-50` states `color` is `Enum ('primary', 'secondary', 'error')` with `Default: 'primary'`. The component's default is `KbqComponentColors.Theme` (`progress-spinner.component.ts:78`), and the theme mixin defines rules for exactly three states — the base `.kbq-progress-spinner`, `&.kbq-contrast` and `&.kbq-contrast-fade` (`_progress-spinner-theme.scss:5, 11, 15`). `[color]="'primary'"`, `'secondary'` and `'error'` each add a `kbq-` class with no CSS behind it, so all three documented snippets (`:53-55`) render an unchanged theme-coloured spinner; the snippets additionally reference a `themePalette` symbol that is never declared. Two in-repo dev call sites already make this request and get nothing — `components-dev/all/template.html:735` (`[color]="'error'"`) and `components-dev/loader-overlay/template.html:75` (`[color]="themePalette.Error"`). The colours that *do* work, `contrast` and `contrast-fade` (added by DS-4583, commit `fec9db9a`), are documented nowhere and are only discoverable from `progress-spinner-indeterminate-example.ts:12-13`. (2) `size` is a real public input used by the library's own examples (`progress-spinner-indeterminate-example.ts:11`, `loader-overlay-large-example.ts:21`) and by `loader-overlay.component.html:5`, and it appears in neither guide. (3) The `[kbq-progress-spinner-text]` and `[kbq-progress-spinner-caption]` content directives — two of the four exported symbols — are documented in neither guide either. (4) `progress-spinner.ru.md` ends at line 44 with no `color` and no `Theming` section, so the two mirrors describe different components; and its snippets at `:24` and `:41` write `value="30"`, a static string attribute bound to `input<number>` — under `tsconfig.json:117` `strictTemplates: true` that is a compile error, not a silent coercion, so a reader copying the Russian snippet gets a build break where the English reader gets a working one.
**Fix:** rewrite the `color` section against reality — document the default (`theme`) and the two supported overrides (`contrast`, `contrast-fade`), state explicitly that other `KbqComponentColors`/`ThemePalette` values apply a class but no styling, and drop the undeclared `themePalette` reference in favour of literal strings as the examples already use. Add a `size` section (`'compact' | 'big'`, default `'compact'`) and a short section on the two content directives with the snippet already living in `e2e.ts:9-12`. Port the whole `color`/`Theming` block to `progress-spinner.ru.md` and change both `value="30"` occurrences to `[value]="30"`. If the `error`/`warning`/`success` colours are genuinely wanted, that is a separate feature — add `--kbq-progress-spinner-circle-error-background` and friends to `progress-spinner-tokens.scss` plus matching `&.kbq-error` branches in the theme mixin, and then the two dev call sites become the acceptance test.

### P2 — Should fix

**PSP-A11Y-02 · Under `prefers-reduced-motion` the indeterminate spinner freezes into a static arc with no substitute signal** — `progress-spinner.scss:65-76`, and `:24` for the uncovered transition.
`.kbq-progress-spinner_indeterminate .kbq-progress-spinner__inner` animates a full rotation (`:66`) and answers `@media (prefers-reduced-motion: reduce)` with `animation: none` (`:68-70`). Because the component exposes no ARIA (PSP-A11Y-01), rotation is the *only* channel through which "something is loading" is communicated — so a reduced-motion user is left with a static three-quarter arc that is indistinguishable from a determinate spinner stuck at ~80%, and no non-visual announcement either. `prefers-reduced-motion` asks for reduced *non-essential* motion; a loading indicator's motion is the content. Separately, `transition: stroke-dashoffset 0.3s` (`:24`) sits outside the media query, so the determinate animation keeps moving while the indeterminate one is killed — the file is inconsistent with itself. `progress-bar.scss:49-55` has the identical shape, so whatever is decided should be applied to both.
**Fix:** land PSP-A11Y-01 first — with `role="progressbar"` and no `aria-valuenow` in indeterminate mode, AT announces "busy" regardless of the visual, which is the substantive part of the fix. Then replace `animation: none` with a reduced but present motion (`animation-duration: 3s; animation-timing-function: linear`) rather than a freeze, or, if a full stop is a deliberate design decision, make the frozen state read as indeterminate by shortening the arc (a 25% dash rather than 80%). Bring `:24` inside the same media query for consistency. Because `playwright.config.ts:101` forces `reducedMotion: 'reduce'` on every context, the current baselines already show this state — see PSP-TEST-02 for how to photograph both.

**PSP-API-01 · `size` is a legacy accessor `@Input` widened to `| string` that side-effects into a public mutable field, and the CSS modifier can be applied without it** — `progress-spinner.component.ts:50-65`; API report `tools/public_api_guard/components/progress-spinner.api.md:23-26`; consumers `components-dev/all/template.html:741, 748, 752`, `loader-overlay/loader-overlay.component.ts:100-101`.
Three coupled problems. (1) `size` is an accessor pair carrying the auto-generated "Accessor inputs cannot be migrated as they are too complex" TODO (`:50-51`); it is not complex — it assigns a backing field and derives a radius, which `input()` + `computed()` expresses directly. (2) It is typed `ProgressSpinnerSize | string`, so the `ProgressSpinnerSize` union documents nothing and enforces nothing: `size="large"`, `size="Big"` and `size="compct"` all compile under `strictTemplates` and silently fall through to compact, because both the class binding (`:40`) and the radius (`:60`) test `=== 'big'`. (3) The derived state lives in `svgCircleRadius`, a public mutable field written only by the setter and exported into the public API report (`api.md:26`). That makes the CSS modifier and the SVG radius two independent surfaces that can desynchronize, and they already have: `components-dev/all/template.html:741, 748, 752` apply `class="kbq-progress-spinner_big"` directly with no `[size]` binding, so those three spinners get the 48px box and the 6% stroke from `progress-spinner.scss:48-56` while the circle keeps `r = 42.5%` — an undersized ring in an oversized box, plus the PSP-BUG-01 over-fill that the `big` radius would have avoided. Anyone writing the class instead of the input hits this, and nothing warns them.
**Fix:** `readonly size = input<ProgressSpinnerSize>('compact')` and `protected readonly svgCircleRadius = computed(() => this.size() === 'big' ? '47%' : '42.5%')`, folded into the PSP-BUG-01 rewrite so the radius and the dash length are derived from one expression. Narrowing away the `| string` is source-breaking for exactly one in-repo caller — `loader-overlay.component.ts:100-101` returns `string` from its `spinnerSize` getter — so change its return type to `ProgressSpinnerSize` in the same commit; per repo policy a public narrowing needs an `ng-update` migration in `packages/schematics`, so confirm the breaking-change route before merging. Dropping `svgCircleRadius` from the public surface changes `progress-spinner.api.md`, so run `yarn run build:components` then `yarn run approve-api` (build first — the guard reads `dist/*.d.ts`).

**PSP-TEST-01 · Three of the nine Jest assertions cannot fail, and the whole `size`/geometry surface is untested** — `progress-spinner.component.spec.ts:74, 96, 115`, `:119-132`.
Three vacuous assertions, each of which passes against a deliberately broken implementation. (1) `:74` asserts that `.kbq-progress-spinner__circle_indeterminate` is absent — that class exists nowhere in the repository (`grep` returns only this line), so the assertion is true by construction and the test named "should show determinate circle" verifies only that a `.kbq-progress-spinner__circle` element exists, which is unconditional. (2) `:96` calls `.query(By.css('.kbq-progress-spinner_indeterminate'))` on the spinner's own `DebugElement`; that class is a *host* binding (`progress-spinner.component.ts:41`) and `DebugElement.query` walks descendants only, so it can never match — the sibling test at `:85` gets it right by querying from `fixture.debugElement`. (3) `:115` asserts `getAttribute('id')` is `toBeDefined()`; `getAttribute` returns `null` when the attribute is absent and `null` is "defined" to Jest, so the auto-generated-id test would pass with `[attr.id]` deleted. Beyond the vacuous three, nothing covers `size` at all (neither the `kbq-progress-spinner_big` class nor `svgCircleRadius`), nothing covers `dashOffsetPercent` — the one piece of real arithmetic in the component, and the site of PSP-BUG-01 — nothing covers the `[style]` binding that suppresses `stroke-dashoffset` in indeterminate mode (`progress-spinner.component.html:9`), and nothing instantiates `KbqProgressSpinnerText`/`KbqProgressSpinnerCaption`, two of the four exported symbols. The host `TestApp` (`:119-132`) also declares `color`, `mode` and `id` without initializers and types `mode: string` where the input is `ProgressSpinnerMode` — a mismatch Jest's JIT compilation does not check but AOT would.
**Fix:** replace `:74` with an assertion on the host class (`expect(el.classList).not.toContain('kbq-progress-spinner_indeterminate')`), fix `:96` to query from `fixture.debugElement` like `:85` does, and change `:115` to `expect(...getAttribute('id')).toMatch(/^kbq-progress-spinner-\d+$/)`. Add cases for `size`: `'big'` applies `kbq-progress-spinner_big` and yields `r="47%"`, `'compact'` and the default yield `r="42.5%"`. Add the `dashOffsetPercent` table from PSP-BUG-01 and an assertion that the `stroke-dashoffset` style is absent in indeterminate mode. Add the ARIA cases from PSP-A11Y-01. Initialize every `TestApp` field and type `mode: ProgressSpinnerMode`. Validate the suite by mutation: reverting `[class.kbq-progress-spinner_big]` to a constant, or `MAX_DASH_ARRAY` to `300`, must turn at least one case red.

**PSP-TEST-02 · The Playwright baselines photograph the reduced-motion fallback, and a quarter of the fixture cells are duplicates** — `e2e.playwright-spec.ts:8-16`, `e2e.ts:8-54`, `playwright.config.ts:87, 101`, `__screenshots__/01-{light,dark}.png`.
`playwright.config.ts:101` sets `contextOptions.reducedMotion: 'reduce'` for every project, and `progress-spinner.scss:68-70` answers that by disabling the indeterminate animation entirely. The six indeterminate cells in the fixture (`e2e.ts:26-30, 38-42, 50-54`) therefore render as a frozen arc in both baselines, and the shipped animation — the component's whole indeterminate behaviour — has no visual regression guard whatsoever. `toHaveScreenshot`'s `animations: 'disabled'` (`playwright.config.ts:87`) would already have frozen the animation deterministically at its finished state, so the `page.waitForTimeout(50)` at `e2e.playwright-spec.ts:11` guards nothing either. Separately the fixture is 25% redundant: `compact` is the default (`progress-spinner.component.ts:63`), so `e2e.ts:8-12` and `:32-36` render identically, as do `:26-30` and `:38-42` — four of the sixteen cells are byte-identical duplicates. And every cell pins `[value]="44"`, so no baseline covers `0`, `100`, or the `≥ 91` band where PSP-BUG-01 saturates.
**Fix:** add a second Playwright test that overrides the context (`test.use({ contextOptions: { reducedMotion: 'no-preference' } })`) so both the animated and the reduced-motion renderings are captured; keep `animations: 'disabled'` for determinism and drop the `waitForTimeout(50)`. Collapse the four duplicate cells and spend the space on a determinate row at `value` ∈ {0, 92, 100} at the default size — that row is the regression guard for PSP-BUG-01 and the reason the current suite could not catch it. Baselines are Linux-only at `threshold: 0`, so regenerate exclusively with `yarn run e2e:docker:update-snapshots`.

**PSP-CSS-01 · Two stroke-width tokens and one gap token are declared but never referenced; the stroke width is hardcoded** — `progress-spinner-tokens.scss:3, 7, 8`, `progress-spinner.scss:23, 40, 55`.
`--kbq-progress-spinner-size-compact-stroke-width: 2px` (`:3`) and `--kbq-progress-spinner-size-big-stroke-width: 3px` (`:7`) are declared and used nowhere — `grep` finds no consumer inside or outside the package. The SCSS instead hardcodes `stroke-width: 13%` (`progress-spinner.scss:23`) and `6%` (`:55`), which merely *approximate* the tokens (13% of a 16px box ≈ 2.08px, 6% of a 48px box ≈ 2.88px) and drift the moment either box size changes. The practical consequence is that a consumer who overrides `--kbq-progress-spinner-size-big-stroke-width` — the documented way to customize a Koobiq component — gets no effect at all. Likewise `--kbq-progress-spinner-size-big-content-gap-vertical` (`:8`) is unreachable: the text's `margin-bottom` is written once at `progress-spinner.scss:40` against the *compact* token and is never re-declared under `.kbq-progress-spinner_big` (`:48-63` overrides the box size, the stroke width and the horizontal gap, but not the vertical one). Today both gap tokens resolve to `var(--kbq-size-3xs)`, so nothing is visually wrong — the token is simply dead, and a future design change to the big variant's vertical gap would silently do nothing.
**Fix:** drive the stroke from the tokens rather than from percentages. Percentages are needed because the `viewBox` is unitless, so either compute them in SCSS from the box-size/stroke-width token pair, or set `stroke-width` in user units and let `vector-effect: non-scaling-stroke` hold the pixel width — the latter makes `--kbq-*-stroke-width` directly meaningful. Add a `.kbq-progress-spinner_big .kbq-progress-spinner-text { margin-bottom: var(--kbq-progress-spinner-size-big-content-gap-vertical) }` rule, or delete the token if the two sizes are meant to share one gap. Guard the result with the e2e rows from PSP-TEST-02, which already render both sizes side by side.

### P3 — Nice to have / hygiene

**PSP-STYLE-01 · Un-namespaced `--stroke` property, a duplicated `stroke` declaration whose fallback is dead, and a "background" token holding a foreground colour** — `progress-spinner.scss:19-26`, `_progress-spinner-theme.scss:4-18`, `progress-spinner-tokens.scss:11-13`.
Three small style-surface issues. (1) `_progress-spinner-theme.scss:5` declares `--stroke` — a bare, un-namespaced custom property — on `.kbq-progress-spinner`. Every other custom property in the package is `--kbq-`-prefixed. Because the component uses `ViewEncapsulation.None` and the property inherits, anything projected into `[kbq-progress-spinner-text]` (an inline SVG icon, say) silently inherits the spinner's `--stroke`; conversely a consumer's own `--stroke` on an ancestor is shadowed with no warning. (2) `progress-spinner.scss:21` writes `stroke: var(--stroke, var(--kbq-progress-spinner-circle-background))` while `_progress-spinner-theme.scss:7-9` writes `stroke: var(--stroke)` at higher specificity from a mixin included at the bottom of the same file (`progress-spinner.scss:78`). The theme rule always wins and `--stroke` is always defined, so the fallback in `:21` is unreachable — two declarations for one property, one of them dead. (3) `--kbq-progress-spinner-circle-background` (`progress-spinner-tokens.scss:11`) and its two `-contrast-` siblings name a *stroke* (foreground) colour "background"; unlike `progress-bar`, which genuinely has a background track and a foreground line (`progress-bar-tokens.scss:7-8`), the spinner draws no track at all (`progress-spinner.scss:20` sets `fill: none` and there is only one `<circle>`).
**Fix:** rename `--stroke` to `--kbq-progress-spinner-circle-stroke` and delete the duplicate declaration at `progress-spinner.scss:21`, keeping the theme mixin as the single source. Rename the three colour tokens to `…-circle-color` / `…-circle-contrast-color` / `…-circle-contrast-fade-color`, keeping the old names as aliases for one minor version. If a determinate track is wanted (it would make the arc's endpoint readable and is what `progress-bar` already provides), that is a feature request, not part of this cleanup.

**PSP-ARCH-01 · Unused `PlatformModule` import reaching the public API report, derived state as getters rather than `computed()`, and two stale TODOs** — `progress-spinner.module.ts:1, 7`, `progress-spinner.component.ts:6, 50-51, 67-73`, `progress-spinner.scss:72`; API report at `tools/public_api_guard/components/progress-spinner.api.md:8, 50`.
`KbqProgressSpinnerModule` imports `PlatformModule` from `@angular/cdk/platform` (`:1, 7`); nothing in the package injects `Platform` or uses any of its directives. The dead import is not merely cosmetic — it is baked into the published module declaration and shows up in the API guard report as `import * as i1 from '@angular/cdk/platform'` (`api.md:8`) and `typeof i1.PlatformModule` inside `ɵmod` (`api.md:50`), so it is part of the shipped contract. Separately, `percentage` (`:67-69`) and `dashOffsetPercent` (`:71-73`) are derived from the `value()` signal but implemented as getters, so they are recomputed on every change-detection pass of every spinner on the page and are invisible to the signal graph; AGENTS.md mandates `computed()` for derived state. The same template line also builds a fresh object literal for the `[style]` binding on every pass (`progress-spinner.component.html:9`). Finally there are two stale comments: `//@TODO use Exclude<KbqDefaultSizes, 'normal'> from '@koobiq/components/core' instead` (`:6`) and the auto-generated migration TODO at `:50-51`, plus `// TODO: rework this place` at `progress-spinner.scss:72`, which PSP-BUG-01 explains and resolves.
**Fix:** delete `PlatformModule` from the module's `imports` and re-run `yarn run build:components && yarn run approve-api` (fold into the PSP-API-01 cycle so the report churns once). Convert `percentage` and `dashOffsetPercent` to `computed()` as part of the PSP-BUG-01 rewrite. Resolve `:6` by actually using `Exclude<KbqDefaultSizes, 'normal'>` if it matches `'compact' | 'big'`, or delete the comment if it does not; delete `:50-51` once `size` becomes a signal input; delete `progress-spinner.scss:72` once the dash length is computed.

**PSP-API-02 · Every public member is `// (undocumented)`, and the `id` input shadows the native attribute for no benefit** — `tools/public_api_guard/components/progress-spinner.api.md:11-65`, `progress-spinner.component.ts:9, 46`.
All eight exported symbols — `KbqProgressSpinner`, `KbqProgressSpinnerText`, `KbqProgressSpinnerCaption`, `KbqProgressSpinnerModule`, `ProgressSpinnerMode`, `ProgressSpinnerSize`, and every member of the component — carry `// @public (undocumented)`, and the report ends with `(No @packageDocumentation comment for this package)` (`api.md:67`). There is no prose anywhere in the package except two TODOs, so the non-obvious parts (that `value` is clamped to 0–100, that `size` also switches the SVG radius, that `color` supports only three of the eight `KbqComponentColors`) are documented in no location at all. Separately, `id` (`:46`) is an `input<string>` defaulting to `kbq-progress-spinner-${id++}` from a module-level counter (`:9`) and reflected to `[attr.id]` (`:42`); nothing in the component consumes it — no `aria-labelledby`, no `for` — so it duplicates the native `id` attribute, cannot be suppressed, and shadows the DOM property for consumers. The initializer also references the module-level `id` binding from inside a field named `id`, which reads as self-referential. `progress-bar` carries the same design (`progress-bar.component.ts:41`) and additionally stamps the value twice, on the host and on an inner div.
**Fix:** add `/** */` blocks to the class and to `value` (state the clamp), `mode`, `size` (state that it also selects the SVG radius) and both content directives; add a `@packageDocumentation` comment. Note the mechanics: adding JSDoc removes the `(undocumented)` markers and therefore changes `progress-spinner.api.md`, so the `api` job fails until `approve-api` is re-run — batch it with the PSP-API-01 cycle. Give `id` a reason to exist by wiring it into the `aria-labelledby` from PSP-A11Y-01; if that is not taken, consider deprecating the input and letting consumers use the native attribute.

**PSP-DOC-02 · `examples.progress-spinner.*.md` are dead placeholder files** — `examples.progress-spinner.en.md:1-5`, `examples.progress-spinner.ru.md:1-5`, `apps/docs/src/app/structure.ts:814-825`.
Both files carry the standard "🚧 Documentation in progress 🚧" stub. They are not a broken user-facing surface: the docs structure entry sets `hasExamples: false` (`structure.ts:824`), so the Examples tab never renders for progress-spinner and neither file is reachable. They are two dead files that keep appearing in "in progress" greps and inviting someone to fill them in. Two real examples exist and are already embedded in the guide via `<!-- example(progress-spinner-overview) -->` and `<!-- example(progress-spinner-indeterminate) -->` (`progress-spinner.en.md:11, 44`; `progress-spinner.ru.md:11, 44`), and both are registered in `packages/docs-examples/components/progress-spinner/index.ts:7-10`.
**Fix:** decide one way. Either delete both stubs — the guide already embeds both examples inline, so nothing is lost — or populate them with the two `<!-- example(…) -->` embeds and flip `hasExamples: true` at `structure.ts:824`. Deleting is the lower-cost option and matches what the structure entry already declares. The sibling `progress-bar` entry (`structure.ts:812`) is in the identical state, so handle both together.

## 4. Recommended Remediation Phases

**Phase 1 — Make the arc mean what the number says.**
IDs: PSP-BUG-01, PSP-API-01, PSP-ARCH-01. Derive the radius and the dash length from one `computed()` pair keyed off a narrowed `size` signal input, bind `stroke-dasharray` from the template, delete `MAX_DASH_ARRAY`, `progress-spinner.scss:22`, the public `svgCircleRadius` field, the `PlatformModule` import and the three stale TODOs. `loader-overlay.component.ts:100-101` must be narrowed in the same commit. One `yarn run build:components && yarn run approve-api` cycle closes the API churn for all three. This is first because it is the only finding that renders wrong numbers to real users and because every later phase's tests assert against the corrected geometry.

**Phase 2 — Give the component semantics.**
IDs: PSP-A11Y-01, PSP-A11Y-02. Add `role="progressbar"` with the three `aria-value*` attributes conditioned on `mode()`, an `ariaLabel` input defaulting through a new `loading` key in `kbqInjectA11yLocaleConfiguration()`, `aria-hidden` on the `<svg>`, and `aria-labelledby` wired to the projected text via the existing `id`. Then revisit the `prefers-reduced-motion` branch now that a non-visual channel exists. Delete the hand-rolled `role="status"` wrapper at `notification-center.html:104-108` — its removal is the acceptance criterion. Mirror the change into `progress-bar`, which has the identical gap.

**Phase 3 — Repair the published contract.**
IDs: PSP-DOC-01, PSP-DOC-02, PSP-API-02. Rewrite the `color` section against the three states the theme actually implements, add `size` and the two content directives, port the missing block to the Russian guide and fix its two non-compiling `value="30"` snippets, add JSDoc to every public member and a `@packageDocumentation` comment, and resolve the dead examples stubs. Depends on Phase 1 (the `size` documentation must describe the narrowed type) and Phase 2 (the guide should document the new `ariaLabel` input).

**Phase 4 — Close the test and style gaps.**
IDs: PSP-TEST-01, PSP-TEST-02, PSP-CSS-01, PSP-STYLE-01. Fix the three vacuous Jest assertions, add the `size`/geometry/ARIA cases, add the un-reduced-motion Playwright test and the low/high-value determinate row, collapse the duplicate fixture cells, drive `stroke-width` from its tokens, add the missing big-variant vertical gap rule, and rename `--stroke`. In practice the Jest geometry table should be written *before* Phase 1 lands so the fix is verified rather than assumed; the Playwright and style work follows.

## 5. Verification Strategy

General gates, run sequentially (never in parallel — see `project_no_parallel_heavy_builds`):

- `yarn run eslint`, `yarn run stylelint`, `yarn run prettier` on touched files.
- `yarn run build:components`, then `yarn run check-api`; `approve-api` only in Phases 1 and 3 where the surface intentionally changes.
- `yarn run e2e:docker` for anything visual; regenerate baselines only with `yarn run e2e:docker:update-snapshots`.
- Manual smoke: `yarn run dev:progress-spinner` (both sizes, both modes, a live percentage readout beside each spinner) and `yarn run dev:loader-overlay`.

Per-phase assertions:
- **Phase 1:** for both sizes and `value` ∈ {0, 25, 50, 91, 100}, the rendered arc length equals `2π·r·value/100` within 0.5% — assert on `dashOffsetPercent` in Jest and confirm visually that `value="92"` at the default size is *not* a closed ring. `grep -n "295" packages/components/progress-spinner/` returns nothing. `svgCircleRadius` is absent from `progress-spinner.api.md`; `check-api`'s diff contains only the accessor→`InputSignal` transition, the removed field and the removed `@angular/cdk/platform` import. `build:components` still compiles all six consumer packages.
- **Phase 2:** `getComputedRole()` on a default spinner reports `progressbar`. In determinate mode `aria-valuenow`, `aria-valuemin` and `aria-valuemax` are all present and `aria-valuenow` tracks the clamped value; in indeterminate mode all three are **absent** (a present `aria-valuenow` here is the specific failure to guard against). Every spinner has a non-empty accessible name, sourced from the locale config and overridable. `jest-axe` reports no violations on a fixture containing both modes. With `notification-center.html:104-108`'s `role="status"` wrapper deleted, its existing spec at `notification-center.spec.ts:163` still passes and the loading state is still announced.
- **Phase 3:** every `[color]` value named in `progress-spinner.en.md` produces a visibly different stroke, or is explicitly documented as class-only. `progress-spinner.en.md` and `progress-spinner.ru.md` have the same section list. Both guides' snippets compile under `strictTemplates` — `yarn run e2e:docs` covers this. `check-api` shows only the removal of `(undocumented)` markers.
- **Phase 4:** each of the three repaired assertions fails when the behaviour it names is deliberately broken (mutation check — an assertion suite that passes against a broken binding is worth nothing). `npx jest` reports the `size` and geometry cases green. The Playwright suite produces two distinct indeterminate baselines, animated and reduced-motion, and they differ. Overriding `--kbq-progress-spinner-size-big-stroke-width` in the dev app visibly changes the ring thickness.

## Appendix A — Review Methodology

Findings were gathered by reading the complete package (all 15 files: every `.ts`, `.html`, `.scss` and `.md`, plus the e2e fixture and Playwright spec), then cross-checking each candidate against five independent sources: the workspace compiler settings (`tsconfig.json:114-118`), the Playwright configuration (`playwright.config.ts`, whose global `reducedMotion` setting turned out to be load-bearing), the API guard report (`tools/public_api_guard/components/progress-spinner.api.md`), the live design-token files under `@koobiq/design-tokens/web/new/`, and every in-repo consumer of `<kbq-progress-spinner>` found by grep across `packages/` and `apps/` — 12 production call sites in `file-upload` (2), `loader-overlay`, `notification-center`, `select`, `tree`, plus 6 docs examples and 3 dev-app call sites. The sibling `progress-bar` package was read in full as a control: it shares the ARIA gap and the `id` design but not the geometry bug (it has no SVG), and it is *missing* the `setDefaultColor()` call that progress-spinner gets right. Consumer evidence is what upgraded PSP-A11Y-01 from an opinion to a confirmed defect (`notification-center` built the announcement itself) and PSP-API-01 from a typing nit to a real desynchronization (three dev call sites apply the modifier class without the input). PSP-BUG-01 was verified numerically with a standalone `node -e` computation of `2πr` against the hardcoded constant for both radii before being written down.

Refuted during verification:
- **"The component has no `prefers-reduced-motion` handling"** — refuted. It is present at `progress-spinner.scss:68-70` and matches `progress-bar.scss:52-54`. The defect is *what the fallback is* (a frozen arc with no substitute signal), which is filed as PSP-A11Y-02 at a lower severity than a missing query would have warranted.
- **"The `--kbq-progress-spinner-*` tokens do not resolve"** — refuted. Every global token the package references is defined: `--kbq-icon-theme`, `--kbq-icon-contrast`, `--kbq-icon-contrast-fade`, `--kbq-foreground-contrast` and `--kbq-foreground-contrast-secondary` in `css-tokens-light.css:32-33, 56-58` and the dark mirror; `--kbq-size-l`, `--kbq-size-5xl`, `--kbq-size-3xs` and `--kbq-size-s` in `css-tokens.css:1288-1298`. The token problem is the opposite one — three declared tokens that nothing reads (PSP-CSS-01).
- **"`--kbq-progress-spinner-circle-background` is referenced from another package and is out of scope there"** — refuted, by analogy with the equivalent `divider`/`code-block` defect. `grep` finds no reference to any `--kbq-progress-spinner-*` token outside this package.
- **"The module-level `id` counter leaks between Jest test cases"** — refuted. `jest.config.js:13-14` sets `clearMocks: true` and `resetModules: true`, so the counter resets per module load, and the spec never asserts a specific number anyway (that assertion is broken for a different reason — PSP-TEST-01).
- **"`page.waitForTimeout(50)` makes the indeterminate screenshot flaky"** — refuted. `playwright.config.ts:87` sets `animations: 'disabled'` and `:101` forces `reducedMotion: 'reduce'`, so the captured frame is deterministic twice over. The sleep is dead weight, and the real problem is the inverse: the animation is never captured at all (PSP-TEST-02).
- **"`this.color = KbqComponentColors.Theme` in the constructor overwrites a consumer's `[color]` binding"** — refuted. The constructor runs before input bindings are applied, and the adjacent `setDefaultColor(Theme)` call (`progress-spinner.component.ts:79`) is what makes `[color]="''"` fall back correctly through `color.ts:52-53`. This is one of the places progress-spinner is *better* than its sibling.
- **"The component is SSR-unsafe"** — refuted. There is no `window`, no `document`, no `getComputedStyle` and no `Renderer2` bypass anywhere in the package; rendering is entirely declarative and `KBQ_WINDOW` is not needed.

Corrected on verification:
- **PSP-BUG-01** was first drafted as "values below ~9.5% render nothing at the compact size", from reading the dash-offset direction backwards. Re-deriving it numerically (`node -e` over `2πr` and the SVG dash-pattern semantics) showed the opposite symptom — a uniform 10.5% *over*-fill and saturation to a full ring from `value ≥ 90.52`. The severity stayed P1; the wording, the numbers and the acceptance test all changed.
- **PSP-A11Y-01** was drafted as P0 on the AGENTS.md "MUST pass all AXE checks" mandate. axe-core does not flag a custom element that simply carries no role, so this is a WCAG 4.1.2/1.3.1 judgement plus demonstrable consumer inconsistency, not an automated failure — filed as P1 on those grounds.
- **PSP-TEST-02** was drafted as a P3 about redundant fixture cells. Finding that `playwright.config.ts:101` forces `reducedMotion: 'reduce'` on every context — which `progress-spinner.scss:68-70` answers with `animation: none` — showed that the indeterminate animation has no baseline at all, and the finding was rewritten and raised to P2.
