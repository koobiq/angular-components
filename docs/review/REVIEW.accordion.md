# Koobiq `accordion` Component — Code Review & Improvement Plan

> Scope: `packages/components/accordion` (container, item, trigger/content/header primitive pairs, styles, tests, docs) · Commit `18ea72fe` · 2026-06-29
> Generated by an automated multi-agent review (7 dimensions: architecture, correctness, RxJS/lifecycle, accessibility, public API/types, tests, templates/styles) with **adversarial verification of every finding** against the actual code and `@angular/core` / `@angular/cdk` 20.3.x sources.
> Raw: 60 findings → **38 confirmed, 19 disputed (severity-corrected, still real), 3 refuted**. De-duplicated to a canonical **2×P1, 10×P2, ~28×P3** below. This document is a review + roadmap; no source is modified by it.

## 1. Executive Summary

- **The component is well-built on the modern Angular baseline.** Standalone, `OnPush`, `inject()`, signal `contentChildren`, native host-object bindings, no `ngClass`/`ngStyle`, no `@HostBinding`/`@HostListener`. There are **no P0 release blockers**. The finding set is dominated by a handful of correctness edge cases, one real keyboard-accessibility defect, and a long tail of API/type/style/test hygiene.
- **Top risk #1 — the `disabled` override bug (`ACC-BUG-01`, P1).** The item `disabled` getter uses `??` (`this.accordion.disabled() ?? this._disabled`). Because Angular runs the `booleanAttribute` transform only on *bound* values, the idiomatic `<kbq-accordion [disabled]="false">` makes `disabled()` return `false`, and `false ?? this._disabled` **silently ignores an item's own `[disabled]="true"`** — the section becomes clickable/keyboard-operable and reports `aria-disabled="false"`, contradicting the docs. A one-character fix (`||`).
- **Top risk #2 — the WAI-ARIA keyboard model (`ACC-A11Y-01`, P1).** The container hijacks Tab/Shift+Tab to move between headers and `preventDefault()`s them. The APG accordion pattern requires Tab to move to the next focusable element (e.g. into an open panel's content) and Arrow Up/Down to move between headers. Because the handler never checks `event.target`, Tab pressed *inside an open panel* is pulled back to a header, so keyboard/screen-reader users can't reach interactive content in an open section. It is **not** a literal keyboard trap (focus escapes at the first/last item) and Arrow/Home/End nav is already wired — the fix is to delete the two Tab branches.
- **Controlled-`value` correctness needs work (P2 cluster).** Dispatcher matching uses `String.includes` (substring collisions: `item-10` also opens `item-1`, `ACC-BUG-03`); `multiple` mode never closes items on `[value]` reassignment (`ACC-BUG-04`); and a content-less item crashes on first toggle because one `content()` call lost its optional chain (`ACC-BUG-02`).
- **State-saving is the weakest subsystem.** `localStorage` persistence lives in the UI container and is keyed by an unstable auto-generated id (`ACC-ARCH-01`, P2) — reliable only for a fixed, statically-rendered set of accordions — and it is **entirely untested** (`ACC-TEST-01`, P2), including the constructor `JSON.parse` path.
- **Lifecycle is mostly disciplined, with two P2s.** `onValueChangeSubscription` lacks a `Subscription.EMPTY` initializer (early-destroy NPE, `ACC-LIFE-01`), and the `onValueChange` merge + `FocusKeyManager` are built once over a static `items()` snapshot, so dynamically added items neither emit nor become arrow-navigable (`ACC-LIFE-02`).
- **What's strong.** ARIA *attribute* coverage is genuinely good (trigger `role`/`aria-expanded`/`aria-controls`, content `role="region"`/`aria-labelledby`, unique id linkage, reactive `aria-disabled`), `prefers-reduced-motion` is honored for the height transition, disabled items are correctly skipped by the CDK key manager (a refuted finding), and the trigger/content directive split is a deliberate, well-used primitive pattern.
- **What needs attention.** (1) The two P1s; (2) the controlled-`value`/dispatcher P2 cluster; (3) extracting + testing state-saving; (4) the lifecycle P2s; (5) a SemVer-gated API/type pass (`getState(): any`, `variant` degrading to `string`, no two-way `value`, missing JSDoc, internal directives re-exported); (6) test gaps on risky paths (state-saving, teardown, Arrow/Home/End nav).

## 3. Prioritized Findings (deduplicated, verified)

### P1 — High

**ACC-BUG-01 · `disabled` getter uses `??`, so accordion `[disabled]="false"` stomps an item's own `[disabled]="true"`** — `accordion-item.ts:123`.
`get disabled() { return this.accordion.disabled() ?? this._disabled; }`, with `disabled = input<boolean, unknown>(undefined!, { transform: booleanAttribute })` (`accordion.component.ts:92`). Angular does **not** run the transform on the initial value, so with no binding `disabled()` is `undefined` and the `??` fallthrough works. But the idiomatic `[disabled]="false"` (or a signal resolving to `false`) runs the transform → `disabled()` is `false` → `false ?? this._disabled` returns `false`, ignoring an item marked `[disabled]="true"`. The disabled gate guards `toggle()/open()/close()` (`accordion-item.ts:189/196/203`), ENTER/SPACE (`accordion.component.ts:215`), and `aria-disabled`/`data-disabled` — so the section becomes operable **and** misreports its disabled state (accessibility + correctness, contradicting the "Inactive Section" docs). Verified against `@angular/core` 20.3.24 input-signal semantics. Untested.
**Fix:** `return this.accordion.disabled() || this._disabled;` (the `undefined` default is falsy → per-item behavior preserved; explicit `false` no longer overrides). Add a regression test for the binding combination.

**ACC-A11Y-01 · Tab / Shift+Tab is hijacked to move between headers, breaking the WAI-ARIA APG keyboard pattern** — `accordion.component.ts:219-228`.
`keydownHandler` intercepts TAB/Shift+TAB, calls `keyManager.setNextItemActive()/setPreviousItemActive()` + `preventDefault()`. APG requires **Tab → next focusable element** (e.g. into an expanded panel) and **Up/Down Arrow → move between headers**. The handler is bound to host `(keydown)` and never checks `event.target`, so Tab pressed *inside an open `role="region"` panel* is also pulled back to a header — keyboard/SR users can't Tab to interactive content in an open section. Not a literal WCAG 2.1.2 trap (the handler `return`s without `preventDefault` at the first/last item, so focus escapes at the boundaries — hence P1, not P0). Arrow/Home/End nav is already wired (`withVerticalOrientation`/`withHorizontalOrientation`/`withHomeAndEnd`, `accordion.component.ts:180-186`) and forwarded via `keyManager.onKeydown` in the `else` branch.
**Fix:** delete both TAB branches (`219-228`) and let Tab fall through natively; header nav continues via the already-handled Arrow/Home/End keys. Update the tests that assert the wrong behavior (`ACC-TEST-03`, `ACC-TEST-13`); evaluate focus-sync (`ACC-A11Y-04`) in the same change.

### P2 — Should fix

**ACC-BUG-02 · `content().toggle()` lacks optional chaining → crashes a content-less item** — `accordion-item.ts:93`.
`content` is an optional `contentChild(forwardRef(() => KbqAccordionContentDirective))`. Every other access uses `this.content()?.…` (lines `184`, `216`, `221`), but the `expanded` setter hot path calls `this.content().toggle()`. An item with a header/trigger but no `<kbq-accordion-content>` throws `TypeError: …reading 'toggle'` on first toggle (click/ENTER/SPACE/`open()`/`openAll()`/`[value]`). All shipped examples pair item↔content 1:1, so it's latent.
**Fix:** `this.content()?.toggle();`. (Drives `ACC-TEST-06`.)

**ACC-BUG-03 · Dispatcher matching uses `id.includes(this.value)` — substring collisions expand the wrong items** — `accordion-item.ts:159` (multiple), `:163` (single).
`String.prototype.includes` is substring matching. The single-mode `value` setter, saved-state restore, and item-to-item notify all pass a **string** payload, so notifying `'item-10'` also matches an item whose value is `'item-1'` (`'item-10'.includes('item-1') === true`) — breaking single-selection. Triggers with substring-overlapping value schemes (e.g. `item-1`/`item-10`); untested (fixtures use non-overlapping values).
**Fix:** normalize to an array + exact element match, e.g. `Array.isArray(id) ? id.includes(this.value) : id === this.value`.

**ACC-BUG-04 · In `multiple` mode the dispatcher listener never closes items, so reassigning `[value]` accumulates** — `accordion-item.ts:158-161`.
The multiple-mode branch only ever assigns `this.expanded = true`; it never assigns `false` (unlike single mode at `:163`). `[value]="['item-1']"` then `[value]="['item-2']"` opens item-2 but leaves item-1 open — rendered state diverges from the "controlled value". Untested (the `value` spec is single-mode).
**Fix:** in multiple mode derive expanded from membership and assign unconditionally (with exact matching per `ACC-BUG-03`): `this.expanded = this.accordion.id === accordionId && <value ∈ id>;`.

**ACC-LIFE-01 · `onValueChangeSubscription` has no `EMPTY` initializer → `ngOnDestroy` can NPE on early destroy** — `accordion.component.ts:155` (decl), `:200` (teardown).
Declared without initializer, assigned only in `ngAfterContentInit` (`:188`), then `ngOnDestroy` unconditionally calls `.unsubscribe()`. If content-init throws earlier (e.g. `new FocusKeyManager(...)` at `:180`), the field is still `undefined` and teardown throws a second masking error. The sibling does it right (`accordion-item.ts:154`, `= Subscription.EMPTY`).
**Fix:** `private onValueChangeSubscription: Subscription = Subscription.EMPTY;` (or guard with `?.unsubscribe()`).

**ACC-LIFE-02 · `onValueChange` merge + `FocusKeyManager` are built once over a static `items()` snapshot** — `accordion.component.ts:180` (key manager), `:188-190` (merge).
`this.items()` evaluates the `contentChildren` signal to a plain array, not a `QueryList`/signal. CDK `ListKeyManager` only auto-tracks changes for a `QueryList` or signal arg (verified in `list-key-manager.mjs`). Consequence: items added later (e.g. via `@for` growth) **don't fire `onValueChange`** and are **not arrow-navigable**; a removed active item leaves a dangling `activeItem`. Untested (only static items).
**Fix:** rebuild the merge inside an `effect`/`takeUntilDestroyed`-scoped subscription keyed off `items()`, and pass the `items` signal (with an injector) to `FocusKeyManager` so CDK's effect branch tracks changes — or document that dynamically added/removed items are unsupported.

**ACC-ARCH-01 · State persistence (localStorage) lives in the UI container and is keyed by an unstable auto-id** — `accordion.component.ts:64, 87, 157, 162-178, 252-266`; callbacks at `accordion-item.ts:95, 172`.
`saveItemState`/`getSavedState` read/write `localStorage` (via the `KBQ_WINDOW` token, SSR-guarded by `isBrowser`), keyed by `this.id = kbq-accordion-${counter}`. There is **no consumer input to set a stable id/key**, so the key is instantiation-order-dependent — stable only for a fixed, statically-rendered set; it silently mismatches under lazy routes / conditional / reordered rendering. Storage policy in a UI component is an architecture smell; `KbqAccordionState` is unexported with no eviction.
**Fix:** extract an injectable persistence strategy (`KbqAccordionStateStore` via `InjectionToken`) and require a consumer-supplied stable key when state-saving is on (dev-warn if missing). Keep `KbqAccordion` free of direct storage access. Pairs with `ACC-ARCH-03`/`ACC-API-08`.

**ACC-A11Y-02 · `aria-level` is hardcoded to `2` with no way to fit the document outline** — `accordion-header.directive.ts:8`.
`role="heading"` + `aria-level="2"` is valid and a fine default, but it's fixed for every consumer. An accordion nested under an `h3` section yields an illogical heading outline for SR users navigating by level (WCAG 1.3.1). Not an automatic AXE failure (hence P2).
**Fix:** expose `level = input<number>(2)` (on the header or accordion) bound to `[attr.aria-level]`; document that consumers should match their page outline.

**ACC-TEST-01 · State-saving (`useStateSaving`/localStorage) is entirely untested** — `accordion.component.spec.ts` (gap).
Non-trivial, risky logic (constructor `JSON.parse`, restore-on-init at `:170-178`, force-vs-non-force write guard at `:253`) has zero coverage; no fixture sets `useStateSaving` and `localStorage` is never mocked.
**Fix:** add `describe('useStateSaving')` with a fake `KBQ_WINDOW.localStorage`: assert write on toggle (key = accordion id, serialized `{expanded,value}`), restore an open item from a pre-seeded entry, `hasSavedState` reflects parsed JSON, and a corrupt/empty stored value doesn't crash.

**ACC-TEST-02 · No teardown / subscription-leak tests; also covers the `ACC-LIFE-01` early-destroy NPE** — `accordion.component.spec.ts` (gap) for `:197-201` and `accordion-item.ts:176-181`.
None of the `ngOnDestroy` behaviors (focusMonitor stop, `openCloseAllActions.complete`, unsubscribe, item `destroyed`/listener removal) are asserted.
**Fix:** spy on `FocusMonitor.stopMonitoring` / `openCloseAllActions.complete`; subscribe to `item.destroyed` then `fixture.destroy()`; add a create-then-immediately-destroy test to catch the uninitialised-subscription NPE.

**ACC-TEST-03 · Arrow Up/Down + Home/End navigation is untested (only ENTER/SPACE/TAB covered)** — `accordion.component.spec.ts:394-474` (gap) for `accordion.component.ts:180, 182-186, 230`.
The whole reason `withHomeAndEnd()`/orientation config exists (the `else → keyManager.onKeydown` path) has no test, so a broken wiring wouldn't be caught. After `ACC-A11Y-01`, the TAB tests at `433-473` should be replaced by Arrow tests (`ACC-TEST-13`).
**Fix:** dispatch `DOWN_ARROW`/`UP_ARROW`/`HOME`/`END` to the host and assert active-item movement (`0→1` on Down, last on End, `0` on Home).

## 4. Refuted on verification (excluded — do not re-file)

- **"Disabled items aren't skipped by `FocusKeyManager` (no `skipPredicate`)."** False. CDK `ListKeyManager` installs a default `_skipPredicateFn = item => item.disabled` (`list-key-manager.mjs:27-29`), and `KbqAccordionItem.disabled` matches it, so Arrow/Home/End/typeahead already skip disabled items. A `.skipPredicate(...)` "fix" would be a no-op.
- **"`FocusKeyManager` typeahead subscription leaks."** False. `withHomeAndEnd()` does not enable typeahead; `withTypeAhead()` is never called, and `new FocusKeyManager(this.items())` passes a plain array (not a `QueryList`/signal), so no effect/QueryList subscription is created. `keyManager.destroy()` would be an effective no-op (still worth adding defensively — folded into `ACC-BUG-05`).
- **"Content measured while hidden → `--radix-accordion-content-height` is 0; expanded-on-init renders at 0px."** Contradicted by the committed visual baseline (`__screenshots__/01-light.png` shows initially-expanded panels at full height). The only valid residue — measured once, never re-measured on dynamic content change — is a narrow latent edge case (no `ResizeObserver`), captured implicitly by the `ACC-TPL`/`ACC-LIFE` notes.

## 5. Recommended Remediation Phases

**Phase 1 — Correctness & a11y blockers (land together).**
