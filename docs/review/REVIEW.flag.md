# Koobiq `flag` Component — Code Review & Improvement Plan

> Scope: `packages/components/flag` (component, SCSS, Jest spec, e2e fixture + Playwright spec + committed baselines, user guides, API guard report, all 8 docs examples, dev app, docs navigation) · Commit `b665e503` · 2026-08-28
> Generated by a multi-dimension review (architecture, correctness, accessibility, public API/types, styles, tests, docs) with manual verification of every finding against the source, the design-token set, the Angular sanitizer allowlist and a pixel-level decode of the committed Playwright baselines. 10 findings confirmed (P0×0, P1×2, P2×4, P3×4); 6 candidate findings refuted during verification (see Appendix A). This document is a review + roadmap; no source is modified by it.

---

## 1. Executive Summary

`KbqFlag` is a 47-line presentational wrapper (`flag.ts`) with an `<ng-content />` template, five signal inputs and a 53-line stylesheet. It is the newest component in the library — the package has exactly **one** functional commit (`7c3bdd8`, DS-1405, 2026-07-10; the other two are a Playwright bump and an SEO docs pass), so nothing here has yet been through a regression cycle. The code itself is modern and clean; both P1s are about what the component *renders* and what the docs *omit*.

- **Two of the three documented shapes do not crop — they letterbox, and the committed screenshots prove it.** `flag.scss:27` applies `object-fit: cover` to `svg, img`, but `object-fit` has no effect on an inline `<svg>` (it applies to replaced elements only), and inline SVG is the delivery mechanism used by 6 of 8 shipped examples, by the e2e fixture and by one of the Jest cases. Decoding `__screenshots__/01-light.png` at column x=255 shows the `square` flag sitting in an **11-device-px band of pure page background** at the top and the bottom; the same column in `01-dark.png` reads `rgb(19,22,29)` — identical to the page background — proving the band is transparency, not white flag content. The `circle` variant is worse: the same bands become two visible chords across the disc. The baselines were approved in this state, so the visual suite currently *guards* the defect instead of catching it (FLG-CSS-01).
- **The only working way to pass an SVG is a sanitizer bypass, and the guide never says so.** `<svg>` is absent from Angular's `VALID_ELEMENTS` allowlist (`@angular/core`, `core/fesm2022/debug_node.mjs:5589-5603`), so a plain `[innerHTML]` binding strips the flag entirely — which is why every SVG-bearing example calls `DomSanitizer.bypassSecurityTrustHtml`. `flag.en.md`/`flag.ru.md` show only `<img src>` projection (`:81-83, :87-90`) and mention neither `[innerHTML]`, nor the bypass, nor the fact that the bypass is only safe for build-time-bundled strings. Eight copy-paste-ready examples teach an unbounded XSS sink by example (FLG-DOC-01).
- **The accessibility contract exists but is entirely opt-in, and the repo's own fixture ships the state the guide forbids.** `flag.ts:24-26` is a well-designed three-way ARIA binding, yet the default — no `label`, no `decorative` — emits no `role`, no `aria-label` and no `aria-hidden`, which is exactly the case `flag.en.md:92` declares "not allowed". `flag.spec.ts:141-155` codifies that state as expected behaviour, and all six `<kbq-flag>` instances in `e2e.ts:20-27` are written that way (FLG-A11Y-01).
- **A documented extension point is demonstrated nowhere.** `flag.en.md:19` tells consumers that non-3:2 flags are supported by overriding `--kbq-flag-aspect-ratio`; `git show 96072c7a1` shows the surrounding heading was renamed from "## Aspect ratio" to "## Shape / ### Rectangle" without touching the example beneath it, which is a select demo (`@title Flags in a select`). No example, no test and no e2e case overrides that variable anywhere in the repo (FLG-DOC-02).

Genuine strengths worth preserving, and there are real ones: this is the most modern component file in the library — signal inputs with `booleanAttribute` transforms, JSDoc on **every** public member (the API report at `flag.api.md:9-20` carries no `(undocumented)` marker outside the `ɵ` internals, which almost no sibling package achieves), tight union types in a dedicated `flag.types.ts`, `OnPush`, standalone, host-object bindings, zero `@HostBinding`, zero RxJS, zero lifecycle hooks and zero SSR-hostile globals. The Jest spec uses a fresh single-purpose host per case rather than one mutable host — the pattern other reviews in this series ask for. Both design tokens resolve in light and dark (`css-tokens-light.css:74, 96`). And the guides are genuinely good product writing: eight real examples, perfect EN/RU section parity, and a whole section arguing that a flag is not a language — including an example that deliberately does not use the component at all.

## 3. Prioritized Findings (deduplicated, verified)

### P0 — Release blockers

None.

### P1 — High

**FLG-CSS-01 · `object-fit: cover` is inert on inline `<svg>`, so `square` and `circle` letterbox instead of cropping — and the committed baselines enshrine it** — `flag.scss:20-28, 40-47`, `e2e.ts:7-13, 20-22`, `__screenshots__/01-light.png`, `__screenshots__/01-dark.png`.
`.kbq-flag` sizes its child with `svg, img { width: 100%; height: 100%; object-fit: cover; }` (`flag.scss:22-28`) and the shape modifiers only switch `--kbq-flag-aspect-ratio` to `1 / 1` (`flag.scss:40-43`). `object-fit` applies to replaced elements; an inline `<svg>` in an HTML document is not one, so the property is dropped and the SVG's own `preserveAspectRatio` default (`xMidYMid meet`, i.e. *contain*) decides the fit. An `<img src="…3x2/DE.svg">` therefore **crops**, while the byte-identical flag delivered as inline SVG **letterboxes** — and inline SVG is what 6 of the 8 shipped examples, the e2e fixture and `flag.spec.ts:34-49` actually use. The e2e baselines make this measurable rather than theoretical. The fixture renders a 22×16 (11:8) sample SVG at `font-size: 48px` (`e2e.ts:7-13, 36`) at 2× device scale; decoding `01-light.png` down column x=255 (the `square` cell) gives: border hairline at y=32-33, then **y=34-44 pure `rgb(255,255,255)`**, red field from y=46, and the mirror band at y=115-125 — an 11-device-px transparent band top and bottom, exactly the 6.5 CSS px the `meet` fit predicts for 11:8 content in a 1:1 box. The same column in `01-dark.png` reads `rgb(19,22,29)` for that band, identical to the page background at y=0, which rules out "white flag content" and confirms transparency. The `rectangle` cell letterboxes too whenever the source ratio is not 3:2 — row y=60 of `01-light.png` shows 4-device-px white bands at x=34-37 and x=170-173, inside the hairline. In the `circle` cell (column x=400) the bands become two visible chords across the disc, which is the most obviously broken of the three. The guide papers over the square case by telling consumers to source 1:1 images (`flag.en.md:25`, `flag.ru.md:25`), but that is advice, not a fix: the component silently produces two different renderings for the same shape depending on how the flag was supplied, and the approved screenshots mean CI will never report it.
**Fix:** emulate `cover` for inline SVG, which `object-fit` cannot do. Inside `.kbq-flag` add a rule for the direct SVG child — `position: absolute; top: 50%; left: 50%; translate: -50% -50%; width: auto; height: auto; min-width: 100%; min-height: 100%;` — the host already sets `position: relative` (`flag.scss:10`) and `overflow: hidden` (`flag.scss:17`), so the overflow is clipped and the result matches `<img>`'s `cover`. Keep `object-fit: cover` on `img`, and note in the SCSS comment at `flag.scss:20-21` that the two elements need different mechanisms — the comment currently asserts they are interchangeable. If a DOM-level fix is preferred instead, normalise a projected direct `<svg>` child to `preserveAspectRatio="xMidYMid slice"` through `Renderer2`, but the CSS route needs no imperative code and is SSR-safe. Then change `e2e.ts` so `square`/`circle` are rendered from an explicitly non-square source (the current 22×16 sample already is) *and* regenerate the baselines with `yarn run e2e:docker:update-snapshots` — never natively. Acceptance is pixel-level: column x=255 of the new `01-light.png` must show red at y=34, with no run of page-background colour between the hairline and the flag.

**FLG-DOC-01 · The only mechanism that actually renders an SVG is an undocumented sanitizer bypass** — `flag.en.md:81-90`, `flag.ru.md:81-90`; examples `flag-overview-example.ts:15, 49`, `flag-square-example.ts:14, 34`, `flag-circle-example.ts:14, 33`, `flag-stylized-example.ts:13, 53`, `flag-sizes-example.ts:23, 34`, `flag-fallback-example.ts:20, 56`, `flag-aspect-ratio-example.ts:36, 46, 83`; `flag.spec.ts:34-49`; `e2e.ts:21, 25-26, 52`.
Both guides show exactly two markup snippets and both project an `<img>` (`flag.en.md:82, 88`). Every shipped example does something else: it binds a `SafeHtml` produced by `DomSanitizer.bypassSecurityTrustHtml` into `[innerHTML]` on the `<kbq-flag>` host. That is not stylistic preference — it is mandatory. Angular's HTML sanitizer allowlist is built from `VOID_ELEMENTS`/`BLOCK_ELEMENTS`/`INLINE_ELEMENTS` (`@angular/core`, `core/fesm2022/debug_node.mjs:5589-5603`) and contains no `svg` entry, and `svg` is not in `SKIP_TRAVERSING_CONTENT_IF_INVALID_ELEMENTS` either, so an unbypassed `[innerHTML]="'<svg …>'"` has the root element *and* its `<path>`/`<rect>` children stripped and renders nothing. The consequence is that a consumer following the published guide cannot reproduce a single one of the eight examples, and a consumer following the examples copies `bypassSecurityTrustHtml` with no statement anywhere of when that is safe. Today the bypassed strings are compile-time imports from `country-flag-icons` (`flag-overview-example.ts:4`), which is fine; swap that constant for a country code coming from an API response and the same three lines become a stored-XSS sink, with the library's own documentation as the provenance. The package publishes an `.md` file whose Accessibility section is precise to the point of enumerating a forbidden case (`flag.en.md:92`) while saying nothing at all about the one API surface with a security consequence.
**Fix:** add a "Passing the flag" section to `flag.en.md`/`flag.ru.md`, before "## Shape", that shows all three delivery forms with their trade-offs: projected `<img src>` (safest, no bypass, `object-fit` works), projected inline `<svg>` written in the template (no bypass needed — Angular compiles the SVG namespace directly), and `[innerHTML]` with `bypassSecurityTrustHtml` for strings from a flag package. State explicitly that `bypassSecurityTrustHtml` must only ever receive a build-time constant, and that flag markup arriving over the network must be re-derived from a validated ISO code and looked up in the local set — never bypassed. Cross-link the `hasFlag` guard already shown at `flag.en.md:54-61`, which is the right pattern and only needs to be connected to this one. Guard the regression with a `yarn run e2e:docs` pass over the corrected snippets.

### P2 — Should fix

**FLG-ARCH-01 · `[innerHTML]` on the host structurally conflicts with the component's own `<ng-content />`** — `flag.ts:14`, `flag.spec.ts:34-49`, `e2e.ts:21`, `flag-aspect-ratio-example.ts:36`.
The template is `<ng-content />` (`flag.ts:14`), so the host element is where Angular inserts projected nodes. `[innerHTML]` bound from a parent view compiles to a write of `hostElement.innerHTML` during that parent's update pass — after the component's own view has been created. When nothing is projected, `<ng-content />` contributes no DOM and the two coexist by accident, which is why all current usages work. Combine them and the innerHTML write silently removes the projected nodes on the first change-detection cycle; if the projected content was structural (`@if`/`@for`, as at `flag-fallback-example.ts:19-25`), the view's insert/remove anchors now point at nodes that are no longer children, and the next structural update throws at the DOM level. Nothing in the package prevents, detects or documents this: the class JSDoc (`flag.ts:5-10`) advertises projection, the Jest suite blesses `[innerHTML]` (`flag.spec.ts:34-49`), and the SCSS comment at `flag.scss:20-21` treats them as two equal options ("whether it is projected directly or bound via `[innerHTML]`"). The two are not equal; they are mutually exclusive on the same element.
**Fix:** give the string form its own slot instead of borrowing the host. Wrap the projection in a container the component owns — `template: '<span class="kbq-flag__content"><ng-content /></span>'` is not required, because the existing style rule already matches descendants rather than direct children (`flag.scss:22-23`, and its comment says so) — and add a first-class input, e.g. `readonly svg = input<SafeHtml | string>()`, rendered into a sibling `<span [innerHTML]="svg()">` that is only created when the input is set. Then migrate the eight examples and `e2e.ts` off host-level `[innerHTML]`. Cheapest interim step if the input is deferred: state the exclusivity in the class JSDoc and in the new guide section from FLG-DOC-01, and add a Jest case that projects an `<img>` **and** binds `[innerHTML]` on the same `<kbq-flag>` and asserts the projected node survives — it fails today, which is the point.

**FLG-A11Y-01 · The documented accessibility rule has no default and no enforcement; the forbidden state is what the component ships** — `flag.ts:24-26`, `flag.spec.ts:141-155`, `flag.en.md:92`, `flag.ru.md:92`, `e2e.ts:20-27`.
The host block is genuinely well designed: `[attr.role]` emits `img` only when a `label` is present and `decorative` is not, `[attr.aria-label]` mirrors it, and `[attr.aria-hidden]` emits `true` for the decorative case (`flag.ts:24-26`) — three branches, all three covered by tests (`flag.spec.ts:108-156`). The problem is the fourth state. With neither input set, the component emits nothing at all, so an inline `<svg>` (the mechanism from FLG-DOC-01) reaches the accessibility tree as a nameless graphic. `flag.en.md:92` is unambiguous that this is the one case that must not happen: a flag must have either adjacent visible text plus `decorative`, or a `label`. The library then does three things that push consumers into it: it makes that state the default, it asserts it as correct behaviour (`flag.spec.ts:141-155`, "should not set role/aria when neither labelled nor decorative"), and it ships it in its own fixture — all six `<kbq-flag>` instances in `e2e.ts:20-27` carry neither input. Note the precise claim: this is a WCAG 1.1.1 judgement, not an automated failure — axe-core does not flag a custom element that carries no role, which is exactly why the state survived review. Separately, `decorative` silently wins over `label` when both are set (`flag.ts:24-25`; the behaviour is deliberate and tested at `flag.spec.ts:125-139`), but a consumer who adds `decorative` to a flag that already had a meaningful `label` gets no signal that the name was discarded.
**Fix:** make the fail-safe the default — extend `[attr.aria-hidden]` to `"decorative() || !label() ? 'true' : null"` so a flag with no accessible name is never announced as a nameless graphic, and keep `decorative` as the explicit, self-documenting form. Update `flag.en.md:92`/`flag.ru.md:92` to describe the resulting default (unlabelled ⇒ hidden) so the rule and the implementation agree. Add `decorative` to all six fixture instances in `e2e.ts:20-27` — a fixture is documentation too. Add Jest cases for the new branch (unlabelled ⇒ `aria-hidden="true"`, labelled ⇒ no `aria-hidden`), and rewrite `flag.spec.ts:141-155` rather than deleting it, since it is the case that changes.

**FLG-DOC-02 · The documented `--kbq-flag-aspect-ratio` override is demonstrated nowhere, and the example placed under it demonstrates something else** — `flag.en.md:19`, `flag.ru.md:19`, `flag-aspect-ratio-example.ts:24-26, 59-63`; history at `96072c7a1`.
`flag.en.md:19` promises that "flags with a different ratio (e.g. 4:3) are supported by overriding the `--kbq-flag-aspect-ratio` CSS variable", and `flag.ru.md:19` says the same. A repo-wide grep for `--kbq-flag-aspect-ratio` returns four hits: the two guide sentences, and the two declarations in `flag.scss:7, 42`. Nothing overrides it — not an example, not the dev app, not the e2e fixture, not a test. The example embedded directly beneath that sentence, `flag-aspect-ratio`, is a country picker: its `@title` is "Flags in a select" (`flag-aspect-ratio-example.ts:24-26`) and it pins `height: 12px` rather than touching the ratio. `git show 96072c7a1` explains how: the SEO pass renamed the section from "## Aspect ratio" to "## Shape / ### Rectangle" and rewrote the prose without moving or renaming the example, so a directory name that used to match its section now contradicts its content. The example carries a second, smaller inconsistency of its own — the comment at `flag-aspect-ratio-example.ts:59` says the prefix flag is matched "to the flag shown inside the options (21×14)" while the rule beneath it sets `height: 12px`, which at the default 3:2 ratio is 18×12, not 21×14. The override also has an undocumented specificity requirement: `--kbq-flag-aspect-ratio` is declared on `.kbq-flag` (`flag.scss:7`, specificity 0,1,0), so a consumer's single-class rule in a global stylesheet ties with it and loses on source order once the component's `ViewEncapsulation.None` styles are injected into `<head>`. It works from an Angular component's `styles` block only because emulated encapsulation appends an attribute selector (0,2,0) — which is why `flag-stylized-example.ts:16-18` can successfully override `--kbq-flag-border-radius` and a plain global rule cannot.
**Fix:** add a genuine 4:3 case. Either extend `flag-aspect-ratio-example` with a second row that sets `--kbq-flag-aspect-ratio: 4 / 3` on a non-3:2 source and rename the directory to match what it shows (`flag-select`), or add a small `flag-custom-ratio` example and re-point the `<!-- example(…) -->` anchor at `flag.en.md:21`/`flag.ru.md:21` — renaming a directory also requires regenerating `packages/docs-examples/components/flag/index.ts` and the dev-app template at `packages/components-dev/flag/module.ts:9-16`. Fix the `(21×14)` comment to `(18×12)` or change the height to `14px`. And document the specificity requirement in one sentence: the override must be set on the element (inline style or a component-scoped rule), not from a bare global class.

**FLG-TEST-01 · The `square` modifier and the `rectangle` default are untested, and the visual suite covers the one dimension it should not lock in** — `flag.spec.ts:79-92, 94-106`, `e2e.ts:18-29`.
The Jest suite is 9 cases and structurally good — a fresh single-purpose host per case, no shared mutable state. The coverage map is uneven, though. `shape` is exercised only through `circle` (`flag.spec.ts:79-92`), which asserts `kbq-flag_circle` present and `kbq-flag_square` absent; `shape="square"` is therefore never asserted *present*, and the `rectangle` default — the only state in which neither modifier class must appear — is never asserted at all, so a typo in either of the two class bindings at `flag.ts:20-21` would be caught in one direction only. `empty` is asserted present (`flag.spec.ts:94-106`) but its `false` default is not; `shadow` is well covered in both directions (`:51-63, :65-77`); `label`'s empty-string edge (`label=""` falls to `null` through the `||` at `flag.ts:25`) is untested. The e2e side is the bigger gap. The fixture (`e2e.ts:18-29`) renders three shapes and two shadows plus `empty` at `font-size: 48px` — but never renders a flag inline with text, which is the component's primary documented use and the only thing that exercises `height: 1em` and `vertical-align: middle` (`flag.scss:14, 16`); never exercises a token override, so `--kbq-flag-border-radius` and `--kbq-flag-aspect-ratio` have no visual guard; and, per FLG-CSS-01, its approved baselines currently certify the letterboxed rendering as correct.
**Fix:** add Jest cases for `shape="square"` (class present), the `rectangle` default (neither modifier class present), the `empty` default, and `label=""` ⇒ no `role`/`aria-label`; add the FLG-A11Y-01 branch cases at the same time. Extend `e2e.ts` with a third row containing a flag inline in a sentence of body text at a normal font size, plus a cell overriding `--kbq-flag-aspect-ratio` to `4 / 3` and one overriding `--kbq-flag-border-radius`. Regenerate baselines only through `yarn run e2e:docker:update-snapshots`. A mutation check is worth running once: revert `[class.kbq-flag_square]` to a constant and confirm at least one Jest case fails — today none would. `jest-axe` is deliberately not recommended here (see Appendix A).

### P3 — Nice to have / hygiene

**FLG-CSS-02 · `circle` hardcodes its radius instead of switching the token, so the documented radius token is inert for circles** — `flag.scss:6, 18, 40-47`.
The stylesheet establishes a clean pattern for shape: `--kbq-flag-aspect-ratio` is declared once (`flag.scss:7`), consumed once (`:15`) and *switched* by the modifiers (`:40-43`). `border-radius` breaks it: the token is declared at `:6` and consumed at `:18`, but `.kbq-flag_circle` writes `border-radius: 50%` directly (`:45-47`). Because that rule is `.kbq-flag.kbq-flag_circle` (0,2,0) and the token consumer is `.kbq-flag` (0,1,0), a consumer setting `--kbq-flag-border-radius` on a circular flag gets no effect and no diagnostic — the value is computed and discarded. It also means the two shape properties are configured through two different mechanisms for no stated reason. The `::after` hairline is unaffected either way since it uses `border-radius: inherit` (`:35`).
**Fix:** replace `border-radius: 50%` at `flag.scss:46` with `--kbq-flag-border-radius: 50%`, matching the aspect-ratio modifier immediately above it. Behaviour is identical for every current caller — `flag-stylized-example.ts:18` is the only in-repo override and it targets a rectangle — and the token becomes uniformly meaningful. Cover with the `--kbq-flag-border-radius` e2e cell from FLG-TEST-01.

**FLG-CSS-03 · The `empty` placeholder is painted with a translucent *disabled-state* token** — `flag.scss:5, 49-52`; token values at `css-tokens-light.css:96`, `css-tokens-dark.css:96`.
`--kbq-flag-empty-background` resolves to `--kbq-states-background-disabled`, which is `oklch(24.7% 0.1052 257.1 / 0.08)` in light and `oklch(84.5% 0.0860 281.6 / 0.10)` in dark — an 8–10% alpha overlay, not an opaque neutral. Two consequences. Semantically, the placeholder means "unknown country code", not "disabled control", and the guides describe it as "a neutral placeholder (a gray rectangle, square, circle…)" (`flag.en.md:65`, `flag.ru.md:65`) — a reader picking a token from that description would not pick a states token. Visually, a 0.08-alpha fill is a tint of whatever sits behind it, so on the default page background it reads as the intended light grey (visible in `01-light.png`), but inside a coloured card, a selected list option or a toast it takes on that surface's hue instead of reading as an absent flag. The `empty` cell also still gets the inset hairline because `shadow` defaults to `inset` (`flag.ts:40`), which is the right call and worth keeping.
**Fix:** point `--kbq-flag-empty-background` (`flag.scss:5`) at a background token that carries the intended meaning rather than a state — `--kbq-background-secondary` or the closest opaque neutral in `css-tokens-{light,dark}.css` — and verify it against both themes in the e2e fixture, which already has an `empty` cell (`e2e.ts:27`). If a translucent fill is deliberate, say so in the SCSS comment at `flag.scss:49` so the next reader does not "fix" it.

**FLG-STYLE-01 · Package file layout deviates from the documented component structure** — `packages/components/flag/` (no `flag-tokens.scss`, no `_flag-theme.scss`), `module.ts`, `flag.api.md:22-30`.
AGENTS.md specifies `<component-name>-tokens.scss`, `_<component-name>-theme.scss` and `<component-name>.module.ts`; this package has none of the three. The four custom properties live inline at `flag.scss:4-7` and the NgModule is a bare `module.ts`. None of this is functionally wrong — 53 of the 64 component packages carry a `-tokens.scss`, but nothing aggregates those files (a grep for `divider-tokens` finds exactly one reference, from `divider.component.ts` itself), so the split is organisational; and a `_*-theme.scss` is genuinely unnecessary here because both colours come from theme-adaptive design tokens that already resolve in both themes (`css-tokens-light.css:74, 96`, `css-tokens-dark.css:74, 96`). The bare `module.ts` matches `skeleton` and diverges from everything else. One small real gap: `KbqFlagModule` is the single member of the public surface still marked `// @public (undocumented)` (`flag.api.md:22`), in a report that is otherwise fully documented.
**Fix:** decide once and record it. Either split the four declarations at `flag.scss:4-7` into `flag-tokens.scss` and add it to `styleUrls` (the pattern at `divider.component.ts:7`) and rename `module.ts` → `flag.module.ts`, or leave both and add the exception to AGENTS.md alongside the `checkbox`/`datepicker`/`skeleton` naming notes so the next reviewer does not re-file this. Add a one-line JSDoc to `KbqFlagModule`; remember that removing an `(undocumented)` marker changes the report, so the same change needs `yarn run build:components` then `yarn run approve-api` — build first, the guard reads `dist/*.d.ts`.

**FLG-DOC-03 · The docs entry ships no preview image, so the gallery card and the social preview both fall back** — `apps/docs/src/app/structure.ts:650-661`, consumed at `apps/docs/src/app/components/welcome/welcome.component.html:22` and `apps/docs/src/app/services/seo.ts:85, 107`.
The flag entry sets `svgPreview: ''` (`structure.ts:656`). The welcome grid substitutes `generic-${theme}.png` (`welcome.component.html:22`, and only `generic-light.png`/`generic-dark.png` exist under `assets/images/welcome/`), and the SEO service returns `FALLBACK_IMAGE` with the generic alt text (`seo.ts:85, 107-109`) — so every `og:image` for the flag pages is the site-wide placeholder. Only three entries in the whole structure file have an empty `svgPreview` (`structure.ts:236, 278, 656`), and the other two are non-component pages. The component is also flagged `isNew: expiresAt('2026-10-07')` (`structure.ts:660`), so it is being actively promoted in the navigation with no artwork behind it. Worth landing before the `isNew` badge expires on 2026-10-07, since that is the window in which the card gets the most traffic.

## 4. Recommended Remediation Phases

**Phase 1 — Make the shapes render what they promise.**
IDs: FLG-CSS-01, FLG-CSS-02. Emulate `cover` for inline SVG, route the circle's radius through its own token, then regenerate the Playwright baselines through Docker. This is the only user-visible rendering defect and it depends on nothing below it. The acceptance criterion is pixel-level, not "looks right" — see the column assertion in Verification Strategy.

**Phase 2 — Document and harden the content contract.**
IDs: FLG-DOC-01, FLG-ARCH-01, FLG-DOC-02. Add the "Passing the flag" section covering all three delivery forms and the bounds on `bypassSecurityTrustHtml`; give the string form its own slot instead of the host element; make the `--kbq-flag-aspect-ratio` claim true with a real example. Sequenced after Phase 1 because the guide's advice about which shape to use with which source changes once cropping works. Ships with `yarn run e2e:docs` over the corrected snippets.

**Phase 3 — Close the accessibility contract.**
IDs: FLG-A11Y-01. Default the unlabelled flag to `aria-hidden="true"`, align `flag.en.md:92`/`flag.ru.md:92` with the implementation, mark the fixture instances `decorative`, and rewrite the "neither" test around the new behaviour. Independent of Phases 1–2 but placed after them because it edits the same two guide files and the same fixture, and doing it last avoids three rounds of conflicts.

**Phase 4 — Tests and hygiene.**
IDs: FLG-TEST-01, FLG-CSS-03, FLG-STYLE-01, FLG-DOC-03. Close the `square`/`rectangle`/default gaps in Jest, add the inline-with-text and token-override e2e rows, re-token the empty placeholder, settle the file-layout question, ship the preview artwork. The e2e additions should land in the same Docker baseline run as any Phase 4 style change so the snapshots churn once.

## 5. Verification Strategy

General gates, run sequentially — never in parallel (`project_no_parallel_heavy_builds`):
- `npx jest packages/components/flag`. There are no in-repo consumers of `<kbq-flag>` outside the package's own docs examples and dev app, so no sibling suites are at risk — a genuinely unusual amount of freedom for a change of this size.
- `yarn run eslint`, `yarn run stylelint`, `yarn run prettier` on touched files.
- `yarn run build:components`, then `yarn run check-api`. `approve-api` only in Phase 4, where the `KbqFlagModule` JSDoc intentionally changes the report.
- `yarn run e2e:docker` for anything visual; regenerate baselines only with `yarn run e2e:docker:update-snapshots` — the committed `__screenshots__` are Linux, compared at `threshold: 0` with no platform suffix, so a native run fails on font rasterization alone.
- Manual smoke: `yarn run dev:flag` renders all eight examples (`packages/components-dev/flag/module.ts:9-16`) with a theme toggle, which covers both token themes in one page.

Per-phase assertions:
- **Phase 1:** decode the regenerated `__screenshots__/01-light.png` down column x=255 — the run of `rgb(255,255,255)` between the hairline at y=32-33 and the red field must be gone, and the same column in `01-dark.png` must contain no run of `rgb(19,22,29)` inside the flag box. Visually: the `circle` cell has no chords. `<kbq-flag shape="square">` fed a 3:2 `<img>` and the same flag fed as inline SVG must be pixel-identical — that equivalence is the actual contract being restored.
- **Phase 2:** grep the guides for `bypassSecurityTrustHtml` — it appears with an explicit "build-time constants only" caveat. Every example still renders in `yarn run dev:flag` after migrating off host-level `[innerHTML]`. A new Jest case projects an `<img>` alongside the string input and both survive change detection. `grep -rn -- '--kbq-flag-aspect-ratio' packages/` returns at least one *override*, not only declarations and prose.
- **Phase 3:** `<kbq-flag><img src="…" alt=""/></kbq-flag>` with no inputs reports `aria-hidden="true"`; adding `label="Germany"` removes it and reports role `img` with that name. AXE passes on the dev page both before and after — it passed before too, which is why the finding is a WCAG judgement and not an automated failure.
- **Phase 4:** `npx jest packages/components/flag` reports the new cases green, and reverting `[class.kbq-flag_square]` (`flag.ts:20`) to a constant makes at least one of them fail — a class-assertion suite that passes against a broken binding is worth nothing. The docs welcome grid shows a flag-specific card image in both themes, and `curl`ing the flag page's `og:image` no longer returns the generic asset.

## Appendix A — Review Methodology

Findings were gathered by reading the complete package — all 12 source files plus both committed screenshots — then cross-checking each candidate against five independent sources: the workspace compiler and Jest settings (`tsconfig.json:114-118`, `jest.config.js:13-14`), the API guard report (`tools/public_api_guard/components/flag.api.md`) and its registration (`tools/api-extractor/config.json:26`), the live design-token set (`@koobiq/design-tokens/web/new/css-tokens-{light,dark}.css`), Angular's own sanitizer allowlist in `node_modules`, and the git history of the package. A repo-wide grep for `kbq-flag`/`KbqFlag` outside the package returns only the two generated SEO description strings (`apps/docs/src/app/seo-descriptions.ts:123-124`), so unlike most components in this review series there is **no consumer evidence to lean on** — nobody in the tree has yet had to work around anything. That absence is itself informative: the package has had exactly one functional commit (`7c3bdd8`, DS-1405, 2026-07-10) and has never been exercised by a second author.

Because consumer workarounds were unavailable, FLG-CSS-01 was verified directly against the committed Playwright baselines instead. Both PNGs were decoded with a throwaway zlib-based reader (no image library exists in this workspace) and sampled row- and column-wise; the numbers quoted in the finding are measured pixel runs, not estimates, and the light/dark comparison of the same coordinate is what distinguishes "transparent letterbox band" from "white content".

Refuted during verification:
- **"`--kbq-flag-shadow-color` and `--kbq-flag-empty-background` reference undefined tokens"** — refuted. `--kbq-line-contrast-fade` and `--kbq-states-background-disabled` are both defined in the live set (`css-tokens-light.css:74, 96`; `css-tokens-dark.css:74, 96`), so neither `var()` is dead. The surviving concern is the *choice* of the states token, filed as FLG-CSS-03.
- **"The `examples.flag.*.md` stubs break the Examples tab"** — refuted; the equivalent finding exists in sibling packages but not here. No `examples.flag.*.md` files exist, `structure.ts:659` sets `hasExamples: false`, and all eight examples are embedded inline in the overview guide, so there is no dead file and no broken surface. This is the cleanest handling of the examples question in the packages reviewed so far.
- **"The Jest spec should run `jest-axe`, per the AGENTS.md AXE mandate"** — refuted as a repo requirement. Only 5 of 64 component packages use `jest-axe`, so its absence is the norm rather than a deviation; more to the point, axe-core would pass the exact state FLG-A11Y-01 describes, because a custom element carrying no role is not a violation. Adding it would create false confidence, so it is deliberately absent from the FLG-TEST-01 fix.
- **"`llms-full.txt` contradicts the published guide"** — refuted as a flag defect. `apps/docs/src/llms-full.txt:14158` still carries the pre-SEO wording ("By default flags use a 3:2 ratio…") that `96072c7a1` replaced, but `llms.txt` is a release-time generated snapshot regenerated by the release tooling, not inside a component change (`project_llms_txt_generated_stale`).
- **"Default ARIA text must come from `kbqInjectA11yLocaleConfiguration()`"** — refuted, not applicable. `KbqFlag` provides no default ARIA string of its own; the only accessible name is the consumer-supplied `label` input (`flag.ts:46`), so there is nothing for the component to localize.
- **"The examples depend on `country-flag-icons` without declaring it"** — refuted. It is declared as a root devDependency (`package.json:105`) and as a peer dependency of the published `@koobiq/docs-examples` package, so a consumer installing the examples package is told to bring it.

Corrected on verification:
- **FLG-CSS-01** was drafted as "`square`/`circle` may distort a non-square flag". Decoding the baselines showed the opposite failure mode — no distortion at all, but transparent letterbox bands — and identified the cause (`object-fit` does not apply to inline `<svg>`, only to replaced elements). The finding moved from a speculative styling note to a P1 with measured pixel evidence and a pixel-level acceptance test.
- **FLG-A11Y-01** was drafted as P1 "the host carries no ARIA at all", by analogy with the divider review. Reading `flag.ts:24-26` showed a complete, three-branch, fully tested ARIA contract does exist; the real defect is that it is opt-in with no safe default, so the wording was rewritten around the fourth (unhandled) state and the severity dropped to P2.
- **FLG-DOC-02** was drafted as "the `flag-aspect-ratio` example is misnamed". `git show 96072c7a1` showed the name was accurate until the SEO pass renamed the surrounding section without touching the example, which reframed the finding around the larger problem: a documented CSS extension point with zero demonstrations and an undocumented specificity requirement.
