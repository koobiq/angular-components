# OpenSpec baseline audit

<!-- cspell:disable -- the findings quote code identifiers verbatim -->

A static audit of the 63 main specs in `openspec/specs/` against the code at `c9c196a9b` (2026-10-21). Each requirement was mapped to a test that asserts it, or confirmed by reading the source after an attempt to refute it. Nothing was built or run.

- **By test** — a unit or e2e test asserts the requirement.
- **By source** — no test; the code implements it.
- **Wrong** — the code or a test contradicts at least one statement in it.
- **Unverifiable** — only a real browser could settle it.

Every wrong requirement was corrected in a change `correct-<component>-baseline` (`MODIFIED`, or `REMOVED` plus `ADDED` when a scenario had to go). All of them passed `openspec validate --strict` and were archived on 2026-10-21 into `openspec/changes/archive/2026-10-21-correct-<component>-baseline/`, so the main specs already carry the corrections.

## accordion

Correction change: `correct-accordion-baseline`

- **Controlled value** (modified): The spec says a bound string or array expands exactly the items whose values it contains, and that the bound value is applied again only when it changes. In single mode, `valueArray` keeps only the first non-empty value, so binding `\['item-1','item-2'\]` expands only `item-1`. A `stateSavingKey` change also re-notifies the bound value even though it did not change, which undoes the user's toggles. Evidence: packages/components/accordion/accordion.ts:231-235 (slice(0, 1) outside multiple mode); accordion.ts:284-289 + 397-398 (ngAfterContentChecked -> restoreState(false) -> initialValue returns valueArray while value is bound)
- **Unusable saved payloads** (modified): The spec says any payload that is not an array of strings (or the previous format) is ignored. `normalizeAccordionState` keeps the string entries of a mixed array such as \['item-1', 42\] and restores them. It rejects an array only when the array is non-empty and holds no string at all. Objects are accepted when at least one entry has a boolean `expanded` and a string `value`, and the other entries are dropped. Evidence: packages/components/accordion/accordion.ts:63-83 (line 69: `values.length || !parsed.length ? values : null`)
- **Changing the state saving key** (modified): The spec says that after a key change the state saved under the new key is restored, or the current state is kept when nothing is saved there. While `value` is bound, `initialValue()` returns the bound value before reading the saved state. A key change therefore re-applies the bound value: the new key's state is not restored, and the user's toggles are undone even when nothing is saved under the new key. Evidence: packages/components/accordion/accordion.ts:284-289, 350-356, 397-398

## actions-panel

Correction change: `correct-actions-panel-baseline`

- **Closing only once** (modified): The spec says that once a panel has started closing, further close calls on its reference are ignored and beforeClosed never emits again. Only KbqActionsPanelRef.close() clears containerInstance. A panel closed by history navigation or Dialog.closeAll() goes through handleOverlayDetachments/DialogRef.close without that call, so a later ref.close() still emits beforeClosed, after afterClosed. Evidence: packages/components/actions-panel/actions-panel-ref.ts:78-92, 113-120; @angular/cdk dialog.mjs DialogRef.close/closeAll; \_overlay-module-chunk.mjs OverlayRef.attach (disposeOnNavigation) and dispose()
- **Close button** (modified): The spec says clicking the button closes the panel. In fact the button calls close() on the KbqActionsPanel that the container's injector resolves, and that injector is parented on config.injector when one is given. If the injector option resolves another instance, the click closes that instance's panel (or nothing) and this panel stays open. Evidence: packages/components/actions-panel/actions-panel-container.ts:73,139,161-163; actions-panel.ts:201-204; cdk dialog.mjs \_attachContainer
- **Escape closes the panel** (modified): The spec says Escape inside the panel always closes it. handleEscape() calls the same injector-resolved KbqActionsPanel.close() as the close button, so the injector-option case fails the same way. Angular's keydown.escape listener also does not fire when Alt, Control, Meta or Shift is held, so Shift+Escape leaves the panel open. Evidence: packages/components/actions-panel/actions-panel-container.ts:93,195-201; @angular/platform-browser \_browser-chunk.mjs KeyEventsPlugin.matchEventFullKeyCode (lines 220-244)
- **Pop-ups of the content are not scoped to the element** (modified): The spec says content overlays are "placed as for a trigger outside the panel". When a kbqOverlayLayer encloses the element, findLayer() skips any layer whose host contains the scoped .cdk-overlay-container. A dropdown from inside the panel therefore stays in the application-wide container, while one from a trigger elsewhere in that layer goes into the layer. Evidence: packages/components/core/overlay/overlay-layer.ts:157-173; overlay-layer.spec.ts test 'keeps a panel opened from an overlay container inside the element in the application-wide container'; dropdown-trigger.directive.ts:691-693
- **Size options** (modified): The spec says that without maxWidth the panel is never wider than its container. That cap is only the CDK stylesheet's max-width: 100% on .cdk-overlay-pane. A minWidth larger than the container is written inline and wins over max-width under CSS rules, so the panel becomes wider than its container. Evidence: @angular/cdk \_overlay-module-chunk.mjs .cdk-overlay-pane { max-width: 100% } and OverlayRef.\_updateElementSize(); actions-panel-config.ts:74-86
- **Text direction** (modified): The spec says direction defaults to 'ltr' whatever the application's direction. That default is a field of KbqActionsPanelConfig, so it holds only with the built-in default config. A default config provided without direction (e.g. kbqActionsPanelDefaultConfigProvider({ disableClose: true })) leaves direction undefined. createOverlayRef then uses Directionality.value (rtl in an RTL document), and the RTL class is not added. Evidence: packages/components/actions-panel/actions-panel-config.ts:16-19,93; actions-panel.ts:133-136; actions-panel-container.ts:90; cdk \_overlay-module-chunk.mjs createOverlayRef line 2083

## alert

Correction change: `correct-alert-baseline`

- **Status icon slot** (modified): The spec says kbq-alert\_\_icon is rendered only while an icon is projected into the slot, 'so an alert without one has no empty icon box'. The wrapper actually follows contentChild(KbqIcon/KbqIconItem, {descendants:false}). That query looks through a top-level \<ng-container> and through every root node of a control flow block. The slot, though, takes only top-level nodes by attribute, and takes a control flow block only when its content is a single element. So an icon inside an ng-container, or inside an @if that also holds text, ends up in the text, still tinted, and an empty icon box is rendered. Evidence: packages/components/alert/alert.component.ts:105-107,144; alert.component.html:1-5; node\_modules/@angular/core/fesm2022/\_debug\_node-chunk.mjs:9308-9325 (embeddedTView/isApplyingToNode) and :15664 (ɵɵprojectionDef only matches componentNode.child siblings); node\_modules/@angular/compiler/fesm2022/compiler.mjs:23365 (ingestControlFlowInsertionPoint returns null for several root nodes)
- **Explicit icon color wins** (modified): The spec says an icon that has an explicit color when it is projected keeps that color whatever the status. The effect re-tints any icon whose color() equals lastAutoColor, and lastAutoColor is never reset. So if an earlier icon was auto-tinted (for example to error) and is replaced by an icon with \[color\]=error, the next alertColor change overwrites the explicit color. Evidence: packages/components/alert/alert.component.ts:147,155-163 (lastAutoColor only ever assigned, never cleared)
- **Re-tint on status change** (modified): The spec says any status icon the alert tinted is re-tinted when alertColor changes. Only projectedIcon() (the kbq-icon, else the icon item) is re-tinted, and only while its color still equals lastAutoColor. Take an icon item that was tinted while it was alone: once a kbq-icon is projected next to it, the item keeps the old status color. A tinted icon whose color the consumer later changed to another color is not re-tinted either. Evidence: packages/components/alert/alert.component.ts:144,155-163
- **Close control slot** (modified): The spec says the kbq-alert\_\_close-button wrapper is rendered only while a close control is projected into the slot. The wrapper follows contentChild(KbqAlertCloseButton, {descendants:false}), which also finds a close control inside a top-level ng-container or inside a control flow block with several root nodes. Such a control is projected into the text instead: the wrapper is rendered empty, and a click on the control never reaches the wrapper's (click) listener, so closed does not emit. Evidence: packages/components/alert/alert.component.ts:118; alert.component.html:21-25; Angular query/projection code cited for Status icon slot
- **Dismissible host class** (modified): The spec says the host has kbq-alert\_dismissible only while a close control is projected and must not have it otherwise. The class follows the same closeButton() query, so it is also set when the only close control sits in a top-level ng-container or in a control flow block with several root nodes. That control is rendered in the text and cannot emit closed. Evidence: packages/components/alert/alert.component.ts:97,118
- **Title layout modifiers** (modified): The spec says kbq-alert\_\_content\_title and kbq-alert\_\_icon\_title are present only while a title is projected. They follow title(), a directive query that also finds a title inside a top-level ng-container or inside a control flow block with several root nodes. That title is rendered inside kbq-alert\_\_text, not above it, and the modifiers are still applied. Evidence: packages/components/alert/alert.component.ts:114; alert.component.html:2,7-8
- **Action controls** (modified): The spec says kbq-alert\_\_button-stack is rendered only while a control is projected into it. The stack follows control(), a directive query that also finds controls inside a top-level ng-container or inside a control flow block with several root nodes. Those controls are projected into the text, so the stack is rendered empty. Evidence: packages/components/alert/alert.component.ts:116; alert.component.html:14-18

## app-switcher

Correction change: `correct-app-switcher-baseline`

- **Placement** (modified): The spec says kbqPlacementChange emits whenever the overlay applies a position. The trigger re-emits only what the CDK positionChanges reports, and the CDK emits only for a new position or a changed scroll visibility. Because the position is locked, re-applying it (for example on a reposition when the popup's own list scrolls, or on resize with the same placement) emits nothing. Evidence: packages/components/core/pop-up/pop-up-trigger.ts:560 (withLockedPosition), :617-650 (onPositionChange); @angular/cdk \_overlay-module-chunk.mjs:1150 (locked -> reapplyLastPosition), :1459-1461 (emit only if position !== \_lastPosition or visibility changed), :203 (reposition strategy re-applies on every ScrollDispatcher scroll)
- **Outer scroll closes the switcher** (modified): The spec says scrolling the page or any scrollable container outside the popup closes it. closingActions only listens to ScrollDispatcher.scrolled(), which hears the document's non-capture scroll listener and registered CdkScrollables (cdkScrollable, kbq-scrollbar viewport). A plain overflow:auto container's scroll event does not bubble, so it never closes the switcher. Evidence: packages/components/app-switcher/app-switcher.ts:953-971; @angular/cdk scrolling.mjs:225 (renderer.listen('document','scroll') without capture); packages/components/scrollbar/scrollbar.ts:299
- **Inline icon sanitization** (modified): The spec says HTML elements are removed. The sanitizer matches elements by local name only, in any namespace, so an HTML element whose name is on the SVG allow-list is kept, for example the HTML title element parsed from '\<title>x\</title>' or an unknown element such as a top-level '\<path>'. 'URL attributes' is also narrower than it reads: only href and xlink:href are checked, while fill='url(...)' is kept. Evidence: packages/components/app-switcher/app-switcher-icon-sanitizer.ts:45 ('title' allowed), :156 (URL\_ATTRIBUTES = href, xlink:href), :210 (ALLOWED\_ELEMENTS.has(element.localName.toLowerCase()))
- **Grouping by type** (modified): The spec groups by 'type' and says a type with three or fewer applications renders as plain rows. defaultGroupBy keys and names groups by type.toString(), so two apps of type 1 and two of type '1' form a single group of four instead of two sets of plain rows. Evidence: packages/components/app-switcher/app-switcher.ts:126-142 (defaultGroupBy, appType = app.type.toString())
- **Row order** (modified): The spec says group rows come in the order in which their type first appears. makeGroupsForApps collects groups in a plain object and iterates Object.values(), which puts integer-like keys first in ascending numeric order. Four apps of type 2 followed by four of type 1 therefore render the '1' group first. The small-type rows at the end follow the same key order. Evidence: packages/components/app-switcher/app-switcher.ts:159 (const groups = {}), :165 (Object.values(groups).forEach)
- **Flyout follows the row that opened it** (modified): The spec says the flyout switches to another site or group row after NESTED\_HOVER\_SWITCH\_DELAY (50 ms). activateSafeArea switches at the first mousemove that lands outside the safe triangle between the leave point and the near edge of the flyout. The 50 ms timer applies only while the pointer stays inside that triangle, so the 'Crossing a row' guarantee also holds only inside it. Evidence: packages/components/dropdown/dropdown.component.ts:474-531 (mousemove listener -> immediate onExit + switchTarget; timer(NESTED\_HOVER\_SWITCH\_DELAY) only via hovered()); packages/components/core/overlay/safe-area.ts:57-64; packages/components/dropdown/dropdown-trigger.directive.ts:522-536, 878-908

## autocomplete

Correction change: `correct-autocomplete-baseline`

- **Scroll strategy** (modified): The spec says the default strategy repositions the panel when anything outside it scrolls. KbqRepositionScrollStrategy only listens to the CDK ScrollDispatcher, which hears document scrolls and registered CDK scrollables such as cdkScrollable or kbqScrollbarViewport. A plain overflow container that scrolls does not reposition the panel. Evidence: packages/components/core/overlay/reposition-scroll-strategy.ts:54-57; autocomplete-trigger.directive.ts:86-97; CDK ScrollDispatcher listens to 'scroll' on document only
- **Selected state of options** (modified): The spec says choosing another option leaves the other options untouched. With autoActiveFirstOption on (the default), Enter on a non-first option closes the panel first and then calls resetActiveItem(). That makes the first option active, and the key-manager change handler calls selectViaInteraction() on it because the panel is closed. The first option ends up kbq-selected too, and the scenario fails when the choices are made with Enter. The corrected scenario uses clicks. Evidence: packages/components/autocomplete/autocomplete-trigger.directive.ts:396-410, 558-561, 1006-1014
- **Values written by the form** (modified): The spec says null and undefined always show an empty field. setTriggerValue passes every written value, null included, to displayWith and shows its result. The field is empty only when there is no displayWith or it returns null or undefined; a displayWith that maps null to text shows that text, and one that reads value.name throws. Evidence: packages/components/autocomplete/autocomplete-trigger.directive.ts:747-756
- **Active option stays in view** (modified): The spec says keyboard navigation always scrolls the active option into view. The subscription to keyManager.change that scrolls and refocuses is made once in ngAfterViewInit, and only for the panel bound at that moment. A panel bound later, or bound in its place, is never scrolled by the arrow keys. Evidence: packages/components/autocomplete/autocomplete-trigger.directive.ts:392-411
- **Panel anchored to the caret** (modified): The spec says the field's box is used when the caret cannot be measured. kbqGetCaretRect does return the field's own box for RTL or centred text. For a field without a text selection, such as an email input, it returns null, and measureCaretOrigin then uses getConnectedElement(): the custom origin, otherwise the kbq-form-field container, otherwise the field. Evidence: packages/components/autocomplete/autocomplete-trigger.directive.ts:947-955; packages/components/core/form-field/caret-rect.ts:88
- **Text mode query is the word before the caret** (modified): The spec says there is never a query after whitespace. That holds only with the default minimum length. With kbqAutocompleteMinLength set to 0, kbqGetTextQuery returns an empty query after whitespace, which opens the panel. Evidence: packages/components/core/form-field/text-query.ts:45-49
- **Trigger characters start a query** (modified): The spec says the query runs from the closest trigger that counts. findTriggeredQuery only looks at the last occurrence of each trigger (lastIndexOf) and does not fall back to an earlier one. With trigger '/', typing '/docs/api' gives no query, although the first '/' starts the line with no whitespace before the caret. With several triggers, a non-counting occurrence of one trigger does not block an earlier counting occurrence of another. Evidence: packages/components/core/form-field/text-query.ts:75-96 (lastIndexOf at :83, token check at :88-90)

## badge

Correction change: `correct-badge-baseline`

- **Color given as a plain string** (modified): The spec says any other non-empty string is rendered as the `kbq-badge\_\<value>` class. The host `\[class\]` binding goes through Angular's class string parser, which splits at whitespace, so `success foo` adds `kbq-badge\_success` and `foo`. The delta limits the rule to strings without whitespace, states the split and adds a scenario for it. Evidence: packages/components/badge/badge.component.ts:115,136; node\_modules/@angular/core/fesm2022/\_debug\_node-chunk.mjs classStringParser/parseClassName (~15913, 16040)
- **Supported color and fill combinations** (modified): The spec says the prebuilt theme styles the color and fill combinations. The badge color rules come from the component's own stylesheet, which includes `kbq-badge-theme()`. `koobiq-theme()` and prebuilt/theme.scss contain no badge rules, and the colors come from the @koobiq/design-tokens CSS. The delta names the badge stylesheet in the description and in both scenarios. Evidence: packages/components/badge/badge.component.scss:62; packages/components/badge/\_badge-theme.scss:24-95; packages/components/core/styles/\_koobiq-theme.scss:14-26; packages/components/core/styles/theming/prebuilt/theme.scss
- **Leading icon is marked** (modified): The spec gives an invariant: an icon that is the first of more than one child node gets kbq-icon\_left. The styler effect reads only the `icons()` content query, so the classes are computed only on the first render and when the set of icons changes. An icon-only badge that gets text later through @if never gets the class. Whitespace-only text nodes also count, because only comments are filtered out. The delta scopes the rule to the moments the classes are computed and states that whitespace-only text nodes count. Evidence: packages/components/badge/badge.component.ts:65-100; packages/components/core/utils/utils.ts:31-33; @angular/core LQueries\_.dirtyQueriesWithMatches and refreshSignalQuery (cached \_flatValue)
- **Trailing icon is marked** (modified): The same invariant wording as the leading icon. The classes are computed only on the first render and when the icon set changes, so text added later does not mark or unmark the trailing icon, and whitespace-only text nodes count. The delta scopes the rule the same way. Evidence: packages/components/badge/badge.component.ts:65-100; packages/components/core/utils/utils.ts:31-33
- **Icons that are alone, in the middle or nested are not marked** (modified): The spec says an icon that is the only child node, or neither first nor last, gets no spacing class. The icon classes are cleared only inside the `length > 1` branch. So when a removal leaves one icon alone, that icon keeps its earlier kbq-icon\_left or kbq-icon\_right. Text added later can also move a marked icon into the middle without a recomputation. The delta states that classes hold between computations and that a lone icon keeps an earlier class. The host-class part was already correct. Evidence: packages/components/badge/badge.component.ts:74-99 (removeClass of icon classes only at 84-85 inside the branch at 80)
- **Icon classes follow icons added or removed later** (modified): The spec says the badge recomputes the classes of the host and of every icon it still contains. When one child node or fewer is left, only the host classes are removed and the remaining icon keeps its classes. Content without a direct icon (text, a caption) added or removed later never triggers a recomputation: the query is dirtied only by views that hold a match, and an unchanged result returns the cached array. The delta states both limits and adds the scenarios 'Text added after the first render' and 'One icon left after a removal'. Evidence: packages/components/badge/badge.component.ts:70,78,80-98; @angular/core \_debug\_node-chunk.mjs:9204-9219 (dirtyQueriesWithMatches), 9555-9573 (refreshSignalQuery)

## breadcrumbs

Correction change: `correct-breadcrumbs-baseline`

- **Routing through the item** (modified): The spec says the item's routerLink together with its queryParams, fragment and the other RouterLink inputs becomes the entry's destination. The entry and the dropdown row receive only `item.routerLink?.urlTree`. That tree is built from the commands, queryParams, fragment, queryParamsHandling, preserveFragment and relativeTo, so the item's target, state, info, replaceUrl and skipLocationChange are dropped. Evidence: packages/components/breadcrumbs/breadcrumbs.html:51,97; node\_modules/@angular/router/fesm2022/\_router\_module-chunk.mjs:254-308 (createUrlTree, urlTree, onClick extras)
- **Single tab stop** (modified): The spec says the host has tabindex -1 when every entry is disabled or not focusable. The expand button is bound `\[focusable\]="!disabled()"` and stays registered even while hidden, so an enabled auto trail of two or more items keeps the host at tabindex 0 even when no entry can take focus. kbq-button and the roving item each bind `\[attr.tabindex\]`, and Angular writes a binding only when its own value changes. So an entry re-enabled after the first render gets tabindex 0 from kbq-button (the expand button loses its tabindex), and the roving -1 is never rewritten. The rule 'entries are -1 except the last focused' also covers only kbqBreadcrumb elements. Evidence: breadcrumbs.html:38; roving-focus-group.directive.ts:87-89,100-124; roving-focus-item.directive.ts:23,84-86; button.component.ts:319,432-436; @angular/core ɵɵattribute (bindingUpdated)
- **Arrow keys move between entries** (modified): The spec says the arrows skip disabled entries and move to the next entry that can take focus. The candidates are the registered kbqBreadcrumb elements filtered only by `focusable`, so plain focusable elements of a custom template are skipped. A custom `\<a kbq-button kbqBreadcrumb disabled>` that stays focusable is reached, and once focus is on it, the capture-phase keydown halt of the disabled kbq-button stops Left and Right from moving focus. ## top-bar

Correction change: `correct-top-bar-baseline`

- **Sticky positioning needs an inset** (modified): The spec says setting --kbq-top-bar-inset-block-start makes the bar stick to its nearest scrolling ancestor, with no conditions. ## tree

Correction change: `correct-tree-baseline`

- **Node template context** (modified): The spec says `index` is the row's position in the rendered list. In the code, `index` (and `level`) are set once when the row is created and never updated. A row keeps its old `index` after rows are inserted above it, and `trackBy` reuse keeps the old `level`. Evidence: packages/components/tree/tree-base.ts:408, :414-420, :353-366
- **Flattening nested data** (modified): The spec says the flattener builds a depth-first list, reading children from the first emission of an Observable. If the Observable emits after `flattenNodes()` has returned, the children are pushed onto the end of the list that was already returned, so they are out of depth-first order. Evidence: packages/components/tree/data-source/flat-data-source.ts:59-79 (subscribe at :71)
- **Expansion through the tree control** (modified): The spec says a rendered tree follows `expand`/`collapse` without further action. The tree only re-renders when its data stream emits, and only a source that re-emits on expansion (`KbqTreeFlatDataSource`) does that. An array, an Observable that ignores expansion, or `KbqTreeNestedDataSource` leave the rows unchanged. Evidence: packages/components/tree/data-source/flat-data-source.ts:178-199; tree-base.ts:559-560
- **Indentation of nodes** (modified): The spec says a row with no toggle gets 24 more. The padding directive only detects a toggle through a `kbq-tree-option`'s content queries. A `kbq-tree-node` row always gets the extra 24, even when it has a toggle. So does an option that carries `kbqTreeNodeToggle` on its own element. Evidence: packages/components/tree/padding.directive.ts:21, :86, :48-56; tree-option.component.ts:337-339
- **Toggle state** (modified): The spec says a disabled toggle ignores clicks. In the code, `toggle()` returns before `stopPropagation()`, so the click bubbles to the option's click listener and selects the row. For example, clicking a chevron during a search selects that row. Evidence: packages/components/tree/toggle.ts:50-61; tree-option.component.ts:138
- **Text filter** (modified): The spec says `filterNodes(query)` publishes the query on `filterValue`, and a query that matches nothing leaves the tree empty. Both are true only for a non-empty query. An empty query publishes the kept nodes (`value || result`), and if nothing is kept it ends the filter instead of emptying the tree. Evidence: packages/components/tree/control/flat-tree-control.ts:140; data-source/flat-data-source.ts:189
- **Expansion while filtering** (modified): The spec says filtering with an empty query ends the filter. It ends only when the filter stages keep no node for that query. With `FilterByValues` holding values, which is the spec's own pipeline scenario, or with a node whose view value contains "null", the kept nodes are published and the filter stays active. Evidence: packages/components/tree/control/flat-tree-control.ts:123-143; tree-selection.component.spec.ts 'should filter selected nodes by 1 level by click'
- **Default view value matching** (modified): The spec says a node matches when its view value contains the query. For an empty query that should match every node. Instead the empty query becomes `null`, and `escapeRegExp(null)` returns `null`, so the test is the regex /null/gi. Only view values containing "null" match, and a custom `compareViewValues` receives `null`. Evidence: packages/components/tree/control/flat-tree-control.filters.ts:21; flat-tree-control.ts:10; core/highlight/highlight-base.ts:8-14
- **Ctrl or Cmd click** (modified): The spec says a Ctrl/Cmd click toggles the node and keeps the rest of the selection, without naming a mode. In single selection the toggle goes through a single-selection `SelectionModel`, so Ctrl-clicking another node replaces the selected one. Evidence: packages/components/tree/tree-selection.component.ts:1114-1120
- **Shift range** (modified): The spec anchors the range on the previously active option. The code anchors on `keyManager.previousActiveItemIndex`. That index is set only by `setActiveItem()`, never by the focus-driven `updateActiveItem()`, and is reset when focus leaves the tree. After Down moves from row 1 to row 2, a Shift-click on row 4 spans rows 1-4 with row 1's state. Also, when the active option did not move but the anchor is a different option, the code applies a range instead of a toggle. Evidence: packages/components/tree/tree-selection.component.ts:1132-1162, :1607, :1618; core/a11y/key-manager/list-key-manager.ts:219, :380
- **Non-selectable options** (modified): The spec says no attempt on a non-selectable option emits `selectionChange`. A Shift+arrow range that lands on a non-selectable option always calls `emitChangeEvent(option)`, even when nothing changed. The existing test checks only the value, not the event. Evidence: packages/components/tree/tree-selection.component.ts:1085-1089
- **Tri-state checkbox** (modified): The spec says an expandable option with `checkboxThirdState` shows checked or indeterminate from its descendants. The code rolls up only while `isExpandable` is true, and that is false while the option's toggle is disabled, which is the case for every toggle during a filter. During a search such a branch shows only its own selection. Evidence: packages/components/tree/tree-option.component.ts:320-326, :463; toggle.ts:35-40
- **Disabled tree** (modified): The spec says a disabled tree ignores clicks. A toggle's disabled state reads only its own input and the filter, not the tree, so clicking a toggle in a disabled tree still expands or collapses the row. Only selecting clicks and select all are ignored. Evidence: packages/components/tree/toggle.ts:40, :50-61; tree-selection.component.ts:1257
- **Expansion is restored** (modified): The spec says a payload that is not an array of strings restores nothing. `normalizeTreeState` keeps the string entries of any array, so \['Pictures', 1\] restores Pictures. Only a non-array, or an array that has entries but no string, restores nothing. Evidence: packages/components/tree/tree-base.ts:49-57
- **Focus entering the tree** (modified): The spec says focus goes to the first selected node's option, else the previously active option, else the first enabled option. With nothing selected the code always goes to the first enabled option. When the option it finds is disabled, `option.focus()` returns without focusing anything, so focus stays on the tree element. Evidence: packages/components/tree/tree-selection.component.ts:925-957; tree-option.component.ts:511
- **Vertical keyboard navigation** (modified): The spec says PageUp/PageDown move by a page and stop at the ends. When the page lands on a disabled option, the key manager keeps stepping by whole pages, and does not move at all once that runs past the end. Evidence: packages/components/core/a11y/key-manager/list-key-manager.ts:348-366, :443-461
- **Row semantics** (modified): The spec says rows with a checkbox carry `aria-checked`. The ARIA attribute actually follows the option's `showCheckbox`, not the checkbox the row shows. A single-selection row that projects its own `kbq-pseudo-checkbox`, as the tree-selection-separate-from-focus docs example does, carries `aria-selected`. Evidence: packages/components/tree/tree-option.component.ts:410, :271-273; tree-option.html:3-7

## tree-select

Correction change: `correct-tree-select-baseline`

- **Focus moves into the open panel** (modified): The spec says DOM focus always moves onto the active option once the panel renders. A disabled option refuses focus, and opening the panel can make a disabled option active (see Active option on open). In that case focus does not move onto it. Evidence: packages/components/tree/tree-option.component.ts:509-511 (focus returns early when disabled); packages/components/tree-select/tree-select.component.ts:1944-1964 (highlightCorrectOption)
- **Active option on open** (modified): The spec says the first selected node 'that is not disabled' becomes active. firstSelected only skips nodes the tree control's isDisabled reports. A node disabled through its option's disabled input or through a disabled tree is still found, and setActiveItem activates it without checking disabled. Evidence: packages/components/tree-select/tree-select.component.ts:1419-1421 (firstSelected), 1951-1956 (setActiveItem(selectedOption))
- **Selection mode and value type** (modified): The spec says changing the multiplicity of the projected tree's multiple input throws the same error as the tree-select: "Cannot change `multiple` mode of select after initialization.". The tree actually throws its own error instead, getKbqTreeSelectionOwnedMultipleError, whose text is "Cannot change the multiplicity of `multiple` on a `kbq-tree-selection` rendered inside a `kbq-tree-select`...". Evidence: packages/components/tree/tree-selection.component.ts:717-725; packages/components/tree/tree-errors.ts:38-43; tree spec test 'should throw when the multiplicity is changed on a model owned by a tree-select'
- **Disabled and non-selectable options** (modified): The spec says a disabled option MUST NOT be selected by keyboard. In multiple mode, Enter and Space call toggleFocusedOption, which checks selectable but never disabled. So a disabled option that the panel made active on open (for example the only selected node, disabled through its option input) is deselected and reselected by Space or Enter. Evidence: packages/components/tree/tree-selection.component.ts:1165-1182 (toggleFocusedOption); packages/components/tree-select/tree-select.component.ts:1671-1676
- **Values are matched by the tree control** (modified): The spec says a written value selects 'the data nodes' whose getValue matches. FlatTreeControl.hasValue uses find, so each value selects only the first matching node in data order. Other nodes with an equal value, such as the two 'Pictures' or two 'src' nodes in the test data, stay unselected. Evidence: packages/components/tree/control/flat-tree-control.ts:119-121; packages/components/tree/tree-selection.component.ts:1382-1392 (setOptionsFromValues)
- **Select-all scope and state** (modified): The spec says disabled and non-selectable nodes are left out. selectAllTargets leaves out only rendered options that are disabled or not selectable, plus nodes the tree control's isDisabled reports. A node in a collapsed branch is still covered, and selected by the row, even when its option binds disabled or selectable=false or the tree is disabled. Evidence: packages/components/tree/tree-selection.component.ts:493-516 (selectAllTargets); tree-option.component.ts:248-251 (JSDoc of selectable: unrendered options are not checked)
- **Select-all action** (modified): The spec says each activation emits selectionChange 'when something changed'. selectAllOptions emits only when a selectable rendered option changed. When only nodes inside collapsed branches change, the value changes and is reported to the form, but no selectionChange fires; only onSelectAll does. The spec's 'Disabled nodes MUST NOT change' also fails for collapsed nodes disabled only through their option's input. Evidence: packages/components/tree/tree-selection.component.ts:1261-1276
- **Keys in the search field** (modified): The spec says Enter in the search field acts on the tree while focus returns to the field. In single-selection mode with autoSelect on (the default), the Enter branch closes the panel and focuses the tree-select. It also says 'a selection returns focus to the field', but only the tree's selectionChange refocuses the field. A single-mode click closes the panel, and the cleaner, tag removal and a select-all that changes only collapsed nodes do not refocus it. Evidence: packages/components/tree-select/tree-select.component.ts:1671-1679 (Enter branch), 1117-1127 (refocus on tree.selectionChange), 1110-1114 (single-mode click closes)

Unverifiable:

- Vertical navigation in the open panel: whether PageUp/PageDown move by 'one visible page'. The page size is floor(tree element height / first option height) (tree-selection.component.ts:1068-1082). The tree element is `height: 100%` inside `.kbq-tree-select\_\_content`, which has only `max-height` (tree-select.scss:20-21, core/styles/common/\_select.scss:227-236).
