# Koobiq `top-bar` Component — Code Review & Improvement Plan

> Scope: `packages/components/top-bar` (`KbqTopBar` + the `KbqTopBarContainer` / `KbqTopBarSpacer` structural directives, tokens, SCSS, Jest spec, e2e fixture + Playwright spec, user guides, API guard report) · Commit `b665e503` · 2026-08-28
> Generated by a multi-dimension review (architecture, correctness, layering/styles, accessibility, public API & types, tests, docs) with manual verification of every finding against the source, the seven in-repo consumers, the `dropdown-demote-overlay` migration schematic and the design-token files. 12 findings confirmed (P0×0, P1×1, P2×6, P3×5); 5 candidate findings refuted during verification (see Appendix A). This document is a review + roadmap; no source is modified by it.

---

## 1. Executive Summary

`top-bar` is a 57-line, three-export package: a `kbq-top-bar` flex row whose template is a bare `<ng-content />`, plus two class-only directives (`[kbqTopBarContainer]` with a required `start | end` placement, `[kbqTopBarSpacer]`). It has no runtime logic at all — no subscriptions, no lifecycle hooks, no DOM reads — so essentially everything it does, it does through 77 lines of SCSS and 11 CSS custom properties. That is where all the defects are.

- **The single serious defect is a layering one.** `top-bar.scss:24` pins the host to `overlay.$overlay-z-index` — literally the same SCSS variable the CDK overlay layer uses for `.cdk-overlay-pane` and `.cdk-global-overlay-wrapper` (`_overlay.scss:53, 63`), and numerically equal to the `.cdk-overlay-container`'s own `z-index: 1000` (`_overlay.scss:4-5, 32`). After a grep across `packages/`, `top-bar.scss:24` is the **only** line outside the overlay stylesheet that still references that variable: `navbar` had the identical defect and it was fixed in `26cf45df` by introducing a documented layer scale (`--kbq-navbar-z-index: 990`, `navbar-tokens.scss:10-16`). Worse, the library's own `ng update` migration for DS-5288 prints "lower your sticky chrome below the overlay container z-index" (`dropdown-demote-overlay/data.ts:89-90`, `README.md:25-28`) while naming `kbq-top-bar` as the sticky chrome in question — advice a consumer cannot follow through a token, because top-bar ships no z-index token. The docs site already carries the workaround (`_docsearch.scss:4-5`, `z-index: 1001`, with the comment "higher than kbq-top-bar") (TB-CSS-01).
- **The component pays for stickiness it never delivers.** `--kbq-top-bar-position` defaults to `sticky` (`top-bar-tokens.scss:2`, consumed at `top-bar.scss:32`), but no `top`/`bottom`/`inset` is declared anywhere in the package, and a grep over `packages/` + `apps/` finds no consumer that supplies one either. A sticky box with all four insets `auto` has no sticky constraint and behaves exactly like `position: relative` — so the default never sticks, while still creating a positioned box that (together with the z-index above) opens a stacking context at the overlay layer for nothing (TB-CSS-02).
- **The layout defaults are not the ones any caller uses.** `--kbq-top-bar-container-start-basis` ships as `0` and feeds `flex: 1 0 var(...)` (`top-bar.scss:59`), giving the left/title container no floor when the bar overflows. **Five of the seven docs examples override that token** (55px / 115px / 115px / 160px / 180px) and two of them add a `min-width` on top. Meanwhile the guide's only token documentation is for `--kbq-top-bar-spacer-min-width` — the one token nobody overrides — and never mentions the one everybody does (TB-CSS-03).
- **The published API documentation is untrue.** `withShadow`'s JSDoc says it applies `kbq-top-bar-overflow` (`top-bar.ts:54`); the class the host actually toggles is `kbq-top-bar_with-shadow` (`top-bar.ts:49`), and `kbq-top-bar-overflow` exists nowhere in the repository. `KbqTopBarContainer`'s JSDoc documents "a placement value (left or right)" for an input whose type is `'start' | 'end'` (`top-bar.ts:19, 33`). Both strings are what the docs site renders on the API tab (`structure.ts:1121-1122`, `hasApi: true`), and neither guide documents any API at all (TB-DOC-01).
- **Test coverage is one binding.** All three Jest cases assert the same `kbq-top-bar_with-shadow` class (`top-bar.spec.ts:21-38`); `KbqTopBarContainer` — the export with a required input and two mutually exclusive class bindings — and `KbqTopBarSpacer` have zero unit coverage, and the Playwright suite is a single static screenshot pair with none of the adaptive behaviour the guide advertises (TB-TEST-01, TB-TEST-02).

Genuine strengths worth preserving: this is one of the most modern packages in the library — standalone, `OnPush`, host-object bindings only, `input()` / `input.required()` / `booleanAttribute` throughout, no `@HostBinding`, no `@Input` accessors, no legacy migration TODOs. It is SSR-clean by construction (nothing in it touches a browser global) and cannot leak, because it holds no state and subscribes to nothing. Styling is fully token-driven — all 11 custom properties resolve, including `--kbq-background-bg` and `--kbq-shadow-overflow-normal-bottom` in both light and dark. The bare-attribute form `<kbq-top-bar withShadow>` type-checks under `strictTemplates` because the input is correctly typed `input<boolean, unknown>` — the exact hazard the divider review had to file as a defect. And the overflow-items integration, whatever its coupling cost, gives the component a real responsive story that seven docs examples exercise.

## 3. Prioritized Findings (deduplicated, verified)

### P0 — Release blockers

None.

### P1 — High

**TB-CSS-01 · The host is pinned to the CDK overlay layer, contradicting the library's own `ng update` guidance** — `top-bar.scss:2, 24`; `core/styles/common/_overlay.scss:4-5, 32, 53, 63`; `packages/schematics/src/migrations/dropdown-demote-overlay/data.ts:85-91` and `README.md:19-28`; `apps/docs/src/styles/_docsearch.scss:3-6`; contrast `navbar-tokens.scss:10-16` + `navbar.scss:6`.
`.kbq-top-bar` declares `z-index: overlay.$overlay-z-index`, i.e. `1000` (`_overlay.scss:5`) — the same value `.cdk-overlay-container` uses (`_overlay.scss:4, 32`) and the same variable `.cdk-overlay-pane` and `.cdk-global-overlay-wrapper` use (`:53, 63`). Two positioned boxes at equal `z-index` in the same stacking context are ordered by DOM position alone; the overlay container happens to be appended to `<body>` after app content, so today dropdown/select/popover panels do paint above the bar — but only by accident of insertion order, not by design. Three independent pieces of in-tree evidence say this is a real problem and not a style opinion. **(1)** `top-bar.scss:24` is the *only* reference to `$overlay-z-index` anywhere outside the overlay stylesheet itself (verified by grep across `packages/`) — every other component has moved off it. **(2)** `navbar` had the identical line and it was fixed in `26cf45df` ("errors following a full review of the component", DS-5403) by introducing a documented layer scale with an explicit rationale comment: "The navbar is page chrome: it sits above the page content but below every CDK overlay (1000)" (`navbar-tokens.scss:11-16`). Top-bar is page chrome by exactly the same argument and was left behind. **(3)** The `dropdown-demote-overlay` migration — shipped in `packages/schematics` and printed during `ng update` — tells consumers verbatim: "If your app relied on the old behaviour, lower your sticky chrome below the overlay container z-index (the library ships `$overlay-container-z-index: 1000`)" while naming `kbq-navbar` / `kbq-top-bar` as that chrome (`data.ts:87-90`). A consumer who follows that advice finds no `--kbq-top-bar-z-index` to lower: the package ships 11 tokens (`top-bar-tokens.scss:1-13`) and none of them is a layer token. The library's own documentation site is already living the consequence — `_docsearch.scss:4-5` raises the DocSearch modal to `1001` with the comment "higher than kbq-top-bar". Note also that the z-index is unconditional, so every consumer pays for a stacking context at the overlay layer even in the common case where the bar is not sticky at all (TB-CSS-02).
**Fix:** mirror the navbar fix exactly. Add `--kbq-top-bar-z-index: 990;` to `top-bar-tokens.scss` under a `/* LAYER TOKENS */` heading with the same one-sentence rationale the navbar tokens carry, change `top-bar.scss:24` to `z-index: var(--kbq-top-bar-z-index);`, and drop the now-unused `@use '../core/styles/common/overlay';` at `top-bar.scss:2` (the navbar fix removed the identical import at `navbar.scss:2`). `990` is the right value: the only thing the z-index needs to win against is the page content the `with-shadow` box-shadow spills over. Then delete the workaround at `_docsearch.scss:3-6` — its removal is the acceptance criterion, not just the diff. Guard with a Jest case asserting the computed `z-index` of a default `<kbq-top-bar>` is below `1000`, and re-run the `dropdown` suite (`dropdown.spec.ts` already contains the DS-5288 layering assertions).

### P2 — Should fix

**TB-CSS-02 · `position: sticky` ships as the default but has no inset, so it never sticks** — `top-bar-tokens.scss:2`, `top-bar.scss:32`; contrast `top-bar-overflow-example.ts:145-164`.
`--kbq-top-bar-position` defaults to `sticky` and is consumed as `position: var(--kbq-top-bar-position)`. Per CSS Positioned Layout, a sticky box's shift is computed from its inset properties, and an `auto` inset imposes no constraint on that side; with all four insets `auto` the box is never offset and lays out exactly as `position: relative`. The package declares no `top`, `bottom`, `inset` or `inset-block-start` anywhere (`top-bar.scss` has none), and neither does any consumer — a grep for `--kbq-top-bar-position` across `packages/` and `apps/` returns exactly two hits, both inside this package, so no caller overrides the token either, and a grep for `top:`/`inset` under a `.kbq-top-bar` selector returns nothing repo-wide. The default is therefore inert in every shipped usage. What it is not free of is cost: `sticky` makes the host a positioned box, which is what lets the `z-index: 1000` of TB-CSS-01 open a stacking context. The one place the docs promise scroll behaviour — "The toolbar can remain fixed while scrolling the page" (`top-bar.en.md:56-60`, `top-bar.ru.md:57-61`) — is demonstrated by `top-bar-overflow-example.ts`, which achieves it purely with flex layout (`:host { display: flex; flex-direction: column; height: 400px }` at `:146-149` and a separately scrolling sibling at `:159-164`), never touching `position` at all. So the feature the token names is neither implemented nor needed by the example that advertises it.
**Fix:** decide, do not leave it half-built. Either (a) complete it — add `--kbq-top-bar-inset-block-start: 0;` to the tokens and `inset-block-start: var(--kbq-top-bar-inset-block-start);` next to `top-bar.scss:32`, then add a docs example that actually scrolls a page under a stuck bar; or (b) drop it — change the token default to `relative` (or delete the `position` declaration and the token), which also removes the stacking context and makes TB-CSS-01 moot for non-sticky users. (b) is the smaller change and matches how every in-repo consumer already uses the component. Whichever is chosen, add a line to both guides stating what `--kbq-top-bar-position` does and what else the caller must set for it to have an effect, and cover the sticking case in `e2e.ts` with a scrolled fixture if (a) is taken.

**TB-CSS-03 · The start container ships a `0` flex-basis that five of seven docs examples override, and the guide documents the wrong token** — `top-bar-tokens.scss:8-9`, `top-bar.scss:56-62`; consumers `top-bar-actions-example.ts:102-103`, `top-bar-overview-example.ts:99-100`, `top-bar-title-counter-example.ts:106-107`, `top-bar-title-counter-adaptive-example.ts:142-143`, `top-bar-breadcrumbs-adaptive-example.ts:163-166`, `top-bar-breadcrumbs-example.ts:100-101`; docs `top-bar.en.md:36-41`, `top-bar.ru.md:37-41`.
`.kbq-top-bar-container__start` is `flex: 1 0 var(--kbq-top-bar-container-start-basis)` with `min-width: 0` (`top-bar.scss:59, 61`), and the token defaults to `0` (`top-bar-tokens.scss:9`). `flex-grow: 1` means the container absorbs all *positive* free space, which is fine; but `flex-shrink: 0` combined with a `0` basis means that once the bar overflows — the exact situation the guide's whole "Responsive mode" section is about — the growth factor no longer applies and the title/breadcrumbs container has no floor to fall back to, while the spacer (`flex: 0 0 80px`, `:44`) and the end container keep their space. Every docs example that puts content on the left works around this: `--kbq-top-bar-container-start-basis` is set to `55px`, `115px`, `115px`, `160px` and `180px` in five separate example files, and `top-bar-breadcrumbs-example.ts:100-101` and `top-bar-breadcrumbs-adaptive-example.ts:163-164` add a hand-written `min-width` (238px / 180px) on top. Five overrides, five different values, zero of them documented: the guides mention exactly one CSS variable, `--kbq-top-bar-spacer-min-width` (`top-bar.en.md:40`, `top-bar.ru.md:41`), which is the one token no example ever changes, and say nothing about the one every example must.
**Fix:** two moves. (1) Give the token a usable default — either a non-zero basis, or replace the pattern with `flex: 1 1 auto; min-width: var(--kbq-top-bar-container-start-min-width, 0)`, which lets the container shrink toward a caller-set floor instead of collapsing past it; verify against all five examples and delete their token overrides as the acceptance test. (2) Add a "CSS variables" subsection to both guides listing the tokens a caller is expected to set — at minimum `--kbq-top-bar-container-start-basis`, `--kbq-top-bar-container-start-gap`, `--kbq-top-bar-container-end-gap`, `--kbq-top-bar-padding-*` and the spacer width — since the API tab documents inputs only and these are the real configuration surface. Guard the layout with the flex-row e2e case from TB-TEST-02.

**TB-ARCH-01 · The package styles another package's internal classes, and its two selectors disagree about depth** — `top-bar.scss:4-21, 47-54, 70-73`; `overflow-items/overflow-items.ts:82, 94`; history `3b216dd8` (DS-4531), `e5edf0bd` (DS-5023).
`top-bar.scss` reaches directly into `@koobiq/components/overflow-items` internals: `.kbq-overflow-item` (`:7`), `.kbq-overflow-items-result` (`:13, 18`) and `.kbq-overflow-item_always-visible` (`:13`), all of which are host classes owned by that other package (`overflow-items.ts:82, 94`). Renaming any of them there breaks top-bar silently — nothing in either package's tests covers the pair. That coupling has already produced two consecutive fixes: `3b216dd8` widened `:has(> .kbq-overflow-items)` to `:has(.kbq-overflow-items)`, and `e5edf0bd` two days later narrowed the *other* selector to `&.kbq-overflow-items, > .kbq-overflow-items` while also deleting a `KbqOverflowItems` DI lookup from `KbqTopBarContainer`. The result today is an asymmetry that is a bug on its own terms: the block at `:48-54` matches an overflow-items host at **any** depth and applies `gap: unset`, `overflow: hidden` and `margin-top/-bottom: calc(-1 * var(--kbq-size-border-width))`, while the block at `:70-73` — which supplies the `padding` and the per-item `margin-right` that replace that removed gap — only matches self-or-direct-child. A container whose `kbqOverflowItems` sits one level deeper therefore loses its gap and gains 2px of negative block margin compensating a padding that was never added: action buttons run together, and the bar is 2px shorter than designed. No in-repo example nests it that way (all seven put `kbqOverflowItems` on a direct child), which is precisely why this has not been noticed.
**Fix:** make both selectors agree — use `> .kbq-overflow-items, &.kbq-overflow-items` in the `:has()` at `:48` too, so the compensation and the trigger always fire together. Longer term, move the integration into `overflow-items` itself: expose the item gap as an `--kbq-overflow-items-gap` token there and have top-bar set that token instead of writing margins onto another component's elements, which removes the cross-package selector dependency entirely. Add a Jest case rendering `kbqTopBarContainer` with a nested `kbqOverflowItems` and asserting the classes/computed gap, and an e2e row for the same nesting.

**TB-A11Y-01 · The bar exposes no landmark or grouping semantics, and neither guide gives any accessibility guidance** — `top-bar.ts:47-50` (host block); consumers `apps/docs/src/app/components/navbar/navbar.template.html:3-76`, `packages/components-dev/ssr/components/breadcrumbs.ts:20-39`, the four `notification-center` examples; docs `top-bar.en.md`, `top-bar.ru.md`.
The host block binds one static class and one conditional class and nothing else — no `role`, no `aria-label`, no `aria-labelledby` hook. `<kbq-top-bar>` is therefore an unknown element with no accessible semantics, and the same is true of `[kbqTopBarContainer]` and `[kbqTopBarSpacer]`. The consequence is visible in the library's own flagship consumer: the documentation site's header — site logo link, section anchor, Telegram/GitHub links, search, theme and language controls — is a bare `<kbq-top-bar>` (`navbar.template.html:3`) with no wrapping `<header>` and no `role="banner"` anywhere in `apps/docs/src` (grep finds `<header>` only in `welcome.component.html:2` and a StackBlitz template), so a screen-reader user gets no banner landmark for the site chrome and no way to jump to or past it. Be precise about what this is and is not: axe-core does not flag a custom element that carries no role, so this is not an automated AXE failure, and missing landmarks are not a discrete WCAG SC failure — it is a WCAG 1.3.1 (Info and Relationships) judgement plus a missing affordance. It is also not obvious that the component should hardcode a landmark: `<kbq-top-bar>` is used both as page chrome (docs site, `components-dev/ssr`) and as a panel header inside a page mock (the four `notification-center` examples), and a page may contain only one `banner`. Only five of the library's guides have an Accessibility section at all (`alert`, `button-toggle`, `flag`, `list`, plus one more); top-bar is not among them, so a consumer has nothing to copy.
**Fix:** do not guess a landmark — give the caller the hook and the instruction. (1) Add an `Accessibility` section to `top-bar.en.md` and `top-bar.ru.md` with concrete markup: use `<kbq-top-bar role="banner">` (or wrap in `<header>`) when the bar is the page header, use `role="toolbar"` **only** if the caller implements roving focus themselves, and add `aria-label` whenever more than one bar exists on a page. (2) Make it possible to say it once: give `KbqTopBar` an optional `ariaLabel` input bound as `'[attr.aria-label]'` and sourced from `kbqInjectA11yLocaleConfiguration()` when unset, per the AGENTS.md rule. (3) Fix the flagship consumer — add `role="banner"` at `navbar.template.html:3` — and add a `jest-axe` assertion to `top-bar.spec.ts` over a populated bar, which is what stops the next regression.

**TB-DOC-01 · The JSDoc that fills the docs-site API tab names a class that does not exist and the wrong input values** — `top-bar.ts:18-20, 30-33, 53-56`; `top-bar.ts:49`; `apps/docs/src/app/structure.ts:1113-1124`; `tools/public_api_guard/components/top-bar.api.md:9-25`.
Three wrong strings, all of them published. **(1)** `withShadow`'s JSDoc reads "Enables overflow behavior, applying `kbq-top-bar-overflow` to show a bottom shadow" (`:54`). The host toggles `kbq-top-bar_with-shadow` (`:49`), and `kbq-top-bar-overflow` appears nowhere in the repository except in that comment — a grep across `packages/` and `apps/` returns exactly one hit, the comment itself. A consumer who reads the API tab and writes a CSS override against `kbq-top-bar-overflow` gets a rule that never matches. The stale wording has outlived its own source: the Jest spec still describes the same input as "the overflow class" in all three case names (`top-bar.spec.ts:21, 26, 32`). **(2)** `KbqTopBarContainer`'s class JSDoc says "based on a placement value (left or right)" (`:19`) for an input typed `'start' | 'end'` (`:33`) — a reader who tries `placement="left"` gets an NG-level type error under `strictTemplates`, having been told to. **(3)** `placement`'s own JSDoc — "Conditionally applies a CSS class based on the value" (`:31`) — says nothing a reader does not already know from the name, and is what makes `KbqTopBarContainer` the one export the API report marks `// @public` rather than `(undocumented)` (`top-bar.api.md:18`). These strings matter because they are the only API documentation that exists: `structure.ts:1121-1122` sets `hasApi: true, apiId: 'top-bar'`, and neither guide contains a single input name, directive selector or code snippet (grep for `withShadow`, `kbqTopBarContainer`, `kbqTopBarSpacer` in both `.md` files returns nothing).
**Fix:** rewrite all three comments — `withShadow`: "Applies the `kbq-top-bar_with-shadow` modifier, which draws the bottom shadow used to signal that page content is scrolled under the bar"; the container class: "Marks a slot inside `kbq-top-bar` and applies `kbq-top-bar-container__start` / `__end` according to `placement`"; `placement`: state the two accepted values and that the input is required. Rename the three spec case names off "overflow" in the same commit. Note the API-report interaction: adding JSDoc to `KbqTopBar`, `KbqTopBarSpacer` and `KbqTopBarModule` removes their `(undocumented)` markers and changes `top-bar.api.md`, so fold this into TB-API-01 and run one `yarn run build:components && yarn run approve-api` cycle rather than two.

**TB-TEST-01 · Three Jest cases all test one class binding; two of the three exports are untested** — `top-bar.spec.ts:1-49`.
The spec has three `it`s (`:21-24`, `:26-30`, `:32-38`) which assert, in order, that `kbq-top-bar_with-shadow` is absent by default, present when `withShadow` is `true`, and absent again after flipping back to `false` — i.e. the same single host binding three times, with the third case adding nothing over the first two. Not covered anywhere: `KbqTopBarContainer`'s two mutually exclusive class bindings (`top-bar.ts:25-26`) and its `input.required` contract, `KbqTopBarSpacer`'s class at all, `booleanAttribute` coercion of the bare-attribute form `<kbq-top-bar withShadow>` that two docs examples actually use (`top-bar-breadcrumbs-adaptive-example.ts:64`, `top-bar-title-counter-adaptive-example.ts:63`), and every one of the CSS behaviours in TB-CSS-01..03. The host itself has three defects of its own: `readonly topBar = viewChild.required(KbqTopBar)` (`:47`) is never read by any case — dead since it was introduced, and it survived the DS-4934/DS-5288 churn that added and later removed the dropdown-host cases around it; the queried element is stored as `menuElement` (`:9, 18`), a copy-paste name from a menu component; and `KbqTopBarModule` is imported twice, once into the TestBed (`:13`) and once into `TestApp` (`:43`).
**Fix:** collapse the three shadow cases into two (default off, on) plus one `booleanAttribute` case driving the bare attribute; add a `ContainerTestApp` asserting `kbq-top-bar-container__start` for `placement="start"`, `__end` for `"end"`, and that the two never co-occur; add a one-line spacer case. Delete the unused `topBar` viewChild, rename `menuElement` to `topBarElement`, and drop the duplicated module import. Then apply a mutation check: replacing `[class.kbq-top-bar-container__start]` with a constant `true` must fail at least one case — a class-assertion suite that passes against a broken binding is worth nothing.

### P3 — Nice to have / hygiene

**TB-STYLE-01 · BEM element syntax used for modifiers, one dead declaration, physical margins** — `top-bar.ts:25-26`, `top-bar.scss:9, 14, 19, 43, 56, 64`.
Three style-surface issues. **(1)** `kbq-top-bar-container__start` / `__end` are *modifiers* of `.kbq-top-bar-container` written with the `__` element separator. The repo convention is unambiguous in both directions — `__` marks elements (`kbq-alert__title`, `kbq-breadcrumb__separator`, ~200 occurrences) and a single `_` marks modifiers (`kbq-alert_compact`, `kbq-badge_contrast`) — and this very component follows it correctly one line away, in `kbq-top-bar_with-shadow` (`top-bar.ts:49`). **(2)** `.kbq-top-bar-spacer { height: 100% }` (`top-bar.scss:43`) is dead: a percentage height resolves against a *definite* parent height, and `.kbq-top-bar` is a flex row with `align-items: center` (`:27`) and no height, so it computes to `auto` — on an element that is empty anyway. **(3)** The overflow-items mixin uses physical `margin-right` / `margin-left` (`:9, 14, 19`) and the end container uses `justify-content: end` (`:67`), so the item spacing does not mirror under `dir="rtl"` while the flex layout does.
**Fix:** rename the two modifier classes to `kbq-top-bar-container_start` / `_end`. This is breaking — four docs examples target the old names in their `styles` blocks (`top-bar-actions-example.ts:102`, `top-bar-overview-example.ts:99`, `top-bar-title-counter-example.ts:106`, `top-bar-title-counter-adaptive-example.ts:142`) and external consumers will too — so either keep the old names as aliases for one minor or pair the rename with an `ng-update` migration (see `project_breaking_changes_need_migration_schematics`). Delete the dead `height: 100%`, and switch the three margins to `margin-inline-end` / `margin-inline-start`.

**TB-API-01 · Three of four exports are `(undocumented)` and the package has no `@packageDocumentation`** — `tools/public_api_guard/components/top-bar.api.md:9, 27, 37, 45`; `top-bar.ts:16, 52`; `module.ts:14`.
`KbqTopBar`, `KbqTopBarModule` and `KbqTopBarSpacer` all carry `// @public (undocumented)`, and the report closes with "(No `@packageDocumentation` comment for this package)" (`top-bar.api.md:45`). `KbqTopBarSpacer` is the sharpest case: it is an exported public directive with no JSDoc, no mention in either guide, and no test — its entire specification is one class name (`top-bar.ts:13`) and one CSS rule (`top-bar.scss:42-45`). A consumer's only route to understanding it is reading the examples.
**Fix:** add a class-level JSDoc to each of the three, stating for `KbqTopBar` that it is a flex row expecting `[kbqTopBarContainer]` slots and an optional `[kbqTopBarSpacer]` between them, and for `KbqTopBarSpacer` that it reserves `--kbq-top-bar-spacer-min-width` of guaranteed clearance between the two sides. Add a `@packageDocumentation` block to `public-api.ts`. Batch with TB-DOC-01 and run `yarn run build:components` then `yarn run approve-api` once — the guard reads `dist/*.d.ts`, so the build must come first.

**TB-TEST-02 · The e2e fixture is one static screenshot over 306 lines with three copy-pasted blocks and a dead field** — `e2e.ts:19-26, 47-96, 98-147, 149-202, 280-302`; `e2e.playwright-spec.ts:8-14`; `__screenshots__/01-{light,dark}.png`.
The Playwright suite is a single test taking one light and one dark screenshot of a static page (`e2e.playwright-spec.ts:8-14`). None of the behaviour the guide advertises is covered: the overflow-items collapse into the dropdown (the "Responsive mode" section), the `withShadow` toggle driven by scroll ("Scroll behavior"), or the breadcrumbs/title adaptive variants — the fixture is rendered at three fixed widths and never resized. The fixture itself has hygiene problems: `e2e.ts:47-96`, `:98-147` and `:149-202` are three near-identical copies of the same top-bar-with-overflow-items block differing only in an inline width and the left-hand content, ~150 of the file's 306 lines; and `E2eTopBarAction.icon` (`:24`) is populated for all three actions (`:285, :292, :299`) but never rendered anywhere in the template — a grep for `action.icon` in the file returns nothing.
**Fix:** extract the repeated block into a local child component or an `@for` over a small config array, delete the unused `icon` field (or render it, which is presumably what was meant), and add rows that exercise the real behaviours: a narrow container where overflow-items collapses, a `withShadow` on/off pair, and the flex-row start-container case that guards TB-CSS-03. Baselines must be produced with `yarn run e2e:docker:update-snapshots` — the committed PNGs are Linux, compared at `threshold: 0` with no platform suffix, so a native run fails on font rasterization alone.

**TB-DOC-02 · `examples.top-bar.*.md` are dead placeholder files** — `examples.top-bar.en.md:1-5`, `examples.top-bar.ru.md:1-5`, `apps/docs/src/app/structure.ts:1123`.
Both files carry the standard "🚧 Documentation in progress 🚧" stub. They are not a broken user surface: `structure.ts:1123` sets `hasExamples: false`, so the Examples tab is never rendered for top-bar and the files are unreachable. All seven examples under `packages/docs-examples/components/top-bar/` are already embedded inline in both guides (`top-bar.en.md:3, 11, 15, 21, 34, 46, 54, 60`), so nothing is missing from the reader's point of view — these are simply two dead files that keep surfacing in "in progress" greps.
**Fix:** delete both stubs, matching what the structure entry already declares. (Populating them and flipping `hasExamples: true` is the alternative, but it would duplicate the guide, which already carries every example.)

**TB-DOC-03 · Two examples style the container through an attribute selector that only works for one of the two binding forms in use** — `top-bar-breadcrumbs-example.ts:98-103`, `top-bar-breadcrumbs-adaptive-example.ts:159-167`; contrast `top-bar-actions-example.ts:102`, `notification-center-overview-example.html:133, 140`.
Both breadcrumbs examples select the container with `.kbq-top-bar-container[placement='start']` rather than the `.kbq-top-bar-container__start` class the directive exists to apply (`top-bar.ts:25`). That works only because those templates happen to write the *static attribute* form `placement="start"`, which Angular renders into the DOM. The repo uses both forms — `notification-center-overview-example.html:133` writes `placement="start"` but `:140` writes `[placement]="'end'"`, a property binding that leaves no attribute behind — so a maintainer who normalises the binding style silently deletes the styling, with no compile error and no test to catch it. The three other top-bar examples do it correctly via the class (`top-bar-actions-example.ts:102`, `top-bar-overview-example.ts:99`, `top-bar-title-counter-example.ts:106`), so the library is demonstrating two patterns for the same thing, one of which is a trap.
**Fix:** change both selectors to `.kbq-top-bar-container__start` (or `_start` after TB-STYLE-01). While in these files, align the exported class name of the adaptive example — `ExampleTopBarBreadcrumbs` (`top-bar-breadcrumbs-adaptive-example.ts:176`) is the only one of the seven that does not follow the `<Name>Example` convention its siblings use.

## 4. Recommended Remediation Phases

**Phase 1 — Get off the overlay layer.**
IDs: TB-CSS-01, TB-CSS-02. Add a `--kbq-top-bar-z-index` layer token at `990` with the navbar's rationale comment, drop the `overlay` `@use`, and resolve the inert `position: sticky` one way or the other — the two are coupled, because a non-positioned bar needs no stacking context at all. Delete `apps/docs/src/styles/_docsearch.scss:3-6` in the same PR; that deletion is the proof the fix worked. No API change, no baseline churn beyond the top-bar screenshots.

**Phase 2 — Repair the published contract.**
IDs: TB-DOC-01, TB-API-01, TB-A11Y-01, TB-DOC-02, TB-DOC-03. Rewrite the three wrong JSDoc strings, document the three undocumented exports and the package, add an Accessibility section plus the `ariaLabel` hook, delete the dead example stubs, and fix the two attribute-selector examples. One `build:components` + `approve-api` cycle covers every API-report change in this phase. This is what an external consumer meets first, and none of it depends on Phase 1.

**Phase 3 — Make the layout defaults usable.**
IDs: TB-CSS-03, TB-ARCH-01, TB-STYLE-01. Give the start container a floor that callers do not have to invent, make the two overflow-items selectors agree about depth, rename the two modifier classes and fix the dead/physical declarations. Removing the five `--kbq-top-bar-container-start-basis` overrides from the docs examples is the acceptance criterion. Requires updated Playwright baselines via Docker, and the class rename is breaking — schedule with a minor and pair it with aliases or an `ng-update` migration.

**Phase 4 — Close the test gaps.**
IDs: TB-TEST-01, TB-TEST-02. Bring the Jest spec to cover all three exports plus coercion and the ARIA hook from Phase 2, and rebuild the e2e fixture around the responsive behaviour the guide advertises. Best done incrementally alongside Phases 1–3 — each phase above names the specific assertion it needs — with this phase collecting the leftovers (dead viewChild, `menuElement`, duplicated e2e blocks, dead `icon` field).

## Appendix A — Review Methodology

Every file in the package was read in full (9 source files, 671 lines excluding screenshots), then each candidate finding was checked against four independent sources: the workspace compiler settings (`tsconfig.json:114-118`), the API guard report and its `api-extractor` registration (`tools/api-extractor/config.json:59`), every in-repo consumer of `<kbq-top-bar>` / `[kbqTopBarContainer]` / `[kbqTopBarSpacer]` found by grep across `packages/` and `apps/` (7 docs examples, 4 notification-center examples, the docs-site header, the SSR dev app), and the design-token files. Consumer evidence is what upgraded TB-CSS-01 and TB-CSS-03 from style opinions to confirmed defects: in both cases a workaround already exists in the tree, written by someone who hit the problem. Git history was used to date the coupling in TB-ARCH-01 (two fixes two days apart) and to establish the navbar precedent for TB-CSS-01 (`26cf45df`, DS-5403). Design tokens were verified as resolvable: `--kbq-background-bg` (`css-tokens-light.css:6`, `css-tokens-dark.css:6`), `--kbq-shadow-overflow-normal-bottom` (`:168` / `:167`) and the `--kbq-size-*` family (`css-tokens.css:1285-1298`). This review deliberately drops the *RxJS & Lifecycle* and *Performance* scorecard dimensions: the package contains no subscriptions, no lifecycle hooks and no runtime computation, so both would be vacuous A's.

Refuted during verification:
- **"The missing `_top-bar-theme.scss` leaves the component unthemed"** — refuted, and it was the first thing checked. The package has exactly two colour declarations, `background-color: var(--kbq-top-bar-background)` (`top-bar.scss:33`) and `box-shadow: var(--kbq-top-bar-shadow-bottom)` (`:38`); both tokens are declared in `top-bar-tokens.scss:3, 11` and forward `--kbq-background-bg` and `--kbq-shadow-overflow-normal-bottom`, which are defined in both `css-tokens-light.css` and `css-tokens-dark.css`. Theme mixins in this repo are not aggregated — each component `@include`s its own from its own SCSS (`divider.scss:30`, `navbar.scss:31`), and `core/styles/_koobiq-theme.scss:15-28` pulls in only seven global ones — so a separate theme partial would buy nothing here. Both values are token-level, so there is no light/dark split left to express. Not a defect.
- **"`--kbq-top-bar-spacer-min-width` is applied as a fixed `flex-basis`, so the guide's '80px minimum' is really a fixed 80px"** — refuted. The spacer is `flex: 0 0 80px` (`top-bar.scss:44`), but the start container is `flex: 1 0 …` (`:59`) and therefore absorbs all positive free space; the 80px is the *guaranteed minimum* clearance between the two sides and the visible gap is normally wider. `top-bar.en.md:40` / `top-bar.ru.md:41` are accurate as written.
- **"`z-index: 1000` puts the bar above CDK overlays, so dropdowns render behind it"** — refuted as stated. The values tie, and `.cdk-overlay-container` is appended to `<body>` after app content, so painting order gives the overlay the win — which is the behaviour DS-5288 intends. The defect filed as TB-CSS-01 is the tie itself, the absence of a layer token and the contradiction with the shipped migration advice, not an observed inversion.
- **"`justify-content: space-between` on `.kbq-top-bar` (`:28`) is dead CSS"** — refuted. In the documented three-slot structure the start container's `flex-grow: 1` leaves no free space to distribute, so it is inert *there*; but `packages/components-dev/ssr/components/breadcrumbs.ts:20-39` puts a bare `<nav>` directly inside `<kbq-top-bar>` with no container and no spacer, and `space-between` is what positions it. The declaration is load-bearing for the container-less usage.
- **"The bare `module.ts` violates the AGENTS.md `<component-name>.module.ts` convention"** — refuted as a top-bar defect. Twelve packages use a bare `module.ts` (`actions-panel`, `clamped-text`, `content-panel`, `dynamic-translation`, `flag`, `inline-edit`, `overflow-items`, `resizer`, `skeleton`, `time-range`, `top-bar`, `username`). That is repo-wide convention drift worth one umbrella decision, not a finding against this package.

Corrected on verification:
- **TB-CSS-02** was drafted as a P1: "the guide promises the toolbar stays fixed while scrolling, and `position: sticky` cannot deliver it". Reading `top-bar-overflow-example.ts:145-164` showed the example delivers exactly that with flex layout, placing the bar outside the scroll container — so the guide is honest and the severity dropped to P2, with the finding narrowed to the inert token and the stacking context it opens for free.
- **TB-A11Y-01** was drafted as a P1, mirroring the divider review's `DIV-A11Y-01`. The evidence is weaker here: no consumer hand-rolls a `role` on `<kbq-top-bar>` (divider had five different hand-rolled patches), a missing landmark is not an axe failure, and it is genuinely arguable whether the component should pick a landmark at all given it is used both as page chrome and as a panel header. Filed P2, with the fix reframed from "add a role" to "give the caller a hook and tell them which role to use".
- **TB-ARCH-01** was drafted as "top-bar styles another package's internals" — a coupling observation with no demonstrated failure. Reading the two selectors side by side showed a concrete, derivable bug (the `:has()` at `:48` matches at any depth while the compensating mixin at `:70-73` matches only self-or-child), which is what moved it from P3 to P2.
