# Koobiq `icon` Component — Code Review & Improvement Plan

> Scope: `packages/components/icon` (`KbqIcon`, `KbqIconButton`, `KbqIconItem`, `KbqIconRegistry`, providers, tokens, themes, both Jest specs, e2e fixture + Playwright spec, four user guides, API guard report) · Commit `b665e503` · 2026-08-28
> Generated by a multi-dimension review (architecture, RxJS/lifecycle, correctness, accessibility, public API/types, styles, tests, docs) with manual verification of every finding against the source, the 1 607 in-repo call sites, the `@koobiq/icons` font stylesheet and the workspace compiler settings. 13 findings confirmed (P0×0, P1×4, P2×5, P3×4); 5 candidate findings refuted during verification (see Appendix A). This document is a review + roadmap; no source is modified by it.

---

## 1. Executive Summary

`icon` is the most-consumed package in the library: 403 `[kbq-icon]` call sites live inside `packages/components` alone (1 607 across `packages/`), and 86 component packages depend on it. It ships three components on one inheritance chain — `KbqIcon` (168 lines), `KbqIconButton` (119), `KbqIconItem` (28) — plus a 345-line `KbqIconRegistry` that resolves SVG sprites, URLs and inline literals. Because everything else in the library renders through it, its defects are amplified 403 times over.

- **The single most serious defect is that the SVG resolution stream terminates on its first error, and in the default font-icon configuration that error is guaranteed to happen.** `ngAfterContentInit` subscribes once, through `switchMap`, to `registry.getNamedSvgIcon()`, which returns `throwError(...)` for any unregistered name (`icon-registry.ts:166`). With no sprite/resolver configured — the documented default — the very first replayed name errors, the outer subscription completes, and every later `[kbq-icon]` change on that element is silently dropped: `updateMaxHeight()` never re-runs, so a stale inline `max-height` clips the new glyph, and in registry-configured apps a previously injected `<svg>` is left in the DOM beside the new font class (ICN-BUG-01).
- **Icons are never hidden from assistive technology.** The registry writes `aria-hidden="true"` onto the injected `<svg>` (`icon-registry.ts:287, 312`), but the dominant font path never writes anything onto the host — which renders a Private-Use-Area glyph through `content: "\f501"` (`kbq-icons.css:37`) behind a `speak: none` (`:20`) that no browser implements. Consumers have noticed unevenly: of 403 in-repo call sites, 8 carry a hand-written `aria-hidden`, and all 8 live in just two packages (ICN-A11Y-01).
- **`KbqIconButton` makes non-interactive elements focusable without making them buttons.** The host binds `tabindex` unconditionally (`icon-button.component.ts:35`) but no `role`, no `keydown` activation and no `aria-disabled`; 129 of 180 in-repo call sites put it on `<i>`, where `[attr.disabled]` is inert. `KbqTagRemove` already fights the binding by re-declaring `[attr.tabindex]': '-1'` on the same element (ICN-A11Y-02).
- **Every documented SVG setup snippet is broken.** The sprite section in both languages, and the URL-resolver section in Russian, import `provideHttpClient` and then omit it from `providers` — while `icon-registry.ts:319-324` throws "HttpClient is required for loading icons from URLs" the moment a sprite is fetched. A reader copying the first documented SVG approach gets a runtime throw (ICN-DOC-01).
- **`KbqIcon` and `KbqIconItem` have no unit tests at all.** The package's 24 Jest cases cover `KbqIconButton`'s host classes (8) and the registry (16); nothing exercises the class binding, the SVG injection/replacement, the error fallback, `updateMaxHeight`, `autoColor`/`hasError` or `parseIconSize` (ICN-TEST-01).

Genuine strengths worth preserving: the registry is a careful piece of work — literals are sanitized through `SecurityContext.HTML` with an explicit throw on empty output (`icon-registry.ts:71-75`), concurrent URL fetches are deduped and released in `finalize` (`:332-341`), parsed sets are cached per URL (`:260-271`), and the XSS behaviour is pinned by four dedicated specs (`icon-registry.spec.ts:178-232`). The provider surface (`kbqIconsProvider` / `kbqIconsResolverProvider` / `kbqIconsDictProvider`) is small, composable and well documented in JSDoc. `icon-error-state-context.ts` is exactly the narrow injection token AGENTS.md asks for instead of a concrete-class dependency. And the state/style e2e fixture is genuinely thorough — 6 colours × 8 state rows across icon, icon-item and both icon-button host elements, in light and dark.

## 3. Prioritized Findings (deduplicated, verified)

### P0 — Release blockers

None.

### P1 — High

**ICN-BUG-01 · The SVG resolution stream terminates on the first unresolved name — which the default font configuration guarantees** — `icon.component.ts:98-102, 104-154`, `icon-registry.ts:160-166`.
`ngAfterContentInit` opens exactly one subscription: `svgIconName.pipe(switchMap(name => registry.getNamedSvgIcon(name)), takeUntilDestroyed()).subscribe({ next, error })` (`icon.component.ts:112-153`). `switchMap` propagates an inner error to the outer stream, so the `error` callback is terminal — the subscription closes and the `ReplaySubject` at `:69` has no listener left. The trigger is not exotic: `getNamedSvgIcon` ends in `throwError(() => Error('no icon registered for …'))` when no icon config, resolver or icon set matches (`icon-registry.ts:166`), and `KbqIconRegistry` is `providedIn: 'root'` so `inject(..., { optional: true })` always yields an *empty* registry in a font-icon app. `ngOnChanges` pushes the first name (`:98-102`) before `ngAfterContentInit` subscribes, the `ReplaySubject(1)` replays it at subscribe time, and the stream is dead before the first frame is painted — in **every** application that follows the documented default setup (`icon.en.md:1-29`). Three consequences follow. (1) `updateMaxHeight()` is only ever called at `:110` and from the error handler at `:150`, so after the stream dies an inline `max-height` written for the initial name is never revised: `<i [kbq-icon]="name">` moving from `kbq-chevron-down-s_16` to `kbq-play_64` keeps `max-height: 16px` while the font rule raises `font-size` to 64 px, and the glyph is clipped (`.kbq` is `display: inline-block`, `kbq-icons.css:15`, so `max-height` bites). (2) In a registry-configured app, an icon that first resolves and then moves to a missing name keeps its old `<svg>`: the `error` branch (`:147-152`) sets `svgIcon = false` and calls `markForCheck()` but never removes the node that `:144` inserted, so the element renders the stale SVG *and* the newly re-applied font class from `'[class]': 'svgIcon ? null : iconName'` (`:30`). (3) No later name is ever resolved as SVG on that element again. There is no consumer workaround short of destroying and recreating the host element.
**Fix:** make the failure non-terminal. Move the fallback into the stream — `switchMap(name => … ? registry.getNamedSvgIcon(name).pipe(catchError(() => of(null))) : of(null))` — and handle `null` in `next` by clearing any injected `<svg>`, setting `svgIcon = false` and calling `updateMaxHeight()`; drop the `error` callback entirely. Extract the "remove previously injected SVG" block (`:131-134`) so both branches run it, and make `updateMaxHeight()` clear the inline style when `parseIconSize()` returns `NaN` rather than leaving the previous value (see ICN-BUG-03). Guard with three Jest cases in a new `icon.component.spec.ts`: an unregistered name followed by a registered one resolves to an `<svg>`; a registered name followed by an unregistered one leaves **no** `<svg>` in the host; and `[kbq-icon]` moving from `*_16` to `*_64` updates `style.maxHeight`.

**ICN-A11Y-01 · Font icons are exposed to assistive technology; only the SVG path is hidden** — `icon.component.ts:28-32` (host block), `node_modules/@koobiq/icons/fonts/kbq-icons.css:13-20, 37`, `icon-registry.ts:287-288, 312-313`; consumers `app-switcher/app-switcher.html:4`, `app-switcher/app-switcher-list-item.ts:47`, `filter-bar/filter-refresher.ts:19, 27`, `filter-bar/filters.html:45, 61`, `filter-bar/pipe-add.ts:42`, `filter-bar/pipes/pipe-button.ts:38`.
The host block binds `class`, `[class]` and `[class.kbq-error]` — no `role`, no `aria-hidden`. The registry is careful in the opposite direction: every SVG it produces gets `aria-hidden="true"` and `focusable="false"` (`icon-registry.ts:287-288` for sprite symbols, `:312-313` for literals and fetched files). So the *minority* path is hidden and the *default* path is not. The default path renders a Private-Use-Area codepoint through a `::before` rule (`content: "\f501"`, `kbq-icons.css:37`); the `speak: none` declaration at `:20` is an aural-CSS property that was dropped from the spec and is implemented by no shipping browser, so it does nothing. Screen readers that expose generated content — Chrome/Chromium with NVDA and JAWS, Safari with VoiceOver — therefore announce an unmapped glyph inside otherwise labelled controls. The library's own tree shows how uneven the situation is: of 403 `[kbq-icon]` call sites under `packages/components`, exactly 8 carry a hand-written `aria-hidden`, and all 8 sit in `app-switcher` and `filter-bar` — two packages out of the 86 that consume icons. This is a WCAG 1.3.1/4.1.2 judgement, not an automated failure: axe-core does not flag a custom element that carries no role, which is precisely why 395 unguarded call sites have survived. Note also that `<i>` is a *presentational* element being used for a glyph, so nothing else supplies semantics.
**Fix:** default the host to decorative — add `'[attr.aria-hidden]': 'ariaHidden()'` to `icon.component.ts:28-32` with `readonly ariaHidden = input(true, { transform: booleanAttribute, alias: 'aria-hidden' })`, so `<i kbq-icon="…">` is hidden unless a caller explicitly opts out with `aria-hidden="false"` for a meaningful icon (which must then also carry `role="img"` and an `aria-label` — document that pairing in `icon.en.md`/`icon.ru.md`, which currently say nothing about accessibility). Keep `KbqIconButton` out of the default: an icon button is interactive and must expose its own name, so override the host binding there to `null` and cover it in ICN-A11Y-02. Then delete the 8 hand-written `aria-hidden` attributes so the library speaks with one voice, and add a Jest case asserting `aria-hidden="true"` on a bare `<i kbq-icon>` plus its absence on `<button kbq-icon-button>`.

**ICN-A11Y-02 · `KbqIconButton` makes any element focusable without giving it a button's role, keyboard or disabled semantics** — `icon-button.component.ts:32-42, 63-72, 78-88`, `_icon-button-theme.scss:22-25, 93-103`; consumers: 129 of 180 in-repo call sites on `<i>`, `tags/tag.component.ts:751-758`.
The host block binds `[attr.tabindex]` (default `0`, `:35, 63-72`) and `[attr.disabled]` (`:36`), plus `.kbq-disabled`, and nothing else — no `role`, no `(keydown.enter)`/`(keydown.space)`, no `[attr.aria-disabled]`. On `<button>` that is fine; on `<i>` it is not, and `<i>` is what the repo actually uses: 129 of the 180 in-repo `kbq-icon-button` call sites are on `<i>`, 11 on `<button>`. Those 129 elements are in the tab order, look and behave clickable, and expose no role at all, so a screen-reader user reaches an unlabelled, unnamed stop (WCAG 4.1.2) that cannot be activated from the keyboard because `click` never fires from Enter/Space on a non-button (WCAG 2.1.1). `[attr.disabled]` is inert on `<i>` — only `.kbq-disabled { pointer-events: none }` (`icon-button.scss:18-20`) actually blocks the mouse, and nothing tells assistive technology the control is unavailable. Only 18 of the 180 call sites carry an `aria-label`; none carries a `role`. The intrusiveness of the unconditional `tabindex` binding has already caused a collision: `KbqTagRemove` re-declares `'[attr.tabindex]': '-1'` on the very same element (`tags/tag.component.ts:755`), so which value survives depends on directive-application order. Separately, `_icon-button-theme.scss:22-25` removes the native `outline` for *all* focus origins while the replacement ring is `box-shadow` under `.cdk-keyboard-focused` only (`:93-103`) — a `box-shadow` is not painted in forced-colors mode, and the repo has no `forced-colors` handling anywhere (grep across `packages/**/*.scss` returns nothing), so the focus indicator vanishes there (WCAG 2.4.7 / 1.4.11).
**Fix:** in `icon-button.component.ts` add `'[attr.role]': "isNativeButton ? null : 'button'"` (computed once from `elementRef.nativeElement.nodeName`), `'[attr.aria-disabled]': 'disabled || null'`, and `'(keydown.enter)'`/`'(keydown.space)'` handlers that `preventDefault()` and dispatch a click when the host is not a native button. Make `tabindex` fall back to a host-provided value instead of overwriting it, so `KbqTagRemove` can keep `-1` without a race. Require an accessible name: reuse `kbqInjectA11yLocaleConfiguration()` the way `KbqCleaner` does (`form-field/cleaner.ts:81-87`) or emit a dev-mode `console.warn` when neither `aria-label` nor `aria-labelledby` is present, matching the existing `button-toggle` accessible-name check. Add `@media (forced-colors: active) { outline: 1px solid }` next to the `box-shadow` ring. Guard with Jest cases per branch (role on `<i>` vs `<button>`, Enter/Space activation, `aria-disabled`) and a `jest-axe` pass on a fixture holding both host forms — the repo already runs `toHaveNoViolations` in five packages.

**ICN-DOC-01 · Three of the four documented SVG setups omit `provideHttpClient()` and throw at runtime** — `icon.en.md:41-52`, `icon.ru.md:39-50, 66-74`; contract at `icon-registry.ts:318-324`.
The sprite snippet — the *first* SVG approach a reader meets — imports `provideHttpClient` (`icon.en.md:42`) and then lists only `kbqIconsProvider(...)` in `providers` (`:45-52`). Sprites are fetched over HTTP (`loadIconSet` → `fetchUrl`, `icon-registry.ts:266, 318`), and `fetchUrl` opens with `if (!this.httpClient) throw Error('KbqIconRegistry: HttpClient is required for loading icons from URLs. Provide it via provideHttpClient() or HttpClientModule.')` (`:319-324`). So the documented snippet does not merely fail to load icons — it throws, and because the throw is synchronous rather than an error notification (see ICN-API-02) it escapes as an unhandled exception from the first icon that renders. The Russian mirror repeats the sprite defect (`icon.ru.md:39-50`) and adds a second one the English file does not have: the URL-resolver snippet also omits `provideHttpClient()` from `providers` (`:70-74`) where English includes it (`icon.en.md:72-77`). The two files have additionally drifted in prose — `icon.en.md:35` introduces the SVG section ("SVG icons render inline and support CSS color theming via `currentColor`. Choose one of the approaches below…"); the Russian file jumps straight from the heading to `#### Спрайт-файл`, so a Russian reader gets no guidance on choosing between the approaches. `noUnusedLocals` does not police Markdown, and the docs site does not compile guide snippets, so nothing catches any of this.
**Fix:** add `provideHttpClient()` to the `providers` array of the sprite snippet in both files and of the URL-resolver snippet in `icon.ru.md`; port the missing intro paragraph from `icon.en.md:35` into `icon.ru.md`. State explicitly in both guides that the sprite and URL approaches require `provideHttpClient()` and that only inline literals (`kbqIconsDictProvider` with `<svg…` values) work without it — that asymmetry is currently documented only in `icon-registry-providers.ts:37-44`. Guard the pair with a docs assertion: the `yarn run e2e:docs` smoke suite already loads every guide page, so a compiled snippet stays compiled; failing that, a small Jest case that boots `KbqIconRegistry` without `HttpClient` and asserts the thrown message keeps the contract visible.

### P2 — Should fix

**ICN-BUG-02 · `autoColor` is read exactly once, and the error-state subscription captures a snapshot of the control** — `icon.component.ts:49, 104-108, 156-160`; provider at `form-field/form-field.ts:131-141`.
`autoColor` is a plain `@Input` read in a single `if` at `ngAfterContentInit` (`:105`). Nothing watches it afterwards, so `[autoColor]="someSignal()"` flipping to `true` after init never subscribes to the error-state context, and flipping to `false` never unsubscribes or resets `hasError` — the icon stays tinted red. The workaround visible in the tree is that every in-repo consumer binds a constant (`datepicker-toggle.component.ts:41`, `form-field/stepper.ts:74, 84`, `time-range/time-range-editor.html:31, 55`) or writes the field imperatively before init (`form-field/cleaner.ts:94`), which is exactly the "your application code writes to the input" case the migration TODO at `icon.component.ts:47-48` records. There is a second, subtler snapshot: `this.errorStateContext?.stateChanges.pipe(...)` (`:106`) evaluates the `stateChanges` getter once. `form-field.ts:136-138` deliberately exposes it *as a getter* over `formField.control()` — a `contentChild` signal — because the control can be replaced at runtime; the icon defeats that by subscribing to whichever `Subject` the first control happened to own, so an icon inside a form field whose control is swapped (an `@if` alternating input types) stops tracking error state entirely.
**Fix:** convert `autoColor` to `readonly autoColor = input(false, { transform: booleanAttribute })` and drive the wiring from an `effect()` (or `toObservable(this.autoColor).pipe(switchMap(on => on ? … : EMPTY))`), resetting `hasError = false` on the off-branch. Re-read the context through the signal on every emission — `toObservable(...).pipe(switchMap(() => this.errorStateContext?.stateChanges ?? EMPTY))` — so a swapped control is picked up. `KbqCleaner` writes the field in its constructor (`cleaner.ts:94`), which a signal input rejects; give it `setDefaultAutoColor()` (mirroring the existing `setIconName()` escape hatch at `icon.component.ts:81-84`) in the same change. Cover with a spec that toggles `[autoColor]` after init and one that swaps the form field's control while an `autoColor` icon is projected.

**ICN-BUG-03 · Icon pixel size is inferred from the icon *name* by string surgery, written as an inline style and never cleared** — `icon.component.ts:86-96, 137-142, 162-167`.
`parseIconSize()` takes the icon name, drops anything before `:`, splits on `_`, takes the last segment and `parseInt`s it (`:162-167`). The result is written two ways: as an inline `style.maxHeight` on the host (`:94`) and as `width`/`height` attributes on the injected `<svg>` (`:140-141`). Three problems. (1) It is a heuristic over a *user-chosen* string: a custom icon registered as `brand_2024` yields `2024`, so the SVG is emitted at `width="2024" height="2024"` and the host gets `max-height: 2024px`; `logo_v2` yields `NaN` and is skipped, which is correct but only by accident. The `@koobiq/icons` `_16`/`_24` convention is nowhere enforced or documented as a requirement, yet `kbqIconsResolverProvider` invites arbitrary names (`icon-registry-providers.ts:33-35`). (2) `updateMaxHeight()` only ever *sets* — `if (size) { … }` (`:93-95`) has no `else` clearing a previously written value, so a name change from a sized to an unsized icon leaves the old ceiling in place. (3) The write bypasses `Renderer2` (as do `host.removeChild`/`host.insertBefore` at `:134, 144`), so the component is tied to a DOM renderer and the injected `<svg>` is invisible to Angular's template-serialization path; the same applies to `KbqColorDirective`, which mutates `classList` directly (`core/common-behaviors/color.ts:57-62`). The `if (this.name !== 'KbqIcon') return` guard at `:87` — a string comparison standing in for `instanceof` — means icon-button and icon-item silently skip the sizing entirely, which is intentional but undiscoverable.
**Fix:** make the size explicit rather than inferred: add `readonly size = input<number | undefined>(undefined)` and fall back to name parsing only when it is unset, with the fallback documented in `icon.en.md`/`icon.ru.md` as the `_<px>` naming convention. Give `updateMaxHeight()` an `else` branch that clears `maxHeight` (via `renderer.removeStyle`) and route all three DOM writes through the injected `Renderer2`, which also removes the `nativeElement.style` write flagged by the SSR rule in AGENTS.md. Replace the `this.name !== 'KbqIcon'` guard with an overridable `protected readonly appliesMaxHeight = true` that the two subclasses set to `false`. Cover `parseIconSize` directly with a table-driven Jest case (`'plus_16'` → 16, `'ns:plus_24'` → 24, `'brand_2024'` → 2024, `'logo'` → `NaN`, `'check-16'` → `NaN`).

**ICN-ARCH-01 · Subclasses inherit the base host *class* but not the base DI *token*, so CSS over-matches while queries under-match** — `icon.component.ts:29`, `icon-button.component.ts:26-44`, `icon-item.component.ts:4-19`; consumers `alert/alert.component.ts:100-102, 139`, `badge/badge.component.ts:56, 80-85`, `button-toggle/button-toggle.component.ts:453`, `dropdown/dropdown-item.component.ts:70`, `link/link.component.ts:60, 105, 128`, `navbar/navbar-item.component.ts:514`, `alert/_alert-theme.scss:40-42`, `dropdown/_dropdown-theme.scss:7`, `schematics/src/migrations/button-toggle-signals-and-aria/data.ts:26-35`.
Angular's `ɵɵInheritDefinitionFeature` copies host bindings down, so `KbqIconButton` and `KbqIconItem` both carry `class: 'kbq kbq-icon'` from `icon.component.ts:29` — but a subclass component does **not** register its base class as a DI token. The result is exactly backwards in both directions. On the CSS side every `.kbq-icon` rule a consumer writes also hits buttons and items, and two packages have already had to exclude them by hand: `alert/_alert-theme.scss:42` (`.kbq-alert__icon > .kbq-icon:not(.kbq-icon-item, .kbq-icon-button)`, with a comment at `:40-41` explaining that they "inherit `.kbq-icon` from KbqIcon but paint their own filled backgrounds") and `dropdown/_dropdown-theme.scss:7`. On the DI side seven query sites across six packages ask for `KbqIcon` and silently see nothing when the projected element is a button or an item: `alert.component.ts:102`, `badge.component.ts:56`, `button-toggle.component.ts:453`, `dropdown-item.component.ts:70`, `link.component.ts:60` and `:128`, `navbar-item.component.ts:514`. The consequences are concrete — `link.component.ts:105` (`hasIcon`) drives `.kbq-text-with-icon` and `updateClassModifierForIcons` (`:160-176`) applies `kbq-icon_left`/`kbq-icon_right` styled at `_link-theme.scss:55, 59`, so an icon-button inside a link gets no spacing; `navbar.component.ts:281` filters collapsible items by `item.icon() && item.title()`, so a navbar item built on `kbq-icon-item` is never collapsed; `badge.component.ts:80-85` decides its icon-button layout by comparing `icons().length` with the child-node count, which an icon-button silently fails. `alert` worked around it by running two queries and merging them (`alert.component.ts:100, 102, 139`), and the schematics package documents the whole trap in a comment: "`KbqIconButton` and `KbqIconItem` extend `KbqIcon` without providing its token, so the query walks past them" (`data.ts:30-32`), and widens its own detection to raw attribute names to compensate (`:35`).
**Fix:** add `providers: [{ provide: KbqIcon, useExisting: forwardRef(() => KbqIconButton) }]` to `KbqIconButton` and the equivalent to `KbqIconItem` — note that `providers` are **not** inherited through the decorator, so each subclass needs its own entry. Then re-check every one of the seven query sites: some (link spacing, navbar collapsing, badge layout) become correct for free; others may need narrowing to `KbqIcon` *excluding* the subclasses, which the token change makes expressible. In the same pass move the `kbq-icon` host class off the base and onto `KbqIcon` only, giving `.kbq-icon-button` / `.kbq-icon-item` their own class contract and letting `alert` and `dropdown` delete their `:not()` guards — deleting those two guards is the acceptance criterion. This is a behaviour change for consumers who rely on `.kbq-icon` matching all three, so pair it with an `ng-update` migration per `project_breaking_changes_need_migration_schematics` and run the `alert`, `badge`, `button-toggle`, `dropdown`, `link` and `navbar` suites.

**ICN-CSS-01 · Theme tokens are declared on `.kbq-icon` itself, so no ancestor can re-theme an icon** — `icon-tokens.scss:1-9`, `_icon-theme.scss:3-30`; consumer `alert/_alert-theme.scss:33-45`.
`icon-tokens.scss` declares all six `--kbq-icon-*-color` custom properties inside a `.kbq-icon { … }` block, i.e. on the icon element itself rather than at `:root` or on a theme scope. CSS custom properties resolve at the element where they are *used*, and a declaration on that same element always beats an inherited one, so a consumer setting `--kbq-icon-warning-color` on a container has no effect whatsoever. `alert` discovered this and documented it in a comment that is worth reading as a bug report against this package: "The token has to be redeclared on the icon element itself: icon-tokens.scss declares `--kbq-icon-warning-color` on `.kbq-icon`, so a value inherited from `.kbq-alert` never wins" (`alert/_alert-theme.scss:38-39`) — followed by a rule that redeclares two tokens directly on the icon (`:42-45`) purely to clear a WCAG 1.4.11 contrast minimum. The same shape forces 29 rules across 18 packages to reach for `.kbq-icon.kbq-empty` to out-specify `_icon-theme.scss`'s `.kbq-icon { color: … }` (`:5`) without clobbering an explicitly-set `[color]`; that idiom is legitimate and must be preserved (`kbq-empty` is computed at runtime by `KbqColorDirective`, see Appendix A), but the token scoping is not.
**Fix:** move the six `--kbq-icon-*-color` declarations out of `.kbq-icon` and into the library's theme scope alongside the other semantic tokens (the pattern `--kbq-icon-theme-color: var(--kbq-icon-theme)` is a pure alias, so relocating it is mechanical), leaving `.kbq-icon` to *consume* them. Verify against `@koobiq/design-tokens/web/new/css-tokens-{light,dark}.css`, which is where the right-hand sides live. The acceptance test is deleting `alert/_alert-theme.scss:42-45` and setting the two tokens on `.kbq-alert` instead — the alert screenshots must stay identical, which means regenerating nothing and running `yarn run e2e:docker` for `alert`, `badge`, `dropdown`, `file-upload`, `form-field`, `link`, `navbar`, `tabs` and `tags`.

**ICN-TEST-01 · The two components with all the logic have no unit tests; the SVG e2e is light-only and its flake was closed by deleting the interaction** — `packages/components/icon/` (no `icon.component.spec.ts`, no `icon-item.component.spec.ts`), `icon-button.component.spec.ts:1-134`, `icon-registry.spec.ts:1-233`, `e2e.playwright-spec.ts:20-27`, commit `0ed83c7e4`.
The package ships 24 Jest cases: 8 in `icon-button.component.spec.ts` (colour class, class preservation, click, native `disabled`, four `size`/`small` combinations) and 16 in `icon-registry.spec.ts`. Not one of them touches `KbqIcon`'s own behaviour — the `'[class]': 'svgIcon ? null : iconName'` binding, SVG injection and replacement, the error fallback, `updateMaxHeight`, `autoColor`/`hasError`, `parseIconSize` — and `KbqIconItem` has no spec at all, so its four host-class bindings (`icon-item.component.ts:12-15`) are unverified. That gap is why ICN-BUG-01, ICN-BUG-02 and ICN-BUG-03 are all invisible to CI. The e2e side is uneven too: the state/style fixture screenshots light *and* dark (`e2e.playwright-spec.ts:14-16`) while the SVG fixture screenshots light only (`:25`), even though `icon.scss:4-7` paints SVGs with `fill: currentColor` and therefore has a dark-theme story. And the one recorded flake was closed by deletion rather than diagnosis: `0ed83c7e4` removed the dropdown-open step and the `e2eIconSvgDropdownTrigger` element from the spec, then pulled `../dropdown/dropdown-tokens.scss` and `../dropdown/dropdown.scss` into the fixture (`e2e.ts:359`) to fake the styling the real overlay used to provide — so the fixture now asserts a hand-assembled approximation of a dropdown item. Note that animation was not the cause: `playwright.config.ts:101` sets `reducedMotion: 'reduce'` for every browser context.
**Fix:** add `icon.component.spec.ts` covering the class binding for plain and `ns:name` values, SVG injection through a `kbqIconsDictProvider` literal, replacement on a name change, the fallback path (ICN-BUG-01's three cases), `updateMaxHeight` set-and-clear, `parseIconSize`'s table, and `autoColor` with a stub `KBQ_ICON_ERROR_STATE_CONTEXT`; add `icon-item.component.spec.ts` for the four host classes and the `big`/`fade` defaults. Add a dark screenshot to the SVG e2e (`02-dark.png`), produced only via `yarn run e2e:docker:update-snapshots`. Restore the dropdown case as its own fixture that screenshots the overlay container rather than the host element — that is what made the original assertion unstable — and drop the borrowed dropdown SCSS from `e2e.ts`.

### P3 — Nice to have / hygiene

**ICN-API-01 · A dead input, a stringly-typed identity and two type lies in the published surface** — `icon.component.ts:46, 58, 60, 87, 162-166`, `icon-button.component.ts:51, 63-72`, `icon.api.md:35, 49, 51, 60, 82, 91, 93-94, 121`.
Four items on one surface. (1) `KbqIcon.small = input(false)` (`icon.component.ts:46`) is never read by `KbqIcon` — not in its host block (`:28-32`), not in `icon.scss`, not in `_icon-theme.scss` — and no in-repo call site binds `small` on a plain `[kbq-icon]` (grep across `packages/`). It is nonetheless published as `readonly small: i0.InputSignal<boolean>` (`icon.api.md:60`) and is shadowed by `KbqIconButton`'s own `small`, which *is* used and *is* deprecated (`icon-button.component.ts:51`, `icon.api.md:91`) — so the report advertises the same input twice with different deprecation status. (2) `protected name = 'KbqIcon'` (`:60`), overridden to `'KbqIconButton'` / `'KbqIconItem'`, is a hand-rolled `instanceof` used at `:87` and published at `icon.api.md:51, 82, 121`; a subclass that forgets the override silently changes behaviour. (3) `iconName: string` (`:58`) is declared non-optional but is provably `string | undefined` — the implementation itself guards it with `iconName?.includes(':')` and `baseName?.split(...)` (`:164, 166`), and `strictPropertyInitialization` is off (`tsconfig.json` sets `strictNullChecks` without `strict`), so nothing catches the lie. (4) `tabindex` is typed `any` on both accessors (`icon-button.component.ts:63-72`, `icon.api.md:93-94`). On top of that `KbqIcon`, `KbqIconButton`, `KbqIconItem` and `KbqIconModule` are all `// @public (undocumented)` at class level, and 11 of `KbqIcon`'s 14 published members carry `// (undocumented)`.
**Fix:** delete `KbqIcon.small` (no in-repo consumer; announce it as a removal since it is published); replace `protected name` with the overridable boolean proposed in ICN-BUG-03; type `iconName` as `string | undefined` and drop the now-meaningful `?.` guards' ambiguity; type `tabindex` as `number | null`. Add class-level JSDoc to all three components and to `KbqIconModule`. Every one of these changes `icon.api.md`, including the ones that only add a comment (adding JSDoc removes the `(undocumented)` marker), so fold them into one `yarn run build:components` → `yarn run approve-api` cycle — build first, the guard reads `dist/*.d.ts`.

**ICN-API-02 · `KbqIconRegistry` breaks the Observable contract and builds a CSS selector by concatenation** — `icon-registry.ts:188-197, 278-281, 318-324`.
Two contract defects in an otherwise careful service. (1) `fetchUrl` throws *synchronously* when no `HttpClient` is available (`:319-324`) while every other failure in the class returns `throwError(...)` (`:166, 200, 251, 256, 329`). Because `loadIcon` calls it inline (`:189`) and `getNamedSvgIcon` calls `loadIcon` inline (`:132, 157`), a consumer who calls `registry.getNamedSvgIcon('x')` on a registry with no `HttpClient` gets an exception at the call site instead of an `error` notification — the one case a `catchError` cannot handle. Inside `KbqIcon` the throw happens within `switchMap` and is converted, which is why nothing has noticed; the direct-call path is what ICN-DOC-01 sends readers down. (2) `extractIconFromSet` looks up sprite symbols with `setElement.querySelector('#' + name)` (`:279`). Symbol ids come from the caller's sprite file, so a name starting with a digit (`3d-view_16`) or containing a `.` produces an invalid or wrongly-parsed selector; the `DOMException` is swallowed by the `catchError` at `:238` and degrades into "icon not found in any registered icon set", which is a misleading diagnosis for what is really a selector bug.
**Fix:** return `throwError(() => Error(...))` from `fetchUrl` instead of throwing, so the whole class has one failure channel. Use `CSS.escape(name)` in `extractIconFromSet` (or `Array.from(setElement.querySelectorAll('symbol')).find(s => s.id === name)`, which needs no escaping at all). Add registry specs for both: `getNamedSvgIcon` on a `TestBed` without `provideHttpClient()` emits an error rather than throwing, and a sprite whose symbol id starts with a digit resolves.

**ICN-STYLE-01 · A static "modifier" class, two redundant class pairs and a still-emitted deprecated alias** — `icon-item.component.ts:10-16`, `_icon-item-theme.scss:11-13`, `icon-button.component.ts:40-41`, `icon-button.scss:12-16`.
`KbqIconItem`'s host always emits `kbq-icon-item_filled` (`icon-item.component.ts:11`, a static class with no binding), and the theme keys off `.kbq-icon-item.kbq-icon-item_filled` (`_icon-item-theme.scss:12`) — a modifier that can never be absent exists only to add a specificity point, and it reads as though an unfilled variant is coming. The same host then spends four classes on two booleans: `_normal`/`_big` for `big()` and `_fade-off`/`_fade-on` for `fade()` (`:12-15`), where one class per boolean plus a default rule would do. On the icon-button side the deprecated `kbq-icon-button_small` class is still emitted alongside `_compact` (`icon-button.component.ts:40-41`) and still carried in the stylesheet (`icon-button.scss:12-16`) with a misspelled `@deprcated` tag in both places; DS-5338 already scheduled the removal.
**Fix:** drop `_filled` from the host and from the theme selector (specificity is unchanged relative to the rules it competes with once both lose a class); collapse `_normal`/`_fade-off` into defaults on `.kbq-icon-item` and keep only `_big`/`_fade-on` as modifiers. Remove `kbq-icon-button_small` from both the host and `icon-button.scss` in the DS-5338 major, and fix the `@deprcated` spelling in the meantime so the token is greppable. All four are screenshot-visible, so run `yarn run e2e:docker` for `icon`, `alert`, `empty-state` and `notification-center`.

**ICN-DOC-02 · Dead example stubs, an undocumented public provider, and an example directory with a space in its name** — `examples.icon.en.md:1-5`, `examples.icon.ru.md:1-5`, `apps/docs/src/app/structure.ts:576, 587, 599`, `packages/docs-examples/components/icon/icon-button-custom size/`, `packages/docs-examples/components/icon/index.ts:2`, `packages/docs-examples/example-module.ts:3069`, `icon-registry-providers.ts:37-47`, `packages/components-dev/icon/template.html:7, 11, 15`.
Four docs-plumbing issues. (1) `examples.icon.en.md`/`.ru.md` are the standard "🚧 Documentation in progress 🚧" stubs, and all three docs entries set `hasExamples: false` (`structure.ts:576, 587, 599`), so the Examples tab never renders for icon, icon-button or icon-item — the stubs are unreachable files, not a broken surface, and there is no equivalent stub pair for icon-button/icon-item at all even though those two guides embed eight live examples. (2) One of those examples lives in `packages/docs-examples/components/icon/icon-button-custom size/` — a directory whose name contains a literal space, which leaks into the import at `index.ts:2` and into `packagePath` at `example-module.ts:3069`; the id everywhere else is the hyphenated `icon-button-custom-size`. Spaces in paths are a portability and URL-encoding hazard and this is the only such directory under `docs-examples`. (3) `kbqIconsDictProvider` is exported and published (`icon.api.md:172`) but appears in no user guide, no example and no dev app — the only description of it is the JSDoc at `icon-registry-providers.ts:37-44`, which also holds the only statement that inline-`<`-prefixed values skip the HTTP request (the fact ICN-DOC-01 needs). (4) The dev app labels its provisioning demos "Approach A", "Approach B", "Approach D" (`components-dev/icon/template.html:7, 11, 15`) — the missing C reads as a demo that was deleted and never renumbered, most plausibly the dict provider.
**Fix:** delete `examples.icon.en.md`/`.ru.md` (nothing links to them) or populate all three example surfaces and flip `hasExamples: true` for the entries that would then have content — the guides for icon-button and icon-item already carry the embeds, so flipping those two is nearly free. Rename `icon-button-custom size` to `icon-button-custom-size` and update `index.ts:2` plus the regenerated `example-module.ts` (see `project_docs_example_module_generated` — the module is generated, so regenerate rather than hand-edit). Add a "Dictionary" subsection to `icon.en.md`/`icon.ru.md` documenting `kbqIconsDictProvider` and the no-HTTP guarantee, and renumber the dev-app approaches.

## 4. Recommended Remediation Phases

**Phase 1 — Make the icon render the icon it was asked for.**
IDs: ICN-BUG-01, ICN-BUG-03. Replace the terminal `error` callback with an in-stream `catchError` fallback, clear the previously injected `<svg>` on both branches, make `updateMaxHeight()` clear as well as set, and route the three DOM writes through `Renderer2`. Land it with the new `icon.component.spec.ts` — this phase is the reason that file has to exist, and every later phase is easier to verify once it does. No public API change.

**Phase 2 — Give icons and icon buttons their semantics.**
IDs: ICN-A11Y-01, ICN-A11Y-02. Default `[kbq-icon]` to `aria-hidden="true"` with an explicit opt-out, add `role="button"` / keyboard activation / `aria-disabled` to non-native icon-button hosts, make `tabindex` yield to a host-provided value, and add the forced-colors focus ring. Delete the 8 hand-written `aria-hidden` attributes in `app-switcher` and `filter-bar` as the acceptance criterion. Ship with per-branch Jest cases and a `jest-axe` fixture.

**Phase 3 — Fix the published contract.**
IDs: ICN-DOC-01, ICN-DOC-02, ICN-BUG-02. Add the missing `provideHttpClient()` to three snippets, re-sync the Russian guide's prose, document `kbqIconsDictProvider`, resolve the example stubs and the space in the directory name, and make `autoColor` a reactive signal input with a `setDefaultAutoColor()` escape hatch for `KbqCleaner`. These are what an external consumer hits first and none of them depends on Phases 1–2.

**Phase 4 — Untangle the inheritance chain.**
IDs: ICN-ARCH-01, ICN-CSS-01, ICN-STYLE-01. Provide the `KbqIcon` token from both subclasses, move the `kbq-icon` host class off the base, relocate the `--kbq-icon-*-color` declarations out of `.kbq-icon`, and clean up the class emissions. Sequenced last because it is the only breaking change in the set and it touches six consumer packages; it needs an `ng-update` migration and fresh Docker baselines. The acceptance criteria are deletions: the two `:not()` guards in `alert`/`dropdown` and the token redeclaration at `alert/_alert-theme.scss:42-45`.

**Phase 5 — Close the API and test gaps.**
IDs: ICN-API-01, ICN-API-02, ICN-TEST-01. Delete the dead `small` input, replace the stringly-typed `name`, fix the two type lies, add class JSDoc, give the registry one failure channel and an escaped selector, add `icon-item.component.spec.ts` and the dark SVG screenshot, and restore the deleted dropdown e2e case as its own fixture. One `build:components` → `approve-api` cycle covers the whole API surface, so run it once here rather than in every phase.

## 5. Verification Strategy

General gates, run sequentially (never in parallel — see `project_no_parallel_heavy_builds`):

- `yarn run eslint`, `yarn run stylelint`, `yarn run prettier` on touched files.

- `yarn run e2e:docker` for anything visual — icons appear in nearly every package's baselines, so treat a green `icon` suite as necessary but not sufficient. Regenerate baselines only with `yarn run e2e:docker:update-snapshots`.

A spec that sets an unregistered name first and a registered one second finds an `<svg>` in the host; the reverse order finds none. Deliberately reverting the `catchError` to the old `error` callback makes at least two cases fail (mutation check).

## Appendix A — Review Methodology

Findings were gathered by reading the complete package (every `.ts`, `.scss`, `.md`, both spec files, the e2e fixture and Playwright spec, 2 183 lines in total), then cross-checking each candidate against five independent sources: the workspace compiler settings (`tsconfig.json:104-118` — `strictNullChecks` without `strict`, `strictTemplates: true`), the API guard report (`tools/public_api_guard/components/icon.api.md`, 182 lines) and its registration at `tools/api-extractor/config.json:28`, the shipped `@koobiq/icons` font stylesheet, the docs navigation (`apps/docs/src/app/structure.ts:566-600`), and every in-repo consumer found by grep — 403 `[kbq-icon]` call sites under `packages/components` and 1 607 across `packages/`, 180 `kbq-icon-button` sites, 144 `kbq-icon-item` sites, 7 `KbqIcon` content queries and 29 `.kbq-icon.kbq-empty` style rules in 18 packages. Consumer evidence is what upgraded ICN-ARCH-01 and ICN-CSS-01 from design opinions to confirmed defects: in both cases the workaround already exists in the tree, written independently, with a load-bearing comment explaining why. Git history (66 commits touching the package; the last 18 inspected) supplied the flake context for ICN-TEST-01 and the DS-5338 deprecation state for ICN-STYLE-01.

Refuted during verification:
- **"`.kbq-icon.kbq-empty` is dead code — no source assigns `kbq-empty`"** — refuted. The class is computed at runtime: `KbqColorDirective`'s constructor assigns `this.color = KbqComponentColors.Empty` and the setter writes `classList.add('kbq-' + color)` (`core/common-behaviors/color.ts:57-71`), so every icon that has not been given an explicit `[color]` carries `kbq-empty`. That is why a grep for the literal string finds nothing while 29 rules in 18 packages select on it. The idiom is load-bearing — it lets a consumer colour default icons without overriding an explicitly-coloured one — and must survive the ICN-CSS-01 token move.
- **"`KbqIconItem` is dead weight and should be removed"** — refuted. It has 144 in-repo call sites, is projected by `alert` (`alert.component.html:3`), injected by `empty-state` (`empty-state.component.ts:22`), queried by `alert.component.ts:100`, and backs four published docs examples. What *is* dead is `badge.component.ts:129`'s `contentChild(KbqIconItem)`, which is never read anywhere in the class or its template — that is already filed against the badge package as BDG-API-02 in `docs/review/REVIEW.badge.md`, not against `icon`.
- **"Fetched SVG text is written to `innerHTML` unsanitized — XSS"** — refuted as filed. `svgElementFromText` does assign `div.innerHTML = text` (`icon-registry.ts:298-300`), but every caller that can carry attacker-influenced content sanitizes first: literals at `:71`, inline `<`-prefixed names at `:115`, resolver results at `:148`. The remaining path — content fetched from a URL (`:191, 268`) — is reached only through a `SafeResourceUrl` that was itself sanitized under `SecurityContext.RESOURCE_URL` (`:254, 326`), i.e. an origin the application developer explicitly trusted. This matches the `MatIconRegistry` contract exactly. Worth documenting as a stated trust boundary, not worth a finding.
- **"`OnPush` plus imperative DOM writes means the injected SVG never appears"** — refuted. Both the `next` and `error` branches call `changeDetectorRef.markForCheck()` (`icon.component.ts:145, 151`), and the SVG is inserted directly rather than through a template binding, so it does not depend on a check running at all. The genuine lifecycle defect is the terminated subscription (ICN-BUG-01), which is unrelated to change detection.
- **"The `[class]` host binding clobbers classes written by `KbqColorDirective` and by consumers"** — refuted for the case that is actually covered. `icon-button.component.spec.ts:29-41` adds `custom-class` via `classList` and asserts it survives a `[color]` change, and it passes. The binding and the directive write disjoint class sets in practice. The residual risk — a `[color]` change removing `kbq-error` while `'[class.kbq-error]': '… || hasError'` (`icon.component.ts:31`) still believes it owns the class — requires `autoColor` and a dynamic `[color]` on the same element, a combination that occurs nowhere in the repo, so it is noted here rather than filed.

Corrected on verification:
- **ICN-BUG-01** was initially drafted as "the SVG stream dies after a missing icon, affecting apps that use the registry". Tracing `providedIn: 'root'` on `KbqIconRegistry` and the `ReplaySubject` replay order showed the termination happens in *every* application that follows the documented font-icon default, before the first paint — which is what pulled in the stale-`max-height` consequence and moved the finding from P2 to P1.
- **ICN-ARCH-01** was initially two candidates ("subclasses over-match `.kbq-icon` selectors" and "content queries miss icon buttons"). Reading `schematics/.../data.ts:26-35` showed both are the same root cause seen from two sides — host metadata is inherited, DI tokens are not — so they were merged, and the severity settled at P2 because each individual consequence is cosmetic even though the pattern is systemic.
- **ICN-DOC-01** was initially "the Russian guide omits `provideHttpClient()`". Re-reading the English file showed the sprite snippet omits it too, in both languages, so the finding widened from a translation drift to three broken snippets and rose to P1.
