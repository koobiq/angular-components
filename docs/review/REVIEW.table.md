# Koobiq `table` Component — Code Review & Improvement Plan

> Scope: `packages/components/table` (component + cell directive, tokens, theme, SCSS, e2e fixture + Playwright spec, both user guides, examples stubs, API guard report), plus the five docs examples, the dev app, and every in-repo consumer of `kbq-table` · Commit `b665e503` · 2026-08-28
> Generated by a multi-dimension review (architecture, correctness, accessibility, performance, public API/types, styles, tests, docs) with manual verification of every finding against the source, the compiled `dist` bundle, Angular's own selector parser, the design-token files and the in-repo consumers. 10 findings confirmed (P0×0, P1×1, P2×5, P3×4); 5 candidate findings refuted during verification (see Appendix A). This document is a review + roadmap; no source is modified by it.

---

## 1. Executive Summary

`table` is not a data grid and does not wrap the CDK table. It is a **styling layer over a native `<table>`**: a 40-line file holding a component whose selector is the attribute `table[kbq-table]` (`table.component.ts:13`) and whose template is a bare `<ng-content />`, three boolean signal inputs that toggle three host classes, and a second directive meant to shrink the padding of cells that contain a button. All behaviour lives in 83 lines of SCSS and a 64-line theme mixin. Its guide says so explicitly: "Only standard HTML table capabilities are available" (`table.en.md:1`). That is a defensible, low-ambition design, and most of what the package does it does correctly.

- **The one genuine bug is in the only piece of TypeScript logic the package has.** `KbqTableCellContent` declares `selector: 'kbq-table td'` (`table.component.ts:33`). Angular's selector grammar has no descendant combinator: `CssSelector.parse('kbq-table td')` returns a single selector whose element is `td` — the second tag simply overwrites the first. The directive therefore matches **every `<td>` in every template that imports `KbqTableModule`**, not the cells of a `kbq-table`, and the `kbq-table` element it names has never existed anywhere in the repository. The intended scoping is absent, and it has been absent since the package's first commit (`1365df2d2`, DS-1820) (TBL-BUG-01).
- **The package is the only one of 63 component packages with no Jest spec at all.** Its entire automated verification is one Playwright test producing two screenshots (`e2e.playwright-spec.ts:8-16`). The two most recent feature commits — `stickyHeader` (`c36b56a81`) and `disableHover` (`8a4ef8dd3`) — each added docs, an example, an e2e fixture row, new baselines and an API-guard update, and neither added a unit test. A ten-line spec asserting that `KbqTableCellContent` does *not* match a `<td>` outside a `kbq-table` would have caught TBL-BUG-01 two years ago (TBL-TEST-01).
- **The token set is size-only, so nothing themable can be retargeted.** `table-tokens.scss` declares three size custom properties and no colours (`table-tokens.scss:1-5`); every colour is a direct global-token reference inside the theme mixin. The visible consequence: the sticky header hardcodes `var(--kbq-background-bg)` (`_table-theme.scss:32`), the *page* background. In dark theme that is `oklch(20.0% …)` while `--kbq-background-card` — what modals and sidepanels actually use — is `oklch(25.1% …)`, so a sticky-header table on any card surface paints a visibly darker band and offers no token to fix it (TBL-CSS-01).
- **The hover highlight is painted per-`<td>`, not per-row, and a consumer has already tripped over it.** `_table-theme.scss:24-25` targets `tr:hover td`, so a body row led by a `<th>` — a shape the package explicitly styles elsewhere (`_table-theme.scss:15-17, 57-58`) — is highlighted only from the second cell on. The docs app tries to switch the highlight off for API tables with `.kbq-docs-table.kbq-table > tbody > tr:hover { background: none }` (`component-viewer.scss:282-284`); because the colour is on the cell, that override does nothing at all (TBL-CSS-02).
- **Nothing on the public surface is documented.** Every member in `table.api.md` carries `// @public (undocumented)`, and the guide names `disableHover` and `stickyHeader` in prose but never names `border` — the reader has to open the example to discover the input exists (TBL-DOC-01).

Genuine strengths worth preserving: the inputs are already modern (`input(false, { transform: booleanAttribute })`, `table.component.ts:27-29`) with `OnPush`, standalone, a host object and no `@HostBinding` anywhere; there is no runtime state, no subscription and no lifecycle hook, so there is nothing to leak; the attribute selector on a native `<table>` means the component inherits full table semantics from the platform for free rather than reinventing them with ARIA; the size tokens mirror the values shipped by `@koobiq/design-tokens` exactly (`css-tokens.css:19, 1355-1356`); both guides are complete and mirrored, with five live examples; and the Playwright fixture is unusually thorough for a styling package — eight table variants covering first/middle/last row hover, borders, multiline cells, `disableHover` and a scrolled sticky header, in light and dark.

## 3. Prioritized Findings (deduplicated, verified)

### P0 — Release blockers

None.

### P1 — High

**TBL-BUG-01 · `KbqTableCellContent`'s selector is not a valid Angular selector; it degrades to `td` and matches every cell in scope** — `table.component.ts:32-40`, `tools/public_api_guard/components/table.api.md:31`, `table.scss:34-37`, `table.module.ts:10-15`, `dist/components/fesm2022/koobiq-components-table.mjs:30`.
The directive is declared `selector: 'kbq-table td'` with a host binding `'[class.kbq-table-cell_has-button]': '!!button()'` and a `contentChild(KbqButton)` query. Angular's directive selector grammar supports element names, attributes, classes and `:not(…)` — it has **no combinators**. Its parser walks the selector left to right and calls `setElement()` for each bare tag it finds, so the second tag overwrites the first: `CssSelector.parse('kbq-table td')` (from the workspace's own `@angular/compiler`) returns exactly one selector, `{ element: 'td', classNames: [], attrs: [] }`. The effective selector is `td`. Two consequences follow. First, the scoping the author wrote does not exist: any component that imports `KbqTableModule` gets a directive instance plus a live content query on **every** `<td>` in its template, including tables that have nothing to do with `kbq-table` — thirteen in-repo call sites import the module today (`docs-examples/components/{badge,filesize-formatter,highlight,number-formatter,skeleton,table,tooltip}`, `components-dev/{checkbox,table,typography}`, `apps/docs` token viewers). Second, the `kbq-table` *element* the selector names has never existed: `grep -rn "<kbq-table"` across `packages/` and `apps/` returns nothing, because the component is an attribute on a native `<table>` (`table.component.ts:13`). The behaviour appears to work only by accident — the CSS rule is scoped `.kbq-table .kbq-table-cell_has-button` (`table.scss:34`), so the over-matching is invisible until someone puts a `kbq-button` in a plain `<td>` inside a `.kbq-table` subtree. It also means the padding fix is unreachable for anyone following the repo's own "always use standalone components over NgModules" rule: `imports: [KbqTable]` never pulls `KbqTableCellContent` in, and nothing in the class or the guide says it must be imported separately. The published API report reproduces the meaningless string verbatim (`table.api.md:31`). Finally, this one CSS class is the sole reason `@koobiq/components/table` — a 9 KB bundle whose entire job is styling — statically imports `@koobiq/components/button` (`table.component.ts:10`, `dist/…/koobiq-components-table.mjs:3`), which in turn depends on `checkbox`, `dropdown`, `icon`, `title` and `core`.
**Fix:** delete the directive and express the rule in CSS, which is what it always was. `KbqButtonCssStyler` binds `.kbq-button` / `.kbq-button-icon` on the button host (`button/button.component.ts:132-136`), so `.kbq-table > tbody > tr > td:has(.kbq-button, .kbq-button-icon)` reproduces the current semantics exactly (the existing query is `descendants: true`, so keep the descendant form); `:has()` is already used in `accordion`, `app-switcher`, `button` and `button-toggle` SCSS, so there is no new browser-support question. That removes the malformed selector, the per-cell directive instances and the `button` dependency in one edit. If a directive must be kept for some API reason, the only correct spelling is `selector: 'td'` plus `inject(KbqTable, { optional: true })` and an early return when it is `null` — but then it is a removal candidate anyway. Removing an exported class is breaking: pair it with an `ng-update` migration that strips `KbqTableCellContent` from consumer `imports` arrays (see `project_breaking_changes_need_migration_schematics`), and re-run `build:components` + `approve-api`. Guard it with the first two cases of the new spec (TBL-TEST-01): a `<td>` with a `kbq-button` inside a `kbq-table` gains `kbq-table-cell_has-button`; a `<td>` in a plain `<table>` in the same template does not.

### P2 — Should fix

**TBL-TEST-01 · No Jest spec at all — the only one of 63 component packages** — `packages/components/table/` (no `*.spec.ts`), `e2e.playwright-spec.ts:1-18`, `e2e.ts:6`.
Enumerating `packages/components/*/` and excluding `core` gives 63 component packages; every one of them has at least one top-level `*.spec.ts` except `table`. The whole automated surface is a single Playwright test that takes two screenshots (`e2e.playwright-spec.ts:8-16`); there is not one assertion about the three class bindings, the `booleanAttribute` coercion of the bare-attribute form the guide recommends (`table.en.md:19, 25`), or the cell directive. This is not an old package coasting on age: the last two feature commits each shipped a full support cast and skipped the spec — `c36b56a81` (`stickyHeader`, DS-4911) touched the theme, the SCSS, the e2e fixture, both guides, a new docs example, both baselines and `table.api.md`; `8a4ef8dd3` (`disableHover`, DS-5234) did the same. The gap is not only unit-level: the e2e fixture imports `KbqTableModule` and nothing else (`e2e.ts:6`), so no button is ever rendered in a cell and the `.kbq-table-cell_has-button` rule (`table.scss:34-37`) has **zero** coverage of any kind — which is precisely how TBL-BUG-01 survived from the first commit to today. Calibration note: a coverage gap is not by itself a user-visible defect, which is why this is P2 and not P1; it is listed first in P2 because it is the reason the P1 exists.
**Fix:** create `table.spec.ts` with a host that renders a bare `<table kbq-table>` and assert, at minimum: the default classes (`kbq-table` only, no modifier); each of `border`, `disableHover`, `stickyHeader` toggling its modifier class both as a property binding and as a bare attribute (the coercion path); and the two `KbqTableCellContent` cases from TBL-BUG-01. Name the host without the `Kbq` prefix, per repo convention. Add a ninth block to `e2e.ts` importing `KbqButtonModule` with one row whose last cell holds a `kbq-button` and one whose cell holds text, so the reduced padding is visible in the baseline — regenerate through `yarn run e2e:docker:update-snapshots` only. Include a mutation check in review: reverting `'[class.kbq-table_disable-hover]'` to a constant must fail at least one case, or the suite is decoration.

**TBL-CSS-01 · The token set carries no colour or radius tokens, so the sticky header paints the page background on card surfaces and cannot be retargeted** — `table-tokens.scss:1-5`, `_table-theme.scss:31-33`, `table.scss:60-68`; tokens `css-tokens-dark.css:6, 10`, `css-tokens.css:1284, 1294`.
`table-tokens.scss` declares three custom properties, all sizes. Every colour in `_table-theme.scss` is a raw global-token reference — `--kbq-foreground-contrast-secondary` (`:6`), `--kbq-line-contrast-less` (`:9, 39`), `--kbq-foreground-contrast` (`:17`), `--kbq-states-background-transparent-hover` (`:26`), `--kbq-background-bg` (`:32`) — so a consumer cannot retheme any of them through the token layer the library otherwise offers. Compare the sibling convention: `link-tokens.scss:9-20` splits its file with a `/* THEME TOKENS */` marker and routes every colour through a `--kbq-link-*` token, and the library's own *second* table implementation does the same — `markdown-tokens.scss:73-75` defines `--kbq-markdown-table-header`, `--kbq-markdown-table-body` and `--kbq-markdown-table-border` pointing at the exact same three globals this theme hardcodes. The concrete symptom is the sticky header: `_table-theme.scss:32` sets `background-color: var(--kbq-background-bg)`, the *page* background. Modals and sidepanels render on `--kbq-background-card` (`modal-tokens.scss:21`, `sidepanel-tokens.scss:21`). In light theme both are `oklch(100% …)` so the mismatch is invisible; in dark theme `--kbq-background-bg` is `oklch(20.0% 0.0150 270.0)` and `--kbq-background-card` is `oklch(25.1% 0.0187 269.0)` (`css-tokens-dark.css:6, 10`), so a sticky-header table inside a modal, sidepanel or card shows a visibly darker band where the header is — and a table inside a sidepanel is an in-repo pattern already (`docs-examples/components/skeleton/skeleton-in-sidepanel/skeleton-in-sidepanel-example.ts:58`). The same gap explains the corner radius: `table.scss:61-67` uses `var(--kbq-size-m)` — a **spacing** token worth 12px (`css-tokens.css:1294`) — where the design system ships `--kbq-size-border-radius: 8px` (`:1284`), and there is no `--kbq-table-…-border-radius` token to override either way.
**Fix:** add a `/* THEME TOKENS */` block to `table-tokens.scss` mirroring `link-tokens.scss`: `--kbq-table-header-text`, `--kbq-table-body-text`, `--kbq-table-border-color`, `--kbq-table-states-hover-background`, `--kbq-table-sticky-header-background` (default `var(--kbq-background-card)`, not `--kbq-background-bg` — a table that is not on a surface will look identical in light and can be pinned by the consumer in dark), and `--kbq-table-size-row-border-radius` defaulting to today's `var(--kbq-size-m)` so the change is inert. Rewrite `_table-theme.scss` to consume only `--kbq-table-*`. Verify with a new e2e block that places a sticky-header table inside a `--kbq-background-card` container — the dark baseline is the regression guard, and it must be produced in Docker.

**TBL-CSS-02 · Row hover and corner radii are painted on `<td>` only, so row headers break and consumer overrides are silently dead** — `_table-theme.scss:22-29`, `table.scss:58-79`; consumer `apps/docs/src/app/components/component-viewer/component-viewer.scss:277-285`.
The hover rule is `&.kbq-hovered td, &:hover td { background-color: … }` (`_table-theme.scss:24-26`) and the pill radii are `> td:first-child` / `> td:last-child` (`table.scss:60, 65`) — cell-level, and `td`-only. But the package explicitly supports `<th>` inside `<tbody>`: it colours it (`_table-theme.scss:15-17`), unweights it (`:57-58`), pads it (`table.scss:12-13`) and borders it in the `bordered` variant (`:50-51`). A row led by a row header therefore highlights from its second cell onward and gets no left radius — the highlight visibly starts a cell late. The second consequence has already been paid in this repository: the docs app disables the highlight for its generated API tables with `.kbq-docs-table.kbq-table > tbody > tr:hover { background: none; }` (`component-viewer.scss:282-284`), which targets the **row's** background while the component paints the **cell's**, so the rule is a no-op and those tables still highlight. That is a consumer discovering the wrong mental model — "hover is a row state" — and being silently punished for it, which is the strongest kind of evidence that the surface is misleading. Note the bordered branch already gets this right: `_table-theme.scss:37-38` and `table.scss:50-51` both list `th, td`.
**Fix:** replace `td` with `:is(td, th)` in the hover rule (`_table-theme.scss:24-25`) and in the four radius rules (`table.scss:60, 65, 71, 75`) so a row is highlighted and rounded as a unit regardless of its leading cell type. Add an e2e row with a `<th scope="row">` first cell in both the hovered and the non-hovered state. Once TBL-CSS-01 lands, the docs app should switch `component-viewer.scss:282-284` to `disableHover` on the generated markup or to setting `--kbq-table-states-hover-background: transparent`; deleting that dead rule is the acceptance criterion, not just the theme diff.

**TBL-A11Y-01 · The sticky header can obscure focused content in a scrolled row** — `table.scss:40-46`, `_table-theme.scss:31-33`; no `scroll-margin`/`scroll-padding` anywhere in `packages/` or `apps/`.
`stickyHeader` pins `thead > tr > th` with `position: sticky; top: 0; z-index: 1` and gives it an opaque background. Nothing in the package sets `scroll-margin-block-start` on body rows or asks the scroll container for `scroll-padding-block-start` — a repo-wide grep for `scroll-margin|scroll-padding` in `.scss` returns zero hits. When a keyboard user tabs to a control in a row just below the fold, the browser scrolls it to the container edge, where the opaque sticky header covers it. That is WCAG 2.2 SC 2.4.11 *Focus Not Obscured (Minimum)*, Level AA — inside the AA bar AGENTS.md states as a mandate. Focusable cell content is a first-class shape here, not a hypothetical: the package ships a whole directive whose only purpose is to adjust the padding of cells containing a button (TBL-BUG-01), and the dev app puts `<button kbq-button>` in cells twice (`components-dev/table/template.html:17, 58`). Be precise about the claim: this is a WCAG judgement, not an automated failure — axe-core has no rule for obscured focus, which is why the existing tooling is silent. The docs example's own scroll container (`table-sticky-header-example.ts:14`) reproduces the geometry.
**Fix:** two layers. (1) Document it: the guide's `stickyHeader` section should tell the consumer to put `scroll-padding-block-start` on their scroll container. (2) Make the default correct: when `stickyHeader()` is set, observe the `thead` with CDK's `SharedResizeObserver` — already used in `actions-panel`, `clamped-text`, `code-block` and `core/overflow-shadow` — and write its height to `--kbq-table-size-sticky-header-height` on the host, then add `.kbq-table_sticky-header > tbody > tr > :is(td, th) { scroll-margin-block-start: var(--kbq-table-size-sticky-header-height, 0px); }`. Cover it with a Playwright assertion rather than a screenshot: focus the first control below the fold, then assert its bounding box top is greater than or equal to the sticky header's bottom.

**TBL-DOC-01 · Nothing on the public surface is documented, and `border` is named in neither guide** — `tools/public_api_guard/components/table.api.md:12-34`, `table.component.ts:26-30, 38-39`, `table.en.md:9-15`, `table.ru.md:9-15`.
Every entry in the API report is `// @public (undocumented)` — the two classes, the module, all three inputs and the `button` query. `structure.ts:954-955` sets `hasApi: true, apiId: 'table'`, so the docs site renders an API tab built from those `.d.ts` comments: three input rows with empty descriptions. The guide only partially compensates. It names `disableHover` in prose and explains when to use it (`table.en.md:19`) and does the same for `stickyHeader` (`:25`), but the "Borders" section (`:9-15`) discusses *when* borders are appropriate for two paragraphs and never names the input that produces them — a reader has to open `table-with-borders-example.ts:13` to learn it is `[border]`. The name is also the odd one out in its own package: the input is `border` while the class it toggles is `kbq-table_bordered` (`table.component.ts:20`), and `border` is additionally the name of the obsolete presentational attribute on `<table>`, so `bordered` would read better on both counts. `table.ru.md` carries the identical gap at the identical lines, so there is no correct version to fall back on.
**Fix:** add `/** */` blocks to `KbqTable`, `KbqTableModule` and all three inputs, each stating the modifier class it toggles and its `false` default; name `border` in prose in both guides ("Use `border` to draw a line under every row"). Be aware of the ordering hazard: adding JSDoc to a public member removes its `(undocumented)` marker and therefore changes `table.api.md`, so the `api` job fails until `approve-api` is re-run after `build:components` (see `project_jsdoc_on_public_member_changes_api_md`) — fold this into the same rebuild cycle as TBL-BUG-01 so the report churns once. If `border` is renamed to `bordered`, it is breaking and needs an `ng-update` migration.

### P3 — Nice to have / hygiene

**TBL-ARCH-01 · The NgModule imports two CDK modules the package never uses** — `table.module.ts:1-2, 6-17`.
`KbqTableModule` imports `A11yModule` and `PlatformModule`. Neither appears anywhere else in the package — there is no `cdkTrapFocus`, no `cdkMonitorElementFocus`, no `cdkAriaLive`, no `Platform` injection in `table.component.ts`, and neither module is re-exported, so consumers do not get their directives either. They are pure dead weight in the injector graph, carried since the package's first commit (`1365df2d2`). Verified against the compiled bundle: `dist/components/fesm2022/koobiq-components-table.mjs:44-50` still lists both in `ɵmod`/`ɵinj`.
**Fix:** drop both imports; `imports: [KbqTable, KbqTableCellContent]` (or just `[KbqTable]` after TBL-BUG-01) is sufficient. This changes `table.api.md:43`, so it belongs in the same `approve-api` cycle as TBL-DOC-01.

**TBL-ARCH-02 · The `.kbq-table` class contract is consumed without the component, but `ViewEncapsulation.None` styles exist only while an instance is alive** — `table.component.ts:15-17`; consumers `tools/api-gen/rendering/templates/property-list.template.html:4`, `method.template.html:17, 48`, `function.template.html:27`; mechanism `node_modules/@angular/platform-browser/fesm2022/dom_renderer.mjs:452-454, 785-795`.
The repo's own API-reference generator emits static HTML carrying `class="kbq-docs-table kbq-table kbq-table_bordered layout-fill"` — the table's visual contract consumed purely as CSS classes, with no `kbq-table` attribute and therefore no Angular component. That only works while the `.kbq-table` rules are actually in the document, and with `ViewEncapsulation.None` they are not global: Angular adds a component's styles when the renderer for that component type is first created (`dom_renderer.mjs:452-454`, `applyStyles()`) and removes them again when that renderer is destroyed under the default `removeStylesOnCompDestroy` (`:788-795`). There is no global stylesheet path either — the docs app's `main.scss:1-12` pulls in design tokens and app styles only, and `packages/components/_index.scss` forwards `core` alone. So the generated tables are styled exactly as long as some other live `KbqTable` instance keeps the styles resident. The point is the contract, not a specific broken route: the package publishes class names it cannot honour on its own, and neither guide documents them as a supported surface.
**Fix:** decide which contract is real. Either document `.kbq-table` / `.kbq-table_bordered` / `.kbq-table_sticky-header` / `.kbq-table_disable-hover` as a public CSS API and expose the styles through a `@mixin kbq-table-styles()` a global stylesheet can include (the theme file already has the mixin shape), or change the api-gen templates to render an Angular `<table kbq-table [border]="true">`. Verify by loading a docs API tab that renders no other table and confirming the header border and cell padding are present.

**TBL-STYLE-01 · Physical properties block RTL, and `<tfoot>` is laid out but never themed** — `table.scss:10, 14-22, 60-68`, `_table-theme.scss:4-20, 46-63`.
Three small style-surface issues. (1) Every directional value is physical: `text-align: left` (`table.scss:22`), `padding-right`/`padding-left` (`:16, 18`), and the four `border-*-*-radius` longhands (`:61-67`). The library is not RTL-agnostic — `accordion.ts:67` and `app-switcher.ts:332` inject `Directionality`, and `core/forms/_forms.scss:24, 58` already uses `text-align: start` — so a `kbq-table` under `dir="rtl"` left-aligns its text and rounds the wrong corners. `text-align: start` and `padding-inline`/`border-start-start-radius` are drop-in replacements. (2) `text-align: left` is emitted at specificity (0,1,3) (`.kbq-table > thead > tr > th`), so a consumer centring a column with a single class loses and has to escalate; routing alignment through a `--kbq-table-cell-text-align` token would avoid that. (3) `table.scss:10` lays out `> tfoot` with the same padding and alignment as the other sections, but neither the theme mixin nor the typography mixin mentions `tfoot` (`_table-theme.scss:5, 13, 48, 56` cover `thead` and `tbody` only), so a footer row gets library spacing with browser-default colour and typography — a half-supported element. No `<tfoot>` exists anywhere in the repo today, so this is cheap to fix now and expensive to discover later.
**Fix:** swap the physical properties for logical ones; add `tfoot` to the two mixins or drop it from `table.scss:10` and say the element is unsupported. Extend the e2e fixture with a `dir="rtl"` block and a `<tfoot>` block.

**TBL-DOC-02 · Dead examples stubs, Russian-only examples embedded in the English guide, and an unused field in the overview example** — `examples.table.en.md:1-5`, `examples.table.ru.md:1-5`, `apps/docs/src/app/structure.ts:946-957`, `docs-examples/components/table/table-overview/table-overview-example.ts:2, 59`.
Three docs-layer nits. (1) Both `examples.table.*.md` carry the standard "🚧 Documentation in progress 🚧" stub, but `structure.ts:956` sets `hasExamples: false`, so the Examples tab never renders for `table` and the files are unreachable — two dead files that keep surfacing in "in progress" greps, not a broken user surface. (2) Four of the five examples are Russian-only — `table-overview-example.ts:17-51` ("Клиент", "Значение", "Зарегистрирован"), `table-full-width-example.html:4-34`, `table-with-borders-example.ts:16-46`, and the date column of `table-disable-hover-example.ts:34-37` — yet `table.en.md` embeds all of them, so an English reader gets a fully Russian overview. This is a repo-wide pattern (169 of 670 example files contain Cyrillic), which is why it is P3 rather than higher, but `table` is one of the worse instances: only `table-sticky-header` is language-neutral. (3) `table-overview-example.ts:59` declares `protected readonly colors = KbqComponentColors;` and `:2` imports it, but the template no longer contains a button — dead code left behind when the example was simplified.
**Fix:** delete both stub files (the guide already embeds all five examples inline, so nothing is lost) or populate them and flip `hasExamples: true` — deleting matches what `structure.ts:956` already declares. Give the four Russian examples neutral, translatable content the way `table-sticky-header-example.ts:45-54` does. Drop the unused `colors` field and its import.

## 4. Recommended Remediation Phases

**Phase 1 — Make the one piece of logic honest, and stand up a spec.**
IDs: TBL-BUG-01, TBL-TEST-01. Create `table.spec.ts` first, with the two `KbqTableCellContent` scoping cases written against the *intended* behaviour so they fail; then replace the directive with the `:has()` rule and watch them pass. That ordering is what turns the fix from an assertion into a demonstration. The removal is breaking, so it carries an `ng-update` migration and one `build:components` + `approve-api` cycle; it also drops the `@koobiq/components/button` edge from the entry point.

**Phase 2 — Fix what the eye sees.**
IDs: TBL-CSS-01, TBL-CSS-02, TBL-A11Y-01. Introduce the theme-token block and move every colour behind it (defaulting the sticky background to the card surface), widen the hover and radius rules from `td` to `:is(td, th)`, and add the sticky-header `scroll-margin` plus its documentation. All three are visual and share one Docker baseline regeneration, so they should land together. The acceptance criterion for TBL-CSS-02 is the deletion of `component-viewer.scss:282-284`, not the theme diff.

**Phase 3 — Document the surface.**
IDs: TBL-DOC-01, TBL-ARCH-01, TBL-DOC-02. Add JSDoc to every public member, name `border` in both guides, drop the two unused CDK module imports, resolve the dead example stubs and de-localise the four Russian examples. The JSDoc and the module-imports change both move `table.api.md`, so run them through a single `build:components` + `approve-api`.

**Phase 4 — Direction, footers and the class contract.**
IDs: TBL-STYLE-01, TBL-ARCH-02. Swap physical properties for logical ones, decide whether `<tfoot>` is supported and finish or remove it, and settle whether the CSS class names are a public API — this last one is a cross-team decision with `apps/docs` and `tools/api-gen`, which is why it sits last rather than because it is unimportant.

## Appendix A — Review Methodology

The package is small enough to read exhaustively, so every file was read in full (`table.component.ts`, `table.module.ts`, `public-api.ts`, `index.ts`, `ng-package.json`, `table.scss`, `table-tokens.scss`, `_table-theme.scss`, `e2e.ts`, `e2e.playwright-spec.ts`, both guides, both example stubs). Candidates were then cross-checked against five independent sources: the compiled output in `dist/components/fesm2022/koobiq-components-table.mjs` (which confirmed what the partial-compilation declaration actually carries); Angular's own selector parser, invoked directly on the workspace's `@angular/compiler` to settle TBL-BUG-01 rather than reasoning about it; the design-token files under `@koobiq/design-tokens/web/new/` for every `var()` the theme consumes; the API guard report and `tools/api-extractor/config.json`; and every in-repo consumer of `kbq-table` found by grep across `packages/`, `apps/` and `tools/` (16 template call sites plus the four api-gen HTML templates). Consumer evidence is what upgraded TBL-CSS-02 from a style opinion to a confirmed defect — the workaround is already in the tree and already broken. Structure-file completeness was checked against AGENTS.md: `table` has tokens, theme, module, `public-api.ts` and the e2e pair, and is missing only the spec.

Refuted during verification:
- **"`KbqTableCellContent` never matches, so `.kbq-table-cell_has-button` is dead CSS"** — refuted, and inverted. This was the first reading: `<kbq-table>` does not exist anywhere in the repo, so a selector rooted at it looked unreachable. Running `CssSelector.parse('kbq-table td')` showed the selector collapses to `td`, so the directive matches *more* than intended, not less, and the class is applied correctly in the common case. See "Corrected on verification" below.
- **"`--kbq-table-size-row-padding-vertical: 10px` is a magic number that should be a token"** — refuted. `10px` is the value `@koobiq/design-tokens` itself publishes for that token (`web/new/css-tokens.css:19`, mirrored in `web/deprecated/css/components/table/table.css:6`), so the local declaration reproduces the design source rather than inventing a value. The genuine token gap is the absence of *colour* tokens, filed as TBL-CSS-01.
- **"`stickyHeader` silently requires the consumer to supply a scroll container, which the guide never mentions"** — refuted. `position: sticky` resolves against the nearest scrolling ancestor, which may be the document, so the behaviour the guide describes ("keep the column names visible while you scroll down", `table.en.md:25`) works with no wrapper at all. The wrapper in `table-sticky-header-example.ts:14` is one valid arrangement, not a precondition. The real sticky-header defect is the focus obscuring in TBL-A11Y-01.
- **"`.kbq-hovered` in the theme is a test-only hook leaking into production CSS"** — refuted. `KbqHover` is a real directive (`core/common-behaviors/hover.ts:11-18`) that binds the class from live `mouseenter`/`mouseleave`, and the same `.kbq-hovered` pairing appears in the `link`, `icon`, `file-upload` and `option` themes. The table is following a library-wide convention, and it is what lets the Playwright fixture capture hover states deterministically.
- **"Missing `role`/`scope`/`<caption>` is an AXE failure and therefore a P0 under AGENTS.md"** — refuted as an automated failure. A native `<table>` carries the implicit `table` role, and assistive technology infers column headers from `thead > th` for simple tables, so axe-core does not flag any of the five shipped examples (none of which, nor any table in the repo, uses `scope` or `<caption>`). Header association only becomes a WCAG 1.3.1 question for the complex tables the guide points at (`table.en.md:13`), and that is a documentation gap rather than a component defect.

Corrected on verification:
- **TBL-BUG-01** was drafted as "the cell directive never matches; its CSS rule is dead". Parsing the selector with Angular's own parser reversed the direction: the effective selector is `td`, so the finding became over-matching plus absent scoping plus an unreachable-when-standalone symbol. The severity stayed P1 but the fix changed completely — from "repair the selector" to "delete the directive and use `:has()`", which also removes the `@koobiq/components/button` dependency that was originally going to be filed separately as a performance finding.
- **TBL-TEST-01** was drafted as P1 on the strength of `table` being the only one of 63 component packages without a spec. It was recalibrated to P2 to stay consistent with the severity scale used across this review family — a coverage gap is not itself a user-visible defect — while keeping it first in the P2 list, since it is the mechanism by which the P1 survived from the first commit.
- **TBL-CSS-01** was drafted as "the sticky header uses the wrong background token". Reading `table-tokens.scss` against `link-tokens.scss` and `markdown-tokens.scss` showed the wrong token is a symptom of a structural gap — the package has no colour tokens at all, unlike the library's own second table implementation — so the finding was widened and the fix now delivers an override path rather than a one-line swap.
