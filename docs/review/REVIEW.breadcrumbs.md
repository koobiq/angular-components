## 1. Executive Summary

`KbqBreadcrumbs` is the library's navigation-trail component: 324 lines of TypeScript across five exported classes, an 84-line template, a 222-line stylesheet, and a vendored copy of Radix's roving-focus directive pair (`roving-focus-group.directive.ts`, `roving-focus-item.directive.ts`, `utils.ts` — 339 lines together) that provides arrow-key navigation. It delegates overflow collapsing to `KbqOverflowItems` and item rendering to `KbqButton` + `KbqTitleDirective`, which is the right architecture. There are **no release blockers** — the component renders and navigates — but for a component whose entire purpose is a *navigation landmark*, the accessibility surface is where it is weakest, and two published inputs do nothing at all.

- **The component announces itself as an unlocalized, unoverridable "breadcrumb".** The host writes `'[attr.aria-label]': "'breadcrumb'"` (`breadcrumbs.ts:176`) — a hardcoded English literal, in a library whose ARIA defaults are mandated to come from `kbqInjectA11yLocaleConfiguration()` (AGENTS.md), whose default locale is `ru-RU` (`core/locales/a11y.ts:11`), and which the same file already uses correctly one line away for the expand button (`breadcrumbs.html:23`). Because it is a *binding*, it also overwrites any `aria-label` the consumer authored on the host, so two breadcrumb trails on one page are two identically named landmarks with no way to tell them apart. Separately, the element form `<kbq-breadcrumbs>` ships no `role` at all: **all 21 non-spec call sites in the repository write `<nav kbq-breadcrumbs>`**, and the element form appears only in the Jest spec (BCR-A11Y-01).
- **The separator is read aloud.** The default separator is `<i kbq-icon="" class="kbq-breadcrumb__separator">&nbsp;/&nbsp;</i>` (`breadcrumbs.html:82`) — literal text, no `aria-hidden`. A screen reader reads "Main slash Standards slash Advanced Encryption Standard slash Edit". The repo convention is unambiguous the other way: `aria-hidden="true"` on decorative icons in `app-switcher` and `filter-bar`, and on every SVG the icon registry injects (`icon-registry.ts:287, 312`). There is also no list structure, so users get no "item 2 of 4" position information (BCR-A11Y-02).
- **`KbqBreadcrumbs.disabled` is published, documented ("When disabled, user interactions are blocked") and never read.** It appears in the API report (`breadcrumbs.api.md:52`) and nowhere else — not in the template, not in the stylesheet, not in the class (BCR-API-01). `KbqBreadcrumbItem.current` is the same story one level down, complete with a matching dead `.kbq-breadcrumb_current` rule in the theme mixin (BCR-API-02).
- **The roving-focus group is a `tabindex="0"` element with `outline: none` welded on inline.** `style: 'outline: none;'` in the host object (`roving-focus-group.directive.ts:14`) cannot be overridden from a stylesheet, and the entry handler bails out for mouse-origin focus and after a Shift+Tab, so focus can sit invisibly on the `<nav>` (WCAG 2.4.7). The `isTabbingBackOut` latch that gates it is reset from a `(blur)` host listener — but `blur` does not bubble in Angular, unlike React's `onBlur` in the code this was ported from (BCR-A11Y-03).
- **`firstItemNegativeMargin` — which the guide devotes a whole section to — is inert in two of the three wrap modes**, because the CSS hangs off `.kbq-overflow-items`, a wrapper only the `auto` branch renders. `breadcrumbs-with-wrap-example.ts:12` already binds `[firstItemNegativeMargin]="false"` on a `wrapMode="wrap"` nav: a no-op written by someone who believed it mattered (BCR-CSS-01).

Genuine strengths worth preserving: the overflow machinery is properly delegated rather than reimplemented — `KbqOverflowItems` owns the `SharedResizeObserver` and the debounce, and `enforceMaxVisible()` layers the `max` limit on top of it with correct restore semantics (`breadcrumbs.ts:281-323`), covered by four focused `fakeAsync` specs. Everything is standalone, `OnPush`, signal-based, host-object-bound, with `takeUntilDestroyed()` on the one long-lived subscription. The customization surface (`kbqBreadcrumbsSeparator`, `kbqBreadcrumbView`, `kbqBreadcrumbsConfigurationProvider`) is genuinely flexible, and twelve live examples exercise it. The Jest spec's comments about what jsdom cannot measure (`breadcrumbs.spec.ts:134-137, 237-238`) are the kind of honesty that makes a suite trustworthy.

## 3. Prioritized Findings (deduplicated, verified)

### P0 — Release blockers

None.

### P1 — High

**BCR-A11Y-01 · The landmark name is a hardcoded English literal that overwrites the consumer's own, and the element form carries no role at all** — `breadcrumbs.ts:154, 169-177`; correct counter-example one file away at `breadcrumbs.html:23`; consumers: 21 `<nav kbq-breadcrumbs>` call sites, 3 `<kbq-breadcrumbs>` (all in the spec).
The host block ends with `'[attr.aria-label]': "'breadcrumb'"` (`breadcrumbs.ts:176`). Three things are wrong with that one line. (1) It is a hardcoded string in a library where AGENTS.md states "Source all component-provided default ARIA text from `kbqInjectA11yLocaleConfiguration()`" — and `KbqA11yLocaleConfiguration` (`core/locales/types.ts:13-37`) has no key for it, while the default locale factory returns `ruRULocaleData.a11y` (`core/locales/a11y.ts:11`), so a Russian application gets a Russian close button, a Russian expand button and an English landmark. The very same component already does this correctly for the expand button (`breadcrumbs.html:23`, added by `4b710125f`/DS-5385) — the host `aria-label` was simply missed in that pass. (2) It is a *binding*, not a static host attribute, so it is written during change detection and overwrites any `aria-label` the consumer authored on the same element. A page with a top-bar trail and an in-content trail therefore exposes two landmarks both named "breadcrumb", which is precisely the case ARIA landmark labelling exists to disambiguate; the consumer has no way out short of an `ngAfterViewInit` `setAttribute`. (3) The `<kbq-breadcrumbs>` element form (`breadcrumbs.ts:154`) has no `role`, so on that form the label is attached to an element with no accessible role — ignored by assistive technology at best, flagged by axe's `aria-prohibited-attr` at worst. The evidence that nobody trusts the element form is total: grepping the whole repository, **21 call sites write `<nav kbq-breadcrumbs>`** — all 12 docs examples, all 4 e2e fixtures, the top-bar e2e, the SSR dev fixture, the two top-bar docs examples and even one spec host — while `<kbq-breadcrumbs>` appears three times, exclusively inside `breadcrumbs.spec.ts`. Every author independently reached for the native landmark the component does not provide.
**Fix:** add a `breadcrumbs` (or `breadcrumbsLabel`) key to `KbqA11yLocaleConfiguration` and all five locale files, and change the host binding to `'[attr.aria-label]': 'ariaLabel() ?? a11yLocaleConfiguration().breadcrumbs'` behind a public `ariaLabel = input<string | null>(null)` so a consumer can name the trail; alternatively bind `null` when the host already carries an `aria-label`/`aria-labelledby`. Add `'[attr.role]': "isNav ? null : 'navigation'"`, computed once in the constructor from `elementRef.nativeElement.tagName === 'NAV'`, so the element form is a landmark too and the attribute form does not double up on `<nav>`'s implicit role. Guard both with Jest cases asserting the resolved name follows a `kbqA11yLocaleConfigurationProvider` override and that a consumer-set `aria-label` survives, plus a `jest-axe` run over a two-trail fixture (see BCR-TEST-01).

**BCR-A11Y-02 · The `/` separator is announced as text, and the trail has no list semantics** — `breadcrumbs.html:78-84`, `breadcrumbs.scss:212-215`; repo convention at `app-switcher/app-switcher.html:4`, `filter-bar/filters.html:45, 61`, `icon/icon-registry.ts:287, 312`.
The fallback separator is `<i kbq-icon="" class="kbq-breadcrumb__separator" [color]="…">&nbsp;/&nbsp;</i>` — the slash is real text content in the DOM, and neither the template nor `KbqIcon`'s host block (`icon/icon.component.ts:28-32`) adds `aria-hidden`. A screen reader therefore reads the punctuation between every pair of items; on the SSR fixture's four-level trail that is four extra spoken "slash"es. This is not how the rest of the library treats decorative glyphs: `app-switcher` and `filter-bar` write `aria-hidden="true"` on their icons by hand, and `icon-registry.ts:287, 312` stamps it onto every SVG it injects — the separator escapes only because `kbq-icon=""` resolves no SVG and falls through to the text path. The `user-select: none` already applied to it (`breadcrumbs.scss:213`) shows the authors do consider it decorative; they just did not carry that through to ARIA. On top of that the trail is a flat row of `<div class="kbq-breadcrumb-item__container">` with no `<ol>`/`<li>` and no `role="list"`/`role="listitem"`, so there is no "list of 4 items, item 2 of 4" announcement — the WAI-ARIA APG breadcrumb pattern's other half. Note the current page is additionally rendered as `<a kbq-button>` with `[disabled]="item.disabled() || last"` (`breadcrumbs.html:69`), which `KbqButton` turns into `role="button" aria-disabled="true" tabindex="-1"` (`button/button.component.ts:327-329, 558-580`), so the item carrying `aria-current="page"` is announced as a disabled button rather than as the current location. This is a WCAG 1.3.1 judgement, not an automated axe failure — axe has no rule for un-hidden decorative text.
**Fix:** add `aria-hidden="true"` to the separator `<i>` at `breadcrumbs.html:82` and document the same requirement for custom `kbqBreadcrumbsSeparator` templates in both guides. Wrap the rendered items in `role="list"` on the flex container and `role="listitem"` on `.kbq-breadcrumb-item__container` (cheaper than restructuring to `<ol>`/`<li>`, and survives the `display: flex` layout that a real list would fight). For the current page, stop routing it through the button's disabled path: render it as a non-interactive `<span aria-current="page">` when `last && !item.customTemplateRef()`, which also removes the `role="button"` + `aria-disabled` pair. Cover with Jest assertions on `aria-hidden`, on the list roles, and on the current item's tag/role.

**BCR-A11Y-03 · The roving-focus host is focusable with `outline: none` welded on inline, and its focus-entry guard can leave focus parked there invisibly** — `roving-focus-group.directive.ts:6-15, 46-49, 51-54, 68-98, 100-103`.
The group host object sets `style: 'outline: none;'` (`:14`) — a static *inline* style, so no stylesheet can restore the focus ring without `!important` — while `[attr.tabindex]': 'tabIndex'` (`:8`) puts the same element in the tab order with `0` whenever it has at least one focusable item (`:47-49`). The design intends focus never to rest there: `handleFocus` (`:69-98`) immediately forwards to the first candidate. But it forwards only when `isKeyboardFocus && !this.isTabbingBackOut()`, and `isClickFocus` is set by the `(mousedown)` host listener (`:101-103`), so clicking the `<nav>`'s own padding — which every one of the four sizes has, via `.kbq-overflow-items { padding: 1px }` and the flex gap — focuses an element with a suppressed outline and no forwarding. Focus is then invisible (WCAG 2.4.7 Focus Visible, an AA criterion AGENTS.md mandates), and because `currentTabStopId` is still `null` at that point every roving item renders `tabindex="-1"` (`roving-focus-item.directive.ts:18, 71-73`), so the next Tab leaves the breadcrumbs entirely rather than entering them. The `isTabbingBackOut` latch that also gates the forward path compounds this: it is set by `onItemShiftTab()` (`:112-114`) and cleared only by `handleBlur()` (`:52-54`), which is wired to the host's `(blur)` — and `blur` does not bubble in Angular, unlike React's synthetic `onBlur` (backed by `focusout`) in the Radix code this is a port of. Once the user Shift+Tabs out of a breadcrumb, the group element itself never receives focus again (its `tabIndex` getter now returns `-1`), so nothing ever clears the latch for the lifetime of the component.
**Fix:** three independent changes, all small. (1) Drop `style: 'outline: none;'` from the host object and, if the ring is genuinely unwanted, move it to a stylesheet rule the consumer can override — or better, keep a visible ring, since the element is a real tab stop. (2) Bind `(focusout)` instead of `(blur)` for `handleBlur` so the latch clears when focus leaves the group by any route; `focusout` bubbles and is what the original relies on. (3) Make the entry forward unconditional on origin — a click on the container's padding should still land on a breadcrumb — or set `tabindex="-1"` on the group whenever `currentTabStopId` is `null` so it is never a keyboard-reachable dead end. Verify with a Playwright keyboard test (Tab in, Shift+Tab out, Tab in again — focus must return to a breadcrumb, not skip the trail) and a Jest case asserting the group's `tabindex` after a Shift+Tab followed by a `focusout`.

**BCR-API-01 · `KbqBreadcrumbs.disabled` is published, documented as blocking interaction, and never read** — `breadcrumbs.ts:203-207`; `tools/public_api_guard/components/breadcrumbs.api.md:52`.
`readonly disabled = input<boolean, unknown>(false, { transform: booleanAttribute })` carries the JSDoc "Indicates whether the breadcrumbs are disabled. When disabled, user interactions are blocked." Grepping the package for `disabled` returns exactly four other hits, all of them `KbqBreadcrumbItem.disabled` (`breadcrumbs.html:34, 66, 69`) or unrelated `--kbq-*-disabled-*` tokens in the stylesheet. `KbqBreadcrumbs.disabled` is referenced nowhere: not in the host block (which would be the natural place — a `kbq-disabled` class, or `aria-disabled`), not in the template, not in the SCSS, not in `enforceMaxVisible()`. A consumer who writes `<nav kbq-breadcrumbs [disabled]="isReadOnly">` gets no compile error (the input exists, so `strictTemplates` is satisfied), no visual change, and every link still clickable — the worst possible failure mode, because the binding *looks* honoured. The input is on the published surface (`breadcrumbs.api.md:52`) and the docs site renders it in the generated API tab, so the promise is user-facing. No in-repo call site binds it, which is why this has survived.
**Fix:** implement or delete, and say which in the changelog. Implementing is small and matches the JSDoc: add `'[class.kbq-disabled]': 'disabled()'` plus `'[attr.aria-disabled]': "disabled() || null"` to the host block, pass `disabled() || item.disabled() || last` into the rendered anchors' `[disabled]` at `breadcrumbs.html:69`, force `[focusable]="false"` at `:66`, and close/disable the expand dropdown trigger. Deleting is breaking and needs an `ng-update` migration stripping the attribute (see `project_breaking_changes_need_migration_schematics`). Either way add a Jest case that binds `[disabled]="true"` and asserts every rendered anchor is `aria-disabled` and no roving item is registered — the absence of exactly that case is why this shipped.

### P2 — Should fix

**BCR-CSS-01 · `firstItemNegativeMargin` — a documented, default-on behaviour — is inert in `wrap` and `none` modes and for short trails** — `breadcrumbs.scss:27-31`, `breadcrumbs.html:1-11`, `breadcrumbs.ts:50, 189-191`; no-op binding already in the tree at `docs-examples/.../breadcrumbs-with-wrap-example.ts:12`.
The rule is `&.kbq-breadcrumbs_first-item-negative-margin { .kbq-overflow-items { margin-left: var(--kbq-breadcrumb-item-negative-margin); } }` — the offset is applied to the `.kbq-overflow-items` wrapper, not to the host or the first item. That wrapper exists only in the `@else` branch of the template (`breadcrumbs.html:12`); the `@if` branch, taken whenever `allItems.length < minVisibleItems || wrapMode() !== 'auto'` (`:2`), emits `.kbq-breadcrumb-item__container` divs directly under the host with no wrapper at all. So with `wrapMode="wrap"` or `wrapMode="none"` — or with fewer than two items in any mode — the class lands on the host and matches nothing. The default is `true` (`breadcrumbs.ts:50`), so this is not an opt-in path: switching a working `auto` trail to `wrap` silently shifts the whole row right by `--kbq-breadcrumb-item-horizontal-padding` and breaks its alignment with the surrounding content, which is the entire point of the negative margin. The guide devotes a section to the property (`breadcrumbs.en.md:48-78`, `breadcrumbs.ru.md:48-78`) and never mentions the restriction. The proof that this misleads: `breadcrumbs-with-wrap-example.ts:12` writes `<nav wrapMode="wrap" kbq-breadcrumbs [firstItemNegativeMargin]="false">` — an explicit binding, on the one mode where the property does nothing, written by someone who thought it mattered. The SSR fixture (`components-dev/ssr/components/breadcrumbs.ts:22`) uses `wrapMode="none"` and is in the same position.
**Fix:** move the offset onto the host — `&.kbq-breadcrumbs_first-item-negative-margin { margin-left: var(--kbq-breadcrumb-item-negative-margin); }` — so it applies to both template branches, and verify the `auto` branch renders identically (the wrapper is the host's only flex child there, so the offset is equivalent). Then delete the no-op binding in `breadcrumbs-with-wrap-example.ts:12` or keep it and let it finally take effect — decide deliberately and re-baseline. Add an e2e row to `E2eBreadcrumbsStateAndStyle` pairing `firstItemNegativeMargin: true` with `wrapMode: 'wrap'`; the current state matrix (`e2e.ts:106-132`) sets `firstItemNegativeMargin: false` on every single row, which is why no screenshot covers this.

**BCR-BUG-01 · The collapsed-items dropdown rebuilds each hidden breadcrumb from `text()` alone, discarding the custom template, the destination and the current state** — `breadcrumbs.html:31-39`, `breadcrumbs.ts:126-151`; affected examples `breadcrumbs-with-auto-wrap-adaptive-example.ts:68-72`, `breadcrumbs-dropdown-example.ts:43-50`, `e2e.ts:75-82`.
When items overflow, the hidden ones are re-rendered inside the expand dropdown as `<a kbq-dropdown-item [routerLink]="item.routerLink?.urlTree" [disabled]="item.disabled()">{{ item.text() }}</a>`. Three pieces of the item are dropped on that path. (1) `item.customTemplateRef()` is ignored entirely, so an item authored with `*kbqBreadcrumbView` — an icon, a nested dropdown trigger, a truncated label — collapses into a plain text row. (2) `text` is optional with an `undefined!` default (`breadcrumbs.ts:131`, reported as `InputSignal<string>` at `breadcrumbs.api.md:39`), and the dropdown is the *only* place it is ever rendered, so a custom-view item authored without `text` becomes a blank, unlabelled interactive row. The repo has two such items — `breadcrumbs-dropdown-example.ts:43` and `e2e.ts:75` — which escape only because both happen to be last and therefore `alwaysVisible` (`breadcrumbs.html:47`). (3) When `routerLink` was never set on `<kbq-breadcrumb-item>`, `item.routerLink` is `null`, `RouterLink` removes the `href`, and the dropdown row is an anchor that navigates nowhere. That is not hypothetical: `breadcrumbs-with-auto-wrap-adaptive-example.ts:70` — the example the guide uses to demonstrate the primary `auto` overflow behaviour — renders `<kbq-breadcrumb-item [text]="breadcrumb.label" />` with no `routerLink`, so every item that collapses into its dropdown is a dead row. `aria-current` is not carried over either, so the dropdown never marks which entry is the current page.
**Fix:** make `text` `input.required<string>()` (breaking, but it is already effectively required and the compiler will find every call site), or fall back to the item's projected text content. Render `item.customTemplateRef()` inside the dropdown row via `ngTemplateOutlet` when one exists, exactly as the inline path does at `breadcrumbs.html:59-60`, and forward `aria-current` for the item that is current. For the missing destination, either document that `routerLink` on `<kbq-breadcrumb-item>` is mandatory for overflow-capable trails, or emit a dev-mode `console.warn` when an item without a `routerLink` is hidden. Regression test: a Jest case that forces three items hidden and asserts each dropdown row has a non-empty accessible name and a resolvable `href`.

**BCR-LIFE-01 · Roving-focus registration happens once in `ngOnInit`, so later `focusable` changes desync the group and leak detached elements** — `roving-focus-item.directive.ts:32, 42-64`; driver at `breadcrumbs.html:66`.
`ngOnInit` registers the element only `if (this.focusable())` (`:47-52`) and `ngOnDestroy` unregisters only `if (this.focusable())` (`:59-64`) — but `focusable` is an `input()` signal that changes at runtime. In this component it changes constantly: the template binds `[focusable]="!item.disabled() && !last"` (`breadcrumbs.html:66`), and `last` is recomputed on every trail change. In the `@if` branch (`wrapMode` `wrap`/`none`, used by `breadcrumbs-with-wrap-example.ts:12` and the SSR fixture) the `@for` tracks by item identity, so appending a breadcrumb reuses the previously-last item's view: its `focusable` flips `false → true` and it is **never registered** — permanently unreachable by arrow keys, `Home` and `End`, for the rest of the page's life. The reverse direction is a leak: an element registered while `focusable` was `true` and destroyed after it flipped to `false` is never removed from `focusableItems()` (`roving-focus-group.directive.ts:134-138`) and never decrements `focusableItemsCount` (`:122-124`), so the array accumulates detached nodes across re-renders and the group's `tabIndex` getter (`:47-49`) can never return to `-1`. `focusFirst` then iterates detached elements whose `.focus()` is a silent no-op (`utils.ts:39-45`), so arrow navigation appears to "stick" on the first press.
**Fix:** replace the two lifecycle hooks with a single `effect()` that registers on `focusable() === true` and unregisters on `false`, and make `ngOnDestroy` unregister unconditionally (`unregisterItem` already filters by identity, so an unregister of an unregistered element is harmless; `onFocusableItemRemove` already floors at zero). While there, drop the parallel `focusableItemsCount` bookkeeping entirely and derive the count from `focusableItems().length` — the two counters are updated in lockstep from the same two call sites and can only ever disagree because of this bug. Cover with a Jest case that toggles `[focusable]` on a mounted item and asserts `focusableItems()` tracks it in both directions, and one that destroys a fixture after flipping `focusable` to `false` and asserts the array is empty.

**BCR-BUG-02 · `KbqBreadcrumbButton` overwrites the button's `color` and `kbqStyle` inputs from `ngOnInit`, clobbering the consumer's own bindings** — `breadcrumbs.ts:81-100`; base inputs at `button/button.component.ts:367-403`, source-ranking flags at `:424-435`.
`ngOnInit` assigns `this.button.color = KbqComponentColors.Contrast; this.button.kbqStyle = KbqButtonStyles.Transparent` directly onto the injected `KbqButton`. Both are real `@Input` accessors, and both setters record *why* the value was set: `color` sets `colorSetExplicitly = true` and `colorSetFromGroup = false` (`button.component.ts:397-403`), `kbqStyle` sets `kbqStyleSetExplicitly = true` (`:372-377`). Those flags exist to rank three sources — the button's own binding, a surrounding `KbqButtonGroupRoot`, and the style's default colour (`:429-435`) — and `KbqBreadcrumbButton` writes into the top of that ranking from outside. Two concrete consequences. A consumer writing `<a kbq-button kbqBreadcrumb color="error">` has the binding applied at creation and then silently reset to `contrast` when `ngOnInit` runs, with no error and no warning; it comes back only if the bound expression later changes to a *different* value. And a `kbqBreadcrumb` button placed inside a `KbqButtonGroupRoot` is permanently opted out of the group's colour propagation, because `colorSetExplicitly` is now `true`. The template's own `[kbqStyle]="KbqButtonStyles.Transparent"` on the expand button (`breadcrumbs.html:25`) is redundant for the same reason — the directive sets it anyway — which suggests the interaction was not fully understood when it was written.
**Fix:** stop writing the inputs. Express the breadcrumb appearance as defaults instead: set `defaultColor` (the mechanism `KbqColorDirective` already provides at `core/common-behaviors/color.ts:38, 52-53`) and, for the style, only assign when the consumer has not — `KbqButton` already tracks that in `kbqStyleSetExplicitly`, so exposing a narrow `applyDefaultStyle(style)` on the button is the clean seam. Failing that, guard both writes behind an explicit "not set by the consumer" check rather than assigning unconditionally. Then drop the now-redundant `[kbqStyle]` at `breadcrumbs.html:25`. Add a Jest case binding `color="error"` on a `kbqBreadcrumb` anchor and asserting the class survives `ngOnInit`.

**BCR-A11Y-04 · The group writes `dir="ltr"` onto the host unconditionally, and `dir` is not reachable through `hostDirectives`** — `roving-focus-group.directive.ts:9, 24`; `breadcrumbs.ts:178`; direction-aware key mapping at `utils.ts:20-24, 26-33`.
`RdxRovingFocusGroupDirective` binds `'[attr.dir]': 'dir()'` with `dir = input<Direction>('ltr')`, so **every** `<nav kbq-breadcrumbs>` renders `dir="ltr"` whether or not anyone asked for it. In an RTL document (`<html dir="rtl">`) that attribute wins over inheritance for the entire breadcrumbs subtree, so the trail lays out left-to-right inside a right-to-left page — a visible rendering bug, not just a semantic one. And it cannot be corrected from the outside, because `KbqBreadcrumbs` declares `hostDirectives: [RdxRovingFocusGroupDirective]` in its bare form (`breadcrumbs.ts:178`) with no `inputs` array: `dir`, `loop` and `preventScrollOnEntryFocus` are all unreachable on `<kbq-breadcrumbs>`, unlike `focusable`, which `KbqBreadcrumbButton` does forward explicitly (`breadcrumbs.ts:84-89`). The knock-on is that `getDirectionAwareKey` (`utils.ts:20-24`) never sees `'rtl'`, so `ArrowLeft`/`ArrowRight` are never swapped and arrow navigation runs backwards in RTL locales. The component does not inject CDK `Directionality` either, so there is no fallback source of truth.
**Fix:** stop emitting the attribute when the value is the default — `'[attr.dir]': "dir() === 'ltr' ? null : dir()"` — so the element inherits the document direction, and drive the signal from CDK `Directionality` (`inject(Directionality, { optional: true })`, `dir.value`) in `KbqBreadcrumbs`'s constructor next to the existing `group.orientation = 'horizontal'` assignment (`breadcrumbs.ts:256-258`). If explicit control is still wanted, forward the input properly: `hostDirectives: [{ directive: RdxRovingFocusGroupDirective, inputs: ['dir', 'loop'] }]`. Note that forwarding changes `breadcrumbs.api.md:73`, so it needs `build:components` + `approve-api`. Verify with a Playwright case rendering the fixture under `<html dir="rtl">` and asserting both the visual order and that `ArrowRight` moves focus leftward.

**BCR-A11Y-05 · `PageUp`/`PageDown` are swallowed while a breadcrumb has focus, so the page cannot be scrolled from the keyboard** — `utils.ts:9-18, 26-33`; `roving-focus-item.directive.ts:99-136`, especially `:110-115`.
`MAP_KEY_TO_FOCUS_INTENT` maps `PageUp → 'first'` and `PageDown → 'last'` alongside `Home`/`End` (`utils.ts:15-16`). `handleKeydown` calls `event.preventDefault()` for any non-`undefined` intent (`roving-focus-item.directive.ts:115`), and the orientation guard in `getFocusIntent` only filters `ArrowUp`/`ArrowDown` for a horizontal group (`utils.ts:30`) — `PageUp`/`PageDown` pass straight through. So while focus is on a breadcrumb, pressing `PageDown` moves focus to the last breadcrumb instead of scrolling the document, and the default scroll is cancelled. That is inherited from the Radix roving-focus primitive, where the consumers are toolbars and tab lists — composite widgets that legitimately own paging keys. A breadcrumb trail is a navigation landmark, not a composite widget: WAI-ARIA APG's breadcrumb pattern specifies no key bindings at all beyond `Tab`, and the component's own keyboard documentation (`breadcrumbs.en.md:98-105`, `breadcrumbs.ru.md:98-105`) lists `Home` and `End` but never mentions `PageUp`/`PageDown` — so the behaviour is both surprising and undocumented. Breadcrumbs typically sit at the top of a scrollable page, which is exactly where a user is most likely to press `PageDown` right after tabbing past them.
**Fix:** delete the `PageUp`/`PageDown` entries from `MAP_KEY_TO_FOCUS_INTENT` (`utils.ts:15-16`), or gate them behind a new `RdxRovingFocusGroupDirective` input that `KbqBreadcrumbs` leaves off. `Home`/`End` already provide the first/last jumps the documentation promises, so nothing is lost. Add a Jest case dispatching `PageDown` on a focused breadcrumb and asserting `defaultPrevented === false`.

**BCR-TEST-01 · 17 Jest cases and 5 Playwright tests, none of which assert anything about accessibility or keyboard navigation** — `breadcrumbs.spec.ts` (481 lines, 17 cases), `e2e.playwright-spec.ts` (87 lines, 5 tests); precedent at `accordion`, `app-switcher`, `button-toggle`, `list`, `navbar` specs.
The Jest suite covers item counts, the size class, the disabled *item* state, `max` transitions in four `fakeAsync` cases, and the focusable-ordering effect. Nothing asserts `aria-label`, `aria-current`, `role`, `aria-hidden` on the separator, or the accessible name of the expand button — for a navigation-landmark component that is the coverage that matters most, and its absence is why BCR-A11Y-01 and BCR-A11Y-02 survived a full button-accessibility pass (`4b710125f`) that touched this very file. `jest-axe` is already a dependency (`package.json:90, 121`) and is used by five sibling specs, so the infrastructure cost is zero. Keyboard behaviour is equally uncovered: the only key exercised anywhere is `DOWN_ARROW` opening a dropdown (`breadcrumbs.spec.ts:161-186`); `ArrowLeft`/`ArrowRight` roving, `Home`/`End`, `Tab` entry and Shift+`Tab` exit — the five rows of the guide's own keyboard table — are asserted nowhere, in either suite. Add a Playwright `keyboard` test: Tab into the trail, assert focus is on the first breadcrumb; `ArrowRight` twice; `End`; `Home`; Shift+Tab out and Tab back in, asserting focus re-enters the trail (this is the regression guard for BCR-A11Y-03). Assertion-only tests need no new baselines; anything visual goes through `yarn run e2e:docker:update-snapshots`.

**BCR-SSR-01 · `utils.ts` reaches for the global `window` behind two `eslint-disable` comments, and its only caller passes an `HTMLElement` where `Document | ShadowRoot` is declared** — `utils.ts:35-45`, especially `:36-37, 43-44`; call sites `roving-focus-item.directive.ts:130-134` and `roving-focus-group.directive.ts:93`.
`focusFirst` reads `rootNode?.activeElement ?? window.document.activeElement` (`:37`) and `window.document.activeElement` again (`:44`), each preceded by `// eslint-disable-next-line no-restricted-globals`. That rule exists in this repo specifically to enforce the AGENTS.md SSR mandate ("Use `inject(KBQ_WINDOW)` instead of the global `window`"), and these are the only two suppressions of it in the package. The exposure is latent rather than live — `focusFirst` is only reachable from focus and keydown handlers, which never run on the server — but a suppression comment records that the rule was noticed and stepped over, and it removes the guard for whoever moves this call next. The second half is a real, present defect: `roving-focus-item.directive.ts:132` calls `focusFirst(candidateNodes, false, this.elementRef.nativeElement)` while the parameter is declared `rootNode?: Document | ShadowRoot` (`utils.ts:35`). It compiles only because `inject(ElementRef)` without a type argument yields `ElementRef<any>` (`roving-focus-item.directive.ts:28`), so `nativeElement` is `any` and defeats the check. At runtime an `HTMLElement` has no `activeElement`, the optional chain yields `undefined`, and the `??` silently falls back to the document — meaning the parameter that exists to make the helper shadow-DOM-correct is inert at the only place it is used, while the group's own call (`roving-focus-group.directive.ts:93`) omits it entirely.
**Fix:** type the injection as `inject<ElementRef<HTMLElement>>(ElementRef)` in both roving-focus directives — that alone turns the bad call site into a compile error — then pass `this.elementRef.nativeElement.getRootNode() as Document | ShadowRoot`, which is what the parameter was written for, at both call sites. Replace the two globals with an injected `KBQ_WINDOW` (or take the active element from the resolved root node, which removes the need for `window` at all) and delete both `eslint-disable` comments. No behaviour change is expected outside shadow DOM, so the existing suite is the regression guard.

**BCR-API-02 · `KbqBreadcrumbItem.current` is published, documented and dead, and so is the `.kbq-breadcrumb_current` rule that was meant to pair with it** — `breadcrumbs.ts:136-140`, `breadcrumbs.scss:174-183`, `breadcrumbs.api.md:35`.
`readonly current = input<boolean, unknown>(false, { transform: booleanAttribute })` is documented as "Indicates whether the breadcrumb item is the current/active item." Grepping the entire repository for `current` (excluding `aria-current` and the unrelated `currentTabStopId`) returns the declaration, its JSDoc, and nothing else — the template derives `aria-current` from `$last` instead (`breadcrumbs.html:68`), so a consumer marking a non-terminal item as current gets no effect. The stylesheet's matching half is equally orphaned: `.kbq-breadcrumb_current` (`breadcrumbs.scss:174-183`) is the only occurrence of that class name anywhere in `packages/`, `apps/` and `tools/` — ten lines of theme overrides that can never match. **Fix:** delete both, or wire them together — `[class.kbq-breadcrumb_current]="item.current() || last"` on the rendered anchor and `[attr.aria-current]="(item.current() || last) ? 'page' : null"` — which would also give trails that do not end at the current page (a detail view reached from a list, for example) a way to say so. **BCR-API-03 · A vendored third-party directive pair is published from the breadcrumbs entry point, undocumented, with two API-Extractor warnings baked into the golden report** — `public-api.ts:4-5`, `roving-focus-group.directive.ts:4-5, 17`, `roving-focus-item.directive.ts:15-16, 27`; `breadcrumbs.api.md:122-184`, warnings at `:128, 146`.
`RdxRovingFocusGroupDirective` and `RdxRovingFocusItemDirective` are exported from `@koobiq/components/breadcrumbs` with selectors `[rdxRovingFocusGroup]` and `[rdxRovingFocusItem]` — a foreign prefix in a library whose every other export is `Kbq*`. The report marks both classes `// @public (undocumented)` and publishes 20 and 12 members respectively, including the mutable `orientation` field, the `focusableItems` `WritableSignal` that `KbqBreadcrumbs` reaches in and reorders (`breadcrumbs.ts:277`), and every internal handler (`handleFocus`, `handleBlur`, `handleMouseUp`, `onItemShiftTab`, `registerItem`, `unregisterItem`). Two `ae-forgotten-export` warnings are recorded in the golden file itself (`:128, 146`): `Direction` and `Orientation` are used in public signatures but not exported from the entry point, so a consumer cannot name the type of `dir` or `orientation`. Nothing in the docs mentions any of this — `structure.ts:376-387` describes one component, and the generated API tab will show a Radix directive pair with no prose. Half of the package's public surface is machinery that exists to serve one component.
**Fix:** decide what the intended surface is. If the roving-focus pair is meant to be reusable, move it to `packages/components/core`, rename to `KbqRovingFocus*`, export `Direction`/`Orientation`, and document it — it is genuinely useful and three other packages hand-roll equivalents. If it is not, drop lines 4-5 of `public-api.ts` and make the members that only `KbqBreadcrumbs` needs `@internal` (note `@internal` alone does not strip them from the report — that needs `stripInternal`; see `project_api_guard_internal_not_stripped`). Either move changes `breadcrumbs.api.md`, so run `yarn run build:components` then `yarn run approve-api` — build first, the guard reads `dist/*.d.ts`.

**BCR-BUG-03 · Two of `handleFocus`'s three focus-candidate lookups can never match** — `roving-focus-group.directive.ts:86-93`; `roving-focus-item.directive.ts:17-25, 33, 37`; compensating hack at `breadcrumbs.ts:269-278`.
The entry handler builds `candidateItems = [activeItem, currentItem, ...items]` from two lookups. `currentItem = items.find((item) => item.id === this.currentTabStopId())` compares the DOM `id` property of an `HTMLElement` against the directive's generated `rf-item-<random>` string (`roving-focus-item.directive.ts:37`) — but the item directive's host block (`:17-25`) binds `tabindex`, `data-orientation`, `data-active` and `data-disabled`, and never writes `id`. No breadcrumb element carries an `id`, so this always evaluates `'' === 'rf-item-…'` and yields `undefined`. `activeItem = items.find((item) => item.getAttribute('data-active') === 'true')` fares no better: `active` defaults to `true` (`:33`) and is bound nowhere in this package, so every roving item renders `data-active="true"` and the lookup degenerates to "the first registered item". The net result is that the group can only ever restore focus to `items[0]`, never to where the user actually was. That degeneration is also what the reordering `effect()` in `KbqBreadcrumbs` (`breadcrumbs.ts:269-278`) exists to paper over — it swaps the expand button out of position zero because position zero is the only position that matters — and three of the spec's 17 cases (`breadcrumbs.spec.ts:198-231`) guard the hack rather than the behaviour. Impact is modest because the browser bypasses `handleFocus` entirely whenever some item still holds `tabindex="0"`; it bites after the current tab stop is destroyed by a route change or an overflow collapse, when the user is returned to the start of the trail instead of near where they left.
**Fix:** bind `'[attr.id]': 'id()'` in the item's host block so `currentTabStopId` can be resolved (and clear `currentTabStopId` in `unregisterItem` when the removed element was the tab stop), and flip `active` to default `false` so `data-active` discriminates. Then re-check whether the reordering `effect()` is still needed; if it is, add the comment it is missing, explaining that the expand button registers first because it is a direct host-view node while the breadcrumbs live in `NgTemplateOutlet` embedded views.

**BCR-ARCH-01 · A full `KbqIcon` component per separator, mixed `ngTemplateOutlet` syntaxes, and an effect that writes the signal it reads** — `breadcrumbs.html:5, 7, 43, 44, 82`, `breadcrumbs.ts:269-278`; `icon/icon.component.ts:22-33, 97-151`.

(1) The default separator instantiates `KbqIcon` with an empty name (`breadcrumbs.html:82`) purely for its colour and typography classes: each instance injects the registry, allocates a `ReplaySubject`, runs `ngOnChanges` and sets up a `switchMap` subscription in `ngAfterContentInit` (`icon.component.ts:97-151`) that immediately short-circuits to `EMPTY` because the name is falsy. A five-level trail pays for four of these. A `<span class="kbq-breadcrumb__separator kbq-contrast-fade">` would render identically. (2) The same template uses both `*ngTemplateOutlet` (`:5, 14, 43, 49`) and `[ngTemplateOutlet]` (`:7, 15, 29, 44, 60, 80`) for the same purpose, sometimes two lines apart — the micro-syntax form is the odd one out in a repo that has otherwise moved to `@if`/`@for`. (3) The constructor's `effect()` (`breadcrumbs.ts:269-278`) reads `group.focusableItems()` and, in the same body, calls `group.focusableItems.set(...)`. It converges — after the swap, `focusableItems[0]` is no longer the expand button, so the guard at `:273` short-circuits on the next run — but a self-writing effect with no comment is a trap for the next reader, especially since its purpose is non-obvious (see BCR-BUG-03).
**Fix:** replace the separator's `<i kbq-icon="">` with a plain `<span>` carrying the same classes and verify against the existing `01-light.png`/`01-dark.png` baselines. Normalize every `*ngTemplateOutlet` to `[ngTemplateOutlet]` (or the reverse) in one pass. Add a comment above the effect stating the registration-order problem it solves.

**BCR-STYLE-01 · Type and declaration hygiene across the package** — `breadcrumbs.ts:122-124, 131, 135, 213-214, 234-241`; `roving-focus-group.directive.ts:21-23`; `roving-focus-item.directive.ts:34`; `tools/check-public-api-any/baseline.json:8`.

## Appendix A — Review Methodology

Findings were gathered by reading the complete package (all 21 files, 2,008 lines including the Jest spec and the e2e pair) and then following the component outward along four axes: **inward** to what it composes — `KbqButton` (role and disabled handling for anchors, the `color`/`kbqStyle` source ranking), `KbqIcon` (what an empty icon name does), `KbqOverflowItems` (`id` typing, `changes`, `hide`/`show`), `KbqTitleDirective`, and `KbqA11yLocaleConfiguration` with all five locale files; **outward** to every in-repo consumer found by grepping `kbq-breadcrumbs`/`kbqBreadcrumb` across `packages/`, `apps/` and `tools/` — 12 docs examples, 4 e2e fixture navs, the top-bar e2e and its two docs examples, the SSR dev fixture and the dev app; **downward** to the workspace configuration (`tsconfig.json:114-118`, `jest.config.js:13-14`, `playwright.config.ts:96-104`) and the API guard (`breadcrumbs.api.md`, `tools/api-extractor/config.json:10`, `tools/check-public-api-any/baseline.json:8` and the tool that produces it); and **backward** through the package's 31-commit history, in particular `4b710125f` (DS-5385, the button review that added the localized expand-button label to this very template and left the host label hardcoded), `577815966` (DS-4578, dropdown close), `3b309a416` (DS-4622, render flicker) and `a96c0ced9` (the Karma → Jest/Playwright migration that produced the current spec).

Consumer evidence is what upgraded two findings from opinions to confirmed defects. BCR-A11Y-01 rests on a complete census: 21 `<nav kbq-breadcrumbs>` call sites against 3 uses of the element form, all three inside the spec — every author in the repository worked around the missing landmark independently. BCR-CSS-01 rests on `breadcrumbs-with-wrap-example.ts:12`, an explicit binding of a property that does nothing in the mode it is written in.

Refuted during verification:
- **"The package is missing `_breadcrumbs-theme.scss`, so its colours are unthemed"** — refuted. The theme mixin exists, inline: `_kbq-breadcrumbs-theme` at `breadcrumbs.scss:92-184`, applied at `:220` alongside the geometry and typography mixins, and every colour it sets resolves to a `--kbq-*` token from `breadcrumbs-tokens.scss:1-10` or the global set. The deviation from the AGENTS.md file layout is cosmetic and matches several sibling packages. The only genuinely dead part of the theme is `.kbq-breadcrumb_current` (`:174-183`), filed as BCR-API-02.
- **"`<i kbq-icon=\"\">` on the separator throws or logs an error for the empty icon name"** — refuted. `ngAfterContentInit`'s `switchMap` short-circuits to `EMPTY` for a falsy name (`icon/icon.component.ts:112-117`) and `parseIconSize()` returns `NaN`, which the guard at `:91` treats as absent. The cost is a wasted component instance per separator, folded into BCR-ARCH-01, not a runtime failure.
- **"The constructor's `effect()` writes a signal it reads and will loop"** — refuted. After the swap at `breadcrumbs.ts:277`, `focusableItems[0]` is the first breadcrumb rather than the expand button, so the guard at `:273` returns early on the next run and the effect converges after one write. It is filed only as an uncommented fragility under BCR-ARCH-01.
- **"The package carries 14 untyped members on its public surface (`baseline.json:8`)"** — refuted as stated. Nine of the fourteen are the `unknown` in `InputSignalWithTransform<boolean, unknown>`, the shape `booleanAttribute` always produces, and one is `Set<unknown>` inherited from `KbqOverflowItem.id`'s untyped `input.required()` (`overflow-items/overflow-items.ts:102`). Only the four `TemplateRef<any>` are this package's to remove; recorded that way inside BCR-STYLE-01.
- **"`examples.breadcrumbs.*.md` are dead '🚧 Documentation in progress 🚧' stubs like several sibling packages"** — refuted. Both files carry two real `<!-- example(…) -->` embeds (`examples.breadcrumbs.en.md:1-12`, `.ru.md:1-12`), `structure.ts:386` sets `hasExamples: true`, and the two examples they embed (`breadcrumbs-selectable-text`, `breadcrumbs-routing`) are correctly disjoint from the main guide's ten. This is one of the better-populated Examples tabs in the library.
- **"The Playwright screenshots are flaky because breadcrumb transitions are not disabled"** — refuted. `playwright.config.ts:101` sets `reducedMotion: 'reduce'` on every browser context, so animation is not a variable in the three committed baselines.
- **"`aria-orientation` should be added next to the roving group's `data-orientation`"** — refuted as inapplicable. `aria-orientation` is valid on composite-widget roles (`listbox`, `tablist`, `separator`), not on a `navigation` landmark or a role-less element; adding it would introduce a jest-axe `aria-allowed-attr` failure rather than remove one (cf. `project_aria_orientation_not_allowed_on_role_group`).

Corrected on verification:
- **BCR-A11Y-01** was first drafted as **P0**, on the reading that a hardcoded ARIA string is a stated AGENTS.md mandate violated with no workaround. Downgraded to P1: the component still exposes every item to assistive technology and the 21 `<nav>` call sites do get a landmark, so the failure is a degraded and unlocalizable name rather than an inaccessible component. The P0 reading is recorded here so the next reviewer does not have to re-derive it.
- **BCR-A11Y-02** was first drafted as "the separator has no `aria-hidden`, an AXE failure". Corrected: axe has no rule for un-hidden decorative text, so this is a WCAG 1.3.1 judgement. It stays P1 on the strength of the repo's own unambiguous convention (`aria-hidden="true"` on decorative icons in two packages and on every registry-injected SVG) plus the missing list semantics.
- **BCR-BUG-03** was first drafted at P2 as "arrow-key navigation cannot restore focus". Tracing when `handleFocus` actually runs showed the browser bypasses it entirely whenever any item still holds `tabindex="0"`, so the failure only surfaces after the tab stop is destroyed. Severity dropped to P3 and the wording moved from "cannot restore focus" to "always restores to the first item".
- **BCR-SSR-01** was first drafted as a pure SSR violation. Reading the call graph showed `focusFirst` is unreachable on the server, so the SSR exposure is latent; the finding was re-centred on the two suppressed lint rules and on the `HTMLElement`-for-`Document|ShadowRoot` call site that `ElementRef<any>` hides, which is a present defect.
- **BCR-DOC-01** initially claimed the middle-truncation example's duplicated CSS and its inert `[minVisibleLength]` binding as breadcrumbs defects. Both are already filed against the owning package as ELC-CSS-01 and ELC-API-01 in `REVIEW.ellipsis-center.md`; this review cites them only as context and keeps the breadcrumbs-side claim to the guide presenting four unimplemented modes as component features.
