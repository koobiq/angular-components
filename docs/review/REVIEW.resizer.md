# Koobiq `resizer` Component — Code Review & Improvement Plan

> Scope: `packages/components/resizer` (both directives, Jest spec, user guides, examples stubs, API guard report, dev app, docs-example) plus its two in-repo consumers `content-panel` and `dl`, and `splitter` as the comparable prior art · Commit `b665e503` · 2026-08-28
> Generated by a multi-dimension review (architecture, RxJS/lifecycle, correctness, accessibility, performance, public API/types, styles, tests, docs) with manual verification of every finding against the source, the consumers, the API guard report and `tsconfig.json`. 12 findings confirmed (P0×1, P1×3, P2×4, P3×4); 5 candidate findings refuted during verification (see Appendix A). This document is a review + roadmap; no source is modified by it.

---

## 1. Executive Summary

`KbqResizer` is a 310-line, two-directive package with no stylesheet, no tokens, no theme, no e2e fixture and no Playwright spec — the whole shipped surface is `resizer.ts` plus a 16-line guide. The pointer code inside it is the best part of the package and is genuinely good: pointer capture, `pointercancel` and `lostpointercapture` handling, a cross-box-model measurement path, and a body-cursor save/restore that preserves `!important` priority. Everything around that core is where the package fails.

- **The library's only resize primitive cannot be operated by keyboard, and it ships a keyboard-inoperable control because of it.** The host block (`resizer.ts:72-79`) binds a class and `[style.cursor]` and nothing else — no `tabindex`, no `keydown`, no focus handling. `KbqContentPanelContainer` renders a `[kbqResizer]` handle with `disableResizer` defaulting to `false` (`content-panel.ts:237, 288`), so **every** documented content panel ships a resize control that a keyboard user cannot reach or move. That is WCAG 2.1.1 (Level A), below the AA minimum AGENTS.md mandates (RSZ-A11Y-01).
- **`dl` had to re-implement the entire separator on top of the directive — roughly sixty lines of it.** `dl.component.ts:66-83` hand-writes `role="separator"`, `aria-orientation`, `tabindex="0"`, `aria-label`, `aria-valuemin`, `aria-valuemax` and `aria-valuenow`; `:251-269` writes the arrow/Home/End handler; `:315-334` maintains the boundary cursor state machine; `:244-248` demotes the focus origin to work around the directive's `preventDefault()` on pointerdown. None of that is reusable, and `content-panel` — written by someone else — has none of it (RSZ-A11Y-01, RSZ-A11Y-02).
- **The directive ships no stylesheet, so `touch-action: none` is left to the caller, and one of the two callers forgot.** `dl.scss:71` sets it on the handle; `content-panel-container.scss:24-31` does not, so on a touch device the browser is free to claim the gesture and fire `pointercancel`, which `resizer.ts:163-165` dutifully honours by aborting the drag. This is one host-binding line the directive can own without a stylesheet at all (RSZ-BUG-01).
- **The guide documents one of four public members and its only snippet does not work.** `resizer.en.md` is 16 lines covering `kbqResizer` and nothing else — `sizeChange`, the output through which the directive is actually consumed, is never mentioned in prose, and neither are `resizeStart` or `cursor`. Its snippet is `<i [kbqResizer]="[1, 0]"></i>`: an empty inline element with no box, i.e. a handle with zero hit area (RSZ-DOC-01).
- **Three `document` listeners per instance, wired for the directive's whole lifetime rather than for the drag.** The shipped overview example alone puts nine `[kbqResizer]` elements on one page (`resizer-overview-example.ts:14-42`), six of them `[0, 0]` grid spacers that can never resize anything, for 27 permanent document listeners. `splitter`, solving the same problem, registers on mousedown and tears down on mouseup (`splitter.component.ts:415-425, 536-539`) (RSZ-PERF-01).

Genuine strengths worth preserving: the pointer-capture lifecycle is more careful than most implementations of this kind — it filters on `button`/`isPrimary`/`pointerId`, refuses a second concurrent drag, falls back to `!event.buttons` when a `pointerup` never arrives, and handles `pointercancel` and `lostpointercapture` as first-class exits. Teardown is correct and provably so: every subscription carries `takeUntilDestroyed(this.destroyRef)` and `destroyRef.onDestroy` restores the body cursor if the directive dies mid-drag (`resizer.ts:147`), with a test for exactly that (`resizer.spec.ts:186-199`). SSR hygiene is exemplary — `inject(KBQ_WINDOW)` rather than the global, and the entire DOM path behind `afterNextRender`. And `getResizableSize()` (`:210-220`) is a real bug fix with a real explanation attached: it asks the element which box model it is in before writing a size back into it.

## 3. Prioritized Findings (deduplicated, verified)

### P0 — Release blockers

**RSZ-A11Y-01 · The resize primitive has no keyboard operation, and a shipped component is keyboard-inoperable as a direct result** — `resizer.ts:72-79` (host block), `:182`; consumers `content-panel.ts:235-240, 288`, `dl.component.ts:66-83, 244-248, 251-269`.
`KbqResizer`'s host block declares exactly two things: `class: 'kbq-resizer'` and `'[style.cursor]': 'resolvedCursor()'`. There is no `tabindex`, no `keydown` binding, no focus management, and the only entry point into the whole state machine is `handleElementPointerDown` (`:174`). Resizing is therefore reachable by pointer and by nothing else. This is not an abstract gap: `KbqContentPanelContainer` renders `<div class="kbq-content-panel-container__panel-resizer" [kbqResizer]="[-1, 0]" (sizeChange)="handleResizerSizeChange($event)" (dblclick)="handleResizerDBLClick($event)">` (`content-panel.ts:235-240`) with **no** `tabindex`, no `role` and no key handler, and `disableResizer` defaults to `false` (`content-panel.ts:288`) — so the handle is present in every content panel unless a consumer explicitly turns it off. There is no alternative keyboard path to the panel width: the only other host key binding in the component is `(keydown.escape)` for closing (`content-panel.ts:252`). A keyboard or switch user cannot change the width at all. That is WCAG 2.1.1 Keyboard, Level A — beneath the AA floor AGENTS.md states as a hard requirement.
The proof that the gap belongs to the directive rather than to `content-panel` is `dl`: the same primitive, in the hands of an author who did care, required `tabindex="0"` and `(keydown)` on the handle (`dl.component.ts:71, 80`) plus a nineteen-line `handleResizeKeydown` covering `ArrowLeft`/`ArrowRight`/`Home`/`End` with an RTL-aware step (`:251-269`), plus `focusMonitor.focusVia(handle, 'mouse')` on `resizeStart` (`:244-248`) purely to undo the focus suppression caused by the directive's own `event.preventDefault()` on pointerdown (`resizer.ts:182`). Every line of that is generic. Note this is a WCAG judgement backed by a shipped defect, not an automated axe failure — axe does not flag a `<div>` that simply has no role and no tabindex, which is exactly why this survived two feature commits.
**Fix:** move the keyboard layer into `KbqResizer`. Add to the host block `tabindex: '0'` and `'(keydown)': 'handleKeydown($event)'`, and a `step = input(8, { transform: numberAttribute })`. In `handleKeydown`, map `ArrowLeft`/`ArrowRight` to `±step` on the x axis when `direction()[0]` is non-zero and `ArrowUp`/`ArrowDown` likewise on y, then run the result through the *same* path a pointer move takes — read the current size with `getResizableSize()`, write it with the renderer, emit `sizeChange` — so every consumer's existing clamping (`content-panel.ts:392-397`, `dl.component.ts:305-313`) applies unchanged with no consumer edit. Call `event.preventDefault()` only on the keys you consume. Gate the whole thing behind the existing "no direction means not resizable" guard (`resizer.ts:178`) so `[0, 0]` handles stay out of the tab order. Guard it with Jest cases per key per axis, plus one that asserts a `[0, 0]` handle has no `tabindex`, and add the `dl` keyboard suite's assertions to a new resizer e2e fixture (RSZ-TEST-01). Then delete `dl.component.ts:251-269` and `:71, 80` and confirm the `dl` Jest and Playwright suites still pass — that deletion is the acceptance criterion.

### P1 — High

**RSZ-A11Y-02 · No separator semantics and no accessible name; `dl` hand-writes seven ARIA attributes the directive should own** — `resizer.ts:72-79`; consumers `dl.component.ts:66-83, 200, 206-207`, `content-panel.ts:235-240`; locale `core/locales/types.ts:37`, `core/locales/en-US.ts:16`, `core/locales/ru-RU.ts:16`.
A resize handle is a `separator` with a value: ARIA defines `role="separator"` in its focusable form as taking `aria-orientation`, `aria-valuenow`, `aria-valuemin` and `aria-valuemax`, and `aria-orientation` **is** valid there (unlike on `role="group"`). `KbqResizer` emits none of them, and it knows enough to emit two: `direction()` fully determines the orientation, and `resolvedCursor()` already derives a four-way classification from it (`:125-138`). `dl` writes the full set by hand — `role="separator"`, `aria-orientation="vertical"`, `[attr.aria-label]`, `[attr.aria-valuemax]`, `[attr.aria-valuemin]`, `[attr.aria-valuenow]` (`dl.component.ts:69-77`) — and sources the default name from `kbqInjectA11yLocaleConfiguration()` (`:200, 206-207`), for which a `resizeColumns` key had to be added to the locale type and all five locale files (`core/locales/types.ts:37`, `en-US.ts:16`, `ru-RU.ts:16`, `es-LA.ts:16`, `pt-BR.ts:16`). `content-panel`'s handle has none of it: to a screen reader it is an unlabelled `<div>`, announced as nothing. Two consumers, two completely different answers, and the one that got it right had to extend the shared locale to do so.
**Fix:** put the direction-derivable half in the directive's host block: `role: 'separator'` and `'[attr.aria-orientation]': "direction()[0] ? 'vertical' : 'horizontal'"` (a vertical separator is the one you drag horizontally — mind the inversion, and assert it in a test rather than trusting the reading). Add an `ariaLabel` input defaulting to a new generic `resize` key in `kbqInjectA11yLocaleConfiguration()` — `resizeColumns` is `dl`-specific wording ("Resize columns" / "Изменить ширину колонок") and must not be reused for a panel. The value triple needs bounds the directive does not have, so add optional `min`/`max` inputs (they also serve `Home`/`End` in RSZ-A11Y-01 and the clamping in RSZ-ARCH-01) and bind `aria-valuenow`/`aria-valuemin`/`aria-valuemax` only when they are supplied. Then strip `dl.component.ts:69-77` down to the values it alone knows and add the same to `content-panel`; a `jest-axe` pass over both consumer fixtures is the guard.

**RSZ-BUG-01 · No `touch-action: none`, so a touch drag is the browser's to claim — and it takes it from `content-panel`** — `resizer.ts:55-79` (neither directive declares any style), package has no `.scss` file at all; consumers `dl.scss:59-74` (sets it), `content-panel-container.scss:24-31` (does not); in-repo precedents `tabs/_tabs-common.scss:148`, `scrollbar/deprecated/scrollbar.component.scss:478`.
Pointer-driven dragging requires the element to opt out of the browser's default touch behaviours; without `touch-action: none` the user agent may treat the gesture as a pan or a zoom, at which point it fires `pointercancel` and the drag ends. The directive handles `pointercancel` correctly (`resizer.ts:163-165` → `handleDocumentPointerUp` → `finishDrag`), so the failure mode is not a crash — it is a handle that simply refuses to move under a finger. Because the package ships no stylesheet, the declaration has to come from the consumer, and the two consumers disagree: `dl.scss:71` sets `touch-action: none` on `.kbq-dl__resize-handle`; `.kbq-content-panel-container__panel-resizer` (`content-panel-container.scss:24-31`) sets `position`, `top`, `left`, `width`, `height` and `z-index` and stops there. Three other drag surfaces in this repo set the property (`dl.scss:71`, `tabs/_tabs-common.scss:148`, `scrollbar/deprecated/scrollbar.component.scss:478`), so the convention exists — it just is not enforced by the primitive that needs it. Note that `event.preventDefault()` on pointerdown (`resizer.ts:182`) does not substitute: it suppresses text selection and focus, not scrolling.
**Fix:** one host binding on `KbqResizer`, no stylesheet needed: `'[style.touch-action]': "'none'"` — or better, make it conditional on the handle being live, `"direction()[0] || direction()[1] ? 'none' : null"`, so the `[0, 0]` spacers in the overview example keep normal scrolling. Then delete `dl.scss:71` as redundant. Guard with a Jest assertion on the computed host attribute for both the live and the `[0, 0]` case, and add a Playwright touch-emulation drag to the new e2e fixture (RSZ-TEST-01) — a jsdom test cannot show that the gesture actually completes.

**RSZ-DOC-01 · The guide covers one member out of four and its only snippet produces a handle with no hit area** — `resizer.en.md:1-16`, `resizer.ru.md:1-16`; class doc `resizer.ts:44-54`; contrast `resizer-overview-example.ts:29-31, 54-72`.
The published guide is sixteen lines. It explains `kbqResizer`'s `[x, y]` tuple and stops. `sizeChange` — the output through which the directive is *actually* consumed, in both in-repo consumers and in the package's own example — appears nowhere in the prose; neither does `resizeStart`, nor `cursor`, nor `KbqResizerSizeChangeEvent`. The one code block, identical in both languages, is `<div kbqResizable><i [kbqResizer]="[1, 0]"></i></div>`: an empty `<i>` is an inline element with no content, therefore a zero-by-zero box, therefore a handle that cannot be grabbed. The class-level `@example` in the source has the same defect with a `<div>` (`resizer.ts:49-53`) — an empty block element is full-width but zero-height. Nothing anywhere tells a consumer the three things they must supply themselves: the handle's box, its hit area, and its `touch-action` (RSZ-BUG-01) — which is precisely the knowledge that `content-panel` and `dl` each had to rediscover, arriving at `--kbq-content-panel-resizer-width` (`content-panel-tokens.scss:2`) and `--kbq-description-list-resizer-hit-area-width` (`dl.scss:69`) independently. The sign convention is also only written down in the implementation: the guide says `-1` is "left", but what the code means (`resizer.ts:301-302`) is "pointer movement in the negative x direction increases the size", which is why `content-panel`'s left-edge handle is `[-1, 0]`.
**Fix:** rewrite both guides around a snippet that works — give the handle explicit dimensions and an absolute position on the edge it belongs to, and show `(sizeChange)` writing a signal, which is what every real caller does. Add sections for `cursor`, `resizeStart`, `sizeChange` and the `KbqResizerSizeChangeEvent` shape, and one for what the consumer owns (box, hit area, `touch-action`, focus ring). Say explicitly that the sign is relative to pointer movement, not to the edge, and that a missing ancestor `kbqResizable` is a runtime `NullInjectorError` rather than a no-op. Fix `resizer.ts:49-53` to match. The docs site compiles guide snippets under `yarn run e2e:docs`, so a corrected snippet stays compiling — but note that compiling is not the same as usable here, which is the whole point of this finding.

### P2 — Should fix

**RSZ-PERF-01 · Three permanent `document` listeners per instance, subscribed in the constructor rather than for the duration of a drag** — `resizer.ts:149-171`; comparison `splitter.component.ts:415-425, 536-539`; scale evidence `resizer-overview-example.ts:14-42`.
`afterNextRender` wires five subscriptions per directive instance, three of them on `document`: `pointermove` (`:155-157`), `pointerup` (`:159-161`) and `pointercancel` (`:163-165`). They live for the directive's entire lifetime, not for the drag, and they are created regardless of direction — a `[0, 0]` handle, which `handleElementPointerDown` refuses to act on at `:178`, still subscribes all three. The package's own overview example is the clearest illustration: nine `[kbqResizer]` elements on one page (`resizer-overview-example.ts:14, 17, 20, 23, 26, 29, 34, 37, 42`), six of them `[0, 0]` grid spacers, giving 27 permanent document listeners of which 18 belong to handles that can never resize anything. `dl` instantiates one per resizable description list, so a page of twenty lists carries sixty. Each `pointermove` handler does return early on `isActivePointer` (`:224`), and the work runs outside the Angular zone (`:150`), so this is a constant-factor cost rather than a correctness problem — but it is an avoidable one, and the repo already contains the better shape: `splitter` pushes its `document` `mousemove`/`mouseup` listeners onto a list at drag start (`splitter.component.ts:415-425`) and unsubscribes them all at drag end (`:536-539`).
**Fix:** keep the `pointerdown` subscription on the element permanent; move the three document subscriptions into `handleElementPointerDown`, torn down in `finishDrag()`. Hold them in a single `Subscription` field (or a `Subject` piped through `takeUntil`) so `finishDrag` — which is already the one funnel for pointerup, pointercancel, lost-capture and destroy (`:147, 231-251`) — remains the only teardown point. Also skip the element `pointerdown` subscription entirely, or early-return before it, while `direction()` is `[0, 0]`. Guard with a Jest case that counts `document.addEventListener` calls before, during and after a drag (spy on the document in `beforeEach`); the existing "should stop resizing on pointerup" case (`resizer.spec.ts:367-384`) already proves the behaviour is unchanged.

**RSZ-ARCH-01 · The directive both writes the size and emits it, with no way to take one of the two jobs away** — `resizer.ts:296-309`; consumers `content-panel.ts:230-232, 392-397`, `dl.component.ts:62-64, 305-313`.
`updateSize` writes `style.width`/`style.height` straight onto the resizable element with `renderer.setStyle` (`:305-306`) *and* emits the same numbers on `sizeChange` (`:308`). Both in-repo consumers then write the same properties back on the same element: `content-panel.ts:231` binds `[style.width.px]="widthState()"` and clamps in `handleResizerSizeChange` (`:392-397`); `dl.component.ts:64` binds `[style.width.px]="dtWidth()"` and clamps in `setDtWidth` (`:305-313`). Two owners, one property. The consumer's write is a no-op whenever clamping produces a value it already holds — `dl` even guards it explicitly, `if (constrainedWidth !== this.dtWidth())` (`:312`) — so at a bound the element keeps the directive's *unclamped* inline size, and what stops that from being visible is only that both consumers also bind `[style.min-width.px]`/`[style.max-width.px]` on the same element (`content-panel.ts:230, 232`, `dl.component.ts:62-63`). The directive's write is load-bearing for nobody here and actively in the way for anyone who wants to own the size — to animate it, to snap it, to persist it, or to apply a constraint the CSS box does not express.
**Fix:** add bounds and an opt-out. `min`/`max` inputs (shared with RSZ-A11Y-02's `aria-value*` and RSZ-A11Y-01's `Home`/`End`) let the directive clamp before it writes, which removes the divergence at a stroke; a `disableStyleWrite` (or `readonly`/"controlled mode") input lets a consumer take the write entirely and keep only the event. With both, `content-panel.ts:392-397` collapses to `this.widthState.set(width)` and `dl.component.ts:305-313` keeps only its cursor bookkeeping. Guard with a Jest case asserting that with `max` set, neither the emitted payload nor the written inline style exceeds it, and one asserting that with the write disabled the element's inline size never changes while `sizeChange` still fires.

**RSZ-API-01 · No `resizeEnd`, no `disabled`, no bounds; `[cursor]` is an unprefixed input on an attribute-selector directive** — `resizer.ts:105-120`, `:39-42`, `:132`; `tools/public_api_guard/components/resizer.api.md:19-30`; consumer `dl.component.ts:73`.
Four API gaps, all small, all felt by the two existing consumers. (1) There is a `resizeStart` (`:115`) and a per-move `sizeChange` (`:120`) but no `resizeEnd` — a consumer that wants to persist a final size, drop a "resizing" class, or commit a transaction has to infer the end from a global `pointerup`, which is exactly the listener the directive already owns. (2) Disabling is spelled `[kbqResizer]="[0, 0]"`, which reads as a direction and is used as one — six times in the package's own example, purely for grid spacing — while still costing a subscription set (RSZ-PERF-01) and still writing `cursor: default` inline (`:132`); a `disabled` input would say what is meant. (3) There are no `min`/`max` inputs, which is what forces both consumers to clamp downstream (RSZ-ARCH-01) and leaves the ARIA value triple unimplementable (RSZ-A11Y-02). (4) `cursor` (`:110`) is an un-namespaced input on a directive matched by a bare attribute, so it collides with any other directive on the same element that wants `[cursor]`, and reads as an HTML attribute at the call site — `dl.component.ts:73` binds `[cursor]="resizeCursor()"` on a `<div>` that also carries `cdkMonitorElementFocus`. Separately, `KbqResizerSizeChangeEvent` (`:39-42`) always carries both axes but only the axis with a non-zero direction is live; the other is the pointer-down baseline, unchanged. The spec documents this in a comment (`resizer.spec.ts:359-364`); the public type does not.
**Fix:** add `resizeEnd = output<KbqResizerSizeChangeEvent>()` emitted from `finishDrag()` when a drag was actually in progress (guard on `pointerId !== null` so destroy-without-drag stays silent). Add `disabled = input(false, { transform: booleanAttribute })` and fold it into the `:178` guard alongside the zero-direction check, keeping `[0, 0]` working for back-compat. Add `min`/`max` per RSZ-ARCH-01. Rename `cursor` to `kbqResizerCursor` with `alias: 'cursor'` retained for one minor and a deprecation note, then update `dl.component.ts:73`. Document the inert-axis rule in the `KbqResizerSizeChangeEvent` JSDoc. All of this changes `resizer.api.md`, so run `yarn run build:components` before `yarn run approve-api` — the guard reads `dist/*.d.ts`.

**RSZ-TEST-01 · No browser coverage at all, and every geometry assertion runs against a stub** — package has no `e2e.ts` and no `*.playwright-spec.ts`; `resizer.spec.ts:50-60, 323-344`; the only real-browser exercise is `dl/e2e.playwright-spec.ts:64-94`.
Of the 38 component packages inventoried, `resizer` is one of three with neither an `e2e.ts` fixture nor a Playwright spec — and unlike the other two it is a *pointer-geometry* directive, the category where jsdom is least able to stand in. jsdom computes no layout, so `getResizableSize()` (`resizer.ts:210-220`) can only be tested by replacing the window: `windowStub` (`resizer.spec.ts:50-60`) hands back a fixed `boxSizing`, `width` and `height`, and `getBoundingClientRect` is a `jest.spyOn` mock (`:336`). The box-model cases at `:323-344` therefore verify the branch, not the measurement — which matters, because that branch exists because of a shipped regression (`31b605079`, "measure element size in one box model"). Nothing in this repo drags a `kbqResizer` in a real browser except `dl`, whose Playwright suite does it properly (`dl/e2e.playwright-spec.ts:64-94`: real `mouse.down`/`mouse.move`, real `boundingBox()`, cursor and `aria-valuenow` assertions across a boundary and back). That suite is currently the resizer's only integration test, and it belongs to another package. Note that Playwright runs every context with `reducedMotion: 'reduce'` (`playwright.config.ts:101`), so any screenshots added here capture the reduced-motion state — irrelevant for this directive, which animates nothing, but worth knowing before baselining.
**Fix:** add `packages/components/resizer/e2e.ts` with three fixtures — a `content-box` resizable, a `border-box` one, and a bounded one with CSS `min-width`/`max-width` — each with a real, sized handle. Add `e2e.playwright-spec.ts` asserting: a drag changes the element's real `boundingBox()` by the pointer delta in both box models; a drag past a CSS bound and back returns to the correct size (the round trip `dl/e2e.playwright-spec.ts:79-91` proves for `dl`); the body cursor is applied during the drag and restored after; and, once RSZ-A11Y-01 lands, arrow-key resizing and tab-reachability. Add a touch-emulation drag for RSZ-BUG-01. Screenshots, if any, must be baselined only through `yarn run e2e:docker:update-snapshots`.

### P3 — Nice to have / hygiene

**RSZ-TEST-02 · Production code shaped by jsdom, and eight cases that dispatch the wrong event type** — `resizer.ts:194, 248-250, 253-255`; `resizer.spec.ts:36-48, 251-255, 291-320, 338-355, 370-381`.
Three pieces of the implementation exist to accommodate the test environment rather than any browser. `getPointerId` falls back to `1` (`:253-255`) — real `PointerEvent.pointerId` is always a number, so the `??` branch is only reachable from a plain `MouseEvent`, which is what the spec dispatches. `setPointerCapture` (`:194`), `hasPointerCapture` and `releasePointerCapture` (`:248-250`) are all called through `?.` — these are unconditionally present on `Element` in every browser; they are absent in jsdom, which is why the capture test has to `Object.defineProperties` them onto the element by hand (`resizer.spec.ts:251-255`). On the other side, the spec's own `createPointerEvent` helper (`:36-48`) builds a `MouseEvent` and patches `isPrimary`/`pointerId` onto it — but eight cases skip the helper and dispatch bare `new MouseEvent('pointerdown')` (`:291-320, 338-355, 370-381`), so they exercise the `?? 1` fallback rather than the pointer-id path that the cases above them go to some length to verify. The suite is good — 19 declarations covering cursor derivation, cursor restore under four different exit routes, pointer filtering and both box models — but its geometry half is testing the stub.
**Fix:** register `PointerEvent` (or a minimal shim) once in the Jest setup so the spec can construct real pointer events, then drop `createPointerEvent`'s patching and use it uniformly in all cases. With that in place, delete the `?? 1` fallback and the three `?.` on the capture methods — if a browser ever lacked them the drag would be silently uncaptured, which is worse than throwing. Convert the box-model cases to the e2e fixture from RSZ-TEST-01 and keep the Jest versions as branch tests only.

**RSZ-ARCH-02 · Package layout deviates from the documented structure, and two host classes are declared and styled by nobody** — `packages/components/resizer/` (9 files, no `.scss`, no `-tokens.scss`, no `_-theme.scss`, no `public-api.ts`, `module.ts` rather than `resizer.module.ts`); `resizer.ts:58, 75`; grep for `.kbq-resizer` / `.kbq-resizable` across `packages/` and `apps/` returns one hit, in the package's own example (`resizer-overview-example.ts:54`).
AGENTS.md's structure pattern asks for `<component-name>.module.ts` and `public-api.ts`; `resizer` has a bare `module.ts` (one of twelve packages that do) and no `public-api.ts` at all (54 of 64 packages have one) — `index.ts` re-exports `./module` and `./resizer` directly. The absent `.scss`, tokens and theme are *not* a defect on their own: the directive draws nothing, has no colour and no intrinsic dimension, so a theme mixin would be empty; that is a deliberate and correct choice, and the one style declaration it genuinely must own is filed separately as RSZ-BUG-01. What is odd is that both directives declare host classes — `kbq-resizable` (`:58`) and `kbq-resizer` (`:75`) — that nothing in the library styles and neither consumer targets: `dl` styles `.kbq-dl__resize-handle` and `content-panel` styles `.kbq-content-panel-container__panel-resizer`. The classes are a public hook with no baseline behind them, which is why every caller starts from zero on hit area and focus ring.
**Fix:** low priority and partly a judgement call. Rename `module.ts` to `resizer.module.ts` and add a `public-api.ts` only as part of a repo-wide sweep — twelve packages share the deviation and fixing one is churn. Either commit to the host classes by shipping a minimal `resizer.scss` giving `.kbq-resizer` a sane hit area and the `touch-action` from RSZ-BUG-01, or document in the guide that they are markers only (RSZ-DOC-01's "what the consumer owns" section is the right home for that sentence).

**RSZ-DOC-02 · Dead examples stubs, and an overview example built out of six inert handles and a `console.debug`** — `examples.resizer.en.md:1-5`, `examples.resizer.ru.md:1-5`, `apps/docs/src/app/structure.ts:838-849`; `resizer-overview-example.ts:14-34, 54-72, 82`.
Both `examples.resizer.*.md` carry the standard "🚧 Documentation in progress 🚧" stub. They are not a broken user surface — `structure.ts:848` sets `hasExamples: false`, so the Examples tab never renders for `resizer` and the files are unreachable — but they are two dead files that will keep surfacing in "in progress" greps. The single real example is weaker than it looks: `resizer-overview-example.ts` renders a 3×3 grid in which six of the nine cells are `[kbqResizer]="[0, 0]"` divs used purely as spacers (`:14, 17, 20, 23, 26, 34`), each carrying a `(sizeChange)` handler that can never fire and a full listener set that can never act (RSZ-PERF-01). The resizable itself is bounded by `min-width: 125px; max-width: 100%` (`:60-65`) with nothing clamping the emitted values, so the example demonstrates the exact situation RSZ-ARCH-01 describes without acknowledging it. And `sizeChanged` is a `console.debug` (`:82`) shipped in a published example.
**Fix:** delete both stub files — the guide already embeds the one example inline. Rewrite the example to use plain `<div>`s for the spacer cells and keep `[kbqResizer]` only on the three live handles; replace `console.debug` with a rendered size readout, which also demonstrates `sizeChange` (the output the guide never mentions, RSZ-DOC-01); and either add clamping in the handler or drop the CSS bounds, so the example does not model the divergence.

**RSZ-API-02 · API report hygiene: a public DOM handle and an undocumented module** — `tools/public_api_guard/components/resizer.api.md:9-16, 35-43`; `resizer.ts:62-67`.
`KbqResizable` exposes `readonly element: HTMLElement` as a public member (`resizer.api.md:11`). It is marked `@docs-private` in the source (`resizer.ts:63-66`), but that is a koobiq docs-site convention, not an API Extractor directive — it does not strip the member from the report, exactly as `@internal` does not (`project_api_guard_internal_not_stripped`). So the published surface includes a raw DOM handle to a consumer's element, which anyone can read and mutate. `KbqResizerModule` is the only `// @public (undocumented)` entry in the report (`:35`) — every other top-level export has a doc comment. Note the standard hazard before fixing the latter: adding a JSDoc block removes the `(undocumented)` marker and therefore changes `resizer.api.md`, so `check-api` fails until `approve-api` is re-run.
**Fix:** if `element` must stay public for the `KbqResizer`→`KbqResizable` link, that is defensible — but then say so with a real `/** */` block explaining the contract, and consider narrowing the link to an `InjectionToken` exposing only what `KbqResizer` uses (`getBoundingClientRect` and a style target), per the AGENTS.md rule that a child depending on its host should inject a narrow token rather than the host's concrete class. Add a one-line JSDoc to `KbqResizerModule`. Fold both into the single `build:components` + `approve-api` cycle that RSZ-API-01 already requires.

## 4. Recommended Remediation Phases

**Phase 1 — Make the primitive operable and announced.**
IDs: RSZ-A11Y-01, RSZ-A11Y-02, RSZ-BUG-01. Add the keyboard layer, `role="separator"` with direction-derived `aria-orientation`, a locale-sourced accessible name, and the `touch-action` host binding. These are the three that reach real users and none of them depends on anything below — the keyboard path can route through the existing `sizeChange` so no consumer changes are needed to benefit. Ship with `jest-axe` over both consumer fixtures and the `dl` Playwright suite green, then delete `dl.component.ts:69-77, 251-269` and `dl.scss:71` and confirm nothing regresses; those deletions are the acceptance criterion.

**Phase 2 — Give the directive the bounds it is missing.**
IDs: RSZ-ARCH-01, RSZ-API-01. Add `min`/`max`, `disabled`, `resizeEnd`, the `disableStyleWrite` opt-out, and the `cursor` rename. `min`/`max` are a prerequisite for the `aria-value*` triple and for `Home`/`End` from Phase 1, so this phase closes them out. One `yarn run build:components && yarn run approve-api` cycle. Then simplify `content-panel.ts:392-397` and `dl.component.ts:305-313` to prove the new inputs actually removed work rather than adding a second way to do it.

**Phase 3 — Build the browser coverage this package has never had.**
IDs: RSZ-TEST-01, RSZ-TEST-02. Add `e2e.ts` and `e2e.playwright-spec.ts` with the three fixtures, move the geometry assertions off the `getComputedStyle` stub, register a real `PointerEvent` in Jest, and delete the `?? 1` and the three optional-chained capture calls. Best done immediately after Phase 1 in practice — the keyboard and touch behaviour added there cannot be verified any other way.

**Phase 4 — Repair the published contract and tidy the package.**
IDs: RSZ-DOC-01, RSZ-DOC-02, RSZ-API-02, RSZ-PERF-01, RSZ-ARCH-02. Rewrite both guides around a snippet that works and document all four members; rebuild the overview example; delete the dead stubs; JSDoc the module and the `element` handle; move the three document subscriptions into the drag. The docs work is last only because it should describe the API that Phases 1–2 leave behind, not the one that exists today.

## Appendix A — Review Methodology

Findings were gathered by reading the complete package (all 9 files, 310 lines of `resizer.ts` and 385 of `resizer.spec.ts`), then cross-checking every candidate against four independent sources: the two in-repo consumers found by grepping `kbqResizer`/`kbqResizable`/`KbqResizer` across `packages/`, `apps/` and `tools/` (`content-panel`, `dl`, plus the docs example and dev app — no other call sites exist); `splitter`, which solves the same drag-to-resize problem with a different design and is the natural comparison; the API guard report (`tools/public_api_guard/components/resizer.api.md`, confirmed listed at `tools/api-extractor/config.json:42`); and the git history (5 commits, two of them substantive: `f42396102` added `resizeStart`, the `cursor` input and the document-cursor machinery for `dl` column resizing; `31b605079` fixed the box-model measurement regression). Consumer evidence is what turned the accessibility findings from opinion into fact — `dl` re-implements the missing layer in full and `content-panel` ships without it, and the divergence between them is visible in the tree rather than inferred.

Refuted during verification:
- **"The document listeners leak — nothing unsubscribes them."** Refuted. All five subscriptions carry `takeUntilDestroyed(this.destroyRef)` (`resizer.ts:152, 156, 160, 164, 168`), and `destroyRef.onDestroy(() => this.finishDrag())` (`:147`) restores the body cursor if the directive is destroyed mid-drag — with a test that proves it (`resizer.spec.ts:186-199`). The teardown is correct; the defect is *when* they subscribe, which is RSZ-PERF-01 and a performance finding, not a leak.
- **"Dragging past a consumer's clamp leaves a dead zone on reversal."** Refuted, and this was the most promising-looking candidate. `updateSize` recomputes from the pointer-*down* origin, `this.width + directionX * (x - this.x)` (`resizer.ts:301-302`), not from the previous move, so the raw size tracks the pointer absolutely and reversal takes effect immediately. `dl/e2e.playwright-spec.ts:79-91` asserts exactly that round trip in a real browser: drag to `x = 1` (well past the minimum), then back to `startX + 50`, and `aria-valuenow` immediately exceeds the minimum again.
- **"The comments about a 'size boundary' at `resizer.ts:193` and `:274` describe behaviour the directive does not implement."** Refuted. They describe the `cursor` input being driven from outside during a drag, which `dl.component.ts:315-334` does — switching to `e-resize`/`w-resize` at the bounds — and `dl/e2e.playwright-spec.ts:81-90` verifies. The comments are accurate; the `effect` at `resizer.ts:141-145` exists precisely to reflect that mid-drag change onto the body.
- **"`getResizableSize` reads the banned global `window`."** Refuted. It goes through `inject(KBQ_WINDOW)` (`resizer.ts:87`, used at `:211`) per the SSR rule, and the whole DOM path sits behind `afterNextRender` (`:149`) so it never runs on the server. SSR hygiene in this package is better than average.
- **"Emitting outputs from outside the Angular zone means consumers miss change detection."** Not asserted. Both emits happen inside `runOutsideAngular` (`resizer.ts:150, 197, 308`), but Angular's template output binding marks the view dirty independently of the zone, and both in-repo consumers write signals in their handlers. I could not demonstrate a missed update by static reading, and the rule here is that an unanchored finding is worse than a missing one, so it is recorded here rather than filed.

Corrected on verification:
- **RSZ-BUG-01** began as "the package is missing `-tokens.scss` and `_-theme.scss` per the AGENTS.md structure pattern". Reading the directive showed it paints nothing and has no intrinsic dimension, so a theme mixin would be empty and the omission is deliberate and correct. The finding was narrowed to the one style declaration the directive genuinely must own — `touch-action: none` — re-filed as a correctness bug with the `content-panel`/`dl` divergence as evidence, and the structural observation demoted to RSZ-ARCH-02 (P3).
- **RSZ-A11Y-01** was drafted as P1, on the argument that a low-level pointer primitive may legitimately be pointer-only (Angular CDK's `cdkDrag` is). It was raised to P0 after confirming `disableResizer` defaults to `false` (`content-panel.ts:288`) — so the inoperable handle is present in every content panel by default, not opt-in — and that the component offers no other keyboard route to the panel width (`content-panel.ts:252` is the only other key binding, and it closes the panel). A Level A failure shipped on by default in a documented component is a blocker.
- **RSZ-ARCH-01** was drafted as "the unclamped inline write overrides the consumer's clamped value and the panel visibly overshoots". Tracing both consumers showed each also binds `[style.min-width.px]`/`[style.max-width.px]` on the same element (`content-panel.ts:230, 232`, `dl.component.ts:62-63`), so CSS clamps what the directive wrote and the overshoot is invisible today. The wording was changed from a user-visible bug to a two-owners-one-property hazard, and the severity dropped from P1 to P2.
