# Koobiq `splitter` Component — Code Review & Improvement Plan

> Scope: `packages/components/splitter` (component + 3 directives, template, SCSS, theme mixin, Jest spec, e2e fixture + Playwright spec, user guides, API guard report, docs examples, dev app) · Commit `b665e503` · 2026-08-28
> Generated by a multi-dimension review (architecture, RxJS & lifecycle, correctness, accessibility, performance, public API/types, styles, tests, docs) with manual verification of every finding against the source, the in-repo sibling implementations (`resizer`, `dl`), the API guard report and the workspace compiler settings. 16 findings confirmed (P0×1, P1×3, P2×8, P3×4); 7 candidate findings refuted during verification (see Appendix A). This document is a review + roadmap; no source is modified by it.

## 1. Executive Summary

`KbqSplitterComponent` is a 673-line file holding four exported classes — the splitter, `KbqGutterDirective`, `KbqGutterGhostDirective` and `KbqSplitterAreaDirective` — that together implement drag-to-resize panes with an optional "ghost" preview bar. It is one of the oldest files in the library (present in the initial commit, `bebf3bbef`) and it shows: the last 20 commits touching it are Angular-version migrations, lint sweeps and docs moves, with exactly **one** behavioural fix in the whole history (`e702d5549`, an SSR guard on a single method). Nothing has ever been fixed in the drag math, because nothing tests it.

- **The splitter cannot be operated without a mouse.** `<kbq-gutter>` carries no `tabindex`, no `role`, no keydown handler — its only interaction is `(mousedown)` (`splitter.component.html:11`, `splitter.component.ts:68`). This is a WCAG 2.1.1 (Keyboard, Level A) failure on the component's *only* function, and AGENTS.md states WCAG AA minimums including focus management as a mandate. There is no consumer workaround: the gutter is rendered by the splitter's own template, not projected, so a consumer cannot attach `tabindex`/`keydown` from outside. Meanwhile `packages/components/dl/dl.component.ts:66-83` implements the full ARIA window-splitter pattern — `role="separator"`, `tabindex="0"`, `aria-orientation`, `aria-valuemin/now/max`, a localized `aria-label`, and Home/End/Arrow keyboard resizing — for the same interaction, in the same library (SPL-A11Y-01, SPL-A11Y-02).
- **The ghost's lower clamp has an inverted sign.** `minPos = leftPos[key] - leftMin` (`splitter.component.ts:504`) should add the left pane's minimum, not subtract it; the symmetric `maxPos` on the next line is correct. With a `min-width` on the first pane the ghost is allowed to travel that many pixels *past* the splitter's own origin, where `overflow: hidden` (`splitter.scss:9`) clips it out of sight, and the drop is then silently rejected by `resizeAreas` (`:521`). Every fixture in the repo — Jest, Playwright and the dev app — happens to put the un-constrained pane on the left, which is exactly why this has never been seen (SPL-BUG-01).
- **The drag mixes two different pixel spaces.** Offsets come from `event.screenX`/`screenY` (`:373-376, 488-491`) while everything they are compared against — `offsetLeft`, `offsetWidth`, computed `min-width` — is layout CSS pixels. The two coincide only at 100 % browser zoom; at 200 % the panes move twice as far as the cursor. The sibling `resizer` uses `event.x`/`event.y` (`resizer.ts:185-186`) (SPL-BUG-03).
- **The drag has no pointer capture and no teardown.** Listeners are attached with `renderer.listen('document', …)` and released only from the `mouseup` handler (`:415-425, 535-542`). Release the button outside the browser window and no `mouseup` arrives: `_isDragging` stays true, the ghost stays visible, the forced cursor stays, and `.kbq-splitter-area_resizing { pointer-events: none }` (`splitter.scss:15-17`) leaves the entire splitter's content dead until the user clicks again — at which point the panes jump to wherever the pointer happened to be. `ngOnDestroy` (`:362-364`) never releases them either. `resizer` guards all of this explicitly (`resizer.ts:147, 180, 194, 226`) (SPL-BUG-02).
- **The default drag mode has zero test coverage in either suite.** `useGhost` defaults to `false`, yet all three Jest ghost cases and the only Playwright fixture set `[useGhost]="true"` (`splitter.spec.ts:105, 123`, `e2e.ts:10`), and the one default-mode case never dispatches a `mousemove`. `resizeAreas` is therefore only ever reached through the ghost's mouseup path. Worse, jsdom returns `0` for every `offsetWidth`/`offsetLeft` in this workspace (verified), so both geometry assertions in the Jest spec (`:190-198, 247-262`) compare `0` with `0` and cannot fail (SPL-TEST-01).

Genuine strengths worth preserving: the `mousemove` listener is registered inside `ngZone.runOutsideAngular` and the move path writes styles straight through `Renderer2` (`:419-425, 619-625`), so a drag costs zero change-detection cycles per frame — better than several newer components in this library; `.kbq-splitter-area_resizing { pointer-events: none }` correctly neutralises `<iframe>`s inside panes, and the dev app carries a dedicated case for it (`template.html:19-26`); `KBQ_WINDOW` is used instead of the global; and the Playwright suite drives a real drag against real geometry (`e2e.playwright-spec.ts:34-71`), which is rarer in this repo than it should be. The architecture — flex `order` plus a gutter between every adjacent pair — is sound; the defects are in the arithmetic, the event model and the semantics laid over it.

## 3. Prioritized Findings (deduplicated, verified)

### P0 — Release blockers

**SPL-A11Y-01 · The splitter cannot be resized without a mouse, and consumers cannot fix it from outside** — `splitter.component.html:5-12`, `splitter.component.ts:62-71, 366-369`; contrast `packages/components/dl/dl.component.ts:66-83, 251-269`.
`<kbq-gutter>` is rendered by the splitter's own template with five bindings and one event: `(mousedown)="onMouseDown($event, $index, $index + 1)"` (`splitter.component.html:11`). The directive's host block adds one more mouse binding and three classes (`splitter.component.ts:64-69`). There is no `tabindex`, no `role`, no `keydown`, no `FocusMonitor`, no `focus`/`blur` handling anywhere in the 673-line file — a keyboard or switch-control user cannot move a pane boundary by any means. That is WCAG 2.1.1 (Keyboard, Level A) failed on the component's sole purpose, against an AGENTS.md rule that states WCAG AA minimums "including focus management" as a mandate. Two things make this a blocker rather than a gap. First, **there is no workaround**: the gutter is a view child of `KbqSplitterComponent`, not projected content, so a consumer has no element to attach `tabindex`/`(keydown)` to; the only escape is to stop using the component. Second, **the library already knows how to do this correctly** — `packages/components/dl/dl.component.ts:66-83` renders a resize handle with `role="separator"`, `aria-orientation="vertical"`, `tabindex="0"`, `cdkMonitorElementFocus`, a localized `aria-label`, and `(keydown)="handleResizeKeydown($event)"`, whose implementation (`dl.component.ts:251-269`) maps `Home`/`End` to the minimum and maximum and `ArrowLeft`/`ArrowRight` to a `keyboardResizeStep`, with `event.preventDefault()`. `dl` is a description list; `splitter` is the library's primary pane-resizing surface, and it is the one that is unreachable. Note this is a WCAG judgement plus an APG-pattern gap, not an automated AXE failure: axe-core does not flag an unknown custom element that carries no role, which is precisely why it has survived since the initial commit.
**Fix:** make the gutter a focusable window splitter. On `KbqGutterDirective`'s host block add `tabindex: '0'` (or `'-1'` when the splitter is `disabled`), `role: 'separator'`, and `'(keydown)': 'handleKeydown($event)'`. Extract the clamping arithmetic from `resizeAreas` (`:514-533`) into a single `resizeBy(leftArea, rightArea, delta)` primitive that both the pointer path and the keyboard path call — this is the reason SPL-BUG-01/SPL-BUG-03 should land first. Map `ArrowLeft`/`ArrowUp` and `ArrowRight`/`ArrowDown` to `±step` (default `10`, exposed as a `keyboardResizeStep` input mirroring `dl`), `Home`/`End` to the pane's minimum and maximum, `Enter` to toggle collapse-to-zero and back, and call `event.preventDefault()` on every handled key so arrows do not scroll the page. Guard with (a) a Jest case that focuses a gutter, dispatches `ArrowRight` and asserts the two adjacent areas' inline `width` changed by exactly one step, (b) a Playwright case in the style of `dl/e2e.playwright-spec.ts:80-131` that tabs to the gutter and asserts real `boundingBox()` movement, and (c) a `jest-axe` pass over the dev-app fixture.

### P1 — High

**SPL-BUG-01 · Inverted sign in the ghost's minimum-position clamp** — `splitter.component.ts:495-508`, specifically `:504`; masked by every fixture in the repo (`e2e.ts:10-13`, `splitter.spec.ts:105-108, 123-128`, `components-dev/splitter/template.html:9-17`).
During a ghost drag the component computes the two positions the ghost bar may occupy:

```
const minPos = leftPos[key] - leftMin;                                              // :504
const maxPos = rightPos[key] + (rightArea.area.getSize() || 0) - rightMin - currentGutter.size;  // :505
```

`maxPos` is right: the right pane's far edge, minus its minimum, minus the gutter's own thickness — the furthest the gutter may move while still leaving `rightMin` behind it. By the same reasoning `minPos` must be *the left pane's origin plus its minimum*, `leftPos[key] + leftMin`. The code subtracts. With a `min-width: 200px` on the first pane and `offsetLeft === 0`, `minPos` evaluates to `-200`, so `this.ghost()[key] = newPos < minPos ? minPos : …` (`:508`) permits the ghost to be dragged 200 px past the splitter's own left edge, where `.kbq-splitter { overflow: hidden }` (`splitter.scss:9`) clips it and it simply disappears from under the cursor. Releasing there computes a large offset (`:547-550`) which `resizeAreas` then rejects outright at `:521` — so the user drags, watches the bar vanish, lets go, and nothing happens. The reason this was never caught is uniform across all three harnesses: the Playwright fixture's left pane is `style="flex: 1"` with no minimum (`e2e.ts:11`), both Jest ghost hosts are the same shape (`splitter.spec.ts:106, 125`), and the dev app's ghost section also puts `dev-min-width-enabled` on the *second* pane (`template.html:10-11`). `getMinSize()` returns `NaN` for a pane with no explicit minimum (computed `min-width` is `auto`/`""`; verified in this workspace's jsdom), and `NaN || 0` at `:500` collapses it to `0`, which makes the sign error invisible.
**Fix:** change `:504` to `const minPos = leftPos[key] + leftMin;`. Then add the missing regression fixture: a second e2e block whose **first** pane carries `min-width: 120px`, asserting that the ghost's `left` never drops below the pane's origin plus 120 and that the pane lands exactly on its minimum. While in this method, replace `getMinSize() || 0` with an explicit `Number.isFinite` normalisation so a `NaN` minimum is a deliberate `0` rather than an accident, and mirror the same normalisation into `resizeAreas` (`:518-521`), where a `NaN` minimum currently disables the guard through comparison semantics rather than by intent.

**SPL-BUG-02 · Mouse-only drag with no pointer capture, no button guard and no teardown; a lost `mouseup` freezes the whole splitter** — `splitter.component.ts:366-428, 535-542, 362-364`; contrast `packages/components/resizer/resizer.ts:147, 163-169, 180, 194, 226`.
`onMouseDown` registers `document` `mouseup` and `mousemove` listeners and stores their unsubscribe functions in `this.listeners` (`:415-425`); the array is drained only from `onMouseUp` (`:536-542`). Four consequences follow, and the sibling `resizer` — written later, for the same interaction — guards against every one of them. (1) **No pointer capture.** Release the button outside the browser window and the document never sees `mouseup`: `_isDragging` stays `true`, the listeners stay attached, the ghost stays visible (`:400`), the forced `row-resize`/`col-resize` cursor stays on the host (`:401-404`), and `.kbq-splitter-area_resizing { pointer-events: none }` (`splitter.scss:15-17`) keeps every pane's content unclickable. The splitter is stuck until the user clicks again — and that click ends the drag wherever the pointer happens to be, resizing the panes unintentionally. `resizer.ts:194` calls `setPointerCapture` and `resizer.ts:226` additionally ends the drag on the first move that reports `!event.buttons`. (2) **No touch or pen support.** `mousedown`/`mousemove` are the only inputs; a touch drag on the gutter produces no compatibility `mousemove` stream, so the splitter is inoperable on touch devices. `resizer` uses `pointerdown`/`pointermove`/`pointerup`/`pointercancel`/`lostpointercapture` (`resizer.ts:151-169`). (3) **No button guard.** Any button starts a drag; `resizer.ts:180` requires `event.button === 0 && event.isPrimary !== false` and refuses to start a second drag while one is active. (4) **Nothing releases the drag on destroy.** `ngOnDestroy` (`:362-364`) unsubscribes `areasChangeSubscription` and nothing else, so a splitter destroyed mid-drag (route change, an `@if` above it) leaves two document listeners holding a closure over the destroyed component and its areas. `resizer.ts:147` is a one-liner: `this.destroyRef.onDestroy(() => this.finishDrag());`.
**Fix:** port the `resizer` model. Replace the `mousedown` host/template bindings with `pointerdown`, add `pointercancel` and `lostpointercapture` alongside `pointerup`, call `gutterElement.setPointerCapture(event.pointerId)` on start and release it in a single `finishDrag()` that also drains `this.listeners`, track `activePointerId` and ignore events from any other pointer, add the `event.button !== 0 || event.isPrimary === false` guard, treat `!event.buttons` on a move as an implicit end, and register `inject(DestroyRef).onDestroy(() => this.finishDrag())`. Guard with a Playwright case that presses on the gutter, moves outside the viewport, dispatches `pointercancel`, and asserts the ghost is hidden and the panes are still clickable; and a Jest case that destroys the fixture mid-drag and asserts a subsequent `document` `mousemove`/`pointermove` reaches no handler.

**SPL-A11Y-02 · No separator semantics: no role, no orientation, no value range, no name, and an invalid `disabled` attribute** — `splitter.component.ts:62-71`, `splitter.component.html:5-12` (esp. `:6`), `_splitter-theme.scss:16-20`; contrast `packages/components/dl/dl.component.ts:69-78` and `packages/components/dl/e2e.playwright-spec.ts:80-131`.
The gutter's host block declares one class and three bindings and no ARIA at all (`splitter.component.ts:64-69`). To assistive technology `<kbq-gutter>` is an unknown element with no role, no name and no value — a screen-reader user is given no indication that a resizable boundary exists between two panes, let alone where it currently sits between its limits. The ARIA window-splitter pattern needs `role="separator"`, `aria-orientation` (which **is** valid on `separator`, unlike on `role="group"`), `aria-valuemin`/`aria-valuenow`/`aria-valuemax` describing the primary pane's size, `aria-controls` pointing at that pane, and an accessible name. The splitter has none. Separately, `[attr.disabled]="disabled || null"` (`splitter.component.html:6`) writes a bare `disabled` attribute onto a custom element, where it is not a real attribute and conveys nothing programmatically; it exists purely as a CSS hook for `_splitter-theme.scss:16-20`, and the correct spelling for both purposes is `aria-disabled`. The comparison is again internal: `dl.component.ts:69-78` binds `role`, `aria-orientation`, `tabindex`, `aria-label`, `aria-valuemin`, `aria-valuenow` and `aria-valuemax` on its handle, and `dl/e2e.playwright-spec.ts:80-131` asserts `aria-valuenow` actually tracks the drag. Like SPL-A11Y-01 this is a WCAG 1.3.1/4.1.2 judgement rather than an automated AXE failure.
**Fix:** on `KbqGutterDirective`'s host block add `role: 'separator'`, `'[attr.aria-orientation]': "isVertical ? 'vertical' : null"` (horizontal is the ARIA default for `separator`, so emit nothing there), and `'[attr.aria-disabled]': 'disabled || null'`, then drop `[attr.disabled]` from the template and switch the theme selector to `&[aria-disabled='true']`. Feed the value range from the splitter, which already has the numbers: `aria-valuemin` from the preceding area's `getMinSize()`, `aria-valuemax` from the pair's combined size minus the following area's minimum, `aria-valuenow` from the preceding area's `getSize()`, refreshed on drop and on every keyboard step from SPL-A11Y-01. Add a `resizePanes` entry to `KbqA11yLocaleConfiguration` (`packages/components/core/locales/en-US.ts:4-17` already carries `resizeColumns` for `dl`) and bind it through `kbqInjectA11yLocaleConfiguration()` as `aria-label`, with an input override. Cover with a Jest case per attribute and a Playwright case mirroring `dl/e2e.playwright-spec.ts:80-89` that asserts `aria-valuenow` moves with the drag.

### P2 — Should fix

**SPL-BUG-03 · Drag offsets are measured in screen pixels and applied to layout pixels** — `splitter.component.ts:373-376, 488-493, 496-508, 514-533`; contrast `packages/components/resizer/resizer.ts:185-186`.
The drag origin is `{ x: event.screenX, y: event.screenY }` (`:373-376`) and each move recomputes `{ x: event.screenX, y: event.screenY }` (`:488-491`), giving `offset = startPoint.x - endPoint.x` (`:493`). Every quantity that offset is then combined with is a layout measurement in CSS pixels: `initialSize` from `offsetWidth`/`offsetHeight` (`:627-631`), `getPosition()` from `offsetLeft`/`offsetTop` (`:633-638`), and `getMinSize()` from computed `min-width`/`min-height` (`:640-644`). `screenX` is reported in the screen's coordinate space and is not scaled by page zoom, while layout pixels are; the two are equal only at 100 % zoom. At 200 % browser zoom a 50-CSS-pixel cursor movement reports a 100-unit `screenX` delta, so the pane resizes twice as fast as the pointer and the ghost detaches visibly from the cursor — and browser zoom is not an exotic configuration but the assumed mechanism behind WCAG 1.4.4/1.4.10. A multi-monitor setup with per-display scaling produces the same divergence at 100 %. The correct reading is the viewport-relative pair, which is what `resizer.ts:185-186` uses (`this.x = event.x; this.y = event.y`). Neither test suite can see this: Playwright drives the mouse at an implicit 100 % page zoom, so `screenX` and `clientX` deltas coincide, and in jsdom every value involved is `0` (see SPL-TEST-01).
**Fix:** replace `screenX`/`screenY` with `clientX`/`clientY` (or `event.x`/`event.y` after the pointer migration in SPL-BUG-02) at `:374-375` and `:489-490`. Because both `startPoint` and `endPoint` change together the fix is behaviour-neutral at 100 % zoom, so the existing Playwright assertion (`e2e.playwright-spec.ts:69-70`) remains a valid regression guard. Add a Playwright case that sets a non-unit page zoom (`page.evaluate(() => document.body.style.zoom = '2')` or a CDP `Emulation.setPageScaleFactor`) and asserts a 30-pixel cursor move still produces a 30-pixel pane delta.

**SPL-BUG-04 · No RTL handling anywhere: a horizontal splitter resizes the wrong pane under `dir="rtl"`** — `splitter.component.ts:450-452, 493, 502-508, 514-533, 633-638`; the whole package contains no reference to `Directionality`, `dir`, or `rtl` (verified by grep across all 16 files).
`isVertical()` (`:450-452`) is the component's only notion of axis; the horizontal branch treats the flex main axis as strictly left-to-right. `offset = startPoint.x - endPoint.x` (`:493`) is a physical delta, and `resizeAreas` applies `-offset` to the *logically first* area (`:515`) — the one with flex `order: 0`. Under `dir="rtl"` a `flex-direction: row` container lays `order: 0` out on the **right**, so dragging the cursor to the right (which should shrink the order-0 pane) grows it: the drag is inverted, and every gutter moves the opposite way from the pointer. The ghost path is worse, because `getPosition()` returns `offsetLeft` (`:635`, `:135`), a physical measurement, and `KbqGutterGhostDirective` positions itself with the physical `left` (`:170`); so `minPos`/`maxPos` (`:504-505`) are computed from the *physical* left pane's origin while `leftArea`/`rightArea` are the *logical* pair, and the clamps end up applied to the wrong boundary entirely. RTL is not hypothetical in this library: `accordion.ts:2`, `app-switcher.ts:1` and `actions-panel-config.ts:1` all consume `@angular/cdk/bidi`, so a consuming application that sets `dir="rtl"` gets a correct accordion and a backwards splitter in the same page.
**Fix:** inject `Directionality` and negate the horizontal delta when `dir === 'rtl'` — a single `const dirSign = !this.isVertical() && this.dir.value === 'rtl' ? -1 : 1;` applied to `offset` at `:493` fixes the non-ghost path. For the ghost, express the clamps in logical terms: compute the gutter's allowed travel as an interval on the *inline* axis and convert to `left` only at the point of writing, or switch `KbqGutterGhostDirective` to `inset-inline-start` (`:170`) so the browser resolves the direction. Subscribe to `Directionality.change` and re-run the layout side of `ngOnInit` (see SPL-BUG-05). Guard with a Playwright case: the existing `E2eSplitterGhost` fixture inside a `dir="rtl"` wrapper, asserting a rightward drag *shrinks* the first pane.

**SPL-BUG-05 · `direction` and `gutterSize` are silently init-only inputs** — `splitter.component.ts:284-291, 320-334, 347-353, 120-131, 595-606`; the ghost is reactive at `:196-199, 210-213`, proving the pattern was known.
All three classes apply their layout in `ngOnInit`/`ngAfterViewInit` and never again. `KbqSplitterComponent.ngOnInit` writes the host's `flex-direction` once (`:352`). `KbqGutterDirective.ngOnInit` writes `flex-basis`, the cross-axis dimension, `order` and `flex-direction` once (`:120-131`) — so a later `[gutterSize]` change updates `_gutterSize` (`:328-332`) and the input binding on the gutter, but no style. `KbqSplitterAreaDirective.ngAfterViewInit` writes `width: 100%` or `height: 100%` on the axis that was current at init (`:598-606`). Bind `[direction]` to a signal and flip it at runtime and the result is a splitter that has swapped its gutter cursors (`[class.kbq-gutter_vertical]` is a live binding, `:66`) and its resize arithmetic (`isVertical()` reads the current value, `:450-452`) but kept its old `flex-direction`, its old gutter dimensions, and its areas stretched along the wrong axis — a visually broken layout with no error. The inconsistency is internal, not merely theoretical: `KbqGutterGhostDirective`'s `direction` and `size` setters both call `updateDimensions()` (`:196-199, 210-213`), so the ghost *is* reactive while the real gutter is not. The Jest cases that look like they cover this (`splitter.spec.ts:154-172`) assign `direction` before the fixture's first `detectChanges()`, so they only ever exercise the initial value.
**Fix:** move every layout write out of the lifecycle hooks. Express the host's `flex-direction`, the gutter's `flex-basis`/`width`/`height`/`order` and the area's `width`/`height` as host style bindings driven by the current input values — `'[style.flexDirection]': "isVertical() ? 'column' : 'row'"` and so on — which makes them reactive for free and removes 11 imperative `renderer.setStyle` calls. Where a binding is impractical (the area's axis flip depends on the parent), migrate the inputs to signals (SPL-ARCH-01) and drive the writes from an `effect()`. Guard with Jest cases that flip `[direction]` and change `[gutterSize]` *after* the first `detectChanges()` and assert the inline styles follow.

**SPL-LIFE-01 · Every area subscribes to the splitter's output and never unsubscribes** — `splitter.component.ts:582, 595-609, 611-613, 670-672`; Angular semantics at `node_modules/@angular/core/fesm2022/resource.mjs:39-62`.
`KbqSplitterAreaDirective.ngAfterViewInit` ends with `this.splitter.gutterPositionChange.subscribe(this.emitSizeChange)` (`:608`), and `ngOnDestroy` (`:611-613`) calls only `this.splitter.removeArea(this)` — the returned `OutputRefSubscription` is discarded. `OutputEmitterRef` cleans up its listeners when *its owner* is destroyed, i.e. when the splitter goes away, not when a subscriber does; so an area destroyed while its splitter lives — exactly the `splitter-dynamic-data` scenario shipped as a documented example (`packages/docs-examples/components/splitter/splitter-dynamic-data/splitter-dynamic-data-example.ts:18-20`) and covered by `splitter.spec.ts:266-289` — stays in the splitter's `listeners` array forever. Two consequences. First a leak: the closure retains the destroyed directive, which retains its `ElementRef` and therefore a detached DOM subtree, for the entire lifetime of the splitter, and the array grows by one on every toggle. Second, noise and a false signal: on every subsequent drop, `emitSizeChange` (`:670-672`) fires on the destroyed directive and calls `this.sizeChange.emit(...)`, which Angular answers with `console.warn('Unexpected emit for destroyed OutputRef…')` (`resource.mjs:56-62`) — one warning per destroyed area per drop, in every consumer's console.
**Fix:** capture the subscription and release it — `private readonly subscription = …` assigned at `:608` and `this.subscription?.unsubscribe()` added to `ngOnDestroy`, or more idiomatically `this.splitter.gutterPositionChange.subscribe(this.emitSizeChange)` replaced with the `takeUntilDestroyed(inject(DestroyRef))` form used elsewhere in the repo. Better still, invert the dependency: have `onMouseUp` (`:557-562`) walk `this.areas` and call each area's emit directly, which removes the cross-object subscription entirely. Guard with a Jest case that toggles an `@if`-wrapped area off, performs a drag, and asserts the removed host's `sizeChange` handler was not called and no `console.warn` was emitted.

## Appendix A — Review Methodology

Findings were gathered by reading every file in the package (four `.ts`, one `.html`, two `.scss`, four `.md`, plus `index.ts`/`public-api.ts`/`ng-package.json`, the Jest spec and the e2e pair), then cross-checking each candidate against five independent sources: the workspace compiler settings (`tsconfig.json:20, 114-118`), the API guard report and `tools/api-extractor/config.json:49`, the docs structure entry (`apps/docs/src/app/structure.ts:69, 922-933`), every in-repo usage found by grep (the dev app, `components-dev/all`, `components-dev/popover`, and the five docs examples — the splitter has **no** consumer inside `packages/components/`), and the two sibling implementations of the same interaction, `packages/components/resizer/resizer.ts` and `packages/components/dl/dl.component.ts`. Those two siblings are what turned several style opinions into confirmed defects: `resizer` already solves pointer capture, the button guard, the lost-`mouseup` case and destroy-time teardown, and `dl` already ships the complete ARIA window-splitter pattern with keyboard resizing — so for every gap in this package the library contains a working reference, written by the same team. Angular's `OutputEmitterRef` semantics were read from `node_modules/@angular/core/fesm2022/resource.mjs:26-72`; jsdom's layout and CSSOM behaviour was verified directly rather than assumed; design tokens were checked against `@koobiq/design-tokens/web/new/css-tokens-{light,dark}.css`. Git history (20 commits, of which exactly one is a behavioural fix) informed the test-coverage severities.

Refuted during verification:
- **"Dynamically added areas are registered twice — `addArea` pushes while `areaRefs.changes` has already rebuilt the array"** (`splitter.component.ts:342-345, 356-359`) — refuted. Angular's `refreshView` refreshes embedded views *before* it refreshes content queries, so an `@if`-added area's `ngAfterViewInit` (and its `addArea` push) runs before `areaRefs.changes` emits; the subsequent `this.areas = data.map(this.mapAndOrderArea)` replaces the array wholesale and re-derives every `order` from DOM order, discarding the transient duplicate inside the same change-detection pass. The shipped `splitter-dynamic-data` example toggles exactly this path. The redundant `detectChanges()` it costs is filed under SPL-ARCH-01 instead.
- **"`StyleProperty.MinWidth = 'minWidth'` is camel-cased while `MinHeight = 'min-height'` is dashed, so `getMinSize()` reads `undefined` for horizontal splitters"** (`:46-47, 640-644`) — refuted as a runtime defect. CSSOM defines both a dashed and a camel-cased attribute for every hyphenated property, and this workspace's jsdom honours both (`getComputedStyle(el)['min-width']` and `['minWidth']` each return `"10px"`; verified). The inconsistency is real but cosmetic, and is filed under SPL-ARCH-01.
- **"`reducedMotion: 'reduce'` (`playwright.config.ts:101`) bakes a frozen animation into the committed screenshots"** — not applicable to this package. `splitter.scss` and `_splitter-theme.scss` contain no `transition` or `animation`, and there is no `__screenshots__` directory at all — the Playwright suite is purely assertion-based. Recorded because the setting is a genuine trap for sibling packages that do animate.
- **"`getPosition()` lacks the `platform.isBrowser` guard that `getSize()` received in DS-5266, so SSR breaks"** (`:633-638`, `:133-138` vs `:628`) — refuted. Both `getPosition()` implementations are reachable only from `onMouseDown`/`onMouseMove`/`onMouseUp`, which never execute during server rendering. The asymmetry is untidy, not broken.
- **"Dragging over an `<iframe>` loses the drag"** — refuted for iframes inside the splitter. `.kbq-splitter-area_resizing { pointer-events: none }` (`splitter.scss:15-17`) is applied to every area for the duration of the drag via `[class.kbq-splitter-area_resizing]="isResizing()"` (`:574`), and the dev app carries a dedicated "With iframe inside" case (`components-dev/splitter/template.html:19-26`). Iframes *elsewhere on the page* remain a hazard, which is one more argument for the pointer capture in SPL-BUG-02.
- **"`@use '../core/styles/common/tokens' as *;` at `_splitter-theme.scss:1` is a dead import"** — true but not a defect: 20+ sibling theme files carry the same import as a house convention, and removing it here alone would be noise.
- **"`gutterPositionChange` fires on a click that never moved the gutter"** (`:557-562`) — real but deliberate: `splitter.spec.ts:185-198` asserts exactly this behaviour (a `mousedown` immediately followed by a `mouseup` must emit once). Left as documented behaviour rather than filed; worth revisiting only if the output is ever renamed to something that implies movement.

Corrected on verification:
- **SPL-BUG-01** was drafted as "the ghost can be dragged past a pane's minimum". Reading `:504-505` side by side showed the two clamps are not merely loose but asymmetric — `maxPos` is correct and `minPos` has an inverted sign — which both widens the impact (the ghost leaves the splitter's box entirely and the drop is then silently rejected) and reduces the fix to one character. Severity raised from P2 to P1.
- **SPL-TEST-01** was drafted as "thin unit coverage — add cases". Verifying jsdom's layout behaviour (`offsetWidth`/`offsetLeft` are unconditionally `0`) showed the two geometric cases are not thin but *vacuous*: both sides of every size assertion evaluate to `0`, so they cannot fail. The finding changed from "add cases" to "the existing cases prove nothing", and the discovery that no fixture anywhere uses the default `useGhost: false` was folded in.
- **SPL-A11Y-01** was initially drafted together with the ARIA gap as a single P1. It was split out and raised to P0 once `splitter.component.html:5-12` confirmed the gutter is a view child of the splitter's own template rather than projected content — which removes the consumer workaround that would otherwise have capped the severity.
