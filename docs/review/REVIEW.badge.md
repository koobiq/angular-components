# Koobiq `badge` Component — Code Review & Improvement Plan

> Scope: `packages/components/badge` (component, styler directive, caption directive, tokens, theme, SCSS, Jest spec, e2e fixture + Playwright spec, user guides, examples, API guard report) plus its in-repo consumers, the docs examples and the dev app · Commit `b665e503` · 2026-08-28
> Generated by a multi-dimension review (architecture, correctness, lifecycle, accessibility, public API/types, styles, tests, docs) with manual verification of every finding against the source, the consumers, the design tokens and `tools/public_api_guard`. 10 findings confirmed (P0×0, P1×2, P2×6, P3×2); 5 candidate findings refuted during verification (see Appendix A). This document is a review + roadmap; no source is modified by it.

---

## 1. Executive Summary

`KbqBadge` is a small status chip: a 146-line file holding an 11-value colour enum, the component itself, a marker directive for the caption, and a second directive that positions projected icons. The component renders correctly in every configuration the repository actually exercises — and the two most serious findings are both about configurations it *doesn't* exercise, which the API nevertheless allows.

- **`[outline]="true"` is unstyled for five of the eleven colours.** `_badge-theme.scss:71-95` emits outline rules only for the five `fade-*` colours and `disabled`; `contrast`, `theme`, `success`, `warning` and `error` have no outline rules and no outline tokens (`badge-tokens.scss:74-103`). `<kbq-badge [outline]="true" [badgeColor]="colors.Error">` therefore renders with no colour, no background and an unset `border-color`, silently. Every fixture in the repo dodges it: the e2e component keeps a separate `outlineColors` list (`e2e.ts:51-58`), and all 8 outline usages across docs examples and the dev app use `fade-*` or `disabled` (BDG-CSS-01).
- **Half the component's behaviour lives in a second standalone directive that nothing forces you to import.** `KbqBadgeCssStyler` (`badge.component.ts:49-112`) owns all icon spacing and is applied only through `KbqBadgeModule`. Two places in the repo already import `KbqBadge` on its own — `dl/e2e.ts:2` and the published `file-upload-primitive` example (`file-upload-primitive-example.ts:2, 29`) — and get a badge with no icon spacing and no diagnostic. The sibling `button` package has exactly this split and guards it twice: `KbqButton` injects the styler (`button.component.ts:340`) and the styler warns in dev mode when it is applied without its component (`button.component.ts:195`). Badge has neither (BDG-ARCH-01).
- **`badgeColor` cannot round-trip.** The setter stores the raw value, the getter returns `` `kbq-badge_${value}` `` (`badge.component.ts:136-143`), and the host binds the getter into `[class]` (`:125`). So `badge.badgeColor = badge.badgeColor` yields the class `kbq-badge_kbq-badge_error`, which matches no rule — and the published type says the input takes `string`, so nothing stops it (BDG-API-01).
- **The styler runs `detectChanges()` on the parent view to maintain a field nobody reads.** `isIconButton` (`:60, 84-87`) is written, compared against itself, and never used — it is a copy of `button.component.ts:133-134`, where the same value drives host classes. In badge it drives one `cdr.detectChanges()` call from inside an `effect()`, i.e. a synchronous re-entrant change-detection run on the parent component for no observable effect (BDG-LIFE-01).
- **Icon spacing is derived from DOM child order and fails quietly off the happy path.** `findIndex` over the host's child nodes (`:98`) assigns the left class at index 0 and the right class at the last index; an icon anywhere in the middle gets neither, and so does an icon wrapped in any element. `getNodesWithoutComments` (`core/utils/utils.ts:28-32`) filters comment nodes only, so text nodes participate in the indexing (BDG-BUG-01).

Genuine strengths worth preserving: the colour system is entirely token-driven with a generated theme mixin, so light/dark comes free and there is not one hardcoded colour in the package; the async-icon fix (`bbb12c9bf`, DS-5272) is well done — the `effect()` at `:69` correctly re-runs class assignment when icons arrive behind an `@if`, and it shipped with both a Jest case and a Playwright assertion that measures the computed margin (`e2e.playwright-spec.ts:19-29`) rather than only a screenshot. The Playwright suite covers all 11 colours × compact × light/dark in two screenshots. For a component of this size the visual layer is in good shape; the debt is in the API and in what the fixtures avoid.

## 3. Prioritized Findings (deduplicated, verified)

### P0 — Release blockers

None.

### P1 — High

**BDG-CSS-01 · `outline` is silently unstyled for the five solid colours** — `_badge-theme.scss:71-95`, `badge-tokens.scss:74-103`, `badge.component.ts:124, 132`; fixtures that avoid it: `e2e.ts:51-58`, `docs-examples/components/badge/badge-overview/badge-overview-example.html:51-77`, `components-dev/badge/template.html:216-226`.
`KbqBadgeColors` has eleven members (`badge.component.ts:20-33`) and `outline` is a plain boolean input (`:132`) that toggles `.kbq-badge-outline` (`:124`), so all eleven combinations are reachable from the API and all eleven type-check. The theme emits outline rules for six of them — the five `fade-*` values and `disabled` (`_badge-theme.scss:72-94`) — and the token file mirrors that: every `--kbq-badge-outline-*` token is `fade-on-*` or `fade-on-disabled` (`badge-tokens.scss:74-103`). For `contrast`, `theme`, `success`, `warning` and `error` there is no `.kbq-badge-outline.kbq-badge_<colour>` rule at all, so the badge keeps the base rule only: `border-style: solid` with a width from `--kbq-badge-size-normal-border-width` and **no** `border-color`, which falls back to `currentColor`, itself unset because no rule set `color`. The result is a washed-out chip whose appearance depends on inherited text colour — no error, no warning, no failing test. That this is a gap rather than a decision is visible in how carefully the repo tiptoes around it: `E2eBadgeStyles` renders `Object.values(KbqBadgeColors)` for filled (`e2e.ts:50`) but a hand-curated six-value `outlineColors` list for outline (`:51-58`), and all eight outline usages in docs examples and the dev app stay inside that same six.
**Fix:** decide and enforce. If outline is intended only for fade colours, make the API say so — narrow `badgeColor` to a union type, or drop `.kbq-badge-outline` to a no-op with a dev-mode warning for unsupported combinations — and document it in the guide. If all eleven should work, add the missing five outline blocks to `_badge-theme.scss` plus their `--kbq-badge-outline-fade-off-*` tokens, and switch `E2eBadgeStyles` to `Object.values(KbqBadgeColors)` for the outline rows too; that screenshot is the regression guard, and it must be produced through `yarn run e2e:docker:update-snapshots`.

**BDG-ARCH-01 · Icon spacing lives in a second standalone directive that nothing links to the component** — `badge.component.ts:49-52, 114-127`, `badge.module.ts:6-19`; consumers importing the component alone: `packages/components/dl/e2e.ts:2, 7`, `packages/docs-examples/components/file-upload/file-upload-primitive/file-upload-primitive-example.ts:2, 29`; precedent at `button/button.component.ts:195, 340`.
`KbqBadgeCssStyler` is declared with the same selector as the component (`kbq-badge`, `:50` vs `:115`) and owns every icon-related class the styles depend on — `kbq-icon_left`, `kbq-icon_right`, `kbq-badge-icon_left`, `kbq-badge-icon_right`. Nothing connects the two: `KbqBadge` does not list it in `hostDirectives`, does not inject it, and the only thing that applies both is `KbqBadgeModule` (`badge.module.ts:10-12`). In an Angular v19+ codebase where standalone imports are the default, `imports: [KbqBadge]` is the natural spelling — and two places in this repository already write it, including a *published documentation example*. Both happen to render text-only badges today, so nothing is visibly broken; the moment either adds an icon, the margins from `badge.component.scss:31-37` never apply, because no element ever receives `kbq-icon_left`/`kbq-icon_right`. The library has already solved this once next door: `KbqButton` injects `KbqButtonCssStyler` (`button.component.ts:340`), which makes a missing styler a hard DI failure, and the styler itself warns in dev mode when it cannot find its component (`button.component.ts:195`). Badge has neither guard. (The module file also imports `A11yModule` and `PlatformModule` (`badge.module.ts:8-9`), neither of which any badge class uses — the file is legacy scaffolding that nobody has re-read.)
**Fix:** add `hostDirectives: [KbqBadgeCssStyler]` to `KbqBadge` and drop the styler from the module's `imports`/`exports` — one line, no behaviour change for module consumers, and standalone consumers stop silently losing half the component. Keep the class exported for one minor for backwards compatibility, then deprecate it. If `hostDirectives` is rejected (it changes the API report), mirror the button: `protected styler = inject(KbqBadgeCssStyler)` in `KbqBadge`. Either way, delete the two unused CDK module imports. Regression test: a Jest case whose host imports `KbqBadge` alone, projects an icon, and asserts `kbq-icon_right` is present — it fails today.

### P2 — Should fix

**BDG-API-01 · `badgeColor`'s getter and setter speak different languages, so the input cannot round-trip** — `badge.component.ts:125, 134-145`, `tools/public_api_guard/components/badge.api.md:21-22`.
The setter takes a raw colour (`'error'`, or `KbqBadgeColors.Error`) and stores it verbatim, defaulting empty values to `fade-contrast` (`:141-143`). The getter returns the *CSS class* built from it, `` `kbq-badge_${this._badgeColor}` `` (`:137-139`), because the host binds it straight into `[class]` (`:125`). The published signature admits the asymmetry without explaining it: `get badgeColor(): string; set badgeColor(value: string | KbqBadgeColors)` (`badge.api.md:21-22`). Consequences: reading the property gives a value that is invalid to write back, so `[badgeColor]="badge.badgeColor"`, a `[(badgeColor)]`-shaped pattern, or any state round-trip through a store produces `kbq-badge_kbq-badge_error` — a class that matches nothing in `_badge-theme.scss`, so the badge loses all colour with no diagnostic. The input type `string` also accepts a typo (`'succes'`) with the same silent outcome, and the `TODO: Skipped for migration because: Accessor inputs cannot be migrated as they are too complex` (`:134-135`) is untrue — the body is one `||` default.
**Fix:** make the input a signal that stores the semantic value and compute the class separately: `readonly badgeColor = input<KbqBadgeColors | KbqEnumValues<KbqBadgeColors>>(KbqBadgeColors.FadeContrast)` plus `protected readonly colorClass = computed(() => \`kbq-badge_${this.badgeColor()}\`)` bound to `[class]`. That fixes the round-trip, tightens the type against typos, and removes the false TODO. It changes the API report, so run `yarn run build:components` then `yarn run approve-api` — build first, the guard reads `dist/*.d.ts`. Guard with a Jest case that writes `badge.badgeColor` back from a read and asserts a single `kbq-badge_*` class.

**BDG-LIFE-01 · An `effect()` calls `detectChanges()` on the parent view to maintain a field nothing reads** — `badge.component.ts:54, 60, 62-70, 77-87`; contrast with `button/button.component.ts:133-134, 226`.
`KbqBadgeCssStyler` injects the parent's `ChangeDetectorRef` with `skipSelf` (`:54`) and, inside the effect registered at `:69`, computes `currentIsIconButtonValue` and — when it differs from the previous value — assigns `this.isIconButton` and calls `this.cdr.detectChanges()` (`:84-87`). `isIconButton` is read nowhere: not in this file, not in the package's styles, not anywhere in `packages/` or `apps/` (the only other hits are `button.component.ts`, a different class, and the generated `llms-full.txt`). The pattern is a straight copy of `KbqButton`, where the same computation drives two host class bindings (`button.component.ts:133-134`) and therefore genuinely needs a change-detection pass. Here it buys nothing and costs something real: a synchronous `detectChanges()` on the *parent component's* view, issued from inside an effect that itself runs as part of change detection, on every transition of a value with no observers — exactly the re-entrancy that Angular's effect documentation warns about, and a hazard that grows with the size of the host component.
**Fix:** delete `isIconButton` and the `detectChanges()` call. If icon-only badges do need distinct styling later, express it as a host class binding on a `computed()` signal rather than a manual field plus a CD kick. If the field must stay for backwards compatibility (it is public in `badge.api.md:75`), keep it as a `readonly` signal with no CD side effect and deprecate it. Verify by asserting the async-icon spec still passes — it exercises the exact transition this code path was written for.

**BDG-BUG-01 · Icon spacing is derived from DOM child order and fails silently for any icon that is not first or last** — `badge.component.ts:78, 89-110`, `core/utils/utils.ts:28-32`.
`updateClassModifierForIcons` builds `filteredNodesWithoutComments` from the host's `childNodes` and looks each icon up with `findIndex(node => node === iconHostElement)` (`:98`), applying `kbq-icon_left` at index `0` and `kbq-icon_right` at the last index. Three consequences follow. (1) An icon in the middle — `text <kbq-icon/> text` — matches neither branch, so it gets no margin at all and sits flush against the surrounding text; the badge also gets neither `kbq-badge-icon_left` nor `kbq-badge-icon_right`. (2) An icon that is not a *direct* child (wrapped in a `<span>`, or projected inside a caption) is never equal to any entry of `childNodes`, so `findIndex` returns `-1` and again nothing is applied. (3) The helper filters comment nodes only (`utils.ts:29-31` — `nodeType !== 8`), so text nodes count as positions; that is deliberate and correct for the leading-text case the spec covers, but it means the whole assignment depends on how Angular's whitespace handling happens to have compiled the template, which no test pins down. The `filteredNodesWithoutComments.length > 1` guard (`:91`) additionally means a badge containing exactly one icon and nothing else gets no classes at all — intentional for icon-only badges, but undocumented and indistinguishable from the failure modes above.
**Fix:** replace positional DOM inspection with the structure the component already has: give the icons their spacing through CSS adjacency (`.kbq-badge > .kbq-icon:first-child`, `:last-child`) or through `:has()`, so no imperative class assignment is needed at all, and the middle case degrades to a defined rule rather than nothing. If the imperative path is kept, handle `iconIndex === -1` explicitly (warn in dev mode, like the button does) and add Jest cases for the middle icon, the wrapped icon and the icon-only badge — none of the three is covered today.

**BDG-API-02 · Dead content query, an `any[]` signal from an unnecessary `forwardRef`, public mutable fields, and constants duplicated from `core`** — `badge.component.ts:43-47, 56, 58-60, 129`; `tools/public_api_guard/components/badge.api.md:13-16, 26, 73-77, 96-99`; `core/utils/utils.ts:34-35`; `tools/check-public-api-any/baseline.json` (badge: 1).
Four surface defects in one small file. (1) `readonly iconItem = contentChild(KbqIconItem)` (`:129`) is never read — not in the class, not in the template (`'<ng-content />'`, `:116`) — yet it is published (`badge.api.md:26`) and compiled into the component's content queries (`badge.api.md:30`, `["iconItem"]`), so every badge instance runs a query for nothing. (2) `contentChildren(forwardRef(() => KbqIcon))` (`:56`) types the result as `Signal<readonly any[]>` (`badge.api.md:73`) because `forwardRef` erases the type — and that single `any` is the entirety of badge's entry in the untyped-surface ratchet. The `forwardRef` is not needed: `KbqIcon` is imported eagerly at `:18` from `@koobiq/components/icon`, and `icon` does not import `badge` (verified by grep), so there is no cycle to break. (3) `nativeElement` and `isIconButton` are public mutable fields on a published directive (`badge.api.md:75, 77`) — consumers can reassign both. (4) `leftIconClassName`/`rightIconClassName` are declared at `badge.component.ts:43-44` and exported from the badge entry point (`badge.api.md:96-99`) while `core/utils/utils.ts:34-35` declares the same two constants with the same values; two published sources of truth for one CSS contract, free to drift.
**Fix:** delete `iconItem`; drop the `forwardRef` so `icons` types as `Signal<readonly KbqIcon[]>` and re-run `yarn run approve-public-api-any` to ratchet badge to zero; make `nativeElement` and `isIconButton` `private`/`readonly` (or delete the latter per BDG-LIFE-01); and re-export `leftIconClassName`/`rightIconClassName` from `@koobiq/components/core` instead of redeclaring them. All four change `badge.api.md`, so fold them into one `build:components` → `approve-api` cycle together with BDG-API-01.

**BDG-A11Y-01 · An icon-only badge has no accessible name, and the code detects that exact case then discards it** — `badge.component.ts:60, 77-87, 114-127`; precedent at `button/button.component.ts:292`.
`KbqBadge` renders `<ng-content />` into a plain `<kbq-badge>` element with no `role` and no ARIA attributes (`:114-127`). For the ordinary text badge that is correct — the text is the accessible name and an extra role would add noise. But the component explicitly supports the icon-only form: `currentIsIconButtonValue` is precisely "every non-comment child is an icon, and there are at most two" (`:81-82`), and the styles have a dedicated code path for it. In that configuration the badge exposes no text at all, so a screen reader announces nothing; the status the badge encodes — the whole point of the component, per the guide's first line — is conveyed by colour and glyph only (WCAG 1.1.1 and 1.4.1). This is a judgement rather than an automated AXE failure: axe does not flag an unknown element carrying no role. The library's own answer to the same situation is one package away: `KbqButton` warns in dev mode when an icon button has no accessible name (`button.component.ts:292`), using the same `isIconButton` detection that badge computes and throws away.
**Fix:** in dev mode, warn when `isIconButton` is true and the host has neither `aria-label` nor `aria-labelledby` nor text content — the detection already exists, it just needs a consumer (which also gives BDG-LIFE-01's field a reason to live, if that is preferred to deleting it). Document in the guide that an icon-only badge requires an `aria-label`, and add one to the icon-only examples. Verify with a `jest-axe` case over an icon-only badge with and without a label.

**BDG-TEST-01 · Three Jest cases, none of which touch the inputs; the outline screenshot excludes the broken combinations** — `badge.component.spec.ts:25-27, 47-65`; `e2e.ts:51-58`; `e2e.playwright-spec.ts:8-13`.
The Jest suite asserts that the host gets `kbq-badge` (`:25-27`) and that an asynchronously projected icon gets `kbq-icon_right` plus `kbq-badge-icon_right` (`:54-65`). Nothing asserts `badgeColor` (its default, its `||` fallback, or the class it produces), `compact`, `outline`, `kbq-badge-caption`, or any icon layout other than trailing — which is why BDG-CSS-01, BDG-API-01 and BDG-BUG-01 are all invisible to CI. The async case uses `setTimeout` + `done` (`:58-64`) rather than `fakeAsync`/`tick`, so it depends on real timer ordering; the first `describe` wraps its `beforeEach` in `fakeAsync` (`:12-23`) without ever calling `tick`, and calls `TestBed.compileComponents()` without awaiting it (`:17`) — cargo-culted ceremony that does nothing. On the Playwright side the colour screenshot (`e2e.playwright-spec.ts:8-13`) is genuinely good for what it covers, but its fixture feeds outline a hand-curated colour list (`e2e.ts:51-58`), so the five unstyled combinations are outside the frame.
**Fix:** add Jest cases for the `badgeColor` default and class output, the empty-value fallback, `compact`, `outline`, the caption directive, and the icon positions from BDG-BUG-01; convert the async case to `fakeAsync` + `tick`. Change `outlineColors` to `Object.values(KbqBadgeColors)` once BDG-CSS-01 is resolved so the screenshot covers the full matrix. Mutation check: reverting `[class.kbq-badge_compact]` to a constant, or dropping the `||` default in the `badgeColor` setter, must each fail at least one case — today neither does.

### P3 — Nice to have / hygiene

**BDG-CSS-02 · `border: transparent` resets more than the colour, and nine declared tokens are never consumed** — `_badge-theme.scss:17-21`, `badge.component.scss:15, 22-25`, `badge-tokens.scss:3-8, 14-20`.
Two style-surface issues. (1) The theme's filled branch writes the shorthand `border: transparent` (`_badge-theme.scss:18`), which sets `border-color: transparent` but also resets `border-style` to `none` and `border-width` to `medium`, discarding the `solid` from `badge.component.scss:15` and the token width from `:23`. With `border-style: none` no border box is reserved, so a filled badge's content box is 2px wider and taller than an outline badge's at the same fixed height — text and icons shift by a pixel when `outline` is toggled. `border-color: transparent` is what was meant. (2) Nine of the twenty-four sizing tokens are declared and never referenced anywhere in the repository: the four `--kbq-badge-size-normal-icon-{left,right}-{width,height}`, the four `compact` equivalents, and `--kbq-badge-size-compact-vertical-padding` (`badge-tokens.scss:3-4, 6-7, 14-15, 17-18, 20`). They are part of the theming contract consumers can see, and setting any of them does nothing.
**Fix:** replace the shorthand with `border-color: transparent`, then re-run the colour screenshot to confirm the 1px shift disappears. Either delete the nine unused tokens or wire them up (the icon width/height pair looks like it was meant to size `.kbq-icon` inside the badge, which the styles currently leave to the icon component). Deleting is a visible change to the theming contract, so mention it in the changelog even though no rule consumes them.

**BDG-DOC-01 · The guide documents examples but not the API, and the `examples.badge.*` stubs are dead** — `badge.en.md:1-41`, `badge.ru.md`, `examples.badge.en.md:1-5`, `examples.badge.ru.md:1-5`, `apps/docs/src/app/structure.ts:373-374`.
The guide is a good read — six embedded examples, a recommendations section that draws a real line between badges and tags — but it contains no properties table and never names `badgeColor`, `compact`, `outline` or `kbq-badge-caption`. A consumer cannot learn from the documentation that `outline` exists at all, let alone that it works for six of eleven colours (BDG-CSS-01), or that a caption is available as a projected `[kbq-badge-caption]` element. `KbqBadgeCaption` (`badge.component.ts:35-41`) is documented nowhere outside the dev app, which uses it 12 times. Separately, `examples.badge.en.md`/`.ru.md` carry the standard "🚧 Documentation in progress 🚧" stub while `structure.ts:374` sets `hasExamples: false`, so — as with `divider` — the Examples tab never renders and the two files are simply unreachable.
**Fix:** add a properties section to both guides covering the three inputs (with the outline/colour matrix stated explicitly), the caption directive and the icon-projection rules; the six examples already exist to link from. Delete the two example stubs, or populate them and flip `hasExamples: true` — deleting matches what the structure entry already declares.

## 4. Recommended Remediation Phases

**Phase 1 — Close the two silent failures.**
IDs: BDG-CSS-01, BDG-ARCH-01. Decide the outline/colour matrix and either implement or restrict it, and link the styler to the component with `hostDirectives`. These are the two ways a consumer gets a visibly wrong badge with no diagnostic, and neither depends on anything below. Ships with an expanded e2e colour matrix and a standalone-import Jest case.

**Phase 2 — Clean the public surface.**
IDs: BDG-API-01, BDG-API-02, BDG-LIFE-01. Convert `badgeColor` to a signal input with a separate class `computed()`, delete `iconItem` and the `forwardRef`, tighten the public fields, drop `isIconButton` and its `detectChanges()`. One `build:components` → `approve-api` → `approve-public-api-any` cycle covers all three; sequencing them together keeps the API report churning once.

**Phase 3 — Make icon layout defensible.**
IDs: BDG-BUG-01, BDG-CSS-02. Move spacing to CSS adjacency (or handle the `-1` and middle cases explicitly), fix the `border` shorthand, resolve the unused tokens. Requires new Playwright baselines through Docker; best done after Phase 2 so the styler's remaining surface is already settled.

**Phase 4 — Coverage, access and documentation.**
IDs: BDG-TEST-01, BDG-A11Y-01, BDG-DOC-01. Bring the Jest suite up to the inputs it never touches, add the icon-only accessible-name warning and its axe case, write the properties tables, and resolve the dead example stubs.

## 5. Verification Strategy

General gates, run sequentially (never in parallel — see `project_no_parallel_heavy_builds`):
- `npx jest packages/components/badge`, plus `packages/components/dl` and `packages/components/file-upload` — the two packages that consume `KbqBadge` directly.
- `yarn run eslint`, `yarn run stylelint`, `yarn run prettier` on touched files.
- `yarn run build:components`, then `yarn run check-api` and `yarn run check-public-api-any`; `approve-api` only in Phase 2.
- `yarn run e2e:docker` for anything visual; baselines only via `yarn run e2e:docker:update-snapshots`.
- Manual smoke: `yarn run dev:badge` (the dev template already covers the full colour × size × caption matrix at `components-dev/badge/template.html`).

Per-phase assertions:
- **Phase 1:** `E2eBadgeStyles` renders `Object.values(KbqBadgeColors)` in all four rows and the outline rows show a visible border and text colour for every colour (or unsupported combinations produce a dev-mode warning and are rejected by the type). A host importing `KbqBadge` alone and projecting an icon still gets `kbq-icon_right` and the 4px margin the Playwright case measures.
- **Phase 2:** writing `badge.badgeColor = badge.badgeColor` leaves exactly one `kbq-badge_*` class on the host. `badge.api.md` no longer lists `iconItem`, `icons` types as `readonly KbqIcon[]`, and `check-public-api-any` reports badge at 0.
- **Phase 3:** a badge with `text <kbq-icon/> text` has defined margins around the icon; toggling `[outline]` no longer shifts the content by 1px (compare computed `padding`/`border` boxes in the Playwright fixture).
- **Phase 4:** `npx jest packages/components/badge` covers every input, and reverting the `badgeColor` `||` default fails a case. An icon-only badge without a label produces a dev-mode warning and a `jest-axe` violation; with a label, neither. Both guides list the properties, and the docs site renders unchanged.

## Appendix A — Review Methodology

Findings were gathered by reading the whole package (component, styler, caption directive, module, tokens, theme, SCSS, Jest spec, e2e fixture and Playwright spec, both guides, both example stubs), then cross-checking each candidate against four independent sources: the API guard report and the untyped-surface baseline; every in-repo consumer of `KbqBadge`/`KbqBadgeModule`/`kbq-badge-caption` found by grep across `packages/` and `apps/` (the `dl` e2e fixture, the `file-upload-primitive` docs example, six docs examples, and an 800-line dev-app template); the design tokens the theme references; and the sibling `button` package, which implements the same styler split and the same icon detection with guards that badge lacks. The fixtures themselves turned out to be evidence: `E2eBadgeStyles` maintains a separate, shorter colour list for outline, which is what turned BDG-CSS-01 from a suspicion into a confirmed gap.

Refuted during verification:
- **"`ViewEncapsulation.None` leaks badge styles into consumers"** — refuted. It is the library-wide convention, every selector is namespaced under `.kbq-badge`, and the tokens are scoped to that class rather than `:root` (`badge-tokens.scss:1`).
- **"`.kbq-icon.kbq-empty` in the theme (`_badge-theme.scss:13`) is a dead selector — no such class exists in the icon package"** — refuted. `kbq-empty` is built at runtime by `KbqColorDirective` as `` `kbq-${color}` ``, so it never appears as a literal in the source; the rule is live.
- **"The guide's links to `/en/components/tag`, `/tag-autocomplete` and `/tag-input` (`badge.en.md:39`) are broken"** — refuted. All three ids exist in the docs structure (`structure.ts:73-75`, entries at `:976-1015`).
- **"`getNodesWithoutComments` should filter whitespace text nodes too"** — refuted as a defect in the helper. Leading text is a legitimate badge child and must occupy an index for the trailing-icon case to work; the spec at `badge.component.spec.ts:82-87` depends on exactly that. The genuine problem is the positional algorithm itself, filed as BDG-BUG-01.
- **"`badge` is missing from the API guard configuration or its report is stale"** — refuted. The report exists, is current with the DS-5272 changes (it lists `icons` and `updateClassModifierForIcons`), and the untyped-surface ratchet records badge explicitly.

Corrected on verification:
- **BDG-ARCH-01** was first drafted as "importing `KbqBadge` alone is broken in the repo today". Both call sites turned out to render text-only badges, so nothing is currently mis-rendered; the finding was rewritten as a latent trap with no guard, and the button's two guards became the evidence that the pattern is known and solved elsewhere. Severity stayed P1 because the failure is silent and the API invites it.
- **BDG-A11Y-01** was first drafted as a P1 AXE failure. axe-core does not flag a custom element with no role and no name, so the claim was narrowed to a WCAG judgement about the icon-only configuration and dropped to P2.
- **BDG-CSS-02**'s `border: transparent` item started as "the border disappears in filled badges" — which is the intended effect. Working through the shorthand's resets showed the real consequence is a 2px difference in the content box between filled and outline, which is why it is P3 rather than higher.
