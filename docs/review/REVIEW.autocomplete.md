# Koobiq `autocomplete` Component — Code Review & Improvement Plan

> Scope: `packages/components/autocomplete` (component, trigger directive, origin directive, template, SCSS/tokens/theme, Jest spec, e2e fixtures + Playwright spec, user guides, API guard report) plus the `core` machinery it composes (`core/option`, `core/a11y/key-manager`, `core/overlay/panel-width`) · Commit `b665e503` · 2026-08-28
> Generated by a multi-dimension review (architecture, RxJS/lifecycle, correctness, accessibility, performance, public API/types, templates/styles, tests, docs) with manual verification of every finding against the source, the in-repo consumers, the built `dist/*.d.ts` and the workspace configuration. 17 findings confirmed (P0×2, P1×4, P2×5, P3×6); 6 candidate findings refuted during verification (see Appendix A). Findings that live in shared `core` code are cross-referenced to `REVIEW.select.md` rather than restated. This document is a review + roadmap; no source is modified by it.

## 1. Executive Summary

`kbq-autocomplete` is a two-part package: a 285-line panel component (`autocomplete.component.ts`) that is nothing but a `TemplatePortal` host, and a 758-line trigger directive (`autocomplete-trigger.directive.ts`) that owns the overlay, the `ControlValueAccessor` and all keyboard handling. It shares its option list, key manager and panel-width resolver with `select` and `tree-select`, so several defects already documented in [REVIEW.select.md](./REVIEW.select.md) apply verbatim here and are cited rather than re-derived.

- **The combobox is not a combobox.** The trigger's host block binds a class, `autocomplete`, and five DOM events — and nothing else (`autocomplete-trigger.directive.ts:116-126`). There is no `role="combobox"`, no `aria-expanded`, no `aria-controls`/`aria-owns`, no `aria-autocomplete`, no `aria-activedescendant`. The panel *does* carry `role="listbox"` (`autocomplete.html:3`), which makes the situation worse rather than better: its children are `<kbq-option>` elements with no `role="option"` (`core/option/option.ts:149-160`), so this is an automated axe `aria-required-children` failure, not merely a WCAG judgement — and `jest-axe` is now a project dependency (`package.json:121`), so there is no tooling excuse left. Nothing is announced when results appear, change count, or run out (AC-A11Y-01, AC-A11Y-02, AC-A11Y-03).
- **Two shipped correctness bugs, both created by the same focus/active-item design.** Selecting an option with `Enter` closes the panel and then calls `resetActiveItem()`, which — under the shipped `autoActiveFirstOption: true` default — re-activates option 0 while the panel is closed, and the trigger's own `keyManager.change` handler answers that by calling `selectViaInteraction()` on it. The user picks the fourth option and the first one is silently marked selected too (AC-BUG-01). Separately, every active-item change moves real DOM focus into the option and immediately back to the input (`:283-292`, `:466-468`); the input's `(blur)` is wired straight to `onTouched()` (`:122`), so **merely clicking into an autocomplete field marks its form control as touched** and a `required` control renders its error before the user has typed anything (`core/error/error-state-matcher.ts:59-63`) (AC-BUG-02).
- **The Jest suite is pinned to the inverse of the shipped default, which is why both bugs shipped.** `autocomplete.spec.ts:74` provides `KBQ_AUTOCOMPLETE_DEFAULT_OPTIONS` as `{ autoActiveFirstOption: false }` for all 121 cases, while the library ships `true` (`autocomplete.component.ts:71-73`). Under that override `resetActiveItem()` degenerates to `setActiveItem(-1)`, the key manager emits no active item, and both defects become unreachable. Two tests then assert behaviour that is simply false in production — `'should reset the active option when closing by selecting with enter'` (`:1006-1029`) passes only because the default was flipped (AC-TEST-01).
- **Overlay sizing is measured at open time and never re-measured against the trigger.** `updateSize()` is called on first attach, on re-attach, on viewport change and once on the first stable tick (`:637, :646, :674`) — never when the trigger itself grows. The guide explicitly advertises the tag-input integration, where the field grows as tags are added (`autocomplete.en.md:40`), and option changes only call `reapplyLastPosition()`/`updatePosition()` (`:513, :532`) (AC-BUG-03).

Genuine strengths, and there are real ones: the panel-width policy is coherent end to end — the shared `kbqResolvePanelWidth()` resolver (`core/overlay/panel-width.ts:78-104`) picks the content-sized policy by default and the CSS `min-width: 100%` / `max-width` pair (`autocomplete.scss:15-18`) is what makes the guide's "never narrower than the field, never clamps an explicit `panelWidth`" promise literally true; the panel-width guide is one of the more accurate documents in the repo and is mirrored faithfully in Russian. The Playwright suite is unusually good for this library — six tests including a `elementFromPoint` probe that proves the trigger↔panel gap is transparent padding rather than a dead zone (`e2e.playwright-spec.ts:10-33`), a real above-position flip assertion, a panel-growth assertion and a scroll-strategy fixture. The overlay lifecycle is disciplined (window-blur listener, viewport subscription and closing-actions subscription all torn down in `ngOnDestroy`, `:296-303`), the scroll-strategy token has a root default so it works outside the NgModule (`:68-79`, DS-3522), and the sole long-lived stream in the panel component is correctly piped through `takeUntilDestroyed` (`autocomplete.component.ts:228-237`).

## 3. Prioritized Findings (deduplicated, verified)

### P0 — Release blockers

**AC-A11Y-01 · The trigger exposes no combobox semantics at all** — `autocomplete-trigger.directive.ts:113-127` (host block), `autocomplete.component.ts:101-102`, `autocomplete.html:2-3`.
The host object binds exactly one attribute — `'[attr.autocomplete]': 'autocompleteAttribute()'` (`:118`) — plus a class and five event handlers. Grepping the whole package for `aria` returns three hits, two of them comments (`autocomplete.component.ts:101`, `autocomplete-trigger.directive.ts:627`) and one the `role="listbox"` in the template. So an `<input kbqAutocomplete>` is announced as a plain text field: a screen-reader user gets no indication that a popup exists, no indication that it opened, no way to reach the option list, and no announcement of which option is active while arrowing through it. This violates WCAG 4.1.2 (Name, Role, Value) and 1.3.1, and it is the same defect chain as SEL-A11Y-01/02/04 in [REVIEW.select.md](./REVIEW.select.md) — except that autocomplete is *further* along, because it already renders a listbox to point at and already runs an `ActiveDescendantKeyManager` (`autocomplete.component.ts:104-105, 225`) whose entire reason for existing is to drive `aria-activedescendant`. The component even documents the missing wiring as if it existed: `/** Unique ID to be used by autocomplete trigger's "aria-owns" property. */` (`autocomplete.component.ts:101`) — the trigger never reads `autocomplete().id`, and the id is bound to the outer wrapper (`autocomplete.html:2`) rather than to the listbox, so honouring that comment literally would point `aria-owns` at a container that also holds the footer.
**Fix:** move the id onto the listbox element and add the four missing bindings to the trigger host block: `'[attr.role]': "'combobox'"`, `'[attr.aria-autocomplete]': "'list'"`, `'[attr.aria-expanded]': 'panelOpen'`, `'[attr.aria-controls]': 'panelOpen ? autocomplete()?.id : null'`, `'[attr.aria-activedescendant]': 'panelOpen ? activeOption?.id : null'` (`KbqOption` already binds `[id]`, `core/option/option.ts:156`). Guard each expression for the undefined-panel case (see AC-BUG-04). This must land together with AC-A11Y-02 and after AC-BUG-02, because `aria-activedescendant` is only meaningful once DOM focus stays on the input. Cover with a Jest a11y `describe` asserting each attribute in the closed and open states plus `expect(await axe(fixture.nativeElement)).toHaveNoViolations()` — `jest-axe` is already a dependency (`package.json:90, 121`) and is used by five sibling suites (`accordion`, `app-switcher`, `button-toggle`, `list`, `navbar`).

**AC-A11Y-02 · `role="listbox"` over children that carry no `role="option"`, and the listbox has no `id`** — `autocomplete.html:2-3`, `core/option/option.ts:149-160`, `core/option/optgroup.ts`.
`<div #panel role="listbox" class="kbq-autocomplete-panel__content kbq-scrollbar">` wraps the projected content directly, so its children are `<kbq-option>` custom elements whose host block binds `tabindex`, `id` and four classes and **no role** (`core/option/option.ts:149-160`). A `listbox` that owns no `option`-role children is a violation of axe-core's `aria-required-children` rule — an automated failure, which is the material difference from the select case: select has no listbox role at all (SEL-A11Y-02), so axe has nothing to check, whereas autocomplete asserts a role it does not fulfil. `role="listbox"` also implies its children are not individually tabbable, yet every enabled option renders `tabindex="0"` (`core/option/option.ts:391-393`), putting the whole option list into the page tab order while the panel is open. Finally the listbox element carries no `id`; `[id]="id"` sits on the outer `.kbq-autocomplete-panel` wrapper (`autocomplete.html:2`) which also contains the footer, so there is no valid target for the `aria-controls` that AC-A11Y-01 needs. Optgroups projected into the panel have the same missing-`role="group"` problem as in select (SEL-A11Y-07, shared).
**Fix:** add `[attr.role]="'option'"`, `[attr.aria-selected]="selected"`, `[attr.aria-disabled]="disabled"` to `KbqOption`'s host and mark the pseudo-checkbox `aria-hidden` — this is SEL-A11Y-03/08 and should be fixed once in `core/option`, benefiting select, tree-select and autocomplete together. In this package: move `[id]="id"` from the wrapper (`autocomplete.html:2`) to the `#panel` listbox element, keeping the footer outside the listbox subtree where it already correctly sits (`autocomplete.html:6`). Change the option `tabindex` to `-1` when the parent is an autocomplete (the `KBQ_OPTION_PARENT_COMPONENT` token is already injected, `core/option/option.ts:165`). Guard with an axe assertion on the open panel — it fails today and passes after the change.

### P1 — High

**AC-BUG-01 · After a keyboard selection the first option is silently selected as well** — `autocomplete-trigger.directive.ts:406-409, 279-293, 743-751`, `autocomplete.component.ts:71-73`, `core/a11y/key-manager/list-key-manager.ts:213-222, 315-317, 435-453`, `core/option/option.ts:380-389`.
`handleKeydown` on `ENTER` runs `this.activeOption.selectViaInteraction()` and *then* `this.resetActiveItem()` (`:406-409`). The first call is synchronous all the way through: `selectViaInteraction()` emits `onSelectionChange` (`core/option/option.ts:387`), which reaches `optionSelections` → `panelClosingActions` → the `take(1)` subscription in `subscribeToClosingActions()` → `setValueAndClose()` → `closePanel()`, so by the time line 408 executes `overlayAttached` is already `false`. `resetActiveItem()` then reads the shipped default `autoActiveFirstOption: true` (`autocomplete.component.ts:71-73`) and calls `keyManager.setFirstItemActive()`, which moves the active index from (say) 3 to 0 and therefore emits `change` (`core/a11y/key-manager/list-key-manager.ts:217-221`). The trigger's own `keyManager.change` handler (`:283-292`) sees `panelOpen === false` and takes its second branch: `keyManager.activeItem?.selectViaInteraction()`. `selectViaInteraction()` has no already-selected guard (`core/option/option.ts:380-389`), so option 0 is set `_selected = true`. Net user-visible result: choose "Option 4" with `Enter`, reopen the panel, and both "Option 1" and "Option 4" render as selected in a single-select autocomplete. The `else` branch that does this ("if the panel is closed and something is active, select it") has no comment explaining what it is for, and the only path that legitimately needs it — `Shift`+arrow — is already handled explicitly twelve lines above (`:419-423`).
**Fix:** reorder `handleKeydown` so `resetActiveItem()` runs *before* `selectViaInteraction()`, or gate the reset on `this.panelOpen`. Independently, delete the `else if (!this.panelOpen && …) selectViaInteraction()` branch (`:289-291`) — nothing in the repo depends on active-item movement selecting while the panel is closed, and `Shift`+arrow covers the documented case. Add a regression test that selects the *third* option with `Enter` under the shipped default and asserts `options().filter(o => o.selected).length === 1`; it fails today once AC-TEST-01 unpins the configuration.

**AC-BUG-02 · Opening the panel marks the form control as touched, showing validation errors before the user types** — `autocomplete-trigger.directive.ts:122, 279-293, 466-468`, `core/option/option.ts:313-321, 391-393`, `core/error/error-state-matcher.ts:59-63`.
The trigger host binds `'(blur)': 'onTouched()'` (`:122`). The `keyManager.change` handler calls `scrollActiveOptionIntoView()` followed immediately by `this.elementRef.nativeElement.focus()` (`:287-288`), and `scrollActiveOptionIntoView()` is a misnomer — it calls `this.autocomplete().keyManager.activeItem?.focus()` (`:466-468`), which is a real `element.focus()` on a real focusable element (`core/option/option.ts:313-321` and `tabindex="0"` at `:391-393`). So every active-item change moves DOM focus off the input and back, and the browser fires `blur` on the input in between. Under the shipped `autoActiveFirstOption: true` this happens on the very first open: focusing the field opens the panel, the stable tick calls `resetActiveItem()` → `setFirstItemActive()` → `change` → option focus → input blur → `onTouched()`. Koobiq's default `ErrorStateMatcher` is `control.invalid && (control.touched || form.submitted)` (`core/error/error-state-matcher.ts:59-63`), so a `required` autocomplete paints its error message the instant the user clicks into it, having entered nothing. The same ping-pong repeats on every arrow key. It is also what makes AC-A11Y-01's `aria-activedescendant` unimplementable as written: the pattern requires focus to *stay* on the combobox, and the class doing the work is literally called `ActiveDescendantKeyManager`.
**Fix:** stop moving DOM focus into options. Replace `scrollActiveOptionIntoView()`'s `activeItem?.focus()` with a scroll-only implementation — `activeItem.getHostElement().scrollIntoView({ block: 'nearest' })`, or a `scrollTop` computation against `autocomplete().panel()` (the `setScrollTop`/`getScrollTop` helpers this package already exports for exactly that purpose, `autocomplete.component.ts:240-252`, are otherwise dead — see AC-API-02). Then delete the compensating `this.elementRef.nativeElement.focus()` at `:288`. Add a Jest case under the shipped default asserting `stateCtrl.touched === false` after opening the panel and after three `DOWN_ARROW` presses, and a second asserting `document.activeElement` is still the input while arrowing.

**AC-A11Y-03 · Nothing is announced when results appear, change or disappear** — `autocomplete.component.ts:254-265`, `autocomplete.html:1-8`, `core/locales/en-US.ts:4-17`.
`setVisibility()` toggles `kbq-autocomplete_visible` / `kbq-autocomplete_hidden` on the panel and nothing else; there is no live region anywhere in the package (`grep -n "aria-live" packages/components/autocomplete` is empty), and `core/locales/en-US.ts:4-17` contains no autocomplete strings, so there is nothing for `kbqInjectA11yLocaleConfiguration()` to supply even if one were added. A screen-reader user typing into the field therefore gets silence: no "5 results available", no "no results", no notice that the list shrank from 20 to 1 as they typed. Since AC-BUG-02's fix removes the per-option focus events, this is the *only* channel through which the result set could be conveyed, which is why it is filed at P1 rather than as a nice-to-have. The repo already knows this pattern is needed and applies it elsewhere: `filter-bar/pipe-add.ts:61` hand-rolls `<div class="cdk-visually-hidden" aria-live="polite" aria-atomic="true">` for exactly this kind of announcement, with a WCAG 4.1.3 comment.
**Fix:** render a visually-hidden `aria-live="polite" aria-atomic="true"` region as a sibling of the trigger (not inside the overlay — overlay content is attached and detached, which suppresses announcements), fed by a `computed()` over `autocomplete().options.length` and `panelOpen`. Source the text from `kbqInjectA11yLocaleConfiguration()` per AGENTS.md: add `a11y.autocomplete.resultsAvailable` (`'{{ number }} results available'`) and `a11y.autocomplete.noResults` to `core/locales/en-US.ts` and `ru-RU.ts`, following the existing `select.hiddenItemsText` interpolation convention (`core/locales/en-US.ts:18`). Debounce so a fast typist is not machine-gunned. Test by asserting the live region's text after filtering, in both locales.

**AC-TEST-01 · The whole Jest suite runs with `autoActiveFirstOption` inverted, hiding both P1 bugs** — `autocomplete.spec.ts:74`, `autocomplete.component.ts:71-73`, `autocomplete.spec.ts:981-1029`.
`createComponent()` — the single factory behind all 121 cases — unconditionally provides `{ provide: KBQ_AUTOCOMPLETE_DEFAULT_OPTIONS, useFactory: () => ({ autoActiveFirstOption: false }) }` (`:74`), while `KBQ_AUTOCOMPLETE_DEFAULT_OPTIONS_FACTORY` ships `true` (`autocomplete.component.ts:71-73`). Under the override `resetActiveItem()` takes its `setActiveItem(-1)` branch (`autocomplete-trigger.directive.ts:749`), `activeItem` resolves to `itemArray[-1] === undefined` (`core/a11y/key-manager/list-key-manager.ts:374-380`), the key manager emits no useful active item, and every path in AC-BUG-01 and AC-BUG-02 becomes unreachable. Only two cases opt back into production behaviour, and both do it locally (`:1243-1252` sets the property imperatively, `:1253-1269` re-provides the token) — so the *default* configuration is exercised by two assertions, both of which only check that option 0 has the `kbq-active` class. Worse, two tests now assert things that are false in production: `'should reset the active option when closing with the escape key'` (`:981-1004`) and `'should reset the active option when closing by selecting with enter'` (`:1006-1029`) both end with `expect(trigger.activeOption).toBeFalsy()`, which under the shipped default would be option 0, not falsy. The test names document the override, not the component.
**Fix:** delete the provider at `:74` so the suite runs the shipped default, then repair the fallout: rename/retarget the two `activeOption` assertions to state what actually happens (`toBe(options()[0])`), and add an explicitly-provided `autoActiveFirstOption: false` block for the handful of cases that genuinely need it. Do this **first** — it converts AC-BUG-01 and AC-BUG-02 from arguments into red tests, which is the cheapest possible proof that the subsequent fixes work.

### P2 — Should fix

**AC-BUG-03 · Panel width is measured at open time and never re-measured when the trigger resizes** — `autocomplete-trigger.directive.ts:510-517, 525-545, 634-640, 641-647, 666-676, 729-737`, `autocomplete.en.md:40`.
`updateSize(this.getOverlaySize())` has exactly three call sites: the `ViewportRuler.change()` subscription (`:637`), the re-attach branch (`:646`), and the one-shot stable tick after attach (`:672-675`). `getOverlaySize()` resolves through `kbqResolvePanelWidth(panelWidth, panelMinWidth, this.getHostWidth())` (`:729-737`), where `getHostWidth()` reads `getBoundingClientRect().width` of the connected element *at that moment*. Nothing observes the trigger. When the option list changes, `subscribeToClosingActions()` calls `positionStrategy.reapplyLastPosition()` (`:513`) and `overlayRef.updatePosition()` (`:532`) — position only, never size. So any trigger resize that is not a window resize leaves a stale width baked into the overlay config: with the default content-sized policy the pane keeps the old `minWidth` floor and the panel ends up narrower than the field, contradicting the guide's "never narrower than the field" (`autocomplete.en.md:19`); with `panelWidth="auto"` the pane keeps a frozen pixel width (`core/overlay/panel-width.ts:91-93`). The case is not hypothetical — the guide's closing line advertises exactly the layout where it happens: "The same attributes apply when the autocomplete is attached to a [tag input], where the panel is measured against the whole field rather than the input" (`autocomplete.en.md:40`), and a tag list grows and wraps as tags are added while the panel is open. This area already has history: DS-5327 ("apply reposition & size recalculation") and DS-3244 ("unify dropdown panel width") both touched it.
**Fix:** observe the connected element with `SharedResizeObserver` — already a `core` utility used by ten packages (`actions-panel`, `clamped-text`, `code-block`, `dl`, `inline-edit`, …) — subscribed in `attachOverlay()` and torn down in `closePanel()`, calling `overlayRef.updateSize(this.getOverlaySize())` outside the zone with a `distinctUntilChanged()` on the resolved width. Add `updateSize()` alongside the existing `updatePosition()` in the `options.changes` path (`:532`) for the content-driven case. Verify with a Playwright test on the `tags` e2e route: open the panel, add a tag that forces the field to wrap, assert the panel's `boundingBox().width` matches the field's.

**AC-LIFE-01 · The `keyManager.change` subscription is never torn down and reads the panel exactly once** — `autocomplete-trigger.directive.ts:279-294, 296-303, 175-190`.
`ngAfterViewInit()` does a bare `autocomplete.keyManager?.change.subscribe(…)` with no `takeUntilDestroyed`, no stored `Subscription` and no matching teardown in `ngOnDestroy()` (`:296-303`, which unsubscribes `viewportSubscription` and completes `closeKeyEventStream` but not this). Koobiq's `ListKeyManager` has no `destroy()` method at all and never completes its `change` subject (`core/a11y/key-manager/list-key-manager.ts:27-30`), and `KbqAutocomplete` never disposes the manager, so nothing ends the subscription from the other side either. When the trigger outlives the panel this is harmless; when the panel outlives the trigger — the shape the package's own spec exercises, `<kbq-autocomplete>` declared as a sibling of an `@if`-wrapped input (`autocomplete.spec.ts:1501-1536`, and the same layout in `components-dev/autocomplete/template.html:10-21`) — a destroyed trigger keeps running `this.elementRef.nativeElement.focus()` on a detached element. Second problem in the same three lines: `autocomplete` is read once, so a `[kbqAutocomplete]` binding that resolves *after* `ngAfterViewInit` (a panel inside `@if`, or a swapped panel reference) never gets a subscription at all, and arrow navigation then silently stops scrolling the active option into view. The class already knows this can happen — `openedChange` is deliberately built on `toObservable(this.autocomplete)` with a comment explaining that "the panel is bound after the consumers of this stream are created" (`:175-190`).
**Fix:** rebuild the handler on the same foundation as `openedChange`: `toObservable(this.autocomplete).pipe(filter(Boolean), switchMap(a => a.keyManager.change), takeUntilDestroyed())` in a field initializer, subscribed in `ngAfterViewInit`. This fixes teardown and late binding in one move. Add a spec that destroys the trigger's host `@if` while the panel component survives and asserts no further `focus()` calls.

**AC-API-01 · `classList` is published as `string` but returns an object, and its setter wipes the host's classes with a raw DOM write** — `autocomplete.component.ts:153-176`, `dist/components/autocomplete/index.d.ts:83-84`, `tools/public_api_guard/components/autocomplete.api.md:64-65`, `autocomplete.spec.ts:1557-1576`.
`private _classList: any = {}` is an object map, and every writer keeps it that way (`:166-170`, `setVisibility()` `:256-260`, `updateFocusClass()` `:280-283`). But the emitted declaration is `get classList(): string; set classList(value: string);` — verified in the built artefact at `dist/components/autocomplete/index.d.ts:83-84` and mirrored in the API guard report at `tools/public_api_guard/components/autocomplete.api.md:64-65`. A consumer writing `autocomplete.classList.split(' ')` type-checks cleanly and throws `TypeError: …split is not a function` at runtime. The setter has a second problem: `this.elementRef.nativeElement.className = ''` (`:172`) is a direct DOM write that bypasses `Renderer2` (banned for SSR by AGENTS.md, and unguarded by any platform check) and clears *every* class on the host — the package's own spec asserts the consequence, `expect(autocomplete.classList).not.toContain('class-one')` (`autocomplete.spec.ts:1573-1574`), so a consumer's own host classes are silently destroyed rather than moved. This is inherited Material machinery that predates Angular's own `[class]` handling.
**Fix:** type the field as `Record<string, boolean>` and annotate the getter explicitly so the declaration stops lying; that alone changes `autocomplete.api.md` and needs `yarn run build:components && yarn run approve-api`. Replace the `className = ''` write with `Renderer2.removeClass` per parsed token, or — better — drop the `@Input('class')` accessor entirely in favour of a normally-named `panelClass` input plus Angular's own host class handling, keeping `classList` as a deprecated alias for one minor. Add a Jest case asserting the host retains `kbq-autocomplete` after `[class]` is bound.

**AC-BUG-04 · Focusing a trigger whose panel is not bound throws a raw `TypeError` instead of the package's own error** — `autocomplete-trigger.directive.ts:451-458, 609-614, 101-111`, `autocomplete.spec.ts:2564-2576`.
`handleFocus()` short-circuits through `!this.panelOpen && this.canOpen()` and then dereferences `this.autocomplete().openOnFocus` (`:454`). With no panel bound, `panelOpen` returns `false` harmlessly because `overlayAttached` short-circuits first (`:163-165`), `canOpen()` only inspects the native input (`:753-757`), and the third term throws `Cannot read properties of undefined (reading 'openOnFocus')`. The package goes to real trouble to produce a good error for exactly this situation — `getKbqAutocompleteMissingPanelError()` names the cause and the fix (`:101-111`) — but it is only thrown from `attachOverlay()` (`:612-614`), which `handleFocus()` never reaches. So `handleClick()` produces the helpful error and `handleFocus()` produces a stack trace, for the same misconfiguration. The spec has the fixture for it (`AutocompleteWithoutPanel`, `autocomplete.spec.ts:2564-2576`, whose `[kbqAutocomplete]="auto"` binds an undeclared property) but only exercises `open()` (`:1537-1545`) and `control.setValue()` (`:1547-1556`), never focus.
**Fix:** hoist the guard: `const autocomplete = this.autocomplete(); if (!autocomplete) { return; }` at the top of `handleFocus()` — silently doing nothing is right here, because a panel bound later must not crash the field in the meantime (this is the same late-binding reality `openedChange` accounts for at `:175-190`). **AC-CSS-01 · The divider offset rule targets a class that does not exist** — `autocomplete.scss:48-52`, `divider.component.ts:11-14`.
```scss

// they throw off the keyboard navigation inside the panel.
.kbq-divider-horizontal {
    margin-top: -1px;
}
```
`KbqDivider` emits `kbq-divider_horizontal` with an underscore (`divider.component.ts:13`); the hyphenated `kbq-divider-horizontal` appears in exactly one place in the entire repository — this rule (`grep -rn "kbq-divider-horizontal" packages/ apps/` returns a single hit). **Fix:** decide deliberately rather than by typo. Either correct the selector to `.kbq-divider_horizontal` and verify the result visually in both themes with a new e2e row (watching for the doubled-alpha seam), or delete the rule and its comment — the e2e fixtures place no dividers in the panel (`e2e.ts:10-27, 49-65, 93-109, 138-154`), so nothing in the repo depends on either outcome. **AC-API-03 · Five legacy accessor inputs with false migration TODOs, asymmetric coercion, and no `ngAcceptInputType_*`** — `autocomplete.component.ts:118-121, 157-176, 178-193, 205-216`, `autocomplete-trigger.directive.ts:204-217`.

**AC-ARCH-01 · Mixed query styles in one class, and a public input whose only caller lives in another package** — `autocomplete.component.ts:114-116`, `autocomplete-trigger.directive.ts:219-231`, `tags/tag-input.ts:306`.

Separately, `onInputBlur` (`autocomplete-trigger.directive.ts:219-231`) is a public input on the autocomplete trigger that the autocomplete never calls; its one caller in the entire repo is `tags/tag-input.ts:306`. ## Appendix A — Review Methodology

Every file in the package was read in full (`.ts`, `.html`, `.scss`, `.md`, both e2e files, the 2,805-line spec), then each candidate finding was checked against four independent sources: the shared `core` code it composes (`core/option/option.ts`, `core/a11y/key-manager/list-key-manager.ts`, `core/overlay/panel-width.ts`, `core/error/error-state-matcher.ts`, `core/locales/en-US.ts`), the built declaration file (`dist/components/autocomplete/index.d.ts`) alongside the API guard report, the workspace configuration (`tsconfig.json`, `playwright.config.ts`, `package.json`), and every in-repo consumer found by grepping `kbqAutocomplete` across `packages/` and `apps/` (`tags/tag-input.ts`, three docs examples, four dev-app templates, the `tags` e2e fixtures). Because `autocomplete` shares its option list, key manager and panel-width resolver with `select`, findings that live in that shared code are cited to [REVIEW.select.md](./REVIEW.select.md) (SEL-A11Y-02/03/07/08, SEL-API-01, SEL-TPL-06) rather than counted twice here; only the autocomplete-specific half is filed. The control-flow chain behind AC-BUG-01 was traced statement by statement through five files before being written down.

Refuted during verification:
- **"`panelMaxWidth` never reaches `OverlayConfig`, so the documented cap does nothing"** — refuted. `getOverlaySize()` deliberately returns only `{ width, minWidth }` (`core/overlay/panel-width.ts:48-51`); the cap is applied in CSS on the panel itself, via `[style.max-width.px]="panelMaxWidth()"` (`autocomplete.html:2`) over the `--kbq-panel-size-width-max` default (`autocomplete.scss:18`). The `min-width: 100%` on the same rule (`autocomplete.scss:15`) is what makes the guide's two promises — never narrower than the field, never clamps an explicit `panelWidth` — literally true, since `min-width` outranks `max-width` in CSS. The design is correct as shipped.
- **"`--kbq-panel-size-width-max` is undeclared, so the 640px cap never applies"** — refuted. It is referenced only ever with a `640px` fallback (`autocomplete.scss:18`, `core/styles/common/_select.scss:180`, `dropdown-tokens.scss:6`); it is an intentional consumer-set override point, documented as such in `dropdown.en.md:108`.
- **"No `prefers-reduced-motion` handling, matching SEL-A11Y-09"** — refuted, twice over. The component registers no animations at all (`autocomplete.component.ts:75-95` has no `animations` entry, unlike `select.component.ts:195`), so there is nothing to gate; and Playwright contexts already force `reducedMotion: 'reduce'` for every browser (`playwright.config.ts:101`), so the e2e baselines would not observe one anyway.
- **"A root-singleton locale-service leak, matching SEL-LEAK-01"** — refuted. Neither class injects `KbqLocaleService`. The only long-lived subscription in the panel component is the parent form-field's `ngControl.valueChanges`, and it is correctly piped through `takeUntilDestroyed(this.destroyRef)` (`autocomplete.component.ts:228-237`).
- **"Two `NG_VALUE_ACCESSOR` providers collide on `<input kbqInput kbqAutocomplete>`, which Angular rejects"** — refuted. `KbqInput` does not provide `NG_VALUE_ACCESSOR`; the only input-package provider is on the separate `kbqNumberInput` directive (`input/input-number.ts:113`), so the trigger is the sole custom accessor on the element and `selectValueAccessor` has nothing to reject.
- **"The `E2eAutocompleteStates` screenshot cannot capture the panel, because the overlay is outside the component host"** — refuted. Playwright clips an element screenshot to the locator's bounding box and captures whatever is painted over it, and the fixture's `height: 340px` (`e2e.ts:34`) is sized to cover the field plus the panel's `256px` cap. The baseline does show the open panel.

Corrected on verification:
- **AC-A11Y-02** was first drafted as "no listbox role at all", mirroring SEL-A11Y-02. `autocomplete.html:3` does carry `role="listbox"` — which makes the finding worse rather than milder: a listbox with no `option`-role children is an automated axe `aria-required-children` failure, whereas select's role-less panel is only a WCAG judgement. The severity stayed P0 but the argument and the fix both changed.
- **AC-TEST-01** started as "the spec has no ARIA coverage" — true, but merely a restatement of the A11Y findings. Reading `autocomplete.spec.ts:74` surfaced the much larger problem: the suite pins `autoActiveFirstOption` to the inverse of the shipped default, which is the direct reason AC-BUG-01 and AC-BUG-02 are in the release. The finding was re-scoped and promoted to P1.
- **AC-BUG-02** was initially filed as accessibility-only ("focus is stolen from the combobox"). Tracing `(blur)` → `onTouched()` → `ErrorStateMatcher.isErrorState` showed a consequence that sighted keyboard and mouse users see too — a premature validation error on a `required` field — so it was re-filed as a correctness bug with the a11y impact noted inside it.
- **AC-BUG-03** was drafted as "the panel is never repositioned while open"; `subscribeToClosingActions()` does call `reapplyLastPosition()` and `updatePosition()` (`:513, :532`). The gap is narrower and more specific: *position* is refreshed, *size* is not, and only a window resize re-measures the trigger.
