# Koobiq `code-block` Component — Code Review & Improvement Plan

> Scope: `packages/components/code-block` (component + template, the `KbqCodeBlockHighlight` directive and its vendored `highlightjs-line-numbers` plugin, tokens, theme, SCSS, Jest spec, e2e fixture + Playwright spec, user guides, API guard report) · Commit `b665e503` · 2026-08-28
> Generated by a multi-dimension review (security/sanitization, architecture, RxJS & lifecycle, correctness, accessibility, SSR, performance, public API/types, styles, tests, docs) with manual verification of every finding against the source, the installed `highlight.js@11.11.1`, the in-repo consumers and the docs app. 16 findings confirmed (P0×1, P1×3, P2×8, P3×4); 6 candidate findings refuted and 2 corrected during verification (see Appendix A). This document is a review + roadmap; no source is modified by it.

## 1. Executive Summary

`kbq-code-block` is the library's largest single-purpose component: a 593-line component (`code-block.ts`) plus a 608-line highlight directive (`code-block-highlight.ts`) of which 400 lines are a verbatim copy of the upstream `highlightjs-line-numbers.js@2.9.0` plugin, inlined as a private method. It drives the whole of koobiq.io — every documentation snippet and every live-example source view is a `kbq-code-block`.

- **First, the good news on the question this review was asked to settle: `code-block` does *not* share the `markdown` package's P0 sanitizer bypass.** The pipeline is `hljs.highlight()` (which HTML-escapes the source) → `DomSanitizer.sanitize(SecurityContext.HTML, …)` (`code-block-highlight.ts:176` — the real sanitizer, not `bypassSecurityTrust*`) → line-number assembly → `innerHTML`. The escaping and the sanitizer are both genuine, and no `bypassSecurityTrust*` call exists anywhere in the package. What is worth hardening is that the *last* step re-assembles the sanitized string and writes it through `Renderer2.setProperty(el, 'innerHTML', …)` (`:183`), which performs no sanitization of its own (`el[name] = value`, `dom_renderer.mjs:640-648`) — so the safety of the whole chain rests on a transform that no test covers (CB-SEC-01, P3).
- **The one release blocker is an accessible-name gap.** The soft-wrap toggle button (`code-block.html:31-46`) contains nothing but an icon `<i>` and has no `aria-label`, while its three siblings in the same file — download, copy, external link — all carry `[attr.aria-label]` (`:53, :68, :82`). The library itself detects the condition and stamps `.kbq-button_no-label` on the element (`button.component.ts:150-152`), and the button ships enabled on koobiq.io's own overview example. AGENTS.md states "It MUST pass all AXE checks"; `button-name` is exactly such a check, and a consumer cannot patch a name onto a button inside the component's own view (CB-A11Y-01).
- **Two legal inputs crash the component.** The `files` setter guards with `this._files.length < this.activeFileIndex` (`code-block.ts:260`), which is off by one: a `files` array that shrinks to exactly `activeFileIndex` leaves the index out of range, `@let file = files[activeFileIndex]` resolves to `undefined`, and `@if (file.link)` (`code-block.html:78`) throws during change detection (CB-BUG-01). Separately, `content: ''` — a legal value for a required `string` field — reaches `addLineNumbersBlockFor('')`, where `getLines` returns `[]` and `lines[-1].trim()` throws (`code-block-highlight.ts:436, 558-562`, reproduced with `node -e`); the rejection escapes into the promise chain and `pending()` is left permanently `true`, so every queued `scrollTo()` silently never runs (CB-BUG-02).
- **The vendored plugin is installed once per component instance and never uninstalled.** Every `KbqCodeBlockHighlight` that loads hljs assigns `window.hljs` (`:199`), adds a `<style>` element to `<head>` (`:354-367`) and registers a `document`-level `copy` listener (`:332-352`). The directive has no `ngOnDestroy` at all. Ten code blocks on a docs page mean ten copy handlers and ten style elements, and they survive the components that created them (CB-LIFE-01).
- **Line numbers are always built, then hidden with CSS.** `lineNumbers` only toggles a class (`code-block.ts:131`, `code-block.scss:105-107`); the directive never sees the input and unconditionally rewrites multi-line content into `<table class="hljs-ln">`. The package's own spec proves it: `should apply lineNumbers plugin` (`code-block.spec.ts:214-221`) asserts the table exists on a host whose `lineNumbers` is `false` (`:127`). Every default code block therefore exposes tabular semantics to assistive technology for content that is not a table (CB-A11Y-03).

Genuine strengths worth preserving: the async highlight.js loading design is excellent — a DI-configurable core + per-language lazy loaders (`kbqCodeBlockHighlightJsConfigProvider`) with a `pending` signal that `scrollTo()` and the overflow detector both correctly await (`code-block.ts:424-439, 506-515`); the resize path uses CDK's `SharedResizeObserver` with `takeUntilDestroyed`, which is the right primitive and is torn down correctly; the actionbar hover tracking is a clean `effect()` with `onCleanup` and is covered by five focused specs; the locale layer is fully typed and overridable, with a load-bearing comment explaining why `localeConfiguration` is a getter over a signal (`:318-320`); and the 50-case Jest suite covers the async-loading and deferred-scroll paths thoroughly — those are the hardest parts of the component and they are the best-tested.

## 3. Prioritized Findings (deduplicated, verified)

### P0 — Release blockers

**CB-A11Y-01 · The soft-wrap toggle button ships with no accessible name** — `code-block.html:31-46`; siblings at `:53, :68, :82`; corroboration in `button/button.component.ts:132-136, 150-152`.
The button rendered under `@if (canToggleSoftWrap())` has exactly one child — `<i kbq-icon="kbq-text-overflow_16">` or `<i kbq-icon="kbq-text-wrap_16">` (`code-block.html:41-45`). `KbqIcon`'s template is `<ng-content />` with an icon-font class (`icon.component.ts:22-32`), so the element carries no text; the glyph is CSS `::before` content. There is no `aria-label`, no `aria-labelledby`, no `title`. `kbqTooltip` contributes nothing either — the tooltip package binds no ARIA at all (grep for `aria` across `tooltip.component.ts`, `tooltip.component.html` and `core/pop-up/pop-up-trigger.ts` returns zero hits), and `KbqButton`'s host block adds only `disabled`/`aria-disabled`/`tabindex` (`button.component.ts:325-332`). The result is an interactive control whose accessible name is the empty string — an axe-core `button-name` violation (WCAG 4.1.2, Level A), which AGENTS.md's "It MUST pass all AXE checks" mandate makes a blocker rather than a judgement call. The three sibling actions in the same `<div class="…__button-stack">` all get it right (`[attr.aria-label]="localeConfiguration.downloadTooltip"` at `:53`, `…copyTooltip` at `:68`, `…openExternalSystemTooltip` at `:82`), so this is an omission, not a design decision. Two further pieces of evidence that it is real: the button library already *detects* the condition and stamps `.kbq-button_no-label` on exactly this element ("Whether the projected label holds no text at all, e.g. an icon-only button", `button.component.ts:150-152`); and `canToggleSoftWrap` is enabled in the published overview example (`docs-examples/components/code-block/code-block-overview/code-block-overview-example.ts:22`), so the defect is live on koobiq.io. A consumer cannot fix it — the button lives inside `kbq-code-block`'s own view, and there is no input, token or projection slot that reaches it.
**Fix:** add `[attr.aria-label]` to the soft-wrap button, mirroring its siblings and following the icon that is actually shown: `[attr.aria-label]="softWrap ? localeConfiguration.softWrapOffTooltip : localeConfiguration.softWrapOnTooltip"`. Also add `aria-pressed` (`[attr.aria-pressed]="softWrap"`) so the toggle state is exposed, and set `aria-hidden="true"` on the two decorative `<i kbq-icon>` children. Note the repo's stronger rule while you are there: AGENTS.md says component-provided default ARIA text should come from `kbqInjectA11yLocaleConfiguration()` — the whole actionbar currently sources ARIA from the `codeBlock` locale section instead, which is defensible (the strings are localized and consumer-overridable) but should be a deliberate, documented choice. Guard it with a Jest case that renders `canToggleSoftWrap` and asserts a non-empty computed accessible name, and add a `jest-axe` pass over the full actionbar (all four buttons enabled) — the package currently has no axe assertion anywhere.

### P1 — High

**CB-BUG-01 · Off-by-one in the `files` setter leaves `activeFileIndex` out of range, and the template throws** — `code-block.ts:252-267` (specifically `:260`), `code-block.html:1, 78, 109`.
The setter resets the selection with `if (this._files.length < this.activeFileIndex) { this.onSelectedTabChange(0); }` (`:260`). Valid indices are `0 … length - 1`, so the reset is needed whenever `activeFileIndex >= length` — the condition misses the boundary case `activeFileIndex === length` exactly. Concrete reproduction, entirely within the documented API: render three files, let the user click the third tab (`onSelectedTabChange(2)` sets `activeFileIndex = 2`, `:461-467`), then rebind `[files]` to a two-element array. `2 < 2` is false, the index stays at `2`, and `@let file = files[activeFileIndex]` (`code-block.html:1`) evaluates to `undefined`. The very next dereference in the template, `@if (file.link)` at `:78`, throws a `TypeError` during change detection; if that line were guarded, `[file]="file"` at `:109` would push `undefined` into `KbqCodeBlockHighlight.set file`, where `this.highlight(file)` reads `file.content` (`code-block-highlight.ts:166`) and throws instead. Input-ordering makes the trap easy to walk into: Angular applies inputs in template declaration order, so a consumer writing `[files]` before `[activeFileIndex]` — as the package's own spec host does (`code-block.spec.ts:93, 103`) — always runs the setter against the *previous* index. `numberAttribute` on `activeFileIndex` (`:274`) adds a second door: a non-numeric bound value yields `NaN`, `length < NaN` is false, and `files[NaN]` is `undefined` again. No spec covers a shrinking `files` array.
**Fix:** change the guard to `if (this.activeFileIndex >= this._files.length) { this.onSelectedTabChange(0); }` and add a `Number.isInteger` / clamp step so `NaN` and negative values also fall back to `0`. Because `onSelectedTabChange` emits `activeFileIndexChange` (`:464`), the clamp also repairs the two-way binding, which currently keeps reporting a dead index. Add Jest cases for: three files → select index 2 → rebind to two files (asserts no throw and `activeFileIndex === 0`); the same with a one-element array; and `[activeFileIndex]="'x'"`. Consider making the whole read defensive in the template too (`@let file = files[activeFileIndex] ?? files[0]`), so a future regression degrades instead of crashing.

**CB-BUG-02 · Empty file content throws inside the line-numbers plugin and leaves `pending()` stuck at `true`** — `code-block-highlight.ts:147-186` (`:177`), `:414-422`, `:432-437`, `:558-562`; type contract at `types.ts:9-13`.
`KbqCodeBlockFile.content` is a required `string`, and `''` is a legal value — an empty file, a snippet that has not loaded, an API field that came back blank. Follow it through: `hljs.highlight('', { language: 'plaintext' })` returns `{ value: '' }` (verified against the installed `highlight.js@11.11.1`); `DomSanitizer.sanitize(SecurityContext.HTML, '')` returns `''`; `lineNumbersValue('')` passes its `typeof value !== 'string'` guard (`:414-415`), sets `element.innerHTML = ''`, and calls `addLineNumbersBlockFor('', …)`; `getLines('')` returns `[]` because of its `if (text.length === 0) return []` early exit (`:558-559`); and the very next line, `if (lines[lines.length - 1].trim() === '')` (`:436`), dereferences `lines[-1]`, which is `undefined`. Reproduced in isolation with `node -e` on the exact plugin code: `TypeError: Cannot read properties of undefined (reading 'trim')`. The throw happens inside `this.load(…).then(() => this.highlight(file))` (`:115`) or in the synchronous branch at `:117`, so on the async path it surfaces as an unhandled promise rejection rather than an error the consumer can catch. Worse than the console noise is the state it leaves behind: `highlight()` sets `_pending.set(true)` at `:148` and never reaches `_pending.set(false)` at `:185`, so `pending()` stays `true` forever for that render. `KbqCodeBlock.scrollTo()` explicitly waits on that signal (`code-block.ts:429-435`), which means every `scrollTo` — including the one `onSelectedTabChange` fires on tab switch (`:465`) and the one `toggleViewAll` fires on collapse (`:417`) — is queued and never executes. The interpolated `{{ file.content }}` in the template means nothing is visibly missing, so the failure is silent.
**Fix:** two independent guards, take both. (1) In `addLineNumbersBlockFor`, bail out before the dereference: `if (lines.length === 0) return inputHtml;`. The vendored file's header says it "is not intended for editing" (`:203-206`), so make the patch explicit — a short comment naming the upstream divergence, or better, move the plugin to its own file where a diff against `v2.9.0` is reviewable. (2) In `highlight()`, wrap the transform in `try { … } finally { this._pending.set(false); }` so a future failure in the vendored code cannot wedge `pending` and strand every queued `scrollTo`. Add Jest cases for `content: ''`, `content: '\n'` and `content: '   '` (the last two currently work and should stay working), plus one asserting `pending()` returns to `false` after a highlight that throws.

**CB-A11Y-02 · A successful copy is confirmed only to mouse users; keyboard and screen-reader users get nothing** — `code-block.ts:551-559, 391-397`, `code-block.html:63-76`; mechanics in `core/pop-up/pop-up-trigger.ts:529-533, 668-670`.
`copyCode()`'s entire feedback channel is one line: `copyButtonTooltip.content = this.localeConfiguration.copiedTooltip` (`:557`). Three things go wrong with it. **(1) The tooltip is mounted on a wrapper `<div>`, not on the button** (`code-block.html:64`: `<div #copyButtonTooltip="kbqTooltip" [kbqTooltip]="…">` wrapping the `<button>` at `:65`). `KbqTooltipTrigger` defaults to `hover, focus` (`tooltip.component.ts:343, 350`) and binds its listeners with `getNativeElement().addEventListener(event, listener)` (`pop-up-trigger.ts:668-670`) — that is, on the `<div>` itself. `mouseenter`/`mouseleave` still fire, because the pointer entering the button also enters the wrapper; `focus` does **not**, because `focus` does not bubble and the wrapper is not focusable. A keyboard user who tabs to the copy button therefore never sees the tooltip at all, before or after copying. **(2) There is no live region.** Even for a mouse user with a screen reader, silently rewriting a tooltip's text is not an announcement; the tooltip package binds no `role="tooltip"` and no `aria-describedby` (verified by grep across the package), so nothing associates the changed text with the button, whose own `aria-label` remains the unchanged "Copy" (`code-block.html:68`). **(3) Failure is swallowed.** `this.clipboard.copy(file.content)` returns `false` when the underlying `execCommand` fails — a real outcome under some permission and iframe configurations — and the `&&` at `:556` simply does nothing, so a failed copy is indistinguishable from a successful one for every user. A fourth, narrower defect sits in the same area: the `visibleChange` subscription that restores the "Copy" text is established once in `ngAfterViewInit` (`:391-397`) with an optional chain; if `canCopy` is `false` at that moment and flipped on later, `copyButtonTooltip()` is `undefined`, the subscription is never created, and the tooltip stays on "Copied" permanently after the first copy. The package's own spec host starts with `canCopy = false` (`code-block.spec.ts:131`), so this is exactly the untested path.
**Fix:** move `[kbqTooltip]` and the `#copyButtonTooltip` reference onto the `<button>` itself and delete the wrapper `<div>` — the wrapper buys nothing that the button cannot do, and it is what breaks the focus trigger. Announce the result through CDK's `LiveAnnouncer`: `this.liveAnnouncer.announce(copied ? localeConfiguration.copiedTooltip : <failure string>, 'assertive')`, capturing the boolean instead of discarding it, and add a failure string to `KbqCodeBlockLocaleConfiguration` (`core/locales/types.ts:41-55`) in all shipped locales. Note that `LiveAnnouncer` appears nowhere in `packages/components` today, so this establishes the pattern — keep the injection lazy and document it. Replace the one-shot `ngAfterViewInit` wiring with an `effect()` over the `copyButtonTooltip()` signal so a later `canCopy` flip still gets its reset subscription. Cover with specs that (a) assert `clipboard.copy` was called with `files[activeFileIndex].content` rather than spying on `copyCode` itself (see CB-TEST-01), (b) drive `focusMonitor.focusVia(button, 'keyboard')` and assert the tooltip overlay appears, and (c) mock `Clipboard.copy` to return `false` and assert the failure announcement.

### P2 — Should fix

**CB-LIFE-01 · The line-numbers plugin is re-installed per component instance and never uninstalled** — `code-block-highlight.ts:127-145, 196-201, 208-232, 332-352, 354-367`; no `ngOnDestroy` anywhere in the class.
`load()` ends with `this.initLineNumbersPlugin(instance)` (`:144`), which assigns `this.window['hljs'] = instance` (`:199`) and then runs the vendored plugin body. That body unconditionally (a) overwrites four functions on the global `hljs` object (`:221-226`), (b) calls `addStyles()`, which creates a `<style>` element and appends it to `<head>` (`:354-367`), and (c) registers a `copy` listener on the whole `document` (`:332-352`). None of the three is guarded against having already run, and `load()` runs once per directive instance because `this.hljs` is per-instance state (`:97, 114`). Ten `kbq-code-block` elements on a documentation page therefore mean ten identical `<style>` nodes in `<head>` and ten `copy` handlers on `document`, every one of which fires on every copy anywhere in the application, walks the DOM via `isHljsLnCodeDescendant` (`:233-245`) and — for a selection inside a code block — calls `e.preventDefault()` and `setData` redundantly. Because `KbqCodeBlockHighlight` declares no `ngOnDestroy`, all of it outlives the components: navigating a docs site accumulates listeners and style nodes for the lifetime of the page. There is also a re-entrancy hole: `set file` checks `if (!this.hljs)` (`:114`) *before* the async load resolves, so two rapid `[file]` changes issue two `load()` calls, install the plugin twice for one instance, and resolve in arbitrary order — whichever promise settles last wins, regardless of which file is actually selected. Finally, `window.hljs` is a global the component does not own; an application that already uses highlight.js has its instance silently replaced.
**Fix:** hoist the plugin out of the directive. Move it to a module-scope function in its own file (which also makes it diffable against upstream `v2.9.0` — see CB-BUG-02) and install it exactly once behind a module-level `let installed = false` flag or a `providedIn: 'root'` service, so the `<style>` node and the `copy` listener are created once per application. Stop writing to `window.hljs`: keep the instance on the service and pass it in, so `highlight()` can call `lineNumbersValue` directly instead of routing through the global (`:177`). Register the `copy` listener with an `AbortController` (or return a teardown from the installer) and dispose it from the service's `DestroyRef`. Close the re-entrancy hole by caching the in-flight promise (`private loading: Promise<void> | null`) and reusing it, and by capturing a request id so a stale `highlight()` cannot overwrite a newer one. Guard with a spec that creates and destroys three code blocks and asserts `document.querySelectorAll('style').length` and the `copy` listener count are unchanged.

**CB-A11Y-03 · The line-number `<table>` is generated unconditionally, so every multi-line code block exposes tabular semantics** — `code-block.ts:131`, `code-block.html:106-109`, `code-block-highlight.ts:177, 432-469`, `code-block.scss:105-107`; proof in `code-block.spec.ts:127, 214-221`.
`lineNumbers` on `KbqCodeBlock` only drives a class: `'[class.kbq-code-block_hide-line-numbers]': '!lineNumbers()'` (`code-block.ts:131`), and the SCSS hides the number cells with `display: none` (`code-block.scss:105-107`). The value never reaches `KbqCodeBlockHighlight` — `code-block.html:109` binds only `[file]`, and the directive has no `lineNumbers` input — so `highlight()` always calls `lineNumbersValue` (`code-block-highlight.ts:177`), and `addLineNumbersBlockFor` wraps anything with more than one line into `<table class="hljs-ln">` with a `<tr>`/two-`<td>` pair per line (`:440-465`). The package's own test says so out loud: `should apply lineNumbers plugin` (`code-block.spec.ts:214-221`) asserts `querySelector('.hljs-ln')` is an `HTMLTableElement` on a host whose `lineNumbers` is `false` (`:127`). For assistive technology this turns a block of prose-like code into a data table: a screen reader announces "table, N rows, 2 columns" and switches the user into table-navigation mode for content that has no tabular meaning (WCAG 1.3.1). Note the precision — this is a WCAG judgement, not an automated axe failure; axe does not flag a layout table that carries no header cells. There is also a plain cost dimension: a 500-line snippet becomes 500 `<tr>`s with 1000 `<td>`s and 500 `<div>`s regardless of whether numbers are shown.
**Fix:** two moves. (1) Emit `role="presentation"` on the generated table and `role="presentation"` on its rows/cells (a one-line change to the `format('<table class="{0}">{1}</table>', …)` call at `:465` and the row template at `:444-462`), so the structure stops being announced as data. (2) Forward the toggle so the table is not built at all when it is not wanted: add a `lineNumbers` input to `KbqCodeBlockHighlight`, bind it from `code-block.html:109`, and skip `lineNumbersValue` entirely when it is `false` — the sanitized HTML can go straight to `innerHTML`, which also removes one unsanitized transform from the chain (see CB-SEC-01). Keep the CSS rule as a fallback for the `hideTabs`-style class overrides that already exist in the wild. Cover with a spec asserting that `lineNumbers=false` yields **no** `.hljs-ln` element (the inverse of the current `:214-221` case, which must be rewritten rather than kept).

**CB-BUG-03 · `hideTabs` latches to `true` and is never reset when `files` changes back** — `code-block.ts:257-267` (`:264-266`), `:291-299`.
The `files` setter contains a one-way rule: `if (this._files.length === 1 && !this._files[0].filename) { this.hideTabs = true; }` (`:264-266`). There is no `else`. Once a code block has been given a single unnamed file, the tab bar is gone for good: rebinding `[files]` to a multi-file array leaves `_hideTabs` at `true`, the `@if (!hideTabs)` block in the template (`code-block.html:4`) never renders again, and the user loses access to every file but the active one. The `hideTabs` setter also emits `hideTabsChange` (`:298`) from inside an input setter, so a consumer using `[(hideTabs)]` is told about the latch but never about a release. The package's own spec documents the fragility of the current arrangement without naming it: `should NOT hide tabs for single file without filename when set outside` (`code-block.spec.ts:292-309`) only passes because `[files]` is declared before `[hideTabs]` in the host template (`:93, :99`), so Angular's declaration-order input application lets the explicit binding overwrite the latch. Reorder those two lines in a consumer's template and the same code hides the tabs. Note also that `hideTabs` is an `@Input` the component writes to itself — the same pattern the migration TODOs at `:289-291` flag.
**Fix:** make the derivation total instead of one-way. Track the auto-derived value separately from the consumer's explicit one: keep `_hideTabs` as the explicit override (`undefined` when unbound) and compute the effective value as `computed(() => this._hideTabs() ?? (files.length === 1 && !files[0]?.filename))`. That removes the write-to-own-input, makes the rule symmetrical, and stops `hideTabsChange` firing from inside a setter. If the accessor pair must stay for now, the minimum fix is an `else this.hideTabs = false;` branch plus a guard so the emit only fires on an actual change. Cover with a spec that goes single-unnamed → multi-named and asserts the tab bar returns, and one that declares `[hideTabs]` *before* `[files]` in the host template and asserts the same result as the existing `:292-309` case.

**CB-BUG-04 · Overflow detection is wired once, so a `maxHeight` bound later never gets a "View all" button** — `code-block.ts:388-389, 495-521`, `:201, 206-208`.
`setupContentOverflowDetection()` runs exactly once, from `ngAfterViewInit` (`:389`), and returns early on `if (!this.maxHeight()) return;` (`:498`). `maxHeight` is a signal input (`:201`), so a consumer binding `[maxHeight]="height()"` where `height()` starts at `0`/`undefined` and becomes `400` later gets no `SharedResizeObserver` subscription, no `checkOverflow()`, and therefore `contentExceedsMaxHeight` stays `false` forever — the `@if (contentExceedsMaxHeight())` block in the template (`code-block.html:111`) never renders and the content is silently clipped with no way to expand it. `calculatedMaxHeight` (`:206-208`) meanwhile reacts immediately, so the clipping *does* apply; only the escape hatch is missing. The two guards are also inconsistent with each other — `:498` uses `!this.maxHeight()` while `:207` uses `this.maxHeight() > 0` — which matters for a bound value of `NaN` (from `numberAttribute` on a non-numeric input): `!NaN` is `true` so detection is skipped, and `NaN > 0` is `false` so no clipping is applied, which happens to be consistent by accident rather than by construction. The git history shows this area has already needed one repair (`96b8ed7bc` "fix(code-block): show viewAll on overflow (#DS-4920)").
**Fix:** replace the one-shot call with an `effect()` that re-establishes the observer whenever `maxHeight()` changes, using `onCleanup` to drop the previous subscription — the component already uses exactly this shape for hover tracking (`:470-493`), so the pattern is in-file. Unify the two guards on a single `hasMaxHeight = computed(() => this.maxHeight() > 0)` and use it in both places. **CB-PERF-01 · `codeContentTabIndex` forces layout on every change-detection pass, and the scrollable region is untabbable whenever `maxHeight` is active** — `code-block.ts:331-347`, `code-block.html:98-104`, `code-block.scss:123-127, 178-182`; fixture at `e2e.ts:64-67`.
`[tabIndex]="codeContentTabIndex"` (`code-block.html:104`) is a template binding onto a getter that calls `canCodeContentBeFocused`, which reads `scrollHeight`, `scrollWidth`, `clientHeight` and `clientWidth` off the live element (`code-block.ts:341-347, 524-526`). Every change-detection pass over this view therefore forces four synchronous layout reads per code block; with `provideZoneChangeDetection({ eventCoalescing: true })` in the docs app (`apps/docs/src/app/config.ts:24`) and a dozen code blocks on a reference page, that is dozens of forced reflows per tick, for a value that changes almost never. Two correctness problems ride along. **(1) Staleness:** the getter reads no signal, so nothing re-evaluates it when the content changes; the single `changeDetectorRef.markForCheck()` that exists for this purpose runs in `ngAfterViewInit` (`:399-401`), which is *before* the async highlight resolves and rewrites the subtree. Under zone.js the promise resolution happens to schedule a pass; a zoneless application gets a permanently stale `tabindex`. **(2) An unreachable scroll region:** `canCodeContentBeFocused` requires `!this.calculatedMaxHeight` (`:346`), so whenever `maxHeight` is set and `viewAll` is false the region is `tabindex="-1"`. When the content also overflows vertically this is tolerable — the "View all" button is offered — but when it does *not* overflow vertically the `@if` never renders the button, `:not(:has(.kbq-code-block__view-all))` gives the region `overflow: auto` (`code-block.scss:178-182`), and a long single line becomes horizontally scrollable content that no keyboard user can reach or scroll (WCAG 2.1.1). That combination is not hypothetical: it is an e2e fixture case, `e2eCodeBlockMaxHeightSingleLine` (`e2e.ts:64-67`), which pairs `maxHeight="200"` with a one-line file.
**Fix:** stop measuring during rendering. Derive focusability from the same `SharedResizeObserver` stream that already exists for overflow detection (extend it to run unconditionally, not just when `maxHeight` is set) plus the `highlight().pending()` signal, and store the result in a `signal<boolean>` that the template reads — one measurement per real layout change instead of one per change-detection pass, and no staleness under zoneless. Fix the `maxHeight` branch by making focusability depend on actual scrollability rather than on the presence of a max height: keep `tabindex="0"` whenever `hasScroll(element)` is true, including the collapsed state, and drop the `!calculatedMaxHeight` term. While there, give the region an accessible name — it already carries `role="tabpanel"` from `kbqTabNavPanel`, whose `aria-labelledby` is only populated when a tab is active (`tab-nav-bar.ts:141-146, 337-340`), which is never the case for a single file (see the `$count > 1` condition at `code-block.html:11`) or when `hideTabs` is set. Cover with a Playwright case that tabs into a `maxHeight` single-line block and asserts the region receives focus, and with a Jest case asserting `tabindex` flips to `0` after the mock resize observer reports scrollable metrics.

**CB-SSR-01 · The directive's SSR guards are unreachable, and the whole highlight pipeline runs on the server for a component that already opts out of hydration** — `code-block-highlight.ts:112, 211, 127-145, 196-201`; token at `core/tokens/window.ts:7-21`; contrast with `code-block.ts:342, 496`; server stub at `apps/docs/src/config.server.ts:6-54`.

### P3 — Nice to have / hygiene

**CB-SEC-01 · The sanitized HTML is re-assembled by untrusted-by-construction code before it reaches a raw `innerHTML` sink, and nothing tests the chain** — `code-block-highlight.ts:161-183` (`:176, :177, :183`), `:414-422, :432-469, :540-556`; contrast with `markdown.component.ts:99` and `docs/review/REVIEW.markdown.md` (MD-BUG-01); sink semantics in `node_modules/@angular/platform-browser/fesm2022/dom_renderer.mjs:640-648`.
State the conclusion first, because it is the question this review was asked to answer: **`code-block` does not share the `markdown` package's P0.** There is no `bypassSecurityTrustHtml` anywhere in the package; `highlight()` escapes the source through `hljs.highlight()` (highlight.js HTML-escapes all emitted text, verified against `11.11.1`) and then runs the result through the genuine Angular sanitizer, `this.domSanitizer.sanitize(SecurityContext.HTML, highlightedHTML)` (`:176`) — the exact opposite call to the one that makes `markdown` unsafe. What remains is a defence-in-depth gap rather than a live vulnerability, and it is worth closing before someone widens the pipeline. The sanitized string is **not** the string that reaches the DOM: it is handed to `lineNumbersValue` (`:177`), which sets it as `innerHTML` on a detached `<code>` (`:417-419`), mutates the parsed tree via `duplicateMultilineNode`'s own `element.innerHTML = result` (`:555`), reads `element.innerHTML` back, splits it on `/\r\n|\r|\n/` (`:429, 558-562`) — a split that can cut through markup rather than between elements — and re-concatenates the pieces into a `<table>` with a `String.replace`-based templating helper (`:444-462, 581-585`). The output of all that is written with `this.renderer.setProperty(this.nativeElement, 'innerHTML', …)` (`:183`), and `Renderer2.setProperty` sanitizes nothing: `DefaultDomRenderer2` does `el[name] = value` after a synthetic-prop check (`dom_renderer.mjs:640-648`). A template `[innerHTML]` binding would have compiled to `ɵɵsanitizeHtml`; this call does not. So the security of the component rests on the correctness of 130 lines of vendored string manipulation that has no test, and on the fact that the class documents itself as "not intended for editing" (`:203-206`). Neither guide mentions sanitization or a trust boundary at all, so a consumer feeding user-authored content has no stated contract to rely on.
**Fix:** move the sanitizer to the end of the chain so it guards the string that is actually assigned: `renderer.setProperty(el, 'innerHTML', this.domSanitizer.sanitize(SecurityContext.HTML, highlightedHTMLWithLineNumbers))`. Keeping the existing call at `:176` as well is cheap and worth it (it keeps the detached-element parse clean). Better still, combine with CB-A11Y-03's second move: when line numbers are off, skip `lineNumbersValue` entirely and assign the sanitized string directly, which removes the untested transform from the default path. Add the contract to `code-block.en.md`/`code-block.ru.md` in one sentence — "content is HTML-escaped by highlight.js and sanitized by Angular before rendering" — and guard it with Jest cases that feed `content: '<img src=x onerror=alert(1)>'`, `'<script>alert(1)</script>'` and `'</td></tr><tr><td onclick=alert(1)>'` (the last one specifically probes the line-splitting reassembly) and assert on the **rendered** `code.innerHTML` that no `onerror`/`onclick` attribute survives.

**CB-API-01 · A `@docs-private` directive is published as `@public` with two inputs no consumer can reach, and the deprecated inputs are still used by the repo's own docs app** — `code-block-highlight.ts:77-89, 121-125`, `public-api.ts:2`, `tools/public_api_guard/components/code-block.api.md:133-142, 56-61, 94-95`; consumer at `apps/docs/src/app/components/live-example-viewer/docs-live-example-viewer.html:48`.
`KbqCodeBlockHighlight`'s class JSDoc says `@docs-private` (`:80`), the NgModule does not export it (`code-block.module.ts:4-7`), and nothing in the repo applies `code[kbqCodeBlockHighlight]` outside `code-block.html:109` — yet `public-api.ts:2` re-exports the whole file, so the API guard lists the class as `// @public` with a stable signature (`code-block.api.md:133-142`). `@docs-private` is a documentation tag; it does not strip anything from the report or from `dist`. The consequence is a frozen contract nobody meant to make, and it is visibly half-built: `startFrom` (`:122`) and `singleLine` (`:125`) are real, transformed inputs that `code-block.html:109` never binds, so a consumer of `kbq-code-block` cannot start numbering at anything but `1` and cannot get numbers on a single-line file — the features exist, are exported, are typed, and are unreachable. Separately, three deprecated inputs remain live: `canLoad` → `canDownload` (`code-block.ts:217-220`), `codeFiles` → `files` (`:240-243`) and the `scrollableCodeContent` view child marked "will be removed from public API (mark as private) in the next major release" (`:146`). The repo's own docs app still uses one of them — `docs-live-example-viewer.html:48` binds `[codeFiles]` — so the deprecation is not being followed internally, which is the usual sign that it will not be followed externally either.
**Fix:** decide the directive's status. If it is internal, mark it `@internal`, drop it from `public-api.ts` and keep it a private import of the component (note that `@internal` alone does **not** remove a member from `*.api.md` without `stripInternal: true`). If it is public, delete the `@docs-private` tag, document it in the guide, and forward `startFrom`/`singleLine` from `KbqCodeBlock` as real inputs so they are reachable. Either way, migrate `apps/docs` off `[codeFiles]` onto `[files]` in the same change, and schedule `canLoad`/`codeFiles` for removal with an `ng-update` migration schematic in `packages/schematics` — AGENTS.md requires one for a breaking change. Run `yarn run build:components` then `yarn run approve-api`; the guard reads `dist/*.d.ts`, so build first.

**CB-BUG-05 · `openLink()` opens consumer URLs without `noopener`, and `downloadCode()` never revokes its object URL** — `code-block.ts:566-573` (`:571`), `:583-592` (`:588-591`).
Two small defects in the actionbar's side effects. **(1)** `this.window.open(safeURL.toString(), '_blank')` (`:571`) omits the `'noopener'` window feature. The implicit-`noopener` behaviour modern browsers apply to `<a target="_blank">` does not extend to `window.open`, so the opened document receives a live `window.opener` reference to the host application and can navigate it (reverse tabnabbing). The URL comes from `KbqCodeBlockFile.link` (`types.ts:34`), which is consumer-supplied and therefore usually trusted — but an application that renders file metadata from an API has an attacker-influenced value here. Worth noting in passing: the `if (safeURL)` guard at `:570` is dead. Angular's URL sanitizer does not return `null` for a rejected value; it returns the original string prefixed with `unsafe:`, which is truthy. The rejection still works — the browser cannot navigate to an `unsafe:` scheme — but the guard reads as if it were the defence, and it is not. **(2)** `downloadCode()` creates a blob URL with `URL.createObjectURL(blob)` (`:586`) and never calls `URL.revokeObjectURL`. The blob is pinned in memory for the lifetime of the document; a user who downloads a 2 MB file ten times has leaked 20 MB. The detached `<a>` is also never appended to the document, which is fine in current browsers but is worth a comment since it is a common source of "download does nothing" reports on older engines.
**Fix:** `this.window.open(safeURL.toString(), '_blank', 'noopener')` — and either drop the dead `if (safeURL)` or replace it with a real check (`!safeURL.startsWith('unsafe:')`) plus a dev-mode warning, so a rejected link fails loudly instead of opening a broken tab. In `downloadCode()`, revoke on the next task: `link.click(); setTimeout(() => URL.revokeObjectURL(url));` (the timeout is needed — revoking synchronously after `click()` cancels the download in some browsers). Cover both with the behavioural specs described in CB-TEST-01.

**CB-STYLE-01 · 102 CSS custom properties are declared with the literal value `null` and referenced nowhere, plus one always-dead cross-package `var()`** — `code-block-tokens.scss:18-119, 134`; theme at `_code-block-theme.scss:3-5, 48-305`.
The token file declares 238 custom properties, of which 102 follow the pattern `--kbq-code-block-font-hljs-<scope>-font-style: null;` / `…-font-weight: null;` (`:18-119`, 51 hljs scopes × 2). SCSS does not elide a `null` in a custom-property declaration the way it does for a normal property — the value is emitted verbatim — so every `.kbq-code-block` element in the shipped stylesheet carries 102 declarations whose value is the token `null`. The cost is small but the signal is not: the names read like a themable surface, and a designer who sets `--kbq-code-block-font-hljs-comment-font-style: italic` will find it does nothing, because the theme never applies font style or weight per token type at all. **Fix:** either delete the 102 `null` declarations, or make them real — apply `font-style: kbq-code-block-hljs-attr(<scope>-font-style)` and `font-weight` alongside the existing background/color pair in the `kbq-code-block-theme` mixin and give them non-`null` defaults, which is what the naming already promises (italic comments and bold keywords are the two most-requested code themes). Do not leave them declared-but-inert. Replace `var(--kbq-divider-color, var(--kbq-line-contrast-less))` at `:134` with the fallback it always resolves to, and coordinate with DIV-STYLE-01 so only one package changes. ## Appendix A — Review Methodology

Findings were gathered by reading the complete package end to end (`code-block.ts`, `code-block-highlight.ts`, `code-block.html`, all three SCSS files, `types.ts`, the Jest spec, the e2e fixture and Playwright spec, both guides and both examples stubs), then cross-checking each candidate against six independent sources: the installed `highlight.js@11.11.1` (probed directly with `node -e` for the empty-content and escaping behaviour), the installed `@angular/platform-browser` renderer implementation (`dom_renderer.mjs:640-648`, to establish whether `setProperty` sanitizes), the shared components the template composes (`tabs/tab-nav-bar.ts`, `tooltip/tooltip.component.ts`, `core/pop-up/pop-up-trigger.ts`, `core/overflow-shadow/overflow-shadow.ts`, `button/button.component.ts`, `icon/icon.component.ts`), the API guard report, the workspace configuration (`tsconfig.json:114-118`, `eslint.config.js:72-108`, `apps/docs/src/app/config.ts:24`, `apps/docs/src/config.server.ts`), and every in-repo consumer found by grep. Design tokens were resolved by extracting every `var(--kbq-…)` reference from the SCSS and the theme mixin's interpolated names and diffing them against `code-block-tokens.scss` plus `@koobiq/design-tokens/web/new/css-tokens-{light,dark}.css` and `web/css/index.bundled.css` — every referenced token resolves; the finding is the inverse (102 declared and unreferenced). The `markdown` package's review (`docs/review/REVIEW.markdown.md`, MD-BUG-01) was read in full specifically to determine whether `code-block` shares its sink; it does not, and CB-SEC-01 records the comparison explicitly rather than leaving the question open.

Refuted during verification:
- **"`code-block` shares the `markdown` P0 sanitizer bypass"** — refuted, and this was the primary question. There is no `bypassSecurityTrust*` call in the package; `code-block-highlight.ts:176` calls the real `DomSanitizer.sanitize(SecurityContext.HTML, …)`, and highlight.js escapes the source before that. The residual concern is the *post*-sanitizer reassembly, filed as CB-SEC-01 at P3 — a hardening item, not a vulnerability.
- **"The `SharedResizeObserver` subscriptions leak"** — refuted. Both of them are piped through `takeUntilDestroyed(this.destroyRef)`: the component's own at `code-block.ts:517-520`, and the one inside `KbqOverflowShadowContainer` at `core/overflow-shadow/overflow-shadow.ts:123-126`. CDK's `SharedResizeObserver` refcounts and disconnects when the last subscriber leaves. The teardown gap in this package is entirely in the vendored plugin (CB-LIFE-01), which uses raw `addEventListener`, not the observer.
- **"Copying requires the Clipboard API permission and can be blocked"** — refuted as stated. CDK's `Clipboard.copy` uses a hidden `<textarea>` plus `document.execCommand('copy')`, which needs a user gesture but no Permissions API grant and triggers no permission prompt. It can still return `false`, which the component ignores — that part survives, inside CB-A11Y-02.
- **"Pressing Enter on the 'View all' button toggles twice, because `(keydown.enter)` and `(click)` both fire"** — refuted. `onViewAllEnterKeydown` calls `event.preventDefault()` first (`code-block.ts:534`), and the synthesized `click` is the default action of the `keydown` on a native `<button>`, so it is suppressed. The related real observation — that the spec cannot detect a regression here because its `KeyboardEvent` is not `cancelable` — is filed inside CB-TEST-01.
- **"The tab switcher cannot be operated from the keyboard"** — refuted. `KbqPaginatedTabHeader` installs a `FocusKeyManager` with horizontal orientation (`tabs/paginated-tab-header.ts:225-229, 296-316`), and `KbqTabLink.handleKeydown` converts ENTER/SPACE into a native `click` when a `tabNavPanel` is present (`tab-nav-bar.ts:312-326`), which is what `code-block.html:13` listens for. Arrow-key roving and activation both work for multi-file blocks. The genuine gap is narrower — for a single named file `[active]="$count > 1 && …"` (`code-block.html:11`) leaves every tab `aria-selected="false"` and `tabindex="-1"`, and the panel gets no `aria-labelledby` — and it is recorded inside CB-PERF-01's fix rather than as its own finding.
- **"The overflow shadow is stale after the async highlight rewrites the content"** — refuted in practice. `KbqOverflowShadowContainer.checkOverflow()` computes `top: scrollTop > 0` (`overflow-shadow.ts:108-111`) and only the top shadow is used here (`code-block.html:3`); a freshly rendered block has `scrollTop === 0`, so the value is correct without a recheck. The directive's own JSDoc warning about content that grows `scrollHeight` without a box-size change (`:53-57`) applies to the bottom shadow, which `code-block` does not use.

Corrected on verification:
- **CB-A11Y-01** was drafted as "the actionbar buttons have no accessible names". Reading `code-block.html` showed three of the four are correctly labelled at `:53, :68, :82`; only the soft-wrap button is missing one. Narrowing it made the finding stronger, not weaker — the in-file inconsistency is what proves it is an omission rather than a design decision, and it kept the P0 defensible.
- **CB-PERF-01** was drafted as two separate findings ("layout thrash in a getter" and "the scroll region is not keyboard reachable under `maxHeight`"). They share one cause — a template-bound getter that measures live layout and gates on `calculatedMaxHeight` — and one fix, so they were merged. During the merge the keyboard claim was narrowed: with vertical overflow the "View all" button provides a keyboard path, so the reachability failure is specific to the *non*-overflowing case with horizontal scroll, which the `e2eCodeBlockMaxHeightSingleLine` fixture happens to construct.
