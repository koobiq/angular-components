# Koobiq `scrollbar` Component — Code Review & Improvement Plan

> Scope: `packages/components/scrollbar` (the dependency-free implementation, the `deprecated/` secondary entry point, tokens and SCSS, Jest spec, e2e fixture + Playwright spec, user guides, both API guard reports, the `scrollbar-deprecated-path` migration schematic and the migration guide) · Commit `b665e503` · 2026-08-28
> Generated by a multi-dimension review (architecture, RxJS/lifecycle, correctness, accessibility, performance, public API/types, styles, tests, docs, SSR) with manual verification of every finding against the source, the in-repo consumers, the design-token package and the workspace/Playwright configuration. 16 findings confirmed (P0×0, P1×3, P2×8, P3×5); 8 candidate findings refuted during verification (see Appendix A). This document is a review + roadmap; no source is modified by it.

---

## 1. Executive Summary

`scrollbar` was rewritten from a wrapper into a first-party component three weeks before this review (`3e49f593b`, DS-3176). The `overlayscrollbars@2.7.3` wrapper still exists, unchanged, behind `@koobiq/components/scrollbar/deprecated`, and an `ng update` schematic rewrites import paths for it. The new implementation is a 694-line, zero-dependency component with 67 Jest cases and 27 Playwright tests — one of the better-tested packages in the library. Its problems are almost all *systemic* rather than local: what it does to the rest of the application, not what it renders.

- **Every `KbqScrollbarViewport` silently registers a `CdkScrollable` on the app-wide `ScrollDispatcher`, with no opt-out — and three consumers have already invented three different guards against the fan-out.** `hostDirectives: [CdkScrollable, CdkMonitorFocus]` (`scrollbar.ts:249`) is unconditional, so scrolling inside any panel that uses a scrollbar broadcasts to every overlay in the application. `app-switcher.ts:904` filters with a bespoke `isInnerScroll()`; `notification-center.ts:534-541` *mutates the emitted event object* behind an `eslint-disable rxjs-x/no-nested-subscribe`; `popover.component.ts:462-463` and `app-switcher.ts:849` check for a magic `.kbq-hide-nested-popup` class. This is the same fan-out class that produced DS-5407; the scrollbar rewrite widened its blast radius from one component to every overlay panel in the library (SCB-ARCH-02).
- **The component polls the DOM with up to four independent, never-stopping `requestAnimationFrame` loops per instance.** `animationFrame()` (`scrollbar.ts:44-66`) is a recursive rAF chain with no completion condition; the track subscribes twice (`:591`, `:607`) and each thumb once (`:432`). Every throttled tick reads `clientHeight`/`scrollHeight`/`clientWidth`/`scrollWidth` off the viewport, forcing a layout flush 10 times a second per thumb and 3 times a second per track — whether or not the content overflows, whether or not the scrollbar is on screen, and forever (SCB-PERF-01).
- **The package's own `public-api.ts` is not wired to its entry point, so `KbqScrollbarModule` was never published.** `index.ts:1` reads `export * from './scrollbar';` where every sibling package (and the package's own `deprecated/index.ts:1`) reads `export * from './public-api';`. `public-api.ts` and `scrollbar.module.ts` are unreachable dead files, the module is absent from `tools/public_api_guard/components/scrollbar.api.md`, and anything a future author adds to `public-api.ts` will be dropped from the build *and* from `check-api` without a single warning (SCB-ARCH-01).
- **Two geometry bugs sit in code the tests mock around.** Drag-to-scroll maps the pointer through the *bar's* box rather than the viewport's client box (`scrollbar.ts:461, 465-466` vs `:525-526`), so when both axes overflow the drag over-scrolls by 15px of range and the thumb outruns the cursor; the Jest drag case mocks the bar rect to exactly `clientHeight` (`scrollbar.spec.ts:453-454`), the one geometry where the bug cancels. `scrollToElement`/`scrollIntoView` walk the `offsetParent` chain (`scrollbar.ts:108-120`) but `.kbq-scrollbar-viewport` never sets `position`, so a standalone `[kbqScrollbarViewport]` on a static element scrolls to the wrong offset; every test bypasses it with `offsetParent: null` (SCB-BUG-01, SCB-BUG-02).
- **The thumb advertises an interactive `role="scrollbar"` that no keyboard user can reach or operate**, there is no `tabindex` anywhere in the package, and nothing honours `prefers-reduced-motion` even though nine sibling packages and one direct consumer already do (SCB-A11Y-01, SCB-A11Y-02, SCB-A11Y-03).

Genuine strengths worth preserving, and they are substantial: the zone discipline is exemplary and *explained* — `zoneFree`/`zoneFreeScheduler`/`zoneOptimized` (`scrollbar.ts:69-105`) with a comment (`:53-56`) that correctly identifies why a recursive rAF must re-schedule outside the zone; teardown is complete (`takeUntilDestroyed()` on both thumb streams, `toSignal` on both track streams, an rAF cancel in the observable's teardown); SSR is handled deliberately via `KBQ_WINDOW` and a `requestAnimationFrame` capability check (`:45, 49-51`) rather than a `typeof window` hack; every public member carries real JSDoc, so the API report has zero `(undocumented)` markers on the component surface; the `hover` mode keys off `.cdk-keyboard-focused` rather than `:focus-within`, with a Playwright regression test for exactly the mouse-focus case that motivated it (`e2e.playwright-spec.ts:233-248`); and the migration guide (`docs/guides/migration.en.md:843-887`) is unusually honest, including the selector-collision warning most libraries omit. The engineering quality inside the file is high — the gaps are at its edges.

## 3. Prioritized Findings (deduplicated, verified)

### P0 — Release blockers

None.

### P1 — High

**SCB-ARCH-02 · Every viewport registers a `CdkScrollable` on the app-wide `ScrollDispatcher` with no opt-out; three consumers guard against the fan-out three different ways** — `scrollbar.ts:234-250` (`hostDirectives: [CdkScrollable, CdkMonitorFocus]`), consumers `app-switcher/app-switcher.ts:842-849, 898-911`, `notification-center/notification-center.ts:530-545, 598-604`, `popover/popover.component.ts:460-473`, `tabs/tab-body.html:4`.
`KbqScrollbarViewport` applies `CdkScrollable` unconditionally, and `CdkScrollable` registers itself with the root `ScrollDispatcher`, which is an application-wide bus rather than a per-subtree one: every registered scrollable's `scroll` event reaches every subscriber, including `CloseScrollStrategy`, which detaches any overlay it does not itself contain. Before the rewrite this affected the handful of elements that carried `[kbqScrollbar]`; now it affects every panel that uses `<kbq-scrollbar>` or `[kbqScrollbarViewport]` — which is app-switcher, content-panel, notification-center, the docs sidenav, and anything a consumer wraps. The evidence that this is a real, felt problem is that three components in this repository independently invented three different guards, none of them shared: `app-switcher.ts:904` pipes `scrolled()` through a private `isInnerScroll()` that does `nativeElement.closest('.kbq-app-switcher, .kbq-app-switcher-sites')`, with a five-line comment stating that without it "every arrow key would close the panel"; `notification-center.ts:534-541` subscribes to `closingActions()` and *rewrites the emitted event* (`event['kbqPopoverPreventHide'] = true; event['type'] = 'click';`) behind an `// eslint-disable-next-line rxjs-x/no-nested-subscribe`; `popover.component.ts:462` and `app-switcher.ts:849` both test for a `.kbq-hide-nested-popup` class that only `tabs/tab-body.html:4` sets. Three authors, three answers, one of which needs a lint suppression — that is the signature of a missing library-level facility, not of three unrelated bugs.
**Fix:** give `KbqScrollbarViewport` an explicit contract for dispatcher participation and stop making every consumer discover the problem. Two complementary moves: (1) add an input (e.g. `kbqScrollbarDispatchScroll`, default `true`) that, when false, provides a component-scoped `ScrollDispatcher` (or omits `CdkScrollable` via a second directive) so a panel author can opt out declaratively; (2) ship the shared guard the DS-5407 follow-up already scoped — a `kbqIsInnerScroll(overlayElement, scrollable)` helper in `core/overlay` — and replace all three hand-rolled guards with it, deleting the `rxjs-x/no-nested-subscribe` suppression at `notification-center.ts:533`. Guard with a Jest case per consumer asserting that a scroll inside the panel does not emit through that panel's `closingActions()`, plus a cross-component Playwright case: open a tooltip, scroll a `<kbq-scrollbar>` elsewhere on the page, assert the tooltip is still attached.

**SCB-PERF-01 · Up to four unconditional `requestAnimationFrame` loops per scrollbar instance, each forcing a layout read, none of which ever stop** — `scrollbar.ts:43-66` (`animationFrame()`), subscribers at `:432` (thumb), `:591` and `:607` (track); measurement getters at `:481-486` and `:620-627`.
`animationFrame()` returns an observable whose subscribe handler schedules `requestAnimationFrame(function loop(t) { subscriber.next(t); frameId = requestAnimationFrame(loop); })` — a chain with no termination condition, correctly documented at `:54-56` as one that "never stops on its own". It is subscribed four times per fully-overflowing scrollbar: `KbqScrollbarTrack.visibility` (`:591`, throttled to 300ms), `KbqScrollbarTrack.viewportBlockSize` (`:607`, 300ms), and one per `KbqScrollbarThumb` (`:432`, 100ms). Each throttled emission calls `getDimension()`/`scrollbars`, which reads `scrollTop`, `scrollHeight`, `clientHeight`, `scrollLeft`, `scrollWidth`, `clientWidth` from the viewport — six layout-dependent properties, i.e. a forced synchronous layout on every tick. So a page with one `<kbq-scrollbar>` performs ~26 forced layouts per second indefinitely; the docs application has one in the sidenav plus one per open panel. The polling is unconditional: it runs when the content does not overflow (nothing to draw), when the scrollbar is scrolled out of the viewport, and when nothing on the page has changed. Only the tab being hidden stops it, because rAF itself stops. The `throttleTime` operators reduce the *work*, not the *wake-ups* — the rAF callback still fires at display refresh rate and is simply discarded. Note this is not a leak: `takeUntilDestroyed()`/`toSignal` do cancel the loop on destroy (`:63`), so the cost is steady-state CPU, not unbounded growth.
**Fix:** replace the polling with observation. The three things being polled are all observable directly: viewport size and content size → one `ResizeObserver` watching the viewport element and `.kbq-scrollbar__content` (covers `visibility`, `viewportBlockSize` and the thumb's size fraction); scroll offset → the `scroll` listener that already exists at `:433` and is deliberately not throttled. A `MutationObserver` on the content subtree covers the residual case of content that changes `scrollHeight` without a resize of any observed box. Keep `animationFrame()` only if a measured case survives, and if so bound it — `takeWhile` on an "is dirty" flag, or restart it from a `ResizeObserver` tick rather than running it forever. Guard the change with a Jest case that asserts no `requestAnimationFrame` is scheduled for a non-overflowing `<kbq-scrollbar>` after the first render, and keep the existing Playwright thumb-metrics tests (`e2e.playwright-spec.ts:336-394`) as the behavioural regression net — they are already written against `expect.poll`, so they do not care how the update arrives.

**SCB-ARCH-01 · `index.ts` bypasses `public-api.ts`; `KbqScrollbarModule` was never published and anything added to `public-api.ts` is silently dropped** — `index.ts:1`, `public-api.ts:1-2`, `scrollbar.module.ts:1-15`, `ng-package.json:2-4`, `tools/public_api_guard/components/scrollbar.api.md:16-89`; contrast `deprecated/index.ts:1`, `divider/index.ts:1`, `button/index.ts:1`, `alert/index.ts:1`, `list/index.ts:1`.
`ng-package.json` names `index.ts` as the entry file, and `index.ts` contains exactly `export * from './scrollbar';`. `public-api.ts` — the file AGENTS.md designates as "Public exports" and which every other package in the library re-exports from `index.ts` — contains `export * from './scrollbar'; export * from './scrollbar.module';` and is imported by nothing. `git show 3e49f593b -- packages/components/scrollbar/index.ts` shows the line was changed *from* `export * from './public-api';` in the rewrite commit, so this is a regression, not an original design. Three consequences follow. (1) `KbqScrollbarModule` (`scrollbar.module.ts:15`) is unreachable: `import { KbqScrollbarModule } from '@koobiq/components/scrollbar'` does not compile, and the class is absent from `scrollbar.api.md` — which is why the report shows `KbqScrollbar`, `KbqScrollbarViewport`, `KbqNativeScrollbar` and the tokens but no module. AGENTS.md lists an NgModule wrapper as part of the standard package shape for legacy consumers; this one exists in the tree and ships nowhere. (2) The API guard's coverage silently shrank: `check-api` reads `dist/components/scrollbar/index.d.ts`, so anything reached only through `public-api.ts` is invisible to it. (3) The trap is durable — a future author adding an export to `public-api.ts` (the obvious place) gets a green build, a green `check-api`, and a package that does not export it.
**Fix:** restore `index.ts` to `export * from './public-api';`. Then rebuild and re-approve: `yarn run build:components && yarn run approve-api` (build first — the guard reads `dist/*.d.ts`), which will add `KbqScrollbarModule` to `scrollbar.api.md` as an intentional, reviewed surface addition. Since the module carries `/** @docs-private */` (`scrollbar.module.ts:13`) it will land documented rather than as an `// (undocumented)` marker. Add a one-line structural assertion to the Jest spec — `import { KbqScrollbarModule } from './public-api'` and `expect(TestBed.configureTestingModule({ imports: [KbqScrollbarModule] }))` compiles and creates a `<kbq-scrollbar>` — so the module is exercised rather than merely exported. Worth a repo-wide sweep in the same pass: `for d in packages/components/*/; do head -1 $d/index.ts; done` finds any sibling with the same drift.

### P2 — Should fix

**SCB-BUG-01 · Drag and track-click map the pointer through the bar's box instead of the viewport's client box, so both axes over-scroll whenever the other axis is visible** — `scrollbar.ts:459-471`, contrasted with `scrollbar.ts:516-527`; geometry at `scrollbar-track.scss:13-15, 49-66`; asserted by `e2e.playwright-spec.ts:153-167`; concealed by `scrollbar.spec.ts:448-467, 484-503`.
`getScrolled()` reads its geometry from `this.nativeElement.parentElement!.getBoundingClientRect()` (`:461`) — the *bar*, not the viewport — and then computes `maxTop = viewport.scrollHeight - height` and `maxLeft = viewport.scrollWidth - width` (`:465-466`) using that bar's height and width. The true scroll range is `scrollHeight - clientHeight`, which is exactly what the *rendering* path uses (`getScrolledFraction`, `:525-526`). The two disagree by however much the bar differs from the viewport's client box, and it always differs: the track host is `min/max-inline-size: calc(100% - 1px)` (`scrollbar-track.scss:13-14`), and when both axes overflow each bar additionally reserves the other's thickness — `_has-horizontal { inset-block-end: var(--kbq-scrollbar-track-size) }` (`:60-62`) and `_has-vertical { inset-inline-end: … }` (`:64-66`), 14px, a value the Playwright suite pins exactly (`e2e.playwright-spec.ts:163-166`). So the drag denominator is 15px larger than the real range on each axis. The visible effect scales inversely with the overflow: on the e2e scroll-to fixture (600px of range) the thumb outruns the cursor by ~2.5% and the drag saturates just short of the end; on a container with a small overflow (say 20px of range) `maxTop` is 35 instead of 20 and dragging the thumb halfway scrolls 17.5px instead of 10 — a 75% error. A second consequence lives in the same expression: `scrolledTop` divides by `height - offsetHeight` (`:467`), which goes negative once the CSS floor (`min-block-size: calc(32px + 3px*2)`, `scrollbar-track.scss:96`) makes the thumb taller than its bar — a viewport under ~53px tall with both bars visible drags *backwards*. The Jest coverage cannot catch any of this: `scrollbar.spec.ts:453-454` mocks the bar rect to `height: 100, width: 100` while `setMetrics` gives the viewport `clientHeight: 100, clientWidth: 100` — the single geometry in which bar and client box coincide and the bug cancels exactly.
**Fix:** derive the scroll range from the viewport, not the bar: `const { scrollHeight, clientHeight, scrollWidth, clientWidth } = this.viewport.nativeElement;` then `maxTop = scrollHeight - clientHeight`, `maxLeft = scrollWidth - clientWidth`, keeping the bar rect only for the pointer→fraction conversion (`top`/`left`/`right`/`height`/`width` in the `scrolledTop`/`scrolledLeft` numerator and denominator, which correctly describe thumb travel). Clamp the travel denominator with `Math.max(height - offsetHeight, 1)` so a floored thumb degrades to "jump to the click" rather than inverting. Then re-shape the Jest drag cases so the bar and the viewport have *different* dimensions (e.g. bar 85px inside a 100px viewport, matching the both-axes case) and assert the exact expected `scrollTop`; the current assertions pass against the broken code, which is why they must change, not just be added to. Add a Playwright drag case to `E2eScrollbarTrack` (which already renders the both-axes fixture) that drags the vertical thumb to the bar's bottom edge and asserts `scrollTop === scrollHeight - clientHeight` on the nose.

**SCB-BUG-02 · `scrollToElement`/`scrollIntoView` assume the viewport is the target's `offsetParent`, but `.kbq-scrollbar-viewport` never sets `position`** — `scrollbar.ts:107-120` (`getElementOffset`), `:325-351`, `:680-688`; `scrollbar-viewport.scss:1-25` (no `position` rule anywhere); consumers `notification-center/notification-center.scss:87-97`, `apps/docs/src/app/components/sidenav/sidenav.scss:33-35`; tests neutralize it at `scrollbar.spec.ts:736, 753, 987, 1004`.
`getElementOffset(ancestor, element)` accumulates `offsetTop`/`offsetLeft` while walking `current = current.offsetParent` until `current === ancestor`. `offsetParent` skips every statically positioned ancestor, so the loop only terminates on `ancestor` when the viewport itself establishes a containing block. `<kbq-scrollbar>` does (`scrollbar.scss:2`, `position: relative`), which is why the component form works. The directive form does not: `scrollbar-viewport.scss` sets `scrollbar-width`, `-ms-overflow-style`, `display` and opacity transitions and never touches `position`, so `[kbqScrollbarViewport]` on an ordinary element inherits `position: static`. The loop then walks straight past the viewport to the nearest positioned ancestor — or to `null` — and returns offsets measured from the wrong origin, which `scrollTo` faithfully applies. This is not hypothetical for the directive's advertised use: the guide tells consumers to put `kbqScrollbarViewport` on arbitrary elements including `cdk-virtual-scroll-viewport` (`scrollbar.en.md:18`), and both in-repo directive consumers are statically positioned — `.kbq-notification-center-container` (`notification-center.scss:87-97`: `height`, `overflow`, `border-radius`, `padding-bottom`, no `position`) and `.docs-sidenav__menu` (`sidenav.scss:33-35`: `overflow-y`, `flex`, no `position`). Neither calls `scrollToElement` today, so nothing is currently broken in-repo — but the two public methods are documented (`scrollbar.en.md:29-30`) and every test that touches them defines `offsetParent: null` on the target (`scrollbar.spec.ts:736, 753, 987, 1004`), which terminates the walk after one iteration and never exercises the `ancestor` condition at all. `cdk-virtual-scroll-viewport` happens to be safe because CDK's own stylesheet sets `position: relative` on it.
**Fix:** make the assumption true rather than documenting it. Add `position: relative;` to a `.kbq-scrollbar-viewport` rule in `scrollbar-viewport.scss` (it is already the behaviour of the component form, so this only aligns the directive with it and is layout-neutral for a static element with no absolutely positioned children). Belt-and-braces in the walk itself: bail out and fall back to `getBoundingClientRect()` deltas when the loop reaches `null` without seeing `ancestor`, so a consumer who forces `position: static` back gets a correct scroll rather than a silent wrong one. Replace the `offsetParent: null` mocks with a real nested-element host (`<div kbqScrollbarViewport><div class="wrapper"><div #target>`) and assert the resolved offset; add an `E2eScrollbarScrollTo` variant built on `[kbqScrollbarViewport]` rather than `<kbq-scrollbar>`, since the existing e2e case (`e2e.playwright-spec.ts:318-323`) only covers the component form.

**SCB-A11Y-01 · The thumb advertises an operable `role="scrollbar"` that cannot be focused or driven from the keyboard** — `scrollbar.ts:377-387`, `:451-456`, `:477-479`; no `tabindex` or key handler exists anywhere in `packages/components/scrollbar`.
The thumb host block sets `role: 'scrollbar'` with `aria-orientation`, `aria-controls`, `aria-valuemin`, `aria-valuemax` and a continuously updated `aria-valuenow`. The required-attribute side of this is done carefully — there is even a comment at `:445-450` explaining why `aria-valuenow` is applied in `afterNextRender` so it is never observed missing — and axe-core is therefore satisfied (`aria-required-attr` passes), which is precisely why nothing has flagged it. But `scrollbar` in WAI-ARIA is an interactive range widget, and the WAI-ARIA Authoring Practices pattern for it specifies `tabindex="0"` plus Up/Down (or Left/Right), Page Up/Page Down and Home/End. This thumb has none of that: no `tabindex`, no `keydown` handling, no `aria-label`. A screen-reader user in browse mode is therefore told there is a scroll bar at 43%, and cannot reach or operate it — an announced control that does not exist as a control, which is worse than silence. Compounding it, `applyValueNow` writes the attribute via `setAttribute` on every scroll event and on every throttled rAF tick (`:441-442, 477-479`), so assistive technology sees a high-frequency value stream from a widget the user can never focus.
**Fix:** pick one of two coherent positions rather than the current half-implementation. (a) Make it real: add `tabindex: '0'`, an `aria-label` sourced from `kbqInjectA11yLocaleConfiguration()` per AGENTS.md, and a `keydown` handler mapping ArrowUp/ArrowDown/ArrowLeft/ArrowRight to one line-step, PageUp/PageDown to one viewport-step and Home/End to the range ends, all through the existing `scrollTo` path so `behavior` and RTL normalization come for free. (b) Make it decorative: drop `role="scrollbar"` and the four ARIA attributes and set `aria-hidden="true"` on the thumb, on the grounds that native scrolling is preserved and the scroll position is already conveyed by the scroll container itself. (b) is smaller and defensible; (a) is what the role promises. Either way pair it with SCB-A11Y-02 — the two answers are only coherent together — and add a `jest-axe` case to `scrollbar.spec.ts` (the pattern exists at `accordion.spec.ts`, `app-switcher.spec.ts`, `button-toggle.component.spec.ts`, `list-selection.component.spec.ts`, `navbar.component.spec.ts`) plus a Playwright case that Tabs onto the thumb and asserts `scrollTop` moves, if (a) is chosen.

**SCB-A11Y-02 · A scrollbar whose content has no focusable children has no keyboard path into it** — `scrollbar.ts:234-250`, `scrollbar.scss:1-13`, `scrollbar-viewport.scss:16-25`; e2e coverage only for the focusable-child case at `e2e.playwright-spec.ts:250-284`.
`<kbq-scrollbar>` is `overflow: auto` (`scrollbar.scss:12`) with no `tabindex`, no `role="region"` and no `aria-label`, and `[kbqScrollbarViewport]` adds none of those either. Whether such a region is keyboard-reachable is therefore left entirely to the browser: Firefox and Chrome 127+ make a scroll container focusable when it contains no focusable descendants, Safari does not. A `<kbq-scrollbar>` wrapping plain prose — which is exactly the shape of the library's own `native-scrollbar` example (`packages/docs-examples/components/scrollbar/native-scrollbar/native-scrollbar-example.ts:10-38`, three `<p>` elements and nothing focusable) — is thus unreachable and unscrollable by a keyboard-only user on Safari, a WCAG 2.1.1 (Keyboard) failure. Note this is a WCAG judgement, not an automated one: axe-core does not flag a scroll container without `tabindex`. The package's own SCSS comment assumes the problem away — `scrollbar-viewport.scss:19-20` describes the track as staying visible "while, e.g., arrow keys scroll the content", which presupposes something inside already holds focus — and the Playwright suite tests only that presupposed case, tabbing to a `<button>` inside the fixture (`e2e.playwright-spec.ts:259-260, 276-278`).
**Fix:** make the viewport focusable when, and only when, it needs to be. Add a `tabindex` binding on `KbqScrollbarViewport` that resolves to `0` when the viewport scrolls (either axis overflowing — the track already computes exactly this at `scrollbar.ts:620-627`) and to `null` otherwise, together with `role="region"` and an `aria-label` from `kbqInjectA11yLocaleConfiguration()` so the region is announced rather than being an unlabelled tab stop. Expose an opt-out input for panels that manage their own focus (the app-switcher and notification-center cases). Add a Playwright case using a fixture with *no* focusable content: Tab into the scrollbar, press ArrowDown, assert `scrollTop` increased — and run it on the WebKit project, since Chromium's built-in scroller focus would make it pass vacuously.

**SCB-A11Y-03 · Nothing in the package honours `prefers-reduced-motion`, and a consumer has already patched around it in CSS** — `scrollbar-viewport.scss:11-14, 21-25`, `scrollbar-track.scss:23-31, 40-47`, `scrollbar.ts:300-303, 305-323`; consumer workaround at `notification-center/notification-center.scss:99-107`; nine in-repo precedents including the shared helper `core/styles/common/_animation.scss:57`.
The package animates in three places and gates none of them: the track's opacity transition (`scrollbar-viewport.scss:12` and `:23`, `var(--kbq-scrollbar-transition-duration)`), the bar's enter/leave keyframe (`scrollbar-track.scss:23-31` plus `animate.enter`/`animate.leave` at `scrollbar.ts:554-555, 565-566`), and the public `behavior` parameter, which `scrollTo`/`scrollToTop`/`scrollToBottom`/`scrollStart`/`scrollEnd`/`scrollToElement`/`scrollIntoView` all forward straight to the platform and which the guide advertises as supporting `smooth` (`scrollbar.en.md:32`). ### P3 — Nice to have / hygiene

**SCB-ARCH-03 · Two CSS token values are hardcoded in TypeScript, so overriding the token silently desynchronizes the thumb math** — `scrollbar.ts:165-176`, mirroring `scrollbar-tokens.scss:2-3` and `scrollbar-track.scss:94-101`.
`MIN_THUMB_SIZE = 32` is annotated "Based on --kbq-scrollbar-thumb-min-size" and `THUMB_GAP = 3` "Based on --kbq-scrollbar-thumb-gap"; `MIN_THUMB_BOX_SIZE` sums them and drives `getCompensation()` (`:529-538`), which reserves the top-offset room that keeps a floored thumb from overhanging the track's trailing edge — the exact behaviour asserted at `scrollbar.spec.ts:537-551` and `e2e.playwright-spec.ts:370-394`. The tokens they mirror are `--kbq-scrollbar-thumb-min-size: var(--kbq-size-3xl)` (32px, confirmed at `@koobiq/design-tokens/web/new/css-tokens.css:1290`) and `--kbq-scrollbar-thumb-gap: 3px`. The values agree today, and a comment at `:171-175` explains carefully why the box size rather than the bare min-size is the right quantity — but the coupling is invisible from the SCSS side, and the tokens are scoped to `:where(.kbq-scrollbar-viewport, .kbq-native-scrollbar)` (`scrollbar-tokens.scss:1`) precisely so consumers can override them, which the package's own e2e fixture demonstrates for the sibling colour tokens (`e2e.ts:106-107, 258-259`). A consumer who sets `--kbq-scrollbar-thumb-min-size: 48px` gets a CSS floor of 54px and a JS compensation still computed for 38px — the overhang the compensation exists to prevent.
**Fix:** read the values instead of duplicating them. In `KbqScrollbarThumb`, resolve `--kbq-scrollbar-thumb-min-size` and `--kbq-scrollbar-thumb-gap` once per measurement pass with `getComputedStyle(this.nativeElement).getPropertyValue(...)` (through `inject(KBQ_WINDOW)`, per AGENTS.md), or read the thumb's own resolved `min-block-size`/`min-inline-size`, which the browser has already computed from the tokens. If the extra style read is unacceptable on the hot path, cache it and invalidate from the same `ResizeObserver` introduced by SCB-PERF-01. Guard with a Jest case that overrides `--kbq-scrollbar-thumb-min-size` on the host and asserts the resulting `top` percentage changes accordingly — today it would not.

**SCB-STYLE-01 · `--kbq-scrollbar-color` is a documented extension point that nothing reads** — `scrollbar-track.scss:18-20`; sole occurrence in the repository.
The track host declares `color: var(--kbq-scrollbar-color, currentColor);` under a two-line comment claiming it "lets a consumer theme one scrollbar instance without a class hook to target". Nothing in the package consumes `color` or `currentColor`: the thumb paints from `--kbq-scrollbar-thumb-default-background` / `-hover-` / `-active-` (`scrollbar-track.scss:79, 87, 91`), and the bar from `--kbq-scrollbar-track-background` (`:36`). `grep -rn -- '--kbq-scrollbar-color'` across `packages/`, `apps/` and the design-token package returns exactly this one line, so the property is neither defined anywhere nor read anywhere — a consumer following the comment would set it and see nothing change. The real, working extension point is the token set at `scrollbar-tokens.scss:1-17`, which the e2e fixture already uses.
**Fix:** delete the declaration and its comment, and if a single-instance colour override is genuinely wanted, document the existing tokens instead — they already work at any scope, since `scrollbar-tokens.scss:1` scopes them to a class both the viewport and the native-scrollbar host carry. If the intent was to let `currentColor` drive the thumb, that is a different change: make `--kbq-scrollbar-thumb-default-background` default to a `color-mix()` of `currentColor`, and say so in the guide.

**SCB-API-02 · The `scrollbar/deprecated` entry point has an API report that `check-api` never checks** — `tools/api-extractor/config.json:2-68`, `tools/api-extractor/api-extractor.ts:14-22, 72-74`, `tools/public_api_guard/components/scrollbar-deprecated.api.md` (158 lines).
`api-extractor.ts` iterates `buildConfig.components` and runs the extractor once per entry (`:72-74`); `check-api` is `approve-api onlyCheck`, i.e. the same loop with `localBuild = false`. The `components` array lists `"scrollbar"` (`config.json:43`) and nothing else scrollbar-shaped — there is no `"scrollbar/deprecated"` entry. `scrollbar-deprecated.api.md` was therefore produced by a one-off manual invocation (the script supports it: `params.split('/')` at `api-extractor.ts:19`, and the flattened report filename is handled deliberately at `:37-43`), and is now a snapshot nothing compares against. Any change to the deprecated wrapper's public surface — including one made while removing it — passes CI silently. The surface is not trivial: 158 lines, and its four exported type aliases (`KbqScrollbarOptions`, `KbqScrollbarEvents`, `KbqScrollbarTarget`, `KbqScrollbarEventListenerArgs`, `scrollbar.types.ts:3-6`) are direct re-exports of `overlayscrollbars` types, so a peer-version bump alone can change it.
**Fix:** add `"scrollbar/deprecated"` to `tools/api-extractor/config.json`'s `components` array. The script already handles the nested path (`mainEntryPointFilePath` keeps the real `dist/components/scrollbar/deprecated/index.d.ts`, `reportFileName` flattens to `scrollbar-deprecated.api.md`), so this is a one-line change; verify with `yarn run build:components && yarn run check-api` and confirm the existing report is reproduced byte-for-byte rather than rewritten. While there, note the same config file lists `"button-toggle"` twice (`:9` and `:17`) — harmless duplicate work, worth a separate one-line cleanup.

**SCB-SSR-01 · The track's relocation runs in `afterNextRender`, which never runs on the server, so server-rendered markup places `<kbq-scrollbar-track>` outside the viewport** — `scrollbar.ts:353-370`; no SSR coverage in the package; deprecated entry point still uses the raw global at `deprecated/scrollbar.directive.ts:62-63, 72-73`.
`createTrack()` creates the track through `this.viewContainerRef.createComponent(...)`, which anchors it as a sibling of the viewport's host element, and then relocates it into the viewport with `insertBefore` inside `afterNextRender` (`:362-367`). The comment there explains the *why* (sticky positioning needs the track to be a direct child) and correctly guards against a stale `trackRef`, but `afterNextRender` callbacks are skipped during server rendering by design, while the `effect()` that calls `createTrack()` (`:271-287`) does run as part of server-side change detection. The serialized HTML therefore contains a stray `<kbq-scrollbar-track>` next to `<kbq-scrollbar>` instead of inside it. It renders empty — `visibility` starts at `[false, false]` via `startWith` (`:594`) and the rAF source never emits without a frame — so the practical cost is a misplaced empty element in the SSR payload that jumps into place after hydration, not a crash. The rest of the package's SSR handling is genuinely good: `KBQ_WINDOW` instead of the global (`:45`), an explicit `requestAnimationFrame` capability check (`:49-51`), and no layout reads outside event handlers and render hooks. The deprecated entry point is the weaker half, still reading the global `window` behind two `// eslint-disable-next-line no-restricted-globals` suppressions.
**Fix:** move the relocation out of `afterNextRender` and into a path that runs on both platforms — the simplest is to have the effect create the track through a `ViewContainerRef` that already lives inside the viewport (project an `<ng-container #trackHost>` into the viewport's own template for the component form), or to call the `insertBefore` directly after `createComponent` when `isPlatformServer(inject(PLATFORM_ID))`. Add SSR coverage to the package: the repo's SSR gaps are known (`ng serve` returns a CSR shell), so the cheap version is a Jest case that renders `KbqScrollbar` with `TestBed` under a server-platform provider and asserts `viewportEl.firstChild` is the track — which today it is not on the server path.

**SCB-API-03 · `scrollIntoView` shadows the native method name with different semantics** — `scrollbar.ts:341-351`, `:685-688`; `scrollbar.en.md:30`, `scrollbar.ru.md:70`.
`KbqScrollbar.scrollIntoView(target, behavior?)` always centres the target on *both* axes: `top = offsetTop + offsetHeight / 2 - clientHeight / 2` and the same for `left`. `Element.scrollIntoView(options)` does the minimum scroll by default and takes `block`/`inline` alignment options, and the rest of this repository uses the native method with those options — `inline-edit.ts:518` (`{ block: 'center', inline: 'nearest', behavior: 'smooth' }`), `clamped-text.ts:178`, `apps/docs/.../anchors.component.ts:165, 173, 190`. A reader who knows the platform method will assume "scroll it into view if it isn't", get a forced re-centre of an already-visible element, and have no way to ask for `nearest` or to scroll only one axis. The guide's one-line description, "centers an element within the viewport" (`scrollbar.en.md:30`), is accurate but is the only place the difference is stated.
**Fix:** rename to `scrollToCenter` (or `centerElement`) and keep `scrollIntoView` as a thin `@deprecated` alias for one minor, then remove it — this is an additive change plus a deprecation, so it needs no `ng-update` migration until the removal. Alternatively keep the name and widen the signature to `scrollIntoView(target, options?: { block?: 'center' | 'nearest' | 'start'; inline?: …; behavior?: ScrollBehavior })` with `center` as the default, so the platform's vocabulary works. Either way run `yarn run build:components && yarn run approve-api` — both `KbqScrollbar` and `KbqScrollbarViewport` expose the method, so the report changes twice.

## 4. Recommended Remediation Phases

**Phase 1 — Stop the application-wide side effects.**
IDs: SCB-ARCH-02, SCB-PERF-01. These are the two things this component does *to the rest of the app*, and neither depends on anything below. Add the dispatcher opt-out and the shared inner-scroll guard, then delete the three bespoke consumer guards (the deletion is the acceptance criterion, not the new API). Replace the four rAF pollers with a `ResizeObserver` plus the existing `scroll` listener. Sequence the dispatcher work first: it touches four packages' specs, and the perf change is verified against the same Playwright suite.

**Phase 2 — Repair the entry point and the dependency contract.**
IDs: SCB-ARCH-01, SCB-API-01, SCB-API-02. One `index.ts` line, one `peerDependenciesMeta` entry, one `config.json` entry, plus the stale `ng-add` comment. All three are packaging-level and share a single `build:components` → `approve-api` cycle, which is why they belong together and why nothing else should be in flight during it.

**Phase 3 — Fix the pointer and scroll-to geometry.**
IDs: SCB-BUG-01, SCB-BUG-02, SCB-ARCH-03. Correct the drag denominators, give `.kbq-scrollbar-viewport` a containing block, and read the thumb's floor from CSS rather than from two hardcoded constants. Do this after Phase 1: the `ResizeObserver` introduced there is where the cached token read from SCB-ARCH-03 naturally invalidates. Requires reshaping two Jest cases whose current mocks make the bugs unreproducible, and new Playwright baselines through Docker.

**Phase 4 — Close the accessibility gaps.**
IDs: SCB-A11Y-01, SCB-A11Y-02, SCB-A11Y-03. Decide the thumb's role question and the viewport's focus question together — they are two halves of one answer — then add the reduced-motion media queries and route `behavior` through the preference so `notification-center.scss:105-107` can be deleted. Depends on Phase 3 only in that the keyboard step sizes should be computed from geometry that is already correct.

**Phase 5 — Docs, dead styles and hygiene.**
IDs: SCB-DOC-01, SCB-CSS-01, SCB-STYLE-01, SCB-SSR-01. Populate the Examples tab (or turn it off), migrate the eleven `.kbq-scrollbar` call sites off the deprecated theme so the build-wide `@warn` can be removed, delete the dead `--kbq-scrollbar-color`, and make the track land inside the viewport on the server. SCB-CSS-01 is the largest item here because it changes rendered output in eleven packages and needs regenerated screenshots — schedule it as its own PR.

## Appendix A — Review Methodology

Findings were gathered by reading the complete package — all 4235 lines across both entry points, including both e2e fixtures, both Playwright specs, both Jest specs, both language guides and both API guard reports — and then cross-checking every candidate against five independent sources: the workspace compiler and Jest configuration (`tsconfig.json:114-118`, `jest.config.js:13-14`), the Playwright configuration (`playwright.config.ts:90-104`), the design-token package (`@koobiq/design-tokens/web/new/css-tokens{,-light,-dark}.css`), the migration schematic and migration guide that shipped alongside the rewrite (`packages/schematics/src/migrations/scrollbar-deprecated-path/`, `docs/guides/migration.{en,ru}.md:843-887`), and every in-repo consumer found by grepping for `kbq-scrollbar`, `kbqScrollbar`, `kbqScrollbarViewport` and `kbqNativeScrollbar` across `packages/` and `apps/` (24 call sites plus 11 legacy `.kbq-scrollbar` class users). `git log -20 -- packages/components/scrollbar/` and `git show 3e49f593b` were used to separate long-standing behaviour from what the three-week-old rewrite introduced; two findings (SCB-ARCH-01, SCB-DOC-01) are regressions traceable to a single line of that commit's diff. Consumer evidence is what upgraded SCB-ARCH-02 from an architectural opinion to a confirmed defect: three components, three independently written guards, one requiring a lint suppression.

Refuted during verification:
- **"The scrollbar dispatches synthetic `scroll` events, violating the DS-5407 prohibition"** — refuted. `new Event('scroll')` appears nine times in `scrollbar.spec.ts` (`:425, 439, 546, 609, 613, 617, 628, 783, 818`) and nowhere in production code. The drag path writes `viewport.scrollLeft`/`scrollTop` directly (`scrollbar.ts:423, 425`), so every event the browser then emits is genuine. The DS-5407 hazard survives in a different shape — a real inner scroll reaching a global bus — and is filed as SCB-ARCH-02.
- **"The package wraps a third-party scrollbar library, so most of its public API is not really ours"** — refuted for the default entry point, confirmed for the secondary one. `overlayscrollbars@2.7.3` is imported only by the four files under `deprecated/`, whose API report is ~100% re-exported third-party types (`scrollbar.types.ts:3-6`). The current `@koobiq/components/scrollbar` has no third-party import at all; its only external types are `ExtendedScrollToOptions` and `ScrollBehavior`. The residue is a packaging problem (SCB-API-01), not an API-ownership one.
- **"A missing `_scrollbar-theme.scss` violates the AGENTS.md package structure"** — refuted. The new implementation loads `scrollbar-tokens.scss`, `native-scrollbar.scss` and `scrollbar-viewport.scss` exactly once per application through `_CdkPrivateStyleLoader` and a private `ScrollbarStyleLoader` component (`scrollbar.ts:186-193, 214, 269`). A theme mixin would double-apply the same declarations and reintroduce the global-selector coupling the rewrite removed. The deprecated entry point keeps its own `_scrollbar-component-theme.scss`, consumed locally at `deprecated/scrollbar.component.scss:2, 80`.
- **"Both entry points export `KbqScrollbar`, `KbqScrollbarModule` and `KbqScrollbarOptions` under the same names, and both match `kbq-scrollbar` — an undocumented migration trap"** — refuted as a documentation gap. The collision is real (`scrollbar.ts:632` vs `deprecated/scrollbar.component.ts:53`; `KbqScrollbarOptions` is `{ mode }` in one and `PartialOptions` in the other), but `docs/guides/migration.en.md:879` states it explicitly: "Do not import both the old and the new implementation into the same standalone component." Nothing to file.
- **"`--kbq-scrollbar-track-z-index: 101` in notification-center is a consumer workaround for a too-low default"** — refuted as a defect. `--kbq-scrollbar-track-z-index` is declared at `scrollbar-tokens.scss:5` and read at `scrollbar-track.scss:3` precisely so an instance can be re-layered; `notification-center.scss:88-89` uses it exactly as designed, with a comment explaining the sticky sub-header it has to clear. This is the extension point working.
- **"`scrollbar-virtual-scroll-example.ts:16` uses a banned structural directive"** — refuted. AGENTS.md bans `*ngIf`/`*ngFor`/`*ngSwitch`; `*cdkVirtualFor` is a CDK directive with no `@`-block equivalent, and the e2e fixture's equivalent (`e2e.ts:246-248`) correctly uses `@for` because it is not virtualized.
- **"`mode` is declared twice — on `KbqScrollbar` and again through the `KbqScrollbarViewport` host directive — so one of them is dead"** — refuted. `scrollbar.ts:640` exposes the host directive's `kbqScrollbarMode` and `:648` declares the component's own signal under the same alias; `scrollbar.spec.ts:150-167` proves both receive the bound value, and the component's copy is what makes `scrollbar.mode()` readable from a template reference. Redundant-looking, not broken.
- **"The guides document methods that do not exist"** — refuted. Every member named in `scrollbar.en.md:24-32` and `scrollbar.ru.md:64-72` (`scrollTo`, `scrollToTop`, `scrollToBottom`, `scrollStart`, `scrollEnd`, `scrollToElement`, `scrollIntoView`, `scrollChanges`) exists on `KbqScrollbar` (`scrollbar.ts:651-693`) and in `tools/public_api_guard/components/scrollbar.api.md:34-43`, as do `kbqScrollbarMode`, `kbqScrollbarOptionsProvider`, `kbqScrollbarViewport`, `kbqNativeScrollbar` and `kbqNativeScrollbarDescendants`. Under `strictTemplates: true` a documented-but-absent input would be a hard NG8002; there are none here.

Corrected on verification:
- **SCB-CSS-01** was drafted as "the deprecated `.kbq-scrollbar` theme is dead code left over from the rewrite". Reading `_koobiq-theme.scss:25` showed it is still included unconditionally by the mixin every consumer must call, that `_scrollbar-theme.scss:26` `@warn`s from inside it, and that eleven first-party components still emit the class — so it moved from dead code to unavoidable build noise misdirected at the wrong audience, and from P3 to P2.
- **SCB-DOC-01** was initially filed as P3 following the divider precedent ("dead stub files"). `structure.ts:860` sets `hasExamples: true` and `page-paths.ts:24` publishes the route, so the stub is a live, linked page rather than an unreachable file — raised to P2, and the `git show` on the rewrite commit showed it is a regression rather than a never-written page.
- **SCB-PERF-01** was drafted as "the rAF loop keeps running for the lifetime of the component". Counting subscriptions showed it is not one loop but up to four independent ones per instance (`:591`, `:607`, and `:432` per thumb), each forcing a six-property layout read on every throttle window — that multiplication is what moved it from P2 to P1.
- **SCB-BUG-01** was drafted as "the drag mapping is off by one pixel" after reading the vertical-only case. Tracing the `_has-horizontal`/`_has-vertical` insets (`scrollbar-track.scss:60-66`) and the Playwright assertion that pins them at 14px (`e2e.playwright-spec.ts:163-166`) showed the error is 15px of scroll range on each axis whenever both bars are visible, which is a visible drift on small overflows rather than a rounding nit.
