# Ревью компонента: `username`

> Scope: `packages/components/username` (компонент, шаблон, оба пайпа и функция сборки текста, токены, SCSS, Jest-спека со снапшотом, e2e-фикстура и Playwright-спека, руководства, отчёт API guard, примеры документации, dev-приложение, потребители внутри репозитория) · Commit `b665e503` · 2026-08-28
> Подготовлено многомерным ревью (архитектура, корректность, доступность, i18n/RTL, публичный API и типы, стили, тесты, документация) с ручной проверкой каждой находки по исходникам, отчёту API guard, набору дизайн-токенов и настройкам компилятора рабочей области. Подтверждено 15 находок (P0×0, P1×3, P2×8, P3×4); 6 кандидатов отклонено при проверке (см. Приложение A). Документ — ревью и дорожная карта; исходный код им не меняется.

## 1. Резюме

`kbq-username` выводит человека из записи `KbqUserInfo`: отформатированное полное имя, логин и подсказку с сайтом, в трёх режимах раскладки и четырёх визуальных стилях. Пакет небольшой (131 + 126 + 76 + 35 строк TS/HTML) и современный — сигналы везде, `OnPush`, host-объект, ни одного `@HostBinding`, никакого RxJS, никакого `window`. Дефекты лежат не в механике отрисовки, а в *контракте форматирования*, и все они срабатывают молча.

- **Компонент теряет имя пользователя, если в профиле нет одного из полей `firstName` / `lastName`.** `hasFullName` требует **оба** (`username.ts:124`), и на нём завязана каждая ветка шаблона (`username.html:8, 23, 26`). Профиль вида `{ lastName: 'Root', login: 'mroot' }` отрисует только `mroot`; профиль с именем и отчеством, но без фамилии и без логина отрисует **пустой элемент**. При этом `KbqUsernamePipe.transform` для той же записи возвращает `"Root"` — то есть пример поиска (`username-search-example.ts:86-91`) фильтрует по строке, которую компонент отказывается показывать. Ни один из 18 Jest-кейсов не покрывает неполный профиль (USR-BUG-01).
- **Формат по умолчанию у custom-пайпа несовместим с поставляемым маппингом по умолчанию.** `kbqDefaultFullNameFormatCustom = 'L f. m.'` (`constants.ts:5`) использует ключ `L`, но фабрика `KBQ_PROFILE_MAPPING` описывает только `f`, `m`, `l`, `.` (`constants.ts:23-29`), а тип, которому она соответствует, — `KbqFormatKeyToProfileMapping` — *исключает* `F`/`M`/`L` по построению (`types.ts:41-48`). Неотображённые символы выводятся как есть (`username.pipe.ts:84-88`), поэтому `{{ user | kbqUsernameCustom }}` со штатными настройками библиотеки печатает `L M. A.` — буквальную заглавную `L` на месте фамилии (USR-BUG-02).
- **Внедрение пайпа ровно так, как учит руководство, молча игнорирует локальный маппинг.** У обоих пайпов стоит `@Injectable({ providedIn: 'root' })` *и* `@Pipe` (`username.pipe.ts:11-15, 55-59`), в результате компилятор генерирует и `ɵprov`, и `ɵpipe` (`username.api.md:69-71, 113-115`). Внедрённый экземпляр — корневой синглтон, его `inject(KBQ_PROFILE_MAPPING)` разрешается в корневом инжекторе и никогда не видит переопределения на уровне компонента, ради которого токен и существует и которое использует сам пример из документации (`username-custom-example.ts:86-88`). `username.en.md:27` обещает, что внедрённый `transform` «возвращает ту же строку, которую компонент отображает по умолчанию»; при любом локальном маппинге это неправда (USR-ARCH-01).
- **Имена сокращаются по кодовым единицам и показываются без доступного раскрытия.** Инициалы берутся как `fieldValue[0]` (`username.pipe.ts:40, 93`), что разрывает суррогатную пару — имя, начинающееся вне BMP, даёт одиночный суррогат, отрисовываемый как `�.` (USR-BUG-03). У отрисованного элемента нет ни `role`, ни `aria-label`, ни `<abbr>`; тултип `kbq-title` по умолчанию берёт собственный `textContent` хоста (`title.directive.ts:171-172`), то есть ту же сокращённую строку, так что несокращённое имя нигде не доступно, а скобки `(corp)` не имеют программной подписи (USR-A11Y-01). В пакете нет ни одного ARIA-атрибута и ни одного вызова `kbqInjectA11yLocaleConfiguration()`.
- **Покрытие тестами широко по форме и пусто по существу.** Все 18 Jest-кейсов передают явный `customMapping`, поэтому поставляемый по умолчанию `KBQ_PROFILE_MAPPING` — то, что реально исполняется у любого потребителя без настройки — не выполняется ни разу (`username.spec.ts:36-41, 77-85`). Самого компонента касаются только два кейса, а `isCompact`, усечение текста и `KbqUsernameModule` не проверяются нигде; единственный Playwright-скриншот рисует `<td>` с шириной по содержимому, где переполнение невозможно в принципе (USR-TEST-01).

Сильные стороны, которые стоит сохранить: SCSS раскладки — маленькая и аккуратно разложенная работа: миксин `_kbq-username-content-wrapper` прозрачно перенаправляет все правила раскладки на спроецированный пользовательский шаблон (`username.scss:5-10`), четыре варианта стиля управляются всего двумя CSS-переменными, для отступа в inline-режиме используется собственный хелпер репозитория `rtl-prop`, захардкоженных цветов нет вовсе. Публичная поверхность построена на сигналах с корректным `booleanAttribute`, хелпер `kbqBuildUsernameText` — продуманный ответ на вопрос «как искать по тому, что нарисовано», а шесть живых примеров покрывают компонент от обзора до интеграции с filter bar.

## 3. Приоритизированные находки (дедуплицированы, верифицированы)

### P0 — Блокеры релиза

Нет.

### P1 — Высокий приоритет

**USR-BUG-01 · Профиль без `firstName` или без `lastName` полностью теряет имя, а иногда отрисовывается пустым элементом** — `username.ts:119-125`, `username.html:7-10, 21-28`.
`hasFullName` — это `userInfo?.lastName && userInfo?.firstName` (`username.ts:124`), логическое И, поэтому оно ложно, если отсутствует хотя бы одно поле. На нём завязано каждое место, где отформатированное имя попадает в DOM: в некомпактной ветке основной span рисуется только `@if (hasFullName())` (`username.html:8-10`), в компактной — так же, с откатом на логин лишь когда `hasFullName()` ложно (`username.html:23-28`). Последствия для обычных данных тяжёлые и незаметные. `{ lastName: 'Root', login: 'mroot' }` отрисует `mroot` и больше ничего — фамилия отброшена, хотя `KbqUsernamePipe.transform` для этой записи возвращает `"Root"` (цикл в `username.pipe.ts:33-45` пропускает отсутствующие поля по отдельности, ровно как и должен). `{ firstName: 'Maxwell', middleName: 'Alan' }` — профиль с именем, но без логина — не отрисует **ничего**: ни основного span, ни логина, только пустой `<kbq-username>` с тремя классами-модификаторами и без текста. Мононимы, служебные учётные записи, импортированные каталоги с единственным `displayName`, положенным в `lastName`, и большинство незападных именных систем попадают именно в эту яму. Расхождение прямо видно в поставляемом примере поиска: `username-search-example.ts:86-91` фильтрует по `kbqBuildUsernameText({ name: this.usernamePipe.transform(user), … })`, поэтому запрос, совпавший с фамилией неполного профиля, даёт строку результата, в которой фамилии нет. Ни один Jest-кейс не строит неполный профиль — `mockProfile` (`username.spec.ts:29-33`), `TestComponent.userInfo` (`:188-193`) и e2e-фикстура (`e2e.ts:43-49`) заполнены целиком.
**Fix:** перестать считать «есть полное имя» предусловием для вывода имени. Заменить `hasFullName` на `hasName = computed(() => !!this.formattedName())`, где `formattedName` — один раз вычисленный результат пайпа (о корректно заскоупленном экземпляре см. USR-ARCH-01), и завязать основной span на него — пайп уже корректно деградирует до тех полей, которые есть. Откат на логин оставить для действительно безымянного случая и добавить явную ветку пустого состояния, чтобы `<kbq-username>` с непригодным профилем рисовал осознанный плейсхолдер, а не пустую коробку. Закрыть Jest-таблицей по `{}`, `{ lastName }`, `{ firstName }`, `{ firstName, middleName }`, `{ login }` и полной записи с проверкой отрисованного `textContent` в обоих состояниях `isCompact` — пять из шести случаев падают на текущей реализации.

**USR-BUG-02 · Собственный формат по умолчанию у `kbqUsernameCustom` несовместим с поставляемым маппингом и печатает буквальную `L`** — `constants.ts:5, 20-30`, `username.pipe.ts:64-97`, `types.ts:41-48`.
`KbqUsernameCustomPipe.transform` по умолчанию берёт `format = kbqDefaultFullNameFormatCustom = 'L f. m.'` (`username.pipe.ts:66`, `constants.ts:5`). Правило разрешения такое: найти символ в маппинге; если поля нет — **вывести символ как есть** (`username.pipe.ts:84-88`), именно так в результат попадают пробелы и точки из формата. Но фабрика `KBQ_PROFILE_MAPPING` по умолчанию описывает только `f`, `m`, `l` и `.` (`constants.ts:25-28`), и объявлена как `satisfies KbqFormatKeyToProfileMapping<…>` (`constants.ts:29`) — mapped-тип, который *исключает* `FirstNameFull`, `MiddleNameFull` и `LastNameFull` по построению (`types.ts:41-48`). Значит `L` не отображена, попадает в ветку «как есть», и `{{ user | kbqUsernameCustom }}` со штатными настройками библиотеки рисует `L M. A.` для Maxwell Alan Root: заглавная `L` там, где должна быть фамилия. Токен принимает и расширенную форму (`constants.ts:20-22`), так что исправление — одна строка в значении по умолчанию, но ничто не подталкивает потребителя к нему, а свидетельство того, что на это натыкаются, лежит в репозитории: `username-custom-example.ts` и провайдит расширенный `KBQ_PROFILE_MAPPING` на уровне компонента (`:86-88`), и передаёт тот же объект третьим аргументом пайпа (`:47`) — двойная страховка для вызова, которому не нужно было ни то, ни другое. У обычного пайпа есть зеркальный дефект: `KbqUsernamePipe` с форматом из `F`/`M`/`L` возвращает пустую строку (все ключи не отображены, `profile[undefined]` ложно, и цикл ничего не добавляет, `username.pipe.ts:35-43`) — по крайней мере это ограничено типом, а не выглядит как правильный вывод.
**Fix:** привести поставляемый маппинг по умолчанию к `KbqFormatKeyToProfileMappingExtended` — добавить в фабрику `constants.ts:23-29` записи `[KbqUsernameFormatKey.FirstNameFull]: 'firstName'`, `MiddleNameFull: 'middleName'`, `LastNameFull: 'lastName'` и поменять `satisfies`. `KbqUsernamePipe` при этом не меняется (он игнорирует ключи, которых нет в его формате), а `kbqUsernameCustom` начинает работать «из коробки». Дополнительно сделать ветку «вывести как есть» громкой в dev-режиме: `!field` должно различать «это пунктуация или пробел» и «это `KbqUsernameFormatKey` без маппинга», и во втором случае писать `console.warn` — именно молчаливый вывод ключа формата как текста и спрятал этот баг. Закрыть Jest-кейсом, который получает пайп **без** аргумента `customMapping` и проверяет `'Root M. A.'`; сегодня ни один тест в файле этот аргумент не опускает.

**USR-ARCH-01 · Пайпы — корневые синглтоны, поэтому `inject(KbqUsernamePipe)` (документированный сценарий) игнорирует локальный `KBQ_PROFILE_MAPPING`** — `username.pipe.ts:11-17, 55-61`, `constants.ts:17-30`, `username.en.md:27`, `username.ru.md:23`, `username.api.md:69-71, 113-115`.
На обоих классах пайпов стоят два ангуляровских декоратора: `@Injectable({ providedIn: 'root' })` над `@Pipe({ … })` (`username.pipe.ts:11-15` и `:55-59`). Компилятор генерирует обе записи — в отчёте API у каждого класса есть и `ɵpipe`, и `ɵprov` (`username.api.md:67-71, 111-115`), — то есть существует два независимых пути создания с двумя разными инжекторами. В шаблоне пайп создаётся на представление, против node-инжектора, поэтому `{ provide: KBQ_PROFILE_MAPPING, useValue: … }` на уровне компонента виден. Полученный через `inject(KbqUsernamePipe)` — это **корневой** синглтон, и его `inject(KBQ_PROFILE_MAPPING, { optional: true })` (`username.pipe.ts:17`) разрешается в корневом инжекторе, локальное переопределение невидимо. Провайдить маппинг на уровне компонента или маршрута — вся суть токена (`constants.ts:17-19`, и `username-custom-example.ts:86-88` делает ровно это), так что один и тот же класс осознанно выдаёт две разные строки для одного профиля в зависимости от того, как его получили. Оба руководства рекомендуют для поиска именно внедрение — «внедрите `KbqUsernamePipe` как сервис и вызовите его метод `transform` — он вернет ту же строку, которую компонент отображает по умолчанию» (`username.ru.md:23`, `username.en.md:27`), — и два поставляемых примера следуют этому совету (`username-search-example.ts:67`, `username-filter-bar-option-example.ts:47`). Обещание держится только для потребителей, которые никогда не скоупят маппинг; для остальных фильтр молча ищет не по той строке, которую показывает список.
**Fix:** разделить две роли. Оставить `@Pipe` на классах пайпов и убрать `@Injectable({ providedIn: 'root' })`; вынести логику форматирования в обычный инжектируемый сервис (`KbqUsernameFormatter`, `providedIn: 'root'`), чей `transform` принимает маппинг аргументом, либо в свободную функцию `kbqFormatUsername(profile, format, mapping)`, и оба пайпа делегируют ей. Потребитель, которому нужна ровно строка компонента, вызывает `kbqFormatUsername(profile, format, inject(KBQ_PROFILE_MAPPING))` из своего контекста внедрения, где маппинг разрешается там, где живёт *он*. Обновить `username.en.md:27` / `username.ru.md:23` и оба примера. Публичная поверхность меняется — нужен `yarn run build:components`, затем `yarn run approve-api`; удаление `providedIn: 'root'` с класса, который потребители уже могут внедрять, — breaking change и требует миграции `ng-update` (см. `project_breaking_changes_need_migration_schematics`). Закрыть спекой, которая провайдит `KBQ_PROFILE_MAPPING` на уровне компонента и проверяет, что внедрённый и шаблонный пути совпадают — сегодня они расходятся.

### P2 — Стоит исправить

**USR-API-01 · Один enum формата, две взаимно несовместимые трактовки и JSDoc, неверный для обеих** — `types.ts:4-35, 41-57`, `username.pipe.ts:33-45, 81-94`.
`KbqUsernameFormatKey` документирует строчные члены как краткую форму, а прописные — как полную: «Short form of the first name (e.g., `John` → `J`)» (`types.ts:5-8`), «Full form of the first name» (`:10-13`). Ни один пайп это не реализует. `KbqUsernameCustomPipe` выводит краткость из **регистра** буквы — `const isShort = letter === letter.toLowerCase()` (`username.pipe.ts:90`), что совпадает с JSDoc, но лишь потому, что маппинг случайно определяет оба регистра; само значение enum смысла не несёт. `KbqUsernamePipe` выводит краткость из **следующей точки** — `const isShort = array[index + 1] === KbqUsernameFormatKey.Dot` (`username.pipe.ts:39`), поэтому в его же формате по умолчанию `'lf.m.'` (`constants.ts:7`) ключ `l`, задокументированный как «Short form of the last name» (`types.ts:26-28`), даёт *полную* фамилию, а `f` даёт инициал только потому, что за ним стоит `.`. Два пайпа, один enum, противоположные правила, и комментарий, описывающий поля второго, тогда как первый — библиотечное значение по умолчанию. Две константы формата усугубляют: у `kbqDefaultFullNameFormat` и `kbqDefaultFullNameFormatCustom` побайтно одинаковый JSDoc — «Default name format: Last name full, first and middle as initials.» (`constants.ts:4-7`) — для строк (`'lf.m.'`, `'L f. m.'`), не взаимозаменяемых ни в одну сторону.
**Fix:** документировать правило там, где оно реализовано. Дать каждому пайпу JSDoc уровня класса с его собственным правилом («`KbqUsernamePipe`: ключ, за которым идёт `.`, даёт инициал, иначе полное значение; разделители вставляются автоматически» против «`KbqUsernameCustomPipe`: строчные ключи дают инициал, прописные — полное значение; любой неотображённый символ выводится как есть»), переписать JSDoc членов `KbqUsernameFormatKey` так, чтобы он описывал *поле*, а не форму, которой enum не управляет, и дать двум константам разные комментарии с указанием пайпа. Отразить оба правила в `username.en.md` / `username.ru.md`, где сейчас нет ни одного. **USR-BUG-03 · Инициалы берутся по кодовой единице, поэтому первый символ вне BMP превращается в одиночный суррогат** — `username.pipe.ts:39-40, 90-93`.
Оба пайпа сокращают через `fieldValue[0]` (`username.pipe.ts:40` и `:93`), что возвращает первую **кодовую единицу** UTF-16, а не первый символ. Для любого имени, первый символ которого лежит вне Basic Multilingual Plane, результат — непарный старший суррогат, который браузеры рисуют как `�`: профиль с именем, начинающимся с `U+1D4A5`, даёт `Root \uD835. \uD801.` там, где корректный вывод — `Root 𝒥. 𐑐.`. Это задевает математические алфавитно-цифровые символы, используемые стилистически в отображаемых именах, исторические и расширенные плоскости CJK и эмодзи в именах — всё это встречается в реальных каталогах. Кириллица, греческий, иврит, арабский и обычный CJK лежат в BMP и не затронуты, поэтому баг не видно ни в одной фикстуре репозитория (`username.spec.ts:29-33`, `e2e.ts:43-49`, все шесть примеров документации). Второй, смежный острый угол: `fieldValue[0]` также отрывает базовый символ от комбинирующих знаков, так что имя, начинающееся с разложенной буквы, теряет в инициале диакритику.
**Fix:** заменить оба вызова `fieldValue[0]` на получение первого символа с учётом кодовых точек — `[...String(fieldValue)][0]` минимально по объёму и корректно для суррогатных пар; `Intl.Segmenter` с гранулярностью графем дополнительно сохраняет комбинирующие знаки, ценой рантайм-проверки API (он есть во всех целевых браузерах библиотеки, но для серверной сборки его стоит закрыть guard'ом). Заметим, что `fieldValue` типизирован как `T[keyof T]` и доходит до `[0]` только потому, что `noImplicitAny` выключен (`tsconfig.json:3-26` задаёт `strictNullChecks`, но никогда `strict`/`noImplicitAny`), поэтому приведение к строке должно стать явным, а не побочным.
