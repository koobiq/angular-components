# Koobiq `inline-edit` Component — Code Review & Improvement Plan

> Scope: `packages/components/inline-edit` (component + 3 directives, template, SCSS + tokens, Jest spec + snapshot, e2e fixture + Playwright spec, user guides, examples guides, API guard report, dev app, 18 docs examples) · Commit `b665e503` · 2026-08-28
> Generated by a multi-dimension review (architecture, RxJS/lifecycle, correctness, accessibility, performance, public API/types, templates & styles, tests, docs) with manual verification of every finding against the source, the in-repo examples, the axe-core rule set actually bundled with `jest-axe`, and the workspace compiler/test configuration. 16 findings confirmed (P0×1, P1×4, P2×6, P3×5); 8 candidate findings refuted during verification (see Appendix A). ## 1. Executive Summary

`KbqInlineEdit` ([inline-edit.ts](../../packages/components/inline-edit/inline-edit.ts), 736 lines) is one of the most behaviour-heavy components in the library: it projects a view template and an edit template, opens the edit template in a CDK connected overlay sized to the view, drives save/cancel from keyboard, pointer and Tab-out, chains Tab between neighbouring inline edits, and shows a validation tooltip that first scrolls the invalid control into view. It ships 11 inputs, 3 outputs, 47 Jest cases and 7 Playwright screenshot pairs, and it has been patched 10 times by `fix(inline-edit)` commits. It has no consumers inside `packages/` — the only call sites are its own 18 docs examples and e2e fixtures — so nothing in the repo has yet pushed back on its contract.

- **The one release blocker is an automated accessibility failure inside the component's own template.** The edit-mode overlay renders two sentinels carrying `aria-hidden="true"` *and* `tabindex="0"` ([inline-edit.html:46, 92](../../packages/components/inline-edit/inline-edit.html)). That is precisely what axe-core's default-enabled `aria-hidden-focus` rule (serious, `wcag2a`/`wcag412`/`wcag131`) forbids, and because the focus trap on the panel is explicitly disabled (`[cdkTrapFocus]="false"`), a keyboard user really does land on them: they are live tab stops that announce nothing. AGENTS.md states "It MUST pass all AXE checks", and no consumer can patch a template they do not own (IE-A11Y-01).
- **Nothing tells assistive technology that the read mode is editable.** The host binds a `tabindex` and eight classes and not one ARIA attribute (`inline-edit.ts:147-159`): no `role`, no accessible name, no `aria-expanded` when the overlay opens, no `aria-disabled` when disabled. When view content is interactive the host drops to `tabindex="-1"` and the only keyboard entry point becomes a nameless visually-hidden `<div tabindex="0">` (`inline-edit.html:14-19`). Separately, `KbqInlineEditMenu` stamps `role="button"` (`inline-edit.ts:113`) on an element it does not name — an axe `aria-command-name` failure in every one of the six in-repo usages (IE-A11Y-02, IE-A11Y-03).
- **`commit()` does not run the validation its own JSDoc promises.** `isInvalid()` reads `KbqFormField.invalid`, which is `errorState` (`form-field.ts:262-264`) — a cached flag produced by the `ErrorStateMatcher`, i.e. `touched || submitted` (`error-state-matcher.ts:59-62`). Only the keydown path marks the controls touched (`inline-edit.ts:543`); `commit()` and the Save button do not. Called on a pristine control — exactly the documented "select-style editor, commit on `selectionChange`" pattern (`inline-edit.spec.ts:1416`) — `commit()` sees `errorState === false` and writes an invalid value through (IE-BUG-01).
- **The published guides document design, not the component.** Across 220 lines of `inline-edit.en.md` / `inline-edit.ru.md` not one of the 11 inputs, 3 outputs or 2 public methods is named, and there is no `### Keyboard` section although sibling guides carry one (`list.en.md:108-112`) — so Escape-cancels, Enter-saves, Ctrl+Enter-in-textarea and Tab-chaining are undocumented. Worse, the Validation section promises the system "displays an error message … and keeps focus in the input"; the message only appears if the consumer passes `[validationTooltip]`, and nothing in the component ever returns focus to the input (IE-DOC-01).

Genuine strengths worth preserving: the component is fully signal-based and modern (`input()`/`output()`/`computed()`/`contentChild()`/`viewChild()`, OnPush, host object, no `@HostBinding`); it is SSR-clean, injecting `KBQ_WINDOW` and `DOCUMENT` rather than reaching for globals, and it is exercised by the SSR dev app (`packages/components-dev/ssr/module.ts:193`); the save/cancel buttons take their ARIA names from `kbqInjectA11yLocaleConfiguration()` exactly as AGENTS.md requires; the validation-tooltip scroll strategy is overridden *per instance* rather than through DI, with a spec that proves it does not leak into projected tooltips (`inline-edit.spec.ts:983-1000`); and several of the hairiest code paths carry genuinely useful explanatory comments (`inline-edit.ts:176-184, 397-398, 437-447, 449-450`) that made this review far cheaper than it would otherwise have been.

## 3. Prioritized Findings (deduplicated, verified)

### P0 — Release blockers

**IE-A11Y-01 · The edit overlay renders two `aria-hidden="true"` elements with `tabindex="0"` — a default axe failure and two live dead-end tab stops** — `inline-edit.html:46, 92`, `inline-edit.ts:72-93, 605-624`.
Both Tab sentinels are written as `<div class="cdk-visually-hidden" aria-hidden="true" kbqFocusRegionItem tabindex="0"></div>`. axe-core's `aria-hidden-focus` rule matches every outer-most `[aria-hidden="true"]` element, and its `focusable-not-tabbable` check collects tabbable elements *including the node itself* (`axe-core/lib/commons/dom/get-tabbable-elements.js`), failing with impact **serious** whenever any of them has `tabindex >= 0` and no modal dialog is open. The rule is enabled by default in the axe-core the repo actually runs — 4.12.1, bundled under `node_modules/jest-axe/node_modules/axe-core` — with tags `cat.name-role-value`, `wcag2a`, `wcag412`. `jest-axe` is already used in this repo (`accordion.spec.ts:1518`, `app-switcher.spec.ts:1780`), so the failure is one assertion away from being visible in CI, and AGENTS.md states the mandate plainly: "It MUST pass all AXE checks." This is not a theoretical violation either. The panel disables its focus trap (`[cdkTrapFocus]="false"`, `inline-edit.html:52`), so tab order inside the overlay runs sentinel → panel controls → sentinel, and the sentinel handler only fires once `focusin` has already set `isFocused` (`inline-edit.ts:75, 86-88`) — the design *requires* focus to land there. A screen-reader user therefore tabs onto an element the accessibility tree has been told does not exist, hears nothing, and has to press Tab a second time. There is no consumer workaround: the sentinels are in the component's own template.
**Fix:** delete both sentinels and detect the boundary on the panel itself — bind `(keydown.tab)`/`(keydown.shift.tab)` on `.kbq-inline-edit__panel` and compare `event.target` against the first/last tabbable descendant resolved with CDK's `InteractivityChecker` (`isTabbable`), which is what `FocusTrap` uses internally; `KbqFocusRegionItem` then disappears along with its export (see IE-API-01). If the sentinel shape must be kept short-term, the minimum change that clears axe is removing `aria-hidden="true"` from both — do **not** swap it for `role="presentation"`/`role="none"`, which trips axe's `presentation-role-conflict` instead. Guard it with `expect(await axe(overlayContainerElement)).toHaveNoViolations()` asserted **in edit mode**, mirroring `app-switcher.spec.ts:1780`.

### P1 — High

**IE-A11Y-02 · View mode has no role, no accessible name and no expanded state; with interactive content the only tab stop is a nameless hidden div** — `inline-edit.ts:147-159, 285-293`, `inline-edit.html:8-19`.
The host block binds `[attr.tabindex]` and six classes and nothing else — no `role`, no `aria-label`/`aria-labelledby`, no `[attr.aria-expanded]` tracking `isEditMode()`, no `[attr.aria-disabled]` alongside `kbq-inline-edit_disabled`. A `<kbq-inline-edit>` in view mode is therefore an unknown element that happens to be focusable: a screen reader reads the projected text and gives no indication that pressing Enter or Space opens an editor, and when the editor does open nothing is announced at all. That is WCAG 4.1.2 (Name, Role, Value) plus 1.3.1 — note this one is a *judgement*, not an automated failure: axe does not flag a focusable element that simply carries no role, which is exactly why it has survived. The interactive-content path makes it worse rather than better. When view content matches `interactiveSelectors`, `tabIndex()` returns `-1` (`inline-edit.ts:290`) and the component substitutes a focus anchor — `<div class="kbq-inline-edit__focus-anchor cdk-visually-hidden" tabindex="0">` (`inline-edit.html:14-19`) — with no role, no name and no content. The component's sole keyboard entry point is then an element assistive technology can describe only as "blank". The library already has the right mechanism for the missing string: `KbqA11yLocaleConfiguration` (`core/locales/types.ts:13-38`) carries `save` and `cancel` keys documented as belonging to the inline edit, and the component already injects it (`inline-edit.ts:166`).
**Fix:** put the widget semantics on `.kbq-inline-edit__view-content` (`inline-edit.html:9`), **not** on the host — a widget-role host containing the `kbqInlineEditMenu` button would then fail axe's `nested-interactive` rule, which is also enabled by default in 4.12.1. Move `[attr.tabindex]` there and add `role="button"`, `[attr.aria-expanded]="isEditMode()"`, `[attr.aria-disabled]="disabled() || null"`, and `[attr.aria-label]` defaulting to a new `edit` key added to `KbqA11yLocaleConfiguration` with an input override for consumers who want a field-specific name. Give the focus anchor the same treatment (it becomes the same element or inherits the same attributes) and cover each branch with a Jest case plus the edit-mode axe assertion from IE-A11Y-01.

**IE-A11Y-03 · `kbqInlineEditMenu` stamps `role="button"` on an element it never names — axe `aria-command-name` fails in every in-repo usage** — `inline-edit.ts:110-125` (role at `:113`); usages at `inline-edit-menu-example.ts:37-42, 62-69`, `e2e.ts:137-142, 193-198`, `inline-edit.spec.ts:1101-1106, 1311`.
`KbqInlineEditMenu` adds `role: 'button'` unconditionally to whatever element the consumer applies it to. axe-core 4.12.1's `aria-command-name` rule (impact **serious**, tags `wcag2a`/`wcag412`, selector `[role="link"], [role="button"], [role="menuitem"]`, matcher `no-naming-method-matches`) requires visible text, `aria-label`, `aria-labelledby` or `title` on such an element, and explicitly matches elements without a native naming method — which an `<i>` is. Every usage in this repository is an icon-only `<i kbqInlineEditMenu kbq-icon-button="…">` with no name: both menus in the documented example, three fixtures in `e2e.ts`, and the spec host. `KbqIconButton` supplies `[attr.tabindex]` (`icon-button.component.ts:34`), so the element is genuinely reachable and genuinely unnamed. The library is the party creating the obligation — it stamps the role — and never discharges it, and its own documentation teaches the failing pattern. Unlike IE-A11Y-01 there *is* a consumer workaround (add `aria-label` on the element you own), which is why this is P1 rather than P0.
**Fix:** stop hardcoding the role. Either drop `role: 'button'` and require consumers to apply `kbqInlineEditMenu` to a real `<button>`/`kbq-button` host (the icon-button already renders like one), or keep the role and pair it with a name: add an `aria-label` input to `KbqInlineEditMenu` that defaults to a new `menu` key in `KbqA11yLocaleConfiguration`, plus a dev-mode `console.warn` when the host resolves to no accessible name — the same shape `list` uses for its invalid-`multiple` warning. Then add `aria-label` to the two menus in `inline-edit-menu-example.ts` and the three `e2e.ts` fixtures, and assert `axe()` over a menu fixture in the spec.

**IE-BUG-01 · `commit()` does not run "the same validation as a normal save" — a pristine invalid value is written through** — `inline-edit.ts:339-342, 396-411, 542-543, 639-645`; `form-field.ts:262-264`; `error-state.ts:86-97`; `error-state-matcher.ts:59-62`.
`commit()`'s JSDoc reads "Saves the current value and returns to view mode, **running the same validation as a normal save**". It calls `save()`, which gates on `isInvalid()` → `formFieldRefList.some(ref => ref.invalid)` → `!!control.errorState`. `errorState` is not the control's validity: it is a **cached** boolean recomputed only inside `KbqErrorStateTracker.updateErrorState()`, which the control calls from `ngDoCheck` (`input.ts:235-241`), from the default `ErrorStateMatcher` — `control.invalid && (control.touched || form.submitted)`. So an invalid but *untouched* control reports `errorState === false` and `save()` takes the success branch. The keydown path compensates by calling `markAllAsTouched()` before deferring the save (`inline-edit.ts:543, 554-555`, with the `setTimeout` giving change detection a pass to refresh `errorState`). `commit()` does neither, and neither does the Save button (`inline-edit.html:69-74` calls `save($event)` directly). The exposed case is the pattern the docs themselves recommend: a select that commits from `(selectionChange)` (`inline-edit.spec.ts:1413-1428`), where the user picks an option with the mouse and the control may never be touched — and the guides recommend offering an explicit empty option ("Not specified", `inline-edit.en.md:89-91`), which is exactly the value a `required` validator rejects. The existing invalid-save specs all hand-mark the control touched first (`inline-edit.spec.ts:340, 378, 808`), so the hole is invisible to the suite. Note also that with no `KbqFormField` in the edit template at all — the documented `getValueHandler`/`setValueHandler` shape, `inline-edit-custom-handler-example.ts:39, 53-54` — `isInvalid()` returns `false` unconditionally (`inline-edit.ts:642`), so validation is bypassed by construction there too.
**Fix:** make `save()` self-sufficient: call `markAllAsTouched()` as its first statement (removing the two calls from `onOverlayKeydown`, see IE-BUG-03 for the rest of that path) and gate on the control's real validity rather than its display state — `formFieldRefList().some(ref => ref.control().ngControl?.control?.invalid ?? ref.invalid)` — leaving `errorState`/`ErrorStateMatcher` to decide only whether the error *styling* is shown. Add two specs: `commit()` on a `required` control that was never touched must keep the component in edit mode and must not emit `saved`; the Save button on the same pristine control must do likewise. Both fail against today's code.

**IE-DOC-01 · The guides document no API, no keyboard model, and promise error behaviour the component does not implement** — `inline-edit.en.md:1-115`, `inline-edit.ru.md:1-107` (Validation at `:34-42` / `:31-39`); `inline-edit.ts:404, 396-411`; `inline-edit.html:53-64`.
Both guides are pure design guidance. Across 220 lines they never name `showActions`, `showTooltipOnError`, `validationTooltip`, `disabled`, `editModeWidth`, `tooltipPlacement`, `overlayPanelClass`, `getValueHandler`, `setValueHandler`, `canSaveOnEnter`, `interactiveSelectors`, `saved`, `canceled`, `modeChange`, `toggleMode()` or `commit()`, and there is no `### Keyboard` section — although the repo's convention plainly has one where it matters (`list.en.md:108-112`). Every keyboard behaviour the component implements is therefore undiscoverable from the docs: Space/Enter opens, Escape cancels and reverts (`inline-edit.ts:547-550`), Enter saves except in a `<textarea>` where Ctrl/Cmd+Enter is required (`:216-219, 551-558`), Tab out of the panel saves and opens the next inline edit (`:605-637`). Two specific statements are also untrue. The Validation section says the system "displays an error message, highlights the field, and keeps focus in the input" (`inline-edit.en.md:36`, mirrored at `ru.md:33`): (1) the message is opt-in — `save()` shows the tooltip only `if (this.showTooltipOnError() && this.validationTooltip())` (`inline-edit.ts:404`) and `validationTooltip` has no default, which is why all four validation demos pass it explicitly (`inline-edit-validation-example.ts:80, 97`); (2) nothing returns focus to the input after a rejected save — `save()` neither focuses nor prevents the focus move that the outside-click path has already caused (`:396-411, 571-578`).
**Fix:** add `### Keyboard` and `### Accessibility` sections to both guides listing the key bindings above and (after IE-A11Y-02) the announced role/name. Correct the Validation section: either give `validationTooltip` a localized default so the documented message really appears out of the box, or state that it is required for the tooltip and that `kbq-error` inside the form field is the alternative; and either implement the promised focus retention (refocus the first invalid `KbqFormField` at the end of the invalid branch of `save()`) or delete the claim. Keep EN and RU in lockstep — today the two already diverge in the Validation section's paragraph ordering. A `yarn run e2e:docs` pass covers the corrected snippets.

### P2 — Should fix

**IE-A11Y-04 · Leaving edit mode can drop focus to `<body>`; the component never returns focus itself** — `inline-edit.ts:325-327, 396-411, 528-539`; `inline-edit.html:13-19, 47-52`; `@angular/cdk/fesm2022/a11y-module.mjs:571-578, 600-603`.
No code path in `inline-edit.ts` moves focus when edit mode closes. `save()` and `cancel()` both just call `toggleMode()`, the overlay's `[cdkConnectedOverlayOpen]` goes false, the embedded view is destroyed, and whatever was focused inside it disappears. The only restore mechanism is CDK's, via `cdkTrapFocusAutoCapture` on the panel (`inline-edit.html:49`): `_captureFocus()` records `document.activeElement` at attach time and `ngOnDestroy()` calls `.focus()` on that stored node. That works for the common case — clicking or Enter-ing the host, which is focusable, so the host is restored. It does **not** work for the interactive-content case: there the host is `tabindex="-1"` and the focused element is the focus anchor, which is rendered under `@if (hasInteractiveContent() && mode() === 'view' && …)` (`inline-edit.html:13`). While editing, that node is destroyed; when mode flips back, Angular creates a *new* node. CDK still holds the old, detached one, and `.focus()` on a detached element is a no-op — focus falls to `<body>` and the keyboard user loses their place in the page. The same happens after Tab-chaining if the next inline edit rejects the save. Nothing in the 47-case spec asserts where focus is at any point.
**Fix:** own the restore rather than delegating it. Record the entry element in `onClick()`/the anchor's Enter handler, and in an `effect()` on `mode` returning to `'view'` refocus it via `FocusMonitor.focusVia(el, origin)` so the focus ring is restored correctly (see `project_kbq_focus_ring_mechanism`) — resolving the anchor lazily at restore time rather than holding a node reference across the destroy. Add specs: after `cancel()` and after a successful `save()`, `document.activeElement` must be the inline edit's own focusable element, asserted for both the plain and the interactive-content host (`TestComponent` and `TestWithTagContent` already exist).

**IE-BUG-02 · Tab-chaining to the next inline edit silently breaks when the next one has interactive content** — `inline-edit.ts:626-637` (class check at `:633`), `:285-293`; `inline-edit.html:13-19`.
`saveAndFocusNextInlineEdit()` saves, waits a macrotask, then reads `document.activeElement` and fires a synthetic `new KeyboardEvent('keydown', { key: 'Enter' })` at it **only if** it carries the class `kbq-inline-edit`. But the component's own design guarantees a case where it does not: when the next inline edit has interactive view content, `tabIndex()` returns `-1` for its host (`:290`) and the element that receives focus is `.kbq-inline-edit__focus-anchor` (`inline-edit.html:15`). The chain therefore stops dead at the first tag-list or link-bearing field — silently, with no error, and with the user's Tab having already been consumed. Two secondary problems ride along: the technique itself (driving a sibling component by dispatching a fabricated, untrusted `KeyboardEvent` at a DOM node found through `activeElement`) is the same anti-pattern the repo has already banned for scroll events (DS-5407), and it depends on Angular's `keydown.enter` host binding continuing to match a `KeyboardEvent` built with only `key` and no `keyCode`.
**Fix:** resolve the neighbour structurally instead of by class name — `const host = (this.document.activeElement as HTMLElement | null)?.closest('.kbq-inline-edit')` covers both the host and the anchor case — and replace the synthetic dispatch with a real call into the neighbouring instance's public `toggleMode()`, obtained through a small `KbqInlineEditRegistry` (or `ɵɵgetComponent`-free DI lookup) rather than through the DOM. Cover with a two-field fixture where the second field has tag content: Tab out of the first must open the second.

**IE-BUG-03 · Every keystroke in edit mode marks all controls touched, flipping the field into its error look mid-typing** — `inline-edit.ts:542-543, 554, 733-735`; `error-state-matcher.ts:59-62`; corroborated by `inline-edit-validation-example.ts:41-64`.
`onOverlayKeydown()` calls `this.markAllAsTouched()` unconditionally, *before* the switch — so every arrow key, every character, every Shift press marks every projected control touched. With the default `ErrorStateMatcher` (`control.invalid && (control.touched || form.submitted)`) that means a `required` field enters its red error state on the very first keystroke, while the user is still typing the value that will make it valid. The evidence that this is felt as a defect is inside the library's own documentation: `inline-edit-validation-example.ts` ships a bespoke `ExampleResetTouchedOnFirstInput` directive whose entire job is to call `markAsUntouched()` on the first `input` event after focus (`:41-64`), plus a `CustomErrorStateMatcher` that additionally requires `form?.submitted` (`:34-39`). A documented example needing two hand-written workarounds to make the component behave reasonably is a bug report. The same method is then called a second time inside the `Enter` branch (`:554`), where it is pure duplication.
**Fix:** delete both calls from `onOverlayKeydown()` and make `markAllAsTouched()` the first statement of `save()` instead (this is the same move IE-BUG-01 requires, so land them together) — touching controls is a save-time concern, not a keystroke-time one. Then delete `ExampleResetTouchedOnFirstInput` and `CustomErrorStateMatcher` from the validation example and confirm the demo still behaves. Add a spec: type one character into a pristine `required` control and assert the form field has not entered its error state.

**IE-LIFE-01 · The `scrollend` fallback branch drops its own teardown handle, leaking a `window` listener and retaining the component** — `inline-edit.ts:448-519`, especially `:451, 495-502, 510-516`, and the only external cancel at `:359-362`.
`showValidationTooltip()` registers a capturing `scrollend` listener on `window`, arms an 800 ms fallback timer, and publishes a `{ cancel }` handle so the overlay's `detachments()` subscription can tear everything down. The fallback path breaks that contract: `onTimeout()` sets `this.validationTooltipScrollHandle = null` while deliberately keeping the listener alive (`:498-501`), and the comment claims it is "Removed by `cancel()` or the next `onScrollEnd` call" — but `cancel()` is only reachable *through* the handle that was just discarded, so `this.validationTooltipScrollHandle?.cancel()` at `:362` becomes a no-op. From that moment the listener is unreachable: it survives overlay detach and component destroy, and its closure keeps the `KbqInlineEdit` instance alive. Nulling the handle also releases the re-entrancy guard at `:451`, so a second rejected save registers a *second* permanent listener — the count grows with every failed save. The path is not exotic: the JSDoc itself names "cases where nothing ends up scrolling" (`:442-443`), which happens whenever the origin is clipped by a non-scrollable ancestor, and older Safari/Firefox never fire `scrollend` at all. The spec exercises exactly this branch (`inline-edit.spec.ts:956-969`) and asserts only that `show()` is not called twice; it never checks that the listener went away.
**Fix:** keep the handle installed after the fallback fires — `onTimeout()` should set `shown = true` and nothing else — and make `cancel()` the single teardown, called from `detachments()` as today *and* from a `DestroyRef.onDestroy(() => this.validationTooltipScrollHandle?.cancel())`. Extend the existing spec to assert `window.removeEventListener` was called with `('scrollend', fn, { capture: true })` after detach, and add a case where two rejected saves in a row register exactly one listener. The TODO at `:445-446` (extract "scroll into view, then act once settled" into `packages/components/core`) is the right long-term home for this and should carry the fixed lifecycle with it.

**IE-PERF-01 · A forced layout read runs from a template binding on every change-detection pass, for every instance** — `inline-edit.html:36`; `inline-edit.ts:261, 311-313`.
`[cdkConnectedOverlayOffsetY]="-overlayOrigin.offsetHeight"` reads `offsetHeight` directly in a binding expression. Angular re-evaluates binding expressions on every change-detection pass of the view, in view mode as well as edit mode, so every `<kbq-inline-edit>` on the page forces a style/layout flush on every tick. The component is explicitly designed for lists — `inline-edit-vertical-list`, `inline-edit-horizontal-list` and `inline-edit-controls` are the first three examples in the guide — so the cost is N reads per tick, and the read sits on the layout-thrash side of any surrounding write. `overlayOrigin` compounds it: it is a plain mutable field (`:261`) reassigned from an `effect()` (`:311-313`) rather than a `computed()`, so the value the template reads and the value the effect writes are ordered only by Angular's scheduling, and nothing marks the binding dirty when it changes.
**Fix:** turn `overlayOrigin` into a `computed(() => this.label() ? this.viewContainer().nativeElement : this.elementRef.nativeElement)` and delete the effect, then hold the offset in its own signal updated in `onAttach()` and on the `SharedResizeObserver` tick that `setOverlayWidth()` already subscribes to (`:711-717`) — the same observation that already drives `overlayWidth` and `overlayRef.updatePosition()`. Bind `[cdkConnectedOverlayOffsetY]` to that signal. The existing resize spec (`inline-edit.spec.ts:389-408`) already provides a stubbed `SharedResizeObserver` and can be extended to assert the offset updates.

**IE-TEST-01 · No focus-management assertions, no axe, and no browser coverage of the mode transition** — `inline-edit.spec.ts` (47 cases, 7 `describe` blocks); `e2e.playwright-spec.ts:1-123`; `playwright.config.ts:101`.
The Jest suite has real depth where it exists — validation tooltips, scroll-settle, select-style editing, multi-form-field save/cancel — but three things it never touches are exactly the three the component is *about*. (1) **Focus**: not one case asserts `document.activeElement` after entering or leaving edit mode, which is why IE-A11Y-04 is invisible. (2) **Accessibility**: `jest-axe` is established in this repo (`accordion.spec.ts:1518`, `app-switcher.spec.ts:1780`) and is not imported here — an `axe()` assertion in edit mode would have caught IE-A11Y-01 and IE-A11Y-03 the day they were written. (3) **The browser**: all seven Playwright checks are static screenshots of hover/open/invalid states; none presses Escape, Enter or Tab, so the entire keyboard contract is verified only against jsdom. The scroll-settle logic added by the most recent fix (DS-5420) is doubly unverifiable in the browser: `playwright.config.ts:101` sets `reducedMotion: 'reduce'` for every context, so the `behavior: 'smooth'` scroll at `inline-edit.ts:518` degrades to an instant jump and neither the `scrollend` branch nor the 800 ms fallback is ever exercised outside the jsdom test that mocks `getBoundingClientRect` wholesale (`inline-edit.spec.ts:902-931`).
**Fix:** add to the Jest suite — an `axe(overlayContainerElement)` assertion in edit mode; focus assertions on enter/exit for both `TestComponent` and `TestWithTagContent`; the `commit()`-on-pristine case from IE-BUG-01; the touched-on-first-keystroke case from IE-BUG-03; and the listener-teardown case from IE-LIFE-01. Add to Playwright a keyboard scenario over `E2eInlineEditStates` (Tab in → Enter → type → Escape reverts → Enter → Ctrl+Enter in the textarea fixture → Tab chains to the next field), asserted on DOM state rather than pixels so it needs no baseline. If the scroll-settle path is to be covered in a browser, add a dedicated project or `test.use({ reducedMotion: 'no-preference' })` for that spec, and regenerate any screenshot baselines only through `yarn run e2e:docker:update-snapshots`.

### P3 — Nice to have / hygiene

**IE-ARCH-01 · An unreachable branch, a `WritableSignal` that is never written, and a self-toggling focus flag** — `inline-edit.ts:276, 86-92, 605-624`; `inline-edit.html:46, 92`.
Three small structural defects. (1) `setOverlayKeydownListener()` branches on `regionItems.length === 1` (`:613`) to handle "single item: Tab moves to next edit" — but both sentinels are unconditional in the template (`inline-edit.html:46, 92`) and `viewChildren` only sees the component's own view, so the length is always exactly 0 (detached) or 2. The single-item branch is dead code, and the comment above it (`:601-604`) documents behaviour that cannot occur. (2) `scrollStrategy` is declared `signal<ScrollStrategy>(this.overlay.scrollStrategies.reposition())` (`:276`) and never `.set()` anywhere; the signal implies a mutability that does not exist, and the strategy object is built eagerly in every instance's field initializer whether or not that instance is ever edited — N objects for a list of N fields. (3) `KbqFocusRegionItem.onTabOut()` ends with `this.isFocused = !this.isFocused` (`:91`) rather than `= false`; it is correct only because focus always leaves after the emit, and nothing enforces that — called once while `isFocused` is false it arms the flag, so the next Tab emits `tabOut` from a sentinel that never had focus.
**Fix:** collapse `setOverlayKeydownListener()` to the two-sentinel case and drop the dead branch and its comment (or delete the whole mechanism as part of IE-A11Y-01, which is the better order); make `scrollStrategy` a plain `protected readonly` field, or better, build it lazily in `onAttach()`; set `isFocused = false` explicitly and clear it from a `(focusout)` handler.

**IE-API-01 · The three outputs are `protected`, an internal directive is exported, and two `any`s remain** — `inline-edit.ts:71-93, 199, 214, 231-235, 278`; `tools/public_api_guard/components/inline-edit.api.md:24-35, 43, 63-64, 76, 86`; `module.ts:4-8`.
`saved`, `canceled` and `modeChange` are declared `protected` (`:231-235`) and are reported as such (`inline-edit.api.md:43, 64, 76`). Template binding still works — Angular's type-check block reaches outputs through element access, which TypeScript permits on protected members — but a consumer holding a `viewChild(KbqInlineEdit)` cannot write `ref.saved.subscribe(...)`: it does not compile. That is inconsistent with the rest of the surface, which is deliberately built for programmatic use (`commit()`, `toggleMode()`, `modeAsReadonly` are all public). Alongside that: `KbqFocusRegionItem` is an internal helper marked `/** @docs-private */` (`:71`) that is nevertheless exported from the package entry point and appears in the API report (`:24-35`) — and is *not* in `KbqInlineEditModule`'s declaration list (`module.ts:4-8`), so NgModule consumers cannot even use the thing they can import (`@docs-private` does not strip a member from the report; see `project_api_guard_internal_not_stripped`). Finally `validationTooltip` is `string | TemplateRef<any>` (`:199`) and `setValueHandler` is `(value: any) => void` (`:214`) where `unknown` would do, and `modeAsReadonly` (`:278`) names its implementation rather than its meaning — `mode` would read better once the writable signal behind it is renamed.
**Fix:** make the three outputs `public` (additive, no migration needed), stop exporting `KbqFocusRegionItem` from `public-api`/`index.ts` — or delete it outright with IE-A11Y-01 — and replace both `any`s with `unknown`. All of these change `inline-edit.api.md`, so run `yarn run build:components` then `yarn run approve-api` in one cycle (build first: the guard reads `dist/*.d.ts`). Removing an export is technically breaking; since the repo has no consumer of `KbqFocusRegionItem`, schedule it with the next major and skip the schematic.

**IE-BUG-04 · Interactive-content detection runs once and never again; `closest()` is unbounded** — `inline-edit.ts:315-321, 580-590, 592-598`.
`hasInteractiveContent` is computed by an `effect()` that schedules a single `setTimeout` per `interactiveSelectors()` change (`:315-321`) and queries `.kbq-inline-edit__view-content` once (`:587`). There is no `MutationObserver` and no re-run tied to the projected content, so any view content that arrives after that first macrotask — tags fetched from a server, a `@if` that flips when the value loads, the extremely common `@if (value) { … } @else { placeholder }` shape used by every example in the package — is never seen. The component then keeps `tabIndex()` at `0` and never renders the focus anchor, so the host and the now-interactive children are both tab stops and the `kbq-inline-edit_anchor-focused` highlight never appears. Separately, `isInteractiveElement()` calls `target.closest(selectors.join(','))` (`:597`) with no boundary: the walk continues past the component to the document root, so an inline edit placed inside an `<a>` (a clickable table row, for instance) treats every click as interactive and can never be opened by pointer. Note also that the default list `['a', 'kbq-tag']` (`:228`) omits `button`, `input` and `[role="button"]`, which is why the spec host has to extend it (`inline-edit.spec.ts:437`), and the input is documented nowhere outside its JSDoc.
**Fix:** replace the one-shot timeout with a `ContentObserver` (or CDK `MutationObserverFactory`) subscription on the view-content element, debounced and torn down with `takeUntilDestroyed()`, re-running `detectInteractiveContent()` on every content change; scope the `closest()` walk with `this.elementRef.nativeElement.contains(match)`; and document `interactiveSelectors`, its default and its extend-don't-replace semantics in the guide alongside the keyboard section from IE-DOC-01.

**IE-STYLE-01 · One dead token and a private helper occupying the unprefixed `.kbq-mask` namespace** — `inline-edit-tokens.scss:1-8` (`:6`), `inline-edit.scss:5-40, 42-82, 200-205`.
`--kbq-inline-edit-panel-shadow: var(--kbq-shadow-popup)` is declared (`inline-edit-tokens.scss:6`) and read nowhere in the repository — the panel and the action buttons hardcode `box-shadow: var(--kbq-shadow-popup)` instead (`inline-edit.scss:202`). A token whose whole purpose is to be the override point, that the component then bypasses, is worse than no token: a consumer who sets it sees nothing change. Separately, the local `_mask($config)` mixin (`inline-edit.scss:5-40`) emits the class names `.kbq-mask`, `.kbq-mask__fade` and `.kbq-mask__container`. Those names appear nowhere else in the repository, so a private helper has claimed a generic, library-wide-looking namespace; under `ViewEncapsulation.None` the only thing keeping them from colliding with a future shared mask utility is that every rule happens to be nested under `.kbq-inline-edit`. The rest of the style surface is clean — no hardcoded colours, every value a token, and the theme mixin properly parameterised.
**Fix:** point `inline-edit.scss:202` at `var(--kbq-inline-edit-panel-shadow)` so the declared token is the real override point (or delete the token). Rename the mask classes to `kbq-inline-edit__mask*` and drop the parallel unprefixed names, or promote the mixin to `packages/components/core/styles` if a shared fade-mask is genuinely wanted. Neither change is visual, so the existing screenshots stay valid.

**IE-TEST-02 · A dead test host, a `@Directive` used as a base component, and an input default no test ever sees** — `inline-edit.spec.ts:1004-1014, 1009, 1329-1331`.
Three spec-hygiene issues. (1) `TestWithFullTabOrder` (`:1329`) is declared, exported and never instantiated — `git log -S` shows it arrived with `87afa15e` (`fix(inline-edit): handle tab order according to UX guidelines`, DS-4810) and its tests either never landed or were removed; because it is exported, no lint rule flags it, and it will keep looking like coverage that does not exist. (2) `BaseTestComponent` is a `@Directive({ selector: 'name' })` (`:1004-1007`) used purely as a field bag, and it shares the selector `name` with every `@Component` in the file. (3) All six hosts that extend it bind `[showTooltipOnError]="showTooltipOnError()"` from `signal(undefined)` (`:1009`) — and `booleanAttribute(undefined)` is `false`, because Angular's implementation is `value != null && value !== 'false'`. Every one of those hosts therefore runs with `showTooltipOnError` **false**, silently overriding the input's documented `true` default, and no test in the suite ever exercises the value the component actually ships with. Test hosts are otherwise correctly named without the `Kbq` prefix, per repo convention.
**Fix:** delete `TestWithFullTabOrder` or give it the tab-order cases it was written for (it is the only fixture that covers an interactive element inside `<kbq-label>`, which is a real gap — see IE-BUG-04). Replace the `@Directive` base with a plain (non-decorated) class or inline the fields. Stop binding the optional inputs from `undefined` signals: drop the bindings from the hosts that do not need them so the shipped defaults are what the suite runs against, and add one explicit case asserting the tooltip does appear with `showTooltipOnError` left at its default.

## 4. Recommended Remediation Phases

**Phase 1 — Clear the accessibility blockers.**
IDs: IE-A11Y-01, IE-A11Y-02, IE-A11Y-03. Remove the `aria-hidden`/`tabindex` sentinels and move the Tab-boundary detection onto the panel; give the view mode a role, a localized name and an expanded state on `.kbq-inline-edit__view-content` (not the host, to avoid `nested-interactive`); name the menu button or stop stamping its role. Ship with a `jest-axe` assertion in edit mode plus per-branch ARIA cases — that assertion is the acceptance criterion for all three, and it is what stops the family of defects recurring. Adding an `edit`/`menu` key to `KbqA11yLocaleConfiguration` touches `core`, so land that first.

**Phase 2 — Make save/cancel mean what they say.**
IDs: IE-BUG-01, IE-BUG-03, IE-DOC-01. Move `markAllAsTouched()` out of the keydown path and into `save()`, gate the save on the control's real validity rather than on `errorState`, then delete the two workaround classes from the validation example. With the behaviour correct, rewrite the guides' Validation section and add the `### Keyboard` / `### Accessibility` sections. Depends on nothing above; sequence it second because it is the largest user-visible correctness win.

**Phase 3 — Focus, chaining and lifecycle.**
IDs: IE-A11Y-04, IE-BUG-02, IE-LIFE-01, IE-PERF-01. Own the focus restore instead of relying on `cdkTrapFocusAutoCapture` across a node that gets recreated; resolve the Tab-chain neighbour through `closest()` + a registry rather than a synthetic `KeyboardEvent`; keep the `scrollend` teardown handle alive past the fallback timer and add a `DestroyRef` hook; turn `overlayOrigin` into a `computed()` and move the `offsetHeight` read out of the template. Phase 1 changes the tab-stop topology, so this must follow it.

**Phase 4 — API, hygiene and coverage.**
IDs: IE-ARCH-01, IE-API-01, IE-BUG-04, IE-STYLE-01, IE-TEST-02, IE-TEST-01. Make the outputs public, drop the exported internal directive and the two `any`s, remove the dead branch and the unwritten signal, wire the dead token, make interactive-content detection observational, clean the spec hosts, and close the coverage gaps (axe, focus, keyboard e2e). One `yarn run build:components && yarn run approve-api` cycle covers the API changes. IE-TEST-01's individual cases are written as part of Phases 1–3; this phase adds the Playwright keyboard scenario and reconciles the whole suite.

## Appendix A — Review Methodology

Findings were gathered by reading the complete package end to end — `inline-edit.ts` (736 lines), `inline-edit.html` (95), `inline-edit.scss` (206), `inline-edit-tokens.scss`, `module.ts`, `index.ts`, `inline-edit.spec.ts` (1,521 lines / 47 cases / 7 `describe` blocks), its Jest snapshot, `e2e.ts` (326) and `e2e.playwright-spec.ts` (123), both user guides and both examples guides — then cross-checking every candidate against five independent sources: the collaborating library code (`form-field.ts`, `error-state.ts`, `error-state-matcher.ts`, `input.ts`, `dropdown-trigger.directive.ts`, `icon-button.component.ts`, `core/locales/types.ts`), the CDK implementations the component delegates to (`CdkTrapFocus` in `@angular/cdk/fesm2022/a11y-module.mjs`), the axe-core rule set that `jest-axe` actually loads (4.12.1, under `node_modules/jest-axe/node_modules/axe-core` — the root `node_modules/axe-core` is a different, older 3.5.6 copy), the API guard report, and every in-repo call site found by grep. Two accessibility findings were promoted from judgement to confirmed automated failure by reading the axe rule JSON and its evaluate functions rather than relying on the rule names. Because the component has **no consumers inside `packages/`** — the only call sites are its own docs examples, dev app and e2e fixtures — the usual "consumer workaround" evidence was replaced by workarounds inside the library's own examples, which is where IE-BUG-03's corroboration comes from.

Refuted during verification:
- **"The package is unthemed — there is no `_inline-edit-theme.scss`"** — refuted. The theme mixin is defined locally as `_inline-edit-theme` (`inline-edit.scss:42-82`) and included at `:99`; every colour resolves through a `--kbq-inline-edit-*` token declared in `inline-edit-tokens.scss:1-8` or a global semantic token. The file split is a convention difference, not a functional gap; the only real style defect is the dead token in IE-STYLE-01.
- **"`module.ts` violates AGENTS.md, which specifies `<component-name>.module.ts`"** — refuted as a defect. 12 of the 64 component packages use a bare `module.ts` (`actions-panel`, `clamped-text`, `content-panel`, `dynamic-translation`, `flag`, `inline-edit`, `overflow-items`, `resizer`, `skeleton`, `time-range`, `top-bar`, `username`). It is an established minority convention, not an inline-edit problem. The missing `public-api.ts` (10 of 64 packages lack one) is the same story and was dropped for the same reason.
- **"`cancel()` cannot restore the value through `[(ngModel)]`"** — refuted. `setValue()` reaches `AbstractControl.setValue` (`inline-edit.ts:678`), which runs the registered change pipeline and calls `NgModel.viewToModelUpdate`, emitting `ngModelChange` back to the host binding. `inline-edit.spec.ts:248-278` asserts the round trip end to end.
- **"The `tabOut` subscriptions in `setOverlayKeydownListener()` accumulate across attach/detach cycles"** — refuted. The sentinels live inside the overlay's embedded view, which the `CdkConnectedOverlay` destroys on detach; each `OutputEmitterRef` is torn down with its own `DestroyRef`, so every attach subscribes to fresh emitters and the old ones are already dead. No accumulation.
- **"The reposition scroll strategy leaks into tooltips projected into edit mode"** — refuted. It is passed per instance through `[kbqTooltipScrollStrategy]` (`inline-edit.html:61`) rather than provided via DI, and the class JSDoc says so explicitly (`inline-edit.ts:176-184`). `inline-edit.spec.ts:983-1000` proves a projected `kbqTooltip` keeps the library's `CloseScrollStrategy`.
- **"Global `window`/`document` usage breaks SSR"** — refuted. `KBQ_WINDOW` (`:170`) and `DOCUMENT` (`:169`) are both injected; every `addEventListener`/`innerHeight`/`activeElement` access goes through them. `inline-edit-overview-example` is part of the SSR dev app (`packages/components-dev/ssr/module.ts:193`), so the path is exercised.
- **"`examples.inline-edit.*.md` are dead stub files"** — refuted. `structure.ts:611` sets `hasExamples: true`, and both files carry four real `<!-- example(…) -->` embeds, not the "🚧 Documentation in progress 🚧" placeholder. Every example id referenced across all four markdown files resolves to a directory under `packages/docs-examples/components/inline-edit/`; the one example that exists without a markdown reference, `inline-edit-overview`, is deliberately consumed by the dev app and the SSR app.
- **"Escape leaks past the component and closes an enclosing modal"** — refuted as unanchorable. `onOverlayKeydown` does not call `preventDefault()`/`stopPropagation()` for `Escape` (`inline-edit.ts:547-550`), but the event reaches the handler through CDK's `OverlayKeyboardDispatcher`, which routes to the top-most overlay only, and the overlay container is a sibling of the application root — so no in-repo path was found where a second component also acts on it. Worth a defensive `preventDefault()`, not worth a finding.

Corrected on verification:
- **IE-A11Y-03** was drafted at P0 alongside IE-A11Y-01, since both are automated axe failures under the same AGENTS.md mandate. It was downgraded to P1 on the workaround test: the unnamed element belongs to the consumer, who can add `aria-label` today, whereas the IE-A11Y-01 sentinels are inside the component's own template and cannot be reached from outside.
- **IE-BUG-01** was drafted as "the Save button commits invalid values". Tracing the event order showed the click is preceded by a `blur` that marks the control touched and a change-detection pass that refreshes `errorState`, so the button path is usually safe in a real browser. The finding was narrowed to the programmatic paths — `commit()` and any direct `save()` — which never mark controls touched at all, and which the component's own documented select-commit pattern uses.
- **IE-ARCH-01** originally led with "no `public-api.ts` and a misnamed `module.ts`". Counting the other packages showed both are established minority conventions (see Refuted), so the finding was re-centred on the three defects that are genuinely local: the unreachable `regionItems.length === 1` branch, the never-written `scrollStrategy` signal, and the self-toggling `isFocused` flag.
