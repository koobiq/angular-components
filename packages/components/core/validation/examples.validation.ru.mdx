## Методы валидации

Валидаторы Angular определяют, **что** является недопустимым значением, но не управляют тем, **когда** сообщать об ошибке пользователю. Без дополнительного механизма ошибки появлялись бы сразу при загрузке страницы, ещё до того, как пользователь начал ввод данных.

В Koobiq эта задача решается через `ErrorStateMatcher`.

### ErrorStateMatcher

`ErrorStateMatcher` — это механизм, определяющий момент отображения ошибки. Он анализирует состояние контрола (`AbstractControl`) и формы (`FormGroupDirective | NgForm`), возвращая `true`, если ошибку нужно показать.

Валидаторы и `FormControl` при этом остаются неизменными — `ErrorStateMatcher` не добавляет и не удаляет ошибки. Он только решает, когда `kbq-form-field` должен показать дочерние элементы `<kbq-error>` и применить CSS-класс `kbq-invalid`.

Иными словами: **ошибки принадлежат `FormControl`**. Вызов `control.hasError('required')` вернет `true` с момента инициализации контрола, если поле обязательно для заполнения. `ErrorStateMatcher` лишь определяет, когда стоит сообщить об этом пользователю.

**Подключение:**

Применить `ErrorStateMatcher` ко всем элементам управления внутри компонента через `providers`:

```ts
@Component({
    providers: [
        // Устанавливаем кастомный ErrorStateMatcher для всего компонента
        kbqErrorStateMatcherProvider(ShowOnFormSubmitErrorStateMatcher)
    ]
})
```

Переопределить для конкретного элемента управления через input `[errorStateMatcher]` (поддерживается в `kbq-tag-list`, `kbq-file-upload` и других):

```html
<kbq-file-upload [errorStateMatcher]="myMatcher" ... />
```

**Список тегов**

**Загрузка файлов**

Компоненты загрузки файлов поддерживают `ErrorStateMatcher`, но имеют собственный layout вне `kbq-form-field`, поэтому вывод ошибок отличается от полей ввода. Все примеры валидации — на странице [Загрузка файлов](/ru/components/file-upload).

## Кастомный ErrorStateMatcher

Используйте `ShowRequiredOnSubmitErrorStateMatcher`, если нужно разделённое поведение:

- Если поле не заполнено, не показывать ошибку `required`, пока не отправится форма.
- Если поле заполнено, проверять его при потере фокуса.

## Cross-field валидация

Некоторые правила сравнивают сразу несколько полей: «подтвердите пароль», «новый пароль должен отличаться от
старого», «дата окончания не может быть раньше даты начала». Один `FormControl` не видит значение соседнего
поля. Поэтому для такого правила естественное место — валидатор на `FormGroup`, а не на одном из полей.

### Почему ошибка на FormGroup ничего не подсвечивает

`<kbq-error>` и красная рамка зависят от одного: `errorState` контрола.

`errorState` — это просто возвращаемое значение `ErrorStateMatcher.isErrorState(control, form)`. А `control`
здесь — всегда собственный `FormControl` поля: `ErrorStateMatcher` никогда не видит группу.

Поэтому валидатор может сделать группу невалидной, а проверка все равно ответит «нет». Ни одно поле не
станет красным. `<kbq-error>` не появится.

Это не баг. Это разделение ответственности: валидаторы решают, **что** невалидно, а `ErrorStateMatcher` решает,
**когда и где** это показать.

### Рекомендуемый паттерн

Валидатор остается на группе — его логика и форма ошибки полностью ваши. `ShowOnCrossFieldErrorStateMatcher`
добавляет недостающую половину: он показывает ошибку группы на тех контролах, которых она касается.

Ошибка показывается лишь тогда, когда затронуты (`touched`) **все** ее контролы, или когда отправлена форма
— иначе пара полей покраснела бы, пока пользователь еще набирает второе значение.

От вас нужно одно — функция, которая по каждой ошибке возвращает имена нужных ей контролов.

<Example id="validation-cross-field-password" />

Одного экземпляра `ErrorStateMatcher` хватает на любое число правил на группе — в примере выше на одной группе
два правила, и оба показывает один и тот же `ErrorStateMatcher`.

### Сравнение значений, которые не примитивы

Компаратор по умолчанию (`===`) не работает для дат и других объектных значений: нужен `compareDate()` /
`compareDateTime()` / `sameDate()` из `DateAdapter` либо свой компаратор.

### Когда так делать не нужно

Один случай не подходит под этот паттерн: «хотя бы одно из этих полей должно быть заполнено». Для такого
правила поля не помечают невалидными, а показывают общий алерт над формой. См.
[руководство по валидации](/ru/other/validation) и его пример «Одно обязательное поле из нескольких».

### Асинхронные правила

Правило, которое может проверить только сервер, вешается на группу как `AsyncValidatorFn`. Ошибка при этом
ложится на группу, а не на дочерние контролы. Поэтому `OnPush`-вью не перепроверяет себя сама — нужен сигнал
из `statusChanges` группы.
