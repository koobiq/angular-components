## Методы валидации

Валидаторы Angular определяют, **что** является недопустимым значением, но не управляют тем, **когда** сообщать об ошибке пользователю. Без дополнительного механизма ошибки появлялись бы сразу при загрузке страницы, ещё до того, как пользователь начал ввод данных.

В Koobiq эта задача решается через `ErrorStateMatcher`.

### ErrorStateMatcher

`ErrorStateMatcher` — это механизм, определяющий момент отображения ошибки. Он анализирует состояние контрола (`AbstractControl`) и формы (`FormGroupDirective | NgForm`), возвращая `true`, если ошибку нужно показать.

Валидаторы и `FormControl` при этом остаются неизменными — `ErrorStateMatcher` не добавляет и не удаляет ошибки. Он только решает, когда `kbq-form-field` должен показать дочерние элементы `<kbq-error>` и применить CSS-класс `kbq-invalid`.

Иными словами: **ошибки принадлежат `FormControl`**. Вызов `control.hasError('required')` вернет `true` с момента инициализации контрола, если поле обязательно для заполнения. `ErrorStateMatcher` лишь определяет, когда стоит сообщить об этом пользователю.

**Подключение:**

Применить матчер ко всем элементам управления внутри компонента через `providers`:

```ts
@Component({
    providers: [
        // Устанавливаем кастомный матчер для всего компонента
        kbqErrorStateMatcherProvider(ShowOnFormSubmitErrorStateMatcher)
    ]
})
```

Переопределить для конкретного элемента управления через input `[errorStateMatcher]` (поддерживается в `kbq-tag-list`, `kbq-file-upload` и других):

```html
<kbq-file-upload [errorStateMatcher]="myMatcher" ... />
```

## Кастомный ErrorStateMatcher

Используйте `ShowRequiredOnSubmitErrorStateMatcher`, если нужно разделённое поведение:

- Если поле не заполнено, не показывать ошибку `required`, пока не отправится форма.
- Если поле заполнено, проверять его при потере фокуса.

## Cross-field валидация

Правило, связывающее несколько полей, — «подтвердите пароль», «новый пароль должен отличаться от старого»,
«дата окончания не раньше даты начала» — сравнивает значения нескольких контролов, поэтому естественное место
для него — валидатор на `FormGroup`.

### Почему ошибка на FormGroup ничего не подсвечивает

`<kbq-error>` и красная рамка управляются полем `errorState` **контрола**, а это возвращаемое значение
`ErrorStateMatcher.isErrorState(control, form)`. В `control` приходит собственный `FormControl` поля, поэтому
ошибка, лежащая на группе, для него не существует: группа невалидна, сообщение можно вывести вручную, но ни
одно поле не помечено.

Это правило отображения, а не ошибка — и чинится оно там же, где возникает. Валидаторы решают, **что**
невалидно; матчер решает, **когда и где** это показать.

### Рекомендуемый паттерн

Валидатор остаётся на группе, а матчер учится читать её ошибки. Для этого валидатор должен сообщить, к каким
контролам относится ошибка:

```ts
return { matchAll: { controls: ['newPassword', 'confirmPassword'] } };
```

В собственном `errors` у группы лежат только ошибки валидаторов самой группы и никогда — ошибки её потомков,
поэтому `control.parent?.errors` — это ровно множество cross-field ошибок. Матчер определяет имя контрола
среди соседей и проверяет, названо ли оно в ошибке.

Одно правило здесь важнее прочих: показывать ошибку только когда затронуты (`touched`) **все** перечисленные в
ней контролы либо отправлена форма. Пока пользователь ещё набирает второе значение, пара всегда «не совпадает»,
и подсветка в этот момент только мешает. С этим правилом группа загорается при потере фокуса, и все связанные
правилом поля загораются одновременно.

Контракт — это массив имён контролов, поэтому один и тот же матчер обслуживает любое число полей и любое число
правил на одной группе. Меняется только валидатор:

```ts
// Значения перечисленных контролов должны идти по возрастанию.
const exampleOrder =
    (controls: string[]): ValidatorFn =>
    (group: AbstractControl): ValidationErrors | null => {
        const values = controls.map((name) => group.get(name)?.value);
        const ordered = values.every((value, index) => index === 0 || values[index - 1] <= value);

        return ordered ? null : { order: { controls } };
    };
```

### Сравнение значений, которые не примитивы

Строгое равенство годится для строк и чисел и не годится ни для чего, у чего есть идентичность. Два объекта
`Date`, `DateTime` из Luxon или Moment, обозначающие один и тот же момент, — это разные ссылки, поэтому `===`
считает их разными, и правило на совпадение будет проваливаться всегда: молча и с правдоподобным сообщением.
Именно для этого правила в примере принимают компаратор:

```ts
exampleMatchAll(['startDate', 'endDate'], (a, b) => adapter.sameDate(a as D, b as D));
```

У `DateAdapter` для этого есть `sameDate()`, а для сравнения по порядку — `compareDate()` и
`compareDateTime()`. То же касается любых объектных значений: массивов из тег-листа, опций селекта.

После того как поле попало в состояние ошибки, оно проверяется заново по мере ввода — ошибка исчезает, как только
значение исправлено. Это [общее правило](/ru/other/validation) для всех полей библиотеки, и cross-field правила
не исключение.

### Контролы без ErrorStateMatcher

`kbq-file-upload` матчер поддерживает: он получает его через тот же DI-токен и подсвечивается из того же
`errorState`. Отличается только вывод сообщения — проекции `<kbq-error>` там нет, видимостью `<kbq-hint>`
управляете вы сами, что для cross-field правила скорее упрощение.

У `kbq-checkbox`, `kbq-radio`, `kbq-toggle` и `kbq-button-toggle` состояния ошибки нет вовсе. Правило с их
участием через матчер показать нельзя — выводите его алертом над формой либо навешивайте класс самостоятельно.

### Когда так делать не нужно

Для правила «хотя бы одно из полей должно быть заполнено» гайд требует **не** помечать поля невалидными, а
показать общий алерт над формой. См. [руководство по валидации](/ru/other/validation) и пример «Одно
обязательное поле из нескольких».

### Альтернатива: директива-валидатор на зависимом поле

Второй вариант — оставить ошибку на самом контроле. Сложность в том, что правило зависит от контрола, которым
поле не владеет, поэтому его правка должна перезапускать валидатор. Штатный механизм для этого —
`registerOnValidatorChange`: переданная Angular функция обратного вызова заново проверяет host-контрол, поэтому связь описана
декларативно и уничтожается вместе с директивой, а не живёт в компоненте подпиской с
`updateValueAndValidity()`.

Ошибка при этом ложится на зависимый контрол, и его подсвечивает обычный `ErrorStateMatcher` без какой-либо
дополнительной проводки — ценой того, что помечено будет только одно поле.

### Когда запускать проверку

Матчер отвечает на вопрос «когда показывать». Если нужно управлять ещё и тем, «когда проверять», есть такие
инструменты:

**`updateOn: 'blur'`** — на контроле или сразу на всей группе:

```ts
new FormGroup({ ... }, { updateOn: 'blur' });
```

Валидатор перестаёт срабатывать на каждый символ, но модель начинает отставать от поля ввода: живая обратная
связь вроде `kbq-reactive-password-hint` замирает до потери фокуса. Обычный компромисс — разные стратегии на
разных контролах.

**`AbstractControl.events`** — единый поток событий `ValueChangeEvent`, `TouchedChangeEvent`,
`PristineChangeEvent`, `StatusChangeEvent`, `FormSubmittedEvent` и `FormResetEvent`. Это единственный
поддерживаемый способ реагировать на смену `touched`, а момент показа cross-field ошибки зависит именно от
неё. В связке с `toSignal` даёт сигнальный вывод текста ошибки:

```ts
readonly events = toSignal(this.form.events);
readonly mismatch = computed(() => (this.events(), this.form.hasError('matchAll')));
```

**`addValidators` / `removeValidators` / `hasValidator`** — для правил, которые включаются и выключаются по
условию, — вместо того чтобы пересобирать группу.

**Асинхронные правила** переводят группу в состояние `pending` на время запроса. Их стоит сочетать с
`updateOn: 'blur'`, иначе запрос уйдёт на каждый символ.

### Подводные камни

**Не проталкивайте ошибку группы в потомков через `setErrors`.** Он заменяет объект ошибок целиком, и
следующий прогон собственных валидаторов контрола её затирает.

**Валидатор, читающий `control.parent.get('sibling')`, получит `null` во время конструирования
`FormGroup`** — соседний контрол ещё не зарегистрирован. Проверка обязательна.

**Состояние ошибки пересчитывается при проверке вью хозяйского компонента.** Пока поля находятся в одном
шаблоне, ввод в одном помечает вью грязной, и остальные пересчитываются сами. Если поля разнесены по разным
`OnPush`-компонентам, изменение одного до других не доходит: при появлении ошибки на группе у соседних
контролов не срабатывают ни `valueChanges`, ни `statusChanges`. В этом случае подпишитесь на `statusChanges`
группы и вызовите `markForCheck()`.

### Границы паттерна

По количеству полей паттерн масштабируется — контракт это массив имён. Границы проходят в других местах, и
их проще обойти на этапе проектирования, чем потом отлаживать:

**Один уровень вложенности.** Матчер читает `control.parent?.errors` и разрешает имена среди непосредственных
соседей. Правило, повешенное на корневую группу, до контролов внутри вложенной `FormGroup` не дотянется, и
путь вида `'passwords.newPassword'` не разрешится. В `FormArray` именами оказываются индексы, а они съезжают
при вставке и удалении строк.

**Условие «все touched» неверно, если поле заполнено заранее.** В правиле «дата начала не позже даты окончания», где окончание
подставлено по умолчанию, пользователь, который правит только начало, окончания не коснётся никогда — и
ошибка дождётся только submit. Правилам над полями, куда пользователь заходить не обязан, нужно другое условие:
«затронуто хотя бы одно» либо «затронуто то, которое редактировали».

**Проверка на пустоту заточена под строки.** `null`, `undefined` и `''` считаются «ещё не заполнено», а `[]`
из тег-листа и `false` из чекбокса — нет, и уходят в сравнение как настоящие значения. (`0` — настоящее
значение намеренно.)

**Payload обязателен.** Ошибку на группе без массива `controls` — например, серверную через
`form.setErrors(...)` — матчер игнорирует. Ничего не ломается, но и не подсвечивается.

**У двух независимых форм нет общего родителя**, поэтому правило, связывающее их, этим механизмом не
покрывается вовсе.
