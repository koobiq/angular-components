### Operating modes

In the clear mode, filters remain on the panel after clicking the button with a cross, and in the delete mode, they disappear. Do not mix the two modes on one screen. If the buttons with the cross icon work differently for adjacent filters, this will confuse the user.

#### Cleaning

Use when the system has few filters or users often use several popular parameters. Filter buttons without selected values ​​are pre-showed on the screen, the filled filter is cleared by the cross, but the button itself does not disappear.

In the cleaning mode, you should not give the opportunity to add new filters from the menu, as this will conflict with the fact that the cross will either reset or delete the filter.

<Example id="filter-bar-cleanable" />

#### Removal

In this mode, the user has the option to hide the component if there are no values ​​selected in the filter. When filled, the button with a cross resets the filter values ​​and hides it.
Filters with the ability to delete are usually hidden in the menu to avoid cluttering the screen. The user will select the desired parameter from the drop-down list, and then the corresponding element will be added to the filter panel.

<Example id="filter-bar-removable" />

### Required filter

A filter can be added to the filter panel regardless of the operating mode, which will always be filled and cannot be cleared. The user will only be able to change its value.

### Filter types

<Example id="filter-bar-pipe-types" />

For the `select` and `multiselect` types, the pipe template accepts an optional `compareWith` — a comparator forwarded to the underlying select that controls how the selected value is matched against the option list. Override it when options are compared by a business key, or when the selected value is a distinct object (e.g. restored from a saved filter) rather than the same reference. When omitted, options are matched by their `id`. A custom comparator is responsible for its own null handling — unlike the default, which never matches a `null`/`undefined` value.

The `input` type is the only one without a popover: it renders a bare input that is typed into directly in the bar, using the pipe's `name` as its placeholder. The value is applied as you type — 200 ms after the last keystroke (`debounceTime`) and only from 3 characters on (`minLength`) — rather than through an Apply button. Text shorter than the threshold, including an emptied field, is applied as `null`, so the bar never keeps filtering by text that is no longer in the input. `Enter` and blur apply the value immediately and ignore the threshold: an explicit action is always applied as typed. Its only clear affordance is the built-in cleaner inside the input, so `removable` has no effect — an `input` pipe can only be removed programmatically. Values are trimmed, and a blank value is applied as `null`. Set its width with the `--kbq-filter-bar-pipe-input-width` CSS variable.

### Custom option content

For `select`, `multiselect`, `tree-select` and `multi-tree-select`, set `valueTemplate` to customize option content. Flat pipes pass the source value as `option`; tree pipes pass the source node as `option` and the current query as `search`. Use them to render icons, multiline text, counters or other Angular content. An option `name` may be a signal — a label the built-in views resolve, but your template receives the union as it is. Resolve it in the component and use that resolver in the template:

```ts
protected readonly resolveName = kbqResolveFilterBarName;
```

```html
<ng-template #optionTemplate let-option="option" let-search="search">
    <span [innerHTML]="resolveName(option.name) | kbqHighlightBackground: search"></span>
</ng-template>
```

Filtering and search use the resolved `name`. Tree templates highlight matches themselves, typically with `kbqHighlightBackground` applied to the resolved text and the `search` context value; the flat pipes' context has no query. Select-all, selected values and the text-only trigger keep their standard behavior. With a custom template, a signal-backed name still shows its resolved name in the built-in trigger and tooltip — the template owns only the option content in the panel. For `select` and `multiselect`, a string name keeps the existing behavior, where the trigger uses the text the template rendered; the `tree-select` and `multi-tree-select` triggers always resolve `node.name`, with or without a custom template. Set `multilineOptions` to wrap long names instead of truncating them; this option works independently of `valueTemplate`. Multiline rows are taller than 32px, so fewer of them fit under `panelMaxHeight`.

<Example id="filter-bar-value-template" />

### Collapsed tree on open

By default the `tree-select` and `multi-tree-select` pipes open the dropdown with every branch expanded. Pass `defaultExpanded: false` in the pipe template to open it collapsed instead: only the ancestors of the selected node(s) are expanded, so the current selection stays visible. Searching still expands the parent branches of the matches temporarily and restores the collapsed state once the query is cleared. The option is ignored by other pipe types.

### Date and time limits

The `date` and `datetime` pipe templates accept optional limits for the custom period. `minDateTime` and `maxDateTime` bound the selectable range — the `datetime` pipe uses the full instant (date and time), the `date` pipe only the day. `minInterval` and `maxInterval` constrain the length of the selected period (`end − start`) as a duration-like object (e.g. `{ days: 3 }`, `{ hours: 1 }`); a period outside these bounds shows an error and disables Apply, with the limit formatted for the current locale. All four are ignored by other pipe types.

### Locked values

The `multiselect` and `multi-tree-select` pipe templates accept an optional `lockedValues` — the list of values whose selection cannot be removed. They are always selected: rendered as disabled options with a checked checkbox, kept by clearing the pipe, and folded into an incoming filter value silently, without a change event. A pipe holding nothing but its locked values reads as empty — it renders unfilled and hides its clear button. Note that "reads as empty" is about the UI only: because a pipe's `value` is meant to be applied as-is, clearing removes just the entries the user was able to select, and both `onClearPipe` and `onChangePipe` still carry a `value` listing the locked ones.

"Select all" ignores them entirely: it neither selects nor deselects a locked option, and the master checkbox reflects only the options the user can actually toggle. Note that under `selectedAllEqualsSelectedNothing` a full selection is still committed as an empty `value` — there the locked values are implied rather than listed.

Entries of `lockedValues` have the same shape as the entries of the owning pipe's `value`: `{ name, id }` objects for `multiselect` (matched with `compareWith`, falling back to `id`), and raw node values for `multi-tree-select`. Locking a tree branch locks its whole subtree. The option is ignored by other pipe types.

Because locked options are rendered as `disabled`, keyboard navigation skips them.

<Example id="filter-bar-locked-options" />

### Dropdown height

By default the dropdown list of the `select`, `multiselect`, `tree-select` and `multi-tree-select` pipes is 256px tall — exactly eight 32px options, so a list of eight fits without a scrollbar. Pass `panelMaxHeight` in the pipe template, in pixels, to change that:

```ts
pipeTemplates: KbqPipeTemplate[] = [
    {
        name: 'Select',
        type: KbqPipeTypes.Select,
        values: [/* ... */],
        panelMaxHeight: 160,

        cleanable: false,
        removable: false,
        disabled: false
    }
];
```

The value caps the scrollable list only, and the list's own padding is added on top of it — so a multiple of the 32px option height fits without a scrollbar and without a clipped row. The pipe's search field is rendered above the list and adds to the panel's total height, while the "select all" row scrolls with the options and is counted by the cap. A value taller than the room left in the viewport is clipped by the overlay rather than scrolled. Omitting the option — or passing `null` — restores the default. The option is ignored by other pipe types.

An option with a `caption`, and any option under `multilineOptions`, is taller than 32px, so fewer of them fit.

### Saving filters

The user can quickly get search results by selecting a saved filter, without re-configuring the parameters. It is also possible to create a new set of filters and use them in the future.

<Example id="filter-bar-saved-filters" />

A saved filter is application data. If a pipe, an option or a date preset has a signal-backed `name`, the filter holds a function, which neither `JSON.stringify` nor `structuredClone` can represent: call `kbqFilterBarToSerializableFilter(filter)` before persisting. It returns a copy whose signal-backed `name` fields — of pipes, select options and date presets — are resolved to their current strings, and leaves the live filter untouched.

Only `name` is a label. Plain objects and arrays are copied; every other value stays by reference — a business value held in a signal, a `compareWith` copied from a template or a date-adapter value keeps its identity, and JSON drops or flattens what it cannot represent exactly as it always did. A payload that `structuredClone` rejects — a function held as a business value, a DOM node — keeps the existing restriction: the helper's copy is not cloneable either, and `structuredClone(filter)` on a live filter with signal names remains unsupported.

When the application hands a restored filter to `<kbq-filters>` and the user selects it, the built-in `select`, `multiselect`, `date` and `datetime` values are rehydrated from the current `pipeTemplates` by stable `id`. The trigger and the panel show the labels of the active locale while the persisted business value is preserved. An option or preset the templates no longer contain keeps its persisted value, and a custom date range passes through unchanged. A tree value needs no rehydration: its selection is the node `value`, and its label comes from the current tree.

The helper resolves pipe names as well, so a persisted copy keeps the pipe names of the save time. Only the built-in values are rehydrated: a pipe `name` is part of your filter definition, so take it from `pipeTemplates` when you translate pipe names at runtime.

The example below stores its saved filters through the helper and keeps the pristine versions it compares against with their labels still as signals.

### State Saving

The filter bar remembers which filter is selected and the edits made to it, and restores the state after a page reload. On by default — use `[useStateSaving]="false"` to turn it off on a specific component.

This is a different thing from the section above. There the user saves a named filter, and the application stores it; here the component keeps the state on the device.

<Example id="filter-bar-state-saving" />

Restoring writes through the `filter` model, so it overrides the value a `[filter]` binding supplied at initialization, and `filterChange` fires before the user has touched anything. Only a later change wins.

Project the pipes from the value the bar reports — bind `[(filter)]`, or assign what `(filterChange)` hands you. Restoring replaces the filter object and every pipe in it, exactly as picking a filter from `<kbq-filters>` already does, so a pipe projected from an array of your own is no longer the one in `filter`: editing it does not reach the persisted state, and its remove button stops working.

Values come back as new objects, which is what `compareWith` is for — see [Filter types](#filter-types). A filter is identified by its `name`, so one that is no longer in `filters` restores nothing. A pipe is rebuilt from the filter or from `pipeTemplates`, so one your application builds itself, outside both, is not restored — put it in `pipeTemplates` if it has to come back.

The automatic state stores built-in values with the labels of the moment. Restoring resolves them to the current option or preset of the same `id`, so a stored state follows the active translation, and no signal is ever written to the storage.

`saveFilterState()` / `restoreFilterState()` keep every Angular signal in the in-memory snapshot by reference — name signals and business signals alike — while copying the arrays and plain objects around them. A restored filter therefore shares those signal references: a name signal stays reactive to a later translation, and a business signal keeps its identity. A signal is kept only where the copy walks the structure — as a pipe value, or inside a plain object or an array; one held in a `Map`, a `Set` or a class instance is not walked, and `structuredClone` throws on its container. The same applies to any other value `structuredClone` rejects: a non-signal function, a DOM node or a symbol.

`clearSavedState()` removes what is stored, and `hasSavedState` says whether anything is. Neither has anything to do with `saveFilterState()` / `restoreFilterState()`, which snapshot the filter in memory within one session.

Keys, storage and expiry work the same for every component that persists — see [Saving component state](/en/components/core/overview#saving-component-state).

### Localization

The filter bar takes its own strings — the filters menu, the reset button, pipe tooltips and the date pipe's custom-period flow — from `KbqLocaleService`. The data you pass in `pipeTemplates` and `filter` is never translated: those labels are yours to produce, and `name` is where the bar reads them.

A name may be a plain string or a `Signal<string>` (`KbqFilterBarName`). A signal is read by the built-in view that renders it, so changing its value relabels the pipe, its options, the period list, the trigger, the tooltip and the screen-reader announcements in place — without replacing the filter, its pipes or `pipeTemplates`, and without touching the selected values, the search query, the open panel or the `changed`/`saved` flags. The example below builds its pipes, options, period presets and tree nodes once with `computed()` labels and switches the locale with `KbqLocaleService.setLocale()`; no translation calls `filter.set`.

A signal-backed name is a label, not an identity: give the pipe, option or preset a stable `id`. The bar matches a pipe to its template, a select value to its option and a date preset to its preset list by that `id`, falling back to the `name` only for a legacy string-named item. A signal-named item without an `id` is a configuration error and throws. `KbqFilter.name` is user data — the name of a saved filter — and is never translated.

Custom option content is not rendered by the bar, so it resolves a signal name itself — see [Custom option content](#custom-option-content).

There are three ways to control the locale. `KBQ_DEFAULT_LOCALE_ID` is the fallback (`ru-RU`) used when nothing else is provided — it is a plain constant, not an injection token, so it cannot be provided. `KBQ_LOCALE_ID` fixes the locale once, when `KbqLocaleService` is constructed; it has to be provided alongside the service itself, because the service reads the token from the injector that created it. `KbqLocaleService.setLocale()` changes the locale at runtime.

Each bar below provides its own `KbqLocaleService`, so they are isolated from each other and from the language selector in the footer of this site.
